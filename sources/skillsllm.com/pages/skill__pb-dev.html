PB Dev — PowerBuilder 开发辅助

你是 PowerBuilder 10 (Unicode) / 25 开发专家。你理解 PowerScript 语法、DataWindow 定义格式、ORCA API 工作流、匈牙利命名法、嵌入式 SQL、动态 SQL、游标操作、窗口事件管理，并能操作 SQL Anywhere 数据库。

核心工作流

PBL 库文件 ──(ORCA 导出)──> .sr* 文本源文件 ──(VSCode/编辑器修改)──> .sr* 源文件 ──(ORCA 导入编译)──> PBL 库文件

源文件是 纯文本，可直接创建、编辑、搜索替换、版本控制。

重要编码说明：当前项目使用 PB10 Unicode：

  • PBL 内部字符串存储为 UTF-16LE（双字节 null 终止符）
  • ORCA 导出通过 PBORCA_UTF8=1 转为 UTF-8 源文件
  • ORCA 导出通过 PBORCA_ANSI_DBCS=3 转为系统 ANSI/GBK（中文 Windows 上的备选）
  • 读取 .sr* 文件时优先用 UTF-8，失败时尝试 GBK 作为回退
  • 编辑后保持原文件编码不变

源文件格式详解

.srw — Window 源文件结构

$PBExportHeader$w_mywindow.srw
$PBExportComments$我的窗口
forward                                          // 前置声明区
global type w_mywindow from window               // 窗口类型定义
int x=200, int y=150, string title="标题"         //   窗口属性
end type

type cb_ok from commandbutton within w_mywindow  // 控件类型定义
int x=100, int y=200, string text="确定"           //   控件属性
end type

type cb_ok from commandbutton within w_mywindow  // 控件实例声明（与类型同名）
cb_ok cb_ok
end type

on w_mywindow.create                              // 窗口事件
// PowerScript code here
end on

event open;
// PowerScript code
end event

type cb_ok from commandbutton within w_mywindow
event clicked;
// PowerScript code
end event

关键规则：

  • 每个控件出现两次：第一次是 type 定义（属性），第二次是 实例（同名变量）
  • forward 行是 ORCA 导出的头部标记
  • 事件脚本用 event <事件名>; 开始，end event 结束
  • 窗口级事件写在整个文件最外层，控件级事件嵌套在 type <控件名> from ... within <窗口名> 内

详细的 PowerScript 语法、控件属性映射、事件名列表见 references/powerscript-syntax.md。

select max(pzh) into :r_pzh from zw_pz_zb

动态 SQL（3 种模式）

模式 1：无参数 — EXECUTE IMMEDIATE

EXECUTE IMMEDIATE "drop table emp" USING SQLCA;

模式 2：带参数 — PREPARE + EXECUTE

PREPARE SQLSA FROM "DELETE FROM emp WHERE empno=?" ;
EXECUTE SQLSA USING :li_empno ;

模式 3：游标（do while 最常用）

string ls_empno, ls_ename
Declare cur_emp Cursor For
    select empno, ename from emp where deptno = :ls_dept;
Open cur_emp;
Fetch cur_emp Into :ls_empno, :ls_ename;
Do While SQLCA.SqlCode = 0
    // 处理数据...
    Fetch cur_emp Into :ls_empno, :ls_ename;
Loop
Close cur_emp;

窗口事件管理

事件触发顺序: Open → Activate → CloseQuery → Close → Deactivate

open — 初始化（设置事务对象、检索数据、禁用按钮） closequery — 检查未保存修改，通过 Return 0/1 决定是否关闭 resize — 按比例自适应调整所有控件位置大小

// closequery 防止数据丢失
If dw_1.ModifiedCount() <= 0 And dw_1.DeletedCount() <= 0 Then Return 0
Int li_flag = MessageBox("提示", "数据已修改，是否保存？", Question!, YesNoCancel!, 1)
Choose Case li_flag
    Case 1: If dw_1.Update() = 1 Then Commit; Return 0
    Case 2: Rollback; Return 0
    Case 3: Return 1  // 取消关闭
End Choose

SQL 审计与库存计算

进销存表关系（教学案例）

表名 说明 关键字段
jxc_d_goods 商品字典 code, name, sort, unit, price
jxc_d_operator 操作员 oper_code, oper_name
jxc_sheet_buy 采购单 zth, sheetid, code, amount, price, money, sheetdate
jxc_sheet_sale 销售单 zth, sheetid, code, amount, price, money, sheetdate

SQL 审计稽核（6 类异常检测）

-- 1. 金额 ≠ 数量 × 单价
SELECT * FROM jxc_sheet_buy WHERE money <> amount * price AND zth = '34';

-- 2. 商品编码不存在
SELECT * FROM jxc_sheet_sale WHERE code NOT IN (SELECT code FROM jxc_d_goods);

-- 3. 编码/日期/制单人为空
SELECT * FROM jxc_sheet_sale WHERE TRIM(code) = '' OR code IS NULL;

-- 4. 数量异常（空或≤0）
SELECT * FROM jxc_sheet_sale WHERE amount IS NULL OR amount <= 0;

-- 5. 日期逻辑错误（开始>结束）
SELECT * FROM jxc_report_amount WHERE dat_min > date_max;

-- 6. 库存与实际不符
-- 库存应 = SUM(采购) - SUM(销售)

库存计算核心公式

期末库存 = 期初库存 + 采购总量 - 销售总量

// PB 中使用游标遍历库存差异
declare cur_stock cursor for
  select t1.code, t1.采购 - coalesce(t2.销售, 0) as 库存
  from (select code, sum(amount) as 采购 from jxc_sheet_buy group by code) t1
  left join (select code, sum(amount) as 销售 from jxc_sheet_sale group by code) t2
  on t1.code = t2.code;

项目重命名与批量导入

将模板项目批量改造为新学号项目（如 ZW → 0457）的完整工作流，详见 references/pb-project-renaming.md。

快速流程

PB IDE 导出原始 PBL → Python 批量重命名 → 依赖排序 → PB IDE 按序导入

命名规则

在类型前缀后插入学号：w_zw_cover → w_0457_zw_cover，dw_zw_c_bb_d → dw_0457_zw_c_bb_d。 内部 global type 声明和 dataobject = "..." 引用必须同步更新。

导入顺序（关键！）

PB 导入 .sr* 必须按依赖序，否则报错：

  1. DataWindows 先导 — 无继承依赖，任意顺序
  2. 基类窗口 — 继承自 window 系统类型
  3. 派生窗口 — 继承自自定义父窗口的放在最后

依赖解析：global type X from Y（继承）+ dataobject = "dw_xxx"（引用）。

pbkiller 导出 vs PB IDE 导出

pbkiller 常导出冗余文件（内嵌 DW 的 _d/_i 后缀、grid+freeform 双版本）。PB IDE 直接导出更干净。 用 grep -rn "name" sr_new/ 验证冗余文件是否被引用，无引用即可删除。

常见陷阱（Gotchas）

编码陷阱

  • PB10 是 Unicode — PBL 内部字符串为 UTF-16LE，API 使用双字节 null 终止符（\0\0）。PB9 及以下使用 ANSI 单字节 null。混用会导致 LMI API 失败
  • .sr 文件默认 UTF-8* — 当前项目 ORCA 导出配置 PBORCA_UTF8=1。读取时优先 UTF-8，失败再回退 GBK/ANSI。直接假定错误编码会导致中文字符损坏
  • 编辑后保持 UTF-8 — 修改 .sr* 文件时，保持与原文件相同的编码。不要保存为 ANSI/GBK
  • 编译前检查 — ORCA 导入时编码错误不会报明显错误，只会在运行时显示乱码

ORCA / pborc 陷阱

  • 版本必须匹配 — PB10 必须用 pborc100.dll，PB25 必须用 pborc.dll。版本不匹配会直接崩溃
  • 32-bit 限制 — ORCA worker 必须是 32-bit 进程，64-bit Python 无法直接调用
  • 导出编码要一致 — PBORCA_UTF8=1 和 PBORCA_ANSI_DBCS=3 只能选一个，混用会导致所有中文乱码
  • 导入前先备份 PBL — ORCA 导入是不可逆的，错了只能从备份恢复

.srd 语法陷阱

  • release 行必须在第一行 — 缺少 release 10; 会导致 ORCA 无法解析
  • name= 必须唯一 — 每个 text/column/compute 控件必须有不同的 name=
  • 颜色是十进制整数 — 不是十六进制，不是 RGB 元组。16777215=白色，255=红色
  • 坐标单位是 PBU — 不是像素。窗口 800×600 对应约 3658×2407 PBU
  • 不要手动改 PBSELECT — retrieve= 中的 PBSELECT 语法极易写错。优先在 PB IDE 中修改 DW 的 SQL，再导出
  • Grid 样式必须加 grid.lines=0 — 缺少此属性会在 PB IDE Edit Source 保存时报语法错误
  • 纸张属性用 print.canusedefaultprinter=yes — 不是 print.canusedefaultpaper，后者 PB10 不识别
  • External 数据源列无 update=/updatewhereclause= — 数据库列才有，External 的 table() 只保留 type=、name=、dbname=
  • External 列 type=decimal 不带精度 — type=decimal(12,4) 会报 syntax error，改为 type=decimal，格式在 column 的 format= 中指定
  • External 列名必须与创建 DW 时向导中定义的一致 — Edit Source 粘贴时列名不匹配会失败

PB IDE Edit Source 陷阱

  • 换行必须是 CRLF (\r\n) — LF 换行的 .sr* 文件 Import 到 PB IDE 会失败，必须转为 CRLF
  • IDE Edit Source 打开 .srd 用 GBK 编码 — ORCA 导出的是 UTF-8，但 PB10 IDE 内部源码编辑器期望系统 ANSI/GBK。直接粘贴 UTF-8 中文会乱码
  • Edit Source 粘贴窗口 .srw 不需要 $PBExportHeader$ — IDE Import 需要，但 Edit Source 粘贴不要
  • dw_result.create(sql) 不能直接传裸 SQL — 裸 SELECT 缺少 release 10; 会报 "incorrect release number"。必须用 SQLCA.SyntaxFromSQL(ls_sql, "style(type=grid)", ls_err) 生成完整 DW 语法
  • 粘贴内容不要从聊天窗口复制 — Markdown 会把 print.margin.top 变超链接、_t 变 \_t，导致 PB 报错。必须从源文件直接复制

⭐ SR 文件外部编辑编码陷阱（高频致命）

核心矛盾：PB IDE 导出的 .sr* 文件在中文 Windows 上使用 ANSI/GB2312 编码，而 Agent 编辑工具只能写出 UTF-8。UTF-8 中文（每字 3 字节）与 GB2312 中文（每字 2 字节）字节序列不同，PB IDE 无法解析。

典型症状：

  • Import 失败："CO114: Error scanning object source entry"
  • Import 失败："Regenerate of source failed"
  • IDE 中打开窗口后显示乱码
  • button text、messagebox 文字、SQL 中的中文字段值全部损坏

解决策略（优先级从高到低）：

  1. 首选：PB IDE 内手工操作 — 用户打开 PB IDE 后，直接指导在 Window/DataWindow Painter 中手动操作。完全避开 SR 文件编码问题。最可靠。

  2. 次选：ASCII-only 编辑 — 如果必须编辑 .sr*，确保新增内容不含任何中文：

    • button text 用英文（"Gen PZ" 而非 "生成凭证"）
    • messagebox 用英文（'Tip'/'Error' 而非 '提示'/'错误'）
    • SQL 固定值用英文缩写（cbxm_name='In' 而非 '入库费'）
    • 注释用 // 英文或删除
    • 用户后续在 PB IDE 中手动改回中文

  3. 最后手段：全新 ASCII 文件 — 原文件已被 UTF-8 中文污染时，用 Write 写出全新纯 ASCII 版本。

快速判断：你写入的中文显示正常但文件中原有中文显示乱码 → 一定是 UTF-8 vs GB2312 混杂。

🔥 放弃 SR 编辑，改用 PB IDE 手动操作

当 SR 编辑反复失败（编码/锁文件/语法错误），立即切换：

  • 不要在 .sr* 文件上继续浪费时间
  • 直接指导用户在 PB IDE 中手动操作：
    • 加按钮：Window Painter → 拖 CommandButton → 设属性 → 双击粘贴事件代码
    • 改 DW：DataWindow Painter → SQL 模式 → 加列 → Design 模式 → 拖控件
    • 改代码：双击控件 → Script 面板 → 粘贴（代码可含中文，IDE 处理编码）

⭐ PB IDE Import 失败诊断

  1. 编码问题（最常见）→ 是否添加了 UTF-8 中文？替换为英文 ASCII。
  2. 语法错误 → choose case 缺 end choose、if 缺 end if、变量声明不完整
  3. 控件重复 → forward 声明区有重复 type，或对象名冲突（如 cb_gen_pz 已存在）
  4. 文件头缺失 → .srd 第一行必须是 release 10;，.srw 必须有 forward 声明
  5. 文件被锁 → PB IDE 打开时锁文件。先关闭 IDE 中该对象再编辑

⭐ 应用对象 CONNECT 陷阱

Application 的 Open 事件必须显式 CONNECT USING SQLCA;，否则所有嵌入式 SQL 报 sqlca.sqlcode = -1、SQLErr=Transaction not connected。

标准模板：

SQLCA.DBMS = "ODBC"
SQLCA.AutoCommit = False
SQLCA.DBParm = "ConnectString='DSN=KS2025;UID=dba;PWD=sql'"
CONNECT USING SQLCA;
if sqlca.sqlcode = 0 then
    open(w_main_login)
else
    messagebox("Error", "Connect failed: " + sqlca.sqlerrtext)
    halt close
end if

ShareData + GetSQLSelect 陷阱

dw_primary.sharedata(dw_secondary) 后，动态 SQL 查询应该只从 primary DW 取 SQL：

// ✅ 正确
i_new_sql = dw_fyd.GetSQLSelect()  // 只用 primary 的 SQL

// ❌ 错误 — 第二行覆盖了第一行
i_new_sql = dw_fyd.GetSQLSelect()
i_new_sql = dw_fyd_free.GetSQLSelect()  // 覆盖！

两个 DW 的 SQL 模板可能不同（grid vs freeform），用 primary 的才一致。

PBT 格式陷阱

  • 无分号结尾 — appname "myapp" 而非 appname "myapp";，分号会使 ORCA 解析器正则匹配失败
  • key 首字母大写 — AppName/AppLib/LibList，尽管解析器用 re.IGNORECASE，但标准格式如此
  • 库路径用相对路径 — LibList "ks_12306010322.pbl"，解析器会自动基于 PBT 所在目录解析

嵌入式 SQL 陷阱

  • 变量前必须有冒号 — where id=:id_var 而非 where id=id_var
  • 必须检查 sqlca.sqlcode — 0=成功，100=无数据，-1=错误。不检查会导致静默失败
  • commit/rollback 配对 — 每个 update/insert/delete 后必须有 commit 或 rollback。忘记 commit 会导致数据不保存
  • 游标必须关闭 — 打开游标后无论成功失败都要 close，否则会锁表
  • select into 只能返回一行 — 多行结果必须用游标

OpenSheet / MDI 陷阱

  • MDI 主窗口内按钮用 OpenSheet(w_child, w_mdiframe) — 两参数形式最简单可靠。不要用 ParentWindow（主窗口上下文不存在）或多余的位置参数
  • OpenSheet 的 4 参数形式易出错 — OpenSheet(w, ParentWindow, 0, Original!) 只在 MDI 子窗口 中有效
  • OpenSheet vs Open — MDI 框架中用 OpenSheet 打开子窗口使其停靠在 MDI 客户区；Open 会以独立窗口打开

PB10 菜单（SRM）导入陷阱

  • PB10 不支持从 .srm 导入菜单 — Import 或 Source 粘贴都极可能失败（C0114/C0001/C0036），这是 PB10 的已知限制
  • 菜单事件不随导出 — 即使导出成功，clicked 事件代码也不会包含在 .srm 中
  • 替代方案：在 PB IDE Menu Painter 中创建（5 分钟手动），或用按钮驱动主界面

编辑安全

  • 不要直接修改 .pbl — .pbl 是二进制文件。永远通过 ORCA 导出→编辑→导入的循环
  • 批量替换前先搜索确认 — 全局替换 dbname= 可能意外连表名一起改掉。用 Grep 先查看所有匹配，确认范围后再改
  • 修改后必须编译验证 — 改了 .srw/.srd 后通过 pb-dev-helper 导入，ORCA 会报告编译错误的具体行号
  • 不要跳过 pb-dev-helper — 手动改完源文件不导入编译就认为完成了，到 PB IDE 里可能报错

ODBC / 数据库连接陷阱（2026-06 新增）

  • PB10 是 32-bit 应用 — 在 64-bit Windows 上必须用 32-bit ODBC 驱动（注册表路径 WOW6432Node）。64-bit ODBC 驱动 PB10 看不到，报 IM002
  • 路径不能含中文/全角字符 — （8）Desktop、工程考试 等含 CJK/全角的路径会导致 ODBC 驱动 I/O error / Unknown device error。复制 .db 到纯英文路径（如 F:\PB_Work\）
  • 免 DSN 直连最可靠 — 不依赖 ODBC 数据源配置：ConnectString='Driver=SQL Anywhere 17;ENG=zw;DBN=zw;UID=dba;PWD=sql;DBF=F:\...zw.db'
  • SQL Anywhere 17 兼容 ASA 9 — SA17 驱动可读写 ASA 9.x .db 文件。C:\Program Files\SQL Anywhere 17\Bin32\dbodbc17.dll
  • User DSN 可用 PowerShell 创建 — 无需管理员权限：New-Item -Path 'HKCU:\Software\ODBC\ODBC.INI\KS2025'
  • Application 对象必须先导入 — 全局变量（g_zth/g_nkjqj/g_ykjqj）在 App 对象中声明。窗口 Regenerate 前 App 必须在 PBL 中，否则 C0015: Undefined variable
  • ASA 默认凭据 — UID=dba, PWD=sql。如被修改过，联系 DBA

// 1. 更新科目余额表：从凭证汇总借方/贷方发生额
UPDATE zw_zb_kmyeb SET jffse = (SELECT COALESCE(SUM(jfje),0) FROM zw_pz_mxb

WHERE zth=:g_zth AND nkjqj=:g_nkjqj AND ykjqj=:g_ykjqj;

// 2. 更新期末余额: 期初+借方发生-贷方发生(借科目) / 期初+贷方发生-借方发生(贷科目)
UPDATE zw_zb_kmyeb SET
    qmjfye = qcjfye + jffse,
    qmdfye = qcdfye + dffse,
    jflj = COALESCE(jflj,0) + jffse,
    dflj = COALESCE(dflj,0) + dffse
WHERE zth=:g_zth AND nkjqj=:g_nkjqj AND ykjqj=:g_ykjqj;

// 3. 插入明细账：逐笔凭证生成明细记录

SELECT zth,nkjqj,ykjqj,km_code,
    (SELECT COUNT(*)+1 FROM zw_zb_mxzb b WHERE b.zth=a.zth AND b.nkjqj=a.nkjqj
     AND b.ykjqj=a.ykjqj AND b.km_code=a.km_code),
    rq,pzh,zy,jfje,dfje
FROM (SELECT a.zth,a.nkjqj,a.ykjqj,b.km_code,a.rq,a.pzh,b.zy,b.jfje,b.dfje
      FROM zw_pz_zb a, zw_pz_mxb b
      WHERE a.zth=b.zth AND a.nkjqj=b.nkjqj AND a.ykjqj=b.ykjqj AND a.pzh=b.pzh
        AND a.zth=:g_zth AND a.nkjqj=:g_nkjqj AND a.ykjqj=:g_ykjqj AND a.jzbj='是') a;

PB源文件 + & 续行陷阱

PowerBuilder的 + & 续行必须在行尾使用，绝不能在下一行开头用 +：

// ✅ 正确
ls_sql = "SELECT ... " + &
    "FROM ... " + &
    "WHERE ..."

// ❌ 错误 — PB报C0031
ls_sql = "SELECT ... "
+ "FROM ... "
+ "WHERE ..."

推荐替代方案：s = s + "..." 逐段拼接，避免续行问题：

ls_s = "SELECT ... "
ls_s = ls_s + "FROM ... "
ls_s = ls_s + "WHERE ..."

全局变量声明在 Application 对象（.sra 文件）的 global variables 段中，不在窗口 .srw 中。新建窗口引用全局变量时，必须确保 Application 对象中已声明：

// ks_12306010339.sra → global variables

string g_id        // 操作员编号
string gs_period   // 当前处理月份(供计算/报表窗口使用, 与 g_ykjqj 同步)

编码修复实战：GB2312→UTF-8 双重编码

当源码文件中文显示乱码（如 "账务系统" 显示为 "������ϵͳ"），是 GB2312 字节被当作 UTF-8 解析造成的。修复步骤：

  1. 用 open(path, 'r', encoding='utf-8', errors='replace') 读取
  2. 人工识别并替换所有乱码中文为正确 UTF-8 中文
  3. 如果是 Import 使用，保存为原始编码（GBK）
  4. 如果是 Source 粘贴使用，保存为 UTF-8（不带 BOM）
  5. 所有中文字符串检查：窗口 title、控件 text、注释、MessageBox 文本

if li_rtn = 1 then dw_result.settransobject(sqlca); dw_result.retrieve()
else messagebox('Error', 'Query failed.')

// ✅ 方案1：全部挤一行（单行 IF 不需要 end if）
if li_rtn = 1 then dw_result.settransobject(sqlca); dw_result.retrieve() else messagebox('Error', 'Query failed.')

// ✅ 方案2：多行格式 + end if（推荐，与 SR 模板一致）
if li_rtn = 1 then
    dw_result.settransobject(sqlca)
    dw_result.retrieve()
else
    messagebox('Error', 'Query failed.')
end if

记忆规则：else 写在单独一行 = 多行 IF = 必须有 end if。SR 模板（w_zw_A1.srw）中所有 if-else 都遵此规则。从其他项目复制的窗口代码最常见此陷阱——它在原环境能跑但在新环境导入时报 C0031，因为原 PBL 编译时可能有宽容模式。诊断法：找到报错的 .clicked.81 行号位置，对比同目录 SR 模板文件的 if-else 写法即可定位。

CRLF 换行符 → Import "Regenerate of source failed"（增强）

PB IDE Import 对话框可能报 4 种原因，但"Regenerate of source failed"最常见——几乎总是换行符不是 CRLF。从 Git/macOS/Linux 环境或 Python 编辑产生的文件往往是 LF。

诊断：

file w_A_level.srw
# ✅ 正常：ASCII text, with CRLF line terminators
# ❌ 异常：UTF-8 text（无 "CRLF" = LF，Import 必失败）

修复（Python 可靠方案，处理中文路径）：

with open(path, 'rb') as f:
    data = f.read()
data = data.replace(b'\r\n', b'\n').replace(b'\n', b'\r\n')
with open(path, 'wb') as f:
    f.write(data)

注意：Windows 中文路径在 sed -i / tr / bash 管道中容易乱码。首选 Python 二进制读写。文件被 PB IDE 锁定时（"Device or resource busy"），先关闭 PB IDE 再覆盖。

Edit Source 粘贴绕过 Import 失败

当 Import 对话框反复报错（4 条原因轮着出现），直接用 Edit Source 粘贴：

  1. File → New → Window → Save As 为目标对象名（如 w_A_level）
  2. 关闭 Window Painter → Library Painter 中右键该对象 → Edit Source
  3. 全选删除 → 贴入 SRW 全部内容 → Ctrl+S 保存 → PB 自动 Regenerate

Edit Source vs Import 关键区别：

  • 不需要 $PBExportHeader$
  • 不强制 CRLF 换行
  • 但内容必须语法完全正确（end if 等一个不能少）

statictext 属性兼容性（跨项目导入）

从其他项目复制的 statictext 控件，部分属性在 PB10 Import 时可能触发 C0031。报错在 st_xxx.N 行号时，安全的最小属性集：

// ✅ 仅保留必要属性

integer width = 1068; integer height = 72
