# 网页回归测试

将"用自然语言描述测试需求"转化为一次完整的网页回归测试：自动规划步骤、驱动浏览器执行交互、按多种断言校验结果，并产出可读的专业测试报告。面向测试工程师、开发者，以及需要验收网页交付的非技术人员。

## 语言处理 / Language

本技能面向中、英文用户，**交付语言跟随用户输入语言**：

- 用户用中文描述需求 → 全程中文回复（测试计划、步骤、状态、报告）。
- 用户用英文描述需求 → 全程英文回复，不要给英文需求强行回中文。
- 断言状态标签：中文 `通过 ✅ / 部分通过 ⚠️ / 失败 ❌`；英文 `PASS ✅ / PARTIAL ⚠️ / FAIL ❌`。
- 报告模板按用户语言选用：中文见 `references/report-template.md` 默认模板，英文见其 English Template 段。

这与"自然语言驱动"的定位一致——用户用什么语言下指令，就用什么语言交付。

## 何时使用

- 用户给出网址 + 想测的功能（如"测一下 https://x.com 的登录和下单流程"；英文："Test the login and checkout flow at https://x.com"）
- 用户要求网页 UI 测试、回归测试、冒烟测试、功能验证（英文：UI / regression / smoke / functional testing）
- 用户拿到网页交付物，需要验收是否达标（英文：acceptance of a web deliverable）
- 用户希望"说一句话"就完成原本要写自动化脚本的测试

## 核心差异（相对录制类工具）

本技能不要求录制操作或写代码。输入是自然语言测试需求，输出是"步骤 + 断言结果 + 报告"。把"写自动化脚本"降级为"描述测试意图"——这正是与市场上录制导出脚本类工具的差异点，也是上架卖点。

## 工作流程

### 1. 解析测试需求

从用户输入中提取：

- **目标网址**（必填）
- **测试范围**：登录 / 下单 / 注册 / 表单提交 / 导航 / 搜索 等
- **关键校验点**：用户点名的断言（如"提交后显示订单号"）
- **环境约束**：是否需要登录态、测试账号、前置数据

若缺少目标网址或测试范围，向用户澄清，不要臆测。

### 2. 规划测试步骤

将自然语言需求拆为有序、可执行的步骤序列。每步标注：

- 动作（打开 / 点击 / 输入 / 选择 / 等待 / 导航）
- 目标元素（用可读描述，如"登录按钮""邮箱输入框"）
- 该步预期（用于后续断言）

步骤粒度以"一个用户可感知的操作"为单位，避免过细。

### 3. 执行与断言

按步骤驱动浏览器（使用平台浏览器自动化能力）逐步执行。在每一步的预期点插入断言。断言类型详见 `references/assertion-catalog.md`，常用包括：

> 浏览器驱动准备（尤其 Windows 环境 Chromium 下载失败时如何用 Edge 兜底）见 `references/windows-edge-fallback.md`。
> 测后台管理类站点（登录 + 侧边栏菜单 + 列表 + 搜索）时，通用路径与断言范式见 `references/admin-console-flow.md`。

- 元素存在 / 可见
- 文本内容匹配（包含 / 等于 / 正则）
- URL 变化
- 表单字段值
- 控制台无错误
- 网络请求成功（状态码）

执行中的关键约定（来自真实站点验证）：
- **导航后必重新 snapshot**：元素引用（@eN）随页面刷新失效，每次点击/跳转后先取最新可交互元素再操作，不要沿用旧引用。
- **SPA / 客户端路由**：后台多为前端路由（如 /console、/orders），`wait --load` 不会因路由切换再次触发，应等待"目标元素可见"而非文档 load。
- **登录落地页与断言目标不符**：若登录后落在首页/仪表盘而非断言指定的功能页，先经菜单导航到达目标页再断言，并在报告中标注"落地页差异"（属实现差异，非缺陷）。

执行中若某步失败，记录失败原因与现场（截图 / URL / 控制台），继续完成其余独立步骤，不整体中断。

### 4. 生成测试报告

测试结束后，按 `references/report-template.md` 生成 Markdown 报告，包含：

- 概览：网址、测试范围、通过率、耗时
- 步骤明细：每步动作、预期、实际、通过 / 失败、截图链接
- 缺陷清单：失败项汇总 + 复现线索
- 结论与建议

报告使用客观语言，标注"自动化测试结论，建议人工复核关键路径"。

## 输入格式建议

指导用户按此格式提供，可显著提升准确率：

```
网址：https://...
测试点：登录、下单流程
断言：登录成功跳转首页；下单后显示订单号
环境：已有测试账号 test@x.com / 123456
```

英文示例 / English:
```
URL: https://...
Test points: login, checkout
Assertions: login redirects to dashboard; order number shown after checkout
Env: test account test@x.com / 123456
```

## 环境准备（浏览器驱动）

执行测试前需有可用的浏览器驱动。若使用平台内置浏览器自动化能力，按其默认配置即可；若使用 `agent-browser` CLI 且在 Windows 上遇到官方 Chromium 下载失败，参见 `references/windows-edge-fallback.md` 用本机 Edge 兜底，无需翻墙即可跑通整条流水线。

## 边界与注意

- 仅测试用户明确授权的网址；不绕过登录鉴权、不测未授权系统。
- 动态 / 随机内容（如验证码、实时价格）用"形态断言"（如"包含数字"）而非精确匹配。
- 断言失败不等于 bug，需区分"实现差异"与"真实缺陷"，报告中注明。
- 不将用户测试账号密码存储到技能外部；仅在本次会话使用。
