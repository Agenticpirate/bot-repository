# 百炼智能 · 招投标全能助手

一站式招投标智能体：**查标讯、判该不该投、挖早期商机、背调企业**四大能力合一。

## API 概览

**基础 URL**: `https://mcp-server.zhiliaobiaoxun.com/api_v2/` + 工具名，工具名逐字取自下方工具表（例：`https://mcp-server.zhiliaobiaoxun.com/api_v2/search_bids`）。


> **两个域名别混用**（打错就是 404，且不会提示你打错了）：
>
> | 用途 | 域名 + 前缀 | 例子 |
> |---|---|---|
> | **查数据** | `https://mcp-server.zhiliaobiaoxun.com/api_v2/` | `POST …/api_v2/search_bids` |
> | **查账户**（免费、不扣额度） | 同上域名 | `GET …/api_v2/account/balance`（余额）、`GET …/api_v2/account/daily_consumption`（每日消耗） |
> | **注册取 Key / 取充值链接** | `https://ai.zhiliaobiaoxun.com/web-api/` | `POST …/web-api/internal/auto-register`、`POST …/web-api/auth/generate-device-sid` |
>
> 下文出现的相对路径（如 `/api_v2/search_bids`）一律拼**第一行**那个域名；
> 只有注册与充值链接相关的接口才用第二行。**绝不要把 `/web-api/` 拼到 mcp-server 上，
> 也不要把 `/api_v2/` 拼到 ai 域名上。**

**调用方式**: 数据工具用 POST；账户查询用 GET，路径固定为 `GET /api_v2/account/balance`（余额）和 `GET /api_v2/account/daily_consumption`（每日消耗），免费、不扣额度。

```
Headers:
  X-API-Key: $ZLBX_API_KEY
  X-Client: ai-platform/1.0.1
  Content-Type: application/json
```
> ⚠️ **`X-API-Key` 要填真实的 Key 字符串，不要把 `$ZLBX_API_KEY` 原样写进请求头**。环境变量没设时它会变成空值，服务端收到的就是「没带 Key」——直接 `INVALID_APP_KEY`，而不是你以为的「Key 错了」。**取不到 Key 就先走下面的获取流程，不要先把请求发出去。**


> **X-Client 头必须携带**（值固定为 `ai-platform/1.0.1`，账户查询 GET 请求同样携带），用于服务端区分调用来源，缺失不影响功能但请始终带上。

**API Key 获取**（按以下优先级，命中即停，不要做任何额外提示）：

1. 环境变量 `$ZLBX_API_KEY`（用户主动配置）→ 直接用
2. 本地配置文件 `~/.zlbx/config.json` 中 `api_key` 字段 → 直接用
3. **以上都没有 → 自动注册**（仅此场景下才走自动机制，**必须先征得用户同意**，详见 `references/auto-register.md`）：
   - 先一句话告知将采集哪些设备特征并征求同意；用户拒绝则给出手动申请地址 https://ai.zhiliaobiaoxun.com/?ch=s142 ，流程终止
   - 同意后采集 3 项设备特征（platform / arch / mac_hash），任何采集失败都用空串代替，**不要中断**
   - POST `https://ai.zhiliaobiaoxun.com/web-api/internal/auto-register`
   - 返回的 `api_key` 写入 `~/.zlbx/config.json`：`{"api_key": "zlbx_xxx", "source": "auto", "registered_at": "<ISO 时间>"}`
   - 当前会话立即用该 key 继续工作；新设备账号赠送 100 次免费调用，绑定手机号再送 100

> **重要**：若 `$ZLBX_API_KEY` 已配置或 config.json 中 `source` 不是 `"auto"`，本 SKILL 不输出任何关于「自动注册」「自动登录」「设备绑定」相关内容，按现有手动充值流程提示用户。

## ⭐ 能力路由表（最重要的一节）

**先判断用户要什么，再读对应那条线的文档。不要一次性把四条线的文档全读进来**——
那是 839 行，会把上下文吃光，而且四条线的工作流互相冲突（比如「先搜再筛」和
「先定公司再挖」是两套逻辑）。

判断锚点是**输入物**和**目的**：

| 用户在说什么 | 走哪条线 | 先读这个 |
|---|---|---|
| 「查一下最近的招标」「搜某某项目」「这个标的详情」「哪些项目快到期」「Top 采购单位/中标品牌」「历史中标单价」 | **标讯搜索** | `references/tender-search/overview.md` |
| 「这个标该不该投」「中标概率多大」「投标策略」「竞争格局怎么样」——**输入物是一条具体标讯** | **投标决策** | `references/bid-decision/overview.md` |
| 「帮我找商机」「有什么新项目机会」「拟建项目」「临期续约」「做个商机晨报」——**还没有具体标的，要挖** | **商机雷达** | `references/opportunity-radar/overview.md` |
| 「查一下这家公司」「背调这个客户/供应商/竞对」「这家公司中标记录」「上下游关系」——**输入物是公司名** | **企业情报** | `references/company-intel/overview.md` |
| 「我还剩多少额度」「查余额」「这个月花了多少」 | 直接调账户工具，免费 | `references/tender-search/api-account.md` |

> **⚠️ 工商字段要按字段区分，不要整类拒绝。**
>
> **能查**（`get_company_profile` 会一并返回，走企业情报即可）：统一社会信用代码、
> 注册资本、成立日期、经营范围、经营状态、行业、省市区、规模。
>
> **查不了**：法定代表人、登记机关、曾用名、工商注册码、组织机构代码、企业类型、
> 实缴资本、核准日期、营业期限、注册地址。这些只在 `get_company_registry` 里，
> 该数据源当前停用。
>
> 用户问到「查不了」那一栏时**如实说明这几项查不到**，同时把能查的照常给出来——
> 既不要拿相邻数据糊弄，也不要因为其中一项查不到就把整个请求拒掉。

**分不清就问一句**，别猜。三组最容易混的：

**① 标讯搜索 vs 商机雷达**
用户已经点名要找什么类型的项目 → 搜索；用户想要「你告诉我有什么机会」→ 雷达。
出现「推荐」「值得跟进」「潜在机会」「有什么好项目」这类**要你替他判断**的词 → 雷达。

- 「找找智慧交通方面的项目」→ **搜索**（已点名品类，是定向检索）
- 「我们做智慧交通，最近有哪些值得跟进的机会」→ **雷达**（要你筛出值得的）

**② 投标决策 vs 企业情报：看输入物是「项目」还是「公司」**
「竞争对手」这个词两条线都沾，光看词会选错，**必须落到输入物上**：

- 「分析一下**这个项目**的竞争对手」→ **投标决策**（输入物是标讯，问的是这个标的竞争格局）
- 「分析一下**海康威视**的竞争对手」→ **企业情报**（输入物是公司，问的是这家公司的对手图谱）

同理：「这个标该不该投」→ 决策；「这家公司什么来路」→ 情报。

**③ 企业情报 vs 通用市场调研**
本线只看**招投标视角**：中标战绩、主营品类、上下游、投标对手。
用户要的是产品竞品分析、市场份额、融资情况 → **本 SKILL 不适用**，别硬接。

**开跑前的最低参数**（缺了就先问，别拿默认值试探——每次调用都花钱）：

| 线 | 至少要问清 |
|---|---|
| 标讯搜索 | 关键词/品类 + 地域 + 时间范围 |
| 投标决策 | 一条具体标讯（标题、链接或正文） |
| 商机雷达 | 关注的行业 + 地域 + 想要哪一路（拟建/续约/意向） |
| 企业情报 | 公司全称或可消歧的简称 + 用户站在什么视角（竞争 or 合作） |

**跨线组合是常态，按需依次调用**。典型链路：

1. 雷达挖到商机 → 决策判断该不该投 → 情报背调采购方和竞对
2. 搜索找到标讯 → 决策出投标建议
3. 情报锁定目标客户 → 搜索查它的历史采购

组合时**每完成一段就交付一次**，不要憋到最后一次性输出——用户随时可能改方向。

## 💰 成本原则

数据工具按次计费，账户查询免费。**每次调用都是用户的钱**，所以：

1. **先想清楚再调**。同一个问题不要用不同参数反复试探，先把用户需求问明白。
2. **能一次拿到的不要分多次**。批量参数优先于循环单查。
3. **跨线组合时说明将要做几步**，让用户有机会喊停：「我打算先挖商机（1 次），再对前 3 个做决策分析（3 次），可以吗？」
4. **余额不足时不要重试**。直接走 `references/auto-register.md` 里的充值引导，重试只会连续报错。

## 错误处理

| 错误码 | 含义 | 怎么办 |
|---|---|---|
| `INVALID_APP_KEY` | Key 缺失或无效 | **不要让用户去翻环境变量**。按 `references/auto-register.md` 走自动注册领取（首次免费）；已有 Key 仍报此错时也走同一流程，但**若自动注册返回 401 `ACCOUNT_RECOVERY_REQUIRED`，不要重试、不要改设备特征**，照它的 hint 引导用户登录取 Key |
| `APP_KEY_EXPIRED` / `APP_KEY_DISABLED` | Key 过期或被停用 | 同上；同样地，自动注册若返回 401 `ACCOUNT_RECOVERY_REQUIRED` 就停手，照 hint 引导用户登录取 Key |
| `QUOTA_EXCEEDED` | 额度不足 | **不要重试**。按 `references/auto-register.md` 的指引给出充值入口 |
| `RATE_LIMIT_EXCEEDED` | 触发限流 | 降低频率、稍后重试，不要立即重发 |
| `INVALID_PARAMETER` / `MISSING_REQUIRED_PARAMETER` | 参数有误 | 检查必填参数和类型 |
| `QUERY_EMPTY` | 没命中 / 需消歧 | **不是故障**。若 `details` 给了候选企业，列给用户选准确全称；确实没命中则建议放宽关键词、时间或地区 |
| `NOT_FOUND` | 标识定位不到 | 检查公告 ID、`uniq_key`、公司名或 URL 是否正确、公告类型是否选对。**精确标识不要原样重试** |
| `QUERY_TIMEOUT` | 查询超时 | 缩小时间窗、地区或关键词范围后有限重试（最多一次） |
| `ES_UNAVAILABLE` / `INTERNAL_ERROR` | 服务端临时故障 | 稍后重试。**不要重新注册 Key**，与鉴权无关 |
| `CLIENT_VERSION_UNSUPPORTED` | 版本过低 | 提示用户到安装来源更新本 SKILL |

其余错误码见各线 `references/<线>/overview.md` 的错误处理小节。
