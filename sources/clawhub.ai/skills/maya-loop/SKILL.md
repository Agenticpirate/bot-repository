# Maya Loop — 6步工程执行框架 v5.0

## 核心原则

> **不允许跳步，不允许凭经验绕过去。**
> **每一步都有硬性检查点，不过关不进入下一步。**
> **v5.0 融合 Karpathy 12条 AI 辅助开发铁律 [K1-K12]——AI 无规则时错误率 41%，有规则后 11%。**
> **Maya Loop 是安全网，不是紧箍咒——走完它就敢放心睡觉。**

## 🔴 麦麦自动触发铁律（v5.0 最关键规则）

> **不需要 Jason 说触发词。只要进入研发场景——无论什么产品——麦麦自动启动 Maya Loop。**

麦麦在以下任何时刻**必须**自动对照 Maya Loop 走六步，不等待、不询问、不跳过：

| 触发信号 | 麦麦自动行为 |
|:---|:---|
| `Write` / `Edit` 工具被调用修改代码或配置 | 自动启动 Loop，跑完「定→拆→做→验→备→记」 |
| `Bash` 执行 `docker compose` / `git push` / `systemctl restart` / `scp` 等部署命令 | 自动启动 Loop |
| 对话中出现"部署""上线""发布""改一下""修一下""加个功能" | 自动启动 Loop |
| 任何涉及文件修改 + 需要回滚能力的操作 | 自动启动 Loop |

**这不叫"等 Jason 说"——这叫"麦麦的肌肉记忆"**。就像呼吸一样，不经过大脑决策。这是 Maya Loop 存在的唯一意义。

### 第一步：定（Define）

**做什么 + 为什么 + 影响什么**，三句话说清。带上 AI 辅助开发的假设声明。

- [ ] 明确做什么？边界在哪？
- [ ] **[K2] 写之前先想** — 说清你的实现假设（如"我假设这个服务跑在容器里"），最多列 2-3 个可选方案并给出推荐，不确定就问，不用看似合理的代码填理解空白
- [ ] **[K6] 目标驱动** — 模糊需求先具象化：「做个监控」→「每30分钟扫一次XX源，检测到Y类事件发邮件给Z」
- [ ] 为什么现在做？不做会怎样？
- [ ] 涉及哪些文件/服务？**[K4-prep] 区分白名单文件 vs 红牌文件**
- [ ] 影响面多大？（单文件 / 多文件 / 系统拓扑）
- [ ] 需要走 Plan 模式还是可以直接执行？

**过关标准**：能在三句话内说清楚"做什么、为什么、影响什么" + 方案假设已声明。

### 第二步：拆（Decompose）

**拆成小步骤，每步有验收标准。Karpathy 增强：每个子任务用最简单方案。**

- [ ] 拆成独立可执行的小步骤
- [ ] **[K3] 保持简单** — 每个子任务检查：能用现有工具吗？能用标准库吗？能用开源组件吗？禁止过早抽象、臆想式错误处理、无意义可配置、单实现接口
- [ ] **[K4-prep] 外科手术式** — 确认每一步触及的文件都在白名单内（.env / docker-compose.yml / config/*.yaml / prompts/*.md / collectors/*.yaml），不在白名单的标为红牌禁止触碰
- [ ] 每步有明确的验收标准
- [ ] 标出依赖关系（哪步必须先做）
- [ ] 预估每步的风险等级

**过关标准**：每个步骤有 "做什么 + 怎么验 + 是否在白名单内"。

### 第三步：做（Do）

**执行改动。v5.0 融合 Karpathy 4条+Jason 2条，所有 AI 辅助开发的质量护栏集中在此。**

- [ ] **[J10] 部署前先备份**（当前状态快照）
- [ ] **[K1] 写之前先读** — 改动前读懂目标文件；沿用项目已有模式（项目用 fetch 就别引入 axios）
- [ ] **[J9] 部署路径铁律** — 自问"这个文件被谁读？"（Docker 容器 vs systemd service 路径不同）
- [ ] **[J12] 不改源码改配置** — 开源项目只改 4 类文件：.env / docker-compose.yml / 采集器配置 / prompt 模板
- [ ] **[K4] 外科手术式** — 不触碰任务外的代码；100% 匹配现有文件风格（引号/命名/分号）；不重新格式化文件
- [ ] **[K7] 调试** — 先 100% 复现问题再动手改；一次只改一处，验证后再改下一处；不理解根因不加 workaround
- [ ] **[K8] 依赖管理** — 新增依赖前依次确认：已有工具能实现吗？标准库能覆盖吗？依赖还活着吗？加了必须说明原因

**硬性规则**：
- L3 系统拓扑操作：强制 Plan + 备份 + 验证环境
- 任何破坏性操作：先备份不可逆数据
- **[K12] 白名单原则**：绝不在未授权情况下碰 .py / .js / .tsx / Dockerfile / 数据库 schema 源码

### 第四步：验（Verify）

**验证改动。v5.0 新增 AI 输出→人眼验证环节。**

- [ ] **[K5] 验证三步**：docker logs 看启动 → curl 验 HTTP → 用真实数据跑核心流程
- [ ] **[J11] AI 输出→人眼验证** — AI 生成的报告/代码/配置，必须经人审核后才可交付给客户或上线
- [ ] 新代码特征输出出现在日志中（不只看 service active）
- [ ] 不影响已有功能（回归测试）
- [ ] 资源占用正常（CPU / 内存 / 磁盘）

**硬性规则**：
- "服务 active 不代表代码在跑" — 必须查 journalctl/docker logs
- 容器内验证优于宿主机验证
- **AI 调查报告/告警→先让安全人员看一眼→再发给客户**

### 第五步：备（Backup）

**必须三项，不变。**

- [ ] **版本号更新**（3 位数字：v{major}.{minor}.{patch}）
- [ ] **云端备份**：变更文件 + 数据库 + 配置 + VERSION.txt
- [ ] **本地备份**：同上
- [ ] MD5 校验一致性

**VERSION.txt 必须包含**：版本号、日期、变更摘要、涉及文件列表、回滚命令。

### 第六步：记（Record）

- [ ] 更新项目 MEMORY.md（版本号、教训）
- [ ] 追加当日日志 YYYY-MM-DD.md
- [ ] 如有跨项目通用的教训 → 写全局 ~/.workbuddy/MEMORY.md
- [ ] 如有可复用的工作流 → 固化为 skill
- [ ] **[v5.0 新增] 记录本轮有无违反 Karpathy 12 条的行为及处理方式**

## 不适用 Maya Loop 的场景

- 查询/阅读/分析（不做变更）
- 一次性的临时操作（不需要回滚）
- 纯粹的信息收集

## 五环自主运转基础设施（v6.0 新增）

> Maya Loop 不只是一個開發流程——它是一套讓 AI Agent 可以**跨會話自主呼吸**的基礎設施。
> 六步循環是 Maya 怎麼做事，五環系統是 Maya 怎麼自己呼吸。

### 架構總覽

五個自治環共用審計日誌 + 心跳 + 信號協議三層底座：

| 環 | 做什麼 | 心跳 |
|----|--------|------|
| **Guardian 守護環** | 伺服器巡檢、Docker 管理、站點監測，L0-L3 自治梯度 | 每小時 |
| **Digester 消化環** | 知識庫自動精讀、雙向關聯（正向+反向）、認知更新標記 | 每日 |
| **Sentinel 哨兵環** | 合規矩陣、法規掃描、SSL 證書到期 | 每週 |
| **Shepherd 牧人環** | 會話恢復、心跳監控、信號回執掃描、Dev Loop 監聽、審查追蹤 | 4h |
| **Review 審查環** | 三角審查模式：設計產出 → 外部挑戰 → 收斂 → 決策 | 事件驅動 |

### 三角審查模式（Review Loop）

```
Maya設計 + G老師挑戰 + Jason拍板 = 對抗式協作系統
```

這是 Loop Engineering 的實踐範例，不是 Prompt Engineering。寫程式碼的 Agent 和審程式碼的 Agent 必須分開——同一個模型既當運動員又當裁判，結果永遠是給自己打滿分。

### 底座引擎（scripts/）

| 引擎 | 文件 | 用途 |
|------|------|------|
| 審計日誌 | `scripts/audit.py` | JSONL 記錄鏈 + 回滾，物理隔離於 Memory |
| 心跳+閾值 | `scripts/heartbeat.py` | 分級心跳 + 磁碟/CPU 漸進閾值 |
| 信號協議 | `scripts/signal.py` | 環間信號回執，priority 分級超時 |
| Dev Loop | `scripts/devloop.py` | git/mtime 感知 + 四 check（備份/路徑/版本/部署驗證）|
| 審查引擎 | `scripts/review.py` | 三角審查模式：創建→提交→回饋→修訂→拍板 |

### Guardian 自治梯度

| 級別 | 操作 | 權限 |
|------|------|------|
| L0 自癒 | Docker restart / nginx reload | 自動·事後通知 |
| L1 告警 | 磁碟 85% / CPU 持續高 / 監測中斷 | 即時通知 |
| L2 需確認 | 伺服器 reboot / 回滾部署 / 防火牆 | Jason 確認後執行 |
| L3 僅報告 | 安全入侵跡象 / 數據異常 | 僅分析不操作 |

### 信號回執分級超時

| priority | 超時 | 動作 |
|----------|------|------|
| high（安全漏洞/法規變更）| 15min | 直接告警 + Shepherd 立即介入 |
| medium | 2h | 標記異常，下次心跳報告 |
| low | 6h | 僅記審計日誌 |

### 理論支撐

完整架構文件：`references/architecture.md`

核心理論：
- Prompt → Context → Harness → Loop 四階段瓶頸外移
- Agent = 模型 + Harness（Mitchell Hashimoto）
- Addy Osmani 五大關鍵動作（發現/交接/驗證/持久化/調度）
- 黃仁勳/吳恩達/Karpathy/Steinberger/Cherny 行業共識：Prompt 已死，Loop 是未來

### 部署步驟

1. 創建 `.workbuddy/audit/` 目錄
2. 拷貝 `scripts/` 下五個引擎到該目錄
3. 修改 `devloop.py` 中的 `PROJECT_PATHS`（專案路徑和伺服器位址）
4. 修改 `signal.py` 中的 `SIGNAL_ROUTES`（環間信號路由規則）
5. 設置信號回執的審查者角色（`review.py` 中的 `REVIEW_ROLES`）
6. 設置自動化：Guardian 每小時 + Shepherd 每 4h
7. 首次運行：各環註冊心跳 → 自動創建審計日誌

### 軟性要求

- 審計日誌必須物理隔離於 Memory
- 備份保留策略：最近 5 版本完整，更早僅保留 VERSION.txt
- 工程師新定位：算力分配師 → 決定每一分算力投向哪裡
- 同一 Loop，帶判斷力就放大判斷力，帶懶惰就放大懶惰
