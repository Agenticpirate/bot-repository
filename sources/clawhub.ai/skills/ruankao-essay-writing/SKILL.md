# 软考论文写作指导

辅助用户完成软考高级资格（系统架构设计师 / 信息系统项目管理师 / 系统分析师 / 网络规划设计师 / 系统规划与管理师）论文写作，提供从项目准备到成文校对的全流程指导，确保论文符合阅卷标准、避免常见失分点。默认按系统架构设计师视角组织内容，报考其他资格时按对应视角调整。

## 适用场景

- 需要帮助准备项目素材 → 从 Phase 0 开始
- 只给了题目 → 从 Phase 1 开始
- 已有草稿 → 直接进入 Phase 5 自查
- 需要摘要模板 → 读取 `references/abstract-templates.md`
- 需要提纲模板 → 读取 `references/outline-template.md`
- 需要项目准备指导 → 读取 `references/project-preparation.md`
- 需要检查清单 → 读取 `references/common-issues.md`

---

## 工作方式

论文写作遵循以下步骤：

0. **项目准备与素材库建设** — 考前选定项目、收集资料、建立可复用素材库
1. **分析论文试题** — 精读试题，圈出要点，确保每个子问题不遗漏
2. **撰写提纲** — 按模板列提纲，明确结构、逻辑链条和论证要点
3. **摘要撰写** — 按模板写 300-400 字摘要
4. **正文撰写（填充内容）** — 按提纲填充，运用 SCQA、金字塔原理、5W2H
5. **检查校对** — 逐项检查，确保完整回应试题、结构严谨、逻辑自洽

根据用户所处阶段灵活切入：
- 需要帮助准备项目素材 → 从 Phase 0 开始
- 只给了题目 → 从 Phase 1 开始
- 已有草稿 → 直接进入 Phase 5 自查

## 论文七问：贯穿写作全程的论证主线

写作与自查始终围绕以下七个问题展开，确保论文回答清楚、论证完整。这七个问题覆盖了论文的核心评分维度，任何一问回答不清都会直接扣分：

| # | 问题 | 论文对应位置 | 对应评分维度 |
|---|------|-------------|-------------|
| 0 | 我是否以**架构师视角**去设计架构和撰写论文？ | 全文（视角贯穿） | 应用深度与水平 |
| 1 | 我干了什么项目？我的职责是什么？ | 项目背景 | 实践性 |
| 2 | 我为什么要用这个架构？非它不可吗？ | 理论部分（选型论证） | 应用深度与水平 |
| 3 | 这个架构是什么？怎么组织约束？各构件之间怎么配置连接？ | 理论部分（架构描述） | 应用深度与水平 |
| 4 | 该架构在项目中的**具体实践应用**？ | 分论点（实践展开） | 实践性 |
| 5 | 我用了该架构后遇到了什么困难？ | 分论点（踩坑与反思） | 实践性 |
| 6 | 该架构应用后的效果是什么？ | 总结与感悟 | 实践性 |
| 7 | 论文是否存在**空话、套话**？是否纯理论而没有体现实践性？ | 全文（统摄性检查） | 实践性 + 文字表达能力 |

> 各资格通用：Q2/Q3 中的"架构"按论文主题替换理解——信管对应管理框架、网规对应网络方案、系规对应服务体系，七问框架不变。

要点：

- **七问是主线，不是模板**：不必按序机械罗列，但要确保每问都有答案，且答案依托项目实际
- **Q2 最关键**：阅卷最看重"为什么"，要写出候选方案对比 → 权衡取舍 → 最终选型，体现"非它不可"
- **Q3 要具体**：画出架构图/拓扑，说明组织约束、构件连接方式，避免空谈理论
- **Q5 体现真实**：写出踩坑经历与解决过程，是论文真实性、实践性的最佳证明
- **Q0 贯穿全文**：始终以架构师视角组织内容——先全局设计再细节，突出权衡取舍而非罗列功能
- **Q7 是七问的红线**：空话套话 = 没有回答。每段理论后紧跟"我在项目中……"的具体做法，用量化数据替代形容词（如"大幅提升"→"响应时间从 800ms 降至 120ms"）；做"删段测试"——删掉任一自然段后论文依然成立，该段即为套话，必须重写

## Phase 0：项目准备与素材库建设

> 此阶段为**考前准备**。考试当天直接调用素材库，无需现场构思项目。解决方案必须依托实际项目，脱离项目则所有论证失去立足点。

### 先确认报考资格

不同资格的论文考查视角与项目类型不同，准备素材前先确认报考科目：

- **架构 / 系分** → 选技术类项目，参考 `references/project-examples-arch.md`
- **信管** → 选管理类项目，参考 `references/project-examples-pm.md`
- **网规** → 选网络类项目，参考 `references/project-examples-ne.md`
- **系规** → 选 IT 服务/运维类项目，参考 `references/project-preparation.md` 通用指导并侧重服务管理

### 项目选择

| 条件 | 说明 |
|------|------|
| **熟悉度** | 优先选择自己亲身参与或非常熟悉的项目，能提供真实、详细的案例分析 |
| **时效性** | 优先选择最近两三年内的项目，确保反映当前技术趋势 |
| **符合潮流** | 体现数字化转型、智能化升级、AI应用、大数据、5G、区块链等方向 |
| **复杂度** | 具备业务复杂度（多角色协作/多样性/变更频繁）和技术复杂度（服务治理/质量属性权衡） |

避免选择：小型系统 ❌ 过时技术项目 ❌ 纯硬件项目 ❌ 纯技术项目 ❌

### 项目准备

确定项目后，收集项目文档（需求/设计/测试/用户反馈/故障报告），并梳理以下核心素材：

**项目背景**：项目名称、发起方/承建方、建设目的、我的角色（架构师）、起止时间与里程碑、建设内容、业务/应用/数据/技术架构、项目成果、关键数据指标（用户量/QPS/响应时间等）

**难点与挑战**（最能体现专业能力）：
- 业务难点：流程复杂、跨部门协作、需求变更管理、业务创新
- 技术难点：选型权衡、性能优化（高并发/大数据量）、安全保障、系统集成、技术创新

> 难点不要求是"世界级难题"，只要是"现状与期望目标之间的矛盾"即可。

### 建立素材库

以有限的素材应对无限的考察范围——**以少胜多、以不变应万变**：

1. 选择 **3-7 个核心业务场景**，不管遇到什么主题都写这些业务场景
2. 针对每个场景，按软件工程生命周期梳理：各阶段任务 → 问题挑战 → 解决手段 → 实施效果 → 得失总结
3. 按**金字塔原理 + SCQA 结构**组织，用 **5W2H** 补充细节增强真实性
4. 按**论文七问**预埋答案：Q1 项目与职责、Q2 选型理由、Q3 架构组成与约束、Q4 实践做法、Q5 踩坑经历、Q6 效果数据——考试时直接取用

读取 `references/project-preparation.md` 获取素材库示例及详细指导。

## Phase 1：分析论文试题

> 考试当天第一步，拿到试题后**必须先分析再动笔**。

### 逐题精读，圈出要点

走题是最常见的致命问题。**不要看到熟悉主题就默写准备好的论文**，必须：

1. **逐一阅读每个子问题**，特别是第二个子问题
2. **圈出每个要点**，写作时一定不能遗漏任何一个要点
3. **以试题的子问题为论文的核心段落/部分**

### 分析要点

- 同一主题，问题不同则考查侧重点完全不同
- 第二个子问题通常是理论+实践的核心考查点，**必须每个要点都回答到位**，避免不必要的丢分
- 将试题问题映射到素材库中的素材，确定使用哪些业务场景来支撑论述

## Phase 2：撰写提纲

> 很多人跳过这一步，结果写着写着思维混乱、结构松散，不得不返工重写。**提纲让写作变成"填空题"**。

### 提纲的作用

1. **明确论文结构**：预先设计整体结构，确保各部分清晰、重点突出
2. **梳理逻辑链条**：论点之间的逻辑关系环环相扣，避免跳跃或断裂
3. **提高写作效率**：按提纲逐一展开，不必反复思考"下一步该写什么"
4. **避免遗漏要点**：确保试题中的每个要点都得到回应

### 推荐提纲模板

读取 `references/outline-template.md` 获取完整提纲模板及填写指导。

核心结构概览：

```
## 摘要
项目时间 + 发起方 + 建设方 + 项目名称 + 角色和职责
+ 项目建设内容（概括）+ 中心论点（概括）+ 方案效果 + 项目成果

## 正文

### 项目背景
项目时间 + 发起方 + 建设方 + 项目名称 + 角色和职责
+ 项目建设内容（详细）+ 技术架构（详细）

### {与主题相关的标题}
1. 通过SCQA，引出论文主题
2. 回答子题目2中的理论问题：{要点1} {要点2} {要点3}
3. 简要概括中心论点：我们在项目中是如何做的？

### 分论点1
S： / C： / Q： / A：
举的例子：例子1

### 分论点2
S： / C： / Q： / A：
举的例子：例子2

### 分论点3
S： / C： / Q： / A：
举的例子：例子3

### 总结与感悟
1. 概括解决方案取得的效果
2. 概括项目取得的成果
3. 项目成功交付上线
4. 不足与改进 / 对主题的深刻理解（专业权衡、敬畏之心、沟通技巧等）
5. 未来展望
```

**论文七问与提纲结构的对应关系**：列提纲时即确认每问落在哪个段落，避免写完才发现遗漏：

| 论文部分 | 回答的七问 |
|---------|-----------|
| 摘要 | Q1、Q4、Q6 的浓缩 |
| 项目背景 | Q1 |
| {与主题相关的标题}（理论部分） | Q2、Q3 |
| 分论点 1-3 | Q4、Q5（各选一个实践点展开） |
| 总结与感悟 | Q6 + 反思 |

## Phase 3：摘要撰写

### 核心要求

| 要求 | 标准 |
|------|------|
| 字数 | 300-400 字（不少于 120 字，否则直接不及格；少于 300 字扣 5-10 分） |
| 内容 | 概括正文全貌，含实质性内容，不要只谈大道理 |
| 帽子 | 一般不加"帽子"性语句；字数不够时可加 50 字左右 |

### 摘要模板

读取 `references/abstract-templates.md` 获取 4 种摘要模板及示例。选择与项目素材最匹配的模板，填充具体内容。

### 写作顺序建议

- **写作速度快的考生**：先写正文，后写摘要——正文正常发挥，摘要水到渠成。风险：时间不够则无摘要，损失大。
- **写作速度慢的考生**：先写摘要，后写正文——摘要指导正文方向。风险：可能限制正文发挥。

> 注意：正文不是摘要的延伸，而是摘要的扩展。摘要不是正文的部分，而是正文的抽象。不要把正文"接"着摘要写。

---

## Phase 4：正文撰写（填充内容）

### 正文字数要求

目标 2500-3000 字，不少于 2000 字（显得无内容），不超过 4000 字（时间不够写不完）。

正文完成后，直接对文本计算字数：提取"一、×××"到"结束语/总结"之间的内容，统计中文字符数（`len([c for c in body if '\u4e00' <= c <= '\u9fff'])`），目标 2500-3000 字。

### 内容填充方法

按照提纲逐部分填充，运用以下三个框架：

- **金字塔原理**：结论先行，以上统下，归类分组，逻辑递进
- **SCQA 框架**：Situation（情境）→ Complication（冲突）→ Question（问题）→ Answer（回答）——每个分论点的基本结构
- **5W2H**：Who、What、When、Where、Why、How、How much——补充必要细节，增强真实性

同时以**论文七问**为正文主线串联：背景交代 Q1 → 选型论证 Q2 → 架构描述 Q3 → 实践展开 Q4 → 困难反思 Q5 → 效果收尾 Q6。Q2、Q3 撑起"应用深度与水平"分，Q4-Q6 撑起"实践性"分，缺一问即按对应维度扣分。

### 六大写作原则

六大写作原则的详细解释、示例对比和进阶技巧，请读取 `references/writing-principles.md`。

核心要点摘要：

1. **以自我为中心**：论文考核的是"我"做了什么，必须清楚说明由来、问题、解决方法和效果
2. **站在对应资格的专业视角**：架构/系分→架构或分析视角，信管→项目经理视角，网规→网络规划视角，系规→服务管理视角
3. **忠实于论点**：仔细阅读试题，绝对服从论点，不节外生枝
4. **条理清晰，开门见山**：迅速列提纲，项目概述精练，每段不超过 8 行
5. **标新立异，要有主见**：要有自己的见解，让阅卷专家有耳目一新的感觉
6. **表达书面化，段落转承自然**：使用规范书面语，善用过渡句

### 技术深度要求

选择 **5-6 个**有特色的技术/方法进行深入展开，以便考试时根据时间和篇幅动态删减至 2-3 个最终呈现。每个措施要：
- 紧密结合主题项目
- 以主题项目中的具体内容为例
- 说明"如何做的"而非"是什么"

> 实践部分重点描述理论知识要点在项目中的应用，而不是介绍项目本身功能。

### 交付说明

每次生成论文正文后，按字数统计方法计算正文字数并向用户展示。同时提醒用户：

> **考试论文正文在 2500 字左右即可。在实际誊抄时，对论点进行适当精简，重点说明 2~3 个分论点即可，不必全部堆砌。**

## Phase 5：检查校对

完成初稿后，逐项检查。这是确保文章质量的关键一步，不可因时间紧迫而忽略。读取 `references/common-issues.md` 获取完整 17 项通用检查清单及每条问题的修正建议，并按报考资格补充该资格特有检查项：

- 架构 → 通用 17 项即可
- 信管 → 通用 17 项 + PMBOK 过程域覆盖检查
- 系分 → 通用 17 项 + 建模完整性检查
- 网规 → 通用 17 项 + 网络方案可行性检查
- 系规 → 通用 17 项 + ITIL 流程覆盖检查

按字数统计方法确认字数达标。

同时逐问核对**论文七问**：每问是否都有明确答案、是否依托项目实际？任何一问缺失或空谈理论，都按对应评分维度（应用深度/实践性）扣分——特别是 Q2 选型论证与 Q5 踩坑反思最易被跳过，需重点检查。

再按 **Q7 红线**通读全文：是否存在空话套话段落（大段背书式理论、万能句式、无项目专属细节）？做"删段测试"——删掉任一自然段后论文若依然成立，该段即为套话，必须重写为具体做法 + 数据。

检查完成后，可调用 **ruankao-essay-scoring** 技能对论文进行逐维度评分，获取量化反馈与提分建议。

## 常见错误

| 错误 | 问题 | 解决 |
|------|------|------|
| 走题（最致命） | 看到熟悉主题就默写准备好的论文，忽略试题子问题 | 严格按 Phase 1 分析试题 → 以试题子问题为论文核心段落 → 写完逐段核对 |
| 摘要字数不足或缺失 | 摘要少于 120 字直接不及格 | 按 Phase 3 确保 300-400 字，包含实质性内容（项目背景+中心论点+方案效果） |
| 正文脱离"我"的视角 | 大段罗列课本理论，没有体现"我"做了什么 | 每个技术措施说明"我在项目中如何做"，避免连续 3 句无"我/我们" |
| 技术深度不足 | 只介绍技术是什么，没说如何结合项目使用 | 每个技术点按"引入背景→具体做法→实施效果"三步走，用项目数据支撑 |
| 段落过长或结构混乱 | 单段落超过 8 行，段落间缺乏逻辑衔接 | 每段 ≤ 8 行，段首点明主旨，善用过渡句（"然而""在此基础上""综上所述"）|
| 口语化表达 | 使用"然后""所以说"等口语化连接词 | 使用完整句式，名词化结构替代动词短语，避免感叹号/省略号 |
| 遗漏子问题 | 试题有 3 个子问题，只回答了 2 个 | 提纲阶段将子问题→段落映射，写完逐条核对 |
| 论文七问未答全 | 缺选型论证（Q2）、缺踩坑反思（Q5）、缺效果数据（Q6）等 | 按"论文七问"逐项核对，缺一问补一问，每问都要依托项目实际 |
| 空话套话、纯理论 | 大段背书式理论、万能句式、无项目专属细节 | 每段理论后紧跟"我在项目中……"的具体做法与量化数据，做"删段测试"排查套话 |

## 故障排查

| 问题 | 检查项 | 解决方案 |
|------|--------|---------|
| 生成的论文走题 | 是否按 Phase 1 分析试题？ | 重新分析试题子问题，调整提纲，确保每段都回应子问题 |
| 论文字数不足 | 是否按字数统计方法计算？ | 补充项目背景细节、技术实施过程、效果数据；目标 2500-3000 字 |
| 论文缺乏技术深度 | 是否深入展开 2-3 个技术点？ | 按"引入背景→具体做法→实施效果"补充每个技术点的细节 |
| 摘要字数不够 | 摘要是否达到 300 字？ | 按 `references/abstract-templates.md` 中的模板补充实质性内容 |
| 口语化严重 | 是否有"然后""所以"等词？ | 按 Phase 4"表达书面化"要求，将口语化表达改为书面语 |
| 段落过长 | 是否有超过 8 行的段落？ | 拆分长段落，每段只讲一个分论点 |
| 缺乏"我"的视角 | 是否大段介绍技术/项目？ | 在每个技术措施前加上"我..."的主体表述 |
| 素材库不知如何建 | 是否读了 `references/project-preparation.md`？ | 按该文件指导，选择 3-7 个核心业务场景建立素材 |
