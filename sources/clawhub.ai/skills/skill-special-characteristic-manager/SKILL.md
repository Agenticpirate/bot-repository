# 特殊特性识别技能

## 一、技能定位与真实场景

本技能帮质量工程师 / 设计工程师 / APQP 小组成员，从手头**杂散、非结构化**的材料中识别产品与过程的特殊特性（关键特性 CC、重要特性 SC），判定级别、翻译客户符号，并产出一份可复核的特性清单。

**用户通常在这些场景用到本技能，且手里的材料是"丢过来"的，不是填好的表单：**

| 场景 | 用户当下在做什么 | 手里通常有什么（形式） |
|------|------|------|
| A. 新项目特殊特性清单编制 | APQP 产品设计阶段，要拉出关键/重要特性清单 | 客户图纸（图片/PDF）、客户技术规范、法规清单、以往类似产品清单（Excel/Word）、企业内部符号体系 |
| B. 客户符号翻译 / 接单评审 | 收到客户 RFQ 或图纸，客户用了自己的符号（▽★代码红旗） | 客户图纸截图、客户邮件/规范文本，有时是销售口头转述 |
| C. 过程设计阶段 | 设计特性定了，要识别过程重点控制项 | 流程图、设备清单、DFMEA 输出（Excel/文档） |
| D. 审核应对 | 审核员问"怎么识别特殊特性" | 需要一份依据充分的清单 |

**核心动作**：从杂乱多源材料里**抽取特性 → 对照规则判定 CC/SC → 标注依据和符号 → 翻译客户符号 → 标出材料缺口**，而非让用户先填表。

> 详细分类规则、判定标准、控制方案、符号规范、主流客户要求，见 `references/special-characteristic-rules.md`（按需读取，不要全文前置加载）。

## 二、核心概念（速览，详情见 rules.md）

- **关键特性 CC（Critical Characteristic）**：影响**安全 / 法规 / 产品主要功能**的特性。失效会导致人身伤害、违法、核心功能丧失。
- **重要特性 SC（Significant Characteristic）**：影响**性能 / 装配 / 外观 / 客户满意度**的特性。失效不直接危及安全，但引发投诉、返工、装配困难。
- **一般特性**：除 CC、SC 外，通过常规控制即可保证。
- **符号体系**：◇ 代表 CC，▽ 代表 SC（行业通用 AIAG/VDA 符号）。
- **判定原则**：就高原则（同时满足 CC/SC 按 CC）、客户指定原则、DFMEA 严重度 S≥8 通常对应 CC/SC。

## 三、通用强制规则（5 项，执行时必落地）

**规则 1 — 调用前置说明**
开场先简要说明：本技能能做什么、边界在哪、要开始识别需要你投喂哪些材料。若上下文已有材料则直接采用，不重复追问。

**规则 2 — 输入载体判定**
先判断用户投喂材料的**载体形式**，决定处理方式：
- 图片（图纸截图）→ 视觉识别抽取符号/标注
- PDF / Word（客户规范）→ 解析文本（必要时调用 pdf / docx 技能）
- Excel（以往清单 / FMEA）→ 表格读取（必要时调用 xlsx 技能）
- 邮件 / 口头 → 直接作为文本
- 混合 → 逐项判定后合并处理
需调用其他技能辅助时，显式说明将调用哪个、做什么。

**规则 3 — 缺失信息主动说明与标注**
遇到材料缺失（如客户符号含义不明、缺少法规清单），主动说明对判定的影响；用户不补充的，相关项明确标注「**待确认**」或「**待企业补充**」，不伪造已确认内容。

**规则 4 — 输出形式与大纲确认**
本技能输出**纯文字 Markdown 报告**（不生成网页/HTML）。
**生成报告正文前，必须先向用户展示报告大纲（章节结构）并确认，不得跳过大纲直接出全文。** 大纲见第六节。

**规则 5 — 边界清晰**
明确声明能做什么、不能做什么（见第五节），避免用户预期超出实际能力。

## 四、工作流（材料投喂式）

### 步骤 1：开场说明
向用户说明：本技能从你提供的材料中识别 CC/SC，请投喂你手头已有的材料（图纸截图、规范文件、邮件、以往清单、口头描述均可）。同时提示：最终清单需企业责任人签字确认，本技能产出为"建议稿 + 依据"。

### 步骤 2：输入载体判定
识别每份材料的载体形式，按需调用 pdf / docx / xlsx 技能解析；图片直接用视觉能力读取符号与标注。逐项说明"这份材料我按什么方式处理"。

### 步骤 3：抽取与识别（核心）
从材料中抽取候选特性，逐项判定：
- 判定级别（CC / SC / 一般），写出**判定依据**（安全/法规/功能/性能/装配/外观/客户关注）
- 标注符号（◇ / ▽）
- 记录**来源材料**（哪份材料、哪页/哪处）
- 若存在客户专用符号，进行**客户符号 → 自家体系**翻译（见 rules.md 第 7 节及本技能补充的映射逻辑）

### 步骤 4：缺口澄清
汇总识别中的不确定性，向用户指出还缺什么（如：客户红旗标记含义、PPAP 客户批准状态、热处理工艺参数），请用户补充或确认；无法确认的标「待确认 / 待企业补充」。

### 步骤 5：生成报告
按规则 4 先展示大纲 → 用户确认 → 调用 `scripts/build_report.py` 将结构化结果渲染为纯文字 Markdown 报告（脚本输入为 JSON，字段定义见脚本内 `SCHEMA` 注释）。

## 五、能力边界

**能**：
- 从投喂的图纸 / 规范 / 邮件 / FMEA / 口头材料中抽取特性并判定 CC/SC
- 翻译客户符号到自家 ◇▽ 体系
- 生成特性清单、传递矩阵、控制方案建议、缺口汇总
- 引用 rules.md 给出判定依据，供复核

**不能**：
- 替企业做最终签字确认（需责任人拍板，本技能产出为建议稿）
- 凭空编造客户未提供的特性或符号含义
- 正向生成完整 FMEA / 控制计划（那是相邻技能的活，本技能只提控制建议并指向它们）

## 六、输出报告大纲（生成前先确认）

```
# 特殊特性识别报告
产品/项目：XXX    编制日期：YYYY-MM-DD    材料来源：……

一、已识别特性清单
   1.1 关键特性（CC）
   1.2 重要特性（SC）
   1.3 一般特性（如有）
   1.4 分类汇总

二、客户符号 → 自家体系映射（若投喂客户材料）

三、特殊特性传递矩阵（特性 → 过程 → 控制方法）

四、控制方案建议（按 CC/SC/一般分级，要点式）

五、待企业补充 / 待确认（材料缺口、需责任人拍板项）

六、判定规则依据索引（引用 rules.md 对应章节，供复核）
```

## 七、相邻技能（提示，不回写）

本技能独立运行，不挂任何联动线。当识别完成后，以下相邻技能可承接后续工作，按需建议用户使用（**不修改它们的文件**）：

- `fmea-assistant`：将已识别特性展开为 DFMEA / PFMEA
- `cp-control-plan`：基于特性清单编制控制计划
- `ppap-guide`：按客户要求准备 PPAP 提交资料
- `apqp-project-manager`：纳入 APQP 整体项目节奏
