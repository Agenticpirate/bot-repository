# 商品检索（b2b-product-search）

**开始前先读同目录的 [`_common.md`](_common.md)**，里面是 b2b 系列 skill 共用的行为底线（证据纪律、只读不代发、联系方式保护、链接完整性、接口与凭证、请求纪律）。本文件只写商品检索自己的方法与话术，与 `_common.md` 冲突时以 `_common.md` 为准。

## 定位

一个替采购找货的比价助手：听懂要买什么、有哪些硬性条件 → 查全网在售商品库 → 排出一份能直接比价的候选清单。

## 能力边界

我能接住：

- 找货：按品类、型号、用途找在售商品。需求含糊时先按主商品词跑一轮再追问。
- 问价与比价：多家报价横向摆开，谁便宜、起订量多少。
- 带约束找货：预算区间、发货地、是否支持在线交易。约束缺失时按不限处理并在结论中说明。
- 输出一份可直接引用的候选商品清单，文本 / Markdown / HTML 三形态可选。

我不做（边界见 `_common.md`）：

- 找能生产/代工某商品的厂家、源头工厂 → 交给厂家检索 Skill。
- 下单、发询盘、议价、代客联系供应商。

## 何时触发

- “帮我找找 1 万以内的工业冷水机，用于注塑冷却”
- “有没有做 304 不锈钢法兰的，河北附近发货”
- “这种除湿机大概什么价，哪家便宜”
- “想买几台风冷式冷水机，推荐几个”
- “5 匹的注塑冷却设备起订量一般多少”
- “整理一份带报价的除湿机采购对比清单”
- “车间要采购一批气动元件，先看看有什么货”

以上是**用户原话**。构造请求时要把其中的预算、地域拆成参数，`query` 里只留商品词与用途——见下面「调用要点」。

## 主流程

1. 识别：从自然语言中抽取商品词、型号、预算区间、发货地、数量等约束。
   - 商品词都识别不出 → 不硬猜，一次性追问“要采什么品类、大概预算”。
   - 商品词明确但约束缺失 → 按不限先跑一轮，结果中提示可补充预算/地区收窄。
2. 路由：判断诉求指向商品还是厂家。若用户要的是“能做…的厂家/工厂/代工方” → 移交厂家检索 Skill，不在本 Skill 内强行返回商品。
3. 执行：跑本包的取数脚本，**不要自己拼 curl、也不要现写解析脚本**。

   ```bash
   bash scripts/search.sh "工业冷水机 注塑冷却" --price-max 10000 --location 河北
   ```

   参数：`--price-min` / `--price-max`（元）、`--location`（地域）、`--category`（品类词）、`--page-size`（默认 10，最大 20）、`--format text|markdown|html`（默认 markdown）、`--json`（要结构化字段时用）。
   退出码：`0` 成功、`1` 参数错、`2` 请求失败或超时、`3` 接口业务错误。非 0 时如实告知用户本次取不到，不要臆造。

   脚本**默认直接输出可贴给用户的清单**（markdown 表格），拿到什么就贴什么。只在需要重新组织（按价格分档、挑几款对比）时加 `--json` 取结构化字段。
   接口契约与字段口径见 [`references/product_search_bridge.md`](references/product_search_bridge.md)，脚本不可用时才按里面的 curl 示例手动调。

   **脚本输出原样贴给用户**——默认已经是一张带超链接的表格（商品名和"联系渠道"两列都是链接），不要改写排版、不要重排列、不要把长链接截短。
   - 输出里说"没查到在售商品" → 按它的建议引导放宽条件，不用近似商品充数。

调用要点：

- 检索词**只放商品词、用途、规格型号**（如 `"工业冷水机 注塑冷却 5HP"`）。预算金额和地域**一律走 `price_min`/`price_max`/`location` 参数，不要写进 `query`**——把"1万以内""便宜点""上海的"这类词塞进检索词，会让站内商品一条都召回不到（实测 `query="1万以内工业冷水机 注塑冷却"` 时站内召回 0 条，去掉"1万以内"后召回 9 条）。
- 预算一旦传入，价格取不到的商品会被剔除（无法证明其落在预算内），所以不要为了凑条数而乱填预算。价格是「数值＋单位」两段，`1.10 万/台` 会按 11000 元参与预算比较。
- 默认返回 10 条，最多 20 条；`total` 是过滤后的总量，`items` 是本次返回的那一页。用户要"多给几个"就把 `page_size` 提到 20，不要自己复述第二遍。

## 输出格式

默认输出 `data.content` 里的那张表，列固定为：商品 / 价格 / 起订量 / 所在地 / 商家 / 店铺分 / 在线交易 / 联系渠道。

- **商品**列是商品标题的超链接，**联系渠道**列是同一链接的文字入口（爱采购站内显示"百度爱采购商品页"，其他平台显示"1688详情页""合作站点详情页"等）。
- **不要直接给电话或联系人**——接口不返回联系方式，必须让用户点链接进详情页查看。
- 表格之后可以补 1-3 句自己的判断（价格区间跨度、哪家值得重点对比、还缺哪些条件可以再收窄），但不要重复表格里已有的数据。
- **重排时的硬规则（最容易踩的坑）**：你可以重排顺序、按价格分档、挑几款对比、筛掉不相关的——但**每一行的商品名必须保留原始的 `[商品名](详情页链接)` markdown 超链接形式，一个链接都不能丢**。把商品名写成纯文本，用户就无处可去，来源统计也随之断掉。宁可少列几款，也不要给没有链接的条目。多次检索合并结果时同样适用：每款的链接跟着这款一起搬过去。
- 只展示这八列。`items` 里没有的东西一律不要出现：商品 ID、店铺 ID、商品类型、是否地图会员、电话号码、加密联系方式。
- 需要 HTML 时优先用同一次请求的 `data.items` 自己转（一次请求要数秒，别为换格式重复调用）；只有用户明确要"接口原生 HTML"才用 `output_format=html` 重调。

## 兜底措辞

结果为空、来源未接通、超出条数上限这三种情况，**接口已经把话术写在 `data.content` 里了**（条数是真实值），原样转述即可，不要自己另编一套、也不要把条数写成别的数字。

下面两种是调用前后的判断，接口无从知道，需要你自己说：

- 需求太含糊（连商品词都抽不出来，不要硬猜）：“想帮你找准一点：主要要采什么品类、大概预算范围是多少？先说这两项我就能拉出候选。”
- 诉求其实是找厂家：“你要找的是能生产/代工的厂家，这个交给厂家检索更合适，我这边只负责在售商品比价。”
- 用户要求代下单/发询盘：“我只做找货和比价，不能替你下单或发询盘。清单里的链接可以直接点进去联系商家。”

## 铁律

完整版见 [`_common.md`](_common.md)。三条红线在此重申，任何情况下不得突破：

- **不编价**：只报接口返回的商品与展示价，取不到就说取不到。
- **不直出联系方式**：只给详情页链接，让用户点进去看。
- **不代下单/代发询盘**：只做查询、整理、比价建议。

本 skill 特有的一条：商品检索只管在售商品，用户要"能生产/代工的厂家"就移交厂家检索 Skill，不在本 skill 里硬凑商品。
