# 纸质票据 vs APP 截图 分类归档规范（脱敏版）

> 适用范围：个人 Obsidian 档案库 / 文档管理系统中的「票据凭证、纸质资料、说明书、交易记录」归档。
> 目标：把「收起来就找不到」变成「永远能秒搜」，同时避免把无价值的截图误归档。
> 脱敏说明：本文档只记录通用规则，不包含任何具体金额、账号、机构名、人名。

---

## 一、核心判断标准（先判断再处理）

**1. 手机翻拍的纸质票据**
- 判定：该文件**没有上电子系统 / APP 里查不到**
- 处理：**通常保存价值最大 → 归档 + OCR 落盘可搜**
- ⚠️ **例外（无保存价值，不归档）**：餐饮报销类翻拍等「报销完即弃、金额已登账」的场景

**2. APP 截图**
- 判定：内容**在 APP 内可找回**（除有时限的之外）
- 处理：**默认不存档**（数据已登记进台账/账本即可）
- 但以下 4 类**关键里程碑**必须保留：
  1. 补贴/优惠/权益**申请成功**的截图
  2. **查询时间**相关的截图
  3. **有价值**的内容
  4. **将来一次性在 APP 里找不到**的内容

**3. 车辆专项（名爵/宝马等）**
- 网约车交易单据、里程、APP 电池/续航截图 = **数据登记**（登台账，不归档）
- 购车合同、发票、保单、过户资料 = **票据档案**（归档 + OCR）

**4. 永久保存凭证（禁止清理）**
- **车牌额度**截屏/凭证、办结凭证、有效期查询等 → **永久保存 + OCR 落盘**
- 此类无论翻拍纸质还是 APP 截图，一律永久保留，**不适用「APP 截图不存档」规则**

---

## 二、兜底原则

- **不确定**的截图/资料 → **一律先入暂存区**（只移动、不删除、不擅自归档）
- 定期（例如每两周）做一次**专项核对**，由用户二次确认「归档 / 登记 / 删除 / 继续留」

---

## 三、OCR 落盘流程（让扫描件可全文搜索）

### 引擎选择（优先级）
1. **系统原生 OCR**（macOS Vision framework / 系统级 OCR）——免费、中文支持好、本地运行不耗 token
   - 注意：很多本地 OCR 脚本通过「快捷指令」调用会失败（找不到动作），**直接用框架级 API 最可靠**
2. 本地 VL 小模型——可用但识别质量偏低，仅兜底
3. 云端——仅在必要时，注意 token 成本

### 批量处理
- 遍历归档目录下的 `.jpg/.jpeg/.png/.bmp/.tif`（直接 OCR）和 `.pdf`（先渲染每页为图片再 OCR）
- 为每个扫描件生成**同名 `.ocr.md`**，包含：
  - frontmatter：`source`（源文件名）、`ocr_date`、`ocr_method`、`type`、`date`、`counterparty`、`keywords`
  - 正文：OCR 全文（放入代码块）
- **幂等**：已存在 `.ocr.md` 的文件跳过（可 `--force` 重跑）

### 定期维护
- 每日/定期增量扫描，新文件自动补 OCR（脚本幂等，不会重复处理）

---

## 四、时间线索引（交易/票据按时间组织）

- 从**文件名**自动提取日期（支持 `YYYY-MM-DD`、`YYYYMMDD`、`YYYY年MM月DD日` 等格式）
- 从**文件名 + OCR 文本**识别：
  - `counterparty`（往来方：机构/商户名，用关键词表匹配）
  - `type`（发票/合同/保单/凭证/说明书/证书/黄金票据/补贴/税…用关键词表匹配）
- 为每个归档目录生成**「时间线索引.md」**：按日期排序，列出 日期/类型/往来方/源文件
- 该索引可自动重跑刷新；人工修正 frontmatter 后重跑即更新

---

## 五、目录分类（参考）

**A 类 · 纸质档案（OCR 落盘可搜）**：票据凭证 / 纸质资料备份 / 设备说明书 / 黄金交易记录档案 / 交易记录
**B 类 · 数据登记（不归档）**：账户余额、里程、电量、交易单金额等数据类截图 → 只 OCR 抓值登记台账
**C 类 · 永久保存**：车牌额度等凭证（见一·4），禁止清理

---

## 六、校验与运维

- 每次批量处理 / 登记后 **read-back 验证**（重新读取确认文件未损坏、格式正确）
- 涉及金额/账号的登记：**先反算核验**（明细加总 = 总额），不凭印象
- 判定归属必须**依据特征**（OCR 内容、文件来源），禁止凭外观/量级猜测
- 功能失败超过 3 次停止并汇报，不无限重试
