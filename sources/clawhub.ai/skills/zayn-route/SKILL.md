# ROUTE() Skill 路由与编排

## 1. 基本信息

```text
Skill ID: zayn-route
Display Name: zayn-route
Chinese Name: Skill 路由与编排
Project: WorkFn
Author Prefix: zayn
Category: Skill Orchestration
Version: 0.1.7
Status: Draft for testing
```

## 2. 解决的问题

ROUTE() 用于解决以下问题：

1. 用户遇到复杂问题，不知道先调用哪个 Skill
2. 一个问题可能需要多个 Skill 串联
3. 前一个 Skill 的结果没有被正确传给下一个 Skill
4. Skill 调用顺序错误
5. 信息不足时仍然继续后续分析
6. 多个 Skill 重复分析同一问题
7. 最终输出 Skill 不明确
8. 路由过程越来越复杂，重新变成万能工具

## 3. 适用场景

适用于：

1. 用户的问题涉及多个阶段
2. 需要先理解再澄清
3. 需要先判断再报价
4. 需要先分析客诉再判断责任
5. 需要先检查订单再启动交付
6. 需要先梳理重点再汇报或决策
7. 用户不确定应该调用哪个 Skill
8. 需要明确 Skill 调用链和停止条件
9. 需要在日报、周报、月报、年中报告、年度报告之间选择正确的汇报 Skill
10. 需要在跨部门协同、内部请求、问题升级、领导决策和最终上级沟通之间选择正确路径
11. 需要在企业公开调查、合作风险、舆情、匹配度、竞争、市场研究和选品之间选择正确路径

## 4. 不适用场景

不适用于：

1. 一个明确 Skill 已足够解决的问题
2. 用户已经明确指定要调用的 Skill
3. 只需要执行简单翻译
4. 只需要普通总结
5. 需要 ROUTE() 自己完成全部业务分析
6. 需要自动执行所有 Skill
7. 需要创建复杂多 Agent 系统

## 5. 输入参数

### 必填参数

| 参数 | 说明 |
|---|---|
| user_problem | 用户当前遇到的问题 |
| desired_outcome | 用户最终希望得到什么 |
| available_context | 当前已有上下文和材料 |

### 建议参数

| 参数 | 说明 |
|---|---|
| current_stage | 当前处于理解、澄清、判断、决策、执行、沟通、跟踪或复盘阶段 |
| known_facts | 已确认事实 |
| missing_information | 已知缺失信息 |
| existing_outputs | 已经运行过的 Skill 结果 |
| constraints | 时间、权限、风险、数据和业务限制 |
| final_output_type | 最终希望得到回复、报价、汇报、方案、计划或纪要 |
| user_selected_skill | 用户已经指定的 Skill |
| available_skills | 当前项目已有 Skill 列表 |

## 6. 参数运行要求

正式路由前必须输出参数状态表。

参数状态只使用：

```text
已命中
部分命中
缺失
冲突
待验证
```

最低运行条件：

1. 用户问题基本明确
2. 最终目标基本明确
3. 当前已有上下文可识别
4. 能判断至少一个候选 Skill
5. 能识别是否需要停止补充信息

如果用户问题和最终目标都不明确，不得生成 Skill 调用链。

## 7. 问题类型识别

ROUTE() 必须先判断当前问题属于哪一种或哪几种类型：

1. 理解
2. 澄清
3. 判断
4. 决策
5. 执行
6. 沟通
7. 跟踪
8. 复盘
9. 研究

示例：

```text
客户原话看不懂
```

属于：

```text
理解
```

示例：

```text
客户需求不完整，需要确认配置
```

属于：

```text
澄清
```

示例：

```text
判断是否值得报价
```

属于：

```text
判断
```

示例：

```text
确定价格后生成报价
```

属于：

```text
执行
```

## 8. 单 Skill 优先原则

ROUTE() 必须先判断：

```text
一个 Skill 是否已经足够解决问题。
```

如果一个 Skill 足够，不得为了展示能力而增加调用链。

例如：

```text
帮我检查这份报价是否完整
```

只使用：

```text
QUOTE()
```

例如：

```text
帮我整理会议结论和责任人
```

只使用：

```text
MINUTES()
```

## 9. 多 Skill 调用原则

只有在以下情况下才使用多个 Skill：

1. 当前问题包含明显的前后阶段
2. 后一个 Skill 依赖前一个 Skill 的输出
3. 直接调用后一个 Skill 会缺少关键参数
4. 不同 Skill 之间职责明确
5. 每一步都有必要性
6. 调用链长度合理

第一版建议：

```text
最多推荐 5 个 Skill。
```

超过 5 个时，应重新检查是否过度设计。

## 10. Skill 调用链设计

调用链必须说明：

1. 顺序
2. Skill 名称
3. 作用
4. 所需输入
5. 产出
6. 产出传给哪个 Skill
7. 停止条件

统一格式：

| 顺序 | Skill | 作用 | 所需输入 | 关键输出 | 输出传给 | 停止条件 |
|---|---|---|---|---|---|---|

## 11. 参数传递规则

前一个 Skill 的输出传给下一个 Skill 时，必须：

1. 只传必要字段
2. 不原样传递整段长文本
3. 保留已确认事实
4. 保留待验证信息
5. 保留冲突
6. 不把推测升级为事实
7. 标明来源 Skill
8. 区分内部业务策略与对外可表达内容。`暂停跟进`、`降低投入`、`当前无成交空间`、`停止报价`等内部结论传给 `REPLY()` 时必须标记为内部策略，不得直接改写成客户话术
9. 同时传递需要保留的商业关系入口，例如未来价格变化、其他产品需求或补货机会；不得因此承诺一定找到更低价格或后续供应结果

例如，INTENT_DECODE() 输出：

```text
客户明确表达
客户核心关注点
可能意图
待确认事项
```

传给 CLARIFY() 时，只保留：

```text
已确认需求
待确认事项
不可过度推断的部分
```

## 12. 停止条件

ROUTE() 必须为每个调用链设置停止条件。

常见停止条件：

1. 关键参数缺失
2. 产品身份无法确认
3. 客户需求范围不明确
4. 责任状态无法确认
5. 价格、库存或交期未确认
6. 订单尚未确认
7. 用户目标发生变化
8. 当前证据不足
9. 后续 Skill 不具备最低运行条件
10. 企业主体或官方账号无法确认
11. 国家、司法辖区、市场、客户群或时间范围不明确
12. 关键结论只有单一低质量来源
13. 实时数据源不可访问且用户未提供资料

停止时必须明确说明：

1. 为什么停止
2. 缺什么
3. 应该补什么
4. 补充后从哪个 Skill 继续

## 13. 正式路由触发条件

只有同时满足以下条件，才生成完整 Skill 调用链：

1. 用户问题明确
2. 最终目标明确
3. 至少一个候选 Skill 明确
4. 关键输入可识别
5. Skill 之间有真实依赖
6. 调用链没有明显重复
7. 已设置停止条件

## 14. 输出结构

ROUTE() 必须按以下结构输出：

### A. 参数完整度结论

只使用：

```text
可直接路由
需要补充关键参数
当前只适合单 Skill
存在冲突，暂不建议继续
```

### B. 参数状态表

列出：

1. 用户问题
2. 最终目标
3. 当前阶段
4. 已有材料
5. 已有 Skill 输出
6. 限制条件

### C. 问题识别

```text
当前问题类型：
核心目标：
当前阶段：
```

### D. 单 Skill 或多 Skill 判断

明确说明：

1. 一个 Skill 是否足够
2. 为什么
3. 是否需要调用链

### E. 推荐 Skill 链

使用统一表格。

### F. 当前先执行哪一步

只给一个当前动作。

例如：

```text
先调用 INTENT_DECODE()
```

### G. 参数传递说明

明确哪些结果传给下一个 Skill。

### H. 停止条件

列出必须停止的情况。

### I. 最终输出 Skill

明确最终由哪个 Skill 生成结果。

## 15. 常见路由示例

### 示例一：客户表达不清，需要回复

```text
INTENT_DECODE()
↓
CLARIFY()
↓
REPLY()
```

### 示例二：陌生产品询价并报价

```text
PRODUCT_BRIEF()
↓
CLARIFY()
↓
RFQ()
↓
PRICE()
↓
QUOTE()
↓
REPLY()
```

### 示例三：客户压价

```text
INTENT_DECODE()
↓
PRICE()
↓
NEGOTIATE()
↓
REPLY()
```

### 示例四：客户投诉并要求退款

```text
COMPLAINT()
↓
RESPONSIBILITY()
↓
RMA()
↓
SOLUTION()
↓
REPLY()
```

### 示例五：订单确认后的交付

```text
ORDER()
↓
ORDER_KICKOFF()
↓
DELIVERY()
↓
MEETING()
↓
MINUTES()
```

### 示例六：复杂项目汇报

```text
KEYPOINT()
↓
REPORT()
↓
DECISION()
```

### 示例七：周期性工作汇报

如果用户已明确周期，优先直接路由到对应专项 Skill：

```text
DAILY_REPORT() / WEEKLY_REPORT() / MONTHLY_REPORT() / MIDYEAR_REPORT() / ANNUAL_REPORT()
```

如果用户只说“写个汇报”，但周期、对象或目的不明确，先使用：

```text
REPORT()
```

### 示例八：跨部门协同后对外回复

```text
CROSS_FUNCTIONAL_COLLABORATION()
↓
REPLY()
```

如果只是向内部某部门提出明确问题且无承诺、推责或风险判断，可直接使用：

```text
REQUEST()
```

### 示例九：向经理或老板沟通

如果用户需要把已整理的事实、建议或请求转化为面向直属主管、经理、部门负责人或老板的最终沟通内容，使用：

```text
UPWARD_COMMUNICATION()
```

需要先比较方案并请领导拍板时：

```text
DECISION()
↓
UPWARD_COMMUNICATION()
```

问题超出权限或存在重大风险时：

```text
ESCALATE()
↓
UPWARD_COMMUNICATION()
```

向平级同事或职能部门提出执行请求仍使用 `REQUEST()`；信息明确的请假、调休、工作安排和普通上级沟通可直接使用 `UPWARD_COMMUNICATION()`。

### 示例十：潜在客户公开调查与匹配

先确认公开主体和经营信号：

```text
COMPANY_RESEARCH()
↓
BUSINESS_RISK()
↓
SOCIAL_LISTENING()
↓
COMPANY_FIT()
```

只有需要继续判断业务投入时，才把匹配结果传给 `QUALIFY()`；优先级和客户策略属于后续阶段，不应一次性强行串联全部 Skill。内部询价、订单、付款和售后历史由 `CUSTOMER_PROFILE()` 提供，不让 `COMPANY_RESEARCH()` 重复处理。

### 示例十一：行业研究到选品

```text
MARKET_RESEARCH()
↓
COMPETITOR_ANALYSIS()
↓
PRODUCT_SELECTION()
```

只有候选产品已经形成且需要判断真实项目时，再进入 `OPPORTUNITY()`。如果用户只要求调查某个竞争对手，可直接使用 `COMPETITOR_ANALYSIS()`；如果只要求判断已有候选产品，可直接使用 `PRODUCT_SELECTION()`。

### 示例十二：商业情报停止条件

公司同名主体无法区分时，停在 `COMPANY_RESEARCH()`；司法辖区不明时，不进入 `BUSINESS_RISK()`；账户监测缺少上次检查时间时，`ACCOUNT_WATCH()` 只能执行基线或近期扫描，不得声称发现新增动态；市场地区、产品边界或时间范围不明时，停在 `MARKET_RESEARCH()` 补问；没有我方供应、资金和交付条件时，不进入正式 `PRODUCT_SELECTION()`。

### 示例十三：客户动态到对外跟进

已有明确客户主体、官方来源、我方业务背景和上次检查时间，需要判断新动态是否值得行动：

```text
ACCOUNT_WATCH()
↓
OPPORTUNITY()
↓
FOLLOWUP()
↓
REPLY()
```

如果只需要扫描、分类和保存账户动态，单独使用 `ACCOUNT_WATCH()`。只有出现明确项目、需求、预算、时间或采购角色线索时，才进入 `OPPORTUNITY()`；只有动作已经确定且用户要求最终表达时，才进入 `REPLY()`。招聘、参展、普通转发或节日内容不得直接触发完整调用链。

### 示例十四：价格倒挂后的判断与客户回复

当我方报价高于客户自己的销售价格，需要判断当前机会并生成客户回复：

```text
PRICE()
↓
QUALIFY()
↓
REPLY()
```

`PRICE()` 判断价格是否具备成交空间，`QUALIFY()` 决定继续、降低投入或暂停该报价。传给 `REPLY()` 时，将暂停、降级或退出标记为内部策略；对外只传递已确认的价格事实、沟通目标、不可承诺边界和需要保留的未来交易入口。除非用户明确决定退出、客户要求结束或继续沟通会产生误导，不得默认向客户宣布“停止项目”。

以上示例只是候选路径，不得无条件套用。

## 16. 风险检查

必须检查：

1. 是否推荐过多 Skill
2. 是否存在职责重复
3. 是否跳过参数检查
4. 是否缺少停止条件
5. 是否把一个简单问题复杂化
6. 是否让 ROUTE() 自己完成业务分析
7. 是否把推测继续传给下游
8. 是否忽略用户已指定的 Skill
9. 是否忽略已有 Skill 输出
10. 是否重复询问已经提供的信息
11. 是否在主体未确认时继续归因
12. 是否把“未找到”传成“不存在”
13. 是否将官网自述或匿名评论传成已确认事实
14. 是否把过期研究数据当作当前状态
15. 是否把内部的暂停、降级或退出判断直接传成客户话术
16. 是否为了保留关系而传递无法兑现的价格、货源或更新时间承诺

## 17. 禁止事项

ROUTE() 不得：

1. 自动执行全部 Skill
2. 直接完成所有业务分析
3. 为简单问题创建长调用链
4. 推荐超过 5 个 Skill，除非有明确必要
5. 跳过前置 Skill 的最低运行条件
6. 把前一个 Skill 的全部长文本传给下一个
7. 删除冲突信息
8. 把待验证信息写成确定事实
9. 强行使用所有现有 Skill
10. 覆盖用户指定的合理路径
11. 在关键信息不足时继续后续流程
12. 把路由器重新做成万能工具
13. 将内部策略和对外表达混为同一字段传给 `REPLY()`

## 18. 人工判断边界

1. 用户可以指定或修改路由
2. 用户可以跳过某个 Skill
3. 人工确认事实优先
4. ROUTE() 只能建议，不得强制执行
5. AI 不得修改原始材料
6. AI 不得覆盖已有人工判断
7. 所有自动传递内容必须可追溯到来源 Skill

## 19. 验收标准

一个合格的 ROUTE() 输出必须满足：

1. 能识别问题类型
2. 能判断一个 Skill 是否足够
3. 不为了展示能力增加 Skill
4. 调用顺序合理
5. 参数传递清楚
6. 每一步有明确作用
7. 有停止条件
8. 明确当前先做什么
9. 明确最终输出 Skill
10. 不直接代替业务 Skill
11. 不把问题复杂化
12. 不把待验证信息传成确定事实

## 21. 通用版与行业版选择

先判断用户材料是否包含行业专属证据，再选择 Skill：

1. 服务器、存储、内存、SSD、GPU、网络设备、笔记本配件、PN、固件或硬件兼容问题使用 `zayn-product-brief`；其他实体产品、数字产品或服务使用 `zayn-general-product-brief`。
2. 涉及硬件型号、PN、配置兼容、成色、序列号、保修、锁货或二手备件时，使用 `zayn-alternative`、`zayn-availability` 或 `zayn-condition`；其他行业分别使用对应的 `zayn-general-*`。
3. 涉及硬件工程确认、固件、测试、QC、标签序列号、包装和清关时使用 `zayn-order-kickoff`；普通产品、服务合同或项目启动使用 `zayn-general-order-kickoff`。
4. 涉及硬件序列号、测试、安装兼容、保修、维修、换货、退运检测或供应商退换窗口时，使用原硬件售后 Skill；一般产品、服务、订阅或项目问题使用对应的 `zayn-general-complaint`、`zayn-general-responsibility`、`zayn-general-rma` 或 `zayn-general-solution`。
5. 行业证据不足时默认使用通用版，不得仅因用户提到“产品”“库存”“退货”就触发硬件版。

## 22. 市场与商业情报选择

1. 调查企业公开主体、业务、团队、认证和经营信号，使用 `zayn-company-research`；历史询价、订单、付款和售后仍使用 `zayn-customer-profile`。
2. 调查诉讼、处罚、制裁、出口管制、信用和其他合作风险信号，使用 `zayn-business-risk`；主体或司法辖区不明确时停止。
3. 分析社媒、新闻、论坛、客户评论和员工评价，使用 `zayn-social-listening`；单条或匿名评论不得升级为整体结论。
4. 持续检查某一已确认账户相对历史状态的公开变化、判断信号和行动价值，使用 `zayn-account-watch`；无上次检查时间时只做基线或近期扫描。一次性企业背景调查仍使用 `zayn-company-research`，阶段性舆情分析仍使用 `zayn-social-listening`。
5. 已有公司、风险和业务资料，需要判断与我方能力是否匹配，使用 `zayn-company-fit`；是否值得继续投入由 `zayn-qualify` 判断。
6. 将具体竞争对手与我方比较，使用 `zayn-competitor-analysis`；调查单一企业基本信息时使用 `zayn-company-research`。
7. 研究行业、地区、客户、产业链、需求、供应、监管和竞争格局，使用 `zayn-market-research`。
8. 已有市场证据和候选产品，需要结合供应、资金、库存、利润、物流和售后能力判断进入机会，使用 `zayn-product-selection`。
9. `ACCOUNT_WATCH()` 只把已确认项目、需求、时间窗口、来源和信息缺口传给 `OPPORTUNITY()`；不要把招聘、参展或弱信号直接传成采购需求，也不要自行生成最终回复。
10. 市场情报调用中必须保留主体、来源、日期、事实/推断状态和信息缺口；不得因搜索不到而输出不存在或无风险。

## 23. AI 任务方案诊断选择

1. 用户准备创建 Skill、自动化、程序工具、模板、工作流或 AI 助手，但尚未确认实现方式时，先使用 `zayn-ai-task-diagnosis`。
2. `AI_TASK_DIAGNOSIS()` 通过目标、变化频率、数据证据和最终责任四问，判断应采用普通对话、Skill、定时或条件自动化、程序、模板、人工、人机协作或暂时不做。
3. 用户已经明确指定一个现有 Skill，或请求只是一次性、低风险且可直接完成的简单任务时，不增加 `AI_TASK_DIAGNOSIS()`。
4. 诊断结论为 WorkFn Skill 且任务涉及多个现有 Skill 时，再进入 `ROUTE()`；目标已确认但需要拆解执行步骤时使用 `PLAN()`；方案明显过度复杂时使用 `FOCUS()`。
5. 数据来源、触发条件、责任人或验收标准不清时，停在 `AI_TASK_DIAGNOSIS()` 补问，不得直接承诺自动化或程序开发。

## 24. 目标市场客户开发选择

1. 判断哪些国家、地区、行业或应用场景值得测试、重点开发或暂不进入，使用 `zayn-market-opportunity`。宏观市场结构与趋势研究仍使用 `zayn-market-research`。
2. 把目标市场和我方能力转成“要找哪类公司”的可搜索画像，使用 `zayn-target-customer-profile`。整理某个已有客户的历史事实仍使用 `zayn-customer-profile`。
3. 已有目标市场、产品或服务和客户画像，需要规划人工搜索关键词、渠道和顺序，使用 `zayn-search-strategy`；不得将其用于自动批量抓取。
4. 用户已人工提供候选公司名称、域名、链接、截图、Excel 或 CSV，需要去重、核验和筛选，使用 `zayn-company-screening`。单一企业深度公开调查仍使用 `zayn-company-research`。
5. 公司已被人工确认，且需要规划联系部门、岗位、查找路径与开发角度，使用 `zayn-contact-strategy`。最终客户消息由 `FOLLOWUP()`、`REPLY()` 或 `RELATION()` 生成。
6. 完整业务过程可参考 `MARKET_OPPORTUNITY() → TARGET_CUSTOMER_PROFILE() → SEARCH_STRATEGY() → 人工搜索 → COMPANY_SCREENING() → 人工确认 → CONTACT_STRATEGY()`，但 ROUTE() 每次只推荐当前阶段真正需要的 Skill，不跨越人工搜索或人工确认节点。
7. 未明确产品或服务、目标市场和我方供应能力时，不进入正式市场机会判断；没有候选公司材料时，不进入公司筛选；没有人工确认的公司和证据时，不进入联系策略。
8. 不自动批量搜索、不猜测邮箱、不自动发送外联、不自动写入作战池。

## 26. 参考作品复现前的技术诊断

1. 用户要求依据参考图、视频、网页演示、3D 展示或实体成品制作相似作品，但尚未确认生成机制时，先使用 `zayn-reference-tech-diagnosis`。
2. `REFERENCE_TECH_DIAGNOSIS()` 负责分离视觉表象与生成机制，识别资产来源，建立候选技术假设，比较还原路线，并设计能推翻错误路线的最小判别原型。
3. 用户已明确技术栈且关键机制已由原型验证，只要求普通代码修改、配色、排版或内容更新时，不增加本 Skill。
4. 参考材料不足以区分二维合成、2.5D、真实三维、模型表面采样或随机粒子时，停在 `REFERENCE_TECH_DIAGNOSIS()` 补充多角度、动态、源文件或交互证据，不直接进入完整制作。
5. 诊断结论为网页或程序实现后，再进入对应设计与开发 Skill；结论为视频、3D 建模、实体制造或其他路线时，转交相应专项能力。ROUTE() 只传递已确认机制、竞争假设、还原目标、推荐路线、原型通过标准和未知项，不传递未经验证的技术猜测。
6. 若用户限定的技术路线只能模仿氛围，却要求结构级或机制级还原，先明确冲突并由用户选择降低还原目标或更换路线。
7. 核心判别原型未通过时停止后续页面扩展、视觉微调、发布或制造，不得用反复调参掩盖结构机制错误。

## 25. NETWORKMAP 路由与边界

将 ROUTE() 保持为任务判断和衔接层，将 `$zayn-networkmap` 保持为独立的公开关系研究 Skill。不要在本 Skill 中复制其搜索方法、多语言检索词、证据等级、名单提取、去重流程或其他研究细节。

### 25.1 路由前判断

围绕以下五项判断任务：

1. 使用场景和用户真正要做的决定
2. 已有资料和可复用证据
3. 执行前必须完成的判断
4. 执行边界和停止条件
5. 最小可用输出

优先检查用户提供或已连接的成交、订单、付款、发货、售后、询价、报价、有效沟通、客户记录、人工备注、Obsidian 和 Excel。不得删除原始数据、覆盖人工判断、强行分类，或把疑似信息写成确定事实；新增内容单独输出。

### 25.2 调用条件

在以下任务中调用 `$zayn-networkmap`：

1. 根据行业查核心展会及近期参展公司
2. 根据行业查主要协会、组织及公开会员公司
3. 根据公司查近期参加的展会、会议、峰会、赞助或演讲活动
4. 根据活动查公开记录中的参展商、赞助商、演讲公司或其他参与公司
5. 用公开证据建立行业、展会、协会、活动与公司的关系

范围明确的直接关系研究可直接调用 `$zayn-networkmap`。完整销售开发、市场研究或客户筛选任务，先由 ROUTE() 确认业务目标与范围，再调用该 Skill；返回后再判断是否进入客户筛选、客户补全、开发策略或停止。

同场公司、协会会员和参展公司只作为发现线索。没有独立的产品匹配、真实业务证据、意向或近期动作时，不得将其判定为潜在客户或自动写入作战池。

### 25.3 公司跨行业消歧

公司可能涉及多个明显不同的行业时，依次依据本地真实业务记录与人工备注、公司官网业务及产品页面、公司官方新闻和活动记录、其他可信公开资料判断。不得仅凭公司名称、搜索摘要或模型常识确定行业。

如果行业选择会明显改变展会、协会、活动或同场公司结果，在展开名单研究前停止，并提供二至四个选项。每个选项说明行业名称、关联依据、包含范围和排除的相邻业务；推荐一个选项并说明理由，但由用户最终确认。确认前不得调用 `$zayn-networkmap` 展开名单研究。

仅当用户已指定行业、产品或业务范围足以限定行业，或本地真实业务记录能明确证明范围且不存在明显歧义时，才可直接继续；结果开头仍须声明采用的行业和产品边界。不得用“综合科技”等宽泛标签绕过确认，不得默认采用公司最知名业务，也不得自动纳入相邻产业。

### 25.4 传递输入

尽可能向 `$zayn-networkmap` 传递：研究模式；已确认的行业和产品边界；国家或目标区域；公司名称、官网、别名和本地语言名称；时间范围；本地已有资料和真实业务记录；期望输出数量与名单完整度要求。

用户未指定时采用以下默认值：

1. 公司近期活动覆盖过去 24 个月
2. 周期性展会覆盖最近两个已完成或已正式公布的届次
3. 第一轮研究 5 至 10 个高价值展会或协会
4. 证据不足的公司或关系留空或标记未确认
5. 不为追求名单完整而无限扩大查询

调用前确认公司主体可唯一识别、行业范围已确认、地区和时间窗口足够明确。下游 Skill 无法接收已确认范围或所需输入缺失时，停止并说明缺口；不得形成 ROUTE() 与 `$zayn-networkmap` 的循环调用。

### 25.5 返回后的衔接

保留来源、日期、事实与推断状态、范围限制和信息缺口。把 NETWORKMAP() 返回的公开关系作为研究证据，不直接升级为销售结论。只把下一步所需字段传给客户筛选、客户补全或开发策略 Skill；若没有足够的业务行动依据，明确停止。
