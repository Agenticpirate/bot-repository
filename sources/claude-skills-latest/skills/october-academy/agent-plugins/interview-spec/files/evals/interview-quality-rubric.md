# 좋은 인터뷰 품질 루브릭 (주관적 기준)

근거: Thariq Shihipar (Anthropic Claude Code 팀), "A Field Guide to Fable: Finding Your Unknowns" (x.com/trq212/status/2073100352921215386, 2026-07-03 · claude.com/blog 동명 게시글) + 사용자 지침("unknown unknowns를 밝혀내는 것이 특히 좋은 인터뷰·질문·코칭 스킬").

## 핵심 관점 (주관)

좋은 요구사항 인터뷰는 **빈칸 채우기 양식이 아니라 지도를 다시 그리는 행위**다. Thariq의 프레임: 지도(map)는 사용자가 주는 프롬프트·컨텍스트, 영토(territory)는 코드베이스와 현실 제약이며, 그 간극이 unknowns다. 인터뷰의 존재 이유는 이 간극을 싸게 좁히는 것 — "Every explainer, brainstorm, interview, prototype, and reference is a cheap way to find out what you didn't know before it gets expensive to fix."

인터뷰가 실패하는 두 방향 (Thariq): 너무 구체적이면 피벗이 필요할 때도 지시를 따르고, 너무 모호하면 업계 관행 기반의 안 맞는 가정을 채운다. 좋은 인터뷰는 사용자가 이미 아는 모호함(Known Unknowns)만 해소하는 게 아니라, 사용자가 **생각조차 못 한 것(Unknown Unknowns)** 과 **너무 당연해서 말 안 한 것(Unknown Knowns)** 을 수면 위로 올린다.

## 채점 차원 (각 0–2점, 총 10점)

### D1. 레버리지 우선순위 — "답이 아키텍처를 바꾸는 질문부터"
Thariq의 인터뷰 프롬프트 원문: "prioritize questions where my answer would change the architecture."
- **2**: 첫 라운드가 스펙/설계를 가장 크게 가르는 축(누구를 위한 것인가, 무엇이 트리거인가, 어디까지가 범위인가)부터 공략. 행정적 디테일(문구, 색상, 이름) 없음.
- **1**: 결정적 질문과 지엽적 질문이 섞여 있음.
- **0**: 지엽부터 묻거나 우선순위 감각 없음.

### D2. Unknown-unknown 발굴 — "사용자가 '아 맞다, 그것도' 하게 만드는가"
사용자가 요청에서 말하지 않았고 스스로 인지하지 못했던 실질적 고려사항을 인터뷰어가 먼저 제기해, 결정 또는 명시적 가정으로 착지시켰는가. (예: 알림 기능에서 실패 폭주 시 알림 폭탄 방지, 웹훅 재전송 중복, 최종 실패 후 구독 상태 처리)
- **2**: 이런 항목 1개 이상이 인터뷰어 주도 질문/옵션으로 등장하고 최종 스펙에 결정·가정으로 반영됨.
- **1**: 제기는 했으나 스펙에 착지하지 않음.
- **0**: 사용자가 이미 아는 모호함만 해소함.

### D3. 영토 접지 — "지도만 보지 말고 영토를 밟아라"
Thariq: "Claude can search through your codebase and the internet extremely quickly." 조사로 답할 수 있는 것을 사용자에게 묻는 것은 인터뷰 낭비다.
- **2**: 묻기 전에 코드베이스/프로젝트를 조사하고, 질문·옵션이 실제 코드/사실을 참조함. (조사할 것이 없는 greenfield면: 요청 텍스트에서 파생 가능한 것을 되묻지 않음 + 질문이 사용자의 실제 상황 어휘를 사용)
- **1**: 부분적 조사 또는 일반론 질문 혼재.
- **0**: 영토 확인 없이 템플릿 질문.

### D4. 질문 경제성 — "사용자는 고르기만 하면 되게"
옵션은 그럴듯한 가설(각각이 서로 다른 구현으로 이어짐), "모르겠어요"에는 추천 옵션 제시, 서로 독립인 질문은 한 라운드에 배치하고 의존 질문은 다음 라운드로(적응성), 군더더기 없음.
- **2**: 모든 질문의 답이 스펙을 실제로 바꿈. 필러 없음. 가설 옵션 품질 높음.
- **1**: 일부 필러/중복 질문.
- **0**: 열린 질문 남발 또는 고정 개수 채우기 패딩.

### D5. 정직한 종합 — "결정·가정·잔존 unknown의 삼분"
최종 스펙이 (a) 사용자가 결정한 것, (b) 어시스턴트가 기본값으로 가정한 것, (c) 아직 모르는 것(잔존 Known Unknowns + 해소 방법)을 구분해 기록하고, 날조가 없다. 인터뷰는 코칭이기도 하다 — 끝났을 때 사용자의 지도가 실제로 좋아져 있어야 한다.
- **2**: 삼분이 명확하고 전 항목이 문답으로 추적 가능.
- **1**: 결정 기록은 정확하나 가정/잔존 구분 없음.
- **0**: 근거 없는 스펙 항목 존재(날조) 또는 가정이 결정처럼 위장.

## 판정 노트

- D2가 이 루브릭의 심장이다. 사용자 지침: "unknown unknowns를 밝혀내는 게 특히 좋은 인터뷰·질문·코칭 스킬."
- 시뮬레이션 평가에서 D2 판정 기준: "사용자가 말한 것" = 프롬프트 + 사용자가 답변에서 자발적으로 말한 것. 브리프에 있더라도 인터뷰어가 먼저 제기해 끌어냈다면 발굴로 인정. 브리프에도 없는 실질 고려사항을 제기해 가정으로 남겼다면 상급.
- Thariq의 "one question at a time"과 현행 스킬의 배치(최대 4문항)는 긴장 관계다. 주관적 절충: **독립 질문은 배치, 의존 질문은 순차** — 적응성이 필요한 곳에서만 라운드를 쪼갠다. AskUserQuestion UI에서 배치는 클릭 몇 번이지만, 의존 질문을 같은 라운드에 넣으면 앞 답을 모른 채 뒷 질문 옵션을 설계하게 되어 가설 품질이 떨어진다.

## 원문 전문 확인 후 추가 반영 (2026-07-10)

사용자가 제공한 원문 전문에서 확정한 세 가지 뉘앙스:

1. **인터뷰의 존재 이유 = 지시의 딜레마 탈출.** "지시가 너무 구체적이면 피벗이 더 적절할 때도 그대로 따르고, 너무 모호하면 작업에 안 맞는 업계 모범 사례 기반 가정을 채운다." 인터뷰는 이 양쪽 실패를 피하는 제3의 길이다 — 지시하지 말고 결정 지점을 함께 열거하라. (D1·D5 판정 시 참고: 스펙이 '지시 목록'이 아니라 '결정 기록'인가)
2. **사고의 동반자(thought partner) 스탠스.** "현재 사고 과정의 어느 단계에 있는지 알려주고, 문제와 코드베이스에 대한 경험을 공유하며". 인터뷰어는 심문자가 아니라 동반자 — 사용자의 출발점(경험 수준, 사고 단계)을 파악하고 그에 맞춰 질문 깊이를 조정한다. (D4 판정 시 참고)
3. **기법 선택의 직관.** "매번 모든 기법을 다 쓰는 것은 아니다 — 언제 쓸지 직관을 기르라." 인터뷰는 탐색/브레인스토밍 이후 남는 unknowns를 해소하는 도구다. UU가 지배적이면 블라인드스팟 패스가, UK(보면 안다)가 지배적이면 프로토타입이 먼저다. 좋은 인터뷰 스킬은 자신이 맞는 도구가 아닐 때를 안다. (개선 단계에서 스킬의 When-to-Use 경계에 반영)
