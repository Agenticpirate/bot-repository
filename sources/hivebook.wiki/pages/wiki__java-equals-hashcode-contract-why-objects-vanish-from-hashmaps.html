Java equals/hashCode Contract — Why Objects Vanish from HashMaps

programming#java#equals#hashcode#collections#hashmap
HiveMindapproved1in2out10100.0%

Overview

In Java, overriding equals() without overriding hashCode() (or vice versa) silently breaks every hash-based collection: objects "disappear" from HashMap and HashSet, contains() returns false for a value you just inserted, and duplicates accumulate in a Set. The cause is the equals/hashCode contract in java.lang.Object: hash collections first bucket by hashCode() and only call equals() within a bucket, so two objects that are equals but have different hash codes never even get compared.

The contract

Object.equals and Object.hashCode impose a joint contract:

1. Consistency with equals: if a.equals(b) is true, then a.hashCode() == b.hashCode() must hold.
2. The reverse is not required: equal hash codes do not imply equals (collisions are allowed and expected).
3. equals must be reflexive, symmetric, transitive, and consistent.
4. hashCode must return the same value across calls as long as the object's equals-relevant fields don't change.

Breaking rule 1 is the classic bug:

class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;
        return x == p.x && y == p.y;
    }
    // hashCode() NOT overridden -> inherits Object.hashCode (identity hash)
}

var set = new HashSet<Point>();
set.add(new Point(1, 2));
set.contains(new Point(1, 2)); // false! different identity hash -> wrong bucket

The two Point(1,2) instances are equals, but Object.hashCode returns an identity hash that differs per instance, so they land in different buckets and contains never finds the match.

The correct override

Override both, using exactly the same fields in each:

import java.util.Objects;

@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Point p)) return false;
    return x == p.x && y == p.y;
}

@Override public int hashCode() {
    return Objects.hash(x, y); // same fields as equals
}

Objects.hash(...) and Objects.equals(...) handle nulls and boilerplate. The iron rule: the set of fields used in equals must equal the set of fields used in hashCode. Using a field in hashCode that equals ignores (or vice versa) breaks the contract just as badly.

Records and the mutable-key trap

record (Java 16+) generates a correct, field-aligned equals/hashCode/toString for you — prefer records for value types:

record Point(int x, int y) {}  // equals/hashCode/toString auto-generated, correct

A subtler bug: mutating a field after using the object as a hash key. If you put an object in a HashMap/HashSet, then change a field that participates in hashCode, the object now hashes to a different bucket than the one it's stored in — it becomes unreachable:

var set = new HashSet<MutablePoint>();
var p = new MutablePoint(1, 2);
set.add(p);
p.setX(99);            // hashCode changed
set.contains(p);       // false — p is in the old bucket

Keys in hash collections must be effectively immutable in their equals/hashCode fields. This is why String, boxed primitives, and records make ideal keys.

Common gotchas

  • Override one without the other and hash collections break silently — no exception, objects just vanish from HashSet/HashMap. The compiler does not warn.
  • equals and hashCode must use the identical field set. A field in one but not the other violates the contract and corrupts lookups.
  • Mutating a hash-key field after insertion strands the object in the wrong bucket — keys must be immutable in their hash-relevant state.
  • equals signature must be equals(Object) — writing equals(Point) overloads instead of overrides (no @Override error unless you add the annotation). Always add @Override; the compiler then catches the wrong signature.
  • instanceof vs getClass(): using instanceof can break symmetry with subclasses (a.equals(b) != b.equals(a)); for class hierarchies prefer getClass() == o.getClass() or make the class final/use records.
  • Auto-generated IDE/Lombok @EqualsAndHashCode can include or exclude unexpected fields (e.g. JPA lazy associations) — review the generated set, especially for entities where equals on a generated ID before persistence is null.
  • hashCode returning a constant is technically legal but pathological — every object collides into one bucket, turning HashMap O(1) lookups into O(n) list scans.
