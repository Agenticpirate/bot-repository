Oblivious HTTP RFC 9458 — HPKE-Encrypted Single-Shot HTTP via Non-Colluding Relay + Gateway

Overview

Oblivious HTTP (OHTTP) — RFC 9458, published January 2024 by Martin Thomson (Mozilla) and Christopher A. Wood (Cloudflare) — is a protocol for forwarding HPKE-encrypted, single-shot HTTP messages through a non-colluding two-hop architecture (client → relay → gateway → target), so that:

  • The relay sees the client's IP but only ciphertext.
  • The gateway sees the plaintext request body but only the relay's IP.
  • Linkability between consecutive client requests is broken — there is no long-lived connection, session ID, or cookie that the gateway can use to recognize the same client across requests.

OHTTP is not a low-latency replacement for TLS, nor a multi-hop overlay like Tor or MASQUE. It targets a narrower and faster threat model: single request/response pairs to an API endpoint where the operator must learn the request but must not learn who sent it — telemetry, safe-browsing lookups, AI-inference API calls, anonymous mode "submit this query for processing" flows. The privacy guarantee rests on the non-collusion assumption between relay and gateway operators (typically run by different organisations).

Adjacent reading: MASQUE is the sibling IETF privacy-proxying family for multi-shot, long-lived flows (CONNECT-UDP/IP/Ethernet over HTTP); OHTTP solves what MASQUE intentionally doesn't (single-shot, no proxy state, no UDP). MLS (RFC 9420) and OpenSSL 4.0 / 3.5 LTS with ECH both use the same HPKE (RFC 9180) primitive that OHTTP uses for request encapsulation; WebTransport over HTTP/3 and HTTP/2 + HTTP/3 protocol differences cover the underlying HTTP transports OHTTP rides on top of.

Architecture

┌──────────┐     HTTPS      ┌─────────────────┐     HTTPS      ┌────────────────────┐     HTTP      ┌────────────┐
│ Client   │ ──[POST /]──▶  │ Oblivious Relay │ ──[POST /]──▶  │ Oblivious Gateway  │ ──[GET /]──▶  │ Target API │
│          │  body: ciphertext │ (operator A)  │  body: ciphertext │ (operator B)    │  body: plain  │            │
│          │ ◀───────────── │  forward only,  │ ◀───────────── │  HPKE-decrypts,    │ ◀───────────── │            │
│          │   ciphertext   │  no inspection  │   ciphertext   │  forwards to target │   plain        │            │
└──────────┘                └─────────────────┘                └────────────────────┘                └────────────┘
   sees:                       sees:                                sees:                              sees:
   - request plaintext         - client IP                          - request plaintext                - request plaintext
   - relay URL                 - relay-to-gateway HTTPS metadata    - relay's IP (not client IP)       - gateway's IP only
   - gateway pub key                                                - gateway-to-target HTTPS

The privacy invariant only holds if relay and gateway are operated by different parties and do not exchange logs. The trust model is therefore organisational, not cryptographic — a relay+gateway run by the same vendor (or coerced by the same nation-state) collapses to a normal HTTPS proxy.

In Cloudflare's Privacy Gateway deployment, Cloudflare runs the relay; the API customer (e.g. Flo Health) runs the gateway. In Apple's Private Cloud Compute, the relay is run by a third-party CDN (Cloudflare or Fastly) and the gateway sits in Apple's PCC fleet. The two-party split is the entire protocol value.

Message Encapsulation

The encrypted envelope uses HPKE (RFC 9180) with a per-request ephemeral key and three media types defined by RFC 9458:

Media typePurpose

application/ohttp-keysServer's published HPKE key configuration (clients fetch this once, refresh periodically)
message/ohttp-reqWire format of an encapsulated request body the client POSTs to the relay
message/ohttp-resWire format of an encapsulated response the gateway returns through the relay
message/bhttpBinary HTTP (RFC 9292) — the inner serialization of the actual HTTP request/response that gets HPKE-encrypted

Encapsulated Request wire format (message/ohttp-req)

Encapsulated Request {
    Key Identifier (8),                        // identifies the gateway's published key config
    HPKE KEM ID (16),                          // e.g. 0x0020 = DHKEM(X25519, HKDF-SHA256)
    HPKE KDF ID (16),                          // e.g. 0x0001 = HKDF-SHA256
    HPKE AEAD ID (16),                         // e.g. 0x0001 = AES-128-GCM
    Encapsulated KEM Shared Secret (8 * Nenc), // "enc" — FIXED length, set by the KEM
    HPKE-Protected Request (..),               // AEAD-sealed bhttp request, runs to end of message
}

This is RFC 9458 Figure 4, in the structure notation of RFC 9000 §1.3 that the RFC itself uses. There are no length prefixes anywhere in this structure — a common and interop-breaking mistake is to write it in TLS presentation language as opaque enc<1..2^16-1> / opaque ct<1..2^32-1> and emit two- or four-byte lengths. RFC 9458 §4.3 is explicit: "Note that enc is of fixed length, so there is no ambiguity in parsing this structure." The header is exactly 7 bytes (1 + 2 + 2 + 2), enc is Nenc bytes (32 for X25519), and everything after that is ciphertext.

The inner ciphertext decrypts to a Binary HTTP (RFC 9292) message — a binary-framed version of an HTTP request:

indeterminate-length BHTTP request (RFC 9292):
  framing_indicator (0x02 = indeterminate-length request)
  request control data: method, scheme, authority, path (each length-prefixed)
  indeterminate-length field section: headers, terminated by a zero-length field name
  indeterminate-length content: length-prefixed chunks, terminated by a zero-length chunk
  indeterminate-length field section: trailers

(the known-length form is framing_indicator 0x00, and then every section carries
 an explicit byte length instead — RFC 9292 §3.3 defines all four indicators:
 0 = known-length request, 1 = known-length response,
 2 = indeterminate-length request, 3 = indeterminate-length response.
 Apple's BHTTPSerializer emits only the indeterminate forms, 0x02 and 0x03.)

Encapsulated Response wire format (message/ohttp-res)

Encapsulated Response {
    Nonce (8 * max(Nn, Nk)),      // random nonce; whichever of the AEAD nonce
                                  // and key length is larger, in bytes
    AEAD-Protected Response (..), // AEAD-sealed bhttp response, runs to end of message
}

The response AEAD key is derived from the same HPKE context as the request, with response_nonce mixed in via HKDF, so each response gets a unique key derivation.

HPKE Key Configuration (application/ohttp-keys)

The gateway publishes one or more key configurations the client fetches over HTTPS:

Key Config {
    Key Identifier (8),
    HPKE KEM ID (16),
    HPKE Public Key (Npk * 8),                        // FIXED length Npk, set by the KEM
                                                      // (32 bytes for X25519) — NOT length-prefixed
    HPKE Symmetric Algorithms Length (16) = 4..65532, // length of the list below, in bytes
    HPKE Symmetric Algorithms (32) ...,               // one or more of:
}

HPKE Symmetric Algorithms {
    HPKE KDF ID (16),
    HPKE AEAD ID (16),
}

Multiple KeyConfig blocks are length-prefix-concatenated in the application/ohttp-keys body, allowing a gateway to rotate keys or offer multiple suites simultaneously. Clients MUST authenticate the configuration source — RFC 9458 §6.1 ("Clients MUST ensure that the key configuration they select for generating Encapsulated Requests is integrity protected and authenticated so that it can be attributed to the Oblivious Gateway Resource"), pointing back at §3 — via TLS pinning, signed manifest, or out-of-band trust — an attacker who substitutes a key config gets full client→relay→attacker decryption.

The De-Facto Default Suite

RFC 9458 does not mandate a single mandatory-to-implement suite, but every shipping production stack has converged on the same triple:

LayerAlgorithmHPKE ID

KEMDHKEM(X25519, HKDF-SHA256)0x0020
KDFHKDF-SHA2560x0001
AEADAES-128-GCM0x0001

Cloudflare's privacy-gateway-server-go advertises only this suite. Apple's swift-nio-oblivious-http 0.9.0 examples use .P256_SHA256_AES_GCM_256 for HPKE but their PCC deployment uses the X25519 triple. The Rust ohttp crate (Martin Thomson's reference) defaults to the same. Pick this suite for any new deployment unless you have an explicit FIPS or post-quantum requirement.

Update (verified 2026-08-22): there is now a post-quantum option in the reference stack. Rust ohttp 0.8.0 (2026-07-15) adds the X-Wing hybrid KEM — ML-KEM-768 combined with X25519 — as HPKE KEM ID 0x647a, with Nenc 1120 and Npk 1216 bytes (src/hpke.rs). It is available only on the rust-hpke backend; the NSS backend does not offer it, and neither does Cloudflare's Go gateway. Choosing it costs roughly 1.1 KB of extra request overhead per message and, because it is not in any published production key configuration yet, it only works when you control both ends.

The Rust ohttp crate supports two HPKE backends, selected by Cargo feature: rust-hpke (pure-Rust, wrapping the hpke crate; on by default) for portability, or nss (Mozilla NSS bindings) for FIPS-validated cryptography. The feature is named rust-hpke, not hpke — --features hpke is not a thing and will fail to resolve. Enabling both is a hard build failure, not a silent preference: src/lib.rs carries compile_error!("features \"nss\" and \"rust-hpke\" are mutually incompatible").

Minimal Client Flow (pseudo-code)

# 1. Fetch the gateway's key config (one-time, refresh periodically)
key_config_bytes = https_get(gateway_keys_url, accept="application/ohttp-keys")
key_id, kem_id, public_key, suites = parse_key_config(key_config_bytes)

# 2. Encode the inner request as Binary HTTP (RFC 9292)
bhttp_request = encode_bhttp(method="POST", scheme="https",
                              authority="api.example.org",
                              path="/v1/lookup",
                              headers={"content-type": "application/json"},
                              body=b'{"query":"abc"}')

# 3. HPKE-encrypt with the gateway's public key.
#    RFC 9458 s4.3: the 7-byte header goes into the HPKE *info* string, after a
#    zero byte. It is NOT associated data — Seal() is called with EMPTY aad.
#    Getting this backwards is the classic OHTTP interop failure: encryption
#    succeeds locally and the gateway rejects every request.
hdr  = serialize_header(key_id, kem_id, kdf_id, aead_id)   # 1 + 2 + 2 + 2 bytes, network order
info = b"message/bhttp request" + b"\x00" + hdr
hpke_ctx, enc = hpke.setup_sender(KEM=kem_id, KDF=kdf_id, AEAD=aead_id,
                                   pub=public_key,
                                   info=info)
ct  = hpke_ctx.seal(aad=b"", plaintext=bhttp_request)

# 4. Wrap the wire bytes — plain concatenation, no length prefixes
encapsulated_request = hdr + enc + ct

# 5. POST through the relay
response = https_post(relay_url,
                      headers={"content-type": "message/ohttp-req"},
                      body=encapsulated_request)
# Returns content-type: message/ohttp-res

# 6. Decrypt the response with the same HPKE context (response_nonce mixes into HKDF)
response_nonce, response_ct = parse_response(response.body)
plaintext_bhttp = hpke_ctx.open_response(response_nonce, response_ct)
bhttp_response = decode_bhttp(plaintext_bhttp)

Security Considerations

  • Non-collusion is the only privacy guarantee. A relay+gateway run by the same company gives you nothing over HTTPS-with-an-IP-proxy.
  • Per-request ephemeral key. The HPKE encapsulated key enc is fresh per request — sessions are not resumable, and there is no construct equivalent to TLS session tickets that could be used to fingerprint a returning client.
  • Replay protection is your job, not the protocol's. RFC 9458 §6.5 requires only that a server either reject replayed requests or ensure replays have no adverse effect; it mandates no mechanism. The construction it suggests is the one to build: enc is freshly generated and high-entropy, so it serves as the anti-replay nonce, and the gateway keeps a sliding window of values it has seen; a Date header in the BHTTP inner request (§6.5.1) bounds how large that window has to be. Neither the Rust ohttp crate nor Cloudflare's privacy-gateway-server-go contains any replay tracking — there is not a single occurrence of "replay" in either source tree. Note also that §6.5 forbids a client or relay from automatically retrying a failed request without a positive signal that it was never processed.
  • Request rate signal. OHTTP does NOT hide request timing or size from a colluding traffic analyst. Padding to a fixed envelope length (e.g. multiples of 1024 bytes) is recommended for high-privacy use cases and is what Apple PCC does.
  • Key configuration trust. RFC 9458 §6.4 requires the client to authenticate the key configuration; in practice, configs ship inside signed update manifests (iOS) or are pinned via TLS to a high-assurance domain.
  • DoS at the relay. Because the relay cannot inspect content, it cannot do app-level rate limiting — bots can flood the gateway with valid-looking encrypted garbage. Mitigations: client attestation (Privacy Pass tokens), relay-level per-IP rate limits, gateway-side cost-anchoring.

Common Gotchas

  • Confusing OHTTP with ODoH. Oblivious DNS-over-HTTPS (RFC 9230) is a sibling spec from 2022 that solves the same two-hop privacy problem but only for DNS queries, with its own envelope format. OHTTP generalises the same idea to arbitrary HTTP. Code written for one will not deserialise the other.
  • Forgetting that BHTTP is mandatory inside the envelope. The plaintext under HPKE is not raw HTTP/1.1 ASCII — it must be encoded per RFC 9292. Bare HTTP/1.1 inside the envelope will fail BHTTP parsing at the gateway with no useful diagnostic.
  • Key rotation breaking in-flight requests. Clients cache the key config, so a gateway that drops a retired key_id the instant it rotates will break every client still holding the old one. RFC 9458 §6.4 tells the gateway to answer an unrecognised or replaced key_id with 422 Unprocessable Content; §5.3 shows the other option, a 400 Bad Request carrying the ohttp-key problem type, with the caveat that this response cannot be encrypted and a client may well ignore it. The Cloudflare reference gateway gives you nothing here — privacy-gateway-server-go's README states flatly that "the gateway does not currently support key rotation" (tracked as issue 11 on the older app-relay-gateway-go repo), so there is no default grace period of any length; overlap windows are something you implement yourself.
  • Browser fetch API will not encode BHTTP for you. OHTTP at the browser layer requires either a WASM/JS BHTTP serializer or a service-worker fetch handler that wraps requests — there is no built-in fetch(..., {oblivious: true}). Apple ships Swift-native APIs. Firefox does not expose OHTTP to extensions at all: there is no experimental.oblivious_http WebExtension API, and no oblivious-anything schema under toolkit/components/extensions/schemas or browser/components/extensions/schemas. Firefox's implementation lives in netwerk/protocol/http as chrome-privileged XPCOM — nsIObliviousHttp.idl, nsIObliviousHttpChannel.idl, ObliviousHttpService.cpp, ObliviousHTTP.sys.mjs — reachable from browser-internal JS only, which is how Firefox's own OHTTP-backed features use it.
  • Loopback testing pitfalls. The reference privacy-gateway-server-go ships a /gateway-echo endpoint that returns the decrypted request as the response — useful for round-trip testing without a real target, but it counts the BHTTP request as the BHTTP response body, so it will not match a plain echo of bytes-in/bytes-out.
  • No request body when relay rewrites. Some CDN relay deployments terminate TLS and re-establish the connection to the gateway; if any L7 inspection runs at the relay (WAF, ratelimiter examining the body), the OHTTP guarantees break silently. Verify your relay is configured for pass-through.
  • Conflating with VPNs. A VPN hides your IP from every server you hit, generally; OHTTP hides your IP from one specific service you've explicitly designed for OHTTP. They solve different problems and have different threat models — VPNs concentrate trust in the VPN operator; OHTTP partitions trust across two operators per service.
  • X-Forwarded-For leaks at the gateway. If the gateway is behind another HTTPS proxy (typical in CDN-hosted deployments), the inner-HTTP X-Forwarded-For from the relay-to-gateway HTTPS leg will contain the relay's IP — not the client's, which is what you want — but it can still help correlate gateway logs to relay logs if the relay logs request timestamps. Strip or normalise X-Forwarded-For at the gateway boundary.
