OpenSSF Scorecard v5.5 — Supply Chain Risk Scoring for OSS

Overview

OpenSSF Scorecard is an OpenSSF tool that scores open-source repositories against 19 supply-chain security checks and emits a 0–10 aggregate. Each check (e.g., Branch-Protection, Pinned-Dependencies, Token-Permissions, Vulnerabilities, Dangerous-Workflow) returns 0–10 with a documented risk level (Critical → Low); the aggregate is a weighted average where Critical checks count 10×, High 7.5×, Medium 5×, and Low 2.5×. The intent is automated, attacker-perspective signal on whether a dependency is safe to consume — replacing hand-curated "is this repo trustworthy?" gut checks.

The tool runs as a CLI (scorecard --repo=github.com/foo/bar) and a GitHub Action; pre-computed scores for popular OSS are served from api.scorecard.dev for free. Use it alongside SBOM scanners like Syft+Grype or OSV-Scanner — Scorecard rates project posture, scanners enumerate vulnerabilities in artifacts. Pairs naturally with Sigstore Cosign (signing) and Renovate/Dependabot (updates).

The 19 Checks

CheckRiskWhat it measures

Dangerous-WorkflowCriticalDetects dangerous GitHub Actions patterns (e.g., untrusted code in pull_request_target, script injection via ${{ github.event.* }} in run:).
WebhooksCriticalWhether webhooks have token authentication.
Binary-ArtifactsHighRepo contains committed executables (cannot be reviewed).
Branch-ProtectionHighDefault and release branches require code review, status checks, no force-push.
Code-ReviewHighRecent commits went through PR review.
Dependency-Update-ToolHighUses Dependabot/Renovate or equivalent.
MaintainedHighActive commits and issue activity (not abandoned).
Signed-ReleasesHighReleases are signed or have SLSA provenance attestations.
Token-PermissionsHighGitHub Actions tokens follow least-privilege (permissions: blocks present).
VulnerabilitiesHighNo known unfixed CVEs (queries OSV).
FuzzingMediumProject employs fuzzing (OSS-Fuzz, ClusterFuzzLite, property-based testing).
PackagingMediumProject publishes via package managers (npm, PyPI, crates, etc.).
Pinned-DependenciesMediumDependencies pinned to specific versions/hashes (Docker FROM image@sha256:…, GH Actions uses: foo@<sha>).
SASTMediumCodeQL or equivalent SAST runs on commits/PRs.
Security-PolicyMediumSECURITY.md with disclosure instructions exists.
CI-TestsLowAutomated tests run before merging PRs.
CII-Best-PracticesLowProject holds an OpenSSF Best Practices Badge.
ContributorsLowContributors come from multiple organizations.
LicenseLowRepo has a recognized open-source LICENSE file.

Checks may return ? (insufficient data; doesn't count) instead of a number. The aggregate clamps to 0–10.

CLI Usage

# Install
go install github.com/ossf/scorecard/v5@latest
# Or use the Docker image (now on ghcr.io as of v5.5.0)
docker run -e GITHUB_AUTH_TOKEN ghcr.io/ossf/scorecard:v5.5.0 \
  --repo=github.com/ossf/scorecard --format=json

# Single repo, default JSON output
scorecard --repo=github.com/ossf/scorecard --format=json

# Multiple repos (v5.4+)
scorecard --repos=github.com/foo/a,github.com/foo/b --format=json

# Entire GitHub org (v5.4+)
scorecard --org=ossf --format=json

# Focus on specific checks
scorecard --repo=github.com/foo/bar \
  --checks=Branch-Protection,Token-Permissions,Pinned-Dependencies

# Local repo (no GitHub round-trip for some checks)
scorecard --local=/path/to/repo --format=sarif

# Serve mode (HTTP API on the host)
scorecard serve --port=8080
# then POST {"repo":"github.com/foo/bar"} to /scorecard

Outputs supported: default (human), json (machine), sarif (GitHub Security tab), raw (intermediate findings).

Required environment

  • GITHUB_AUTH_TOKEN — a PAT (any scope; even no-scope works for public repos and is preferred to avoid leaking permissions). Rate-limit avoidance: GitHub anonymous = 60 req/h, authenticated = 5000 req/h. Heavy scans of many repos need an authenticated token.

GitHub Action

# .github/workflows/scorecard.yml
name: Scorecard supply-chain security
on:
  branch_protection_rule:
  schedule: [{cron: "0 6 * * 1"}]   # weekly
  push: {branches: [main]}

permissions: read-all

jobs:
  analysis:
    runs-on: ubuntu-latest
    permissions:
      security-events: write       # upload SARIF
      id-token: write              # publish_results attestation
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: ossf/scorecard-action@v2.4.2
        with:
          results_file: results.sarif
          results_format: sarif
          publish_results: true     # contributes to api.scorecard.dev
      - uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif

publish_results: true opts your project into the public api.scorecard.dev dataset (CDLA-Permissive 2.0 licensed). For private repos keep it false.

API (api.scorecard.dev)

Pre-computed weekly scores for popular OSS, CDN-cached, no auth required:

curl -s https://api.scorecard.dev/projects/github.com/sigstore/cosign | jq .
# → {"date":"…","score":8.6,"checks":[{"name":"…","score":…},…]}

The dataset includes ~1M repos refreshed weekly. Sub-resources:

  • /projects/github.com/<owner>/<name> — latest
  • /projects/github.com/<owner>/<name>/history — historical scores (limited window)
  • /projects?from=YYYY-MM-DD&to=YYYY-MM-DD — bulk queries

Reading a Score

A repository's aggregate score is a guide, not a verdict.

  • 8–10: Good baseline hygiene. Branch protection, code review, pinned deps, signed releases.
  • 5–7: Mixed. Probably missing pinned-dependencies, signed-releases, or branch-protection. Manual review warranted.
  • 0–4: Weak posture or insufficient data. Common for very new repos or single-maintainer projects.

Crucially, a high Scorecard score does not certify the code is secure — it only certifies the project's processes meet OpenSSF baselines. A 9.5 project can still ship a vulnerable function. A low score does not mean the code is broken — it often just means the project lacks SLSA-level CI plumbing.

Common Gotchas

  • Dangerous-Workflow Critical (×10 weight) dominates the score. A single pull_request_target workflow that checks out untrusted code drops the aggregate dramatically. Fix first.
  • Pinned-Dependencies flags every floating tag. GitHub Actions uses: actions/checkout@v4 is unpinned by Scorecard's definition; only uses: actions/checkout@<40-char-sha> counts as pinned. Same for FROM node:20 vs FROM node:20@sha256:…. To pass cleanly without losing readability, pin SHAs and let Dependabot/Renovate update them.
  • Token-Permissions wants explicit permissions: blocks. Workflows without a permissions: at job or top level inherit the legacy "write everything" default and score 0 here.
  • Branch-Protection check requires an admin-scoped token to read protection rules. With a no-scope PAT the check returns 0 or ? (false negative). Use --token=... or GITHUB_AUTH_TOKEN with admin:org for accurate scoring.
  • Fuzzing check is binary. Either project has OSS-Fuzz / ClusterFuzzLite / property-based testing (.NET v5.5.0+) → 10, or doesn't → 0. There's no partial credit.
  • Signed-Releases requires both signing AND provenance. Cosign signing alone counts; SLSA provenance attestations counts; releases with neither score 0. The check looks at the latest 5 releases, so a single signed release won't lift the score.
  • Code-Review looks at recent commit history. Solo-maintainer projects with self-merged commits score 0 even if the code is high quality. There is no flag to opt out of this assumption.
  • Docker image registry moved to ghcr.io in v5.5.0. Old gcr.io/openssf/scorecard:vX images stopped receiving updates; pull from ghcr.io/ossf/scorecard:v5.5.0 going forward.
  • api.scorecard.dev lag. Scores refresh weekly; if you just fixed an issue, the public API may show the old score for up to 7 days. The CLI runs locally and is always current.
  • The aggregate does not include ? (no-data) checks. A repo missing data on 3 checks effectively scores against fewer signals; comparing scores across repos is therefore lossy when no-data counts differ.
  • Public-only. Scorecard relies on GitHub repository metadata, so private repos work only via the CLI with an authenticated token; the public api.scorecard.dev dataset is GitHub-public-OSS only.
