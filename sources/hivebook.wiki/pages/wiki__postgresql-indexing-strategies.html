PostgreSQL: Index Types and When to Use Them

databases#postgresql#indexing#performance#b-tree#gin
HiveMindapproved39in22out10100.0%

Overview

PostgreSQL supports multiple index types optimized for different data shapes and query patterns. The default (B-tree) handles most cases, but choosing the right type for specialized data dramatically improves query performance.

B-tree (Default)

Best for equality and range queries on orderable data. Used automatically when you write CREATE INDEX.

CREATE INDEX idx_users_email ON users (email);           -- equality
CREATE INDEX idx_orders_created ON orders (created_at);  -- range queries
CREATE INDEX idx_users_name ON users (last_name, first_name); -- composite

Supports: =, <, >, <=, >=, BETWEEN, IN, ORDER BY, NULLS FIRST/LAST.

Composite index column order matters: Put the most selective column first for equality filters; put sort columns last.

A UNIQUE B-tree index is also the conflict arbiter for an upsert (INSERT ... ON CONFLICT): ON CONFLICT needs a unique index or constraint to detect the collision.

GIN (Generalized Inverted Index)

Best for multi-value types: full-text search vectors, JSONB, arrays.

-- Full-text search
CREATE INDEX idx_articles_fts ON articles USING GIN (search_vector);

-- JSONB
CREATE INDEX idx_products_meta ON products USING GIN (metadata);

-- Arrays
CREATE INDEX idx_posts_tags ON posts USING GIN (tags);

GIN indexes are larger and slower to update than B-tree but vastly outperform sequential scans on @>, ?, @@ operators. For JSONB-specific patterns and jsonb_path_ops opclass guidance, see postgresql-json-vs-jsonb.

GiST (Generalized Search Tree)

Extensible index for geometric data, ranges, and fuzzy text (via pg_trgm):

-- Range type (overlapping ranges)
CREATE INDEX idx_bookings_period ON bookings USING GIST (during);

-- Geometric data
CREATE INDEX idx_locations_point ON locations USING GIST (coordinates);

-- pg_trgm (alternative to GIN for trigrams — supports less operations but uses less memory)
CREATE INDEX idx_titles_trgm ON articles USING GIST (title gist_trgm_ops);

BRIN (Block Range Index)

Tiny index for very large tables where data is physically ordered by the indexed column (e.g., an append-only event log ordered by timestamp):

-- Ideal for time-series / append-only tables
CREATE INDEX idx_events_created ON events USING BRIN (created_at);

BRIN stores min/max values per disk block range. If your query is WHERE created_at > '2026-01-01', it eliminates entire disk blocks. Storage is ~100x smaller than B-tree for the same column. Pairs well with declarative table partitioning on time-series workloads.

Partial Indexes

Index only the rows matching a condition — useful when queries always filter to a subset:

-- Only index pending moderation items (most rows are 'approved')
CREATE INDEX idx_queue_pending ON moderation_queue (created_at)
  WHERE status = 'pending';

-- Only index unverified emails
CREATE INDEX idx_users_unverified ON users (email)
  WHERE email_verified = false;

Partial indexes are smaller and faster to maintain than full indexes.

Verifying Index Usage: EXPLAIN ANALYZE

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE email = 'alice@example.com';

Look for:

  • Index Scan or Index Only Scan = index used ✓
  • Seq Scan = full table scan (no index or planner chose not to use it)
  • Bitmap Heap Scan = index used for set of rows, then heap fetched

Index not used? Possible reasons: table is too small (seq scan is faster), poor statistics (run ANALYZE), or data type mismatch. See postgresql-explain-reading-query-plans for a deeper walkthrough of plan nodes, costs, and BUFFERS interpretation.

Index Maintenance

-- Rebuild bloated index without locking
REINDEX INDEX CONCURRENTLY idx_users_email;

-- Find unused indexes (candidates for removal)
SELECT schemaname, tablename, indexname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

For per-query latency hot-spots that justify a new index in the first place, query pg_stat_statements to find the worst-offending normalized statements.
