Overview

tcpdump is the standard command-line packet capture tool on Unix-like systems. It captures network packets using libpcap and displays them in real time or writes them to pcap files for later analysis with tools like Wireshark. At the April 2026 baseline the latest stable version was 4.99.6 (December 2025), and it still is. tcpdump is pre-installed on most Linux distributions, macOS, and BSD systems, making it the universal first-response tool for network debugging.

Update (verified 2026-09-07): tcpdump 4.99.6 (released December 30, 2025) remains the current stable release — no 5.0 has shipped, and tcpdump-4.99.6 is still the newest tag in the repository. tcpdump.org describes this release as shipping "whilst the work on tcpdump 5.0 is still in progress". Two corrections to the dependency claim that stood here, made against tcpdump.org and the release tarballs:

  • The project's own wording is that 4.99.6 "requires libpcap 1.10.5 or later to pass all test cases" — not 1.10.6. Note also that the shipped 4.99.6 source tree states no minimum libpcap version anywhere (README.md, INSTALL.md and configure.ac only require that some libpcap be present); the version floor exists solely in the release announcement on tcpdump.org.
  • Current libpcap is 1.10.7, released September 5, 2026 — not 1.10.6.

The CVE attribution that stood here was correct: CVE-2025-11961 (out-of-bounds read/write in pcap_ether_aton()) and CVE-2025-11964 (out-of-bounds write in error-message transcoding, Windows builds only) are both libpcap bugs fixed in 1.10.6. Both score only 1.9 LOW on NVD, so neither is a reason to treat 1.10.6 as a floor.

Security update (2026-09-07) — this one matters for a page about BPF filters: libpcap 1.10.7 fixes seven CVEs, five of them in the BPF filtering path itself. The significant one is CVE-2026-0799 (CVSS 8.7 HIGH): the BPF interpreter did not bounds-check the register index when loading from or storing to its scratch memory store. Alongside it, CVE-2026-31912, CVE-2026-31911, CVE-2026-6244 (division by zero) and CVE-2026-6554 (unbounded jump looping) all land in pcap_offline_filter(), and CVE-2026-18313 / CVE-2026-18238 fix a leak and an under-validated message in rpcap. Every filter expression on this page is executed by that interpreter, so prefer libpcap 1.10.7 over the 1.10.6 this entry previously pinned.

BPF Filter Syntax

tcpdump filter expressions are compiled to Berkeley Packet Filter (BPF) bytecode via pcap_compile() and executed in kernel space — packets that don't match are discarded before reaching userland.

Structure: [direction] [protocol] [type] id

QualifierValuesExample

Directionsrc, dst, src or dst (default), src and dstsrc host 10.0.0.1
Protocoltcp, udp, icmp, arp, ip, ip6, ethertcp port 80
Typehost, net, port, portrangenet 10.0.0.0/8
Logicand / &&, or / ||, not / !port 80 or port 443

TCP flag matching uses byte offset tcp[13] (the flags byte):

ExpressionMatches

tcp[tcpflags] == tcp-synSYN only (new connections)
tcp[13] == 18SYN-ACK (server response)
tcp[13] & 2 == 2Any packet with SYN flag set
tcp[tcpflags] == tcp-rstRST (connection reset)
tcp[tcpflags] & (tcp-rst\|tcp-fin) != 0Any teardown packet

Operator precedence (verified 2026-09-07): the two masked expressions above are correct as written, and are worth not "fixing". In the pcap-filter grammar & binds tighter than the relational operators, the opposite of C — so tcp[13] & 2 == 2 parses as (tcp[13] & 2) == 2 and genuinely means "SYN set", and tcp[tcpflags] & (tcp-rst|tcp-fin) != 0 genuinely means "RST or FIN set". Run against a capture built for the purpose, the first matched every SYN-bearing packet and the second matched exactly the FIN and RST packets, with no over- or under-matching. tcpdump -d '<filter>' prints the compiled bytecode and settles any such question directly.

Packet data accessor: proto[offset:size] reads bytes from protocol headers. Example: ip[2:2] reads the IP total length field.

Practical Debugging Examples

Capture HTTP Traffic

# All HTTP traffic with full packet content
sudo tcpdump -i eth0 -nn -s0 -A port 80

# Extract HTTP request lines
sudo tcpdump -nn -s0 -v -l | grep -iE "POST /|GET /|Host:"

# Only data-carrying HTTP packets (skip handshake/ACKs)
tcpdump 'tcp port 80 and (((ip[2:2] - ((ip[0]&0xf)<<2)) - ((tcp[12]&0xf0)>>2)) != 0)'

DNS Queries

# All DNS traffic (queries + responses)
sudo tcpdump -i eth0 -nn -s0 port 53

# Outbound queries only
tcpdump -nn 'udp dst port 53'

# Verbose DNS with full packet details
sudo tcpdump -nn -vv -s0 port 53

TCP Handshake Analysis

# SYN packets (connection initiations)
tcpdump 'tcp[tcpflags] == tcp-syn'

# SYN + SYN-ACK together
tcpdump 'tcp[13] == 2 or tcp[13] == 18'

# Connection teardowns (RST or FIN)
tcpdump 'tcp[tcpflags] & (tcp-rst|tcp-fin) != 0'

For TCP option-space inspection (uncommon options that tcpdump's decoder does not break out by name) — useful when confirming MPTCP v1 Kind=30 options are surviving middleboxes during the SYN/SYN-ACK handshake:

# Presence check: TCP data offset > 5 means option bytes are present
tcpdump -vvv 'tcp[12] & 0xf0 > 0x50'

Corrected 2026-09-07 (this filter was wrong as originally published, not merely stale). The expression previously given here, tcp[12:1] & 0xfc != 0, is a tautology over TCP — it matches every TCP packet, silently, while reading like a selective filter. tcp[12] is the data-offset/reserved byte, not an options byte, and the data offset is at least 5 for any valid header, so the high nibble alone (0x50) already makes & 0xfc non-zero. Run against a capture of 16 packets in which only 3 carried TCP options, the old expression matched all 13 TCP packets; tcp[12] & 0xf0 > 0x50 matched exactly those 3. The compiled bytecode shows it plainly: the old form emits jset #0xfc on the offset byte, the corrected form emits and #0xf0 followed by jgt #0x50.

Note the real limit here: BPF cannot walk the variable-length TCP option list, so this tells you only that some options are present, never which. To pinpoint one option kind — MPTCP's Kind=30, say — filter broadly with tcpdump and post-process with a dissector that parses the option list, e.g. tshark -r capture.pcap -Y 'tcp.option_kind == 30'.

Host-Specific Traffic

# All traffic to/from a host
tcpdump host 192.168.1.100

# Traffic between two hosts
tcpdump host 192.168.1.100 and host 192.168.1.200

# Subnet monitoring
tcpdump net 192.168.1.0/24

Capture to File for Wireshark

# Full capture to pcap
sudo tcpdump -i eth0 -s0 -w capture.pcap

# Limited capture with filter
sudo tcpdump -i eth0 -s0 -c 1000 -nn -w capture.pcap port 443

# Remote capture piped to local Wireshark
ssh root@remote 'tcpdump -s0 -c 1000 -nn -w - not port 22' | wireshark -k -i -

# Read and filter saved capture
tcpdump -r capture.pcap -nn tcp port 80

Rotating Captures

For long-running captures, use time-based and/or size-based rotation:

# Rotate every 10 minutes, compress, drop privileges
sudo tcpdump -i eth0 -s128 -w capture-%Y%m%d-%H%M%S.pcap \
  -G 600 -z gzip -Z $USER tcp port 12345

# Ring buffer: 5 files of 100 MB each, oldest overwritten
sudo tcpdump -i eth0 -w capture.pcap -C 100 -W 5

# Hourly captures
sudo tcpdump -i eth0 -w capture-%Y%m%d%H.pcap -G 3600

Note: -G requires strftime format specifiers in the filename (e.g., %Y, %m, %s). Corrected 2026-09-07: without them each rotation overwrites the previous file — it does not produce a numbered series. The man page is explicit ("If no time format is specified, each new file will overwrite the previous"), and tcpdump.c applies filename numbering only when -C is also set. A live -G 1 capture to a fixed filename leaves exactly one file behind holding only the final interval. The failure mode is therefore silent data loss, not runaway disk usage.

Counted directly from the shipped binary with tshark -G protocols | wc -l and tshark -G fields, Wireshark/tshark 4.2.2 registers 3,001 protocols and 248,574 display-filter fields. That is the version measured, and it is not the current one — the counts grow with every release, so treat "~3,000" as a floor rather than a fixed number. Current Wireshark stable is 4.6.8 (wireshark.org), with 4.4.18 as old-stable and 4.7.3 as the development line. tcpdump has no comparable count because it has no display-filter language: its decoders print, they do not expose named fields to filter on.

Version discipline for this page (2026-09-07). The examples here were exercised on tcpdump 4.99.4 with libpcap 1.10.4 (the Ubuntu 24.04 package, 4.99.4-3ubuntu4.24.04.1), which is what a current LTS gives you — while the current upstream release is 4.99.6 with libpcap 1.10.7. Distribution packages routinely trail upstream by two releases here; check tcpdump --version, which prints both its own and the linked libpcap version, before assuming a filter behaves as upstream documents it.

Recommended workflow: tcpdump to capture on remote servers, tshark to extract/summarize fields, Wireshark to deep-dive specific flows.

On modern Linux with eBPF JIT enabled, BPF filter bytecode is compiled to native machine code for near-zero filtering overhead.

Common Gotchas

  • Always use -n or -nn — without it, tcpdump performs reverse DNS lookups for every IP, adding latency, generating DNS traffic that pollutes your capture, and creating a display backlog on busy links.
  • Switched networks limit promiscuous mode — on switched Ethernet, promiscuous mode only captures traffic destined for your port plus broadcast/multicast. Seeing only ARP traffic is a classic symptom. Use port mirroring/SPAN on the switch for full visibility.
  • Container network namespaces — tcpdump on the host does not see traffic inside a container's namespace. Use docker exec -it container tcpdump, a sidecar container sharing the network namespace, or nsenter -t $(docker inspect -f '{{.State.Pid}}' container) -n tcpdump.
  • Default snap length is 262,144 bytes — modern tcpdump captures full packets by default. Older tutorials using -s 0 are harmless but unnecessary. Larger snap lengths increase CPU load and can cause drops under heavy traffic; use -s 96 for header-only captures.
  • Pipe buffering — without -l, stdout is block-buffered. tcpdump | grep pattern may show no output until a 4 KB buffer fills. Always add -l when piping.
  • Memory growth in long captures — without -S, tcpdump tracks TCP state for relative sequence numbers, leaking memory over time. Use -S for absolute sequence numbers in long-running captures.
  • Retransmission detection — tcpdump cannot detect TCP retransmissions (same sequence number seen twice). Use Wireshark's tcp.analysis.retransmission display filter or tshark for this.
  • -G without strftime silently destroys your capture (corrected 2026-09-07) — using -G with a fixed filename does not create numbered files and does not accumulate them; each rotation overwrites the last, so a night-long capture leaves you the final interval and nothing else. Numbering is applied only under -C. Always include %Y%m%d-%H%M%S or similar in the filename template. Verified against the 4.99.6 man page, tcpdump.c, and a live -G 1 run that produced exactly one file.
