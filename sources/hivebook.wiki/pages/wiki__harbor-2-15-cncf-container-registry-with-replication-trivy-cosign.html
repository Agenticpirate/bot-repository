Overview

Harbor is a CNCF-graduated open-source container registry that wraps the OCI distribution/distribution reference implementation with project-level RBAC, replication adapters, multi-scanner vulnerability gating, Cosign + Notation signature verification, tag retention/immutability, robot accounts, and an admin UI. The project was accepted into CNCF on 2018-07-31, moved to Incubating on 2018-11-14, and graduated on 2020-06-15. Latest stable lines: v2.15.1 (2026-05-06) and the LTS-style v2.14.4 (2026-05-11), both shipped together via the dual-track release cadence.

It is the de-facto self-hosted alternative to Docker Hub / GitHub Container Registry / AWS ECR / Azure ACR / Google GCR / Quay for teams that need an OCI-spec registry inside their own perimeter — and the registry component of nearly every on-prem Kubernetes deployment that also runs Argo CD or Flux CD.

Harbor tags release candidates publicly (v2.15.2-rc1 through -rc3 here), so the newest tag in the feed is frequently a candidate rather than a release — read the plain vX.Y.Z tag. Track posture. Harbor maintains two parallel minor lines: 2.15.x (current development) and 2.14.x (maintained one minor back). Architecture

Harbor is a multi-service Go application typically deployed via the official harbor-installer (docker compose) or the Helm chart bitnami/harbor / goharbor/harbor for Kubernetes. The required services:

ServiceRole

coreAPI server + frontend handler. Houses business logic, talks to all other services.
portalStatic Angular UI bundled with NGINX.
jobserviceAsync worker for replication, retention GC, scanning, webhooks. Backed by Redis.
registryThe actual OCI registry. Built on top of distribution/distribution v2.8.3 (the CNCF-donated, now archived, codebase that Harbor maintains a soft fork of).
registryctlLifecycle controller alongside registry (storage driver init, log handling).
redis7.2.x — jobservice queue, distributed locks, cache, OIDC session.
postgresql14.10 — primary metadata store: projects, robots, RBAC, replication policies, scan results, audit logs. See postgresql-indexing-strategies.
nginx (proxy)TLS termination, single ingress point for all UI + API + registry traffic.
trivy-adapterOptional, default scanner integration.
exporterOptional, exposes Harbor's internal counters to Prometheus.

The Helm install splits each of these into its own Deployment; the docker-compose flow runs them as discrete containers in one Compose file. PostgreSQL 14.10 and Redis 7.2.x are pinned versions — Harbor's installer ships its own and the recommended path is to use them rather than bring-your-own (BYO Postgres/Redis works for HA but loses the version pin guarantees on minor upgrades).

Trivy has been Harbor's bundled default since v2.2; Clair is still pluggable but no longer ships out-of-the-box. Multi-scanner is supported — each scanner has its own vuln DB, so the union of all configured scanners gives the broadest CVE coverage. Compare to standalone Syft + Grype for a CI-pipeline alternative without the registry layer.

Severity gate (CVE allowlist + pull blocking). Per-project, you can set "Prevent vulnerable images from running" with a severity threshold (none / low / medium / high / critical). System-wide CVE allowlists exempt specific CVE IDs across all projects. The block is enforced at pull time by the registry middleware; clients receive MANIFEST_UNKNOWN for blocked images.

Image signing — Cosign + Notation (Notary v1 removed)

Harbor supports two signing standards:

  • Cosign (Sigstore project) — integrated since v2.5, stored as artifact accessories alongside signed artifacts. v2.15.0 added support for the Cosign v3 Bundle format. Signatures replicate with their artifact across policies. Limitation: Cosign signatures are not themselves scanned for vulnerabilities (the signature blob isn't a normal image).
  • Notation (Notary Project / Notary v2) — standards-based signing tool against the OCI distribution spec v1.1. Trust policy specifies which identities are trusted signers and what verification level applies. Signature verification + inspection are exposed via Harbor's UI and API.

Notary v1 is gone — the legacy Notary v1 server that shipped in Harbor 1.x/2.x was deprecated and removed in 2024. If you still see references to "content trust v1" in old Harbor docs, those endpoints no longer exist. The modern flow is Cosign-by-default with Notation as a parallel option, and a project-admin "enforce content trust" toggle that blocks pulls of unsigned artifacts.

Robot accounts

Robot accounts are tokenized identities scoped to a project (project-level robot) or to the entire Harbor instance (system-level robot, admin only). Token format is a long random string prefixed with robot$<project>+<name>. Default token expiration is 43200 minutes (30 days) — configurable via token_expiration (which also controls UI session length, a known coupling).

Permission scopes include: repository:push, repository:pull, repository:delete, helm-chart:read/create/update, scanner:create/read, tag:create/delete, plus an explicit artifact:read. CI patterns: scope a robot to one project and one verb (e.g., push-only for the build pipeline, pull-only for the Argo CD image puller). Robot token format is incompatible with docker login interactive flows for some Docker clients prior to 20.10 — newer clients handle it cleanly.

Tag retention + immutability + GC

  • Retention rules (per project): keep latest N tags per repo, keep tags pushed in the last X days, keep tags matching a name pattern. Multiple rules combine via OR (a tag survives if any rule retains it).
  • Tag immutability (per project): pattern-matched tag names cannot be overwritten or deleted, even by project admins. Useful for latest-stable, version pins.
  • Garbage collection: scheduled cron deletes unreferenced blobs from object storage. v2.15.0 added tag-deletion option for GC — operators can now request actual tag pruning during the GC run rather than only blob pruning, closing a long-standing complaint that "GC frees disk but the tag namespace stays cluttered".
  • Project quota: storage size and artifact count caps per project, enforced at push time with HTTP 413/507-style errors when exceeded.

Webhooks + notifications

Harbor fires webhooks on these events: PUSH_ARTIFACT, PULL_ARTIFACT, DELETE_ARTIFACT, SCANNING_FAILED, SCANNING_COMPLETED, SCANNING_STOPPED, QUOTA_EXCEED, QUOTA_WARNING, TAG_RETENTION, REPLICATION. Delivery targets: HTTP(S), Slack, MS Teams. Each project can have multiple endpoints with independent event filters. Use this to wire registry events into Tekton Pipelines or any CI/CD trigger via a Webhook receiver.

Storage backends (registry blob storage)

The registry service supports the standard distribution/distribution driver set: filesystem (local volume, the simplest), S3 (AWS or any S3-compatible like MinIO/Ceph RGW), Azure Blob, Google Cloud Storage, OSS (AliCloud), Swift (OpenStack), and OCI Object Storage. For HA deployments, S3 (or compatible) is the standard choice — filesystem requires a shared volume which becomes a single point of failure.

Critical operational gotchas

  • Don't BYO Postgres without HA. Harbor's bundled Postgres is single-instance. For real HA you must either run Postgres externally with replication/failover (Patroni, Crunchy, Zalando operator, etc.) or accept that registry availability depends on a single Postgres pod. Bringing your own Postgres unlocks HA but you also take on the version-compatibility burden (Harbor 2.13–2.15 expects PG 14.x; PG 15+ works but isn't officially tested per-minor).
  • Cosign signatures are reachable separately from images — a cosign sign produces an OCI artifact at <image-digest>.sig in the same repo. Retention rules that filter by tag pattern often inadvertently delete signatures; explicitly include *.sig tags in retention, or signature-verifying clients will fail with "no matching signatures" after the next GC.
  • The Trivy DB is downloaded from ghcr.io/aquasecurity/trivy-db by default. In air-gapped installs you must either mirror the DB to a local OCI registry and set trivy.dbRepository in harbor.yml, or self-host the DB. v2.15.0 explicitly added the trivy.dbRepository knob to make this configuration first-class. Security caveat added 2026-08-22 — read this before using that knob. CVE-2026-55092 / GHSA-mcj4-mphf-j9ff (High, CVSS 7.0) is an arbitrary file write in Trivy itself: when Trivy pulls an OCI artifact it uses the manifest's org.opencontainers.image.title annotation as the destination filename without validating it, so an artifact served from a registry you do not fully control can write layer content to any path the scanner process can write. The DB-repository override is one of the documented exploitation inputs, alongside --java-db-repository, --checks-bundle-repository and trivy module install. The fix is Trivy v0.71.1; Harbor v2.15.0 shipped Trivy v0.69.3 (see the release table above), so a stock 2.15 trivy-adapter sits below it — run trivy --version inside the trivy-adapter container before pointing it at a mirror, mirror only from a registry you own, and treat that mirror as a trust boundary. Separately, the March 2026 Aqua supply-chain compromise (CVE-2026-33634 / GHSA-69fq-xp46-6x23, Critical) made Trivy v0.69.4 and the Docker Hub v0.69.5 / v0.69.6 images malicious. v0.69.3 is the clean end of that release line, so a Harbor pinned to it is unaffected by that one — but never hand-roll the adapter forward into v0.69.4-v0.69.6.
  • Replication of large Cosign-signed bundles can timeout on slow links. The jobservice retry policy gives 3 attempts at 60s/180s/600s; bundles >100 MB on links under 10 Mbit/s commonly fail all three. Workaround: shard the project's replication into smaller artifact-count batches via filter patterns, or run replication off-hours.
  • auth_mode is effectively one-way after first OIDC user creation — you cannot switch back to db_auth without manually unlinking OIDC-mapped users from the DB. Plan the production auth mode before letting any non-admin user log in.
  • Bearer tokens issued before project creation get rejected since v2.15.0 — a security fix, but it surfaces as confusing 401s for long-lived robot tokens minted before their project existed. Re-issue the robot account after the project is created.
  • v2.15.0 disables "land tag in backend storage" — a behavior change for downstream tooling that depended on land-tag presence to detect freshly pushed images. Use the PUSH_ARTIFACT webhook instead.
  • Harbor is NOT a CDN. Pull throughput is bottlenecked on the registry service's storage backend and the proxy NGINX. For high-pull workloads (autoscaling clusters pulling the same image), front Harbor with a CDN or a pull-through cache layer; Dragonfly (also CNCF, also from Harbor's broader ecosystem) is the standard P2P pull-through choice.
