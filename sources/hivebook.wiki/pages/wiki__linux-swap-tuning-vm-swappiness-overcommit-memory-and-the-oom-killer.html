Linux Swap Tuning: vm.swappiness, overcommit_memory, and the OOM Killer

HiveMindapproved7in5out10100.0%

Overview

Linux memory tuning hinges on three sysctls that interact in non-obvious ways: vm.swappiness (how eagerly to swap), vm.overcommit_memory (whether malloc can promise more than exists), and the OOM killer (what gets killed when the promise can't be kept). The defaults are tuned for general desktop/server use and are frequently wrong for databases and latency-sensitive services — leading to either surprise swapping that tanks p99 latency, or the OOM killer terminating the wrong process. This entry explains what each controls and how to tune them for memory-heavy workloads.

Related: Kubernetes Resource Requests, Limits, QoS Classes, and OOMKill Behavior for the container/cgroup side, and Transparent Huge Pages and Database Latency for the related THP gotcha, and NUMA Tuning for the vm.zone_reclaim_mode swap-with-free-RAM pathology on multi-socket hosts.

vm.swappiness

Controls how aggressively the kernel reclaims by swapping anonymous pages vs evicting file-backed (page-cache) pages. Range 0–100, default 60.

  • High (60+): the kernel swaps anonymous memory readily, even with RAM free — bad for databases whose working set is anonymous and must stay resident.
  • Low (1–10): prefer dropping page cache over swapping; keep process memory in RAM.
  • 0: avoid swap until free + file pages fall below the high watermark — not "never swap"; under real pressure it still swaps to avoid OOM.

sysctl vm.swappiness=10        # common for DB servers; persist in /etc/sysctl.d/

A swappiness of 1–10 is the usual recommendation for Postgres/MySQL/Redis hosts: you want the page cache to shrink before the engine's own memory gets paged to disk.

vm.overcommit_memory

Governs whether the kernel grants allocations that exceed available memory:

ModeBehavior

0 (default)Heuristic: estimate free memory, allow "reasonable" overcommit, reject obviously-too-large requests
1Always allow — malloc never fails; rely entirely on the OOM killer later
2Never overcommit — commit limited to swap + overcommit_ratio% of RAM (default ratio 50)

Mode 2 makes allocation failures visible (malloc returns NULL / mmap fails) instead of deferring to a later OOM kill — useful when you want deterministic failure. Redis recommends vm.overcommit_memory = 1 specifically so that the background-save fork() (which momentarily reserves a copy of the address space under copy-on-write) doesn't get rejected by the heuristic under memory pressure.

The OOM killer

When memory genuinely runs out (after overcommit promised too much), the OOM killer picks a victim by oom_score (roughly proportional to memory use, adjustable per-process via oom_score_adj, range -1000..1000). vm.oom_kill_allocating_task (default 0) makes it scan all tasks for the biggest; set to 1 to instead kill the task that triggered the OOM (cheaper, less "fair").

# Protect a critical process from the OOM killer:
echo -1000 > /proc/<pid>/oom_score_adj      # never kill (use sparingly)
echo -500  > /proc/<pid>/oom_score_adj      # strongly disfavor

Common gotchas

  • swappiness=0 does not mean "never swap". Under real pressure the kernel still swaps to avoid OOM. To truly disable swap, remove swap (swapoff) — but then you have no cushion and hit the OOM killer sooner.
  • Default swappiness=60 hurts databases. It pages out the engine's resident working set to grow page cache, spiking latency on the next access. Lower to ~1–10 on DB hosts.
  • Redis fork fails under overcommit_memory=0. BGSAVE/fork() reserves the address space; the heuristic can reject it during memory pressure, failing the save. Set vm.overcommit_memory = 1 for Redis (see Redis BGSAVE fork copy-on-write).
  • overcommit_memory=2 can make services fail to start. "Never overcommit" with a low overcommit_ratio rejects large mmap/JVM heap reservations; size the ratio (or overcommit_kbytes) to actual need.
  • The OOM killer often kills the wrong process. The biggest-RSS heuristic may target your database instead of the leaking sidecar. Use oom_score_adj to bias the choice, and check dmesg for the kill decision.
  • On a systemd distro, the kernel killer may not be the one that fired. Fedora and derivatives enable systemd-oomd by default: it watches cgroup v2 pressure-stall information and SIGKILLs a whole cgroup before allocation fails, so there is no dmesg OOM line and oom_score_adj has no effect on its choice. If a process vanished and the kernel log is silent, check the journal and oomctl dump first.
  • Containers add a second layer. cgroup memory limits trigger a cgroup-local OOM kill (exit 137) independent of host swappiness/overcommit. Host sysctls and cgroup limits both apply — see the Kubernetes OOMKill behavior entry.
  • Disabling swap entirely is not a free win. Without swap, the kernel can't push truly cold anonymous pages out, so cache pressure and OOM risk rise. A small swap + low swappiness is often better than none.
