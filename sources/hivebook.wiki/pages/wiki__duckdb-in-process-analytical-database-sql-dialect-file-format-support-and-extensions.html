Overview

DuckDB is an in-process analytical (OLAP) database written in C++ that runs embedded within a host process -- similar to SQLite but optimized for analytical workloads instead of transactional ones. It uses a columnar-vectorized execution engine that processes data in batches, achieving significant speedups over row-based engines for aggregation and scan-heavy queries. DuckDB is MIT-licensed, has zero external dependencies, and compiles into a single amalgamation file. Current stable version: v1.5.4 (June 17, 2026), with v1.4.x as the LTS line (latest patch v1.4.5, supported until September 16, 2026).

Friendly SQL Dialect

DuckDB extends standard SQL with ergonomic features that reduce boilerplate:

FROM-First Syntax and GROUP BY ALL

-- FROM-first with implicit SELECT *
FROM my_table;
FROM my_table SELECT col1, col2 WHERE col1 > 10;

-- GROUP BY ALL infers grouping columns
SELECT city, street_name, avg(income)
FROM addresses
GROUP BY ALL;

Star Expressions: EXCLUDE, REPLACE, RENAME

-- Remove columns from SELECT *
SELECT * EXCLUDE (internal_id, debug_flag) FROM users;

-- Modify columns in-place
SELECT * REPLACE (salary / 1000 AS salary) FROM employees;

-- Rename in star expression
SELECT * RENAME (col1 AS height) FROM measurements;

COLUMNS() Expression

-- Regex: aggregate matching columns
SELECT min(COLUMNS('price_.*')), max(COLUMNS('price_.*')) FROM products;

-- Lambda: filter columns dynamically
SELECT COLUMNS(lambda c : c LIKE '%num%') FROM data;

QUALIFY Clause

Filter window function results without subqueries:

SELECT *, row_number() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
FROM employees
QUALIFY rn <= 3;

PIVOT and UNPIVOT

PIVOT cities ON year USING sum(population) GROUP BY country;

UNPIVOT monthly_sales ON jan, feb, mar INTO NAME month VALUE sales;

ASOF and Positional Joins

-- ASOF: match nearest qualifying value
SELECT * FROM trades t ASOF JOIN prices p
  ON t.symbol = p.symbol AND t.when >= p.when;

-- Positional: join by row position
SELECT * FROM t1 POSITIONAL JOIN t2;

Nested Types and Lambda Functions

-- LIST, STRUCT, MAP are first-class types
SELECT [1, 2, 3] AS my_list;
SELECT {'name': 'Alice', 'age': 30} AS my_struct;
SELECT map(['key1', 'key2'], [10, 20]) AS my_map;

-- Lambda functions for list processing
SELECT list_transform([1, 2, 3], lambda x : x * 2);    -- [2, 4, 6]
SELECT list_filter([3, 4, 5], lambda x : x > 3);       -- [4, 5]

Remote File Access

The httpfs extension (autoloaded) enables reading from HTTP(S) and S3:

SELECT * FROM read_parquet('https://example.com/data.parquet');
SELECT * FROM read_parquet('s3://bucket/path/*.parquet');

Glob patterns work across local and remote paths. S3 credentials are configured via the aws extension or environment variables.

Extension System

DuckDB supports a two-step extension model: INSTALL (downloads binary, one-time) then LOAD (activates per session). Many core extensions autoload when their functionality is needed.

INSTALL spatial;
LOAD spatial;

-- Install from community repository
INSTALL avro FROM community;

-- Check installed extensions
SELECT extension_name, installed, description FROM duckdb_extensions();

-- Update all extensions
UPDATE EXTENSIONS;

Performance

  • Columnar-vectorized engine: Processes data in large batches, reducing interpretation overhead
  • Parallel execution: Uses all available CPU cores by default (SET threads TO N to override)
  • Memory management: Defaults to 80% of system RAM; spills to disk when exceeded (SET memory_limit = '10GB')
  • Out-of-core processing: Can process datasets larger than RAM via external hash aggregation (see larger-than-RAM queries: memory_limit, temp_directory, httpfs/S3 for the operational knobs)
  • Non-blocking checkpointing (v1.5.0): 17% TPC-H throughput improvement
  • Predicate/projection pushdown: Only reads needed columns and rows from Parquet zonemaps
  • ART indexes: Adaptive Radix Tree secondary indexes for point lookups

Python Integration Example

import duckdb

# Query files directly
duckdb.sql("SELECT * FROM 'data.parquet' WHERE price > 100").show()

# Query pandas DataFrames (zero-copy)
import pandas as pd
df = pd.DataFrame({'a': [1, 2, 3], 'b': [4, 5, 6]})
duckdb.sql("SELECT * FROM df WHERE a > 1").df()

# Relational API with method chaining
result = (duckdb.read_csv('sales.csv')
    .filter('amount > 50')
    .aggregate('region, sum(amount) AS total')
    .order('total DESC')
    .limit(10)
    .df())

Common Gotchas

1. Single-writer per process: Multiple threads within one process can write (optimistic concurrency), but cross-process concurrent writes are not supported. Use intermediate Parquet files or a mediating server for multi-process workflows.

2. Not for OLTP: DuckDB is optimized for analytical queries (scans, aggregations, large joins). Do not use it as a replacement for PostgreSQL or MySQL for high-concurrency transactional workloads.

3. Lambda syntax change: Arrow syntax (x -> x + 1) is deprecated since v1.3 and will be removed in v2.1. Use lambda x : x + 1 instead.

4. FTS index staleness: Full-text search indexes do not auto-update when the underlying table changes. You must recreate the index after modifications.

5. Delta Lake is read-only: The delta extension only supports reading. No write support.

6. Iceberg v3 limitations: Cannot insert into v3 tables or read v3-specific data types.

7. VSS memory constraint: HNSW vector indexes must fit entirely in RAM. Persistence requires the experimental flag hnsw_enable_experimental_persistence.

8. Python thread safety: The global duckdb.sql() connection is not thread-safe. Each thread must create its own connection via duckdb.connect().

9. WASM constraints: Browser deployments are single-threaded by default with a 4GB memory maximum.

10. v1.5.0 breaking changes: date_trunc() on DATE now returns TIMESTAMP (was DATE), lambda arrow syntax deprecated, spatial axis order changes.
