Kyverno: Kubernetes Policy Engine — ClusterPolicy, CEL ValidatingPolicy, PolicyException, and What Changed in 1.17

Overview

Kyverno is a CNCF-graduated policy engine for Kubernetes. It runs as an admission controller and uses Kubernetes-native CRDs to validate, mutate, generate, and clean up cluster resources — no Rego or custom DSL required. Policies are written in YAML with optional CEL (Common Expression Language) expressions. Kyverno graduated CNCF on 2026-03-16, making it the second graduated policy engine alongside OPA/Gatekeeper.

Key differentiator vs Gatekeeper: Kyverno writes policies as plain Kubernetes YAML (match/exclude/validate/mutate/generate) instead of Rego, and it can mutate and generate resources — not just reject them. As of v1.17 (2026-02-02) Kyverno additionally offers a new CEL-native policy family (ValidatingPolicy, MutatingPolicy, GeneratingPolicy, DeletingPolicy, ImageValidatingPolicy) that aligns with the built-in ValidatingAdmissionPolicy model upstream Kubernetes shipped in 1.30.

This entry covers the current stable lines, the dual policy model (classic ClusterPolicy vs new CEL ValidatingPolicy), the admission/background/reports/cleanup controller split, PolicyException, Pod Security integration, image signature verification, openreports output, and 20 operational gotchas.

Architecture — Four Controllers

The standard Helm install ships four controllers. Only the admission controller is mandatory; the others are opt-in via Helm values.

ControllerRequiredWhat it does

Admission controllerYesTerminates MutatingWebhookConfiguration + ValidatingWebhookConfiguration. Evaluates mutate/validate rules on every admission request.
Background controllerOptionalRuns generate and mutate-existing rules against resources already in the cluster (not on admission).
Reports controllerOptionalAggregates policy evaluation results into PolicyReport/ClusterPolicyReport (or openreports).
Cleanup controllerOptionalExecutes CleanupPolicy / DeletingPolicy on a schedule (CronJob-style).

The admission controller is called by the API server for every matching resource Create/Update/Delete. Webhook failure policy defaults to Ignore for validating webhooks (fail-open) and Fail for mutating webhooks — misconfiguring this is one of the most common operational issues (see Gotchas).

For high availability, the official Helm chart exposes separate replicaCount for each controller; production installs typically run 3 admission replicas + 2 background/reports + 1 cleanup, all spread by a topologySpreadConstraint on kubernetes.io/hostname.

Policy Types

As of v1.17 Kyverno has two parallel families. Both are fully supported and can coexist in the same cluster; pick per-policy based on what you need.

Classic family — kyverno.io/v1 / v2beta1

KindScopeUse for

ClusterPolicyClusterValidate / mutate / generate / verifyImages — the original, most-used kind
PolicyNamespacedSame capabilities, scoped to a single namespace
PolicyExceptionNamespacedExempt specific resources from named policy rules
ClusterCleanupPolicy / CleanupPolicyBothSchedule-driven resource deletion

CEL family — policies.kyverno.io/v1beta1 (v1.17+)

KindNamespaced variantReplaces classic rule

ValidatingPolicy (VPOL)NamespacedValidatingPolicy (NVPOL)validate
MutatingPolicy (MPOL)NamespacedMutatingPolicy (NMPOL)mutate
GeneratingPolicy (GPOL)NamespacedGeneratingPolicy (NGPOL)generate
ImageValidatingPolicy (IVPOL)NamespacedImageValidatingPolicy (NIVPOL)verifyImages
DeletingPolicy (DPOL)NamespacedDeletingPolicy (NDPOL)CleanupPolicy

CEL-family CRDs use a matchConstraints + validations[].expression shape identical to Kubernetes' built-in ValidatingAdmissionPolicy, which means a Kyverno ValidatingPolicy can be auto-emitted as a native ValidatingAdmissionPolicy (enabled by default since v1.15) and offloaded to the API server — zero webhook latency for that rule.

Classic ClusterPolicy is not deprecated as of v1.17.2, but new authoring material and samples increasingly use the CEL family. Large production deployments typically use both: classic ClusterPolicy for mutate/generate and Pod Security, CEL ValidatingPolicy for pure validation that should be offloaded to VAP.

Classic ClusterPolicy — Validation Example

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-app-label
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: check-for-app-label
      match:
        any:
          - resources:
              kinds: ["Pod"]
              operations: ["CREATE", "UPDATE"]
      exclude:
        any:
          - resources:
              namespaces: ["kube-system", "kyverno"]
      validate:
        message: "Pods must have an 'app' label."
        pattern:
          metadata:
            labels:
              app: "?*"

validationFailureAction controls what happens on a policy violation:

  • Enforce — Admission request is rejected. Resource is not created/updated.
  • Audit — Admission request is allowed; the violation is recorded in a PolicyReport / ClusterPolicyReport.

Start in Audit and flip to Enforce once reports are clean. The field is mutable, so the transition is just a policy edit.

Pattern vs deny vs foreach:

  • pattern: — positive overlay; the resource must match this shape. Use "?*" for "must exist and non-empty", "!*" for forbidden.
  • deny: — imperative block with conditions.any/conditions.all using operators (Equals, In, GreaterThan, Contains, …). Good for request-attribute checks like blocking DELETE of certain kinds.
  • foreach: — iterate over spec.containers[] etc. Essential for multi-container pods.

Autogen is the most misunderstood feature: Kyverno automatically duplicates a Pod rule onto all controllers that produce Pods (Deployment, StatefulSet, DaemonSet, Job, CronJob, ReplicaSet). The rule you write matches kind: Pod; Kyverno generates shadow rules (visible in the policy status) that match the controller pod-template path. Set metadata.annotations: pod-policies.kyverno.io/autogen-controllers: none to disable if you specifically want to target Pods only (e.g., bare pods created by another operator).

CEL ValidatingPolicy — Same Rule, New Syntax

apiVersion: policies.kyverno.io/v1beta1
kind: ValidatingPolicy
metadata:
  name: require-app-label-cel
spec:
  validationActions: ["Deny"]     # Deny | Audit | Warn (may combine)
  evaluation:
    admission:
      enabled: true
    background:
      enabled: true
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        resources: ["pods"]
        operations: ["CREATE", "UPDATE"]
  validations:
    - expression: "has(object.metadata.labels) && 'app' in object.metadata.labels && object.metadata.labels['app'] != ''"
      messageExpression: "'Pod ' + object.metadata.name + ' is missing the app label.'"

CEL reserved variables inside expression: object (the new object), oldObject (on UPDATE), request (AdmissionRequest), params (when bound via ParamKind), namespaceObject, authorizer.

New CEL libraries available in v1.17 (in addition to stdlib): kubernetes (semver compare), hash (sha256/sha512), math.round, json.parse/json.marshal, yaml.parse, x509.decodeCert, time.now()/time.truncate, random, quantity (Kubernetes resource quantities), resource.Get(gvr, ns, name) / resource.List(gvr, ns) for cross-resource lookups, image.parseImageReference (renamed from image() in v1.15).

evaluation.admission / evaluation.background control where the policy runs. CEL policies support both; toggle background off for hot paths where you don't want reports generated on every existing resource.

Mutation Example

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: add-default-resources
spec:
  rules:
    - name: set-cpu-mem-requests
      match:
        any:
          - resources: { kinds: ["Pod"] }
      mutate:
        patchStrategicMerge:
          spec:
            containers:
              - (name): "*"
                resources:
                  requests:
                    +(cpu): "100m"
                    +(memory): "128Mi"

Key mutation anchors:

  • +(key): "add if absent" — non-destructive, preserves user-specified values.
  • (key): "conditional" — match this path but do not modify.
  • =(key): "global" — always set.
  • ^(key): "add to array if missing".
  • -(key): "remove".

patchesJson6902: is also supported when strategic merge can't express the change. For existing resources, use mutate.targets + mutate.mutateExistingOnPolicyUpdate: true (runs in the background controller).

Generation Example

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: default-deny-netpol
spec:
  rules:
    - name: create-default-deny
      match:
        any:
          - resources: { kinds: ["Namespace"] }
      generate:
        synchronize: true
        apiVersion: networking.k8s.io/v1
        kind: NetworkPolicy
        name: default-deny
        namespace: "{{request.object.metadata.name}}"
        data:
          spec:
            podSelector: {}
            policyTypes: ["Ingress", "Egress"]

synchronize: true is critical: without it, if someone deletes the generated default-deny NetworkPolicy, Kyverno does not recreate it. With synchronize: true, Kyverno watches the target and reconciles on drift — this is the setting you want for security baselines. Generate rules require the background controller; they are silently a no-op if you disabled it.

Generate rules pair well with Calico CNI or Cilium CNI for enforcing default-deny NetworkPolicies in every new namespace.

Image Verification (Cosign / Sigstore)

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-images
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30    # signature verify is SLOW; bump from default 10
  rules:
    - name: check-signature
      match:
        any:
          - resources: { kinds: ["Pod"] }
      verifyImages:
        - imageReferences:
            - "ghcr.io/myorg/*"
          attestors:
            - entries:
                - keyless:
                    subject: "https://github.com/myorg/ci/.github/workflows/build.yml@refs/heads/main"
                    issuer: "https://token.actions.githubusercontent.com"
          mutateDigest: true      # pin tag to immutable digest on admission
          verifyDigest: true

mutateDigest: true is the hidden superpower: Kyverno rewrites image: myrepo:v1 to image: myrepo@sha256:... at admission time. Without this, a tag can be repointed to a new image after admission and bypass your signature check. The equivalent on the new IVPOL CRD uses spec.images + spec.attestors.

PolicyException — Surgical Exemptions

Exemptions are their own CRD so the policy YAML remains immutable (important for GitOps via Argo CD or Flux CD):

apiVersion: kyverno.io/v2beta1
kind: PolicyException
metadata:
  name: ingress-controller-needs-privilege
  namespace: ingress-nginx
spec:
  exceptions:
    - policyName: require-app-label
      ruleNames: ["check-for-app-label"]
  match:
    any:
      - resources:
          kinds: ["Pod"]
          namespaces: ["ingress-nginx"]
          names: ["ingress-nginx-controller-*"]

Gotcha: PolicyException is not enabled by default. Install with Helm value features.policyExceptions.enabled=true and set features.policyExceptions.namespace=<controlled-ns> to restrict where exceptions may be created — otherwise any namespace admin can silently exempt themselves. For CEL policies, PolicyException works with spec.celExceptions + the matching CEL policy must reference it.

Pod Security Standards (Built-in)

Kyverno ships a podSecurity subrule that evaluates upstream Kubernetes Pod Security Standards without writing individual rules:

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: psp-restricted
spec:
  validationFailureAction: Enforce
  rules:
    - name: restricted
      match:
        any:
          - resources: { kinds: ["Pod"] }
      validate:
        podSecurity:
          level: restricted      # privileged | baseline | restricted
          version: "v1.34"       # pin to a K8s release
          exclude:                # control-by-control relaxation
            - controlName: "Privilege Escalation"
              images: ["ghcr.io/approved/*"]

This replaces hand-rolling ~20 ClusterPolicy rules (run-as-non-root, read-only root FS, drop caps, hostPath, etc.). As of v1.17, supported PSS versions include K8s 1.30–1.32 profiles. level: restricted + version: latest is the recommended greenfield baseline; migrations from PodSecurityPolicy typically start at level: baseline.

Policy Reports (openreports)

Audit results land in PolicyReport (namespaced) and ClusterPolicyReport (cluster). As of v1.15 Kyverno also emits the openreports.io format (alpha) in parallel — same data, slightly different schema, shared between Kyverno, Trivy, Falco, and Polaris. Toggle via Helm value reportsController.openreports.enabled=true.

kubectl get policyreport -A
kubectl get clusterpolicyreport
kubectl get -n default policyreport -o json \
  | jq '.items[].results[] | select(.result=="fail") | {policy, rule, resources: .resources[0].name}'

Reports are aggregated per resource, not per evaluation, and the reports controller coalesces events — do not treat a PolicyReport as an audit trail. For a forensic trail use Kubernetes audit logs with the Kyverno webhook annotations (policies.kyverno.io/patches) or wire the events to Falco / Loki.

Installation

helm repo add kyverno https://kyverno.github.io/kyverno/
helm repo update

helm install kyverno kyverno/kyverno \
  --namespace kyverno --create-namespace \
  --version 3.5.2 \              # chart version, not app version
  --set admissionController.replicas=3 \
  --set backgroundController.replicas=2 \
  --set reportsController.replicas=2 \
  --set cleanupController.replicas=1 \
  --set features.policyExceptions.enabled=true \
  --set features.policyExceptions.namespace=kyverno-exceptions

Install into its own namespace — never kube-system. Kyverno's webhooks self-exclude kyverno and kube-system by default via resourceFilters in its ConfigMap; if you put Kyverno elsewhere you must update the filter or the admission controller can try to validate its own pods and deadlock the cluster.

Chart versions track the app loosely: Helm chart 3.5.x → Kyverno 1.17.x, chart 3.4.x → Kyverno 1.16.x, chart 3.3.x → Kyverno 1.15.x. Use helm search repo kyverno/kyverno --versions and match to the Kyverno app tag you want.

When to pick what:

  • VAP (in-tree) — pure validation on a hot admission path with minimum latency. Works for single-kind simple checks. Kyverno can auto-generate VAP from ValidatingPolicy for offloading.
  • Kyverno — anything involving mutate, generate, image verification, cleanup, cross-resource lookup, or centralized reporting. Also the right choice for platforms that need non-developers to write policy (YAML is more approachable than Rego).
  • Gatekeeper — you have existing Rego investment (OPA-anywhere patterns) or a policy library (Gatekeeper Library) you want to keep using.

What Changed in 1.17 (2026-02-02)

1. CEL policies bumped from v1alpha1 → policies.kyverno.io/v1beta1: ValidatingPolicy, MutatingPolicy, GeneratingPolicy, DeletingPolicy, ImageValidatingPolicy — all five, plus PolicyException.
2. GlobalContextEntry moved to kyverno.io/v2 with DynamicInformer optimization — cross-resource lookups in CEL (resource.Get, resource.List) are now cache-backed rather than live-API.
3. Namespaced variants of all CEL policies — NamespacedValidatingPolicy, NamespacedMutatingPolicy, NamespacedGeneratingPolicy, NamespacedImageValidatingPolicy, NamespacedDeletingPolicy. Scopes a CEL policy to a single namespace without touching RBAC.
4. Pod Security Standards extended to K8s 1.30–1.32 profiles in the podSecurity subrule.
5. Non-RSA key algorithms supported in the auto-generated admission controller certificates (ECDSA, Ed25519).
6. New CEL libraries: hash, math.round, json.parse/marshal, yaml.parse, x509.decodeCert, time.now()/time.truncate, random, and Kubernetes semver comparison.
7. Kubernetes 1.35 support added to the admission/background/cleanup controllers.
8. v1.17.1 (2026-02-19) was a bug-fix point release (data races, nil panics). v1.17.2 (2026-04-23) is the latest stable; v1.18.0-rc.1 (2026-04-21) is the next minor in RC.

What Changed in 1.16 (2025-11-10)

  • Introduced v1beta1 for CEL policies (promoted out of v1alpha1).
  • Added the first three namespaced CEL variants (NamespacedValidatingPolicy, NamespacedImageValidatingPolicy, NamespacedDeletingPolicy).
  • CEL quantity library for comparing Kubernetes resource quantities (quantity("256Mi")).
  • Event generation for CEL policies + configurable policy reporting per-label.
  • spec.evaluation.mode field made selector-addressable.
  • Performance metrics for CEL compilation + evaluation.

What Changed in 1.15 (2025-07-31)

  • Added MutatingPolicy (MPOL), GeneratingPolicy (GPOL), DeletingPolicy (DPOL) as CEL-native peers of ValidatingPolicy.
  • Switched policy reporting to openreports (alpha) alongside the existing PolicyReport schema.
  • Enabled ValidatingAdmissionPolicy auto-generation by default from ClusterPolicy — this is the change that makes K8s-native offloading the happy path.
  • Background reporting for MutatingAdmissionPolicy.
  • Renamed CEL operator image() → parseImageReference.
  • Removed deprecated CLI APIs (Kyverno CLI users on <1.14 must update).

Minimum Production Recipe

# 1. Install Kyverno with HA + exceptions enabled
helm install kyverno kyverno/kyverno \
  -n kyverno --create-namespace --version 3.5.2 \
  --set admissionController.replicas=3 \
  --set features.policyExceptions.enabled=true \
  --set features.policyExceptions.namespace=kyverno-exceptions
kubectl create ns kyverno-exceptions

# 2. Install the Pod Security baseline policies
helm install kyverno-policies kyverno/kyverno-policies \
  -n kyverno --version 3.5.2 \
  --set podSecurityStandard=restricted \
  --set validationFailureAction=Audit     # start in Audit!

# 3. Watch reports for a week; nothing in Enforce yet
kubectl get clusterpolicyreport -o json | jq '.items[].summary'

# 4. Flip to Enforce once reports are clean
kubectl patch clusterpolicy disallow-privileged-containers \
  --type=merge -p '{"spec":{"validationFailureAction":"Enforce"}}'

# 5. Install Kyverno CLI for local policy testing
curl -LO https://github.com/kyverno/kyverno/releases/download/v1.17.2/kyverno-cli_v1.17.2_linux_x86_64.tar.gz
tar -xzf kyverno-cli_v1.17.2_linux_x86_64.tar.gz && sudo mv kyverno /usr/local/bin/
kyverno version

# 6. Test policies locally against sample resources (pre-commit hook)
kyverno test ./policies/
kyverno apply ./policies/ --resource ./test-resources.yaml

Gotchas

1. Webhook failurePolicy: Fail on the mutating webhook + Kyverno down = cluster frozen. Every admission request hangs for 10–30 s then fails. Always run ≥2 admission replicas with PodDisruptionBudget minAvailable: 1 and anti-affinity. The validating webhook defaults to Ignore (fail-open); leave it that way unless you understand the blast radius.
2. Do not install Kyverno into kube-system. The default resourceFilters in the kyverno ConfigMap excludes kyverno + kube-system from admission; putting Kyverno elsewhere means Kyverno tries to validate its own pods and can deadlock cluster startup.
3. validationFailureAction: Enforce on day 1 is the single biggest outage pattern. Ship every new policy in Audit, let reports accumulate, then flip to Enforce. The field is mutable so this is a one-line patch.
4. Autogen doubles your effective rule count. A Pod-kind rule silently generates autogen- duplicates for Deployment/StatefulSet/Job/CronJob/DaemonSet/ReplicaSet. Check kubectl describe clusterpolicy to see the full list before you think "I only wrote one rule".
5. Generate rules need the background controller (default on in Helm but commonly disabled in stripped HA installs). Without it, generate: silently does nothing. Same for mutateExisting.
6. synchronize: false on generate = fire-and-forget. Deleting the generated resource does not recreate it. Security baselines (default-deny NetworkPolicy, default ResourceQuota) must use synchronize: true.
7. verifyImages without mutateDigest: true is bypassable. An attacker can repoint a tag after admission. Either pin to digest at admission (mutateDigest: true) or set verifyDigest: true + require digest-only image references in a separate policy.
8. webhookTimeoutSeconds default is 10 s. Cosign/keyless signature verification in verifyImages often exceeds this on first-call (TUF root, Rekor lookup). Bump to 30 s per-policy.
9. ClusterPolicy vs Policy naming collisions. A ClusterPolicy and a namespaced Policy with the same name are different resources. Reports reference them by scope-qualified name; kubectl get polr -A can confuse them if you do not grep.
10. CEL ValidatingPolicy auto-generates ValidatingAdmissionPolicy (since v1.15), which requires K8s ≥1.30 with the ValidatingAdmissionPolicy feature gate enabled and RBAC for Kyverno to create them. On EKS/AKS/GKE this is on by default; on bare-metal 1.28/1.29 it is a silent no-op.
11. PolicyException is off by default. Helm value features.policyExceptions.enabled=true + features.policyExceptions.namespace=<ns>. Without the namespace restriction, any namespace admin can exempt their own workloads from policy.
12. Background scans can thrash etcd when a new policy applies to every Pod in a 5000-node cluster. Stage policy rollouts; set background: false until the admission path is clean, then turn it on to sweep existing resources.
13. Pod Security podSecurity subrule version mismatches the cluster. Pinning version: "v1.32" on a 1.34 cluster means you miss new controls. Use version: "latest" in 1.17+ or pin to your cluster's minor.
14. Mutate rule order matters. Multiple ClusterPolicy mutations apply in policy-name alphabetical order; the final patch is an ordered sequence of strategic merges. Watch for rules that overwrite each other silently.
15. resource.Get/List CEL functions need RBAC. If a CEL policy calls resource.List("v1/configmaps", ns), the Kyverno ServiceAccount must have list configmaps in that namespace. Errors surface as UNKNOWN evaluation results in the PolicyReport, not as webhook failures.
16. Reports controller can OOM on large clusters. Each resource generates one report entry per matching rule; default requests are 100m CPU / 128Mi memory. At ~10k pods × 30 rules, bump to 500m / 1Gi or reports fall behind and policy counters go stale.
17. Kyverno CLI version must match the controller for kyverno test / kyverno apply. A kyverno-cli 1.17.x running against a policy written for 1.15 CEL shapes fails schema validation even though the cluster accepts it. Pin in CI.
18. PolicyException for CEL policies is separate from classic PolicyException. CEL policies reference exceptions via spec.celExceptions with its own match shape; you cannot reuse a classic PolicyException to exempt a ValidatingPolicy.
19. Cluster upgrade order: CRDs first, then the admission controller. A Helm upgrade that runs both at once can 502 the webhook for a few seconds during the rollout. Use helm upgrade --wait + a pre-install CRD job, or install the CRDs via a separate kyverno-crds chart.
20. kubectl delete clusterpolicy does NOT rollback its mutations or generations. Mutated fields stay mutated; generated resources stay generated (unless synchronize: true — then they are deleted). Plan for policy removal like a migration, not a rollback.
