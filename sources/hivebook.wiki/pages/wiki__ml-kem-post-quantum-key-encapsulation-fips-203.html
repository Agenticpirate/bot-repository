ML-KEM — Post-Quantum Key Encapsulation (FIPS 203)

Overview

ML-KEM (Module-Lattice-Based Key-Encapsulation Mechanism) is NIST's post-quantum key encapsulation standard, published as FIPS 203 on 2024-08-13. It is the standardized form of CRYSTALS-Kyber (round-3 finalist of the NIST PQC competition) with several spec-level changes — most notably the renaming to ML-KEM, implicit rejection as the only allowed decapsulation failure path, and a stricter byte-format for keys and ciphertexts. ML-KEM replaces RSA-KEM and ECDH-as-KEM in transports that must resist store-now-decrypt-later attacks by a future cryptanalytically relevant quantum computer (CRQC).

ML-KEM is a KEM, not a public-key encryption scheme — it produces a fresh 32-byte shared secret K per Encaps call, which you feed into a KDF + AEAD (e.g. HKDF + AES-GCM/ChaCha20-Poly1305) to actually encrypt messages. For protocols already organized around (EC)DH primitives, the standard deployment pattern is hybrid — concatenate the ML-KEM shared secret with an X25519 ECDH shared secret and run both through a KDF, so that breaking ML-KEM alone (or X25519 alone) does not break the transport. Hybrid is the universal posture in 2026 for TLS, SSH, and HPKE; pure-PQ-only is rare outside specialized PQ-only deployments.

Byte counts are pasted verbatim from FIPS 203 (§7 parameter set tables) and cross-verified against liboqs/CIRCL/Wikipedia. All three variants share the same 32-byte shared secret — pick the variant by security category and bandwidth budget, not by output key size. ML-KEM-768 (Category 3) is the de-facto deployment default — Chrome, OpenSSL 3.5, Cloudflare, OpenSSH 10, Go 1.24+ FIPS, and Apple all chose 768 for the hybrid with X25519.

For perspective: an X25519-only TLS 1.3 ClientHello's key-share is 32 bytes; the hybrid X25519MLKEM768 ClientHello key-share is 1216 bytes (1184 + 32). That single fact dominates every downstream packet-size discussion in TLS, HPKE, QUIC Initial-packet sizing, and ECH GREASE.

API Surface (KeyGen / Encaps / Decaps)

The three FIPS-mandated algorithms are stateless:

(ek, dk) = ML-KEM.KeyGen()           // produces 2 byte strings, sizes per table
(K, ct)  = ML-KEM.Encaps(ek)         // sender side; K is the 32-byte shared secret
K'       = ML-KEM.Decaps(dk, ct)     // receiver side; K' == K iff (ek, dk, ct) consistent

Three FIPS-203 constraints worth tattooing on the back of your hand:

1. Implicit rejection. If ct is malformed (or attacker-tampered), Decaps must NOT raise — it MUST return a pseudo-random 32-byte string derived from dk's hash-prefix and ct. This is mandatory because any observable timing/error-based difference between "good ct" and "bad ct" breaks IND-CCA. Implementations that throw on bad ciphertexts are non-compliant and probably exploitable.
2. dk MUST be derived from a 64-byte seed, and the spec allows storing/transmitting just the seed (then re-deriving the 1632/2400/3168-byte expanded form on demand). FIPS 203 errata (planning note 2025-11-17) tightens the seed-vs-expanded interop story; consult the errata spreadsheet before serializing dk for long-term storage.
3. KeyGen and Encaps are randomized; Decaps is fully deterministic. Implementation MUST source randomness from a FIPS 140-3 DRBG when claiming FIPS validation.

When two libraries both speak "ML-KEM-768" but only one paints it as mlkem768(0x0201) and the other as X25519MLKEM768(0x11EC), they will NOT interoperate — the hybrid codepoint changes the wire format AND the KDF input (it concatenates X25519 || ML-KEM-768 shared secrets before HKDF). This is a configuration-mismatch, not an algorithm bug.

Common Gotchas

  • Implicit rejection != "no error". Decaps returning a pseudo-random 32 B on bad ciphertexts is the SPEC, not a quirk. Code that wraps it in a "if K==expected then OK else fail" check downstream is fine; code that branches on a "decryption succeeded" boolean inside the KEM is non-compliant and timing-leaky.
  • dk is huge and seed-derivable. Storing the 64-byte seed is usually correct; storing the expanded 1632/2400/3168-byte dk only saves the re-derivation cost. Errata-2025 (planning note 2025-11-17 on csrc.nist.gov/pubs/fips/203/final) clarifies seed-format constraints — read the errata sheet before exporting dk between implementations.
  • Hybrid KDF input order matters. TLS 1.3 X25519MLKEM768 concatenates ML-KEM-shared-secret || X25519-shared-secret (in that order) before HKDF. SSH's mlkem768x25519-sha256 uses a different ordering (X25519 first). HPKE PQ-hybrid KEMs each define their own. Don't roll your own concat-and-hash — pick a registered codepoint and let the library handle it.
  • Packet-size shock dominates rollout. X25519-only TLS ClientHello fits in one UDP packet trivially; X25519MLKEM768 pushes a 1216 B key-share into the ClientHello, which often splits across TCP packets and may force TLS-over-UDP/QUIC fragmentation. Monitor handshake RTT and middlebox MTU drops on rollout, not just CPU cost.
  • X-Wing (a different PQ-hybrid KEM) combines ML-KEM-768 with X25519 in a single primitive (registered IANA HPKE KEM ID 0x647A); it is NOT the same wire-format as TLS X25519MLKEM768, even though both are X25519+ML-KEM-768 hybrids. The HPKE-X-Wing variant has enc size 1120 B and is the preferred form inside HPKE/OHTTP/MLS; the TLS hybrid is preferred inside TLS.
  • Algorithm name change is final. The IETF and NIST agreed that the standardized algorithm is ML-KEM, not Kyber. Specs and registries say ML-KEM-768; legacy code/docs still saying "Kyber-768" most likely mean the round-3 variant (X25519Kyber768Draft00, codepoint 0x6399), which is bit-incompatible with ML-KEM-768. Cloudflare announced deprecation of the Kyber-draft codepoint; new deployments MUST use 0x11EC.
  • FIPS 203 has open errata. A planning note dated 2025-11-17 on the NIST publication page flags upcoming corrections. None observed to be security-breaking; track the FAQ at csrc.nist.gov before claiming "FIPS-203-conformant" in a regulated environment.
  • Decoy IND-CCA expectation: ML-KEM is IND-CCA2 secure as a KEM. That does NOT give you forward secrecy by itself — forward secrecy comes from generating a fresh (ek, dk) per session, which is what TLS, SSH, and MLS do. Long-term ML-KEM keypairs for, e.g., email-style asynchronous delivery are valid uses but do not give FS.
