Overview

The OAuth Extensions Error Registry is one of 13 IANA-maintained registries under OAuth Parameters (13 as of 2026-08-21; the newest is OAuth Status Types, populated from the Token Status List draft still in the RFC Editor queue as RFC-ietf-oauth-status-list-21, with values VALID 0x00 / INVALID 0x01 / SUSPENDED 0x02). It is the authoritative list of every standardized OAuth error-code identifier — what error=… strings a client may legitimately see in an authorization-endpoint redirect, a token-endpoint JSON 400, a resource-server WWW-Authenticate 401/403, or a Dynamic-Client-Registration 400. The registry was established by RFC 6749 §11.4; new entries are added through "Specification Required" (RFC 8126) review by designated experts on the oauth-ext-review@ietf.org mailing list.

The registry matters for two practical reasons. First, error codes are not extensible at the wire: clients written against a closed enum will see new codes (e.g. use_dpop_nonce from DPoP RFC 9449, invalid_target from RFC 8707) as servers adopt new extensions. Second, the same string can mean different things in different usage locations — access_denied at the authorization endpoint (RFC 6749) is a user-consent failure, but access_denied at the token endpoint (RFC 8628 device flow) means the user explicitly declined the device authorization request. The registry's Usage Location column is load-bearing.

Registration template (RFC 6749 §11.4)

To register a new error code, the introducing specification supplies:

Error name:                <ascii_string>
Error usage location:      <authorization endpoint | token endpoint
                            | token error response | resource access error response
                            | revocation endpoint error response | registration endpoint
                            | implicit grant error response | ...>
Related protocol extension: <name of the OAuth extension>
Change controller:         <IETF | IESG | OpenID Foundation … WG | Kantara … WG | …>
Specification document(s): <RFC or stable URL>

Error name must be drawn from the set %x20-21 / %x23-5B / %x5D-7E — that restriction is in the registration template itself, RFC 6749 §11.4.1, and is repeated for the wire value of error in §4.1.2.1 (authorization endpoint) and §5.2 (token endpoint). The three sub-ranges are what exclude %x22 double-quote and %x5C backslash; the flat range %x20-7E would include both. (Corrected 2026-08-21 against the RFC text.) Note also that §11.4.1 enumerates only four canonical usage-location values — authorization code grant error response (§4.1.2.1), implicit grant error response (§4.2.2.1), token error response (§5.2), resource access error response (§7.2); the longer set of location strings above is what IANA has actually recorded as later extensions registered their own endpoints. Names cannot collide within a usage location; cross-location collisions are allowed (see access_denied at both authorization endpoint and token endpoint in the device-grant case).

Registration requires "Specification Required" review — RFC 6749 §11.4 cites RFC 5226, which RFC 8126 has since obsoleted as the current IANA-considerations BCP. Reviewers post to oauth-ext-review@ietf.org. Designated experts can request changes; the two-week review window is specified in §11.4 itself ("after a two-week review period on the oauth-ext-review@ietf.org mailing list"), and the IANA registry note repeats that experts should notify IANA within two weeks. Note the one carve-out §11.4 does allow: "to allow for the allocation of values prior to publication, the Designated Expert(s) may approve registration once they are satisfied that such a specification will be published." There is no provisional registration — codes don't appear in the registry until the underlying spec ships.

The error code is in the fragment for response_type=token (legacy implicit), in the query for response_type=code, and in the JSON body for token/resource/registration paths. OAuth 2.1 removes the implicit grant so response_type=token errors are receding from real-world traffic.

Companion fields (RFC 6749 §4.1.2.1 / §5.2 / RFC 6750 §3)

Every error response can carry these optional fields next to error:

  • error_description — human-readable; %x20-21 / %x23-5B / %x5D-7E ASCII (no quote, no backslash, no CR/LF).
  • error_uri — pointer to a documentation page. RFC 6749 requires it to "conform to the URI-reference syntax" with characters restricted to %x21 / %x23-5B / %x5D-7E; it does not require an absolute URI (corrected 2026-08-21 — §4.1.2.1 and §5.2 both use the URI-reference wording).
  • state — opaque CSRF round-trip token, REQUIRED if the client sent one. Authorization-endpoint only: it is defined in §4.1.2.1 (and §4.2.2.1 for the implicit grant), and is not one of the token-endpoint error fields — §5.2 defines exactly error, error_description, error_uri in a JSON body. A client that expects state back from the token endpoint is expecting a field the RFC never puts there.

Some extensions add their own fields. RFC 9449 (DPoP) adds the WWW-Authenticate: DPoP nonce="…" header alongside error="use_dpop_nonce". RFC 9728 §5.1 adds the resource_metadata parameter to WWW-Authenticate. RFC 9470 adds acr_values and max_age to the step-up challenge. These are not registered in the error registry — they're parameters that travel with errors.

Error-code semantics agents need to know

These are the ones AI agents implementing OAuth clients (e.g. an MCP client) actually have to handle correctly:

invalid_target (RFC 8707)


Returned when the resource parameter is missing/unknown/multi-valued-in-a-context-that-doesn't-allow-it. Overloaded — same code for "URI contains fragment" and "AS doesn't recognize this resource" and "client requested multiple resources but AS only issues single-audience tokens". error_description is the only disambiguator. Affects clients implementing RFC 8707 on AWS Cognito (silently drops resource, never returns invalid_target) vs Auth0 / Okta / Keycloak (return invalid_target correctly).

invalid_dpop_proof / use_dpop_nonce (RFC 9449)


DPoP-specific. invalid_dpop_proof means the DPoP JWT failed validation (signature, htm/htu mismatch, iat out of window, jti replay). use_dpop_nonce is the AS or RS telling the client "your DPoP proof is structurally fine but I want a nonce-bound proof — here's the nonce, retry". Clients must retry with the new nonce; the second attempt is success-path, not error-path. See DPoP entry for the full nonce dance.

insufficient_user_authentication (RFC 9470)


The RS is asking the client to step up authentication (e.g. "this token was issued via SMS OTP; this endpoint requires WebAuthn"). Comes with acr_values and/or max_age in WWW-Authenticate. Clients re-run the authorization flow with the requested acr_values parameter and present the new token. The MCP Authorization spec explicitly uses this for scope-step-up on tools that need elevated privilege.

slow_down vs authorization_pending (RFC 8628)


Device-flow specific. authorization_pending means "user hasn't approved yet, keep polling at the current interval". slow_down means "you're polling too fast, increase your interval by at least 5 seconds". Clients that ignore slow_down and keep polling at the same rate will get access_denied from rate-limited ASes after a few seconds.

invalid_grant (RFC 6749)


The most-abused string in OAuth. Catches: expired authorization code, already-used authorization code, expired refresh token, revoked refresh token, mismatched redirect_uri, mismatched code_verifier, refresh-token-rotation-detected-replay, audience mismatch, and ~10 other ASes' interpretations. Always log the full body — error_description is the only signal that disambiguates "user revoked consent" from "your PKCE verifier doesn't match".

invalid_redirect_uri / invalid_client_metadata (RFC 7591)


Dynamic Client Registration. Attribution corrected 2026-08-21: RFC 7591 §3.2.2 defines this code in a single sentence — "The value of one or more redirection URIs is invalid" — and mandates nothing about schemes, fragments or loopback; its only illustration is a non-normative example rejecting http://sketchy.example.com. The rules an AS is actually enforcing when it returns this come from elsewhere: RFC 6749 §3.1.2 ("The redirection endpoint URI MUST be an absolute URI as defined by [RFC3986] Section 4.3 … MUST NOT include a fragment component"), RFC 8252 for native-app loopback and custom schemes, and OAuth 2.1 for exact-match plus the http://localhost exception. In practice invalid_redirect_uri is whatever the AS's own policy rejects, so read the AS's docs, not RFC 7591, to predict it. invalid_client_metadata covers everything else (unsupported token_endpoint_auth_method, malformed jwks, etc.).

Relationship to RFC 9457 Problem Details

OAuth uses its own flat {error, error_description, error_uri, state} JSON shape — not RFC 9457 Problem Details for HTTP APIs. The two are conceptually overlapping but wire-incompatible. There is no IETF draft to migrate OAuth to Problem Details; the registries are independent. If you proxy an OAuth error through a non-OAuth API, you can wrap the OAuth body in a type=https://datatracker.ietf.org/doc/html/rfc6749 Problem Details envelope, but the OAuth client cannot consume that — it expects the flat shape.

Common gotchas

  • access_denied is duplicated — once at the authorization endpoint (user declined consent, RFC 6749) and once at the token endpoint response (user declined the device authorization, RFC 8628). The string is identical; the location disambiguates. Clients that branch only on error without inspecting endpoint context can mis-handle device-flow rejections as authorization-flow rejections.
  • error_description is OPTIONAL and unstable. Don't if error_description == "..." parse — strings are AS-vendor-specific and change with patch releases. Branch on error + error_uri + the endpoint you hit.
  • error_uri is optional and rarely populated in the wild. Auth0 sets it, Okta sets it, Cognito doesn't, Keycloak sets it inconsistently.
  • Server error=server_error HTTP 200 with a redirect is the OAuth way to surface a 5xx — the authorization endpoint never returns 5xx because doing so would break the redirect contract. Clients seeing server_error in a redirect should treat it as a transient 5xx and offer retry.
  • unauthorized_client is not 401. It's a normal 400-class error code that means "this client is registered but isn't allowed to use this grant type". Don't if status == 401 → re-auth on this one.
  • Cross-extension shared codes have subtly different semantics. invalid_request at the authorization endpoint per RFC 6749 means "malformed query"; at the token endpoint per RFC 6749 it means the same; at the resource access error response per RFC 6750 it means "request is missing required parameters" (very different — RS-side, not AS-side). The token-introspection draft adds yet another nuance.
  • OIDC's *_required codes are sticky. login_required and consent_required are returned only when the client sent prompt=none (silent auth). Clients without prompt=none will never see these — they get a normal login screen instead.
  • temporarily_unavailable should NOT be retried at the redirect-followed by-the-user-agent step — by the time the client sees it, the user has already been bounced through the browser. Surface a "try again later" UI; don't auto-retry the auth flow.
  • use_dpop_nonce is not an error from the client's perspective — it's a precondition exchange. Treat it as a 200-equivalent state machine transition. The most common DPoP client bug is treating the first use_dpop_nonce response as a fatal error instead of as "AS issued me a nonce, now I retry with it".
  • The registry table updates faster than client libraries. wallet_unavailable (OpenID4VP 1.0, 2024) and invalid_request_uri_method (also OpenID4VP 1.0) are absent from many client libraries that predate the OpenID4VP final. New verifiable-credentials wallets exposing these codes will surface as "unknown error".
  • oauth-ext-review@ietf.org is the registration list, not the bug-report list. Implementations finding registry inconsistencies should file in the relevant working group; the review list is for new error-code submissions only.
  • No deprecation path. Once registered, a code stays in the registry forever; nothing in the IANA process supports Status: deprecated. The implicit-grant codes (still listed) and pre-OAuth-2.1 codes have effectively zero new traffic but remain valid registrations.
