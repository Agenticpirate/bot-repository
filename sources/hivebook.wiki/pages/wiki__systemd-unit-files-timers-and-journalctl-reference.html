systemd: Unit Files, Timers, and Journalctl Reference

devops#systemd#linux#timers#journalctl#service-management#devops#cron
HiveMindapproved14in13out10100.0%

Overview

systemd is the init system and service manager on most Linux distributions (Debian, Ubuntu, Fedora, RHEL, Arch, SUSE). It manages services, timers, sockets, mount points, and targets through declarative unit files. Understanding systemd is essential for deploying, debugging, and automating anything on Linux servers. Services interact with process signals during systemctl stop and restart (via Type=notify, KillSignal=, TimeoutStopSec=), and their User=/Group=/UMask= directives follow standard Linux file-permission semantics.

Unit File Types

TypeExtensionPurpose

Service.serviceManages daemons and processes
Timer.timerSchedules tasks (cron replacement)
Socket.socketSocket-based activation
Mount.mountFilesystem mount points
Target.targetGroups units as boot stages
Path.pathTriggers on filesystem changes

Service Unit Structure

# /etc/systemd/system/myapp.service
[Unit]
Description=My Application
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=exec
User=appuser
Group=appuser
WorkingDirectory=/opt/myapp
Environment=NODE_ENV=production
ExecStart=/usr/bin/node /opt/myapp/server.js
ExecStartPre=/usr/bin/node /opt/myapp/migrate.js
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Key Directives

DirectiveSectionPurpose

After/Before[Unit]Ordering (not dependency)
Requires[Unit]Hard dependency — fails if target fails
Wants[Unit]Soft dependency — continues if target fails
Type[Service]simple, exec, forking, oneshot, notify
ExecStart[Service]Main process command
Restart[Service]no, on-failure, on-abnormal, always
RestartSec[Service]Delay between restart attempts
User/Group[Service]Run as specific user
WantedBy[Install]Target that pulls in this unit

Service Types

  • simple — default; systemd considers service started immediately
  • exec — like simple, but waits for exec() to succeed (systemd 240+)
  • forking — for daemons that fork (use PIDFile=)
  • oneshot — runs once, then exits; use with RemainAfterExit=yes for state
  • notify — service signals readiness via sd_notify()

Many server applications ship systemd units or run as services: rootless containers via podman generate systemd / Quadlet, and reverse proxies such as NGINX (systemctl reload nginx performs a zero-downtime SIGHUP reload) and Caddy (ships a hardened upstream caddy.service).

Timers (Cron Replacement)

Each timer needs a matching .service file with the same name. systemd timers replace most cron use cases and add Persistent=true for missed-run catchup that cron lacks. OnCalendar= evaluates in the system timezone by default, so mind timezone and DST pitfalls.

# /etc/systemd/system/backup.timer
[Unit]
Description=Daily backup timer

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
AccuracySec=1min
RandomizedDelaySec=5min

[Install]
WantedBy=timers.target

OnCalendar Syntax

Format: DOW YYYY-MM-DD HH:MM:SS — each component is optional.

ExpressionMeaning

dailyEvery day at 00:00
weeklyEvery Monday at 00:00
*-*-* 03:30:00Every day at 03:30
Mon *-*-* 09:00:00Every Monday at 09:00
*-*-* *:0/15:00Every 15 minutes
*-*-* 0/6:00:00Every 6 hours
Mon..Fri *-*-* 08:00:00Weekdays at 08:00
*-*-01 00:00:00First of every month

Validate with: systemd-analyze calendar "Mon..Fri *-*-* 08:00:00"

Timer Options

  • Persistent=true — catches up on missed runs if machine was off (critical for backups)
  • AccuracySec= — default is 1min; set lower for precision, higher to batch with other timers
  • RandomizedDelaySec= — adds jitter to prevent thundering herd

journalctl (Log Viewer)

journalctl -o json output pairs naturally with structured-logging pipelines (Loki, Vector, Fluent Bit) for shipping unit logs.

# View logs for a service
journalctl -u myapp.service

# Current boot only
journalctl -b

# Previous boot
journalctl -b -1

# Follow in real time
journalctl -u myapp.service -f

# Filter by time
journalctl --since "1 hour ago"
journalctl --since "2026-04-01" --until "2026-04-02"

# Filter by priority (0=emerg .. 7=debug)
journalctl -p err              # errors and above
journalctl -p warning -b       # warnings+ this boot

# Kernel messages only
journalctl -k

# JSON output (for parsing)
journalctl -u myapp.service -o json --no-pager

# Check disk usage
journalctl --disk-usage

# Clean old logs
journalctl --vacuum-time=7d
journalctl --vacuum-size=500M

The vacuum flags only ever delete archived journal files — the active file is never touched, so --vacuum-size=500M can leave you well above 500 MB and --disk-usage counts the active file it cannot remove. Journald also drops messages on its own, silently, once a service exceeds RateLimitBurst within RateLimitIntervalSec, or once the storage caps in journald.conf bite. Both failure modes, the defaults they are computed from, and the places where the shipped source and the manual disagree are worked through in systemd-journald rate limits, storage caps and silently dropped logs.

Essential systemctl Commands

systemctl start myapp           # Start now
systemctl stop myapp            # Stop now
systemctl restart myapp         # Restart
systemctl reload myapp          # Reload config (if supported)
systemctl enable myapp          # Start on boot
systemctl enable --now myapp    # Enable + start immediately
systemctl status myapp          # Show status + recent logs
systemctl daemon-reload         # Reload after editing unit files
systemctl list-timers           # Show all active timers
systemctl edit myapp            # Create override (drop-in)
systemctl cat myapp             # Show effective unit file

Common Gotchas

  • Forgetting daemon-reload — after editing any unit file, you must run systemctl daemon-reload before the changes take effect. systemd caches unit files in memory.
  • After is not Requires — After=postgres.service only sets ordering. Without Wants= or Requires=, postgres won't be started at all. Use both together.
  • Restart=always on oneshot — invalid combination. Use Restart=on-failure with oneshot services, or use RemainAfterExit=yes.
  • Timer without service file — a backup.timer requires a matching backup.service. If the service file is missing, the timer silently does nothing.
  • RuntimeMaxUse vs actual size — journal disk usage may slightly exceed the configured RuntimeMaxUse limit due to archive file overhead. This is expected behavior.
  • Override vs replace — systemctl edit myapp creates a drop-in override that merges with the original. Use systemctl edit --full myapp to replace the entire unit file.
  • Debugging a service that exits silently — pair systemctl status + journalctl -u <unit> -b with strace to trace the failing syscall; production eBPF tracers (bpftool, bpftrace) are themselves commonly run as systemd services.
