HTTP Status Codes: Complete Reference

Overview

HTTP status codes are three-digit integers grouped by their leading digit. Knowing the precise semantics prevents common API design mistakes, especially in the 4xx range.

1xx — Informational (interim)

A 1xx response is interim: it precedes the final status on the same request, and a client that reads
one must be prepared for a chain of them before the real response arrives.

CodeNameMeaning

100ContinueSent in reply to Expect: 100-continue; tells the client the body may be uploaded. The client must send the body anyway if no interim response arrives — see HTTP 100-continue
101Switching ProtocolsThe server is switching to the protocol named in Upgrade (the WebSocket handshake, and HTTP/1.1-to-h2c)
103Early HintsCarries Link headers so the client can preload during the server's think-time — see 103 Early Hints

2xx — Success

CodeNameMeaning

200OKStandard success for GET, PUT, PATCH
201CreatedResource successfully created (POST); include Location header pointing to new resource
202AcceptedRequest accepted for async processing; job not yet complete
204No ContentSuccess with no body (DELETE, or PUT with no response body)
206Partial ContentResponse to a range request (Range header); used for video streaming, resumable downloads

3xx — Redirection

CodeNameMeaning

301Moved PermanentlyResource permanently moved; browser and crawlers cache this forever
302FoundTemporary redirect; do not cache
304Not ModifiedConditional GET; client's cached version is still valid (used with ETag/Last-Modified)
307Temporary RedirectLike 302 but method must not change (POST stays POST)
308Permanent RedirectLike 301 but method must not change

Note: 301/302 redirect a POST to a GET. If you need the method preserved, use 307/308.

4xx — Client Errors

CodeNameMeaning

400Bad RequestMalformed request syntax, invalid parameters
401UnauthorizedNot authenticated — no or invalid credentials
403ForbiddenAuthenticated but not authorized — identity known, permission denied
404Not FoundResource does not exist
405Method Not AllowedHTTP method not supported for this endpoint
409ConflictState conflict (e.g., duplicate unique key, edit conflict)
410GoneResource permanently deleted (stronger hint than 404)
417Expectation FailedThe expectation in the Expect request header cannot be met; the client should retry without it
422Unprocessable EntitySyntactically valid but semantically wrong (e.g., validation failure)
429Too Many RequestsRate limit exceeded; include Retry-After header

401 vs 403 — The Most Common Confusion

401: "I don't know who you are. Please authenticate."
     → Return this when no valid credentials are present.
     → Include WWW-Authenticate header.

403: "I know who you are, but you can't do this."
     → Return this when authenticated but lacking permission.
     → Do NOT return 404 to hide resource existence in most cases.

5xx — Server Errors

CodeNameMeaning

500Internal Server ErrorUnhandled exception; generic catch-all
501Not ImplementedMethod or feature not yet implemented
502Bad GatewayUpstream server returned invalid response (load balancer/proxy error)
503Service UnavailableServer temporarily overloaded or in maintenance
504Gateway TimeoutUpstream server did not respond in time

502 vs 504: Both are proxy errors. 502 means the upstream returned garbage or hung up; 504 means it simply didn't respond within the timeout.

Error Body Format

For any 4xx or 5xx response, RFC 9457 — Problem Details for HTTP APIs is the canonical error envelope. It defines application/problem+json (and +xml) with five optional members (type, status, title, detail, instance) plus arbitrary extensions, and obsoletes the older RFC 7807. Most modern frameworks (Spring 6 ProblemDetail, ASP.NET Core IProblemDetailsService, FastAPI, etc.) emit this format by default.

Choosing the Right 4xx for API Validation

// Missing required field → 400
if (!body.email) return Response.json({ error: 'email is required' }, { status: 400 });

// Invalid field value (email format wrong) → 422
if (!isValidEmail(body.email)) return Response.json({ error: 'invalid email format' }, { status: 422 });

// Resource already exists → 409
const existing = await db.query.users.findFirst({ where: eq(users.email, body.email) });
if (existing) return Response.json({ error: 'email already registered' }, { status: 409 });
