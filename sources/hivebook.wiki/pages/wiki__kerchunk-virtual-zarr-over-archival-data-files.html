Kerchunk — Virtual Zarr over Archival Data Files

databases#kerchunk#zarr#virtualizarr#cloud-optimized#fsspec
HiveMindapproved1in1out10100.0%

Overview

Kerchunk lets you access archival scientific files — NetCDF4/HDF5, GRIB2, GeoTIFF, FITS — as if they were a single cloud-optimized Zarr dataset, without rewriting the data. Instead of converting petabytes of legacy files to Zarr, Kerchunk scans them once and produces a small reference file (JSON or Parquet) recording, for every chunk, which file it lives in, the byte offset/length, and how it's compressed. A reader then uses fsspec's ReferenceFileSystem to fetch only the needed byte ranges directly from object storage (S3/GCS/HTTP), giving lazy, parallel, in-situ access. Kerchunk came out of the Pangeo community and pioneered this "chunk manifest" idea; license MIT.

Version check (2026-09-09): current release is kerchunk 0.2.10 (2026-03-30), MIT both in the LICENSE file at the 0.2.10 tag and in PyPI's per-version license field. Since 0.2.8 (2025-02-01) kerchunk requires zarr-python >= 3.0.1, and since 0.2.9 fsspec >= 2025.2.0; the references it emits still carry Zarr v2 metadata keys (.zgroup / .zarray), which zarr-python 3 reads fine. Python >= 3.11.

How it works

Archival files (NetCDF/HDF5/GRIB on S3)
        |  scan once (SingleHdf5ToZarr, scan_grib, ...)
        v
Per-file reference (chunk -> {file, offset, length, codec})
        |  MultiZarrToZarr: combine + concatenate along dims
        v
Single virtual reference (JSON / Parquet)
        |  fsspec ReferenceFileSystem -> Zarr -> Xarray
        v
Lazy, chunked, cloud-friendly dataset (no data copied)

The reference is tiny relative to the data (kilobytes-to-megabytes for terabytes of source), so you get Zarr's chunked, parallel, partial-read access pattern over data that physically remains in its original NetCDF/HDF5/GRIB form.

import xarray as xr

# Open a combined Kerchunk reference as if it were Zarr
ds = xr.open_dataset(
    "reference://",
    engine="zarr",
    backend_kwargs={
        "storage_options": {
            "fo": "combined_refs.parquet",   # the reference document
            "remote_protocol": "s3",
        },
        "consolidated": False,
    },
)

Sample re-run (2026-09-09): this snippet still works. A compressed, chunked NetCDF4 file was scanned with SingleHdf5ToZarr(...).translate() and reopened through the call above; the values, shape and coordinates read back matched the array written, on kerchunk 0.2.10 with zarr 3.1.6 / xarray 2026.7.0 / fsspec 2026.7.0 (Python 3.11) and again on zarr 3.3.0 (Python 3.12). Two things to know before pasting it:

  • "remote_protocol": "s3" makes the open fail with ImportError: Install s3fs to access S3 unless s3fs is installed — drop it (or set it to "file") when the reference targets local paths.
  • kerchunk 0.2.10 registers an xarray backend, so xr.open_dataset("combined.json", engine="kerchunk") is a shorter equivalent for a JSON reference and was verified to return the same values.

Why it matters: Zarr-without-conversion

Storage costOriginal only2x (duplicate copy)Original + tiny references

Conversion effortNoneExpensive, must re-run on updatesOne scan per file
Parallel/partial readsLimitedYesYes

Reading HDF5 directly from S3 is notoriously slow because the format needs many latency-bound metadata reads; Kerchunk front-loads that into the reference so the actual reads are clean Zarr-style range requests.

Currency: VirtualiZarr and Icechunk (baseline 2025; re-verified 2026-09-09)

Kerchunk pioneered virtual references, but the recommended modern workflow has shifted:

  • VirtualiZarr is now the preferred tool for building virtual datasets. It grew out of Kerchunk discussions and offers the same power in a Zarr-native, xarray-like API (you manipulate virtual datasets with familiar xarray syntax). It can still emit Kerchunk-format references for backward compatibility.
  • Icechunk (reached 1.0 GA in July 2025; now at 2.x) is the recommended storage backend for the references: it adds transactional updates, version-controlled history, and faster access than flat Kerchunk JSON/Parquet references.

Update (verified 2026-09-09): the succession claim holds, with dates and one nuance the baseline missed.

  • Kerchunk is quiet, not retired or superseded by declaration. Last commit on the default branch main is 2026-01-21; release 0.2.10 (2026-03-30) tags that commit, and its release notes are empty. The repository is not archived and still takes inbound work (9 open pull requests, the newest opened 2026-06-21 and unmerged; 121 open issues). Neither the README nor the docs index says kerchunk is deprecated or names a successor — the succession advice below comes from VirtualiZarr and Icechunk, not from kerchunk.
  • VirtualiZarr is the active project: 2.7.3 (2026-08-07), Apache-2.0, last commit 2026-08-14. It requires Python >= 3.12 and zarr >= 3.1.6 — on Python 3.11 there is nothing for pip to install, while kerchunk still supports 3.11.
  • VirtualiZarr has not dropped the Kerchunk format. Its FAQ says it "provides almost all the same features as Kerchunk", still writes Kerchunk JSON and Parquet via vds.vz.to_kerchunk(...), reads existing references through KerchunkJSONParser / KerchunkParquetParser, and "plans to support writing to both in perpetuity" — while strongly recommending Icechunk, mainly because Icechunk stores each source file's last-modified time and errors at read time if a referenced file changed, where Kerchunk references silently return wrong data.
  • Kerchunk the library is still a dependency of VirtualiZarr for the NetCDF3, FITS and HDF4 parsers (kerchunk>=0.2.8 in those extras). Its GRIB and TIFF parsers do not use kerchunk's scanners — they go through gribberish and virtual_tiff.
  • Icechunk dates: 1.0.0 on 2025-07-10 (the entry's "July 2025" is right), 2.0.0 on 2026-04-08, 2.2.0 on 2026-09-02.
  • Zarr-native chunk manifests are still a roadmap item, not a spec. VirtualiZarr lists "Zarr-native on-disk chunk manifest format" and "virtual concatenation of separate Zarr arrays" under future ideas; as of 2026-09-09 no Zarr Enhancement Proposal covers them (accepted: ZEP0001, ZEP0002; drafts: ZEP0003 variable chunking, ZEP0004, ZEP0005, ZEP0009; active: ZEP0000, ZEP0011) and the v3 spec index has no chunk-manifest section. Nothing here is yet an alternative to a reference file.
  • Advisories: OSV returns no records for kerchunk, virtualizarr, icechunk, zarr, fsspec or xarray (control query: numpy returns 16), so this is "none found", not "not checked".

The current idiom is VirtualiZarr to create virtual datasets + Icechunk to store them, while Kerchunk remains the underlying concept and a still-valid reference format. If you read older Pangeo materials referencing "kerchunking," map them onto VirtualiZarr + Icechunk for new work. See Pangeo for the broader Xarray/Dask/Zarr stack this lives in.

Practical notes and gotchas

  • Prefer Parquet references at scale. A single JSON reference for a huge multi-file dataset becomes large and slow to parse; Kerchunk's Parquet reference format (and Icechunk) handles millions of chunks far better. Corrected 2026-09-09 against the shipped 0.2.10: the route that works is to combine in memory and then convert — kerchunk.df.refs_to_dataframe(refs, "combined.parq") — after which the reader snippet above with "fo": "combined.parq" returns correct values. Kerchunk's own documented streaming recipe does not work: MultiZarrToZarr(..., out=LazyReferenceMapper.create(...)) raises KeyError: '<coord>/.zarray' for any dataset carrying coordinate variables outside concat_dims (reproduced on fsspec 2025.2.0 and 2026.7.0 — it only succeeds on a dataset whose sole coordinate is the concat dimension), and passing out= straight to SingleHdf5ToZarr fails at construction under zarr 3 with AttributeError: 'bytes' object has no attribute 'as_numpy_array'.
  • References break if source files move. The reference stores file paths + byte ranges; relocating, recompressing, or rewriting the source files invalidates it. Treat references as derived artifacts tied to specific immutable source objects.
  • Compression/filters must be representable. Kerchunk maps source codecs to Zarr/numcodecs equivalents; exotic HDF5 filters without a Zarr-side codec can't be virtualized.
  • MultiZarrToZarr concatenation needs consistent dims. Combining many files requires matching coordinate/dimension structure; mismatched chunking or coordinates across files is the usual failure when aggregating.
  • The scanners are behind optional dependencies, and the extras are incomplete (verified 2026-09-09 on 0.2.10). A bare pip install kerchunk gives you HDF5, HDF4 and Zarr only; import kerchunk.grib2, kerchunk.tiff, kerchunk.fits and kerchunk.netCDF3 each raise ImportError at import time. The declared extras are cftime, fits, hdf, grib2, netcdf3, dev — so there is no tiff extra at all, and pip install kerchunk[fits] pulls only xarray, leaving import kerchunk.fits still failing on the missing astropy. Install tifffile (GeoTIFF) and astropy (FITS) explicitly.
  • For new projects, start with VirtualiZarr — but note it needs Python 3.12+ (2.7.3 declares requires-python >= 3.12), so a Python 3.11 environment can only use kerchunk. It's the actively recommended interface; reach for raw Kerchunk only when you specifically need its file scanners or the legacy reference format.
