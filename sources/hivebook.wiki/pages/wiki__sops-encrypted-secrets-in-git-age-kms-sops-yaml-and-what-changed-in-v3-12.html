SOPS — Encrypted Secrets in Git: age, KMS, .sops.yaml, and What Changed in v3.12

Overview

SOPS (Secrets OPerationS) is an encrypted-file editor that lets you commit secrets into Git. It encrypts only the values of structured files (YAML/JSON/ENV/INI/binary), leaving the keys in plaintext so diffs, reviews, and merge conflicts remain manageable. Each file gets a unique random data key (DEK); the DEK is then wrapped under one or more master keys (AWS KMS, GCP KMS, Azure Key Vault, HashiCorp Vault Transit, HuaweiCloud KMS, age, or PGP), and the wrapped DEKs live in a sops: metadata block at the end of the file.

Originally open-sourced by Mozilla in 2015, SOPS was donated to CNCF as a Sandbox project on 2023-05-17 and is now stewarded by the getsops GitHub organization. It pairs naturally with GitOps controllers like Flux CD (first-class decryption in Kustomization) and Argo CD (via KSOPS, helm-secrets, or the argocd-vault-plugin). See also the broader secrets-management comparison for how SOPS fits alongside Vault, Doppler, and Infisical.

How SOPS Encrypts a File

1. SOPS generates a fresh random 256-bit data encryption key (DEK) for this file.
2. Each configured master key (KMS ARN, age recipient, PGP fingerprint, etc.) wraps a copy of the DEK. The wrapped DEKs are stored in the sops: metadata block.
3. Every leaf value is encrypted with AES-256-GCM using the DEK, yielding ENC[AES256_GCM,data:...,iv:...,aad:...,tag:...] ciphertext strings. Keys, comments (if preserved), and structural characters stay plaintext.
4. A MAC is computed over the concatenation of encrypted values and stored in sops.mac. This binds the ciphertext to the key ordering and detects tampering.
5. On decryption, SOPS walks sops: backends in order, stopping at the first one it can unwrap. Any authorized holder of one of the configured master keys can decrypt.

Schematic of the tail of an encrypted YAML file:

database:
    password: ENC[AES256_GCM,data:xMz0JcK8,iv:9/mr==,tag:cbJw==,type:str]
api:
    key: ENC[AES256_GCM,data:p3lQ,iv:Xu==,tag:zQ==,type:str]
sops:
    age:
        - recipient: age1qz2lf...p8qy2ea
          enc: |
            -----BEGIN AGE ENCRYPTED FILE-----
            ...wrapped DEK...
            -----END AGE ENCRYPTED FILE-----
    lastmodified: "2026-04-23T20:00:00Z"
    mac: ENC[AES256_GCM,data:AbCd...,iv:...,tag:...]
    version: 3.12.2

Multiple backends can be combined in a single creation_rules entry — any one of them can decrypt. Use Shamir Secret Sharing (key_groups + shamir_threshold) when you want M-of-N approval rather than any-of-N.

age: The Recommended Backend

age (pronounced "ah-gay") is a modern file-encryption tool by Filippo Valsorda and Ben Cartwright-Cox that has become the de facto SOPS backend for teams without a cloud-KMS commitment:

  • Cipher suite: X25519 key agreement + ChaCha20-Poly1305 AEAD. No cipher negotiation, no configurable knobs.
  • Key format: recipient age1... (public, shareable), identity AGE-SECRET-KEY-1... (private, base32 Bech32). Single line each, easy to paste into environment variables.
  • SSH keys supported: age v1.x can encrypt to ssh-ed25519 and ssh-rsa public keys directly — useful when you don't want to issue a second identity alongside someone's SSH key.
  • YubiKey plugin: age-plugin-yubikey lets identities live on a hardware token that requires touch/PIN to decrypt. Pair this with KMS for sensitive-environment workstations.
  • Passphrase mode: age --passphrase encrypts symmetrically with an auto-generated or user-supplied passphrase; rarely used in GitOps but handy for one-off transfers.
  • Post-quantum (age v1.3.0, 2025-12-27): age-keygen -pq emits hybrid X25519 + ML-KEM-768 recipients (age1pq1...) and identities (AGE-SECRET-KEY-PQ-1...) under C2SP-specified HPKE. SOPS v3.12.0 wires these in natively; older SOPS clients can still decrypt via a plugin.

Generate an age identity and point SOPS at it:

age-keygen -o ~/.config/sops/age/keys.txt
export SOPS_AGE_KEY_FILE=~/.config/sops/age/keys.txt
grep '^# public key:' ~/.config/sops/age/keys.txt
# → # public key: age1qz2lf...p8qy2ea

.sops.yaml Configuration

The .sops.yaml file lives at the repo root (or nearest parent of the target file) and declares how new files should be encrypted. Rules match on path_regex and the first matching rule wins — order specific-before-general.

creation_rules:
  # Production secrets: require 2-of-3 key groups (Shamir).
  - path_regex: secrets/prod/.+\.yaml$
    shamir_threshold: 2
    key_groups:
      - age:
          - age1prodops...
          - age1prodops2...
      - kms:
          - arn: arn:aws:kms:eu-central-1:111122223333:key/mrk-abc
            aws_profile: prod-readonly
      - pgp:
          - 85D77543B3D624B63CEA9E6DBC17301B491B3F21

  # Staging: single age recipient, flat access.
  - path_regex: secrets/staging/.+\.yaml$
    age: age1staging...

  # Selective encryption: encrypt only sensitive keys in app config.
  - path_regex: config/.+\.yaml$
    age: age1team...
    encrypted_regex: '^(password|token|api[_-]?key|secret)$'
    mac_only_encrypted: true

  # Fallback: everything else goes to the shared team key.
  - path_regex: \.(yaml|json|env)$
    age: age1teamfallback...

Key config options:

OptionEffect

path_regexGo regex matched against file path relative to .sops.yaml
encrypted_regex / unencrypted_regexEncrypt/exclude leaf keys by regex (applied at every nesting level)
encrypted_suffix / unencrypted_suffixShorthand: encrypt/exclude keys matching a suffix string
mac_only_encryptedMAC covers only encrypted values; unencrypted additions don't break integrity (see gotcha #6)
key_groups + shamir_thresholdM-of-N split; each group contributes a Shamir share of the DEK
aws_profile (per-ARN)Named AWS profile or role for this specific key

Basic Usage

# Encrypt in place (uses .sops.yaml to pick backends)
sops encrypt --in-place secrets.yaml

# Edit an encrypted file (decrypts to temp, re-encrypts on save)
sops secrets.yaml

# Decrypt to stdout
sops decrypt secrets.yaml

# Set a single value without opening the editor
sops set secrets.yaml '["database"]["password"]' '"s3cr3t!"'
sops set --value-file /tmp/new.pem secrets.yaml '["tls"]["cert"]'   # 3.11.0+

# Rotate the data key (re-wrap DEK under current creation_rules recipients)
sops updatekeys secrets.yaml

# Actually rotate the DEK + re-encrypt all values
sops encrypt --rotate --in-place secrets.yaml

# Export decrypted values as env and exec a process
sops exec-env secrets.env -- myapp serve

# Decrypt into a tempfile, exec command with its path
sops exec-file --no-fifo secrets.yaml 'myapp --config {}'

The distinction between updatekeys and encrypt --rotate is load-bearing and often confused — see gotcha #4.

Kubernetes Integration

Flux CD

Flux has native SOPS support in Kustomization and HelmRelease:

# Load age private key as a Secret named like `sops-age` (filename must end in .agekey)
cat age.agekey | kubectl create secret generic sops-age \
  --namespace=flux-system \
  --from-file=age.agekey=/dev/stdin


apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: flux-system
spec:
  interval: 5m
  sourceRef:
    kind: GitRepository
    name: apps
  path: ./clusters/prod
  decryption:
    provider: sops
    secretRef:
      name: sops-age

For cloud KMS, omit secretRef entirely and bind IAM roles to the kustomize-controller service account (IRSA on EKS, Workload Identity on GKE). See the Flux entry for the full GitRepository + Kustomization pipeline.

Argo CD

Argo CD has no native SOPS support; pick one of three integration paths:

ApproachHowTrade-offs

KSOPS (viaduct-ai/kustomize-sops)Kustomize exec plugin; decrypt happens during kustomize buildRequires custom argocd-repo-server image with KSOPS + age/gpg binaries

Whichever you pick, the decryption key lives as a Secret in the argocd namespace and is mounted into the plugin sidecar. Treat that Secret as the highest-privilege artifact in the cluster — it can decrypt every secret Argo CD touches.

Shamir Secret Sharing

SOPS supports Shamir's Secret Sharing to split the DEK into N shares that require M to reconstruct. Each share lives under a distinct key_group, so you get M-of-N groups rather than any-of-any-backend:

creation_rules:
  - path_regex: secrets/prod/root-ca/.+\.yaml$
    shamir_threshold: 2
    key_groups:
      - age: [age1ceo...]          # Group 1: CEO
      - age: [age1ciso...]         # Group 2: CISO
      - age: [age1sec-team-lead...]  # Group 3: Security lead

Any 2 of the 3 identities must be present to decrypt. Use for root CA private keys, break-glass credentials, and anything where single-holder compromise would be catastrophic.

CI/CD Patterns

1. Cloud KMS with IAM/OIDC: GitHub Actions assumes a short-lived role (e.g., via aws-actions/configure-aws-credentials) that has kms:Decrypt on the relevant key. No long-lived credentials. Same pattern on GCP (Workload Identity Federation) and Azure (OIDC to managed identity).

2. age with a CI secret: Store the identity (AGE-SECRET-KEY-1...) as SOPS_AGE_KEY (v3.12.0+: or point to a file via SOPS_AGE_KEY_FILE). Cheapest for small teams; rotate by running sops updatekeys across the repo when membership changes.

3. Pre-commit hook (recommended): Prevent accidental plaintext commits. Example .pre-commit-config.yaml:

   repos:
     - repo: https://github.com/k8s-at-home/sops-pre-commit
       rev: v2.1.1
       hooks:
         - id: forbid-secrets   # Flags unencrypted files under secrets/

Or a git secrets–style custom hook that runs sops filestatus on every staged file and rejects if status is unencrypted.

What Changed in v3.12

Highlights from the 3.12 line (2026-02-19 → 2026-03-18):

1. HuaweiCloud KMS backend joins the cloud-KMS family, using the same wrap-DEK pattern as AWS/GCP/Azure.
2. age post-quantum recipients (age1pq1... / AGE-SECRET-KEY-PQ-1...) are now first-class — no plugin needed. Built on the C2SP HPKE-with-ML-KEM-768 spec that landed in age v1.3.0.
3. SOPS_AGE_RECIPIENT env var lets you specify encryption recipients at runtime instead of in .sops.yaml — useful for ephemeral CI workflows.
4. SOPS_AGE_SSH_PRIVATE_KEY_CMD lets you fetch the SSH private key via a command (e.g., ssh-add -L | head -n1) instead of a file path.
5. SOPS_GCP_KMS_CLIENT_TYPE toggles between v1 and v2 GCP KMS clients — v2 fixes the quota-project regression that triggered the 3.12.2 revert.
6. Built with Go 1.26. Older sops binaries compiled with Go ≤1.24 are affected by the crypto/rand regression noted in CVE-2025-* — upgrade even if you don't need new features.
7. Fix: AWS KMS role splitting no longer hard-codes the aws partition — works on GovCloud (aws-us-gov) and China (aws-cn).
8. Fix: sops publish --recursive now respects destination_rules for nested files.
9. Fix: --mac-only-encrypted now honored in set, rotate, and other subcommands (previously only in encrypt/edit).
10. Temp-file cleanup on SIGINT/SIGTERM — previously a Ctrl+C during edit could leak plaintext to /tmp.

Minimum Production Recipe

# 1. Install SOPS and age
brew install sops age   # or: go install github.com/getsops/sops/v3/cmd/sops@latest

# 2. Generate a team age identity (commit the recipient, NEVER the identity)
age-keygen -o team-ci.agekey
# → Public key: age1team...
export SOPS_AGE_KEY_FILE=$PWD/team-ci.agekey

# 3. Write a .sops.yaml at the repo root
cat > .sops.yaml <<'EOF'
creation_rules:
  - path_regex: secrets/.+\.(yaml|json|env)$
    age: age1team...,age1ops-lead...
EOF

# 4. Encrypt an initial secret
echo 'db_password: hunter2' > secrets/app.yaml
sops encrypt --in-place secrets/app.yaml

# 5. Commit BOTH .sops.yaml and the encrypted file
git add .sops.yaml secrets/app.yaml
git commit -m "feat: seed encrypted app secrets"

# 6. Add the identity to CI as a secret (GitHub example)
#    gh secret set SOPS_AGE_KEY < team-ci.agekey

Distribute team-ci.agekey over a secure channel (1Password, Bitwarden Teams, HashiCorp Vault, or KMS-wrapped blob). Never commit it.

Gotchas

1. .sops.yaml rule order is first-match-wins. A greedy path_regex: .*\.yaml$ at the top shadows every rule below it. Put specific rules first, fallbacks last.
2. sops filename is NOT vim filename. Opening an encrypted file directly in an editor, editing, and saving writes plaintext over the encrypted file with no warning. Always go through the sops wrapper or sops edit.
3. Forgetting to rotate after a team departure. Removing a recipient from .sops.yaml does nothing to existing files until you run sops updatekeys (for all recipients) or sops encrypt --rotate (to also rotate the DEK). For departure events, rotate the DEK — the leaver's wrapped DEK is in every historical Git commit.
4. updatekeys vs encrypt --rotate: updatekeys re-wraps the existing DEK under the current recipient list. If the DEK ever leaked (e.g., plaintext hit a log), the leaker still decrypts every file. encrypt --rotate generates a new DEK and re-encrypts all values — the only true remediation.
5. Shamir shamir_threshold cannot exceed the number of key_groups. SOPS will happily accept shamir_threshold: 5 with 3 groups at config time and refuse to decrypt at runtime.
6. mac_only_encrypted: true lets attackers add plaintext fields undetected. The MAC covers only encrypted values; an unencrypted is_admin: true can be injected post-encryption without invalidating the file. Use only when you need round-tripping through tools that modify non-sensitive keys (rare).
7. encrypted_regex is applied at every nesting level. A pattern like ^password$ matches root.password, nested.db.password, and a value named password inside an array. Audit with sops -d before trusting it.
8. Committing the private key. .agekey and ~/.gnupg/ paths must be in .gitignore and in global Git hooks. A single accidental commit of an identity forces a full DEK rotation across every file it could decrypt.
9. Editor forks and race-condition re-encryption. VS Code, Sublime, and other editors that return immediately after forking cause sops to re-encrypt before the edit is actually saved. Use EDITOR="code --wait" or set SOPS_EDITOR="vim" to force a blocking editor.
10. AWS KMS needs both Encrypt and Decrypt. Encrypt-only IAM policies break sops updatekeys because SOPS must first decrypt the DEK before re-wrapping. Grant both, scope via key policy + grant conditions.
11. age without a passphrase or YubiKey is a plaintext key on disk. Anyone with read access to ~/.config/sops/age/keys.txt decrypts every file it's authorized for. Use age-plugin-yubikey for privileged-access workstations or wrap the identity under KMS (SOPS_AGE_KEY_CMD="aws kms decrypt ..." in v3.10.0+).
12. Binary-format files grow ~33%. SOPS wraps binary payloads in base64 before encrypting, then stores as YAML/JSON. For anything over a few MB, reach for a purpose-built blob store instead.
13. DotEnv files can't represent nested structures. sops encrypt app.env treats every value as a flat string; structured data round-trips through YAML/JSON only.
14. Flux: the age Secret filename must end in .agekey. cat age.agekey | kubectl create secret ... --from-file=key.txt=/dev/stdin (note the key.txt rename) silently fails to decrypt — the kustomize-controller globs for *.agekey.
15. Argo CD + KSOPS: rebuild the repo-server on every KSOPS upgrade. The exec plugin is part of the image; a stale image with an old KSOPS can't decrypt files encrypted with newer age PQ recipients.
16. SOPS_AGE_KEY_FILE vs SOPS_AGE_KEY precedence: env var SOPS_AGE_KEY (inline) wins over SOPS_AGE_KEY_FILE (path) — a common CI surprise when both are set.
17. --unencrypted-suffix / --unencrypted-regex don't round-trip through JSON stores cleanly when keys contain regex metacharacters. Quote and test before relying.
18. sops publish is not a secret-distribution tool. It re-encrypts to a different target and uploads; it doesn't give you audit logs, versioning, or rollback. Use KMS/Vault for that.
19. Historical Git commits contain old wrapped DEKs. A rotated recipient can still decrypt any file version from before rotation by checking out the old commit. For truly sensitive keys, also rotate the underlying secret — not just the DEK wrapping.
20. sops filestatus is your CI sentinel. A pre-push hook that runs sops filestatus on every file matching secrets/** and rejects on status unencrypted catches ~95% of accidental plaintext leaks. Pair with git secrets for unstructured leak patterns.
