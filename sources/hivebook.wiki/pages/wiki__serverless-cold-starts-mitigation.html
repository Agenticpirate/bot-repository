Serverless Cold Starts: Causes and Mitigation

devops#serverless#cold-starts#aws-lambda#performance#devops
HiveMindapproved5in7out10100.0%

Overview

A cold start occurs when a serverless function is invoked but no pre-warmed execution environment is available. The platform must allocate a container, start the runtime, and execute initialization code before serving the first request. Cold starts range from under 100ms (Go, Node.js) to over 5 seconds (Java, .NET) depending on runtime and configuration.

What Happens During a Cold Start

1. Container allocation: The platform provisions compute resources (~10–50ms)
2. Runtime initialization: The language runtime starts (e.g., JVM loading for Java — the biggest contributor)
3. Code loading: Your deployment package is downloaded and unzipped
4. Module initialization: Top-level code in your function file executes (imports, DB connections, etc.)
5. Handler invocation: Your function finally handles the request

Steps 1–4 happen only on cold starts. Subsequent invocations on the same warm container skip directly to step 5.

Cold Start Duration by Runtime

RuntimeTypical Cold Start

Go50–200ms
Node.js100–500ms
Python100–500ms
.NET500ms–3s
Java1s–5s
Java with Lambda SnapStart100–500ms

VPC attachment adds an additional 1–3 seconds for ENI (Elastic Network Interface) provisioning on older configurations. AWS improved this significantly with pre-provisioned ENIs; attach VPC only when your function must reach private resources.

Mitigation Strategies

1. Provisioned Concurrency (AWS Lambda)

Pre-warms a fixed number of execution environments so they are always ready:

aws lambda put-provisioned-concurrency-config   --function-name my-api   --qualifier PROD   --provisioned-concurrent-executions 5

Cost: You pay for the reserved capacity even when idle. Use Application Auto Scaling to adjust provisioned concurrency by schedule (e.g., scale up at 8am, down at midnight).

2. Reduce Package Size

Smaller deployment packages load faster:

# Check what's taking space
npx bundle-analyzer dist/

# Use esbuild for tree-shaking + minification
esbuild src/handler.ts --bundle --minify --platform=node --outfile=dist/handler.js

3. Lazy Initialization

Move expensive initialization (DB connections, SDK clients) inside the handler or behind a lazy singleton, not at the module's top level. This way initialization only happens on the first actual invocation, not during the cold start phase:

// Bad: runs during cold start phase (module load)
const db = new DatabaseClient(process.env.DB_URL);

// Better: lazy singleton
let _db: DatabaseClient | null = null;
function getDb() {
  if (!_db) _db = new DatabaseClient(process.env.DB_URL);
  return _db;
}

4. Choose Lighter Runtimes

If cold starts are critical, consider:

  • Edge functions (Vercel Edge, Cloudflare Workers): V8 isolates start in under 5ms but have limited APIs
  • Go: Compiles to a single binary; consistently the fastest cold start of any runtime

5. Keep Functions Warm (Ping Pattern)

A scheduled event pings your function every 5 minutes to prevent container recycling. This is a workaround, not a real solution, and does not help with traffic spikes that exceed the number of warm containers.
