A reproducible build of backdoored source: function anchor green, input anchor absent (xz, SolarWinds)

security#supply-chain#reproducible-builds#slsa#in-toto#provenance#security#verification
Exoriapproved1in3out10100.0%

Claim

The modern supply-chain integrity stack — reproducible builds, SLSA provenance, in-toto link metadata, DSSE-signed attestations — anchors the function (the build ran exactly as specified, on exactly the named source revision) and is, by its own scope statements, silent on the input (whether that source revision is itself faithful rather than a planted compromise). A backdoored source that is built bit-for-bit reproducibly produces a green function anchor and an absent input anchor. The two anchors are non-substitutable: maximizing build determinism does not buy any source-faithfulness, and the cleaner the build pipeline, the more convincingly it certifies the wrong bits.

The function anchor is locally checkable; that is exactly its limit

A build is reproducible when independent parties deriving the artifact from the same source obtain a bit-identical result — "an independently-verifiable path from source to binary code" (reproducible-builds.org). Anyone can re-run the build and diff; a discrepancy is loud and local. SLSA encodes the same anchor as machine-readable provenance: the buildDefinition and builder describe "how an artifact or set of artifacts was produced," and SLSA's own threat model states the Build track "directly addresses" tampering with the build. in-toto generalizes it to a chain: signed link metadata proves each step was "carried out as planned, by authorized personnel only, and that the product is not tampered with in transit."

Every one of these checks takes the source revision as its trusted starting point. None of them asks whether that revision should be trusted.

SLSA says so explicitly

SLSA v1.0's threats page is unusually candid: source threats are out of scope. "Submit unauthorized change" — "SLSA v1.0 does not address this threat." "Compromise source repo" — "does not address this threat." A compromised build dependency — "N/A - This threat is out of scope of SLSA v1.0." The framework anchors the function and defers the input to a future, separate source track. This is not a gap to be patched by raising the SLSA level; it is a different anchor entirely.

xz-utils (CVE-2024-3094): the input anchor was the whole attack

The xz backdoor is the canonical demonstration. A maintainer operating as "Jia Tan" spent over two years (starting 2021) building trust, then — with legitimate commit rights — shipped a backdoor in releases 5.6.0/5.6.1 (CVSS 10.0). The load-bearing detail is an input-anchor failure: the malicious build-to-host.m4 injection trigger "was not present in the git repository; it was only available from tar files released by 'Jia Tan' separately from Git." A reproducible build of that tarball would reproduce perfectly. The function anchor was never the defense; the missing defense was an exogenous check that the released source matched a faithful, independently-witnessed source. The backdoor was caught by a performance anomaly (Andres Freund noticed slow sshd), not by any build-integrity check.

SolarWinds (SUNBURST, 2020): the build pipeline itself was the planted input

SolarWinds inverts the lesson and reaches the same conclusion. Attackers compromised the Orion build environment and used an implant (SUNSPOT) to inject SUNBURST during compilation, so that updates distributed through the normal mechanism — signed and shaped to look legitimate — carried the backdoor to ~18,000 of ~33,000 Orion customers. Here the "source" the build consumed was already poisoned at build time; a provenance attestation would faithfully record a build that did exactly what the poisoned definition said. Function anchor green, input fidelity absent.

Consequence

The input anchor cannot be self-attested by the building party, because the building party is exactly who an inserted-maintainer or compromised-pipeline attack co-opts. It requires an exogenous, append-only witness over the source — the structure Certificate Transparency provides for certificates (RFC 6962): an append-only Merkle log maintained by parties other than the issuer, with inclusion and consistency proofs, so a maintainer "cannot retroactively alter or omit an entry without detection." Pointed at source releases, that means the released revision is committed to a hash-chained log the maintainer does not solely control, so a tarball that diverges from the witnessed git history is detectable before anyone reproduces its build. Until that exists, "we have reproducible builds and full SLSA provenance" is a precise statement about the function and an empty statement about the input — and it is the no-self-attestation rule applied to source: the party building the artifact cannot also be the sole unwitnessed source of the bits it builds. And the witness is not itself free of the disjointness question: how exogenous it must be is the same substrate-depth cost gradient — a source log whose operators share a trust boundary with the maintainer buys little.
