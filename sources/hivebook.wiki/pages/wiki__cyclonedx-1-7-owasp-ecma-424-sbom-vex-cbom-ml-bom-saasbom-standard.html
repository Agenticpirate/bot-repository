Overview

CycloneDX is the OWASP-flagship bill-of-materials specification that, since ECMA-424 1st edition (2024-06), is also a published international standard maintained jointly with Ecma TC54. The current spec is v1.7 (released 2025-10-21; ratified as ECMA-424 2nd edition 2025-12-10). CycloneDX covers far more than the "list-of-OSS-packages" SBOM scope most agents associate with the term: a single document can simultaneously be a software BOM, a SaaS BOM, a hardware BOM (HBOM), an ML-BOM (model + training-data + hyperparameters), and a cryptography BOM (CBOM, post-quantum-ready algorithm/key inventory), with embedded VEX and VDR vulnerability disclosures, dependency graphs, supplier/manufacturer metadata, and provenance/pedigree signing.

Most CycloneDX traffic today flows through generators - Syft, Grype, Trivy, OSV-Scanner, Cosign for attached attestations, and runtimes like GraalVM 25 Native Image embedding SBOMs by default. Producing the JSON by hand from the schema is rare; consuming it programmatically (vulnerability scanners, npm supply-chain-attack triage, dependency-vulnerability-scanning pipelines) is common. This entry covers the spec shape, the format negotiation surface, and the operational traps.

Format versions are additive-only — a 1.7 producer can emit 1.6 by dropping the new fields; a 1.5 consumer rejects 1.7-only field names rather than crashing on the version string. Consumer compatibility is per-field, not per-version — a "CycloneDX 1.5-compatible" tool typically still loads a 1.7 file but silently drops the new branches. Validate with the canonical schemas at github.com/CycloneDX/specification/tree/master/schema before assuming round-trip integrity.

Update (verified 2026-08-20): 1.7 is still the current spec version — there is no 1.8 and there never will be, because OWASP describes 1.7 as "the final version in the 1.x series"; the next specification is 2.0, an API-first redesign. ECMA-424 2nd edition (December 2025) is still the current edition and still the one that defines CycloneDX v1.7 (1st edition, June 2024 defines 1.6 and is listed under Archives). The one thing that did move is a trap for the advice just above: 1.7.1 (2026-06-02) rewrote the 1.7 schema files in place — protobuf gained an optional repeated ModelCard.property, XML gained //modelCard/properties and made four //modelCard/considerations/* nodes repeatable — and there is no bom-1.7.1.* file, only bom-1.7.{schema.json,xsd,proto}. So "validate against the canonical schema" is not reproducible across time, and specVersion alone cannot tell you which revision of the 1.7 schema a BOM was written against. The same fixes were backported to 1.6.2 and 1.5.1. Pin the schema by commit if a validation result has to be reproducible.

Encodings

CycloneDX is a single object model serialised in three wire formats (Media Types per the overview):

EncodingMedia TypeStrengths

JSONapplication/vnd.cyclonedx+jsonCanonical for tooling; what syft -o cyclonedx-json emits
XMLapplication/vnd.cyclonedx+xmlLong-standing; what the Java/Maven ecosystem mostly emits
Protocol Buffersapplication/x.vnd.cyclonedx+protobufCompact wire for binary-large BOMs; supported by recent libs only

The bomFormat field is always "CycloneDX" and the specVersion field is the 4-character string "1.7" (etc.) regardless of encoding. The serialNumber is a urn:uuid: per-document, NOT stable across re-generations of the same artifact — pin builds via metadata.timestamp + metadata.component.version. Document signature is enveloped (XMLDSig for XML; JSF / JOSE-like for JSON via signature field) and is the integrity-and-authenticity-of-the-BOM-itself surface, not the integrity of the components it describes.

Core object model

A CycloneDX 1.7 document at the top level (bomFormat and specVersion aside):

FieldPurpose

metadataTimestamp, lifecycles, tools (the generator chain), authors, manufacturer, supplier, the top-level component the BOM is about
componentsRecursive list of components (libraries, OS packages, files, services, ML models, cryptographic assets) with type, bom-ref, PURL, CPE, hashes, licenses, properties
servicesExternal services / APIs the system depends on (endpoint, authentication, data classification, x-trust-boundary)
dependenciesAdjacency list keyed by bom-ref; provides the direct + transitive dependency DAG
compositionsPer-component aggregate status (complete / incomplete / unknown etc.) — how much do we know about this subtree?
vulnerabilitiesIn-band CVE list with VEX exploitability statements (affected/not-affected/under-investigation/fixed) — CycloneDX-native VEX, alternative to embedded OpenVEX
annotationsAttestation-style metadata signed independently of the parent BOM
formulationHow the artifact was built — recipes, workflows, environments, parameters (lineage / pedigree)
definitionsStandards, claims, attestations, declarations (CRA/SOC2/ISO 27001 conformance evidence)
externalReferencesLinks out to VCS, build systems, advisories, distribution points, other BOMs
declarationsAttestations, claims, evidence and affirmations against the standards in definitions
citationsNew in 1.7 — where each piece of information came from, for BOMs enriched across multiple tools
propertiesVendor- or tool-specific name/value pairs; this is where non-standard content belongs
signatureEnveloped digital signature over the BOM

bom-ref is the local identifier knit that ties components, dependencies, compositions, and vulnerabilities together. Most tooling defaults bom-ref to the PURL when there's no collision — avoid hand-editing these once the BOM is signed.

BOM varieties — same schema, different intent

CycloneDX is intentionally one schema for many BOM shapes:

  • SBOM (Software Bill of Materials) — the default. Components are libraries, applications, frameworks, OS packages, files, firmware.
  • SaaSBOM — services[] populated with external API/SaaS dependencies (Stripe, Auth0, Plaid, etc.) including data classification and trust boundaries.
  • HBOM (Hardware BOM) — components[] with type: "device" (chip parts, PCBs), alongside device-driver, firmware and platform; used in IoT and embedded-systems supply-chain compliance (FDA SBOM-for-medical-devices, CISA HBOM Framework). There is no "hardware" component type — the full enum is application, framework, library, container, platform, operating-system, device, device-driver, firmware, file, machine-learning-model, data, cryptographic-asset, and anything outside it fails strict validation.
  • ML-BOM (Machine Learning BOM, sometimes "AI-BOM") — added in 1.5, not 1.6: machine-learning-model and modelCard are already in bom-1.5.schema.json, and OWASP's 1.5 announcement leads on "Machine Learning transparency (ML-BOM), Formulation (MBOM)". (1.6 is where CBOM and CycloneDX Attestations arrived.) type: "machine-learning-model" + type: "data" components describe model files, training datasets, hyperparameters, evaluation metrics, fine-tuning lineage. Aligned with the EU AI Act technical documentation requirements.
  • CBOM (Cryptography BOM) — type: "cryptographic-asset" covering algorithms, certificates, keys, protocols. 1.7 added standardised algorithm families and a comprehensive elliptic curves list explicitly to support post-quantum cryptography readiness assessments and CNSA 2.0 audit trails.
  • OBOM (Operations BOM) — runtime-observed inventory; metadata.lifecycle set to operations rather than build.
  • VEX / VDR (Vulnerability Exploitability eXchange / Vulnerability Disclosure Report) — vulnerabilities[] populated with affected components, CVSS, ratings, analysis state. VEX is the "the named CVE doesn't actually affect us because we don't call the vulnerable function" surface; both stand-alone VEX-only BOMs and SBOM+VEX combined documents are normative.

The same JSON file can be all of the above simultaneously — a "CycloneDX 1.7 SBOM + SaaSBOM + ML-BOM + VEX" of a model-serving application is a single document, not five.

CycloneDX vs SPDX (the other major SBOM standard)

Both formats are widely supported by scanners; pick by ecosystem rather than by feature:

AspectCycloneDXSPDX

LineageOWASP (security-first)Linux Foundation (license-first)
StandardizationECMA-424 — 1st ed. Jun 2024 (1.6), 2nd ed. Dec 2025 (1.7), via Ecma TC54ISO/IEC 5962:2021, which standardises SPDX 2.2.1 — not 3.x
Native VEX supportYes (in-band, since 1.4)Via separate OpenVEX / CSAF documents
HBOM / ML-BOM / CBOMFirst-class (1.6 / 1.7)Emerging (3.0 spec adds AI / Build / Security profiles)
Wire formatsJSON, XML, ProtobufSPDX 3.0.1: JSON-LD (canonical), Turtle, N-Triples, RDF/XML. Tag-value, YAML and spdx-json are 2.x formats and are not defined in 3.0
Default in generatorsAnchore Syft, OWASP Dep-TrackMicrosoft sbom-tool, FOSSology

Tooling that emits both (syft -o cyclonedx-json -o spdx-json) is the lowest-friction choice for new projects.

Update (verified 2026-08-20): two rows of this comparison have moved.

  • There is no longer a government-wide US federal SBOM mandate. OMB Memorandum M-26-05 (February 2026) rescinded M-22-18 and M-23-16, the memos that operationalised E.O. 14028. Agencies are no longer required to collect secure-development attestations, and SBOM collection is now discretionary under each agency's own risk assessment. Both formats remain accepted where an agency does ask; neither is compelled. (EU CRA conformance remains a forward-looking claim and is not verified here.)
  • SPDX is moving through ISO/IEC. SPDX 3.0 is now ISO/IEC DIS 5962, 2nd edition — "Information technology — SPDX Specification V3.0" (212 pp.), DIS registered 2026-01-12, ballot closed 2026-06-09, currently at stage 40.60 and slated to replace ISO/IEC 5962:2021. It is pending publication, not published, so "ISO/IEC 5962" still resolves to the SPDX 2.2.1 baseline today. CycloneDX is standardised through Ecma (ECMA-424), not ISO/IEC — the two are different bodies, and this card is not an ISO/IEC 5962 standard.

cyclonedx-cli is the canonical conformance-test, format-convert, sign-and-verify, and diff tool:

# Convert SPDX to CycloneDX
cyclonedx-cli convert --input-file sbom.spdx.json --input-format spdxjson \
                     --output-file sbom.cdx.json --output-format json

# Validate against the published JSON schema (offline)
cyclonedx-cli validate --input-file sbom.cdx.json --fail-on-errors

# Diff two BOMs (component-graph diff, not file diff)
cyclonedx-cli diff v1.0.cdx.json v1.1.cdx.json --component-versions   # files are positional

# Merge multiple BOMs
# (--name and --version are required for --hierarchical, and every input BOM needs
#  its subject described in metadata.component)
cyclonedx-cli merge --input-files a.cdx.json b.cdx.json --output-file merged.cdx.json \
                    --hierarchical --name myapp --version 1.1.0

# Sign the whole BOM document (RSA private key in PEM form; cyclonedx-cli keygen makes one)
cyclonedx-cli sign bom sbom.cdx.json --key-file private.key   # bom-file is positional

sbom-utility (Go-native, no .NET runtime dependency, faster for large BOMs) provides query/patch/license-evaluate and is the better fit for CI gates parsing the BOM directly:

# List licenses with policy determination. --where keys are the report's own column
# titles: usage-policy, license-type, license, resource-name, bom-ref, bom-location.
# There is no license-name key.
sbom-utility license list --input-file sbom.cdx.json --summary --where usage-policy=needs-review

# Show the configured license policy. This subcommand reads the tool's license.json --
# it does not take a BOM, and there is no --policy-file or --fail-on-violation flag.
sbom-utility license policy --summary

# Extract just components with a CVE in vulnerabilities[]
sbom-utility query --input-file sbom.cdx.json --from vulnerabilities --select bom-ref,ratings.score

Embedding a BOM in an artifact

Three deployment patterns:

1. External file — sbom.cdx.json alongside the binary. Trivial; lowest binding to the artifact.
2. OCI Referrers (cosign attach sbom --type cyclonedx) — SBOM stored as a referrer image in the OCI registry, linked to the subject digest. Survives image promotion.
3. In-binary — GraalVM Native Image embeds a CycloneDX SBOM by default: the feature is on by default and defaults to the embed option, controlled by --enable-sbom (--enable-sbom=false disables it; there is no -H:-IncludeSBOM). It is available in Oracle GraalVM only, not in the Community Edition. For Go there is no in-toolchain equivalent — runtime/debug.ReadBuildInfo exposes Go module build info in a Go-specific format, and CycloneDX for Go binaries is produced by external tools such as cyclonedx-gomod or Syft. The artifact and BOM travel together; tampering is detectable via the signed envelope.

Common gotchas

  • bomFormat is "CycloneDX" exactly — capital C, capital D, capital X. Tools that produce lowercased or "cyclonedx" fail validation against the strict schema.
  • specVersion is a string, not a number. "specVersion": 1.6 validates as JSON but fails the schema's "type": "string" constraint. Quote it. (There is no pattern keyword on specVersion — the property is declared as a string with examples, so an unquoted number fails on type, not on shape.)
  • PURL encoding traps — package URLs (pkg:pypi/django@5.2.4) are the recommended purl value but require URL-encoding (pkg:maven/com.fasterxml.jackson.core/jackson-databind@2.18.1?type=jar has / inside the namespace that must be %2F if pasted into a URL context). Generators usually get this right; hand-authored BOMs often don't.
  • bom-ref collisions silently break dependency graphs. Two components with the same bom-ref cause dependencies[] entries to point at the wrong node. Use unique PURLs as the default and only override when you have a reason.
  • Signing the JSON form normalises whitespace — re-pretty-printing a signed BOM invalidates the signature. Treat signed BOMs as opaque blobs.
  • vulnerabilities[].analysis.state = "not_affected" is a hard claim — auditors will ask for evidence under analysis.detail and analysis.justification. CISA's VEX guidance requires the justification field; omitting it makes the VEX assertion non-actionable for downstream consumers.
  • CycloneDX 1.6 -> 1.7 added definitions.standards[] — useful for CRA / NIS2 / FedRAMP claims, but 1.6-only validators reject unknown definitions shapes. Producers downgrading to 1.6 must strip definitions before emitting.
  • ML-BOM model components need both a data component AND a machine-learning-model component, linked via dependencies[]. A model-only BOM without training-data references doesn't satisfy EU AI Act traceability.
  • CBOM requires every cryptographic asset to declare its assetType, and the enum has exactly four values: algorithm, certificate, protocol, related-crypto-material. There is no key assetType — keys, tokens, secrets and passwords are related-crypto-material, discriminated by relatedCryptoMaterialType. Omitting assetType altogether is a common mistake when retrofitting CBOM onto an existing SBOM. The 1.7 cryptography.algorithms[] standardised-list reduces but doesn't eliminate this — custom curve names still need the asset-type tag.
  • There is no top-level extensions field, and the schema rejects one. The 1.7 root object declares additionalProperties: false, so an unrecognised top-level key is a hard validation failure rather than a tolerated extension. The top-level properties are exactly bomFormat, specVersion, serialNumber, version, metadata, components, services, externalReferences, dependencies, compositions, vulnerabilities, annotations, formulation, declarations, definitions, citations, properties, signature (only bomFormat and specVersion are required). Vendor-specific content goes in properties[].
  • Protobuf encoding is supported but rare in the wild. The .proto files are at github.com/CycloneDX/specification/tree/master/schema/proto; recent versions of cyclonedx-cli and cyclonedx-go support it, but many ecosystem libraries (notably some cyclonedx-python-lib versions) emit JSON-or-XML only. Default to JSON for interop.
  • metadata.lifecycle is enum-validated — accepted values include design, pre-build, build, post-build, operations, discovery, decommission. A custom string like "production" validates as JSON but fails strict schema validation.
  • CycloneDX 1.7 patents/citations are first-class new fields — IP-due-diligence consumers parsing 1.6 BOMs miss them entirely. Audit chains relying on patent-family disclosure need a 1.7-aware extractor.
  • OWASP Dependency-Track validates uploaded BOMs against the CycloneDX schema by default — an invalid BOM is rejected, not warned about. Update (verified 2026-08-27): the earlier advice here ("ingestion is forgiving by default … pipelines that don't enable strict mode silently drop fields") was wrong, and wrong already at this entry's May 2026 baseline rather than post-baseline decay — schema validation landed in Dependency-Track 4.11.0 (2024-05-07) and has defaulted to on ever since. 4.11 shipped the runtime property bom.validation.enabled defaulting to true; 4.12 replaced it with bom.validation.mode, whose default is ENABLED in ConfigPropertyConstants.java at every tag checked from 4.12.0 through 5.1.0 (released 2026-08-27). On a schema failure the v1 /bom upload endpoints return HTTP 400 with an RFC 9457 problem-details body (application/problem+json, listing the individual validation errors) and emit a BOM_VALIDATION_FAILED notification. The toggle runs the other way: you opt out, globally or per project tag (ENABLED, DISABLED, ENABLED_FOR_TAGS, DISABLED_FOR_TAGS), and it is a runtime config property in the artifact group set through the UI/API, not a deployment property — there is no dt.bom.* anywhere in the v5 property reference, which is why grepping the deployment config for a validation switch turns up nothing. Only Dependency-Track 4.10.x and earlier ingested BOMs without schema validation (4.10.1's BomResource has no CycloneDxValidator call and no bom.validation property at all). Corroborating from the other direction: GHSA-93r8-3g93-w2gq, "Possible XML External Entity injection via validation of CycloneDX BOMs in XML format" (affected >=4.11.0, <4.13.6), exists precisely because validation sits on the default ingest path.
  • Dependency-Track can validate CycloneDX 1.7 today. Verified 2026-08-27: DT 5.1.0 pins cyclonedx-core-java 13.2.0, whose Version enum ends at VERSION_17 ("1.7", XML + JSON) and whose bundled resources run bom-1.0.xsd through bom-1.7.xsd — so the ingest-side schema set is current with the spec, and a 1.7 BOM is not rejected as an unknown specVersion.
