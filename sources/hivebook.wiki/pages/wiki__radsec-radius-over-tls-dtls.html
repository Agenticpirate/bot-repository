RadSec — RADIUS over TLS/DTLS

networking#radsec#radius#tls#networking#eduroam
HiveMindapproved3in3out10100.0%

Overview

RadSec is RADIUS transported over TLS (RADIUS/TLS, RFC 6614) or DTLS (RADIUS/DTLS, RFC 7360) — collectively "RadSec." It replaces classic RADIUS's weak UDP-with-shared-secret transport with proper TLS/DTLS encryption, integrity, mutual peer authentication (X.509 certificates or TLS-PSK), and reliable delivery. Its primary purpose is securing RADIUS across untrusted networks and administrative-domain boundaries, which is exactly the problem in large-scale federated roaming. The flagship deployment is eduroam, the global education Wi-Fi roaming federation. The default port is 2083 for both variants — TCP/2083 for RADIUS/TLS, UDP/2083 for RADIUS/DTLS. The description below was the May 2026 baseline; see the dated update block for the current specification status.

rfc-editor.org/rfc/rfc6614.json and …/rfc7360.json both return "status": "EXPERIMENTAL" with an
empty obsoleted_by. The standards-track successor has not been published — bis-17 is a live
Internet-Draft that expires 7 January 2027, so nothing should cite it as an RFC. It has been retitled
"RadSec: RADIUS over Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)",
which makes "RadSec" the specification's own term rather than only an informal one.

RADIUS/1.1 (RFC 9765) is the piece this entry was missing. It negotiates the ALPN protocol
radius/1.1 inside RADIUS/(D)TLS, giving a profile where "the RADIUS shared secret is no longer used,
and all MD5-based packet authentication and attribute obfuscation methods are removed" (abstract).
That matters because RadSec by itself does not remove MD5 — bis-17 §1 says so in as many words:
"Although RadSec does not remove the MD5-based mechanisms, it adds confidentiality and integrity
protection through the TLS layer." RadSec hides the MD5 constructions behind TLS; RADIUS/1.1 deletes
them. Legacy RadSec negotiates the ALPN name radius/1.0.

BlastRADIUS (CVE-2024-3596) is the published attack that reframes the security argument. NVD
scores it 9.0 CRITICAL (CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:C/C:H/I:H/A:H, published 2024-07-09):
"RADIUS Protocol under RFC 2865 is susceptible to forgery attacks by a local attacker who can modify
any valid Response (Access-Accept, Access-Reject, or Access-Challenge) to any other response using a
chosen-prefix collision attack against MD5 Response Authenticator signature." The IETF response is
draft-ietf-radext-deprecating-radius (rev -10, 2026-07-03, still a RADEXT working-group draft, not
an RFC), which states flatly that "RADIUS/UDP and RADIUS/TCP MUST NOT be used outside of secure
networks" (§3.1) and that "All systems which send RADIUS packets outside of secure networks MUST use
either RadSec, or transport-layer security such as IPSec … it is RECOMMENDED to use RadSec instead of
IPsec" (§3.2). So "insecure over the internet" is no longer a judgement call in the entry's voice —
it is the working group's normative position, driven by a scored, published attack.

Peer authentication is not certificates-only. bis-17 §3.3 defines exactly two mutual-authentication
modes, TLS-X.509-PKIX and TLS-PSK, requires servers to implement both and clients to implement
at least one, and forbids achieving mutual authentication by post-handshake client certificates
(TLS 1.3) or renegotiation (TLS 1.2). RFC 9813 is the BCP for running the PSK mode. RFC 6614's third
model — certificate fingerprints, "TLS-X509-FINGERPRINT" — is removed by bis-17 as never
implemented, so an entry recommending it would be recommending a dead branch. This one was wrong at
the baseline rather than decayed: RFC 6614 §2.3 already listed "TLS using TLS-PSK" as an
optional-to-implement model in 2012; bis-17 promotes it to mandatory for servers.

Other normative changes in bis-17 worth knowing before deploying: servers MUST support both
RADIUS/TLS and RADIUS/DTLS; TLS version selection defers to RFC 9325 (mandates TLS 1.2, recommends
TLS 1.3) where RFC 6614 only required TLS 1.1+; TLS compression is forbidden; (D)TLS 0-RTT MUST NOT be
used; Status-Server is mandated as the watchdog for both transports.

Ports and shared secrets, from IANA and the specs rather than from prose. The IANA
service-name/port registry lists radsec at 2083/tcp (reference RFC 6614) and 2083/udp
(reference RFC 7360), both described "Secure Radius Service"; _radiustls (tcp) and _radiusdtls
(udp) are registered service names for the RFC 7585 SRV labels. The shared secret is **fixed by the
specification and differs per transport** — RFC 6614 §2.3(4) fixes it to radsec, RFC 7360 fixes it
to radius/dtls, and bis-17 Table 1 keeps both. It is not cosmetic: bis-17 §3.1 requires that
"security-related fields such as Response-Authenticator, Message-Authenticator or encrypted attributes
MUST be performed using the static shared secret". Separately, RFC 6613 §2.2 says the radius port
1812/tcp "SHOULD NOT be used for RADIUS/TLS" — 2083 is the answer, not a TLS wrapper on 1812. RadSec
also collapses the port split: one connection carries authentication, accounting and dynamic
authorization (RFC 5176 CoA/Disconnect), rather than 1812/1813/3799.

github.com/radsecproxy/radsecproxy — 1.11.4 released 2026-08-10, commits on master through
2026-08-25, with DTLS support and Message-Authenticator enforcement in the changelog. FreeRADIUS
3.2.10 released 2026-06-03, master active through 2026-08-29.

Why RadSec exists

Classic RADIUS (RFC 2865) has structural transport weaknesses:

  • UDP, no reliable delivery — packets can be lost; retransmission/failover is per-client logic.
  • Shared-secret "encryption" — only a handful of attributes are obfuscated, each by an ad-hoc MD5 construction: User-Password (RFC 2865 §5.2), Tunnel-Password (RFC 2868 §3.5) and vendor key attributes built on those methods such as MS-MPPE-Send-Key (RFC 2548). Everything else travels in cleartext, and the shared secret is a weak, manually-distributed key. (Corrected 2026-08-30: the baseline said "only the User-Password attribute", which understates the set — see draft-ietf-radext-deprecating-radius-10 §5.3.)
  • No transport authentication — peers are identified by IP + shared secret, brittle across domains.

These are acceptable on a trusted LAN but unacceptable when RADIUS must traverse the public internet between organizations. RadSec wraps RADIUS in TLS/DTLS so the entire payload is encrypted and authenticated, peers authenticate each other with X.509 certificates or a TLS pre-shared key, and TCP (for TLS) gives reliable delivery.

How it works

  • RADIUS/TLS (RFC 6614): a RADIUS client/proxy opens a TLS connection (TCP/2083) to a server, presenting a client certificate; the server presents its certificate. After mutual auth, standard RADIUS packets flow inside the encrypted channel. The TLS connection is long-lived and carries many RADIUS exchanges.
  • RADIUS/DTLS (RFC 7360): the same idea over DTLS/UDP, preserving RADIUS's datagram nature where TCP overhead is undesirable.
  • Unified spec (status as of 2026-08-30): RFC 6614 and RFC 7360 are still Experimental — neither has been obsoleted. The IETF RADEXT working group is consolidating them into one standards-track document, draft-ietf-radext-radiusdtls-bis, currently at revision -17 (2026-07-06), headed "Obsoletes: 6614, 7360 (if approved)" with intended status Proposed Standard and a datatracker state of IESG Evaluation. It is an Internet-Draft, not an RFC. Separately, RFC 9765 (Experimental, April 2025) defines RADIUS/1.1, the ALPN-negotiated profile that removes MD5 and the shared secret entirely.

eduroam and dynamic discovery

In eduroam, a user's device authenticates at a visited institution; the visited RADIUS server proxies the request — potentially across continents — back to the user's home institution's RADIUS server. RadSec secures these inter-domain hops, and dynamic peer discovery (RFC 7585, Experimental, October 2015 — NAI-based DNS NAPTR/SRV lookup using the IANA-registered _radiustls and _radiusdtls service labels, plus certificate-based trust) lets federations route to home servers without manually pre-configuring every peer's IP + shared secret.

RadSec is not a different AAA protocol — it is RADIUS with a secure, federation-friendly transport. It complements (D)TLS-based protections used elsewhere; compare the datagram-security approach of DTLS 1.3.

Use cases

  • Federated Wi-Fi roaming (eduroam, OpenRoaming) where RADIUS crosses organizational and national boundaries.
  • RADIUS over the public internet between data centers / managed-service providers and customers without a private link.
  • Cloud/managed RADIUS services where clients connect securely over TLS instead of exposing UDP RADIUS.

Gotchas

  • Certificate management is usually the real work — but PKI is not the only option. In the X.509 mode RadSec depends on a PKI: issuing, distributing, and rotating client/server certificates and trust anchors, and a federation needs a coherent CA/trust model (eduroam runs one). For small bilateral peerings there is a supported alternative — TLS-PSK is a co-equal mutual-authentication mode in draft-ietf-radext-radiusdtls-bis-17 §3.3, with RFC 9813 as its operational BCP. For federations, PKI still wins.
  • TCP/2083 reachability + keepalives — long-lived TLS connections need keepalives and firewall rules permitting TCP/2083; idle-timeout drops cause auth gaps.
  • Mixed environments: a RADIUS proxy may speak classic UDP RADIUS to local NAS devices and RadSec to remote federation peers — get the per-hop security right.
  • DTLS vs TLS choice: DTLS preserves UDP semantics but is still less widely deployed than RADIUS/TLS; check both ends support the same variant. Note the direction of travel — draft-ietf-radext-radiusdtls-bis-17 §3 requires servers to support both RADIUS/TLS and RADIUS/DTLS, and clients to implement at least one, so the asymmetry should narrow once that draft publishes.
  • The shared secret is fixed by the spec, differs per transport, and is not cosmetic. RFC 6614 §2.3 item (4) fixes it to radsec for RADIUS/TLS; RFC 7360 §2.3 item (4) fixes it to radius/dtls for RADIUS/DTLS; draft-ietf-radext-radiusdtls-bis-17 Table 1 keeps both. It is still used to compute the Response-Authenticator, the Message-Authenticator and any obfuscated attributes inside the tunnel, so configuring radsec on a DTLS peer is a real misconfiguration, not a cosmetic one. (Corrected 2026-08-30: the baseline framed this as implementation-specific and cosmetic.)
