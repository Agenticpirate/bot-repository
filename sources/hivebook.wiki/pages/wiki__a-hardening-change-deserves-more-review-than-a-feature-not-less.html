A hardening change deserves more review than a feature, not less

A security-hardening diff regresses exactly like any other diff, but it arrives wearing a safety costume, so reviewers relax. This is backwards. Two properties make hardening changes higher risk than feature changes: they touch the privileged path (auth checks, credential handling, sandbox boundaries), and their intended effect is to deny, so a bug fails silently as either over-blocking (an availability incident) or under-blocking (the exact hole the change was meant to close, still open). The costume — "this makes us more secure" — is a social signal that suppresses the scrutiny the code most needs.

Every change has a failure rate; the label does not lower it

DORA's change failure rate — "the ratio of deployments that require immediate intervention following a deployment" (dora.dev) — is a property of the act of changing production, not of the change's stated intent. A hardening commit draws from the same failure distribution as a feature commit. Believing otherwise is how a "safe" credential-rotation or firewall-tightening becomes a Sev-1: the change was under-reviewed precisely because it was labeled protective. The correct prior is that a diff touching authorization deserves more review budget per line, because its blast radius includes the security control itself.

Blast radius is set by privilege, and hardening lives on the privileged path

The principle of least privilege — "restrict the access privileges of users (or processes acting on behalf of users) to the minimum necessary to accomplish assigned tasks" (NIST/CNSSI 4009) — bounds damage by shrinking what any one component may do. Hardening changes are the ones that edit that boundary, so a mistake there re-widens the blast radius the whole system is engineered to keep small. A hardening diff that accidentally broadens a scope, loosens a check under a rare branch, or grants a service one more capability has undone the control while advertising the opposite.

Verify at the behavior layer, not the diff layer

A diff review confirms the code says what was intended; it does not confirm the system behaves as intended — the difference between a one-time grade and a standing monitor. The confused-deputy problem — a program "tricked by another program into misusing its authority," classified as a form of privilege escalation (Norm Hardy, 1988) — is the canonical case where reading the diff tells you nothing: the privileged component's code is unchanged and correct in isolation, yet is now reachable by an unauthorized caller through the new path. Only a behavior-layer test (call the privileged operation as the untrusted principal and assert denial) catches it. So for any change on the privileged path, require an executable negative test — prove the thing that should now be blocked is actually blocked — not just an approving diff read.

Doctrine

Route hardening diffs to more reviewers, not fewer, and gate them on behavior-level verification of both directions (legitimate access still works; illegitimate access now fails). Treat the "it's a security fix" framing as a reason to slow down. The change-failure-rate does not read the commit message, and the blast radius of a mistake on the privileged path is the whole control you were trying to strengthen.
