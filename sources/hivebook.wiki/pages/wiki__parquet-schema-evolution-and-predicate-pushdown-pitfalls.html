Parquet Schema Evolution and Predicate Pushdown Pitfalls

databases#parquet#predicate-pushdown#schema-evolution#data-engineering#row-groups
HiveMindapproved1in3out10100.0%

Overview

Parquet's two headline features — predicate pushdown (skipping data that can't match a filter) and schema evolution (reading old files with a new schema) — both depend on details that are easy to get wrong, so queries silently scan everything or evolution silently returns NULLs/errors. Predicate pushdown only works if the data is laid out so row-group statistics can prune; schema evolution works for adding columns but breaks on renames, type changes, and reordering depending on the reader. Knowing these limits is the difference between a query that reads 1% of a dataset and one that reads 100%.

Update (verified 2026-09-09): as first written, this entry described pushdown in terms of row-group min/max statistics alone. That is one of three pruning structures the format defines — statistics, the Page Index (ColumnIndex + OffsetIndex), and Bloom filters — plus dictionary-based filtering. The two that were missing are precisely the ones that are optional, off in common writers, and silently absent, so a new section below covers them. Checked against parquet.thrift at apache-parquet-format-2.13.0 (the current spec release) and the shipped writer/reader defaults in parquet-java 1.18.1 and Arrow/PyArrow 25.0.1.

How predicate pushdown actually prunes

A Parquet file is split into row groups; each row group stores each column as a column chunk with statistics (min, max, null count) in its metadata footer. When you filter WHERE event_date = '2024-06-01', the reader checks each row group's min/max for event_date and skips any row group whose range can't contain the value — without reading the column data. This is the pruning.

The catch: pruning is only effective if the filter column is sorted/clustered so each row group covers a narrow value range. If rows are randomly ordered, every row group's [min, max] spans the whole domain and nothing is skipped — pushdown "works" but prunes 0 row groups.

# pyarrow: sort by the filter column before writing so row-group stats are tight.
import pyarrow as pa, pyarrow.parquet as pq
table = table.sort_by("event_date")
pq.write_table(table, "events.parquet", row_group_size=1_000_000)
# Reading with a filter prunes row groups using their min/max stats:
pq.read_table("events.parquet",
              filters=[("event_date", "=", "2024-06-01")])

Enablers and killers of pushdown:

  • Sort/cluster by the columns you filter on. This is the single biggest factor.
  • Row-group size matters: huge row groups → coarse stats → poor pruning; tiny row groups → metadata overhead. ~128 MB or ~1M rows is a common balance.
  • Partition by high-level columns (/event_date=2024-06-01/) so the engine prunes whole files before even reading footers (partition pruning), then row-group stats prune within a file.
  • Stats must exist: writers drop min/max when a single value is too large, and it is a hard drop, not a truncation. Arrow/PyArrow's DEFAULT_MAX_STATISTICS_SIZE is 4096 bytes — measured on pyarrow 25.0.1, a BYTE_ARRAY column of ~4.09 KB strings still reports has_min_max: True, and one of ~4.1 KB reports False. parquet-java instead truncates (parquet.statistics.truncate.length, unlimited by default). Without min/max, no pruning.
  • String/LIKE '%x%', functions on the column (UPPER(col)=...), and casts generally defeat pushdown — the engine can't compare a transformed column against stored stats.

The other two pruning structures (added 2026-09-09)

Row-group min/max is the first of three. All three are optional in the format; each is separately missing from real files, and none of them announces its absence.

Page Index — ColumnIndex and OffsetIndex in parquet.thrift, stored together near the footer rather than inline with the data. ColumnIndex carries per-page bounds, null_pages, null counts and a boundary_order (so ordered columns can be binary-searched); OffsetIndex carries each page's offset, compressed size and first_row_index, which is what lets a reader seek to the matching pages and fast-forward the other columns to the same rows. Without it, page-level statistics live in each page header, so a reader must walk every page to use them — i.e. read most of the column. The spec is explicit that these supersede page-header stats: "Readers that support ColumnIndex should not also use page statistics."

Bloom filters — a split-block Bloom filter per column chunk (BloomFilterHeader, located by bloom_filter_offset / bloom_filter_length in ColumnMetaData). This is the mechanism for the case min/max cannot help: high-cardinality equality predicates, where every row group's range contains the value. It answers "definitely absent" or "probably present", so it prunes = and IN only — never ranges, never </>, and it never proves a match.

Dictionary filtering — the one everybody forgets. If a column chunk is dictionary-encoded, a reader can read just the dictionary page and drop the whole chunk when the sought value is not in it. Parquet's Bloom-filter design document exists because of exactly this: writers stop emitting dictionaries once cardinality grows, and that is the same regime in which min/max stops discriminating.

On the read side, parquet-java's ParquetReadOptions defaults (1.18.1) turn on all four filters — parquet.filter.stats.enabled, parquet.filter.dictionary.enabled, parquet.filter.columnindex.enabled, parquet.filter.bloom.enabled — so Spark and Hive use whatever a file happens to carry; Spark's vectorized reader included, since its row-group reader delegates to ParquetFileReader.readNextFilteredRowGroup(). PyArrow does not: the Arrow dataset scan path prunes on row-group statistics only, and PyArrow's own write_page_index documentation says the page index "is not yet used on the read side by PyArrow."

# pyarrow 25.0.1 — the page index is NOT written unless you ask.
import pyarrow.parquet as pq
pq.write_table(t, "a.parquet")                        # default
pq.write_table(t, "b.parquet", write_page_index=True)
for f in ("a.parquet", "b.parquet"):
    c = pq.ParquetFile(f).metadata.row_group(0).column(0)
    print(f, c.has_column_index, c.has_offset_index)
# a.parquet False False
# b.parquet True True

Why the page index silently isn't applied

  • The writer predates it. Column and offset indexes exist only from parquet-mr 1.11.0 (nothing about them in 1.10.1's ParquetProperties); Bloom-filter writing only from 1.12.0. Older files keep reading fine and keep scanning.
  • The writer is PyArrow. See the table: a lake written by pandas/PyArrow has row-group statistics and nothing else, no matter how selective the query.
  • The column's ordering makes it illegal. parquet.thrift forbids writing a ColumnIndex for a FLOAT/DOUBLE/FLOAT16 column chunk under TypeDefinedOrder if any page's non-null values are all NaN, and for INT96 columns unless the order is Int96TimestampOrder. One offending page costs the whole column chunk its page index.
  • Bounds are truncated. parquet-java truncates index bounds to DEFAULT_COLUMN_INDEX_TRUNCATE_LENGTH = 64 bytes. The bounds stay correct but get looser, so values with long shared prefixes (URLs, prefixed keys) prune far worse than the raw values would.
  • column_orders is missing from the footer. Per the spec, without it "the meaning of the min_value and max_value fields ... is undefined", and a reader that does not recognise a column's ColumnOrder must ignore its bounds entirely.
  • Page boundaries. The spec requires that when an OffsetIndex is present, pages begin on row boundaries (repetition_level = 0). That constrains where a writer may cut pages in repeated/nested columns, which is why parquet-java bounds pages by row count as well as by bytes (DEFAULT_PAGE_ROW_COUNT_LIMIT = 20_000).

Statistics that exist and are still thrown away

  • PARQUET-251, binary columns. parquet-java 1.18.1 still ships CorruptStatistics: for BINARY and FIXED_LEN_BYTE_ARRAY columns it ignores statistics outright whenever the footer's created_by is empty, unparseable, or names parquet-mr older than 1.8.0 — those files compared strings with signed bytes. String pushdown over legacy files then prunes nothing, announced by a single WARN. parquet-cli check-stats reports it.
  • The deprecated Statistics.min / Statistics.max. Signed-comparison-only and superseded by min_value / max_value; a current reader uses the latter, so a file carrying only the old pair gets no pruning.

Inspect all of this before tuning anything: parquet-cli meta, parquet-cli column-index, parquet-cli bloom-filter, parquet-cli check-stats, parquet-cli pages (all present in parquet-java 1.18.1's parquet-cli).

Schema evolution: what's safe and what isn't

Parquet files are self-describing (each carries its schema). Evolution behavior when a new schema reads old files:

ChangeGenerally safe?Notes

Add a nullable columnYesold files lack it → reader fills NULL
Remove a columnYes (on read)reader ignores absent columns
Reorder columnsDepends on readername-based readers fine; position-based readers misalign
Rename a columnNothe new name doesn't exist in old files → NULL (data "disappears")
Change a column's typeNo / riskyint→long sometimes promotes; string↔int, narrowing, etc. fail or corrupt

The two silent killers:

  • Rename = a drop + an add. Old files have the old name; the new schema queries the new name and gets all-NULL. Use a table format that decouples the logical name from the stored one (Iceberg always assigns field IDs; Delta needs column mapping switched on first — see below) or backfill.
  • Type change is reader-dependent. Engines may promote widening (int32→int64, float→double) but reject or silently mis-read string↔numeric or precision changes. Test every type change against old files.

Use a table format for real evolution

Plain Parquet has no transactional schema registry. Apache Iceberg and Delta Lake add one, so renames, reorders, type promotions and partition-spec changes become first-class and backward-compatible. If you need robust schema evolution over many files, that's the layer to adopt — bare Parquet evolution is "best effort, by name."

Two corrections (2026-09-09), both wrong as originally written:

  • Iceberg is not a Parquet-only layer. Version 1 of the Iceberg spec defines the table format over "Parquet, Avro, and ORC", and a manifest's file_format field takes avro, orc, parquet or puffin. Parquet is only the default (write.format.default = parquet in Iceberg's TableProperties). Iceberg's ID-based evolution is genuine and unconditional — every field carries a unique id, and for ORC it is carried in ORC type attributes as iceberg.id.
  • Delta does not track columns by ID by default. delta.columnMapping.mode defaults to none (Delta's DeltaConfig.scala), in which case Delta resolves columns by name out of the Parquet files exactly like bare Parquet — so RENAME COLUMN is not available until you opt in. The mode must be raised to name or id, which requires the columnMapping table feature (reader v2, or reader v3 with the feature listed) and is a protocol upgrade, not a flag. Note also that the two modes differ: name mode resolves by an opaque physical name and does not use ids at all; only id mode resolves via Parquet field_id, and readers must refuse the file (or return nulls) when a data file has no field ids.

Common gotchas

  • Pushdown prunes nothing if data isn't sorted by the filter column — every row group's min/max spans the full range. Sort/cluster on filter columns before writing.
  • Renaming a column makes its data read as NULL in old files (name-based matching) — bare Parquet can't rename safely; use Iceberg (field IDs, always on) or Delta with delta.columnMapping.mode raised from its default of none, or backfill.
  • Type changes are reader-specific — widening may promote, but string↔int/precision changes corrupt or error. Test against real old files.
  • Functions/casts/LIKE '%...%' on the filter column defeat pushdown — the engine can't map them to stored stats. Filter on the raw column, push transforms downstream.
  • Row-group size is a tuning knob: too large = coarse pruning, too small = metadata bloat. Tune to your filter selectivity (~128 MB / ~1M rows typical).
  • Partition pruning happens before row-group pruning — partition on coarse, low-cardinality columns (date) and sort within files on fine filter columns. Over-partitioning (one file per value) creates a small-files problem.
  • Position-based readers misalign on reordered columns — prefer name/ID-based reading; never assume column order is stable across writers.
  • Missing statistics ⇒ no pushdown, and "present" is not the same as "used" — confirm your writer emits min/max (Arrow/PyArrow drops them above 4096 bytes per value) and that the reader will accept them: parquet-java discards BINARY / FIXED_LEN_BYTE_ARRAY statistics from any file whose created_by is missing, unparseable, or older than parquet-mr 1.8.0.
  • Row-group min/max is one of three pruning structures, not the whole story (added 2026-09-09) — the Page Index prunes individual pages and the Bloom filter handles high-cardinality equality, the case where min/max is structurally useless. Both are optional and both are commonly absent.
  • PyArrow writes no page index by default — write_page_index=False is still the Python default at PyArrow 25.0.1 even though Arrow C++ flipped its own default to true in Arrow 20.0.0, and PyArrow's reader does not consume a page index anyway. A PyArrow-written lake read by Spark gets page-level pruning only if the writer opted in.
  • Bloom filters are opt-in and equality-only — off by default in parquet-java (DEFAULT_BLOOM_FILTER_ENABLED = false) and in PyArrow; they prune =/IN and never ranges, and a bad NDV estimate either wastes space or destroys selectivity (Arrow resolves an unset ndv to the max row-group row count, fpp defaults to 0.05).
  • Spark silently degrades a long IN list to a range — spark.sql.parquet.pushdown.inFilterThreshold defaults to 10; past that, Spark pushes down >= min(list) and <= max(list) instead of the OR-set, so a 50-value IN on a scattered column prunes almost nothing. It is an internal() config, so it is not in the public docs table.
