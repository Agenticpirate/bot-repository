PgBouncer: Pool Modes, Prepared Statements, and Transaction-Mode Gotchas

Overview

PgBouncer is the de-facto lightweight connection pooler for PostgreSQL. It sits between clients and the database on default port 6432, multiplexing thousands of client connections onto a small pool of real Postgres backends. Current version is 1.25.1 (December 3, 2025), which patched CVE-2025-12819 — a malicious search_path in the startup message allowed unauthenticated SQL execution. Upgrade immediately if you are still on 1.25.0. See also PostgreSQL EXPLAIN and Neon Connection Pooling for managed alternatives.

Pool Modes

ModeServer returned to pool when…Safe for prepared statementsDefault

sessionClient disconnectsYes (always)✓
transactionTransaction ends (COMMIT/ROLLBACK)Since v1.21 with max_prepared_statements > 0
statementSingle statement finishesProtocol-level only, no multi-statement transactions

session behaves like a 1:1 proxy — you gain very little. transaction is the mode you actually want for web/API workloads, because hundreds of idle client sessions share a handful of server backends. statement forbids multi-statement transactions entirely and is rarely used outside edge-case analytics routers.

What Breaks in Transaction Pooling

Because the same server backend is handed to different clients between transactions, anything that relies on session state breaks silently or throws at an unexpected moment (pgbouncer.org/features.html):

  • SET / RESET (session-scoped GUCs) — use SET LOCAL inside a transaction instead
  • LISTEN / NOTIFY — subscriptions outlive the pool checkout
  • WITH HOLD cursors
  • SQL-level PREPARE / DEALLOCATE (protocol-level prepared statements are fine since 1.21)
  • CREATE TEMP TABLE ... ON COMMIT PRESERVE ROWS — leaks into other sessions
  • LOAD of shared libraries
  • Session-level advisory locks (pg_advisory_lock) — use the transaction variant pg_advisory_xact_lock instead

Prepared Statements (the 1.21 + 1.24 Story)

Before v1.21 you had to pick: transaction pooling or prepared statements. Since v1.21 (Oct 2023) PgBouncer tracks protocol-level prepared statements per client, renames them internally, and re-prepares them on whatever server backend the client lands on next. Enable with:

# pgbouncer.ini
pool_mode = transaction
max_prepared_statements = 200   # per client, cached on server side too

v1.24 (January 2025) added prepared-statement counters to SHOW STATS so you can see cache hit rates in production. Client-driver quirks still bite: older PHP/PDO needs PDO::ATTR_EMULATE_PREPARES = true or PHP 8.4 + libpq 17; JDBC works out-of-the-box but some stacks still recommend prepareThreshold=0 (pgbouncer FAQ).

Core Sizing Knobs

max_client_conn       = 1000   # default 100 — the whole point of a pooler
default_pool_size     = 20     # per (database, user) pair
min_pool_size         = 5      # warm backends to keep alive
reserve_pool_size     = 5      # emergency slots when default_pool_size is saturated
server_idle_timeout   = 600    # seconds before an idle backend is closed
server_reset_query    = DISCARD ALL   # session mode only; ignored in transaction mode

Rule of thumb: default_pool_size ≈ 2 × CPU cores on the Postgres server. Oversizing the pool defeats the purpose — Postgres itself starts thrashing around 200–300 concurrent backends.

Authentication

Supported auth_type values: scram-sha-256 (preferred), md5, cert, hba (delegate to a pg_hba-style file), ldap (added in v1.25), pam, trust, any, plain (deprecated). Store credentials in userlist.txt or use auth_query to look them up in Postgres at runtime. v1.25 also added client-side direct TLS (no StartupMessage plaintext round-trip) — set client_tls_sslmode = require and clients can use sslnegotiation=direct in the connection string (PgBouncer 1.25.0).

Common Gotchas

1. SET search_path = ... silently leaks between tenants in transaction mode. Use SET LOCAL inside BEGIN/COMMIT, or put the path in the connection URL.
2. Advisory locks persist on the wrong session. pg_advisory_lock in transaction mode holds a lock on a backend that will be handed to another client. Use pg_advisory_xact_lock.
3. LISTEN appears to work, then randomly doesn't. Whichever backend was holding your subscription got returned to the pool. Route LISTEN clients to a separate session-mode pool or bypass PgBouncer.
4. DEALLOCATE ALL inside the client throws prepared statement "…" does not exist — the rename layer can't find it. Don't manually deallocate; let max_prepared_statements evict.
5. max_client_conn is not default_pool_size × n_users. It is the total TCP connections PgBouncer itself accepts. Forgetting this caps your app's effective concurrency at 100.
6. Monitoring queries the wrong database. SHOW POOLS, SHOW STATS, SHOW CLIENTS must be run against the virtual pgbouncer database, not your app DB.
7. server_reset_query = DISCARD ALL runs in session mode only. In transaction mode it is ignored — cleanup is assumed to be implicit. Old configs copied forward do nothing here.
8. CVE-2025-12819. Any PgBouncer < 1.25.1 accepts a crafted search_path in the startup message before auth completes. Patch or block direct client access at the network layer.
9. HA is your problem. PgBouncer is a single process with no built-in clustering. Run two behind a TCP load balancer or keepalived VIP; pool state (prepared statement cache, stats) is not replicated.
10. Transaction pooling + long-running transactions = head-of-line blocking. A client sitting in BEGIN holds its backend until COMMIT. A 60-second query is a 60-second pool slot outage. Set transaction_timeout (new in v1.25) globally or per user.
