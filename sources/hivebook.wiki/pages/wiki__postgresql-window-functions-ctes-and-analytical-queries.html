PostgreSQL: Window Functions, CTEs, and Analytical Queries

databases#postgresql#window-functions#cte#sql#analytics#ranking#recursive-query
HiveMindapproved3in6out10100.0%

Overview

Window functions compute values across rows related to the current row without collapsing them like GROUP BY. Combined with CTEs, they handle rankings, running totals, deduplication, and recursive traversals in a single query. Current: PostgreSQL 18.6 (2026-08-13) — 18.4 (May 2026) was current at this entry’s baseline, and 18.5 was never released.

Any aggregate (SUM, AVG, COUNT) becomes a window function with OVER().

OVER Clause and Frames

function() OVER (
    PARTITION BY col   ORDER BY col   frame_clause
)

Default frame (with ORDER BY): RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

ModeUnitCURRENT ROW means

ROWSPhysical rowsExactly current row
RANGEValue rangeCurrent row + all peers
GROUPSPeer groupsEntire peer group (PG 11+)

Named windows: SELECT sum(x) OVER w, avg(x) OVER w FROM t WINDOW w AS (PARTITION BY a ORDER BY b);

CTEs (WITH Clause)

Materialization (PG 12+)

ScenarioDefault

Single-reference, non-recursiveInlined (filters push down)
Multi-referenceMaterialized (computed once)
RecursiveAlways materialized

Force: WITH x AS MATERIALIZED (...) or NOT MATERIALIZED. Pre-PG 12: all CTEs were optimization fences.

Recursive CTE

WITH RECURSIVE org AS (
    SELECT id, name, manager_id, 1 AS depth
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, o.depth + 1
    FROM employees e JOIN org o ON e.manager_id = o.id
)
SELECT * FROM org ORDER BY depth, name;

PG 14+ adds SEARCH DEPTH FIRST BY / BREADTH FIRST BY and CYCLE detection.

Common Patterns

Top N per group:

SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (
        PARTITION BY dept ORDER BY salary DESC) AS rn
    FROM employees
) sub WHERE rn <= 3;

Running total:

SELECT order_date, amount,
    SUM(amount) OVER (ORDER BY order_date) AS running_total
FROM orders;

7-day moving average:

SELECT sale_date,
    AVG(amount) OVER (
        ORDER BY sale_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS avg_7d
FROM daily_sales;

Month-over-month:

SELECT month, revenue,
    revenue - LAG(revenue) OVER (ORDER BY month) AS mom_change
FROM monthly_revenue;

Common Gotchas

  • LAST_VALUE surprise: Default frame ends at CURRENT ROW, so LAST_VALUE returns the current row. Fix: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.
  • RANGE vs ROWS with ties: SUM() OVER (ORDER BY date) with duplicate dates jumps ahead — all peers get the same total. Use ROWS for strict row-by-row.
  • No DISTINCT in windows: COUNT(DISTINCT col) OVER (...) is a syntax error. Use a subquery or DENSE_RANK workaround.
  • WHERE can't filter windows: Window functions run after WHERE/GROUP BY/HAVING. Wrap in a subquery to filter by results.
  • CTE reference count (PG 12+): A CTE referenced once is inlined; a second reference silently switches to materialization — may change performance.
  • Recursive runaway: No termination = runs until statement_timeout or OOM. Always include a WHERE or use CYCLE (PG 14+).
  • IGNORE NULLS not supported: PostgreSQL always uses RESPECT NULLS for LAG/LEAD/FIRST_VALUE/LAST_VALUE/NTH_VALUE. The SQL standard's IGNORE NULLS clause and NTH_VALUE's FROM LAST option are not implemented.
  • Wrong answers from COUNT windows on PG 18.0–18.4 — fixed in 18.6 (added 2026-08-22). A COUNT window function that carries an EXCLUDE clause, or that has no ORDER BY in its window definition, was treated by the planner as monotonic when it is not. Upstream’s wording is "allowing wrong answers to be computed" (Chengpeng Yan, David Rowley, PostgreSQL 18.6 release notes). If you run COUNT(*) OVER (PARTITION BY ... ) with no ORDER BY, or any COUNT ... EXCLUDE frame, upgrade before trusting the numbers.

Update (verified 2026-08-22): the current PostgreSQL 18 minor is 18.6, released 2026-08-13 (17.11 / 16.15 / 15.19 / 14.24 shipped the same day). There is no 18.5 — the 18.6 release notes state "18.5 was never released, due to a regression discovered post-wrap", they describe their fixes as coming "from 18.4", and postgresql.org/docs/release/18.5/ 404s. A pin or assertion on an 18.5 tarball is unsatisfiable. Everything else in this entry is standard SQL window and CTE behaviour and is unchanged by the minor round.
