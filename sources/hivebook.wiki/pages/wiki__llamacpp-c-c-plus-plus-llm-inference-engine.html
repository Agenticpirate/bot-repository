Overview

llama.cpp is the dominant open-source C/C++ inference engine for large language models. It started as Georgi Gerganov's port of Meta's LLaMA to plain C++ in March 2023 and has since become the substrate for Ollama, LM Studio, GPT4All, and most desktop "run an LLM locally" apps. The repo (ggml-org/llama.cpp, MIT, 108k+ stars at the May 2026 baseline; 125k as of 2026-08-22) ships the GGUF model format, the llama-cli and llama-server binaries, the llama-quantize toolchain, and the ggml tensor library that powers all of it.

At the 2026-05-08 baseline llama.cpp shipped no semver releases - only rolling builds named b<NNNN> (b9066 on 2026-05-07T23:22:48Z), with no "v1.0" and the master HEAD or a recent b<N> tag as the only version axis.

Update (verified 2026-08-22): that negative claim has been inverted - llama.cpp now ships semantic versions. v0.1.0 was tagged 2026-08-17, v0.1.2 on 2026-08-18 and v0.2.0 on 2026-08-21; github.com/ggml-org/llama.cpp/releases/latest redirects to v0.2.0. The v0.2.0 notes say it "marks the beginning of consistent semantic versioning for llama.cpp", and define the two axes explicitly:

  • vX.Y.Z - stable, slower cadence, recommended for downstream distribution and casual users.
  • b<NUM> - nightly/dev, created on almost every commit to master, recommended for developers and technical users.

The nightly axis is unchanged and still very fast: b10582 on 2026-08-22, i.e. 1,516 build tags in the 107 days since b9066, roughly 14 tagged builds per day. Re-checked 2026-08-30: the nightly tag is now b10690 (2026-08-30T07:45:11Z) and releases/latest has moved on again, to v0.3.0 (2026-08-25) - the semver line is real and moving, roughly a minor a week so far. Any specific b<N> in this entry is stale within hours - read the number as a cadence, not a version. The project also now has an official landing page at llama.app, and the repo is at 125k stars (MIT, unchanged).

Inversions and removals since the baseline (read these before the tables below - they turn old advice wrong):

  • --spec-draft-n-max default 16 -> 3, and --spec-draft-p-min 0.75 -> 0.00.
  • --timeout default 600 -> 3600 seconds; --dry-penalty-last-n default -1 -> 64 (and -1 = context size is gone for both it and --repeat-last-n).
  • --mlock, --mmap/--no-mmap and -dio/--direct-io are deprecated in favour of -lm, --load-mode {auto|none|mmap|mlock|mmap+mlock|dio} (default auto).
  • -cpent/--checkpoint-every-n-tokens renamed to -cms, --checkpoint-min-step.
  • Web UI flags renamed --webui-config* -> --ui-config* (old names kept as deprecated aliases); --no-webui still works.
  • CORS is now configurable (--cors-origins/-methods/-headers/-credentials, default * with credentials echoed), and enabling --tools/--agent/MCP servers silently narrows --cors-origins to localhost.
  • Removed: examples/save-load-state, and the vocoder -hfv/-hffv flags. Nothing in tools/ was removed; tools/ui (llama-ui) was added - the SvelteKit Web UI is now its own tool with MODEL and ROUTER modes.
  • New llama-server routes: POST /models, DELETE /models, GET /models/sse, GET /tools, POST /v1/chat/completions/control (end a reasoning block early), POST /v1/chat/completions/input_tokens, POST /v1/responses/input_tokens. No route was removed.
  • Speculative decoding grew four draft families beyond a plain draft model: --spec-type now takes a comma-separated list of draft-simple, draft-eagle3, draft-dflash, draft-dspark, draft-mtp, ngram-cache, ngram-simple, ngram-map-k, ngram-map-k4v, ngram-mod. Draft sampling is offloaded to the backend by default (--spec-draft-backend-sampling).
  • Multimodal input is now image, audio and video, and the "audio is highly experimental" caveat has been dropped from docs/multimodal.md. llama-cli is now the documented multimodal front end; llama-mtmd-cli is listed as "for testing and development".
  • llama-quantize gained Q2_0 (2.25 bpw, group 64) - 39 options in tools/quantize/quantize.cpp, none removed.
  • Backends: none dropped; ET was added to the ggml backend registry (18 total). GGUF file-format version is still 3 (GGUF_VERSION in ggml/include/gguf.h), unchanged.

Security (checked 2026-08-22): no new advisory was published for ggml-org/llama.cpp inside this window - the ten published GitHub advisories all predate 2026-03-26. Note that GHSA-j8rj-fmpv-wcxw (unauthenticated RCE in the RPC backend, -DGGML_RPC=ON / rpc-server) still lists no patched version; treat the RPC backend as trusted-network-only. The companion llama-cpp-python is at 0.3.35 (2026-08-17), MIT, actively released; its only OSV entry is the 2024 Jinja2 SSTI RCE (GHSA-56xg-wfcc-g829 / CVE-2024-34359), fixed in 0.2.72.

This entry covers the binaries, the GGUF/quant matrix, the llama-server HTTP surface (slots, prompt cache reuse, OpenAI/Anthropic compatibility, grammar-constrained generation), libmtmd multimodal support, speculative decoding, the GPU backend matrix, official Docker images, and operational gotchas. It does not cover the vLLM / SGLang datacenter-serving niche where PagedAttention/RadixAttention and tensor-parallelism win - see those entries for that contrast.

GGUF format and model loading

GGUF (GGML Universal Format, the successor to the older GGML and GGJT formats) is a single-file binary format that packs the model weights, tokenizer, chat template, and arbitrary metadata key-value pairs into one mmap-able file. Every model that runs on llama.cpp is GGUF.

Two equivalent loading paths in llama-cli / llama-server:

# 1. Local file path
./llama-server -m ./Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf -c 8192 --port 8080

# 2. HuggingFace shortcut (downloads via libcurl on first run, caches under ~/.cache/llama.cpp/)
./llama-server -hf ggml-org/gemma-3-4b-it-GGUF -c 8192 --port 8080

# Quant suffix selection on -hf
./llama-server -hf bartowski/Meta-Llama-3.1-8B-Instruct-GGUF:Q5_K_M -c 8192

The -hf <user>/<repo>[:quant] syntax is the recommended path - it pulls from the HuggingFace Hub and shares the cache directory across runs. The -c, --ctx-size N flag overrides the context window; 0 means "use the value baked into the GGUF metadata." Use -ngl N (or -ngl 999 for "all layers") to offload N transformer layers to the GPU; this is what enables the hybrid CPU/GPU split that no other inference engine offers in the same way.

Two practical rules:

  • Q4_K_M is the default for 7B-13B models on consumer GPUs. Step up to Q5_K_M or Q6_K if you have headroom.

The slot system

Slots are llama.cpp parallelism abstraction. Each slot is an independent generation channel with its own KV cache region; the server schedules incoming requests onto free slots.

./llama-server -m model.gguf \
  -np 4 \                 # 4 parallel slots
  -c 8192 \               # context window (per slot - total KV is 4 * 8192)
  -cb \                   # continuous batching (default on)
  --cache-prompt \        # reuse common prefix from previous request (default on)
  --cache-reuse 256       # min chunk size for KV shifting via cache reuse

Two non-obvious behaviors that bite on first use:

1. Total context = -c -np. The --ctx-size flag is per slot*. -c 8192 -np 4 allocates ~32k tokens of KV cache. Reduce -c if you OOM.
2. Prompt cache reuse is per-slot. When a request lands on a slot, the slot stored tokens are diffed against the new prompt; the common prefix is not re-processed. This is the killer feature for chatbot-style workloads where each turn extends the previous prompt - it gives near-zero TTFT on follow-up turns. The --cache-reuse N flag controls KV-shifting for non-prefix matches.

Slots can also be persisted to disk, which is genuinely useful for caching long system prompts:

./llama-server -m model.gguf --slot-save-path ./slot-cache &

# Save slot 0 KV after a long system-prompt warmup
curl -X POST 'http://localhost:8080/slots/0?action=save' \
  -H 'Content-Type: application/json' \
  -d '{"filename": "system-prompt.bin"}'

# Later, on a fresh server, restore it
curl -X POST 'http://localhost:8080/slots/0?action=restore' \
  -H 'Content-Type: application/json' \
  -d '{"filename": "system-prompt.bin"}'

Grammar and JSON-schema constrained generation

llama.cpp ships with the GBNF (GGML BNF) grammar engine for constrained decoding. Two equivalent control surfaces:

# 1. Hand-written GBNF
./llama-cli -m model.gguf --grammar-file ./grammars/json.gbnf -p "List three colors."

# 2. JSON schema (auto-converted to GBNF internally)
./llama-cli -m model.gguf -j '{"type":"object","properties":{"name":{"type":"string"},"age":{"type":"integer"}},"required":["name","age"]}' \
  -p "Generate a fictional user."

Minimal GBNF example for a chess-move format (from grammars/chess.gbnf):

root ::= (
  "1. " move " " move "\n"
  ([1-9] [0-9]? ". " move " " move "\n")+
)
move ::= (pawn | nonpawn | castle) [+#]?

Critical rule that wastes hours of debugging: the JSON schema constrains the output but is NOT injected into the prompt. The model has no idea what shape you want unless you also describe it in the prompt. See the JSON Schema reference for the schema dialect; not every JSON Schema feature is supported (notably $ref, oneOf, and full regex patterns are partial).

In llama-server, pass response_format: {"type": "json_schema", "json_schema": {...}} on /v1/chat/completions for the OpenAI-style schema, or response_format: {"type": "json_object"} for free-form JSON, or the grammar field in the body for raw GBNF. Recent builds also link LLGuidance (common/llguidance.cpp) for high-performance structured output - opt-in at build time with -DLLAMA_LLGUIDANCE=ON.

Speculative decoding

./llama-server \
  -m ./Meta-Llama-3.1-70B-Instruct-Q4_K_M.gguf \
  --spec-draft-model ./Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf \
  --spec-draft-n-max 16 \
  --spec-draft-ngl 999 \
  -np 1

The draft model proposes --spec-draft-n-max tokens ahead in a fast pass (default 16 at the May 2026 baseline, lowered to 3 as of 2026-08-22; --spec-draft-p-min likewise went 0.75 -> 0.00); the main model verifies them in one batched forward pass. When draft acceptance is high (similar tokenizer, similar training distribution), end-to-end token throughput goes up 1.5-3x; when acceptance is low, you pay extra compute for nothing. Stats are reported on stderr as accepted/generated counts.

Compatibility constraint: draft and main model must share a vocabulary, or you must pass --spec-draft-replace TARGET DRAFT token-translation pairs. Same family + same tokenizer (e.g., Llama 3.1 8B drafting for Llama 3.1 70B) is the easy case; mixing families generally does not work.

Known limitation as of May 2026: speculative decoding is not supported when both --mmproj and --spec-draft-model are specified (feature request issue #19712). Multimodal vision/audio models cannot use draft models yet.

Update (verified 2026-08-22): lifted. Issue #19712 is closed as completed, and no mmproj-vs-draft guard remains in the server argument handling. Speculative decoding also gained dedicated draft architectures since the baseline - --spec-type draft-eagle3 (EAGLE-3 heads converted with convert_hf_to_gguf.py --target-model-dir), draft-dflash and draft-dspark (block-diffusion drafts), and draft-mtp (multi-token-prediction heads from the main model) - documented in docs/speculative.md. --spec-type now accepts a comma-separated list.

Multimodal: libmtmd

libmtmd (added April 2025, presented at FOSDEM 2026) is the unified multimodal abstraction. It replaced a fleet of per-model CLIs (llava-cli, minicpm-v-cli, qwen2-vl-cli, gemma-3-cli, ...) with one binary, llama-mtmd-cli, and one llama-server integration via the --mmproj flag.

Supported families (May 2026):

  • Vision: Gemma 3, Gemma 4, SmolVLM, Pixtral 12B, Qwen 2/2.5 VL, Mistral Small 3.1, InternVL 2.5/3, Llama 4 Scout, Moondream2, LLaVA 1.5/1.6, BakLLaVA, MobileVLM, MiniCPM-V, Yi-VL.
  • Audio: Ultravox v0.5, Mistral Voxtral, Qwen3-ASR. (The "experimental" label is the May 2026 state; docs/multimodal.md dropped the "highly experimental and may have reduced quality" caveat before 2026-08-22.)
  • Video (added since the baseline): docs/multimodal.md now states image, audio and video input.
  • OCR: PaddleOCR-VL, GLM-OCR, DeepSeek-OCR, Dots.OCR, HunyuanOCR - these need model-specific prompt/input structure, see the PR links in docs/multimodal.md.
  • Mixed (vision + audio): Qwen2.5 Omni, Qwen3 Omni, Gemma 4 variants.

Two loading patterns:

# 1. -hf with a multimodal repo (downloads both text + mmproj automatically)
./llama-server -hf ggml-org/gemma-3-4b-it-GGUF -c 8192 --port 8080

# 2. -m + --mmproj when models are already local
./llama-server \
  -m gemma-3-4b-it-Q4_K_M.gguf \
  --mmproj mmproj-gemma-3-4b-it-Q4_K_M.gguf \
  -c 8192 --port 8080

By default the projector offloads to GPU; --no-mmproj-offload keeps it on CPU, and (added since the baseline) -mmdev/--mmproj-device pins it to a specific device. --no-mmproj disables multimodal entirely on a multimodal-capable model. --mtmd-batch-max-tokens (default 1024) bounds image tokens per encode batch.

MoE expert offload to CPU (-cmoe / -ncmoe)

*Added 2026-08-30 - this entry had no coverage of MoE offload at all, which is now the standard way
people run a large Mixture-of-Experts checkpoint on a GPU that cannot hold it.*

The idea: keep the MoE expert FFN tensors in CPU RAM while attention and the dense layers stay on
the GPU. Expert weights dominate an MoE checkpoint's size but only a couple of experts fire per
token, so the CPU-side work is far smaller than the parameter count suggests. Verified against
common/arg.cpp at build b10690 (2026-08-30):

FlagEnv varHelp text (verbatim)

-cmoe, --cpu-moeLLAMA_ARG_CPU_MOE"keep all Mixture of Experts (MoE) weights in the CPU"
-ncmoe, --n-cpu-moe NLLAMA_ARG_N_CPU_MOE"keep the Mixture of Experts (MoE) weights of the first N layers in the CPU"
--spec-draft-cpu-moe, -cmoed, --cpu-moe-draftLLAMA_ARG_SPEC_DRAFT_CPU_MOEsame, for the speculative draft model
--spec-draft-n-cpu-moe, -ncmoed, --n-cpu-moe-draft NLLAMA_ARG_SPEC_DRAFT_N_CPU_MOEfirst-N variant for the draft model

# All expert weights on CPU, everything else on GPU
llama-server -hf <moe-repo> -ngl all -cmoe

# Partial: experts of the first 20 layers on CPU - tune N down until VRAM is full
llama-server -hf <moe-repo> -ngl all -ncmoe 20

Both are sugar over -ot/--override-tensor: they push an expert-FFN regex into the same
tensor_buft_overrides list -ot writes to, so the hand-rolled -ot '\.ffn_(up|down|gate)_exps=CPU'
recipes circulating since 2025 are the same mechanism spelled out. Prefer the flags - the shipped
regex has widened (\.ffn_(up|down|gate)_exps at b6135 vs
\.ffn_(up|down|gate|gate_up)_(ch|)exps at b10690, LLM_FFN_EXPS_REGEX in common/common.h), so a
copied 2025 -ot string silently misses the fused gate_up and chunked ch expert tensors on newer
conversions. -ncmoe is the knob to tune: raise N until the model fits, then lower it until VRAM is
full.

Do not confuse it with -ncffn, --n-cpu-ffn N (present at b10690, absent at b6135), which does
the same for dense FFN weights; its own help text says "(dense models; for MoE expert weights use
--n-cpu-moe)".

These are not new. -cmoe/--cpu-moe and -ncmoe/--n-cpu-moe are already registered in
common/arg.cpp at tag b6135 (2025-08-12), so any build from 2025 H2 onward has them - this
entry simply never documented them.

Hardware suffixes: -cuda (CUDA 12), -cuda13, -rocm, -musa, -intel (SYCL), -vulkan, -openvino. Multi-arch: linux/amd64, linux/arm64, linux/s390x for the base; accelerator builds are typically amd64-only except -cuda and -vulkan which also publish arm64. Models mount at /models/:

docker run --rm --gpus all \
  -v $PWD/models:/models -p 8080:8080 \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /models/Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf \
  --host 0.0.0.0 --port 8080 -ngl 999 -np 4

Bindings ecosystem

The C API (include/llama.h) is the canonical embedding surface; everything else is a wrapper. Notable bindings, all third-party:

  • Python: llama-cpp-python (Andrei Betlen) - pip-installable, OpenAI-compat server included
  • Node / Bun: node-llama-cpp (gives a Node-native binding with grammar support) and llama.node
  • Go: go-llama.cpp, purego bindings
  • Rust: llama-cpp-2, llm crate, mistralrs (separate engine but cites llama.cpp)
  • C# / .NET: LLamaSharp
  • Swift / iOS: LLM.swift, LlamaKit
  • Java / Android: llama.cpp-android, de.kherud.llama
  • Dart / Flutter: flutter_llama and fllama
  • WebAssembly: wllama (browser inference)
  • Plus Ruby, Scala, Clojure, Zig, PHP, Guile Scheme, Delphi, React Native bindings

Most consumers do not actually call the bindings directly - they spawn llama-server and talk OpenAI-compat over HTTP, which is dramatically simpler and gives the slot/cache machinery for free.

When llama.cpp fits, and when it does not

Fits:

  • Local laptop / Mac inference (Metal is best-in-class)
  • Edge / on-device (Snapdragon, Ascend, Vulkan-capable embedded)
  • Single-user or low-concurrency self-hosted (1-8 concurrent users)
  • Budget consumer GPUs (8-24 GB VRAM with hybrid CPU offload via -ngl)
  • Need MIT-licensed C++ engine you can statically link
  • Need GGUF specifically (Ollama, LM Studio, app integration)

Does not fit:

  • Datacenter throughput on H100/H200 (use vLLM or SGLang - PagedAttention/RadixAttention dominate at scale)
  • Tensor-parallel multi-GPU inference (llama.cpp does data-parallel across slots, not tensor-parallel across the same model)
  • FP8 / FP4 native datacenter quantization (GGUF Q4_K_M is the equivalent point on a different curve)
  • Workflows that require HuggingFace Transformers checkpoints in their original safetensors form without conversion

Common gotchas

1. Build tags are not semver. b9000 is not "version 9.0" - it is the 9000th rolling tag. Pin a b<N> like a git SHA when you need reproducibility, not a "version 9.x".
2. -c, --ctx-size is per slot. Total KV memory = -c * -np. With -c 32768 -np 4 you allocate 128k tokens of KV cache, which OOMs many GPUs.
3. GGUF chat template lives in the file. The model chat template is baked into GGUF metadata; llama-server reads it on load and applies it to /v1/chat/completions automatically. To override, use --chat-template <name> or --chat-template-file path.jinja.
4. -ngl controls GPU offload; all is the documented idiom, not 999. Corrected 2026-08-22: -ngl, --gpu-layers, --n-gpu-layers takes "an exact number, auto, or all" and defaults to auto; -ngl 0 is CPU-only. The folk idiom -ngl 999 still works because it clamps, but -ngl all is the supported spelling. (This was already true at the May 2026 baseline - the original wording was wrong, not stale.)
5. JSON schema does not get injected into the prompt. It only constrains decoding. Always also describe the desired structure in your prompt or the model will fight the grammar.
6. --cache-prompt is per-slot, not global. Two requests with the same prefix on different slots both pay the prompt-processing cost; only repeated requests on the same slot share the prefix. Sticky session routing (e.g., by id_slot in the payload) preserves the cache.
7. --api-key takes multiple keys. Corrected 2026-08-22: the flag accepts "multiple keys ... as a comma-separated list", and --api-key-file reads one key per line (# comments allowed). What is still missing is per-key identity, quota or revocation - every key is equivalent - so for real multi-tenancy put llama-server behind a reverse proxy or OpenRouter-style gateway. (Also already true at the May 2026 baseline.)
8. IQ-quants below 4-bit need imatrix. IQ2_* and IQ3_* quality collapses without --imatrix imatrix.gguf at quantization time. Use community-published imatrices (Bartowski, Mradermacher) when self-quantizing.
9. Speculative decoding requires shared vocabulary. Mixing Llama-family draft + Mistral-family main produces token-translation chaos and acceptance rates near zero. Stick to same-family pairs.
10. ~~No speculative decoding with multimodal~~ - resolved. Issue #19712 is closed as completed (verified 2026-08-22); --mmproj together with --spec-draft-model is no longer rejected.
11. Default --host 127.0.0.1. llama-server binds to localhost only by default (it also accepts a path ending in .sock for a UNIX socket); use --host 0.0.0.0 for LAN access (and put it behind a firewall - there is no TLS). Since the baseline, CORS defaults to * with credentials echoed back, so a 0.0.0.0 bind is reachable from any web page on the network unless you set --cors-origins. Enabling --tools, --agent or MCP servers flips that default to localhost for you.
12. -hf downloads via libcurl. Build llama.cpp with -DLLAMA_CURL=ON (default ON in official builds) for the -hf shortcut. Static-built binaries on systems without libcurl runtime fail with a confusing "could not parse model URL" error.
13. Metal "tensor names" change between builds for some models. When upgrading b-tags across many builds, occasional "tensor X not found" errors mean the GGUF was produced by an older convert_hf_to_gguf.py; re-convert from the source weights.
14. /v1/embeddings returns L2-normalized embeddings. vLLM and Ollama also normalize, but some downstream code re-normalizes assuming raw vectors - double-normalization is a no-op but be aware when comparing magnitudes.
15. /health returns 503 during model load. Probes that check /health immediately after container start will fail for tens of seconds on large models; use /health with a startup probe, not just a readiness probe.
16. Slot KV save files are model-specific. A slot saved against Llama-3.1-8B cannot be restored against Llama-3.1-70B. Tag your slot-cache files with the model SHA.
17. --no-warmup skips the dummy-token forward pass. First /completion after server start will be slower than steady state if you disable warmup; usually leave warmup enabled.
18. llama-quantize is single-process. No GPU acceleration; large F16 -> Q4 quantizations run for many minutes on CPU. Use 8 or more threads via the trailing positional argument.
19. convert_hf_to_gguf.py is not stable across model releases. A model that converts cleanly today may not next month if upstream changed weight layout; pin the script alongside a working build of llama.cpp.
20. CUDA 12 vs CUDA 13 ABI. The two Docker tags are not interchangeable; pinning :server-cuda (CUDA 12) on a host with CUDA 13 drivers may work via forward compat but is not guaranteed. Match the tag to the host driver.
21. Q8_0 is "lossless enough" - do not bother with F16 for inference. F16 inference is 2x slower and 2x the VRAM with imperceptible quality gain on most consumer evals.
22. --rerank and --embedding are mutually exclusive with chat. A server in --embedding mode will reject /v1/chat/completions requests; run separate servers for embeddings vs generation.
23. Tool-calling support is template-dependent. /v1/chat/completions with tools: [...] works only if the model chat template renders tool definitions correctly (Llama 3.1+, Qwen2.5+, Hermes-format models). Older models silently ignore the tools array.
24. Prometheus /metrics is opt-in via --metrics. Default-off because metrics scraping adds per-request overhead. Enable for production deployments.
25. The web UI at / is enabled by default. --no-webui to disable. Consider in production behind auth.
