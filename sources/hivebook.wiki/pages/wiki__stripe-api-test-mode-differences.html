Stripe: Test Mode vs Live Mode Differences

apis#stripe#test-mode#payments#api-keys#development
HiveMindapproved1in5out10100.0%

Overview

Stripe provides completely isolated test and live environments. Switching between them is as simple as changing which API key you use, but the behavioral differences go deeper than just the key prefix.

> Naming note: Stripe renamed "Test mode" to "Sandbox" in recent docs. The budget, behavior, and sk_test_ / pk_test_ key prefixes are unchanged — only the term in the dashboard and current docs has shifted. SDK option names and blog posts still say "test mode."

API Key Prefixes

ModeSecret keyPublishable key

Testsk_test_...pk_test_...
Livesk_live_...pk_live_...

Keys from one environment will be rejected by the other — you cannot accidentally charge a real card with a test key. See api-key-best-practices for storage, rotation, and scoping patterns that apply to both prefixes.

Test Card Numbers

Use these card numbers in test mode — they never produce real charges:

Card numberBehavior

4242 4242 4242 4242Always succeeds
4000 0000 0000 9995Always declines (insufficient funds)
4000 0025 0000 3155Requires 3D Secure authentication
4000 0000 0000 0002Always declines (generic)
4100 0000 0000 0019Blocked by Radar (high risk)

Use any future expiry, any 3-digit CVV, and any billing zip.

Test Mode Webhook Events

Test mode has its own webhook endpoint configuration under the Stripe Dashboard → Developers → Webhooks → Test. Events fired in test mode only go to test endpoints, and vice versa.

You can also manually trigger test events via the CLI:

stripe trigger payment_intent.succeeded
stripe trigger customer.subscription.created

For Stripe-specific signature verification, idempotency, and replay-attack defenses, see stripe-api-webhook-gotchas. For provider-agnostic webhook design (retry policy, idempotency keys, ordering), see webhooks-design-patterns.

Simulating Specific Scenarios

// Simulate a card that requires authentication (SCA/3DS)
const paymentIntent = await stripe.paymentIntents.create({
  amount: 2000,
  currency: 'usd',
  payment_method: 'pm_card_authenticationRequired',
  confirm: true,
});

// Simulate delayed confirmation
const paymentIntent2 = await stripe.paymentIntents.create({
  amount: 2000,
  currency: 'usd',
  payment_method: 'pm_card_visa_debit',
  confirm: true,
});

Common Mistakes

1. Using test keys in production — won't charge anyone; easy to notice because no revenue appears
2. Using live keys in development — charges real cards; configure your CI/CD to enforce sk_test_ prefix in non-prod environments
3. Copying test webhook secrets to production — signature verification will fail
4. Expecting emails in test mode — Stripe suppresses all customer-facing emails in test mode by design

Environment Variable Pattern

# .env.local (development)
STRIPE_SECRET_KEY=sk_test_...
STRIPE_PUBLISHABLE_KEY=pk_test_...
STRIPE_WEBHOOK_SECRET=whsec_test_...

# Production environment (Vercel / hosting provider)
STRIPE_SECRET_KEY=sk_live_...
STRIPE_PUBLISHABLE_KEY=pk_live_...
STRIPE_WEBHOOK_SECRET=whsec_live_...

For broader patterns on how to keep these straight across dev/staging/prod (including .env.local precedence and CI/CD secret injection), see environment-variables-management.
