Overview

Wazuh is an open-source security platform that combines XDR (Extended Detection and Response) and SIEM (Security Information and Event Management) capabilities for endpoints, cloud workloads, and containers. It runs as a server-indexer-dashboard stack ingesting telemetry from a lightweight agent installed on monitored hosts (Linux, Windows, macOS, AIX, Solaris, HP-UX), then correlates events, scores them against rules, and triggers active response or external integrations. Wazuh is GPLv2-licensed (server, agent, ruleset) with the indexer and dashboard derived from the OpenSearch and OpenSearch Dashboards forks of Elasticsearch/Kibana. Wazuh, Inc. is the commercial steward — but the entire detection stack is OSS, with no telemetry phone-home and no feature gating between community and "enterprise" editions.

This entry covers the 4.14.x stable line and the 5.0 beta line. Its baseline is v4.14.5 (2026-04-23) and v5.0.0-beta1 (2026-04-15); as of a 2026-08-13 re-check the stable line has advanced to v4.14.7 (2026-07-30) and 5.0 is still in beta — see the version table. A 2026-09-06 re-check confirms v4.14.7 is still the newest stable and that the 5.0 line has reached beta5 (2026-09-01) with no GA cut; both the 4.14.5 stable baseline and the 5.0.0-beta1 baseline now sit inside published advisory windows — see Security posture. Wazuh sits next to Falco (which is runtime-only and ephemeral) and to vuln scanners like Trivy and Semgrep (CI-time, not runtime), filling the persistent-agent-on-host-telemetry niche — file integrity monitoring, log ingestion, host vulnerability detection, compliance scoring, and threat hunting.

Agent-manager traffic is AES-256-GCM encrypted by default (or Blowfish), keyed via a per-agent symmetric key minted at enrollment. Manager-indexer traffic moved from Filebeat-bridged HTTPS in 4.x to a native Java indexer-connector inside wazuh-server in 5.0 (Filebeat removed). All inter-component links above 4.14 default to mTLS with autogenerated CA bundles.

Deployment shapes:

  • All-in-one (single host): server + indexer + dashboard on one VM. Suitable for ≤25 agents. curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh && sudo bash ./wazuh-install.sh -a.
  • Distributed (3 hosts minimum): indexer cluster (3 nodes), server (1+ nodes), dashboard (1+ nodes). Default install path for 100+ agents.
  • Multi-master server cluster: cluster.disabled: no in /var/ossec/etc/ossec.conf; 1 master + N workers, agent traffic load-balanced across workers, master handles ruleset + agent metadata sync. In 5.0, cluster.disabled is removed and every install is a single-node cluster by default.

Install (Single-Node Quickstart)

# Wazuh all-in-one (RHEL/Ubuntu/Amazon Linux) — installs 4.14.7 as of 2026-09-06
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
sudo bash ./wazuh-install.sh -a
# Credentials and TLS bundle land in wazuh-install-files.tar
sudo tar -O -xvf wazuh-install-files.tar wazuh-install-files/wazuh-passwords.txt

# Then enroll an agent (Linux, agent-side):
WAZUH_MANAGER='10.0.0.10' WAZUH_AGENT_GROUP='default' apt install wazuh-agent
systemctl enable --now wazuh-agent

Version note (verified 2026-09-06): packages.wazuh.com/4.14/wazuh-install.sh declares readonly wazuh_version="4.14.7", so the command above installs 4.14.7 — not the 4.14.5 this entry was first written against. Do not pin 4.14.5 or 4.14.6: both sit inside published advisory windows (see Security posture).

Agent Capabilities

The agent is a single Go-and-C binary set with 7 capability modules, each declaratively configured under <ossec_config> blocks in /var/ossec/etc/ossec.conf:

ModuleWhat it doesConfig Block

Log data collection (logcollector)Reads syslog/Windows EventLog/journald/files, tags with program_name, ships to manager for decoder/rule evaluation<localfile>
File Integrity Monitoring (syscheckd/FIM)Hashes (SHA-256), perms, owner of watched paths; raises alerts on add/modify/delete; Windows Registry watcher<syscheck>
Security Configuration Assessment (SCA)YAML policies scored against CIS Benchmarks (Linux/Windows/Docker/Kubernetes); pass/fail per check rolls up to a percentage score<sca>
System Inventory (syscollector)Hardware (CPU/RAM/NIC), OS, installed packages, running processes, listening ports, network interfaces<wodle name="syscollector">
Rootcheck / Malware DetectionSignature-based rootkit + trojan checks; suspicious-file rules; hidden-process detection via getsid mismatch<rootcheck>
Vulnerability DetectionCross-references syscollector package inventory against NVD/RedHat/Canonical/Debian/Microsoft CVE feeds; emits CVE alerts per agent<vulnerability-detection>
Active ResponseTriggers scripted host action on rule match (block IP via firewall, kill process, disable account); whitelist/timeout supported<active-response> + <command>

Additional modules:

  • Container Security (Docker listener) — subscribes to /var/run/docker.sock events, tags container telemetry by image + container ID.
  • Cloud Connectors — AWS (CloudTrail, GuardDuty, VPC Flow, WAF, S3), Azure (Sign-in, Activity logs), GCP (Pub/Sub, Asset Inventory), Office 365, GitHub audit log. Each runs as an azure-logs, aws-s3, gcp-pubsub, etc. wodle.
  • MITRE ATT&CK Mapping — rules carry <mitre><id>T1059</id></mitre> IDs; dashboards group alerts by tactic/technique.
  • Anomaly Detection — manager-side wazuh-analysisd baselines event frequency per agent + decoder and raises alerts on deviation (>3σ default).
  • Regulatory Mapping — every rule can carry <pci_dss>, <hipaa>, <nist_800_53>, <gdpr>, <tsc> tags; dashboards roll up by compliance framework.

Server-Side Pipeline

agent (1514) → wazuh-remoted → analysisd (decoders → rules → alerts.json) → indexer-connector → Wazuh Indexer
                                                                                ↘ active-response → exec on agent
                                                                                ↘ integrations (Slack, PagerDuty, VirusTotal, …)

  • Decoders (/var/ossec/etc/decoders/) — regex-on-incoming-log producers; extract fields like srcip, user, command.
  • Rules (/var/ossec/etc/rules/ + /var/ossec/ruleset/rules/) — XML, ordered by <rule id=...> with severity level="0..15" (12+ triggers default email; 7+ is "noteworthy"). Rules cite MITRE technique IDs, compliance refs, and decoder dependencies.
  • CDB lists — append-only key:value text files for IP blocklists / user whitelists / hash IOCs; referenced via <list>etc/lists/blacklist-alienvault</list> then <list field="srcip" lookup="address_match_key">etc/lists/blacklist-alienvault</list>.

Custom rule example (alert on SSH brute-force from a blacklisted IP):

<group name="ssh,authentication_failures,">
  <rule id="100001" level="10">
    <if_sid>5710</if_sid>  <!-- inherit SSHd auth-failure decoder -->
    <list field="srcip" lookup="address_match_key">etc/lists/blacklist-alienvault</list>
    <description>SSH login attempt from blacklisted IP $(srcip)</description>
    <mitre>
      <id>T1110.001</id>  <!-- Brute Force: Password Guessing -->
    </mitre>
    <group>pci_dss_11.4,nist_800_53_AC.7,hipaa_164.312.b,</group>
  </rule>
</group>

API + Integration Surface

The Wazuh REST API runs on port 55000 (TLS, basic-auth-then-JWT, RBAC-aware). Example queries:

# Get a JWT (15 min default expiry; configurable via wazuh-api-config)
TOKEN=$(curl -k -u wazuh:WAZUH_API_PWD -X POST   "https://wazuh:55000/security/user/authenticate" | jq -r '.data.token')

# List agents
curl -k -H "Authorization: Bearer $TOKEN"   "https://wazuh:55000/agents?pretty=true&limit=100"

# Restart an agent (active response)
curl -k -X PUT -H "Authorization: Bearer $TOKEN"   "https://wazuh:55000/agents/001/restart"

# Run a syscheck scan on demand
curl -k -X PUT -H "Authorization: Bearer $TOKEN"   "https://wazuh:55000/syscheck?agents_list=001"

External integration shims (/var/ossec/integrations/): virustotal, slack, pagerduty, shuffle, maltiverse. Wire one up with:

<ossec_config>
  <integration>
    <name>slack</name>
    <hook_url>https://hooks.slack.com/services/T00/B00/XXX</hook_url>
    <level>10</level>
    <alert_format>json</alert_format>
  </integration>
</ossec_config>

Security posture (verified 2026-09-06)

Wazuh's release notes and CHANGELOG.md describe security fixes in neutral engineering language and carry no CVE identifiers — documentation.wazuh.com/current/release-notes/release-4-14-5.html, -4-14-6 and -4-14-7 list none at all. The CVEs live only on the repository's own advisory tab, published in batches weeks after the fix ships. So v4.14.5 — the version this entry was written against and the one its install snippet used to name — sits inside 25 advisory windows, and v4.14.6 inside 12. The three criticals closed in 4.14.6 are all cluster-protocol: CVE-2026-48024 (merged-file header path traversal → arbitrary file write), CVE-2026-48162 (a cluster peer reads arbitrary master files and forges offline REST API administrative state) and CVE-2026-49441 (peer-controlled metadata key in process_files_from_worker); alongside them, CVE-2026-44901 (DAPI protocol deserialization → RCE) and CVE-2026-45798 (pre-auth stack overflow reachable from wazuh-authd). The 4.14.7 batch is the same attack surface one layer deeper — CVE-2026-61802 and CVE-2026-61783 (cluster.key disclosed to low-privilege API users), CVE-2026-61800 (an incomplete fix for CVE-2026-30893), CVE-2026-54083 / CVE-2026-54085 (active-response path traversal and argument injection), CVE-2026-71540 and CVE-2026-74046 (pre-auth memory amplification, zlib decompression bomb) — plus an advisory with no CVE at all, "SQL injection → RCE in wazuh-dbd (PostgreSQL output)", which is why 4.14.7 removed that daemon outright rather than merely deprecating it.

v4.14.7 carries no advisory of its own as of 2026-09-06. Cross-checks, because no single database answers this: an NVD CPE query for cpe:2.3:a:wazuh:wazuh:4.14.5 returns 18 CVEs — a floor, not a census, since the newest ids are still vulnStatus: Received with no CPE configuration — while the same query on 4.14.7 returns only CVE-2026-67307, whose CPE range is over-broad (its advisory scopes it to 5.0.0-beta1, fixed in beta3). OSV has no wazuh coordinate at all ({"package":{"name":"wazuh"}} → 400 invalid query), so an empty OSV result for Wazuh means "not indexed", never "clean". Practical rule: on the 4.14 line, 4.14.7 is the only version with nothing outstanding against it, and packages.wazuh.com/4.14/wazuh-install.sh already pins it.

Vulnerability Detection (detail)

Wazuh's vuln detector cross-references syscollector's package inventory against per-distro CVE feeds:

  • NVD (NIST National Vulnerability Database) — full CVE catalog with CVSS v3/v4 scores
  • Red Hat OVAL — RHEL-specific patches and "fixed in" advisories
  • Canonical OVAL — Ubuntu USNs
  • Debian Security Tracker — DSAs
  • Microsoft MSRC — Windows + Office patches
  • Arch Linux Security Tracker — for the rolling-release Arch agents

A CVE alert carries package.name, package.version, cve.id, cve.cvss3.base_score, vulnerability.severity, vulnerability.published, and vulnerability.reference. Per OSV-Scanner parallels, Wazuh's vuln detector is agent-installed-package centric (host-level, not project-level) — it scans what's running on the box, not what's declared in a package-lock.json. The two are complementary: use Trivy/OSV-Scanner pre-deploy, Wazuh post-deploy.

Common Gotchas

  • Agent ID 000 is the manager itself, not "no agent". Pre-5.0, manager-internal events use ID 000. 5.0 removes this special case — manager events now route through a normal-shaped agent record. Scripts that filter agent.id != "000" to skip the manager break on 5.0; switch to agent.id != manager.name.
  • OpenSearch version pin is rigid. Wazuh Indexer 4.14.x is a specific OpenSearch 2.x fork — you cannot run a "vanilla" OpenSearch 2.x cluster and point Wazuh server at it. The Wazuh fork carries security-template + index-template differences that vanilla rejects. Verified 2026-09-06 from the artifact: wazuh-indexer's buildSrc/version.properties reads opensearch = 2.19.5 at tag v4.14.7 and opensearch = 3.6.0 at v5.0.0-beta5 — so the 5.0 Indexer is an OpenSearch 3.x fork. The pin is not just rigid, it crosses a major version at the 5.0 re-deploy.
  • FIM cost is hash + stat per watched path on every check_interval (default 12 hours). Watching / recursively on a 1M-file host can spike wazuh-syscheckd to multi-GB RSS during a scan. Scope with <directories check_all="yes" realtime="yes"> only for hot paths; rely on whodata (audit subsystem) on Linux for low-overhead real-time watching of large trees.
  • Decoders are XML, not Grok/Sigma. Wazuh decoders use <regex> + <order> + <prematch> semantics; Logstash Grok patterns and Sigma rules do not translate 1:1. Checked 2026-09-06: there is no official Sigma backend for Wazuh. SigmaHQ's plugin directory (SigmaHQ/pySigma-plugin-directory, pySigma-plugins-v1.json) lists 36 plugins — 31 backends and 5 pipelines — and the string wazuh does not appear anywhere in the file. What exists is one community project by a single author: theflakes/sigma_to_wazuh (Python), whose README's first line now says the work has moved and will not be updated (last commit 2025-09-13), and its Go successor theflakes/StoW, whose README still describes its own state as a "Skeleton PoC" (last commit 2026-04-28). Neither has ever cut a tagged release. The subset limit is visible in the shipped code rather than only in the prose: stow.go hard-skips any Sigma rule whose detection contains timeframe:, plus near, parenthesised and CIDR conditions, and the Python version's own sample run reports 119 of 1,017 rules skipped. Treat Sigma coverage as a hand-porting exercise, not a conversion step — and note that the 5.0 Engine changes the asset format again (src/engine/ruleset/ is YAML plus JSON schemas including wazuh-decoders.json), so anything you build against 4.14.x XML decoders is a second port later.
  • The "Wazuh API" (port 55000) and the "Wazuh Indexer API" (port 9200) are different services with different auth. The 55000 API is JWT after basic-auth-to-/security/user/authenticate. The 9200 API is HTTP basic-auth (admin:password from wazuh-passwords.txt). RBAC roles in the 55000 API have no effect on direct Indexer queries — locking down Dashboard ≠ locking down the raw indexer endpoint.
  • cluster.key in ossec.conf is a 32-character hex secret that all manager nodes must share. A typo on a worker silently breaks worker → master sync (wazuh-clusterd connects, fails auth, retries forever, logs only to /var/ossec/logs/cluster.log). Always validate cluster health via /var/ossec/bin/cluster_control -l after a reconfig. Treat it as an API-reachable secret, not just a config value: CVE-2026-61802 (GET /cluster/local/config returned it to any cluster:read user) and CVE-2026-61783 (the RBAC permission-effect check in mask_sensitive_config) both disclosed cluster.key to low-privilege API callers on every 4.14.x before 4.14.7. Rotate it on any cluster that ran 4.14.0–4.14.6 with non-admin API users.
  • Vuln detector NVD feed pulls require outbound HTTPS to nvd.nist.gov from the manager — air-gapped installs need a Trivy-style offline DB mirror, configured via <offline_url> in <vulnerability-detection>. In 5.0 this moves into the Indexer as a managed CTI integration.
  • NVD CVSS scores can differ from upstream CNA scores by ≥1 point. Wazuh emits the NVD score per alert; cross-reference against the cvss.base_severity in services.nvd.nist.gov/rest/json/cves/2.0?cveId=... when escalating — vendor advisories (Red Hat, GitHub) sometimes score differently for the same CVE.
  • active-response runs as root by default on Linux. A typo in your block-IP script (e.g. forgot to validate srcip shape) is a remote-trigger root-shell vector if attackers can spoof a log event matching a rule that triggers it. Always sanitize $ARGV[3] (srcip) against ^(\d{1,3}\.){3}\d{1,3}$ before invoking firewall commands. Wazuh's own bundled scripts carried this bug: CVE-2026-54085 (missing input validation across several active-response scripts, allowing argument injection) and CVE-2026-54083 (path traversal in ip-customblock allowing arbitrary file creation and deletion) were both fixed in 4.14.7 — the diff of src/active-response/ip-customblock.c between v4.14.6 and v4.14.7 is exactly the addition of validated srcip parsing.
  • Manager → indexer Filebeat output is gone in 5.0. Migration scripts that piped through Filebeat (Logstash, kafka, S3) need to re-anchor on the Indexer's own ingest pipelines or use the indexer-connector config-driven outputs.
  • Agent registration via agent-auth is removed in 5.0. Use the /agents REST endpoint or the dashboard's "Add new agent" wizard; agent-auth shell calls in provisioning scripts break.
  • GPLv2 license on the agent matters for vendored distribution. Embedding the Wazuh agent in a closed-source appliance distribution requires either an exception from Wazuh Inc. or open-sourcing the surrounding agent-launching code. The server side changes in 5.0: its new src/engine/ component is AGPL-3.0, not GPLv2 — see License.
