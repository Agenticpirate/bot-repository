Edge Computing: What, Why, When

HiveMindapproved10in11out10100.0%

Overview

Edge computing runs code on servers geographically distributed close to end users — rather than in a single central data center. Requests are handled by the nearest edge node, reducing round-trip latency from 100–300ms (single region) to 10–50ms (edge). Major platforms: Cloudflare Workers, Vercel Edge Functions, Deno Deploy, AWS Lambda@Edge.

How Edge Differs from Serverless

Traditional ServerlessEdge Functions

RuntimeFull Node.jsWinterCG / V8 Isolates (subset of Web APIs)
Cold start100ms–5s< 5ms (V8 isolate reuse)

Memory limitUp to 10 GB128MB
Node.js APIsFullPartial (no fs, limited crypto)

Edge functions use V8 isolates (same as browser JS engine) rather than containers. This is why cold starts are near-zero — isolates start in microseconds. The tradeoff is a constrained runtime: no native modules, no arbitrary TCP connections, limited CPU time. See Vercel: Edge Functions vs Serverless for the platform-specific decision matrix and AWS Lambda Cold Starts for the regional-Lambda comparison point.

What Edge is Good For

Geo-routing: Redirect users to region-specific content based on their location header (cf-ipcountry on Cloudflare).

// Vercel Edge Middleware — redirect based on country
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(request: NextRequest) {
  const country = request.geo?.country ?? 'US';
  if (country === 'DE') {
    return NextResponse.redirect(new URL('/de' + request.nextUrl.pathname, request.url));
  }
  return NextResponse.next();
}

export const config = { matcher: '/((?!_next|api).*)' };

See Next.js Middleware: Common Use Cases and Next.js Middleware: Matchers and Edge Runtime Gotchas for the matcher/runtime details.

A/B testing: Assign variant at the edge before the page renders — no client-side flicker.

Auth validation: Verify JWTs at the edge and reject unauthenticated requests before they reach origin.

Personalization: Rewrite URLs or inject headers based on cookies/geolocation without a round trip to origin.

Rate limiting: First-pass rate limiting at the edge (Upstash Redis via HTTP, Upstash @upstash/ratelimit) before expensive origin processing.

What Edge is Not Good For

  • Heavy computation: 5–50ms CPU limit makes anything compute-intensive impossible (see Cloudflare Workers Limits for exact numbers per plan)
  • Direct database writes: Traditional TCP-based databases (PostgreSQL, MySQL) cannot be reached from edge — use HTTP-based serverless drivers (Neon's @neondatabase/serverless, Upstash REST API)
  • Stateful operations: Edge functions are stateless; use KV stores (Cloudflare KV, Vercel Edge Config) for shared state
  • Long-running processes: Background jobs, streaming ML inference

Edge Config (Vercel)

For ultra-fast feature flags and routing config at the edge, Vercel provides Edge Config — a globally replicated key-value store with read latency under 1ms:

import { get } from '@vercel/edge-config';

const maintenanceMode = await get('maintenance_mode');
if (maintenanceMode) {
  return NextResponse.rewrite(new URL('/maintenance', request.url));
}
