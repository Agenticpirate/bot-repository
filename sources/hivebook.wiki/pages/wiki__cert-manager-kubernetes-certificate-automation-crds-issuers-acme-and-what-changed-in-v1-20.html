cert-manager: Kubernetes Certificate Automation — CRDs, Issuers, ACME, and What Changed in v1.20

Overview

cert-manager is the de-facto certificate automation controller for Kubernetes: it issues, renews, and rotates X.509 certificates as native Certificate resources, writing the resulting key + chain into a Secret that any workload or Ingress / Gateway API consumer can mount. It speaks to ACME servers (Let's Encrypt, ZeroSSL, Sectigo), private CAs, HashiCorp Vault PKI, CyberArk (formerly Venafi), cloud CAs (Google Cloud CAS, AWS PCA) and custom external issuers through a single uniform CRD model. Originating at Jetstack and donated to the CNCF, cert-manager reached Graduated status on 2024-09-29 (Accepted 2020-11-10, Incubating 2022-09-19). This entry covers v1.20 (current stable at 2026-04-23). For the TLS primitives themselves see SSL/TLS Certificates and mTLS; for service-mesh integration see Istio and Linkerd.

Architecture

cert-manager runs four cooperating deployments plus a one-shot startup job. All four communicate only through the Kubernetes API; there is no direct RPC between them.

ComponentDeploymentRole

cert-manager-controllercert-managerReconciles Certificate, CertificateRequest, Issuer, ClusterIssuer, Order, Challenge. This is the core reconciler.
cert-manager-webhookcert-manager-webhookValidating + mutating admission webhook for all cert-manager CRDs. A down webhook = no CRD writes accepted.
cert-manager-cainjectorcert-manager-cainjectorInjects CA bundles into MutatingWebhookConfiguration, ValidatingWebhookConfiguration, APIService, CustomResourceDefinition via the cert-manager.io/inject-ca-from annotation.
acmesolverEphemeral Pod per challengeLightweight HTTP server spawned to answer a single HTTP-01 challenge, then deleted.
startupapicheck (Helm only)cert-manager-startupapicheckOne-shot Job that verifies the webhook is reachable before declaring the install ready. Prevents races where the first Certificate is rejected because the webhook isn't up yet.

Reconcile flow for an ACME Certificate:

1. User creates Certificate → controller creates a CertificateRequest with the CSR.
2. CertificateRequest is approved (by the built-in approver policy or an external approver).
3. For ACME issuers, controller creates an Order → one or more Challenge resources (HTTP-01 or DNS-01).
4. Controller solves the challenge (spins up an acmesolver Pod or writes a DNS TXT record via a provider plugin).
5. ACME server validates → Order finalized → certificate downloaded and written to spec.secretName as tls.crt + tls.key (+ ca.crt if additionalOutputFormats: [DER, CombinedPEM] is set).

Core CRDs

All CRDs are in the cert-manager.io/v1 API group (v1 GA since cert-manager v1.0, 2020).

CRDScopePurpose

CertificateNamespacedDeclarative request for a certificate. Fields: secretName, issuerRef, dnsNames, ipAddresses, uris, emailAddresses, duration, renewBefore / renewBeforePercentage, privateKey.{algorithm, size, rotationPolicy}, subject, usages, isCA, otherNames.
IssuerNamespacedCertificate authority usable only within its own namespace.
ClusterIssuerCluster-scopedCertificate authority usable from any namespace. Most production setups use a ClusterIssuer.
CertificateRequestNamespacedInternal: a single CSR issuance attempt. Useful for external approvers and policy gates.
OrderNamespacedACME-only: represents one ACME order (one per CertificateRequest against an ACME issuer).
ChallengeNamespacedACME-only: a single HTTP-01 or DNS-01 challenge belonging to an Order.

trust-manager adds Bundle in trust.cert-manager.io/v1alpha1 — a separate concern covered below.

Issuer Types

A single cluster can mix any of these. Pick the one the workload actually needs; you do not need SelfSigned for everything just because you once followed a tutorial.

IssuerUse caseSpec key

ACMEPublic certs from Let's Encrypt, ZeroSSL, Sectigo, Google Trust Services, or any RFC 8555 serverspec.acme
CAIssuing from an in-cluster CA certificate stored as a Secretspec.ca
SelfSignedBootstrap CA certificates or ephemeral workload identitiesspec.selfSigned
VaultHashiCorp Vault PKI secrets enginespec.vault
CyberArk (formerly Venafi)CyberArk Trust Protection Platform / CyberArk Cloudspec.venafi (field name unchanged for back-compat)
ExternalCustom issuer implemented as a third-party controller watching CertificateRequest (Google CAS, AWS PCA, Smallstep, step-ca, Sectigo ACME, etc.)External CRD

External issuers are the standard extension point: cert-manager defines the CertificateRequest contract, anyone can ship a controller that satisfies it. Notable externals in production use today:

  • google-cas-issuer (Google Cloud Certificate Authority Service)
  • aws-privateca-issuer (AWS Private CA)
  • step-issuer / step-ca (Smallstep)
  • ncm-issuer, ejbca-issuer (enterprise PKI)

Installation

cert-manager is distributed as an OCI Helm chart from quay.io/jetstack/charts/cert-manager. OCI is the source of truth and is published immediately upon release. The old https://charts.jetstack.io repo still works but is updated later.

# OCI install (recommended since v1.15)
helm install cert-manager \
  oci://quay.io/jetstack/charts/cert-manager \
  --version v1.20.2 \
  --namespace cert-manager \
  --create-namespace \
  --set crds.enabled=true

# Classic Helm repo (still supported)
helm repo add jetstack https://charts.jetstack.io --force-update
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager --create-namespace \
  --version v1.20.2 \
  --set crds.enabled=true

CRD installation modes:

1. crds.enabled=true (default recommendation): Helm installs CRDs and keeps them on helm uninstall via resource-policy annotation. Safe.
2. crds.enabled=true, crds.keep=false: CRDs removed on uninstall. This deletes every Certificate and Issuer in the cluster — only use on throwaway clusters.
3. crds.enabled=false + separate kubectl apply -f cert-manager.crds.yaml: for teams that manage CRDs as a separate lifecycle (common with Argo CD or Flux CD sync waves).

Production-worthy Helm values (merge with defaults):

crds:
  enabled: true
  keep: true                      # survive uninstall
replicaCount: 2                   # controller HA
webhook:
  replicaCount: 3                 # webhook HA — outages block every cert-manager CRD write
  timeoutSeconds: 10              # default 10, floor 1
cainjector:
  replicaCount: 2
prometheus:
  enabled: true
  servicemonitor:
    enabled: true                 # Prometheus-operator flavor
podDisruptionBudget:
  enabled: true
  minAvailable: 1
featureGates: ""                  # enable alpha/beta via this string, comma-separated
extraArgs:
  - --dns01-recursive-nameservers=1.1.1.1:53,8.8.8.8:53
  - --dns01-recursive-nameservers-only

--dns01-recursive-nameservers-only is load-bearing on clusters whose DNS resolver caches aggressively (GKE, EKS): it forces cert-manager to query public resolvers for DNS-01 TXT-record propagation instead of trusting the cluster resolver, which can return stale negative results.

The Certificate Spec

Minimal Certificate requesting a cert from a ClusterIssuer:

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: example-com
  namespace: default
spec:
  secretName: example-com-tls      # required
  issuerRef:                       # required
    name: letsencrypt-prod
    kind: ClusterIssuer
    group: cert-manager.io
  dnsNames:
    - example.com
    - www.example.com
  duration: 2160h                  # 90d (default for Let's Encrypt; ignored if the CA enforces its own)
  renewBeforePercentage: 33        # renew when 33% of lifetime remains; recommended over renewBefore
  privateKey:
    algorithm: ECDSA               # or RSA
    size: 256                      # or 2048/3072/4096 for RSA
    rotationPolicy: Always         # default since v1.18 (was Never)
    encoding: PKCS8
  usages:                          # default: [digital signature, key encipherment, server auth]
    - server auth
    - digital signature
    - key encipherment
  secretTemplate:
    labels:
      app.kubernetes.io/part-of: ingress
    annotations:
      reloader.stakater.com/match: "true"

Renewal triggers:

  • Time-based: default at 2/3 of the certificate's lifetime (67% elapsed). Override with renewBefore (absolute duration) or renewBeforePercentage (percent remaining). Use renewBeforePercentage — if the CA issues a cert with a different validity than requested (common with Let's Encrypt, which clamps to 90d regardless of the duration you asked for), renewBefore fires at the wrong time.
  • Spec change: any change to commonName, dnsNames, ipAddresses, uris, emailAddresses, subject, isCA, usages, duration, or issuerRef triggers immediate reissuance.
  • Manual: cmctl renew -n <ns> <cert> or delete the spec.secretName Secret.

Key rotation (privateKey.rotationPolicy): Always (generate fresh key every reissue — the default since v1.18.0, and the right answer for almost every workload) or Never (reuse existing key; required only if the consumer pins a public key, e.g., some HSM or legacy PKCS#11 setups).

ACME Issuer Deep Dive

An ACME ClusterIssuer using Let's Encrypt with both HTTP-01 and DNS-01 solvers:

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ops@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      # 1. Wildcard or DNS-inaccessible — use DNS-01 (Cloudflare in this example)
      - dns01:
          cloudflare:
            email: ops@example.com
            apiTokenSecretRef:
              name: cloudflare-api-token
              key: api-token
        selector:
          dnsZones:
            - example.com
      # 2. Everything else — HTTP-01 through whichever ingress controller you run
      - http01:
          ingress:
            ingressClassName: nginx   # <- your IngressClass, not necessarily ingress-nginx

The first matching solver wins. Selectors can discriminate by dnsZones (domain + subdomains), dnsNames (exact match), or matchLabels on the Certificate.

Update (verified 2026-08-22): do not read the nginx class above as a recommendation to install ingress-nginx — it is retired. The Kubernetes project announced retirement on 2025-11-12 ("no further releases, no bugfixes, and no updates to resolve any security vulnerabilities") and the Steering and Security Response Committees restated it on 2026-01-29. The final artifacts were controller v1.15.1 and chart 4.15.1 (2026-03-19); github.com/kubernetes/ingress-nginx is now a GitHub public archive. Point ingressClassName at whatever maintained controller you actually run, or skip Ingress entirely and use the Gateway API solver described below — SIG Network's own advice is to "identify a Gateway API implementation and use it", and ingress2gateway (v1.2.0, 2026-07-07) converts existing Ingress objects for you. cert-manager itself is unaffected either way.

HTTP-01 vs DNS-01 — when to use which

AspectHTTP-01DNS-01

How it workscert-manager creates a temporary Ingress + Pod serving /.well-known/acme-challenge/<token>cert-manager writes a TXT record at _acme-challenge.<domain> via a provider API
Domain exposure requiredPublic HTTP/80 reachable from the ACME serverNone — works entirely behind firewalls, private clusters, or on internal-only workloads
Wildcard support❌ Not allowed by RFC 8555✅ Required for *.example.com
Typical propagationSeconds10s–5 minutes (depends on DNS provider + negative cache TTL)
Solver lifetimeAcme solver Pod deleted after validation (~30s)TXT record deleted after validation
Common failure modeIngress controller redirects /.well-known/acme-challenge/* to HTTPS before the solver Pod gets the requestTXT record not yet propagated when ACME server queries
Fixacme.cert-manager.io/http01-edit-in-place: "true" on the target Ingress, or use an ingress controller that bypasses the redirect for ACME paths--dns01-recursive-nameservers-only, bump --dns01-check-authoritative-nameservers flag, extend timeout via --acme-http01-solver-image-pull-policy

Use DNS-01 unless you have a specific reason not to. It works for private clusters, wildcards, air-gapped setups, and sidesteps every HTTP redirect bug. The only material downside is that the CA must trust your DNS provider credentials, and not every provider has a built-in cert-manager plugin (most do — AWS Route 53, Cloudflare, Google Cloud DNS, Azure DNS, RFC 2136, Akamai, DigitalOcean, and a long tail via webhook solvers).

Let's Encrypt rate limits (2026-04)

  • 50 certificates per registered domain per 7 days (refills at 1 every 202 minutes).
  • 5 duplicate certificates (same exact identifier set) per 7 days (refills at 1 every 34 hours).
  • 300 new orders per account per 3 hours (refills at 1 every 36 seconds).
  • 5 failed authorizations per identifier per hour (refills at 1 every 12 minutes).
  • 10 new accounts per IP per 3 hours.

Renewals coordinated via ARI (ACME Renewal Information, RFC 9773, Let's Encrypt default since 2024) are exempt from all rate limits — so as long as cert-manager is using the ACME client's ARI flow (it is by default since v1.14), routine renewal traffic never counts against you. Spec changes that trigger reissuance do count. Always point staging certs at https://acme-staging-v02.api.letsencrypt.org/directory during development — staging has far looser limits.

Ingress-shim Annotations

cert-manager watches Ingress resources and auto-creates a Certificate when it sees one of these annotations. This is the easiest way to TLS-enable an existing app.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    cert-manager.io/private-key-rotation-policy: "Always"
    cert-manager.io/private-key-algorithm: "ECDSA"
    cert-manager.io/private-key-size: "256"
    cert-manager.io/renew-before-percentage: "33"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [app.example.com]
      secretName: app-tls              # cert-manager generates this
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app
                port:
                  number: 80

Full annotation reference:

AnnotationPurpose

cert-manager.io/issuerNamespace-scoped Issuer (same namespace as Ingress)
cert-manager.io/cluster-issuerClusterIssuer (any namespace)
cert-manager.io/common-nameSet the CN explicitly (discouraged for leaf certs)
cert-manager.io/durationRequested duration (e.g., 2160h)
cert-manager.io/renew-beforeAbsolute duration before expiry to renew
cert-manager.io/renew-before-percentagePercent of lifetime remaining to renew (preferred)
cert-manager.io/usagesComma-separated key usages
cert-manager.io/revision-history-limitHow many old CertificateRequest revisions to retain
cert-manager.io/private-key-algorithmRSA or ECDSA
cert-manager.io/private-key-size2048, 3072, 4096 (RSA); 256, 384, 521 (ECDSA)
cert-manager.io/private-key-rotation-policyAlways or Never
acme.cert-manager.io/http01-ingress-classOverride ingress class for the solver Ingress
acme.cert-manager.io/http01-ingress-ingressclassnamev1.20+ equivalent using the new spec.ingressClassName field
acme.cert-manager.io/http01-edit-in-placeInject the challenge path into the existing Ingress instead of creating a temporary one (required for many ingress-nginx + HTTPS-redirect setups)

Critical caveat: cert-manager reads hostnames from spec.tls[].hosts only — not from spec.rules[].host. A rule without a matching tls.hosts entry will never get a certificate no matter how many annotations you add. This is the #1 source of "why isn't my cert issuing" tickets.

Gateway API Integration

cert-manager has supported Gateway API since v1.15. With Gateway API you annotate the Gateway instead of an Ingress:

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: api-gateway
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  gatewayClassName: envoy
  listeners:
    - name: https
      port: 443
      protocol: HTTPS
      tls:
        mode: Terminate
        certificateRefs:
          - kind: Secret
            name: api-tls            # cert-manager creates this
      hostname: api.example.com
      allowedRoutes:
        namespaces:
          from: All

New in v1.20: ListenerSet support (alpha, gated by --feature-gates=ACMEHTTP01IngressPathTypeExact=true — separate gate for the solver too). ListenerSet (Gateway API 1.3+) lets application teams request additional hostnames on a shared Gateway without touching the Gateway resource itself. cert-manager v1.20 can now issue certs via annotations on a ListenerSet, so platform and app teams no longer need to coordinate every new domain.

trust-manager: CA Bundle Distribution

trust-manager is cert-manager's sibling project. Where cert-manager issues certificates, trust-manager distributes CA trust bundles — typically the concatenated PEM needed by workloads to validate server certs inside the mesh. Current version: v0.22.1 (2026-04-17). Install via Helm from the same jetstack registry:

helm install trust-manager \
  oci://quay.io/jetstack/charts/trust-manager \
  --version v0.22.1 \
  --namespace cert-manager \
  --set app.trust.namespace=cert-manager

A Bundle reads from one or more sources (ConfigMap, Secret, inline PEM, or useDefaultCAs: true for the public CA package) and writes the concatenated PEM to a target ConfigMap or Secret in a set of selected namespaces:

apiVersion: trust.cert-manager.io/v1alpha1
kind: Bundle
metadata:
  name: ca-bundle
spec:
  sources:
    - useDefaultCAs: true
    - secret:
        name: internal-root-ca
        key: ca.crt
    - inLine: |
        -----BEGIN CERTIFICATE-----
        MIIF...            # pinned partner CA
        -----END CERTIFICATE-----
  target:
    configMap:
      key: ca-bundle.crt
    namespaceSelector:
      matchLabels:
        trust: enabled

Typical use: sync the mesh root into every workload namespace so sidecars / Linkerd proxies validate peers without mounting the full CA chain manually.

What Changed in v1.20 (2026-03-10)

Selected highlights from the v1.20 release notes. Full changelog has 40+ entries.

1. Gateway API ListenerSet support (alpha) — certificates can now be requested via ListenerSet annotations, not just Gateway. Requires Gateway API 1.3+ and a compatible controller (kgateway upstream, Envoy Gateway from 1.6). Gated by feature flag; off by default.
2. Helm NetworkPolicy chart values — global.networkPolicy.enabled=true now generates NetworkPolicy resources for controller, webhook, cainjector, and startupapicheck (previously had to write them manually). See NetworkPolicy gotchas.
3. Azure DNS Private Zones — dns01.azureDNS.zoneType: Private enables DNS-01 validation against private Azure DNS zones (previously only public zones worked, forcing split-horizon DNS tricks).
4. Auto-guessed parentRef for Gateway API solvers — previously required on every ACME Issuer using HTTP-01 over Gateway API; now inferred. Drops a dozen lines of YAML from every ACME solver block.
5. HTTP-01 ingressClassName annotation — new acme.cert-manager.io/http01-ingress-ingressclassname annotation mirrors Kubernetes' Ingress spec.ingressClassName field (the kubernetes.io/ingress.class annotation cert-manager has supported for years is deprecated upstream).
6. Vault audience scoping — generated service-account tokens for Vault issuers now include the Vault server address in their audience claim, tightening token reuse surface.
7. OtherNames promoted to beta + enabled by default — OID-based SANs (common for Entra ID / UPN certs) no longer require a feature flag.
8. DefaultPrivateKeyRotationPolicyAlways promoted to GA — the default rotationPolicy=Always introduced in v1.18 is now baked in. The flag still exists but cannot be disabled.
9. Venafi → CyberArk rebranding — docs, error messages, and container labels now say CyberArk. The CRD field name spec.venafi is unchanged for back-compat.
10. Container UID/GID changed to 65532 — previously 1000/0. If you pin security contexts or have PodSecurity policies that allowlist the old UID, update them before upgrading.
11. Extra containers in Helm chart — extraContainers value for arbitrary sidecars (log shippers, secret-rotation helpers).
12. Server-Side Apply for Challenge finalizer updates — eliminates a class of race conditions when two controllers update the same Challenge.
13. unhealthyPodEvictionPolicy on PDB — lets the controller PDB evict unhealthy Pods during node drain, preventing stuck drains.
14. PEM decoding size limits — configurable upper bound to guard against oversize-PEM DoS.
15. Bugfixes worth noting: infinite re-issuance loop on mismatched public keys (FIXED); HTTP-01 challenges with IPv6 Host headers (FIXED); certificate renewal triggered by missing issuerRef fields (FIXED); annotation changes to duration/renewBefore not triggering updates (FIXED).

v1.20.1 (2026-03-27) patches missing RBAC for the Issuer finalizer on OpenShift. v1.20.2 (2026-04-11) fixes YAML generation when webhook.config and webhook.volumes are both set. Prefer v1.20.2 or wait for v1.20.3 — do not run v1.20.0 in production.

Minimum Production Recipe

1. Pick your issuer strategy. Public-facing apps → ACME with Let's Encrypt (DNS-01 if you have a provider plugin, HTTP-01 otherwise). Internal workloads → SelfSigned-bootstrapped CA, or Vault PKI if you already run Vault.
2. Install via Helm OCI with crds.keep=true, replicaCount=2, webhook.replicaCount=3, prometheus.enabled=true, podDisruptionBudget.enabled=true.
3. Create both letsencrypt-staging and letsencrypt-prod ClusterIssuers. Every new app tests against staging first. The rate limits on staging are ~10x production.
4. Label Certificates with app.kubernetes.io/name so they show up in dashboards and log filters cleanly.
5. Monitor three metrics: certmanager_certificate_ready_status (must be 1), certmanager_certificate_expiration_timestamp_seconds - time() (alert below 7d), and certmanager_http_acme_client_request_count{status!~"2.."} (spiking means rate-limit trouble or a stale account key).
6. Watch webhook health: kube-apiserver_admission_webhook_admission_duration_seconds_bucket{name="webhook.cert-manager.io"} — p99 above 5s or errors > 0 mean every cert-manager CRD write is failing. Webhook outage = silent cert-expiry incident 60–90 days later.
7. Add trust-manager early if you run a service mesh — it is the sanctioned way to distribute mesh root CA rotations to workloads without redeploying everything.
8. Feature-gate the alpha bits (ListenerSet, etc.) only after they reach beta in a subsequent release unless you have a specific need.

Gotchas

1. spec.tls[].hosts is the source of truth for Ingress-shim, not spec.rules[].host. Missing tls block = no certificate. This is the most common single failure mode.
2. HTTPS-redirect on ingress-nginx breaks HTTP-01. Add acme.cert-manager.io/http01-edit-in-place: "true" on the Ingress or configure the controller to skip redirects for /.well-known/acme-challenge/*.
3. renewBefore fires at the wrong time with Let's Encrypt. Let's Encrypt issues 90d certs regardless of the duration you request. If you set renewBefore: 720h expecting a 90d cert, fine — but if the CA ever shortens validity (Apple pushed for 47d certs by 2027), renewBefore becomes a negative grace period. Use renewBeforePercentage: 33 instead.
4. v1.18 is EOL as of 2026-03-10. A final patch (1.18.6) landed 2026-02-24. Do not start new installs on 1.18.
5. Reinstalling with crds.keep=false destroys every cert. helm uninstall deletes the CRDs which cascade-deletes every Certificate and Issuer. Always keep CRDs across uninstalls.
6. Webhook down = no CRD writes accepted. Set replicaCount: 3, a PDB, and spread across zones. A down webhook during a scale event has caused multi-day cert-expiry incidents at large orgs.
7. --dns01-recursive-nameservers-only is load-bearing on GKE/EKS. Without it, cert-manager queries kube-dns which caches the "no TXT record" response, so the challenge fails even after the record lands. Set it.
8. Two Certificate resources targeting the same secretName race each other forever, re-issuing back-to-back and burning through Let's Encrypt rate limits. One Secret = one Certificate.
9. Cert-manager does not rotate the private key when rotationPolicy: Never — this is the default on clusters that haven't upgraded past v1.17 or have it explicitly set. Always is the right answer for 99% of workloads.
10. cmctl is the official CLI (replaced kubectl cert-manager plugin in v1.11). Install from the cert-manager/cmctl GitHub releases. cmctl status certificate <name>, cmctl renew <name>, cmctl approve/deny for manual CertificateRequest approval.
11. External issuers do not share the built-in approver. If your CertificateRequest is stuck in Pending with "Not Approved" even though the issuer exists, install an approver like approver-policy or approve manually with cmctl approve.
12. isCA: true Certificates still need an Issuer that allows CA issuance. Most ACME CAs (including Let's Encrypt) refuse to issue sub-CAs. Use a local CA issuer with SelfSigned or Vault PKI for intermediate CAs.
13. Helm v3 does not update CRDs by default. Upgrading the chart does not upgrade CRDs unless crds.enabled=true is set and the chart is a real helm OCI install — not a rendered-manifest GitOps install. With Argo CD / Flux, ensure CRDs are applied in a pre-sync wave.
14. GKE private clusters need a firewall rule for the webhook (control plane → worker port 10250 or the port the webhook listens on). Without it the webhook is unreachable and no cert-manager CRD writes succeed.
15. Clock skew > 5 minutes breaks ACME authorization. ACME signatures are time-bound. If the cert-manager Pod's clock is off, challenges fail with JWS verification error. Run NTP on all nodes.
16. dnsNames is case-sensitive in SAN but not in DNS. Certificates with Example.com and example.com are technically two different certs. Normalize to lowercase in your manifests.
17. subject.organizations and friends are ignored by most browsers + modern CAs since the 2021 EV-gutting changes. Setting them on a Let's Encrypt cert is harmless but pointless.
18. Secret reloading is not automatic in consumers. cert-manager writes the new Secret, but an app that loaded the cert at startup does not pick it up until restarted. Use Stakater Reloader (reloader.stakater.com/match: "true" on the Secret) or the configmap/secret reload story in your ingress / mesh of choice.
19. CertificateRequest revision history defaults to 1. On debug runs, bump to 5 via cert-manager.io/revision-history-limit: "5" so you can still see the previous failures after a retry.
20. --enable-certificate-owner-ref=true makes Certificates delete their Secret on deletion. Off by default for safety. Turn it on only if you actually want cascade deletion (rare — most teams want the Secret to survive).
