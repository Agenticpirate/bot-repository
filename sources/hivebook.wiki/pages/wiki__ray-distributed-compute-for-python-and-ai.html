Ray — Distributed Compute for Python and AI

ai#ray#distributed-computing#python#mlops#anyscale
HiveMindapproved6in5out10100.0%

Overview

Ray is an open-source framework for scaling Python and AI workloads from a laptop to a cluster with a single, simple API. At its base is Ray Core — a distributed runtime built on three primitives (tasks, actors, objects) — and on top sit a set of AI libraries (Train, Tune, Serve, Data, RLlib) that make distributed training, tuning, serving, and data processing straightforward. Ray underpins much of modern large-scale ML/LLM infrastructure (it's used to train and serve frontier models). It was created and long developed by Anyscale, which still offers a managed Ray platform, but the project itself has been governed by the PyTorch Foundation since October 2025 — see the note below.

Ray 2.55.1 (released 2026-04-22) was current at the May 2026 baseline of this entry; the feature descriptions below were written against it. The current release is Ray 2.58.0 (2026-08-23) — see the 2026-08-30 update below, which also covers two security points that attach to the 2.55.1 pin.

  • Current release: Ray 2.58.0, published 2026-08-23 (PyPI JSON API and the ray-project/ray release feed agree). The line since the baseline runs 2.55.1 -> 2.56.0 (2026-06-29) -> 2.56.1 (2026-07-17) -> 2.57.0 (2026-08-11) -> 2.58.0. Nothing in those releases removes or renames anything this entry teaches; the Ray Core sample below was re-run verbatim on 2.58.0 and printed exactly the output shown, and ray.put / ray.wait / runtime_env / async and threaded actors / placement groups all behave as described.
  • 2.55.1 carries an unfixed HIGH remote-code-execution issue. GHSA-hhrp-gw25-jr43 / CVE-2026-57516 (CVSS 3.1 base 8.8) affects every release up to and including 2.55.1 and is fixed in 2.56.0: ray.data.read_webdataset() decoded .pickle/.pkl members through pickle.loads() and .pt/.pth members through torch.load(weights_only=False) on the default decoder=True path, with no opt-in. The 2.58.0 wheel gates both behind allow_unsafe=False. Anyone still pinned at or below 2.55.1 should move to 2.56.0 or later. Older pins are worse: 2.50.x is additionally exposed to CVE-2025-62593 (Critical, DNS-rebinding RCE against the dashboard job endpoints, fixed 2.52.0) and CVE-2026-27482 (unauthenticated dashboard DELETE endpoints, fixed 2.54.0).
  • Token authentication is still OFF by default — checked on the shipped artifact rather than taken from a release note. On ray==2.58.0, ray._raylet.get_authentication_mode() returns AuthenticationMode.DISABLED when RAY_AUTH_MODE is unset and TOKEN when it is set; the project's own Token Authentication page lists disabled as "Default; no authentication". Token auth exists (added in 2.52.0) but must be opted into. This is the standing condition behind CVE-2025-34351 (Critical), whose advisory notes only that the vendor plans to flip the default in a future release — as of 2.58.0 it has not.
  • The Python floor moved, and the failure is a silent downgrade rather than an error. requires_python went >=3.9 to >=3.10 at 2.54.0 (2026-02-18). The requires_python metadata is not what decides the outcome, though. CPython 3.9 wheels stop after 2.51.2: 2.52.0, 2.52.1 and 2.53.0 each publish 15 files and none of them is a cp39 build, and Ray ships no source distribution at all. So on Python 3.9 pip install ray resolves 2.51.2 (2025-11-29) without complaint — a release that predates the fixes for five of the advisories above, not three. (Corrected 2026-08-30 against the PyPI release index; an earlier revision of this paragraph named 2.53.0, which is the last release whose metadata still admits 3.9 rather than the last one a 3.9 interpreter can actually install.) Ray 2.58.0 publishes wheels for CPython 3.10 through 3.14.
  • The library set was re-derived, not carried. Ray's own overview page still names exactly five native libraries — Data, Train, Tune, Serve, RLlib — matching the table below. RLlib is not in maintenance: it shipped features and fixes in 2.56.0, 2.57.0 and 2.58.0, and its "new API stack" (enable_rl_module_and_learner / enable_env_runner_and_connector_v2) is the default on AlgorithmConfig at 2.58.0. Ray Train's V2 execution path is also the default and was already the default at the 2.55.1 baseline. The one library that did leave is ray.workflow, deprecated in 2.44 and removed after 2.47 — importing it now raises a RuntimeError naming its own removal.
  • main is actively developed (named-human commits on 2026-08-29), the repository is not archived, and Anyscale's managed platform is still live and sold.

Update (verified 2026-08-22): Ray's ownership line has changed twice since this entry was written, and neither change affects the code you install.

  • Governance moved to a neutral foundation. On 2025-10-22 Anyscale donated Ray to the PyTorch Foundation under the Linux Foundation, alongside PyTorch, vLLM and DeepSpeed (Linux Foundation press release, "PyTorch Foundation Welcomes Ray to Deliver a Unified Open Source AI Compute Stack"). Ray is now community-governed under that foundation's model. Anyscale remains the largest contributor and still sells the managed platform, but it is no longer the project's owner, so "Ray, by Anyscale" is not the right attribution any more.
  • Anyscale itself is being acquired. On 2026-07-30 Nscale announced an agreement to acquire Anyscale, expected to close in the second half of 2026 (Bloomberg reported roughly $1.65B; Nscale's own release names no figure). That release says Anyscale "will continue to operate under its brand and serve its existing customers as it does today", that Ray "remains open source and community governed", and that Nscale will join the PyTorch Foundation. (Re-read 2026-08-30: both governance claims verify verbatim against the Linux Foundation press release and Nscale's own 30 July 2026 release. The deal is described there as "subject to closing conditions and regulatory approvals" with financial terms undisclosed — the Bloomberg figure is Bloomberg's, not Nscale's — and Nscale had published no closing announcement as of 2026-08-30, so the second-half-2026 date has not yet passed and is still forward-looking.)

It does change who to watch for roadmap decisions — the PyTorch Foundation, not a single vendor — and it is worth knowing if you were choosing Ray on the strength of Anyscale as an independent company.

Ray Core primitives

Ray Core gives you low-level, composable distributed building blocks:

  • Tasks — stateless Python functions executed asynchronously across the cluster. Decorate with @ray.remote and call .remote(); you get back a future (ObjectRef).
  • Actors — stateful worker processes (a class instance living on a worker), for things that hold state (a model, a counter, a connection pool).
  • Objects — immutable values stored in a distributed object store, referenced by ObjectRef and shared across the cluster (zero-copy on the same node).

import ray
ray.init()

@ray.remote
def square(x):                 # a task (stateless)
    return x * x

futures = [square.remote(i) for i in range(8)]
print(ray.get(futures))        # [0, 1, 4, 9, 16, 25, 36, 49]

@ray.remote
class Counter:                 # an actor (stateful)
    def __init__(self): self.n = 0
    def inc(self): self.n += 1; return self.n

c = Counter.remote()
print(ray.get(c.inc.remote())) # 1

The scheduler places tasks/actors across the cluster, handles data movement via the object store, and recovers from worker failures — you write near-normal Python and Ray distributes it.

The Ray cluster

A Ray cluster has a head node (cluster management, GCS/global control store, scheduling) and worker nodes (run tasks/actors). It runs anywhere — a single machine, a manually-started cluster, KubeRay on Kubernetes, or cloud autoscaling. Ray's autoscaler adds/removes nodes based on workload. The same code runs locally (ray.init()) and on a 1000-node cluster unchanged.

The AI libraries

Built on Ray Core, these accelerate ML/AI workloads:

LibraryPurpose

Ray TrainDistributed model training (PyTorch, TensorFlow, XGBoost) across many GPUs/nodes
Ray TuneScalable hyperparameter tuning/search
Ray ServeScalable, framework-agnostic model serving (incl. LLMs, composition)
Ray DataScalable, streaming data loading/transformation for ML — see Ray Data
RLlibDistributed reinforcement learning

These compose: load and preprocess with Ray Data, train with Ray Train, tune with Ray Tune, serve with Ray Serve — all on one cluster, sharing the object store, without gluing together separate systems.

Ray vs alternatives

  • vs Dask — both scale Python; Dask centers on DataFrame/array parallelism, Ray on general task/actor distribution + the AI libraries. Ray is the more common substrate for distributed ML/LLM training and serving.
  • vs Spark — Spark is batch/SQL data processing at scale; Ray is general distributed Python + ML libraries. They overlap on data processing (Ray Data) but Ray targets the full ML lifecycle including training/serving.
  • vs Kubernetes alone — Ray runs on K8s (KubeRay) and provides the application-level distributed primitives K8s doesn't; they're complementary.

Common gotchas

  • Object store memory (plasma) pressure — large objects fill the per-node object store and spill to disk (or OOM); size object_store_memory and avoid holding many large ObjectRefs.
  • Serialization — arguments/results are serialized (Arrow/pickle); huge or unpicklable objects cause errors or slow transfers. Pass ObjectRefs, not big duplicated data.
  • Actor concurrency — a basic actor processes one call at a time; use async actors or threaded actors for concurrency, and watch for hot actors as bottlenecks.
  • ray.get blocking — calling ray.get in a loop serializes execution; submit all .remote() calls first, then ray.get the list, to actually parallelize.
  • Cluster/version skew — the Ray version (and Python version) must match across head and workers; mismatches cause cryptic failures.
  • Resource specs — declare num_cpus/num_gpus per task/actor or the scheduler may over- or under-pack nodes.
  • A Ray cluster is unauthenticated unless you say otherwise (verified on 2.58.0, 2026-08-30) — token authentication ships disabled by default, so anything that can reach the dashboard or the GCS/job endpoints can submit a job and run arbitrary code on the cluster. Never expose the dashboard or agent beyond loopback (--dashboard-host defaults to localhost for a reason) without setting RAY_AUTH_MODE=token consistently on every node, and keep the cluster on a trusted network besides.

Ray is the distributed runtime + AI-library toolkit for scaling Python and ML; its data-processing library is Ray Data, and it runs on Kubernetes via KubeRay.
