MCP-Atlas — Scale's Tool-Use Benchmark Across 36 Real MCP Servers and 220 Tools

Overview

MCP-Atlas is Scale AI's open-source benchmark for measuring how well large language models drive real production Model Context Protocol servers — not toy simulations. The dataset is 1,000 single-turn natural-language tasks (500 public + 500 private) authored and verified by human experts, spanning 36 real MCP servers and 220 tools. Each task exposes a controlled ENABLED_TOOLS subset of 6–37 tools (only 2–8 are relevant; the rest are plausible distractors), and the model's answer is scored against atomic factual claims grounded in tool outputs (mean 4.7 claims per task, range 1–23).

Scale first announced the benchmark 2025-09-19, posted the paper as arXiv 2602.00933 v1 on 2026-01-31, open-sourced the harness, and shipped a methodology overhaul in April 2026 (judge upgrade, retry handling, 100-tool-call budget replacing the older 20-turn limit). The paper is still at v3 (2026-05-19) — the arXiv abstract page lists v1/v2/v3 and no v4 as of 2026-08-25 — and the public 500-task subset (500 rows, five string columns) lives on Hugging Face under CC-BY-4.0. Among the 20 frontier models evaluated in the v3 paper, pass rates top out at 82.2% at the 0.75 claim-coverage threshold (Muse Spark) — a meaningful but unsaturated ceiling.

Update (verified 2026-08-25): the live Scale Labs leaderboard is no longer the paper's 20-model set. It now carries 30 entries and tops out at 88.1% — Muse Spark 1.1 (Meta), on the board since 2026-07-09 — with claude-opus-5 (xhigh) second at 85.8% (2026-08-03). Quote 82.2% as "the v3 paper's top result", not as the current leaderboard maximum.

The benchmark is widely cited as an agent-tool-use evaluation alongside SWE-Bench on 2026-vintage frontier-model launch pages (see also Hivebook's LLM benchmarks index).

The April 2026 methodology change is the most operationally important version line: a model evaluated under the old 20-turn limit will look weaker than one evaluated under the 100-tool-call budget, so any score lifted from a paper or blog post written before that date should be re-checked against the current leaderboard before quoting.

Dataset Composition

The full benchmark is 1,000 tasks split into a 500-task public release (on Hugging Face) and a 500-task private holdout (only Scale runs scoring on this — the leaderboard pass rates blend both subsets, while local runs touch only the public half). Each row of the ScaleAI/MCP-Atlas parquet has five fields:

FieldTypePurpose

TASKstr24-character unique task ID
ENABLED_TOOLSstrControlled subset of 6–37 tools (only 2–8 relevant per task; the rest are plausible distractors); harness enforces — extra tools are unreachable
PROMPTstrSingle-turn natural-language request requiring multiple tool calls
GTFA_CLAIMSstrSet of independently verifiable claims forming a ground-truth final answer, each grounded in tool outputs
TRAJECTORYstrReference sequence of tool calls (names, methods, dependencies, arguments, outputs) that resolves the task

On the "220 tools" count (verified 2026-08-25): the paper abstract and the Hugging Face dataset card both say "36 real MCP servers and 220 tools", and Appendix B is explicit that this is "36 production MCP servers exposing 220 distinct tools across all tasks" — i.e. tools actually exercised by the 1,000 tasks. The repo's own enumeration counts differently: services/agent-environment/src/agent_environment/mcp_server_template.json plus the inventory gist the README links describe 36 servers and 307 total tools available in the sandbox. Both are correct at different scopes; the 220 in this entry's title is the paper's task-coverage figure. The 36-server list is verbatim-stable — mcp_server_template.json at main on 2026-08-25 still enumerates exactly the 36 servers below, no additions or removals.

The 36 production MCP servers fall into five environment buckets. The most-used servers by task count are oxylabs (155 tasks), filesystem (133), exa (108), wikipedia (99) and mongodb (98); the tail is context7 (4 tasks). 98.6% of tasks require tools from two or more servers (mean 2.55 servers — 51.7% need exactly two, 38.2% three, 8.7% four or more; paper §3.2) and roughly one-third include conditional branching — single-server tasks were deliberately under-weighted because they fail to discriminate frontier from mid-tier models.

Scoring Methodology

MCP-Atlas uses claim-coverage scoring, not exact-match or pairwise preference. For each task:

1. The model receives the PROMPT and the ENABLED_TOOLS subset over the MCP transport.
2. It calls tools (one or many, in any order) until it issues a final answer or hits the 100-tool-call budget.
3. A judge model reads the final answer alongside the task's GTFA_CLAIMS list and scores each claim. Corrected 2026-08-25: the primary judge is Gemini 3.1 Pro Preview, not Gemini 2.5 Pro. Paper §4.4 names it as primary, and the shipped harness agrees — EVAL_LLM_MODEL defaults to gemini/gemini-3.1-pro-preview in both run_eval.py and services/scoring/score_claims.py. The Scale leaderboard page's "Judging Protocol" section still reads "Gemini-2.5-Pro, temperature 0.0" and is stale on this point (the same page also still carries a pre-April-2026 "top performer: Claude Opus 4.5 with 62.3%" line). The per-claim scale is:

ScoreMeaning

1.0Fully fulfilled — the fact is present and correct
0.5Partially fulfilled — the fact is partially addressed
0Not fulfilled — absent or incorrect

4. The task's coverage rate = (sum of per-claim scores) ÷ (total claim count).
5. A task passes when coverage ≥ 0.75 (the headline threshold). Corrected 2026-08-25: the additional thresholds are Pass@0.50 and Pass@0.90 — paper Table 8 — not 0.5 and 1.0, and they are reported in the paper, not on the leaderboard. The public leaderboard shows only the 0.75 pass rate, in two columns: "Pass Rate % (All 1000)" and "Pass Rate % (Public 500)". The shipped scorer writes coverage_stats_*.json at the 0.50 and 0.75 thresholds.
6. The benchmark pass rate is the share of the 1,000 tasks that pass.

Corrected 2026-08-25 — there is no 100-task human-rating study and no "78% agreement" figure in the paper. What the paper actually reports (§4.4, Appendix F Table 7) is a cross-judge sensitivity study: all 1,000 tasks were re-scored for every model by three judges — Gemini 3.1 Pro Preview (primary, mean pass rate 65.4%), GPT-5.4 (strictest, 62.3%) and Claude Opus 4.6 (63.9%). Per-model score ranges span 2.1–4.6 percentage points; rankings are broadly preserved, and the largest movement is Claude Opus 4.7, which ranks 2nd under the primary judge, 3rd under GPT-5.4 and 5th under Opus 4.6. The paper's limitations section is blunter still: absolute pass rates "should be read modulo a 2–5 point cross-judge band", and it recommends always reporting and pinning the judge version. So the judge's identity is a real moving variable in score reproducibility — just not the one earlier versions of this entry described.

The harness sends completions to whichever model is under test over any OpenAI Chat-Completions-compatible endpoint, configured as LLM_BASE_URL — in practice a LiteLLM proxy, which is how one harness covers OpenAI, Anthropic, Gemini, Fireworks-hosted open weights and self-hosted vLLM/TGI without a per-provider plug-in. Since harness v2.0.0 the agent loop is TypeScript with per-provider "strategy" files, and the bundled strategy is the LiteLLM one. Paper Table 9 records the exact route per model — e.g. GLM-5.1 was run as fireworks_ai/glm-5p1.

Diagnostic Taxonomy

A pass/fail score alone would not be enough to make MCP-Atlas useful as an engineering benchmark — Scale publishes an 11-category diagnostic taxonomy organised into two families that pinpoints why a model loses points (paper §3.3, Tables 3–4):

FamilyFailure modes

Tool-call (4 modes)Malformed parameters; wrong tool selection; no tool use; failed error recovery
Cognitive (7 modes)Task misunderstanding; faulty synthesis; response misparsing; early termination; hallucinated facts; logical errors; constraint violations

Across the roughly 6,900 diagnosed failures from the 20 evaluated frontier models, the aggregate split is 63.3% cognitive and 36.7% tool-call related (paper §4.2). Tool-call failures still dominate the tail of the leaderboard — o3 Pro 57.6% tool-related (with 40.1% of its failed trajectories containing no tool invocation at all), GPT-5.1 50.4%, Claude Haiku 4.5 46.7% — but among stronger models the bottleneck shifts from issuing tool calls to terminating and synthesising the evidence chain.

Per-model patterns called out in the paper:

  • Early-termination signature for one high-performing subgroup: Gemini 3.1 Pro Preview 42.8%, GPT-5.4 41.4%, Claude Opus 4.6 36.3% of their diagnosed failures are early termination.
  • Newer frontier models almost eliminate early termination (GPT-5.5 3.6%; Claude Opus 4.7 3.8%) but trade it for higher faulty-synthesis rates (GPT-5.5 19.8%; Claude Opus 4.7 25.0%) — an emerging frontier regime in which agents persist through the workflow but still miscombine, misinterpret, or misreport the evidence they collect.
  • Tool-use policy mismatch on reasoning-trained checkpoints: o3 Pro produces no tool calls on 40.1% of its failed tasks despite topping mathematical and coding benchmarks — its default tool-use policy is poorly calibrated for MCP with unknown tools and realistic distractors.

This split is the single most actionable number in the paper: improving the MCP transport, retry handling, or tool documentation can only close the tool-call ~36.7% — the cognitive ~63.3% is squarely on the base model. Builders shipping MCP-server-backed agents on top of Anthropic's tool-use API or the A2A protocol should expect a similar split. The next gains on MCP-Atlas, per the paper's discussion, likely require both claim-aware stopping criteria and trajectory-grounded verification of the final answer against the collected tool evidence.

Running the Benchmark Locally

The MIT-licensed harness lives at github.com/scaleapi/mcp-atlas — active, not archived: commits on main run through 2026-08-03, and LICENSE at main is verbatim MIT ("Copyright (c) 2026 Scale"). The "Python 67.5% / Shell 31%" language split quoted by earlier versions of this entry predates the v2.0.0 rewrite; the agent harness is now TypeScript (Express + @modelcontextprotocol/sdk), while scoring and diagnostics remain Python. Corrected 2026-08-25: uv is not a requirement. The README's stated prerequisites are Docker, jq and Python 3.10+; the "pyproject.toml-only install path" claimed by earlier versions of this entry does not exist — Python deps come from make install-python. Of the 36 servers, 20 need no setup, 11 require API keys, and 5 require keys plus data setup; the 20 keyless ones are enabled by default and key-gated ones switch on when their keys are present.

Run loop, corrected against the shipped repo on 2026-08-25. docker pull ghcr.io/scaleapi/mcp-atlas:1.2.7 then make run-docker (sandbox on :1984; wait for Uvicorn running on http://0.0.0.0:1984), make install-harness && make run-harness (TypeScript agent loop on :3001, exposing /v2/mcp_eval/run_agent), then make install-python && python run_eval.py --model "openai/gpt-4o" --output outputs.csv — which pulls the 500-task public split from Hugging Face by default and resumes safely if interrupted. Scoring is a separate step, python services/scoring/score_claims.py, writing scored_<model>.csv, coverage_stats_<model>_*.json and a coverage histogram — CSV and JSON, not JSON Lines. Failure diagnosis is a third step, python services/diagnostics/single_model_diagnostic.py. The make run-mcp-completion and uv run python mcp_completion_script.py commands named by earlier versions of this entry belonged to the Python harness at services/mcp_eval/mcp_completion/, which v2.0.0 removed. Useful run_eval.py defaults: --max-tool-calls 100, --max-turns 256, --concurrency 5, --timeout 1800. The harness is reproducible across machines thanks to the Docker-pinned MCP server images, but the LLM-as-judge step still depends on the judge model's API stability.

Common Gotchas

  • Pre-April 2026 scores are not directly comparable. The April 2026 methodology update replaced a 20-turn limit with a 100-tool-call budget, upgraded the judge model, and added retry-on-transient-error handling. Tasks that previously timed out at turn 20 now succeed, so headline numbers from the v1 paper or 2025-Q4 launch posts shift upward by several points under the new harness. Always check whether a quoted score predates 2026-04 before benchmarking against it.

  • The judge is itself a variable. Pass rates use Gemini 3.1 Pro Preview as the primary LLM-as-judge (harness default gemini/gemini-3.1-pro-preview) — not Gemini 2.5 Pro, and there is no published 78% human-agreement figure; both claims are corrected as of 2026-08-25. The paper's three-judge study puts per-model spread at 2.1–4.6 percentage points, and its limitations section widens that to a 2–5 point cross-judge band. Rankings are broadly preserved, but the crowded 75–82% cluster reshuffles: Claude Opus 4.7 moves between 2nd and 5th depending on the judge. Pin the judge model and record its version alongside the score.

  • Public 500 ≠ Leaderboard 1000. Local runs against the Hugging Face dataset cover only the public half. The official leaderboard pass rates blend public + private subsets, so a model's local score and its leaderboard score will not match exactly. Corrected 2026-08-25: the gap is much larger than the "1–2 points" claimed by earlier versions of this entry. Paper §4.5 measures split gaps of −0.8 to +9.6 pp, with most models scoring higher on the public half — OpenAI models average +8.4 pp (range +7.0 to +9.6), Google +5.2, Anthropic +4.8, open-weights +3.8, and Kimi K2.5 is the only model that does better on the private half. The leaderboard prints both columns so the discrepancy is visible: gpt-5.4 (xhigh) is 70.6% on all 1,000 and 75.4% on the public 500. Scale reads these gaps as split-sensitivity and exposure-monitoring signals rather than contamination evidence, but either way: report a local number as "MCP-Atlas public-500", never as "MCP-Atlas".

  • Cognitive failures dominate aggregate diagnostics. Across all 20 frontier models, ~63.3% of diagnosed failures are cognitive (task misunderstanding, faulty synthesis, misparsing, early termination, hallucinated facts, logical errors, constraint violations); the remaining ~36.7% are tool-call related (malformed parameters, wrong tool selection, no tool use, failed error recovery). Improving the MCP transport or adding retries closes the tool-call half but cannot fix the cognitive half. Note that the cognitive-dominates split is a frontier-model phenomenon — tool-call failures DO dominate at the bottom of the leaderboard (o3 Pro 57.6% tool-related, GPT-5.1 50.4%, Claude Haiku 4.5 46.7%). If your in-house score is plateauing, look at the per-category breakdown before adding more transport machinery.

  • Single-server tasks under-discriminate. The benchmark is dominated by cross-server composition, so a model that aces tool selection on a single server but stumbles when chaining two or three may still rank well on naive multi-tool benchmarks while failing MCP-Atlas. Conversely, MCP-Atlas overweights orchestration relative to depth-in-one-tool — pair it with depth-focused benchmarks (e.g. SWE-Bench for coding) for a complete picture.

  • Tool exposure is enforced by the harness, not the prompt. The ENABLED_TOOLS subset of 6–37 tools (only 2–8 relevant per task) is set at the MCP-transport layer — adding tools to the system prompt won't help and may actually hurt by inflating the context with tools the model cannot call. Trust the harness and let the model discover capabilities via the standard MCP tools/list round-trip.

  • Fast tiers can outperform pro tiers. As read on 2026-08-25, gemini-3.5-flash (high reasoning, 83.6%) is third on the board and still ahead of claude-opus-4-7 (max, 79.1%) and gpt-5.5 (xhigh, 75.3%). Model speed is not inversely correlated with MCP-Atlas competency — if your agent loop's latency budget is tight, do not assume the cheaper/faster tier costs you accuracy on tool use. Re-benchmark fast tiers explicitly.
