Voyage AI — Embeddings & Rerankers for RAG

Overview

Voyage AI is a specialist provider of text + multimodal embedding models and cross-encoder rerankers built for retrieval-augmented generation. Acquired by MongoDB in February 2025, Voyage has stayed independent as a research lab — its current flagship voyage-4-large (March 2026) uses a Mixture-of-Experts backbone and consistently leads public RAG benchmarks above OpenAI text-embedding-3-large and Cohere embed-v3.

Two product lines: (1) embeddings at POST /v1/embeddings, mapping text/code/images into dense vectors; (2) rerankers at POST /v1/rerank, scoring (query, document) pairs jointly with a cross-encoder. Both share a generous 200 M-token free tier per model, OpenAI-compatible request shapes, and SDKs in Python (voyageai) and TypeScript (voyageai). For RAG pipelines, the canonical pattern is embed-and-store with voyage-4/voyage-context-3, then rerank top-k with rerank-2.5 before sending to the LLM.

Voyage-4 family introduced a shared embedding space across all dimensions and output_dtype quantizations (Matryoshka representation learning): the same 2048-dim float embedding can be truncated to 256/512/1024 and quantized to int8/uint8/binary without re-embedding. This is unique among major providers — OpenAI requires re-embedding for different dimensions, and Cohere mixes only int8 quantization, not binary.

voyage-4-large (March 2026) added Mixture-of-Experts routing: at inference time, each input is dispatched to a subset of expert sub-networks per token; activated parameters are smaller than the full model, so throughput stays close to voyage-4 despite higher quality scores on long-context retrieval (MTEB, BEIR, FollowIR).

Free tier: 200 M text tokens + 150 B pixels. Endpoint: POST /v1/multimodalembeddings. Interleaved input is the differentiator — unlike CLIP-style models that encode text and image through separate towers, Voyage runs both through a single backbone, so you can pass [{"type":"text","text":"..."},{"type":"image_base64","image_base64":"..."}] as one input and get a single vector. v3.5 added video (treated as a temporal stack of frames, max 20 MB) and three additional output dims (256/512/2048) on top of v3's 1024-only.

Embedding Request — Anatomy

import voyageai
vo = voyageai.Client()

result = vo.embed(
    texts=["What is the capital of France?", "Paris is the capital of France."],
    model="voyage-4-large",
    input_type="query",        # or "document" — see gotcha below
    output_dimension=1024,     # 256, 512, 1024, 2048 (Matryoshka truncation, no quality loss)
    output_dtype="float",      # "float", "int8", "uint8", "binary", "ubinary"
    truncation=True,            # silently truncate >32k inputs (default True)
)

print(len(result.embeddings))       # 2
print(len(result.embeddings[0]))    # 1024 (because output_dimension=1024)
print(result.total_tokens)          # ~14

REST equivalent:

POST /v1/embeddings
{

  "model": "voyage-4-large",
  "input_type": "query",
  "output_dimension": 1024,
  "output_dtype": "float",
  "truncation": true
}

input_type — the most-missed knob

Set to "query" for the user's question and "document" for items in the corpus. Voyage prepends a different instruction prefix internally for each, which lifts retrieval nDCG@10 by 1–4 points on MTEB. Default is None (no prefix) — symmetric tasks like clustering should leave it unset; retrieval should always set it. Mixing query-as-document is the #1 cause of "my recall feels worse than OpenAI" reports.

Contextualized Chunk Embeddings (voyage-context-3)

Standard embedding treats each chunk in isolation, losing document-level context (cross-reference, antecedents, section heading). voyage-context-3 embeds each chunk conditioned on its sibling chunks — the encoder sees the full document at inference but produces one vector per chunk.

result = vo.contextualized_embed(
    inputs=[[
        "Section 1: A boy walks his dog.",
        "He throws the ball.",
        "The dog catches it mid-air."
    ]],
    model="voyage-context-3",
    input_type="document",
)
# result.results[0].embeddings -> list of 3 vectors, each contextualised

REST: POST /v1/contextualizedembeddings. Inputs are list-of-lists (each inner list is one document's chunks). Limits: max 1000 documents per request, 16k chunks total, 120k tokens total. Default dim 1024 (also 256, 512, 2048).

Why it matters: Voyage's own quickstart shows a "golden chunk" containing the answer ranking 8th with standard embeddings and 1st with contextualised — the surrounding chunks supply pronoun resolution and topic anchoring that the embedding alone cannot infer.

Rerank Request — Anatomy

result = vo.rerank(
    query="What is the capital of France?",
    documents=[
        "Paris is the capital and largest city of France.",
        "London is the capital of the United Kingdom.",
        "Berlin is the capital of Germany.",
    ],
    model="rerank-2.5",
    top_k=2,
    truncation=True,
)
for r in result.results:
    print(r.index, r.relevance_score, r.document[:60])
# 0 0.93 Paris is the capital and largest city of France.
# 2 0.41 Berlin is the capital of Germany.

REST shape (POST /v1/rerank):

{
  "query": "What is the capital of France?",
  "documents": ["Paris is the capital...", "London is..."],
  "model": "rerank-2.5",
  "top_k": 2,
  "return_documents": true,
  "truncation": true
}

Token budget calculation

Voyage charges and limits rerank requests as: (query_tokens × document_count) + sum(document_tokens). A query of 200 tokens reranking 100 documents at ~500 tokens each costs (200×100) + (100×500) = 70 000 tokens per call. Most expensive misuse: sending the full chat-history-prefix as the query string — it's multiplied by document count. Trim the query to the actual retrieval intent.

Multimodal Embeddings

import base64
with open("chart.png", "rb") as f:
    img_b64 = base64.b64encode(f.read()).decode()

result = vo.multimodal_embed(
    inputs=[
        {"content": [{"type": "text", "text": "Q4 revenue chart"},
                     {"type": "image_base64", "image_base64": img_b64}]}
    ],
    model="voyage-multimodal-3.5",
    input_type="document",
)

REST: POST /v1/multimodalembeddings. Image limits: max 16 M pixels, 20 MB; video: 20 MB total. Image cost in tokens: pixels / 560 (approximate; price is per billion pixels). Interleaved text + image in a single input produces one vector for the combined input — useful for figure-caption retrieval over scientific PDFs.

Batch API (33 % discount)

Submit a JSONL file of requests to POST /v1/batches; results return within 24 h at a 33 % discount vs synchronous endpoints. Same model lineup, same request shapes. File storage at $0.05/GB-month. Useful for nightly index rebuilds over millions of documents — keeps the synchronous endpoint headroom free for query-time work.

Common Gotchas

1. Forgetting input_type — symmetric None defaults are correct for clustering, wrong for retrieval. Document-side index built without input_type="document" then queried with input_type="query" causes the query prefix to never see its matching document prefix; recall drops 5–15 %.
2. Reranker token math is multiplicative — (query_tokens × N_docs) + Σ document_tokens, not query_tokens + Σ document_tokens. A 500-token system-prompt-as-query reranking 200 documents at 1000 tokens = (500×200) + (200×1000) = 300 000 tokens per call. Trim the query.
3. Matryoshka truncation needs L2-normalisation — when you truncate a 2048-d float vector to 256-d, the result is not unit-norm. Renormalise on the client (v / np.linalg.norm(v)) before cosine-similarity lookups, or use the SDK helper. Skipping this corrupts cosine scores subtly — distance still works for ranking but absolute scores are meaningless.
4. binary output is one bit per dimension, packed into bytes — a 2048-d binary embedding is 256 bytes, not 2048. Use Hamming distance (XOR popcount) for similarity, not cosine. Many vector DBs lack first-class binary support; pgvector 0.8+ has bit() and hamming_distance(), Qdrant has binary quantization mode.
5. voyage-multimodal-3.5 videos are framed at one frame per second by default — a 60-second clip becomes 60 frames internally, multiplying pixel cost. Pre-frame the video to the actual frames you need before sending, especially for high-resolution sources.
6. voyage-context-3 is one of the most expensive models at $0.18/M tokens — only use it when chunk-level context matters (legal contracts, long technical docs). For chat-message corpora or short snippets, voyage-4 at $0.06 gives similar recall at one-third the price.
7. The TypeScript SDK lagged behind Python until 2026-03 — voyageai@0.2.0 (npm, 2026-03-02) was the first TS release with voyage-4 model support. Earlier versions still call the API correctly if you pass model: "voyage-4-large" as a literal string; only the typed enum lagged.
8. Free-tier quotas are per-model, not per-account — burning 200 M tokens on voyage-4 does not reduce the 200 M free pool for voyage-4-large. Useful for experimenting across the model lineup without paying.
9. Batch API is 24-hour SLA, not always-best-effort — for production index rebuilds at night this is fine; not appropriate for query-time work. Synchronous endpoints have a 30-minute completion window when input is at maximum payload.
10. truncation=true (default) silently drops content past 32k tokens — if your chunker emits longer chunks, you lose tail context with no warning. Set truncation=false to receive a 400 error and split the chunk client-side.
11. voyage-code-3 is not just voyage-4 for code — it was trained with code-specific positive/negative pairs (GitHub issue threads, doc-comment-code pairs, programming-Q&A); generic models lose 5–8 nDCG points on CodeSearchNet. Pay the $0.18/M premium for codebase retrieval; use voyage-4 for everything else.
12. No on-prem / self-hosted option — Voyage is API-only; the closest thing is the AWS/Azure marketplace deployment which still calls Voyage-managed inference. For air-gapped requirements use open-weight alternatives (BGE-large, jina-embeddings-v3, Nomic Embed) and accept the quality gap.
