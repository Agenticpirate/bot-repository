Kubernetes ConfigMap and Secret Mounting: Volumes, envFrom, Projected Volumes, and Refresh Behavior

Overview

Kubernetes ConfigMaps and Secrets decouple configuration and credentials from container images. Both are namespaced, capped at 1 MiB by etcd, and can be consumed as environment variables, volume files, or projected volumes. They look similar, but differ in subtle ways that cause most production incidents: subPath mounts never auto-update, envFrom invalid keys are silently dropped, and Secrets are only base64-encoded, not encrypted, unless encryption-at-rest is configured on the API server.

Mounting as a Volume

Each key becomes a file under mountPath. Files are symlinks into an atomically-swapped ..data directory, so updates are atomic across all keys:

volumes:
- name: config
  configMap:
    name: app-config
    defaultMode: 0444
    items:
    - key: app.yaml
      path: app.yaml
containers:
- name: app
  volumeMounts:
  - name: config
    mountPath: /etc/app
    readOnly: true

Auto-update: The kubelet refreshes mounted ConfigMaps/Secrets when the object changes. Propagation is eventually consistent — typically under a minute with the default Watch strategy (configMapAndSecretChangeDetectionStrategy in KubeletConfiguration; alternatives are Cache and Get). Applications must re-read files or use a sidecar like Reloader to restart pods.

Environment Variables (env and envFrom)

Single key via valueFrom:

env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-creds
      key: password

All keys via envFrom:

envFrom:
- configMapRef:
    name: app-config
- secretRef:
    name: db-creds
    optional: true

Critical: environment variables are resolved once at container start. Updating the ConfigMap or Secret does not update running container env vars — the pod must be restarted. Keys that are not valid shell variable names (contain -, start with a digit, etc.) are silently skipped when using envFrom; only an event is emitted.

Projected Volumes

Projected volumes merge multiple sources into one mount — typically ConfigMap + Secret + downwardAPI + serviceAccountToken:

volumes:
- name: all-in-one
  projected:
    defaultMode: 0400
    sources:
    - configMap:
        name: app-config
    - secret:
        name: db-creds
    - downwardAPI:
        items:
        - path: pod-name
          fieldRef:
            fieldPath: metadata.name
    - serviceAccountToken:
        audience: vault
        expirationSeconds: 3600
        path: vault-token

Supported sources: configMap, secret, downwardAPI, serviceAccountToken, clusterTrustBundle (beta v1.33), podCertificate (beta v1.35). All sources must live in the same namespace as the pod. Note that projected Secrets use name: (not secretName:), unlike the top-level secret volume source.

Bound Service Account Tokens

serviceAccountToken projection replaces the legacy long-lived kubernetes.io/service-account-token Secrets. Tokens are short-lived JWTs bound to the pod lifecycle, audience-scoped, and auto-refreshed by the kubelet at ~80% of expirationSeconds (minimum 600s, maximum cluster-configured). Since Kubernetes v1.24 the token-controller no longer auto-creates the legacy Secrets for new ServiceAccounts.

Immutable ConfigMaps and Secrets

Set immutable: true to lock the data. Benefits:

  • Protects against accidental edits.
  • Kubelet stops watching — reduces kube-apiserver load at scale (thousands of pods × thousands of ConfigMaps).

Trade-off: the only way to change an immutable object is to delete and recreate it (with a new name — typically a hash suffix, the pattern Helm and Kustomize use via generateName hashing).

Common Gotchas

1. subPath breaks auto-updates. Using subPath to mount a single key (e.g., /etc/nginx/nginx.conf) makes the file a one-time copy — it is never refreshed when the ConfigMap/Secret changes. Same for projected serviceAccountToken with subPath: the token expires and the pod's API calls start failing. Use mountPath with items.path instead.
2. envFrom does not reload. Env vars are baked in at container start. Changing the ConfigMap has no effect on running pods — restart or use a reloader controller.
3. Invalid env keys silently skipped. envFrom drops any key that isn't a valid env var name (contains -, starts with a digit, etc.). A ConfigMapRef with db-host produces no error — the variable just isn't there. Rename keys or use explicit env with valueFrom.
4. Base64 is not encryption. kubectl get secret -o yaml shows base64 — anyone with RBAC read on Secrets reads the plaintext. Enable EncryptionConfiguration (AES-GCM, KMS v2 GA v1.29) to encrypt at rest in etcd.
5. 1 MiB hard cap. Large binary blobs (certs bundles, ML models, big JSON) can blow the limit. Split into multiple objects or mount from a PVC / init-container download.
6. Same namespace only. Pods cannot mount ConfigMaps or Secrets from another namespace. Replicate them (controllers like kubernetes-replicator) or use a cluster-wide secret manager.
7. Static pods cannot use them. Pods defined via kubelet's staticPodPath have no API-server access — embed config directly.
8. Immutable is one-way. Once immutable: true is set, you cannot un-set it. Delete and recreate.
9. JSON defaultMode must be decimal. YAML supports octal (0400); JSON does not. Use 256 in JSON for 0400, or stick to YAML manifests.
10. Dot-prefixed keys create hidden files. A key named .env mounts as a hidden file — handy for some tools, surprising for others when ls shows an empty directory.
11. Dropped keys on envFrom block diagnostics. If a pod is missing a key, check kubectl describe pod for the InvalidVariableNames event — the controller reports skipped keys there but does not fail the pod.
12. Secret deletion doesn't evict running pods. Deleting a mounted Secret doesn't stop current pods; volumes keep the last known content via the kubelet cache until the pod restarts, at which point it fails to start.
