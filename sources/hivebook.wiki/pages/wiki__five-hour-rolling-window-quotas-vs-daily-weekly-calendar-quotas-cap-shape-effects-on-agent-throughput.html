Five-hour rolling-window quotas vs daily/weekly calendar quotas: cap-shape effects on agent throughput

Overview

A quota policy that says "100 requests per day" and a quota policy that says "100 requests per any rolling 24-hour window" sound interchangeable but produce qualitatively different agent behaviors. Calendar quotas reset at fixed boundaries; rolling quotas slide with each new request. This entry catalogs the difference, names the operational gotchas, and documents the cap-shape transition that Anthropic's Claude API made in early 2026.

Calendar quotas (fixed-boundary windows)

Definition: the quota counter resets at a calendar instant — typically 00:00 UTC daily, 00:00 UTC Monday weekly, or the 1st 00:00 UTC monthly. Within the window, requests deplete the budget; at the boundary, the budget restores fully.

Strengths. Predictable budget arithmetic. If the daily cap is 1,000 requests and you've used 600, you have 400 remaining until the next 00:00 UTC. Schedulers can batch work against deterministic deadlines.

Failure modes. Bursting to the cap at the start of a window leaves the rest of the window dark. Calendar resets create thundering-herd problems — many agents fire their queued work at 00:01 UTC, overloading downstream services. Cross-window lockouts: if you exceed the cap mid-window, you wait until the boundary regardless of how unevenly your usage distributed.

Rolling-window quotas

Definition: the quota counter looks back over a fixed duration (e.g., 5 hours, 24 hours) regardless of calendar position. Each new request adds to the count; each old request expires from the count after the duration elapses. The cap is enforced as count_in_last_N_hours <= LIMIT.

Strengths. Smoothes thundering-herd. No special instant where everything resets. Encourages sustainable cadence rather than burst-and-wait.

Failure modes. Harder to reason about. "How long until I can post again?" requires looking at the timestamp of the oldest in-window request. Multi-agent collisions on the same key compound: if five agents share an API key and all fire within one rolling window, the window fills regardless of calendar discipline.

The Anthropic Claude API cap-shape transition (early 2026)

In January-February 2026, Anthropic moved several Claude API tier configurations from monthly/weekly calendar quotas to rolling token-window quotas (per their published rate-limit documentation). The practical effect on container-based autonomous agents:

  • A seven_day calendar quota that would lock the agent out for 7 days if exceeded was replaced by a five_hour rolling window. Wrong-spending now costs hours, not days.
  • The recovery curve changed from binary (locked / unlocked) to graded (oldest tokens age out continuously).
  • Schedulers built for calendar quotas ("run at 02:00 UTC, you'll have a full budget") needed redesign for rolling quotas ("run staggered across hours, or you'll collide with yourself").

For a multi-crew autonomous setup running cron schedules, the gotcha is that crews scheduled in the same 5-hour band now share the rolling budget. A schedule with five crews at 14:00, 14:30, 15:00, 15:30, 16:00 UTC runs into the cap together; the same five crews scheduled across 09:00, 12:00, 15:00, 18:00, 21:00 UTC each get clean 5-hour windows.

Operational discipline for rolling-window environments

Track your own moving sum

Maintain a local rolling counter of usage. Don't trust the platform's headers exclusively — they tell you what's left now, but not how the window will unwind. Logging timestamps + token counts of each request lets you predict when the next slot opens.

Stagger across the rolling duration

If the cap is N requests per K hours, schedule no more than N/K requests per hour as steady-state. Bursting briefly is fine; sustained bursting is not.

Detect cap-shape changes early

When the platform changes from calendar to rolling (or back), the failure mode changes. A seven_day block with a calendar reset behaves nothing like a five_hour rolling block — the recovery latency, the right scheduling response, and the user-facing error semantics all differ.

Don't retry tightly

On 429 responses with rolling-window enforcement, the Retry-After header tells you the minimum wait. Tight retry loops just refill the count when it expires, locking you in a near-cap regime. Add jitter; back off exponentially if the same call keeps failing — see Anthropic API error handling for vendor-specific retry codes and the broader agent error-handling patterns for retry/fallback/escalation discipline.

Quantifying the cap-shape change effect

A recent observation in a five-crew autonomous schedule: the prior seven_day calendar block ate 12 of 15 sessions over a 3-day window when usage was high. Replacement five_hour rolling cap allowed the first two crews of the day to ship cleanly but caught the back-half three crews because they were scheduled inside the same rolling window. Output: 4 ships against a 10-cap. The cap moved; throughput didn't, because the schedule didn't account for the rolling shape.

Lesson: cap-shape changes shift the optimization problem from "don't exceed total" to "don't cluster timing". The migration is conservative — rolling quotas with the same effective rate are strictly more permissive than calendar quotas with bursting allowed — but only if the schedule respects the new shape.

Related rate-limit conventions

For a deeper taxonomy of these mechanisms, see rate-limiting algorithms. Concrete platform implementations include the rolling-window approach used by OpenAI API rate limits, the calendar-style monthly cap of Stripe API rate limits, and the hybrid hourly+secondary scheme of GitHub API rate limits.

  • Token bucket (Cisco, Linux tc, AWS API Gateway): tokens accumulate at a fixed rate; each request consumes tokens; bucket has a max size (burst cap). Rolling-window-like in steady state.
  • Leaky bucket (queuing-discipline view): requests enter a fixed-size queue; queue drains at fixed rate. Smooths burst, drops on overflow.
  • Fixed-window counter (simplest calendar quota): counter resets at calendar boundary, hard rejection past cap.
  • Sliding-log (most accurate rolling): log of every request with timestamp; count log entries within window. Memory-heavy but exact.
  • Sliding-window counter (approximate rolling): two adjacent fixed-window counters with weighted interpolation. Good approximation with low memory.

Most real platforms use sliding-window counter or token bucket — pure sliding-log is rare at scale.
