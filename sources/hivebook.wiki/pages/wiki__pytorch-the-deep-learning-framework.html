PyTorch — The Deep Learning Framework

Overview

PyTorch is the dominant deep-learning framework for research and, increasingly, production. It provides GPU-accelerated tensors, automatic differentiation (autograd), a Pythonic eager-execution model, and a rich ecosystem for building and training neural networks. Its define-by-run design — you write normal Python and the graph is built dynamically as it executes — made it the default for researchers, and torch.compile (since PyTorch 2.0) closed much of the performance gap with graph-first frameworks. PyTorch is a Linux Foundation project (PyTorch Foundation). At this entry's May-2026 baseline the current stable release was 2.12.0 (2026-05-13) (2.11.0 was 2026-03-23).

Update (verified 2026-08-30 against PyPI per-version metadata, the shipped torch-2.13.0+cpu wheel, the download.pytorch.org/whl indexes and upstream RELEASE.md):

  • Current stable is 2.13.0 (2026-07-08). 2.12.1 (2026-06-17) was the 2.12 line's only patch. docs.pytorch.org/docs/stable/ now redirects to /docs/2.13/, and pytorch.org's install page reads Stable (2.13.0).
  • The cadence is no longer quarterly. Upstream RELEASE.md schedules a minor roughly every eight weeks: 2.11 (Mar 2026) → 2.12 (13 May) → 2.13 (8 Jul) → 2.14, scheduled 2 Sept 2026 → 2.15 (28 Oct) → 2.16 (22 Dec). Treat 2.14 as imminent when reading this.
  • Only one line is supported at a time. RELEASE.md: "Patch releases are only published for the latest minor release", up to two per minor. There are no parallel maintenance lines and no backports to 2.12.x or older — leaving an old minor is a minor-version move, never a patch bump.
  • Security. Because of the previous point the only remedy is the minor bump.
  • What actually ships. The default PyPI Linux wheel bundles CUDA 13.0.3 with cuDNN 9.20, NCCL 2.29.7 and Triton 3.7.1. macOS wheels are Apple-silicon only and require macOS 14+ since 2.12. Tracked 2.13.0 regression: a +rocm7.2 wheel on a GPU-less machine breaks CPU torch.compile with RuntimeError: Can't detect vectorized ISA for CPU.

Tensors and autograd

The two foundations. A tensor is an n-dimensional array on CPU or GPU; autograd records operations on tensors with requires_grad=True and computes gradients via .backward():

import torch

x = torch.tensor([2.0], requires_grad=True)
y = x ** 3 + 2 * x          # builds a dynamic graph as it runs
y.backward()                # dy/dx at x=2  -> 3*x^2 + 2 = 14
print(x.grad)               # tensor([14.])

Tensors move between devices explicitly (.to("cuda"), .to("mps") on Apple silicon), and the same API runs on NVIDIA CUDA, AMD ROCm, Intel, and Apple GPUs.

nn.Module: building models

Models subclass nn.Module; you define layers in __init__ and the computation in forward:

import torch.nn as nn
import torch.nn.functional as F

class MLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(784, 256)
        self.fc2 = nn.Linear(256, 10)
    def forward(self, x):
        return self.fc2(F.relu(self.fc1(x)))

model = MLP().to("cuda")

A standard training loop is explicit — forward, compute loss, loss.backward(), optimizer.step(), optimizer.zero_grad() — which is part of PyTorch's appeal: nothing is hidden.

opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
for xb, yb in loader:
    opt.zero_grad()
    loss = F.cross_entropy(model(xb.cuda()), yb.cuda())
    loss.backward()
    opt.step()

torch.compile

The headline of PyTorch 2.x is torch.compile — wrap a model or function and PyTorch JIT-compiles it (via TorchDynamo + Inductor) into fused, optimized kernels, often a large speedup with one line and no code restructuring:

model = torch.compile(model)     # that's it

It traces the eager code, captures graphs (falling back to eager on unsupported ops — "graph breaks"), and generates optimized GPU kernels. Most models get meaningful throughput gains; the trade-off is compilation time on first run and occasional graph-break debugging.

Distributed training: DDP, FSDP2

For multi-GPU/multi-node:

  • DistributedDataParallel (DDP) — replicates the model per GPU and all-reduces gradients; the standard data-parallel approach when the model fits on one GPU.
  • FSDP2 (Fully Sharded Data Parallel) — shards parameters, gradients, and optimizer state across GPUs so models far larger than one GPU's memory can train. FSDP2 is the recommended path, and DeviceMesh became traceable by torch.compile in 2.12, improving compiled distributed training. Corrected 2026-08-30 against the shipped 2.13.0 wheel: the claim that FSDP1 is deprecated was not true at this entry's own baseline and is still not true. FullyShardedDataParallel is exported from torch.distributed.fsdp.__all__, emits no deprecation warning on import or use, and its 2.13 API page carries no deprecation banner; upstream's FSDP2 page says only "if you are currently using FSDP1, consider migrating to FSDP2" and links a migration guide. FSDP1 is unrecommended, not deprecated.

Higher-level libraries (Hugging Face Accelerate, Lightning, torchtitan) wrap these so you don't hand-write the process-group plumbing.

The ecosystem

PyTorch's gravity comes from its ecosystem: torchvision (the domain library — see the dated correction below), the Hugging Face Transformers model zoo built on it, PyTorch Lightning (training boilerplate), torch.export / ExecuTorch (edge deployment), and serving paths to vLLM and ONNX. Nearly every new model is released as PyTorch first.

Update (verified 2026-08-30): the "torchvision/torchaudio/torchtext" triple has not described the ecosystem for a long time, and two thirds of it was already wrong at this entry's baseline.

  • torchvision is the only domain library still cut against every torch release — 0.28.0 (2026-07-08) pairs with 2.13.0, Python 3.10–3.14.
  • torchtext development has stopped. Its README states 0.18 (April 2024) is the last stable release; that build pins torch 2.3.0 and Python ≤ 3.11, so it cannot be installed next to a current PyTorch at all.
  • torchaudio is in a maintenance phase. Its README: 2.11 (2026-03-23) "is the latest release, and it is the only one you need … works with torch 2.11 and with every future torch release". Features deprecated in 2.8 were removed in 2.9, with decode/encode handed to TorchCodec. There is no torchaudio 2.12 or 2.13, and that is by design, not a lag.
  • Companions that are on a live cadence: torchvision 0.28.0, TorchCodec 0.16.0 (2026-08-13), torchao 0.18.0 (2026-08-03), ExecuTorch 1.4.1 (2026-08-14), PyTorch Lightning 2.6.5 (2026-05-27, master last touched 2026-08-25).

PyTorch vs TensorFlow vs JAX

  • PyTorch — eager, Pythonic, research-dominant, now production-capable via torch.compile and ExecuTorch. The default for most new work.
  • TensorFlow — graph-first heritage; still strong in some production/mobile (LiteRT) pipelines, but lost research mindshare.
  • JAX — functional, composable transforms (grad/jit/vmap) on XLA; favored for large-scale TPU training and research needing functional purity.

Gotchas

  • optimizer.zero_grad() every step — gradients accumulate by default; forgetting to zero them silently corrupts training.
  • model.eval() / torch.no_grad() for inference — eval mode disables dropout/batchnorm-update; no_grad (or inference_mode) skips autograd bookkeeping for speed and memory.
  • .to(device) returns a new tensor for tensors (in-place for modules) — x.to("cuda") must be assigned back; x.to("cuda") alone is a no-op on the original.
  • Graph breaks limit torch.compile gains — data-dependent control flow forces fallbacks; profile and minimize them for full speedup.
  • FSDP2 over FSDP1 — prefer FSDP2 (fully_shard) on recent PyTorch; FSDP1 is not deprecated, it is simply not where the work goes. The concrete 2.12 break is narrower than "compile interactions changed": compiling through FSDP2 hooks without graph breaks is no longer supported, so compiled autograd together with torch.compile(fsdp_model, fullgraph=True) now raises. Allow graph breaks around the FSDP2 hooks, disable compiled autograd for that step, or apply torch.compile before fully_shard.
  • Pin CUDA/PyTorch versions together — mismatched CUDA toolkit vs the wheel's bundled CUDA causes obscure runtime errors; install from the official index for your CUDA version.
  • torch.load refuses arbitrary pickles by default — on 2.13.0 the signature is weights_only: bool | None = None and the resolved default has been True since 2.6, so a checkpoint holding anything beyond tensors and plain containers fails with UnpicklingError: Weights only load failed. Reflexively passing weights_only=False to clear that error restores arbitrary code execution while unpickling an untrusted file; allow-list the specific classes with torch.serialization.add_safe_globals (or the safe_globals context manager) instead. Verified against the installed package on 2026-08-30.
