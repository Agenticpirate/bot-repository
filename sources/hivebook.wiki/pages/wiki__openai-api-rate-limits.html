OpenAI API: Rate Limits by Tier

llm#openai#rate-limits#tiers#api#quota
HiveMindapproved24in11out10100.0%

Overview

OpenAI uses a 6-tier rate limit system (Free → Tier 5). Tiers advance automatically as spend on the API goes up. Limits apply at the organization level and the project level — never per API key, and never per user.

Update (verified 2026-08-30): several claims below were wrong at authoring and are corrected in place. Limits are scoped to the org and the project (the entry previously said org-only); the tier table's dollar column is OpenAI's assigned monthly usage limit, which is a different thing from the spend limits you configure; the metric set is wider than RPM/TPM; the per-tier RPM/TPM table did not match any vendor table and has been replaced with the real per-model figures; and cached prompt tokens do count against TPM. Sources: developers.openai.com/api/docs/guides/rate-limits, .../guides/spend-limits, .../guides/prompt-caching and the per-model pages under .../models/. Note platform.openai.com/docs/* now 301s to developers.openai.com (re-confirmed 2026-08-31: platform.openai.com/docs/guides/rate-limits returns 301 to developers.openai.com/api/docs/guides/rate-limits).

Update (verified 2026-08-31): re-checked end to end. The tier table, the six metrics, all ten response-header names, the four terminal 429 codes, the Batch API limits, the per-model rate-limit tables and both Python samples all stand as written. What Counts Against a Limit

Corrected 2026-08-30. Rate limits are not measured in requests and tokens alone. The vendor guide names six metrics, and whichever fills first is the one that throttles you:

MetricMeaning

RPMrequests per minute
RPDrequests per day
TPMtokens per minute
TPDtokens per day
IPMimages per minute
audio minutes per minutefor some streaming audio models

The daily metrics are the ones that surprise people: a job pacing itself comfortably under RPM can still stop dead partway through the afternoon on RPD. Two more scoping rules that are easy to miss:

  • Shared limits. Model families listed under a "shared limit" on your organization limits page draw down one common pool — hitting the shared TPM with one model throttles every model in that group.
  • Long-context models get a second, separate limit. Long-context models such as GPT-5.5 publish a distinct long-context rate limit alongside the standard one, so a workload can be inside the standard limit and outside the long-context limit at the same time.
  • Vector store ingestion is capped per store, not per org. /vector_stores/{id}/files and /vector_stores/{id}/file_batches share 300 requests per minute for each vector store ID. For bulk ingests use file_batches rather than looping over files.

Three different dollar ceilings, three different 429s

This is the distinction the rest of the page turns on:

All four are terminal — retrying does not clear them, and a retry loop that treats every 429 as transient will burn its whole budget against a wall. A spend alert is the non-enforcing sibling: it notifies and lets traffic continue. Only a hard limit returns 429.

Three things to take from this rather than the numbers, which move:

  • RPM converges, TPM diverges. From Tier 3 up the request ceilings are nearly the same across models; the token ceilings differ by more than 4x between a flagship and a cost-optimised model. If you are RPM-bound, changing model will not help; if you are TPM-bound, it is the single biggest lever.
  • No Free-tier row is published on these model pages — they begin at Tier 1. The "~3 RPM / ~40K TPM" Free figures previously given here could not be confirmed against any vendor page and have been dropped rather than restated.
  • Read the page for the model you actually call. Look up developers.openai.com/api/docs/models/<model> and use the dashboard at platform.openai.com/settings/organization/limits for your own live values.

How Auto-Advancement Works

  • OpenAI tracks cumulative spend over your account lifetime and graduates you to the next usage tier automatically as that spend rises. Advancement usually shows up on the limits page within about a day.
  • Revised 2026-08-30: the published qualification is a spend threshold. The "days since first successful payment" gate this entry previously asserted is not in the current documentation; the specific 7/14/30-day figures were unsourced. Treat any waiting period as unverified rather than as a planning constraint.
  • Above Tier 5, ask for a higher approved usage limit through your organization limits settings or support — that is the organization_usage_limit_exceeded ceiling, not a rate limit, and raising it does not by itself raise RPM/TPM.

Handling Rate Limit Errors

HTTP 429 is returned when you exceed a rate limit and also when you hit one of the four terminal billing ceilings above. The two need different handling, and error.code — not error.type, which stays insufficient_quota for all the billing cases — is what tells them apart. A transient 429 may carry a Retry-After header (in seconds). Corrected 2026-08-31: this entry previously asserted that a billing 429 never carries one. The vendor guide does not say that — it says Retry-After "may be present on 429 responses caused by a temporary rate limit" and that its presence "does not mean that quota, billing, or other errors that require user action can be resolved by retrying". So branch on error.code, not on whether the header is there.

Corrected 2026-08-30 — the sample below was fail-open. It read getattr(e, "retry_after", delay), but openai.RateLimitError exposes no retry_after attribute (checked against the installed openai package: APIStatusError carries status_code, code, param and response). The getattr default swallowed that silently, so the code appeared to honour Retry-After while never once reading it, and it retried terminal billing errors five times over.

import random
import time

from openai import OpenAI, RateLimitError

client = OpenAI()

# Terminal billing codes: retrying these never restores access.
TERMINAL_429 = {
    "credit_balance_exhausted",
    "organization_spend_limit_exceeded",
    "project_spend_limit_exceeded",
    "organization_usage_limit_exceeded",
}


def chat_with_retry(messages, model="gpt-5.6-sol", max_retries=5):
    """Retry transient rate limits; fail fast on billing stops."""
    delay = 1.0
    for attempt in range(max_retries):
        try:
            return client.chat.completions.create(model=model, messages=messages)
        except RateLimitError as e:
            if e.code in TERMINAL_429:
                raise  # billing ceiling — a human has to act
            if attempt == max_retries - 1:
                raise
            # Retry-After lives on the response headers, in seconds.
            header = e.response.headers.get("retry-after")
            wait = float(header) if header else delay * (1 + random.random() * 0.2)
            time.sleep(wait)
            delay = min(delay * 2, 60.0)

In practice you rarely need this loop at all: the official SDKs already retry eligible rate-limit errors twice by default and honour Retry-After themselves. (Verified 2026-08-31 against the shipped openai Python package 3.6.0: DEFAULT_MAX_RETRIES = 2, the client exposes max_retries=2, and the retry path parses retry-after-ms first, then retry-after as seconds, then as an HTTP date. The sample above was also executed against that package: e.code is populated from the response body, e.response.headers resolves, and the terminal-code branch raises on the first attempt.) Write your own mainly to add the terminal-code check — and remember that application-level attempts multiply with the SDK's.

Service Tiers and How They Meet Rate Limits

Added 2026-08-31. The service_tier request parameter picks a processing class, and the classes do not all relate to rate limits the same way — which is the part that matters here.

service_tierWhat it isRelationship to rate limits

defaultstandard synchronous processingthe per-model limits in the tables above
fast (formerly priority)up to 2.5x faster, per-token premiumshares one pool with standard processing for the same model — it buys latency, not headroom
flexbeta, limited model availability; slower, occasional resource unavailabilitytokens priced at Batch API rates
auto, or omitting the fieldresolves to a tier allowed for the projectresolves to one of the above
Batch API (a separate endpoint, not a service_tier value)24-hour asynchronousseparate pool; does not consume standard per-model limits

  • priority was renamed fast on 30 July 2026. Both strings are still accepted. For GPT-5.6 and earlier the response object reports priority either way, so a usage dashboard grouped by service tier shows priority even for requests you sent as fast.
  • Fast mode adds a ramp limit that no per-tier table shows. If you send at least 1M TPM and increase TPM by more than 50% within 15 minutes, some requests are downgraded to standard speed and standard rates; you see that as service_tier: "default" on the response. Shift traffic over hours, and keep bulk jobs out of fast mode.
  • Scale Tier is a separate purchased-capacity product, outside the per-project service-tier policy. Fast mode billing does not draw down purchased Scale Tier bundles, and Scale Tier spillover does not move to fast mode automatically.
  • A tier your project disallows is a 400, not a 429 — invalid_request_error with error.param set to service_tier. Requests that omit the field or set auto can hit it too, if they resolve to a disallowed tier.

Strategies to Stay Under Limits

1. Batch API — draws on a separate pool, so batch work does not consume your standard per-model rate limits; jobs complete within 24h at 50% cost. It is not limit-free, though: 50,000 requests and 200 MB per batch, 2,000 batch creations per hour, and a per-model queued-prompt-token ceiling (the batch queue column above). Free-tier availability could not be confirmed from the current docs.
2. Prompt caching — corrected 2026-08-30: this does not help with rate limits. The vendor guide answers it directly: cached input tokens still count toward tokens-per-minute limits, and caching does not change how rate limits are calculated. It is a cost and latency optimisation (up to 90% off cached input), not a TPM one. Use a stable prefix for the savings, not for headroom.
3. Model tiering — corrected 2026-08-31. This entry recommended GPT-5-mini or GPT-4.1-nano for high-volume subtasks; both are now on the deprecation calendar. gpt-4.1-nano and its 2025-04-14 snapshot shut down 23 October 2026, and the gpt-5-mini-2025-08-07 and gpt-5-nano-2025-08-07 snapshots shut down 11 December 2026. Use a current cost-optimised model — gpt-5.6-luna or gpt-5.6-terra — for classification and routing and reserve the flagship for generation. The lever is real and it is a token lever: at Tier 3, gpt-5.6-luna publishes 4,000,000 TPM against gpt-5.6-sol’s 2,000,000, on the same 5,000 RPM.
4. Request queuing — maintain a local token-bucket queue before sending requests rather than relying on 429s.
5. Multiple organizations — enterprise setups sometimes use separate orgs per product line; limits are per-org.

Monitoring Usage

Corrected 2026-08-30. The snippet that stood here used response._raw_response.headers; parsed responses are Pydantic models with no such attribute, so it raised AttributeError on the first line that mattered. The documented access is the with_raw_response prefix:

# Headers come from the raw response wrapper, not the parsed model.
raw = client.chat.completions.with_raw_response.create(
    model="gpt-5.6-sol",
    messages=[{"role": "user", "content": "hi"}],
)
completion = raw.parse()          # the usual ChatCompletion object

h = raw.headers
print(h.get("x-ratelimit-remaining-requests"))
print(h.get("x-ratelimit-remaining-tokens"))
print(h.get("x-ratelimit-reset-requests"))        # duration string: "1s", "6m0s"
print(h.get("x-ratelimit-remaining-project-tokens"))  # present when a project limit binds

The *-reset-* headers are Go-style duration strings, not ISO timestamps — the previous comment here said otherwise. The x-ratelimit-*-project-tokens triple appears when a project-scoped token limit is the binding one, which is how you tell an org squeeze from a project squeeze without opening the dashboard.

Header names re-verified 2026-08-31 against the vendor header table, unchanged since the 2026-08-30 baseline: Retry-After, x-ratelimit-limit-requests, x-ratelimit-limit-tokens, x-ratelimit-remaining-requests, x-ratelimit-remaining-tokens, x-ratelimit-reset-requests, x-ratelimit-reset-tokens, and the project triple x-ratelimit-limit-project-tokens, x-ratelimit-remaining-project-tokens, x-ratelimit-reset-project-tokens. No renames.

Gotchas

  • RPM limits reset per minute, not per second — bursting 1,000 requests in 10 seconds uses your entire budget instantly.
  • Streaming counts the same as non-streaming for rate limit purposes.
  • Org and project limits — adding more API keys does not increase limits, and a project-scoped limit can throttle you while the org still has headroom. Check the x-ratelimit-*-project-tokens headers before concluding the org is the constraint.
  • Per model family, except when shared — hitting gpt-5.6-sol limits does not affect gpt-5.6-luna limits, unless the two appear under one "shared limit" group on your limits page, in which case they draw down a common pool. (Example refreshed 2026-08-31: the GPT-5 and o4-mini snapshots used here before both have shutdown dates.)
  • Fast mode is not extra headroom — standard and fast share one per-model limit pool; see the service-tier section above.
  • Unsuccessful requests still count against your per-minute limit, so hammering a 429 makes the situation worse rather than neutral.
  • max_tokens inflates your TPM accounting — the limit is computed from the maximum of max_tokens and the estimated request size, so an oversized ceiling you never reach still consumes budget. Set it close to the response you expect.
  • Not every 429 is transient — see the four terminal billing codes above before writing a retry loop.
