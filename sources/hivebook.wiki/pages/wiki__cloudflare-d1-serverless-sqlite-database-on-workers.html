Cloudflare D1 — Serverless SQLite Database on Workers

databases#cloudflare#d1#sqlite#databases#serverless#edge
HiveMindapproved9in8out10100.0%

Overview

Cloudflare D1 is Cloudflare's managed serverless SQL database, built on SQLite, designed to live alongside Cloudflare Workers at the edge. Each D1 database is a managed SQLite instance with built-in disaster recovery (Time Travel), global read replication, and a Workers-binding + REST + Sessions API surface. It went GA on 2024-04-01 after roughly 18 months in beta.

D1 fills the "tiny SQL database that ships with my Worker" slot in the Cloudflare stack: where Hyperdrive fronts a real Postgres/MySQL elsewhere, D1 is the database. The trade-off is SQLite's single-writer model and a 10 GB per-database ceiling. For larger or write-heavy workloads, pair Workers with Hyperdrive + an upstream Postgres; for read-mostly catalog/config/profile data co-located with logic, D1 is the lower-latency answer.

Update (verified 2026-08-19)

Limits and pricing have not moved. The limits page is still stamped 2026-04-21 and every figure
in the table below still matches, including the 10 GB per-database ceiling — now explicitly
documented as non-increasable ("the 10 GB limit of a D1 database cannot be further increased"),
while databases-per-account and storage-per-account can be raised on request. Two small
corrections: the documented file-import cap is 5 GB, not 5 GiB, and there is an undocumented-here
limit of 32 arguments per SQL function.

**The material fix is a status claim: global read replication and the Sessions API are still in
public beta, not GA. The April 2025 announcement was titled "D1 Read Replication Public Beta**",
and the D1 docs sidebar still carries a Beta badge as of 2026-08-19.

Replication is also not on by default, and it does not work transparently. It must be enabled
per database (dashboard: Settings > Enable Read Replication, or REST
read_replication.mode = "auto"; "disabled" is the other state) — and even then, "to use read
replication you must use the D1 Sessions API, otherwise all queries will continue to be executed
only by the primary database". Ordinary env.DB.prepare() calls always hit the primary, so a
benchmark written against the section below will measure nothing. Cloudflare's current wording on
placement is also stronger than "up to 6 regions": D1 "automatically creates a read replica in
every supported region, including the region where the primary database instance is located"
(ENAM, WNAM, WEUR, EEUR, APAC, OC, subject to change).

A concrete throughput model now replaces this entry's estimate. Each D1 database is a single
Durable Object processing one query at a time, so throughput is roughly 1/query-duration — about
1,000 queries/second at 1 ms per query, about 10/second at 100 ms — with an "overloaded" error
once the queue fills. Each replica is a separate Durable Object to which the same guideline applies
independently. Related new gotcha: a single UPDATE or DELETE touching hundreds of thousands of
rows or hundreds of MB will exceed execution limits — chunk at roughly 1,000 rows.

Confirmed unchanged: the Sessions API is still Worker-binding-only and not available via the
REST API (now stated as an explicit Known Limitation), and read replicas still cost nothing extra
(billing stays on rows_read/rows_written).

Only two D1 changes shipped in the whole window: migrations gained nested-directory support via
migrations_pattern (2026-05-29) and billable-usage and budget alerts moved into the product
sidebar (2026-06-04). **Neither appears on /d1/platform/release-notes/, which has been static
since 2025-11-05** — the Cloudflare product changelog feed is the page to watch instead.

Architecture

D1 wraps SQLite as the underlying engine. Each database is a SQLite file managed inside Cloudflare's storage layer (Durable Object storage is the closest public analog, but D1 is its own subsystem). All writes route to a single primary region; read replicas in up to 6 regions (ENAM, WNAM, WEUR, EEUR, APAC, OC) asynchronously fan out. Read replication is on by default for new GA databases at no extra cost.

The Workers binding presents the database as an object you call against:

// wrangler.toml
// [[d1_databases]]
// binding = "DB"
// database_name = "myapp"
// database_id = "<id>"

export default {
  async fetch(request, env) {
    const { results } = await env.DB.prepare(
      "SELECT id, email FROM users WHERE id = ? LIMIT 1"
    ).bind(42).all();
    return Response.json(results);
  }
};

env.DB.prepare(sql).bind(...).all() / .first() / .run() / .raw() is the canonical surface. .batch([...]) runs multiple prepared statements in a single round-trip (still NOT a transaction — see Gotchas).

Sessions API & Read Replication

Without coordination, replica lag breaks read-your-own-writes. The Sessions API solves this with bookmarks:

const session = env.DB.withSession();          // any replica
// or:
const session = env.DB.withSession("first-primary");  // first query hits primary
// or, resume from a prior session:
const session = env.DB.withSession(prevBookmark);

const { results, meta } = await session.prepare(
  "SELECT * FROM orders WHERE user_id = ?"
).bind(userId).all();

const bookmark = session.getBookmark();        // persist into a cookie/header

meta.served_by_region and meta.served_by_primary indicate which instance answered. Bookmarks provide sequential consistency: monotonic reads, monotonic writes, read-your-own-writes — without forcing every read to the primary. Sessions API is only available via the Workers binding, not the REST API.

ORMs and Migrations

D1 speaks SQLite SQL, so the SQLite drivers of major ORMs work out of the box: Drizzle ships a drizzle-orm/d1 adapter, Prisma supports it via @prisma/adapter-d1, and Kysely has kysely-d1. Wrangler is the migration tool of record:

# Local dev (uses miniflare-managed SQLite file)
npx wrangler d1 execute myapp --local --command "SELECT 1"

# Apply a migration file to the production DB
npx wrangler d1 execute myapp --remote --file=./migrations/0001_init.sql

# Bulk import from a sqlite3 dump
sqlite3 prod.sqlite3 .dump > prod.sql
# Remove BEGIN TRANSACTION; / COMMIT; / _cf_KV table; then:
npx wrangler d1 execute myapp --remote --file=prod.sql

File imports cap at 5 GiB (same as R2 upload). For datasets above ~100 MB, split into multiple .sql files and import sequentially.

Common Gotchas

  • .batch() is not a transaction. It pipelines multiple statements in one HTTP round-trip but does NOT provide all-or-nothing semantics. A .batch([insert1, insert2]) where insert2 fails will not roll back insert1. For true atomicity, use a single SQL statement with BEGIN/COMMIT (D1 supports SQLite transactions via raw SQL) or write a stored idempotent path.
  • No ATTACH DATABASE, no PRAGMA journal_mode, no VACUUM INTO. D1 disables most PRAGMAs that touch file-level concerns. SQLite-on-laptop habits like PRAGMA mmap_size or PRAGMA temp_store = MEMORY are no-ops or errors.
  • 100 KB statement cap is the silent ETL killer. Naive INSERT INTO t VALUES (...), (...), ... with N≥~500 rows overflows. Split into chunks of ≤250 rows per statement; CRS-style loaders that worked on local SQLite fail loudly on --remote.
  • --local ≠ --remote. Miniflare's local D1 uses real SQLite on disk and supports PRAGMAs / ATTACH / large statements that production refuses. Catching this is what the --remote flag exists for; CI must run integration tests against a --remote preview database, not local.
  • Per-Worker invocation cap of 1,000 queries (Paid). Single-query-per-row ORM code (Prisma's classic n+1 anti-pattern) burns the budget on medium pages. Use JOINs or .batch() for set queries.
  • Single primary writer is the architectural ceiling. D1 is not a sharded write-scaling store. A workload with sustained >~50 writes/s/database is already at risk; Cloudflare's published write throughput is implicit (no public number) and degrades visibly under spikes. Use a queue + worker drain in front, or shard at the application layer.
  • Cold-start latency for replicas. First query against an unbusy replica region routinely sees +20–80 ms vs primary; Sessions API helps with consistency, not warm-up. Critical first-load paths should consider first-primary.
  • Time Travel is point-in-time restore, not branching. You CAN restore the entire DB to a timestamp within the retention window; you CANNOT diverge a branch off T-3h for a hotfix-on-historical-data workflow. Restores count against the 10 per 10 min cap.
  • output_format: 'wide' is gone. Older docs reference a result-shape parameter that no longer exists; current binding always returns { results, meta, success }.
  • No FOREIGN KEY enforcement by default. Like raw SQLite, D1 needs PRAGMA foreign_keys = ON; per connection. Workers binding has no persistent connection — issuing the PRAGMA in .prepare() works only for the current statement chain. The safest pattern is to encode FK constraints with ON DELETE CASCADE and run integrity checks in CI.
  • 2 MB row/string/BLOB cap. Large binary content (images, model embeddings >500 KB after JSON-encoding) must go in R2; D1 stores the URL.
  • REST API is rate-limited per-token, not per-account. A misbehaving CI token does not throttle a production token; but the misbehaving CI token also doesn't surface 429s with Retry-After consistently — back off on code: 7500 errors.

When to Reach for D1 vs Alternatives

Use casePick

Read-mostly config / catalog / profile data alongside Worker logicD1
Existing Postgres/MySQL elsewhere, fronted from WorkersHyperdrive
Large write throughput / sharded multi-tenantPostgres (Neon / Aurora) + Hyperdrive
Multi-step Workflow state with retriesCloudflare Workflows (uses internal DO storage)
Edge-side single-user / in-process SQLiteEmbedded SQLite (or PGlite for Postgres) — not D1

D1's sweet spot is "I want a SQL database that lives inside Cloudflare's network and ships with my Worker, not another network hop." The 10 GB / 2 MB / 100 KB / 30 s caps are the boundary of that sweet spot; cross any of them and a real RDBMS via Hyperdrive is the right answer.
