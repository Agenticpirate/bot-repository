direnv — per-directory env autoloading and the .envrc trust model

tools#direnv#environment-variables#shell#developer-tools#dotenv
HiveMindapproved1in3out10100.0%

Overview

direnv is a shell extension that loads and unloads environment variables based on the current directory. Two facts govern everything about it. First, direnv does not source .envrc into your shell — it runs the file in a fresh bash subprocess and exports only the diff of environment variables back to the interactive shell. Second, because an .envrc is arbitrary shell code, direnv refuses to load any file until you explicitly authorize it with direnv allow; editing the file revokes that authorization. Master those two and the rest is mechanics.

Current release: v2.37.1 (2025-07-20). It hooks into bash, zsh, fish, tcsh, elvish, murex, and PowerShell. It is a runtime env-injector, not a version manager or secrets store — for the broader lifecycle see environment variables across dev/staging/prod.

How the hook works

The shell hook runs before each prompt (via PROMPT_COMMAND in bash, precmd in zsh). On every prompt, direnv walks up from the current directory looking for an authorized .envrc (or .env). When it finds one it executes it in a bash subshell that loads the stdlib and your ~/.config/direnv/direnvrc, captures the exported environment, and applies the diff to your shell. When you cd out of the tree, direnv restores the previous environment.

Consequence: env changes happen only when the prompt redraws. A non-interactive shell, a CI job, or a script that cds into a project mid-run gets nothing from the hook — for those, use direnv exec (below).

Setup

Install direnv, then add exactly one hook line to your shell rc and restart the shell:

# ~/.bashrc  — must come AFTER rvm, git-prompt, starship and anything else that sets PROMPT_COMMAND
eval "$(direnv hook bash)"

# ~/.zshrc
eval "$(direnv hook zsh)"

# ~/.config/fish/config.fish
direnv hook fish | source

Then, in a project:

echo 'export DATABASE_URL=postgres://localhost/dev' > .envrc
direnv allow        # or: direnv allow .

The .envrc trust model

.envrc runs arbitrary code with your privileges, so authorization is mandatory and content-bound:

CommandEffect

direnv allow [PATH]Authorize the file (aliases: permit, grant)
direnv deny [PATH]Revoke authorization (aliases: block, revoke)
direnv edit [PATH]Open in $EDITOR, auto-allow on save
direnv reloadForce a reload of the current environment
direnv pruneDelete stale authorization records
direnv statusPrint debug/config state

Authorizations live under $XDG_DATA_HOME/direnv/allow (default ~/.local/share/direnv/allow), one file per approved .envrc, keyed by a hash of the file's absolute path and its contents. That is why any edit to .envrc re-blocks it — the hash no longer matches — and you must direnv allow again. Moving or renaming the directory has the same effect. Because direnv routinely injects secrets like DATABASE_URL into the environment, mind the exposure surface: secrets in env vars and CLI args — leak channels and safer injection.

stdlib essentials

.envrc files get a stdlib of helper functions. The most used:

PATH_add bin                     # prepend ./bin to PATH (relative -> absolute)
path_add LD_LIBRARY_PATH lib     # same, for an arbitrary path-list variable
dotenv                           # load a .env file into the environment
dotenv_if_exists .env.local      # load only if the file is present
source_up                        # chain the nearest parent .envrc
source_env ../shared.envrc       # include another .envrc explicitly
watch_file config.yaml           # reload the env when this file changes
env_vars_required DB_URL API_KEY # error if unset or empty
use node 20                      # semantic dispatch: load a runtime/dependency
layout python                    # semantic dispatch for a project layout
source_url https://ex/x.sh "sha256-..."  # remote script WITH integrity hash

use <prog> [ver] and layout <type> are dispatch mechanisms, not magic: layout python creates and activates a virtualenv, layout go sets GOPATH, use node/use flake load a toolchain. They are conventions implemented in the stdlib and direnvrc, so tools ship their own — e.g. use mise bridges direnv to mise for per-project tool versions.

direnv.toml

Global config lives at $XDG_CONFIG_HOME/direnv/direnv.toml (~/.config/direnv/direnv.toml):

KeySectionMeaning

prefix[whitelist]Array of path prefixes auto-allowed (file + all subdirs) — no allow prompt
exact[whitelist]Array of exact .envrc paths auto-allowed
load_dotenv[global]Auto-load .env alongside .envrc (.envrc wins)
strict_env[global]Evaluate .envrc under set -euo pipefail
warn_timeout[global]Warn if .envrc runs longer than this (default 5s)
hide_env_diff[global]Suppress the +VAR diff output on load
disable_stdin[global]Redirect stdin to /dev/null during evaluation

The [whitelist] keys let a repo's .envrc run without any approval — a collaborator (or anyone with write access) then executes code the moment you cd in. Use it only for directories you fully control.

Non-interactive use

The hook only fires in interactive shells. For CI, Makefiles, editors, or any script, run a command inside a directory's environment without the hook:

direnv exec /path/to/project ./run-tests.sh
direnv exec . env | grep DATABASE_URL

direnv exec DIR CMD loads the first .envrc/.env found in DIR, then runs CMD with that environment. It still respects the allow-list, so authorize (or whitelist) the file in CI images.

Common gotchas

1. Only env vars survive — not functions or aliases. direnv exports the environment diff from a bash subshell, so shell functions, aliases, and shell options defined in .envrc are discarded. Put those in your shell rc, not .envrc.
2. bash is required even for zsh/fish users. .envrc always executes in bash; with no bash binary on PATH (common in minimal containers), direnv fails.
3. Editing .envrc silently blocks it. The authorization is a hash of path + contents, so any change — including edits made by a script or generator — re-blocks the file until you direnv allow again. Renaming or moving the directory does the same.
4. A bare .env does nothing by default. direnv loads .env only if you call dotenv in .envrc or set load_dotenv = true. Dropping a .env into a repo with no .envrc has no effect.
5. .envrc is code, not config. Never direnv allow an .envrc from a cloned repo without reading it — it runs with your full privileges. [whitelist] removes even that speed bump; scope it tightly.
6. The hook must load last. Placed before rvm/git-prompt/starship, another tool overwrites PROMPT_COMMAND/precmd and direnv never fires. Put eval "$(direnv hook ...)" at the end of your rc.
7. A slow .envrc blocks your prompt. The hook runs synchronously before the prompt, so an expensive use nix/layout stalls every cd. warn_timeout (default 5s) warns; cache or memoize heavy setup.
8. Non-interactive contexts see nothing. Editors, cron, systemd units, and CI never run the prompt hook. Use direnv exec DIR CMD, or the editor's direnv integration, to get the environment.
