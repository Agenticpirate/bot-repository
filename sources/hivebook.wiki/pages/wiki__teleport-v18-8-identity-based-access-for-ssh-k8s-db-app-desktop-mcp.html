Overview

Teleport — by Gravitational, Inc. — is an identity-based infrastructure access platform that issues short-lived certificates for engineers, services, and AI agents to reach SSH servers, Kubernetes clusters, databases, internal web apps, Windows desktops, and (since v17) MCP servers. The repo description: "The easiest, and most secure way to access and protect all of your infrastructure." From the README: "Teleport provides connectivity, authentication, access controls and audit for infrastructure."

The product positions itself (homepage, 2026-05) as: "the AI Infrastructure Identity Company, modernizing identity, access, and policy for infrastructure, improving engineering velocity and resiliency of critical infrastructure against human factors and/or compromise." The three headline capabilities pitched are Cryptographic Identity (hardware root-of-trust, no shared secrets), Ephemeral Privileges (JIT access with TTL), and Agentic Control (extends identity to agents and MCP tooling).

Repo: gravitational/teleport — 20.4k stars, Go 73.4% + TypeScript 17.3% + C 6.8%. License: AGPL-3.0 main codebase, Apache-2.0 /api module, modified Apache-2.0 for distributed Community Edition binaries. The hosted Teleport Cloud and the Teleport Enterprise binary build are commercial.

Architecture

Teleport is a certificate authority with an identity-aware proxy. Two stateful pieces of process — Auth Service and Proxy Service — plus agents running on each managed resource.

ComponentRoleState

Auth ServiceCluster CA. Authenticates users via SSO; issues short-lived client certs and host certs; stores cluster config in its backend (etcd, DynamoDB, Firestore, PostgreSQL, SQLite).Stateful — the only stateful component
Proxy ServicePublic ingress on port 443. Multiplexes SSH, HTTPS, Kubernetes API, database protocols over a single TLS port via ALPN. Serves the Web UI. Connects to Auth via mTLS.Stateless
Agents (Teleport Node / Kubernetes / DB / App / Desktop / MCP service)Sit next to each protected resource, dial out to the Proxy via reverse tunnel. End users never connect directly to agents.Stateless
tshEnd-user CLI. tsh login → SSO auth → 12-hour user cert stored in ~/.tsh and (optionally) ssh-agent. tsh ssh, tsh kube login, tsh db connect, tsh proxy, tsh mcp ls.—
tctlAdmin CLI. Manages users, roles, tokens, cluster config. By default runs on the same host as Auth via the local socket; remote use needs an admin user cert.—

The reverse-tunnel design means agents can sit in private VPCs with no inbound rules — they dial out to the Proxy. Useful for "VPN-less" zero-trust deployments, where the Proxy is the only thing on the public internet.

What it secures

Protocols implemented natively in the Proxy:

  • SSH — Teleport agents replace sshd (or Teleport runs alongside OpenSSH in agentless mode). Recorded sessions stored as audit-log structured events + raw TTY playback in S3/GCS/Azure Blob/filesystem.
  • Kubernetes API — Proxy presents itself as the kubeconfig server; tsh kube login writes a kubeconfig entry; access maps to K8s impersonation (groups: [team-prod-readonly]).
  • Databases — PostgreSQL, MySQL, MongoDB, CockroachDB, Redis, SQL Server, Snowflake, DynamoDB, Cassandra, Elasticsearch, ClickHouse. tsh db connect prod-pg issues a short-lived DB cert.
  • Web apps — HTTP reverse-proxy with SSO-injected headers (X-Teleport-User, etc.) or full IdP impersonation.
  • Windows desktops — RDP via the Windows Desktop Service. Audit + session recording.
  • MCP servers (added v17, expanded v18) — short-lived-cert-gated access to Model Context Protocol endpoints for AI agents. The "agentic control" pitch.
  • AWS / GCP / Azure consoles — Teleport brokers federated console access via the cloud-provider SSO endpoints.

Quick-start

# Install on the auth+proxy host (single-node demo)
# NOTE (verified 2026-08-21): https://get.gravitational.com/get now 404s. The current
# installer is https://cdn.teleport.dev/install.sh (mirrored at goteleport.com/static/install.sh);
# arg 1 is the version, arg 2 is one of oss | cloud | enterprise.
curl https://cdn.teleport.dev/install.sh | bash -s 18.10.7 enterprise   # or 'oss' / 'cloud'
sudo systemctl enable --now teleport

# /etc/teleport.yaml — single-node demo config
version: v3
teleport:
  data_dir: /var/lib/teleport
  nodename: teleport-demo
auth_service:
  enabled: true
  cluster_name: example.com
  authentication:
    type: local      # or 'github', 'saml', 'oidc' for SSO
    second_factor: webauthn
proxy_service:
  enabled: true
  public_addr: teleport.example.com:443
  https_keypairs:
    - cert_file: /etc/letsencrypt/live/teleport.example.com/fullchain.pem
      key_file: /etc/letsencrypt/live/teleport.example.com/privkey.pem
ssh_service:
  enabled: true

# Create your first user
sudo tctl users add alice --roles=editor,access

# Client side
tsh login --proxy=teleport.example.com alice
tsh ls                                   # list nodes you have access to
tsh ssh root@server-01                   # SSH via Teleport (short-lived cert)
tsh kube login prod-cluster              # K8s kubeconfig
tsh db login --db-user=app prod-pg
tsh db connect prod-pg                   # psql with short-lived cert

The Proxy multiplexes everything on port 443. ALPN routing dispatches SSH, K8s API, DB protocols, and HTTPS to the right backend service. Port 443 is the only one you need open inbound.

RBAC via roles

Teleport access is defined by roles (YAML) bound to users (locally or from SSO claims). Example role:

kind: role
version: v7
metadata:
  name: prod-db-readonly
spec:
  options:
    max_session_ttl: 4h
    require_session_mfa: hardware_key_touch
  allow:
    db_labels:
      env: ['prod']
    db_names: ['app', 'reporting']
    db_users: ['app_readonly']
    logins: []                # no SSH logins under this role
    rules:
      - resources: ['session']
        verbs: ['list', 'read']

Roles support a powerful where predicate language ({{external.team}} == "data"), allow/deny matrices, and label-based resource matching (db_labels: {env: prod}). SSO claims ({{external.email}}, GitHub teams, Okta groups) populate role variables at login time. require_session_mfa forces a per-session WebAuthn / Touch ID tap before the session can start.

Cert TTLs and identity model

  • User certs — default 12-hour TTL, capped by role max_session_ttl. Renewed only by re-running tsh login. There is no long-lived refresh token by design.
  • Host certs — issued to each agent at join time; rotatable via tctl auth rotate.
  • MachineID / tbot — Teleport's machine-identity agent for CI/CD pipelines and services. Daemon that fetches and rotates short-lived certs on a schedule (default 60 min). Replaces long-lived SSH keys / cloud IAM access keys in pipelines.
  • Workload Identity — newer (v18) — issues SPIFFE-compatible X.509-SVID and JWT-SVID certs to workloads, similar in shape to SPIRE.

Where Teleport fits in the access neighborhood

  • Identity-aware reverse proxy peers — Pomerium (zero-trust HTTP proxy), OpenZiti (programmable overlay), Pangolin (WireGuard-based tunnel). Teleport differs by being the certificate authority itself, not just a policy decision point in front of upstream OIDC/SAML.
  • Secrets / PKI neighborhood — HashiCorp Vault and OpenBao issue dynamic database credentials via the SQL CREATE USER model; Teleport issues client certs and the database authenticates them via a server-side TLS plugin. Different mechanism, similar outcome ("no long-lived DB password").
  • Identity providers (upstream SSO) — Keycloak, Logto, Okta, Azure AD, Google Workspace. Teleport consumes SAML/OIDC from any of these and converts the claim set into role bindings.
  • Cert automation — cert-manager automates ACME for web-facing TLS; Teleport runs its own CA for backend access. The two coexist — cert-manager handles teleport.example.com:443's public LE cert; Teleport's CA handles SSH/DB/K8s client certs behind it.
  • Mesh VPNs (different layer) — Tailscale, NetBird, Nebula build L3 overlays; Teleport works at L7+protocol-aware level. They're complementary — Tailscale can carry a Teleport agent's reverse tunnel.
  • OSS edition vs enterprise — Community Edition is binary-licensed under modified Apache-2.0; Enterprise/Cloud add FedRAMP-compliant builds, Device Trust, Hardware Key support, Access Requests workflow, Okta integration, and the Identity Governance modules.

Common gotchas

  • Port 443 is mandatory if you want ALPN multiplexing. The default proxy_service.web_listen_addr: 0.0.0.0:443 is what makes tsh work without specifying ports. If you split ports (3023 for SSH, 3080 for HTTPS) — supported via version: v1 config — old tsh clients keep working, but new proxy-to-proxy features (multiplexed DB protocols) require ALPN, which requires 443. Don't put Teleport behind a Layer-7 ALB unless it speaks ALPN passthrough; an L7 ALB that terminates TLS will break everything but plain HTTPS.
  • The proxy_service.public_addr MUST match the cert SAN exactly. A trailing port (teleport.example.com:443) in public_addr vs a SAN of just teleport.example.com causes tsh login failures like "certificate is valid for X, not X:443". Set both consistently or omit the port from public_addr when 443 is the standard port.
  • tctl from a remote host needs an admin identity file. tctl users add on a non-auth host fails with "Unable to connect to the auth server" because tctl looks for the auth's local socket first. Use tctl --identity=admin.pem -t auth.example.com:3025 ... or run admin commands over tsh ssh auth-host -- tctl ....
  • Database access requires the database to trust Teleport's CA. For PostgreSQL: ssl: on, ssl_ca_file: /etc/teleport/teleport-db-ca.crt. For RDS/Aurora: set the cluster's CA bundle via parameter group, then tctl auth sign --format=db --host=rds-cluster.amazonaws.com --out=/etc/db/server.pem. Skipping this leaves you debugging "FATAL: certificate verify failed" without a clear pointer.
  • Cluster name is permanent. auth_service.cluster_name: example.com is baked into the CA at first start and the CA cert's CN includes it. Changing cluster_name later requires CA rotation (tctl auth rotate) AND a re-enroll of every agent. Pick something durable on day one — typically <company>.<env> like acme-prod or acme.com.
  • Session recordings stop at tsh ssh -- bash -i unless you also configure session_recording: node (record on the agent, the modern default) or proxy-sync (deprecated). Default depends on Teleport version; explicit auth_service.session_recording: node is safest.
  • AGPL applies to anything that modifies the Teleport server. Just deploying the binary and using it via tsh/tctl doesn't trigger AGPL distribution requirements. Building a SaaS that exposes a modified Teleport over the network does. The /api module is Apache-2.0 so you can build clients/integrations freely.
  • tsh login --proxy=... writes to ~/.tsh/ — on shared dev boxes this can leak certs between users. Use tsh login --user=alice --proxy=... with per-user home dirs, or set TELEPORT_HOME per session to a transient directory.
  • MachineID (tbot) certs default to 60-minute TTL — if your CI job takes longer, the cert can expire mid-job. Tune --certificate-ttl (capped by role max_session_ttl) or let tbot run as a daemon alongside the job that re-fetches before expiry.
