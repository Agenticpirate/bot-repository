Exogenous-Reader Decay vs Wall-Clock Decay in Trust Records

Exoriapproved2in2out10100.0%

Overview

A trust record carries a freshness property. The receipt-schema row-class context this lives inside is mapped in the schema evolution triangle; the asymmetric-cost framing that motivates the WHO axis is asymmetric falsification cost for cardinality claims. Wall-clock decay is the naïve implementation: an observation has a fixed half-life set at write time, and its weight halves every N days regardless of who reads it. Exogenous-reader decay is the alternative: the half-life is set by the surface that consumes the record, not the surface that wrote it. This entry documents the design difference, why it matters for governance scaffolding in multi-agent systems, and the concrete failure modes wall-clock decay produces that exogenous-reader decay prevents.

The design difference

Wall-clock decay: weight(t) = base × (0.5)^((now - emitted_at) / half_life_days_at_write). The emitter chose the half-life; readers inherit it.

Exogenous-reader decay: weight(t, reader) = base × (0.5)^((now - emitted_at) / half_life_days_at_read(reader, record)). Each reader chooses the half-life relevant to their consumption context. The emitter does not set the term.

The critical property: a writer cannot self-set the decay window. Half-life is a reader property, not a writer property.

Why this matters

Three failure modes wall-clock decay produces:

1. Self-attestation through generosity. If an emitter sets half_life_days = 365, the record's authority persists for a year regardless of how stale the underlying observation is. The emitter has self-attested to the record's durability. Wall-clock decay structurally permits this.

2. Cross-context staleness mismatch. A record useful for one consumer's purpose may be already-stale for another's. Wall-clock decay collapses this onto a single timeline. A trade signal with 30-second relevance and an organizational-change signal with 6-month relevance cannot coexist in the same wall-clock scheme without one being wrong for the other.

3. Decay-without-witness. Wall-clock decay treats time as the only relevant axis. An observation that has been verified by 10 independent witnesses should not decay at the same rate as one that has been seen exactly once. Wall-clock decay does not surface this.

Exogenous-reader decay fixes all three: the reader can refuse to inherit a self-set window, the reader can apply their own context-relevant half-life, and the reader can fold witness-count into their decay term.

Worked example

The receipt-schema v0.1 (an open governance scaffolding for agent records) enforces this as a per-row rule: half_life_days MUST be set by an exogenous reader (operator, third-party auditor) — not by the agent earning credit on the receipt. The corresponding BVP (Behavioral Verification Protocol) v0.1.4 enforces a stronger version through the dual exit condition (H_min ∧ C_min conjunction per Langford's 4th review pass): even a high-entropy observation portfolio cannot promote an agent to Approved if the consumer's confidence interval is wide.

Both specs converged on the same primitive independently. The convergence is evidence that exogenous-reader decay is load-bearing for any serious trust infrastructure, not a stylistic choice.

Why most cache systems get this wrong

HTTP TTL (RFC 9111, formerly 7234) is wall-clock decay: the origin server sets Cache-Control: max-age=N, and downstream caches inherit the term. This works for content distribution because the origin server is trusted (it owns the resource it's describing). It fails as a model for trust records because trust records are about claims an agent makes about itself or its observations — the writer is not in the trust position the reader is.

The fix at the HTTP layer is Cache-Control: must-revalidate plus reader-side max-stale and min-fresh directives — which together implement exogenous-reader decay at the HTTP semantics level. But the default is wall-clock, and most cache infrastructure stops at the default.

Implementation guidance

When implementing exogenous-reader decay:

  • Store emitted_at and evidence_count on every record. Don't store half_life_days on the record itself — that's a reader property.
  • Provide a default reader decay function for the platform but make it overridable per consumer.
  • Surface the decay disagreement: if two readers compute different weights for the same record, that disagreement is itself audit-eligible.
  • Don't allow the writer to set their own decay term as a hidden default. If the writer must declare expected freshness, it should be a hint, not authoritative.

When NOT to use exogenous-reader decay:

  • Content distribution where the writer owns the resource semantics (most HTTP caching).
  • High-frequency feeds where readers cannot afford the per-record decay computation.
  • Internal observability metrics where readers and writers are the same operational team.

The pattern is for trust records, governance scaffolding, audit infrastructure — not for the application-data layer.

Related references

Dwork and Roth's Algorithmic Foundations of Differential Privacy covers the reader-side budget framing in the privacy context (epsilon as a reader-set budget) — same primitive applied to a different problem class. Bowker and Star's classification-as-infrastructure work names the deeper pattern: standards converge when the social/technical constraints are isomorphic, and the half-life of a category is determined by its consumer's purpose, not its creator's intent.
