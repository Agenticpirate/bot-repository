Redis Persistence: RDB, AOF, Multi-Part AOF, and Hybrid Mode

Overview

Redis offers two persistence mechanisms — RDB (point-in-time snapshots) and AOF (append-only command log) — that can run together, independently, or be disabled for pure cache workloads. Since Redis 7.0 the AOF is no longer a single file: it is a directory containing a base snapshot, one or more incremental logs, and a manifest. Getting the trade-offs right matters because misconfigured persistence either silently loses data or silently fills the disk.

Related: see Redis data types for what actually ends up in dump.rdb, Valkey for the OSS fork that inherits this persistence model, and caching strategies for when to skip persistence entirely.

RDB — point-in-time snapshots

RDB is a compact binary dump of the keyspace. On BGSAVE (or a matching save rule), Redis fork(2)s a child that writes the snapshot using copy-on-write; the parent keeps serving traffic. Only the child touches the disk.

Key config (Redis 8.0 redis.conf defaults):

DirectiveDefaultMeaning

save3600 1 + 300 100 + 60 10000OR-combined triggers: one write in 1h, 100 in 5m, or 10k in 1m triggers BGSAVE
dbfilenamedump.rdbSnapshot filename
dir./Working directory for RDB and AOF
rdbcompressionyesLZF-compress string values in the dump
rdbchecksumyesCRC64 footer; off = 10 bytes saved, no integrity check
stop-writes-on-bgsave-erroryesReject writes if the last BGSAVE failed (avoids silent data loss)
rdb-del-sync-filesnoDelete temp RDB files used for diskless replication

Disable snapshotting entirely with an empty string: save "".

Commands:

CommandEffect

BGSAVEFork + async snapshot; returns Background saving started. Errors if another BGSAVE or AOF rewrite is running
BGSAVE SCHEDULESame, but queues behind an in-progress AOF rewrite instead of failing (since Redis 3.2.2)
SAVESynchronous — blocks all clients until the dump is on disk. Production use is a footgun
LASTSAVEUnix timestamp of the last successful save — the way to verify BGSAVE succeeded
DEBUG RELOADSave + flush + reload; useful for validating that the RDB round-trips

Strengths: very compact file, fast restart for large datasets, trivial to back up (the file is immutable once written — the rename is atomic).

Weakness: between snapshots you lose whatever was written. A save 3600 1 default means a crash right before the hourly trigger loses an hour of writes.

AOF — append-only file

The AOF logs every write command in the Redis serialization protocol (RESP) format. On restart Redis replays the log to rebuild state.

Key config:

DirectiveDefaultMeaning

appendonlynoMaster switch. Must be yes for AOF
appendfilename"appendonly.aof"Base name; individual files live inside appenddirname
appenddirname"appendonlydir"Directory holding base/incr/manifest (Redis 7.0+)
appendfsynceverysecalways / everysec / no — durability vs throughput
no-appendfsync-on-rewritenoIf yes, skip fsync during BGREWRITEAOF to reduce latency (accepts risk)
auto-aof-rewrite-percentage100Trigger rewrite when AOF grew ≥100% over the last rewrite size
auto-aof-rewrite-min-size64mbBelow this, never auto-rewrite
aof-load-truncatedyesOn a partial tail (common after kill -9), load what's valid and warn
aof-use-rdb-preambleyesWrite the base file in RDB format, appended with AOF commands (hybrid)
aof-timestamp-enablednoEmbed #TS:<unix> markers for point-in-time truncation

fsync policies — the only knob that matters for durability

PolicyWorst-case lossThroughputNotes

always1 commandLowestfsync per write. Only for audit/financial workloads
everysec~1 secondHighDefault. Background thread fsyncs once per second
noOS page-cache flush interval (~30s on Linux)HighestDisk flush is entirely up to the kernel

everysec is the pragmatic default; always serializes Redis behind disk latency and makes a single slow fsync a full stop-the-world.

BGREWRITEAOF

Over time the AOF accumulates redundant commands (SET k v1, SET k v2, DEL k, …). BGREWRITEAOF (or automatic rewrite, triggered by auto-aof-rewrite-*) forks a child that reads the current in-memory state and writes the minimal command sequence to reproduce it. The parent keeps appending new writes to a fresh incremental file during the rewrite.

Multi-Part AOF (Redis 7.0+)

Before 7.0 the AOF was a single file and the rewrite used a double-write buffer: the parent piped new commands to the child so they could be merged at the end. That buffer could balloon under write pressure. Redis 7.0 replaced this with a directory of files coordinated by a manifest, eliminating the double-write entirely.

Directory layout (inside appenddirname):

appendonlydir/
├── appendonly.aof.1.base.rdb       # BASE — RDB or AOF snapshot, at most one
├── appendonly.aof.2.incr.aof       # INCR — appended live. Multiple allowed
├── appendonly.aof.3.incr.aof
└── appendonly.aof.manifest         # MANIFEST — authoritative file list + seq

File roles:

  • BASE — a full snapshot created by the most recent rewrite. When aof-use-rdb-preamble yes (default), this is literally RDB on disk.
  • INCR — incremental command log. A new INCR is opened at each rewrite so the child never has to consume the parent's buffer.
  • HISTORY — old BASE/INCR files from before the last rewrite, kept transiently and auto-deleted by Redis (not stored in the manifest as active).
  • Manifest — the only authoritative record of which files compose the current AOF. Back it up together with the file set.

On restart Redis parses the manifest, loads the base, then replays each incremental file in sequence.

Hybrid mode (default since 7.0)

With aof-use-rdb-preamble yes, the BASE file is written in RDB format and the INCRs are AOF. Restarts parse the compact RDB first (fast) and then replay only the AOF tail since the last rewrite (complete). You get RDB's load speed and AOF's durability with no extra configuration — this is the recommended setup for most workloads.

Restart precedence: if both AOF and RDB are enabled, Redis loads the AOF (it is the more complete record). dump.rdb is ignored at startup when appendonly yes.

Choosing a strategy

WorkloadConfigRationale

Pure cache (loss OK)save "" + appendonly noZero disk I/O. Use with eviction policy (caching strategies)
General app stateDefault RDB + appendonly yes + everysec~1s worst-case loss, fast restart via RDB preamble
Financial / auditappendonly yes + appendfsync alwaysPer-command durability. Expect a throughput cliff
Replica-only persistencePersist on replica, save "" on primaryKeep the primary CPU-bound, not disk-bound. Durability lives on the replica

Redis 8.0 / 8.2 persistence-relevant changes

Redis 8.0 GA (2025-05-01) and 8.2 GA (2025-08-08) touched replication and AOF in ways that matter for operators:

  • Replication offset embedded in AOF (8.0-M04, PR #13773) — during recovery, compare AOF replication offsets to pick the most up-to-date file across nodes.
  • New replication mechanism (8.0-M03, PR #13732) — more robust partial resync behavior; replica-full-sync-buffer-limit added to bound replica-side accumulation during full sync.
  • RDB channel replication fix (8.0-RC1, PR #13895) — replicas now transition to online only after BGSAVE completes, fixing a window where the replica served stale reads.
  • CVE-2025-27151 (fixed in 8.0.2) — redis-check-aof stack overflow / potential RCE on malicious AOF input. Upgrade the tool before using it on untrusted files.
  • I/O threads (io-threads, 8.0+) — parallelize network I/O; does not change fsync semantics. 8.2 made arg/rewrite-object memory release run on I/O threads too.

Redis 8 also folded RediSearch, RedisJSON, RedisTimeSeries, and RedisBloom into the core distribution — but those modules add nothing to the persistence path.

Backups

RDB: copy dump.rdb while the server runs. The file is immutable between BGSAVE calls and the final rename is atomic, so a plain cp is safe.

AOF (7.0+): the file set must be copied atomically relative to the manifest. Safe procedure:

# 1. Disable auto-rewrite so files don't shift under you
redis-cli CONFIG SET auto-aof-rewrite-percentage 0

# 2. Confirm no rewrite is in flight
redis-cli INFO persistence | grep aof_rewrite_in_progress   # want 0

# 3. Snapshot the whole directory (hard links are fine on the same FS)
cp -r /var/lib/redis/appendonlydir /backup/appendonlydir.$(date -u +%Y%m%dT%H%M%SZ)

# 4. Re-enable auto-rewrite
redis-cli CONFIG SET auto-aof-rewrite-percentage 100

Copying only the .aof files without the manifest produces an unusable backup on 7.0+.

Switching RDB → AOF on a running server

redis-cli CONFIG SET appendonly yes
# Wait for the first rewrite to complete:
redis-cli INFO persistence | grep -E 'aof_rewrite_in_progress|aof_last_bgrewrite_status'
# Persist the change to redis.conf so it survives restart:
redis-cli CONFIG REWRITE

Skipping CONFIG REWRITE is the most common footgun — the server silently reverts to RDB-only at next restart.

Common Gotchas

  • SAVE blocks every client. Never run it in production; use BGSAVE. The synchronous SAVE exists for disaster recovery scripts where clients are already disconnected.
  • stop-writes-on-bgsave-error yes fails writes loudly when the disk is full or perms are wrong. The error message mentions MISCONF. Turning this off to "fix the error" trades a loud failure for silent data loss — fix the underlying disk/perms instead.
  • Copy-on-write memory spike. A BGSAVE or BGREWRITEAOF can briefly double RSS if the write rate is high enough that most pages get dirtied. Size the host with 2× the working set as headroom, or use a replica for persistence.
  • everysec is "up to 2 seconds" in practice. The fsync runs in a background thread; if the previous fsync is still running when the next tick fires, Redis waits. Measure with latency history fsync-main.
  • appendfsync always does not mean "per write". It fsyncs when the event loop flushes the write queue. Pipelined writes in the same event-loop iteration share one fsync — durable, but not per-command.
  • no-appendfsync-on-rewrite yes is a latency knob that trades durability. During a rewrite, Redis skips fsync on the main AOF — a crash in that window loses all writes since the last fsync. Only enable if fsync-induced stalls are documented in your latency graphs.
  • Don't back up .aof files without the manifest (7.0+). The manifest is the index; restoring without it — or with a stale one — loads an incomplete dataset and Redis will not warn you, because each individual file is internally valid.
  • aof-load-truncated yes hides kill -9 data loss. After an unclean shutdown Redis loads what's valid and logs a warning. Parse redis.log for AOF loaded anyway in monitoring — don't assume clean startup means no loss.
  • aof-timestamp-enabled is opt-in. Without it, point-in-time recovery is impossible — AOF records what happened, not when. Managed services like Alibaba Tair rely on this flag being set to offer PITR.
  • Disk-full during RDB write leaves a temp-*.rdb file. Redis writes to a temp file and atomically renames on success; a partial temp file is harmless but will fill the disk if monitoring misses it.
  • debug reload triggers a BGSAVE + flush + reload and is the only way to confirm the on-disk RDB can actually rebuild the running state. Run it on a staging replica before trusting a new config.
  • Replica persistence is independent of the primary. A primary with save "" and appendonly no is legal; persistence lives on the replica. On failover, the new primary's AOF/RDB is what survives — verify the replica's persistence config, not just the primary's.
  • redis-check-aof before Redis 8.0.2 has CVE-2025-27151 (stack overflow / RCE on a crafted AOF). Never run older versions against AOF files from untrusted sources.
