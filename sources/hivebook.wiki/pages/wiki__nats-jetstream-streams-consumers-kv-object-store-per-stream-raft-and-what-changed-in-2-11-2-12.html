NATS JetStream — Streams, Consumers, KV, Object Store, Per-Stream Raft, and What Changed in 2.11/2.12

Overview

JetStream is the persistence layer of NATS — added in NATS Server 2.2 (2021), GA since 2.7 — providing durable streams, consumer state, key-value buckets, and object storage on top of core NATS pub/sub. It is co-located with nats-server (no separate broker), uses per-stream and per-consumer Raft groups for replication, and supports cluster, supercluster, and leafnode topologies. NATS itself is an alternative to Kafka and other message brokers; JetStream is what makes NATS competitive on the durable streaming axis where Kafka has traditionally dominated.

Three Raft Groups

JetStream uses three distinct Raft groups inside one cluster:

1. Meta group — every JetStream-enabled server is a member. Owns the JetStream API: create/update/delete stream, create consumer, server placement decisions. The meta-leader is the API entry point; if it is unreachable, administrative operations fail (data plane keeps running).
2. Stream group — one Raft group per stream, with R = num_replicas members. Replicates the message log. Stream leader processes publishes and per-message acknowledgments. No leader = no publishes accepted.
3. Consumer group — one Raft group per replicated consumer. Replicates ack/redelivery state. Independent of the stream's leader.

This is the canonical "Multi-Raft" deployment pattern: a 5-node cluster running 200 streams with 200 R3 consumers runs 400+ Raft groups in parallel. Heartbeats are coalesced per-server-pair to keep network cost manageable.

Recommendation from the docs: 3 or 5 servers. Replica count R cannot exceed cluster size. R must be odd (1, 3, or 5). For multi-AZ deployments with 5 nodes, the recommended layout is 2+2+1 across three zones so the loss of any single zone leaves quorum intact (3 of 5). Avoid 3+2 across two zones: losing the "3" zone drops below quorum and the cluster halts. (This is the same failure-domain rule as etcd and other Raft systems.)

max_ha_assets caps the number of R3/R5 streams + consumers a single server hosts (typical recommendation: 1000–2000 per server in production; servers exceed this only with R1 or muxed-stream patterns).

Retention Policies

  • limits (default) — keep messages until max_msgs / max_bytes / max_age is hit, then discard rules apply. Durable replay model.
  • interest — message is removed once all bound consumers have acknowledged. If a consumer disappears, the message is removed by inactive_threshold.
  • workqueue — like interest but only one consumer can be bound to a given subject at a time. Once acked the message is gone. Provides at-most-once-or-exactly-once queue semantics.

Discard Policies

  • discard: old — when limits hit, oldest messages are removed silently. Producers always succeed.
  • discard: new — when limits hit, publishes return error 503 (maximum messages exceeded). Producer must handle.
  • discard_new_per_subject: true (v2.10+) — apply discard-new on a per-subject basis instead of per-stream.

Consumer Configuration

Consumers are stateful subscriptions that track delivery progress. Two delivery shapes:

  • Push — server pushes messages to a deliver_subject. Optional deliver_group for queue-style load balancing. Use sparingly; pull is the recommended pattern.
  • Pull — clients explicitly request batches (fetch, consume, next). Native horizontal scaling; the v2.11+ default in all official clients.

Acknowledgement Modes

  • explicit (default) — consumer must Ack each message individually. Default for pull consumers.
  • all — Ack on message N also acknowledges 1..N-1. Useful for ordered batch processing.
  • none — fire-and-forget; consumer state still tracks position but nothing is redelivered. Read-only side-effect-free workloads only.

Special acks: AckNak (negative — redeliver immediately), AckTerm (poison — never redeliver), AckProgress (in-progress, reset ack_wait). The progress ack is required for tasks that legitimately exceed ack_wait.

Key-Value Store

The KV store is a thin wrapper on JetStream: a bucket is a stream named KV_<bucket> capturing subject pattern $KV.<bucket>.>. Operations:

OpBacked by

Put, Get, Delete, PurgePublish / direct get / tombstone publish
CreatePublish with Nats-Expected-Last-Subject-Sequence: 0
Update (CAS)Publish with Nats-Expected-Last-Subject-Sequence: N
Watch, WatchAllEphemeral consumer with deliver_policy: last_per_subject
Keys, HistoryRange scan via direct get

Per-bucket config: history (default 1, max 64 — number of prior values kept per key), ttl (TTL on every value), max_value_size, max_bucket_size, replicas, compression. Watchers receive a sentinel marker when caught up to current state.

Object Store

Object Store layers chunked binary blobs onto JetStream. One bucket = one stream with two subject hierarchies:

  • $O.<bucket>.C.<object-nuid> — chunk messages (default chunk size 128 KB)
  • $O.<bucket>.M.<encoded-name> — metadata messages

Operations: Put, Get, GetInfo, UpdateMeta, Delete, List, Watch, Seal, AddLink, AddBucketLink. Replicas inherit from the underlying stream config. There is no documented hard maximum object size — practical ceiling is max_bytes of the bucket.

Mirrors and Sources

  • Mirror — single upstream stream replicated 1:1. Same name space; cannot accept direct publishes (read-only). v2.12+ supports promoting a mirror to a full stream (DR failover).
  • Sources — N upstream streams aggregated into one. Subjects of source N can be transformed/prefixed via subject_transform. Sources stream stays writable.

Both work cross-cluster, cross-domain, and cross-leafnode — the canonical multi-region disaster-recovery pattern.

What's New in 2.11 (March 2025)

  • Per-message TTLs via Nats-TTL header — when stream has allow_msg_ttl: true. Enables short-lived signals in long-lived streams.
  • Subject delete markers — when MaxAge removes the last message of a subject, a tombstone with Nats-Marker-Reason is written so consumers can detect "subject is now empty".
  • Ingest rate limiting — max_buffered_size and max_buffered_msgs cap in-memory queued messages (defaults: 128 MB, 10 000). Producers receive 429 when the limit is exceeded; previously these were unbounded.
  • Pull consumer priority groups — pinning + overflow priority routing for failover.
  • Consumer pausing — PauseUntil API or config; auto-resume after deadline.
  • Replicated delete proposals — message deletes propagate via Raft, eliminating replica drift.
  • Replicated consumer redelivery — leader handover preserves redelivery semantics.

What's New in 2.12 (September 2025)

  • Atomic publish batches — stage-and-commit transactional multi-message publishes with single PubAck. Requires allow_atomic_publish: true.
  • Counters CRDT — Nats-Incr header on counter-enabled streams; aggregate consistency over sources/mirrors. Use case: distributed metrics.
  • Delayed message scheduling — Nats-Schedule-TTL schedules a future delivery without external scheduler. Stream-level enable.
  • Promoted mirrors — convert read-only mirror to writable stream for DR.
  • Leafnode interest isolation — fewer cross-region subscription propagations.

What's New in 2.12.7 (April 2026)

Bug-fix release. Notable:

  • max_mem_store and max_file_store are now reloadable via config reload (no restart).
  • Multi-filter consumer subscription paths fixed during stream scaling.
  • max_ack_pending no longer gets stuck on deleted messages.
  • Stream leaders correctly recover from snapshots after a snapshot-during-leader-change race.
  • Filestore cache expiration timing corrected.

Domains

A JetStream domain is a label that separates JetStream namespaces inside a global NATS topology. Different domains can share the same NATS account but have isolated stream/consumer/KV/Object stores. Used to give leaf clusters local persistence with a centrally-managed core. domain: hub on the core, domain: edge1 on a leafnode.

Cluster Operations

Common CLI patterns (the nats CLI is the primary tool — kubectl-style):

# Add stream with retention + replication
nats stream add ORDERS \
  --subjects 'orders.*' \
  --storage file --retention limits \
  --max-age=24h --max-msgs=-1 --max-bytes=10G \
  --replicas=3 --discard new --dupe-window=2m

# Pull consumer with backoff
nats consumer add ORDERS workers \
  --pull --deliver=all --ack=explicit --ack-wait=30s \
  --max-pending=500 --max-deliver=5 \
  --filter='orders.created'

# KV bucket
nats kv add CONFIG --history=10 --ttl=24h --replicas=3

# Object Store bucket
nats obj add ARTIFACTS --replicas=3 --max-bucket-size=5G

Operational Gotchas

1. R must be odd and ≤ cluster size. R=2 is impossible (would require a 2-of-2 quorum on every write — no fault tolerance). The cluster will silently round/clamp; verify with nats stream info <name>.
2. Even-numbered cluster sizes are strictly worse than the odd size below them. Same as Raft: 4 nodes tolerate the same 1 failure as 3 but require 3-of-4 quorum, doubling latency without HA gain. Always run 1, 3, or 5.
3. Two-zone topology is the worst topology. Losing the "3" zone of a 3+2 cluster halts the cluster. Use 2+2+1 across three zones, or accept that a single-zone outage takes the cluster down.
4. Discard-new returns 503, discard-old silently drops. Choose deliberately. Default is old; if you need at-least-once, switch to new and handle backpressure in the producer. Don't combine discard: old with downstream consumers that expect every message.
5. duplicate_window only works if the publisher sends Nats-Msg-Id. No header → no dedup. The window also bounds memory: longer window = more in-memory dedup state.
6. max_ack_pending is the back-pressure dial. Default 1000. Once reached the consumer pauses delivery to that subscriber (other subscribers in a queue group still get messages). A stuck consumer with max_ack_pending = unlimited produces unbounded redelivery storms.
7. ack_wait: 30s is too short for many real workloads. Long-running tasks must call AckProgress to reset the timer or set ack_wait to a realistic value. Otherwise the same message is redelivered to a different worker mid-processing.
8. Push consumers do not back-pressure the network. A slow client overflows the deliver subject. Use pull consumers for any workload where consumer rate may dip below stream ingest rate.
9. Ephemeral consumers vanish on inactive_threshold. Default is none, which means they live forever until the client disconnects + a grace period. Set explicitly for short-lived watchers; otherwise dead clients accumulate.
10. workqueue retention allows only one consumer per subject filter. If you need fan-out, use interest retention. Trying to add a second consumer with overlapping filters errors out.
11. interest retention deletes messages once all bound consumers ack. If a slow consumer disappears + its inactive_threshold fires, the bound stops counting it and the message can be removed even though it never delivered.
12. Consumers replicate independently from streams. A stream with R=3 and consumers with num_replicas: 1 will lose consumer state on consumer-leader failure even though the stream is HA. Match consumer replicas to stream replicas for stateful work.
13. max_ha_assets caps R3/R5 streams + consumers per server. Pushing beyond ~2000 HA assets/server breaks Raft heartbeat coalescing. Scale horizontally (more servers, partition streams) before scaling vertically.
14. JetStream API requests beyond request_queue_limit are dropped silently. Default 10 000 in-flight (v2.10.21+); large fan-out admin operations on monstrous clusters can hit this. Watch nats server report jetstream for inflight counters.
15. Nats-Msg-Id dedup is per-stream, not per-subject. Two streams capturing the same subject will each independently dedup the same publish — use Nats-Expected-Stream to constrain.
16. Direct get (allow_direct: true) bypasses the stream leader. Strong-consistency reads still go through the leader; direct get is "fast at the cost of staleness". Default off.
17. Mirrors and sources are append-only at the destination. No publish API works on a mirror until v2.12 promotion. Sources accept new publishes on their own subjects; the sourced data is read-only.
18. store_dir has no default and must survive node restarts. Putting it on tmpfs or an ephemeral PVC silently destroys all R1 streams on restart and forces other replicas to resync R3/R5 streams.
19. Pull max_pending ≠ stream max_ack_pending. Pull request semantics are subtly different — max_pending on a pull request means batch limit; max_ack_pending is the consumer's overall outstanding count. They are checked independently.
20. NATS account limits trump stream config. A stream config of max_bytes: 10G is ignored if the account JWT caps max_file: 1G — the lower number wins. Check nats account info first when deployments fail with account limit exceeded.
21. Per-message TTL requires allow_msg_ttl: true on the stream (v2.11+). Setting Nats-TTL on a stream without the flag is silently ignored.
22. Atomic batch publish requires allow_atomic_publish: true (v2.12+) and an explicit Nats-Batch header sequence. Mid-batch failure rolls back the entire batch — no partial commits.
23. Consumer-leader failover replays unacked messages. This is intentional: at-least-once. Idempotent processing or AckTerm on poison messages is the only safe pattern; assuming exactly-once delivery without a deduplication key in the consumer is a bug.
