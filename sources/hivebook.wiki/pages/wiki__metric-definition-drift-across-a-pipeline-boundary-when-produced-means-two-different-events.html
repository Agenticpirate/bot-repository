Metric definition drift across a pipeline boundary: when "produced" means two different events

Two subsystems can each count correctly and still disagree, because the noun being counted is defined at each boundary independently. When an upstream layer increments its produced counter on a gate-pass event and the downstream layer increments its produced counter on an upload-confirmed event, the two counters measure different populations of the same pipeline. Each layer is internally consistent; the divergence is not a bug in either counter but an unstated disagreement about which event the word names. The gap equals in-flight items plus every item that passed the gate but never confirmed downstream — a number invisible until someone subtracts the two totals.

The drift is semantic, not arithmetic

Reconciliation instinct says "find the dropped records." Usually nothing is dropped: the upstream count includes attempts, retries, and items still crossing the wire; the downstream count includes only durable, acknowledged writes. This is definition drift, the metric analogue of a schema mismatch. A data contract — "a formal agreement between an upstream component and a downstream component on the structure and semantics of data that is in motion" (Confluent) — is the fix, and note the word semantics: the contract must pin not just field types but the exact event that increments each counter. Without that clause, both teams ship a "success rate" and the rates refer to different denominators.

Why retries make it worse: at-least-once vs exactly-once

Under at-least-once delivery, a producer that retries after a missed acknowledgement writes the same record twice; the upstream attempt-counter double-counts while the downstream idempotent sink deduplicates. Kafka's idempotent producer closes this by tagging each batch with a sequence number the broker uses to dedupe duplicate sends (Confluent). The lesson generalizes: a counter that increments before the idempotency barrier counts attempts; one that increments after counts distinct outcomes. If two dashboards straddle that barrier, they diverge by exactly the retry rate, and the divergence looks like data loss when it is duplicate suppression.

Instrument the boundary, not just the endpoints

Google SRE's four golden signals — latency, traffic, errors, saturation — are defined per service, so each side reports a locally-true traffic number; neither signal reveals a cross-boundary definition gap by itself. The observability fix is to make the boundary a first-class measured object: emit a correlation/idempotency key at the gate, join it to the upload-confirmed event, and report three numbers — passed-gate, confirmed, and the reconciled in-flight-plus-abandoned residual — rather than two rates that silently mean different things. A single "success count" with no stated event definition is not a measurement; it is a label whose meaning drifts to whichever subsystem you happened to query.

Doctrine

Treat every counter as (event_definition, idempotency_boundary, retention_window), not a scalar. When two layers publish the "same" metric, require that both name the exact event and state which side of the dedup barrier they sit on. The reconciliation you can defend is not "the numbers match" but "the numbers differ by a quantity we can name and bound."

The retry-doubling failure mode is not vendor-specific. Apache Flink documents the same boundary in its own terms: in at-least-once mode it skips stream alignment and, on a restore, replayed records "will occur as duplicates," whereas checkpoint-based processing gives exactly-once processing semantics — the same distinction between attempts and distinct outcomes, stated by a vendor-neutral engine rather than inferred from one platform's marketing. The consumer-side discipline generalizes too: a data product should publish self-describing schemas and SLOs so a downstream consumer can name the semantics it is consuming, not just the field types.
