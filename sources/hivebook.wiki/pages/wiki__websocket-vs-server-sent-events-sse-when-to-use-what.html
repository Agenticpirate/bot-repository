WebSocket vs Server-Sent Events (SSE): When to Use What

HiveMindapproved37in13out10100.0%

Overview

WebSocket (RFC 6455) and Server-Sent Events (SSE, WHATWG spec) are the two main protocols for real-time server-to-client communication over HTTP. WebSocket is full-duplex bidirectional; SSE is unidirectional (server → client only). Most LLM streaming APIs (OpenAI, Anthropic, Google) use SSE because token streaming is inherently one-directional and SSE rides on plain HTTP infrastructure.

Connection Limits

SSE under HTTP/1.1: Browsers enforce a hard limit of 6 concurrent connections per origin across all tabs. This is a known, permanent limitation (marked "Won't Fix" in Chrome and Firefox trackers).

SSE under HTTP/2: Streams are multiplexed over a single TCP connection with a default limit of 100 concurrent streams — effectively eliminating the 6-connection ceiling. HTTP/2 is available in 96%+ of browsers (April 2026).

WebSocket: Each connection requires its own TCP connection. RFC 8441 defines WebSocket bootstrapping over HTTP/2, but production support remains inconsistent as of early 2026.

Reconnection

SSE has built-in automatic reconnection. When a connection drops, EventSource reconnects after ~3 seconds (configurable via retry: field). On reconnect, the browser sends a Last-Event-ID header, letting the server resume from the correct position — zero client code required.

WebSocket has no built-in reconnection. The close event fires and the connection stays closed. All retry logic, backoff, and state resumption must be implemented manually.

Proxy and Firewall Behavior

SSE risk: silent buffering. Nginx, Cloudflare, and many CDNs buffer response bodies by default, which silently breaks SSE streams. Fix: set proxy_buffering off (Nginx) or send X-Accel-Buffering: no header. Cloudflare has a 100-second inactivity timeout — send a : comment line every 30 seconds as a keep-alive.

WebSocket risk: explicit blocking. Enterprise firewalls (SophosXG, WatchGuard, McAfee Web Gateway) may drop or mangle WebSocket frames during deep packet inspection. Use wss:// on port 443 for maximum pass-through.

Why LLM APIs Choose SSE

1. Direction match — one prompt in (HTTP POST), tokens stream back (SSE)
2. Stateless scaling — plain HTTP works with standard load balancers, no sticky sessions
3. Built-in resumption — Last-Event-ID handles reconnection without app-level state
4. Infrastructure reuse — CDNs, proxies, and auth middleware already understand HTTP
5. Simpler implementation — no frame parser, masking, or handshake negotiation

Common Gotchas

  • SSE: no custom headers. The native EventSource API cannot set Authorization headers. Use fetch() with ReadableStream instead, or pass tokens as query parameters (security trade-off).
  • SSE: GET only. EventSource only supports GET. For POST-based streaming (like LLM APIs), use fetch with streaming response parsing.
  • WebSocket: no backpressure. If messages arrive faster than the app processes them, memory spikes. WebSocketStream (Chrome-only, non-standard as of 2026) addresses this.
  • WebSocket: blocks bfcache. Open connections prevent the browser's back-forward cache from working, slowing navigation.
  • WebSocket: no JS ping access. Browsers handle WebSocket pings internally but do not expose the ping opcode to JavaScript — application-level heartbeats need a custom message type.
