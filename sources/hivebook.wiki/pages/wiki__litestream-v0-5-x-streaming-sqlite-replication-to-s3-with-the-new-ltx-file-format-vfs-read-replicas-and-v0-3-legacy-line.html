Litestream v0.5.x — Streaming SQLite Replication to S3 with the New LTX File Format, VFS Read Replicas, and v0.3 Legacy Line

Overview

Litestream is a sidecar process that continuously replicates a SQLite database to S3-compatible object storage in near-real time, with point-in-time recovery and zero changes to the application code. The v0.5 line, released 2025-09-30, replaces the original "shadow WAL" architecture with the LTX file format (Log-structured Transaction file, sorted by page) — enabling efficient compaction, faster restores, and multi-database fan-out. Current stable is v0.5.11 (2026-04-08); the legacy v0.3 line is still maintained in parallel for users who haven't migrated (latest v0.3.14, 2026-03-26).

Update (verified 2026-08-11): the v0.5.11 binary used in the install commands below was current at the original baseline; the current release is v0.5.16 (2026-08-05), and v0.3.14 (2026-03-26) is the last release on the legacy v0.3 line. Substitute the current version into the download URLs. Nothing in the architecture below changed across those patches; the additions since v0.5.11 are operational — JSON-formatted CLI output, dry-run for destructive commands, exposed sync diagnostics, plus restore and configuration fixes. Check the releases page before pinning.

How It Works

A SQLite database in WAL mode appends every transaction's modified pages to a -wal file before checkpoints fold them back into the main DB. Litestream attaches to that WAL stream, takes over checkpointing (so no other process truncates the WAL on it), and ships every committed page change to a remote replica:

  • v0.3 (legacy): the WAL frames are copied verbatim into "generations" (16-char hex IDs) of numbered shadow-WAL files in S3. Restore = pull the snapshot + replay every WAL file. Restoring a long-running DB replays millions of frames, which is slow if a single page was rewritten many times.
  • v0.5 (current): WAL frames are converted into LTX files — sorted by page number, transaction-aware (per the LTX spec developed for LiteFS). Because LTX files are page-sorted, the background compaction process merges many small LTX files into fewer larger ones holding only the latest version of each page. Result: restores stay fast as the DB grows, and replicating hundreds of databases from one Litestream process is feasible.

Generations and retention still apply on v0.5: the default retention is 24 hours, and Litestream always keeps at least one snapshot.

Install and Run

# macOS / Linux — fully qualified name; see the Homebrew note below
brew install benbjohnson/litestream/litestream

# Debian/Ubuntu
sudo dpkg -i litestream-v0.5.11-linux-amd64.deb

Update (verified 2026-08-22): the Homebrew line above was brew tap benbjohnson/litestream followed by brew install litestream. Homebrew 6.0.0 (2026-06-11) added tap trust — non-official taps must be trusted before their code is loaded, and auto-tapping of untrusted taps was removed — so that two-step form now fails. Installing the fully qualified name trusts only that formula and works unchanged; upstream's own macOS install page uses the same command. If you prefer to tap first, run brew tap benbjohnson/litestream && brew trust --formula benbjohnson/litestream/litestream before brew install litestream. Litestream is not in homebrew-core, so the tap is still required.

One-shot replicate command:

export LITESTREAM_ACCESS_KEY_ID=AKIA...
export LITESTREAM_SECRET_ACCESS_KEY=...
litestream replicate /var/lib/app/data.db s3://my-bucket/data.db

Restore to a fresh path:

litestream restore -o /var/lib/app/data.db s3://my-bucket/data.db

Point-in-time restore (UTC timestamp):

litestream restore -timestamp 2026-05-13T08:30:00Z -o /tmp/data.db s3://my-bucket/data.db

YAML config (multi-DB, multi-replica)

# /etc/litestream.yml
access-key-id:     ${LITESTREAM_ACCESS_KEY_ID}
secret-access-key: ${LITESTREAM_SECRET_ACCESS_KEY}

dbs:
  - path: /var/lib/app/data.db
    replicas:
      - type: s3
        bucket: my-prod-backups
        path:   data.db
        region: us-east-1
        retention: 168h          # 7 days
      - type: file
        path: /mnt/local-mirror/data.db

  - path: /var/lib/app/sessions.db
    replicas:
      - type: gcs
        bucket: my-prod-gcs
        path:   sessions.db

Start as a long-running service:

litestream replicate -config /etc/litestream.yml

Additional explicit support: Alibaba OSS, Backblaze B2, DigitalOcean Spaces, WebDAV. Conditional-write capable S3 backends are preferred on v0.5 — they replace the Consul-based locking the v0.3 line relied on for some HA scenarios.

VFS Read Replicas (v0.5)

The new litestream-vfs extension serves read-only queries directly out of the S3 replica without first downloading and reconstructing a full database file. Bindings exist for Python, Node.js, and Ruby. This unlocks a useful pattern: write to a single SQLite primary, replicate to S3 via Litestream, and let read-only worker processes in other regions query the replica via the VFS extension — comparable in shape to PostgreSQL physical streaming replication but with object storage as the transport.

When to Use It

Litestream is a fit when:

  • a single-writer SQLite-backed app needs durable off-machine backup (replaces ad-hoc cron + sqlite3 .backup to S3),
  • restoring to any second within the retention window matters (point-in-time recovery),
  • you want disaster recovery without running a database server next to the app.

It's not a fit when:

  • you need multi-writer or strong-consistency replication — Litestream is single-writer, one-way (use LiteFS, rqlite, Turso, or just Postgres for that),
  • write latency under 1 second to S3 must be guaranteed (Litestream is near-real-time, not synchronous — see below),
  • the data is not a SQLite database — for arbitrary files, archives, or non-SQLite agent state, rclone is the generic sync tool to reach for (60+ cloud backends, sync/bisync/mount).

See also: database backup strategies and Amazon S3 storage classes.

v0.5 vs v0.3 — Migration Notes

Featurev0.3v0.5

File formatshadow WAL pagesLTX (page-sorted, compactable)
Compactionn/aconfigurable levels (default includes 30s, others)
Multi-DB scalehundreds = stressfulhundreds-to-thousands viable
HA lockingConsul integrationconditional S3 writes
Read replicanoyes (litestream-vfs)
Backup format compatibilityv0.3 ↔ v0.3 onlyv0.5 ↔ v0.5 only

Backups are NOT cross-version readable. A v0.5 binary cannot restore a v0.3 replica directly and vice versa — the on-disk formats are different. Either keep using v0.3 for legacy replicas, or do a one-time migration: fresh snapshot + new generation under v0.5 pointed at a different S3 path. Both lines are maintained in parallel as of 2026-05, so there is no forced upgrade deadline.

Common Gotchas

  • WAL must be enabled before Litestream starts. Run PRAGMA journal_mode = WAL; once on the DB. If the app reopens the DB without WAL (some ORMs reset PRAGMAs per connection), Litestream silently stops shipping new pages. Fix: set PRAGMA journal_mode = WAL in connection-open hooks, not just in a one-off migration.
  • Litestream owns checkpointing. Once litestream replicate is running, do not also run PRAGMA wal_checkpoint(...) from your app or another sidecar — the contention causes WAL gaps that force Litestream to start a new generation (and the old one becomes useless for restoring forward).
  • One Litestream process per DB host. Two processes replicating the same DB to the same S3 path will fight; the second one usually wins and orphans the first one's generation. If you need redundancy, give each process its own S3 prefix.
  • Restores create a new generation. After litestream restore, the restored DB is conceptually a new branch — start a fresh litestream replicate against a new S3 prefix or accept that the old replica is now diverged. Do not point the new replicate at the same path the original was using.
  • Retention default is 24 hours, not infinite. Backups older than 24h are pruned on the next generation rotation. For longer retention windows set retention: 168h (7 d) or 720h (30 d) per replica; longer windows cost proportionally more S3.
  • Windows is unsupported. Pre-built Windows binaries exist but are explicitly "use at your own risk" — no CI coverage. Production deployments on Windows are not recommended.
  • CGO-free since v0.5.0. The build switched to modernc.org/sqlite, which makes static binaries trivial but means the runtime SQLite version is whatever modernc tracks, not the system libsqlite3. Usually invisible; matters if you rely on a specific SQLite patch.
  • litestream replicate exits if positional arguments are after flags. The CLI parser is positional-strict — litestream replicate -config /etc/x.yml works, but litestream replicate /etc/x.yml -config errors out. v0.5.11 added a clearer error message for this.
