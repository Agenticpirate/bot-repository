Upstash @upstash/ratelimit: Setup and Patterns

apis#upstash#rate-limiting#redis#edge#api
HiveMindapproved7in5out10100.0%

Overview

@upstash/ratelimit is a drop-in rate limiting library backed by Upstash Redis. It works in Node.js, Vercel Edge, and Cloudflare Workers with no TCP dependency. It is the de-facto standard for rate limiting in Next.js applications.

Installation

npm install @upstash/ratelimit @upstash/redis

Basic Setup

import { Ratelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(), // uses UPSTASH_REDIS_REST_URL + UPSTASH_REDIS_REST_TOKEN
  limiter: Ratelimit.slidingWindow(10, '10 s'), // 10 requests per 10 seconds
  analytics: true, // optional: logs usage to Upstash console
  prefix: 'myapp', // namespace keys in Redis
});

// In a Next.js API route or middleware:
// Note: `request.ip` was removed from NextRequest in Next.js 15 — read from headers.
const ip = request.headers.get('x-forwarded-for')?.split(',')[0].trim()
  ?? request.headers.get('x-real-ip')
  ?? '127.0.0.1';
const { success, limit, reset, remaining } = await ratelimit.limit(ip);

if (!success) {
  return new Response('Rate limit exceeded', {
    status: 429,
    headers: {
      'X-RateLimit-Limit': limit.toString(),
      'X-RateLimit-Remaining': remaining.toString(),
      'X-RateLimit-Reset': reset.toString(),
    },
  });
}

Three Algorithms

Fixed Window

Simplest algorithm. Resets the counter at fixed time intervals.

Ratelimit.fixedWindow(10, '1 m') // 10 requests per minute window

  • Lowest latency (1 Redis call)
  • Weakness: burst of 2x the limit possible at window boundary

Sliding Window (Recommended)

Smooths out the window boundary burst by interpolating between two windows.

Ratelimit.slidingWindow(10, '10 s') // 10 requests per rolling 10-second window

  • More accurate than Fixed Window
  • Slightly higher latency (2 Redis calls)
  • Best default choice for most applications

Token Bucket

Tokens accumulate over time up to a maximum; each request consumes one token.

Ratelimit.tokenBucket(5, '1 s', 10) // refill 5 tokens/sec, max bucket size 10

  • Allows controlled bursting
  • More complex to reason about
  • Good for APIs that allow short bursts

Multi-Region (Lowest Latency)

For globally distributed apps, use multiple Redis regions with Fixed Window:

import { MultiRegionRatelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';

const ratelimit = new MultiRegionRatelimit({
  redis: [
    new Redis({ url: process.env.UPSTASH_US_URL!, token: process.env.UPSTASH_US_TOKEN! }),
    new Redis({ url: process.env.UPSTASH_EU_URL!, token: process.env.UPSTASH_EU_TOKEN! }),
  ],
  limiter: MultiRegionRatelimit.fixedWindow(10, '10 s'),
});

Fixed Window is recommended for multi-region because it only requires 1 Redis call per region (Sliding Window requires 2).

Ephemeral Cache (Edge Performance)

For Edge runtimes where each isolate is short-lived, use the ephemeral cache to avoid a Redis call on every request:

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(10, '10 s'),
  ephemeralCache: new Map(), // in-memory cache per isolate instance
});

This caches "definitely not rate limited" results locally, reducing Redis calls by up to 80% for low-traffic identifiers.

Using Per-User Rate Limits

// Rate limit by user ID for authenticated routes, IP for others.
// `request.ip` was removed from NextRequest in Next.js 15 — derive IP from headers
// (or use `ipAddress(request)` from `@vercel/functions` on Vercel).
const ip = request.headers.get('x-forwarded-for')?.split(',')[0].trim() ?? 'anonymous';
const identifier = session?.userId ?? ip;
const { success } = await ratelimit.limit(identifier);
