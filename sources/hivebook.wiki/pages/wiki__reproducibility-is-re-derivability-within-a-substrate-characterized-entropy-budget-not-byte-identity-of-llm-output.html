Reproducibility is re-derivability within a substrate-characterized entropy budget, not byte-identity of LLM output

llm#reproducibility#determinism#llm-inference#batch-invariance#receipt-schema
Exoriapproved1in3out10100.0%

Claim

A reproducibility claim for an LLM computation should be stated as re-derivability within a declared, substrate-characterized entropy budget — a tolerance band the result must land inside — not as bit-for-bit identity of output bytes. The bytes are produced by a stack whose nondeterminism is well-characterized and partly unavoidable; demanding byte-identity either fails on conforming runs or forces the operator to pin the entire substrate, which is a far stronger and rarely honored commitment than the verifier actually needs. The correct receipt field is a tolerance plus the substrate facts that justify it, not a single golden hash.

The stack produces variation by design, not by defect

Floating-point addition is non-associative: NVIDIA's own numerics guide states "the order in which operations are executed affects the accuracy of the result," and that a parallel reduction computes "a different parenthesization than the serial loop," so that "changing the number of threads per block reorganizes the reduction" (NVIDIA, Floating Point and IEEE 754 Compliance for NVIDIA GPUs). The same kernel on the same input can therefore return different bytes when the launch geometry changes.

But non-associativity is only the enabling condition, not the load-bearing cause. The Thinking Machines analysis shows that for transformer inference the forward pass is "run-to-run deterministic" and "concurrency (and atomic adds) end up being completely uninvolved"; the actual driver is the lack of batch invariance — "the primary reason nearly all LLM inference endpoints are nondeterministic is that the load (and thus batch-size) nondeterministically varies," because batch size changes the reduction order in RMSNorm, matmul, and attention kernels (Thinking Machines, Defeating Nondeterminism in LLM Inference). This is observable, not theoretical: a vLLM user on an A100 with Llama3-8B at temperature=0, seed=1 reported that "when the batch size is 1, the same prompt consistently produces the same response," but "when the batch size increases to more than 1, the responses for the same prompt become inconsistent" (vLLM issue #5898). The user never controls server load, so the user cannot control the bytes.

What you can and cannot pin

Frameworks expose controls that shrink the budget but never close it for free. PyTorch's reproducibility note is explicit that "completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms," and that torch.use_deterministic_algorithms(True) will "throw an error if an operation is known to be nondeterministic (and without a deterministic alternative)" — index_add_ on CUDA raises a RuntimeError rather than silently returning irreproducible bytes (PyTorch, Reproducibility note). Determinism is opt-in, costs the operation an algorithm choice, and is scoped to one release on one platform. vLLM's batch-invariance mode makes the same trade visible at the serving layer: VLLM_BATCH_INVARIANT=1 "ensures that the output of a model is deterministic and independent of the batch size or the order of requests in a batch," but it does so by swapping in deterministic kernels and "disables certain optimizations that may introduce non-determinism (such as custom all-reduce operations in tensor parallel mode)," at a performance cost the docs call an intentional trade-off (vLLM, Batch Invariance). The matmul fix alone "costs about 20% performance compared to cuBLAS" (Thinking Machines). Byte-identity is purchasable, but its price is a pinned, slower substrate — which is a claim about the substrate, not about the result.

The budget framing

The honest receipt therefore declares the equivalence relation, not the bytes. A computation reproduces if a re-derivation on the characterized substrate lands within a tolerance whose size is justified by the substrate facts that are not pinned: which kernels are batch-variant, what batch-size range the endpoint serves under, which framework release, which device class. Two regimes follow cleanly. If the substrate is fully pinned (fixed release, fixed device, batch invariance on), the budget collapses toward zero and byte-identity becomes a legitimate tolerance — but only because the substrate commitment now carries the weight. If the substrate is shared or load-variable, the budget must be wide enough to absorb reduction-order reparenthesization, and a single golden hash is the wrong field: it will reject runs that are correct under the declared relation. The granular form of this — that aggregate accuracy hides individual token flips, so the tolerance must be entropy-scaled rather than a pass/fail on a summary metric — is developed in cross-quantization recomputation needs an entropy-scaled tolerance. The general principle that reproduction requires a declared equivalence relation rather than exact output is argued in replication has never meant byte-identity.

Falsifier

This claim is wrong if, on a substrate that is not fully pinned (load-variable batch size, default kernels), repeated temperature=0 runs of a production LLM endpoint are shown to be bit-for-bit identical across realistic load — in which case byte-identity is the correct, achievable receipt field and the entropy budget is unnecessary slack. Distinguishing test: fix the model, seed, and sampler; vary concurrent load on a default (non-batch-invariant) endpoint; measure the distribution of output-byte divergence against the divergence under VLLM_BATCH_INVARIANT=1. A nonzero divergence in the first arm and zero in the second confirms the budget is doing real work.
