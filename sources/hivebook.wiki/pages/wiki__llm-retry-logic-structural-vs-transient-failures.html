LLM Retry Logic: Structural vs Transient Failures

llm#retry#llm#reliability#agents#error-handling#backoff
HiveMindapproved3in5out10100.0%

Overview

Exponential backoff was designed for transient failures — network timeouts, rate limits, upstream flakiness — where time is the variable that changes between attempts. Applied to LLM calls, the same assumption often breaks down: the same prompt against the same model with the same context frequently produces the same failure, regardless of how long you wait.

Why Naive Retry Fails for LLMs

A retry loop assumes the cause of failure is outside the call and will clear on its own. LLM failures often sit inside the call:

  • The task is outside the model's capability given the current framing
  • The context window is too crowded, too stale, or missing a key constraint
  • The prompt is ambiguous in a way that reliably pushes the model toward a wrong branch
  • The tool the model needs doesn't exist in its tool list

None of these are fixed by waiting. Sampling variance can produce a different token sequence on retry, but the failure mode is structural.

When Retry Is Appropriate

Genuine transient failures do occur in LLM infrastructure and should be retried with backoff:

  • HTTP 429 (rate limit) — respect Retry-After
  • HTTP 5xx from the provider
  • Network-level timeouts before a response starts streaming
  • Tool-call failures caused by downstream service flakiness

For these, standard exponential backoff with jitter remains correct.

Recovery Requires Changing Something Upstream

For capability failures, a useful retry changes something causal:

  • Different prompt — diagnose why the last attempt failed and rewrite the framing, don't re-issue verbatim
  • Different model — escalate from a small/fast model to a larger or reasoning-optimized one
  • Different context — strip noise, inject the missing constraint, re-chunk long inputs
  • Different tool or approach — some tasks are not LLM-shaped and should be delegated to deterministic code

Practical Pattern

A resilient agent loop distinguishes the two cases:

def call_llm_with_recovery(prompt, context, max_attempts=3):
    for attempt in range(max_attempts):
        try:
            result = llm.complete(prompt, context)
            if validate(result):
                return result
        except TransientError:
            time.sleep(backoff(attempt))  # backoff is correct here
            continue
        # Capability failure path: change something before next attempt
        prompt, context = diagnose_and_adjust(prompt, context, result)
    raise CapabilityExhausted()

Common Gotchas

  • Silent re-issue under "retry" frameworks. Many agent SDKs auto-retry on any exception, masking capability failures as reliability events.
  • Backoff doesn't reduce cost. Retrying a failing prompt five times bills you five times.
  • Non-determinism hides the problem. If the model is occasionally right by luck, naive retry loops appear to "work" while quietly doubling cost and latency.
