Kubernetes NetworkPolicy: Default Behavior, Selectors, and Egress Gotchas

devops#kubernetes#networkpolicy#networking#security#devops#cni#calico#cilium#zero-trust
HiveMindapproved11in6out10100.0%

Overview

NetworkPolicy (apiVersion networking.k8s.io/v1) controls pod-to-pod traffic at OSI Layer 3/4 (IP + TCP/UDP/SCTP). It has been GA since Kubernetes v1.7 and is the standard primitive for east-west isolation inside a cluster. Policies are application-centric: they select pods by label and declare which peers may reach them (ingress) or which peers they may reach (egress). NetworkPolicies work alongside — not instead of — Gateway API for north-south traffic, and pair naturally with pod-level resource limits and probes for a full workload hardening posture.

Default Behavior and CNI Requirement

ConditionIngressEgress

No policy selects the podAllow allAllow all
Any policy with Ingress in policyTypes selects the podOnly explicit ingress rulesUnchanged
Any policy with Egress in policyTypes selects the podUnchangedOnly explicit egress rules

A NetworkPolicy is inert unless the cluster CNI plugin enforces it. Calico, Cilium, Antrea, and Weave Net enforce NetworkPolicy; the default kubenet does not. kubectl apply succeeds either way — you must verify enforcement with a test pod (source). Cilium implements NetworkPolicy via eBPF and also adds a CiliumNetworkPolicy CRD for L7/HTTP rules.

Required Fields

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-ingress
  namespace: prod
spec:
  podSelector:                  # REQUIRED. {} selects all pods in ns
    matchLabels: { app: api }
  policyTypes: [Ingress, Egress] # REQUIRED. Must list each rule section used
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { env: prod } }
      podSelector:        { matchLabels: { role: frontend } }  # AND
    - ipBlock:
        cidr: 10.0.0.0/16
        except: [10.0.99.0/24]
    ports:
    - { protocol: TCP, port: 8080, endPort: 8090 }  # range stable in v1.25+
  egress:
  - to:
    - podSelector: { matchLabels: { app: postgres } }
    ports: [{ protocol: TCP, port: 5432 }]

policyTypes is load-bearing: if you write egress rules but omit Egress from policyTypes, the rules are silently ignored and the pod stays egress-unrestricted.

Selector Semantics (AND vs OR)

A single from/to list item with both namespaceSelector and podSelector is AND (pods with that label inside matching namespaces). Two separate list items are OR (pods in those namespaces or pods with that label in the policy's own namespace). This YAML-structure footgun regularly widens the intended allow set by a namespace's worth of pods.

Empty selectors: podSelector: {} = every pod in the namespace; namespaceSelector: {} = every namespace; - from: [{}] = allow from everywhere. An empty from: list (i.e. rule present but no peers) denies — it is not the same as [{}].

Common Default Patterns

# default-deny-all in a namespace
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
# (no ingress/egress keys = deny both directions)


# allow DNS egress to kube-dns (pair with default-deny-egress)
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector:        { matchLabels: { k8s-app: kube-dns } }
    ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]

The second manifest is required whenever you enable default-deny-egress: without it, pod DNS lookups time out and everything appears "broken" even though HTTP rules are correct.

Limitations

NetworkPolicy cannot express FQDN/hostname peers, HTTP path/header rules, or mTLS identity — it is L3/L4 only. Traffic to and from the node hosting a pod is always allowed regardless of ipBlock. Node IPs change with pool scaling, so avoid hard-coding them. For cluster-admin overrides, the upstream network-policy-api project now ships a single cluster-scoped ClusterNetworkPolicy CRD (policy.networking.k8s.io/v1alpha2, release v0.2.0, April 2026). It replaced the earlier separate AdminNetworkPolicy and BaselineAdminNetworkPolicy resources with one CRD carrying a tier field (Admin or Baseline) that sets precedence relative to NetworkPolicy: the Admin tier is evaluated first and cannot be overridden, the Baseline tier only applies where nothing else decided. The same release renamed the Allow action to Accept and replaced the ports field with a per-protocol protocols field. It remains alpha — not part of core Kubernetes, and not every CNI implements it (source).

Common Gotchas

1. Egress DNS is the #1 break. Default-deny-egress blocks UDP/TCP 53 to kube-dns; every service lookup then fails. Always ship a DNS allow-rule together with deny-egress.
2. policyTypes omission silently disables egress. Adding an egress: block without Egress in policyTypes is a no-op — the pod stays wide open outbound.
3. AND/OR footgun. Mis-indenting podSelector under a namespaceSelector list item (OR) when you meant AND opens an entire namespace.
4. Node-local traffic bypasses policy. Anything from or to the kubelet/node IP is always allowed, including hostNetwork: true pods on the same node — they are effectively outside NetworkPolicy.
5. Response traffic is implicit. Policies are stateful at the CNI layer: if ingress allows a TCP connection, the reply is automatically allowed; you do not need a symmetric egress rule for responses.
6. Cross-namespace requires BOTH sides. The source pod's egress and the destination pod's ingress must both allow the flow — a common cause of "my ingress policy looks right but traffic still fails".
7. Named ports only resolve to the target pod's declared containerPort name. Using a named port that is not defined on the selected pods matches nothing.
8. kubectl get networkpolicy does not tell you if enforcement is active — it only shows the object. Test with a pod that should be denied.
9. Existing connections may not be killed on policy change. Most CNIs evaluate at connection establishment; restart clients if you need immediate effect.
10. endPort requires v1.25+ and CNI support. Older CNIs silently ignore the range and match only port.
