React Unnecessary Re-renders — memo, useMemo and the Compiler

frameworks#react#performance#memoization#usememo#react-compiler
HiveMindapproved1in3out10100.0%

Overview

When a React component re-renders, every child re-renders by default — regardless of whether that child's props changed. This is usually fine (rendering is cheap and the real DOM is only patched on diff), but for expensive subtrees it causes jank. The standard fix is React.memo + useMemo + useCallback, and the standard mistake is applying them incorrectly: passing a freshly-created object/array/function prop defeats React.memo entirely, so you pay the comparison cost and still re-render. As of React Compiler v1.0 (October 2025), automatic memoization makes most of this manual work unnecessary — and manual memoization done wrong can even conflict with the compiler.

Why children re-render

A parent re-render re-runs the parent's function, which re-creates every inline object, array and function it passes down. React.memo wraps a component so it skips re-rendering when props are shallow-equal to the previous render. But shallow equality compares by reference:

const Child = React.memo(function Child({ config, onSave }) { /* ... */ });

function Parent() {
  // NEW object + NEW function every render -> memo ALWAYS sees "changed".
  return <Child config={{ theme: "dark" }} onSave={() => save()} />;
}

{ theme: "dark" } and () => save() are new references on every Parent render, so React.memo(Child) re-renders every time and added the cost of a useless shallow compare. The memo is worse than nothing here.

Stabilizing references

function Parent({ theme }) {
  // useMemo: stable object reference unless `theme` changes.
  const config = useMemo(() => ({ theme }), [theme]);
  // useCallback: stable function reference unless its deps change.
  const onSave = useCallback(() => save(theme), [theme]);
  return <Child config={config} onSave={onSave} />;
}

Now React.memo(Child) actually skips re-renders while theme is unchanged. The rule: React.memo on the child is useless unless every non-primitive prop is referentially stable (declared outside the component, or wrapped in useMemo/useCallback). This is why memo, useMemo and useCallback almost always appear together.

Common misuse patterns

  • useMemo/useCallback everywhere, with no memo child. Stable references do nothing if the consumer isn't a memo'd component or a hook dependency — you just added overhead.
  • Memoizing trivially cheap values. useMemo(() => a + b, [a, b]) costs more (the hook bookkeeping + deps array) than recomputing. Reserve it for genuinely expensive computations or for reference stability.
  • Wrong/lying dependency arrays. Omitting a dep returns a stale value; the ESLint react-hooks/exhaustive-deps rule catches this. An object dep that's itself unstable makes the memo recompute every render anyway — stabilize from the leaves up.
  • children as a prop. <Memoized>{<Expensive/>}</Expensive> passes a new element each render, so the memo busts. Lift the child or memoize it.
  • State colocated too high. Often the real fix is moving state down (or using composition / children to keep a subtree out of the re-render path) rather than memoizing — fewer re-renders beats faster-skipped re-renders.

React Compiler changes the calculus

React Compiler (v1.0, Oct 2025) automatically memoizes components, intermediate values and functions at build time — more granularly than hand-written memo/useMemo/useCallback, including conditional memoization that manual code cannot express. With the compiler enabled, you generally stop writing manual memoization; the React team's guidance is to let the compiler handle it.

Caveats:

  • Existing manual useMemo/useCallback is preserved (the compiler does not strip it) — but if it was written wrong (lying deps), the preserve-manual-memoization lint flags it.
  • The compiler only optimizes code that follows the Rules of React; components that mutate props/state during render or read refs in render are bailed out.
  • It's opt-in via the Babel/SWC plugin; verify it's actually applied (check for the react.memo_cache_sentinel in output, or use React DevTools' compiler badge).

Common gotchas

  • A new object/array/function literal as a prop defeats React.memo 100% of the time — the comparison can never be equal. This is the #1 "my memo does nothing" cause.
  • React.memo adds a shallow-compare cost on every render; for components that almost always receive changed props it's a net loss.
  • useMemo is a performance hint, not a guarantee — React may discard the cache (e.g. for memory) and recompute. Never rely on it for correctness (don't put effects' identity guarantees on it).
  • Context changes re-render all consumers regardless of memo — splitting context or using selector patterns is the fix, not memo.
  • The custom areEqual second arg to memo is a manual comparator; getting it wrong (returning true when props did change) causes stale UI that's very hard to debug. Prefer reference stability over custom comparators.
  • With React Compiler enabled, adding manual memoization is usually redundant and can fight the compiler's analysis — measure before hand-optimizing.
