Overview

Iroh is a Rust library for direct peer-to-peer connectivity over QUIC, built and maintained by number 0 (n0). The lib establishes authenticated, end-to-end-encrypted connections between two endpoints by hole-punching through NATs and falling back to relay servers when direct paths fail. v1.0.0-rc.0 was published on 2026-05-07, the first release candidate before the long-promised 1.0 stability commitment, after the 0.94 → 0.98 series finalised the API surface, swapped the QUIC implementation from Quinn to noq, and rebuilt NAT traversal on top of an emerging IETF draft. That was the state at this card's 2026-05-10 baseline; iroh 1.0.0 shipped on 2026-06-15 and the current stable release is 1.1.0 (2026-08-25) — see the dated update under the version timeline.

Iroh is what you reach for when you want native applications to talk directly to each other without a coordination server, without a central message-bus, and without WebRTC's signaling complexity. Concrete consumers in 2026 include the Iroh blobs BLAKE3 transfer protocol, the Iroh gossip broadcast layer, and the Delta Chat peer-to-peer email client.

What iroh actually is

Iroh is not a libp2p replacement and not a WebRTC replacement — it sits in a third space. The five-line elevator pitch:

  • Wire protocol: QUIC, with TLS 1.3 inside. Direct path first, relay fallback second, and (with multipath since 0.96) both at once in a single QUIC connection.
  • Identity: Each endpoint has a long-lived 32-byte Ed25519 keypair. The public key is the address — EndpointId (formerly NodeId).
  • Discovery: DNS, mDNS, or DHT lookups translate an EndpointId to a current EndpointAddr (relay URL + zero-or-more direct IP/UDP transport addresses).
  • NAT traversal: As of 0.96, QNT (an IETF draft for QUIC-layer hole-punching) is wired into noq itself, so traversal piggy-backs on QUIC framing for retransmit and DDoS protection.
  • Application layer: None opinionated. Iroh ships only the connection layer; you pick your own framing on top (raw QUIC streams, blobs, gossip, RPC, or anything else).

This is why iroh shows up in projects that previously would have reached for Tailscale (overlay mesh, full L3) or WireGuard (kernel tunnel, no NAT-traversal-by-default) but want per-application P2P without the mesh-VPN baggage.

noq: number 0 QUIC

Since v0.96, iroh's QUIC implementation is noq ("number 0 QUIC"), a hard fork of Quinn maintained at github.com/n0-computer/noq. The fork happened because iroh's relay-as-a-path and multipath ambitions required structural changes to the connection state machine that Quinn upstream wasn't going to take.

What this means for users:

  • Symbol rename in 0.97: Anywhere you previously used iroh_quinn or iroh_quinn_proto, the symbols are now under noq and noq_proto. The semantic API is intentionally close to Quinn's, but any explicit re-exports or use paths break in 0.97 and again at 1.0-rc.0.
  • Connection API in 0.96: A single generic Connection<T> replaces multiple separate types — Connection<HandshakeCompleted> (default, what you get from accept().await?.await?), Connection<OutgoingZeroRtt> (client-side 0-RTT), and Connection<IncomingZeroRtt> (server-side 0-RTT).
  • Multipath: Once a connection is open, both relay and direct paths can stay live. Path selection is governed by noq, not iroh — you observe via Connection::paths(), which in 0.98 returned a PathWatcher but as of 1.0.0-rc.0 returns a PathList snapshot taken at call time (this is the "redesigned path observation" in the rc.0 notes). For a live view use Connection::paths_stream() (a stream of PathList snapshots) or Connection::path_events() (individual PathEvents).
  • Multipath congestion control: Each path runs an independent congestion controller (default Cubic; BBRv3 configurable per build). The classic single-path-fairness story doesn't directly apply — you're not contending with one TCP flow but with however many simultaneous paths are alive.

QNT: QUIC NAT Traversal

Before 0.96, iroh used a custom hole-punching protocol layered above QUIC. As of 0.96 it uses QNT, an emerging IETF draft (draft-seemann-quic-nat-traversal; the n0-computer/iroh-spec repository cited in the original version of this card does not exist and its link 404s) that integrates hole-punching as a QUIC frame type rather than out-of-band ICE-style signaling.

The benefits of moving traversal into the QUIC layer:

  • Encrypted by default — traversal traffic rides inside the existing TLS 1.3 channel, so the relay never sees probe contents.
  • Built-in loss recovery — a lost probe gets QUIC's PTO-driven retransmit for free instead of needing custom timers.
  • DDoS protection — QUIC's address-validation token machinery already filters spoofed probes; the holepunch path inherits it.
  • Retries fixed in 0.98 — a regression in 0.96/0.97 left abandoned paths "stuck" and didn't re-trigger holepunching across network changes; v0.98.0's "Getting back to traversing NATs" announcement called this out and fixed it. PTO is now capped at 2 seconds post-handshake, off-path probes are retried during traversal rounds, and the path-abandonment ACK path no longer stalls.

The Endpoint Takeover (v0.94)

In 0.94, every "node"-flavoured identifier in iroh was renamed:

Before 0.940.94+Notes

NodeIdEndpointIdThe 32-byte Ed25519 public key
NodeAddrEndpointAddrNow wraps a TransportAddr enum (relay URL, UDP/IP, custom)
node_id fieldendpoint_idField rename, search-and-replace
RelayNodeRelayConfigRenamed for semantic accuracy
Endpoint::node_idEndpoint::idMethod rename
Endpoint::node_addrEndpoint::addrMethod rename

The motivation was simple: iroh stopped trying to be "a node-graph thing" and accepted that it's a connection library — one whose primary unit is an Endpoint, not a node. The EndpointAddr redesign was the more substantive change: addresses are no longer hardcoded to (RelayUrl, Vec<SocketAddr>), they hold a TransportAddr enum that can include WebRTC, BLE, Tor, or any other transport implementation.

If you're upgrading from < 0.94, the rename is mostly mechanical but does break public APIs. There is no compatibility shim — you fix the call sites and ship.

Custom transports (v0.97)

v0.97 adds a unstable-custom-transports cargo feature that exposes the trait surface needed to plug a non-UDP transport into iroh. From the v0.97 announcement:

> "the custom transport API is unstable and will remain so for some time even after iroh 1.0 is released."

Translation: 1.0's API stability commitment does not cover unstable-custom-transports. Plan for breakage on the 1.0.x patch line if you depend on it.

Concrete reference implementations:

  • Tor (onion services) — see n0-computer/iroh-tor-transport and the Tor custom transport blog post. Documented as the "good starting point" for writing your own.
  • Nym — separate project at n0-computer/iroh-nym-transport for mixnet-routed traffic. (n0-computer/iroh-nym, the URL this card originally gave, 404s.)
  • Bluetooth Low Energy (BLE) — planned but community-led; not yet a published reference implementation.

The implementation contract: anything that can move 1200-byte unreliable datagrams round-trip works. You implement low-level send/receive traits, define a custom address ID, and serialize the address into an opaque CustomAddr type that gets carried inside EndpointAddr::TransportAddr::Custom.

Pluggable crypto backends (v0.98)

v0.98.0 made the rustls crypto backend selectable so consumers can choose between ring and aws-lc-rs, or supply their own via Builder::crypto_provider. The motivation is FIPS — aws-lc-rs has a FIPS-validated profile and is the path of least resistance for federal compliance.

The feature names are tls-ring and tls-aws-lc-rs. There is no ring feature, no aws-lc-rs feature and no crypto-provider feature — an earlier version of this card named all three, and none of them exist in the published Cargo.toml of 0.98.x, 1.0.0-rc.0 or 1.0.3.

# Cargo.toml — tls-ring is already in iroh's default features
[dependencies]
iroh = "1"

# For the aws-lc-rs backend instead, turn defaults off:
# iroh = { version = "1", default-features = false, features = ["tls-aws-lc-rs", "metrics", "portmapper"] }

default = ["metrics", "fast-apple-datapath", "portmapper", "tls-ring"], so doing nothing still gives you ring — the "you must now install a provider explicitly or nothing works" claim was never true. If both backends are enabled, presets::Minimal and presets::N0 prefer ring. The only case where you must supply a provider yourself is presets::Empty, which sets nothing at all and is documented to fail if you pass it straight to Endpoint::bind.

Post-quantum status: NOT YET

Iroh v1.0.0-rc.0 still uses classical key exchange. From the iroh FAQ:

> "Iroh uses Ed25519 for signing and X25519/P-256 for ECDH. These algorithms are not post-quantum-secure."

The team's public reasoning is overhead: a Xyber (X25519+ML-KEM-768 hybrid) public key is ~37x larger than a raw Ed25519 key, which would inflate handshake bytes and DNS-discovery packets enough to fragment. v1.0.0-rc.0 release notes do mention "post quantum key exchange documentation examples" (PR #4196) — that's a docs/preview surface, not a production-default switch. Compare to OpenSSH 10.x, which made mlkem768x25519-sha256 the default key exchange in 2025, or to the MLS protocol's PQ ciphersuite work. Iroh is later than both.

Update (verified 2026-08-22): "not the answer" was too strong, and is now clearly wrong. Hybrid post-quantum key exchange (X25519MLKEM768 — X25519 and ML-KEM-768 combined, safe as long as either primitive holds) is available in iroh today, opt-in rather than default. n0's post-quantum handshakes post (2026-05-19) documents the recipe: enable iroh's tls-aws-lc-rs feature and rustls' prefer-post-quantum feature, since aws-lc-rs is the only rustls backend shipping ML-KEM. The shipped crate carries two runnable examples for it — prefer-pq-key-exchange (PQ when both sides support it, classical fallback) and pq-only-key-exchange (strips kx_groups to the PQ group, so non-PQ peers fail the handshake) — both present in 1.0.0-rc.0 and still shipped in 1.1.0, and both gated on tls-aws-lc-rs.

Two caveats that still hold. PQ-only cannot use n0 public infrastructure: iroh's crypto_provider is shared with relay and discovery TLS, and n0's relays and DNS servers do not negotiate PQ key exchange, so a PQ-only endpoint must run with RelayMode::Disabled and its own discovery. And only confidentiality is protected — signatures are still classical Ed25519, so authentication remains quantum-vulnerable. The FAQ text quoted above has not been updated and still reads as a flat "no".

Public n0 relay infrastructure

The default presets::N0 builder uses four public relay servers operated by number 0 — two in the US, one in EU, one in Asia. They're free for development and rate-limited to discourage abuse. Production deployments are expected to either:

  • Pay for managed-relay hosting via iroh services (the "🟢 iroh services" launch in v0.93) — tiers re-read 2026-09-06: Community ($0/mo — shared public relays in US/EU/Singapore, rate-limited, no uptime guarantee), Pro ($19/mo, 10,000 concurrent connections and 100 GB egress included, then $0.003/endpoint and $0.09/GB), Dedicated ($199/mo per region, an add-on to Pro) and Enterprise (custom), per iroh.computer/pricing. Three corrections to the earlier version of this line: the entry tier is called Community, not "Free"; there is a fourth Dedicated tier this card omitted; and the "$0.27 per relay-hour" rate it quoted does not exist — neither "0.27" nor "relay-hour" appears anywhere in that page's markup, and Pro overage is billed per endpoint and per GB of egress, not per relay-hour; or
  • Self-host using iroh-relay — straightforward Tokio binary, single-tenant.

presets::N0 is convenient for hobby projects and testing, not for any application that should not share infrastructure with arbitrary other iroh users. Define your own RelayMap and use presets::Empty or presets::Minimal for production.

Connecting two endpoints — the minimal example

// Cargo.toml
// [dependencies]
// iroh = "1"   # tls-ring ships in default features
// tokio = { version = "1", features = ["full"] }

use iroh::{Endpoint, endpoint::presets};   // NB: `presets` is under `iroh::endpoint`, not the crate root

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // Server side — bind, advertise an ALPN, accept one connection.
    let server = Endpoint::builder(presets::N0)
        .alpns(vec![b"my-app/1".to_vec()])
        .bind()
        .await?;
    let server_addr = server.addr(); // NB: `addr()` is synchronous — it reads the current watcher value
    println!("server endpoint id: {}", server.id());

    tokio::spawn(async move {
        let conn = server.accept().await.unwrap().await.unwrap();
        let (mut send, mut recv) = conn.accept_bi().await.unwrap();
        let msg = recv.read_to_end(1024).await.unwrap();
        send.write_all(&msg).await.unwrap();
        send.finish().unwrap();
    });

    // Client side — bind, connect by EndpointAddr, send/recv on a bidirectional stream.
    let client = Endpoint::bind(presets::N0).await?;
    let conn = client.connect(server_addr, b"my-app/1").await?;
    let (mut send, mut recv) = conn.open_bi().await?;
    send.write_all(b"hello").await?;
    send.finish()?;
    let echo = recv.read_to_end(1024).await?;
    println!("got back: {:?}", echo);
    Ok(())
}

Import path — corrected 2026-09-06 against the shipped crate. presets lives at iroh::endpoint::presets and EndpointHooks at iroh::endpoint::EndpointHooks; neither is re-exported at the crate root. Both samples on this card previously wrote use iroh::{Endpoint, presets};, which does not build — cargo check on a fresh crate with iroh = "1" (resolved 1.1.0, rustc 1.95.0) fails with error[E0432]: unresolved import iroh::presets — no presets in the root. With only the import line fixed, both samples compile clean. This was wrong when written, not a 1.1.0 regression: iroh 1.0.3's own lib.rs doc examples already read use iroh::{Endpoint, EndpointAddr, endpoint::presets};. Endpoint, EndpointId, EndpointAddr and SecretKey are at the crate root, so those imports were fine.

presets::N0 sets exactly three things (src/endpoint/presets.rs): the rustls crypto provider, a pkarr publisher plus DNS address lookup against n0's iroh.link servers, and the default relay mode (the four public n0 relays). It does not enable mDNS or the mainline DHT — as of 1.0 those live in separate crates, iroh-mdns-address-lookup and iroh-mainline-address-lookup, and you add them with Builder::address_lookup. presets::Minimal is thinner still: it sets only the crypto provider, so it gives you no discovery and no relays, not "mDNS only". presets::Empty sets nothing and is documented to fail if handed straight to Endpoint::bind. The example uses Tokio as the async runtime — iroh does not support async-std or smol. MSRV is not 1.81: the published rust-version is 1.89 for the 0.98 line and 1.91 for every 1.0.x release, on Rust edition 2024.

EndpointHooks: connection-time interception (v0.96)

The EndpointHooks trait gives you two checkpoints for authn/authz/observability. Read the direction carefully — an earlier version of this card had it backwards:

  • before_connect(&self, remote_addr: &EndpointAddr, alpn: &[u8]) -> BeforeConnectOutcome — intercepts outgoing connections only, i.e. calls to Endpoint::connect / connect_with_opts, before any packet is sent. It is not in the accept loop and will never see an inbound peer, so it cannot be used to build an inbound allow-list.
  • after_handshake(&self, conn: &Connection) -> AfterHandshakeOutcome — fires for both incoming and outgoing connections once the TLS handshake completes and the remote endpoint id and ALPN are known. This is the hook that gates inbound peers: return AfterHandshakeOutcome::Reject { error_code, reason } to close the connection. Do not clone the Connection out of the hook — use Connection::weak_handle() if you need to keep a reference.

Both have default implementations that accept, hooks are installed on the Builder and may be installed more than once, and they run in installation order until one rejects. There is no HookError type in iroh — the outcome enums are the whole error surface.

use iroh::Endpoint;
use iroh::endpoint::{AfterHandshakeOutcome, Connection, EndpointHooks, presets};

#[derive(Debug)]
struct AllowList { allowed: Vec<iroh::EndpointId> }

impl EndpointHooks for AllowList {
    // Inbound *and* outbound, after the handshake: this is where an allow-list belongs.
    async fn after_handshake(&self, conn: &Connection) -> AfterHandshakeOutcome {
        if self.allowed.contains(&conn.remote_id()) {
            AfterHandshakeOutcome::Accept
        } else {
            AfterHandshakeOutcome::Reject {
                error_code: 0u32.into(),
                reason: b"not on allow list".to_vec(),
            }
        }
    }
}

let ep = Endpoint::builder(presets::N0)
    .hooks(AllowList { allowed: vec![/* ... */] })
    .bind()
    .await?;

This replaces the previous "wrap accept() in your own auth check" pattern that was easy to bypass — after_handshake is on the critical path for every connection, inbound and outbound, and a rejection there closes the connection with a QUIC close frame. EndpointHooks also predates this card's baseline by a release: the trait shipped in 0.96 and is unchanged in signature through 1.1.0 (re-read in the published crate on 2026-09-06).

Stewardship of libp2p — corrected 2026-09-06. One attribution to avoid: Interplanetary Shipyard is not libp2p's steward, notwithstanding the sentence still on its homepage — "We are the core maintainers of IPFS, libp2p, and other foundational open-source web3 primitives." Shipyard's own engineering blog contradicts that boilerplate twice. When a vendor's marketing page and its own engineering blog disagree about who maintains something, the blog wins.

The closest direct competitors for "I want native P2P over QUIC" are libp2p and rolling your own with Quinn + STUN. Iroh wins when you want batteries-included NAT traversal + relay fallback without taking on libp2p's much larger protocol surface (libp2p is an independent project, not "the IPFS stack"); libp2p wins when you want the Kademlia DHT, multistream protocol negotiation, or the broader libp2p ecosystem (gossipsub, autonat, etc.).

Common gotchas

  • 0.93 → 0.94 is a hard rename (and it sticks for every later release). NodeId, NodeAddr, node_id, RelayNode are gone — search-and-replace the lot. There is no pub use NodeId = EndpointId; shim.
  • 0.96 → 0.97 is a noq rename. Anywhere you imported iroh_quinn::* or iroh_quinn_proto::* symbols, replace with noq::* and noq_proto::*. The path-of-least-resistance is to import from iroh::quic re-exports rather than reach for the underlying crate directly.
  • Endpoint::empty_builder() was removed in 0.98. Use Endpoint::builder(presets::Empty) or Endpoint::builder(presets::Minimal) instead.
  • The crypto features are tls-ring and tls-aws-lc-rs, and tls-ring is on by default. There are no ring, aws-lc-rs or crypto-provider features — those names do not build. You only need to think about this if you turn default features off, or if you want the aws-lc-rs/FIPS backend.
  • SecretKey::generate() lost its RNG generic in 0.98. The signature is now fn generate() -> SecretKey (uses the system OS RNG); you can no longer pass a deterministic test RNG. For tests, use SecretKey::from_bytes(&[u8; 32]) with a fixed seed.
  • unstable-custom-transports is not 1.0-stable. Custom transports will break on 1.0.x patches. Don't promise SLAs around it.
  • presets::N0 shares infrastructure with everyone. The four public n0 relays are rate-limited and not for production tenants that care about isolation. Use managed iroh services or self-host iroh-relay for any real workload.
  • Post-quantum key exchange is opt-in, not absent. The default handshake is classical, but hybrid X25519MLKEM768 works today via the tls-aws-lc-rs feature plus rustls' prefer-post-quantum, with prefer-pq-key-exchange and pq-only-key-exchange examples in the crate. A PQ-only endpoint cannot use n0's public relays or discovery (their TLS is classical), and signatures stay Ed25519 either way.
  • Browser/WASM does work — this card previously said it did not, which was wrong. The crate has wasm32-unknown-unknown targets and wasm_browser code paths (browsers resolve discovery over pkarr HTTPS instead of DNS), and the 1.0 announcement states n0 "built & continually check that iroh can compile to WASM & run in the browser". The real limitation is that browsers cannot hole-punch: a browser endpoint is relay-only, which is why the FAQ still points at WebRTC for hole-punched browser connections. If you need direct browser connectivity, WebTransport or WebRTC is still the alternative.
  • Holepunching does NOT auto-restart on every network change in 0.96/0.97. v0.98 fixed the regression where abandoned paths got stuck and didn't re-trigger holepunching after suspend/resume or interface changes. Do not pin to 0.96.x or 0.97.x for mobile clients — upgrade to 0.98.0+ (or 1.0.0-rc.0) before shipping.
  • Relay protocol v2 is on the wire from 0.98. Mixed-version deployments (v0.97 client talking to v0.98 relay or vice versa) negotiate the lower version cleanly, but if you self-host relays, plan to upgrade them first, then clients — old clients can talk to new relays, not the other way around.
  • Connection::paths() is a snapshot, not a Watcher — it returned PathWatcher in 0.98 but returns a point-in-time PathList from 1.0.0-rc.0 onward. To follow changes use Connection::paths_stream() or Connection::path_events(); both end when the connection closes.
  • presets::N0 is DNS/pkarr discovery only — no mDNS, no DHT. On an isolated network its lookups just time out, and presets::Minimal will not save you: it configures nothing but the crypto provider. For offline LAN you must add the iroh-mdns-address-lookup crate yourself via Builder::address_lookup (in 0.98 the equivalent lived behind iroh's own non-default address-lookup-mdns feature; it moved out of the crate at 1.0).
  • Do not pin to a git tag or to the RC line. There was never a crates.io publish lag — 1.0.0-rc.0 landed on crates.io on 2026-05-07 — and stable 1.0.x has been on crates.io since 2026-06-15. Use iroh = "1"; the 0.9x and RC lines are explicitly outside the 1.0 support commitment.
