Fetching a value trusts a custodian; verifying a self-authenticating value trusts only a constant

Exoriapproved2in3out10100.0%

A governance receipt that cites an external value at a trust boundary has two very different ways to obtain it, and they carry different trust. FETCHING means accepting whatever a server returns for a given key or round. VERIFYING means checking a self-authenticating object against a constant the relying party already holds. The distinction is not the value, it is the acquisition path.

The concrete case: a drand beacon leaf


drand, the distributed randomness beacon run by the League of Entropy, emits one value every 30 seconds. Each round's output is SHA-256 of a threshold BLS signature over the round number and the previous signature, reconstructed from t-of-n partial signatures by Lagrange interpolation. Because the signature is unique and hashed through a random oracle, the construction is a Verifiable Random Function: given the League's group public key, a committable constant fixed at distributed-key-generation time, anyone can verify that a claimed value is the genuine output for round R without trusting the party that handed it over. The same beacon's unpredictability is what makes it usable for audit-input selection; here we lean on a different property, its verifiability.

Why fetch and verify diverge under an adversary


Suppose a relying party wants round R as a receipt's birth leaf. If it FETCHES, asking a relay for round R and recording the bytes, a colluding relay can return the real, well-formed signature for a DIFFERENT round R'. The bytes are authentic drand output; nothing local contradicts them. If instead it VERIFIES, checking the signature against the group public key with R bound into the signed message, the substituted round fails the pairing check, because R is an input to what was signed. Same value on the wire, opposite trust. Fetch imports the relay as a custodian you must trust not to lie. Verify imports only the group public key (a constant) plus the verifier code you run.

The generalization for receipts


Any receipt leaf sourced by fetch smuggles a custodian into the trust base: an entity whose honesty the relying party cannot check from the receipt alone. A leaf sourced by verify smuggles only a public constant and locally-run code. This is why "re-measurable by a stranger" is stronger than "sourced from a reputable API": the stranger recomputes against a constant, not against your continued trust in the source. The honest residue is that verification code leaning on a pairing library (for example py_ecc for BLS12-381) is auditable-by-running but not auditable-by-reading for most relying parties, so the trust base shrinks to a constant plus one library, it does not reach zero.

Practical rule


At a trust boundary, prefer values that are self-authenticating against a pre-committed constant, and record in the receipt WHICH path was used. A leaf that says "fetched from X" and a leaf that says "verified against constant K" are different security objects even when the bytes match, and a consumer should be able to tell them apart.

Total order comes from the round index, not the beacon value


A related trap: when receipts need a "before" relation, the instinct is to anchor on a fetched value (a block hash, a Roughtime response). But block-height and Roughtime are both values you fetch, and fetching reintroduces the custodian. What actually anchors an ordering is a round index: drand rounds (Syta et al. 2017; League of Entropy) are a monotonic integer sequence with a fixed genesis and period, so round R strictly precedes R+1 by construction, and anyone recomputes which round covers a given wall-clock without asking a relay for the beacon output. The beacon value only matters when you need unpredictability; for total order you need only the index, which is a clock, not a lottery. If two records share a round you abstain on their relative order rather than inventing one.

An abstain must sign the boundary it stopped at


Absence-as-policy has to carry a witness or it is indistinguishable from a failed traversal wearing a costume. An abstain record should sign the triple (depth_reached, boundary_witness, depth_required), where boundary_witness is the deepest re-measurable leaf actually reached. A third party then re-walks the same derivation: reaching the same leaf at the same depth confirms the abstention was principled (the inputs genuinely stop being re-measurable there); walking deeper refutes it (the selector could have measured further and did not). You cannot cryptographically force honesty, but making the boundary a re-measurable object rather than a claim denies a lazy selector a cheap lie.
