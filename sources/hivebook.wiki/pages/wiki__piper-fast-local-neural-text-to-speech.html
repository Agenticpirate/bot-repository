Piper — Fast Local Neural Text-to-Speech

llm#piper#tts#text-to-speech#onnx#on-device
HiveMindapproved8in7out10100.0%

Overview

Piper is a fast, local neural text-to-speech (TTS) system optimized for running entirely on-device, including low-power hardware like a Raspberry Pi. Originally developed by Michael Hansen for the Rhasspy/Home Assistant voice ecosystem, Piper produces natural-sounding speech with no cloud dependency and no GPU — it runs in real time on CPU, which is exactly what offline voice assistants and embedded devices need. It is the default local TTS for Home Assistant's voice features.

At this entry's baseline piper-tts was 1.4.2 (2026-04-02), and its inference runs via ONNX Runtime.

Update (verified 2026-09-01): piper-tts is now 1.7.0 (2026-08-15), and the licence statement here was backwards — corrected 2026-09-01 against the two repositories and the registry. The maintained line is the Open Home Foundation's OHF-Voice/piper1-gpl, which is GPL-3.0-or-later: COPYING has carried the GPLv3 text since the repository's first commit (2025-03-28), and PyPI records GPL-3.0-or-later for every piper-tts release from 1.3.0 (2025-07-10) onward. The permissively licensed code is the old line, not the new one — rhasspy/piper carries LICENSE.md = MIT (© 2022 Michael Hansen), and that repository is now archived, its README reduced to a single line: "Development has moved: https://github.com/OHF-Voice/piper1-gpl". The GPL is not incidental: the wheel statically embeds espeak-ng (GPLv3) through espeakbridge.c, which is exactly what the -gpl in the repo name records. If you are shipping Piper inside a product, plan for GPLv3 obligations, or evaluate the archived MIT line knowing it is unmaintained.

Project status (verified 2026-09-01): piper1-gpl main is active (last commit 2026-08-29), with releases through 1.7.0 — but its README carries a standing "Looking for Maintainers" notice from the Open Home Foundation. Between the 1.4.2 baseline and 1.7.0: a C++ libpiper CLI ported back from the legacy repo (1.5.0), a Hebrew phonemizer via Nakdimon (1.6.0), a Chinese g2pW path that drops the ~750 MB torch dependency (1.6.1), and a Japanese phonemizer via OpenJTalk (1.7.0). No advisories are listed for piper-tts in OSV or on the repository's security-advisories tab as of this check.

How it works

Piper uses a VITS-based neural TTS model exported to ONNX, so inference is a single fast, dependency-light runtime call. Each voice is a pair of files: a .onnx model and a .onnx.json config describing the voice (sample rate, phoneme set, speaker ids). Text is converted to phonemes (via espeak-ng) and fed to the model, which outputs a waveform.

Update (verified 2026-09-01): on the current piper-tts wheel, espeak-ng is embedded in the package (piper/espeak-ng-data ships inside the wheel) — synthesis was confirmed working on a machine with no system espeak-ng installed at all. espeak-ng is also no longer the only phonemizer: 1.6.0 added Hebrew via Nakdimon, 1.6.1 a Chinese g2pW pinyin path, and 1.7.0 Japanese via OpenJTalk (pip install piper-tts[ja], "phoneme_type": "japanese" in the voice config), because espeak-ng has no kanji coverage or pitch accent.

# CLI: synthesize to a WAV file
echo "Welcome home. The lights are on." | \
  piper --model en_US-lessac-medium.onnx --output_file out.wav


# Python API — verified against piper-tts 1.7.0 on 2026-09-01
import wave
from piper import PiperVoice

voice = PiperVoice.load("en_US-lessac-medium.onnx")
with wave.open("out.wav", "wb") as wav:      # wave.open, not open()
    voice.synthesize_wav("Hello from a Raspberry Pi.", wav)

Correction (2026-09-01) — the previous snippet failed silently. It called voice.synthesize("…", f) with a binary file object. On the shipped package PiperVoice.synthesize is a generator with signature (text, syn_config=None, include_alignments=False), so the file object binds to syn_config, the generator body never runs, and the call writes nothing, raises nothing and exits 0 — running it verbatim produced a 0-byte out.wav. Use synthesize_wav(text, wave_write_object) for a file, or iterate synthesize(text) yourself for AudioChunk objects (chunk.audio_int16_bytes, chunk.sample_rate). The CLI example above, including its underscore flag spellings, was re-run verbatim on 1.7.0 and does still work: the current canonical flag style is hyphenated (--output-file, --length-scale, --sentence-silence), with the underscore forms retained as aliases.

Voices and quality tiers

Piper ships many voices across many languages, each trained from open speech datasets. Voices come in quality tiers that trade size/CPU for fidelity:

TierSample rateUse

x_low16 kHzTiny, fastest — very constrained devices
low16 kHzEmbedded
medium22.05 kHzGood default balance
high22.05 kHzBest quality, more CPU

Multi-speaker voices expose several speakers in one model (selectable by speaker id). You can also fine-tune/train new Piper voices from your own data using the training scripts.

Catalogue re-derived (2026-09-01) from voices.json in the Hugging Face repo rhasspy/piper-voices — that is where the models are hosted; there is no rhasspy/piper-voices repository on GitHub (404). It lists 175 voices across 56 language codes, distributed as medium 121, low 26, x_low 14, high 14, of which 26 are multi-speaker (the largest, en_US-libritts-high, exposes 904 speakers). The tier/sample-rate table above was re-checked against the shipped .onnx.json configs and is correct: x_low and low are 16 kHz, medium and high are 22.05 kHz. Fetch a voice with python3 -m piper.download_voices en_US-lessac-medium (list them with the same module and no argument); --data-dir controls where it writes and where -m looks.

On-device and embedded focus

Piper's whole reason for existing is local, real-time, CPU-only synthesis:

  • Runs in real time on a Raspberry Pi 4/5 with no GPU (a vendor-level claim; see the stamped measurement below).
  • No network calls — good for privacy and offline operation.
  • Small footprint — but see the measured sizes below; a medium voice is larger than "a few tens of MB".
  • Streams audio sentence by sentence, so playback can start after the first sentence rather than after the whole passage.

This makes it ideal for voice assistants (Home Assistant, Rhasspy), kiosks, accessibility tools, and any embedded product needing speech output. Home Assistant's own Piper add-on still tracks this project (its config.yaml points at OHF-Voice/piper1-gpl and defaults to en_US-lessac-medium), confirmed 2026-09-01.

Measured baseline (2026-09-01), so the performance claims are stamped rather than asserted:

  • piper-tts 1.7.0, en_US-lessac-medium, CPU-only on an Intel Xeon @ 2.10 GHz (4 vCPU, x86-64): 34.1 s of audio synthesized in 5.68 s — real-time factor 0.17, i.e. about 6× faster than real time, excluding one-off model load. Not a Raspberry Pi; treat it as an upper bound and expect a Pi 4/5 to be several times slower, which is still consistent with real-time for medium.
  • Model sizes on disk (.onnx, median across the catalogue): x_low ≈ 28 MB, low ≈ 63 MB, medium ≈ 63 MB, high ≈ 114 MB (largest high voice 137 MB). The quality tiers buy sample rate and fidelity, not a proportional size reduction — only x_low is meaningfully smaller.
  • Streaming granularity is one AudioChunk per sentence: a three-sentence input yielded exactly three chunks.
  • --cuda exists for GPU acceleration (requires the onnxruntime-gpu package); "no GPU" means none is required, not that none can be used.

Piper vs other local TTS

PiperXTTS / coqui-ttsF5-TTS / StyleTTS2

StrengthSpeed on CPU/embeddedVoice cloning, multilingualHigh-quality / zero-shot cloning
HardwareCPU, real-time on PiNeeds GPU (4–6 GB) for good speedGPU for best results
Voice cloningNo (fixed trained voices)Yes (few-second reference)Yes (zero-shot)
Best forOffline assistants, embeddedCloned/expressive voicesResearch-grade quality/cloning

Piper deliberately does not do zero-shot voice cloning — it trades that flexibility for being the fastest, lightest reliable option. For cloning or expressive prosody, reach for coqui-tts/XTTS, F5-TTS, or StyleTTS 2. Piper complements speech-to-text systems like Whisper to complete an offline voice loop.

Gotchas

  • espeak-ng phonemization drives most voices and pronunciation quality depends on it (custom words may mispronounce). Corrected 2026-09-01: you do not need to install espeak-ng separately — the piper-tts wheel embeds it. You can inject raw espeak-ng phonemes inline with [[ … ]] blocks.
  • Pick the right quality tier — high sounds better but uses more CPU; medium is the usual sweet spot; x_low for the tiniest devices.
  • Licensing moved — in the opposite direction to what this entry originally said (corrected 2026-09-01). Newer Piper is GPL-3.0-or-later (OHF-Voice/piper1-gpl, all piper-tts releases from 1.3.0 on); the older rhasspy/piper line was MIT and is now archived. If licence matters, this is the direction that matters: the current, maintained, actively released Piper is copyleft.
  • Voice files are paired — you need both the .onnx and its .onnx.json; a missing config breaks synthesis.
  • It's synthesis only — for the recognition side, combine with a local STT engine.
