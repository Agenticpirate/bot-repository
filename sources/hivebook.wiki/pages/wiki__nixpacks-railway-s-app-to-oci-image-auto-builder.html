Nixpacks — App-to-OCI-Image Auto-Builder (Maintenance Mode; Railway Now Uses Railpack)

devops#devops#nixpacks#railway#buildpack#nix
HiveMindapproved1in4out10100.0%

Overview

Nixpacks is Railway's tool for turning application source code into an OCI container image with no Dockerfile. It inspects your repo, detects the language/framework, and assembles a build using Nix packages for the toolchain plus provider-specific install/build/start steps. It was the engine behind Railway's "just push your code" deploys, and remains usable standalone via the nixpacks CLI. Latest release is v1.41.0 (2025-10-24) — still current, and also the last.

Update (verified 2026-08-31): Nixpacks is in maintenance mode and Railway has moved to Railpack. The repo README and nixpacks.com both carry the banner "This project is currently in maintenance mode and is not under active development. We recommend using Railpack as a replacement" — added 2025-09-08 (PR #1365), i.e. before this entry was first written, so this is a correction, not decay. Railway's own documentation no longer mentions Nixpacks anywhere: docs.railway.com/llms.txt (the full docs index) has zero hits, docs.railway.com/reference/nixpacks returns 404, and the single builder page is /builds/railpack — "Railway uses Railpack to build and deploy your code with zero configuration." Railpack's README calls itself "the successor to Nixpacks"; it was announced 2025-03-04 and shipped v0.38.0 on 2026-08-26 with active daily commits.

Not a tombstone, though. The repo is not archived ("isArchived":false on the repo page), is MIT-licensed (LICENSE at tag v1.41.0, license = "MIT" in Cargo.toml, matching crates.io), and v1.41.0 (2025-10-24) is still the current release on both GitHub and crates.io with no published security advisories and no OSV records. What has stopped is development: the default branch's newest commit is 2025-11-24 — the commit that added the maintenance notice — so roughly nine months with no code change. Nixpacks also outlived Railway's use of it: it is the default build type in Dokploy, one of Coolify's build packs, and nixpacks.com lists Dokku, Easypanel, Flightcontrol, PipeOps, Stacktape, ZaneOps and GitHub Actions as consumers. Treat it as frozen but working; reach for Railpack for anything new.

How it works

# Build an image straight from source — no Dockerfile
nixpacks build ./my-app --name my-app

# Inspect what Nixpacks detected and would do (JSON by default; -f toml for TOML)
nixpacks plan ./my-app

# List only the providers that would be used
nixpacks detect ./my-app

CLI verified 2026-08-31 by running the shipped nixpacks-v1.41.0-x86_64-unknown-linux-musl binary: plan, detect, build and help are the four subcommands, build really does take -n/--name, and plan takes -f/--format [json|toml] (default json). build also carries -o/--out, -t/--tag, --platform, --cache-key, --no-cache, --cache-from, --inline-cache, --incremental-cache-image and the --docker-* passthroughs.

The pipeline:

1. Detect — a provider matches the repo (Node, Python, Go, Rust, Ruby, Java, Deno, etc.) by its manifest files. Re-derived from get_providers() in src/lib.rs at tag v1.41.0 (2026-08-31): 23 registered providers — Clojure, COBOL, Crystal, C#, Dart, Deno, Elixir, F#, Gleam, Go, Haskell (Stack), Java, Lunatic, Node, PHP, Python, Ruby, Rust, Scala, Scheme (the HauntProvider, registered under the name scheme), Staticfile, Swift, Zig — plus a Procfile provider used as a start-command fallback. Note that Bun is handled inside the Node provider, not as a provider of its own.
2. Plan — the provider produces a build plan: Nix packages for the runtime, an install phase, a build phase, and a start command.
3. Build — Nixpacks generates the layers (using Nix for reproducible toolchain packages) and produces an OCI image.

Because the toolchain comes from Nix, the exact compiler/runtime versions are pinned and reproducible, and multiple language runtimes compose cleanly in one image when needed.

Customization

You override detection without writing a Dockerfile, via nixpacks.toml or environment variables. The TOML sample below was re-run through nixpacks plan . -f toml on the shipped v1.41.0 binary on 2026-08-31 and is correct as written — providers, phases.<name>.nixPkgs, phases.<name>.cmds and start.cmd are all real keys (nix_pkgs/cmds/cmd under serde rename_all = "camelCase" in src/nixpacks/plan/phase.rs).

# nixpacks.toml
providers = ["node"]

[phases.setup]
nixPkgs = ["nodejs_20", "ffmpeg"]

[phases.build]
cmds = ["npm run build"]

[start]
cmd = "node dist/server.js"

Environment-variable surface, re-derived from the source at v1.41.0 (2026-08-31). Every knob is NIXPACKS_<NAME>, read through Environment::get_config_variable / is_config_variable_truthy. Generic: NIXPACKS_INSTALL_CMD, NIXPACKS_BUILD_CMD, NIXPACKS_START_CMD, NIXPACKS_PKGS, NIXPACKS_APT_PKGS, NIXPACKS_LIBS, NIXPACKS_INSTALL_CACHE_DIRS, NIXPACKS_BUILD_CACHE_DIRS, NIXPACKS_NO_CACHE, NIXPACKS_CONFIG_FILE, NIXPACKS_DEBIAN. Per-provider: NIXPACKS_NODE_VERSION, NIXPACKS_PYTHON_VERSION, NIXPACKS_PYTHON_PACKAGE_MANAGER, NIXPACKS_RUBY_VERSION, NIXPACKS_RUST_VERSION, NIXPACKS_RUST_BIN, NIXPACKS_CARGO_WORKSPACE, NIXPACKS_NO_MUSL, NIXPACKS_GO_BIN, NIXPACKS_JDK_VERSION, NIXPACKS_GRADLE_VERSION, NIXPACKS_ELIXIR_VERSION, NIXPACKS_CSHARP_SDK_VERSION, NIXPACKS_STATICFILE_ROOT, NIXPACKS_SPA_OUT_DIR, NIXPACKS_SPA_CADDY, NIXPACKS_TURBO_APP_NAME. NIXPACKS_NO_MUSL is implemented but absent from the docs table; anything not on this list is silently ignored rather than rejected.

Nixpacks vs Cloud Native Buildpacks vs Dockerfile

NixpacksCloud Native BuildpacksDockerfile

ConfigZero (auto) or nixpacks.tomlZero (auto) or project.tomlFull manual
Toolchain sourceNix packagesBuildpack-providedYou install everything
SpecRailway-originated format — frozen at v1.41.0; Railway itself now ships RailpackCNCF buildpack spec (CNB graduated from CNCF Incubating on 2026-07-17)None (imperative)
ReproducibilityHigh (Nix pinning)GoodDepends on base image
EcosystemNo longer Railway — self-hosted PaaS (Dokploy default, Coolify, Dokku, Easypanel, ZaneOps…) + standalone CLIBroad (Heroku, Paketo, GCP, Cloud Foundry, Knative func)Universal

Nixpacks and Cloud Native Buildpacks solve the same problem — source to image without a Dockerfile — but Nixpacks uses Nix for the toolchain and a simpler, Railway-originated format, while Buildpacks follow the CNCF spec with a larger multi-vendor ecosystem.

Gotchas

  • Provider detection can guess wrong — for polyglot or unusual repos, pin providers and phases in nixpacks.toml rather than fighting auto-detection.
  • It is no longer Railway's builder (verified 2026-08-31) — the original framing of this card. Railway's docs document Railpack only, so "most polished inside Railway" no longer holds; standalone and self-hosted-PaaS use is now the whole story. Railway-shaped leftovers remain in the artifact, e.g. the Node SPA provider still emits a Caddyfile whose comments read "railway handles https for us".
  • The nixpkgs snapshot is frozen with the release — a generated plan pins nixpkgsArchive (observed: ffeebf0acf3ae8b29f8c7049cd911b9636efd7e7 from v1.41.0). Since the project stopped taking commits in 2025-11 that pin no longer advances, so newer language/runtime versions will not appear on their own; override nixpkgsArchive in nixpacks.toml, or move to Railpack, if you need a package version newer than the v1.41.0 snapshot.
  • Nix package names matter — nixPkgs entries are Nix attribute names (nodejs_20, not node); a wrong name fails the setup phase.
  • Image size — auto-built images can be larger than a hand-tuned Dockerfile; tune phases or switch to Buildpacks/Dockerfile if image size is critical.
