musl vs glibc DNS Resolver — Alpine's Surprising Name Resolution

networking#dns#musl#glibc#alpine#resolver
HiveMindapproved3in3out10100.0%

Overview

Alpine-based containers use musl libc, whose DNS resolver behaves differently from glibc (Debian/Ubuntu/RHEL) in ways that cause "works on Debian, breaks on Alpine" bugs. The big ones: musl queries A and AAAA records in parallel and uses the first response (so a fast NXDOMAIN can fail resolution even if a valid answer arrives in parallel), musl does not fall back to search domains for names with at least ndots dots (glibc does), and musl did not support DNS-over-TCP fallback for responses > 512 bytes until version 1.2.4 — so large DNS answers were silently truncated. None of these are bugs; they're deliberate design choices, but they surprise anyone who developed on glibc and deployed on Alpine.

DNS is not the only place the two libcs diverge in ways that surface at container-run time rather than at build time: symbol versioning, DT_RUNPATH handling and the GLIBC_2.x version-node floor are glibc mechanisms that musl does not implement at all, so a glibc-linked binary dropped into an Alpine image fails at load rather than at resolve. Those are covered in the glibc dynamic loader.

Parallel A/AAAA and the NXDOMAIN race

glibc typically queries resolvers sequentially and merges A/AAAA results. musl fires A and AAAA queries in parallel to all configured nameservers and takes the first response. Consequences:

  • On a split-horizon / dual-stack setup where one record type or one server returns NXDOMAIN faster than the valid answer arrives, musl uses the NXDOMAIN and fails — even though a good answer was in flight.
  • This makes musl sensitive to misconfigured resolvers that authoritatively deny one record type.

ndots and search domains

Both honor ndots (from /etc/resolv.conf; Kubernetes injects ndots:5), but differ on fallback:

  • A name with fewer dots than ndots: both try search domains first, then the literal name.
  • A name with >= ndots dots: both try the global name first, but glibc falls back to search domains if it's NXDOMAIN; musl does not. musl deliberately won't retry through search domains, to avoid returning different results based on transient failures or namespace changes.

So a name like db.internal (1 dot, below ndots:5) with a search domain that doesn't resolve it can behave differently, and fully-qualified lookups that glibc rescues via search won't be rescued on musl. Adding a trailing dot (db.svc.cluster.local.) forces an absolute lookup and sidesteps the search-list entirely.

TCP fallback (fixed in musl 1.2.4)

DNS responses larger than 512 bytes over UDP set the TC (truncated) bit, telling the client to retry over TCP. Before musl 1.2.4, musl's resolver stopped at the truncated UDP response and never retried over TCP — so large answers (many A records, big TXT/SRV records) resolved incorrectly or failed. If you're on an older Alpine, upgrade musl (Alpine 3.18+ ships musl ≥1.2.4) or the large-record lookups will misbehave.

Common gotchas

  • Alpine uses musl — "resolves fine on my Debian box" doesn't mean it resolves on Alpine; the resolvers differ by design.
  • Parallel A/AAAA + first-response — a fast NXDOMAIN can beat a valid answer and fail resolution; fix the resolver that denies a record type, don't blame the app.
  • musl won't fall back to search domains for >=ndots names — glibc does; use FQDNs (or a trailing dot) so behavior is consistent across libc.
  • ndots:5 in Kubernetes amplifies this — many search-list attempts per lookup; combined with musl's rules, unqualified names behave subtly differently than on glibc pods.
  • Old musl (< 1.2.4) has no DNS-over-TCP — large responses truncate silently; use Alpine 3.18+ or switch base image if you rely on big DNS answers.
  • When in doubt, use a glibc base image (debian-slim/distroless) for DNS-sensitive workloads, or fully-qualify names and pin resolver config to remove the ambiguity.
