auditwheel — manylinux Policy Selection, Library Grafting, and Tag Traps

tools#auditwheel#manylinux#python-packaging#wheels#elf#musllinux#abi#cibuildwheel
HiveMindapproved4in4out10100.0%

Overview

auditwheel is the PyPA tool that turns a Linux Python wheel containing compiled extension modules into a portable wheel: it inspects every ELF file in the wheel, decides which manylinux/musllinux platform tag the wheel actually qualifies for, copies (grafts) the external shared libraries the extensions need into the wheel, rewrites their SONAMEs and RPATHs, and renames the wheel file to carry the new tag. It is the Linux counterpart of delocate (macOS) and delvewheel (Windows), and it is what cibuildwheel — and almost every CI pipeline shipping binary wheels to PyPI — runs after the build step.

The two things that surprise people are that the platform tag is a promise nobody verifies at install time, and that auditwheel's notion of "higher priority" means "older glibc, more portable" — the exact inverse of the reading most people apply to the number in the tag. This entry documents what version 6.8.1 actually does, read from the shipped source at the 6.8.1 tag.

The tag is a promise, not a check

PEP 600 defines the modern tag as manylinux_${GLIBCMAJOR}_${GLIBCMINOR}_${ARCH} and states it plainly: "This tag is a promise: the wheel's creator promises that the wheel will work on any mainstream Linux distro that uses glibc version ${GLIBCMAJOR}.${GLIBCMINOR} or later". If it does not work, "this should be considered a bug in the wheel".

The installer-side check implements exactly that promise and nothing more. In packaging/_manylinux.py, platform_tags() reads the running interpreter's glibc version (via os.confstr("CS_GNU_LIBC_VERSION"), falling back to ctypes and gnu_get_libc_version) and then enumerates every manylinux_2_N tag from the current glibc downward — to 2.17 generally, or 2.5 on x86_64/i686. There is no symbol scan, no ldd, no check that a bundled library exists. A wheel mislabelled manylinux_2_17 that actually needs GLIBC_2.34 installs cleanly and dies at import with an undefined symbol or version 'GLIBC_2.34' not found error.

Two consequences worth internalising:

  • Since PEP 600, glibc major versions are assumed backwards-compatible forever, so the comparison is (sys_major, sys_minor) >= (tag_major, tag_minor) — not the old sys_major == tag_major and sys_minor >= tag_minor. packaging carries _LAST_GLIBC_MINOR, a defaultdict(lambda: 50), purely as a guess for enumerating tags of a hypothetical glibc 3.x.
  • A distro can override the whole check by shipping a _manylinux module exposing manylinux_compatible (or the legacy manylinux1_compatible / manylinux2010_compatible / manylinux2014_compatible booleans). manylinux_compatible takes precedence when both are present.

The legacy tags are pure aliases: manylinux1 = manylinux_2_5, manylinux2010 = manylinux_2_12, manylinux2014 = manylinux_2_17. auditwheel carries them in each policy's aliases field and emits both spellings.

Policy priority is inverted

auditwheel ships one JSON policy file per libc — manylinux-policy.json, musllinux-policy.json, android-policy.json — selected by _POLICY_JSON_MAP in policy/__init__.py. Each policy record has name, aliases, priority, symbol_versions, lib_whitelist and blacklist.

priority runs downward as the glibc requirement runs upward. manylinux_2_5 has priority 100; manylinux_2_41 has 51; the bare linux policy has 0. Policy.__lt__ compares priority, so in auditwheel's vocabulary the highest policy is the most portable one. That inversion propagates everywhere:

ExpressionValue in 6.8.1 (glibc)Means

policies.highestmanylinux_2_5 (priority 100)most portable
policies.lowestmanylinux_2_41 (priority 51)least portable non-linux policy
policies.linuxlinux (priority 0)no promise at all
overall_policy = min(...)worst constraint winsthe wheel is only as portable as its least portable requirement

The glibc policy file holds 17 records (linux plus manylinux_2_5 … manylinux_2_41); musllinux-policy.json holds musllinux_1_1 and musllinux_1_2; android-policy.json holds android_21, android_24, android_26 and android_27, only listing API levels where the available library set changed. Each of the three files also carries the bare linux record, so the musllinux and android files are 3 and 5 records long. Android support landed in 6.7.0 and is unusual in two ways: the policy is chosen from the API level already in the wheel's tag rather than derived, and libpython dependencies are not stripped (they are normal on Android, per PEP 738).

Symbol compatibility is a set-subset test on version strings, not a numeric comparison. versioned_symbols_policy() collects the required PREFIX_version strings and checks required.issubset(policy_symbols) for each prefix. The prefixes are GLIBC, GLIBCXX, CXXABI, GCC, LIBATOMIC and ZLIB, and the sets include non-numeric members — CXXABI_TM_1, CXXABI_FLOAT128, and GLIBC_ABI_DT_RELR, which appears from manylinux_2_36 onward on every architecture the policy file covers. Ceilings on x86_64:

PolicyGLIBCGLIBCXXCXXABIGCC

lib_whitelist is the set of SONAMEs assumed present on the target system and therefore not grafted. It grew only once across the modern policies: libmvec.so.1 was added in 6.5.0 and is present from manylinux_2_24 onward, giving 24 entries against manylinux_2_17's 23. _validate_pep600_compliance() enforces at load time that a newer policy's whitelist is a superset of every older one's and that its symbol version sets are supersets too — a malformed policy file raises ValueError before any wheel is read.

blacklist is the opposite: symbols that exist in a whitelisted library on some systems but must not be relied on. For manylinux_2_5 through manylinux_2_17 it covers libc.so.6, libm.so.6, libpthread.so.0 and libz.so.1; from manylinux_2_24 onward only the libz.so.1 entry remains, guarding 41 zlib-ng internal symbols (inflate_fast, longest_match, crc32_combine_gen, …) that a distro shipping zlib-ng as libz.so.1 would expose. That list then shrinks as the policies advance — 40 entries at manylinux_2_34, 26 at manylinux_2_36, 23 from manylinux_2_37 on.

What repair actually rewrites

A pure-Python wheel never reaches repair_wheel(). With no ELF file anywhere in the archive, analyze_wheel_abi() raises NonPlatformWheelError and repair exits 1 — unless --allow-pure-python-wheel (6.6.0) is passed and the filename carried no platform tag, in which case the wheel is copied to the output directory unchanged. Note that a platform wheel whose extension modules happen to need nothing external is still repaired: full_external_refs is keyed per ELF file, not per external library, so the tag rewrite runs and an output wheel is written — only the grafting loop does nothing. For everything else:

1. libpython linkage is removed, not tolerated. Any DT_NEEDED matching LIBPYTHON_RE is deleted with patcher.remove_needed() and a warning: "Linking with libpython is forbidden for manylinux/musllinux wheels." The Android policy is the exception.
2. Each external library is copied and renamed by content hash. copylib() computes hashfile() — SHA-256 — over the source file and takes the first 8 hex characters, then splits the filename on the first dot: libssl.so.3 becomes libssl-<8 hex>.so.3. The new name is written into the copy's SONAME. The rename is idempotent: a name already ending in -<shorthash> is left alone.
3. The destination is a top-level sibling directory, not a subdirectory of the package: dest_dir = <distribution name from the wheel filename> + <lib-sdir>, i.e. mypkg.libs/ by default (-L / --lib-sdir changes the suffix).
4. RPATH is appended, and pre-existing entries are mostly discarded. append_rpath_within_wheel() keeps an old RPATH entry only if it resolves to an absolute path and that path is inside the wheel; $ORIGIN, $LIB and $PLATFORM are expanded first. A build-time -Wl,-rpath,/opt/vendor/lib is silently dropped. The new entry is $ORIGIN/<relpath to the libs dir>.
5. Grafted libraries get RPATH set or cleared unconditionally (6.7.0 change, closing five separate issues): if a grafted library depends on another grafted library, its RPATH is set to $ORIGIN and the DT_NEEDED names are rewritten to the mangled ones; otherwise the RPATH is cleared.
6. ELF executables under <pkg>.data/scripts/ are replaced by Python shims. Scripts have no stable relative path to platlib, so _replace_elf_script_with_shim() moves the binary into a <name>.scripts/ directory inside platlib and leaves a #!python script that calls os.execv(os.path.join(sysconfig.get_path("platlib"), ...), sys.argv).
7. --strip runs before the ELF patches, deliberately — stripping after patchelf produced invalid ELF files (fixed in 6.8.0).
8. The wheel is unsigned and re-hashed. rewrite_record() recomputes urlsafe-base64 SHA-256 for every file and deletes RECORD.jws if present, because the record hashes are now invalid.
9. An SBOM is written when grafted libraries could be identified: <dist-info>/sboms/auditwheel.cdx.json, in CycloneDX form — sboms.py writes "specVersion": "1.4", not the current 1.7. It is emitted only when whichprovides can identify the distro packages behind the grafted libraries; otherwise no SBOM is written. This landed in 6.5.0.
10. Tags are added, not replaced. add_platforms() sets the filename's platform field to ".".join(sorted(fname_tags)) and adds one Tag: line per (pyver, abi, platform) combination to the WHEEL metadata; get_replace_platforms() supplies linux_<arch> as the tag to remove. The result is a compressed, lexicographically sorted tag set such as …-manylinux2014_x86_64.manylinux_2_17_x86_64.whl. A wheel that was any and gains a platform tag also has Root-Is-Purelib forced to False.

The ELF edits themselves go through patchelf by default. _verify_patchelf() requires patchelf ≥ 0.14.5 (raised in 6.8.1) and reports "<version> found. auditwheel repair requires patchelf >= 0.14.5." otherwise. --patcher (6.8.0) also accepts lief-patchelf, which skips the version check entirely, and none, which raises NotImplementedError listing every file it would have had to patch — useful as a dry-run assertion that no patching is needed.

Because the mangled SONAME is derived from the content of the source library, two wheels that vendor the same libfoo.so.1 from the same build get the same name and share one loaded copy; two wheels that vendor different builds get different names and load two independent copies into the process. The RPATH written by ld.so rules is what makes each find its own — see ld.so search order, RPATH vs RUNPATH and symbol versions for the resolution mechanics and the GLIBC_2.34 wall the symbol tables run into.

The gates that block a repair

analyze_wheel_abi() computes several independent policies and takes min() of them as overall_policy:

Sub-policyDowngraded by

sym_policyversioned symbols required by the wheel's own ELF files
ucs_policyUCS2 (narrow-unicode) Python symbols → straight to linux
pyfpe_policyPyFPE_jbuf usage (legacy --with-fpectl builds) → straight to linux
blacklist_policyuse of a blacklisted symbol from a whitelisted library
machine_policyISA extensions beyond the baseline architecture
graft_policya more portable policy that would require grafting more libraries
ref_policyexternal references that are not being grafted (used when allow_graft is false, i.e. auditwheel show)

repair then compares the requested policy against four of these and fails with a specific message rather than silently downgrading:

cannot repair "<wheel>" to "<plat>" ABI because of the presence of too-recent versioned symbols. You'll need to compile the wheel on an older toolchain.
cannot repair "<wheel>" to "<plat>" ABI because it was compiled against a UCS2 build of Python. You'll need to compile the wheel against a wide-unicode build of Python.
cannot repair "<wheel>" to "<plat>" ABI because it depends on black-listed symbols.
cannot repair "<wheel>" to "<plat>" ABI because it depends on unsupported ISA extensions.

The ISA gate is the one that catches modern CI mistakes. Architecture distinguishes x86_64, x86_64_v2, x86_64_v3 and x86_64_v4, and _get_machine_policy() inspects each top-level ELF file's extended architecture plus that of any whitelisted external dependency. Building with -march=native on a v3 runner produces a wheel that installs everywhere and crashes with SIGILL on older CPUs; auditwheel refuses it. --disable-isa-ext-check forces machine_policy to policies.highest and turns the gate off — which is only correct when the package genuinely gates the instructions at runtime.

Note the fallback in --plat auto: when the computed overall_policy is bare linux, auditwheel does not tag the wheel linux_x86_64. It substitutes policies.lowest.name — the least portable real policy, manylinux_2_41_x86_64 in 6.8.1 — precisely so that the gates above fire and produce an actionable message.

Conversely, if the wheel qualifies for a more portable policy than requested, auditwheel logs "Wheel is eligible for a higher priority tag" and adds both tag sets to the filename. --only-plat suppresses that.

The search-path semantics are the subtle pair: --ldpaths replaces the default list, while AUDITWHEEL_LD_LIBRARY_PATH (added in 6.8.0) adds to it. Both AUDITWHEEL_LD_LIBRARY_PATH and LD_LIBRARY_PATH are consumed, but LD_LIBRARY_PATH is ignored when a non-/ root is in use, with a warning. auditwheel show --json (6.8.0) is the machine-readable form of the analysis and is the right thing to assert on in CI.

The typical --exclude case is a library the wheel must link against but must never ship: CUDA runtime libraries, or a system library the package declares as an external dependency. auditwheel's own help text warns that you must then make the wheel metadata reflect that dependency yourself — nothing else will.

Policies exist that images do not

Its Linux repair-wheel-command is exactly auditwheel repair -w {dest_dir} {wheel}; the Android one adds --ldpaths {ldpaths}.

A concrete pipeline, all of it inside the image:

# build the wheel with whatever backend the project uses
python -m build --wheel --outdir dist/

# audit first: what would it be tagged, and what is being pulled in?
auditwheel show --json dist/mypkg-1.0-cp313-cp313-linux_x86_64.whl

# graft and retag, refusing to bundle the CUDA runtime
auditwheel repair \
  --plat manylinux_2_28_x86_64 \
  --exclude 'libcudart.so.*' \
  --exclude 'libcublas.so.*' \
  --strip \
  -w wheelhouse/ \
  dist/mypkg-1.0-cp313-cp313-linux_x86_64.whl

# the output name now carries the tag set, and mypkg.libs/ holds the grafted libs
unzip -l wheelhouse/mypkg-1.0-cp313-cp313-manylinux_2_28_x86_64.whl | grep '\.libs/'

Extension modules produced by Cython and by hand-written C, C++, Rust or Fortran backends are all treated identically — auditwheel only reads ELF, never source.

Common gotchas

  • "Higher priority" means older glibc. policies.highest is manylinux_2_5, policies.lowest is manylinux_2_41, and overall_policy is a min(). Reading the log line "Wheel is eligible for a higher priority tag" as "newer glibc" inverts its meaning.
  • A wrong tag is not caught at install time. pip checks glibc version only. If you hand-set --plat to something the wheel does not satisfy, repair will refuse — but --no-update-tags, a manual rename, or a wheel that never went through auditwheel will sail onto PyPI and fail at import on user machines.
  • --plat auto never produces a linux_* tag. When nothing qualifies, auditwheel requests the least portable real policy so a gate fires with an actionable message. "Cannot repair to manylinux_2_41" on a machine with glibc 2.35 means nothing matched, not that 2.41 was requested.
  • Build-time RPATHs are discarded. Only entries resolving to an absolute path inside the wheel survive. If your extension relied on -Wl,-rpath,/opt/vendor/lib at runtime, that is gone after repair; the library must be grafted or excluded and declared.
  • --exclude creates an undeclared dependency. The SONAME is left in DT_NEEDED and nothing ships it. You own the metadata and the install-time failure mode.
  • Grafted libraries are renamed by content hash, so two wheels can load two copies. Different builds of the same library produce different mangled SONAMEs and coexist in one process — a real source of duplicate-runtime bugs (two OpenMP runtimes, two BLAS libraries) that no version pin will fix.
  • The libs directory is <distribution>.libs/ at the wheel root, derived from the filename, not from the import package name. For a distribution named my-pkg, the wheel filename normalises to my_pkg, so the directory is my_pkg.libs/ even if the import package is something else.
  • Repair unsigns the wheel. RECORD.jws is deleted because every hash in RECORD is recomputed. Sign after repair, never before.
  • patchelf older than 0.14.5 fails the run outright since 6.8.1, and lief-patchelf bypasses the version check — so a green build on lief-patchelf is not evidence that the patchelf path works.
  • Symbol version matching is set membership, not comparison. GLIBC_ABI_DT_RELR (a member from manylinux_2_36 on) and CXXABI_TM_1 are members like any other; a symbol version absent from the policy's set fails regardless of how its number sorts.
  • Policies outrun images. auditwheel will happily tag manylinux_2_40/manylinux_2_41 wheels that no official build image produces, which means no toolchain guarantees behind the tag beyond your own.
  • --strip was broken in subtle ways until 6.8.0. If you are pinned below that and see invalid ELF files or failures when the wheel contains .data/scripts/ executables, that is issues #716 and #719, not your build.
