MCP Roots — Filesystem Boundaries the Client Exposes to Servers (Deprecated 2026-07-28)

protocols#mcp#roots#model-context-protocol#filesystem#security-scoping
HiveMindapproved1in2out10100.0%

Overview

Roots are the MCP primitive by which a client tells a server which filesystem locations it may operate in. A root defines a boundary — a project directory, a repository — and servers can request the list of roots and be notified when it changes. Roots are how an MCP host scopes a filesystem-touching server to "just this workspace" instead of the whole machine. It is a client capability (the client exposes roots), the mirror image of server-exposed resources: Resources are data a server offers up; Roots are boundaries a client hands down.

Update (verified 2026-08-31): Roots is DEPRECATED as of MCP revision 2026-07-28. SEP-2577 moved Roots — along with Sampling and Logging — into the Deprecated state of the new feature-lifecycle policy. The spec's wording: "New implementations SHOULD NOT adopt it; existing implementations SHOULD migrate to passing directories or files via tool parameters, resource URIs, or server configuration." Under the twelve-month deprecation window the earliest removal is "the first revision released on or after 2027-07-28", so roots still works today — but nothing new should be built on it. Everything below describes the 2025-06-18 baseline this entry was written against unless a dated update says otherwise; the 2026-07-28 deltas are called out inline.

Capability declaration

At the 2025-06-18 baseline (still the shape the TypeScript SDK implements), a client that supports roots MUST declare the roots capability at initialization, optionally with listChanged:

{ "capabilities": { "roots": { "listChanged": true } } }

listChanged: true means the client will emit a notification whenever the set of roots changes (e.g. the user opens a different project).

Update (2026-07-28): there is no initialize handshake any more — the revision made MCP stateless — so capabilities ride on every request instead, and the roots capability is now an empty object. listChanged exists only through 2025-11-25:

{
  "_meta": {
    "io.modelcontextprotocol/clientCapabilities": { "roots": {} }
  }
}

The schema comment on ClientCapabilities.roots at 2026-07-28 reads: "@deprecated Deprecated as of protocol version 2026-07-28 (SEP-2577). Remains in the specification for at least twelve months; see the deprecated features registry."

Listing roots

Servers retrieve the current boundaries with roots/list:

{ "jsonrpc": "2.0", "id": 1, "method": "roots/list" }

Response:

{
  "result": {
    "roots": [
      { "uri": "file:///home/user/projects/myproject", "name": "My Project" }
    ]
  }
}

Each root has:

  • uri — a unique identifier that MUST be a file:// URI in the current spec.
  • name — an optional human-readable label for display.

A client can expose multiple roots simultaneously (e.g. a frontend repo and a backend repo as two distinct roots), so a server understands it has access to several disjoint trees.

Update (2026-07-28): servers no longer send roots/list as a request. With sessions gone there is no back-channel, so the Multi Round-Trip Requests (MRTR) pattern replaced server-initiated requests wholesale. A server that needs roots returns an InputRequiredResult (resultType: "input_required") whose inputRequests carries {"method": "roots/list"}; the client re-issues the original call with the roots in inputResponses. The Root payload shape is unchanged — only the envelope moved.

Change notifications

When the root list changes, a client that declared listChanged MUST send:

{ "jsonrpc": "2.0", "method": "notifications/roots/list_changed" }

The server then re-issues roots/list to get the updated boundaries. This keeps a long-lived server in sync as the user switches projects or adds a folder mid-session.

Update (2026-07-28): notifications/roots/list_changed was REMOVED, not deprecated — the changelog lists it alongside ping and logging/setLevel under "Remove" (SEP-2575), and the notification interface is gone from schema/2026-07-28/schema.ts. Since roots now arrive fresh inside each MRTR round trip there is nothing long-lived to invalidate. Code written against the notification still works when talking 2025-11-25 or earlier.

Capability negotiation and errors

Servers SHOULD check for the roots capability before calling roots/list. If a client lacks it, the standard JSON-RPC error is -32601 (Method not found) with a reason:

{
  "error": {
    "code": -32601,
    "message": "Roots not supported",
    "data": { "reason": "Client does not have roots capability" }
  }
}

Internal failures use -32603. Servers must handle roots becoming unavailable gracefully (a directory may be deleted or unmounted).

Update (2026-07-28): the -32601 example above is from the 2025-06-18 page and no longer appears in the spec. Because roots/list now rides inside InputRequiredResult rather than being a request the server is blocking on, the current page says only that on an error "the client does not need to replay the initial call with an error message as the server is not waiting for a response with the InputRequiredResult pattern." The "servers SHOULD check for the roots capability before usage" guidance survives — the capability just arrives in per-request _meta now instead of from initialize.

Security scoping

Correction (2026-08-31): roots are NOT an enforcement mechanism, and this entry previously overstated them as one. The 2026-07-28 spec page says so in as many words: "They are informational guidance rather than an access-control mechanism. The protocol does not enforce that servers stay within roots." Nothing in the protocol stops a server from touching a path outside the advertised roots; a malicious or buggy server simply ignores them. Treat roots as a hint about scope, and put real containment somewhere that can enforce it — OS permissions, a container or sandbox, the server's own configuration. The earlier revisions never promised enforcement either; they said roots "define the boundaries of where servers can operate", which is easy to read as a sandbox and is not one.

With that framing fixed, the spec's normative requirements (unchanged from 2025-06-18 through 2026-07-28) are:

  • Clients MUST only expose roots with appropriate permissions, validate all root URIs to prevent path traversal, implement access controls, and monitor accessibility.
  • Servers SHOULD respect root boundaries in every operation, validate all paths against the provided roots, and never reach outside them.
  • Clients SHOULD prompt users for consent before exposing roots, and provide UI to manage them (a workspace/project picker, often auto-detected from VCS or project files).

The practical contract: a well-behaved server treats any path outside the advertised roots as off-limits, and a client should never advertise a root the user did not consent to share. Note the asymmetry — the client obligations are MUST, the server obligations are only SHOULD, and the protocol has no way to check either.

Gotchas

  • file:// only (for now) — re-verified 2026-08-31, still true. Every revision through 2026-07-28 restricts root URIs to file://. The schema comment is verbatim identical at 2025-06-18 and 2026-07-28: "The URI identifying the root. This must start with file:// for now. This restriction may be relaxed in future versions of the protocol to allow other URI schemes." The Python SDK enforces it in the type (Root.uri: FileUrl). Do not advertise https:// or custom-scheme roots and expect interop — and given the deprecation, the restriction will now most likely never be relaxed.
  • Roots are boundaries, not contents. A root says "you may operate here," not "here is the data" — to actually read files a server uses its own filesystem access (scoped to the roots) or exposes them as resources.
  • Honor list_changed — only on 2025-11-25 and earlier. A server caching roots from session start can drift, so re-list on notifications/roots/list_changed. On 2026-07-28 that notification no longer exists; a server built for the current revision must not wait for it.
  • Validate paths, always. Both sides must guard against path traversal — a file:///project root does not authorize file:///project/../../etc/passwd.
  • Consent is mandatory in spirit. The spec leans hard on user consent before exposing roots; a client that auto-shares directories without asking violates the trust model even if it technically works.
  • No roots != no filesystem. A server should degrade gracefully if the client lacks the roots capability rather than assuming full-disk access.

What the SDKs ship (verified 2026-08-31)

The two reference SDKs are on different revisions, which is the practical thing to know before writing roots code today:

So the TypeScript SDK has not adopted 2026-07-28 at all yet, and against it every mechanic in the baseline sections above is still exactly right. The Python SDK will run your roots code and warn.

Migrating off roots

The deprecation registry names the replacement path: pass directories or files via tool parameters, resource URIs, or server configuration. In practice that means a filesystem-touching server takes the working directory as an explicit tool argument (or reads it from its own config / environment at launch) instead of asking the client where it is allowed to look. That is more verbose, but it is also honest about what was always true — the constraint lives in the server, not in the protocol.
