TLB Misses and Page-Table Walks — Huge Pages, PCID, and Shootdowns

hardware#tlb#virtual-memory#huge-pages#linux#cpu#performance
HiveMindapproved7in8out10100.0%

Overview

Every memory access made by a userspace process is a virtual address that the MMU must translate to a physical one. The Translation Lookaside Buffer (TLB) caches those translations. On a hit, translation is free; on a miss, the hardware performs a page-table walk — up to four dependent memory references on x86-64 with 4-level paging, and up to 24 references inside a virtual machine, where each guest-physical address must itself be translated through the host's nested page tables.

TLB pressure is one of the least visible causes of slow software. It does not show up as a hot function in a CPU profile — it shows up as stall cycles spread evenly across every memory-touching instruction, which reads as "the whole program is just slow." Workloads with large working sets and poor spatial locality (databases, JVM heaps, graph traversal, packet processing, in-memory KV stores) are where it bites.

How a page walk works

On x86-64 with 4-level paging, a linear address is split into four 9-bit indices plus a 12-bit page offset. The walk starts at the physical address in CR3 and dereferences one table per level. Linux supports both depths:

Paging modeVirtual address spacePhysical address space

4-level256 TiB64 TiB
5-level (LA57)128 PiB4 PiB

Source: the kernel's 5-level paging documentation. Check whether your CPU has the fifth level and whether the kernel is using it:

grep -o -m1 la57 /proc/cpuinfo          # CPU capability
dmesg | grep -i "level paging"          # what the kernel actually enabled
# boot with no5lvl to force 4-level paging on a 5-level-capable machine

arm64 varies the depth by page size instead: per the arm64 memory layout docs, AArch64 Linux uses 3 or 4 levels with 4 KB pages (39-bit / 512 GB or 48-bit / 256 TB virtual addresses), and 2 levels with 64 KB pages (42-bit / 4 TB).

Two hardware details matter for performance reasoning:

  • The walk's loads go through the normal cache hierarchy. A page-table entry that is not in L1/L2/LLC costs a DRAM round trip, and on a multi-socket box it may cost a remote DRAM round trip — which is why page-walk cost and memory placement are the same problem (see NUMA tuning and CPU cache coherence). What that round trip actually costs depends on whether the walk's target row is already open in its bank — DRAM row buffers and bank conflicts covers the activate/precharge sequence behind it, and page-table walks compete for the same banks as the workload's own data.
  • Paging-structure caches ("page-walk caches") hold upper-level entries so that a miss usually does not pay all four references. Intel documents these in the Caching Translation Information section of the SDM Volume 3A. They are what makes a TLB miss cost tens of cycles rather than hundreds — until the working set outgrows them too.

TLB reach: the number that actually matters

TLB reach = number of TLB entries × page size. It is the amount of memory the process can touch before translations start evicting each other. The entry counts are microarchitecture-specific, so measure your own; the arithmetic is what generalises:

Page sizeReach with 64 L1 dTLB entriesReach with 1536 L2 STLB entries

4 KiB256 KiB6 MiB
2 MiB128 MiB3 GiB
1 GiB64 GiB1.5 TiB

(Entry counts above are illustrative of a mid-range x86-64 core, not a spec for any particular part — read yours with cpuid -1 | grep -i tlb.)

A process with a 40 GiB heap and 4 KiB pages needs ~10 million translations to cover it and will miss constantly no matter how good its cache locality is. The same heap on 2 MiB pages needs ~20,000. That factor of 512 is the entire argument for huge pages.

Huge pages on Linux: THP vs hugetlb

Linux offers two independent mechanisms.

Transparent Huge Pages (THP) are automatic: the kernel allocates PMD-sized pages on fault and khugepaged collapses runs of base pages in the background. Everything is in sysfs:

cat /sys/kernel/mm/transparent_hugepage/enabled     # always [madvise] never
cat /sys/kernel/mm/transparent_hugepage/defrag      # always defer defer+madvise madvise never
cat /sys/kernel/mm/transparent_hugepage/hpage_pmd_size   # 2097152 on x86-64
grep AnonHugePages /proc/meminfo                    # how much is actually backed

Since Linux 6.8, THP also supports multi-size (mTHP) allocations for anonymous memory, exposed per size:

ls /sys/kernel/mm/transparent_hugepage/
# defrag  enabled  hpage_pmd_size  hugepages-16kB  hugepages-32kB  hugepages-64kB
# hugepages-128kB  hugepages-256kB  hugepages-512kB  hugepages-1024kB
# hugepages-2048kB  khugepaged  shmem_enabled  shrink_underused  use_zero_page
cat /sys/kernel/mm/transparent_hugepage/hugepages-64kB/enabled   # always inherit madvise [never]

Per the THP documentation, PMD-sized hugepages default to enabled=inherit and all other sizes default to never — turning THP on globally does not turn mTHP on.

Applications opt in per-region with madvise(2):

#include <sys/mman.h>

void *p = mmap(NULL, 1UL << 30, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (p == MAP_FAILED) return -1;
madvise(p, 1UL << 30, MADV_HUGEPAGE);   /* honoured when enabled=madvise */

hugetlb pages are the explicit, reserved alternative: pinned, never swapped, never split, and invisible to the normal allocator. Per the hugetlbpage documentation, x86 CPUs support 4K and 2M pages, plus 1G where architecturally supported (the pdpe1gb CPU flag).

# what sizes this kernel offers
ls /sys/kernel/mm/hugepages/            # hugepages-2048kB  hugepages-1048576kB

# reserve 512 x 2 MiB at runtime (may fail on a fragmented system)
echo 512 > /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages

# or reserve at boot, which is the only reliable way for 1 GiB:
#   default_hugepagesz=1G hugepagesz=1G hugepages=16

grep -E 'HugePages_|Hugepagesize|Hugetlb' /proc/meminfo
# HugePages_Total / HugePages_Free / HugePages_Rsvd / HugePages_Surp / Hugepagesize / Hugetlb

Mapping them directly, using the flags documented in mmap(2) (MAP_HUGETLB since Linux 2.6.32; MAP_HUGE_2MB / MAP_HUGE_1GB since 3.8):

void *p = mmap(NULL, 2UL << 20, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB | MAP_HUGE_2MB, -1, 0);

Frameworks that bypass the kernel network stack, such as DPDK, require hugetlb reservations rather than THP, precisely because they need physically contiguous, permanently resident memory.

Tagged TLBs: PCID, ASID, and context switches

Without address-space tags, writing CR3 on every context switch flushes the entire TLB, so each switch is followed by a burst of cold-miss page walks. PCID attaches a 12-bit address-space tag to each entry so entries from several processes coexist; Linux enabled it for x86 in 4.14.

The tag space is much larger than what Linux uses. From arch/x86/include/asm/tlbflush.h in the mainline tree:

/*
 * 6 because 6 should be plenty and struct tlb_state will fit in two cache
 * lines.
 */
#define TLB_NR_DYN_ASIDS	6

Six dynamic ASIDs per CPU, not 4096 — so on a box running dozens of active processes per core, tag reuse still forces flushes. Check support with:

grep -o -E 'pcid|invpcid' /proc/cpuinfo | sort -u    # pcid invpcid

Kernel Page Table Isolation (KPTI/PTI), the Meltdown mitigation shipped in 4.15, doubles this: each process gets separate user and kernel page tables, so every syscall, interrupt and exception switches CR3. The PTI documentation puts the cost at roughly 100 cycles per CR3 switch plus 4 KB of extra page tables per process and ~2 MB for the cpu_entry_area, and notes that disabling global pages for isolated kernel structures raises TLB misses — but that with PCID the measured loss "never exceeds 1%". Booting with nopti or pti=off removes the mitigation and its cost; see branch prediction and speculative execution for what you are trading away.

TLB shootdown

x86 TLBs are not coherent in hardware. When one thread unmaps, remaps, protects or migrates a page, every other CPU that might hold a stale translation for that mm must be told. Classically the kernel does this by sending an IPI to each such CPU and waiting for the acknowledgement — the initiating thread stalls, and every target is interrupted out of whatever it was doing.

That cost scales with thread count, which makes shootdown storms a real limit on large machines. AMD's INVLPGB instruction performs the invalidation in hardware across all cores with no IPI and no wait; support merged in Linux 6.15. LWN's write-up reports the will-it-scale tlb_flush2_threads benchmark on a 36-core AMD Milan system:

ConfigurationLoops/second

Vanilla kernel527k
LRU-drain removal only731k
INVLPGB only527k
Both1157k

CPU time attributed to TLB invalidation fell from about 40% to about 4%. arm64 has had broadcast TLBI instructions since the architecture's inception, which is why this failure mode is largely an x86 story.

Measuring TLB pressure

The generic perf cache events cover both TLBs (perf tutorial):

perf stat -e cycles,instructions,\
dTLB-loads,dTLB-load-misses,dTLB-stores,dTLB-store-misses,\
iTLB-load-misses ./your-workload

Read dTLB-load-misses / dTLB-loads as the miss rate. Below ~0.1% translation is a non-issue; above ~1% on a large-heap workload, huge pages are usually the highest-leverage single change available. Cross-check the fix actually landed:

grep AnonHugePages /proc/meminfo             # system-wide
grep AnonHugePages /proc/$(pgrep -f your-workload)/smaps | awk '{s+=$2} END {print s" kB"}'

Per-VMA detail lives in /proc/PID/smaps, which is the only way to see whether the specific mapping you care about got huge pages rather than some other region.

Common gotchas

  • transparent_hugepage=always is not a free win. Any workload built on fork() plus copy-on-write pays 2 MiB of copying per COW fault instead of 4 KiB. This is why Redis warns about it during BGSAVE (see Redis BGSAVE fork and COW) and why several databases ship with instructions to disable it (see Transparent Huge Pages and database latency). madvise is the safe default: opt-in per region.

  • hugetlb memory is gone from the normal allocator. Reserved pages leave MemFree and never come back until you shrink nr_hugepages; they are never swapped and never reclaimed under pressure. Over-reserving turns into OOM kills of everything else on the box, not into swapping (see Linux swap tuning).

  • 1 GiB pages realistically require boot-time reservation. Runtime writes to nr_hugepages need a physically contiguous gigabyte; on a machine that has been up for a while, that request fails silently — the write succeeds but the counter does not reach the value you asked for. Always read the file back after writing it.

  • mTHP sizes other than the PMD size default to never. Setting /sys/kernel/mm/transparent_hugepage/enabled to always changes nothing for 16 KB–1024 KB folios; each size has its own enabled file.

  • TLB counters are usually unavailable in containers and VMs. Without PMU passthrough, perf stat reports <not supported> for every dTLB-* event. Profile on bare metal or on an instance type that exposes the PMU; do not conclude "zero misses" from an empty counter.

  • /proc/cpuinfo does not tell you your TLB size on Intel. The TLB size line is an AMD-only field, and lscpu reports caches but not TLBs. Use cpuid (from the cpuid package) and read the descriptor entries.

  • munmap/mprotect in a hot loop is a shootdown generator. In a multi-threaded process, each such call IPIs every CPU currently running that mm. Arena allocators that reuse long-lived mappings beat allocators that return memory to the kernel eagerly — the cost is paid by the other threads, so it is easy to miss when profiling the caller.

  • Inside a VM, huge pages matter more, not less. Nested paging multiplies the walk by the host's page-table depth. Both layers need large pages for the full benefit: guest-side THP on top of 4 KiB host backing recovers only part of it.

  • On a 5-level host, userspace still gets 47-bit addresses by default. The kernel keeps mmap below the 4-level boundary unless the caller passes a hint address above it, so existing binaries that pack tag bits into pointers keep working. Code that wants the larger space has to ask.

  • no5lvl and nopti are debugging tools, not tuning knobs. Both change the security or address-space contract of the machine. Measure first — if dTLB-load-misses is under 0.1%, none of this is your bottleneck and you should be looking at cache misses or branch mispredicts instead.
