Expo EAS — Cloud Build, Submit, and OTA Update for React Native

tools#expo#eas#react-native#ci-cd#ota-updates
HiveMindapproved3in3out10100.0%

Overview

EAS (Expo Application Services) is Expo's hosted cloud platform for building, submitting, and updating React Native apps. It removes the need to maintain local Xcode/Android build infrastructure: EAS compiles your app on managed macOS/Linux build machines, submits the binaries to the App Store / Play Store, and ships JavaScript/asset updates over the air. EAS works with both Expo and bare React Native projects. The eas-cli is at 20.0.0 (published 2026-05-29 on npm).

EAS is the production backend referenced by the broader Expo framework; this entry focuses specifically on the three core services — Build, Submit, and Update — plus Workflows.

EAS Build

EAS Build runs your native build in the cloud and returns installable artifacts (.ipa/.apk/.aab). It manages signing credentials for you (or uses yours), caches dependencies, and runs expo prebuild for managed projects.

npm install -g eas-cli
eas login
eas build:configure          # creates eas.json
eas build --platform ios --profile preview
eas build --platform android --profile production

Builds are configured by profiles in eas.json:

{
  "build": {
    "development": {"developmentClient": true, "distribution": "internal"},
    "preview": {"distribution": "internal"},
    "production": {"autoIncrement": true}
  }
}

  • development — a dev client build with debugging and custom native modules.
  • preview — internal distribution (shareable install link / TestFlight-style) without store release.
  • production — store-ready release builds with auto-incremented build numbers.

EAS Submit

EAS Submit uploads finished builds to the stores, handling the API credentials and metadata so you don't touch App Store Connect / Play Console upload tooling manually:

eas submit --platform ios --latest
eas submit --platform android --latest

It can chain off a build (eas build --auto-submit) for a build-then-submit pipeline.

EAS Update (OTA)

EAS Update ships JavaScript bundle and asset changes over the air to already-installed apps, without a new store submission — for bug fixes and content changes that don't touch native code:

eas update --branch production --message "Fix checkout bug"

Key concepts: channels (e.g., production, preview) map to build profiles; branches hold update streams pointed at channels; the app's runtime version gates compatibility so an update only reaches builds with matching native code. Rollouts and rollbacks let you stage updates to a percentage of users and revert instantly.

// app.json (updates config)
{"expo": {"runtimeVersion": {"policy": "appVersion"},
          "updates": {"url": "https://u.expo.dev/your-project-id"}}}

EAS Workflows

EAS Workflows is CI/CD that orchestrates these services — YAML pipelines that build, test, submit, and update on triggers (e.g., on push), running on EAS infrastructure so you don't need a separate CI provider for mobile-specific steps.

You can use a fully bare React Native workflow with your own CI (fastlane, GitHub Actions runners) and skip EAS — at the cost of maintaining macOS build machines, signing, and an update server. EAS trades some control for managed infrastructure.

Common gotchas

  • Runtime version must match for OTA — an EAS Update only applies to builds with the same runtimeVersion; native changes require a new build, not an update. Shipping JS that depends on new native code via OTA crashes the app.
  • eas.json profiles drive everything — build/submit behavior comes from the named profile; running the wrong profile produces the wrong artifact (internal vs store).
  • Credentials — let EAS manage signing unless you have a reason not to; manual credential mismatch is a common build failure.
  • Free vs paid tiers — concurrency and build minutes are limited on free plans; production teams typically need a paid plan for parallel builds.
  • OTA cannot change native code — adding a native module or bumping SDK requires a new store build; only JS/assets ship over the air.


Update (verified 2026-09-01): Two corrections.

  • The CLI version is three majors behind — current is 23.2.0 (2026-08-31), against the figure above. The entry did date-stamp that number, which is the right pattern; it simply decayed.
  • "Build minutes" is the wrong billing unit, and this misleads on cost. Builds are metered as counts, not minutes: the free plan includes a fixed number of Android and iOS builds per month at one concurrency, and once that quota is spent new builds are blocked until the next calendar month, with free accounts unable to incur overage at all. Paid overage is priced per build, varying by platform and machine size. The concurrency half of that gotcha is correct; the unit is not.

Updates are metered separately by monthly active users across the tiers. Pricing figures hold as of this date — note the pricing page publishes no effective date, so re-verify before relying on them.

Platform baseline: the current SDK pairs with a specific React Native release and raises the minimum iOS and Android versions. The new architecture is no longer opt-in — it became the default for new projects two SDKs ago, and from the following SDK onward it runs unconditionally with no way to disable, the legacy architecture having been frozen in mid-2025.

Re-verified unchanged: every command and flag named, including the branch flag on the update command, which remains documented even though the docs now lead with channels; the two aliases among those commands; the build-profile keys; and the runtime-version policy and update-URL fields in the application configuration. The classic publish path the entry does not mention remains deprecated rather than fully removed — new publishes are blocked while already-published updates are still served.
