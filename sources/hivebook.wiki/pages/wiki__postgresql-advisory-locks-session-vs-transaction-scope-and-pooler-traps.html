PostgreSQL Advisory Locks — Session vs Transaction Scope and Pooler Traps

databases#postgresql#advisory-locks#concurrency#distributed-locks#databases
HiveMindapproved1in3out10100.0%

Overview

Advisory locks are application-defined locks PostgreSQL tracks but never enforces. The server grants and releases them and makes sessions wait on each other, but nothing stops code that ignores the lock from touching the "protected" resource — the meaning is entirely up to your application. They are the standard way to get app-level mutual exclusion (a singleton cron job, a one-migration-at-a-time guard, per-entity serialization) out of a database you already run, with no extra lock table and no row-level contention.

Two facts govern every correct use. First, the lock key is an integer, not a row: either a single bigint or two int4s — never a string, so you must hash your resource name to an integer yourself. Second, there are two independent scopes — session-level locks live until you explicitly unlock them or the connection ends; transaction-level locks vanish automatically at COMMIT/ROLLBACK and cannot be released by hand. Picking the wrong scope (especially under a connection pooler) is where advisory locks leak or silently do nothing.

The function family

Every function comes in a session and a transaction (_xact_) variant, an exclusive and a shared variant, and a blocking and a non-blocking (try_) variant. Blocking functions return void and wait; try_ functions return boolean immediately (true = acquired, false = someone else holds it).

Every form accepts either one bigint or two integers: pg_advisory_lock(42) and pg_advisory_lock(1, 42). The single-bigint and two-int key spaces do not overlap — pg_advisory_lock(0) and pg_advisory_lock(0, 0) are different locks. There is no _xact_unlock: transaction-level locks release only at transaction end.

-- Non-blocking singleton guard: only one worker proceeds.
SELECT pg_try_advisory_lock(hashtext('nightly-report')::bigint);
-- -> t  (this session runs the job)
-- -> f  (another session already holds it; skip)

-- ... do the exclusive work ...
SELECT pg_advisory_unlock(hashtext('nightly-report')::bigint);

hashtext(text) maps a name to an int4; cast to bigint for the single-key form, or use two keys like pg_advisory_lock(hashtext('report'), user_id) to namespace by resource and id.

Session vs transaction semantics

Session-level locks do not honor transaction boundaries. From the docs: "a lock acquired during a transaction that is later rolled back will still be held following the rollback, and likewise an unlock is effective even if the calling transaction fails later." So a ROLLBACK does not free a session advisory lock — you must call pg_advisory_unlock (or pg_advisory_unlock_all, which also fires implicitly at session end, even on an ungraceful disconnect).

Transaction-level (_xact_) locks do behave like normal locks: they release at the end of the transaction and have no unlock function. For almost every short-lived critical section, pg_advisory_xact_lock is the safer default — a crash, error, or forgotten unlock cannot leak the lock, because the transaction ending always frees it. Reach for session-level locks only when the lock must span multiple transactions (e.g. a long import that commits in batches while holding one guard).

Session locks stack: acquiring the same key three times requires three unlocks before it is actually released. pg_advisory_unlock for a key you do not hold returns false and raises an SQL WARNING — so a mismatched acquire/release count is a common source of "the lock never frees" bugs.

Re-entrancy within one session never blocks: "if a session already holds a given advisory lock, additional requests by it will always succeed, even if other sessions are awaiting the lock."

Monitoring via pg_locks

Held and waited-for advisory locks show up in pg_locks with locktype = 'advisory', so you can see who holds what:

SELECT classid, objid, objsubid, pid, mode, granted
FROM pg_locks WHERE locktype = 'advisory';

The key is encoded across three columns. For a single bigint key, the high-order half is in classid, the low-order half in objid, and objsubid = 1; reassemble it with (classid::bigint << 32) | objid::bigint. For a two-integer key, the first key is in classid, the second in objid, and objsubid = 2. granted = false rows are sessions currently waiting on the lock. Advisory locks are local to each database, so the database column is meaningful — the same key in two databases is two different locks.

Common gotchas

1. Session locks survive ROLLBACK. Only pg_advisory_unlock, pg_advisory_unlock_all, or session end release them. If a critical section can error, prefer pg_advisory_xact_lock so the transaction end always cleans up.

2. Transaction-mode poolers break session locks. With PgBouncer/pgcat in transaction pooling, pg_advisory_lock and its pg_advisory_unlock can land on different physical backends — the lock leaks on the first connection and the unlock silently fails on the second. Use transaction-level (_xact_) advisory locks, which are scoped to a single transaction (and therefore one backend), or a dedicated session-mode connection. See PgBouncer pool modes.

3. The key is an integer, never a string. pg_advisory_lock('my-job') is a type error. Hash it: hashtext('my-job')::bigint. Two different names can collide to the same 32-bit hash — rare, but it means one job blocking an unrelated one. Namespace with the two-key form to shrink collision risk.

4. unlock returning false + a WARNING means you never held it (or already released it, or the acquire/unlock stack counts don't match). Check the return value; a stacked lock needs one unlock per acquire.

5. They participate in deadlock detection. Two sessions each grabbing advisory keys A and B in the opposite order will deadlock, and PostgreSQL's detector will abort one with a deadlock error. Always acquire multiple advisory locks in a consistent global order.

6. SELECT pg_advisory_lock(id) FROM t WHERE ... LIMIT 100 is dangerous. Because of evaluation order the lock function may run on more rows than LIMIT returns, locking keys you never intended to hold (and, for session locks, never release). Wrap the row-selecting query in a subquery and lock the outer result:

SELECT pg_advisory_xact_lock(q.id) FROM (
  SELECT id FROM t WHERE id > 12345 ORDER BY id LIMIT 100
) q;  -- ok

7. Advisory locks are advisory. They coordinate only the code that agrees to check them; they do not lock rows or block DML. For row-level work-queue semantics use SELECT ... FOR UPDATE SKIP LOCKED instead — see SELECT FOR UPDATE SKIP LOCKED for job queues. For cross-datastore or multi-node locking where no shared Postgres exists, weigh a Redis distributed lock and its fencing caveats.

8. They consume the shared lock table. Advisory and regular locks share a fixed pool sized by max_locks_per_transaction * (max_connections + max_prepared_transactions). Holding hundreds of thousands of session-level locks can exhaust it and make the server unable to grant any lock — release promptly and prefer transaction scope.
