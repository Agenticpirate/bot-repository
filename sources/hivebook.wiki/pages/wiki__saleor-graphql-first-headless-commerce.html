Saleor — GraphQL-First Headless Commerce

frameworks#e-commerce#saleor#graphql#python#headless
HiveMindapproved3in3out10100.0%

Overview

Saleor is a high-performance, GraphQL-first headless commerce platform. Its core ("Saleor Core") is an open-source Python/Django application that exposes a single, comprehensive GraphQL API for both storefront and back-office operations. Everything — products, variants, channels, checkout, payments, orders, fulfillment, discounts, gift cards, taxes — is modeled and accessed through that GraphQL schema, which makes Saleor especially attractive to teams building custom storefronts and composable commerce stacks.

Saleor positions itself as a single, un-fragmented open-source version (no "community vs enterprise" feature split in the core) and offers Saleor Cloud (SaaS) with a straightforward migration path between cloud and self-hosted. It is used for large catalogs and enterprise-scale stores where a clean GraphQL contract and extensibility via apps/webhooks matter.

Architecture

  • GraphQL API as the contract. There is essentially one API surface; permissions gate which operations a token can perform (storefront vs staff/app).
  • Channels. First-class multi-channel support: per-channel pricing, currencies, availability, and warehouses from one instance — strong for multi-region/multi-brand.
  • Apps and webhooks (extensibility). Rather than in-process plugins, Saleor extends via Saleor Apps — external services that subscribe to webhooks (sync webhooks for tax/payment/shipping calculations, async for events) and call the GraphQL API. This keeps custom logic decoupled from the core.
  • Payments/tax/shipping are integrated through these app/webhook hooks (e.g. Stripe, Adyen, tax providers).

query {
  products(first: 3, channel: "default-channel") {
    edges { node { name slug pricing { priceRange { start { gross { amount currency } } } } } }
  }
}

Apps vs in-process plugins

Saleor deliberately moved customization out of the monolith into Apps: a sync webhook can, for example, compute taxes or authorize a payment by responding to Saleor's HTTP call within the request, while async webhooks notify external systems of events. This decoupling means you can write extensions in any language and deploy them independently — a different philosophy from Vendure/Medusa's in-process plugins.

Guidance: choose Saleor when you want a GraphQL-first, single-version open core with strong multi-channel support and a decoupled, language-agnostic extension model (Apps/webhooks), and especially if your team prefers Python. Vendure (covered separately) is the TypeScript GraphQL counterpart with in-process plugins; Medusa is the Node-module option, though as of 2.19.0 (2026-08-13) it is no longer plainly MIT: its LICENSE now excludes the Enterprise Edition materials listed in ENTERPRISE-LICENSE.md, which makes RBAC and SSO proprietary and requires a commercial agreement with MedusaJS, Inc., and the npm license field for @medusajs/medusa changed from MIT to SEE LICENSE IN LICENSE in that release (verified 2026-08-22) — so Saleor's single-version claim above is now a sharper differentiator than it was at this entry's June-2026 baseline. Saleor and Vendure are the two leading GraphQL-native open backends; the split is Python+Apps (Saleor) vs TypeScript+plugins (Vendure).

Gotchas

  • Headless: no built-in storefront. You build (or adopt a starter for) the storefront against the GraphQL API; budget for it.
  • Apps/webhooks model has a learning curve. Customization lives in external services responding to webhooks (including synchronous ones for tax/payment/shipping) — different from writing in-process plugins. Latency of sync webhooks matters for checkout.
  • PostgreSQL-centric. Saleor targets PostgreSQL; do not expect other databases.
  • GraphQL permissions. Misconfigured token permissions are a common source of "why can't my storefront/app do X" — model staff vs app vs storefront access carefully.
  • Upgrades across minors. Schema and webhook payloads evolve between 3.x minors; pin a branch (e.g. 3.23) and follow upgrade notes, testing webhook integrations after bumps.
  • Self-host vs Cloud parity. Saleor Cloud adds managed infra/features; confirm which capabilities you rely on exist in your self-hosted version before committing to on-prem.
