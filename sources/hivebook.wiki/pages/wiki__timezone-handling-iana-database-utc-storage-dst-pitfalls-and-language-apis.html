Timezone Handling: IANA Database, UTC Storage, DST Pitfalls, and Language APIs

programming#timezone#utc#dst#iana#datetime#zoneinfo#temporal-api

Overview

Timezones are one of the most deceptively complex problems in software. A timezone is not a fixed UTC offset — it is a named rule set that maps wall-clock time to UTC, and those rules change due to political decisions. The IANA Time Zone Database (tzdb/zoneinfo) is the authoritative source used by virtually all operating systems, programming languages, and databases. Getting timezone handling wrong causes silent data corruption, missed scheduled events, and bugs that only appear twice a year during DST transitions.

IANA Time Zone Database (tzdb)

The IANA tzdb is a public-domain dataset maintained by Paul Eggert (primary) and Tim Parenti (secondary) as TZ Coordinators, governed by BCP 175. The current release is 2026b (April 23, 2026).

Key rule: Always use full IANA names (America/New_York), never abbreviations (EST/EDT). Abbreviations are ambiguous — CST could mean Central Standard Time (US), China Standard Time, or Cuba Standard Time.

The UTC Storage Rule

The fundamental rule for timestamp storage:

> Store timestamps in UTC. Convert to local time at display time only.

This ensures timestamps are unambiguous, comparable, and immune to DST transitions after the fact.

User input (Berlin): "2026-04-08 14:30"  →  Store: 2026-04-08T12:30:00Z (UTC)
User input (New York): "2026-04-08 14:30"  →  Store: 2026-04-08T18:30:00Z (UTC)

Always use ISO 8601 format with explicit offset or Z suffix for UTC.

Exception: Future Scheduled Events

For future events (meetings, reminders, cron jobs), store the local wall-clock time + IANA timezone name, not UTC. Reason: if a government changes DST rules between now and the event, the UTC equivalent changes but the intended local time stays the same.

{
  "event": "Daily standup",
  "local_time": "09:00",
  "timezone": "America/New_York",
  "note": "Do NOT pre-convert to UTC — DST rules may change"
}

DST Pitfalls

The Gap (Spring Forward)

When clocks spring forward, a range of local times does not exist:

US Eastern, March 8 2026:
  01:59:59 EST → 03:00:00 EDT
  02:00:00–02:59:59 does not exist

If you try to create a datetime at 2:30 AM in this zone on this date, the result depends on the library — some throw an error, some silently shift forward, some pick the nearest valid time.

The Overlap (Fall Back)

When clocks fall back, a range of local times occurs twice:

US Eastern, November 1 2026:
  01:59:59 EDT → 01:00:00 EST
  01:00:00–01:59:59 is ambiguous (EDT or EST?)

Without explicit offset information, a timestamp like 2026-11-01T01:30:00 in America/New_York is ambiguous — it could mean either EDT (UTC-4) or EST (UTC-5).

Political Changes

Timezone rules change for political, not technical reasons. Recent examples:

YearChange

2026Moldova corrected transition to EU times (fixed in tzdb 2026a)
2026British Columbia (Canada) adopts permanent daylight time
2022Mexico ends DST (permanent standard time)
2019Brazil suspends DST
2016Turkey adopts permanent summer time
2014Russia moves to permanent standard time

The EU Parliament voted to end seasonal time changes in 2019, but implementation has stalled (April 2026).

Language-Specific APIs

JavaScript: Temporal API (ES2026)

The legacy Date object only supports two timezones: UTC and the device's local zone. The Temporal API (TC39 Stage 4, part of ES2026) fixes this:

TypePurposeTimezone-aware?

Temporal.InstantExact point in time (nanosecond precision)No (always UTC)
Temporal.ZonedDateTimeDate + time + timezoneYes
Temporal.PlainDateTimeWall-clock date + timeNo (intentionally)
Temporal.PlainDateCalendar date onlyNo
Temporal.PlainTimeWall-clock time onlyNo

// Create a timezone-aware datetime
const meeting = Temporal.ZonedDateTime.from(
  "2026-04-08T14:30:00[Europe/Berlin]"
);

// Convert to another timezone
const inNewYork = meeting.toInstant()
  .toZonedDateTimeISO("America/New_York");
console.log(inNewYork.toString());
// "2026-04-08T08:30:00-04:00[America/New_York]"

// Check DST transitions
const nextTransition = meeting.getTimeZoneTransition("next");
const hoursInDay = meeting.hoursInDay; // 23, 24, or 25

Browser support (April 2026): Chrome 144+, Firefox 139+, Edge 144+. Safari: Technical Preview only. Use @js-temporal/polyfill or temporal-polyfill for broader support.

Python: zoneinfo (3.9+)

Python 3.9 introduced zoneinfo in the standard library, replacing the third-party pytz:

from datetime import datetime, timezone
from zoneinfo import ZoneInfo

# Create timezone-aware datetime
berlin = ZoneInfo("Europe/Berlin")
dt = datetime(2026, 4, 8, 14, 30, tzinfo=berlin)

# Convert to UTC
utc_dt = dt.astimezone(timezone.utc)
# datetime(2026, 4, 8, 12, 30, tzinfo=timezone.utc)

# Convert to another timezone
ny = ZoneInfo("America/New_York")
ny_dt = dt.astimezone(ny)
# datetime(2026, 4, 8, 8, 30, tzinfo=ZoneInfo('America/New_York'))

Critical: Never mix naive (no tzinfo) and aware (with tzinfo) datetimes — Python raises TypeError on comparison or arithmetic. On Windows and minimal containers, install the tzdata PyPI package to provide IANA zone data.

Go

package main

import (
    "fmt"
    "log"
    "time"
)

func main() {
    // Load timezone
    loc, err := time.LoadLocation("America/New_York")
    if err != nil {
        log.Fatal(err) // tzdata not available
    }

    // Create time in timezone
    t := time.Date(2026, 4, 8, 14, 30, 0, 0, loc)

    // Convert to UTC
    fmt.Println(t.UTC()) // 2026-04-08 18:30:00 +0000 UTC

    // Convert to another timezone
    berlin, _ := time.LoadLocation("Europe/Berlin")
    fmt.Println(t.In(berlin)) // 2026-04-09 00:30:00 +0200 CEST
}

In minimal Docker images (scratch, distroless), tzdata is not included. Embed it at compile time with import _ "time/tzdata".

PostgreSQL

-- TIMESTAMP WITH TIME ZONE (timestamptz): stores UTC internally
CREATE TABLE events (
  id SERIAL PRIMARY KEY,
  name TEXT,
  starts_at TIMESTAMPTZ NOT NULL  -- always use this
);

-- Insert with timezone — stored as UTC
INSERT INTO events (name, starts_at)
VALUES ('Standup', '2026-04-08 14:30:00 Europe/Berlin');

-- Query converts to session timezone automatically
SET timezone = 'America/New_York';
SELECT starts_at FROM events;  -- shows 08:30:00-04

-- Explicit conversion
SELECT starts_at AT TIME ZONE 'Asia/Tokyo' FROM events;

Important: TIMESTAMP WITHOUT TIME ZONE discards timezone info on insert and assumes the session timezone on read — avoid it for anything except truly timezone-independent data (e.g., "the show airs at 8 PM local time everywhere").

Common Gotchas

1. Using fixed offsets instead of IANA names. UTC+5:30 is not the same as Asia/Kolkata — the offset can change if India ever adopts DST. Fixed offsets cannot represent DST transitions.

2. Assuming UTC offset is constant for a timezone. America/New_York is UTC-5 in winter (EST) and UTC-4 in summer (EDT). Hardcoding -05:00 breaks half the year.

3. Forgetting to update tzdata. Deployed applications bundle a tzdata snapshot. If a country changes its rules and you do not update, your conversions are wrong. The IANA tzdb releases 3–10 updates per year.

4. Scheduling cron jobs during DST transitions. A daily job at 2:30 AM in America/New_York will skip on spring-forward day (2:30 does not exist) and may run twice on fall-back day (2:30 occurs twice). See cron syntax reference for details.

5. Comparing naive and aware datetimes (Python). Mixing datetime objects with and without tzinfo raises TypeError. Always ensure all datetimes in a calculation have the same awareness.

6. Using Date instead of Temporal in JavaScript. The legacy Date object silently converts everything to the device's local timezone or UTC — there is no way to specify an arbitrary timezone without Intl.DateTimeFormat. Use Temporal.ZonedDateTime for timezone-aware operations.

7. Storing local time as UTC for future events. If a meeting is scheduled for "9 AM New York time next month" and you convert to UTC now, a DST change between now and then means the stored UTC is wrong. Store local time + IANA timezone name for future events.
