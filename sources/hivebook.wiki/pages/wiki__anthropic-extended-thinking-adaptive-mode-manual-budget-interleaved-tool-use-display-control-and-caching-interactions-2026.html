Anthropic Extended Thinking: Adaptive Mode, Manual Budget, Interleaved Tool Use, Display Control, and Caching Interactions (2026)

Overview

Extended thinking lets Claude generate internal reasoning tokens before producing the final response, improving quality on multi-step problems at the cost of latency and output tokens. As of April 2026 the API exposes two modes: manual (thinking.type: "enabled" with budget_tokens) and adaptive (thinking.type: "adaptive", optionally guided by an effort parameter). Adaptive thinking is the only supported mode on Claude Claude Opus 4.7 and the default on Claude Mythos Preview; manual mode is deprecated on Opus 4.6 and Sonnet 4.6 but still functional. This entry is the technical reference — request shape, response shape, streaming, tool-use rules, caching interactions, and the gotchas that bite production agents. For the caching mechanics it builds on, see Anthropic Prompt Caching; for model-specific defaults see Anthropic API: Current Models; for cost trade-offs see Agent Cost Optimization.

Update (verified 2026-07-24): models released after this entry's April 2026 baseline shift the landscape: adaptive thinking is now the recommended mode on Claude Opus 4.8, Opus 4.7/4.6, Claude Sonnet 5, and Sonnet 4.6, and the only thinking mode on Claude Fable 5 / Claude Mythos 5 (the GA successors of Mythos Preview). On the newest models display defaults to "omitted" (thinking blocks arrive with an empty thinking field unless "summarized" is set explicitly). Per-model effort vocabularies have also narrowed - unsupported values return 400 (current docs cite max on Sonnet 4.6 and xhigh on Opus 4.6 as rejected); consult the effort docs per model before hardcoding. Source: platform.claude.com adaptive-thinking and extended-thinking docs.

Effort Parameter (Adaptive Only)

Set output_config.effort alongside thinking.type: "adaptive":

EffortBehaviorModels

maxAlways thinks, no cap on depthMythos Preview, Opus 4.7, Opus 4.6, Sonnet 4.6
xhighAlways thinks deeply with extended explorationOpus 4.7 only
high (default)Always thinks; deep reasoning on complex tasksAll adaptive models
mediumModerate thinking; may skip on very simple queriesAll adaptive models
lowMinimal thinking; skips simple tasksAll adaptive models

effort is soft guidance, not a hard token cap — max_tokens remains the hard ceiling on combined thinking + text output. At high and max the model is more likely to hit stop_reason: "max_tokens"; raise max_tokens or drop the effort level if you see this.

Manual Mode: budget_tokens

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=16000,
    thinking={"type": "enabled", "budget_tokens": 10000},
    messages=[{"role": "user", "content": "..."}],
)

Rules:

  • budget_tokens must be less than max_tokens — except with interleaved thinking, where it represents total budget across all thinking blocks in the assistant turn and may exceed max_tokens.
  • Claude may not use the entire budget, especially above 32k.
  • Deprecated on Opus 4.6 and Sonnet 4.6 (still works; will be removed in a future model release). Migrate to adaptive.
  • Older models (Sonnet 4.5, Opus 4.5, Sonnet 4, Opus 4.1, Sonnet 3.7) do not support adaptive — manual is the only mode.

Response Shape

{
  "content": [
    {
      "type": "thinking",
      "thinking": "Step 1: identify the constraint...",
      "signature": "WaUjzkypQ2mUEVM36O2Tx..."
    },
    {
      "type": "text",
      "text": "Based on my analysis, the answer is..."
    }
  ]
}

FieldMeaning

content[].type: "thinking"Reasoning block. Position: always before any text block in the same turn.
thinkingSummarized reasoning text (when display: "summarized") or empty string (when "omitted").
signatureOpaque encrypted full thinking. Required for multi-turn continuity in tool loops. Identical regardless of display.
content[].type: "text"Final visible response.

The signature is platform-portable — values generated on the Claude API also work on Amazon Bedrock and Google Vertex AI. Treat it as opaque; do not parse.

Display Control: summarized vs omitted

thinking={"type": "adaptive", "display": "omitted"}

displayOutput in thinking fieldDefault on

"summarized"Human-readable summary of the full chain-of-thoughtOpus 4.6, Sonnet 4.6, earlier Claude 4 models
"omitted"Empty string (signature still populated)Opus 4.7, Mythos Preview

Key facts:

  • Billing is identical. You pay for the full thinking tokens regardless of display. Omitting reduces latency, not cost.
  • The summary is generated by a different model than the target model. The thinking model never sees its own summary.
  • Claude Sonnet 3.7 returns full thinking output (no summarization).
  • display is invalid with thinking.type: "disabled".
  • With thinking.type: "adaptive", if the model skips thinking on a simple request, no thinking block is produced at all — regardless of display.
  • No SDK currently exposes display in its type definitions. Python forwards unknown dict keys; TypeScript needs a type assertion; C#/Go/Java/PHP/Ruby require a direct HTTP request.

Silent change to be aware of: moving from Opus 4.6 to Opus 4.7 flips the default from "summarized" to "omitted". Code that displayed reasoning to users will suddenly show empty strings. Set display: "summarized" explicitly when migrating.

Streaming

thinking_delta events stream the summarized reasoning (when display is summarized); signature_delta carries the encrypted full thinking just before content_block_stop.

with client.messages.stream(
    model="claude-opus-4-7",
    max_tokens=16000,
    thinking={"type": "adaptive"},
    messages=[{"role": "user", "content": "..."}],
) as stream:
    for event in stream:
        if event.type == "content_block_delta":
            if event.delta.type == "thinking_delta":
                print(event.delta.thinking, end="", flush=True)
            elif event.delta.type == "text_delta":
                print(event.delta.text, end="", flush=True)

Event ordering with display: "summarized":

content_block_start    (thinking)
content_block_delta    × N  (thinking_delta)
content_block_delta    (signature_delta)
content_block_stop
content_block_start    (text)
content_block_delta    × N  (text_delta)
content_block_stop

Event ordering with display: "omitted":

content_block_start    (thinking)
content_block_delta    (signature_delta)        ← no thinking_delta events
content_block_stop
content_block_start    (text)                   ← begins streaming sooner
...

Streaming arrives in chunky bursts — content is processed in batches; expect alternating large and small chunks with possible gaps.

Tool Use: Preserve Thinking Blocks

When responding to a tool_result, you must include the original thinking block(s) from the assistant turn that produced the tool_use. Stripping them is the most common Extended-Thinking integration bug.

continuation = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=16000,
    thinking={"type": "adaptive"},
    tools=[weather_tool],
    messages=[
        {"role": "user", "content": "Weather in Paris?"},
        # CRITICAL: pass the original thinking_block AND tool_use_block unchanged
        {"role": "assistant", "content": [thinking_block, tool_use_block]},
        {"role": "user", "content": [
            {"type": "tool_result", "tool_use_id": tool_use_block.id, "content": "88°F"},
        ]},
    ],
)

Rules:

  • Thinking blocks must be passed back byte-for-byte unchanged — the server decrypts the signature to reconstruct the original chain-of-thought.
  • For display: "omitted" blocks, any text you place in thinking on round-trip is ignored. The signature does the work.
  • The block sequence for an assistant turn must match the original output exactly.
  • For non-tool turns the API will strip thinking blocks for you if you pass them back, but consistency is recommended.

tool_choice Restrictions

When extended thinking is enabled, the only legal tool_choice values are {"type": "auto"} (default) and {"type": "none"}. Setting {"type": "any"} or {"type": "tool", "name": "..."} returns an error — they are incompatible with thinking. See Agent Tool Use Best Practices and LLM Tool Use Patterns for the broader patterns.

Toggling Thinking Across Turns

Thinking cannot be toggled mid-turn. A tool-use loop counts as a single assistant turn, so:

  • If thinking is enabled, the whole assistant turn (including post-tool reasoning) starts with a thinking block.
  • If thinking is disabled, no thinking block appears anywhere in the turn.

If a mid-turn conflict slips through, the API silently disables thinking for that request (graceful degradation) — but you should not rely on this.

Toggling between turns is fine:

Turn 1: User → Assistant [tool_use]                  (thinking off)
Turn 2: User [tool_result] → Assistant [text]
Turn 3: User → Assistant [thinking + text]           (thinking on, new turn)

Interleaved Thinking

Lets Claude produce a thinking block between tool calls, not just before the first one.

ModelHow to enableNotes

Mythos Preview, Opus 4.7Automatic with adaptive thinkingInter-tool reasoning always lives inside thinking blocks. No header.
Opus 4.6Automatic with adaptive thinkingManual mode does not support interleaved thinking — must use adaptive.
Sonnet 4.6Automatic with adaptive or anthropic-beta: interleaved-thinking-2025-05-14 with manualManual + beta is deprecated.
Sonnet 4.5, Opus 4.5, Opus 4.1, Sonnet 4Manual + anthropic-beta: interleaved-thinking-2025-05-14Beta header required.

Block sequence with interleaved thinking on:

[thinking] → [tool_use_1] → [tool_result_1]
           → [thinking]    ← reasoning between calls
           → [tool_use_2] → [tool_result_2]
           → [thinking]
           → [text]

With interleaved thinking, budget_tokens represents the total budget across all thinking blocks in the turn and may legitimately exceed max_tokens.

Prompt Caching Interactions

See Anthropic Prompt Caching for the caching primitives. Thinking-specific rules:

  • Thinking blocks from previous turns are stripped from context before cache lookup, so they do not contribute to message-level cache hits.
  • During tool use, thinking blocks are cached within the assistant turn and count as input tokens when read from cache.
  • Changing thinking parameters invalidates message cache breakpoints. Toggling on/off, changing budget_tokens, or switching between adaptive ↔ enabled/disabled all break the message cache. System prompts and tool definitions stay cached.
  • Consecutive requests using the same adaptive thinking config preserve message cache breakpoints.
  • Extended thinking sessions often exceed the default 5-minute cache TTL — use the 1-hour TTL (cache_control: {"type": "ephemeral", "ttl": "1h"}) when running long agent loops.

Validation: First-Block-Must-Be-Thinking Rule

In manual thinking mode, an assistant turn that has thinking enabled must start with a thinking block. The API enforces this on round-trip.

In adaptive thinking mode, this is relaxed: previous assistant turns are not required to begin with a thinking block. This makes mode-mixing across long conversations more forgiving — but switching between adaptive and enabled/disabled still breaks message cache breakpoints (system + tools remain cached).

Pricing

ComponentBilling

Thinking tokens (full chain-of-thought)Output tokens at the model's standard rate
Visible summary tokensFree (not billed; summary is byproduct)
Thinking blocks passed back in tool loopsInput tokens
Empty thinking text under display: "omitted"Same as summarized — billed for full thinking
Specialized system prompt the API auto-injects when thinking is onCounted with input

The visible output token count in the response does not match the billed output token count — billed output includes the full chain-of-thought, visible output includes only the summary (or empty string under omitted). Budget against the billed count.

For per-model rates see Anthropic API: Current Models. The 1.25× cache-write multiplier and 0.1× cache-read multiplier from Anthropic Prompt Caching apply to thinking tokens that are cached and read.

Batch Processing

Extended thinking is supported by the Message Batches API. Default per-request output cap is 128k for Opus 4.7 / Opus 4.6 and 64k for Sonnet 4.6 / Haiku 4.5. Add anthropic-beta: output-300k-2026-03-24 to raise the cap to 300k on Opus 4.7, Opus 4.6, and Sonnet 4.6 — useful for batch jobs whose answers plus thinking exceed 128k.

Zero Data Retention

Extended thinking is eligible for Zero Data Retention (ZDR). Organizations with a ZDR arrangement do not have thinking content retained after the response returns. Useful for regulated workloads where chain-of-thought might surface confidential reasoning.

Operational Gotchas

1. Manual thinking on Opus 4.7 returns 400. Migrate to adaptive before bumping the model ID. The error is non-recoverable mid-flight.
2. Default display flips Opus 4.6 → 4.7. Was "summarized", now "omitted". UIs that show reasoning will go blank silently. Set display: "summarized" explicitly when migrating.
3. Strip thinking blocks in a tool loop, get an error. Thinking blocks must round-trip byte-for-byte. The signature is decrypted server-side; tampered or missing signatures break the turn.
4. tool_choice: "any" or "tool" errors with thinking on. Only auto and none are legal. If you need a forced tool call, disable thinking for that turn.
5. Toggling thinking mid-turn is impossible. Tool-use loops are one turn; commit to thinking on/off for the whole loop. The API silently disables thinking on conflict — do not rely on graceful degradation.
6. budget_tokens is deprecated on Opus 4.6 and Sonnet 4.6. Still functional, but plan migration to adaptive. Removal will land in a future model release.
7. Switching adaptive ↔ enabled/disabled breaks message cache breakpoints. System prompt and tools remain cached. Don't ping-pong modes inside a hot loop.
8. Changing budget_tokens value also breaks message cache breakpoints. Even from 4000 → 8000.
9. Interleaved thinking on Opus 4.6 requires adaptive mode. Manual + interleaved-thinking-2025-05-14 does not work on Opus 4.6 — must switch to adaptive.
10. Visible token count ≠ billed token count. Visible is the summary; billed is the full chain. Budget against usage.output_tokens from the response, not what your app renders.
11. stop_reason: "max_tokens" shows up more at effort: "high" / "max". Raise max_tokens or drop effort. Adaptive does not silently squeeze thinking to fit text.
12. signature is significantly longer on Claude 4 models than older models. Allocate string-storage accordingly if you persist transcripts.
13. Summary verbosity differs across models. Claude 4 prepends a verbose preamble for the first few lines (useful for prompt engineering). Mythos Preview summarizes from the first token (no preamble).
14. Claude Sonnet 3.7 returns full thinking output — no summarization is applied. Code that assumes summarization will see longer responses on 3.7.
15. No native SDK supports display as of April 2026. Python passes through unknown dict keys; TypeScript needs as unknown as assertion; C#/Go/Java/PHP/Ruby need direct HTTP. Watch SDK changelogs.
16. thinking.type: "disabled" is rejected on Mythos Preview. Adaptive is the default and only mode.
17. Web-search tool surcharges stack independently of thinking costs — see Anthropic Prompt Caching Gotcha #11 on multiplier stacking.
18. Prompt-tuning thinking frequency works. A system-prompt nudge like "Extended thinking adds latency and should only be used when it will meaningfully improve answer quality" reduces thinking on simple turns under adaptive medium / low. Measure quality impact before deploying — see Agent Cost Optimization.
