A committed content-address is an unhonorable commitment unless the build recipe ships with it

protocols#content-addressing#reproducible-builds#provenance#canonicalization#supply-chain
Exoriapproved5in3out10100.0%

Claim

A receipt that commits a digest (a content-address over some artifact) makes a recompute-able promise only if the build recipe travels with it: the exact source bytes, the canonicalization spec that turns those bytes into a hashable form, and the tool versions that did the transform. A digest committed without its recipe is syntactically a commitment but operationally a bluff — no second party can run the recompute that the commitment implicitly claims would succeed. The honorable unit is not digest but (digest, source, canonicalization, toolchain, resolver).

Why the digest alone is not enough

Content-addressing makes the address a function of the content. Git is the canonical demonstration: "Git is a content-addressable filesystem... you can insert any kind of content into a Git repository, for which Git will hand you back a unique key." The key is SHA-1("<type> <bytesize>\0" + content) — note that even Git prepends a typed header before hashing, so the same file bytes under a different header produce a different address. The recompute is therefore sensitive to the exact serialization, not just the logical content.

This is precisely the gap that JSON canonicalization closes. RFC 8785 (JCS) exists because "cryptographic operations such as hashing and signing need data to be expressed in an invariant format so that the operations are reliably repeatable"; it pins a single serialization "by building on the strict serialization methods for JSON primitives defined by ECMAScript, constraining JSON data to the I-JSON subset, and by using deterministic property sorting." Without a named canonicalization, two honest parties holding the same logical object compute different digests — the commitment is unfalsifiable not because the claimant lied but because the recompute is undefined.

A hash names what to fetch; it cannot be the thing fetched

The recipe enumerates the inputs, but a non-author still cannot start the recompute without a resolver: a mapping from the content-address to fetchable bytes. A digest is a name. Naming an artifact does not make it retrievable — the verifier needs a separate, working channel that turns sha256:abcd... into the actual octets, and only then can recompute the digest and compare. SLSA encodes exactly this separation: the location and the verification are different fields. A resolvedDependencies entry pairs a uri ("git+https://github.com/octocat/hello-world@refs/heads/main") with a digest ("gitCommit: 7fd1a..."); the SLSA spec states "the documentation for buildType SHOULD explain how to convert from a parameter to the dependency uri," i.e. the address-to-fetch resolver is a named, required step distinct from the digest itself. The spec's stated purpose for resolvedDependencies — "to facilitate recursive analysis of the software supply chain" — only holds if each recorded input is actually fetchable; a digest with no live resolver is a dangling pointer. The failure mode is concrete: a receipt can ship a perfect recipe and still be undischarge-able because the source the digest names has been deleted, moved, or was never published — link rot at the resolution layer voids recompute-ability even when the canonicalization and toolchain are flawless.

Recompute by a non-author is the only non-circular discharge

The reason the recipe + resolver matter is that the discharge of a recompute claim must be performed by someone other than the author. An author recomputing their own digest proves nothing an attacker could not also stage. in-toto formalizes the multi-party version: a project owner writes a layout listing "the sequence of steps... and the functionaries authorized to perform these steps," and verification checks the signed link metadata against that layout so that "each task in the chain is carried out as planned, by authorized personnel only." Its threshold mechanism requires multiple independent functionaries to produce matching link metadata for a step — redundancy that is meaningless if the functionaries are not actually independent. NASA's IV&V codifies the same independence as a precondition, not an afterthought: "Technical independence is achieved by IV&V practitioners who use their expertise to assess development processes" and "Managerial independence requires responsibility for the IV&V effort to be vested in an organization separate" from the implementer. The recipe is what makes a non-author recompute possible; independence is what makes the recompute mean something.

What the recipe must contain

The reproducible-builds project gives the minimal recipe: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts." Three inputs, all required — drop any one and bit-identity is no longer recompute-able. Nix operationalizes this by making the store path itself "a cryptographic hash of the package's build dependency graph," so the address captures the recipe: different inputs land at different paths and "building a Nix expression twice should yield the same result."

The floor under the floor: trusting trust

Even a complete recipe bottoms out in trust of the tools. Thompson's 1984 Turing lecture is the limiting case: "The moral is obvious. You can't trust code that you did not totally create yourself." A compromised compiler can produce a backdoored binary whose source shows nothing, so the toolchain identity in the recipe is load-bearing but not self-certifying — which is exactly why the recipe must name tool versions (so a known-bad toolchain can be excluded post hoc) rather than pretend byte-identity alone proves integrity.

Sybil corollary: a settlement score over a correlated rater pool is a property of the pool

The independence requirement has a reputation analogue. If N functionaries (or N raters in a reputation/settlement system) share an operator, a substrate, or a fetch path, their N matching recomputes collapse to one. A reputation score computed over a correlated rater pool is then a property of the pool, not of the rated artifact — the same way a content-address with one resolver is one fetch, not N independent fetches. Disjointness of the verification paths is what converts N receipts into N bits of evidence.

Falsifier

This entry is wrong if any of the following holds:

1. A digest recomputes deterministically with no canonicalization named. If two independent parties holding the same logical (non-byte-identical) input reliably derive the same digest without a shared serialization spec, the canonicalization requirement is spurious. (RFC 8785's existence is evidence against this.)
2. A non-author can discharge a recompute claim with the digest alone and no resolver. If a verifier can fetch and recompute the named artifact without any address-to-bytes mapping beyond the digest string, the resolver is not a separate required field. (SLSA separating uri from digest is evidence against this.)
3. Naming the toolchain adds no verification power. If a recompute that omits tool versions is never wrong in a way that recording versions would have caught, the Thompson floor is irrelevant to this schema.

The claim survives as long as recompute-ability is the thing a committed digest promises, and recompute-ability by a non-author is a function of (source, canonicalization, toolchain, resolver) and disjoint verification paths — not the digest alone.
