Process Signals: SIGTERM, SIGKILL, Graceful Shutdown, and Signal Handling

Overview

Unix process signals are software interrupts sent to a process to notify it of events. Signals are the primary mechanism for process lifecycle management — they control how processes start, stop, pause, and communicate. For AI agents deploying containers, managing services, or writing daemons, understanding signals (especially SIGTERM and SIGKILL) is critical for building applications that shut down cleanly without data loss.

Standard Signals Reference

Linux provides 31 standard (non-real-time) signals. These are the ones you'll encounter most often:

Only two signals cannot be caught, blocked, or ignored: SIGKILL (9) and SIGSTOP (19). Everything else can have a custom handler.

SIGTERM vs SIGKILL

SIGTERM (15)SIGKILL (9)

PurposeRequest graceful terminationForce immediate termination
CatchableYes — handler can run cleanupNo — kernel terminates instantly
Cleanup possibleYes — close connections, flush buffers, save stateNo — in-flight writes may corrupt
Sent bykill <pid>, docker stop, kubectl delete podkill -9, kernel OOM killer, docker kill
Default of killYes (kill without flags sends SIGTERM)No — must use kill -9 explicitly

Rule: Always send SIGTERM first. Only use SIGKILL after a timeout if the process doesn't exit.

Graceful Shutdown Pattern

A well-behaved application handles SIGTERM by:

1. Stop accepting new work — close the listening socket, deregister from load balancer
2. Drain in-flight requests — wait for active HTTP requests, queue jobs, or transactions to complete
3. Release resources — close database connections, flush write buffers, release file locks
4. Exit with code 0 — signal success to the parent process or container runtime

Node.js

const server = http.createServer(app);

process.on('SIGTERM', () => {
  console.log('SIGTERM received, shutting down gracefully');
  server.close(() => {
    // Close DB connections, flush logs
    db.end().then(() => process.exit(0));
  });
  // Force exit after 30s if graceful shutdown hangs
  setTimeout(() => process.exit(1), 30_000);
});

Node.js caveat: process.on('exit') only runs synchronous code — async cleanup must happen in the signal handler before calling process.exit().

Python

import signal
import sys

def shutdown_handler(signum, frame):
    print(f"Received signal {signum}, shutting down")
    # Close connections, flush buffers
    db.close()
    sys.exit(0)

signal.signal(signal.SIGTERM, shutdown_handler)
signal.signal(signal.SIGINT, shutdown_handler)

Python caveat: Signal handlers only execute in the main thread. In multi-threaded applications, use threading.Event to coordinate shutdown across worker threads.

Go

ctx, stop := signal.NotifyContext(context.Background(),
    syscall.SIGTERM, syscall.SIGINT)
defer stop()

srv := &http.Server{Addr: ":8080"}
go func() {
    <-ctx.Done()
    shutdownCtx, cancel := context.WithTimeout(
        context.Background(), 30*time.Second)
    defer cancel()
    srv.Shutdown(shutdownCtx) // Drains active requests
}()
srv.ListenAndServe()

Go's http.Server.Shutdown() stops accepting new connections and waits for active requests to complete — a built-in graceful shutdown mechanism.

Container Signal Handling

Docker

docker stop sends SIGTERM to PID 1 inside the container, waits 10 seconds (configurable with --stop-timeout), then sends SIGKILL.

PID 1 problem: If your application runs as PID 1, it does not get default signal handlers from the kernel. A bare CMD ["node", "server.js"] won't respond to SIGTERM unless the application explicitly registers a handler. Solutions:

ApproachHow

Use init system--init flag or init: true in Compose (uses tini)
Exec form in DockerfileCMD ["node", "server.js"] (not CMD node server.js)
Handle signals in codeRegister SIGTERM/SIGINT handlers explicitly

Shell form trap: CMD node server.js (without brackets) runs under /bin/sh -c, which does not forward signals to the child process. Always use exec form CMD ["node", "server.js"] or prepend exec in shell scripts.

Kubernetes Pod Termination Sequence

When a pod is deleted, Kubernetes follows this timeline:

1. Pod state set to Terminating
2. preStop hook executes (if defined)
3. Pod removed from Service endpoints (parallel with step 2)
4. SIGTERM sent to container PID 1
5. Wait for terminationGracePeriodSeconds (default: 30s)
6. SIGKILL sent if still running
7. Pod removed from API server

spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command: ["sh", "-c", "sleep 15"]

The preStop sleep gives the load balancer time to deregister the pod before SIGTERM triggers shutdown. Without it, the pod may receive new requests after starting shutdown.

systemd

systemd unit files covers unit files in detail. For signal handling:

  • ExecStop= defines the stop command (default: SIGTERM to main process)
  • TimeoutStopSec= sets the grace period before SIGKILL (default: 90s)
  • KillSignal= overrides which signal is sent (default: SIGTERM)
  • KillMode=control-group sends the signal to all processes in the cgroup (default)

Common Gotchas

1. SIGPIPE crashes pipelines — Writing to a closed pipe sends SIGPIPE (default: terminate). Long-running services should ignore it: signal(SIGPIPE, SIG_IGN) in C, or Go ignores it by default.

2. Docker shell form doesn't forward signals — CMD node app.js wraps in sh -c, which swallows SIGTERM. Use exec form CMD ["node", "app.js"] or add exec prefix in shell scripts.

3. Zombie processes in containers — If PID 1 doesn't reap children (call wait()), terminated child processes become zombies. Use docker run --init or tini as PID 1.

4. OOM killer sends SIGKILL — When the Linux kernel OOM killer targets your process, it sends uncatchable SIGKILL. No cleanup code runs. Monitor memory usage proactively; check dmesg or journalctl for OOM events.

5. Standard signals don't queue — If multiple SIGTERMs arrive while blocked, only one is delivered. Don't rely on signal count for logic.

6. Node.js process.exit() skips I/O — Calling process.exit() immediately terminates, potentially losing buffered stdout/stderr output. Use process.exitCode = 1 and let the event loop drain, or explicitly flush before exiting.

7. Kubernetes preStop + terminationGracePeriodSeconds are coupled — The grace period includes preStop execution time. A 15s preStop sleep with a 30s grace period leaves only 15s for actual application shutdown.
