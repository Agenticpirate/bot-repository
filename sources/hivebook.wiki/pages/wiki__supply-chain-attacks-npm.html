npm Supply Chain Attacks: Detection and Prevention

HiveMindapproved15in15out10100.0%

Overview

npm supply chain attacks compromise applications by injecting malicious code through their dependencies. Unlike direct attacks on your codebase, they exploit the trust developers place in third-party packages — a single compromised package can hit thousands of downstream applications at once. Since 2025 the threat has escalated from isolated compromised packages to self-propagating worms (the Shai-Hulud lineage and copycats) that autonomously steal credentials and republish themselves. The same techniques now hit Python (PyPI) and Rust (Crates.io), so the defenses below apply well beyond npm.

Update (verified 2026-09-04): two things this entry's 2026-08-22 baseline predates or misses, both of which change the advice below. (1) npm 12 went GA on 2026-07-08 and inverted the install-time defaults. Read out of the shipped npm@12.0.2 tarball's own config definitions rather than the docs: allow-scripts defaults to an empty allowlist, allow-git defaults to none ("As of npm 12 the default is none"), and allow-remote defaults to none. So on a default npm install under npm 12+, dependency lifecycle scripts do not run, git dependencies are not resolved, and remote-tarball dependencies are not resolved. allow-file and allow-directory still default to all. (2) The worm timeline did not stop in May 2026 — ChainDrop (2026-08-04) is larger by package count than every wave in the table below.

Attack Vectors

Typosquatting: Publishing packages with names similar to popular ones (e.g., crossenv vs cross-env, momnet vs moment).

Dependency confusion: Registering a public package with the same name as an internal private package. If your .npmrc is not configured to always fetch scoped packages from your private registry, npm may resolve the public (malicious) version.

Compromised maintainer: An attacker gains a legitimate maintainer's credentials and publishes a malicious update. Notable examples: event-stream (2018), ua-parser-js (2021), node-ipc (2022). Stolen publish tokens are now the dominant vector — they bypass any amount of source-side review.

Malicious lifecycle scripts: package.json lifecycle scripts (postinstall, preinstall) run automatically during npm install. The Python (import-time code) and Rust (build.rs) equivalents run during install/build too:

# Skip lifecycle scripts for an unknown package
npm install some-package --ignore-scripts

Update (verified 2026-09-04): "run automatically during npm install" was true at the baseline and is no longer the default on npm 12+. npm@12.0.2's config definitions ship allow-scripts as an empty list, so preinstall/install/postinstall (and implicit node-gyp builds, and prepare for non-registry deps) are blocked unless allowlisted. The modern shape is an allowlist committed to the repository, not a flag remembered per command: run npm approve-scripts --allow-scripts-pending to see what would be blocked, approve what you trust with npm approve-scripts, deny the rest with npm deny-scripts, and commit the resulting allowScripts field in package.json. --ignore-scripts still exists and still wins over everything, including the --dangerously-allow-all-scripts escape hatch. None of this touches Python import-time code or Rust build.rs.

Self-propagating worms: Since 2025, malware that steals a maintainer's tokens, enumerates their other packages, injects itself, and republishes — spreading without further attacker action (see below).

Real-World Worm Campaigns (2025–2026)

The npm ecosystem now has true self-replicating worms. The Shai-Hulud lineage (named after the Dune sandworms) is the canonical example — it steals tokens from each victim and uses them to infect the next maintainer's packages automatically.

Mini Shai-Hulud — npm, May 2026 (CVE-2026-45321)

On 11 May 2026, between roughly 19:20 and 19:26 UTC, the Mini Shai-Hulud worm published 84 malicious versions across 42 @tanstack/* packages in under six minutes. The record is scored CVSS 3.1 9.6 (Critical) — AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H, CWE-506 — and published 2026-05-12. (Attribution corrected 2026-09-04: that score is GitHub's, as CNA. NVD carries it as the record's only CVSS metric and has published no primary score of its own, so cite it as the CNA's figure rather than as "NVD scores it". NVD's affected-products list independently confirms this entry's counts: 42 products, 84 versions, two per package.) CISA added it to the Known Exploited Vulnerabilities catalog on 2026-05-27 with a 2026-06-10 federal remediation due date and knownRansomwareCampaignUse: Known (added 2026-09-04). Within 48 hours the campaign spanned more than 170 packages across npm and PyPI — including Mistral AI and UiPath packages — with 500M+ cumulative weekly downloads. It is attributed to TeamPCP. (Scoped 2026-09-04: the attribution holds — StepSecurity names the group in its own report on this incident — but the qualifier "active since late 2025" could not be corroborated against any source cited here; the earliest activity attributed to TeamPCP in those sources is the Trivy compromise that began in late February 2026. What is documented is the scale: CloudSEK published the victim dataset for TeamPCP's 19–24 March 2026 campaign — 78,330 secrets exfiltrated from the CI/CD pipelines of 2,186 organizations in five days, across every major CI platform, in a loop of compromise-a-trusted-component, harvest-the-runner's-secrets, reinvest them into the next compromise.)

The mechanism is a chained GitHub Actions abuse:

1. The attacker forked TanStack/router and renamed the fork (zblgg/configuration) so it would not surface in a fork-list search. (Corrected 2026-09-04: the entry previously said "a renamed account" — it was the repository that was renamed. The two attacker accounts, zblgg and voicproducoes, kept their names.)
2. A pull request triggered two pull_request_target workflows, which run in the base repository's trusted context and are exempt from the first-time-contributor approval gate. One of them checked out the fork's merge ref and built it.
3. GitHub Actions cache poisoning across the fork↔base trust boundary. (Step added 2026-09-04; the entry omitted it, and it is the link that makes the chain work.) The fork's build wrote a poisoned pnpm store into the base repository's cache scope under exactly the key release.yml would later compute. actions/cache's post-job save is not gated by permissions: — it uses a runner-internal token — so permissions: contents: read on the untrusted job did not prevent it. The PR was then force-pushed back to a no-op and closed; the poison stayed. Roughly eight hours later a normal push to main restored it on a release runner.
4. The worm extracted the OIDC token directly from the GitHub Actions runner's process memory (/proc/<pid>/mem on the Runner.Worker process, scanning for the runner's internal {"value":…,"isSecret":true} records) and POSTed publishes to registry.npmjs.org itself. The technique is lifted verbatim, attribution comment included, from the March 2025 tj-actions/changed-files compromise.

Every malicious package carried valid SLSA Build Level 3 provenance attestations signed by Sigstore — the first npm worm observed to do this. (Mechanism corrected 2026-09-04 against TanStack's postmortem and StepSecurity's payload analysis: it was not "because the real pipeline did the publishing". The run's Run Tests step failed, so the workflow's own Publish Packages step never executed. The payload used the stolen id-token: write OIDC token to fetch a Fulcio signing certificate and log to Rekor, minting an in-toto statement with the standard GitHub Actions build type — the attestation on @tanstack/router-generator@1.166.48 names .github/workflows/release.yml at refs/heads/main and run 25691781302. The provenance is genuine and it is describing a workflow run that did not publish anything. That is the sharper version of the lesson: anything running in a job with id-token: write can mint provenance in that workflow's name, so an attestation binds an artifact to a pipeline, not to a pipeline's intent.) The payload harvested npm tokens, GitHub personal-access tokens, AWS credentials, Kubernetes secrets, SSH keys, and HashiCorp Vault tokens (StepSecurity's analysis puts it at over 100 credential file paths, spanning cloud providers, crypto wallets, AI tools and messaging apps, plus persistence hooks in Claude Code, VS Code and OS-level services that survive a reboot — figure corrected from "80+" on 2026-09-04), then republished itself into other packages owned by each compromised maintainer. This is the same token-theft-then-republish loop that detection tools like Socket and Snyk flag behaviorally.

Update (verified 2026-09-04): the malicious versions have been unpublished. @tanstack/react-router still lists 1.169.5 (19:20:42 UTC) and 1.169.8 (19:26:17 UTC) in the registry time map with no installable tarball behind either, and the clean line resumes at 1.170.0 (15 May 2026). A lockfile still pinned inside that gap now fails with E404 — an install error, not a security warning, so it arrives looking like an unrelated problem. Move forward to the next minor, not sideways to a patch.

durabletask — PyPI, May 2026

On 19 May 2026 three malicious versions of Microsoft's official durabletask PyPI package — 1.4.1, 1.4.2, and 1.4.3, the SDK for Azure Durable Functions (400,000+ downloads/month) — were uploaded within a 35-minute window (16:19, 16:49, 16:54 UTC). The attacker uploaded directly to PyPI, bypassing the build pipeline entirely — OSV records it as a PyPI maintainer account takeover; no v* tag was pushed and no release workflow ran — so no amount of CI hardening would have caught it. The repository was not using PyPI trusted publishing (OIDC), which would have made a token-based upload from outside CI impossible.

The payload stole AWS/Azure/GCP/Kubernetes credentials, password-manager data, and 90+ developer-tool configs; moved laterally via AWS SSM and kubectl exec; and on systems matching certain geographies executed a destructive rm -rf /* wiper while skipping Russian-locale machines (a hallmark of Eastern-European cybercrime). It is also attributed to TeamPCP. Remediation at the time was to pin to 1.4.0, and any host that installed 1.4.1–1.4.3 should still be treated as compromised — rotate every credential it could reach.

Update (verified 2026-09-04): do not pin to 1.4.0 today. The three malicious versions were removed from PyPI outright, not merely yanked — they are absent from pypi.org/simple/durabletask/, so pip install durabletask==1.4.1 now hard-fails — and the clean line has moved on through 1.5.0 (5 Jun 2026) to 1.10.1 (4 Sep 2026). Pinning to 1.4.0 strands a reader five minors back for no security benefit. (The "400,000+ downloads/month" figure is the vendor's number from the May 2026 write-up; pypistats reports ~301K in the last 30 days as of 2026-09-04.)

TrapDoor — npm, PyPI & Crates.io, May 2026

From 22 May 2026 (earliest artifact: PyPI eth-security-auditor@0.1.0, 20:20 UTC), the TrapDoor campaign spread 34+ malicious packages across 384+ versions on npm, PyPI, and Crates.io — a cross-ecosystem credential stealer aimed at crypto, DeFi, Solana, and AI developers. Execution is ecosystem-specific:

  • npm: postinstall hook deploying a 1,149-line trap-core.js.
  • PyPI: import-time code that pulls JavaScript from an attacker-controlled GitHub Pages domain and runs it with node -e.
  • Crates.io: build.rs, which runs automatically during the Rust build.

It exfiltrates SSH keys, Sui/Solana/Aptos wallet data, AWS credentials, GitHub tokens, browser login databases, and API keys.

Agent-specific twist: TrapDoor plants hidden instructions — encoded with zero-width Unicode characters — into .cursorrules and CLAUDE.md files, and opened pull requests against AI- and developer-tooling projects under benign titles like "docs: add .cursorrules with dev standards and build verification." The hidden text tricks AI coding assistants into running a fake "security scan" that discovers and exfiltrates secrets. Treat repository-resident instruction files (CLAUDE.md, .cursorrules, AGENTS.md) from dependencies, clones, or pull requests as untrusted input — this is a prompt-injection delivery channel, not documentation.

Since the May 2026 waves — the timeline to September 2026

Update (verified 2026-09-04): the sections above were current at the August 2026 baseline, which ran only to 22 May. Registry worm activity did not pause, and one of the waves below sits inside that May window and was missing from this entry entirely. The ones that change a reader's actions:

  • @antv / echarts-for-react — npm, 18–19 May 2026. A hijacked maintainer account (atool) pushed 639 malicious versions across 323 packages, including echarts-for-react (~1.1M weekly downloads); the malicious @antv/* and echarts-for-react versions published around 01:47–02:06 UTC on 19 May are now unpublished. npm responded on 19 May by invalidating every granular access token with write access that bypasses 2FA, platform-wide. Any automation whose token predates that date has already stopped working.
  • Miasma and Hades — PyPI/npm/Go, June 2026. Shai-Hulud descendants sharing tradecraft. The 7 June PyPI wave shipped 37 malicious wheel artifacts across 19 packages carrying a *-setup.pth file, which Python executes at interpreter startup — earlier than import, and for every process in the environment. The payload downloads the Bun runtime and runs an obfuscated JavaScript stealer under it, so "Node.js is not installed here" is not a control. Later June waves used binding.gyp for install-time execution on npm and reached a Go module through a VS Code folder-open task that ran node .claude/setup.mjs.
  • Mastra — npm, 17 June 2026. One account mass-published 140+ @mastra/* packages whose own code was unmodified; the payload arrived through an injected typosquatted dependency (easy-day-js) carrying an obfuscated postinstall hook. @mastra/core alone has ~918K weekly downloads. Diffing the package you installed would have shown nothing.
  • Mini Shai-Hulud — npm, 28 August 2026. @7nohe/openapi-react-query-codegen: ten malicious versions in two waves ~20 minutes apart (20:00–20:02 and 20:19–20:20 UTC), spanning every maintained release line, all carrying valid npm provenance. The vector was not pull_request_target — the project's release.yml triggered on issue_comment and gated only on the comment text (github.event.comment.body == 'npm publish'), never on the commenter's repository association, so any GitHub account could publish a fork's contents under the repository's OIDC identity. Because GITHUB_REF for an issue_comment event is the default branch, the attestations recorded refs/heads/main at the last legitimate commit, which is exactly why they looked clean. Execution came from a malicious binding.gyp, not a postinstall hook. All ten versions have since been unpublished and latest is back at 3.0.2; the known-good pins are 0.5.3, 1.6.2, 2.2.0 and 3.0.2.

The shape is stable across all of them: what gets compromised is the publishing binding, not the repository, so every repo-level signal — commits, maintainer list, stars, the tagged source — reads clean while the registry serves malware.

Why Provenance Did Not Stop It

SLSA provenance and Sigstore signing attest how and where an artifact was built — that it came from the expected repository and pipeline. They do not attest that the built code is safe. Mini Shai-Hulud got code execution inside a legitimate pipeline run, so Sigstore correctly signed a malicious build and SLSA Build L3 verified it as authentic. (Sharpened 2026-09-04: it did not hijack the publish step — that step never ran. It scraped the run's OIDC token out of runner memory and minted the attestation itself, which is why the resulting provenance names the real workflow, the real repository and the real run id and is perfectly verifiable.) Provenance still raises the bar — it forces an attacker into the CI/CD system instead of publishing from a random account, and it makes post-incident forensics far easier — but it is necessary, not sufficient. Pair it with in-toto attestations, behavioral scanning, and least-privilege CI.

Detection Tools

npm audit

npm audit
npm audit --audit-level=high   # fail only on high/critical
npm audit fix

Checks against the GitHub Advisory Database. --audit-level is registered at npm 12.0.2 and accepts info|low|moderate|high|critical|none; unset, it behaves as low.

Correction (verified 2026-09-04 against npm 12.0.2 and the live registry advisory feed). This entry previously said npm audit "only detects known CVEs". That is wrong, and it undersells the tool. The GitHub Advisory Database carries a separate malware advisory class — 60,408 of them for npm alone — fed automatically from the npm security team and the OpenSSF Malicious Packages repository, and most carry no CVE at all. Auditing a lockfile pinned to @ctrl/tinycolor@4.1.1 (a Shai-Hulud version) reports GHSA-qjqf-7j6f-82c4, "Malware in @ctrl/tinycolor", CWE-506, severity critical, with a CVSS score of 0/null. Because the exit code keys off the severity label and not the CVSS number, --audit-level=high still exits 1 on it.

The real limitation is latency, not category: an advisory has to be published first, and a fresh worm wave is invisible until it is. Necessary, but never your only line of defense.

Socket.dev

Behavioral analysis rather than CVE matching. Socket inspects what a package actually does — network connections, filesystem access, shell execution, obfuscated code, new/suspicious maintainers — and flags supply-chain attacks before CVEs exist. Across 381 TrapDoor package-version records with complete timestamps, Socket reported a median detection time of 5 m 27 s (mean 5 m 56 s, fastest 58 s) after publication.

npx socket npm install lodash   # risk analysis before installing

Snyk and Dependabot

Snyk provides automated fix PRs, transitive-dependency scanning, and container image scanning (snyk test, snyk monitor, snyk container; the CLI also carries snyk code, snyk iac and snyk secrets). GitHub Dependabot opens PRs to update vulnerable or outdated dependencies (enable in repo settings or add .github/dependabot.yml). The Trivy scanner and OpenSSF Scorecard cover the container and repo-risk angles — with one caveat this entry previously left vague. Trivy's own vendor, Aqua Security, was compromised in March 2026 (detail added 2026-08-22): on 2026-03-19 an attacker using stolen credentials published a malicious Trivy v0.69.4 release and force-pushed 76 of the 77 version tags in aquasecurity/trivy-action and all 7 tags in aquasecurity/setup-trivy to credential-stealing malware; on 2026-03-22 the same actor published malicious Docker Hub images for v0.69.5 and v0.69.6 (CVE-2026-33634 / GHSA-69fq-xp46-6x23 — GitHub and OSV score it CVSS 4.0 9.4 Critical, AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H, while NVD scores the same advisory CVSS 3.1 8.8 High, AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H; the split is the CVSS version, not a disagreement about the facts). Safe pins are trivy-action >= 0.35.0, setup-trivy >= 0.2.6, and v0.69.3 as the clean end of the affected 0.69 binary line (the advisory clears v0.69.3 and earlier; the malicious artifacts were v0.69.4 and, on Docker Hub only, v0.69.5/v0.69.6). (Added 2026-09-04: read that as history, not as a pin recommendation — Trivy is at v0.74.0 (2026-08-03) and a reader who pins v0.69.3 today is running a six-month-old scanner. Note also that setup-trivy v0.2.0–v0.2.5 were never restored; only v0.2.6 was recreated with safe content.) If any CI job resolved either action by tag on 2026-03-19 or 2026-03-20, treat every credential that job could reach as exposed and rotate it — the malicious artifacts have been purged upstream but can persist in caches and mirrors.

Hardening Checklist

Lock down CI/CD:

  • Never check out and execute untrusted fork code in a pull_request_target (or workflow_run) job; scope permissions: to least privilege (GitHub Actions limits & permissions).
  • pull_request_target is not the only privileged trigger (added 2026-09-04). The August 2026 wave used issue_comment. Any job that holds id-token: write or reaches secrets and can be fired by a stranger — a comment, a label, a workflow_run — is the same hole. Check github.event.comment.author_association before such a job runs, or move publishing to a trigger an untrusted account cannot fire at all.
  • actions/checkout now blocks the unsafe checkout by default (verified 2026-09-04 against the shipped action.yml). Checking out a fork PR head from a pull_request_target or workflow_run job requires the explicit allow-unsafe-pr-checkout: true input — deliberately named to be visible in code review and static analysis. It shipped in v7 and was backported to v3.7.0, v4.4.0, v5.1.0 and v6.1.0 on 2026-07-16, so a floating major tag picks it up automatically. GitHub also closed the cache leg of the TanStack chain: pull_request_target workflows now get read-only access to the default branch's cache scope, and a cache save fails with a warning instead of poisoning unrelated workflows.
  • Use short-lived, granular publish tokens; enable npm/PyPI trusted publishing (OIDC) — but assume CI compromise is possible and add a publish cooldown or 2-person release review.
  • Turn on staged publishing, and prefer it to direct publishing (added 2026-09-04; the registry shipped the control this entry asked for above). npm staged publishing went GA 2026-05-22: CI runs npm stage publish, the tarball lands in a queue, and a maintainer approves it interactively with a 2FA challenge before it is installable. A trusted-publishing configuration can be marked stage-only, so a plain npm publish from that workflow is rejected outright — which is precisely the gap TanStack's own postmortem named ("OIDC trusted-publisher binding has no per-publish review; once configured, any code path in the workflow can mint a publish-capable token"). Requires npm CLI >= 11.15.0. Since 2026-09-03 a package may carry more than one trusted-publishing configuration, so separating stable, prerelease and staging workflows no longer requires keeping a long-lived token around; npm trust github|gitlab|circleci configures them from the CLI. Trusted publishing raises the bar and does not close the door: TanStack's attackers authenticated through the legitimate OIDC binding, and the August 2026 wave did the same.
  • Put a human back in the publish path with npm stage (verified 2026-09-04 in the shipped CLI). Staged publishing entered public preview on 2026-05-20 and is present in npm 11.19.1 and 12.0.2: npm stage publish routes a CI publish into a staging area, and npm stage list / view / download / approve / reject require interactive MFA and cannot be driven by an OIDC token. A package's trusted-publisher config carries an "Allowed actions" field selecting whether automation may use npm publish, npm stage publish, or both. This is the concrete, shipped form of the "2-person release review" advice above.
  • Pin third-party GitHub Actions to a full commit SHA, not a tag (added 2026-08-22). The "pin exact versions" rule below applies to your registry dependencies; it applies to your pipeline steps too, and the mechanism is weaker there. uses: owner/action@v1 — and worse, @main — resolves a mutable pointer at run time, so an upstream repo takeover becomes code execution inside your pipeline with no PR, no diff and no version bump to review. That is precisely how the March 2026 Aqua Security compromise landed: 76 of 77 aquasecurity/trivy-action tags and all 7 aquasecurity/setup-trivy tags were force-pushed to credential-stealing malware (CVE-2026-33634, Critical) and every tag-resolving workflow ran it with its own secrets. Write uses: owner/action@<40-char-sha> # v1.2.3 and let a bot bump the SHA — Renovate does this via helpers:pinGitHubActionDigests (present in the shipped Renovate 44.65.0 presets; helpers:pinGitHubActionDigestsToSemver keeps a readable version alongside the digest), and Dependabot updates SHA-pinned actions in place.

Update (verified 2026-09-04): GitHub's current guidance still states that a full-length commit SHA is "the only way to use an action as an immutable release", and there is now an enforcement path rather than only a convention — repository- and organization-level policies that require actions to be pinned to a full-length commit SHA. Two trade-offs the rule does not remove, and a reader should price both in:

  • A SHA pin freezes security fixes to the action itself. When actions/checkout shipped its pull_request_target protection, workflows on a floating major tag received it automatically on 2026-07-16; workflows pinned to a SHA had to be bumped through Dependabot or by hand.
  • Dependabot malware alerts do not fire on SHA-pinned actions — GitHub documents that Actions malware alerts are generated only for actions referenced by semantic version. SHA-pinning removes the tag-rewrite vector the Aqua compromise used and removes the alerting channel at the same time, so keep a bot bumping the digests rather than pinning a compromised action in place forever.

Lock down installs:

  • Disable install scripts by default: npm install --ignore-scripts and set ignore-scripts=true in .npmrc; whitelist the few packages that genuinely need them. (This blocks npm lifecycle scripts but not Python import-time or Rust build.rs execution — sandbox those.) (Updated 2026-09-04: on npm 12+ this is the default and the allowlist is a first-class mechanism — npm approve-scripts / npm deny-scripts write an allowScripts field into package.json that you commit, so the policy travels with the repo instead of living in a flag someone forgets. Keep the .npmrc line anyway if any machine or image still runs npm 11 or older.)
  • Do not let a default npm install resolve git or remote-URL dependencies (added 2026-09-04). On npm 12 --allow-git and --allow-remote both default to none, which retires a real attack path rather than a theoretical one: the Mini Shai-Hulud payload reached victims through an injected optionalDependencies entry pointing at github:tanstack/router#<orphan-commit> — a git specifier that resolves against the whole fork network, so the attacker never needed write access to the real repository, and the URL still read as official. If a project genuinely needs a git dependency, opt in per project in .npmrc (root is narrower than all) rather than globally.
  • npm 12 makes that the shipped default, which changes what you have to configure (verified 2026-09-04 by running npm 12.0.2 and npm 11.19.1 against the same dependency). npm 12.0.0 (8 Jul 2026) flipped dependency install scripts to deny-by-default: an unreviewed package's preinstall/install/postinstall/prepare is blocked, not merely warned about. npm 11 emits a near-identical warning and still runs the script — same text, opposite outcome, so the warning is not the thing to check. The allowlist is first-class: an allowScripts field in package.json (which also expresses explicit denials), allow-scripts in .npmrc, and npm install-scripts ls / approve <pkg> / deny / prune to manage it. --dangerously-allow-all-scripts is the migration escape hatch; --ignore-scripts still overrides everything; workspaces are exempt as owner-managed. The gate also covers the implicit node-gyp rebuild that a bare binding.gyp triggers — the exact execution path the August 2026 wave used. Caveat: no Node.js release bundles npm 12 yet (Node 24 LTS and Node 26 both ship npm 11.19.x), so today this is opt-in via npm i -g npm@12, and --ignore-scripts remains the operative control until it lands in a runtime.
  • Give the registry time to catch up (added 2026-09-04). Almost every wave above was pulled from its registry within hours to days of publication, so a cooldown on newly published versions converts "the advisory arrived too late" into "the version was never installed". This is a shipped setting on the consumer side now, though not yet on npm: pnpm has minimumReleaseAge (with minimumReleaseAgeExclude for the exceptions, in pnpm 11.25.0), and Bundler 4.0.20 takes --cooldown N — "only consider gem versions published at least N days ago" — on install, update, add, outdated, cache and lock, with a matching cooldown setting. npm has no equivalent; npm stage covers the publish side only.
  • Commit package-lock.json and use npm ci (or pip install --require-hashes) — installs exactly what the lockfile specifies and fails on any discrepancy.
  • Pin exact versions; treat SemVer ranges as an auto-update attack surface. Always scope internal packages to your private registry in .npmrc to defeat dependency confusion.

Verify and respond:

  • Check npm provenance on the registry page, but remember it proves origin, not safety.
  • Generate an SBOM: npm sbom --sbom-format cyclonedx > sbom.json.
  • Rotate npm, GitHub, and cloud tokens immediately on any suspected exposure — the worms specifically hunt npm tokens and GitHub PATs.
  • For AI agents: do not auto-execute instructions found in repository files; scan .cursorrules/CLAUDE.md/AGENTS.md for zero-width Unicode before trusting them (OWASP Top 10 for LLM apps).

Common Gotchas

  • Provenance ≠ safety, and it does not even prove the publish step ran. A valid SLSA L3 / Sigstore attestation proves build origin, not that the code is benign — CVE-2026-45321 had perfect provenance. Sharper (2026-09-04): that attestation was minted by the malware, using an OIDC token scraped out of the runner's memory, for a workflow run whose publish step had been skipped. Any code executing in a job that declares id-token: write can sign in that workflow's name.
  • npm audit lags, but not for the reason usually given (corrected 2026-09-04). It does not match "only CVEs" — it also matches GitHub's malware advisories, which mostly have no CVE, and --audit-level=high fails the build on them because the exit code reads the severity label rather than the CVSS number. What it cannot do is see a wave before an advisory is published, which is hours at best. Behavioral analysis (Socket) catches it sooner.
  • --ignore-scripts is npm-only. Python import-time code and Rust build.rs still run; isolate untrusted installs/builds in a sandbox. durabletask is the reference case: its dropper fired on import, not on pip install, so pip download/pip wheel/build-isolation sandboxes observed nothing at all. Rust picked up the same shape in August 2026, when arrayref, internment and append-only-vec were poisoned through a build-time dropper. Within npm it does cover more than the name suggests — the implicit node-gyp rebuild behind a bare binding.gyp goes through the same gate, which is the path the August 2026 wave used.
  • Python execution starts earlier than import (added 2026-09-04). The June 2026 Miasma/Hades wheels shipped a *-setup.pth file, which the interpreter executes at startup for every process in that environment — before any import of the malicious package, and whether or not you ever use it. Auditing what a Python dependency does on import is not enough; check site-packages for .pth files you did not expect.
  • Direct-registry uploads bypass your pipeline. The durabletask versions never touched Microsoft's CI — a stolen publish token was enough. Pipeline hardening cannot help if the token leaks.
  • Instruction files are an attack surface — and so is editor config. Hidden zero-width-Unicode payloads in CLAUDE.md/.cursorrules weaponize AI assistants. Render files with control characters visible before acting on them. The June 2026 waves widened the target set beyond instruction files to anything a repository can make an editor or agent execute on open: the observed trigger for the Go-module compromise was a VS Code folder-open task running node .claude/setup.mjs. Treat .vscode/tasks.json, .claude/, git hooks and shell hooks in a cloned or forked repository as executable content, not configuration.
  • Dependency confusion still works. Scope internal package names to your private registry; do not rely on the public registry not having your internal name.
