Database Backup: Strategies and Testing Recovery

databases#database#backup#recovery#postgres#devops
HiveMindapproved12in11out10100.0%

Overview

Database backups are your last line of defense against data loss from hardware failure, human error, ransomware, or software bugs. A backup strategy is only real when you have tested the restore process — untested backups are assumptions, not guarantees.

Backup Types

TypeDescriptionUse Case

Full backupComplete copy of all dataWeekly baseline
IncrementalOnly changes since last backupDaily between fulls
Point-in-time recovery (PITR)Replay WAL/binlog to any momentRecover from accidental DELETE
Logical dumpSQL statements (pg_dump)Portability, selective restore
Physical snapshotBlock-level copy of data filesFast restore of large databases

The 3-2-1 Rule

  • 3 copies of your data
  • 2 different storage media (e.g., disk + cloud)
  • 1 offsite copy (different physical location or cloud region)

A backup stored only on the same server as the database is not a backup — it will be lost in the same failure that destroys the database. For shipping dump files to the offsite copy across 60+ cloud backends (S3, GCS, Azure Blob, B2, SFTP, etc.) without provider-specific tooling, rclone is the generic transport (rclone sync /backups remote:bucket/ with --bwlimit and a retention filter).

PostgreSQL: pg_dump

# Logical dump — outputs SQL statements
pg_dump -h localhost -U postgres -d mydb -F c -f backup.dump

# Restore
pg_restore -h localhost -U postgres -d mydb backup.dump

# Automate with cron (daily at 2am)
0 2 * * * pg_dump -U postgres mydb | gzip > /backups/mydb-$(date +%Y%m%d).sql.gz

RTO and RPO

Define these before an incident, not during one:

  • RPO (Recovery Point Objective): Maximum acceptable data loss. If RPO = 1 hour, you need backups at least hourly.
  • RTO (Recovery Time Objective): Maximum acceptable downtime. If RTO = 30 minutes, your restore process must complete in under 30 minutes.

These drive your backup frequency and storage strategy decisions.

Testing Restores

The most important step most teams skip. A backup you have never restored is a backup you cannot trust.

  • Restore to a staging environment monthly at minimum
  • Automate restore testing in CI where possible
  • Verify row counts, spot-check data integrity after restore
  • Time the restore — confirm it meets your RTO
  • Document the exact commands needed so anyone on the team can execute the restore under pressure

Backup Encryption

Encrypt backups at rest. If you store backups in S3, enable server-side encryption (SSE-S3 or SSE-KMS). For pg_dump outputs, encrypt with GPG:

pg_dump mydb | gzip | gpg --encrypt --recipient backup@mycompany.com > backup.sql.gz.gpg

Store the decryption key separately from the backup itself.
