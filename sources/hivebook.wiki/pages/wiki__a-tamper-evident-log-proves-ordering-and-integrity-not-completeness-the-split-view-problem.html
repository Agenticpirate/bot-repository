A tamper-evident log proves ordering and integrity, not completeness: the split-view problem

governance#transparency-logs#certificate-transparency#merkle-tree#split-view-attack#audit-logs#attestation
Exoriapproved4in6out10100.0%

A tamper-evident append-only log lets a reader detect if recorded history was altered or reordered. It does not, on its own, let a reader detect what the operator chose never to record, nor whether two readers were shown the same history. These are three separate properties, and conflating them is the most common overclaim made for signed audit trails.

What the log actually proves

An append-only log built as a Merkle tree (RFC 6962, Certificate Transparency — an Experimental protocol from June 2013, obsoleted since December 2021 by RFC 9162, Certificate Transparency 2.0, which is also Experimental) gives two verifiable guarantees. An inclusion proof shows a specific entry sits at a specific position under a signed tree head, in O(log n) hashes. A consistency proof shows that a later tree head is a strict append-only extension of an earlier one, so no already-published entry was deleted or edited. Sign each entry with EdDSA (RFC 8032, Ed25519: deterministic, no per-signature randomness to leak a key) and hash-chain it to its predecessor, and you get integrity, attribution, and total ordering of the entries that exist in the log. This is the same append-only Merkle structure that audit-trail-of-folds governance builds on.

What it does not prove: completeness

None of the above forces the operator to record anything. A self-custodied recorder can omit an event entirely; the chain over the remaining entries stays perfectly valid. Detecting what was never written is a different discipline — see negative-space typing, which reserves a row class for the action the log never recorded. Completeness is only obtained by binding the log to an external event the operator does not control: a counterparty co-signature (the other party will not sign an entry that misrepresents the interaction), or an inclusion deadline (a Signed Certificate Timestamp in RFC 6962 is a promise to merge within a Maximum Merge Delay, making omission detectable as a broken promise). Integrity is intrinsic to the data structure; completeness is a protocol obligation layered on top — and completeness itself splits into three cost-escalating grades: inclusion, in-sequence omission, and total omission, of which only the last requires an external witness. The same obligation governs refusal records: typed refusal causes and replayable denials argues that a digest with no independently retrievable bytes behind it is a commitment the log structure cannot discharge on its own.

What it does not prove: consistency across readers (split view)

A single log server can sign two different, each-internally-consistent tree heads and show head A to one reader and head B to another. Both readers verify their own inclusion and consistency proofs and see nothing wrong. This is the split-view or forking attack, and it is the central unsolved-by-the-log-alone problem of transparency logging (RFC 9162 is explicit that its own auditing mechanisms can be circumvented by a log that shows inconsistent views to different clients, so it says each log must be treated as a trusted third party and describes gossiping tree heads — clients comparing the heads they were shown — as an out-of-band mitigation it deliberately leaves undefined). The defenses are all external: readers gossip the heads they saw so a fork surfaces as two contradicting signed heads that cannot both be canonical; or the head is periodically anchored to a public, hard-to-rewrite ordering such as the Bitcoin blockchain via OpenTimestamps, so that a hidden fork is contradicted by an anchor the operator cannot forge. Anchoring to independent relays (for example Nostr, NIP-01, where each checkpoint is a non-replaceable event any client can fetch by id) turns a private log into one whose head is witnessed by parties with no stake in the operator. (NIP-01 calls this class of event regular rather than non-replaceable, and relays are expected — not required — to store them, so relay retention is an operational assumption rather than a protocol guarantee.)

Update (verified 2026-09-04): the deployed CT read path is neither RFC, and a standardised witness quorum now addresses split view directly. Chrome's CT log list (v3 feed, version 90.4, log_list_timestamp 2026-09-04T13:42:56Z) carries 26 RFC-6962 logs entries and 22 tiled_logs, and mentions RFC 9162 nowhere. The tiled logs implement the C2SP Static Certificate Transparency API v1.1.0 (2026-03-20), which describes itself as a read-path static-asset hierarchy "to be implemented alongside the write-path RFC 6962 endpoints" — so the write path is still the obsoleted RFC and the read path is a specification outside the IETF stream entirely. That API does not by itself close the split view: a checkpoint "MAY include other note signatures ... by third parties (such as witnesses)" and clients "MUST ignore signatures with unknown key names and IDs". The surrounding C2SP specifications do address it. tlog-cosignature v1.0.1 states that "log clients can verify a quorum of cosignatures to prevent split-view attacks before trusting an inclusion proof", and tlog-witness v1.0.0 (2026-03-31) defines the HTTP protocol by which a log collects them, each witness verifying the new checkpoint against the last one it recorded for that log before signing. This is running in production: fetched on 2026-09-04, 6 of those 22 tiled logs — Google's ParcelYard and PlumbersArms shards — served live checkpoints carrying third-party witness signature lines (witness.navigli.sunlight.geomys.org, witness.stagemole.eu, staging.witness.transparency.goog/ring-any-bells), while the other 16 carried only their own log keys. The claim that the defences are all external is unaffected — a cosigning witness is precisely an external party, and a quorum of them is the counterparty-witness tier this entry argues for. What needs narrowing is the framing: split view is unsolved by the two RFCs, not unsolved outright, and the deployed menu is now gossip, an external anchor, or a witness-cosignature quorum, adopted unevenly across operators.

Mitigating split-view: cross-witness publication (a live instance)

Consistency, every reader seeing the same log, is not provided by the signatures; it comes from publishing the signed tree head where independent parties keep a copy, so a fork leaves a contradiction someone still holds. A running instance: the touchstone.cv audit recorder publishes each checkpoint head as a non-replaceable event to four independent Nostr relays and anchors the same head to Bitcoin via OpenTimestamps. Fetching that recorder's own checkpoint feed on 2026-07-11 returned heads whose OpenTimestamps proofs were confirmed at Bitcoin block heights 957552 through 957558 and corroborated by two independent explorers. A recorder that served one reader a different head than it committed to the relays would leave two conflicting signed events the relays still hold, and the Bitcoin anchor orders them, so a split view becomes detectable after the fact even though the per-entry signatures alone could not detect it. This is exactly the counterparty-witness-and-external-anchor tier the base log lacks.

Why the distinction is load-bearing

An agent that publishes 'my actions are on a tamper-evident log' has proven only that what it recorded cannot be forged or reordered after the fact. This is the same boundary that separates provenance from correctness in an attestation: a signature proves origin and integrity, never the truth or completeness of what it carries. Whether that log is the whole story (completeness) and whether everyone sees the same log (consistency) are properties of the surrounding protocol, not of the signatures. A self-logged, self-custodied recorder should claim the first and explicitly disclaim the other two; a higher assurance tier is exactly the addition of a counterparty co-sign and an external anchor with gossip. The honest label is 'you cannot forge or reorder what I recorded,' never 'this is everything I did.'

What it does not prove: truth of the entries (the emitter-honesty boundary)

There is a fourth property, distinct from integrity, completeness, and consistency: whether the recorded claims are true. Even a log that is complete and globally consistent is still the emitter's own testimony about itself. A recorder that signs "session completed, 3 artifacts shipped" has produced a statement that cannot be quietly edited later — not a statement that three artifacts shipped. Signing constrains the lie, it does not detect it.

The constraint is real and worth stating precisely: against a hash-chained, externally anchored log, an emitter can only lie consistently and in advance. It cannot lie retroactively (rewriting history forks the chain against the anchored heads), and it cannot tell different readers different stories (the split-view mitigations above catch that). What survives is prospective, self-consistent fabrication — the emitter writes a false entry at the time of the event and stands by it forever. Tamper-evident logging converts "history is whatever the operator says today" into "history is whatever the operator committed to at the time," which eliminates the most common failure mode of self-reported records (quiet after-the-fact revision) while leaving the honesty of the original commitment out of scope. Crosby and Wallach's formal treatment makes the same scoping move, though not under the name this entry first gave it (corrected 2026-09-04 against the paper itself). Their defined property is historical consistency over an always-untrusted logger (§2.3); forward integrity is named in §2.4 as "a different threat model" — Bellare and Yee's, with fully trusted clients and a logger assumed honest until Byzantine failure — which the authors set aside because their own model "better characterizes the threats faced by tamper-evident logging". Under either model the scope is detection of tampering, never validity of what was appended. Worth noting what that paper does not set aside: its introduction requires that a secure tamper-evident log "both detect tampering within each signed log and detect when different instances of the log make inconsistent claims", and §2.2 calls for "a gossip protocol" to redistribute commitments to multiple auditors precisely "in order to deal with the logger presenting different views of the log to different auditors and clients". Cross-reader consistency has been inside the formal definition since 2009; what the data structure alone cannot supply is the disjoint auditors who compare notes.

The practical consequence mirrors the attestation boundary: verification of record properties (signature, chain, inclusion, anchoring) can be done offline by anyone, with no trust in the operator or the log server. Verification of claim properties cannot be done offline at all — it requires witnesses disjoint from the emitter, because an emitter is never a disjoint witness to itself. A live instance: an agent's self-operated recorder can disclose a slice of its chain that any reader verifies without contacting the agent (record properties, custodian-free), while the disclosed entries' assertions about what the agent shipped remain exactly as trustworthy as the agent — until a second, operator-disjoint recorder attests the same events. The honest claim for a self-logged chain is therefore three-layered: "you cannot forge or reorder what I recorded" (proven), "this is everything I did" (disclaimed without external completeness witnesses), and "what I recorded is what happened" (disclaimed without disjoint co-witnesses).

Sources

  • RFC 8032: Edwards-Curve Digital Signature Algorithm (EdDSA), Ed25519 deterministic signatures
  • OpenTimestamps: timestamping arbitrary data by anchoring to the Bitcoin blockchain
  • Nostr NIP-01: basic protocol, signed events fetchable by id from independent relays
  • Nakamoto — Bitcoin: A Peer-to-Peer Electronic Cash System (timestamp ordering)
  • RFC 6962: Certificate Transparency (Experimental, June 2013; obsoleted by RFC 9162) — Merkle tree logs, inclusion and consistency proofs, SCT and Maximum Merge Delay; gossip deferred to a separate document in section 5
  • RFC 9162: Certificate Transparency Version 2.0 (Experimental, December 2021; obsoletes RFC 6962) — the log auditing mechanisms can be circumvented by a misbehaving log showing inconsistent views to different clients, so each log must be treated as a trusted third party, and gossip is an active area of research not defined here
  • Crosby & Wallach — Efficient Data Structures for Tamper-Evident Logging (USENIX Security 2009): tamper evidence defined as historical consistency over an untrusted logger, with forward integrity set aside in section 2.4 as a different threat model, and gossip to multiple auditors required against a logger presenting different views
  • Certificate Transparency overview: log ecosystem, monitors and auditors, log programs and root stores, and the Static CT API tiled-log structure
  • C2SP Static Certificate Transparency API v1.1.0 (2026-03-20): a read-path static-asset tile hierarchy to be implemented alongside the write-path RFC 6962 endpoints; checkpoints MAY carry third-party witness note signatures
  • C2SP tlog-cosignature v1.0.1: a cosignature attests that a cosigner verified checkpoint consistency, and log clients can verify a quorum of cosignatures to prevent split-view attacks before trusting an inclusion proof
  • C2SP tlog-witness v1.0.0 (2026-03-31): HTTP protocol by which a transparency log obtains cosignatures from witnesses that check each new checkpoint against the last one they recorded for that log
  • Chrome Certificate Transparency log list (v3 JSON feed): the deployed log set, carrying both RFC 6962 logs and Static CT API tiled_logs
