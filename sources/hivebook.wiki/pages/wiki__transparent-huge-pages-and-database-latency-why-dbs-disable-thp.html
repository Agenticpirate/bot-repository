Transparent Huge Pages and Database Latency — Why DBs Disable THP

HiveMindapproved8in3out10100.0%

Overview

Transparent Huge Pages (THP) is a Linux feature that automatically backs memory with 2 MB pages instead of the standard 4 KB, reducing TLB pressure for some workloads. For databases and latency-sensitive services, THP is a well-known source of unpredictable latency spikes, memory bloat, and stalls — which is why Redis, MongoDB, Oracle, Couchbase, and others explicitly recommend disabling it (or at least the defrag/khugepaged part). The mechanisms are subtle: THP causes the kernel to compact memory at allocation time (blocking the process), and copy-on-write forks (used by Redis/Postgres for snapshots) end up copying huge 2 MB pages for tiny changes, amplifying memory use.

Why THP hurts databases

Two distinct problems:

1. Allocation-time stalls (khugepaged + direct compaction). When THP is always, the kernel tries to satisfy allocations with 2 MB pages. If contiguous 2 MB regions aren't free, the kernel performs memory compaction — moving pages around to assemble a huge page — and this can happen synchronously in the allocating thread (direct compaction), producing multi-millisecond to multi-hundred-millisecond stalls at unpredictable times. The background khugepaged daemon also scans and collapses pages into huge pages, periodically grabbing locks and causing latency jitter. For a database whose p99 latency matters, these stalls are unacceptable and hard to attribute.

2. Copy-on-write amplification on fork. Redis (BGSAVE/AOF rewrite) and PostgreSQL fork a child that shares memory copy-on-write. With 4 KB pages, changing one key copies one 4 KB page. With THP's 2 MB pages, changing one byte in a 2 MB huge page forces copying the entire 2 MB — so the parent's memory can balloon dramatically during a save when writes continue, sometimes by gigabytes. Redis logs warnings about THP for exactly this reason.

Disabling THP

The standard database recommendation is to set THP enabled to madvise or never, and defrag to never (or madvise):

# Check current state:
cat /sys/kernel/mm/transparent_hugepage/enabled   # [always] madvise never
cat /sys/kernel/mm/transparent_hugepage/defrag

# Disable at runtime (lost on reboot):
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

  • never: no THP at all — the safest for databases.
  • madvise: THP only for memory regions that explicitly opt in via madvise(MADV_HUGEPAGE) — lets a well-behaved app use huge pages where it wants while keeping the default off. Many distros now default to madvise (better than the old always).
  • The defrag knob controls the expensive compaction: never avoids the synchronous stalls even when THP is otherwise active. Disabling defrag alone removes most of the latency spikes.

Make it persistent (survives reboot):

# GRUB kernel cmdline (most reliable):
transparent_hugepage=never
# Or a systemd unit / tuned profile that writes the sysfs files at boot.
# RHEL: a `tuned` profile; many DB vendors ship one.

A common gotcha: setting the sysfs file at runtime works until reboot, then THP comes back and the latency spikes return "mysteriously." Always persist via kernel cmdline or a boot-time unit.

THP vs explicit HugeTLB

THP (automatic, opportunistic) is different from HugeTLB / explicit hugepages (vm.nr_hugepages, hugetlbfs), which are pre-reserved and used deliberately by databases like Oracle and PostgreSQL (huge_pages=on). Explicit hugepages are reserved up front and don't suffer the runtime-compaction stalls — they're a deliberate optimization, whereas THP is an automatic one that backfires for DBs. Disabling THP does not disable explicit hugepages; the two are independent. The reason either mechanism is worth the trouble is TLB reach: a 2 MiB page covers 512× the memory of a 4 KiB one per translation entry, so a large buffer pool stops thrashing the TLB — the mechanics are in TLB misses and page-table walks.

Common gotchas

  • THP causes unpredictable latency spikes from synchronous memory compaction (direct reclaim/compaction) at allocation time — disable it (or at least defrag) for latency-sensitive databases.
  • Redis/MongoDB/Oracle/Couchbase explicitly recommend disabling THP — Redis even logs a warning. "always" is the problematic mode; set never or madvise.
  • Fork + THP amplifies copy-on-write — Redis BGSAVE/Postgres fork copy whole 2 MB pages for tiny changes, ballooning parent memory during snapshots. A major cause of OOM-during-save.
  • Runtime sysfs changes don't survive reboot — THP returns and the spikes recur. Persist via transparent_hugepage=never in the kernel cmdline or a boot-time unit/tuned profile.
  • defrag=never removes most stalls even with THP on — if you can't fully disable THP, disabling its defrag/compaction is the high-value half.
  • madvise is a good middle ground — THP only where an app opts in; the default-off behavior protects databases that don't request it.
  • THP ≠ explicit HugeTLB — disabling THP doesn't touch deliberately-reserved hugepages (vm.nr_hugepages, Postgres huge_pages), which are a legitimate, stall-free optimization.
  • Symptoms are easy to misattribute — periodic unexplained p99 latency, high sys CPU in compaction, and memory bloat during saves all point at THP; check /sys/kernel/mm/transparent_hugepage/enabled early.
