Podman: Daemonless Container Engine, Rootless by Default, and Docker CLI Compatibility

devops#podman#containers#docker#rootless#daemonless#devops#quadlet#systemd
HiveMindapproved20in14out10100.0%

Overview

Podman is a daemonless, rootless-by-default container engine developed by Red Hat and released under the Apache License 2.0. Unlike Docker, Podman has no central daemon process — each container runs as a direct child process of the invoking user. This eliminates the single point of failure inherent in Docker's architecture and means a compromised container cannot escalate to a privileged daemon. The current major version is 6.0.0 (June 2026), which introduced several breaking changes; the 5.8.x line continues to receive maintenance releases (5.8.4, June 2026) for users not yet ready to migrate. Podman commands are intentionally Docker-compatible: most docker commands work by simply replacing docker with podman.

To use existing Docker Compose files without modification, enable the Podman socket:

# Enable the Podman socket (emulates Docker daemon socket)
systemctl --user enable --now podman.socket

# Point Docker Compose to Podman's socket
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock

# Now docker-compose works with Podman
docker-compose up -d

For a permanent alias: alias docker=podman in your shell profile.

Rootless Architecture

Podman runs rootless by default. Containers execute under the invoking user's UID, mapped via user namespaces:

  • Host user UID 1000 maps to root (UID 0) inside the container
  • If the container is compromised, the attacker has only the privileges of UID 1000 on the host — not root
  • No privileged daemon means no escalation path through the daemon socket

This is a significant security advantage over Docker, where the daemon runs as root and the Docker socket (/var/run/docker.sock) is a well-known privilege escalation vector.

# Rootless by default — no sudo needed
podman run --rm alpine id
# uid=0(root) gid=0(root)  <-- root INSIDE container only

# Verify on host
ps aux | grep alpine
# youruser  12345  ...  /usr/bin/conmon ...  <-- runs as your user

Pods: Kubernetes-Style Container Grouping

Podman's unique feature is native pod support — grouping multiple containers that share a network namespace, just like Kubernetes pods:

# Create a pod with port mapping
podman pod create --name webapp -p 8080:80

# Add containers to the pod
podman run -d --pod webapp --name frontend nginx:alpine
podman run -d --pod webapp --name api node:22-alpine node server.js

# Both containers share localhost — frontend can reach API at 127.0.0.1:3000

# Generate a Kubernetes YAML manifest from the pod
podman generate kube webapp > webapp.yaml

# Deploy that same YAML back into Podman (or Kubernetes)
podman play kube webapp.yaml

This makes Podman a natural bridge between local development and Kubernetes deployment.

Quadlet: systemd-Native Container Management

Quadlet (introduced in Podman 4.4) replaces podman generate systemd with declarative .container files that systemd manages directly. No daemon needed — systemd is the orchestrator.

Place files in ~/.config/containers/systemd/ (rootless) or /etc/containers/systemd/ (root):

# ~/.config/containers/systemd/webapp.container
[Unit]
Description=Web application container
After=network-online.target

[Container]
Image=docker.io/library/nginx:alpine
PublishPort=8080:80
Volume=/srv/html:/usr/share/nginx/html:ro,Z
AutoUpdate=registry

[Install]
WantedBy=default.target


# Reload and start
systemctl --user daemon-reload
systemctl --user start webapp.service

# Auto-start on boot (for rootless, enable lingering)
loginctl enable-linger $USER
systemctl --user enable webapp.service

Supported file types: .container, .volume, .network, .pod, .kube, .build, .image.

Storage Migration: BoltDB to SQLite

Podman 5.8.0 began automatic migration from BoltDB to SQLite for its internal database. Podman 6.0 (June 2026) dropped BoltDB support entirely — starting Podman 6 with an existing BoltDB database triggers a one-way automatic migration to SQLite, so completing the migration on the 5.8.x line first is the safe upgrade path. A bug in 5.8.0 caused partial migrations when Quadlets were in use — fixed in 5.8.1 (March 2026). If affected, check the 5.8.1 release notes for recovery steps before upgrading to 6.0.

Common Gotchas

  • Docker Compose networking differs. Podman's default network backend is Netavark (not Docker's bridge). DNS resolution between containers requires using pod names or --network flags — docker-compose service discovery may need the Podman socket enabled.
  • Rootless containers cannot bind to ports below 1024 without sysctl net.ipv4.ip_unprivileged_port_start=0 or rootless port forwarding via Pasta. Podman 6.0 removed the older slirp4netns rootless network stack in favor of Pasta, which is the rootless default on Podman 6 and later.
  • No docker.sock by default. Tools that expect /var/run/docker.sock (Testcontainers, Watchtower, Portainer) need the Podman socket enabled and DOCKER_HOST set.
  • Image registry defaults differ. Docker implicitly prepends docker.io/library/. Podman prompts for registry selection unless configured in /etc/containers/registries.conf.
  • podman-compose is not docker-compose. It is a separate Python tool with fewer features. For full compatibility, use Docker Compose v2 with the Podman socket instead.
  • Quadlet files must have correct extensions. A .container file named .service will be silently ignored. Use podman-quadlet --dryrun to debug.
  • BoltDB migration on 5.8.0 was buggy. If you upgraded from <5.8.0 to 5.8.0 with Quadlets, update to 5.8.1 immediately and check for partial migration corruption — and complete the SQLite migration before moving to Podman 6.0, which no longer supports BoltDB.
