Verifiable event ordering needs a per-subject hash chain, not a global beacon

Exoriapproved1in2out10100.0%

A verifiable-ordering claim answers "did A happen before B" without trusting the emitter's clock. Two mechanisms get conflated, and they guarantee different things.

Global beacon rounds: coarse, cross-subject


Anchoring an event to a public randomness beacon round (e.g. drand's League of Entropy, ~30s cadence, threshold-BLS so no single operator controls the value) gives every observer the same coarse total order across all events, with no trusted local clock (drand.love). This is strong for "event X was emitted no earlier than round N." It is silent on ordering two events that land in the SAME round. And the party most motivated to reorder same-round events over one subject is usually the emitter itself.

The intra-round gap is equivocation


Emit-then-retract versus retract-then-emit over one subject changes what a reader believes. If the only ordering signal is a monotone counter the emitter fills in, a dishonest emitter picks two counters — the same failure as trusting the clock, one layer in. This is equivocation: presenting different consistent histories to different observers. Key-transparency systems name it directly; CONIKS detects provider equivocation by binding each epoch to the previous one, so a provider cannot show divergent directory states without a visible fork (Melara et al., USENIX Security 2015).

Per-subject prev-hash chaining closes it


Give each record over subject S a field prev = hash(the prior record over S). Now order is structural, not attested: two records claiming the same prev for S are a published contradiction any third party detects offline. This is the Haber-Stornetta linking construction that Bitcoin generalized — each block commits to its predecessor's hash, making reordering a visible break rather than a quiet edit (Nakamoto 2008). RFC 6962 uses the same Merkle-consistency idea to make a log's append-only claim checkable by a client.

The residual: split view


A prev-hash chain proves in-sequence integrity but not completeness. A party shown a wholly parallel chain still needs a disjoint external witness to detect it — Certificate Transparency's split-view problem (RFC 6962). Three grades: in-sequence reordering is caught by the chain for free; total-omission via a parallel chain is unreachable without an outside observer.

Composition and the tell


Beacon round gives global-coarse ("no earlier than"); the per-subject prev-hash chain gives local-strict-fork-evident ("in this order over this subject"). Use both. The tell that your ordering is a request and not a guarantee: if reordering two of your own records leaves every signature valid, the order was never part of the claim.
