Vertical Pod Autoscaler (VPA): updateMode, InPlaceOrRecreate GA, Recommender Algorithm, and What Changed in v1.6

Overview

Vertical Pod Autoscaler (VPA) is the Kubernetes controller that tunes a pod's CPU and memory requests (and optionally limits) to match observed usage, rather than changing replica count like the HorizontalPodAutoscaler. It ships as an out-of-tree controller at kubernetes/autoscaler, not as part of core Kubernetes, and publishes the VerticalPodAutoscaler CRD under autoscaling.k8s.io/v1. Agents picking the autoscaler quartet should think of VPA as the right-sizer: HPA moves replicas 1↔N, VPA moves per-container requests, KEDA drives HPA from external events, Karpenter adds nodes when the first three ask for capacity.

Update (verified 2026-07-21): VPA v1.7.0 is now current (Helm chart 0.10.0, 2026-06-14, pins app v1.7.0); v1.7 adds an alpha InPlace update mode that never falls back to eviction and requires Kubernetes 1.33+ with the InPlacePodVerticalScaling feature gate. This entry's feature baseline: VPA v1.6.0 released 2026-02-12, which promoted InPlaceOrRecreate to GA (release notes). It builds against Kubernetes 1.35 libraries and now pairs cleanly with the InPlacePodVerticalScaling feature gate that graduated to GA in Kubernetes v1.35 (December 2025). Before VPA 1.4, every updateMode: Auto/Recreate change required a pod eviction; with 1.6 GA the updater can mutate a running pod's CPU and memory via the /resize subresource and only falls back to eviction when in-place is refused.

Architecture

VPA ships as three deployments, typically in kube-system:

ComponentPurposeLeader-electPort

vpa-recommenderReads metrics.k8s.io + Prometheus history, maintains CPU/memory histograms, writes status.recommendation on each VerticalPodAutoscaler and VerticalPodAutoscalerCheckpoint objectsoptional:8942
vpa-updaterReads recommendations, decides which pods drift outside bounds, either calls /resize (in-place) or eviction APIoptional:8943
vpa-admission-controllerMutatingAdmissionWebhook; applies the current recommendation to new pods at creation timeoptional:8944 (metrics), 8000 (webhook)

The vpa-recommender owns the statistics. The vpa-updater and the admission-controller are its clients: both read .status.recommendation.containerRecommendations[] from the VPA object. If the admission controller is not running, newly created pods won't receive recommendations — the updater will still evict for drift, so the pod starts with its original requests and is immediately restarted. Keep the admission controller's failurePolicy in mind (below).

The Checkpoint CRD

The VerticalPodAutoscalerCheckpoint CRD (autoscaling.k8s.io/v1, same API group) is the recommender's persistence layer. One Checkpoint object per (vpaObjectName, containerName) stores the serialized histogram so recommender restarts don't zero out 24h of history. The recommender writes these on a fixed loop (--checkpoints-gc-interval=10m). Don't edit Checkpoint objects by hand.

Helm chart alternative (vertical-pod-autoscaler/charts/vertical-pod-autoscaler in the autoscaler repo; chart vertical-pod-autoscaler v0.8.1 on 2026-02-28 pins app v1.6.0; chart README still carries an "under development, not ready for production" warning):

helm repo add autoscalers https://kubernetes.github.io/autoscaler
helm upgrade -i vertical-pod-autoscaler autoscalers/vertical-pod-autoscaler \
  --version 0.8.1 --namespace kube-system

VPA needs metrics-server running in the cluster. The recommender also wants Prometheus for historical data (--prometheus-address, default http://prometheus.monitoring.svc) to backfill history on first start; without it, the first history-length (default 8 days) of recommendations will be conservative until the in-memory histograms fill.

The VerticalPodAutoscaler CRD

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: api-vpa
  namespace: prod
spec:
  targetRef:                         # must point to a /scale-capable controller or a pod-owning controller
    apiVersion: apps/v1
    kind: Deployment
    name: api
  updatePolicy:
    updateMode: InPlaceOrRecreate    # Off | Initial | Recreate | Auto (deprecated) | InPlaceOrRecreate
    minReplicas: 2                   # updater won't evict if fewer replicas Ready — default 2
    evictAfterOOMSeconds: 60         # OOMKill → eligible for eviction after this delay
    evictionRequirements:            # ALL must hold before updater evicts
      - resources: [cpu, memory]
        changeRequirement: TargetHigherThanRequests   # or TargetLowerThanRequests
  resourcePolicy:
    containerPolicies:
      - containerName: '*'           # default policy; override per-container below
        minAllowed:
          cpu: 50m
          memory: 64Mi
        maxAllowed:
          cpu: 4
          memory: 8Gi
        controlledResources: [cpu, memory]            # default; can restrict to [memory] to leave CPU alone
        controlledValues: RequestsAndLimits           # or RequestsOnly (preserves limit/request ratio)
      - containerName: istio-proxy
        mode: Off                                     # exclude sidecars entirely

targetRef rules

The controller pointed to by targetRef must either (a) expose the /scale subresource (Deployment, StatefulSet, ReplicaSet, ReplicationController) or (b) own the pods directly (DaemonSet, Job, CronJob). Arbitrary custom CRDs work only if they implement /scale. Pointing at a bare pod label selector is not supported — the recommender needs an owner to walk the pod tree.

GA'd 2026-02-12. Dramatically reduces evictions

InPlaceOrRecreate requires both sides enabled: the kubelet's InPlacePodVerticalScaling feature gate (GA and on-by-default in K8s 1.35; beta and on-by-default in 1.33+) and the VPA's own InPlaceOrRecreate feature gate (alpha in 1.4, beta in 1.5, GA and default-enabled in 1.6.0). Before 1.6 you must pass --feature-gates=InPlaceOrRecreate=true on all three components.

resizePolicy on the pod spec

In-place resize is also gated by the pod's spec.containers[].resizePolicy entries. If none are set, the kubelet's default is NotRequired for CPU and memory — i.e., resize without restart. Applications that must see a restart on memory change (JVMs, Go binaries that sized heap from cgroup at boot) should set:

spec:
  containers:
    - name: api
      resizePolicy:
        - resourceName: memory
          restartPolicy: RestartContainer    # NotRequired (default) or RestartContainer
        - resourceName: cpu
          restartPolicy: NotRequired

With RestartContainer the VPA updater will still attempt in-place — the kubelet will honour the resize by restarting just that container in-place, without rescheduling the pod.

Limitations that force eviction

Even with InPlaceOrRecreate and both feature gates enabled, the kubelet refuses in-place resize for pods using swap, the static CPU Manager policy, or the static Memory Manager policy, and for any change that would alter the pod's QoS class (e.g. removing a limit makes a Guaranteed pod Burstable). VPA falls back to eviction in those cases — budget for that.

The Recommender algorithm

The recommender is a histogram + percentile engine, not an ML model:

  • CPU: every sampling interval (default 1m via --recommender-interval) it appends a sample per container to an exponentially-decaying histogram. Buckets start at 0.01 cores (10m) and grow 5% per bucket. Each sample's weight halves every 24h (--cpu-histogram-decay-half-life=24h). The target recommendation is the 90th percentile of the weighted histogram, lowerBound is the 50th, upperBound is the 95th.
  • Memory: peak-based rather than percentile-based — it computes the peak in sliding 24h windows (--memory-aggregation-interval=24h) and feeds those peaks into a separate histogram. Target ≈ 90th percentile of daily peaks.
  • OOM handling: when the recommender sees an OOMKill, it bumps the memory sample up by --oom-bump-up-ratio=1.2 (20% bump) but at least --oom-min-bump-up-bytes=100Mi, so one OOM doesn't immediately starve you but does push the histogram.
  • Confidence: if a container has less than --confidence-interval-cpu=24h or --confidence-interval-memory=24h of history, the recommender multiplies the recommendation range to be wider. This is why VPA appears "conservative" for the first day of a fresh deployment — it is, by design.
  • History: the recommender can backfill from Prometheus on startup over --history-length=8d. If Prometheus is unreachable it just warms its own histograms from live metrics — the first 24h of recommendations on a cold-start recommender are the same as first-deploy.

The Updater

The updater polls every --updater-interval=1m. For each VPA with updateMode in {Recreate, InPlaceOrRecreate}:

1. Compute the recommendation's distance from current pod requests. If within --pod-update-threshold=0.1 (10%), skip — "close enough".
2. Check evictionRequirements: all must hold. If changeRequirement: TargetHigherThanRequests is set and the target is lower, skip this pod.
3. Check replica count vs --min-replicas=2 (global default) — override per-VPA via spec.updatePolicy.minReplicas. If evicting one pod would put Ready replicas below this floor, skip.
4. Check --eviction-rate-limit=-1 (unlimited by default, can set qps) and --eviction-rate-burst=1.
5. For InPlaceOrRecreate: try the /resize subresource first; on failure, fall back to eviction. The new --in-place-skip-disruption-budget flag (VPA 1.6) skips PDB checks when every container has resizePolicy: NotRequired, since that's a truly non-disruptive update.
6. For Recreate: call the Eviction API. This goes through PodDisruptionBudgets and can wedge.

The --in-recommendation-bounds-eviction-lifetime-threshold=12h prevents endless churn: a pod whose requests already fall inside [lowerBound, upperBound] won't be evicted just because the target moved within that range — only after 12h.

HPA coexistence

The textbook "don't use VPA and HPA together" is outdated. Three patterns work:

1. HPA on custom/external metric + VPA on CPU & memory. HPA reads a queue depth or latency metric, VPA right-sizes each replica. No conflict.
2. HPA on CPU + VPA on memory only. Set spec.resourcePolicy.containerPolicies[].controlledResources: [memory] — VPA leaves CPU requests alone, HPA's CPU utilization ratio stays meaningful.
3. HPA on CPU + VPA updateMode: Off. VPA is pure advisor, dashboards consume the recommendation.

The anti-pattern is VPA on CPU with HPA on CPU: VPA raises requests → HPA's currentCPUUtilizationPercentage = usage / requests drops → HPA scales down → fewer replicas handle the load → per-pod usage rises → VPA raises requests further. This oscillates and is the single most-reported VPA bug that isn't a bug.

Examples

Off-mode observation

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata: {name: worker-observe, namespace: prod}
spec:
  targetRef: {apiVersion: apps/v1, kind: Deployment, name: worker}
  updatePolicy: {updateMode: Off}
  resourcePolicy:
    containerPolicies:
      - containerName: '*'
        controlledResources: [cpu, memory]

Check the recommendation after 24h:

kubectl get vpa worker-observe -n prod -o jsonpath='{.status.recommendation.containerRecommendations}' | jq

Output shape:

[{
  "containerName": "worker",
  "target":        {"cpu": "312m", "memory": "1462Mi"},
  "lowerBound":    {"cpu": "210m", "memory": "1089Mi"},
  "upperBound":    {"cpu": "523m", "memory": "1822Mi"},
  "uncappedTarget":{"cpu": "312m", "memory": "1462Mi"}
}]

uncappedTarget is what the histogram said before minAllowed/maxAllowed/container-recommendation-max-allowed-* clamped it. If target and uncappedTarget differ, your policy is actively capping.

In-place mode with restart-on-memory

apiVersion: v1
kind: Pod
metadata: {name: java-api, labels: {app: api}}
spec:
  containers:
    - name: api
      image: internal/java-api:2026.04
      resources:
        requests: {cpu: 500m, memory: 1Gi}
        limits:   {cpu: 2,    memory: 1Gi}
      resizePolicy:
        - resourceName: cpu
          restartPolicy: NotRequired
        - resourceName: memory
          restartPolicy: RestartContainer
---
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata: {name: java-api, namespace: prod}
spec:
  targetRef: {apiVersion: apps/v1, kind: Deployment, name: api}
  updatePolicy:
    updateMode: InPlaceOrRecreate
    minReplicas: 2
  resourcePolicy:
    containerPolicies:
      - containerName: api
        minAllowed: {cpu: 250m, memory: 512Mi}
        maxAllowed: {cpu: 4,    memory: 8Gi}
        controlledValues: RequestsAndLimits

Result: CPU bumps are invisible (no container restart); memory bumps restart just the api container, keeping the pod sandbox and its sidecar connections alive.

20 Gotchas

1. VPA + HPA on the same resource metric is the anti-pattern. If both manage CPU, you get an oscillation: VPA raises requests → HPA's utilization% drops → HPA scales in → load per pod rises → VPA raises requests further. Either put HPA on a non-resource metric, or restrict VPA with controlledResources: [memory].
2. minReplicas default is 2 — single-replica workloads won't get Recreate updates. VPA will still write recommendations, they just never get applied. Either bump replicas or use InPlaceOrRecreate (which doesn't evict) or Initial (which applies only on next recreate you trigger).
3. Auto mode is deprecated as of 1.5. It's still an alias for Recreate, but new YAML should use Recreate or InPlaceOrRecreate explicitly.
4. InPlaceOrRecreate needs both feature gates. The kubelet's InPlacePodVerticalScaling (GA in K8s 1.35, beta on in 1.33+) and the VPA's InPlaceOrRecreate (GA on in 1.6). On K8s ≤1.32 with VPA 1.4–1.5, resize calls silently fail and every update becomes a Recreate.
5. Memory is peak-based, CPU is percentile-based. Memory recommendations only decrease after the 24h peak window rotates past a large spike. A one-minute spike at 4 GiB keeps the recommendation elevated for a full day — not a bug, but surprising.
6. The first 24h after a fresh VPA is conservative. Confidence intervals widen when history <24h, so the recommendation envelope will be wider than you'd expect. Don't tune maxAllowed based on day-1 numbers.
7. containerName: '*' is the default policy, not a match-all override. Per-container policies are merged: a * entry provides defaults that specific containerName entries can override field-by-field.
8. controlledValues: RequestsAndLimits preserves the current request:limit ratio. If your pod has requests.cpu: 100m, limits.cpu: 1 (ratio 10), a target request of 300m results in a 3 CPU limit. Set controlledValues: RequestsOnly to keep limits untouched — often what you want for CPU throttling.
9. Admission controller webhook timeout default is 30s — unsafe for prod. During a recommender or API outage, every pod creation in the cluster stalls until the webhook times out. Set --webhook-timeout-seconds=5 and ensure the webhook's failurePolicy: Ignore (the chart default is Ignore; raw manifests historically used Fail).
10. Admission controller sees pod creations cluster-wide unless scoped. The default MutatingWebhookConfiguration matches all pod creations, but VPA only mutates pods whose owning controller has a matching VPA. Scope the webhook via namespaceSelector if you have large clusters where this CPU overhead matters.
11. spec.recommenders on the VPA selects a non-default recommender. Leaving it unset uses default. With VPA 1.4+ you can run custom recommenders alongside the default for specific workloads.
12. DaemonSets need Initial or Off, not Recreate. Evicting a DS pod can't reschedule it off-node, and the pod's new request might exceed the node's remaining allocatable → pending forever. Use Initial so each node's DS pod gets the latest recommendation on its next natural restart.
13. Static CPU Manager and static Memory Manager block in-place resize. Check /var/lib/kubelet/config.yaml — cpuManagerPolicy: static forces eviction for every change, even with InPlaceOrRecreate.
14. Changing a pod from Burstable to Guaranteed (or vice versa) forces eviction. The kubelet refuses in-place resizes that would cross QoS class boundaries, so VPA falls back.
15. The updater respects PDBs. A misconfigured PDB with minAvailable: 100% wedges VPA Recreate forever. In-place updates (VPA 1.6) can bypass PDB with --in-place-skip-disruption-budget when every container has resizePolicy: NotRequired, since nothing actually goes unready.
16. evictionRequirements are AND-joined, not OR-joined. Setting multiple entries narrows the set of eligible evictions. A common use case: [{resources: [memory], changeRequirement: TargetHigherThanRequests}] to only evict for memory increases (preventing OOMKills) while letting CPU drift downward stay applied at next natural pod recreation.
17. evictAfterOOMSeconds default is 0 (immediate) at the CRD level, but the updater's --evict-after-oom-threshold=10m. Pod-specific delay wins if set; otherwise global applies.
18. Scope your recommender's informers (--informer-namespace or namespace-scoped RBAC) on large multi-tenant clusters. VPA 1.6 memory-optimized this but still scales O(pods in watched namespaces × containers). Clusters with 50k+ pods will OOMKill an unscoped recommender on default memory limits.
19. Leader-election lease renamed in 1.3.0. The default changed from vpa-recommender to vpa-recommender-lease to avoid conflicting with GKE's managed VPA. If you run both VPAs (raw + GKE managed) and upgrade the raw one across 1.3, pass --leader-elect-resource-name=vpa-recommender to keep the old name and prevent dual-leader windows.
20. v1beta2 CRDs are gone as of 1.3.0. They're still readable from etcd (served: false, storage: false) so your old objects are preserved, but kubectl apply with apiVersion: autoscaling.k8s.io/v1beta2 fails. Migration is mechanical — every field exists in v1.

Minimum production recipe

For a standard web service on Kubernetes 1.33+ with VPA 1.6:

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-api
  namespace: prod
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api
  updatePolicy:
    updateMode: InPlaceOrRecreate
    minReplicas: 2
    evictAfterOOMSeconds: 60
    evictionRequirements:
      - resources: [memory]
        changeRequirement: TargetHigherThanRequests    # only evict to prevent OOMs; drift-down applies on natural recreate
  resourcePolicy:
    containerPolicies:
      - containerName: web-api
        minAllowed: {cpu: 100m,  memory: 256Mi}
        maxAllowed: {cpu: 4,     memory: 8Gi}
        controlledResources: [cpu, memory]
        controlledValues: RequestsOnly                 # preserve hand-tuned CPU limits
      - containerName: istio-proxy
        mode: Off                                      # don't touch the sidecar
---
# Paired Pod spec fragment — resizePolicy to opt into in-place behavior explicitly
spec:
  containers:
    - name: web-api
      resizePolicy:
        - resourceName: cpu
          restartPolicy: NotRequired
        - resourceName: memory
          restartPolicy: NotRequired    # flip to RestartContainer if the app sizes heap from cgroup at boot
      readinessProbe:                    # see kubernetes probes
        httpGet: {path: /healthz, port: 8080}
        periodSeconds: 5

Pair this with a conservative PodDisruptionBudget (minAvailable: max(1, N-1)), readiness probes so Recreate-fallback evictions drain cleanly, and requests sized such that minAllowed lets VPA size down when a deploy over-provisions. On K8s 1.35 specifically, memory limit decreases are now allowed in-place, which closes the last common reason InPlaceOrRecreate would fall back to eviction on steady-state workloads.
