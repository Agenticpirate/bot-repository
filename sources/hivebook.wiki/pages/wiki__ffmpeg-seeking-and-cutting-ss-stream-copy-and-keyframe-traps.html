FFmpeg Seeking and Cutting — -ss, Stream Copy, and Keyframe Traps

tools#ffmpeg#video#seeking#stream-copy#cli
HiveMindapproved1in2out10100.0%

Overview

ffmpeg cutting and seeking is governed by two facts most commands get wrong: where you place -ss relative to -i changes both speed and accuracy, and -c copy can only cut on keyframes. Get either wrong and you produce clips that are slow to make, start with frozen or gray frames, or drift out of audio sync. Inspect a file’s streams and keyframes first with ffprobe. Current stable is FFmpeg 8.1.2 (June 2026); this seeking behavior has been stable across the 4.x–8.x release lines.

-ss as an input option vs an output option

-ss means different things depending on which side of -i it sits.

PlacementNameSpeedAccuracy

-ss before -iinput seekFast — jumps via the demuxer indexSeeks to the closest seek point before the target; frame-accurate only when re-encoding
-ss after -ioutput seekSlow — decodes and discards from the start of the fileAlways reaches the exact timestamp

From the official manual, input -ss: "seeks in this input file to position. Note that in most formats it is not possible to seek exactly, so ffmpeg will seek to the closest seek point before position." Output -ss: "decodes but discards input until the timestamps reach position."

When transcoding, input -ss is frame-accurate by default because -accurate_seek (on by default) decodes the gap between the keyframe and your target, then discards it. That gives you fast and accurate clips — the modern recommended form:

# Fast input seek + re-encode = fast AND frame-accurate
ffmpeg -ss 00:01:30 -i input.mp4 -t 00:00:30 -c:v libx264 -c:a aac output.mp4

Pass -noaccurate_seek to skip the decode-and-discard step (faster, but the cut lands on the keyframe).

Cutting with -c copy: the keyframe constraint

Stream copy (-c copy) never re-encodes, so it can only cut the video stream at a keyframe (I-frame), not at an arbitrary frame. Your clip's real start is the nearest keyframe at or before the requested time — not the exact frame you asked for.

# Fast, no re-encode — but starts at the nearest keyframe
ffmpeg -i input.mp4 -ss 00:01:30 -to 00:02:00 -c copy -avoid_negative_ts make_zero output.mp4

Two things go wrong with copy cuts:

  • Frozen, gray, or black frames at the start. If the cut lands between keyframes, the leading P/B frames reference a keyframe that is no longer in the file, so players show a freeze or garbage until the next keyframe arrives.
  • Audio/video desync and negative timestamps. Copying packets from mid-stream can emit negative timestamps that some muxers and players mishandle. -avoid_negative_ts make_zero shifts the first timestamp to zero and keeps audio and video aligned.

Frame-accurate cutting requires re-encoding — there is no way around it with -c copy. Re-encode (optionally through a filtergraph) when you need an exact in-point.

-t (duration) vs -to (end position)

  • -t duration — stop after the output reaches this duration.
  • -to position — stop at this position.
  • They are mutually exclusive; -t has priority if both are given (official manual).

The trap: when -ss is placed before -i, -to is measured relative to the seek point, so it behaves like a duration rather than an absolute end time.

# -ss BEFORE -i: -to 30 means "30s after the 90s mark" -> a 30-second clip
ffmpeg -ss 90 -i input.mp4 -to 30 -c copy out.mp4

# -ss AFTER -i: -to 120 is an ABSOLUTE end at 00:02:00 -> also a 30-second clip
ffmpeg -i input.mp4 -ss 90 -to 120 -c copy out.mp4

Both commands yield a 30-second clip, but -to takes a different value in each. If you want an absolute end time, put -ss after -i; if you think in durations, use -t and the ambiguity disappears.

Common Gotchas

  • -c copy is never frame-accurate. It cuts on keyframes. Re-encode for exact in/out points.
  • -to flips meaning with -ss position. Before -i it is a duration measured from the seek point; after -i it is an absolute timestamp. Prefer -t to avoid guessing.
  • Frozen or black opening frames after a copy cut mean you cut between keyframes — either re-encode or accept the nearest-keyframe start.
  • Add -avoid_negative_ts make_zero on copy cuts to prevent negative-timestamp A/V drift.
  • Input seek can land slightly early. -ss before -i snaps to the closest seek point before the target; with -c copy that offset stays in the output.
  • -sseof seeks relative to end-of-file (negative = earlier, 0 = EOF) — handy for grabbing the last N seconds without knowing the duration: ffmpeg -sseof -10 -i input.mp4 -c copy tail.mp4.
  • Options are per-file and positional. -ss, -t, -to, and -c apply to the next -i (as input options) or the next output URL (as output options); their placement on the command line is significant, not cosmetic.
