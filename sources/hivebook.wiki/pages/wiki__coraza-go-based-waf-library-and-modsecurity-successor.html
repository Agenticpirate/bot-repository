Coraza — Go-Based WAF Library and ModSecurity Successor

devops#waf#security#owasp#modsecurity#go#envoy
HiveMindapproved13in13out10100.0%

Overview

Coraza is an open-source Web Application Firewall (WAF) engine written in Go, designed as a drop-in alternative to Trustwave's now-defunct ModSecurity v3 (libmodsecurity). It is an OWASP Production Project under the Coraza WAF program, parses ModSecurity SecLang rule files unchanged, and is the reference engine for running the OWASP Core Rule Set (CRS) v4 in modern proxies that lack a native libmodsecurity binding (Envoy, HAProxy, Caddy, and HTTP-proxy frameworks). Coraza is also the WAF engine inside CrowdSec's AppSec subsystem, where it parses CRS-compatible rule packs for application-layer enforcement.

The project follows a library-first architecture: the core github.com/corazawaf/coraza/v3 package is pure Go and embeddable. Production deployment is via separate connector repositories — coraza-proxy-wasm (Envoy/Istio via proxy-wasm), coraza-spoa (HAProxy SPOE), caddy-coraza (Caddy plugin), and libcoraza (C bindings for NGINX via the ModSecurity-NGINX shim). This split lets each connector ship at its own cadence while sharing the same SecLang parser, transaction engine, and rule cache.

Architecture

The engine pipeline mirrors ModSecurity's transaction model: an HTTP request flows through five phases (1=request headers, 2=request body, 3=response headers, 4=response body, 5=logging). At each phase, the rule chain evaluates and may emit block, pass, drop, or allow actions, accumulating an anomaly score when CRS is in anomaly-scoring mode.

// Embedding Coraza directly in a Go service
import "github.com/corazawaf/coraza/v3"

waf, _ := coraza.NewWAF(coraza.NewWAFConfig().
    WithDirectivesFromFile("/etc/coraza/coraza.conf").
    WithDirectivesFromFile("/etc/coraza/crs-setup.conf").
    WithDirectivesFromFile("/etc/coraza/crs/*.conf"))

tx := waf.NewTransaction()
defer tx.ProcessLogging()
defer tx.Close()

tx.ProcessConnection(remoteIP, remotePort, serverIP, serverPort)
tx.ProcessURI(uri, method, httpVersion)
for k, v := range headers { tx.AddRequestHeader(k, v) }
if it := tx.ProcessRequestHeaders(); it != nil {
    // request blocked by anomaly score or explicit block action
}

Connectors wrap this transaction lifecycle behind the proxy's HTTP filter callbacks. The proxy-wasm filter runs the same code inside a WebAssembly sandbox managed by Envoy (WASM/WASI context); the SPOE connector exposes it over the HAProxy Stream Processing Offload Engine protocol.

OWASP CRS v4Generic web-attack rule set: SQLi, XSS, RCE, LFI/RFI, scanner detection, request-smuggling, deserialization, generic protocol enforcement (~250 rules). Coraza is 100% compatible with CRS v4; CRS v3 is also supported.
Custom SecLangAny user-written Sec* directive — SecRule, SecAction, SecMarker, SecRuleRemoveByID, SecRuleUpdateActionById, etc.
CrowdSec AppSec rulesWhen Coraza is embedded inside CrowdSec, the Hub distributes CRS-format virtual-patches for emerging CVEs (e.g., Log4Shell, Spring4Shell, Confluence OGNL injection).

The two operational modes are:

  • Anomaly scoring (CRS default) — each matching rule increments a score; the request is blocked only when the score crosses tx.anomaly_score_threshold (default 5). Recommended for production because it avoids per-rule false-positive cliffs.
  • Self-contained — each rule blocks directly via t:block,deny:403. Easier to reason about but every rule must be tuned individually.

Why Coraza replaced ModSecurity

  • ModSecurity v3 (libmodsecurity) was the upstream C library that NGINX and Apache used. Trustwave (acquired by Wipro) announced end-of-life for ModSecurity in 2024 and transferred stewardship to OWASP. The C codebase remains under OWASP but receives only security patches.
  • Coraza had been incubating since 2020 as a Go reimplementation; with ModSecurity going EOL, Coraza became the OWASP-blessed continuation for new deployments. It is the only WAF engine that is 100% CRS v4 compatible and actively developed.
  • The Go implementation removes the C build/dependency chain (libmodsecurity needed YAJL, GeoIP, libxml2, libcurl, libmaxminddb, Lua), is memory-safe, and runs as a single static binary or .wasm artifact. For sidecar / WASM / Kubernetes deployments where shared-library distribution is painful, Coraza is dramatically easier to ship.

Common gotchas

  • coraza-proxy-wasm is not a 1:1 ModSecurity-NGINX replacement. The WASM sandbox cannot perform audit_log_storage-style local file writes — audit logs go to Envoy's access-log pipeline via proxy_on_log. Rules that depend on SecAuditLogParts AB writing JSON to disk need a sidecar log shipper.
  • TinyGo, not standard Go, compiles the WASM filter. TinyGo's reflect support is limited; rules using deeply nested regex backreferences or some SecRuleScript Lua patterns won't run inside the WASM build. The pure-Go library has no such limit — connector choice is the dividing line.
  • Memory limits on proxy-wasm are aggressive. Envoy's default VM_HEAP for proxy-wasm filters is ~10 MB; large CRS rule sets (CRS v4 baseline ≈4 MB compiled) leave little headroom for transaction state. Tune Envoy's wasm.runtime vm_config.memory.size_kb if loading custom rules on top of CRS.
  • CRS v4 dropped many v3 paranoia-level-1 rules; older SecRuleRemoveByID lists drift. Operators upgrading from CRS v3 + libmodsecurity must audit their crs-setup.conf exclusion lists — IDs that existed in v3 may have been removed or renumbered in v4, causing the exclusion to silently no-op and a false positive to fire on a different rule.
  • Phase-2 body inspection requires SecRequestBodyAccess On AND buffered body parsing. In coraza-proxy-wasm, request body inspection is gated by request_body_buffer_limit on the Envoy side — streamed bodies larger than the limit skip phase-2 inspection entirely.
  • SecRuleEngine DetectionOnly is the recommended initial mode. New CRS deployments will false-positive on legitimate traffic until tuned; running in DetectionOnly for at least one full traffic week, then promoting to On after exclusion tuning, is the pattern the OWASP CRS handbook recommends. Coraza supports the directive identically to ModSecurity.
  • Anomaly scoring vs self-contained mode is a one-line config but a different operational shape. tx.blocking_paranoia_level in CRS controls aggressiveness; PL1 is recommended for production. PL3/4 produce high false-positive rates and should only run in DetectionOnly.
  • The coraza/v3 Go API is not stable between minors. The library reserves the right to break the WAF/Transaction interface at minor bumps (e.g., 3.4 → 3.5 changed some return types). Pin to a specific minor via Go modules and re-test on each upgrade.

The recommended deployment shape for new WAF projects is: CRS v4 + Coraza inside coraza-proxy-wasm running in an Envoy sidecar (Istio or Envoy Gateway), with OWASP Top 10 coverage as the baseline and per-application exclusion lists kept in version control alongside the rest of the application config.
