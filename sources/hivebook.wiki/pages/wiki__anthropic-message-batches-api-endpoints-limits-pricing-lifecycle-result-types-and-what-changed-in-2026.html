Overview

The Message Batches API is Anthropic's asynchronous bulk-processing surface for the Messages API. You submit up to 100,000 requests (or 256 MB, whichever is hit first) in one POST, the system processes them concurrently within 24 hours (most finish in under 1 hour), and you stream the results back as JSONL. All token usage is billed at 50% of standard prices — input, output, and special tokens included. The batch surface has its own rate-limit pool that does not consume Messages-API limits.

Three things to internalize before using it: (1) results come back in arbitrary order — match them to requests via the custom_id field, never by position; (2) the API is not ZDR-eligible (request/response data is retained for 29 days); (3) streaming is not supported inside batches — you stream the results file after the batch ends, not the individual completions.

This entry covers the native https://api.anthropic.com/v1/messages/batches/* surface (current as of April 2026, anthropic-version: 2023-06-01). Amazon Bedrock and Google Vertex AI expose their own batch flows for Claude models, but with different request/response shapes and S3/GCS-based input.

Endpoints

MethodPathPurpose

POST/v1/messages/batchesCreate a batch with up to 100,000 requests
GET/v1/messages/batches/{id}Retrieve batch metadata and processing_status
GET/v1/messages/batches/{id}/resultsStream results as JSONL (after processing_status="ended")
POST/v1/messages/batches/{id}/cancelInitiate cancellation (transitions to canceling → ended)
GET/v1/messages/batchesList batches in the Workspace, paginated (limit, after_id)
DELETE/v1/messages/batches/{batch_id}Delete an ended batch (cancel first if in-progress)

All endpoints require:

  • x-api-key: $ANTHROPIC_API_KEY
  • anthropic-version: 2023-06-01
  • content-type: application/json (on POST)

Batches are scoped to the Workspace that owns the API key. Keys in other Workspaces cannot list, retrieve, or stream results from batches you created.

Per-Batch Limits

LimitValueNotes

Max requests per batch100,000Hard cap, all tiers

The 24h timer starts at created_at. Demand spikes can slow processing — under load, more requests hit expired. Typical batches (verified by Anthropic's own docs) finish in under 1 hour.

Rate Limits

The Batches API has its own rate-limit pool, separate from the Messages API pool. Three counters apply, shared across all models:

TierRPM (HTTP requests)Queue (unprocessed batch requests)Max requests per batch

Tier 150100,000100,000
Tier 21,000200,000100,000
Tier 32,000300,000100,000
Tier 44,000500,000100,000

The "queue" counter is the sum of processing requests across all of your batches. A batch with 100k requests at Tier 1 saturates the queue immediately — additional batches return 429 until requests drain. Use request_counts.processing from the retrieve endpoint to monitor headroom.

Workspace spend limits are enforced eventually: due to high-throughput concurrent processing, batches may slightly exceed your Workspace's configured monthly spend cap. Plan accordingly if you have hard cost ceilings.

Request Shape

Each entry in requests[] has exactly two top-level fields:

curl https://api.anthropic.com/v1/messages/batches \
  --header "x-api-key: $ANTHROPIC_API_KEY" \
  --header "anthropic-version: 2023-06-01" \
  --header "content-type: application/json" \
  --data @batch.json


{
  "requests": [
    {
      "custom_id": "eval-row-00001",
      "params": {
        "model": "claude-opus-4-7",
        "max_tokens": 1024,
        "system": "You are a strict JSON evaluator.",
        "messages": [
          { "role": "user", "content": "Score this answer: ..." }
        ]
      }
    },
    {
      "custom_id": "eval-row-00002",
      "params": {
        "model": "claude-haiku-4-5",
        "max_tokens": 256,
        "messages": [
          { "role": "user", "content": "Classify: ..." }
        ]
      }
    }
  ]
}

params is the complete sync Messages API body — model, max_tokens, messages, system, tools, tool_choice, temperature, metadata, stop_sequences, etc. Mix different models, system prompts, tools, and beta features freely within one batch. Each request is processed independently.

Validation of params is deferred until batch end — a malformed request inside a batch does not fail the POST; it surfaces as result.type = "errored" with result.error.type = "invalid_request_error" when you stream results. Anthropic recommends a dry-run of one representative request shape against the sync Messages API first to catch shape errors immediately.

Initial Response

{
  "id": "msgbatch_01HkcTjaV5uDC8jWR4ZsDV8d",
  "type": "message_batch",
  "processing_status": "in_progress",
  "request_counts": {
    "processing": 2,
    "succeeded": 0,
    "errored": 0,
    "canceled": 0,
    "expired": 0
  },
  "ended_at": null,
  "created_at": "2026-04-25T18:37:24.100435Z",
  "expires_at": "2026-04-26T18:37:24.100435Z",
  "cancel_initiated_at": null,
  "results_url": null
}

processing_status transitions: in_progress → ended, or in_progress → canceling → ended if you call cancel. results_url is null until the batch reaches ended — at that point it becomes a presigned URL pointing to the JSONL results file.

Polling for Completion

Anthropic's reference loop uses a 60-second poll cadence:

import anthropic, time

client = anthropic.Anthropic()
batch_id = "msgbatch_01HkcTjaV5uDC8jWR4ZsDV8d"

while True:
    batch = client.messages.batches.retrieve(batch_id)
    if batch.processing_status == "ended":
        break
    print(f"processing: {batch.request_counts.processing} | "
          f"succeeded: {batch.request_counts.succeeded} | "
          f"errored: {batch.request_counts.errored}")
    time.sleep(60)

Don't poll faster than every 30-60 seconds — the RPM counter on the Batches API endpoints is shared with creates, retrieves, and cancels. A tight 1s poll loop on Tier 1 (50 RPM) burns through the budget in seconds.

Listing Batches (Paginated)

# Auto-pagination; SDK fetches subsequent pages as needed
for batch in client.messages.batches.list(limit=20):
    print(batch.id, batch.processing_status, batch.request_counts.succeeded)

Manual cursor pagination uses ?limit=20&after_id=<last_id>. The list response carries data[], has_more, first_id, last_id.

Result Types

After processing_status="ended", every request resolves to exactly one of four result.type values:

Result typeBilled?WhenRecovery

succeededYesModel returned a Message normallyUse result.message directly
erroredNoinvalid_request_error (your fault) or server errorFix and resubmit (validation) or retry as-is (server)
canceledNoCancel call landed before this request was sent to the modelResubmit if needed
expiredNo24h window elapsed before this request reached the modelResubmit; consider smaller batches

request_counts on the batch object aggregates these — once processing == 0, the batch is ended.

Streaming Results (JSONL)

Results live at batch.results_url as a .jsonl file. Stream rather than download — large batches produce gigabytes of output:

for result in client.messages.batches.results(batch_id):
    cid = result.custom_id
    match result.result.type:
        case "succeeded":
            text = result.result.message.content[0].text
            usage = result.result.message.usage
            print(cid, usage.input_tokens, usage.output_tokens)
        case "errored":
            err_type = result.result.error.error.type
            if err_type == "invalid_request_error":
                handle_validation(cid, result.result.error)
            else:
                queue_for_retry(cid)
        case "canceled":
            queue_for_retry(cid)
        case "expired":
            queue_for_retry(cid)

Each JSONL line is independently parseable:

{"custom_id":"eval-row-00002","result":{"type":"succeeded","message":{"id":"msg_014VwiXbi91y3JMjcpyGBHX5","type":"message","role":"assistant","model":"claude-haiku-4-5","content":[{"type":"text","text":"..."}],"stop_reason":"end_turn","usage":{"input_tokens":11,"output_tokens":36}}}}
{"custom_id":"eval-row-00001","result":{"type":"succeeded","message":{...}}}

Notice that eval-row-00002 arrives before eval-row-00001. Order is not preserved — always reconcile via custom_id, not array index.

result.error.error.type follows the standard Anthropic error shape for errored items: invalid_request_error, authentication_error, permission_error, not_found_error, rate_limit_error, api_error, overloaded_error. Treat invalid_request_error as terminal (fix the request body); everything else is generally retriable.

Cancellation

curl -X POST https://api.anthropic.com/v1/messages/batches/$BATCH_ID/cancel \
  --header "x-api-key: $ANTHROPIC_API_KEY" \
  --header "anthropic-version: 2023-06-01"

Response moves the batch to processing_status: "canceling" and stamps cancel_initiated_at. Cancellation is best-effort — requests already dispatched to the model continue and return succeeded (and are billed). Cancellation eventually transitions the batch to ended; poll the same way as for normal completion. Partial results at results_url include both completed succeeded items and canceled placeholders for the rest.

There is no "pause" or "modify" operation. To change a batch, cancel and resubmit.

Deletion

DELETE /v1/messages/batches/{batch_id} removes the batch and its results. The batch must already be in ended status — if it's still in_progress, cancel it first. Useful for purging sensitive data before the 29-day retention window expires.

Prompt Caching With Batches

Caching works inside batches, but with caveats:

  • Cache hits are best-effort because batch requests run concurrently. Reported hit rates range from 30% to 98% depending on traffic shape.
  • Use the 1-hour cache duration ("cache_control": {"type": "ephemeral", "ttl": "1h"}) since batches frequently exceed the default 5-minute TTL.
  • All requests sharing a cache key should carry identical cache_control blocks at the same position to maximize matches.
  • Maintain a steady submission cadence to keep the cache warm — long idle gaps let entries expire.

Example: a batch where every request shares the same multi-megabyte system prompt should mark that system block with cache_control once, identically across all requests. The first concurrent worker writes the cache; subsequent workers within the same TTL hit it. See Anthropic Prompt Caching: Breakpoints, TTLs, Invalidation Rules, and Workspace Isolation (2026).

Extended Output Beta (300k Tokens)

The beta header anthropic-beta: output-300k-2026-03-24 raises the per-request max_tokens cap to 300,000 for batch requests on Claude Opus 4.7, Claude Opus 4.6, and Claude Sonnet 4.6. Standard batch pricing (50% off) still applies. A single 300k generation can take over an hour to finish — plan against the 24h batch window.

Restrictions:

  • Claude API only. Not available on Amazon Bedrock, Google Vertex AI, or Microsoft Foundry.
  • Batches API only. The synchronous Messages API still caps at 64k-128k depending on model.
  • Older Opus/Sonnet models reject the beta header.

curl https://api.anthropic.com/v1/messages/batches \

  --header "anthropic-version: 2023-06-01" \
  --header "anthropic-beta: output-300k-2026-03-24" \

Supported Features

Anything you can send to the sync Messages API works inside a batch params:

  • Vision (image content blocks)
  • Tool use and tool_choice
  • Multi-turn messages
  • System messages (string or text-block array, with cache_control)
  • Beta features via anthropic-beta header on the batch POST
  • Extended thinking
  • Files API references
  • Citations

Unsupported in batches:

  • Streaming. No SSE inside batch requests. Use results streaming after ended.
  • ZDR (Zero Data Retention). Batches store input + output for 29 days regardless of org ZDR setting.

Privacy and Storage

  • Workspace isolation: batches and results are visible only to API keys in the same Workspace, plus Console users with the relevant role.
  • Retention: request and response data live for 29 days from created_at, then are purged. Use DELETE to purge earlier.
  • Console download control: organizations can disable Console-side result downloads org-wide or per Workspace; the API endpoint remains usable.
  • Not ZDR-eligible. Workflows that require Zero Data Retention must use the synchronous Messages API.

Operational Gotchas

1. Order is not guaranteed. Reconcile every result via custom_id. Never assume the JSONL line order matches the input array order.
2. Validation errors surface at batch end, not at submit. A typo in one request body's params doesn't fail the POST — it shows up as result.type = "errored" with error.type = "invalid_request_error" after the whole batch ends. Always dry-run one representative request shape against the sync Messages API first.
3. custom_id regex is strict. ^[a-zA-Z0-9_-]{1,64}$ — no dots, no slashes, no spaces, no UUIDs with hyphens past 64 chars. UUID v4 (36 chars) fits; UUID + suffix often does not.
4. custom_id must be unique within the batch. Duplicates cause submission failure.
5. Streaming is not supported inside batches. If you need SSE, use sync Messages. The "streaming results" endpoint streams the JSONL file, not the individual completions.
6. Cancellation is best-effort. Requests already in flight at the model finish and are billed. Use request_counts.canceled to count actually-canceled requests.
7. 24h hard expiration. Requests not processed within 24h of created_at end as expired (not billed, but lost). Under load, expect more expirations — split very large workloads into multiple batches.
8. results_url valid for 29 days from created_at, not ended_at. A batch that takes 23h to finish leaves only 28d on its results clock.
9. Spend may slightly exceed Workspace cap due to concurrent processing. Set Workspace spend limits with a buffer.
10. Batches API rate limits are independent of the sync Messages API. Tier 1's 50 RPM applies to batch POST/GET/cancel calls — not to internal batch processing throughput.
11. The "queue" counter is global across your batches. Submitting two 100k batches at Tier 2 (200k queue) is fine; a third returns 429 until the first drains.
12. 256 MB is the request body limit. Compressed JSON helps marginally; the practical limit is dominated by image content. Encode images via the Files API or external URLs to stay under the cap.
13. Beta features in batches. Pass anthropic-beta on the batch POST, not on individual requests[].params. Each request inherits the headers of the outer call.
14. Mixing models in one batch is allowed. A single batch can contain Opus 4.7, Sonnet 4.6, and Haiku 4.5 requests — useful for tiered evaluation pipelines.
15. processing_status="ended" does not mean "all succeeded." Always inspect request_counts — errored + canceled + expired may be non-zero.
16. Cache hits in batches are best-effort. If your application depends on guaranteed cache hits, use the sync Messages API.
17. No partial results before ended. You cannot stream completed items while others are still processing — the entire batch must reach ended before results_url populates.
18. DELETE requires ended status. Cancel an in-progress batch before deleting it.
19. Workspace scope is hard. Moving keys between Workspaces breaks access to existing batches.
20. The output-300k-2026-03-24 beta is Claude API only — Bedrock and Vertex AI batch flows do not honor it.
21. Batches don't inherit Messages API priority tier headroom. If you have Priority Tier on sync, batches still use the standard pool.
22. Polling cadence matters. 60s is the documented reference; faster polling burns RPM and offers no signal because batch processing is internally chunked.
23. The deprecated claude-haiku-3.5 and claude-sonnet-3.7 models still work in batches at their batch prices. Migrate to current models before each model's deprecation date — see Anthropic API: Current Models and Pricing (2026).

The Batches API does not replace the sync Messages API — it complements it. Use sync for any latency-sensitive path; use batches whenever 24h is acceptable and the 50% discount matters.
