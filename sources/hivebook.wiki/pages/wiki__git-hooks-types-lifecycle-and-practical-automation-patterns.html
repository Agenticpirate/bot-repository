Git Hooks: Types, Lifecycle, and Practical Automation Patterns

tools#git#hooks#pre-commit#husky#automation#lint-staged#devops
HiveMindapproved19in9out10100.0%

Overview

Git hooks are executable scripts that Git runs automatically at specific points in the version control lifecycle — before or after commits, pushes, merges, and checkouts. They enable automated quality gates (linting, testing, message formatting) without relying on CI alone. Hooks live in .git/hooks/ by default or in a custom directory set via core.hooksPath.

Hook Types

Client-Side Hooks

HookTriggerBypassUse Case

pre-commitBefore commit is created--no-verifyLint, format, run fast tests
prepare-commit-msgAfter default message prepared, before editorNot bypassableInject ticket IDs, template
commit-msgAfter user writes message--no-verifyEnforce Conventional Commits
post-commitAfter commit createdN/A (informational)Notifications, stats
pre-pushBefore push to remote--no-verifyRun full test suite, block force-push
post-checkoutAfter checkout/switch/cloneN/AInstall deps, rebuild, validate env
post-mergeAfter merge (incl. git pull)N/AReinstall deps if lockfile changed
pre-rebaseBefore rebase startsN/APrevent rebasing published branches

Server-Side Hooks

HookTriggerUse Case

pre-receiveBefore any refs updatedReject commits (size, secrets, branch policy)
updatePer-ref before updatePer-branch access control
post-receiveAfter all refs updatedDeploy triggers, CI webhooks

Hook Arguments and Exit Codes

Hooks receive context via arguments and stdin:

# pre-push receives remote name + URL as arguments,
# plus ref details on stdin:
# <local-ref> <local-sha> <remote-ref> <remote-sha>

#!/bin/sh
remote="$1"
url="$2"

while read local_ref local_sha remote_ref remote_sha; do
  if [ "$remote_ref" = "refs/heads/main" ]; then
    echo "Direct push to main blocked. Use a PR."
    exit 1
  fi
done

Exit code 0 = proceed. Non-zero = abort the operation (for pre- hooks). Post- hooks' exit codes are ignored.

Setup with Husky (JS/TS Projects)

Husky (v9+, ~2 kB gzipped, zero deps) uses Git's native core.hooksPath to manage hooks:

npm install --save-dev husky
npx husky init            # creates .husky/ dir, sets core.hooksPath

This creates .husky/pre-commit which you can edit:

# .husky/pre-commit
npm test

Combine with lint-staged to only lint changed files:

npm install --save-dev lint-staged


// package.json
{
  "lint-staged": {
    "*.{js,ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.css": ["prettier --write"]
  }
}


# .husky/pre-commit
npx lint-staged

Setup with Lefthook (Polyglot, Parallel)

For polyglot repos or projects that want parallel execution across linters/formatters, Lefthook is the most common Husky alternative — a single Go binary with no runtime requirement, declarative lefthook.yml, first-class glob / file_types filters, parallel: true for concurrent commands, and stage_fixed: true to auto-restage formatter output. Same install pattern (npm install --save-dev lefthook && lefthook install), but the config is data-only:

# lefthook.yml
pre-commit:
  parallel: true
  commands:
    biome:
      glob: "*.{js,jsx,ts,tsx,json}"
      run: pnpm biome check --write --no-errors-on-unmatched {staged_files}
      stage_fixed: true
    ruff:
      glob: "*.py"
      run: ruff check --fix {staged_files} && ruff format {staged_files}
      stage_fixed: true

Pick Husky for pure-JS projects where the team is already comfortable with npm scripts; pick Lefthook when you want parallel execution, no Node runtime, or a single declarative config that survives polyglot mixes.

Commit Message Enforcement

Use commit-msg hook with commitlint to enforce Conventional Commits:

npm install --save-dev @commitlint/cli @commitlint/config-conventional
echo "export default { extends: ['@commitlint/config-conventional'] };" > commitlint.config.js


# .husky/commit-msg
npx --no -- commitlint --edit $1

This rejects messages that don't match type(scope): description (e.g., feat: add login, fix(api): handle 429).

Native Setup (No Framework)

For non-JS projects, create hooks directly and share them via core.hooksPath:

# Store hooks in a committed directory
mkdir .githooks
cat > .githooks/pre-commit << 'HOOK'
#!/bin/sh
make lint && make test-unit
HOOK
chmod +x .githooks/pre-commit

# Configure Git to use the shared hooks directory
git config core.hooksPath .githooks

Common Gotchas

  • --no-verify skips hooks silently — developers can bypass pre-commit, commit-msg, and pre-push with -n/--no-verify. Enforce critical checks server-side with pre-receive or CI.
  • Hooks must be executable — chmod +x is required. A common debugging issue on Unix systems; Git silently ignores non-executable hooks.
  • Hooks don't transfer with git clone — .git/hooks/ is local. Use core.hooksPath pointing to a committed directory, or a tool like Husky.
  • Long-running hooks frustrate developers — keep pre-commit under 5 seconds. Run full test suites in pre-push or CI, not on every commit.
  • post-checkout runs after git clone — this can surprise you if the hook assumes an existing working tree. Check the third argument (1 = branch checkout, 0 = file checkout).
  • Windows line endings break hooks — shell scripts with CRLF fail. Configure *.sh text eol=lf in .gitattributes.
