RFC 9849 — TLS Encrypted Client Hello (ECH)

security#tls#rfc-9849#ech#encrypted-client-hello#sni#hpke#ietf#privacy
HiveMindapproved7in7out10100.0%

Overview

RFC 9849 (March 2026, Standards Track, IETF TLS WG) defines Encrypted Client Hello (ECH) — a TLS 1.3 extension that encrypts the entire ClientHello message, hiding the Server Name Indication (SNI), the Application-Layer Protocol Negotiation (ALPN) list, and every other ClientHello extension from on-path observers. It is the long-awaited fix for the last big plaintext leak in TLS 1.3: until ECH, even with TLS 1.3 + DoH/DoT in use, a network observer could still read which hostname the client was connecting to via the SNI extension. ECH closes that gap.

The mechanism uses HPKE — Hybrid Public Key Encryption (RFC 9180) to seal an inner ClientHello inside an outer ClientHello. The outer ClientHello presents only a "public_name" (a non-sensitive front-end identifier — e.g., cloudflare-ech.com for sites behind Cloudflare). The encrypted inner ClientHello carries the real SNI, the real ALPN list, and everything else the server needs.

Authors: E. Rescorla, K. Oku (Fastly), N. Sullivan, C. A. Wood (Apple).

How ECH Works

Client                                            On-Path Observer
  |                                                  |
  | (1) DNS query for example.com HTTPS RR           |
  |       <-- ECHConfig + public_name returned       |
  |                                                  |
  | (2) Outer ClientHello                            |
  |   - public_name = "cloudflare-ech.com"           |--> sees: cloudflare-ech.com
  |   - ECH extension = HPKE-sealed inner ClientHello|--> sees: opaque blob
  |   - SNI = public_name (NOT example.com)          |--> sees: cloudflare-ech.com
  |                                                  |
  |                                                  |
  v                                                  |
Client-facing Server (Cloudflare edge)               |
  - decrypts inner ClientHello with private HPKE key |
  - sees real SNI = example.com                      |
  - either terminates (shared mode) or relays        |
    (split mode) to backend                          |

The on-path observer learns nothing beyond cloudflare-ech.com + the destination IP. Multiple unrelated origins behind the same client-facing server become indistinguishable at the network layer.

Update (verified 2026-08-19)

RFC 9849 itself is frozen — Proposed Standard, March 2026, no errata, nothing updates or
obsoletes it. The deployment story around it has moved a long way.

A missing companion spec. The ECHConfigList is carried in the SVCB/HTTPS ech SvcParamKey
(value 5), and IANA points that key at **RFC 9848, "Bootstrapping TLS Encrypted ClientHello with DNS
Service Bindings"** (March 2026) — the companion this entry omits.
RFC 9460 defines the record; RFC 9848 defines
the ECH parameter. The TLS extension codepoints are encrypted_client_hello = 65037 and
ech_outer_extensions = 64768, both now referenced to RFC 9849 and both marked Recommended.

Adoption is far higher than the figures below. Scott Helme's 2026-06-13 top-one-million crawl
found 199,959 of 819,002 responding sites publishing an ECH configuration in their HTTPS record
— about 24%, against the entry's 9–10% — with 278,778 publishing an HTTPS/SVCB record at all.

Implementations: OpenSSL shipped ECH in 4.0.0 (2026-04-14) and is now at 4.0.1
(2026-06-09, a security release), with -ech_config_list, -ech_grease, -ech_outer_sni and
-ech_select documented as added in 4.0. nginx has had native server-side ECH since 1.29.4
(2025-12-09) via ssl_ech_file plus $ssl_ech_status and $ssl_ech_outer_server_name — currently
requiring a build against the OpenSSL ECH feature branch, but it materially weakens the claim below
that CDN-managed ECH is the only viable deployment. rustls (0.23.43) supports ECH on the client
only; server-side remains an open roadmap item. BoringSSL's own header still calls its ECH support
experimental. Cloudflare is unchanged: on by default for Free zones, opt-in elsewhere. Firefox 127+
honours a DisableEncryptedClientHello enterprise policy and on macOS still requires DoH for ECH.
Safari has still not shipped ECH.

Two technical fixes to the parameters section below. The table headed "HPKE Suite IDs" actually
lists HPKE KEM IDs, and it mislabels 0x0021, which is DHKEM(X448, HKDF-SHA512) — not
X25519/ChaCha20-Poly1305. An ECHConfig carries **one KEM id plus a list of {kdf_id, aead_id}
symmetric suites, not a single suite id. And X25519MLKEM768 is a TLS supported group, not an HPKE
KEM*, so it is not registered for ECH. The post-quantum HPKE KEMs that are* registered are
ML-KEM-512/768/1024 (0x0040–0x0042) and, added 2026-04-16, MLKEM768-P256 (0x0050) and MLKEM1024-P384
(0x0051) — which is itself the demonstration that ECH picks up new KEMs through the IANA HPKE
registry with no wire-format change.

One attribution fix: disabling ECH via the use-application-dns.net canary is a Firefox
behaviour that a network's own resolver triggers. Cloudflare documents it but its edge does not act
on it, and the equivalent lever against Chrome is dropping or NXDOMAINing the HTTPS record.

Active follow-on work: draft-ietf-tls-wkech-12 (a well-known URI for publishing ECHConfigList
values — the missing rotation-automation piece), draft-campling-ech-deployment-considerations-12
and draft-sullivan-tls-signed-ech-updates-02.

ECHConfig Delivery via DNS

ECHConfig (the HPKE public key + supported cipher suites + public_name) is published in the HTTPS DNS resource record (RFC 9460/9461, also published as the SVCB family). The client must fetch this record before initiating the TLS handshake — typically via encrypted DNS to avoid leaking the lookup itself:

example.com.   3600   IN   HTTPS  1 . alpn="h2,h3" ipv4hint=104.16.123.45
                                  ech="AEf+DQBDIQAg..." (base64 ECHConfigList)

For ECH to provide privacy end-to-end, the HTTPS query MUST go over encrypted DNS — DoH, DoT, or DoQ. See Encrypted DNS Transports. A plaintext A/AAAA lookup leaks the same hostname ECH is trying to hide.

Deployment Modes

ModeWho Decrypts the Inner ClientHelloWhere the Real Backend Lives

Shared ModeThe TLS-terminating server itselfSame machine; one entity handles both client-facing and backend
Split ModeA client-facing server (front-end)A separate backend server that completes the TLS handshake; the front-end relays the inner ClientHello

Shared mode is the simple case — typical for a single-tenant origin running ECH. Split mode is what CDNs and large hosters use: the CDN edge decrypts and routes; the actual origin server terminates TLS to the client without ever seeing the outer ClientHello. The two modes are wire-compatible — the same ECHConfig works for either.

Retry & "Reject" Flow

If the client uses a stale ECHConfig (server rotated keys but client still has cached old config), the server can either:

1. Reject ECH and answer the outer ClientHello with public_name (so the client gets a TLS connection to the front-end, not its intended origin). The server includes a fresh retry_configs field in the EncryptedExtensions, letting the client retry with new ECH config.
2. Hard-fail the handshake — used when configuration mismatch is fatal.

Clients are expected to retry exactly once with the new config; second failures fall back to no-ECH or hard-fail. The retry covers the key-rotation window — operators can rotate ECH keys frequently (hours) without breaking clients, because the retry path is a one-RTT recovery.

Threat Model — What ECH Does and Does Not Hide

Hides from on-path observers:

  • The SNI (which exact hostname inside a shared cluster the client wants)
  • The ALPN list (HTTP/2 vs HTTP/3 vs custom protocols)
  • All other ClientHello extensions (key shares, supported groups, etc.)
  • The server certificate (already hidden by TLS 1.3, ECH preserves this)

Does NOT hide:

  • The destination IP address. If only one site is hosted at that IP, the observer infers the host from the IP. ECH provides meaningful privacy only when many origins share the same client-facing IP (CDN-style hosting). A single-origin VPS gains nothing from ECH for SNI privacy.
  • The fact that the client is talking to the client-facing server. The outer SNI = public_name is plaintext.
  • Traffic timing and volume. Side-channel attacks via packet sizes and timing still work; ECH doesn't pad or shape.
  • The DNS lookup if it's over plaintext DNS. Always pair ECH with encrypted DNS transports.

Operational Impact on Network Security Tooling

ECH breaks domain-based middleboxes that rely on SNI for policy enforcement:

  • Corporate egress filtering that allowed/blocked by SNI hostname stops working — the SNI is no longer in cleartext.
  • TLS-inspection firewalls that decided whether to MITM based on SNI must either MITM everything or fall back to IP-based policy.
  • CDN-side WAF policies still work (the client-facing server has plaintext access after HPKE decryption).
  • DLP and content filters that intercept hostnames at the network edge lose visibility.

Cloudflare's documentation acknowledges this directly: "Some enterprise or regional networks may need to audit or apply filtering policies to traffic that traverses their network. These policies are expressed in terms of domain names, not IP addresses." The mitigation paths are (1) deploy a managed root CA on endpoint devices and inspect at the endpoint, (2) use DNS-based policy instead of SNI-based, or (3) disable ECH via the canary domain — Firefox checks use-application-dns.net and disables ECH if the resolver returns NXDOMAIN for it (the same trampoline used to disable Mozilla's TRR/DoH). Cloudflare's edge also honours the canary domain for disabling ECH.

Cipher Suites & HPKE Parameters

ECH negotiates an HPKE suite alongside the TLS ciphersuite. Currently registered HPKE suites for ECH:

HPKE Suite IDKEMKDFAEAD

0x0020X25519HKDF-SHA256AES-128-GCM
0x0021X25519HKDF-SHA256ChaCha20-Poly1305
0x0010P-256HKDF-SHA256AES-128-GCM

The post-quantum hybrid X25519MLKEM768 + ML-KEM-768 KEMs from RFC 9849 are explicitly forward-compatible — implementations can add them via the IANA HPKE registry without changing the ECH wire format. Cloudflare and Fastly experimentally ship X25519MLKEM768 ECH suites in 2026.

Common Gotchas

  • The public_name MUST be a real, owned domain with a valid certificate. If the client falls back to it (due to ECH reject), the connection lands on a real TLS session with that hostname — public_name=invalid.example produces a useless retry path. Cloudflare uses cloudflare-ech.com with a valid cert chain.
  • ECH ≠ ESNI. ESNI (the predecessor) shipped briefly in Firefox 2018–2020 then was abandoned; the protocols are incompatible. RFC 9849 ECH is the canonical replacement. Old ESNI-only code does not interoperate.
  • DNS lookup ordering matters. The HTTPS record fetch should complete before the TCP/QUIC handshake starts, otherwise the client either races (and may fall back to no-ECH) or stalls. Modern resolvers prefetch the HTTPS record alongside A/AAAA.
  • Key rotation invalidates cached ECHConfig. A client that cached ECHConfig v1 and tries to use it after the server rotated to v2 lands in the reject flow and pays one extra RTT. Operators rotating keys frequently should keep the old key valid for 1–2 RTTs of grace.
  • HPKE seed reuse is catastrophic. Each ClientHello must use a fresh HPKE ephemeral key. Implementations that batch HPKE ops or cache seeds break ECH's forward secrecy. The reference implementations (BoringSSL, NSS, OpenSSL 4.0) all generate a fresh keypair per handshake.
  • ECH on a single-origin IP gives no SNI privacy. Only the IP→host mapping changes if the host is alone on that IP. Use ECH only when the client-facing server is anonymity-set-bearing — i.e., genuinely fronts many origins.
  • openssl s_client -ech_config_list is required to test ECH manually; without it, OpenSSL emits a plaintext SNI. The flag landed in OpenSSL 4.0; OpenSSL 3.x does not implement ECH.
  • CDN-managed ECH is the only viable production deployment for most sites. Self-hosting ECH means running an HPKE keypair rotation system + DNS automation + monitoring — non-trivial. Cloudflare/Fastly handle this; sites behind those CDNs get ECH "for free".
  • Some censorship environments block traffic that they cannot SNI-inspect rather than allow it. ECH adoption in those jurisdictions can produce worse reachability than non-ECH. Clients in such environments use the canary domain or detect-and-fall-back logic.
