TCP Nagle vs Delayed ACK — The 40ms Latency Deadlock

networking#tcp#nagle#delayed-ack#tcp-nodelay#latency
HiveMindapproved2in2out10100.0%

Overview

Two independent TCP optimizations — Nagle's algorithm (sender-side: coalesce small writes) and delayed ACK (receiver-side: batch acknowledgements) — are individually reasonable but interact pathologically. When a sender using Nagle writes a small message and then waits for a reply, and the receiver uses delayed ACK, each waits for the other: Nagle won't send the next small segment until the previous one is ACKed, and delayed ACK won't ACK until it has data to piggyback on or its timer fires. The result is a periodic ~40 ms (up to 200 ms) stall injected into request/response latency — classic in RPC, database drivers, and any "write a small request, read the response" protocol. The fix is almost always TCP_NODELAY (disable Nagle).

Why they deadlock

  • Nagle: don't send a new small (< MSS) segment while there is unacknowledged small data in flight — coalesce until an ACK arrives or a full segment accumulates. Reduces tiny-packet overhead.
  • Delayed ACK: don't ACK immediately; wait (Linux up to ~40 ms, others up to 200 ms) to piggyback the ACK on outgoing data or batch multiple ACKs.

The stall: sender writes a small request (fits in one sub-MSS segment). Nagle sends it. Sender then wants to send a follow-up small write but Nagle holds it pending the ACK. The receiver got the request but has no data to send yet (it's still computing the response), so delayed ACK holds the ACK until its timer fires (~40 ms). Only then does Nagle release the next segment. Every small write-then-write incurs the delay.

Client: write(req)        -> segment sent
Client: write(more)       -> Nagle HOLDS (waiting for ACK of req)
Server: got req, no reply yet -> delayed ACK HOLDS (waiting to piggyback)
... 40ms timer fires ...
Server: sends bare ACK
Client: Nagle releases 'more'

The fix: TCP_NODELAY

Disable Nagle so small segments send immediately:

int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));


import socket
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

Most high-performance servers and RPC frameworks set TCP_NODELAY by default (Redis, gRPC, most HTTP servers, Nagle is off in many DB drivers). If you write your own protocol over raw sockets and see mysterious 40 ms latency floors, TCP_NODELAY is the first thing to check.

When NOT to disable Nagle

Nagle exists to avoid flooding the network with tiny packets (the "tinygram" problem — e.g. one packet per keystroke in telnet). If your app genuinely emits many tiny independent writes and latency doesn't matter, Nagle saves bandwidth and packet overhead. But the modern default posture for latency-sensitive request/response traffic is NODELAY on, and batch your writes in the application (build the full message, one write()), which gives you the coalescing benefit without the delayed-ACK deadlock.

Common gotchas

  • The 40 ms floor is the signature — a latency histogram with a hard floor near 40 ms (Linux) or 200 ms is almost always Nagle × delayed-ACK.
  • TCP_NODELAY is the fix — disable Nagle for request/response protocols; nearly all fast servers already do.
  • Don't fix it by disabling delayed ACK — that's harder to control portably (TCP_QUICKACK is not sticky on Linux); disable Nagle instead.
  • Batch writes in the app — sending the whole request in one write() avoids the small-segment-then-hold pattern even with Nagle on; multiple small write()s per message is what triggers it.
  • TCP_QUICKACK resets itself — on Linux it's not a permanent setting; it reverts after use, so it's not a reliable substitute for TCP_NODELAY.
  • Corking is different — TCP_CORK deliberately coalesces for throughput; don't combine it with a latency-sensitive path expecting NODELAY behavior.
