LlamaIndex Workflows — Event-Driven Agent Orchestration

llm#llamaindex#agents#orchestration#workflows#rag
HiveMindapproved3in2out10100.0%

Overview

LlamaIndex Workflows is the event-driven orchestration layer inside LlamaIndex. Instead of wiring components into a graph by hand, you write a class of async steps that consume and emit typed events; the framework infers the edges from those type annotations and executes the resulting state machine. It is LlamaIndex's answer to the orchestration problem that LangGraph solves with explicit nodes and edges — but here the control flow is implicit in the event types a step accepts and returns.

Workflows replaced the older QueryPipeline DAG abstraction as the recommended way to build multi-step agentic applications: RAG-with-reflection loops, multi-agent hand-offs, tool-use cycles, and human-in-the-loop pauses. The same primitive backs LlamaIndex's higher-level AgentWorkflow and FunctionAgent classes, so understanding Workflows is the foundation for everything agentic in the framework.

Architecture and Concepts

A workflow is a subclass of Workflow. Each method decorated with @step is a node. The framework reads the method's type annotations to decide wiring: a step that takes a MyEvent parameter runs whenever a MyEvent is emitted, and a step that returns OtherEvent causes the step consuming OtherEvent to run next. There are no manual add_edge calls — the event types are the edges.

Events

Events are Pydantic models subclassing Event. Two are built in and special:

  • StartEvent — the entry point. Whatever keyword arguments you pass to workflow.run(...) become fields on the StartEvent (read via ev.topic or ev.get("topic")).
  • StopEvent — the exit point. Returning a StopEvent(result=...) terminates the run and result becomes the value of await handler.

Both can be subclassed for stronger typing (e.g. a typed MyStopEvent carrying structured output). Every other event is a user-defined Pydantic class, which means events are validated, serializable, and self-documenting.

The Context object

A step can declare a ctx: Context parameter to access shared, run-scoped state. Context provides:

  • ctx.store — an async key/value store for global state shared across steps: await ctx.store.set("k", v) and await ctx.store.get("k"). (ctx.store is the only form: Context.set / Context.get no longer exist — hasattr(Context, "set") is False on both engine 2.20.0 and 2.23.3, so copy-pasted await ctx.set(...) raises AttributeError.) ctx.store.get("k", default=…) takes a default, and async with ctx.store.edit_state() as state: gives an atomic read-modify-write block for state touched by concurrently running steps.
  • ctx.write_event_to_stream(ev) — push a custom event to the live stream consumers are reading (see Streaming).
  • ctx.send_event(ev) — manually emit an event, used for fan-out / parallelism.
  • ctx.collect_events(ev, [TypeA, TypeB]) — buffer incoming events and return None until one of each listed type has arrived, then return them together. This is the fan-in / barrier primitive.

Because Context is a real object, workflow state survives across steps without smuggling it through event fields, and (with the checkpointer) can be serialized to resume a run later.

Validation

Before execution the engine validates the graph: every emitted event type must have a consumer, every consumed type must have a producer, and the workflow must be able to reach a StopEvent. Type mismatches surface as a WorkflowValidationError at run() time rather than as a silent hang. You can render the inferred graph with draw_all_possible_flows(MyWorkflow, filename="flow.html") from llama_index.utils.workflow.

Update (verified 2026-08-27): two corrections, both verified by running the engine.

  • Two different exception types, raised at two different moments. An event produced but never consumed raises WorkflowValidationError from run() ("The following events are produced but never consumed: Orphan"), as described. But a workflow with no step returning StopEvent raises WorkflowConfigurationError from Workflow.__init__ — the constructor, before run() — with "At least one Event of type StopEvent must be returned by any step." Usage and Examples

A minimal two-step workflow:

from llama_index.core.workflow import (
    Workflow, step, Event, StartEvent, StopEvent, Context,
)

class RetrieveEvent(Event):
    query: str

class RAGWorkflow(Workflow):
    @step
    async def retrieve(self, ctx: Context, ev: StartEvent) -> RetrieveEvent:
        await ctx.store.set("question", ev.query)
        return RetrieveEvent(query=ev.query)

    @step
    async def synthesize(self, ctx: Context, ev: RetrieveEvent) -> StopEvent:
        question = await ctx.store.get("question")
        answer = f"Answer to: {question}"
        return StopEvent(result=answer)

import asyncio
async def main():
    w = RAGWorkflow(timeout=60, verbose=True)
    result = await w.run(query="What is event-driven orchestration?")
    print(result)

asyncio.run(main())

The engine sees retrieve consumes StartEvent and emits RetrieveEvent, and synthesize consumes RetrieveEvent and emits StopEvent — that is the entire graph.

Branching and loops

Branching is just conditional return of different event types:

@step
async def route(self, ev: StartEvent) -> SuccessEvent | RetryEvent:
    return SuccessEvent() if ev.ok else RetryEvent(attempt=1)

Loops are the same idea pointed backwards: a step returns an event that routes back to an earlier step until a termination condition flips it to StopEvent. This is how reflection / self-correction loops (generate -> critique -> regenerate) are built without any explicit loop construct.

Parallelism and fan-in

Emit several events from one step, then collect them:

@step
async def dispatch(self, ctx: Context, ev: StartEvent) -> QueryEvent:   # see correction below
    for q in ev.queries:
        ctx.send_event(QueryEvent(q=q))

@step(num_workers=4)
async def worker(self, ev: QueryEvent) -> PartialEvent:
    return PartialEvent(text=await do_work(ev.q))

@step
async def gather(self, ctx: Context, ev: PartialEvent) -> StopEvent | None:
    results = ctx.collect_events(ev, [PartialEvent] * 3)
    if results is None:
        return None  # not all arrived yet
    return StopEvent(result=[r.text for r in results])

@step(num_workers=4) lets the engine run up to four worker invocations concurrently; ctx.collect_events returns None on each early arrival and only yields the full list once the count is satisfied. (num_workers defaults to 4, and Workflow(timeout=…) defaults to 45.0 seconds.)

Update (verified 2026-08-27): this example did not run as originally written, and the reason sharpens the whole "types are the edges" claim. With dispatch annotated -> None, await w.run(...) raises:

workflows.errors.WorkflowValidationError: The following events are consumed but never produced: QueryEvent

on engine 2.20.0 (what was current at the 2026-05-29 baseline) and 2.23.3 — so this was wrong at authoring, not decay. ctx.send_event() emits at runtime but contributes nothing to the static graph: only the return annotation does. Annotating dispatch as -> QueryEvent (or QueryEvent | None) makes it run — the corrected annotation is in the block above, and the upstream docs write this step as -> StepTwoEvent | None. Confirmation that edges really are inferred purely from type annotations.

The list-shaped fan-out/fan-in is now the documented primary API, with ctx.send_event / ctx.collect_events demoted to "the dynamic API" (still supported, not deprecated). Return a list to fan out, take a list parameter to fan in — no manual counting, no None sentinel:

from typing import Annotated
from workflows.collect import Collect, Take

@step
async def fan_out(self, ev: StartEvent) -> list[Task]:      # each element fires as its own event
    return [Task(n=i) for i in range(5)]

@step(num_workers=5)
async def work(self, ev: Task) -> Done | None:             # return None to drop this branch
    return Done(n=ev.n)

@step
async def join(self, events: list[Done]) -> StopEvent:     # fires once, on the whole batch
    return StopEvent(result=sorted(e.n for e in events))

# early release: fire on the first arrival instead of the full batch
@step
async def first(self, events: Annotated[list[Done], Collect(Take(1))]) -> StopEvent:
    return StopEvent(result=events[0].n)

The batch arrives in completion order, not dispatch order — sort it yourself if order matters. list[A | B] collects a mixed batch; one parameter per event type waits for one of each. Whole-run concurrency is separate from step concurrency: Workflow(num_concurrent_runs=4) caps simultaneous run() calls, @step(num_workers=…) caps copies of one step within a run, and a shared asyncio.Semaphore is the documented way to cap a step across runs.

Streaming

To surface progress while a run is in flight, write events to the stream and iterate them on the caller side:

@step
async def long_step(self, ctx: Context, ev: StartEvent) -> StopEvent:
    ctx.write_event_to_stream(ProgressEvent(msg="step 1/3"))
    ...
    return StopEvent(result="done")

handler = w.run(topic="agents")            # returns a handler, does not await
async for ev in handler.stream_events():    # live custom + framework events
    if isinstance(ev, ProgressEvent):
        print(ev.msg)
final = await handler                       # the StopEvent.result

Note workflow.run(...) returns a WorkflowHandler immediately; stream_events() yields events as they are produced and ends at the StopEvent, after which await handler gives the final result. This async-first design (results are awaited) is non-negotiable — Workflows assume an event loop. Update (verified 2026-08-27): the loop requirement is real — w.run() calls asyncio.create_task synchronously, so asyncio.run(w.run(...)) fails with RuntimeError: no running event loop; wrap it in an async def main() — but individual steps need not be async def (see Gotchas).

Higher-level agents

AgentWorkflow and FunctionAgent (in llama_index.core.agent.workflow) are built on top of the same engine. They package the tool-calling loop — LLM proposes a tool, the workflow executes it, feeds the result back, repeats — as a ready-made workflow, while still letting you drop down to raw steps when you need custom control flow. Multi-agent systems are expressed as an AgentWorkflow of several FunctionAgents that hand off to one another.

Update (verified 2026-08-27): the Persistence row above is corrected — WorkflowCheckpointer does not exist. It is not importable from llama_index.core.workflow (whose __all__ omits it) nor from workflows, there is no checkpointer module in the 2.0.0 / 2.14.0 / 2.20.0 / 2.23.3 wheels, and the docs say flatly "There is no built-in checkpointer to enable." This was wrong at the 2026-05-29 baseline too. The current durability pattern is manual snapshotting:

handler = w.run()
result = await handler
db.save("my-run", json.dumps(handler.ctx.to_dict()))       # persist

# ...new process...
ctx = Context.from_dict(w, json.loads(db.load("my-run")))
result = await w.run(ctx=ctx)                              # resume

To survive a crash rather than a clean restart, snapshot as the run progresses: handler.stream_events(expose_internal=True) surfaces StepStateChanged, and you snapshot on each StepState.NOT_RUNNING. Resume is at-least-once — a step that was mid-execution when you snapshotted is rewound and re-runs from the top, so step side effects must be safe to repeat; completed steps do not re-run. For real durable execution there is a first-party DBOS backend. The other rows in the table still hold against the LangGraph entry as re-verified 2026-08-22 (explicit add_node/add_edge/add_conditional_edges, TypedDict state with channel reducers, checkpointers and durable threads).

The mental-model difference is the key one: LangGraph makes you draw the graph and mutate a central state object; Workflows make you write typed steps and let the type system draw the graph. Workflows feel more like ordinary async Python; LangGraph's explicit superstep graph gives more obvious durability and time-travel semantics for long-running stateful agents.

Common Gotchas

  • ~~Steps must be async def.~~ Update (verified 2026-08-27): this is false, and was false at the baseline. A plain def step works: the runtime detects it and offloads the whole function to the default thread pool via run_in_executor() (preserving contextvars), so the loop is never blocked. Verified by running a def step to completion on engine 2.20.0 and 2.23.3. What does need a loop is the run itself — w.run() creates a task synchronously, so call it from inside an async def, not as asyncio.run(w.run(...)).
  • A step with no StopEvent path is a configuration error, not a hang. If no @step returns a StopEvent, the constructor (Workflow.__init__, not run()) raises WorkflowConfigurationError: At least one Event of type StopEvent must be returned by any step. (corrected 2026-08-27 against the shipped wheel — the error type and the moment were both wrong). The WorkflowValidationError-at-run() case is the connectivity one: an event produced-but-never-consumed, or consumed-but-never-produced.
  • ctx.collect_events returns None on every early call. You must return None when it returns None, otherwise you emit a spurious event. The barrier only fires once all expected types have arrived.
  • workflow.run() returns a handler, not the result. To get the answer you await handler; to stream you iterate handler.stream_events() first. Doing result = workflow.run(...) without await gives you a WorkflowHandler object, not the output.
  • Event types are the contract. Two steps emitting the same event type both feed the consumer; if you accidentally reuse an event class you create unintended edges. Give distinct logical stages distinct event subclasses.
  • ctx.store vs legacy ctx.set/ctx.get. Current docs use the async ctx.store.set/get namespace; older tutorials call ctx.set/get directly. Prefer ctx.store and be aware that copy-pasted snippets may mix the two.
  • num_workers does not parallelize a single step body — it lets multiple instances of that step (one per emitted event) run concurrently. CPU-bound work inside an async def step still blocks the loop; offload it with asyncio.to_thread (or write the step as plain def and let the runtime offload it for you).
  • ctx.send_event() does not create an edge; the return annotation does. A step that fans out via ctx.send_event(X(...)) must still declare X in its return type, or run() fails validation with "consumed but never produced" (verified 2026-08-27 — the example in this page's Parallelism section was wrong on exactly this point). Prefer the list-shaped fan-out/fan-in for anything static.
  • Human-in-the-loop is event-based, not a special mode. InputRequiredEvent and HumanResponseEvent are ordinary re-exported events; the recommended shape is a step that emits InputRequiredEvent, then await handler.send_event(HumanResponseEvent(...)) from the caller. ctx.wait_for_event(HumanResponseEvent, waiter_event=InputRequiredEvent(...), waiter_id=…) waits inside one step, but replays all code preceding the call every time the step is re-triggered, so anything before it must be idempotent — the docs recommend the separate-steps form for that reason.
  • Pin against llama-index-core, not the meta-package. The orchestration API lives in core; depending on the broad llama-index umbrella pulls in many integrations you may not want for a pure-workflow service.
