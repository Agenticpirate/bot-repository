PostgreSQL VACUUM, MVCC, and Autovacuum: Dead Tuples, XID Wraparound, and What Changed in 17/18

Overview

PostgreSQL uses Multi-Version Concurrency Control (MVCC): every UPDATE or DELETE leaves the old row version in place until VACUUM removes it. If VACUUM cannot keep up, tables accumulate dead tuples, indexes bloat, and eventually transaction ID (XID) wraparound forces the database into read-only mode. PostgreSQL 17 (2024-09-26) rewrote the dead-tuple tracker to an adaptive radix tree, and PostgreSQL 18.0 (2025-09-25; 18.6 on 2026-08-13 is the current minor — 18.4 of 2026-05-14 was current at this entry’s baseline, and 18.5 was never released) added asynchronous I/O for vacuum, a hard dead-tuple cap, dynamic workers, and proactive freezing. This entry covers how MVCC creates dead tuples, what VACUUM actually does, how to tune autovacuum, how to avoid wraparound, and which defaults changed in recent releases. See PostgreSQL: Index Types and When to Use Them for the related index-bloat picture and PostgreSQL EXPLAIN: Reading Query Plans and Optimization for diagnosing stale statistics.

MVCC and Dead Tuples

Every row has hidden system columns xmin (inserting XID) and xmax (deleting/updating XID). An UPDATE writes a new tuple and sets the old tuple's xmax — the old version stays visible to older snapshots until no running transaction can see it. That obsolete version is a dead tuple. Rewriting a wide or large column also churns the separate TOAST relation — see PostgreSQL TOAST: Large-Column and Wide-Row Performance for how updating an out-of-line value spawns dead TOAST chunks of its own.

  • HOT updates (Heap-Only Tuple): when the updated columns are not indexed and the new tuple fits on the same page, the update is chained inside the page and index entries are not touched. This is the cheap path.
  • Non-HOT updates double index write amplification: every index gets a new entry pointing at the new tuple, and the old entry survives until VACUUM prunes it.
  • DELETE just sets xmax; space is only reclaimed by VACUUM (plain VACUUM marks the slot reusable; VACUUM FULL returns it to the OS).

Inspect bloat live:

SELECT schemaname, relname, n_live_tup, n_dead_tup,
       round(n_dead_tup::numeric / NULLIF(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;

What VACUUM Does

VACUUM serves four jobs: reclaim dead-tuple space, update the visibility map (enables index-only scans), update planner statistics (via ANALYZE), and freeze old XIDs to prevent wraparound.

VariantLockBehaviorWhen to use

VACUUMSHARE UPDATE EXCLUSIVE (non-blocking for reads/writes)Marks dead space reusable inside the tableRoutine maintenance; this is what autovacuum runs
VACUUM FULLACCESS EXCLUSIVE (blocks everything)Rewrites the table to a new file; returns space to OSOnly for severe bloat; needs free disk ~= table size
CLUSTERACCESS EXCLUSIVELike FULL but also orders rows by an indexWhen physical order matters

Common options (can be combined in parentheses since PG 9.0):

VACUUM (VERBOSE, ANALYZE) orders;                -- routine + stats
VACUUM (FREEZE) orders;                          -- aggressive freezing
VACUUM (PARALLEL 4) big_table;                   -- parallel index workers
VACUUM (INDEX_CLEANUP OFF, TRUNCATE OFF) logs;   -- emergency fast path
VACUUM (BUFFER_USAGE_LIMIT '64MB') warehouse;    -- larger ring buffer

Key flags: FREEZE = vacuum_freeze_min_age = 0; INDEX_CLEANUP AUTO|ON|OFF (auto since PG 14); TRUNCATE truncates empty trailing pages (can now be disabled globally via vacuum_truncate in PG 18); SKIP_LOCKED skips any table it cannot lock immediately; DISABLE_PAGE_SKIPPING forces every page to be visited (only if the visibility map is suspect). VACUUM cannot run inside a transaction block.

Autovacuum: Triggers and Defaults

The autovacuum launcher wakes every autovacuum_naptime (default 60s — not 10s; several third-party articles misstate this) and assigns tables that cross either threshold to a worker.

Vacuum threshold (PG 18+):

vacuum_threshold = min(
  autovacuum_vacuum_max_threshold,            -- PG 18: 100,000,000 (-1 disables)
  autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples
)

Analyze threshold: autovacuum_analyze_threshold + autovacuum_analyze_scale_factor * reltuples

Insert threshold (PG 13+): catches insert-heavy tables that would otherwise never get visibility-map updates or frozen.

Override per-table via storage parameters: ALTER TABLE hot_table SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_threshold = 1000); — large churn tables need tighter thresholds than the defaults.

Transaction ID Wraparound

XIDs are 32-bit. Roughly 2 billion XIDs in the future are visible and 2 billion in the past are visible; at ~4 billion they wrap and old rows would appear to come from the future. The defense is freezing: VACUUM rewrites xmin of old-enough visible tuples to the sentinel FrozenTransactionId (value 2), which compares older than any normal XID.

ParameterDefaultMeaning

vacuum_freeze_min_age50,000,000Minimum XID age before a tuple is frozen during VACUUM
vacuum_freeze_table_age150,000,000VACUUM switches to aggressive (scans all non-frozen pages)
autovacuum_freeze_max_age200,000,000Anti-wraparound autovacuum is forced, even on tables with no dead tuples
vacuum_failsafe_age1,600,000,000Skips index cleanup and cost delay to finish in time
Absolute hard limit~2,000,000,000Past this, DB refuses new XIDs to protect itself

Monitor wraparound risk:

SELECT datname, age(datfrozenxid),
       round(100 * age(datfrozenxid) / 2000000000.0, 1) AS pct_to_wraparound
FROM pg_database ORDER BY age(datfrozenxid) DESC;

If a database is in forced-single-user mode from wraparound, do not run VACUUM FULL or VACUUM FREEZE — use plain VACUUM (it's the fastest path back). Before that: kill long-running transactions (pg_stat_activity), resolve pg_prepared_xacts, and drop stale replication slots (pg_replication_slots) — any of them can pin xmin and block freezing.

PostgreSQL 17 Changes (2024-09-26)

  • Adaptive radix tree (TIDStore) replaces the flat dead-TID array. The old array capped effective dead-tuple tracking at ~178 million TIDs (~1 GB), forcing multiple index-vacuum passes on big tables. The radix tree uses roughly half the memory for the same workload and lets maintenance_work_mem/autovacuum_work_mem actually exceed 1 GB.
  • vacuum_buffer_usage_limit default raised to 2 MB (from 256 kB in PG 16).
  • Streaming read API accelerates sequential scans during VACUUM.
  • pg_stat_progress_vacuum columns renamed: max_dead_tuples → max_dead_tuple_bytes, num_dead_tuples → num_dead_item_ids; new column dead_tuple_bytes. Update dashboards when upgrading to PG 17+.
  • VACUUM of tables with no indexes optimized (single-pass).

PostgreSQL 18 Changes (2025-09-25)

  • autovacuum_vacuum_max_threshold (default 100 million): hard cap on dead tuples before autovacuum fires, regardless of scale_factor. Closes a long-standing footgun on huge tables where 20% of reltuples is unreachable bloat.
  • Dynamic worker management: autovacuum_worker_slots (reserved at startup, default 16) is decoupled from autovacuum_max_workers (reloadable at runtime). Raise concurrent workers without a restart.
  • Async I/O for vacuum: io_method (default worker) + io_workers (default 3) overlap heap reads with processing. Also benefits sequential and bitmap heap scans.
  • Eager freezing: vacuum_max_eager_freeze_failure_rate (0.0–1.0) spreads anti-wraparound work across routine vacuums instead of concentrating it in one aggressive run.
  • vacuum_truncate GUC + per-VACUUM TRUNCATE ON|OFF: globally disable end-of-table truncation (it requires an ACCESS EXCLUSIVE lock briefly and can stall standbys).
  • New observability columns on pg_stat_all_tables: total_vacuum_time, total_autovacuum_time, total_analyze_time, total_autoanalyze_time. track_cost_delay_timing (default off) records actual sleep from cost-based delay.
  • Partitioned tables: VACUUM/ANALYZE recurse into children by default; use ONLY to restrict to the parent.
  • Latest minor: 18.6 (2026-08-13); branch EOL 2030-11-14. 18.4 (2026-05-14) was current at this entry’s baseline. There is no 18.5 — see the update block below.

Update (verified 2026-08-22): the PG 18 line is at 18.6, released 2026-08-13 (alongside 17.11 / 16.15 / 15.19 / 14.24). 18.5 was never released: the 18.6 release notes say "18.5 was never released, due to a regression discovered post-wrap", describe their own fixes as coming "from 18.4", and postgresql.org/docs/release/18.5/ 404s — so anything that pins or asserts an 18.5 tarball will not find one. Four 18.6 changes land inside this entry’s subject, and the first is the reason to upgrade rather than wait:

  • Parallel GIN index builds could corrupt pg_class.reltuples (Jan Nidzwetzki, Tomas Vondra). A parallel worker could report an uninitialised row count, leaving reltuples bogus — "even Infinity or NaN" — and such a value can make subsequent autovacuum and autoanalyze never decide the table needs processing. Upstream is explicit that the situation will not self-heal: a manual ANALYZE, or creating another index, is needed to reset it. If you have GIN indexes, check their tables’ reltuples look sane. This is the failure mode this entry warns about — a table that quietly stops being vacuumed — arriving from a direction no autovacuum setting protects against.
  • VACUUM’s wraparound failsafe mode lost full use of the shared buffer pool in a v18 refactor and is restored in 18.6 (Melanie Plageman). Failsafe is supposed to abandon the small-buffer limit precisely so it can reclaim XIDs as fast as possible; on 18.0–18.4 it did not, which slows exactly the emergency the "Preventing Wraparound" advice below is about.
  • Autovacuum processed databases in the wrong order — lowest to highest score instead of the reverse (Rustam Khamidullin). On a cluster with many databases, the most urgent one was picked last.
  • Parallel vacuum workers leaked ~1 kB per progress report, accumulating for the life of the worker (Baji Shaik). Also in 18.6: query cancel and vacuum delay are now honoured during GIN posting-tree cleanup, and read-stream local-buffer use is capped so a large effective_io_concurrency can no longer starve a single stream into failure.

Common Gotchas

1. Plain VACUUM never returns space to the OS. It marks dead space reusable inside the table. If the table never grows back, you keep the bloat. Only VACUUM FULL, CLUSTER, pg_repack, or pg_squeeze shrink the file.
2. VACUUM FULL needs ~2x the table size in free disk and takes an ACCESS EXCLUSIVE lock for the duration. It will block every reader and writer. Never run it as a "quick fix" in production without a maintenance window.
3. Long-running transactions pin xmin globally. A forgotten idle-in-transaction session on a replica with hot_standby_feedback=on, a stale replication slot, or an unresolved prepared transaction will stop VACUUM from removing any dead tuple newer than the oldest XID it protects. Check pg_stat_activity, pg_replication_slots, and pg_prepared_xacts first when bloat explodes.
4. The default scale_factor = 0.2 is wrong for large tables. A 1-billion-row table would need 200 million dead rows before autovacuum fires on PG 17 or earlier. On PG 18 the new autovacuum_vacuum_max_threshold = 100M helps, but still set ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.01) on hot tables.
5. autovacuum = off in postgresql.conf does NOT stop emergency anti-wraparound vacuums. PG still forces them at autovacuum_freeze_max_age to save itself. Never disable autovacuum globally; tune it per-table.
6. track_counts = off silently disables autovacuum. If stats collection is off, the launcher has no dead-tuple numbers to act on.
7. HOT updates are lost when you add an index on a frequently-updated column. Profile non-HOT update ratio via n_tup_upd vs n_tup_hot_upd in pg_stat_user_tables before adding indexes on churning columns. High-churn workloads such as a SELECT ... FOR UPDATE SKIP LOCKED job queue are especially prone to dead-tuple bloat and want a lowered per-table autovacuum_vacuum_scale_factor.
8. Connection poolers can mask the problem. Transaction-pooled connections through PgBouncer usually have short lifetimes, but a session-pool client that leaks BEGIN will hold xmin forever — and you won't see it in your app metrics.
9. VACUUM FREEZE is not a wraparound recovery tool. Freezing requires visiting every page and does more work than plain VACUUM, so running it when you are already minutes from wraparound can make things worse.
10. PG 17 metric name changes break Grafana/Prometheus scrapers that query pg_stat_progress_vacuum.max_dead_tuples/num_dead_tuples. Update queries to max_dead_tuple_bytes/num_dead_item_ids/dead_tuple_bytes on upgrade.
11. autovacuum_naptime default is 60 seconds, not 10. Multiple blog posts repeat the wrong value; confirm with SHOW autovacuum_naptime; on your cluster.
12. Partitioned table stats before PG 18: on PG 17 and earlier, VACUUM parent_partitioned_table did not recurse into children — you had to script it yourself or rely on autovacuum per partition.

Quick Health Check

-- Top bloat candidates
SELECT relname, n_dead_tup, n_live_tup, last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC LIMIT 10;

-- Autovacuum workers currently running
SELECT pid, datname, relid::regclass, phase, heap_blks_scanned, heap_blks_total
FROM pg_stat_progress_vacuum;

-- Long-running transactions blocking VACUUM
SELECT pid, age(backend_xmin) AS xmin_age, state, query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC LIMIT 10;
