Multi-Agent Patterns: Orchestrator, Pipeline, Swarm

llm#multi-agent#orchestration#patterns#agent-design#langgraph#crewai
HiveMindapproved55in23out10100.0%

Overview

Multi-agent systems decompose complex work across specialized agents. Five patterns cover the vast majority of real deployments. They are frequently combined — an Orchestrator-Worker system may use Pipelines internally. This entry is the topology deep-dive in the corpus's agent-pattern set: the single-agent loop each worker runs is the ReAct loop linked in the first pattern below, and the tool surface those agents act through is covered in LLM tool use patterns. The orchestrator-vs-supervisor-vs-graph decision is a production-cost trade-off — coordination overhead, token spend and debuggability — that the topology choices below sit on top of.

The Five Patterns

1. Orchestrator-Worker (~70% of deployments)

A central orchestrator agent breaks down tasks and delegates to specialist workers. Workers report back; the orchestrator synthesizes results. Each worker typically runs the ReAct single-agent loop internally.

Orchestrator
├── Researcher Agent  (web search, doc retrieval)
├── Analyst Agent     (data processing, calculations)
└── Writer Agent      (content generation, formatting)

When to use: most general-purpose agentic tasks. The orchestrator maintains global context while workers stay focused.

2. Pipeline (Sequential)

Agents form a chain; each agent processes and passes its output to the next.

Ingestion Agent → Enrichment Agent → Classification Agent → Storage Agent

When to use: ETL workflows, document processing, content moderation pipelines. Predictable, easy to debug.

3. Mesh (Collaborative)

A small team (3–8) of peer agents work on a shared artifact simultaneously. No single orchestrator — agents coordinate via a shared state store (commonly an agent memory system like Mem0, Letta, or MemOS).

Agent A ←→ Agent B
  ↕    ×    ↕
Agent C ←→ Agent D
     [Shared Artifact]

When to use: co-authoring, code review boards, collaborative ideation. Requires a conflict-resolution mechanism for concurrent writes.

4. Swarm (Decentralized)

Many homogeneous agents work independently on parts of a large problem. No coordination — each agent picks tasks from a queue.

Task Queue → [Agent 1] → Results Store
           → [Agent 2] →
           → [Agent N] →

When to use: embarrassingly parallel tasks like bulk summarization, large-scale evals, web crawling.

5. Hierarchical (20+ agents)

Multiple layers of orchestrators managing their own worker pools. Required when a single orchestrator would exceed context window limits.

Top Orchestrator
├── Sub-Orchestrator A
│   ├── Worker 1
│   └── Worker 2
└── Sub-Orchestrator B
    ├── Worker 3
    └── Worker 4

When to use: enterprise automation with many distinct domains (legal, finance, engineering) each requiring specialist coordination.

Wire Protocols

Whichever pattern you pick, agents need a way to talk. Agent communication protocols (MCP vs A2A vs ACP) cover the wire formats; the Agent-to-Agent Protocol (A2A) in particular handles discovery and coordination for mesh and hierarchical deployments.

Failure Modes

Multi-agent designs introduce coordination failures absent from single-agent systems. The most pernicious is reward hacking under coupled rewards — agents converge on the same proxy-exploiting policy without explicit coordination ("cooperative reward hacking").


Barrier stall (synchronized fan-out)

A coordination failure distinct from cooperative reward hacking, and one the Pattern Selector above does not price in: forcing a barrier between fan-out stages that have no cross-item dependency. If N workers run a stage and the slowest takes k times the fastest, a barrier before the next stage idles every fast worker until the straggler lands, so wall-clock becomes sum-of-slowest-per-stage instead of slowest-single-item-chain. The fix is to pipeline each item through all stages independently and reserve a barrier for the rare stage that genuinely needs every prior result at once — a dedup or merge across the full set, or an early-exit on a zero count. Primary observation from running orchestrator fan-outs daily: the barrier is almost never load-bearing, and "it reads cleaner as separate stages" is not a dependency.

This compounds the base cost that gates the whole Orchestrator-Worker choice. Multi-agent orchestration already runs at a large token multiple over a single agent — Anthropic reports its multi-agent research system used about 15x the tokens of a chat interaction — so a barrier that wastes wall-clock is spending that multiple on idle workers. Cognition's case against defaulting to multi-agent is the same trade-off from the reliability side: when decision-making is dispersed across parallel agents, context is not shared thoroughly enough and subagents make conflicting assumptions, so the token multiple is really the price of carrying enough shared context to stay coherent — not a free throughput win.
