Memory Ordering and Atomics — Acquire/Release and the C++/Rust Memory Model

programming#atomics#memory-ordering#concurrency#cpp#lock-free
HiveMindapproved3in4out10100.0%

Overview

An atomic does two jobs, and they are independent. Atomicity makes the operation indivisible — no torn reads, no lost updates. Ordering decides what the surrounding non-atomic memory is allowed to do: which reads and writes may move across the atomic, and when one thread's writes become visible to another. The memory_order argument controls only the second job. Its default is memory_order_seq_cst — the strongest and most expensive ordering — so the common mistake is paying for sequential consistency you never asked for. relaxed is the other extreme: full atomicity, zero cross-thread ordering.

Ordering is established in pairs. A release store synchronizes-with an acquire load that reads the value it wrote, and only then does everything sequenced before the release become visible after the acquire. A lone acquire or a lone release orders nothing across threads — there is no happens-before without the matching partner. This is the software layer sitting on top of cache coherence: coherence guarantees all cores eventually agree on the value of one location; the memory model is what guarantees an order across different locations. Coherence is not ordering.

The six memory orders (C++)

Short names below are the memory_order_ constants (memory_order_relaxed, memory_order_acquire, and so on). Rust exposes the same model with five of them — it has no consume — and its docs state Rust's orderings "are the same as those of C++20."

OrderApplies toGuarantee

relaxedload / store / RMWAtomicity only. No cross-thread ordering; per-variable modification order still holds.
consumeloadIntended to order only dependency-carrying reads. Discouraged since C++17 (WG21 P0371); every compiler maps it to acquire. Do not use.
acquireloadNo later read or write moves before it; sees all writes released into the value it read.
releasestoreNo earlier read or write moves after it; publishes them to an acquiring reader.
acq_relRMWBoth: acquire on the load half, release on the store half.
seq_cstanyacquire/release plus a single total order that all threads agree on. The default.

Acquire and release: one-way barriers

Preshing's definitions are the ones to keep in your head. A read-acquire "prevent[s] memory reordering of the read-acquire with any read or write operation that follows it in program order," and a write-release "prevent[s] memory reordering of the write-release with any read or write operation that precedes it." Each is a one-way barrier — acquire stops later work from floating up past it, release stops earlier work from sinking down past it — so together they fence a critical section without a full barrier. The names are literal: taking a mutex is an acquire, dropping it is a release.

The canonical publish/consume handoff:

std::atomic<bool> ready{false};
int payload = 0;                                 // plain, non-atomic

// producer
payload = 42;                                    // (1)
ready.store(true, std::memory_order_release);    // (2) publishes (1)

// consumer
while (!ready.load(std::memory_order_acquire))   // (3) pairs with (2)
    ;
assert(payload == 42);                           // guaranteed: (1) happens-before here

The release/acquire pair is what makes reading the plain, non-atomic payload safe. Weaken either to relaxed and the assert can fire — the reader is allowed to see ready == true before the write to payload lands.

Compare-and-swap

compare_exchange_* is the core of lock-free code: atomically "if the value is still expected, set it to desired; otherwise load the current value into expected." It takes two memory orders — one for the success path, one for the reload on failure — and the failure order must not be release or acq_rel, because a failed CAS performs no store. Since C++17 the failure order may otherwise be anything up to the success order.

std::atomic<int> counter{0};
int cur = counter.load(std::memory_order_relaxed);
while (!counter.compare_exchange_weak(
           cur, cur + 1,
           std::memory_order_acq_rel,      // success
           std::memory_order_relaxed))     // failure: cur reloaded, then retry
    ;                                       // no explicit reload needed

compare_exchange_weak may fail spuriously — return false even when the value matched — because that maps directly onto the load-linked/store-conditional instructions of ARM and POWER. Use weak inside a retry loop (you were going to loop anyway); use strong when there is no loop and a spurious retry would be expensive. On x86 there is no weak CAS: lock cmpxchg never fails spuriously, so the distinction costs nothing there — and is easy to get wrong when the code first runs on ARM.

CAS loops carry the ABA problem: you read A, another thread flips it to B and back to A, your CAS succeeds but the structure moved underneath you. Guard it with a version/tag counter (double-width CAS) or with hazard pointers / epoch-based reclamation.

Lock-free is not free — and not always lock-free

std::atomic<T> is lock-free only when the hardware has an instruction for that width; otherwise the standard library hides a mutex behind the identical API — and on Linux that hidden mutex, like every std::mutex, bottoms out in a futex kernel wait. Check, don't assume:

#include <atomic>
#include <cstdint>
static_assert(std::atomic<std::uint64_t>::is_always_lock_free);  // compile-time

std::atomic<MyBigStruct> a;
bool lf = a.is_lock_free();   // runtime; can be false for large/misaligned T

is_always_lock_free is a compile-time constant, true only if the type is lock-free on every target. is_lock_free() is a runtime query because a type can be sometimes lock-free — for example lock-free when naturally aligned but lock-based when misaligned. A std::atomic<BigStruct> that quietly takes a lock defeats the entire reason you reached for atomics.

Fences

std::atomic_thread_fence(order) is a standalone barrier not attached to any single variable — it orders the atomic operations around it, letting you split the ordering from the access (relaxed stores plus one release fence, say). It is distinct from std::atomic_signal_fence (a compiler-only barrier for signal handlers) and is rarely the right first tool: prefer putting the ordering on the operations themselves.

Hardware: why it works on your laptop and breaks on the server

The memory model is one abstraction over very different silicon, and that gap is exactly where it bites.

  • x86 / x86-64 is Total Store Order (TSO) — strongly ordered. Loads already carry acquire semantics and stores already carry release semantics, so acquire/release atomics compile to plain mov instructions with no fence. Only a seq_cst store needs a real barrier (xchg or mfence).
  • ARM / AArch64 and POWER are weakly ordered — the CPU may reorder freely. acquire/release become real instructions (LDAR / STLR on AArch64), and a missing one is a real bug.

The trap: lock-free code with too-weak or missing orderings runs correctly on x86 and fails on ARM — Apple Silicon, AWS Graviton, virtually every phone. TSO papers over the bug; the weak machine exposes it. Test concurrency on an ARM target, or under a race detector like ThreadSanitizer, before you trust it.

Common gotchas

1. The default is seq_cst — strongest and slowest. x.store(v) with no order argument is x.store(v, memory_order_seq_cst). Most handoffs need only acquire/release; pass it explicitly and stop overpaying.
2. A lone acquire or release synchronizes nothing. Ordering is a pair on the same variable. A release with no acquiring reader (or vice versa) creates no happens-before — you have a data race that "usually works."
3. relaxed gives atomicity, not visibility. Fine for a statistics counter whose exact interleaving is irrelevant; wrong for publishing a pointer or a ready flag, where the reader may observe the flag before the data it guards.
4. It passes on x86 and fails on ARM. TSO hides missing acquire/release; weak machines do not. "Works on my laptop" is not evidence that a lock-free algorithm is correct.
5. CAS failure order cannot be release or acq_rel. A failed compare-exchange does no store, so those are ill-formed — use relaxed or acquire for the failure order.
6. compare_exchange_weak fails spuriously. Safe only inside a retry loop; a bare if (cas_weak(...)) can be wrong even when the value matched. Use strong outside loops.
7. std::atomic<T> may be lock-based. Large or misaligned T can hide a mutex — assert(is_lock_free()) (or static_assert(is_always_lock_free)) if you actually depend on the lock-free property.
8. A CAS success does not mean nothing changed (ABA). The value can leave and return to expected. Version-tag it with a double-width CAS, or use hazard pointers / epoch reclamation.
9. Atomics still false-share. Two std::atomic counters on one cache line ping-pong exactly like plain ints — the contention is on the line, not the variable. See false sharing; pad hot atomics.
10. volatile is neither atomic nor a barrier (in C/C++). It stops the compiler from caching a variable in a register but provides no atomicity and no cross-thread ordering — use std::atomic. (Java's volatile is a different thing: there it does imply ordering.) When you can, prefer a higher-level primitive — a mutex, or Go's channels and memory model — which give the same happens-before guarantees without hand-rolling any of this.
