Cloudflare Containers — Workers-Native Container Runtime With Sandbox SDK

Overview

Cloudflare Containers run OCI images on the Workers platform, controlled by a Worker via the Durable-Objects binding pattern. They reached general availability on 2026-04-13 alongside the Sandbox SDK, shifting billing from wall-clock to active-CPU time and lifting concurrency caps into the thousands. The product targets the workloads that do not fit inside a Worker isolate — full Linux processes, custom runtimes, CLI tools, headless browsers, code interpreters, FFmpeg-class binaries — while keeping the request path inside a Worker that already terminates TLS, applies WAF/cache, and stays close to the Workers limits for CPU and request shape. The Wrangler CLI builds the image (via local Docker), pushes it to registry.cloudflare.com, and emits the containers[] + durable_objects[].bindings[] config in the same wrangler.jsonc you already use for D1, R2, and Workflows.

Update (verified 2026-08-25): the product is still called Cloudflare Containers and still lives at developers.cloudflare.com/containers/ — no rename, no absorption, no shutdown date. Two things moved since the baseline. First, the Sandbox SDK graduated out of "a GitHub repo with a README" into first-party documentation at developers.cloudflare.com/sandbox, which describes @cloudflare/sandbox as the current stable package rather than a beta; stable is the 0.12.x line (0.12.8, published 2026-08-24) and Sandbox SDK 1.0 is in preview on the @next dist-tag (0.13.0-next.*). Second, Cloudflare published a deprecation announcement on 2026-06-09 retiring several SDK surfaces, with a 2026 deprecation migration guide — details in the Sandbox SDK section below. @cloudflare/containers is at 0.3.7 (2026-06-04). Read the whole dist-tags map before you install: latest is 0.12.8 and next is the 1.0 preview, but the beta tag still points backwards at the placeholder 0.0.0-1558ec9 and must not be used.

To get a shell in a live instance, add an ssh-ed25519 key to authorized_keys in the container config and run wrangler containers ssh <INSTANCE_ID> (enabled by default since 2026-05-12; usable as an OpenSSH ProxyCommand, or with --stdio, since 2026-05-28). Separately, a runtime exec API shipped on 2026-06-18: from inside a Container subclass, await this.ctx.container.exec(["node", "--version"]) starts a process in the already-running instance and returns a handle with streamed stdio, an exit code and signals. The command is an argv array launched without an implicit shell — invoke a shell explicitly if you need pipes or redirects.

Instance Types and Pricing

Each container instance picks one of six predefined shapes or a custom shape. Memory and disk are provisioned (always billed when the instance exists); vCPU is active-CPU metered (billed only when consumed).

Correction (2026-08-25): the 3 GiB-per-vCPU and 2 GB-disk-per-GiB ratios are the constraints on custom instance types, not universal rules — the predefined lite shape ships 2 GB of disk on 256 MiB of memory, which is 8 GB per GiB. Custom instance types have been available to all users since 2026-01-05 (previously Enterprise-only), so the six shapes are a convenience, not a ceiling on shape. Set instance_type to an object instead of a string:

{
  "containers": [
    {
      "class_name": "MyContainer",
      "image": "./Dockerfile",
      "instance_type": { "vcpu": 2, "memory_mib": 6144, "disk_mb": 12000 }
    }
  ]
}

Custom shapes must satisfy: minimum 1 vCPU, maximum 4 vCPU, maximum 12 GiB memory, maximum 20 GB disk, at least 3 GiB memory per vCPU, at most 2 GB disk per 1 GiB memory. Because the floor is a whole vCPU, sub-vCPU workloads still have to use lite or basic. Two legacy names remain as aliases: dev = lite and standard = standard-1. If you omit instance_type entirely the default is lite.

Cold starts are quoted at 1–3 seconds depending on image size — comparable to Fly Machines on small images, slower than the Worker-isolate cold start (sub-millisecond) it gets paired with. Containers do not currently expose GPUs; the GPU-enabled Cloudflare container platform that powers Workers AI, Workers Builds, Remote Browser Isolation, and Browser Rendering API is an internal platform (announced 2024-09-27, blog.cloudflare.com/container-platform-preview) and is not the same surface as the public Containers GA product.

Configuration: wrangler.jsonc

The containers[] array declares one entry per container class. Each class is bound to a Durable Object class via migrations[].new_sqlite_classes so the container's lifecycle inherits DO addressing.

{
  "name": "my-app",
  "main": "src/index.ts",
  "compatibility_date": "2026-05-01",
  "containers": [
    {
      "class_name": "MyContainer",
      "image": "./Dockerfile",
      "instance_type": "standard-1",
      // or a custom shape: { "vcpu": 2, "memory_mib": 6144, "disk_mb": 12000 }
      "max_instances": 100
    }
  ],
  "durable_objects": {
    "bindings": [
      { "name": "MY_CONTAINER", "class_name": "MyContainer" }
    ]
  },
  "migrations": [
    { "tag": "v1", "new_sqlite_classes": ["MyContainer"] }
  ]
}

image can be a local Dockerfile path (built with the locally-installed Docker daemon at deploy time) or a remote image reference (registry.cloudflare.com/..., docker.io/..., <account>.dkr.ecr.<region>.amazonaws.com/...). Cloudflare does not cache Docker Hub or ECR pulls — for high-throughput deploys, push your image to registry.cloudflare.com once with wrangler containers push <IMAGE>:<TAG> or wrangler containers build -p -t <TAG> . and reference it by canonical tag.

Worker Code: getContainer Pattern

A Container class (re-exported from @cloudflare/containers) extends the Durable Object base. The Worker addresses container instances exactly like DOs — by name, by deterministic ID, or via random load-balancing helpers.

import { Container, getRandom } from "@cloudflare/containers";

export class MyContainer extends Container {
  defaultPort = 8080;
  sleepAfter = "10s";
  envVars = {
    MESSAGE: "I was passed in via the container class!",
  };

  override onStart() {
    console.log("Container successfully started");
  }
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const { pathname } = new URL(request.url);

    if (pathname.startsWith("/session/")) {
      const sessionId = pathname.split("/")[2];
      const container = env.MY_CONTAINER.getByName(sessionId);
      return container.fetch(request);
    }

    if (pathname.startsWith("/lb")) {
      const container = await getRandom(env.MY_CONTAINER, 3);
      return container.fetch(request);
    }

    return new Response("not found", { status: 404 });
  },
};

Update (verified 2026-08-25 against @cloudflare/containers@0.3.7): if you do not set sleepAfter, the shipped default is "10m" (DEFAULT_SLEEP_AFTER = '10m' in the package). Cloudflare does not impose a maximum runtime, but when the platform does stop an instance — idle timeout, a rollout, or a host restart — it sends SIGTERM, waits up to 15 minutes, then sends SIGKILL, so handle SIGTERM if you need cleanup. Beyond onStart, the Container class exposes onStop(params), onError(error) and onActivityExpired(); overriding the last one lets you keep an instance alive past sleepAfter conditionally. You can also constrain where instances run with constraints.regions (ENAM, WNAM, EEUR, WEUR, APAC, SAM, plus limited-capacity ME, OC, AFR which cannot be used exclusively) and constraints.jurisdiction (eu or fedramp).

sleepAfter is the idle-shutdown timer (the container exits, disk is wiped, the next request pays a 1–3s cold start). defaultPort is the in-container port the Worker proxies to; additional ports become available once the runtime detects the container has bound them. The DO pattern means each unique session gets a persistent container as long as it stays warm — the same shape PartyKit uses for stateful WebSocket rooms.

Sandbox SDK: Agent-Oriented Companion

Sandbox SDK (@cloudflare/sandbox; 0.10.2 / 2026-05-21 was current at the May 2026 baseline, current stable is 0.12.8, published 2026-08-24, 1,115 GitHub stars) sits on top of Containers and ships a TypeScript API designed for the AI-agent use case — running untrusted code generated by Claude Code, MCP tool servers, or other coding agents.

import { getSandbox } from "@cloudflare/sandbox";

// Re-export the Durable Object class so the binding resolves.
export { Sandbox } from "@cloudflare/sandbox";

// `Sandbox` is a Durable Object class, not something you construct yourself.
const sandbox = getSandbox(env.SANDBOX, "user-123", { transport: "rpc" });

await sandbox.writeFile("/work/main.py", "print('hi')");
const { stdout } = await sandbox.exec("python /work/main.py");

const tunnel = await sandbox.tunnels.get(8080);
console.log(tunnel.url); // *.trycloudflare.com

Headline surfaces (as listed at the 0.10 baseline; all still present in 0.12.8 unless noted below):

  • Command execution with streaming stdout/stderr
  • File management (read/write/list/delete on the container filesystem)
  • Quick tunnels — sandbox.tunnels.get(port) returns a zero-config *.trycloudflare.com URL, useful for exposing a dev server an agent is iterating on
  • Code interpreters for Python and JavaScript with rich-output capture
  • Git integration — gitCheckout() (clone) only
  • Session, terminal, backup/restore and filesystem-watch APIs beyond the headline four

Corrections and updates (verified 2026-08-25), read against the shipped @cloudflare/sandbox tarballs for both 0.10.2 and 0.12.8:

1. new Sandbox(env.SANDBOX) never worked. Sandbox extends the Container Durable Object class; its constructor signature is (ctx: DurableObjectState, env: Env) and the runtime instantiates it for you. The user-facing entry point is the exported helper getSandbox(namespace, id, options?), and your Worker must re-export the class (export { Sandbox } from "@cloudflare/sandbox";) so the binding resolves. This was already true in 0.10.2; the sample above has been corrected rather than updated.
2. There is no sandbox.files namespace. File operations are flat methods on the sandbox stub: writeFile(), readFile(), mkdir(), deleteFile(), renameFile(), moveFile(), listFiles(), exists(). (files is a getter on an internal HTTP client class inside the package, which is why it shows up in a grep but not on anything you can hold.) Also true in 0.10.2.
3. Git is clone-only. The shipped surface is sandbox.gitCheckout(repoUrl, { branch, targetDir, depth, cloneTimeoutMs }). There is no status or diff method in either version, and Cloudflare's own Git workflows guide reaches for sandbox.exec("git status") for the rest.
4. Tunnels require the RPC transport. sandbox.tunnels.get(port) is real and does return a *.trycloudflare.com URL, but calling it over the HTTP or WebSocket transport throws "RPC transport required". Quick-tunnel URLs are cleared on container restart, so a new get(port) after a restart yields a new hostname. The 0.12.x line added named tunnels — tunnels.get(port, { name }) binds a stable <name>.<your-zone> hostname that survives restarts, at the cost of needing an API token and a zone.
5. Deprecations (announced 2026-06-09). HTTP and WebSocket transports are deprecated and will not ship in a future major — set SANDBOX_TRANSPORT: "rpc" in vars, or pass transport: "rpc" to getSandbox(). exposePort() is deprecated in favour of the tunnels API. Default sessions (the behaviour where a cd in one exec() leaks into the next) are deprecated: set enableDefaultSession: false — available from 0.10.3 — and use sandbox.createSession() when you actually want shell state. The separate streaming helpers (execStream, readFileStream, writeFileStream) are being folded into exec(), readFile() and writeFile(). The sandbox.desktop API was not deprecated but removed outright in 0.10.2 for low adoption.
6. Sandbox SDK 1.0 preview. npm i @cloudflare/sandbox@next installs the 1.0 preview (0.13.0-next.*). It is a deliberately thinner SDK: exec() takes an argv array and returns as soon as the process starts, handing back a handle for output/logs/waits/signals; sessions are gone entirely; RPC is the only transport; PTYs move to createTerminal/connect; and the code interpreter becomes an opt-in extension on your Sandbox subclass. Cloudflare recommends new projects start on @next but has not dated the 1.0 stable cut — it is gated on further Containers features landing. Keep the npm package and the container image on the same release line.

No advisories are open against @cloudflare/sandbox (0.10.2 or 0.12.8) or @cloudflare/containers 0.3.7 in OSV as of 2026-08-25; both packages are Apache-2.0 / MIT-or-Apache-2.0 respectively, and cloudflare/sandbox-sdk had commits on the default branch the same day.

This is the closest Cloudflare-native answer to E2B Firecracker sandboxes and Modal sandboxes: isolated process + filesystem + ephemeral disk, lifetime-scoped to a DO-addressed instance, with the Worker-front routing layer doing auth and quota gating before code ever lands in the container.

Image Registry and Pulls

registry.cloudflare.com is the default push target. Wrangler-built images flow through it automatically. Pre-built images push via wrangler containers push <IMAGE>:<TAG>. Per-account image storage is 50 GB at GA — delete unused tags with wrangler containers images delete to free space.

Update (verified 2026-08-25): Google Artifact Registry support landed on 2026-07-01 — only *-docker.pkg.dev hosts, service account needs the Artifact Registry Reader role. GAR pulls are not cached either, and they bill against Google egress. One Docker Hub gotcha the table above glosses: official images live in the library namespace, so write docker.io/library/<IMAGE>:<TAG>, not docker.io/<IMAGE>:<TAG>. GHCR, GitLab and Quay are still not directly supported.

Build images with multi-platform Docker BuildKit targeting linux/amd64 — Containers schedule on x86_64. Cloudflare does not cache external-registry pulls, so for a fast deploy path mirror the image into registry.cloudflare.com once instead of re-pulling on every cold start.

Local Development With wrangler dev

npx wrangler dev (or vite dev) runs containers locally against a Docker-compatible engine (Docker Desktop, Colima, or any daemon honouring DOCKER_HOST).

docker info                  # verify engine reachable
npx wrangler dev             # builds local image, starts container + Worker
# press [r] in the dev console to rebuild container after code changes

Local-dev quirks worth knowing:

1. Container code does not hot-reload like Worker code — press [r] in the dev console to rebuild the image and restart the instance after changes.
2. The Dockerfile must EXPOSE every port the Worker will proxy to (production passes all ports; local enforces the EXPOSE list).
3. vite dev cannot pull from the Cloudflare-managed registry — point it at Docker Hub or ECR for local testing of pre-pushed images.
4. For Cloudflare One / corporate VPN environments that re-sign TLS, the Docker build is what breaks. The One client already exports its CA via SSL_CERT_FILE and NODE_EXTRA_CA_CERTS on the host; pass that certificate into the build (copy it to /usr/local/share/ca-certificates/ and run update-ca-certificates), or disable the One client for the duration of wrangler dev / wrangler deploy.
5. Update (2026-08-25): FUSE now works in local development. Miniflare automatically grants local containers the Docker privileges FUSE needs — for wrangler dev, the Vite plugin and direct Miniflare use — when the Docker daemon runs in a VM (macOS, WSL) or, on Linux, for rootless Docker with /dev/fuse present. Rootful Docker on Linux is the case that still does not work.

Common Gotchas

1. Disk is ephemeral. Every cold start brings a fresh disk. Use R2 (via FUSE mount or direct API), D1, Workers KV, or an external Postgres for anything that must survive a sleepAfter shutdown. Snapshots were announced as "coming soon" at GA — and as of 2026-08-25 they still have not shipped; Cloudflare's lifecycle page and FAQ both still say "coming soon" with no date. Treat the container disk like tmpfs. Two workarounds do exist today: mount R2 with FUSE (now also supported in local development, since 2026-08-20, where Miniflare grants the Docker privileges automatically), or — if you are on the Sandbox SDK rather than raw Containers — use its createBackup() / restoreBackup() APIs, which snapshot a directory to R2 and restore it with a copy-on-write overlay.
2. Memory and disk are billed while idle-but-not-asleep. Only active CPU has the "stops when sleeping" property. Tighten sleepAfter (e.g. "10s" for request-scoped sandboxes, "5m" for warm-pool dev environments) to drop the memory/disk bill when traffic ebbs. Sleep is wall-clock cheap because cold-start is 1–3s — re-warming on demand is usually cheaper than holding a standard-3 warm.
3. No GPU support in the public product. The Workers AI / Browser Rendering internal platform has GPUs, but it is not the same SKU. For GPU-bound agent workloads (e.g. local SDXL, Whisper, custom Llama inference), pair Workers with Modal, Fly Machines GPUs, or RunPod and use Containers only for the CPU stages.
4. Only HTTP traffic enters via the Worker. End-user TCP/UDP cannot reach a container instance directly — every request is proxied via your Worker, which limits use cases like raw TCP databases-as-a-service or QUIC servers facing the public internet. WebSocket upgrade traffic does work (the Worker proxies the upgrade).
5. Custom shapes exist — but the memory:vCPU floor still binds. (Corrected 2026-08-25: this gotcha originally said the six predefined shapes were the only option. Custom instance types went generally available on 2026-01-05, before this entry was written.) A container is sized via instance_type, which takes either one of the six predefined names or an object of vcpu / memory_mib / disk_mb. You still cannot define a 1 vCPU + 1 GiB box, but for a different reason than "the shapes are fixed": custom types must give at least 3 GiB of memory per vCPU, and must allocate at least a whole vCPU, so anything below 1 vCPU has to use lite or basic. Choose the smallest shape whose memory fits your workload; pricing then accrues against the active CPU within that shape's vCPU budget.
6. External registry pulls are not cached. Re-pulling a Docker Hub or ECR image every deploy pulls the bytes through your account's egress allowance. Push once to registry.cloudflare.com via wrangler containers push (or wrangler containers build -p -t <tag> . to build-and-push in one call) and reference the canonical tag from wrangler.jsonc.
7. max_instances is a hard ceiling on concurrently running instances, and it errors rather than queues. (Corrected 2026-08-25 against the Wrangler configuration reference.) It counts only running instances — stopped ones do not count, so you may own more instances than the number overall. A start request that would exceed the limit errors; nothing is queued. The default when you omit the key is 20, and the limit is only enforced in production — wrangler dev ignores it, so a local run will happily exceed what production allows. Plan max_instances * instance_type.vcpu ≤ your account's 1,500 concurrent-vCPU cap.
8. x86_64 only at GA. Build Linux/amd64 images. Apple-Silicon devs running docker build without --platform=linux/amd64 will get arm64 images that fail to schedule at deploy time. Set DOCKER_DEFAULT_PLATFORM=linux/amd64 in your shell to avoid this trap.
9. Cold-start budget is not free. A 1–3 second cold start is fine for sandbox spin-up but is unacceptable for hot user-facing requests. Pair Containers with a warm pool of sticky DO IDs (a small getRandom(env.MY_CONTAINER, N) set kept warm by background traffic) or pre-allocate by name for predictable sessions.
10. The Sandbox SDK moves faster than Containers underneath it. (Rewritten 2026-08-25.) Cloudflare no longer labels the package "beta" — the docs call @cloudflare/sandbox the current stable package — but between the May baseline and 2026-08-25 it went 0.10.2 → 0.12.8, removed sandbox.desktop, deprecated two of its three transports plus exposePort() and default sessions, and opened a 1.0 preview on @next that reshapes exec() into an argv-and-handle API and deletes sessions entirely. Pin the exact version in package.json, keep the container image on the same release line as the npm package, and read the 2026 deprecation migration guide before you upgrade. The underlying Containers API is GA-stable; the SDK abstraction layer on top is the part still in motion.
