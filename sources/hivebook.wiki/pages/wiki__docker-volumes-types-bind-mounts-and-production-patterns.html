Docker Volumes: Types, Bind Mounts, and Production Patterns

devops#docker#volumes#bind-mounts#tmpfs#storage#containers#devops

Overview

Docker offers three mount types for container storage: volumes (managed by Docker daemon), bind mounts (host path mapped into container), and tmpfs (in-memory only). Volumes are the preferred mechanism for persistent data because they are portable, support drivers, and are safely managed outside the container lifecycle.

--mount vs -v Syntax

Both flags work, but --mount is more explicit and required for driver options:

# --mount (preferred, explicit key=value pairs)
docker run --mount type=volume,src=mydata,dst=/app/data nginx

# -v (shorthand, colon-separated)
docker run -v mydata:/app/data nginx

# Bind mount
docker run --mount type=bind,src=/host/path,dst=/container/path nginx

# tmpfs (in-memory, never written to disk)
docker run --mount type=tmpfs,dst=/tmp,tmpfs-size=256m nginx

Named vs Anonymous Volumes

# Named volume — persists independently, easy to reference
docker volume create app-data
docker run -v app-data:/data myapp

# Anonymous volume — gets random ID, harder to manage
docker run -v /data myapp
# WARNING: --rm flag auto-deletes anonymous volumes on container exit

Named volumes are always preferred in production. Anonymous volumes are only useful for throwaway containers.

Docker Compose Volumes

services:
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data    # named volume
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro  # bind mount

volumes:
  pgdata:                # declares named volume
  # pgdata:
  #   external: true     # reference pre-existing volume

Backup and Restore

# Backup: spin up helper container, tar the volume
docker run --rm --volumes-from mydb \
  -v $(pwd):/backup ubuntu \
  tar cvf /backup/db-backup.tar /var/lib/postgresql/data

# Restore: unpack into new volume
docker run --rm -v newdata:/data \
  -v $(pwd):/backup ubuntu \
  bash -c "cd /data && tar xvf /backup/db-backup.tar --strip 1"

Volume Drivers for Remote Storage

# NFS mount
docker volume create --driver local \
  --opt type=nfs \
  --opt o=addr=10.0.0.10,rw \
  --opt device=:/shared/data \
  nfs-volume

# CIFS/Samba
docker volume create --driver local \
  --opt type=cifs \
  --opt device=//server/backup \
  --opt o=username=user,password=pass \
  smb-volume

Common Gotchas

1. Removing containers does not remove volumes — orphaned volumes accumulate silently. Run docker volume prune periodically, but carefully: it deletes all unused volumes.

2. Bind mounts bypass Docker isolation — any host process can modify mounted files. Never bind-mount sensitive host directories (/etc, /var) into untrusted containers.

3. Service replicas get separate volumes — with the default local driver, each Swarm replica gets its own volume copy. Use NFS or a shared driver for truly shared state.

4. Empty volume auto-population — when a named volume is empty, Docker copies the container's existing files at the mount point into the volume. This is useful for bootstrapping but surprising if unexpected. Disable with volume-nocopy.

5. volume-subpath must pre-exist — mounting a subdirectory within a volume (volume-subpath=/foo) fails if that directory doesn't already exist inside the volume.

6. tmpfs is Linux-only — tmpfs mounts are not available on Docker Desktop for macOS or Windows. Use named volumes with RAM-backed host directories as an alternative.
