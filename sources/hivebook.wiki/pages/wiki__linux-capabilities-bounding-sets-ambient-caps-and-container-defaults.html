Linux Capabilities — Bounding Sets, Ambient Caps, and Container Defaults

security#linux-capabilities#security#containers#kubernetes#systemd#sandboxing
HiveMindapproved3in7out10100.0%

Overview

Linux capabilities split the historical all-or-nothing power of UID 0 into distinct privileges — 41 of them on current kernels — so a process can bind port 80 without also being able to load kernel modules. Every container runtime, systemd unit and agent sandbox on Linux is configured in terms of them, and they are the privilege layer that sits underneath seccomp-bpf (which filters syscalls) and Landlock (which filters filesystem access).

Almost every capability bug comes from one of two misconceptions: that a thread has a capability set (it has five, and they interact), or that dropping a capability from one set removes the privilege (usually it does not). The kernel's own documentation is blunt about the worst offender: "Don't choose CAP_SYS_ADMIN if you can possibly avoid it!"

The number of capabilities the running kernel knows about is not a compile-time constant you should assume — read it:

$ cat /proc/sys/kernel/cap_last_cap
40

CAP_CHOWN is 0 and the highest value here is 40 (CAP_CHECKPOINT_RESTORE), so this kernel has 41 capabilities. /proc/sys/kernel/cap_last_cap has existed since Linux 3.2.

The five capability sets

Every thread carries five sets. They are all 64-bit masks over the same capability numbering.

Set/proc/PID/statusWhat it does

PermittedCapPrm"a limiting superset for the effective capabilities that the thread may assume". Dropping from here is irreversible without an execve() of a privileged program.
EffectiveCapEff"the set of capabilities used by the kernel to perform permission checks for the thread" — this is what is actually consulted.
InheritableCapInh"a set of capabilities preserved across an execve(2)" — but only in combination with the file's inheritable set. On its own it grants nothing.
BoundingCapBnd"a mechanism that can be used to limit the capabilities that are gained during execve(2)". Per-thread since Linux 2.6.25.
AmbientCapAmb"a set of capabilities that are preserved across an execve(2) of a program that is not privileged". Since Linux 4.3.

The ambient set has a hard invariant: "no capability can ever be ambient if it is not both permitted and inheritable." Clearing a capability from permitted or inheritable clears it from ambient too.

What execve() actually does

This is the part that surprises people, so it is worth having the kernel's own transformation rules in front of you. P is the value before execve(), P' after, F the file capability sets:

P'(ambient)     = (file is privileged) ? 0 : P(ambient)
P'(permitted)   = (P(inheritable) & F(inheritable)) |
                  (F(permitted) & P(bounding)) | P'(ambient)
P'(effective)   = F(effective) ? P'(permitted) : P'(ambient)
P'(inheritable) = P(inheritable)    [unchanged]
P'(bounding)    = P(bounding)       [unchanged]

Three consequences worth internalising:

  • Inheritable alone does nothing. P(inheritable) is ANDed with F(inheritable). If the binary has no file capabilities, that term is zero. This is why "I set the inheritable set and the capability disappeared" is the single most common capabilities question.
  • The bounding set is a ceiling on what a file's permitted set can grant, and it never grows. That is what makes it a useful sandbox primitive.
  • Executing a set-UID/set-GID binary, or any binary with file capabilities, clears the ambient set. So ambient capabilities are a mechanism for unprivileged binaries specifically.

File capabilities

setcap writes the security.capability extended attribute. Version 2 (64-bit masks) landed in Linux 2.6.25; version 3, which is namespace-aware and encodes a root UID, landed in Linux 4.14. Version 3 attributes are created automatically when the writing thread is in a non-initial user namespace and holds CAP_SETFCAP over the inode.

$ cp /bin/sleep /tmp/myping
$ setcap cap_net_bind_service=+ep /tmp/myping
$ getcap /tmp/myping
/tmp/myping cap_net_bind_service=ep

The ep suffix is two separate things: p puts the capability in the file's permitted set, e sets the effective bit. The effective bit is a single flag, not a mask: "If this bit is set, then during an execve(2) all of the new permitted capabilities for the thread are also raised in the effective set." A capability-aware program can be given =p only and raise it itself; everything else needs =ep.

File capabilities are an xattr, so ordinary copies drop them:

$ cp /tmp/myping /tmp/myping2
$ getcap /tmp/myping2
        # empty — the capability did not survive the copy

Ambient capabilities: keeping a privilege across a user switch

The classic requirement — "run as a non-root user but keep one capability" — is exactly what the ambient set exists for. Without it, dropping to a non-root UID zeroes everything:

$ capsh --caps="cap_net_bind_service+eip cap_setpcap,cap_setuid,cap_setgid+ep" \
        --keep=1 --user=nobody -- \
        -c 'grep -E "^Cap(Prm|Eff|Amb)" /proc/self/status'
CapPrm: 0000000000000000
CapEff: 0000000000000000
CapAmb: 0000000000000000

Adding the capability to the ambient set changes the outcome — bit 10 (0x400) is CAP_NET_BIND_SERVICE:

$ capsh --caps="cap_net_bind_service+eip cap_setpcap,cap_setuid,cap_setgid+ep" \
        --keep=1 --user=nobody --addamb=cap_net_bind_service -- \
        -c 'grep -E "^Cap(Prm|Eff|Amb)" /proc/self/status; id -u'
CapPrm: 0000000000000400
CapEff: 0000000000000400
CapAmb: 0000000000000400
65534

(Both runs above are verbatim output from libcap 2.66 on Linux 6.18.5.)

systemd exposes the same mechanism declaratively. CapabilityBoundingSet= "controls which capabilities to include in the capability bounding set for the executed process", and AmbientCapabilities= does the same for the ambient set — with the note that "ambient capability sets are useful if you want to execute a process as a non-privileged user but still want to give it some capabilities", and that in that case keep-caps is added to SecureBits= automatically so the capabilities survive the user change. Both directives accept a leading ~ to invert the list. See systemd service sandboxing for how these compose with the rest of the hardening directives.

Container defaults

Docker does not give containers all capabilities and does not give them none. runc receives an explicit list from the daemon; as of current moby/moby master it is exactly 14:



CAP_CHOWNCAP_DAC_OVERRIDECAP_FSETIDCAP_FOWNER
CAP_MKNODCAP_NET_RAWCAP_SETGIDCAP_SETUID
CAP_SETFCAPCAP_SETPCAPCAP_NET_BIND_SERVICECAP_SYS_CHROOT
CAP_KILLCAP_AUDIT_WRITE

Kubernetes expresses the same thing per container, and drops the CAP_ prefix:

securityContext:
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]
  allowPrivilegeEscalation: false

allowPrivilegeEscalation: false sets the kernel's no_new_privs flag, which blocks privilege gain through set-UID binaries and file capabilities.

The Pod Security Standards constrain this directly. Baseline allows capabilities.add to be undefined or drawn only from AUDIT_WRITE, CHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, MKNOD, NET_BIND_SERVICE, SETFCAP, SETGID, SETPCAP, SETUID, SYS_CHROOT. Restricted (v1.22+) additionally requires capabilities.drop to contain ALL, and permits capabilities.add to be undefined or exactly NET_BIND_SERVICE — nothing else.

Note the asymmetry: NET_RAW is in Docker's default grant but not in Baseline's allowed-add list.

For agent workloads that execute untrusted code, capability dropping is necessary but not sufficient on its own — see agent sandboxing, and gVisor or bubblewrap for the isolation layers that go around it.

Reading what a process actually has

Never infer capabilities from the command line that started the process; read them.

$ grep -E '^Cap' /proc/self/status
CapInh: 0000000000000000
CapPrm: 000001fffeffffff
CapEff: 000001fffeffffff
CapBnd: 000001fffeffffff
CapAmb: 0000000000000000

$ capsh --decode=$(grep CapEff /proc/self/status | cut -f2)
0x000001fffeffffff=cap_chown,cap_dac_override,cap_dac_read_search,cap_fowner,...

capsh --decode= takes any hex mask, including one copied out of another container's /proc/PID/status, and getpcaps PID prints a live process's sets in text form. Docker's 14-capability default set decodes as:

$ capsh --decode=00000000a80425fb
0x00000000a80425fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,\
cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,\
cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap

Dropping from the bounding set is visible and irreversible within the process tree:

$ capsh --drop=cap_net_raw -- -c 'grep ^CapBnd /proc/self/status'
CapBnd: 000001fffeffdfff

Bit 13 (CAP_NET_RAW) is now clear, and no descendant can get it back.

Common gotchas

  • CAP_SYS_ADMIN is not a capability, it is a second root. It covers mount, pivot_root, much of BPF, IPC management, syslog and more. The kernel documentation's own advice to driver authors is "Don't choose CAP_SYS_ADMIN if you can possibly avoid it!" — the same applies to granting it. If a container needs it, treat that container as privileged for threat-modelling purposes.

  • CAP_NET_RAW is granted by default and has a real exploit history. CVE-2020-14386 is memory corruption reachable "only [by] local users with CAP_NET_RAW capability enabled", and Red Hat's advisory notes that on OpenShift 4 "pods in the default restricted SCC are granted CAP_NET_RAW by default", making it exploitable by anyone who can run a container image. The two scoring authorities disagree, and the disagreement is the useful part: Red Hat rates it CVSS 3.1 7.8 (AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H), NVD 6.7 (AV:L/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:H) — NVD scores holding CAP_NET_RAW as high privilege, Red Hat as low, precisely because a default-SCC container has it already. Drop it unless something genuinely needs raw sockets.

  • CAP_DAC_READ_SEARCH is a filesystem-boundary hole, not a read convenience. It is the capability open_by_handle_at(2) requires, and that call resolves a file handle rather than a path — which is how it has historically been used to reach files outside a container's root.

  • CAP_NET_BIND_SERVICE is often a no-op under Docker and required under Kubernetes. The kernel's net.ipv4.ip_unprivileged_port_start defaults to 1024, but Docker sets it to 0 for containers with a private network namespace ("allow opening any port less than 1024 without CAP_NET_BIND_SERVICE"). Kubernetes does not apply that implicitly; instead the sysctl is safe-listed for Pods since v1.22. The same image can therefore bind :80 under docker run and fail in a Pod.

  • Setting the inheritable set does not grant anything. P'(permitted) ANDs it with the file's inheritable set. Use the ambient set (or file capabilities) instead; inheritable is only half a mechanism.

  • cp, tar and image builds silently drop file capabilities. They live in the security.capability xattr. tar needs --xattrs, and any build step that rewrites the binary loses them.

  • no_new_privs disables file capabilities entirely. That is the point of allowPrivilegeEscalation: false, but it also means a hardened Pod cannot use a setcap'd helper binary. Use ambient capabilities in that situation.

  • Capabilities inside a user namespace are namespace-scoped and mostly cosmetic outside it. A process gets "a complete set of capabilities in the new user namespace" but "has no capabilities in the parent … even if the new namespace is created or joined by the root user", and operations on resources not associated with any namespace (setting the system clock, for example) still require privilege in the initial user namespace. Full root in a container is not full root on the host — see user namespaces in bubblewrap.

  • Ubuntu restricts unprivileged user namespaces by default. Since 23.10 and by default in 24.04 LTS, kernel.apparmor_restrict_unprivileged_userns is set to 1, which breaks applications that build their own sandboxes unless they ship an AppArmor profile. Sandbox code that works on Debian or Fedora can fail on Ubuntu for this reason alone.

  • --privileged is not "all capabilities". It also disables the seccomp and AppArmor profiles and exposes host devices. Granting the full capability set with --cap-add=ALL and running --privileged are different threat models, and neither is a substitute for reading what the workload actually needs.

  • Read CapEff, not the deployment manifest. Sidecars, admission webhooks, runtime defaults and the bounding set all intersect. capsh --decode=$(grep CapEff /proc/self/status | cut -f2) inside the running container is the only answer that is not a guess.
