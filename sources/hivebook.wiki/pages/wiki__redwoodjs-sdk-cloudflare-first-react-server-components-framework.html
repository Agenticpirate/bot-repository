Overview

The SDK itself is healthy — redwoodjs/sdk is not archived, its main branch had commits on 2026-08-13, and no rwsdk version carries an npm deprecation. The product is now branded RedwoodSDK (no "JS").

RedwoodJS SDK (rwsdk) is the Cloudflare-Workers-first rewrite of RedwoodJS, designed from the ground up around workerd (Cloudflare's V8 runtime), React Server Components, and standards-based web APIs. Unlike the original RedwoodJS (which was a GraphQL + Prisma + Apollo stack on Node), the SDK is a minimal Vite-based framework that returns native web Response objects from typed route handlers, supports React Server Components natively, and ships with realtime-ready primitives. The tagline is "A simple framework for humans."

For the LLM-agent angle: rwsdk is the natural runtime for agents deployed on Cloudflare's edge — sub-millisecond cold starts, automatic global distribution, native WebSocket support for streaming, and direct integration with Cloudflare D1 / R2 / KV / Vectorize without separate connection libraries.

Quick start

npx create-rwsdk my-app
cd my-app
npm install
npm run dev          # local Workers preview via wrangler
npm run deploy       # ships to Cloudflare Workers

Routing

Routes are TypeScript functions that return Response:

// src/app/routes.tsx
import { route, prefix } from "rwsdk/router";
import { HomePage } from "./pages/HomePage";

export const routes = [
  route("/", () => new Response("Hello, world!")),
  route("/page", HomePage),               // React component
  route("/api/users/:id", ({ params }) => {
    return Response.json({ id: params.id });
  }),
  prefix("/admin", [
    route("/", AdminHome),
    route("/users", AdminUsers),
  ]),
];

route() is a typed helper returning a standard (request, env, ctx) => Response | Promise<Response> function — so plain Fetch-API patterns interoperate.

React Server Components

// src/app/pages/HomePage.tsx
import { Suspense } from "react";

export async function HomePage({ ctx }) {
  const user = await ctx.db.users.where("id", ctx.userId).first();
  return (
    <html>
      <body>
        <h1>Hello, {user.name}</h1>
        <Suspense fallback={<p>Loading posts...</p>}>
          <UserPosts userId={ctx.userId} />
        </Suspense>
      </body>
    </html>
  );
}

async function UserPosts({ userId }) {
  const posts = await fetchPosts(userId);
  return <ul>{posts.map(p => <li key={p.id}>{p.title}</li>)}</ul>;
}

The page itself is a Server Component — no client hydration unless a "use client"-marked component appears in the tree.

Server Functions

"use server";
export async function createPost(formData: FormData) {
  const title = formData.get("title");
  return await ctx.db.posts.insert({ title });
}

Server Functions are callable from client components and execute server-side automatically.

Middleware

import { middleware } from "rwsdk/router";

const auth = middleware(async (request, next) => {
  const user = await verifyJWT(request.headers.get("authorization"));
  if (!user) return new Response("Unauthorized", { status: 401 });
  return next({ user });   // forward to handler with augmented context
});

export const routes = [route("/profile", auth, ProfilePage)];

Realtime

Built-in primitives for WebSocket-based realtime:

Correction (2026-08-21): rwsdk/realtime is not an export of the package. The published exports map of rwsdk 1.7.2 — and of the baseline 1.2.9 — contains ./realtime/client, ./realtime/worker and ./realtime/durableObject, but no bare ./realtime, so the import below never resolved. The current realtime API on docs.rwsdk.com is the useSyncedState hook, documented under Experimental → Realtime; the earlier broadcast-style API is filed there as "Legacy Realtime".

// Worker side (src/worker.tsx)
import {
  SyncedStateServer,
  syncedStateRoutes,
} from "rwsdk/use-synced-state/worker";

// Client side
// import { useSyncedState } from "rwsdk/use-synced-state/client";

useSyncedState has the same shape as React's useState but syncs bidirectionally with the server and every other connected client, with the server as source of truth. Values live in memory inside the Durable Object, so an eviction or worker restart wipes them unless you add a persistence callback.

Common gotchas

  • Cloudflare Workers limits apply — 30s wall-clock per request on paid plans (10ms CPU on free), 128MB memory, no native filesystem. Long-running tasks need Queues or Durable Objects.
  • No Node-API access — no fs, no child_process, no raw TCP. The Workers runtime is fetch + WebStandards only.
  • D1 has per-request query limits — 100k rows max per query, 1000 KV operations per request. RAG patterns over large datasets need Vectorize or external Postgres.
  • npx create-rwsdk requires Node 22+ (corrected 2026-08-21 — the entry previously said Node 18+). create-rwsdk 3.1.3 declares engines.node: ">=22" on npm, so Node 18 and Node 20 toolchains are refused outright. The local toolchain is Node, the runtime is Workers; they're distinct.
  • Server Components + Cloudflare = no Node-only React packages — many React libraries that import crypto or fs at module scope break on Workers. Audit dependencies.
  • Vite dev server vs Workers production — local dev runs via Vite (Node), production via wrangler dev / deploy (workerd). Behaviors can subtly differ (e.g., timezone handling). Test with wrangler dev before deploying.
  • The package is rwsdk, not @redwoodjs/sdk — the npm name is intentionally short. Search PyPI / npm carefully.
