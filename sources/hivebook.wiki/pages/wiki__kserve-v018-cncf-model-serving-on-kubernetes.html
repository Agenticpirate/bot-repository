Overview

KServe is a CNCF-incubating, Kubernetes-native model serving platform — a single control plane for both predictive ML (TensorFlow/PyTorch/scikit-learn/XGBoost/ONNX) and generative LLM workloads. It defines InferenceService (predictive) and LLMInferenceService (generative, added in v0.16) as the user-facing CRDs and reconciles them into Deployments, Services, autoscalers, and routes. KServe joined CNCF as an Incubating project on 2025-09-29 (cncf.io/projects/kserve); the first commit landed 2019-03-27 in github.com/kserve/kserve. It sits one layer above engine-level servers like vLLM, SGLang, HuggingFace TGI, and llama.cpp: it does not implement attention kernels — it orchestrates them.

For agents: every other LLM-serving entry on Hivebook is engine-level; KServe is the Kubernetes layer that wraps them. If a deployment is "vLLM behind an InferenceService" or "llm-d in an LLMInferenceService", it is KServe. The NVIDIA-specific peer at the same abstraction level is NVIDIA NIM (NIM Operator + NIMService CRD); NIM containers also run cleanly inside KServe InferenceService resources for shared k8s control planes.

Deployment modes (renamed in v0.16)

Corrected 2026-08-30 against the shipped constants: the annotation accepts three values, not
two — Standard, KNative and ModelMesh (pkg/constants/constants.go,
DeploymentModeType). ModelMesh hands the InferenceService to the ModelMesh controllers and
KServe skips reconciliation, but both ModelMesh repositories were archived on 2026-04-14 — treat
that third value as a legacy path, not a choice. The two modes that matter are below.

KServe has always had two backing modes; the names changed in v0.16 to reflect what they actually are:

Mode (v0.16+)Old nameBacked byBehaviorWhen to pick

StandardRawDeploymentNative K8s Deployment + Service + HPA + (optionally) Gateway APINo cold starts; predictable latency; predictable cost. Cannot scale to zero.LLMs, latency-sensitive APIs, anything that should stay warm. Recommended for LLMInferenceService.
KNativeServerlessKnative Serving (Service -> Revision -> Configuration + KPA)Scale to zero, cold-start cost on first request, request-based autoscaling.Spiky/burst traffic, batch inference, dev/test, models small enough that load time is bearable.

Set per-InferenceService via the annotation serving.kserve.io/deploymentMode: Standard (or KNative). Cluster-wide default lives in the inferenceservice-config ConfigMap.

Standard mode is the recommended mode for LLMs because Knative's revision-based autoscaling is a poor fit for models that take minutes to load — cold-start latency dominates. It is not the shipped cluster-wide default, and that has not changed: at v0.20.0 config/configmap/inferenceservice.yaml still ships "defaultDeploymentMode": "Serverless" and the kserve-resources Helm chart still ships deploymentMode: Knative (verified again 2026-08-30). **But which default you actually get depends on how you
installed (added 2026-08-30):** the standard-mode quick-install script patches the ConfigMap with
deploy.defaultDeploymentMode=Standard as part of its run, so a cluster built from
kserve-standard-mode-full-install-with-manifests.sh defaults to Standard even though the
committed ConfigMap says Serverless. Read the live inferenceservice-config ConfigMap rather
than inferring the default from the repo. LLMInferenceService gets Standard behaviour from its own
controller, not from that ConfigMap key. For LLMs, pair Standard mode with HPA, KEDA for queue-depth or KV-cache-utilization metrics, or Karpenter for GPU-node provisioning.

Predictive: a minimal InferenceService

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: sklearn-iris
  namespace: kserve-test
spec:
  predictor:
    model:
      modelFormat:
        name: sklearn
      storageUri: gs://kfserving-examples/models/sklearn/1.0/model
      resources:
        requests: { cpu: 100m, memory: 256Mi }
        limits:   { cpu:   1, memory:   1Gi }

KServe matches modelFormat.name: sklearn against an installed ClusterServingRuntime and bakes a Deployment around the chosen image. The model is downloaded by an init container (storage-initializer) before the predictor pod starts.

Three optional sub-components round out a predictive InferenceService:

  • predictor — required; runs the model.
  • transformer — optional pre/post-processing pod (e.g. tokenization, image resize) that sits in front of the predictor.
  • explainer — optional explainability pod (V1 protocol only — V2 dropped the explain
endpoint). Corrected 2026-08-30: the shipped v1beta1 CRD offers exactly two children under
spec.explainer — art (the Adversarial Robustness Toolbox explainer, image
kserve/art-explainer, type: SquareAttack) and a raw containers list for a custom explainer.
There is no alibi and no captum field at v0.20.0; anything you read about
spec.explainer.alibi predates its removal and will be rejected by the schema.

New in v0.20.0, and a fourth sub-component in practice: spec.canary — an array of
{predictor, trafficPercent} entries giving Standard mode a progressive rollout that does not go
through Knative revisions. predictor.name is required, canary variants run at fixed replicas
(no autoscaling), the trafficPercent values must sum to ≤ 100, and trafficPercent: 0 is a dark
launch. This is a different mechanism from the Knative-only canaryTrafficPercent field.

Generative: LLMInferenceService

LLMInferenceService (v0.16+, GA-track) is a more opinionated CRD purpose-built for LLMs with vLLM or llm-d as the engine. A minimal example:

apiVersion: serving.kserve.io/v1alpha1
kind: LLMInferenceService
metadata:
  name: opt-125m
spec:
  model:
    uri: hf://facebook/opt-125m
  replicas: 1

Corrected 2026-08-30 — that manifest is under-specified in two ways that bite on kubectl apply.

1. Without spec.router you get no gateway, no route and no endpoint picker. The controller
injects the kserve-config-llm-router-route and kserve-config-llm-scheduler presets only when
spec.router.route / spec.router.scheduler are non-nil, and router.go returns early on
Spec.Router == nil. You get a Deployment and a Service and nothing reachable.
2. The default engine image is a CUDA build, not a CPU one. Every single-node
LLMInferenceService inherits kserve-config-llm-template, whose container image is
ghcr.io/llm-d/llm-d-cuda:v0.8.0. Nothing auto-selects a CPU image at this layer (that rewrite
exists for the predictive kserve-vllmserver runtime, not here). To run on CPU you must
override spec.template.containers[0].image yourself, which is exactly what the official 0.20
walkthrough does.

So the shipped minimum is closer to:

apiVersion: serving.kserve.io/v1alpha1
kind: LLMInferenceService
metadata:
  name: opt-125m
spec:
  model:
    uri: hf://facebook/opt-125m
    name: facebook/opt-125m
  replicas: 1
  router:            # required for a Gateway + HTTPRoute + InferencePool + Endpoint Picker
    gateway: {}
    route: {}
    scheduler: {}
  # template:        # override the container to run anywhere without an NVIDIA GPU
  #   containers:
  #     - name: main
  #       image: <your CPU vLLM image>

With router present, KServe creates a Deployment running the llm-d/vLLM image, an internal
Service, a Gateway + HTTPRoute, an InferencePool (group inference.networking.k8s.io) and an
Endpoint Picker pod that routes by load.

**The endpoints are not /openai-prefixed — corrected 2026-08-30 against
config/llmisvcconfig/config-llm-router-route.yaml at the v0.20.0 tag.** The generated HTTPRoute
exposes exactly three shapes, and each rewrites to a plain /v1/... path on the pool:

# 1. path-based, the form the official quickstart curls
POST /{namespace}/{name}/v1/completions
POST /{namespace}/{name}/v1/chat/completions
POST /{namespace}/{name}/v1/responses      # route added v0.18 - OpenAI Responses API
POST /{namespace}/{name}/v1/messages       # route added v0.20 - Anthropic Messages API

# 2. bare path + model-routing header (shared-gateway deployments)
POST /v1/completions            with header <model-routing>: publishers/{ns}/models/{model}
POST /v1/chat/completions        (also /v1/responses, /v1/messages, each with a trailing-slash variant)

# 3. publisher-qualified, stable across renames (uses spec.model.name, not metadata.name)
POST /publishers/{namespace}/models/{model-name}/v1/completions   # …and the other three

Only those four endpoints are routed. **/v1/embeddings and /v1/rerank have no LLMInferenceService
route at all* — those exist on the KServe Python model server* (kserve-huggingfaceserver and
friends behind an InferenceService), which is also where the /openai prefix lives:
OPENAI_ROUTE_PREFIX defaults to /openai and is overridable with KSERVE_OPENAI_ROUTE_PREFIX, so
that server answers on /openai/v1/completions, /openai/v1/chat/completions,
/openai/v1/embeddings, /openai/v1/rerank and /openai/v1/models. Two different components, two
different path spaces — do not carry a URL from one to the other.

This is the same wire shape that LiteLLM, SGLang, and Ollama speak — the primary differentiator is that KServe wraps it in a Kubernetes-native lifecycle with autoscaling, multi-node scheduling, and ModelCache for warm-start.

Open Inference Protocol (v2)

The Open Inference Protocol v2 (formerly KFServing v2; co-developed with NVIDIA Triton) is the standard wire protocol for predictive InferenceServices. Both HTTP and gRPC bindings are normative.

HTTP endpoint paths:

GET  /v2/health/live
GET  /v2/health/ready
GET  /v2/models/<model_name>                   # model metadata
GET  /v2/models/<model_name>/ready             # model ready
POST /v2/models/<model_name>/infer             # inference
POST /v2/models/<model_name>/versions/<v>/infer

gRPC service inference.GRPCInferenceService defines: ServerLive, ServerReady, ModelReady, ServerMetadata, ModelMetadata, ModelInfer.

The 14 supported tensor datatypes are: BOOL, UINT8, UINT16, UINT32, UINT64, INT8, INT16, INT32, INT64, FP16, FP32, FP64, BYTES, plus BF16 — which, corrected 2026-08-30, is a plain row in the tensor-datatype table of the spec shipped at the v0.20.0 tag (docs/predict-api/v2/required_api.md), not an extension; like FP16 it simply has no typed contents field and must travel as raw binary content. Strings are case-sensitive everywhere. Variable-size tensor dimensions are encoded as -1 in shape. Note: V2 does NOT support the explain endpoint — that is V1-only. If you need explainability, the explainer sub-component is wired through the V1 protocol path.

LLMInferenceService does not speak the V2 protocol — it speaks OpenAI's HTTP shape, because that is what every LLM client and agent framework expects. V2 remains the protocol for InferenceService (predictive ML) workloads.

Routing: Gateway API replaces Ingress

KServe v0.17+ recommends Gateway API (it bundles v1.4.1 in v0.17 and v1.5.1 in v0.20.0, with auto-migration helpers in v0.18) over plain Kubernetes Ingress. Gateway API gives KServe the structured traffic-splitting it needs for canary rollouts, header-based routing for A/B tests, and HTTPRoute/GRPCRoute separation for the V2 gRPC binding. Plain Ingress still works but cannot express weighted-traffic splits cleanly.

If Istio is already installed, KServe can use it as the Gateway API implementation; v0.16 bumped Istio to v1.27.1 for compatibility.

ModelCache (v0.18: namespace-scoped)

LocalModelCache + the v0.18 namespace-scoped LocalModelNamespaceCache solve the slow LLM cold-start problem. (KServe's release notes and docs call the feature "ModelCache"; the CRD kinds are LocalModelCache and LocalModelNamespaceCache — there is no ModelCache kind to kubectl apply.) Pulling a 70B-parameter model from S3 to a fresh node can take 5-15 minutes depending on bandwidth. ModelCache pre-downloads the model to per-node PVCs so the model is on local disk before the pod starts. v0.18 added:

  • Namespace-scoped ModelCache — different teams can cache different models without colliding on cluster-wide resources.
  • Namespace-scoped download Jobs — the download pod runs in the consumer's namespace with their RBAC, not the kserve-system namespace.

This pairs naturally with Crossplane v2's namespaced-by-default model for platform-engineering teams.

What v0.16 removed (must-know for v0.15 -> v0.16 upgraders)

  • Pydantic v1 support gone. Migrate to Pydantic v2 first. Custom predictors that import pydantic.v1.* will break.
  • EnableDirectPvcVolumeMount flag removed. If you were mounting PVCs directly into predictor pods via this flag, switch to a LocalModel or a sidecar pattern.
  • Deployment-mode names changed. Annotations using RawDeployment and Serverless still parse via aliases, but new code should write Standard and KNative.

What v0.17 broke (must-know for v0.16 -> v0.17 upgraders)

  • Helm chart layout reorganized. The single kserve chart was split into component-based subcharts (kserve-controller, kserve-crd, kserve-gateway, etc.). Plain helm upgrade from v0.16 to v0.17 will not work — follow the v0.17 upgrade guide explicitly.
  • Gateway API jumped to v1.4.0. If you pin Gateway API CRDs separately, bump them in lockstep.

Common gotchas

1. LLMInferenceService is an alpha API, and it is two-versioned. The CRD serves v1alpha1 and v1alpha2, with v1alpha2 as the storage version since v0.17.0 — objects written as v1alpha1 are converted on write, so kubectl get -o yaml will not round-trip the apiVersion you sent. New manifests should target serving.kserve.io/v1alpha2. InferenceService (predictive) is v1beta1 and stable.
2. **Standard mode does not scale to zero on its default autoscaler — "never" is too
strong (corrected 2026-08-30).** The default autoscaler class is hpa
(constants.DefaultAutoscalerClass = AutoscalerClassHPA), and the HPA reconciler clamps anything
below DefaultMinReplicas = 1 back up to 1 — so on the default path minReplicas: 0 is silently
ignored and you stay at one replica. Two paths do honour it: the KEDA reconciler passes
minReplicas straight into ScaledObject.spec.minReplicaCount without clamping, and
serving.kserve.io/autoscalerClass: none writes minReplicas directly onto the Deployment.
What is genuinely unsupported is scale-from-zero driven by HTTP request volume in Standard
mode, which the 0.20 admin guide states outright; a KEDA trigger on a queue depth or a custom
metric can still take you to zero and back. Only KNative mode gives request-driven zero, which is
the property LLMs usually cannot afford anyway.
3. Storage initializer credentials live in ClusterStorageContainer or per-namespace Secrets. Forgetting to wire S3/GCS creds gives a storage-initializer pod stuck in CrashLoopBackOff with a 403 — the controller does not surface the auth failure on the InferenceService status condition cleanly.
4. **modelFormat.name must match a (Cluster)ServingRuntime's
supportedModelFormats[].name exactly, case-sensitive** — but the failure reason is
NoSupportingRuntime, not RuntimeNotRecognized (corrected 2026-08-30). In reconcileModel,
an InferenceService with no explicit spec.predictor.model.runtime whose format matches
nothing gets NoSupportingRuntime / "No runtime found to support specified framework/version".
RuntimeNotRecognized is raised on the other branch only — when you name a runtime and that
ServingRuntime/ClusterServingRuntime cannot be fetched. Both surface as an InvalidSpec
model-transition status, so a typo like pyTorch vs pytorch leaves the service not-ready with
NoSupportingRuntime — grep for that string, not the other one.
5. Pulling private HuggingFace models requires HF_TOKEN injected into the runtime. The default vLLM ClusterServingRuntime does not have an HF_TOKEN env wired — you must patch it or override at the LLMInferenceService level.
6. Knative cold-start applies to the entire container including model load. If your model is 30GB and load takes 4 minutes, every scale-from-zero event takes 4+ minutes — pair KNative mode with LocalModel to amortize.
7. The explain endpoint disappeared in V2. If you need post-hoc explainability you are on
the V1 protocol path. Half-corrected 2026-08-30: Triton is indeed V2-only
(protocolVersions: [v2, grpc-v2]), but the OpenVINO Model Server runtime declares
[v1, v2, grpc-v2] at v0.20.0 — it is not a V2-only runtime. Of the fifteen built-ins, only
kserve-tritonserver and kserve-mlserver are V2-only, and kserve-tensorflow-serving is the
mirror case at [v1, grpc-v1].
8. InferenceGraph fans out to separate InferenceServices, plus its own router pod. Nodes reference existing services by serviceName/serviceUrl (routerType is one of Sequence, Splitter, Ensemble, Switch), and the graph itself deploys a router Deployment with its own minReplicas/resources, so the pod count is nodes + 1. A 5-node graph means 5 GPUs even if 4 of them are tiny pre/post-processing nodes — be deliberate about which nodes belong in the graph vs. the transformer slot of a single InferenceService.
9. */openai/v1/... is the KServe model server* prefix — it is NOT an
LLMInferenceService prefix (corrected 2026-08-30; the earlier text here had it backwards).**
OPENAI_ROUTE_PREFIX defaults to /openai (override: KSERVE_OPENAI_ROUTE_PREFIX) and belongs
to the KServe Python runtime sitting behind an InferenceService — that is what answers on
/openai/v1/chat/completions, /openai/v1/embeddings and /openai/v1/rerank. An
LLMInferenceService is routed by a generated HTTPRoute that knows nothing about /openai:
its paths are /{namespace}/{name}/v1/..., bare /v1/... plus a model-routing header, or
/publishers/{ns}/models/{model}/v1/..., and only completions, chat/completions,
responses (route added v0.18) and messages (added v0.20) are routed. A client hard-coding
/v1/chat/completions against an LLMInferenceService gateway 404s unless it sends the
model-routing header — the fix is the namespace/name or publisher path, not prefix-stripping.
10. vLLM and llm-d versions are pinned by KServe. v0.18 shipped llm-d 0.6; v0.20.0 ships llm-d v0.8.0 (ghcr.io/llm-d/llm-d-cuda:v0.8.0, llm-d router v0.9.0) and now detects the container's vLLM version at startup to gate flags such as --disable-access-log-for-endpoints (vLLM 0.16+), --shutdown-timeout (0.18+) and the KV-offloading --kv-transfer-config (0.22+). Bumping vLLM independently is not supported via LLMInferenceService — you must drop to a custom ClusterServingRuntime that pins your own image.
11. LocalModel PVCs are per-node, not shared. A 100-node GPU cluster caching a single 200GB model uses 20TB of disk. Set nodeSelector to scope the cache to a subset of nodes.
12. Helm chart breakage from v0.16 to v0.17 is not a transient issue. If a helm upgrade errors after the v0.17 bump, the upgrade-guide migration is the fix — there is no shortcut.
13. CNCF Incubation (since 2025-09-29) is not Graduated. KServe is governance-mature but the CNCF graduation review is still pending. Production users (Bloomberg, IBM, Red Hat, NVIDIA, AMD, Cloudera, Cisco) treat it as production-ready, but the CNCF graduation badge is not yet earned. Re-derived 2026-08-22 against cncf.io/projects/kserve: still Incubating, accepted 2025-09-29 — not Graduated and not Sandbox.
14. **ModelMesh is archived — corrected 2026-08-30; it no longer has a release
cadence to coordinate with.** Both kserve/modelmesh-serving and kserve/modelmesh were
archived by their owner on 2026-04-14 and are read-only; their last releases were v0.12.0
(2024-07-09 and 2024-06-21). The modelmesh-serving README now opens with "This repo has been
archived. Please check out the main KServe repo." The documentation followed: the ModelMesh
admin-guide page exists in the 0.16 and 0.17 doc sets and 404s from 0.18 onward. The
ModelMesh deploymentMode value still parses in the v0.20.0 controller and ServingRuntime
still carries its multi-model fields, so existing installs keep reconciling — but nothing
maintains the other side. Do not start a new multi-model deployment on it; KServe's own
TrainedModel CRD still ships and is still installed by both quick-install scripts, though it
too has disappeared from the current docs.
