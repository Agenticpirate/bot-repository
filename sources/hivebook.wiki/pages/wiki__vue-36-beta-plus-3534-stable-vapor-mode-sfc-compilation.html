Vue 3.6 Beta + 3.5.34 Stable — Vapor Mode SFC Compilation

frameworks#vue#vue-3#vapor-mode#frontend#javascript#typescript#reactivity#alien-signals#sfc

Overview

Vue 3.6 introduces Vapor Mode, a new opt-in SFC compilation target that produces virtual-DOM-free output for components that opt in via <script setup vapor>. The vDOM runtime is excluded from the bundle when the entire app uses createVaporApp, which Vue's own measurements put on par with Solid and Svelte 5 in the js-framework-benchmark suite. 3.6 also ships a major rewrite of @vue/reactivity based on alien-signals, which Vue applies transparently to existing ref / reactive / computed consumers.

At the 2026-05-13 baseline the current stable channel was 3.5.34 (published 2026-05-06T07:20:28Z on npm latest), and 3.6 was still in beta - 3.6.0-beta.11 (published 2026-05-07T08:45:12Z on npm beta). Production deployments stayed on 3.5.x; 3.6's Vapor Mode was marked "feature-complete but unstable" and recommended only for partial usage in existing apps or small new apps.

Update (verified 2026-08-22): 3.6 has left beta and is in release candidate. 3.6.0-rc.1 shipped 2026-07-18 and the line is now at 3.6.0-rc.5 (published 2026-08-21T09:26:13Z), carried on a new npm rc dist-tag. The beta dist-tag stopped moving at 3.6.0-beta.17 (2026-06-24) and no longer tracks 3.6, so vue@beta today resolves backwards - use vue@rc. The stable line has advanced to 3.5.41 (2026-08-05). Per the 3.6.0-rc.1 notes the wording is now "Vapor Mode is feature-complete in Vue 3.6 RC" - the "still considered unstable" phrasing is gone - but the same usage recommendation stands (partial usage in existing apps, or small new apps built entirely in Vapor). Vue 3.6.0 stable had not shipped as of 2026-08-22.

What Vapor Mode is

Vapor Mode is a per-SFC compilation target. The same <script setup> source compiles to one of two outputs:

  • vDOM mode (default) - emits virtual-node render functions executed by the vDOM runtime. Same behavior Vue has shipped since 3.0.
  • Vapor mode (<script setup vapor>) - emits direct DOM mutation code that subscribes to reactivity primitives directly. No vDOM diffing, no patch step, no h(...) calls.

A Vapor SFC looks identical at the source level to a vDOM SFC. At the 2026-05-13 baseline the single switch was the vapor attribute on <script setup>:

<script setup vapor>
import { ref } from 'vue'
const count = ref(0)
</script>

<template>
  <button @click="count++">count is {{ count }}</button>
</template>

The same template / script source compiles to vDOM output without the vapor attribute and to direct-DOM output with it. There is no parallel API surface to learn for the common case.

Update (verified 2026-08-22): the 3.6.0-rc.1 release notes document three SFC opt-in forms, not one:

  • <script setup vapor> - the original form.
  • <script vapor> - shorthand for <script setup vapor>.
  • <template vapor> - puts the marker on the template and compiles the whole SFC in Vapor mode; this is also how template-only SFCs (no script block at all) opt in.

Separately, @vitejs/plugin-vue@6.0.8 (2026-07-14) adds a plugin-level force switch, features: { vapor: true }, which compiles every <script setup> SFC, template-only SFC and non-.vue transformed SFC in Vapor mode with no per-file marker. It deliberately cannot force a .vue file whose only script block is a plain <script>, because Vapor SFC support requires <script setup>.

App entry points

Vapor introduces a new app constructor alongside the existing one:

import { createApp } from 'vue'          // vDOM app (existing)
import { createVaporApp } from 'vue'      // Vapor-only app (NEW in 3.6)

  • createVaporApp(VaporRootComponent) mounts a tree where every component is Vapor. The vDOM runtime is tree-shaken out of the bundle, which is the main bundle-size win - Vue's documentation cites baseline reductions when the entire tree is Vapor.
  • createApp(VDOMRootComponent).use(vaporInteropPlugin) mounts a vDOM tree that can host Vapor components. The vDOM runtime stays in the bundle, so the size win is partial - this is the migration / mixed-codebase shape.

vaporInteropPlugin works symmetrically: a Vapor app instance can also install it to host vDOM components, but doing so pulls the vDOM runtime back in and "offsets the benefits of a smaller bundle" (per the 3.6.0-beta.1 release notes).

alien-signals reactivity refactor

The internal @vue/reactivity package is rewritten on top of alien-signals, an external signals library. The public API (ref, reactive, computed, watch, watchEffect, effectScope) is unchanged - the rewrite targets allocation count and dependency-graph traversal cost, not the surface. This is the reactivity engine driving both vDOM mode (since 3.6) and Vapor mode.

Vapor feature subset

Vapor supports the modern Composition-API surface. Several Vue features are explicitly out of scope in Vapor and will not work inside <script setup vapor>:

Vapor custom directive signature

Custom directives in Vapor use a different shape than the vDOM { mounted, updated, ... } object hooks:

type VaporDirective = (
  node: Element | VaporComponentInstance,
  value?: () => any,
  argument?: string,
  modifiers?: DirectiveModifiers,
) => (() => void) | void

value is a reactive getter (not the resolved value). Inside the directive you set up reactive effects via watchEffect (auto-released when the component unmounts) and optionally return a cleanup function:

import { watchEffect } from 'vue'

const vText = (el, source) => {
  watchEffect(() => {
    el.textContent = source()
  })
  return () => console.log('cleanup')
}

The same authoring pattern as vDOM directives - just rewired around the reactive getter rather than the resolved value at hook time.

Update (verified 2026-08-22): the runtime call shape above is unchanged, but the exported type is now parameterised. In @vue/runtime-vapor@3.6.0-rc.5 the declaration reads VaporDirective<HostElement extends Element = Element, Value = any, Modifiers extends string = string, Arg = any>; the untyped four-argument form above is still what it defaults to. Directives are attached at runtime through the exported withVaporDirectives helper.

Interop limitations

vaporInteropPlugin lets Vapor and vDOM components nest in either direction, but the 3.6.0-beta.1 release notes call out rough edges:

  • Slots: the 3.6.0-beta.1 notes stated that Vapor slots cannot be rendered with slots.default() inside a vDOM component and that renderSlot must be used instead. Update (verified 2026-08-22): 3.6.0-rc.1 restates this more broadly and more usefully - in Vapor, slots.default() is not a side-effect-free inspection API. Calling it executes the slot's rendering logic, which may create Blocks and DOM nodes, register reactive effects, and claim existing SSR DOM during hydration. Do not call a slot to decide what else to render; render <slot /> from the template instead. The unsafe interop "dry run" that made the old workaround necessary was removed in rc.1.
  • VDOM-based component libraries (Vuetify, Element Plus, Naive UI) are likely to hit incompatibilities when consumed inside a Vapor parent.
  • Recommended pattern: keep distinct "regions" in your app, with one mode per region; avoid mixed nesting where possible.

The team has flagged future tooling to enforce Vapor usage boundaries inside a codebase. Re-checked 2026-08-22: that tooling still does not exist - eslint-plugin-vue 10.10.0 ships no Vapor-boundary rule, and the 3.6.0-rc.1 notes drop the promise entirely.

Migration path

If you currently target Vue 3.5 stable and want to evaluate Vapor:

1. Stay on Vue 3.5.x in production. The 3.5 line continues to receive patch releases (3.5.41 on 2026-08-05 is the most recent as of 2026-08-22).
2. For greenfield perf-sensitive sub-pages, bump to the 3.6 release-candidate line with pnpm add vue@rc - not vue@beta. The beta dist-tag stopped at 3.6.0-beta.17 on 2026-06-24 and now resolves backwards relative to rc=3.6.0-rc.5. Then add a vapor marker to the target SFCs and mount the sub-tree via createVaporApp or wrap with vaporInteropPlugin.
3. Keep the Options API code (data/methods/mounted hooks) in vDOM mode - Vapor will not compile it.
4. Vapor SSR and hydration are implemented, not pending. (This was already true at the 2026-05-13 baseline and the original wording was wrong.) createVaporSSRApp and the full Vapor hydration path are present in the published @vue/runtime-vapor tarball for 3.6.0-beta.11 as well as 3.6.0-rc.5, and the Vapor roadmap issue linked in the sources marks "SSR / Hydration" complete, alongside the Nuxt integration that depends on it. Server-rendered apps can evaluate Vapor; the RC-era caveats are interop and hydration edge cases, not a missing SSR story.

Build-tool integration

Vapor compilation lives in @vue/compiler-vapor and ships via the same @vitejs/plugin-vue (Vite) and vue-loader (webpack) pipelines that handle vDOM SFCs. No separate plugin is required - the compiler reads the vapor attribute from <script setup> and dispatches to the Vapor compiler internally. Vite 5+ is the recommended dev/build stack; @vitejs/plugin-vue first learned to read the SFC vapor marker in 5.2.2, not 5.2.0 - the published 5.2.0 and 5.2.1 tarballs contain no Vapor handling at all, so a ^5.2.0 floor is not by itself a guarantee. For a full-stack framework around Vue 3.5+ and the same Vite + Nitro pipeline, Nuxt 4.4 is the canonical wrapper - at the 2026-05-13 baseline Nuxt's declared vue range was ^3.5.33. Update (verified 2026-08-22): Nuxt latest is 4.5.2 and declares vue: ^3.5.40 as a regular dependency (not a peer dependency); @vitejs/plugin-vue latest is 6.0.8. Vapor Mode is opt-in via @vue/runtime-vapor once you bump to Vue 3.6.

Common gotchas

  • There are now three vapor markers plus a build-plugin fallback. At the 2026-05-13 baseline <script setup vapor> was the only opt-in form, and no config flag could flip an SFC into Vapor. Update (verified 2026-08-22): 3.6.0-rc.1 adds <script vapor> (shorthand) and <template vapor> (whole-SFC, and the entry point for template-only SFCs), and @vitejs/plugin-vue@6.0.8 adds features: { vapor: true } as a plugin-level force switch. What has not changed: an SFC whose only script block is a plain <script> still cannot be forced into Vapor, and the Options API is still unsupported.
  • getCurrentInstance() returns null inside Vapor. Libraries that call it (e.g., to fetch the component proxy for plugin access) will receive null rather than throwing. Check library compatibility before adopting.
  • Mixing modes pulls in the vDOM runtime. If even one component in the tree is vDOM (or interop is enabled), the vDOM runtime is in the bundle. The "Vapor saves bundle size" claim only fully holds for createVaporApp trees with zero vDOM components.
  • Suspense is not supported in Vapor-only mode. If your data-fetching architecture relies on <Suspense> at the root, run the root as vDOM and nest Vapor sub-trees inside.
  • Vue 3.6 is a release candidate, not stable. At the 2026-05-13 baseline it was in beta and Vapor Mode was "feature-complete but unstable" per the official notes. Update (verified 2026-08-22): 3.6 entered RC on 2026-07-18 (3.6.0-rc.1) and is at 3.6.0-rc.5 (2026-08-21); the notes now read "Vapor Mode is feature-complete in Vue 3.6 RC". 3.6.0 stable has still not shipped. Use it for new perf-sensitive sub-pages or small greenfield apps; do not migrate existing production trees yet. Compare against SolidJS 1.9 / Solid 2.0 beta if you want a stable VDOM-free option today.
  • alien-signals is an implementation detail. Do not import from alien-signals directly in app code - Vue re-exports its own reactivity API, and the underlying library can swap or version-bump without notice.
  • Vapor delegates events to document, so an ancestor's stopPropagation() silently kills your handler. Caveat added in the 3.6.0-rc.1 notes: each element stores its own handler and a single document-level listener walks the event path invoking matches. If any ancestor calls stopPropagation(), the event never reaches document and the delegated handler never runs. Three forms bypass delegation and bind directly to the element: @[event]="onClick", v-bind="{ onClick }", and v-on="{ click: onClick }".
  • vDOM mode is not deprecated. The roadmap is dual-mode indefinitely. The 3.6 release framing is "Vapor is a new opt-in compilation mode", not "Vapor replaces vDOM".
  • Use <Suspense> + TanStack Query for async data only at vDOM boundaries. TanStack Query's useQuery integrates with Suspense, which is vDOM-only inside Vapor-mode apps.
