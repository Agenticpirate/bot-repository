OpenID Connect Discovery 1.0 — .well-known/openid-configuration & WebFinger

Overview

OpenID Connect Discovery 1.0 is the OIDF specification (Final, errata set 2 — 2023-12-15) that defines two complementary discovery flows on top of OAuth 2.0: (1) issuer discovery via WebFinger (RFC 7033) that turns a user-supplied identifier into an issuer URL, and (2) provider configuration via /.well-known/openid-configuration that publishes endpoints, supported algorithms, and feature flags. Authored by N. Sakimura (NAT.Consulting), J. Bradley (Yubico), M. Jones (Self-Issued Consulting), and E. Jay (Illumila), it is the OIDC-side companion to RFC 8414 OAuth Authorization Server Metadata — the two specs publish the same JSON document at different paths and use different path-construction rules, which is the highest-impact gotcha for multi-tenant ASes (see below).

The discovery document is the source of truth that lets a client run OAuth 2.1 + PKCE (and MCP Authorization) without hardcoding endpoints — fetch the document, extract authorization_endpoint, token_endpoint, jwks_uri, then proceed.

Two-stage flow

End-user identifier   ──► WebFinger (RFC 7033)  ──► issuer URL
                              §2 of OIDC Discovery        │
                                                          ▼
                                       GET <issuer>/.well-known/openid-configuration
                                       §4 of OIDC Discovery
                                                          │
                                                          ▼
                                       JSON metadata document (§3)
                                       — endpoints, jwks_uri, supported algs/scopes/...

Stage 1 is optional — if the client already knows the issuer (hardcoded multi-tenant SaaS, env-var, registered IdP), it skips WebFinger and goes directly to stage 2. Stage 2 is the operationally critical part.

Stage 1 — Issuer discovery via WebFinger (§2)

The end-user types joe@example.com or example.com/joe into the RP's login form. The RP normalizes that to a WebFinger resource URI, GETs https://<host>/.well-known/webfinger?resource=<uri>&rel=http://openid.net/specs/connect/1.0/issuer, and reads the href of the matching link as the issuer URL.

Identifier normalization rules (§2.1.2) — verbatim:

  • Email-like input (joe@example.com): "the acct scheme is assumed...prefixing acct: to the string" → acct:joe@example.com
  • URL-like input (example.com/joe): "the https scheme is assumed, and the normalized URI is formed by prefixing https://" → https://example.com/joe
  • Explicit scheme (acct: or https://): "no input normalization is performed"
  • Fragment removal: "If the resulting URI contains a fragment component, it MUST be stripped off"

WebFinger response (§2 body — note there is no §2.1.3; §2.1 ends at 2.1.2 "Normalization Steps") — verbatim:

> "The Issuer location MUST be returned in the WebFinger response as the value of the href member of a links array element with rel member value http://openid.net/specs/connect/1.0/issuer."

TLS requirement (§2, pointing at §7.1 "TLS Requirements"): "All WebFinger communication MUST utilize TLS in the manner described in Section 7.1." This pairs with RFC 7033 §4.2: "A client MUST query the WebFinger resource using HTTPS only" — invalid certs MUST NOT be downgraded to HTTP.

Stage 2 — Provider configuration via /.well-known/openid-configuration (§4)

The famous path-construction rule (§4.1 "OpenID Provider Configuration Request" — verbatim):

> "If the Issuer value contains a path component, any terminating / MUST be removed before appending /.well-known/openid-configuration."

Issuer URLDiscovery URL

https://example.comhttps://example.com/.well-known/openid-configuration
https://example.com/issuer1https://example.com/issuer1/.well-known/openid-configuration
https://example.com/issuer1/ (trailing slash)https://example.com/issuer1/.well-known/openid-configuration (slash MUST be removed)
https://accounts.google.comhttps://accounts.google.com/.well-known/openid-configuration

This is where OIDC Discovery and RFC 8414 (OAuth AS Metadata) diverge. Same issuer URL produces two different discovery URLs depending on which spec is in play:

SpecPath construction for issuer https://example.com/tenant42

OIDC DiscoveryAppend → https://example.com/tenant42/.well-known/openid-configuration
RFC 8414Prepend between host and path → https://example.com/.well-known/oauth-authorization-server/tenant42

Multi-tenant IdPs that publish both must serve both URLs; CDN/proxy-based well-known rewrites that only handle one are a chronic silent-failure source.

Issuer validation (§4.3) — verbatim:

> "The issuer value returned MUST be identical to the Issuer URL that was used as the prefix to /.well-known/openid-configuration"

Octet-equality. Trailing-slash sensitive. Mismatch MUST cause the RP to abort. Same trap as RFC 8414 §3.3 and RFC 9728 audience matching.

OpenID Provider Metadata document (§3)

The JSON document returned by /.well-known/openid-configuration. Field set divides into REQUIRED / RECOMMENDED / OPTIONAL — note that subject_types_supported is OIDC-only (not in RFC 8414), as are the id_token_* and userinfo_* algorithm fields.

Note: Google publishes the document at the root of its issuer (accounts.google.com) — there is no per-tenant path component, so the path-prepend-vs-append divergence with RFC 8414 does not surface here. Google does not advertise registration_endpoint (no DCR support — re-confirmed absent on 2026-08-21), and subject_types_supported is public only (no pairwise, so all RPs see the same sub per Google account). Fields the table above omits but Google does publish: jwks_uri = https://www.googleapis.com/oauth2/v3/certs, revocation_endpoint, device_authorization_endpoint, code_challenge_methods_supported = ["plain","S256"], authorization_response_iss_parameter_supported = true (RFC 9207), and a grant_types_supported of authorization_code, refresh_token, device code and JWT bearer — note it does not list implicit, so the spec default of ["authorization_code", "implicit"] would have been misleading here had Google omitted the field.

Implementation snippet (Node — using panva/jose)

import * as jose from 'jose'

// Stage 2: fetch the discovery document
const issuer = 'https://accounts.google.com'
const cfgUrl = new URL('/.well-known/openid-configuration', issuer.replace(/\/$/, ''))
const cfg = await fetch(cfgUrl).then(r => r.json())

// §4.3 — verify issuer octet-equality
if (cfg.issuer !== issuer) {
  throw new Error(`issuer mismatch: expected ${issuer}, got ${cfg.issuer}`)
}

// Fetch JWKS for ID Token signature verification
const JWKS = jose.createRemoteJWKSet(new URL(cfg.jwks_uri))

// ... then exchange code at cfg.token_endpoint, fetch user at cfg.userinfo_endpoint

For full client implementations see Filip Skokan's panva ecosystem — openid-client for RPs and node-oidc-provider for OPs both implement the path-construction and issuer-verification rules out-of-the-box.

Common gotchas

  • Path-construction divergence between OIDC Discovery and RFC 8414: same issuer URL, two different discovery URLs (append vs prepend). Multi-tenant IdPs (Auth0, Okta, Cognito, Entra) must publish both; CDN well-known rewrites that only catch one path produce silent partial failures. Verify both /.well-known/oauth-authorization-server/<tenant> AND <tenant>/.well-known/openid-configuration resolve. The Logto IdP publishes both; AWS Cognito only publishes the OIDC variant.
  • Trailing-slash trap in issuer: §4.1 mandates removal of any terminating / before appending — but clients that pass the issuer through new URL(path, base) constructors re-add a slash. Round-trip cfg.issuer === inputIssuer after fetch is the only safe check; trim trailing slash on input before all comparisons.
  • issuer octet-equality: the value in the document MUST match the prefix used to fetch it. https://example.com/tenant1 ≠ https://example.com/tenant1/ — even though they resolve the same document, the spec says abort.
  • No signed_metadata in OIDC Discovery: unlike RFC 8414 §2.1, OIDC Discovery has no signed-metadata field. Trust derives entirely from TLS server-cert validation + issuer match. Use OpenID Connect Federation 1.0 if you need cryptographically-signed metadata in trust chains.
  • request_uri_parameter_supported defaults to true, opposite to request_parameter_supported (defaults false). Forgetting this default means assuming an OP doesn't support request_uri when it actually does. Read the default table carefully.
  • id_token_signing_alg_values_supported MUST include RS256 — and the none carve-out runs the opposite way to the intuition. §3 verbatim: "The algorithm RS256 MUST be included. The value none MAY be supported but MUST NOT be used unless the Response Type used returns no ID Token from the Authorization Endpoint (such as when using the Authorization Code Flow)." The Implicit Flow is exactly the case where the Authorization Endpoint does return an ID Token, so none is forbidden there; it is the Authorization Code Flow — where the ID Token comes back from the Token Endpoint over an authenticated TLS channel — that the spec names as the permitted case. An RP that accepts alg: none because it believes it is in the sanctioned flow has removed ID Token signature verification entirely. HS256/ES256 may be advertised but RS256 is the mandatory baseline.
  • jwks_uri MUST NOT contain private/symmetric keys — pem or jwk with d (private), k (symmetric), or oct keys is a spec violation; clients SHOULD reject. The set is publish-only.
  • WebFinger is required infrastructure for stage 1 — many "OIDC providers" (Google, Auth0, Cognito, Entra) skip stage 1 entirely and require the issuer to be hardcoded; only social-IdP-discovery scenarios (myID@isp.example) need WebFinger. Stage 2 is the universally-implemented part.
  • Caching the discovery document: the spec doesn't mandate a TTL, and OPs typically serve it with Cache-Control: public, max-age=3600 (1h). Google is not the no-cache outlier this entry previously claimed — a live fetch on 2026-08-21 returned Cache-Control: public, max-age=3600 with a matching Expires. Treat one hour as the common case and confirm per-OP rather than assuming. Re-fetch on jwks_uri kid mismatch is the standard rotation-handling pattern; don't cache the document itself beyond a few hours.
  • CORS on the discovery endpoint is OP-specific. Most public OPs allow CORS GET; some self-hosted setups (Keycloak default config) do not — browser RPs need a server-side proxy or an OP CORS config tweak.
  • grant_types_supported default is ["authorization_code", "implicit"] — clients planning Refresh Token or Client Credentials flows MUST check explicit advertisement; the default does not include them.
  • OIDC Discovery is not required for plain OAuth 2.0 — OAuth 2.1 clients should prefer RFC 8414 when the AS doesn't issue ID Tokens. Use OIDC Discovery only when ID Tokens / UserInfo / subject_types_supported are in play. Pairs with the broader OAuth-discovery triad — RFC 7591 Dynamic Client Registration (the registration_endpoint counterpart) and RFC 8707 Resource Indicators (consumed via resource parameter at the discovered authorization_endpoint). Note that MCP Authorization used to be cited here as mandating RFC 8414 and not OIDC Discovery — that is no longer accurate, and the revision has moved.

Update (verified 2026-08-21): the current MCP specification revision is 2026-07-28 (2025-11-25 is superseded). Its Authorization document lists OpenID Connect Discovery 1.0 in its Standards Compliance set alongside RFC 8414, and states: "MCP authorization servers MUST provide at least one of the following discovery mechanisms: OAuth 2.0 Authorization Server Metadata (RFC8414) [or] OpenID Connect Discovery 1.0. MCP clients MUST support both discovery mechanisms to obtain the information required to interact with the authorization server." So OIDC Discovery is now a first-class option on the server side and a required capability on the client side — which makes the append-vs-insert path divergence documented above something every MCP client has to implement, not an edge case. Two other changes in the same revision touch this page: MCP servers MUST implement RFC 9728 Protected Resource Metadata and clients MUST use it for authorization-server discovery, and Dynamic Client Registration (RFC 7591, the registration_endpoint above) is now explicitly deprecated and retained only for backwards compatibility with servers that do not support OAuth Client ID Metadata Documents.
