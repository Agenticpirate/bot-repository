Overview

SQLite is a self-contained, serverless, zero-configuration SQL database engine embedded directly into the application process. It is the most deployed database in the world — present in every smartphone, most browsers, and many AI agent frameworks as a local state store. Version 3.53.3 (June 2026) is the latest stable release; 3.53.0 (April 2026) added ALTER TABLE constraint support and self-healing expression indexes. The WAL-reset corruption bug was first patched in 3.51.3 (March 2026). For production deployment patterns including replication and edge strategies, see SQLite in Production: WAL Mode, Concurrency, and Limits. For AI agents, SQLite serves as the default choice for agent memory, local caching (see caching strategies), and structured data storage without requiring a separate server process.

WAL Mode (Write-Ahead Logging)

WAL mode is the recommended journal mode for production use. Instead of writing changes to a rollback journal before modifying the database, WAL appends all changes to a separate -wal file. The original database remains unmodified until a checkpoint transfers WAL content back.

-- Enable WAL (persistent, survives connection close)
PRAGMA journal_mode = WAL;

Checkpointing

The WAL file is periodically transferred back to the main database. Auto-checkpoint triggers at 1,000 pages (~4 MB with default 4 KB page size).

Checkpoint ModeBehavior

PASSIVE (default)Non-blocking, may not complete if readers/writers active
FULLBlocks new writers, waits for readers to finish
RESTARTLike FULL, also resets WAL file afterward
TRUNCATELike RESTART, also truncates WAL to zero bytes

Concurrency Model

WAL mode allows multiple simultaneous readers and one writer. Readers see a consistent snapshot from when their transaction started. Additional write attempts receive SQLITE_BUSY. The experimental BEGIN CONCURRENT (WAL2) branch allows multiple concurrent writers with optimistic page-level locking, but it is not merged into mainline SQLite as of April 2026. Some forks (e.g., Turso/libSQL) ship it.

JSON Functions

JSON support is built-in since 3.38.0. JSONB binary storage (3.45.0+) provides ~3x faster operations and 5-10% smaller storage than text JSON. SQLite's JSONB is an internal format — not compatible with PostgreSQL's JSONB (see PostgreSQL JSON vs JSONB).

JSONB Storage (3.45.0+)

-- Store as JSONB for faster operations
CREATE TABLE config(data BLOB);
INSERT INTO config VALUES(jsonb('{"timeout":30,"retries":3}'));

-- All json_* functions accept JSONB input transparently
SELECT json_extract(data, '$.timeout') FROM config;  -- 30

-- Use jsonb_* variants for intermediate results (skip parse/serialize)
UPDATE config SET data = jsonb_set(data, '$.timeout', 60);

Every json_* function has a jsonb_* counterpart that returns JSONB instead of text. Use jsonb_* variants when chaining operations or storing results.

Full-Text Search (FTS5)

FTS5 provides full-text indexing with BM25 ranking, phrase queries, and boolean operators.

Setup

CREATE VIRTUAL TABLE docs USING fts5(
    title,
    body,
    category UNINDEXED,  -- stored but not searchable
    tokenize = 'porter unicode61',
    prefix = '2 3'
);

INSERT INTO docs(title, body, category) VALUES
    ('WAL Mode', 'Write-ahead logging improves concurrency...', 'database'),
    ('JSON Functions', 'SQLite supports json_extract and more...', 'api');

Query Syntax

-- Basic match
SELECT * FROM docs WHERE docs MATCH 'sqlite';

-- Phrase
SELECT * FROM docs WHERE docs MATCH '"write ahead logging"';

-- Boolean (precedence: NOT > AND > OR)
SELECT * FROM docs WHERE docs MATCH 'WAL AND performance NOT slow';

-- Prefix
SELECT * FROM docs WHERE docs MATCH 'perf*';

-- Column filter
SELECT * FROM docs WHERE docs MATCH 'title : sqlite';

-- NEAR (within N tokens, default 10)
SELECT * FROM docs WHERE docs MATCH 'NEAR(sqlite performance, 5)';

BM25 Ranking

-- Weighted ranking: title=10x weight, body=1x
SELECT *, bm25(docs, 10.0, 1.0) AS score
FROM docs WHERE docs MATCH 'query terms'
ORDER BY score;  -- lower = more relevant

-- Highlight matches in results
SELECT highlight(docs, 0, '<b>', '</b>') AS title,
       snippet(docs, 1, '<b>', '</b>', '...', 20) AS excerpt
FROM docs WHERE docs MATCH 'sqlite';

Performance Tuning

Recommended PRAGMA Settings

PRAGMA journal_mode = WAL;           -- concurrent reads + writes
PRAGMA synchronous = NORMAL;         -- safe with WAL, much faster than FULL
PRAGMA cache_size = -64000;          -- 64 MB (negative = KiB)
PRAGMA mmap_size = 268435456;        -- 256 MB memory-mapped I/O
PRAGMA busy_timeout = 5000;          -- 5s auto-retry on SQLITE_BUSY
PRAGMA temp_store = MEMORY;          -- temp tables in RAM
PRAGMA foreign_keys = ON;            -- enforce FK constraints
PRAGMA optimize;                     -- run on connection close

Transaction Batching

Individual inserts each trigger a separate transaction with fsync. Wrapping in explicit transactions provides ~20x speedup:

BEGIN;
INSERT INTO logs VALUES(1, 'event_a', datetime('now'));
INSERT INTO logs VALUES(2, 'event_b', datetime('now'));
-- ... batch 1,000-5,000 rows
COMMIT;

Prepared statements provide an additional ~5x speedup over repeated raw SQL by caching the query plan. They also prevent SQL injection.

Common Gotchas

1. WAL mode requires shared memory -- all processes must be on the same machine. WAL does not work over network filesystems (NFS, SMB). Use rollback journal mode for network-mounted databases.
2. synchronous = OFF is dangerous -- it skips fsync entirely. A power loss or OS crash can corrupt the database. Use NORMAL with WAL instead, which is nearly as fast and safe.
3. JSONB is SQLite-internal only -- it is not compatible with PostgreSQL JSONB or any other database's binary JSON format. Do not export JSONB BLOBs expecting cross-database compatibility.
4. FTS5 BM25 scores are negative -- lower (more negative) values indicate better matches. Sort ascending (ORDER BY score) not descending.
5. Auto-checkpoint can stall writers -- if the WAL grows beyond wal_autocheckpoint pages and a long-running reader holds an old snapshot, checkpoint cannot complete and the WAL keeps growing. Monitor WAL file size in production.
6. PRAGMA cache_size is per-connection -- each connection allocates its own page cache. With a connection pool of 10 and cache_size = -64000, total memory usage is up to 640 MB.
7. Contentless FTS5 returns NULL columns -- with content='', you cannot retrieve the original text from FTS5. Use external content tables or store content separately if you need to display results.
