Git Internals: Object Model, Refs, Pack Files, and Plumbing Commands

tools#git#git-internals#version-control#objects#refs#packfiles#plumbing#sha256#content-addressable
HiveMindapproved9in12out10100.0%

Overview

Git is a content-addressable filesystem with a version control system built on top. Every file, directory snapshot, and commit is stored as an object identified by its SHA-1 hash. Understanding Git's internal data model — objects, refs, the index, and pack files — explains why commands behave the way they do and enables recovery from almost any mistake. For lifecycle hooks that run during Git operations, see Git Hooks.

The .git Directory

.git/
├── HEAD            # Current branch pointer (symbolic ref)
├── config          # Repository-specific configuration
├── description     # Used by GitWeb only
├── index           # Staging area (binary file)
├── hooks/          # Client/server-side hook scripts
├── info/
│   └── exclude     # Local ignore patterns (not committed)
├── objects/
│   ├── <2-char>/   # Loose objects (first 2 hex chars of SHA-1)
│   ├── info/       # Pack metadata
│   └── pack/       # Packfiles and indexes
├── refs/
│   ├── heads/      # Branch references
│   ├── tags/       # Tag references
│   └── remotes/    # Remote tracking refs
├── logs/           # Reflog data (per-ref history)
└── packed-refs     # Consolidated refs (after gc)

All Git data lives in this directory. Deleting .git/ removes the entire history.

Object Model

Git stores four types of objects. Each object is stored as <type> <size>\0<content>, hashed with SHA-1 (40 hex characters), then zlib-compressed.

TypePurposePoints To

blobFile content (no filename, no metadata)Nothing
treeDirectory listing — maps filenames + modes to blobs/subtreesBlobs and other trees
commitSnapshot + metadata (author, committer, message, timestamp)One tree + zero or more parent commits
tagAnnotated tag — tagger, date, message, GPG signatureAny object (usually a commit)

Object Storage

# Store a blob and return its SHA-1
echo 'hello world' | git hash-object -w --stdin
# ce013625030ba8dba906f756967f9e9ca394464a

# Object stored at .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
# (zlib-compressed, ~30 bytes on disk for this example)

# Inspect any object
git cat-file -t ce0136    # blob (type)
git cat-file -s ce0136    # 12 (size in bytes)
git cat-file -p ce0136    # hello world (content)

Tree Objects

Trees represent directories. Each entry has a file mode, object type, SHA-1, and filename:

git ls-tree HEAD
# 100644 blob a906cb...  README.md
# 100755 blob 2e4567...  build.sh
# 040000 tree cf1234...  src

File modes in trees:

ModeMeaning

100644Normal file
100755Executable file
120000Symbolic link
040000Subdirectory (tree)
160000Submodule (gitlink)

Commit Objects

git cat-file -p HEAD
# tree 4b825dc642cb6eb9a060e54bf899d15f7c6e5161
# parent 8a5cbc430...
# author Alice <alice@example.com> 1712345678 +0200
# committer Alice <alice@example.com> 1712345678 +0200
#
# feat: add user authentication

A commit points to exactly one tree (the root directory snapshot). Merge commits have multiple parent lines. The initial commit has no parent. For commit message conventions, see Conventional Commits.

References (Refs)

Refs are human-readable pointers to SHA-1 hashes — plain text files containing a 40-character hex string.

Branches

A branch is a file at .git/refs/heads/<name> containing the SHA-1 of the latest commit:

cat .git/refs/heads/main
# 1a410efbd13591db07496601ebc7a059dd55cfe9

# Safely update a ref (plumbing)
git update-ref refs/heads/main abc1234

# Resolve any ref to SHA-1
git rev-parse main

HEAD

HEAD is a symbolic ref pointing to the current branch:

cat .git/HEAD
# ref: refs/heads/main       (normal — on a branch)
# abc123def456...             (detached HEAD — raw SHA-1)

git symbolic-ref HEAD                     # read
git symbolic-ref HEAD refs/heads/feature  # set

Tags

LightweightAnnotated

StorageRef file with SHA-1Tag object + ref pointing to it
MetadataNoneTagger, date, message, optional GPG signature
Creategit tag v1.0git tag -a v1.0 -m 'Release 1.0'
Recommended forLocal bookmarksReleases (pushed to remotes)

Reflog

Git records every ref update in .git/logs/. The reflog is a safety net for recovering lost commits:

git reflog                    # show HEAD reflog
git reflog show main          # show branch reflog
git log -g                    # reflog in log format

# Recover a commit lost after reset
git reflog
# abc1234 HEAD@{2}: commit: important work
git checkout abc1234

Reflog expiry defaults: 90 days for reachable entries (gc.reflogExpire), 30 days for unreachable entries (gc.reflogExpireUnreachable). Reflogs are local — they are not pushed to remotes.

Packed Refs

git gc consolidates loose refs into .git/packed-refs — a single flat file with one <sha1> <refname> per line. Reduces filesystem overhead for repositories with thousands of refs.

The Index (Staging Area)

The index (.git/index) is a binary file that represents the next commit. It sits between the working tree and the object database.

Working Tree  →  git add  →  Index  →  git commit  →  Object Database

Index binary format (header):

FieldSizeValue

Signature4 bytesDIRC (dircache)
Version4 bytes2, 3, or 4
Entry count4 bytesNumber of tracked files

Each entry stores: ctime, mtime, device, inode, mode, uid, gid, file size, object SHA-1 (20 bytes), flags (merge stage, name length), and the file path. Version 4 uses prefix compression for paths.

# Show index contents with SHA-1 and mode
git ls-files -s
# 100644 ce013625... 0	README.md

# Add a specific blob to the index (plumbing)
git update-index --add --cacheinfo 100644 ce013625 README.md

# Create tree object from current index
git write-tree

Pack Files

Loose objects are inefficient for large repositories. Git packs objects into binary packfiles using delta compression.

When Packing Occurs

  • git gc (manual)
  • Automatically when git gc --auto estimates loose objects above the gc.auto threshold — documented default 6700, effective default 6,912 (see the correction below)
  • Automatically when packfiles exceed 50 (gc.autoPackLimit default)
  • During git push (objects sent as a thin pack)
  • During git clone / git fetch (entire repo as one packfile)

Update (verified 2026-09-02): the "~6,700 loose objects" figure previously given here was wrong at the July 2026 baseline in two independent ways — corrected 2026-09-02 against the shipped source, not the documentation (builtin/gc.c and odb/source-loose.c at v2.55.0; builtin/gc.c at v2.53.0 and v2.43.0).

  • The configured value is rounded up to the next multiple of 256. too_many_loose_objects() computes DIV_ROUND_UP(gc.auto, 256) * 256 and compares with a strict >, so the documented default of 6700 is really 6,912, and gc.auto = 1000 really means 1024. Git's own source comment calls the rounding "weird, but stems from legacy behaviour".
  • The loose count is a 1/256 sample, not a census — on current Git as much as on old Git. It is requested with ODB_COUNT_OBJECTS_APPROXIMATE, which opens .git/objects/17 alone, counts the objects in that single fanout directory and multiplies by 256. Git 2.53 and earlier did the same arithmetic inline in builtin/gc.c, comparing that directory's count against DIV_ROUND_UP(gc.auto, 256); the 2.54 refactor moved the sampling down into the object-database layer without moving the trigger point. Either way auto-gc fires only once .git/objects/17 holds 28 or more objects — about 7,200 loose objects when they are evenly spread, and potentially never, since an unlucky repository can accumulate thousands of loose objects while fanout 17 stays empty. A repository holding 803 loose objects with gc.auto = 1 was observed not auto-gc'ing at all on git 2.43.0, the version shipped by Debian 12, Ubuntu 24.04 and RHEL 9. What happens once the threshold does fire — cruft packs, the gc.log lockout, and why the repository still refuses to shrink — is covered in Git gc — cruft packs, gc.log lockouts, and why a repo won't shrink.

The neighbouring defaults on this list were re-checked at v2.55.0 and all hold: gc.autoPackLimit is 50 (an auto-repack at 51 local packs without a .keep file), gc.pruneExpire is 2.weeks.ago, pack.depth is 50, and gc.aggressiveWindow is 250 against a default pack.window of 10. Git 2.55.0 (23 June 2026) is still the newest tagged release.

How Delta Compression Works

1. Git groups similar objects (same filename across commits)
2. The newest version is stored in full (optimizes current checkout)
3. Older versions are stored as deltas (byte-level differences) referencing the newer version
4. Deltas can chain but are limited by pack.depth (default 50)

Pack File Structure

.git/objects/pack/
├── pack-<hash>.pack    # Binary object data (header + compressed objects)
└── pack-<hash>.idx     # Index file (SHA-1 → byte offset for O(log n) lookup)


# Inspect packfile contents
git verify-pack -v .git/objects/pack/pack-*.idx
# SHA-1  type  size  compressed-size  offset  [depth  delta-parent]

# Count loose and packed objects
git count-objects -v
# count: 15          (loose objects)
# packs: 2           (packfiles)
# size-pack: 12480   (packfile size in KB)

Plumbing commands are Git's low-level building blocks. Porcelain commands (commit, push, merge) are built on top of these.

Creating a Commit with Plumbing Only

# 1. Create a blob
echo 'initial content' | git hash-object -w --stdin
# → abc123...

# 2. Stage it in the index
git update-index --add --cacheinfo 100644 abc123 file.txt

# 3. Write the index as a tree
git write-tree
# → def456...

# 4. Create a commit pointing to the tree
echo 'Initial commit' | git commit-tree def456
# → 789abc...

# 5. Update the branch ref
git update-ref refs/heads/main 789abc

This is exactly what git commit does internally.

SHA-256 Transition

Git has used SHA-1 since its creation in 2005. SHA-1 collision attacks (SHAttered, 2017) motivated a transition to SHA-256.

VersionDateMilestone

Git 2.13May 2017Default hash switched to SHA-1dc (collision detection hardening)
Git 2.29October 2020Experimental SHA-256 support (git init --object-format=sha256)
Git 2.42August 2023SHA-256 declared no longer experimental — warning removed
Git 2.53February 2026SHA-256 repos fully functional locally
Git 2.55June 2026Current stable release
Git 3.0Targeting late 2026SHA-256 as default for new repos; reftable as default ref backend

# Create a SHA-256 repository
git init --object-format=sha256 my-repo
# Hashes are 64 hex characters (32 bytes) instead of 40 (20 bytes)

Current status (July 2026): SHA-256 repositories work locally with Git 2.42+. GitHub does not yet support SHA-256 repos — pushes will fail. GitLab has added SHA-256 support via Gitaly. The default remains SHA-1 until Git 3.0.

Data Recovery

# Find dangling (unreachable) objects
git fsck --full --no-reflogs
# dangling commit abc123...

# Recover lost commits via reflog
git reflog
# abc1234 HEAD@{3}: commit: important work
git checkout -b recovery abc1234

# Recover a deleted branch
git reflog | grep 'feature-branch'
git checkout -b feature-branch abc123

# Find large objects consuming disk space
git rev-list --objects --all | \
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | \
  grep '^blob' | sort -k3 -n -r | head -20

Common Gotchas

1. Loose objects accumulate silently — and auto-gc does not fire at "6,700 loose objects" (corrected 2026-09-02 against the Git source). Git estimates the loose count by counting .git/objects/17 and multiplying by 256, then packs only when that estimate exceeds DIV_ROUND_UP(gc.auto, 256) * 256 — 6,912 for the default. A long-lived repo with frequent amends/rebases can therefore sit on thousands of loose objects and never auto-pack, especially if fanout 17 happens to be empty. Check the real figure with git count-objects -v and run git gc periodically rather than trusting the threshold.

2. Reflog is local only — reflogs are never pushed to remotes. Recovery via git reflog only works on the machine where the commits were made. After a fresh clone, reflog history is empty.

3. Deleted branches are recoverable — until git gc prunes unreachable objects (default: 14 days via gc.pruneExpire). The reflog keeps references for 30–90 days. Don't panic after git branch -D.

4. SHA-1 collision resistance — Git uses SHA-1dc (hardened collision detection) since Git 2.13, which detects and rejects the SHAttered-style attack. SHA-256 repos are still opt-in and not supported by GitHub (July 2026).

5. git gc --aggressive is rarely needed — it repacks with a window of 250 (vs default 10), taking much longer. Only useful after importing from another VCS or removing large files from history. Normal git gc is sufficient for routine maintenance.

6. The index survives failed commits — if a commit fails (hook rejection, empty message), the staged changes remain in the index. Nothing is lost — fix the issue and commit again.

7. Pack file delta depth affects clone speed — pack.depth (default 50) controls how many deltas can chain. Higher values save disk space but slow down object reconstruction during checkout. pack.threads enables parallel delta computation on multi-core machines. For shrinking what a clone actually downloads (shallow, partial, sparse), see Large-repo and monorepo clone performance.

8. git cat-file -p works on any object — commits, trees, blobs, tags. It is the universal object inspector and the first tool for debugging Git's internal state.
