PostgreSQL Physical Streaming Replication: WAL Shipping, Replication Slots, Hot Standby, and What Changed in PG 18

Overview

PostgreSQL physical streaming replication ships the binary Write-Ahead Log (WAL) from a primary to one or more standbys, reproducing the primary cluster byte-for-byte. It powers high-availability pairs, read scaling, and point-in-time recovery setups — and is distinct from logical replication, which ships row-level changes at the SQL layer.

This entry covers PostgreSQL 14–18 (all currently supported majors as of April 2026), with a focus on PG 17/18 changes: async I/O (io_method), idle_replication_slot_timeout, max_active_replication_origins, WAL I/O in pg_stat_io, and wire protocol 3.2.

Version Baseline

Update (verified 2026-07-23): the May 2026 minor round has shipped; PG 18 is at 18.4 (PG 19 is in beta, GA expected ~September 2026). Majors and EOL dates below are unchanged.

Update (verified 2026-08-22): the August round superseded that. On 2026-08-13 upstream released 18.6, 17.11, 16.15, 15.19 and 14.24, plus PostgreSQL 19 Beta 3 — the Latest Minor column below has been refreshed to match. Two things a replication operator should carry out of this round:

  • There is no PostgreSQL 18.5. The 18.6 release notes state "18.5 was never released, due to a regression discovered post-wrap", they describe their own fixes as coming "from 18.4", and postgresql.org/docs/release/18.5/ 404s. Any standby-build automation that pins or asserts an 18.5 tarball will fail to find one; 18.4 goes straight to 18.6.
  • 18.6 fixes an incremental-backup correctness bug. WAL logging of operations that clear bits in a table's visibility map was incomplete: those VM changes "were missed by the WAL summarizer, potentially leading to incorrect incremental backups", and full-page images of those VM pages were not logged when needed, so torn page writes could go uncorrected and later produce wrong results from index-only scans (Melanie Plageman, Andres Freund). If you run pg_basebackup --incremental / summarize_wal, this is the round to take. 18.6 also stops the WAL summarizer getting stuck at a timeline switch (Robert Haas), fixes a race in timeline selection that made logical decoding on a standby fail with "requested WAL segment has already been removed" during promotion (Bertrand Drouvot), stops pg_stat_wal_receiver transiently showing the unsanitised connection string during a timeline jump (Chao Li), clears the stale pg_stat_progress_basebackup entry left behind by a failed backup, and prevents an infinite loop in pg_combinebackup when a source file is shorter than expected. From 18.4, still worth knowing: a standby following an older-minor primary could crash-loop on "could not access status of transaction" (checkpoint-replay vs multixact race, Heikki Linnakangas), and free-space-map changes during recovery were not marked dirty when checksums are enabled, so a promoted standby could carry a badly wrong FSM until updates repaired it.

Logical vs Physical Replication

AspectPhysical (this entry)Logical

What shipsRaw WAL bytesDecoded row changes (INSERT/UPDATE/DELETE/TRUNCATE)
GranularityWhole clusterPer-table (via PUBLICATION)
DDLReplicated automaticallyNot replicated; must run DDL on both sides
Cross-versionNo — standby must match primary major (minor OK)Yes — cross-major upgrades supported
Standby writableNo (read-only queries only)Yes (subscriber is a full primary)
wal_levelreplica or higherlogical
Primary use caseHA failover, read scaling, PITRSelective replication, blue/green upgrades, fan-out

Physical replication preserves the full cluster state (indexes, sequences, system catalogs) bit-perfectly; logical replication is semantically aware and more flexible but cannot act as a read replica of the entire cluster.

Architecture

Data flow on a healthy pair:

1. On the primary, each transaction writes WAL records to pg_wal/ (16 MB segments by default) and fsyncs at commit.
2. A walsender backend process (one per standby) reads from pg_wal and streams to the standby over a dedicated replication connection (port 5432, no separate port).
3. The standby's walreceiver background process receives, writes, and fsyncs WAL to its own pg_wal/.
4. A startup (recovery) process replays WAL into the standby's data files.
5. The standby advertises four LSN positions back to the primary: write_lsn, flush_lsn, replay_lsn, and (with hot_standby_feedback) its oldest visible xmin.

Standby identity is signalled by a standby.signal file in the data directory (PG 12+ — the old recovery.conf is gone). Connection config lives in postgresql.auto.conf (written by pg_basebackup -R) or postgresql.conf.

The presence of a standby.signal file in PGDATA is what makes the node a standby — without it, the node starts as a primary.

pg_basebackup — Creating the Standby

pg_basebackup is the standard way to seed a new standby. It takes an online, consistent physical snapshot while streaming WAL so the backup is restorable without the archive.

pg_basebackup \
  --host=primary.example.com \
  --port=5432 \
  --username=replicator \
  --pgdata=/var/lib/postgresql/18/standby \
  --write-recovery-conf \
  --wal-method=stream \
  --create-slot --slot=standby1_slot \
  --checkpoint=fast \
  --progress --verbose

Flag-by-flag:

FlagEffect

-R / --write-recovery-confWrites standby.signal and appends primary_conninfo + primary_slot_name to postgresql.auto.conf. The backup is immediately startable as a standby.
-X stream (default)Opens a second replication connection to stream WAL in parallel with the base backup. Ensures no WAL is lost between backup start and end.
-X fetchFetches WAL only at the end. Requires wal_keep_size large enough; fragile.
-X noneSkips WAL; only useful if you will manually provide it.
-C --slot=<name>Creates a permanent physical slot on the primary with the given name. Without -C, -X stream creates a temporary slot that disappears at backup end — fine for ad-hoc backup, not for setting up a long-lived standby.
-c fastImmediate CHECKPOINT on the primary at backup start (short spike in I/O vs. spread which is gentler).
-F tar -zProduces a single compressed tar per tablespace — convenient for shipping over the network. Use default -F plain if the backup will be restored in place.
-Z zstd:7PG 15+ supports gzip, lz4, zstd with client-side or server-side compression (--compress=server-zstd:7).

After the backup completes, start PostgreSQL on the standby; it will connect via primary_conninfo, attach to the slot, and begin streaming.

Replication Slots (Physical)

A physical replication slot is a named, persistent bookmark on the primary that records the oldest WAL position still needed by a standby. The primary will not recycle WAL past that point until the standby acknowledges it — or until you drop the slot.

SELECT pg_create_physical_replication_slot('standby1_slot');

SELECT slot_name, slot_type, active, restart_lsn,
       pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS retained_bytes
FROM pg_replication_slots;

Slots are load-bearing: without a slot (or sufficient wal_keep_size), a standby that disconnects for longer than the WAL-retention window will fall off a cliff and need to be rebuilt via pg_basebackup or pg_rewind.

Slots are also dangerous: an abandoned slot pins WAL indefinitely and fills pg_wal, eventually stopping the primary. Mitigations:

  • Always bound slots with max_slot_wal_keep_size (default -1 means unbounded — change it).
  • PG 18+: set idle_replication_slot_timeout (e.g. 1h) to auto-invalidate slots that have had no walsender activity.
  • Monitor pg_replication_slots.active = false with restart_lsn falling behind pg_current_wal_lsn().
  • Drop dead slots explicitly: SELECT pg_drop_replication_slot('standby1_slot');

Once a slot is invalidated (via timeout or size limit), it reports invalidation_reason in pg_replication_slots (PG 16+) — the standby cannot reattach and must be rebuilt.

Synchronous Replication

By default, streaming is asynchronous: the primary acknowledges a commit as soon as WAL hits its own disk, regardless of what the standby has. A primary crash can lose in-flight transactions.

Synchronous replication makes the primary wait for standby acknowledgement before returning COMMIT to the client.

synchronous_commit levels

LevelPrimary waits forData-loss window on primary crash

offNothing past WAL bufferLast ~200 ms of commits
localPrimary disk fsync0 (single-node guarantee)
remote_writeStandby OS write (not fsync)Window if both primary and standby OS crash simultaneously
on (default)Standby disk fsync0 (if ≥ 1 sync standby is up)
remote_applyStandby has replayed the commit0; readers on the standby see the row

remote_apply is the only level that guarantees read-your-writes when routing reads to the standby. It also adds the most latency (one round-trip plus replay time).

synchronous_standby_names

Names the standbys whose acks count. application_name in each standby's primary_conninfo determines its name.

# Priority (FIRST N): first N listed standbys are synchronous, rest are potential
synchronous_standby_names = 'FIRST 1 (standby1, standby2, standby3)'

# Quorum (ANY N): commit returns when any N of the group ack
synchronous_standby_names = 'ANY 2 (standby1, standby2, standby3)'

Critical behavior: if every named synchronous standby is down, the primary blocks all writes indefinitely. This is a correctness-over-availability trade — a crash-consistent copy is always reachable. If you cannot tolerate blocking, use ANY N with more standbys than N, or run asynchronous replication with a failover tool that fences the primary.

Hot Standby and Query Conflicts

A standby is read-only but fully queryable (hot_standby = on, which is the default). Because recovery is single-threaded and can conflict with reader transactions, PostgreSQL sometimes must cancel queries.

Conflict sources:

1. AccessExclusiveLock from DDL on the primary (e.g. ALTER TABLE).
2. Tablespace/database drops on the primary.
3. Cleanup records from VACUUM removing rows still visible to a standby transaction.
4. Snapshot too old — primary's oldest xmin advances past what a standby transaction needs (MVCC; see VACUUM entry).

When conflict exceeds max_standby_streaming_delay, the standby cancels the offending query:

ERROR:  canceling statement due to conflict with recovery
DETAIL:  User query might have needed to see row versions that must be removed.

hot_standby_feedback = on makes the standby ship its oldest xmin upstream; the primary's autovacuum then respects it and won't clean rows still visible to standby readers.

The tradeoff: that xmin pins dead rows on the primary, causing table bloat exactly proportional to the longest-running standby query. Disconnect a standby with feedback enabled while running a long analytical query, reconnect later, and you have a bloated primary.

Rules of thumb:

  • HA standby with no analytics: hot_standby_feedback=off, max_standby_streaming_delay=30s.
  • Read-replica for dashboards: hot_standby_feedback=on, keep queries short, monitor primary bloat.
  • Dedicated analytics standby: consider max_standby_streaming_delay=-1 (wait forever) and accept replication lag — but then the standby is not HA-usable.

Inspect conflicts:

SELECT datname, confl_tablespace, confl_lock, confl_snapshot,
       confl_bufferpin, confl_deadlock
FROM pg_stat_database_conflicts;

Monitoring

Five critical views/functions:

-- On primary: who's connected, how far behind each is
SELECT client_addr, application_name, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), write_lsn)   AS write_lag_bytes,
       pg_wal_lsn_diff(pg_current_wal_lsn(), flush_lsn)   AS flush_lag_bytes,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)  AS replay_lag_bytes,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- On standby: receiver status
SELECT status, receive_start_lsn, written_lsn, flushed_lsn,
       latest_end_lsn, latest_end_time, last_msg_send_time, last_msg_receipt_time
FROM pg_stat_wal_receiver;

-- On primary: slot retention
SELECT slot_name, active, wal_status, restart_lsn, safe_wal_size,
       invalidation_reason  -- PG 16+
FROM pg_replication_slots;

-- Quick lag-in-bytes probe
SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS bytes_behind
FROM pg_stat_replication;

-- On standby: is recovery ongoing?
SELECT pg_is_in_recovery(), pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(),
       pg_last_xact_replay_timestamp();

Key columns:

  • state — one of startup, catchup, streaming. Only streaming is healthy.
  • sync_state — async, potential, sync, quorum. potential means the standby could become sync if the current sync one fails.
  • write_lag / flush_lag / replay_lag — PG 10+ interval columns (time, not bytes). Use these to alert on lag in time, which is what users feel.
  • safe_wal_size (PG 13+) — remaining bytes before max_slot_wal_keep_size invalidates the slot. When this drops to zero, you are seconds away from a dead standby.

PG 18 adds WAL I/O rows to pg_stat_io — you can now see WAL-sender and WAL-receiver I/O latency and wait events directly, rather than inferring from pg_stat_wal. For the query-level half of the picture — which statements a replay-lag spike traces back to, and primary-vs-standby query attribution — pair these views with pg_stat_statements.

Failover

Graceful promote (planned)

-- On the standby you want to become the new primary:
SELECT pg_promote(wait => true, wait_seconds => 60);

Or from shell:

pg_ctl promote -D /var/lib/postgresql/18/standby

pg_promote() returns true once the standby has finished recovery and is accepting writes. It's the only promotion mechanism you should use in scripts — it's transactional and returns a usable status.

Repoint remaining standbys

After promotion, other standbys are still pointed at the old primary. Restart each with updated primary_conninfo and primary_slot_name (create a new slot on the new primary first). Set recovery_target_timeline = 'latest' (default since PG 12) so they follow the new timeline automatically.

pg_rewind — salvage the old primary

If the old primary survived (e.g. network partition, not a disk loss), you can avoid a full pg_basebackup rebuild:

pg_rewind \
  --target-pgdata=/var/lib/postgresql/18/old_primary \
  --source-server='host=new-primary user=replicator' \
  --progress

pg_rewind replays diverged blocks from the new primary's WAL so the old primary's data directory matches the new timeline. Requirements: wal_log_hints = on (or data checksums, which PG 18 enables by default in new clusters), and the source must retain enough WAL to cover the divergence point.

Automation

PostgreSQL ships no built-in failover orchestrator. In production, pair streaming replication with one of:

  • Patroni (Zalando, most common open-source choice; uses etcd/Consul/ZK for leader election) — the HA layer that orchestrates physical streaming replication, with DCS, watchdog and sync modes
  • repmgr (2ndQuadrant/EDB)
  • pg_auto_failover (Microsoft/Citus)
  • Cloud-managed Postgres (RDS/Aurora, Cloud SQL, Azure, Neon, Supabase) which handle failover for you

Without a fencing-aware orchestrator, you will eventually split-brain. Do not build your own.

What Changed in PG 18

Released 2025-09-25. Replication-relevant highlights:

1. idle_replication_slot_timeout — new GUC, seconds; auto-invalidates slots with no walsender activity. Finally closes the #1 operational footgun (abandoned slots pinning WAL).
2. max_active_replication_origins — separates origin tracking from max_replication_slots, letting you track many logical origins without inflating slot count.
3. WAL I/O in pg_stat_io — WAL-sender and WAL-receiver rows; buffer access counts and wait events without inference.
4. Asynchronous I/O subsystem — new io_method (worker, io_uring, sync); up to ~3× faster reads for sequential scans, bitmap heap scans, and vacuum. WAL replay benefits indirectly via faster buffer reads on standbys.
5. Wire protocol 3.2 — first bump since PG 7.4 (2003). Backwards-compatible; replication connections negotiate automatically.
6. Data checksums on by default in new clusters. pg_rewind works without wal_log_hints when checksums are on.
7. pg_combinebackup --link — hard-link incrementals instead of copying; much faster merge.
8. pg_basebackup accepts zstd server-side compression (already in 15; tuning options expanded).
9. Faster major-version upgrades — pg_upgrade --swap + preserved planner stats. Not replication per se, but cuts standby-rebuild time during majors.
10. MD5 auth deprecated — replication roles should already use scram-sha-256; plan removal.

Minimum Production Recipe

One primary + one synchronous standby + one async standby for reads:

# 1. On primary: enable replication
psql -c "ALTER SYSTEM SET wal_level='replica';"
psql -c "ALTER SYSTEM SET max_wal_senders=10;"
psql -c "ALTER SYSTEM SET max_replication_slots=10;"
psql -c "ALTER SYSTEM SET max_slot_wal_keep_size='100GB';"
psql -c "ALTER SYSTEM SET idle_replication_slot_timeout='1h';"   # PG 18+
psql -c "ALTER SYSTEM SET synchronous_standby_names='FIRST 1 (standby_sync)';"
psql -c "ALTER SYSTEM SET wal_sender_timeout='10s';"
psql -c "CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'redacted';"
# Append to pg_hba.conf:
#   host  replication  replicator  10.0.0.0/8  scram-sha-256
sudo systemctl restart postgresql

# 2. On each standby: seed with pg_basebackup
sudo -u postgres pg_basebackup \
  -h primary.internal -U replicator \
  -D /var/lib/postgresql/18/main \
  -R -X stream -C -S standby_sync_slot \
  -c fast --progress

# 3. Add application_name to the standby's postgresql.auto.conf
#   primary_conninfo = '... application_name=standby_sync ...'
sudo systemctl start postgresql

# 4. Verify on primary
psql -c "SELECT application_name, state, sync_state FROM pg_stat_replication;"

Always test the failover drill on a staging pair before depending on it. Every production outage where "failover didn't work" traces back to never having tested it.

Gotchas

1. wal_level=minimal breaks streaming silently. Some tuning guides still suggest minimal for write performance; it disables replication entirely. Always verify SHOW wal_level; returns replica or logical.

2. Slots without a size bound will fill the disk. max_slot_wal_keep_size=-1 is the default and it means unlimited. A stopped standby will grow pg_wal until the primary's filesystem is full and the database stops. Set a bound.

3. Unused slots pin WAL forever. Dropping a standby without DROP_REPLICATION_SLOT is the same footgun. PG 18's idle_replication_slot_timeout helps but isn't on by default.

4. Synchronous with one standby = single point of failure. synchronous_standby_names='FIRST 1 (s1)' blocks all writes if s1 is down. Use ANY 1 (s1, s2) with two standbys, or accept async.

5. application_name must match synchronous_standby_names. If primary_conninfo on the standby sets application_name=standby01 and the primary expects standby_sync, the standby will connect as async and you'll think sync replication works but it silently doesn't. Check pg_stat_replication.sync_state.

6. Major-version mismatch fails to start. Physical replication requires the exact same major version (14 ↔ 14). Minor versions may differ but the primary should match or lead. Use logical replication or pg_upgrade for majors.

7. Same architecture / endianness / page layout required. You cannot stream x86 → arm64 across major boundaries where page format differs. When in doubt, pg_basebackup will refuse.

8. pg_basebackup -X fetch without wal_keep_size can silently miss WAL. Prefer the default -X stream.

9. hot_standby_feedback=on bloats the primary. Convenient for analytics replicas but costs dead-row cleanup latency. Combine with aggressive autovacuum settings and short standby queries.

10. max_standby_streaming_delay=-1 can stop replication. Waiting forever for a query means the standby never catches up. Use a large finite value (e.g. 300s) instead of -1.

11. Failing to set recovery_target_timeline='latest' (default since PG 12, but worth verifying) means a standby will not follow a newly-promoted primary after failover.

12. Promoted primary missing a new slot for old standbys. After promote, the new primary has no slots for the former siblings. Create them before reattaching: SELECT pg_create_physical_replication_slot('standby2_slot');.

13. wal_sender_timeout=60s is too slow for most HA setups. Lower to 10s (match wal_receiver_timeout) so walsenders notice a dead standby and you can rotate sync.

14. pgBouncer in transaction-pool mode breaks replication routing. See the pgBouncer entry. Route replication connections directly to postgres, not through pgBouncer.

15. Cascaded standbys cannot be synchronous. Only direct standbys count toward synchronous_standby_names. Cascading relays are always async.

16. primary_conninfo in postgresql.conf beats postgresql.auto.conf. ALTER SYSTEM writes to .auto.conf, which has the lower precedence of the two. If both are set, the postgresql.conf value wins and ALTER SYSTEM appears to be ignored. Consolidate.

17. Replication slot names cannot contain hyphens in some drivers. Stick to a-z, 0-9, and underscore — PostgreSQL itself allows more, but downstream tooling sometimes doesn't.

18. pg_rewind requires wal_log_hints=on or data checksums. PG 18 enables checksums by default in new clusters; older clusters created without them need wal_log_hints=on (set at initdb time, cannot change later without pg_checksums).

19. Split-brain with DIY failover. Do not script your own promote-on-timeout. Use a consensus-based orchestrator (Patroni + etcd). The cost of split-brain (two primaries accepting writes) exceeds any convenience gained.

20. synchronous_commit='remote_apply' adds replay latency to every commit. It guarantees read-after-write on the standby but can be 10–100× slower than on. Use it only where you actually route reads to the standby and need that guarantee.
