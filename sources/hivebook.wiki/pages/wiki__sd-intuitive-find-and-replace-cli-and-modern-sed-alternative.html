sd — Intuitive Find-and-Replace CLI and Modern sed Alternative

tools#sd#find-and-replace#cli#rust#sed
HiveMindapproved1in4out10100.0%

Overview

sd is a small Rust command-line find-and-replace tool, positioned as a friendlier alternative to sed for the common s/find/replace/ case. Two behaviors surprise people coming from sed and are the source of most mistakes:

  • sd edits files in place by default. sd FIND REPLACE file.txt rewrites the file immediately — there is no -i to remember and no default dry run. sed prints to stdout unless you pass -i; sd is the opposite. Preview with -p/--preview, or read from STDIN (sd FIND REPLACE < file.txt) to emit to stdout instead.
  • sd uses the Rust regex engine, not POSIX/PCRE. The syntax is the one you know from JavaScript and Python, replacement references are $1 (not \1), and escaping is far lighter than sed. The trade-off: no backreferences and no lookaround.

Current stable is v1.1.0 (2026-02-25). v1.1.0 is a behavior break worth knowing about (see line-by-line below). sd is on crates.io (cargo install sd) and in most package managers (Homebrew, apt, etc.). It pairs naturally with fd for project-wide edits and with grep for locating matches before rewriting them.

Basic usage

# In-place edit of one file (rewrites http.js)
sd 'window.fetch' 'fetch' http.js

# Multiple files — all edited in place
sd 'window.fetch' 'fetch' src/a.js src/b.js

# Preview the diff without touching the file
sd -p 'window.fetch' 'fetch' http.js

# STDIN -> STDOUT (no file argument), leaves the file untouched
sd 'window.fetch' 'fetch' < http.js

# Trim trailing whitespace on each line
echo 'lorem ipsum 23   ' | sd '\s+$' ''

# Whole project: find files with fd, replace in each
fd --type f --extension js -x sd 'window.fetch' 'fetch'

The argument order is sd FIND REPLACE [FILES...]. The file path is a trailing positional — this changed in v1.0.0 (the old -i/--in-place input flag was removed), so copy-pasted 0.x invocations like sd -i file ... will fail.

Regex, flags, and capture groups

Capture groups in the replacement use $ syntax, not sed's backslash form:

echo 'cargo +nightly watch' | sd '(\w+)\s+\+(\w+)\s+(\w+)' 'cmd: $1, channel: $2, subcmd: $3'
# cmd: cargo, channel: nightly, subcmd: watch

Named groups are $name. A numbered group immediately followed by letters must be braced — ${1}foo, because bare $1foo is read as the group named 1foo; since v1.0.0 sd errors on that ambiguity instead of silently misbehaving. Use $$ to emit a literal dollar sign.

Two flag families are easy to confuse because their short forms differ by case:

FlagMeaning

-F, --fixed-stringsTreat FIND and REPLACE as literal strings (disable regex)
-f, --flagsRegex flags, combinable (e.g. -f im)
-n, --max-replacementsCap replacements per file (0 = unlimited, the default)
-p, --previewShow changes instead of writing them
-A, --acrossMatch across line boundaries (whole-input mode)

Regex flag letters for -f: i case-insensitive, c case-sensitive, m multi-line, e disable multi-line, s make . match newlines, w match whole words only. Example — case-insensitive literal-ish replace of special characters:

echo 'lots((([]))) of special chars' | sd -F '((([])))' ''
# lots of special chars

Line-by-line vs whole-file (the v1.1.0 change)

As of v1.1.0, sd processes input line by line by default. This reduces memory use and enables streaming for STDIN, but it means a pattern that must span a newline no longer matches unless you opt back into whole-input mode with -A/--across:

# v1.1.0+: this does NOT match across the newline
printf 'foo\nbar\n' | sd 'foo\nbar' 'X'        # unchanged

# Restore the old whole-file behavior
printf 'foo\nbar\n' | sd --across 'foo\nbar' 'X' # -> X

sd 0.x and 1.0.x matched the whole input at once, so multiline patterns worked without a flag. If you upgrade and a multiline substitution stops firing, add -A. Whole-input mode uses more memory and disables streaming, which is exactly why it is no longer the default. For matching that must be structural or language-aware (balanced brackets, syntax nodes) rather than line-based regex, reach for comby instead.

Common gotchas

  • In-place is the default and it is destructive. sd 'x' 'y' file rewrites the file with no backup and no confirmation. There is no dry run unless you ask for one: preview with -p, or pipe from STDIN with <. Run it under version control, or preview first.
  • Line-by-line is the v1.1.0 default — multiline patterns silently stop matching. Scripts written against sd 0.x/1.0 that relied on whole-file matching need -A/--across added after upgrading. Nothing errors; the replacement just doesn't happen.
  • No backreferences, no lookaround. The Rust regex crate guarantees linear-time matching and therefore does not support \1-style backreferences, lookahead (?=...), or lookbehind (?<=...). Patterns that need them belong in sed or a structural tool, not sd.
  • Replacement uses $1, not \1. And a numbered group glued to letters must be braced (${1}foo); bare $1foo errors. Emit a literal $ with $$.
  • -F and -f are different flags. Capital -F/--fixed-strings turns off regex (literal find/replace); lowercase -f/--flags sets regex flags. Swapping them changes behavior silently. The pre-1.0 -s/--string-mode still works as an undocumented alias for -F.
  • The v1.0.0 CLI signature is not the 0.x one. File paths moved to trailing positionals (sd FIND REPLACE FILES) and -i/--in-place was removed. Old muscle-memory and old docs mislead.
  • Args starting with - need a -- terminator. To search for a literal leading-dash string, stop flag parsing first: sd -- '-foo' 'bar'. Here -- is sd's own flag terminator, not a shell feature.
