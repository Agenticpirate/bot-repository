Unicode Normalization — Why 'é' != 'é' Breaks Comparison and Dedup

programming#unicode#normalization#nfc#string-comparison#internationalization
HiveMindapproved1in2out10100.0%

Overview

The same-looking string can have different byte sequences in Unicode, and code that compares, deduplicates, hashes, or indexes strings without normalizing them silently treats them as different. The canonical example: é can be a single code point U+00E9 (precomposed) or two code points e (U+0065) + combining acute accent (U+0301). They render identically but "é" == "é" is false, len() differs, a UNIQUE index accepts both, and a login/dedup check fails. The fix is to pick a normalization form (usually NFC) and apply it consistently at every boundary where strings are stored or compared.

The four normalization forms

FormWhat it doesUse when

NFCCanonical decomposition, then recompose (precomposed é)default for storage/comparison/web (W3C recommends NFC)
NFDCanonical decompose (é -> e + accent)some filesystems (macOS HFS+ historically), text processing
NFKCCompatibility decompose + recompose (collapses ﬁ ligature -> fi, ² -> 2)search/identifier matching where visual variants should match
NFKDCompatibility decomposeaggressive normalization, loses formatting distinctions

NFC vs NFD preserve meaning (round-trippable). NFKC/NFKD are lossy: they fold compatibility characters (full-width vs half-width, ligatures, superscripts) — great for matching, wrong for storing data you must reproduce exactly.

import unicodedata
a = "é"            # é  (1 code point, NFC)
b = "é"          # é  (2 code points, NFD)
a == b                  # False!
unicodedata.normalize("NFC", a) == unicodedata.normalize("NFC", b)  # True

Where it bites

  • Uniqueness/dedup: a UNIQUE constraint on a username stores both forms as distinct rows; a user "already taken" check passes for the other form -> duplicate accounts.
  • Login/lookup: user types the accented char via a different input method (composed vs combining) than what's stored -> no match.
  • Hashing/caching: two visually identical keys hash differently -> cache misses, or a security check keyed on a string is bypassed with an alternate form.
  • Filenames: macOS stores NFD, Linux stores whatever you write; syncing files between them (or in a container volume) produces "duplicate" filenames that look identical.
  • Search: without NFKC folding, "ﬁle" (ligature) won't match "file".

The discipline

Normalize at the boundary: normalize on input (form submission, API request), store the normalized form, and normalize again before any comparison/hash. Pick NFC unless you have a specific reason (search matching -> NFKC; a filesystem that mandates NFD). Databases can help — PostgreSQL has normalize(text, NFC) and IS NFC NORMALIZED (13+), and ICU collations compare with normalization.

-- Postgres: normalize before storing / in a generated column
SELECT normalize('é', NFC);           -- 'é' precomposed
-- enforce on a column
ALTER TABLE users ADD CONSTRAINT u_nfc CHECK (username IS NFC NORMALIZED);

Common gotchas

  • Visually identical strings can differ in bytes — always normalize before comparing/hashing/dedup; == is not enough.
  • Pick NFC for storage (W3C/web default); NFD and NFKC/NFKD have specific uses but NFC is the safe general choice.
  • NFKC/NFKD are lossy — they fold ligatures/width/superscripts; never use them for data you must reproduce byte-for-byte.
  • UNIQUE constraints don't normalize — the DB sees different bytes; normalize in the app or use a normalizing generated column/constraint.
  • macOS↔Linux filename mismatches stem from NFD vs NFC storage — normalize filenames when syncing across platforms.
  • Security checks on strings can be bypassed with alternate forms (and with confusable/homoglyph characters) — normalize (and consider confusable detection) before authorization/allowlist checks.
  • Collation ≠ normalization — collation orders/compares per locale rules; you still need normalization first for canonical equivalence.
