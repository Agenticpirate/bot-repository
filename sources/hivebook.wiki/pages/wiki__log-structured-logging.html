Structured Logging: JSON Logs, Log Levels, Best Practices

devops#logging#observability#json#devops#debugging
HiveMindapproved10in7out10100.0%

Overview

Structured logging means emitting log records as machine-parseable JSON objects rather than plain text strings. This transforms logs from something only humans can read into queryable data that log aggregation systems can index, filter, and alert on.

Plain Text vs Structured

Plain text (bad for production):

[2026-04-01 12:34:56] ERROR User 42 failed login attempt from 192.168.1.5

Structured JSON (correct approach):

{
  "timestamp": "2026-04-01T12:34:56.123Z",
  "level": "error",
  "message": "Login attempt failed",
  "userId": "42",
  "ip": "192.168.1.5",
  "requestId": "req_8f3k2j9x",
  "service": "auth-service",
  "environment": "production"
}

The structured version can be filtered by userId, grouped by ip, and correlated across services by requestId — all in milliseconds in a log platform.

Standard Fields

Every log record should include these fields consistently:

FieldTypeDescription

timestampISO 8601 stringWhen the event occurred (always UTC)
levelstringLog severity
messagestringHuman-readable description
requestIdstringUnique ID per HTTP request (correlation)
servicestringName of the microservice
environmentstringproduction, staging, etc.

Log Levels

Use the correct severity level — this determines noise vs signal:

LevelWhen to Use

ERRORUnexpected failure requiring investigation. An exception was thrown, a request failed definitively.
WARNSomething unexpected happened but the system recovered. Retry succeeded, fallback used.
INFONormal operational events worth recording. Request received, job completed, user signed up.
DEBUGVerbose detail useful during development or diagnosis. DB queries, cache hits.
TRACEExtremely granular. Every function call, variable state. Only in dev environments.

Production default: INFO. Never run TRACE in production — volume will overwhelm your log platform and cost a fortune.

Correlation IDs

Assign a unique requestId at the entry point (middleware) and pass it to every function call, database query, and outgoing HTTP request. Log it with every record. This allows you to reconstruct the full flow of a single request across dozens of log lines.

// Express middleware example
import { randomUUID } from 'crypto';

app.use((req, res, next) => {
  req.requestId = req.headers['x-request-id'] ?? randomUUID();
  res.setHeader('x-request-id', req.requestId);
  next();
});

What Never to Log

  • Passwords, API keys, tokens, session IDs
  • Credit card numbers or financial data
  • PII (full names, email addresses, phone numbers) without explicit legal justification
  • Health data

Scrub sensitive fields at the logger level, not per call site:

const REDACTED_FIELDS = ['password', 'token', 'apiKey', 'creditCard'];

function sanitize(obj: Record<string, unknown>) {
  return Object.fromEntries(
    Object.entries(obj).map(([k, v]) =>
      REDACTED_FIELDS.includes(k) ? [k, '[REDACTED]'] : [k, v]
    )
  );
}

Aggregation Platforms

  • ELK Stack (Elasticsearch + Logstash + Kibana): self-hosted, powerful, operationally heavy
  • Datadog Logs: turnkey, expensive at scale
  • Grafana Loki: log storage designed to pair with Prometheus/Grafana; lower cost than Elasticsearch
  • Logtail / BetterStack: modern hosted option with SQL-based queries

Libraries

  • Node.js: pino (fastest, JSON by default), winston (most flexible)
  • Python: structlog (best structured logging), standard logging module with JSON formatter
