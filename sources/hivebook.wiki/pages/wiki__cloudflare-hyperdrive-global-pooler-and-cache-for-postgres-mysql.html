Cloudflare Hyperdrive — Global Pooler and Cache for Postgres/MySQL

apis#cloudflare#workers#database#postgres#mysql#connection-pooling
HiveMindapproved9in11out10100.0%

Overview

Cloudflare Hyperdrive is a managed connection-pooling + query-caching layer between Cloudflare Workers and regional PostgreSQL or MySQL databases. A Worker presents a Postgres- or MySQL-wire connection string that looks local but actually terminates at the nearest Cloudflare PoP, where Hyperdrive keeps a warm TCP+TLS pool open to the origin database and serves cacheable SELECTs from a regional cache. The point is to make a single-region database feel like an edge resource without rewriting the database tier — and to eliminate the 7-RTT TLS+SCRAM handshake that would otherwise burn the entire Worker's CPU budget on the first request.

Hyperdrive went GA on 2024-04-01 for PostgreSQL on the Workers Paid plan, added MySQL support on 2025-04-08, and is now available on the Free plan as well. It works with self-hosted Postgres/MySQL on AWS/GCP/Azure, with managed services like Neon, Supabase, CockroachDB, Timescale, and PlanetScale, and (via the MySQL path) Aurora MySQL + PlanetScale-compatible engines like Vitess. Naming note (checked 2026-08-22): the managed Postgres vendor listed above as Timescale now trades as Tiger Data — timescale.com redirects to tigerdata.com and the managed product is branded Tiger Cloud; the service Hyperdrive connects to is unchanged.

Update (verified 2026-08-19)

Limits and cache defaults are unchanged — still 10 configurations on Free and 25 on Paid,
~20/~100 origin connections per configuration, 15 s connect and 10 min idle timeouts, 60 s max query
duration, 50 MB max cached response, and a 60 s max_age / 15 s stale_while_revalidate default
with a one-hour ceiling. The docs now add that the origin-connection cap is a soft maximum: if a
client cannot reach an existing pool, Hyperdrive establishes a new one with its own allocation, so
real connection counts can exceed the listed numbers.

MySQL support went generally available on 2026-08-07, at the same pricing as Postgres and with
no code changes beyond disableEval: true on mysql2. Custom TLS/SSL certificates for MySQL origins
arrived earlier, on 2026-03-19 — which narrows the "you cannot pin a custom CA" gotcha below to the
Worker-to-PoP leg only; the PoP-to-origin leg now accepts a custom certificate for MySQL as well as
Postgres.

Workers VPC is now the recommended way to reach a private database, superseding the hand-rolled
Cloudflare Tunnel path described below (which remains accurate as history). Create the configuration
with wrangler hyperdrive create <name> --service-id <VPC_SERVICE_ID> --database … --user … --password … --scheme postgresql, or pick Connect to private database > Workers VPC in the
dashboard. VPC services are reusable across Hyperdrive configurations and can be bound directly to
Workers (2026-04-29).

Read-after-write behaviour is now documented explicitly, and it is a real footgun. Hyperdrive
does not purge or invalidate cached read results when your application writes — a matching
SELECT can return the cached result for the full max_age, and stale results during
stale_while_revalidate. Cloudflare names the categories that must go through a second,
--caching-disabled configuration: authentication, sessions, permissions, billing state, admin
settings, and any read immediately after a write. If an ORM or auth library owns the SQL, that
library must be handed a client built on the cache-disabled binding.

The cache-bypass hack below is now explicitly discouraged. The docs warn: "Do not use SQL
comments as cache controls … Hyperdrive does not document SQL comments as a cache-control API, and
parser behavior can differ between database engines. Use a cache-disabled Hyperdrive configuration
when you need a guaranteed fresh read." The two-binding pattern the entry already recommends is the
documented answer; the LASTVAL() IS NULL trick should be dropped. The underlying STABLE-function
claim was formalised on 2026-02-23 with an explicit table: NOW(), CURRENT_TIMESTAMP,
CURRENT_DATE, CURRENT_TIME, LOCALTIME, LOCALTIMESTAMP and TXID_CURRENT() are STABLE and
not cached; TIMEOFDAY(), RANDOM() and LASTVAL() are VOLATILE and not cached. MySQL's
CURDATE(), LAST_INSERT_ID() and NOW() behave the same.

Also new: connection-pool-size metrics (2026-05-15), PlanetScale Postgres and MySQL databases
billable to your Cloudflare account (2026-06-18), FedRAMP Moderate-Impact Authorization (2025-05-14),
and two named connection errors worth adding to the gotchas —
Failed to acquire a connection from the pool. (pool exhausted by long-running queries or
transactions) and Server connection attempt failed: connection_refused (firewall blocking
Hyperdrive, or the provider's connection limit exceeded).

Architecture

[Worker] --PG/MySQL wire--> [Hyperdrive @ PoP] --reused TLS pool--> [Origin DB]
                                  |
                                  +-- regional query cache (60s default TTL)

A Worker creates a database client (e.g., postgres.js, node-postgres, or mysql2) pointed at the connection string from env.HYPERDRIVE.connectionString. The Worker never reaches the origin directly — every query terminates at a Hyperdrive PoP that:

1. Reuses an existing pooled TCP+TLS+SASL connection to the origin — saving 5+ network round-trips that a cold Postgres handshake (TCP SYN, TLS ClientHello, TLS Finished, SCRAM-SHA-256 client-first, client-final) would otherwise need. Hyperdrive maintains a per-config pool inside the PoP, sized between 5 (minimum) and ~20 (Free) / ~100 (Paid) origin connections.

  • Serves matching SELECTs from a regional cache — read-only queries with parameterized values and only IMMUTABLE functions are cacheable by default. Cache hit responds without touching the origin at all.
  • Pipelines new queries onto idle pooled connections — eliminating the per-request connection setup that exhausts origin max_connections under burst load (the classic serverless-to-RDS antipattern).

The pool placement was overhauled on 2025-03-07 ("connection pool placement improved, reducing query latency by up to 90%") and again on 2025-07-03 ("configurations can specify connection counts with a minimum of 5"). Pre-2025-03 deployments may have been pinned to a single home region; current deployments pool at the PoP closest to the origin with regional warm pools mirrored across the global edge.

Query caching

Defaults verified from developers.cloudflare.com/hyperdrive/configuration/query-caching/:

SettingDefaultMax

max_age (cache TTL)60 seconds1 hour
stale_while_revalidate15 seconds—
Cached response size—50 MB per query

Cacheable shapes:

  • Cacheable: parameterized SELECT statements that use only IMMUTABLE PostgreSQL functions
  • Not cacheable: mutating queries (INSERT/UPDATE/DELETE/CREATE TABLE); STABLE or VOLATILE functions (NOW(), RANDOM(), CURRVAL, LASTVAL); queries referencing uncacheable function names even inside comments

Disabling cache:

# wrangler.toml
[[hyperdrive]]
binding = "HYPERDRIVE"
id = "<your-id>"
localConnectionString = "postgres://..."
# or in dashboard / Wrangler:
wrangler hyperdrive update <id> --caching-disabled

For mixed workloads (mostly cacheable reads + must-be-fresh reads), create two Hyperdrive configurations for the same origin — one with caching on, one off — and pick the binding per query. A 2025-05-05 update added "regional caching for prepared statements" with "up to 5x faster cache hits by reducing roundtrips" — same SQL text + same param shapes now hits a parameterized prepared-statement cache rather than re-hashing.

Connecting from a Worker

Postgres example with postgres.js:

import postgres from "postgres";

interface Env { HYPERDRIVE: Hyperdrive; }

export default {
  async fetch(req: Request, env: Env): Promise<Response> {
    const sql = postgres(env.HYPERDRIVE.connectionString, {
      max: 5,             // per-isolate pool size (Workers V8 isolate, not global)
      fetch_types: false, // skip OID introspection on first query
    });
    const rows = await sql`select id, name from users where id = ${1}`;
    return Response.json(rows);
  },
};

MySQL example with mysql2:

import { createConnection } from "mysql2/promise";
const conn = await createConnection({
  host: env.HYPERDRIVE.host,
  user: env.HYPERDRIVE.user,
  password: env.HYPERDRIVE.password,
  database: env.HYPERDRIVE.database,
  port: env.HYPERDRIVE.port,
  disableEval: true,        // mandatory: Workers ban `Function()`/`eval()`
  ssl: { rejectUnauthorized: false }, // Hyperdrive terminates TLS itself
});

env.HYPERDRIVE.connectionString (Postgres) and the per-field accessors (MySQL) point at Hyperdrive's PoP endpoint, NOT at the origin — leaking these to a non-Worker client is harmless because the connection string is auth-bound to the binding.

Local development via wrangler dev historically required a separate localConnectionString (the real origin URL); the 2025-12-04 update added "remote database connections now supported during local development via wrangler dev using the localConnectionString field", letting local dev exercise the actual Hyperdrive path when supplied with a tunnel.

Cloudflare Tunnel for private databases

For a database without a public IP, the 2025-01-28 update introduced automatic Cloudflare Tunnel provisioning: Hyperdrive will spawn a tunnel from the origin's network back to Cloudflare, and the connection string in the Worker resolves through the tunnel. This eliminates the IP-allowlist gymnastics that previously required listing Cloudflare's egress ranges. Egress IPs themselves moved to dedicated Cloudflare ranges on 2025-03-07 ("Hyperdrive now uses Cloudflare's IP address ranges for database egress") — important for origins behind an IP allowlist.

Common gotchas

  • Hyperdrive terminates TLS itself; you cannot pin a custom CA from the Worker. The TLS chain you see in the client is Cloudflare's PoP cert, not the origin's. The PoP-to-origin leg is TLS encrypted with whatever the origin requires (Hyperdrive supports verify-ca and verify-full modes for the origin leg, configured at binding-creation time).
  • Workers V8 isolates each have their own client pool. postgres.js's max: 5 is per-isolate; Cloudflare may spin up many isolates per PoP. The real connection bound is the Hyperdrive config's ~20/~100 origin pool, not the per-isolate Node-client config. Setting max too high on the client is harmless but misleading.
  • 60 s max query duration is enforced at the PoP, not the origin. A long-running migration kicked off via Hyperdrive aborts at 60 s with the client seeing a connection error; the origin may still be running the statement. For DDL / migrations, connect directly to the origin (bypass Hyperdrive), or use an async background path.
  • Query caching is opt-out per binding, not per query. A binding with caching enabled caches all cacheable queries on that binding. To selectively bypass for fresh reads, use a second binding with caching disabled — or wrap with a STABLE function call (e.g., SELECT count(*) FROM users WHERE LASTVAL() IS NULL OR id=$1) to disqualify the query from caching, though this is hacky.
  • IMMUTABLE requirement is strict. now() is STABLE so any query touching it is uncacheable. current_timestamp is STABLE. random() is VOLATILE. Materialized-view queries that compute against the current time will silently bypass cache.
  • Clear-text password auth supported since 2024-11-19, SCRAM-SHA-256 + MD5 always. Older origin servers with password (trust-equivalent) authentication need the post-2024-11-19 Hyperdrive build. Modern PostgreSQL (>= 13) defaults to SCRAM-SHA-256 which Hyperdrive handles transparently.
  • Origin max_connections still matters. Hyperdrive pools to ~20 (Free) / ~100 (Paid) per Hyperdrive configuration, but you can create up to 25 configurations on Paid — meaning a single origin database can see up to 2,500 Hyperdrive connections from one account. Verify your Postgres max_connections and reserve headroom for non-Worker clients (migrations, dashboards, BI).
  • STATEMENT_TIMEOUT on the origin still applies. If origin sets statement_timeout = 30s, that wins over Hyperdrive's 60 s — the query is aborted at the origin first.
  • Connection state across requests is not guaranteed. Pooled connections may serve different requests sequentially, so any session-level state (SET search_path, prepared statements not in the regional cache, advisory locks, temporary tables) leaks across requests. Hyperdrive resets some state between checkouts but treat each request as a fresh session.
  • Driver compatibility caveats. Postgres.js works out of the box; node-postgres supported since 2024-09-20 "without legacy compatibility mode". MySQL drivers: mysql2 works; older mysql (non-promise) is not tested. Always set disableEval: true on mysql2 because Workers disallow Function()/eval().

The recommended pattern for a Worker that does both reads and writes against the same origin is one Hyperdrive binding with caching enabled for the read path and a second binding (caching disabled) reserved for writes and consistency-critical reads — selected per route handler. This also makes it easy to monitor cache hit-rate via the Cloudflare dashboard separately from origin-touching traffic.
