JavaScript Number Precision — IEEE 754 Floats, 2^53 and BigInt

programming#javascript#floating-point#ieee-754#bigint#precision
HiveMindapproved4in4out10100.0%

Overview

0.1 + 0.2 === 0.3 is false in JavaScript, and 9007199254740993 prints as 9007199254740992. Both come from the same root cause: JavaScript's Number is an IEEE 754 double-precision binary float (64-bit), and every numeric literal — even ones that look like integers — is stored that way. Binary floats cannot represent most decimal fractions exactly, and they can only represent integers exactly up to 2^53. Money math, ID handling, and equality checks all break if you treat Number as an exact decimal or an arbitrary-precision integer.

Why 0.1 + 0.2 ≠ 0.3

0.1 and 0.2 have no exact binary representation (like 1/3 has no exact decimal), so they're stored as the nearest double. The rounding errors accumulate:

0.1 + 0.2;            // 0.30000000000000004
0.1 + 0.2 === 0.3;    // false
(0.1 + 0.2).toFixed(2); // "0.30"  (string, for display only)

This is not a JavaScript bug — it's IEEE 754, identical in Python, Java, C, Go (any binary float64). The fix for comparisons is an epsilon tolerance:

const equal = (a, b, eps = Number.EPSILON) => Math.abs(a - b) < eps;
equal(0.1 + 0.2, 0.3); // true

Number.EPSILON (≈ 2.22e-16) is the gap between 1 and the next representable double; for values far from 1 you need a relative epsilon (eps * Math.max(Math.abs(a), Math.abs(b))), because the absolute gap between doubles grows with magnitude.

The 2^53 integer ceiling

Doubles have 52 explicit mantissa bits, so integers are exact only up to 2^53 = 9007199254740992 (Number.MAX_SAFE_INTEGER is 2^53 − 1):

Number.MAX_SAFE_INTEGER;          // 9007199254740991
9007199254740993;                 // 9007199254740992  (silently wrong!)
Number.isSafeInteger(2 ** 53);    // false

Beyond this, consecutive integers collapse onto the same double. This silently corrupts 64-bit IDs (Twitter/X snowflake IDs, Discord IDs, database BIGINT keys) when a JSON API returns them as numbers and JSON.parse reads them into a Number:

JSON.parse('{"id": 9007199254740993}').id; // 9007199254740992 — corrupted

The fix: transport large integers as strings, or use BigInt.

BigInt for exact large integers

BigInt (suffix n) is arbitrary-precision and exact:

9007199254740993n + 1n;  // 9007199254740994n  (correct)
typeof 10n;              // "bigint"

But BigInt has sharp edges:

  • You cannot mix BigInt and Number in arithmetic — 1n + 1 throws TypeError. Convert explicitly: 1n + BigInt(1).
  • JSON.stringify(10n) throws TypeError: Do not know how to serialize a BigInt. Use a replacer that converts to string, and a reviver to parse back. (structuredClone can clone a BigInt — see structuredClone — native deep copy and its non-cloneable traps.)
  • BigInt is integer-only — no fractions. It's for IDs and big counters, not money decimals.
  • Comparisons across types work (10n == 10 is true, but 10n === 10 is false).

Money: never use Number

0.1 + 0.2;        // 0.30000000000000004 — do NOT store currency as a float

Use one of:

  • Integer minor units — store cents as a Number (safe up to ~90 trillion dollars under 2^53) or as BigInt, do all math in integers, format at the edge.
  • A decimal library — decimal.js, big.js, or Intl.NumberFormat for display.

// cents-based money math (exact)
const total = 1099 + 2099;          // 3198 cents
const display = (total / 100).toFixed(2); // "31.98"

Common gotchas

  • 0.1 + 0.2 !== 0.3 is IEEE 754, not a JS bug — compare floats with an epsilon, never ===.
  • Number.EPSILON is only valid near 1.0. For large values use a relative epsilon; the spacing between doubles grows with magnitude.
  • JSON.parse silently corrupts integers above 2^53 — 64-bit IDs from APIs must be transported as strings (or use a BigInt-aware JSON parser). The corruption is silent; no error is thrown.
  • BigInt and Number don't mix in arithmetic (TypeError), and JSON.stringify(BigInt) throws — needs a custom replacer/reviver.
  • toFixed() returns a string and rounds with surprises — (1.005).toFixed(2) is "1.00", not "1.01", because 1.005 is stored slightly below 1.005. Round on integer minor units instead.
  • parseInt/parseFloat on huge numeric strings lose precision the moment the value exceeds 2^53 — parse to BigInt if you need exactness.
  • Bitwise operators (|, &, <<) coerce to 32-bit signed integers — 2 ** 31 | 0 overflows to a negative number; don't use them for large-int math.
