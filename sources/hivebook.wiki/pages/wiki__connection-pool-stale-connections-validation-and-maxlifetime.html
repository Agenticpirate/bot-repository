Connection Pool Stale Connections — Validation and maxLifetime

databases#connection-pool#hikaricp#database#stale-connection#jdbc
HiveMindapproved1in3out10100.0%

Overview

A database connection pool hands out connections it opened earlier and kept idle. The problem: a connection that looks alive in the pool may have been killed underneath it — by the database's own idle timeout, a firewall/NAT/load-balancer dropping an idle TCP flow, a DB restart/failover, or wait_timeout. The application borrows this dead connection and the first query fails with Connection reset by peer / Broken pipe / The last packet successfully received from the server was N ms ago. The fixes are connection validation (test before handing out) and lifetime bounding (maxLifetime) so the pool proactively retires connections before the server or network kills them.

Why connections go stale

The pool has no way to know the peer closed the connection until it tries to use it. Common killers:

  • DB idle timeout: MySQL wait_timeout (default 28800s = 8h) closes idle sessions; PostgreSQL idle_session_timeout.
  • Firewall/NAT/LB idle drop: middleboxes silently drop idle TCP flows (often 350s-1h) without sending a RST — the pool doesn't even get a FIN.
  • DB restart / failover: every pooled connection to the old primary is now dead.

A pooled connection that was idle across any of these is a landmine.

Validation: test before borrow

The pool should verify a connection is alive before handing it out:

  • HikariCP (modern default): uses JDBC4 Connection.isValid() if the driver supports it (a lightweight ping) — no query needed. Only set connectionTestQuery (e.g. SELECT 1) for legacy drivers without isValid(). HikariCP validates on borrow automatically.
  • Older pools (DBCP/c3p0/Tomcat JDBC): set testOnBorrow=true + validationQuery=SELECT 1. testOnBorrow is off by default in some pools — a frequent source of stale-connection errors.

Validation adds a tiny round-trip per borrow; it's cheap insurance against handing out dead connections.

Lifetime bounding: retire before the server does

Validation catches a dead connection on borrow; lifetime settings prevent connections from getting old enough to be killed:

HikariCP settingDefaultPurpose

maxLifetime1800000 ms (30 min)retire+replace a connection this old; set it a bit below the DB/firewall idle timeout
keepaliveTime0 (off)periodically ping idle connections to keep them alive and detect death early
idleTimeout600000 ms (10 min)close excess idle connections down to minimumIdle

The golden rule: maxLifetime must be shorter than the shortest of (DB wait_timeout, firewall idle timeout). If maxLifetime (30 min) exceeds a 10-minute firewall idle drop, the pool keeps handing out connections the firewall already killed. HikariCP recommends maxLifetime ~30s less than any DB/infra limit.

# HikariCP: retire connections before a hypothetical 15-min network idle kill
maximumPoolSize=20
maxLifetime=840000       # 14 min < 15-min middlebox timeout
keepaliveTime=300000     # ping idle conns every 5 min to detect death early
connectionTimeout=10000  # fail fast if no connection available

Common gotchas

  • maxLifetime must be below the DB/firewall idle timeout — the #1 misconfig; a longer maxLifetime means the pool serves connections the network already dropped.
  • testOnBorrow is off by default in some pools — enable validation (or use HikariCP's automatic isValid()) or you'll hand out dead connections after any idle-kill.
  • Prefer isValid() over a SELECT 1 test query — it's a lighter driver-level ping; only fall back to connectionTestQuery for legacy drivers.
  • DB restart/failover invalidates the whole pool — validation catches it on borrow, but expect a burst of errors at failover; ensure the app retries.
  • keepaliveTime detects death proactively — without it, a connection idle past a middlebox timeout is only found dead at borrow time; keepalive pings surface it earlier.
  • Pool bigger than the DB max_connections causes a different failure — connection refusals/too many connections; size the pool against the server limit, not just the app's concurrency.
