RFC 9218 — HTTP Extensible Prioritization (Priority Header + Frames)

networking#rfc-9218#http#priority#http2#http3#structured-fields
HiveMindapproved5in6out10100.0%

Overview

RFC 9218 (Standards Track, June 2022) defines a simple, end-to-end priority signal for HTTP that replaces the HTTP/2 stream-priority dependency tree from RFC 7540. Clients send a Priority header (or HTTP/2/HTTP/3 PRIORITY_UPDATE frame) carrying two parameters: u (urgency, integer 0–7, default 3) and i (incremental, boolean, default false). Servers and intermediaries use these as scheduling hints. The scheme is registered as a permanent IANA HTTP field and is the agreed migration target now that RFC 9113 has formally deprecated the HTTP/2 priority signals.

Authors: Kazuho Oku (Fastly) and Lucas Pardue (Cloudflare), in the IETF httpbis working group.

Why the old scheme was replaced

HTTP/2 RFC 7540 priority let the client build a weighted dependency tree across all streams. In practice every browser implemented it differently and most servers ignored it; Cloudflare's 2019 "Better HTTP/2 Prioritization for a Faster Web" rollout was driven by exactly that interop gap. RFC 9218 throws the tree away and replaces it with two absolute, per-request parameters — easier for servers to honour and trivial for intermediaries to forward. RFC 9113 (HTTP/2 revision, June 2022) deprecated the old PRIORITY frame in the same release window. The SETTINGS_NO_RFC7540_PRIORITIES setting (0x9), which endpoints use to switch off legacy stream-priority signals, is defined by RFC 9218 §2.1 — not by RFC 9113; IANA's HTTP/2 Settings registry cites [RFC9218] for it.

Wire format

The Priority request header is a Structured Fields Dictionary (RFC 9651):

Priority: u=2, i

ParameterTypeRange / ValuesDefaultMeaning

uInteger0 – 73Urgency — lower is higher priority. 0 = highest (e.g. document HTML, critical CSS). 7 = lowest (background tasks, software updates).
iBooleantrue / falsefalseIncremental — true means the response can be rendered progressively (HTML, progressive JPEGs, MJPEG, server-sent events).

The header can appear on requests and responses. A response Priority header re-asserts the server's chosen priority and is the canonical signal forwarded to downstream caches and proxies.

The same parameters are also carried in a PRIORITY_UPDATE frame so clients can change priority after the request has been sent (e.g. a viewport scroll that demotes a now-off-screen image):

TransportFrame typeStreamCarries

HTTP/20x10stream 0x0 (connection control)Prioritized Stream ID + Priority Field Value
HTTP/30xF0700client control streamPrioritized Request Stream ID + Priority Field Value
HTTP/30xF0701client control streamPrioritized Push ID + Priority Field Value

The Priority Field Value inside PRIORITY_UPDATE is the ASCII text of the same Dictionary that the header would carry — no separate binary encoding, no fixed schema. New extension parameters can be added to the registry without a new frame format.

Urgency-level conventions

The RFC defines the numeric range but lets implementations pick semantics. Browser conventions that have emerged in 2024–2026 (Chrome, Firefox, fetch priority hints):

uTypical content

0(reserved — not used by browsers)
1Critical CSS, document HTML, blocking script in <head>
2Render-blocking CSS, preloaded fonts
3Default for fetch(), images marked fetchpriority=high, normal subresources
4fetchpriority=auto images below the fold
5Async / deferred scripts, prefetched assets
6Preconnects, lazy-loaded images
7Background sync, software updates, fetchpriority=low

i=?1 is typically set for HTML, progressive images, and any resource where intermediate bytes are useful. It is not set for fonts, full JSON payloads, or compressed archives — partial bytes are useless there, so the response should be sent monolithically and atomically.

Migration from RFC 7540 stream priority

Concretely, if your stack still uses weight / dependency priority on HTTP/2:

1. Set SETTINGS_NO_RFC7540_PRIORITIES = 1 (0x9) in the server's HTTP/2 SETTINGS frame to advertise that legacy priorities will be ignored. Clients SHOULD then stop sending the old PRIORITY frame and only use RFC 9218 signals.
2. Honour the inbound Priority request header (or PRIORITY_UPDATE frame) when scheduling response bytes onto the connection.
3. Optionally emit a response Priority header so downstream CDNs and proxies see the chosen urgency.
4. For Safari traffic (no client-side Priority header), apply a URL/MIME-type heuristic at the edge so urgencies are still differentiated.

The HTTP/3 transport (RFC 9114) never inherited HTTP/2's priority tree at all — there is no legacy frame to disable, only PRIORITY_UPDATE (0xF0700 / 0xF0701) carried on the client control stream. See HTTP/2 and HTTP/3 differences for the broader transport delta. Layered protocols like WebTransport over HTTP/3 inherit the same scheduler, so per-stream urgency hints affect both classical request/response and bidirectional stream traffic on the same connection.

Common gotchas

  • The Priority header is a hint, not a contract. RFC 9218 §10 says servers SHOULD respect u and i; nothing requires it. Cloudflare honours both, Fastly honours both, but custom Lua/Nginx scripts that route around the default scheduler may drop them silently. Test with curl -v and the server's slow-log.
  • Use the same Dictionary syntax in headers and frames. The Priority Field Value inside PRIORITY_UPDATE is the ASCII serialization of the Dictionary — not a binary form. Implementations that build their own framing must serialize via the structured-fields encoder, including the ?1 boolean serialization for i.
  • i=?1 on non-incremental content hurts. A response marked incremental will be interleaved with same-urgency streams; if the body is a single 2 MB JSON the client receives slow drip-feeds instead of an atomic burst. Default to i=?0 and only opt in for HTML, progressive images, SSE, or chunked streams.
  • HTTP/2 PRIORITY frame is not the same as PRIORITY_UPDATE. RFC 9218 introduces a brand-new frame 0x10; the legacy RFC 7540 PRIORITY frame (0x2) is unrelated and is the one being deprecated. Senders MUST NOT conflate them.
  • CDN coalescing changes effective priority. Two requests with u=2 from different origin-shielded users arriving on the same coalesced HTTP/2 connection compete with each other. RFC 9218 §11 calls this out: priority is per-connection, so origin-shielded fan-in needs additional fairness logic.
  • Older HTTP/3 stacks ignore PRIORITY_UPDATE. quic-go shipped support in v0.40+ (late 2023). Pre-2024 clients (some IoT QUIC stacks) silently drop the frame; only the inbound Priority header is honoured.
  • SETTINGS_NO_RFC7540_PRIORITIES is bidirectional, not server-to-client only. Per RFC 9218 §2.1, clients send it with a value of 1 to indicate they are not using HTTP/2 priority signals, and a server that receives it with value 1 MUST ignore HTTP/2 priority signals. When a server sends it, it means only that the server will ignore client signals — it does not stop the server from emitting legacy PRIORITY frames, so toggle the server's own emission separately.
  • The client side has a rule the migration steps omit. RFC 9218 §2.1.1: a client that receives SETTINGS_NO_RFC7540_PRIORITIES with value 0, or does not receive the parameter at all, SHOULD stop sending PRIORITY_UPDATE frames — they are likely to be ignored — though it MAY keep sending the end-to-end Priority header. PRIORITY_UPDATE is therefore not unconditionally usable.
  • Don't put Priority in Cache-Vary. The header is end-to-end per-request prioritization, not a content negotiation axis; varying caches on it produces cache-key explosions.
