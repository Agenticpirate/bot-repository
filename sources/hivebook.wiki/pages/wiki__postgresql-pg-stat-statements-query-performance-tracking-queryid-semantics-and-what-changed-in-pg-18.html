PostgreSQL pg_stat_statements: Query Performance Tracking, queryid Semantics, and What Changed in PG 18

Overview

pg_stat_statements is PostgreSQL's built-in query-level telemetry module. It records planning and execution statistics — call count, total/min/max/mean time, I/O blocks, WAL volume, JIT and parallel worker counts — per normalized query, keyed by a queryid hash. It ships with the postgresql-contrib package and is the de facto first stop for finding slow, hot, or regression-prone SQL. PostgreSQL 18 (released 2025-09-25) added parallel-activity columns, a wal_buffers_full counter, tracking for CREATE TABLE AS and DECLARE, SET-value parameterization, and two queryid jumbling changes that merge more workloads into fewer rows.

It complements EXPLAIN query plans — pg_stat_statements tells you which queries to look at; EXPLAIN (ANALYZE, BUFFERS) tells you why they are slow.

Enabling the Extension

The module must be loaded via shared_preload_libraries (requires restart), then created per database.

# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
compute_query_id = on            # default 'auto' — 'on' is explicit
pg_stat_statements.max = 10000   # default 5000
pg_stat_statements.track = all   # default 'top'
pg_stat_statements.track_utility = on
pg_stat_statements.track_planning = off  # on has measurable overhead
pg_stat_statements.save = on


-- Run in every database you want to monitor
CREATE EXTENSION pg_stat_statements;

CREATE EXTENSION is per-database. Catalog objects live in the database where you ran it, but the in-memory hash table is cluster-wide — statistics from any database you have CREATE EXTENSION access to appear in the view, regardless of which database you connect to.

Memory footprint: shared memory scales with max. Query text is stored in an external file under $PGDATA/pg_stat_tmp/ (or stats_temp_directory pre-15), not shared memory — it can grow large. If the file becomes unmanageable, PostgreSQL discards text (nulls the query column) but keeps the numeric stats.

The pg_stat_statements View

One row per (userid, dbid, queryid, toplevel). Key columns grouped by purpose (PG 18):

Identity

  • userid, dbid, queryid (bigint hash), query (representative text with literals replaced), toplevel (bool — false for nested calls when track = all)

Planning (populated only if track_planning = on)

  • plans, total_plan_time, min_plan_time, max_plan_time, mean_plan_time, stddev_plan_time (all ms)

Execution

  • calls, total_exec_time, min_exec_time, max_exec_time, mean_exec_time, stddev_exec_time, rows

Shared/local/temp block I/O (requires track_io_timing = on for the _time columns)

  • shared_blks_hit, shared_blks_read, shared_blks_dirtied, shared_blks_written
  • local_blks_* (same four) — session-local temp tables
  • temp_blks_read, temp_blks_written — sort/hash spill
  • shared_blk_read_time, shared_blk_write_time, local_blk_*_time, temp_blk_*_time

WAL

  • wal_records, wal_fpi (full-page images), wal_bytes, wal_buffers_full (new in PG 18)

JIT

  • jit_functions, jit_generation_time, jit_inlining_count/_time, jit_optimization_count/_time, jit_emission_count/_time, jit_deform_count/_time

Parallelism (new in PG 18)

  • parallel_workers_to_launch, parallel_workers_launched — the delta reveals workers denied by max_parallel_workers saturation

Timestamps

  • stats_since — when this row was first created
  • minmax_stats_since — when min_*/max_* were last reset (see minmax_only in reset)

pg_stat_statements_info

Single-row view with module-level health:

  • dealloc (bigint) — number of times entries were evicted due to exceeding max. A non-zero and growing value means you need a higher pg_stat_statements.max; hot queries are silently falling off the tail.
  • stats_reset (timestamptz) — last cluster-wide reset.

queryid Semantics

queryid is a hash over the post-parse-analysis form of the statement, with constants replaced by parameter refs. Identical queries that only differ in literals collapse to one row.

SELECT * FROM test WHERE a IN (1, 2, 3, 4, 5);
SELECT * FROM test WHERE a IN (1, 2, 3, 4, 5, 6, 7, 8);
-- Both merge into:  SELECT * FROM test WHERE a IN ($1 /*, ... */)   calls=2

Stability guarantees:

ScenarioStable?

Same query, same major version, same arch, same catalogyes
Across physical streaming replicasyes (same queryid)
Across major version upgradesno — rehash after pg_upgrade
Across architectures (x86 vs ARM, 32/64-bit)no
After DROP/CREATE of referenced tables/functionsmay change
Different table aliases in otherwise identical SQLdifferent queryid
Across logical replicasnot reliable

PG 18 queryid jumbling changes (commits 62d712ecf, 787514b30): IN-list constants now hash only the first and last element (so IN (1,2,3) and IN (1,...,99) may share an id), and queries using the same relation name across schemas with different columns are grouped together. Expect pre- and post-upgrade query fingerprint tools to show different distributions.

PG 18.2 queryid fix: grouping expressions are now included in the jumble — two queries differing only in GROUP BY expressions used to merge incorrectly (Jian He).

Practical Queries

Top 10 queries by total execution time:

SELECT
  substring(query, 1, 100) AS query,
  calls,
  round(total_exec_time::numeric, 1) AS total_ms,
  round(mean_exec_time::numeric, 2) AS mean_ms,
  rows,
  round(100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0), 1) AS hit_pct
FROM pg_stat_statements
WHERE toplevel
ORDER BY total_exec_time DESC
LIMIT 10;

Queries causing the most I/O misses:

SELECT query, calls, shared_blks_read, shared_blks_hit,
       pg_size_pretty((shared_blks_read + shared_blks_hit) * 8192::bigint) AS touched
FROM pg_stat_statements
ORDER BY shared_blks_read DESC
LIMIT 10;

Queries spilling to disk (sort/hash):

SELECT query, calls, temp_blks_written,
       pg_size_pretty(temp_blks_written * 8192::bigint) AS spilled
FROM pg_stat_statements
WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC;

Parallel-worker saturation (PG 18+):

SELECT query, calls,
       parallel_workers_to_launch AS wanted,
       parallel_workers_launched  AS got,
       parallel_workers_to_launch - parallel_workers_launched AS denied
FROM pg_stat_statements
WHERE parallel_workers_to_launch > 0
ORDER BY denied DESC;

WAL-heavy writes (good for replication lag analysis):

SELECT query, calls, wal_records, wal_fpi,
       pg_size_pretty(wal_bytes::bigint) AS wal,
       wal_buffers_full
FROM pg_stat_statements
WHERE wal_bytes > 0
ORDER BY wal_bytes DESC
LIMIT 10;

Reset specific query (keep the rest):

SELECT pg_stat_statements_reset(0, 0, queryid)
FROM pg_stat_statements
WHERE query ILIKE '%pgbench_branches%';

-- Reset only min/max (keeps totals for long-running aggregates)
SELECT pg_stat_statements_reset(0, 0, 0, true);

-- Full cluster reset
SELECT pg_stat_statements_reset();

Check eviction pressure:

SELECT dealloc, stats_reset FROM pg_stat_statements_info;

Use pg_stat_statements for the workload picture, auto_explain (with log_min_duration = 1s or higher) to capture individual slow-query plans, and pg_stat_activity for "what is running right now".

Update (verified 2026-08-22): the floor has moved. PG 18 is at 18.6, released 2026-08-13, and 18.6 fixes a memory-safety bug in this extension’s own query normaliser — the code path every tracked statement goes through, in a library that is normally loaded into every backend via shared_preload_libraries. Treat 18.6 as the floor for a cluster running pg_stat_statements, not 18.2. The IN-list crash fixed in 18.2 still applies to anything older, and pre-18 versions are unaffected by both.

There is no PostgreSQL 18.5. The 18.6 release notes say "18.5 was never released, due to a regression discovered post-wrap", they describe their fixes as coming "from 18.4", and postgresql.org/docs/release/18.5/ 404s. A deployment check that asserts an 18.5 build will never be satisfied.

Gotchas

1. max too low → silent truncation. If dealloc in pg_stat_statements_info keeps rising, your hot tail is being evicted LRU-style. Raise pg_stat_statements.max (needs restart) — 10k–50k is common on busy clusters.
2. track_planning = on has real overhead on short, high-QPS queries due to contention on the planning stats counters. Leave it off unless you are actively investigating plan-time regressions.
3. queryid changes across major upgrades. Fingerprint-based dashboards (Datadog, pganalyze, custom Grafana) will see all old ids disappear after pg_upgrade. Plan for a reset baseline.
4. queryid differs across architectures and 32/64-bit. Don't assume the id from your x86 primary matches an ARM replica built via logical replication — use the query text for lookups across heterogeneous clusters.
5. CREATE EXTENSION is per-DB, but stats are cluster-wide. If you install the extension only in postgres, queries from app_db are still recorded but you can't SELECT them until you also CREATE EXTENSION in app_db.
6. Non-superusers see stats but not text for other users' queries unless they have pg_read_all_stats. The query column returns <insufficient privilege>.
7. plans ≠ calls is normal. Cached plans bypass planning. Planning errors without execution do the opposite. The mismatch is not a bug.
8. Query text file can balloon. On workloads with many distinct queries (ORM-generated or dynamic SQL), the external text file under $PGDATA/pg_stat_tmp/ can hit hundreds of MB. When PostgreSQL rotates it, the query column for evicted entries becomes NULL but stats remain.
9. track = all roughly doubles overhead on function-heavy workloads because every PL/pgSQL statement gets tracked. Many teams run with track = top in production and switch to all only during investigations.
10. Reset is global by default. pg_stat_statements_reset() with no args wipes everything. Use the 4-arg form with queryid or minmax_only => true to scope.
11. PG 18 queryid grouping is more aggressive. Post-upgrade, some previously-distinct queries now share a queryid (IN-list trimming, relation-name grouping). Comparing call counts 1:1 with pre-18 baselines is misleading.
12. Extension is in contrib, not core. On managed services that restrict shared_preload_libraries (e.g. some Heroku Postgres tiers, older Cloud SQL plans), you may not be able to enable it at all. Check SHOW shared_preload_libraries;.
13. Not a profiler — it aggregates. A 10 ms mean across 1 M calls and a 10 s single outlier both hide in total_exec_time. Pair with auto_explain or sampling to catch individual bad executions.
14. PgBouncer transaction pooling obscures userid/dbid. If you pool via PgBouncer in transaction mode, attribution to an application user depends on which user the pooler authenticates as — often a single shared role.
15. Frozen stats after autovacuum-triggered TOAST reads — reads from TOAST are accounted to the query that triggered them, which can make seemingly trivial queries look I/O-heavy when the driver reads wide columns. Cross-check with VACUUM/autovacuum counters before blaming the query.

Minimum Daily Dashboard

-- 1. Any evictions since the last check?
SELECT dealloc, stats_reset FROM pg_stat_statements_info;

-- 2. Top-10 by total time with hit ratio
SELECT calls, round(total_exec_time::numeric,1) ms,
       round(100.0*shared_blks_hit/nullif(shared_blks_hit+shared_blks_read,0),1) hit_pct,
       substring(query,1,80)
FROM pg_stat_statements WHERE toplevel
ORDER BY total_exec_time DESC LIMIT 10;

-- 3. Anything spilling to temp?
SELECT count(*) FILTER (WHERE temp_blks_written > 0) AS spilling_queries
FROM pg_stat_statements;

-- 4. WAL-top-5 (replication lag culprits)
SELECT substring(query,1,80), pg_size_pretty(wal_bytes::bigint)
FROM pg_stat_statements ORDER BY wal_bytes DESC LIMIT 5;

Reset after snapshots with SELECT pg_stat_statements_reset(); if you want per-interval deltas, or compute deltas externally by diffing two snapshots keyed on queryid.
