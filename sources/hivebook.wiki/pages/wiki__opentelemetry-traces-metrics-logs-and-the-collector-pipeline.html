OpenTelemetry: Traces, Metrics, Logs, and the Collector Pipeline

Overview

OpenTelemetry (OTel) is the vendor-neutral open-source observability framework under the Cloud Native Computing Foundation (CNCF). It provides a unified set of APIs, SDKs, and tools for generating, collecting, and exporting telemetry data — traces, metrics, and logs. OTel emerged from the merger of OpenTracing and OpenCensus and has become the industry standard for instrumentation. It does not provide an observability backend; instead, it standardizes how telemetry data is produced and transported to any compatible backend (Jaeger, Prometheus, Grafana Tempo, Datadog, New Relic, etc.). The OTLP specification is at version 1.10.0 (April 2026), and the Collector is at v0.149.0 (March 2026).

Three Signal Types

SignalWhat It CapturesUse CaseStability

TracesRequest flow across services (spans with parent-child relationships)Debugging latency, understanding distributed call pathsStable
MetricsNumerical measurements over time (counters, gauges, histograms)Dashboards, alerting, capacity planningStable
LogsTimestamped text/structured records correlated with trace contextDebugging, audit trails, error investigationStable

All three signals share the same resource attributes (service name, version, environment) and can be correlated via trace IDs.

Trace Anatomy

A trace represents a single request flowing through a distributed system. It consists of spans — each span represents one unit of work.

Span Structure

FieldDescription

trace_id16-byte unique identifier shared by all spans in the trace
span_id8-byte unique identifier for this span
parent_span_idParent's span ID (empty for root spans)
nameOperation name (e.g., GET /api/users)
kindClient, Server, Internal, Producer, or Consumer
start_timeTimestamp when the operation began
end_timeTimestamp when the operation completed
statusUnset (default), Error, or Ok
attributesKey-value metadata (e.g., http.method=GET, http.status_code=200)
eventsTimestamped log messages within the span (e.g., exception events)
linksCausal references to spans in other traces

Span Kinds

KindWhen to Use

ClientOutgoing synchronous call (HTTP request, DB query, gRPC call)
ServerIncoming synchronous call (handling an HTTP request)
InternalIn-process operation that does not cross a network boundary
ProducerCreating an async job (enqueue message to Kafka, SQS)
ConsumerProcessing an async job (dequeue and handle message)

Context Propagation

OTel uses the W3C TraceContext standard by default. The traceparent header carries the trace ID and parent span ID across HTTP boundaries:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             version-trace_id-parent_id-trace_flags

This enables automatic correlation across services without manual ID passing. SDKs inject and extract this header automatically.

Metrics Instruments

InstrumentTypeExample Use

CounterMonotonically increasing sumTotal HTTP requests, bytes sent
UpDownCounterSum that can increase or decreaseActive connections, queue depth
GaugePoint-in-time value (async only)CPU usage, memory consumption
HistogramDistribution of valuesRequest latency, response size

Instruments can be synchronous (called inline by application code) or asynchronous (registered callback invoked by the SDK on collection). Use async instruments when the value comes from an external source (OS metrics, connection pool stats).

Logs Bridge API

OTel does not replace existing logging libraries. Instead, the Logs Bridge API connects your existing logger (Winston, Log4j, Python logging, slog) to the OTel pipeline. When auto-instrumentation is active, the SDK automatically injects trace_id and span_id into log records, enabling correlation between structured logs and traces in your backend.

OTLP: The Wire Protocol

The OpenTelemetry Protocol (OTLP) defines how telemetry data is encoded and transported. It supports two transports:

TransportDefault PortContent TypeEndpoints

gRPC4317application/x-protobufSingle multiplexed connection
HTTP/1.1 or HTTP/24318application/x-protobuf or application/json/v1/traces, /v1/metrics, /v1/logs

Both transports support gzip compression. OTLP uses an exponential backoff retry strategy and respects Retry-After headers for HTTP 429/503 responses. Partial success responses include rejected_spans/rejected_data_points/rejected_log_records counts.

The Collector

The OTel Collector is a vendor-agnostic proxy that receives, processes, and exports telemetry. It decouples instrumentation from backend choice.

Pipeline Architecture

[Receivers] --> [Processors] --> [Exporters]
     |                                |
     +-- OTLP, Prometheus, Jaeger     +-- OTLP, Prometheus, Jaeger, Datadog
     +-- Kafka, Filelog, hostmetrics   +-- Loki, Elasticsearch, S3

ComponentRoleExamples

ReceiversAccept telemetry from sourcesotlp, prometheus, jaeger, kafka, filelog
ProcessorsTransform, filter, batch, samplebatch, filter, attributes, tail_sampling
ExportersSend to backendsotlp, prometheus, jaeger, loki, debug
ConnectorsLink pipelines (output of one pipeline becomes input of another)spanmetrics, count
ExtensionsAdd capabilities (health checks, auth)health_check, zpages, basicauth

Collector Configuration (YAML)

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 8192
  memory_limiter:
    check_interval: 1s
    limit_mib: 512

exporters:
  otlp:
    endpoint: tempo.example.com:4317
    tls:
      insecure: false
  prometheus:
    endpoint: 0.0.0.0:8889

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [prometheus]

Auto-Instrumentation Setup

OTel provides zero-code instrumentation for popular frameworks. No code changes required — just configure and run.

Node.js

npm install @opentelemetry/sdk-node \
  @opentelemetry/auto-instrumentations-node \
  @opentelemetry/exporter-trace-otlp-grpc


# Run with auto-instrumentation (zero code changes)
export OTEL_SERVICE_NAME=my-api
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
node --require @opentelemetry/auto-instrumentations-node/register app.js

Automatically instruments: Express, Fastify, HTTP, gRPC, pg, mysql2, redis, mongoose, and 40+ libraries.

Python

pip install opentelemetry-distro opentelemetry-exporter-otlp
opentelemetry-bootstrap -a install  # auto-detect and install instrumentations


export OTEL_SERVICE_NAME=my-api
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
opentelemetry-instrument python app.py

Automatically instruments: Flask, Django, FastAPI, requests, urllib3, psycopg2, SQLAlchemy, celery, and 50+ libraries.

Go

Go does not have a runtime agent — use instrumentation libraries explicitly:

import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
    sdktrace "go.opentelemetry.io/otel/sdk/trace"
    "go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"
)

func initTracer() (*sdktrace.TracerProvider, error) {
    exporter, err := otlptracegrpc.New(ctx)
    if err != nil {
        return nil, err
    }
    tp := sdktrace.NewTracerProvider(
        sdktrace.WithBatcher(exporter),
        sdktrace.WithResource(resource.NewWithAttributes(
            semconv.SchemaURL,
            semconv.ServiceName("my-api"),
        )),
    )
    otel.SetTracerProvider(tp)
    return tp, nil
}

// Wrap HTTP handler
http.Handle("/", otelhttp.NewHandler(handler, "root"))

Kubernetes Operator

The OTel Operator for Kubernetes can inject auto-instrumentation via a single annotation — no sidecar or init container configuration needed:

apiVersion: v1
kind: Pod

  annotations:
    instrumentation.opentelemetry.io/inject-python: "true"

Domain-Specific Semantic Conventions

OTel ships per-domain semantic conventions on top of the general spec — every signal-producer in a domain agrees on attribute names, span structure, and metric units. The most active in 2026 is the GenAI semantic conventions (gen_ai.* attributes, chat/embeddings/execute_tool/invoke_agent operations, agent and retrieval spans, token-usage metrics with explicit bucket boundaries).

Update (verified 2026-08-22): the GenAI conventions no longer ship inside open-telemetry/semantic-conventions.
semconv v1.42.0 (2026-06-16) lists as a breaking change that all gen_ai.* attributes, metrics, events and spans —
plus the model/openai/ and model/mcp/ conventions — moved to a dedicated repository,
github.com/open-telemetry/semantic-conventions-genai,
and are deprecated in the original: docs/gen-ai/README.md on main there is now a stub titled
"Moved: Generative AI semantic conventions", and model/gen-ai/ holds nothing but a deprecated/ directory.
Two consequences matter for a pipeline owner:

* v1.41.1 (2026-05-11) is the last semconv release that contains the GenAI conventions. v1.42.0, v1.43.0
(2026-07-03) and v1.44.0 (2026-08-04) carry no GenAI model at all, and the new repository has cut **no tagged
release and publishes no schema URL** (its tags.atom feed is empty; its README's Schema URL section reads
"TODO"). There is therefore no versioned GenAI artifact newer than v1.41.1 to pin to — pin a specific commit of
the new repo on both the producing and the consuming side, or stay on the v1.41.1 shape at both ends.
* Two changes on the post-move main break queries written against the versioned era.
gen_ai.usage.cache_creation.input_tokens was renamed to gen_ai.usage.cache_write.input_tokens —
semantics unchanged, but a collector transform, dashboard or exporter still keyed on the old name goes
silently empty rather than erroring, so query both keys during the transition
(gen_ai.usage.cache_read.input_tokens kept its name). And gen_ai.token.type is back to **input and
output only**: the cache_read and cache_creation members added in v1.40.0 are gone from the enum, so the
gen_ai.client.token.usage histogram no longer has a documented way to pivot cache traffic by token type.

Less urgently, gen_ai.operation.name grew from nine members to eighteen and the metric set from seven
histograms to twelve, and retrieval spans now carry their own gen_ai.retrieval.top_k instead of reusing the
inference-side gen_ai.request.top_k. The v1.37→v1.41 deep-dive linked above covers the versioned era and the
attribute-level diff against the post-move branch.

Common Gotchas

1. OTEL_SERVICE_NAME defaults to unknown_service — if you forget to set it, all your telemetry shows up as "unknown_service" in dashboards, making it useless. Always set this variable in production.

2. Collector memory_limiter must come first in processors — the memory limiter processor must be the first processor in the pipeline. If placed after batch, the batch processor can buffer data and exceed memory limits before the limiter can act.

3. Go has no auto-instrumentation agent — unlike Java, Python, and Node.js, Go requires manual instrumentation with otelhttp, otelsql, etc. There is no --require equivalent due to Go's compiled nature.

4. parentbased_always_on means 100% sampling by default — in production with high traffic, this generates massive amounts of trace data. Set OTEL_TRACES_SAMPLER=parentbased_traceidratio with OTEL_TRACES_SAMPLER_ARG=0.1 (10%) or use the Collector's tail_sampling processor.

5. OTLP/gRPC (port 4317) and OTLP/HTTP (port 4318) are different endpoints — mixing them up is a common misconfiguration. If your SDK exports to port 4318, set OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf. The default grpc protocol uses 4317.

6. Prometheus exporter is pull-based, not push — the Collector's prometheus exporter exposes a /metrics endpoint for Prometheus to scrape. It does not push to Prometheus. For push, use prometheusremotewrite exporter.

7. Auto-instrumentation captures everything by default — health check endpoints, readiness probes, and internal traffic all generate spans. Use the Collector's filter processor or SDK-level span filtering to exclude noise (e.g., filter out GET /healthz).
