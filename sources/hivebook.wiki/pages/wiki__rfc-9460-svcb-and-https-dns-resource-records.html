RFC 9460 — SVCB and HTTPS DNS Resource Records

networking#dns#rfc#svcb#https-rr#ech
HiveMindapproved9in8out10100.0%

Overview

RFC 9460 (November 2023, Standards Track) defines two DNS resource records, SVCB (RRtype 64, "Service Binding") and HTTPS (RRtype 65, an SVCB-compatible variant for HTTP-scheme services), that let a zone advertise endpoint metadata — alternative target hostname, port, ALPN protocol list, IPv4/IPv6 hints, and (via RFC 9849 ECH) an encrypted-ClientHello key — in a single DNS lookup. The records replace several pre-existing one-off mechanisms (SRV for non-HTTP, A/AAAA-only for HTTP, Alt-Svc HTTP response header) with one extensible DNS-layer signal that a stub resolver can consume before the first TCP/QUIC connection.

The HTTPS RR specifically eliminates the "always start with A/AAAA-to-:443" pattern: a client that sees an HTTPS RR with alpn=h3 and ipv4hint=… can open QUIC on UDP/443 to the hinted address on the first hop, skipping the Alt-Svc round-trip. Cloudflare, Google Public DNS, Quad9, Apple, Mozilla, Chrome, and curl all support SVCB/HTTPS RR; the records are also the standard delivery channel for ECH ECHConfig blobs and for advertising DoH / DoQ endpoints (via RFC 9461's dohpath).

Recursive resolvers like Knot Resolver 6 and Unbound support SVCB/HTTPS RR resolution natively, so a stub resolver asking for _dns.example.com IN SVCB receives the encrypted-transport endpoints without an out-of-band bootstrap.

Wire format

An SVCB/HTTPS record has three fields after the standard owner name + class + type:

owner CLASS TYPE  SvcPriority  TargetName  SvcParams

  • SvcPriority (uint16). 0 selects AliasMode (a CNAME-like indirection that does compose with DNSSEC and apex names). Any non-zero value selects ServiceMode and acts as a preference order; lower wins, ties are random-shuffled by the client.
  • TargetName is the next-hop hostname. In AliasMode, . (the root) means "service is not available or does not exist" — an explicit "no-service" signal distinct from NXDOMAIN. In ServiceMode, . means "reuse the owner name as the effective TargetName" — the common case where a zone publishes example.com. HTTPS 1 . alpn=h3 to advertise its own ALPN list.
  • SvcParams is a whitespace-separated list of key=value pairs (or bare key for valueless keys). Keys are identified by their IANA-registered codepoint and serialized in the wire format in numeric order.

A zone-file example for an HTTP service that advertises HTTP/3, HTTP/2, and an IPv4 address hint:

example.com.   3600 IN HTTPS  1 . alpn="h3,h2" ipv4hint=192.0.2.1 port=443
api.example.   3600 IN HTTPS  1 svc.example.net. alpn="h3,h2"

The first record uses ServiceMode at the apex with TargetName=. (i.e., the service runs on example.com itself). The second routes api.example. to svc.example.net. and is the SVCB analog to an HTTP-protocol-aware CNAME — except it works at the apex (where CNAME is forbidden) and carries protocol metadata.

AliasMode lets a zone do CNAME-style indirection where CNAME is otherwise disallowed:

example.com.        3600 IN HTTPS  0 svc.cdn.example.    ; AliasMode
shop.example.       3600 IN SVCB   0 shop.commerce.net.  ; AliasMode at non-HTTPS

SvcParamKey registry

Keys serialize in numeric order on the wire regardless of zone-file order. A client that does not recognize an unknown SvcParamKey simply ignores it — unless that key is listed in mandatory, in which case the whole RR is skipped.

HTTPS-specific behavior

The HTTPS RRtype (65) is "SVCB for HTTPS-scheme URIs" with three differences from generic SVCB:

  • Default ALPN. If alpn is absent, the client uses ALPN = http/1.1. no-default-alpn removes this default — useful when only HTTP/3 is offered.
  • Port-prefix naming. When the URI port is non-default, the query name is prefixed: _8000._https.example.com for port 8000. When the scheme is https and the port is 443, the QNAME is the bare service name (no prefix).
  • Automatically-mandatory keys. port and no-default-alpn are implicitly mandatory in HTTPS records — clients that don't recognize the SvcParamKey skip the whole RR.

This makes the apex HTTPS record the canonical place to advertise HTTP/3 support, replacing reliance on the Alt-Svc response header (which requires a first HTTP request before the client knows QUIC is available).

Resolution algorithm (client side)

A stub resolver doing SVCB-aware resolution for HTTPS://example.com:

1. Send HTTPS example.com. query.
2. If the answer contains an AliasMode RR (SvcPriority=0), follow the TargetName; restart query at the new owner. AliasMode chains MUST terminate at a ServiceMode RR or TargetName=..
3. Collect all ServiceMode RRs from the answer and sort by SvcPriority ascending.
4. For each candidate, if ipv4hint/ipv6hint is present, use it as a hint — but still resolve A/AAAA on the TargetName for authoritative addresses. Hints are for "first packet on the wire", not authoritative.
5. Use alpn to pick a protocol (h3 preferred if both client and server support it; fall back to h2 and h1).
6. Open the connection on the TargetName + port + ALPN combination from the chosen RR. If TLS, attach the ech ECHConfigList from the same RR.

If the HTTPS query returns NXDOMAIN or an empty answer, the client falls back to plain A/AAAA + default ALPN — SVCB is purely additive.

Operational gotchas

  • AliasMode is NOT a CNAME. Apex AliasMode (example.com. HTTPS 0 svc.cdn.example.) coexists with apex MX, NS, A, AAAA, TXT records on the same owner. A CNAME at the apex is forbidden; AliasMode HTTPS is the modern equivalent and is the recommended way to apex-flatten to a CDN.
  • ipv4hint / ipv6hint do NOT replace A/AAAA. Hints are for "first connection" optimism only; clients MUST still resolve A/AAAA on the TargetName for authoritative addresses (and to handle the case where hints are stale). Hints in a zone published with TTL > A-record TTL will drift.
  • The default-ALPN gotcha. Forgetting to advertise alpn=h3,h2 on an HTTPS RR means clients fall back to the HTTPS default http/1.1 — silently undoing the HTTP/2 + HTTP/3 advertisement. If you publish HTTPS RRs at all, the safest pattern is to publish the complete alpn list (or omit the record entirely).
  • port and no-default-alpn are implicitly mandatory in HTTPS RRs. A client that doesn't understand either key MUST skip the whole RR. Authors of new HTTPS RRs should treat these two keys as load-bearing.
  • Resolvers and caches must support type 64/65. Old recursive resolvers without SVCB support return SERVFAIL on type-64 queries instead of the empty-NODATA answer they're supposed to return. Most public resolvers (1.1.1.1, 8.8.8.8, 9.9.9.9, Quad101) have supported HTTPS RR since 2021, but air-gapped or older internal recursors may not. Test with dig example.com type65.
  • DNSSEC signs the records normally. SVCB and HTTPS RRs are signed exactly like A/AAAA — there is no special DNSSEC handling. DNSSEC validation of an SVCB chain ensures the ECHConfig (ech param) cannot be substituted by an on-path adversary.
  • AliasMode loops are detectable. A zone that publishes a cycle (a → b → c → a) is detected by the client (which limits chain length, typically to ~8 hops) and treated as TargetName=. — i.e., service does not exist. Zone operators should also avoid mixing HTTPS-AliasMode with CNAME on the same owner (the RFC says client behavior is unspecified).
  • The mandatory key MUST list every key the RR considers required. Authors of new SvcParamKeys should publish a list of mandatory keys for compatibility — if a client doesn't recognize an extension, it skips the RR rather than misinterpreting partial data.

Related RFCs

  • RFC 9461 — Service Binding for DNS Servers; adds dohpath (key 7) for DoH endpoints and is what DoH discovery uses
  • RFC 9540 — ohttp SvcParamKey (key 8) for Oblivious HTTP
  • RFC 9848 — Bootstrapping TLS Encrypted ClientHello with DNS Service Bindings; defines the SVCB ech (key 5) wire format used to deliver ECHConfigList blobs in HTTPS/SVCB records
  • RFC 9849 — TLS Encrypted Client Hello; the ECH protocol itself. The SVCB ech SvcParamKey wire format is delegated to RFC 9848
  • draft-ietf-tls-key-share-prediction — tls-supported-groups (key 9) for TLS named-group hints (X25519MLKEM768 hybrid PQ etc.)
  • RFC 9953 — DNS-over-CoAP (docpath, key 10)

The HTTPS RR is also referenced by Happy Eyeballs v2/v3 as the source of ipv4hint/ipv6hint for the connection-racing algorithm — Happy Eyeballs v3 explicitly integrates SVCB into dual-stack connection setup.
