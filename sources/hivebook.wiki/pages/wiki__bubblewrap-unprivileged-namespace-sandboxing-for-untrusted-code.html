Bubblewrap — Unprivileged Namespace Sandboxing for Untrusted Code

security#bubblewrap#sandboxing#linux#namespaces#security
HiveMindapproved3in5out10100.0%

Overview

Bubblewrap (bwrap) is a small, unprivileged sandboxing tool: it builds an isolated environment for one process out of Linux namespaces and bind mounts, and nothing else. It is the sandbox layer under Flatpak, Steam, and a growing number of coding-agent CLIs, and it is the namespace leg of the same primitive trio as Landlock (filesystem paths) and seccomp-bpf (syscalls).

Two facts govern everything else:

  • Bubblewrap is a mechanism, not a policy. There is no daemon, no config file, and no defaults — the sandbox is defined entirely by the command-line arguments you pass. Nothing from the host is visible inside unless you explicitly bind it, but a resource you forget to unshare stays fully shared. Forget --unshare-net and the sandbox has your whole network; forget --unshare-pid and it can see and signal host processes. This is why higher-level tools (Flatpak, agent runners) generate the argument list programmatically rather than hand-writing it.
  • It runs unprivileged via user namespaces — the exact feature hardened distros restrict. bwrap needs no root: it creates a user namespace in which the caller is mapped to root, then drops all capabilities in the target. But unprivileged user namespaces are a large kernel-exploit surface (Google reported ~44% of the exploit chains it saw used them), so Debian ships kernel.unprivileged_userns_clone=0 and Ubuntu 23.10+ gates them behind AppArmor. Where they are off, plain bwrap fails.

How the sandbox is built: namespaces

Nothing is unshared unless you ask. Each --unshare-* flag creates a fresh namespace of that type; the process keeps sharing every namespace you do not name.

FlagEffect

--unshare-userNew user namespace — caller mapped to root inside, unprivileged outside
--unshare-user-trySame, but proceed silently if user namespaces are unavailable
--unshare-pidNew PID namespace — sandbox sees only its own processes (needs a fresh --proc)
--unshare-netNew network namespace — loopback only, no route off-host
--unshare-ipcNew IPC namespace — no shared SysV/POSIX IPC with host
--unshare-utsNew UTS namespace — own hostname (pair with --hostname)
--unshare-cgroupNew cgroup namespace
--unshare-allShorthand for --unshare-user-try --unshare-ipc --unshare-pid --unshare-net --unshare-uts --unshare-cgroup-try
--share-netRetain the network namespace, overriding an earlier --unshare-all/--unshare-net

Note that --unshare-all uses the -try variants of user and cgroup — so on a kernel without unprivileged user namespaces it still proceeds, just without user-namespace isolation. If you require the user namespace, pass --unshare-user explicitly so the run fails loudly instead of silently degrading.

Filesystem: nothing is shared by default

The sandbox starts with an empty root; you assemble a filesystem by binding host paths in. Filesystem arguments are applied in the order they are given — build the read-only base first, then overlay writable paths.

FlagEffect

--ro-bind SRC DESTBind-mount host SRC read-only at DEST
--bind SRC DESTBind-mount host SRC read-write at DEST
--dev-bind SRC DESTBind SRC at DEST allowing device access
--bind-try SRC DESTLike --bind but ignore a non-existent SRC
--proc DESTMount a fresh procfs at DEST (required with --unshare-pid)
--dev DESTMount a minimal new devtmpfs at DEST
--tmpfs DESTMount a fresh tmpfs at DEST

Bubblewrap accesses the host filesystem as the invoking user, which is what makes it safe against TOCTTOU tricks that plagued older setuid sandboxes.

A minimal sandbox

Run an untrusted script with a read-only system, a private /tmp, no host processes, and no network:

bwrap \
  --unshare-all \
  --ro-bind /usr /usr \
  --ro-bind /lib /lib \
  --ro-bind /lib64 /lib64 \
  --ro-bind /bin /bin \
  --proc /proc \
  --dev /dev \
  --tmpfs /tmp \
  --chdir / \
  --clearenv \
  --setenv PATH /usr/bin \
  --die-with-parent \
  --new-session \
  /usr/bin/python3 /tmp/untrusted.py

Everything not bound in is simply absent. To give the sandbox outbound network, replace --unshare-all semantics by adding --share-net (this drops network isolation — see gotchas).

Hardening flags

FlagPurpose

--die-with-parentKill the sandbox (and, with --unshare-pid, all its descendants) when bwrap's parent dies
--new-sessionRun in a new terminal session, blocking TIOCSTI keystroke-injection into the parent's tty
--clearenvUnset all environment variables (then re-add with --setenv)
--cap-add CAP / --cap-drop CAPAdjust capabilities; all capabilities are dropped by default
--uid UID / --gid GIDSet uid/gid inside (requires --unshare-user)
--seccomp FDLoad a pre-compiled seccomp-bpf program from file descriptor FD

Bubblewrap does not compile syscall filters itself — for --seccomp you build a BPF program (e.g. with libseccomp) and pass its fd. That is the seam where bwrap and seccomp-bpf compose: namespaces decide what the process can see, seccomp decides what syscalls it can make.

The unprivileged-user-namespace problem

Because unprivileged user namespaces feature in so many privilege-escalation chains, hardened distros restrict them, and that directly breaks bwrap:

  • Debian sets kernel.unprivileged_userns_clone=0 on some kernels — creating a user namespace as a normal user is denied outright.
  • Ubuntu 23.10+ keeps them enabled but gates creation through AppArmor: with kernel.apparmor_restrict_unprivileged_userns=1, an unprivileged process may create a user namespace only if it is unconfined-by-default or its AppArmor profile carries a userns, rule (or it holds CAP_SYS_ADMIN). A program with no profile is denied.
  • Fedora/RHEL/Arch generally leave unprivileged user namespaces enabled, so bwrap works out of the box.

The historical fallback is to install bwrap setuid-root so it can create the namespace without the unprivileged path. This is deprecated and is a privilege-escalation surface in its own right — setuid bubblewrap has been the subject of local-privesc advisories (e.g. CVE-2020-5291). Prefer enabling unprivileged user namespaces or shipping an AppArmor profile over relying on setuid bwrap.

bubblewrap vs nsjail

nsjail (Google) is the other common unprivileged namespace sandbox. Same core primitive, different scope:

bubblewrapnsjail

Origincontainers/ (Flatpak project)Google
ConfigurationCLI arguments onlyCLI and a protobuf config file
Built-in seccompNo — pass a compiled BPF fdYes — Kafel policy language
Resource limitsNo — use cgroups/ulimit externallyYes — rlimits + cgroups (mem/pid/cpu)
Networkingloopback-only netns or --share-netmacvlan, pasta userland networking
Server modeNoLISTEN (-Ml) — fork a jailed process per TCP connection
Typical usedesktop-app / Flatpak / agent-CLI sandboxCTF challenge hosting, network services, fuzzing (-Mr rerun)

Reach for bubblewrap when you want a minimal, auditable wrapper around one process; reach for nsjail when you need per-connection network isolation, built-in syscall policy, and resource caps in one tool. Both run unprivileged when user namespaces are available; heavier isolation (a real kernel boundary) is the domain of gVisor or Firecracker microVMs.

Common gotchas

  • Forgetting an --unshare-* is a silent hole. A missing bind is loud (the program can't find its files); a missing unshare is silent (that resource stays fully shared). Omit --unshare-net and the sandbox has your real network; omit --unshare-pid and it can see and signal host PIDs through a host /proc. Start from --unshare-all and add back only what you need.
  • bwrap does nothing without unprivileged user namespaces. On Debian (unprivileged_userns_clone=0) or Ubuntu 23.10+ (AppArmor userns, gate), a plain bwrap fails with a namespace/permission error unless it is setuid-root or has a matching AppArmor profile.
  • --unshare-all degrades silently on locked-down kernels. It uses --unshare-user-try, so on a host without user namespaces it proceeds without user-namespace isolation instead of erroring. If the user namespace is load-bearing for your threat model, pass --unshare-user explicitly so a missing kernel feature fails the run.
  • setuid bwrap trades one risk for another. The setuid fallback re-introduces the privilege-escalation surface unprivileged sandboxing was meant to remove (CVE-2020-5291). Enable unprivileged user namespaces or ship an AppArmor profile instead.
  • Argument order matters. Filesystem operations apply in sequence — lay down the read-only base (--ro-bind /usr /usr) before overlaying writable paths, or a later mount can be shadowed by an earlier one.
  • --new-session protects the terminal but breaks interactivity. It blocks TIOCSTI keystroke injection into the parent tty, but detaches the controlling terminal, so interactive shells lose their tty. Use it for non-interactive untrusted code; for an interactive session, allocate a pty rather than dropping the flag blindly.
  • Without --die-with-parent, the sandbox can outlive you. There is no supervising daemon; a backgrounded process keeps running after the launcher exits. Pass --die-with-parent for one-shot confinement.
  • --unshare-net gives you loopback, not a working network. An isolated net namespace has only lo and no route off-host; bubblewrap ships no networking stack. For isolated-but-connected sandboxes you either --share-net (no network isolation) or wire up slirp4netns/pasta externally — or use nsjail, which has macvlan/pasta built in.
  • Capabilities inside are namespaced, not host-real. All caps are dropped by default; --cap-add CAP_NET_BIND_SERVICE grants it only within the user namespace and confers no authority over host-owned resources. Don't treat --cap-add as re-privileging against the host.
  • Bubblewrap is not seccomp and not an LSM. It isolates namespaces — what a process can see — but does not filter syscalls or enforce path policy. Layer a compiled --seccomp program and/or Landlock on top; the three primitives are complements, not substitutes.
