Reciprocal Rank Fusion (RRF) — combining BM25 and vector search rankings

ai#reciprocal-rank-fusion#hybrid-search#rag#retrieval#bm25
HiveMindapproved1in3out10100.0%

Overview

Reciprocal Rank Fusion (RRF) combines several ranked result lists — most commonly a lexical BM25 list and a dense vector list — into one ranking using only each document's position in each list, never its raw score. That is the whole point: BM25 scores (unbounded, corpus-dependent) and cosine/dot-product similarities (roughly 0–1) live on incompatible scales, so summing or averaging them directly is meaningless. RRF sidesteps normalization entirely by scoring on rank. It was introduced by Cormack, Clarke & Büttcher (SIGIR 2009), which showed this trivially simple method beats Condorcet fusion and individual learned rankers.

Two facts govern everything below. (1) The score is a sum of reciprocal ranks: score(d) = Σ 1 / (k + rank_d) over the lists in which d appears, where rank_d is the document's 1-based position in that list and k is a smoothing constant; a document missing from a list simply contributes nothing from it (no penalty). (2) k is a magic number whose default differs across engines — 60 in the original paper, Elasticsearch, OpenSearch, and Weaviate's rankedFusion, but 2 in Qdrant — so identical fusion logic produces different orderings on different platforms. Pin it explicitly.

The formula

For a document d appearing across query result lists L:

score(d) =  Σ   1 / (k + rank_L(d))
          L: d∈L

  • rank_L(d) is 1-based (top result = rank 1).
  • k (the "rank constant", ≥ 1) flattens the curve: larger k shrinks the gap between rank 1 and rank 2, giving lower-ranked documents more relative say. With the common k = 60, rank 1 contributes 1/61 ≈ 0.0164, rank 2 1/62 ≈ 0.0161, rank 10 1/70 ≈ 0.0143 — a deliberately small, slowly decaying per-list contribution.
  • A document ranked highly in multiple lists accumulates multiple contributions, which is what lifts consensus results to the top.

Worked micro-example, k = 60, two lists:

vector list:  A, B, C      (A=rank1, B=rank2, C=rank3)
bm25 list:    C, A, D      (C=rank1, A=rank2, D=rank3)

A = 1/61 + 1/62 = 0.03252   ← near the top of BOTH → wins
C = 1/63 + 1/61 = 0.03227
B = 1/62         = 0.01613
D = 1/63         = 0.01587

A ranks first because it is near the top of both lists; a document that is #1 in only one list (B, D) cannot outrank a strong-in-both document.

Hand-rolled RRF (e.g. fusing a pgvector similarity query with a Postgres full-text / BM25 query yourself):

def rrf(ranked_lists, k=60):
    scores = {}
    for ranked in ranked_lists:                        # each: doc ids, best first
        for rank, doc_id in enumerate(ranked, start=1):  # 1-based rank
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

vector_hits = ["A", "B", "C"]
bm25_hits   = ["C", "A", "D"]
fused = rrf([vector_hits, bm25_hits])                  # -> ['A', 'C', 'B', 'D']

Note start=1: RRF ranks are 1-based. A 0-based index gives rank 0 a 1/(k+0) contribution and silently inflates the top document of every list.

Two knobs recur:

  • rank_window_size / prefetch limit — how many results from each list enter fusion. In Elasticsearch it defaults to the final size; a document outside the window in both lists is invisible to RRF even if fusion would have ranked it highly. Set the window ≥ your final size, larger when the two retrievers disagree.
  • weights — by default every list carries equal weight. To bias toward lexical or semantic, use weighted RRF (score += w_L / (k + rank)), Qdrant per-prefetch weights (v1.17+), or Weaviate's alpha (0 = pure BM25, 1 = pure vector, default 0.75). Do not try to bias by scaling raw scores — RRF never looks at them.

RRF vs score-based fusion

RRF's rank-only design is a feature and a limitation:

  • Use RRF when retriever scores are on different or uncalibrated scales (the usual BM25-vs-cosine case), when you have no eval data, or as a robust default. One retriever's outlier scores cannot distort the fusion.
  • Prefer score-based fusion (Weaviate relativeScoreFusion, Qdrant dbsf, or min-max + weighted sum) when your retrievers' scores are well-calibrated and their magnitudes are meaningful — RRF throws that signal away, collapsing "0.99 vs 0.55 cosine" and "rank 1 vs rank 2" into the same tiny gap.

RRF is also not reranking. It only reorders documents the retrievers already returned; it cannot surface a relevant document neither retriever found. For precision on the top-k, follow fusion with a cross-encoder reranker (see rerankers). RRF is the cheap consensus step; the reranker is the expensive precision step.

Common gotchas

1. k default is not universal — 60 in the paper / Elasticsearch / OpenSearch / Weaviate, but 2 in Qdrant. The same fusion "with defaults" reorders differently across engines. Pin k explicitly and treat it as a tunable, not a constant.
2. Rank is 1-based — the top result is rank 1, contributing 1/(k+1). Hand-rolled RRF using a 0-based index gives rank 0 a 1/k contribution, inflating the top document and skewing every score. Use enumerate(list, start=1).
3. RRF discards score magnitude — a document that is a runaway #1 in vector search scores almost identically to a marginal #1. If your scores are calibrated and magnitude carries meaning, relativeScoreFusion / DBSF can beat RRF. RRF's blindness to scale is exactly why it is robust and why it can underperform.
4. The fusion window truncates before fusion — only the top rank_window_size / prefetch-limit of each list participates. A document just outside both windows is invisible regardless of how well it would fuse. Widen the window when precision@k matters or the retrievers disagree.
5. Missing from a list = zero, not a penalty — a document strong in BM25 but absent from the vector list still scores from BM25 alone; there is no negative signal for absence. Consensus is rewarded; disagreement is simply not punished.
6. Equal weight by default — bias with weighted RRF / per-prefetch weights / Weaviate alpha, never by pre-scaling raw scores (RRF will not see them).
7. Ties look non-deterministic — documents with identical fused scores are ordered by the engine's tiebreaker (often internal doc id), so equal-score results can appear in a "random" order across runs or shards. Add an explicit tiebreaker if stable ordering matters.
8. Fusion ≠ retrieval quality — RRF only reorders what you retrieved; garbage from both retrievers fuses into garbage. Fix recall first (the dense leg: HNSW ef_search; the sparse leg: BM25), then fuse.
