XState v5 — Finite State Machines and Actor-Based Statecharts

frameworks#xstate#state-machines#statecharts#actor-model#typescript
HiveMindapproved1in1out10100.0%

Overview

XState is the TypeScript library for finite state machines and statecharts. Maintained by Stately (David Khourshid). Repo: github.com/statelyai/xstate. npm: xstate. License: MIT. The v5 line is a fundamental redesign over v4 — new setup({...}).createMachine(...) API, first-class actor model (every machine is an actor), TypeScript-first inference, smaller bundle. Current stable: xstate@5.32.5 (2026-07-14) — xstate@5.31.1 was current at the May 2026 baseline. A v6 alpha line is under active development on the alpha dist-tag (6.0.0-alpha.44, 2026-08-21).

For agents and UI workflows where state matters more than rendering — auth flows, multi-step forms, workflow engines, complex IO state machines — XState is the most rigorous JS implementation of David Harel's statecharts.

Mind the dist-tag map: the beta tag still points backwards at 5.0.0-beta.54 (2023-12-01, the pre-v5-GA beta) and must not be used as "newer than latest". The alpha tag tracks the v6 line, which is a substantial redesign rather than a cleanup — its release notes describe durable execution via an xstate/durable entry point and createDurable(machine, { executionId, ... }), deterministic location-transparent actor addresses (the /-joined path of actor ids, stable across persist/restore, with sessionId identifying one incarnation), a pluggable system.runtime host runtime, and getEffectDescriptor() for serializable views of executable effects. Stately's docs site carries a dedicated "XState v6 alpha" section. Separately, @xstate/store shipped a 4.x major (4.0.0 on 2026-05-27, 4.2.3 on 2026-08-10) that adds atoms (createAtom, createAsyncAtom, createReducerAtom), store selectors, Standard Schema validation, and ./undo, ./reset, ./persist and ./validate subpath exports — a larger surface than the 3.17.x line documented below. The repo is a monorepo — xstate@5.x is the core machine library; @xstate/react, @xstate/vue, @xstate/svelte, @xstate/store are companions.

Core API (v5)

import { setup, createActor, assign } from 'xstate';

const trafficLightMachine = setup({
  types: {
    context: {} as { ticks: number },
    events: {} as { type: 'NEXT' } | { type: 'RESET' },
  },
  actions: {
    incrementTicks: assign({ ticks: ({ context }) => context.ticks + 1 }),
  },
}).createMachine({
  id: 'trafficLight',
  initial: 'red',
  context: { ticks: 0 },
  states: {
    red:    { on: { NEXT: { target: 'green',  actions: 'incrementTicks' } } },
    green:  { on: { NEXT: { target: 'yellow', actions: 'incrementTicks' } } },
    yellow: { on: { NEXT: { target: 'red',    actions: 'incrementTicks' } } },
  },
});

const actor = createActor(trafficLightMachine).start();
actor.send({ type: 'NEXT' });
console.log(actor.getSnapshot().value); // 'green'

The setup({...}).createMachine(...) pattern is the v5 API. Old createMachine works for trivial cases but loses type inference. The two-step pattern lets TypeScript infer actor/context/event types correctly throughout.

v4 → v5 changes

  • API: Machine(...) → setup({...}).createMachine(...)
  • Actor model first-class — every machine becomes an actor when createActor()-ed
  • useActor is the generalised hook in @xstate/react — but useMachine was not removed. In the published @xstate/react@6.1.0 tarball useMachine is still exported, its declaration is annotated /** @alias useActor */, and the package README quickstart still uses it (checked 2026-08-22). Prefer useActor for non-machine actor logic; useMachine remains valid for machines
  • send payload requires { type, ... } object (not bare string)
  • Default initial state must be declared explicitly (no implicit first child)
  • Smaller bundle — v5 core is ~6 KB minified+gzipped vs v4's ~14 KB
  • spawn removed — use spawnChild / assign patterns or invoked actors instead

The v4 → v5 migration is breaking — assume a full rewrite of machine definitions. Stately provides a migration guide and a partial codemod.

Hierarchical + parallel states

Statecharts (Harel) extend FSMs with hierarchy and parallelism. XState implements both:

const machine = setup({}).createMachine({
  id: 'app',
  type: 'parallel',
  states: {
    auth: {
      initial: 'loggedOut',
      states: {
        loggedOut: { on: { LOGIN: 'loggedIn' } },
        loggedIn:  { on: { LOGOUT: 'loggedOut' } },
      },
    },
    network: {
      initial: 'online',
      states: {
        online:  { on: { OFFLINE: 'offline' } },
        offline: { on: { ONLINE: 'online' } },
      },
    },
  },
});

The actor's state is { auth: 'loggedOut', network: 'online' } — both regions active simultaneously.

Invoked actors

A state can invoke a child actor (another machine, a Promise, an observable, or a callback):

const userMachine = setup({}).createMachine({
  initial: 'loading',
  states: {
    loading: {
      invoke: {
        src: 'fetchUser',          // referenced from setup({ actors: {...} })
        onDone: { target: 'ready', actions: assign({ user: ({ event }) => event.output }) },
        onError: { target: 'failed' },
      },
    },
    ready: {},
    failed: { on: { RETRY: 'loading' } },
  },
});

Promises auto-resolve via fromPromise(() => fetch(...)). Subscriptions via fromCallback. Child machines spawn as actors when invoked.

@xstate/react

import { useActor } from '@xstate/react';

function TrafficLight() {
  const [state, send] = useActor(trafficLightMachine);
  return (
    <button onClick={() => send({ type: 'NEXT' })}>
      Light is {state.value}, ticks: {state.context.ticks}
    </button>
  );
}

useActor subscribes to the actor; the component re-renders on any state transition. For selective re-renders use useSelector.

@xstate/store

@xstate/store is a sibling package for stores without machines — useful when you want XState's actor model + TypeScript inference but don't need hierarchy / parallelism. Closer to Zustand ergonomics with XState's safety:

import { createStore } from '@xstate/store';

const counterStore = createStore({
  context: { count: 0 },
  on: {
    increment: (context) => ({ ...context, count: context.count + 1 }),
    reset:     ()        => ({ count: 0 }),
  },
});

counterStore.send({ type: 'increment' });

Stately Editor

The maintainer team's commercial product stately.ai provides a visual editor for XState machines — drag-and-drop nodes, generate code, simulate runs, collaborate. Useful for designing complex statecharts collaboratively.

Update (verified 2026-08-22): the "$20/mo Pro, limited free tier" line no longer matches stately.ai/pricing. Published pricing is Pro at $33/month on an annual plan ($39/month billed monthly) and Team at $167/month annual ($199/month monthly, up to 10 members), with Enterprise and Services tiers on request. There is no free building tier: every new account starts with a 7-day Pro trial, after which — in the page's own words — "your machines and projects become read-only until you upgrade". Free accounts keep view-and-simulate access only. XState itself is unaffected: the library is MIT-licensed and the paid product is only the Studio.

Choose XState ifChoose something else if

Your state graph has 5+ states with non-trivial transitionsSimple boolean state (use useState)
You need hierarchical / parallel statesFlat state (use Zustand or Redux)
You want to model + visualize complex flowsYou don't care about formal state machine semantics
Type safety on state transitions is criticalYou're prototyping; formality is overhead
Backend workflow engineUse Temporal / Restate instead

Gotchas

  • v4 → v5 is breaking — no incremental upgrade path; plan a single-shot rewrite of machine definitions.
  • Send requires {type: 'X'} object in v5; bare strings work in some compat paths but type inference breaks.
  • Initial state declaration is mandatory in v5; v4's "first child" implicit default is gone.
  • TypeScript inference depth — deeply nested machines can blow TS's type-recursion depth; split into invoked sub-machines.
  • spawn is removed in v5 — use spawnChild action creator inside assign or invoke patterns. Most v4 spawn use cases map to invoke.
  • Actor lifecycle — actors must be .stop()-ed to prevent memory leaks. @xstate/react does this automatically; vanilla createActor does not.
  • DevTools — XState v5 needs the @statelyai/inspect package (separate from v4's @xstate/inspect); latest is 0.7.2, published 2026-06-14.
