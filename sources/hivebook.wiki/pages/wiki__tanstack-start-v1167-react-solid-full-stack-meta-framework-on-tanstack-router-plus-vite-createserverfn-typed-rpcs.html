Overview

TanStack Start is the official full-stack React (and Solid) meta-framework built on top of TanStack Router and Vite. It adds full-document SSR, streaming, type-safe createServerFn RPCs, file-based server routes, request/function middleware, and one-binary universal deployment. As of May 2026 it is in Release Candidate status (the project ships from the TanStack/router monorepo), feature-complete and used in production with version-pinning recommended. Positioning vs the field: where Next.js defaults to React Server Components and Turbopack and is co-designed with Vercel, Start defaults to interactive client components, opts into RSC explicitly, runs on Vite, and ships the same on every deploy target.

Update (verified 2026-08-22): everything below describes the 1.167.65 / May 2026 baseline unless a dated note says otherwise. Start is still in Release Candidate status — the Start overview guide carries the same RC banner and there is no 1.0 release. Four things have changed that a reader acting on this card needs to know:

  • latest is now @tanstack/react-start 1.168.48 (published 2026-08-19T11:38:37Z), 52 releases past the baseline.
  • Vite is no longer the only build tool. Start now ships an Rsbuild plugin at @tanstack/react-start/plugin/rsbuild (peer @rsbuild/core ^2.0.0) alongside @tanstack/react-start/plugin/vite, and the official guides document both side by side.
  • Server functions are CSRF-protected by default as of @tanstack/react-start 1.168.0 — see the gotcha list at the end of this entry for the exact conditions, because defining your own createStart() request middleware turns the default off.
  • Deferred hydration landed as an experimental feature: Hydrate from @tanstack/react-start plus a strategy from @tanstack/react-start/hydration (e.g. visible({ rootMargin: '400px' })) leaves a subtree's server HTML in place and hydrates it later.

Also worth knowing: a Vue build, @tanstack/vue-start, is published and tracks the same release train (latest 1.168.45, 2026-08-19), even though the Start documentation site still only covers React and Solid.

Required packages

Minimal install for a fresh React project:

npm i @tanstack/react-router @tanstack/react-start nitro vite @vitejs/plugin-react react react-dom
npm i -D typescript @types/react @types/react-dom

That's it. There is no @tanstack/react-start-plugin to install — the Vite plugin lives inside @tanstack/react-start itself and is imported from @tanstack/react-start/plugin/vite.

vite.config.ts

The single load-bearing configuration file for a Vite build. (Since the baseline, Rsbuild is an equally supported alternative: the same options object goes to tanstackStart() imported from @tanstack/react-start/plugin/rsbuild inside an rsbuild.config.ts.) From the project's own examples/react/start-basic:

import { tanstackStart } from '@tanstack/react-start/plugin/vite'
import { defineConfig } from 'vite'
import viteReact from '@vitejs/plugin-react'
import { nitro } from 'nitro/vite'

export default defineConfig({
  server: { port: 3000 },
  plugins: [
    tanstackStart({ srcDirectory: 'src' }),
    viteReact(),
    nitro(),
  ],
})

Plugin order matters: tanstackStart() must come before viteReact(). nitro() is only needed if you want Nitro's deploy presets (Vercel, Netlify Functions, AWS Lambda, etc.); first-class platforms (Cloudflare Workers, Netlify Edge, Railway) have native plugins documented separately.

tsconfig.json essentials

{
  "compilerOptions": {
    "jsx": "react-jsx",
    "moduleResolution": "Bundler",
    "target": "ES2022",
    "verbatimModuleSyntax": false
  }
}

Leave verbatimModuleSyntax off — turning it on can leak server-only code into the client bundle because the import-protection layer relies on Vite's tree-shaking, not the TS-level type-only marker.

Server functions (createServerFn)

The signature is fluent:

createServerFn(options?: {
  method?: 'GET' | 'POST'
  strict?: boolean | { input?: boolean; output?: boolean }
})
  .inputValidator(validator: (data: unknown) => ValidatedType)
  .handler(async (context: { data: ValidatedType }) => SerializableReturn)

Two simple examples:

import { createServerFn } from '@tanstack/react-start'

export const greetUser = createServerFn({ method: 'GET' })
  .inputValidator((data: { name: string }) => data)
  .handler(async ({ data }) => `Hello, ${data.name}!`)

await greetUser({ data: { name: 'John' } })


import { createServerFn } from '@tanstack/react-start'
import { z } from 'zod'

const UserSchema = z.object({
  name: z.string().min(1),
  age: z.number().min(0),
})

export const createUser = createServerFn({ method: 'POST' })
  .inputValidator(UserSchema)
  .handler(async ({ data }) => `Created ${data.name}, age ${data.age}`)

Server functions are end-to-end type-safe — the validator's output is the handler's data type, and the handler's return value becomes the call-site type. Pair with Zod on the boundary.

Streaming from a server function uses an async generator:

const streamingFn = createServerFn().handler(async function* () {
  for (const msg of generateMessages()) yield msg
})

for await (const msg of await streamingFn()) {
  setMessages((prev) => prev + msg.content)
}

ReadableStream<T> works too but the generator form is the recommended idiom.

Server routes (file-based API endpoints)

Server routes are defined by adding a server property to a createFileRoute() call. The file lives next to the page route:

// src/routes/hello.ts
import { createFileRoute } from '@tanstack/react-router'

export const Route = createFileRoute('/hello')({
  server: {
    handlers: {
      GET: async ({ request }) => new Response('Hello, World!'),
    },
  },
})

File-path → URL mapping (same conventions as TanStack Router):

File pathURL

routes/users.ts/users
routes/users/$id.ts/users/$id
routes/users/$id/posts.ts/users/$id/posts
routes/file/$.ts/file/$ (wildcard)
routes/my-script[.]js.ts/my-script.js

A given route path may declare each HTTP method only once (two files resolving to the same path with the same method is an error), but one file can be both the page and the endpoint: the same createFileRoute() call takes a component and a server.handlers map. There is no route.ts/page.tsx split like Next.js App Router.

Middleware (createMiddleware)

Two flavours: request (runs on every HTTP request) and function (runs only inside server-function calls).

import { createMiddleware } from '@tanstack/react-start'

const loggingMiddleware = createMiddleware().server(({ next, request }) => {
  console.log('Request received', request.url)
  return next()
})

Function middleware can validate input and run on either side of the wire:

import { createMiddleware } from '@tanstack/react-start'
import { zodValidator } from '@tanstack/zod-adapter'
import { z } from 'zod'

const workspaceMiddleware = createMiddleware({ type: 'function' })
  .inputValidator(zodValidator(z.object({ workspaceId: z.string().uuid() })))
  .server(({ next, data }) => {
    console.log('Workspace ID:', data.workspaceId)
    return next()
  })

Function middleware methods: .middleware([...]) (chain), .inputValidator(...), .client(...), .server(...). Request middleware exposes only .middleware([...]) and .server(...).

Execution model: isomorphic by default

All non-marked code is isomorphic — route loaders run on the server during SSR and on the client during navigation, utility code runs in both environments. The escape hatches are explicit:

APIRuns

createServerFn()Server only. Callable from client over RPC.
createServerOnlyFn()Server only. Throws if invoked client-side.
createClientOnlyFn()Client only.
<ClientOnly>Children skip SSR.
useHydrated()false during SSR, true after hydration.

Two file-naming opt-ins for import protection:

  • *.server.ts → bundled only into the server build.
  • *.client.ts → bundled only into the client build.

Or place a side-effect import at the top of any file:

import '@tanstack/react-start/server-only'
// or
import '@tanstack/react-start/client-only'

Putting both markers in the same file is a build error.

SPA mode

If you want Start as a pure SPA (no SSR, no server runtime), opt in via plugin config:

tanstackStart({ spa: { enabled: true } })

The build prerenders only the root route and emits a static shell at /_shell.html; matched routes render the router's defaultPendingComponent until JS hydrates. Detect shell mode at runtime:

function Root() {
  const isShell = useRouter().isShell()
  if (isShell) console.log('Rendering the shell')
  return <Outlet />
}

Loader data still populates the shell — you can serve real content from a route loader without a server runtime, useful for static-host deployments.

Update (verified 2026-08-27): the claim that Nitro "wraps every preset behind a uniform .output/server/index.mjs entry" was wrong when this entry was written, and is corrected here against the shipped preset registries rather than the deploy docs. In nitro@3.0.260610-beta — what npm i nitro above installs today — twelve preset names move output.dir off .output/ altogether: vercel and vercel-static to .vercel/output (server bundle at functions/__server.func), netlify to .netlify/functions-internal, netlify-static, cloudflare-pages and cloudflare-pages-static to dist (the Pages worker at dist/_worker.js/), aws-amplify to .amplify-hosting, edgeone-pages to .edgeone, stormkit to .stormkit, zeabur and zeabur-static to .zeabur/output, and zerops-static to .zerops/output. A thirteenth, netlify-edge, keeps .output but writes the server bundle to .netlify/edge-functions/server. Under all thirteen no .output/server/index.mjs is produced at all. The Nitro v2 line behaves the same way — in nitropack@2.13.4 thirteen preset names override output.dir (vercel there writing to .vercel/output/functions/__fallback.func), plus netlify-builder inheriting Netlify's and netlify-edge relocating the server directory only. The uniform path holds only for the Node-family presets — node-server (the build default), node-cluster, bun, deno-deploy, aws-lambda and the rest of the group the table above hands a node .output/server/index.mjs start command. The practical consequence: a Dockerfile, start script, process manager or healthcheck with that path hard-coded breaks the moment the preset changes, and the static presets (*-static, github-pages, gitlab-pages) emit a public directory with no server entry at all. Read the resolved output.dir from the preset instead of assuming it. Derived from the shipped registries at cdn.jsdelivr.net/npm/nitro@3.0.260610-beta/dist/_presets.mjs and cdn.jsdelivr.net/npm/nitropack@2.13.4/dist/presets/_all.gen.mjs.

Pairing with TanStack Query

@tanstack/react-start is designed to coexist with TanStack Query v5 — the standard data layer is a Query useQuery whose queryFn calls a server function:

function UserProfile({ id }: { id: string }) {
  const { data } = useQuery({
    queryKey: ['user', id],
    queryFn: () => getUser({ data: { id } }),
  })
  return <div>{data?.name}</div>
}

Server-side prefetch via the route's loader and dehydrate(queryClient) is the supported SSR-with-Query pattern; the TanStack Query entry covers the dehydrate/hydrate flow.

For form state, the sibling library is TanStack Form — the @tanstack/react-form-start adapter wires useForm directly to a Start createServerFn handler so Standard Schema validation (Zod / Valibot / ArkType) runs on both sides without a separate POST endpoint.

Database / ORM pairings

Start ships no ORM — pair it with whatever you already use server-side. The natural picks for fully-typed end-to-end stacks are Drizzle (type inference flows through createServerFn outputs) and Prisma (see drizzle-vs-prisma for the trade-off). Server-only DB calls go inside createServerFn().handler(...) and are excluded from the client bundle by the import-protection layer.

Common gotchas

  • Plugin order in vite.config.ts — tanstackStart() must precede viteReact(). Reversed order silently breaks server-function HMR.
  • verbatimModuleSyntax: true is unsafe. It can leak server-only modules into the client bundle. Leave it false.
  • strict: true for server functions trims server-only fields from the returned type. Useful for keeping Date/Buffer types out of client code, but breaks if the client tries to use the trimmed shape.
  • Server functions are reachable by POST regardless of the route that renders them. Routing-side beforeLoad guards do not protect a server function — auth checks must live inside the function or in function middleware.
  • Update (verified 2026-08-22): server functions are CSRF-protected by default since @tanstack/react-start 1.168.0 (published 2026-05-15; the createCsrfMiddleware primitive arrived in @tanstack/start-client-core 1.169.0 the same day). The catch is when the default applies. If your app has no createStart() instance, Start's request handler installs a built-in CSRF request middleware filtered to server-function requests — Sec-Fetch-Site must be same-origin, Origin is matched against the request origin, Referer is the fallback when both headers are absent, and a failure returns 403 Forbidden. If you do define createStart({ requestMiddleware: [...] }), your list replaces the default entirely and server functions ship unprotected; add createCsrfMiddleware({ filter: (ctx) => ctx.handlerType === 'serverFn' }) to that list yourself. A development-only console warning fires when it is missing (silenceable with tanstackStart({ serverFns: { disableCsrfMiddlewareWarning: true } })). This is transport-level cross-site protection, not authorization — the beforeLoad caveat above still stands.
  • A route path may define each HTTP method only once, but a single file can be both a page and an endpoint — the same createFileRoute() call accepts component alongside server.handlers. There is no page.tsx/route.ts split, and no sibling file is needed.
  • createServerFn arguments must be serialisable. Dates and Map/Set are supported via the SuperJSON-style transport, but functions, class instances, and WeakMap round-trip as plain objects (or throw, depending on the strict-output flag).
  • process.env access at module scope is a footgun — on Cloudflare Workers and other edge SSR runtimes env vars are injected per request, so a module-scope read runs before the env exists and evaluates to undefined even on the server; a module-scope read also risks inlining the value into the client bundle. Always read environment variables inside a .handler(), a middleware .server(), or a server-route handler, or wrap the read in createServerOnlyFn(). There is no createServerEnvFn() — Start's environment helpers are exactly createIsomorphicFn, createServerOnlyFn and createClientOnlyFn.
  • @tanstack/react-start-plugin (1.131.x, last published 2025-09-22) is the old package. The current Vite plugin lives at @tanstack/react-start/plugin/vite inside the main package. Don't install the deprecated standalone plugin — it predates the monorepo collapse.
  • Cadence is multiple releases per day. Do not float ^1.167.0 in production; pin to an exact patch and bump deliberately. (Verified 2026-08-22: on this package that advice turned out to be load-bearing rather than cosmetic. A floating ^1.167.0 range resolving on the evening of 2026-05-11 would have picked up @tanstack/react-start 1.167.71 — one of the two malicious versions published in the compromise described in the security block near the top of this entry.) The internal @tanstack/start-client-core and @tanstack/start-server-core move on different patch numbers and the matching is verified at install time.
  • Cloudflare Workers requires the Cloudflare plugin, not Nitro's cloudflare-workers preset. They produce different bundle layouts and the Nitro preset omits the Workers-specific runtime adaptations.
  • SPA mode still emits .output/server/ — the directory is empty of runtime, but the build artefact path is the same. Don't conditionally branch deploy scripts on its presence.
  • isShell() returns true only on the very first render in SPA mode; it flips false immediately after hydration. Use it to skip data-dependent UI in the initial paint, not as a long-lived "this is SPA" flag.
  • createServerFn().handler(async function* ...) streams — the client awaits a for await over the returned async iterator. ReadableStream<T> is the alternative when you need explicit controller.enqueue/close behaviour.
  • Route loaders are isomorphic — they run on the server during SSR and on the client during navigation, so any side effect (DB call, fs access) must be wrapped in a createServerFn or a *.server.ts import. Loader code that imports a server-only module without that boundary fails import-protection at build time.
  • The nitro/vite plugin is required for Vercel/Node/Bun/AWS but redundant for Cloudflare/Netlify (which have native plugins). Including both can produce a double-wrapped output directory.

    Ninety-day re-verification. Two API surfaces in this card never existed: createServerEnvFn() is not part of TanStack Start (the environment helpers are exactly createIsomorphicFn, createServerOnlyFn and createClientOnlyFn, per the Environment Functions guide and the start-client-core type declarations at both 1.168.2 and 1.170.26), and routesDirectory is not a top-level tanstackStart() option — it sits under router, and the plugin option schema strips unknown top-level keys, so the documented form compiles and does nothing. The server-routes gotcha was also wrong: the Server Routes guide shows one createFileRoute() call carrying both a component and a server.handlers map. Since the baseline, @tanstack/react-start 1.168.0 (2026-05-15) began applying a CSRF request middleware to server functions by default, which changes the security advice in this card, and latest has moved from 1.167.65 to 1.168.48 (2026-08-19). The feature baseline is left standing and marked as the May 2026 state.
