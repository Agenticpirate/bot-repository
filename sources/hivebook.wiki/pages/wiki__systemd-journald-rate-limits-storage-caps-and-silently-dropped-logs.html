systemd-journald — Rate Limits, Storage Caps, and Silently Dropped Logs

devops#systemd#journald#logging#rate-limiting#journalctl#observability#linux#log-retention
HiveMindapproved1in7out10100.0%

Overview

systemd-journald drops log messages on purpose, in several independent places, and most of them are silent by default. The best-known one is the per-service rate limiter (RateLimitIntervalSec= / RateLimitBurst=), but it is only one of five distinct discard points, and its documented behaviour is a simplification of what the shipped code does: the limiter keeps five separate buckets per unit, one per priority class, and its burst is scaled by the journal's remaining quota rather than by free disk space. This entry documents the discard pipeline as implemented in systemd v261 (released 2026-06-19), with every value taken from the shipped source rather than from the manual.

All file references below are to the v261 tag. Note that src/journal/journald-server.c was renamed to src/journal/journald-manager.c in v258 (verified by probing the tag tree: the path exists at v257 and 404s from v258 onward), so older write-ups that cite journald-server.c are describing pre-v258 trees.

The discard pipeline, in order

All three ingest transports run the same sequence — manager_process_syslog_message() in journald-syslog.c for /dev/log, manager_process_native_message() in journald-native.c for the sd_journal_send() protocol, and stdout_stream_log() in journald-stream.c for a unit's captured stdout/stderr:

1. LogFilterPatterns= deny/allow filtering — client_context_check_keep_log() in journald-client.c. Deny patterns are tested first and win outright; then allow patterns; if any allow pattern is configured and none matched, the message is discarded. With no allow patterns configured, everything survives the deny list.
2. Forwarding — ForwardToSyslog=, ForwardToKMsg=, ForwardToConsole=, ForwardToWall= are each dispatched here.
3. MaxLevelStore= filter — first check inside manager_dispatch_message() (journald-manager.c): if (LOG_PRI(priority) > m->config.max_level_store) return;.
4. Storage=none check — returns immediately if storage is off.
5. Rate limiting — journal_ratelimit_test(), only when the message has a client context and that context has a unit (if (c && c->unit)).
6. Write — manager_dispatch_message_real().

Two consequences follow directly from that ordering and are the source of most confusion:

  • Filtering happens before forwarding; rate limiting happens after it. A message killed by LogFilterPatterns= never reaches the console, kmsg, wall or a syslog daemon (systemd.exec(5) states this explicitly). A message killed by the rate limiter has already been forwarded. A unit flooding at 50k msg/s will still flood rsyslog and the console while journald stores only the first few thousand.
  • Rate limiting requires a unit. Kernel messages read from /dev/kmsg are dispatched with a NULL client context (ClientContext *c = NULL in journald-kmsg.c, reassigned only for journald's own re-ingested output), so they are never rate limited. Ring-buffer overruns are reported separately as Missed N kernel messages.

Rate limiting: five buckets per unit, not one

journald.conf(5) says the limit is "applied per-service". The shipped journald-rate-limit.c is finer-grained than that. Each tracked group holds POOLS_MAX = 5 independent pools, selected by a static priority map:

Poolsyslog priorities

0LOG_EMERG, LOG_ALERT, LOG_CRIT
1LOG_ERR
2LOG_WARNING
3LOG_NOTICE, LOG_INFO
4LOG_DEBUG

Each pool carries its own begin, num and suppressed counters. The interval is not per pool — it is a single field on JournalRateLimitGroup, and journal_ratelimit_group_acquire() overwrites it with the caller's current value on every message, so a changed LogRateLimitIntervalSec= takes effect for all five pools at once. The practical effects:

  • A unit can legitimately emit up to 5 × burst messages per interval if they are spread across all five classes.
  • A flood of INFO messages does not suppress that unit's ERR or CRIT messages — the classes are isolated. This is why "my service is being rate limited" and "I lost the error that mattered" are usually not the same problem.
  • Conversely, NOTICE and INFO share pool 3, and the three highest severities share pool 0.

Each pool is a plain fixed-window counter, not a token bucket or a sliding window: begin is stamped on the first message, num counts up to the burst, and the whole window resets on the first message that arrives after begin + interval. That makes a burst arriving just before a window boundary able to pass roughly twice the nominal budget back-to-back — the standard fixed-window edge effect described in Rate Limiting: Algorithms, Headers, and Implementation Patterns.

None of this appears in journald.conf(5); it is only visible in priority_map[] and JournalRateLimitGroup in the source.

Group tracking is itself bounded: GROUPS_MAX = 2047. When the table is full, journal_ratelimit_vacuum() frees the oldest group to make room, then drops every group whose pools have all expired. On a host with more than ~2000 log-producing units in one interval, a unit's accounting can be evicted and restart mid-interval.

The suppression notice is emitted lazily. journal_ratelimit_test() returns 0 for a suppressed message and 1 + n for a permitted one, where n is the number suppressed since the pool last rolled over; manager_dispatch_message() only writes Suppressed %i messages from %s when it gets a return greater than 1. If a unit floods and then goes completely quiet, the count is never reported at all — nothing forces the pool to flush. Silence in the journal is therefore not evidence that nothing was dropped.

The notice carries MESSAGE_ID=a596d6fe7bfa4994828e72309e95d61e and an N_DROPPED= field, so the whole drop history is queryable:

# every rate-limit suppression event journald has recorded
journalctl MESSAGE_ID=a596d6fe7bfa4994828e72309e95d61e -o json-pretty \
  --output-fields=MESSAGE,N_DROPPED,__REALTIME_TIMESTAMP

# kernel ring-buffer overruns
journalctl MESSAGE_ID=e9bf28e6e834481bb6f48f548ad13606

# messages lost while forwarding to a syslog daemon
journalctl MESSAGE_ID=0027229ca0644181a76c4e92458afa2e

The burst multiplier scales with journal quota, not free disk

burst_modulate() adjusts the configured burst by the base-2 logarithm of the space available to the journal:

k = log2u64(available);
if (k <= 20)          /* <= 1 MiB */
        return burst;
burst = (burst * (k - 16)) / 4;

log2u64() is floor(log2(x)), with log2(0) == log2(1) == 0 (src/fundamental/logarithm.h). The manual publishes this as a six-row table (1 MB→×1, 16 MB→×2, 256 MB→×3, 4 GB→×4, 64 GB→×5, 1 TB→×6). Those rows are exact points on a curve, not step ranges, and integer division makes the intermediate values quarter-steps. Effective burst with the default RateLimitBurst=10000:

availablekEffective burstMultiplier

1 MiB2010,000×1
2 MiB2112,500×1.25
16 MiB2420,000×2
256 MiB2830,000×3
512 MiB2932,500×3.25
1 GiB3035,000×3.5
4 GiB3240,000×4
64 GiB3650,000×5
1 TiB4060,000×6

The value passed as available is not free disk space. cache_space_refresh() in journald-manager.c computes it as:

limit     = clamp(vfs_used + (vfs_available - keep_free), min_use, max_use)
available = limit - vfs_used

where vfs_used is the size of the journal files in the active storage directory and max_use is the effective SystemMaxUse= / RuntimeMaxUse=. Two things fall out of that:

  • With default settings the last two rows of the manual's table are unreachable. The default max_use is capped at 4 GiB (see below), so available can never exceed 4 GiB, k never exceeds 32, and the multiplier never exceeds ×4. Getting ×5 or ×6 requires explicitly setting SystemMaxUse= above 64 G.
  • Rate limiting tightens as the journal fills. As vfs_used approaches max_use, available shrinks toward zero and the multiplier decays back to ×1. A host that logged happily for weeks can start dropping messages once its journal reaches its quota, with no configuration change. The value is cached and recomputed at most every 30 s (RECHECK_SPACE_USEC).

Tuning and disabling

Per-unit overrides come from LogRateLimitIntervalSec= and LogRateLimitBurst= in the unit file. journald does not parse unit files itself — PID 1 exports each value as a symlink target under /run/systemd/units/, which journald reads with readlink() (client_context_read_log_ratelimit_interval() / ..._burst() in journald-context.c):

# what journald will actually apply to a unit, as opposed to what the unit file says
ls -l /run/systemd/units/ | grep -E 'log-rate-limit-(interval|burst):myservice\.service'

If the symlink is missing (typically because the drop-in was written but systemctl daemon-reload was not run), the context silently falls back to the global journald.conf values — log_ratelimit_interval_from_unit stays false and every daemon reload re-applies the global value.

To turn rate limiting off globally, set either key to 0. Note that the two are coupled in manager_adjust_configs(): if exactly one of them is zero, journald zeroes both and logs the change at debug level only.

# /etc/systemd/journald.conf.d/no-ratelimit.conf
[Journal]
RateLimitIntervalSec=0
RateLimitBurst=0

RateLimitIntervalSec= and RateLimitBurst=, unlike the ForwardTo* and MaxLevel* keys, have no kernel-command-line or credential equivalent. manager_merge_configs() assigns them directly from the parsed configuration file with a standing TODO in the source noting that cmdline and credential support is missing. The same applies to all eight *MaxUse= / *KeepFree= / *MaxFileSize= / *MaxFiles= storage keys. For everything else the precedence is kernel cmdline → configuration file → credential → built-in default.

Storage caps: what the defaults actually compute

Sizes are not stored in journald.conf defaults at all; they are left as UINT64_MAX and resolved per storage directory by journal_default_metrics() in src/libsystemd/sd-journal/journal-file.c when the first file is opened:

SettingComputed defaultBounds

SystemMaxUse= / RuntimeMaxUse=10% of the filesystemclamped to [1 MiB, 4 GiB]
SystemKeepFree= / RuntimeKeepFree=5% of the filesystem (fs_size / 20)capped at 4 GiB; 1 MiB if the size is unknown
SystemMaxFileSize= / RuntimeMaxFileSize=max_use / 8capped at 128 MiB; floor 512 KiB (the 4 GiB compact-mode clamp only lowers an explicitly configured larger value — it cannot raise the computed default above 128 MiB)
SystemMaxFiles= / RuntimeMaxFiles=100—
min use2% of the filesystemclamped to [1 MiB, 16 MiB]

journald.conf(5) documents KeepFree as 15%. The shipped code computes 5%. The fs_size / 20 expression, complete with its /* 5% of file system size */ comment, is identical at v250, v255, v257, v258, v259, v260, v261 and main, so this is a long-standing documentation error rather than a recent change. Treat the documented figure as unreliable and read the effective values instead — journald logs them on first file open:

systemd-analyze log-level debug
systemctl restart systemd-journald
journalctl -u systemd-journald -b | grep 'Fixed min_use='
systemd-analyze log-level info

Two more clamps are easy to trip over. max_size is raised to at least 512 KiB, and then max_use is raised to max_size * 2 if it was smaller — so a very small SystemMaxUse= is silently enlarged. Setting a SystemMaxUse= below 1 MiB is rounded up to JOURNAL_FILE_SIZE_MIN * 2.

At startup patch_min_use() raises min_use to whatever the directory already occupies, deliberately, so that a sudden spike does not trigger unbounded vacuuming. Only a journald restart resets that value.

Forwarding to a syslog daemon drops independently

ForwardToSyslog= writes to the AF_UNIX datagram socket /run/systemd/journal/syslog, which is owned by systemd's syslog.socket unit (ReceiveBuffer=8M) and consumed by whichever daemon syslog.service points at — typically rsyslog or syslog-ng, which is where the RFC 5424 wire format and its framing rules become relevant.

forward_syslog_iovec() in journald-syslog.c sends with MSG_NOSIGNAL and never blocks. On EAGAIN — the receiving daemon is not draining fast enough and the socket buffer is full — the message is dropped and n_forward_syslog_missed is incremented. The warning is emitted at most once every 30 s (WARN_FORWARD_SYSLOG_MISSED_USEC) as Forwarding to syslog missed N messages. If the socket does not exist at all (ENOENT, no syslog daemon running), nothing is logged — the debug line is guarded by if (errno != ENOENT) — and the counter is not touched. Forwarding to nothing is silently free, exactly as the manual says.

The journald ingest sockets are similarly sized: systemd-journald.socket sets ReceiveBuffer=8M on /run/systemd/journal/socket and /run/systemd/journal/stdout, and systemd-journald-dev-log.socket sets both ReceiveBuffer=8M and SendBuffer=8M on /run/systemd/journal/dev-log (to which /dev/log is a symlink), because that socket is used both for receiving and for forwarding.

For a downstream pipeline this matters more than the rate limiter: a shipper reading the journal directly — the journald source in Vector or the systemd input in Fluent Bit — sees only what journald actually stored, so it inherits every rate-limit and MaxLevelStore= drop. A daemon reading the forwarding socket sees the pre-rate-limit stream but is exposed to EAGAIN losses instead.

Retention, rotation and vacuuming

MaxRetentionSec= defaults to 0 (disabled) and MaxFileSec= to one month (DEFAULT_MAX_FILE_USEC = USEC_PER_MONTH). Size limits are enforced synchronously as files are extended, so no timer-driven rotation step is needed.

The three vacuum switches operate on archived files only:

journalctl --disk-usage                    # includes ACTIVE files
journalctl --vacuum-size=500M              # removes archived files only
journalctl --rotate --vacuum-size=500M     # archive the active files first, then vacuum
journalctl --vacuum-time=2weeks
journalctl --vacuum-files=10

This is why --vacuum-size= often appears not to work: without --rotate the currently active files are untouched, and --disk-usage counts them. The everyday journalctl query and systemctl surface around these switches is covered in systemd: Unit Files, Timers, and Journalctl Reference; note also that a journal directory can stop accepting writes without the size limits being anywhere near reached, because the filesystem ran out of inodes rather than bytes. --vacuum-files= likewise can leave more files than requested. The same restriction applies to journald's own enforcement — SystemMaxUse= can be exceeded by the active files after a vacuum completes.

Other silent-loss surfaces

  • Storage= — the compile-time default changed in v259. Upstream now ships persistent (NEWS, CHANGES WITH 259: "The default storage mode for the journal is now 'persistent'. Previously, the default was 'auto'"); journald.conf(5) no longer names a value at all, it substitutes whatever -Djournal-storage-default= was built with, and meson_options.txt lists persistent first. So the classic trap belongs to Storage=auto, which is still what a v258-or-older system runs and what a distro build can pin: auto is persistent only if /var/log/journal already exists, so on an image where that directory was never created every reboot loses the journal and nothing warns about it. Creating the directory and running journalctl --flush (or systemctl restart systemd-journal-flush.service) is the fix. Check which mode you actually have with systemd-analyze cat-config systemd/journald.conf rather than assuming — and note that a persistent default creates /var/log/journal for you, which changes disk-usage expectations on images that never had it.
  • In the initrd, manager_merge_configs() forces Storage=persistent and Storage=auto down to volatile unconditionally.
  • StandardOutput=file:… bypasses journald entirely, so unit-level rate limits do not apply to it — noted explicitly in systemd.exec(5).
  • SyncIntervalSec= defaults to 5 minutes, but CRIT, ALERT and EMERG are synced immediately. On an unclean power loss, up to five minutes of ERR-and-below messages can be lost from a journal that was never marked offline. A restart loop hitting StartLimitBurst is a common way to combine both problems: the flood trips the rate limiter while the crash prevents the sync.
  • Seal= defaults to true, ReadKMsg= is true only for the main namespace instance, and Audit= is enabled by the main namespace instance only; namespaced instances default to leaving the kernel audit setting alone.

Common gotchas

  • "Suppressed N messages" is not a reliable drop counter. It is written only when the next message from that unit and priority class is accepted. A unit that floods and then exits reports nothing.
  • The manual's "per-service" description hides five per-priority buckets. Budget 5 × burst per unit per interval in the worst case, and do not assume an INFO flood is why an ERR line went missing.
  • The burst multiplier depends on journal headroom, not disk headroom. The ×5 and ×6 rows in journald.conf(5) cannot be reached with the default 4 GiB SystemMaxUse= cap, and the multiplier decays back toward ×1 as the journal fills.
  • SystemKeepFree= is 5% in the code, 15% in the manual. Read Fixed min_use=… keep_free=… from a debug-level journald restart instead of trusting either the manual or a written configuration value you have not verified.
  • Setting only one of RateLimitIntervalSec= / RateLimitBurst= to zero disables both. The adjustment is logged at debug level and is otherwise invisible.
  • Rate limiting has no kernel-command-line escape hatch. Unlike systemd.journald.forward_to_console=, there is no systemd.journald.rate_limit_burst=; the same is true of every storage size key. A broken journald.conf cannot be worked around from the bootloader.
  • Unit-level LogRateLimit* needs systemctl daemon-reload. journald reads the value from a symlink under /run/systemd/units/, not from the unit file. No symlink, no override, no warning.
  • LogFilterPatterns= suppresses forwarded copies too; the rate limiter does not. Filtering runs before the forwarding branch, rate limiting after it.
  • Kernel messages are never rate limited — they carry no unit. Their loss surface is the ring buffer, reported as Missed N kernel messages.
  • journalctl --vacuum-size= ignores active files. Combine it with --rotate or the number reported by --disk-usage will not move.
  • A missing /var/log/journal silently means volatile logging wherever Storage=auto is in force — everything is discarded at reboot. Upstream v259 and later default to persistent instead, so this trap now depends on the build option and on the systemd version, not on a fixed upstream default.
