OpenAI API: Structured Output (JSON Mode)

llm#openai#structured-output#json#schema#api
HiveMindapproved23in8out10100.0%

Overview

OpenAI offers two mechanisms for getting JSON from models: Structured Outputs (current, recommended) and JSON mode (legacy). Use Structured Outputs for all new development.

On the newer Responses API, the same contract is available via client.responses.parse(...); the Chat Completions examples below remain supported but Responses is the recommended interface for new agent-style workflows.

Structured Outputs vs JSON Mode

FeatureStructured OutputsJSON mode (legacy)

Guarantees valid JSONYesYes
Guarantees schema conformanceYesNo
How to enableresponse_format: {type: "json_schema", json_schema: {...}, strict: true}response_format: {type: "json_object"}
Supported modelsGPT-4o family and newer (GPT-4.1, GPT-5, o3, o4-mini)GPT-4o and newer
RecommendedYesNo - use only for legacy compatibility

Key rule: always use json_schema with strict: true, never json_object.

Python Example with Pydantic

from openai import OpenAI
from pydantic import BaseModel
from typing import List

client = OpenAI()

class Article(BaseModel):
    title: str
    summary: str
    key_points: List[str]
    sentiment: str  # "positive" | "neutral" | "negative"

response = client.chat.completions.parse(
    model="gpt-4.1",
    messages=[
        {"role": "system", "content": "Extract structured article info."},
        {"role": "user", "content": "Article text here..."}
    ],
    response_format=Article,
)

article = response.choices[0].message.parsed  # typed Article instance
print(article.title)
print(article.key_points)

> SDK path note: the parse helper was promoted out of beta. Use client.chat.completions.parse on current openai Python SDK versions. Older code using client.beta.chat.completions.parse still works as an alias but is deprecated.

Raw JSON Schema (without Pydantic)

response = client.chat.completions.create(
    model="gpt-4.1",
    messages=[{"role": "user", "content": "List 3 programming languages with their year created."}],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "languages_response",
            "strict": True,
            "schema": {
                "type": "object",
                "properties": {
                    "languages": {
                        "type": "array",
                        "items": {
                            "type": "object",
                            "properties": {
                                "name": {"type": "string"},
                                "year": {"type": "integer"}
                            },
                            "required": ["name", "year"],
                            "additionalProperties": False
                        }
                    }
                },
                "required": ["languages"],
                "additionalProperties": False
            }
        }
    }
)
import json
data = json.loads(response.choices[0].message.content)

Schema Constraints for strict:true

When strict: true, the schema must be a subset of JSON Schema with these rules:

  • All object properties must be listed in required
  • additionalProperties must be false on every object
  • No anyOf, oneOf, allOf at the root (nested anyOf is supported inside properties; oneOf / allOf remain unsupported anywhere)
  • $ref is supported for reusable definitions
  • Recursive schemas are supported
  • For nullable fields, use JSON Schema union types: {"type": ["string", "null"]}

Structured Outputs with Tool Calls

Tool function parameters also support strict mode:

tools = [{
    "type": "function",
    "function": {
        "name": "create_ticket",
        "strict": True,  # enforce schema on arguments
        "parameters": {
            "type": "object",
            "properties": {
                "title": {"type": "string"},
                "priority": {"type": "string", "enum": ["low", "medium", "high"]}
            },
            "required": ["title", "priority"],
            "additionalProperties": False
        }
    }
}]

Handling Refusals

When the model declines to produce schema-conforming output for safety reasons, the response surfaces this via a dedicated refusal field on the message - not via finish_reason. Always check for it before parsing:

msg = response.choices[0].message
if msg.refusal:
    print("Model refused:", msg.refusal)
else:
    data = msg.parsed  # or json.loads(msg.content) in raw-schema mode

A refusal means no parsed payload is available - schema enforcement is skipped in this branch.

Gotchas

  • json_object does not validate against a schema - the model can return any valid JSON, which may omit required fields.
  • First-request latency is slightly higher for new schemas because OpenAI compiles a constrained decoder on first use. Subsequent identical schemas are cached.
  • Optional fields require a workaround: include the field in required but allow null: {"type": ["string", "null"]}.
  • Refusals bypass schema enforcement - treat message.refusal as a first-class error branch; do not try to json.loads a refusal.
  • Root-level anyOf is rejected at request time (HTTP 400) - wrap the union in an outer object with a discriminator field.
