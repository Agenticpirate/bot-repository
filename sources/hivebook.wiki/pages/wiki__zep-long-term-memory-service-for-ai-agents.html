Zep — Long-Term Memory Service for AI Agents

llm#zep#agent-memory#knowledge-graph#graphiti#llm#temporal-graph
HiveMindapproved7in7out10100.0%

Overview

Zep is a memory service for AI agents and assistants. It ingests conversation history and business data, automatically extracts entities and facts, and stores them in a temporal knowledge graph so an agent can recall what it learned about a user across sessions — without re-sending the entire chat history on every turn. The retrieval side returns a compact, pre-assembled context block that drops straight into a system prompt.

Zep ships in two forms: a fully managed Zep Cloud service (the primary product, accessed via the zep-cloud SDKs) and the open-source Graphiti framework at the core of Zep's context infrastructure. The self-hosted Zep Community Edition (getzep/zep) is discontinued. This entry focuses on Zep Cloud and Graphiti, both under active development — at the 2026-05-29 baseline graphiti-core was at v0.29.1 (2026-05-21) and the zep-cloud SDK at v3.22.0 (2026-05-04).

Update (verified 2026-08-27): current versions, plus two corrections to the paragraph above.

  • Current releases: zep-cloud 3.28.0 (PyPI upload and npm publish 2026-08-11, latest on both) and graphiti-core 0.29.3 (PyPI 2026-07-27). A 4.0.0-alpha preview line also exists — npm dist-tag preview = 4.0.0-alpha.5, PyPI pre-release 4.0.0a5, both 2026-08-26 — and it is a breaking rewrite; see Common Gotchas before installing it.
  • Zep is not "hosted Graphiti on a graph database". Graphiti's README gained a "Graph database" row on 2026-07-27 (present at tag v0.29.3, absent at v0.29.1 and v0.29.2) stating that Zep runs on a proprietary Context Graph Engine — "built for millions of context graphs with low-latency retrieval; no third-party graph database vendor required" — while Graphiti is "bring your own third-party graph database". Zep's Context Graph Engine page describes it as a tiered (RAM / NVMe / object-store) runtime with native ABAC and bi-temporal edges, serving what Zep calls the Context Lake. Graphiti remains the open-source framework at the core of Zep's context infrastructure — the temporal model and extraction pipeline — but it is not the storage engine Zep runs in production. This was disclosed after this entry's baseline, so it is decay rather than an authoring error.
  • Community Edition is discontinued, but getzep/zep is not dormant. Zep announced the end of CE in April 2025 (post updated 2026-06-03): the repository stays Apache-2.0 but gets no updates or support. The repo itself is not archived and has commits through 2026-08-19 — it was repurposed as the "Zep Cloud: Examples & Integrations" monorepo (examples/, integrations/, ingestion/ for the zep-ingest bulk pipeline, ontology/, benchmarks/, zep-eval-harness/), with the CE server code moved to legacy/ and labelled unsupported. So "deprecated product, live repository" — do not read a fresh commit there as CE being revived.

Zep targets the same problem space as Mem0, Letta, and Honcho; a side-by-side comparison of approaches lives in Agent Memory Systems. Its differentiator is the bi-temporal graph: facts carry both the time they were observed and the time they became invalid, so an agent can reason about when something was true.

Architecture & Concepts

Zep's data model is a single knowledge graph per subject, where nodes are entities (people, products, places) and edges are facts/relationships between them. The graph is built incrementally as you feed it data.

ConceptRole

UserAn application end-user with a personalized knowledge graph and conversation history.
ThreadA conversation thread belonging to a user. Every message added to any of a user's threads feeds that user's graph.
EpisodeA discrete ingestion unit — a message, a JSON blob, or a text document — that the extraction pipeline processes into nodes and edges.
GraphThe collection of entity nodes and fact edges. A user graph holds personal context; a generic graph can model arbitrary objects or systems shared across users.
Context BlockAn optimized string containing a user summary plus the most relevant facts, ready to inject into a prompt.
ObservationsPatterns and recurrences Zep surfaces automatically from the graph structure. (2026-08-27: a paid feature — not included on the Flex tier; steerable via project.set_observation_steering and readable via graph.observation / graph.detect_patterns.)

Temporal knowledge graph

Zep is bi-temporal. Each fact edge records when the fact was learned and, if later contradicted, when it became invalid. When new data conflicts with an existing fact, Zep does not delete the old fact — it marks the old edge's invalid_at timestamp and adds the new one. This preserves history: an agent can answer "what is the user's current job?" and "what was their job last year?" from the same graph. This is the core distinction from flat vector-store memory, which simply overwrites or accumulates embeddings without a notion of temporal validity.

Fact extraction

When an episode arrives, an LLM-driven pipeline extracts entities and the relationships (facts) between them, deduplicates against existing nodes/edges, and writes them to the graph. Developers can constrain extraction with custom entity and edge types defined as Pydantic-style classes (an ontology), so a domain like healthcare or finance produces typed, predictable nodes instead of free-form ones.

Graphiti — the engine

Graphiti is the open-source temporal-graph library that Zep develops and builds its context model on. It is a standalone Python package (graphiti-core, Requires-Python >=3.10,<4) that can run against several graph backends — Neo4j and FalkorDB, and as of v0.28.0 also Amazon Neptune and the embedded Kuzu driver. Graphiti exposes the same episode-ingestion and graph-search primitives that Zep Cloud builds on, and it also ships an MCP server so agents can read/write the graph over the Model Context Protocol. Compared with batch graph-RAG approaches like LightRAG, Graphiti is incremental: it updates the graph per-episode rather than rebuilding from a static corpus, which is what makes it suitable for live agent memory.

Update (verified 2026-08-27): two things to carry over from the backend list.

  • Kuzu is deprecated — do not start a new self-host there. Upstream kuzudb/kuzu was archived read-only on 2025-10-10 at v0.11.3 ("This repository was archived by the owner on Oct 10, 2025"; PyPI kuzu stops at 0.11.3). graphiti-core 0.29.2 (2026-06-08) followed: KuzuDriver.__init__ in the shipped wheel now emits a DeprecationWarning reading "The Kuzu backend is deprecated and will be removed in a future release — the upstream Kuzu project is no longer maintained. Migrate to Neo4j or FalkorDB." The 0.29.1 wheel this entry was written against carries no such warning, but Kuzu had already been dead for seven months by then — so the uncaveated recommendation above was wrong when written, and the library-side deprecation is the part that decayed.
  • Graphiti's backends are not Zep's backend. Choosing Neo4j / FalkorDB / Neptune is a self-hosting decision; Zep Cloud serves from its own Context Graph Engine and exposes no backend choice. See the Overview update.

Usage & Examples

Install the Cloud SDK and grab an API key from the Zep dashboard.

pip install zep-cloud        # Python
npm install @getzep/zep-cloud  # TypeScript

Python — add memory and retrieve context

from zep_cloud.client import Zep

client = Zep(api_key="<ZEP_API_KEY>")

# 1. Create a user and a conversation thread
client.user.add(user_id="user-123", email="alice@example.com", first_name="Alice")
client.thread.create(thread_id="thread-abc", user_id="user-123")

# 2. Add messages — Zep extracts entities/facts into the user's graph asynchronously
client.thread.add_messages(
    thread_id="thread-abc",
    messages=[
        {"role": "user", "name": "Alice", "content": "I just moved to Berlin for a new job at a fintech."},
        {"role": "assistant", "content": "Congrats on the move! How is Berlin treating you?"},
    ],
)

# 3. Retrieve a ready-to-use context block for the next prompt
memory = client.thread.get_user_context(thread_id="thread-abc")
print(memory.context)   # summary + most-relevant facts as a single string

The returned context string is designed to be concatenated into your model's system prompt. You can request different assembly modes (a fuller summary vs. a lean fact list) depending on token budget.

Adding business data and searching the graph directly

thread.get_user_context is the high-level path; graph.search is the low-level one. You can ingest arbitrary data (not just chat) and query it:

# Ingest a JSON business record into a user's graph
client.graph.add(
    user_id="user-123",
    type="json",
    data='{"order_id": "A-559", "status": "shipped", "total": 129.90}',
)

# Low-level retrieval: search edges (facts) or nodes (entities)
results = client.graph.search(
    user_id="user-123",
    query="What did Alice order?",
    scope="edges",   # 2026-08-27, zep-cloud 3.28.0: edges | nodes | episodes | thread_summaries | observations | auto
)
for edge in results.edges:
    print(edge.fact)

TypeScript

import { ZepClient } from "@getzep/zep-cloud";

const client = new ZepClient({ apiKey: process.env.ZEP_API_KEY });

await client.user.add({ userId: "user-123", email: "alice@example.com" });
await client.thread.create({ threadId: "thread-abc", userId: "user-123" });
await client.thread.addMessages("thread-abc", {
  messages: [{ role: "user", name: "Alice", content: "I prefer dark roast coffee." }],
});

const memory = await client.thread.getUserContext("thread-abc");
console.log(memory.context);

A Go SDK provides the same surface for Go services; as of 2026-08-27 the import path is version-suffixed — go get github.com/getzep/zep-go/v3 (latest stable tag v3.28.0), with v4.0.0-alpha.x tags tracking the preview line. The graph engine can also be reached over MCP via the Graphiti MCP server, which lets MCP-aware agents and IDE assistants read and write memory directly.

Common Gotchas

  • Ingestion is asynchronous. thread.add_messages / graph.add return quickly, but entity/fact extraction runs in the background. If you immediately call get_user_context, recently added facts may not yet appear. Allow a short propagation delay (seconds) or design around eventual consistency.
  • Don't confuse the products. "Zep" can mean Zep Cloud, the open-source Graphiti engine, or the deprecated CE server. SDK package names differ (zep-cloud vs graphiti-core), and tutorials written against pre-v2 Zep (which used sessions and memory.add) won't match the current v3 API that uses threads and thread.get_user_context.
  • API renamed sessions to threads. Older code and blog posts reference client.memory.add(session_id=...). The current SDK uses client.thread.add_messages(thread_id=...) and client.thread.get_user_context. Check the SDK major version (v3.x) before copying examples. (Re-verified 2026-08-27 by installing zep-cloud 3.28.0 and introspecting the client: the top-level namespaces are batch, context, graph, project, task, thread, user, user_group — there is no memory and no session attribute at all, so v2-era snippets fail with AttributeError, not a deprecation notice. Every call in the Python and TypeScript samples above binds cleanly against 3.28.0.)
  • The 4.0 preview breaks every sample on this page (2026-08-27). zep-cloud 4.0.0a5 / @getzep/zep-cloud@4.0.0-alpha.5 sits behind npm's preview dist-tag and as a PyPI pre-release, so a plain pip install zep-cloud / npm install @getzep/zep-cloud still gives you 3.28.0 — but pip install --pre zep-cloud and npm install @getzep/zep-cloud@preview do not. Introspecting the 4.0.0a5 wheel: user.add → user.create, thread.get_user_context → thread.get_context, graph.add → graph.episode.add(graph_uuid, …), and graph.search is split into search_edges / search_nodes / search_episodes / search_observations / search_thread_summaries, all returning pagers. Resources are addressed by server-assigned UUIDs (thread_uuid, graph_uuid) rather than the caller-chosen string ids v3 uses, which is the migration cost, not the renames. The alpha also declares httpx>=0.21.2 with no upper bound, so a clean install picks up httpx 2.x and import zep_cloud.client dies with ModuleNotFoundError: No module named 'httpx._types' — pin httpx<1 if you evaluate it.
  • Use the context block, not raw search, for prompts. get_user_context returns a token-budget-optimized string. Dumping raw graph.search edges into a prompt is noisier and wastes tokens — reserve graph.search for application logic that needs structured facts.
  • Custom ontologies improve precision but cost setup. Defining entity/edge types narrows extraction to your domain and reduces irrelevant nodes, but you must register the types before ingestion; data added under the default schema won't be retroactively re-typed.
  • Self-hosting means running a graph DB. Graphiti needs a backing store (Neo4j, FalkorDB, or Neptune — not Kuzu, deprecated in graphiti-core 0.29.2 after upstream was archived on 2025-10-10) plus an LLM/embedding provider; the extraction quality and latency depend heavily on the model you wire in. This is a meaningfully different operational footprint from the managed Zep Cloud service. For pure retrieval use cases without temporal reasoning, classic RAG over a vector store may be simpler.
