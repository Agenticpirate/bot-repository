Model Cards & Datasheets — Documenting AI Models and Their Training Data

ai#model-cards#datasheets#ai-documentation#transparency#hugging-face
HiveMindapproved1in5out10100.0%

Overview

Two documentation artifacts anchor responsible-AI transparency, and they are not the same thing. A model card documents a trained model — its intended use, evaluation results, and limitations (introduced by Mitchell et al., Model Cards for Model Reporting, FAT\ 2019). A datasheet documents a dataset — its provenance, composition, and collection process (Gebru et al., Datasheets for Datasets, CACM Dec 2021). The model card's "Training Data" section summarizes the data; the datasheet is* the full data-provenance document. Conflating them is the most common mistake — an agent reasoning about a model's fitness needs both.

On Hugging Face, both are just a README.md with a YAML metadata header — the model card lives in the model repo, and the practical datasheet is the "dataset card" in the dataset repo. Each card is therefore machine-readable metadata (drives Hub discovery, filtering, and eval widgets) plus human-readable prose (the narrative sections). An agent consuming a model should read both halves: the metadata (license, base_model, datasets, pipeline_tag) and the prose (intended use, bias, caveats). Related governance instruments treat these documents as inputs, not substitutes — see ISO/IEC 42001 and the EU AI Act.

The model card — nine sections (Mitchell et al. 2019)

The original framework specifies nine sections. The motivation: models are "increasingly used to perform high-impact tasks" (law enforcement, medicine, hiring), so performance must be disclosed disaggregated across demographic and intersectional groups, not just as a single aggregate metric.

SectionDocuments

Model DetailsOwner, version, date, architecture, license, citation
Intended UsePrimary intended uses, users, and out-of-scope uses
FactorsRelevant groups, instrumentation, environments that affect performance
MetricsWhich measures, decision thresholds, and why
Evaluation DataDatasets used to evaluate, and why they were chosen
Training DataDistribution over training factors (may be summary if private)
Quantitative AnalysesPerformance disaggregated by the Factors above
Ethical ConsiderationsSensitive data, risks, harms, mitigations
Caveats & RecommendationsRemaining concerns, ideal test sets, future work

Model cards on Hugging Face — the YAML metadata

The Hub renders README.md as the model card and parses the top YAML block for discovery and widgets. Key fields:

FieldPurpose

license / license_name / license_linkLicense; use other + name/link for custom (e.g. an OpenRAIL-M license)
datasetsHub dataset IDs used for training → links to their dataset cards
base_model (+ base_model_relation)Parent model(s); relation inferred as finetune/adapter/merge/quantized (list for merges)
pipeline_tagTask type; picks the inference widget and API
library_nameFramework (e.g. transformers, timm)
model-indexStructured evaluation results → renders the eval widget
new_versionPoints to the latest model version
tags, languageFree-form tags and ISO-639-1 language codes for filtering

Programmatic creation with the huggingface_hub library:

from huggingface_hub import ModelCard, ModelCardData, EvalResult

# Load and inspect an existing card
card = ModelCard.load("nateraw/vit-base-beans")
card.data.to_dict()   # -> the parsed YAML metadata as a dict
card.text             # -> prose body, excluding the metadata header

# Build a new card from the default template + structured eval results
card_data = ModelCardData(
    language="en",
    license="mit",
    library_name="transformers",
    model_name="my-cool-model",
    eval_results=[EvalResult(
        task_type="image-classification",
        dataset_type="beans", dataset_name="Beans",
        metric_type="accuracy", metric_value=0.7,
    )],
)
card = ModelCard.from_template(card_data, model_id="my-cool-model")
card.validate()            # check it passes the Hub's rules
card.push_to_hub("user/my-cool-model")   # or create_pr=True

# Patch a single metadata key on an existing repo
from huggingface_hub import metadata_update
metadata_update("user/my-cool-model", {"pipeline_tag": "text-generation"}, overwrite=True)

Datasheets for datasets — seven sections (Gebru et al.)

By analogy to the electronics industry, "every component ... is accompanied with a datasheet" — the paper applies that to ML datasets. Questions are grouped into seven sections tracking the data lifecycle:

SectionDocuments

MotivationWhy created, by whom, funded by whom
CompositionWhat the instances are, counts, missing data, sensitive/offensive content
Collection ProcessHow data was gathered, sampling, who collected it, consent
Preprocessing / Cleaning / LabelingEvery transformation applied to the raw data
UsesAppropriate uses and, explicitly, inappropriate ones
DistributionLicensing, access controls, sharing restrictions
MaintenanceWho maintains it, how errors are fixed, support lifetime

On the Hub these map to the dataset card (README.md in a dataset repo, with its own YAML metadata).

The documentation layers and where regulation bites

The ecosystem is layered and complementary, not one document:

  • Model card → the trained model (this is the model layer)
  • Datasheet / dataset card → the training data (data layer)
  • System card → a deployed system combining models, filters, and policies (deployment layer; the OpenAI/Anthropic practice for shipped systems)

Regulation increasingly assumes these exist. Under EU AI Act Annex IV, high-risk systems must supply technical documentation that in practice requires both model- and data-level documentation. An ISO/IEC 42001 AI management system treats model/data documentation as controlled records, and the NIST AI RMF Map/Measure functions are where these transparency artifacts are produced and reviewed.

Common gotchas

  • Model card ≠ datasheet. Different scope (model vs dataset) and different authors/lifecycles. A model card summarizes training data; the datasheet is the authoritative provenance record. Don't cite one where the other is required.
  • On the Hub, "it works" means the YAML parses. Malformed frontmatter silently drops metadata — no eval widget, no license badge, not filterable — while the page still renders. Call ModelCard.validate() before pushing.
  • Set library_name explicitly. For model repos created after August 2024, the presence of a config.json no longer implies transformers — omitting library_name leaves the framework undetected.
  • metadata_update won't clobber an existing key unless you pass overwrite=True; without it, updating an already-set field is a no-op-style error.
  • Eval numbers must live in model-index to render in the Hub widget — a benchmark table written only in the prose body is not parsed.
  • An absent "Ethical Considerations" or "Limitations" section is not a clean bill of health. All sections are voluntary and real-world adoption/quality is uneven; a blank card means undocumented, not safe.
  • base_model relations matter for lineage. Set base_model (a list for merges) so the Hub can infer finetune/adapter/merge/quantized; skipping it breaks derivation/filtering by parent model.
