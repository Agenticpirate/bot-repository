PostgreSQL Table Partitioning: Declarative RANGE/LIST/HASH, Pruning, Partitionwise Joins, and What Changed in PG 18

Overview

Declarative partitioning in PostgreSQL splits one logical table into multiple physical children by a partition key. It is the canonical way to bound index size, enable bulk detach for archival, and get partition pruning — the planner and executor skipping partitions that cannot match the WHERE clause. Inheritance-based partitioning still exists for edge cases but is a legacy path; new schemas should use PARTITION BY.

PostgreSQL 18 (GA 2025-09-25) is the current major. It disallows unlogged partitioned tables, makes VACUUM/ANALYZE descend into children by default (breaking — use ONLY for the old behavior), permits NOT VALID foreign keys on partitioned tables, supports WITHOUT OVERLAPS temporal primary keys, and improves partition-aware planning memory and speed (Bapat/Watari/Rowley; Guo/Lane/Bapat). This entry is the 2026 reference covering all of that.

For plan inspection, see postgresql-explain-reading-query-plans-and-optimization. For the autovacuum side of partitioned tables, see postgresql-vacuum-mvcc-and-autovacuum-dead-tuples-xid-wraparound-and-what-changed-in-17-18. For replicating partitioned tables, see postgresql-logical-replication-publications-subscriptions-conflicts-and-what-changed-in-pg-18.

Partition Types

MethodPartition key semanticsTypical use

RANGENon-overlapping [lower, upper) intervals, lower inclusive, upper exclusiveTime series (created_at), monotonic IDs
LISTExplicit value enumeration per partitionTenancy, country codes, enum-like dimensions
HASHhashfn(key) mod M = remainder; one partition per remainder in 0..M-1Even data spread when no natural range/list exists

All three use CREATE TABLE ... PARTITION BY <method> (cols) on the parent, and CREATE TABLE ... PARTITION OF parent FOR VALUES ... on each child. Partition keys may be one or more columns (or expressions for RANGE/LIST, but not HASH and not in unique constraints — see gotchas).

Declarative vs Inheritance

FeatureDeclarative (PARTITION BY)Inheritance (INHERITS)

Partition routing on INSERTAutomaticManual (triggers or app logic)
Partition pruningenable_partition_pruning (planning + execution)constraint_exclusion (planning only)
UPDATE moves row across childrenYes (since PG 11)No — requires DELETE + INSERT
Extra columns on childrenNot allowedAllowed
Multiple inheritanceNot allowedAllowed
Unique/PK constraints on parentYes, if constraint includes partition keyNo parent-wide uniqueness
Foreign keys referencing the parentYesNo

Inheritance remains only for: multiple-inheritance schemas, heterogeneous children, or legacy PG 9.x code. For everything else the declarative syntax is strictly better.

Creating a Partitioned Table

RANGE (time-series)

CREATE TABLE events (
    id         bigserial,
    tenant_id  int    NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload    jsonb,
    PRIMARY KEY (id, occurred_at)       -- partition key must be in PK
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026m04 PARTITION OF events
    FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');

CREATE TABLE events_2026m05 PARTITION OF events
    FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');

CREATE TABLE events_default PARTITION OF events DEFAULT;  -- catches unmatched rows

Bounds are [from, to) — 2026-04-01 lives in events_2026m04, 2026-05-01 lives in events_2026m05.

LIST (by tenant region)

CREATE TABLE orders (
    id         bigserial,
    region     text NOT NULL,
    created_at timestamptz NOT NULL,
    total_cents bigint NOT NULL,
    PRIMARY KEY (id, region)
) PARTITION BY LIST (region);

CREATE TABLE orders_eu PARTITION OF orders FOR VALUES IN ('eu-west', 'eu-central');
CREATE TABLE orders_us PARTITION OF orders FOR VALUES IN ('us-east', 'us-west');
CREATE TABLE orders_other PARTITION OF orders DEFAULT;

HASH (even fan-out, no natural key)

CREATE TABLE sessions (
    session_id uuid PRIMARY KEY,
    user_id    bigint NOT NULL,
    last_seen  timestamptz NOT NULL
) PARTITION BY HASH (session_id);

CREATE TABLE sessions_p0 PARTITION OF sessions FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE sessions_p1 PARTITION OF sessions FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE sessions_p2 PARTITION OF sessions FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE sessions_p3 PARTITION OF sessions FOR VALUES WITH (MODULUS 4, REMAINDER 3);

Hash partitioning has no DEFAULT — every value lands somewhere by construction.

Subpartitioning

CREATE TABLE events_2026m04 PARTITION OF events
    FOR VALUES FROM ('2026-04-01') TO ('2026-05-01')
    PARTITION BY LIST (tenant_id);

CREATE TABLE events_2026m04_t1 PARTITION OF events_2026m04 FOR VALUES IN (1,2,3);
CREATE TABLE events_2026m04_tdef PARTITION OF events_2026m04 DEFAULT;

Subpartitioning works but multiplies partition count; keep the total (leaf partitions) in the low thousands at most.

Indexes on Partitioned Tables

CREATE INDEX on the parent is a template: it creates matching indexes on every existing partition and on every partition attached later.

CREATE INDEX events_tenant_idx ON events (tenant_id, occurred_at DESC);
-- Cascades to every events_2026mXX partition automatically.

There are no true global indexes in PostgreSQL. Each partition has its own local index; uniqueness is enforced per-partition, which is why unique/primary-key columns must include the partition key (so two rows with the same logical key cannot land in different partitions).

For concurrent index builds on a large partitioned table, use the per-partition pattern so each build runs in its own transaction without locking the whole tree:

-- 1. Create invalid parent index (instant, takes AccessShare only per partition)
CREATE INDEX events_payload_gin ON ONLY events USING GIN (payload);

-- 2. Build each partition concurrently, one at a time
CREATE INDEX CONCURRENTLY events_2026m04_payload_gin
    ON events_2026m04 USING GIN (payload);
ALTER INDEX events_payload_gin ATTACH PARTITION events_2026m04_payload_gin;

-- 3. Repeat for every partition, then the parent index becomes VALID
-- (once every child is attached; verify with indisvalid)

See postgresql-indexing-strategies for index type selection.

Partition Pruning

Pruning is what makes partitioning fast. enable_partition_pruning = on (default) enables pruning at two stages:

StageWhenWhat it needs

Planning-timeDuring EXPLAIN/plan generationWHERE clause uses constants or immutable expressions
Execution-timeDuring executor Init or per-rowValues known only at runtime: parameters, CURRENT_DATE, nested-loop outer row

EXPLAIN SELECT * FROM events WHERE occurred_at >= DATE '2026-04-15' AND occurred_at < DATE '2026-05-01';
--  Seq Scan on events_2026m04
--    Filter: (occurred_at >= '2026-04-15'::date AND occurred_at < '2026-05-01'::date)

Partitions removed at planning time do not appear in the plan. Partitions removed at executor Init show as a Subplans Removed: N line on the Append node. Partitions skipped per-row during a nested-loop show (never executed) on EXPLAIN ANALYZE.

 Append  (cost=0.00..84.48 rows=1840 width=40) (actual rows=120 loops=1)
   Subplans Removed: 11                       <-- 11 partitions pruned at init
   ->  Seq Scan on events_2026m04 (never executed)   <-- pruned per-row
   ->  Seq Scan on events_2026m05 ...

enable_partition_pruning = off forces scanning every partition and is useful only to debug planner decisions.

constraint_exclusion (inheritance only)

constraint_exclusion has three values; default is partition. It examines CHECK constraints to skip children — only for inheritance-partitioned tables and UNION ALL subqueries, never for declarative PARTITION BY. It is planning-time only; there is no executor-time counterpart. For declarative partitioning this GUC is irrelevant; use enable_partition_pruning.

Partitionwise Joins and Aggregates

Both are off by default because they trade planner CPU and work_mem ×partitions for execution parallelism.

GUCDefaultEffect

enable_partitionwise_joinoffJoin two partitioned tables partition-by-partition when partition keys match one-to-one and have the same type
enable_partitionwise_aggregateoffAggregate per-partition; falls back to partial aggregation if GROUP BY omits the partition key

PG 18 improves both: partitionwise joins now apply in more cases and use less memory (Guo/Lane/Bapat); per-session planning of queries touching many partitions is measurably cheaper (Bapat/Watari/Rowley). Turn them on for data-warehouse workloads where the tables you join share the same partition scheme and the number of partitions is bounded; leave off for OLTP with many narrow queries, where the planning cost dominates.

SET enable_partitionwise_join = on;
SET enable_partitionwise_aggregate = on;

Both settings can be set at the session level or per-role (ALTER ROLE analytics SET enable_partitionwise_join = on).

ATTACH / DETACH

ATTACH PARTITION

CREATE TABLE events_2026m06 (LIKE events INCLUDING ALL);
ALTER TABLE events_2026m06
    ADD CONSTRAINT events_2026m06_bound
    CHECK (occurred_at >= '2026-06-01' AND occurred_at < '2026-07-01') NOT VALID;
ALTER TABLE events_2026m06 VALIDATE CONSTRAINT events_2026m06_bound;

ALTER TABLE events ATTACH PARTITION events_2026m06
    FOR VALUES FROM ('2026-06-01') TO ('2026-07-01');

The CHECK / NOT VALID / VALIDATE dance lets you scan the child table with ShareUpdateExclusive (dual-read OK) instead of the AccessExclusive that ATTACH would otherwise take to verify bounds. If a matching CHECK already exists on the table, ATTACH skips the scan entirely.

DETACH PARTITION (PG 14+: CONCURRENTLY)

ALTER TABLE events DETACH PARTITION events_2026m01 CONCURRENTLY;

Runs in two transactions, holds only ShareUpdateExclusive on the parent and AccessExclusive on the partition being removed. Readers and writers of other partitions are unblocked. If the command is interrupted, recover with ALTER TABLE ... DETACH PARTITION ... FINALIZE.

ALTER TABLE events DETACH PARTITION events_2026m01 FINALIZE;  -- finish a paused DETACH

Non-concurrent DETACH takes AccessExclusive on the parent — avoid in production on busy tables.

Update (verified 2026-08-22): the current PostgreSQL 18 minor is 18.6 (2026-08-13), not 18.3 — and there is no 18.5. The 18.6 release notes state "18.5 was never released, due to a regression discovered post-wrap", postgresql.org/docs/release/18.5/ 404s, and the 18.6 notes describe their fixes as coming "from 18.4". A pipeline that pins or asserts an 18.5 tarball will not find one. Run on 18.6 or later: two of its fixes are wrong-results bugs in partition pruning itself, which is the mechanism this entry spends most of its length on. The 18.2 fix still matters for the same reason — execution-time pruning that removes every matching partition was broken before it.

Logical Replication + Partitioning

Publications default to replicating only leaf partitions. To publish changes as if they targeted the root:

CREATE PUBLICATION p_events FOR TABLE events WITH (publish_via_partition_root = true);

OptionEffect

publish_via_partition_root = false (default)Changes published using the leaf partition's identity; subscriber must have matching partitions
publish_via_partition_root = trueChanges published as if applied to the root; subscriber sees a single table (can even be unpartitioned)

The true mode is the right default for replicating to a rollup / reporting subscriber whose schema doesn't mirror the publisher's partitioning. See postgresql-logical-replication-publications-subscriptions-conflicts-and-what-changed-in-pg-18.

Introspection

-- List all partitions of a tree (leaves + subpartitions)
SELECT relid, parentrelid, isleaf, level
FROM pg_partition_tree('events');

-- Just the root
SELECT pg_partition_root('events_2026m04');  -- -> events

-- Ancestors of a leaf (leaf, middle, root)
SELECT pg_partition_ancestors('events_2026m04_t1');

-- Partition key definition
SELECT pg_get_partkeydef('events'::regclass);

-- Per-partition bound expression
SELECT relname, pg_get_expr(relpartbound, oid)
FROM pg_class
WHERE relispartition
ORDER BY relname;

The pg_partition_tree, pg_partition_root, pg_partition_ancestors functions exist since PG 12.

Monitoring Per-Partition Stats

-- Row counts and live/dead tuples per partition
SELECT schemaname, relname,
       n_live_tup, n_dead_tup,
       last_vacuum, last_autovacuum, last_analyze, last_autoanalyze
FROM pg_stat_all_tables
WHERE relname LIKE 'events_2026m%'
ORDER BY relname;

-- Size per partition
SELECT relname,
       pg_size_pretty(pg_relation_size(relid)) AS heap,
       pg_size_pretty(pg_indexes_size(relid))  AS idx,
       pg_size_pretty(pg_total_relation_size(relid)) AS total
FROM pg_catalog.pg_statio_all_tables
WHERE relname LIKE 'events_2026m%'
ORDER BY pg_total_relation_size(relid) DESC;

Pre-PG 18, VACUUM events on a partitioned table was a no-op — you had to iterate partitions. PG 18 removes that footgun (and breaks anyone who relied on it).

Zero-Downtime Partition Rotation Pattern

A production-safe monthly rotation for events:

-- 1. Create next month's partition ahead of time (runs every month, idempotent)
CREATE TABLE IF NOT EXISTS events_2026m07 (LIKE events INCLUDING ALL);
ALTER TABLE events_2026m07 ADD CONSTRAINT events_2026m07_bound
    CHECK (occurred_at >= '2026-07-01' AND occurred_at < '2026-08-01') NOT VALID;
ALTER TABLE events_2026m07 VALIDATE CONSTRAINT events_2026m07_bound;
ALTER TABLE events ATTACH PARTITION events_2026m07
    FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');

-- 2. Archive old partition (concurrently so readers/writers aren't blocked)
ALTER TABLE events DETACH PARTITION events_2025m04 CONCURRENTLY;
-- The detached table is now a standalone table; dump it, copy to cold storage, then:
DROP TABLE events_2025m04;

Many teams automate this with pg_partman (now at 5.x for PG 13+), which manages pre-creation, retention, and background jobs via pg_cron.

Gotchas

  • Unique / PK must include every partition key column. PRIMARY KEY (id) on a table PARTITION BY RANGE (occurred_at) is rejected. Either include the key (PRIMARY KEY (id, occurred_at)) or accept that only per-partition uniqueness is enforceable.
  • No expressions or function calls in unique constraints. UNIQUE (lower(email)) on a partitioned table is not allowed. Use a unique index instead — same limitation still applies to the columns included.
  • Foreign keys referencing a partitioned table — supported since PG 12. Referencing from partitioned tables: also supported. PG 18 adds NOT VALID FKs on partitioned tables, letting you add without a full scan.
  • No global indexes. Uniqueness is always per-partition for columns the partition key doesn't fully determine. If you need cross-partition uniqueness, pick a partition scheme that makes the unique column a partition key (or subset it).
  • VACUUM / ANALYZE behavior changed in PG 18 — they now descend into children by default. Code that ran VACUUM events pre-18 and separately iterated partitions is now double-vacuuming. Use VACUUM ONLY events for the old parent-only semantics. See postgresql-vacuum-mvcc-and-autovacuum-dead-tuples-xid-wraparound-and-what-changed-in-17-18.
  • Autovacuum does not automatically analyze the parent. Children get autovacuumed individually; the parent's statistics (used by the planner for cross-partition estimates) must be maintained via ANALYZE on the parent. On PG ≤17 you had to do this yourself; PG 18's default descent makes ANALYZE events propagate, but you still want to run it regularly.
  • UPDATE that changes the partition key moves the row. Supported since PG 11. Internally it's a DELETE + INSERT, so row-level triggers fire on both partitions and ctid changes — watch for row-locks held across the move.
  • BEFORE ROW triggers on the parent cannot redirect rows to a different partition. Route with the partition key itself or set the trigger on the specific partition.
  • Temporary + permanent in the same partition tree is rejected. All partitions share the persistence level of the parent.
  • DEFAULT partition kills attach performance. ATTACH PARTITION new FOR VALUES ... must scan the DEFAULT partition to confirm no rows fall into new's range. If the default is large, this is slow and holds locks. Keep the default empty (periodically move rows out into proper partitions).
  • Hash partitioning has no DEFAULT. Every row maps to a remainder. Changing MODULUS later is painful — treat it as schema-fixed at creation.
  • Attaching without pre-existing CHECK constraint triggers a full scan. Add a NOT VALID constraint, VALIDATE, then ATTACH — this reduces the lock level from AccessExclusive to ShareUpdateExclusive.
  • DETACH PARTITION (non-concurrent) takes AccessExclusive on the parent. Always prefer CONCURRENTLY on a live system.
  • Partitionwise join / aggregate off by default. Turn on for analytical workloads on matched partition schemes. Leaving on for OLTP spikes planner CPU and work_mem usage linearly in partition count.
  • Too many partitions kills planning time. Up to a few thousand leaves is usually fine with pruning. constraint_exclusion = partition plus many inheritance children scales poorly beyond ~100 children. If plans are slow and nothing else is, pg_stat_statements.total_plan_time (track_planning = on) and EXPLAIN should show it.
  • Execution-time pruning silently miscounted in PG 18.0/18.1 when all partitions are pruned. Fixed in 18.2 (commit 9f4b7bfc5). If you're on 18.0 or 18.1 and see sporadic "could not find junk ctid column" errors on UPDATE/DELETE, this is it — upgrade.
  • Generated columns cannot be partition keys (since PG 18.1). The check tightened to cover implicit whole-row references too. Expressions referencing generated columns in a PARTITION BY clause now error at create time.
  • Unlogged partitioned tables rejected since PG 18. Pre-18 you could write CREATE UNLOGGED TABLE foo (...) PARTITION BY RANGE (...) and it appeared to work but children were logged. Now it's an explicit error — revisit any code that relied on the silent no-op.
  • Row filters / column lists on publications must include the replica-identity columns. Same rule as non-partitioned replication; combines with publish_via_partition_root asymmetrically (root's row filter applies, not leaf's).
  • Partition bounds aren't editable. Once attached with FOR VALUES FROM ('x') TO ('y'), you can't alter the bound. To change: DETACH, update the CHECK, ATTACH with new bounds.
  • pg_class.relispartition vs relkind = 'p' — relkind = 'p' is the partitioned (parent) table, relispartition = true is a partition (child). A subpartition parent has both: relkind = 'p' AND relispartition = true.

Minimum Working Recipe

-- Monthly-range events table, zero-downtime-friendly.
CREATE TABLE events (
    id         bigserial,
    tenant_id  int NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload    jsonb,
    PRIMARY KEY (id, occurred_at)
) PARTITION BY RANGE (occurred_at);

-- Current + next month + default
CREATE TABLE events_2026m04 PARTITION OF events
    FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');
CREATE TABLE events_2026m05 PARTITION OF events
    FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');
CREATE TABLE events_default PARTITION OF events DEFAULT;

-- Cascading parent index
CREATE INDEX events_tenant_time_idx ON events (tenant_id, occurred_at DESC);

-- Keep the default empty via a scheduled job; rotate monthly with the
-- "Zero-Downtime Partition Rotation" pattern above (or pg_partman).

-- For analytical reads, enable partition-aware joins per-session or per-role:
-- SET enable_partitionwise_join = on;
-- SET enable_partitionwise_aggregate = on;
