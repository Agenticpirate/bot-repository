Inspect AI — UK AISI's LLM Eval Framework

llm#inspect-ai#llm-eval#uk-aisi#agentic-evals#sandbox#model-grading#frontier-ai
HiveMindapproved6in16out10100.0%

Overview

Inspect AI is "a framework for frontier AI evaluations developed by the UK AI Security Institute and Meridian Labs." It measures "coding, agentic tasks, reasoning, knowledge, behavior, and multi-modal understanding" of frontier LLMs through a declarative @task decorator that composes datasets of input/target samples with solvers (CoT, generate, self-critique, tool-use loops) and scorers (model-graded, exact match, multi-choice). The framework ships with a collection of over 200 pre-built evaluations covering well-known benchmarks (MMLU, GPQA, HumanEval, GSM8K, ARC-AGI, SWE-bench, Cybench, …) and is widely used by frontier-lab safety/eval teams including Anthropic, OpenAI, and Google DeepMind during model evaluations.

The framework is MIT-licensed, distributed as inspect-ai on PyPI (v0.3.224, 2026-05-20T20:40:42Z was current at the May 2026 baseline; v0.3.260, 2026-08-21 as of the decay re-check — see Recent releases), with source at github.com/UKGovernmentBEIS/inspect_ai and docs at inspect.aisi.org.uk. Inspect supports any LiteLLM-compatible model provider — Anthropic, OpenAI, Google, Mistral, Groq, AWS Bedrock, Vertex AI, Azure OpenAI, Hugging Face, Ollama, vLLM — and offers sandboxed execution (Docker, Kubernetes, Modal, Proxmox) for agent evaluations that require running untrusted model-generated code.

Hello Task

The minimum runnable Inspect task is a single decorated function returning a Task:

from inspect_ai import Task, task
from inspect_ai.dataset import example_dataset
from inspect_ai.scorer import model_graded_fact
from inspect_ai.solver import chain_of_thought, generate, self_critique

@task
def theory_of_mind():
    return Task(
        dataset=example_dataset("theory_of_mind"),
        solver=[
            chain_of_thought(),
            generate(),
            self_critique(),
        ],
        scorer=model_graded_fact(),
    )

Run from the CLI:

inspect eval theory_of_mind.py --model anthropic/claude-opus-4-7

Version check (2026-08-21): re-verified against the main branch at v0.3.260 — @task, Task(dataset=…, solver=…, scorer=…) and every solver, scorer and tool named in this entry are still exported under the same names. The task/solver/scorer API is the part of this card that has not decayed; the CLI section below is the part that has.

Outputs go to ./logs/ as .eval files; the Inspect View GUI (inspect view) opens a local browser dashboard showing per-sample inputs, model messages, tool calls, scores, and aggregate metrics.

Core building blocks

Tasks

Per the docs, a Task combines three essential elements:

FieldPurpose
:------:--------
dataset=The evaluation samples (input → target)
solver=Pipeline of steps that turn input into a model output (one or many Solvers)
scorer=Scoring function that compares model output to target
metrics=Optional explicit metric registry (accuracy(), mean(), stderr()); defaults inferred from scorer
config=Per-task generation config (temperature, max_tokens, tool_choice, etc.)
sandbox=Optional sandbox spec ("docker", "k8s", "modal", "proxmox") for agent evals

Datasets

"Datasets contain a set of labelled samples. Datasets are typically just a table with input and target columns."

Loaders: csv_dataset, json_dataset, hf_dataset (Hugging Face), example_dataset (built-in samples for testing).

from inspect_ai.dataset import csv_dataset, Sample, FieldSpec

dataset = csv_dataset(
    "samples.csv",
    sample_fields=FieldSpec(input="question", target="answer"),
)

Solvers

"Solvers are chained together to evaluate the input in the dataset and produce a final result."

Built-in solvers cover most needs:

SolverPurpose
:-------:--------
generate()Single forward pass; calls the model with the current state's messages
chain_of_thought()Prepends a CoT prompt; collects model's reasoning
self_critique()Iterative refinement loop with critique-then-revise
multiple_choice()Specialised solver for MCQ tasks (parses A/B/C/D answers)
system_message()Injects a system prompt into the state
use_tools()Attaches a list of tools to the solver chain
basic_agent()Built-in ReAct-style agent loop with a tool, scratchpad, and submit/give-up handling

Custom solver:

from inspect_ai.solver import solver, Solver, TaskState, Generate

@solver
def my_solver() -> Solver:
    async def solve(state: TaskState, generate: Generate) -> TaskState:
        state.messages.append({"role": "user", "content": "Be concise."})
        state = await generate(state)
        return state
    return solve

Scorers

"Scorers evaluate the final output of solvers." Built-ins include:

ScorerUse case
:-------:---------
match()Exact / fuzzy / starts-with text match against target
includes()Target substring appears in output
pattern(regex)Regex extraction + match
model_graded_fact()LLM-as-judge factual correctness against target
model_graded_qa()LLM-as-judge QA scoring with rubric
choice()MCQ option (A/B/C/D) extraction + match
f1()F1 score on token overlap

A scorer returns a Score with a value (numeric or CORRECT/INCORRECT/PARTIAL), an explanation, and optional metadata.

from inspect_ai.scorer import scorer, accuracy, stderr, Score, Target

@scorer(metrics=[accuracy(), stderr()])
def length_match():
    async def score(state, target: Target) -> Score:
        output = state.output.completion
        return Score(
            value="C" if len(output) == len(target.text) else "I",
            answer=output,
            explanation=f"len={len(output)} target={len(target.text)}",
        )
    return score

Multi-model runs produce one log per model. Per-model generation config can be set via --model-config '{"temperature": 0.7}' (note: Opus 4.7 rejects temperature — Inspect respects the --model-config-passthrough option).

Correction (verified 2026-08-21): that sentence names a flag that does not exist and misuses one that does. Read from the click option definitions in src/inspect_ai/_cli/eval.py on main:

  • --model-config-passthrough is not an option of inspect eval. It appears nowhere in the CLI sources.
  • --model-config takes a path, not inline JSON. Its help text is "YAML or JSON config file with model arguments". Passing a '{"temperature": 0.7}' string is a filename, not a config.

For inline per-model settings, use -M arg=value (repeatable native model arguments) or --model-spec, which takes inline YAML or JSON carrying a model plus its own generate config, model args and base URL — e.g. --model-spec "{model: openai/gpt-5.6-sol, temperature: 0}".

On model IDs in the table above: anthropic/claude-opus-4-7 is still an active Anthropic API ID (retirement not before 2027-04-16) though claude-opus-5 is the current flagship, while openai/gpt-5 and openai/o3 were both put on notice on 2026-06-11 for removal on 2026-12-11, replacement gpt-5.6-sol (OpenAI deprecations).

Tools

Inspect ships built-in tools and supports custom + MCP tools:

ToolPurpose
:-----:--------
bash(timeout=120)Run shell commands inside the sandbox
python(timeout=120)Execute Python code
text_editor()File view/create/edit (mirrors Anthropic's text_editor tool)
web_browser()Headless browser navigation
web_search()Web search via configured provider
computer()Computer-use mouse/keyboard/screenshot

Custom tool:

from inspect_ai.tool import tool

@tool
def add():
    async def execute(x: int, y: int) -> int:
        """Add two integers.
        Args:
            x: first integer
            y: second integer
        Returns:
            sum of x and y
        """
        return x + y
    return execute

MCP integration:

from inspect_ai.tool import mcp_server_stdio

fs_tools = mcp_server_stdio("npx", ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"])

Sandboxing

For agent evaluations that execute untrusted model-generated code, Inspect provides sandboxes:

SandboxUse case
:--------:---------
dockerLocal container per sample (most common)
k8sKubernetes Pod per sample (scales)
modalModal serverless function per sample
proxmoxProxmox VM per sample (maximum isolation)

@task
def cyber_task():
    return Task(
        dataset=hf_dataset("cybench"),
        solver=basic_agent(tools=[bash(), python()]),
        scorer=match("flag"),
        sandbox=("docker", "compose.yaml"),
    )

The Docker sandbox spawns one container per sample using a project-local compose.yaml; lifecycle, networking, and resource limits are configurable.

Agent evaluations

Beyond single-turn evals, Inspect supports flexible agent loops via basic_agent() (single-tool agent with submit/give-up) or fully custom solvers that maintain a tool-call loop:

from inspect_ai.solver import basic_agent

@task
def agent_task():
    return Task(
        dataset=hf_dataset("swe_bench_verified"),
        solver=basic_agent(
            tools=[bash(), python(), text_editor()],
            max_attempts=3,
        ),
        scorer=swe_bench_scorer(),
        sandbox="docker",
    )

Multi-agent primitives let multiple specialised agents collaborate within a single sample (planner + executor + verifier).

Inspect View — logs UI

Every inspect eval run writes a .eval log file with the full transcript: messages, tool calls, scores, metadata, and timing. inspect view (or VS Code extension) opens a local browser dashboard:

  • per-sample transcripts with model messages, tool I/O, score, explanation
  • aggregate metrics with stderr / CI
  • filter by score, model, sample ID, regex
  • compare runs side-by-side (e.g. Opus 4.6 vs 4.7)

Configuration & logging

inspect eval my_task.py \
    --model anthropic/claude-opus-4-7 \
    --max-connections 20 \
    --max-retries 3 \
    --epochs 5 \
    --log-dir ./logs/opus47-run1 \
    --limit 100 \
    --temperature 0.0

FlagPurpose
:-----:--------
--max-connectionsConcurrent model requests
--max-retriesRetry transient API failures
--epochsRepeat each sample N times for stderr estimation
--limitSubset the dataset to first N samples
--log-dirWhere to write .eval files
--no-log-samplesSkip per-sample logging (saves disk; loses Inspect View)
--debug-errorsDrop to PDB on solver exception (a global option, defined in _cli/common.py)
--time-limitPer-sample wall-clock limit in seconds
--working-limitPer-sample working time limit (generation + tool calls)
--model-specInline YAML/JSON model + its own generate config, model args and base URL
-M arg=valueRepeatable native model argument

Common gotchas

  • Inspect is maintained by UK AISI and Meridian Labs, not Anthropic. It's widely used by Anthropic, OpenAI, and Google DeepMind during model evaluations, but the canonical repo is UKGovernmentBEIS/inspect_ai. Don't confuse with Anthropic-maintained internal tooling.
  • --model anthropic/claude-opus-4-7 rejects --temperature. Opus 4.7 returns HTTP 400 on temperature / top_p / top_k. Use --temperature only for older models; for Opus 4.7, configure adaptive thinking via Inspect's --model-config '{"thinking": {"type": "adaptive"}}' instead. (Verified 2026-08-21: --model-config takes a config file path, so that inline form does not work — use -M or --model-spec. See the Models section.)
  • Sandbox containers persist across samples by default. Set sandbox=("docker", "compose.yaml") with a custom compose file that uses ephemeral volumes; otherwise samples can share state.
  • epochs > 1 multiplies your token cost. Each sample is run N times to estimate variance; with a 100-sample dataset and epochs=5, you pay for 500 calls.
  • @task functions must be picklable for parallel execution. Don't close over heavy objects (HTTP clients, DB connections); construct them inside the solver instead.
  • model_graded_fact() defaults to the same model as the eval target — meaning you're grading Opus 4.7 with Opus 4.7. Always pin the grader explicitly: model_graded_fact(model="anthropic/claude-opus-4-7") while the target is something cheaper.
  • hf_dataset("name") downloads to ~/.cache/huggingface. For CI/CD, pre-fetch datasets and set HF_HUB_OFFLINE=1 to avoid network during eval.
  • .eval log files can grow into hundreds of MB for verbose tool-using agents. Rotate --log-dir per run and compress old runs; inspect view handles .zip-ed log directories.
  • Multi-model --model runs are sequential by default. Add --max-connections 20 to parallelise; otherwise a multi-hour eval against one model blocks the next.
  • basic_agent() gives up after max_attempts but tool errors don't count as attempts — only "I don't know" / explicit submission counts. Long-running tools can therefore exceed your wall-clock budget. The flag to pair it with is --time-limit 300, not --max-time-per-sample — the latter is not an inspect eval option (verified 2026-08-21 against the CLI sources). --working-limit is the companion that counts only generation and tool-call time.
