Overview

The OpenAI Realtime API is a streaming, bidirectional speech-to-speech endpoint that runs a single model (gpt-realtime, gpt-realtime-mini, or the newer gpt-realtime-1.5) over WebRTC, WebSockets, or SIP. It moved from beta to general availability on 2025-08-28 and replaces the older gpt-4o-realtime-preview family. It is a different surface from the OpenAI Responses API: Responses is stateful HTTPS+SSE for text and reasoning workflows; Realtime is a persistent low-latency duplex audio channel for voice agents.

The model accepts audio, text, and (since GA) images on input and emits audio plus text on output, with hosted function calling and remote MCP servers as tools. Choosing the transport is a 1:1 deployment decision: WebRTC for browsers and mobile, WebSockets for backend services, SIP for phone lines. See the WebSocket vs SSE entry for the duplex/half-duplex distinction that makes Realtime fundamentally different from text-streaming SSE endpoints.

Update (verified 2026-08-21): the model line and the beta interface have both moved on.

  • The current model is gpt-realtime-2.1 (released 2026-07-06), with gpt-realtime-2.1-mini as its cost tier. gpt-realtime-2 shipped 2026-05-07 as the first realtime model with configurable reasoning (minimal / low / medium / high / xhigh) and raised the realtime context window from 32K to 128K tokens. Two siblings landed alongside it: gpt-realtime-translate for streaming speech-to-speech translation, and from 2026-07-28 gpt-live-transcribe for low-latency streaming speech-to-text.
  • The OpenAI-Beta: realtime=v1 interface was removed on 2026-05-12 — removed, not merely deprecated. A client that still sends the beta header, the flat top-level voice / input_audio_format / output_audio_format / turn_detection keys, the bare pcm16 / g711_ulaw / g711_alaw format strings, or that listens for response.audio.delta, cannot connect at all today. The GA shapes documented in the rest of this entry — nested audio.input.format, audio.output.{format,voice}, output_modalities, and response.output_audio.delta / .done — are now the only shapes there are.
  • gpt-4o-realtime-preview and gpt-4o-mini-realtime-preview shut down 2026-05-07.
  • The GA-era names shut down 2027-01-20: gpt-realtime and gpt-4o-realtime migrate to gpt-realtime-2.1, gpt-realtime-mini and gpt-4o-mini-realtime to gpt-realtime-2.1-mini (developers.openai.com/api/docs/deprecations). gpt-realtime-1.5 is still listed on the models page; gpt-realtime-mini is already flagged there as deprecated.

Re-checked 2026-08-22: the model line above is unchanged. gpt-realtime-2.1, gpt-realtime-2.1-mini, gpt-realtime-2, gpt-realtime-translate, gpt-realtime-1.5, gpt-realtime-mini (still flagged deprecated), gpt-realtime-whisper, gpt-live-transcribe and gpt-transcribe are all still in the live catalogue, and the only realtime retirement on the deprecations page is still the 2027-01-20 cut for the legacy gpt-realtime / gpt-audio / gpt-4o-audio families onto gpt-realtime-2.1 and gpt-audio-1.5. Nothing in this family retires inside the next 30 days — but one snapshot has already gone: gpt-realtime-mini-2025-10-06 shut down 2026-07-23 (alongside gpt-audio-mini-2025-10-06), so a session still pinned to that dated snapshot fails today. The undated gpt-realtime-mini alias and the 2025-12-15 snapshot run until 2027-01-20.

Several detail claims below were wrong and are corrected in place:

  • Realtime image input is not billed at the text rate, and the transcription models bill per minute, not per token.
  • The DTMF server event is input_audio_buffer.dtmf_event_received, not input_audio_buffer.dtmf, and it is SIP-only.
  • voice is locked once the session has produced audio — it is not freely mutable mid-session.
  • Retention-ratio truncation is {"type": "retention_ratio", "retention_ratio": 0.8}; there is no ratio key, and the number is the fraction retained.
  • An explicit max_output_tokens must be an integer 1–4096 (or "inf"), and idle_timeout_ms is bounded 5000–30000 and only supported under server_vad.

And several things the baseline never covered:

  • There is a fourth realtime surface: translation sessions on /v1/realtime/translations, driven by gpt-realtime-translate. They are continuous — you do not call response.create, and you do not wait for a committed user turn. Transcription sessions likewise have their own create path (/v1/realtime/transcription_sessions, session.type: "transcription").
  • reasoning.effort is the main new tuning knob on Realtime 2. The overview guide says to "start with reasoning.effort set to low for most production voice agents, then adjust based on latency tolerance and task complexity."
  • OpenAI-Safety-Identifier is a recommended (not required) request header carrying a stable, privacy-preserving per-end-user ID. With ephemeral tokens it must be set on the server-side client_secrets call; it does not carry over from Responses API requests.
  • audio.input.transcription.delay tunes streaming-transcription latency against accuracy: minimal, low, medium, high, xhigh. gpt-live-transcribe takes languages (plural) where gpt-transcribe takes language — sending both is an error — and only gpt-transcribe returns detected-language output. Neither returns word timestamps, speaker labels or confidence scores.
  • gpt-realtime-2.1's model card gives a 32,000-token max output and a September 30 2024 knowledge cutoff alongside the 128K context window.
  • The public pricing page now carries only gpt-realtime-2.1 and gpt-realtime-2.1-mini under "Realtime and audio generation models". The older rows in the price table below are retained from the baseline and are no longer independently confirmable from the vendor's pricing page; they remain callable until the 2027-01-20 shutdown.

The transport table, event catalogs and session-config shapes below are still accurate in outline — the GA protocol itself did not change at Realtime 2 — but the model IDs, the transcription-model list and the context-window figure did.

Mini was introduced 2025-10-06 and is the default cost-optimized model for high-volume telephony agents; it loses some instruction-following and voice expressivity relative to full gpt-realtime. There is no batch tier; see the OpenAI Batch API entry for the offline 50%-discount surface (it does not accept Realtime audio jobs). Transports

Realtime ships three transports for the same model and event protocol; only the connection setup differs.

TransportEndpointAuthBest forLatency

WebRTCPOST /v1/realtime/calls (SDP exchange)Ephemeral client secretBrowser, native mobile~300 ms RTT to nearest region
WebSocketwss://api.openai.com/v1/realtime?model=gpt-realtimeAuthorization: Bearer <key>Server-to-server backend, Twilio media streams~400 ms (TCP head-of-line risk)
SIPsip:$PROJECT_ID@sip.api.openai.com;transport=tlsWebhook + project IDPhone lines via SIP trunk (Twilio Elastic, Telnyx, etc.)Telephony-grade

The same three transports also carry two non-conversational session types, which use different create paths and a different lifecycle: translation sessions on POST /v1/realtime/translations (model gpt-realtime-translate; continuous — never call response.create, never wait for a committed user turn) and transcription sessions via /v1/realtime/transcription_sessions with session.type: "transcription". Only the voice-agent session type uses the response.create / response.done turn cycle described in the rest of this entry.

WebRTC is recommended for any client environment because it owns jitter buffering, packet-loss concealment, and adaptive bitrate; WebSockets over the public internet do not. Server-side, WebSocket is simpler to operate and integrates directly with telephony bridges that already terminate SIP and forward 8 kHz mu-law audio (Twilio Media Streams, Vonage, Plivo). SIP is appropriate when the OpenAI endpoint is the SIP user-agent and a SIP trunk routes inbound PSTN calls to it; for outbound calls and finer call control the bridge pattern (your server holds the SIP leg and proxies audio over WebSocket) remains the safe production default in 2026 because the native SIP path is technically GA but documented as relatively new.

For the underlying transport tradeoffs (HTTP/3 vs raw TCP, head-of-line blocking, browser support) see the WebTransport entry.

Authentication: ephemeral client secrets

Browsers must never see the standard sk-... API key. The supported pattern is to mint a short-lived ephemeral key on your server, hand it to the browser, and let the browser establish the WebRTC peer connection directly with OpenAI.

POST https://api.openai.com/v1/realtime/client_secrets
Authorization: Bearer sk-...
Content-Type: application/json

{
  "session": {
    "type": "realtime",
    "model": "gpt-realtime",
    "audio": { "output": { "voice": "marin" } }
  }
}

The response contains a value field (the ephemeral key) and an expiration. The browser then performs the WebRTC SDP exchange against POST /v1/realtime/calls using that ephemeral value as its bearer token. The classic Authorization: Bearer sk-... flow is only legal from server-side WebSocket clients; never embed it in client code.

There is one REST endpoint (/v1/realtime/client_secrets) at GA; the older beta /v1/realtime/sessions flow with the OpenAI-Beta: realtime=v1 header is gone and should be removed when migrating off beta snapshots.

Session configuration

Every connection begins with a session.created event, after which the client sends a session.update to install instructions, voice, modalities, tools, and audio formats. Only fields present in the session.update payload are mutated; fields you omit are left untouched. The server replies with session.updated carrying the full effective config, which is the only authoritative source of truth.

{
  "type": "session.update",
  "session": {
    "type": "realtime",
    "model": "gpt-realtime",
    "instructions": "You are a friendly support agent. Confirm orders before processing.",
    "output_modalities": ["audio"],
    "audio": {
      "input": {
        "format": { "type": "audio/pcm", "rate": 24000 },
        "noise_reduction": { "type": "near_field" },
        "transcription": { "model": "gpt-live-transcribe" },
        "turn_detection": {
          "type": "server_vad",
          "threshold": 0.5,
          "prefix_padding_ms": 300,
          "silence_duration_ms": 500,
          "create_response": true,
          "interrupt_response": true
        }
      },
      "output": {
        "format": { "type": "audio/pcm", "rate": 24000 },
        "voice": "marin",
        "speed": 1.0
      }
    },
    "tools": [],
    "tool_choice": "auto",
    "max_output_tokens": "inf"
  }
}

Most changes can be made mid-session; switching the audio output format is the notable exception (the WebRTC track's encoder is fixed at SDP-negotiation time, so output format is effectively pinned for the connection lifetime).

Audio formats

Format typeSample rateWidthUse

WebRTC negotiates the codec at SDP time and base64 encoding is not used; the audio flows on a normal RTP audio track. Over WebSockets every chunk is base64 in input_audio_buffer.append, which is why telephony bridges typically pass through 8 kHz mu-law unchanged rather than re-encoding to PCM 24 kHz.

Corrected 2026-08-21: this paragraph used to say the beta names were still accepted for migration. They are not. With the realtime=v1 interface removed on 2026-05-12, the bare "pcm16" / "g711_ulaw" / "g711_alaw" strings and the flat top-level input_audio_format / output_audio_format keys are gone — a request built that way does not degrade, it fails to connect. Use the structured audio.input.format / audio.output.format objects with {type, rate} and the audio/pcm, audio/pcmu, audio/pcma type names shown in the table above.

Noise reduction and transcription

The audio.input.noise_reduction block runs before VAD and turn detection. Setting type to near_field is appropriate for headset and laptop microphones; far_field is for room microphones and conference setups; null disables noise reduction entirely.

The audio.input.transcription.model field selects the asynchronous transcription model that produces conversation.item.input_audio_transcription.completed server events. Corrected 2026-08-21: the supported values have turned over. developers.openai.com/api/docs/guides/realtime-transcription now documents gpt-live-transcribe (the recommended model — returns transcript deltas as speech arrives plus a final transcript) and gpt-transcribe (for when transcription should begin only after a committed audio turn, or when you need detected-language output). The older whisper-1 / gpt-4o-transcribe / gpt-4o-transcribe-latest / gpt-4o-mini-transcribe values are no longer listed for realtime sessions. Transcription is billed separately from the conversational model.

Voices

The built-in voice catalog is alloy, ash, ballad, coral, echo, sage, shimmer, verse, marin and cedar — ten values, unchanged at the 2026-08-22 re-check. The older eight are the cross-compatible legacy set carried from the beta and from text-to-speech; marin and cedar arrived with GA, and the reference now simply says "we recommend marin and cedar for best quality" with no per-model restriction stated. voice also accepts a custom voice object — {"id": "voice_1234"}.

Corrected 2026-08-22: voice is not freely mutable mid-session. The reference is explicit — "Voice cannot be changed during the session once the model has responded with audio at least once" — and the conversations guide repeats it. You can change it before the first assistant audio and not after, so pick it when you mint the session.

Voice activity detection (VAD)

VAD lives under audio.input.turn_detection; it is the single largest knob for perceived agent responsiveness.

server_vad is the default at GA. It chunks audio on energy: low energy below threshold for at least silence_duration_ms ends a turn. Defaults are threshold: 0.5, prefix_padding_ms: 300, silence_duration_ms: 500. Lower the threshold in noisy rooms; raise it in quiet rooms. Lower silence_duration_ms for snappier turn-taking but expect more cut-offs on slow speakers.

semantic_vad is the model-driven alternative: a separate classifier infers utterance completion from semantic content rather than energy. The eagerness field controls timing: low lets users take their time, auto (alias medium) is the default, high ends turns as soon as the model thinks an utterance is complete. Semantic VAD costs more (the classifier consumes audio tokens) but is dramatically better for users who pause mid-sentence.

Setting turn_detection: null disables both modes and puts the client in manual turn control: nothing happens until you input_audio_buffer.commit and then response.create. This is the right setting for push-to-talk UIs and for telephony bridges that already do their own DTMF-driven turn-taking.

create_response (default true in conversation mode) auto-fires response.create when a turn is detected; setting it to false lets you inspect a committed buffer and decide whether to respond. interrupt_response (default true) lets a new user turn truncate an in-flight assistant response; set it to false when interruptions should be queued instead.

Conversation items

The conversation is a flat list of items. Each item has a type and a role-or-call_id-keyed shape.

Item typeRole / fieldsPurpose

messageuser / assistant / system + content[]Text or audio in the conversation
function_callname, arguments, call_idModel-emitted call request
function_call_outputcall_id, outputClient-emitted tool result
audioimplicit on assistant messagesServer-emitted speech

Message content[] items use these inner types: input_text, input_audio (base64 over WebSocket), audio (assistant), text (assistant), and item_reference to point at an existing item by id (useful for context summarization).

Adding a system message after the session has begun is done by sending a conversation.item.create with a message item, role system, and input_text content. Use this sparingly; the model treats system content interleaved with user audio as in-conversation guidance, not as immutable policy.

Function calls

Tools are declared in session.update under tools[]. The shape mirrors function calling on the chat-completion side, but with a hard requirement that responses are sent back as function_call_output items.

{
  "type": "session.update",
  "session": {
    "tools": [
      {
        "type": "function",
        "name": "lookup_order",
        "description": "Look up an order by ID",
        "parameters": {
          "type": "object",
          "properties": { "order_id": { "type": "string" } },
          "required": ["order_id"]
        }
      }
    ],
    "tool_choice": "auto"
  }
}

When the model decides to call a tool, server emits response.output_item.added with a function_call item, then streams response.function_call_arguments.delta chunks until response.function_call_arguments.done. Your client executes the function and replies:

{
  "type": "conversation.item.create",
  "item": {
    "type": "function_call_output",
    "call_id": "call_sHlR7iaFwQ2YQOqm",
    "output": "{\"status\":\"shipped\",\"tracking\":\"1Z999AA10123456784\"}"
  }
}

Then send response.create (with no body, or with a partial response config) to let the model continue speaking. At GA, function calling is asynchronous: the session keeps speaking and accepting input while a tool call is pending, so long-running tools no longer freeze the agent. Send a placeholder function_call_output if the call will exceed a few seconds; otherwise the model may hallucinate the result.

MCP servers

The 2025-08-28 GA cut added remote MCP servers as a hosted tool type. Define them once in the session and the platform handles discovery, invocation, and result-injection.

{
  "type": "session.update",
  "session": {
    "tools": [
      {
        "type": "mcp",
        "server_label": "openai_docs",
        "server_url": "https://developers.openai.com/mcp",
        "allowed_tools": ["search_openai_docs", "fetch_openai_doc"],
        "require_approval": "never"
      }
    ]
  }
}

Provide either server_url for a public remote MCP server or connector_id (e.g. connector_googlecalendar) for a built-in OpenAI connector with authorization carrying the OAuth token. require_approval accepts never, always, or auto; on always/auto the model emits mcp_approval_request items and waits for mcp_approval_response from the client before invoking the tool. Tool discovery is async: the session emits mcp_list_tools.in_progress followed by mcp_list_tools.completed; new tools that appear later trigger mcp_tools_changed. Attaching tools on response.create instead of session.update scopes the tool to a single turn.

For the broader MCP context, see the MCP overview and the parallel Anthropic MCP client setup entry.

Image input

Image input was added at GA. Send a conversation.item.create with a message item carrying a content[] array that includes input_text and input_image parts (the base64 or URL form). The model can answer about the image in the next assistant turn; image input is available on the GA-line models (gpt-realtime, gpt-realtime-1.5, gpt-realtime-2 and gpt-realtime-2.1 plus their mini tiers), not on the legacy preview snapshots. Corrected 2026-08-22: image tokens are not billed at the text input rate. The pricing page carries a distinct Image row — $5.00 per 1M ($0.50 cached) on the full models and $0.80 per 1M ($0.08 cached) on mini, against $4.00 and $0.60 respectively for text. They are still not billed as audio.

Stored prompts and reusable prompt versions

GA introduced server-side stored prompts: create a prompt in the OpenAI dashboard with a stable ID, version it, and reference it from the session config:

{
  "type": "session.update",
  "session": {
    "prompt": {
      "id": "pmpt_01HXYZ...",
      "version": "3",
      "variables": { "city": "Paris", "tier": "premium" }
    }
  }
}

Direct fields on session (e.g. instructions) override matching fields from the stored prompt. Stored prompts apply to both Realtime and Responses; use them when the prompt is shared across surfaces or when you want versioned rollback without redeploying clients.

conversation.item.truncate is the most under-documented client event: when a user interrupts, you must truncate the assistant audio item at the byte offset the user actually heard, otherwise the model assumes the entire response was delivered and the next turn references material the user never received.

SIP, DTMF, and call control

A SIP trunk (Twilio Elastic SIP, Telnyx, Vonage) sends inbound calls to sip:$PROJECT_ID@sip.api.openai.com;transport=tls. OpenAI fires a realtime.call.incoming webhook to the URL configured under platform.openai.com - Project - Webhooks; the payload includes call_id and SIP headers (From, To, Call-ID).

EndpointAction

POST /v1/realtime/calls/{call_id}/acceptAccept the call and configure the session inline
POST /v1/realtime/calls/{call_id}/rejectDecline; optional SIP status_code (e.g. 486 Busy Here)
POST /v1/realtime/calls/{call_id}/referTransfer; pass target_uri like tel:+14155550123 or sip:agent@example.com
POST /v1/realtime/calls/{call_id}/hangupEnd the call (works for SIP and WebRTC)

After accept, your server upgrades to a WebSocket on wss://api.openai.com/v1/realtime?call_id={call_id} to stream events. DTMF presses on the phone keypad arrive as input_audio_buffer.dtmf_event_received server events carrying event (the keypad character) and received_at (a UTC Unix timestamp); you can use them for IVR-style flows or to trigger transfers without invoking the model.

sip.api.openai.com performs GeoIP routing and terminates TLS; the dedicated SIP IP ranges added 2026-01-13 let enterprise SIP firewalls allowlist by /32 instead of the previous shared edge IP.

When the conversation outgrows the context, the server auto-truncates older items in chronological order. Set truncation: "disabled" to suppress automatic truncation (you must manually conversation.item.delete to make room) or use retention-ratio truncation — truncation: { "type": "retention_ratio", "retention_ratio": 0.8 }, optionally with token_limits: { "post_instructions": N } — which drops messages until the retained conversation fits inside 80% of the maximum allowed tokens. Corrected 2026-08-22: there is no ratio key, truncation: { ratio: 0.8 } is not a valid shape, and the number is the fraction retained, not the fraction dropped. Over-dropping in one shot is the point: it buys headroom before the next truncation and so preserves more of the prompt cache than per-message eviction.

Migrating from beta to GA

The breaking changes at the 2025-08-28 GA cut, in order of impact:

1. Model name change: gpt-4o-realtime-preview snapshots are legacy; new code uses gpt-realtime or gpt-realtime-mini (or gpt-realtime-1.5 from 2026-02-23).
2. Remove the OpenAI-Beta: realtime=v1 header.
3. Replace /v1/realtime/sessions with POST /v1/realtime/client_secrets for ephemeral keys.
4. Move from flat input_audio_format/output_audio_format to structured audio.input.format and audio.output.format objects with {type, rate}.
5. Update event-name handlers: response.audio.delta to response.output_audio.delta, response.text.delta to response.output_text.delta, and so on.
6. Add a type: "realtime" discriminator at the top of the session object in session.update (it now coexists with type: "transcription" for transcription-only sessions).
7. Function calls are async at GA; remove any blocking pause-the-session-during-tool-call logic on the client.

The OpenAI Agents SDK wraps these differences in TypeScript and Python, and is the recommended migration shortcut if you do not need raw event-level control. The Vercel AI SDK 6 also ships a Realtime adapter for browser apps that abstracts the WebRTC SDP exchange.

For rate limits and error codes, the Realtime API uses the same per-tier RPM/TPM model as the rest of the OpenAI surface, but additionally tracks active concurrent realtime sessions per project; rate limit headers come back inside rate_limits.updated server events rather than HTTP response headers because the connection is long-lived.

Common gotchas

1. Never expose your standard API key in browser code; always go through /v1/realtime/client_secrets and a server-side mint step. The ephemeral key is valid for one session and expires; it cannot be reused across reconnects.
2. The browser-side WebRTC SDP exchange goes to POST /v1/realtime/calls, not wss://api.openai.com/v1/realtime; the WebSocket URL is for server clients only.
3. Audio format mismatches produce static, not errors. Twilio Media Streams send 8 kHz mu-law; setting your output format to PCM 24 kHz puts the wrong samples on the wire and the caller hears noise.
4. pcm16 (the legacy beta string) and audio/pcm (the GA structured form) no longer coexist — corrected 2026-08-21: the beta interface was removed 2026-05-12, so an SDK version old enough to emit pcm16 cannot open a session at all. Upgrade the SDK rather than pinning a format string.
5. Default silence_duration_ms of 500 is too aggressive for elderly callers and slow speakers; bump to 800-1000 ms or use semantic_vad to fix random mid-thought cut-offs.
6. semantic_vad with eagerness: high is what drives the "polite interruption" feel of consumer voice agents; default auto is conservative and feels sluggish.
7. interrupt_response: true plus a missing conversation.item.truncate after the user interrupts is the single most common cause of "the assistant repeats itself"; truncate the assistant audio item to the byte position the user actually heard.
8. conversation.item.truncate requires the audio sample offset, not the text character offset; on WebRTC, you compute it from the playback currentTime of the assistant audio element.
9. WebSocket clients must send input_audio_buffer.append at near-realtime cadence; bursting a whole utterance in one frame triggers VAD on the burst boundary instead of on user-pause boundaries.
10. input_audio_buffer.commit requires at least 100 ms of buffered audio (the minimum chunk); committing an empty buffer raises an error event with code: input_audio_buffer_commit_empty.
11. Function calling is async at GA; do not pause sending audio while waiting for a tool result. The model continues to listen and may queue or interrupt the user before your function_call_output arrives.
12. Tool definitions changed in length tracking: 64 in-flight tools per response is the hard cap; declaring 200 tools in session.update works for declaration but only the model-selected subset can run concurrently.
13. MCP servers are billed by the audio model's tokenization of the tool descriptions; very chatty MCP tools/list responses can balloon every turn's input token count.
14. require_approval: "never" is convenient for prototyping but unsafe; production voice agents that mutate state should use auto and audit mcp_approval_request events.
15. Image input is on gpt-realtime and gpt-realtime-1.5 only; gpt-realtime-mini accepts images on the schema but the snapshots do not yet model them well, and you may see hallucinated descriptions.
16. The 60-minute hard session cap is per connection; for longer calls, save the conversation summary, reconnect, and seed the new session with conversation.item.create carrying the summary as a system message.
17. Prompt caching only persists within a single connection; reconnects always pay the full input price for replayed history.
18. output_modalities defaults to ["audio"]; setting it to ["text"] switches the model to a chat-style behavior that does not generate audio at all (useful for transcript-only sidecars).
19. voice cannot be set in two places that both win: if a stored prompt sets voice: alloy and session.update sets voice: marin, the session field overrides. Be explicit in one place — and set it before the first assistant audio, because the reference locks voice "once the model has responded with audio at least once".
20. idle_timeout_ms is the GA replacement for client-side "are you still there" hacks; set it to 8000-12000 ms for natural conversation. There is no default, the accepted range is 5000-30000 ms, it lives on the server_vad turn-detection object (it is not supported under semantic_vad or manual turn control), the clock starts after the last response's audio has finished playing, and firing emits input_audio_buffer.timeout_triggered plus the usual response events.
21. The GA voices marin and cedar arrived with the GA-line models — gpt-realtime, gpt-realtime-1.5, gpt-realtime-mini and, since 2026-07-06, gpt-realtime-2.1 / -2.1-mini. Re-checked 2026-08-22: the reference no longer states a per-model restriction, it simply recommends the two for best quality. (Updated 2026-08-21: the legacy-preview half of this gotcha is moot — gpt-4o-realtime-preview and gpt-4o-mini-realtime-preview shut down 2026-05-07, so there is no preview snapshot left to set a voice on.)
22. SIP webhooks fire from OpenAI's IP ranges; allowlist the dedicated ranges added 2026-01-13 in your reverse-proxy WAF or webhooks will appear to vanish.
23. DTMF arrives as input_audio_buffer.dtmf_event_received (SIP sessions only), not as transcribed text — and note the event name is the long one; a handler registered for input_audio_buffer.dtmf never fires. Also, the model does not see "1" when the caller presses 1, so build your IVR logic in client code, not in the system prompt.
24. gpt-realtime-1.5 (2026-02-23) silently fixed a number of tool_choice: "required" edge cases; if you forced tool selection on the GA snapshot to work around hallucinated text, you can drop the workaround on 1.5.
25. WebRTC connection setup involves four moving parts (STUN, TURN, ICE candidates, SDP); when "the call connects but no audio plays", the issue is almost always missing audioElement.srcObject = e.streams[0] in the RTCPeerConnection.ontrack handler, not an OpenAI-side problem.
26. The native SIP endpoint is GA but new (2025-08-28); for high-volume telephony, pinning a Twilio bridge in front of WebSocket transport gives more operational levers (recording, bridging to another agent, SBCs) than the bare SIP path.
27. gpt-realtime-mini is dramatically cheaper but loses ~5-10% on instruction-following benchmarks vs full gpt-realtime; A/B before defaulting to mini for regulated or safety-critical voice agents.
