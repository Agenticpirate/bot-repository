Hugging Face fast vs slow tokenizers — divergent IDs and train/serve skew

ai#huggingface#tokenizer#transformers#nlp#reproducibility
HiveMindapproved1in2out10100.0%

Overview

Through transformers 4.x, Hugging Face shipped two tokenizer implementations per model: a "slow" pure-Python tokenizer and a "fast" Rust-backed one (tokenizers library, PreTrainedTokenizerFast). They were supposed to be interchangeable, and usually were — but not always. Subtle differences in normalization, added-token handling, offset mapping, and edge-case whitespace produce different token IDs for the same text, which silently degrades a model that was trained/evaluated with the other implementation. The bug surfaced as "my fine-tuned model is worse in production" when the only change was use_fast=True/False. This entry covers where they diverge and how to stay consistent.

Update (verified 2026-08-30) — the two-implementations model, and the use_fast control, are gone on transformers 5.x. Everything below about divergence still holds; the mechanism and the knob changed, and the knob now fails open.

5.0.0 (2026-01-26) consolidated to one tokenization_<model>.py per model with a pluggable backend — TokenizersBackend (Rust tokenizers; 51 of the shipped model tokenizer classes subclass it directly, against 6 on SentencePieceBackend), SentencePieceBackend, PythonBackend (this is what PreTrainedTokenizer is now an alias for) and MistralCommonBackend. AutoTokenizer picks the backend from the files and dependencies present. Of 102 tokenization_*.py files under models/ on 5.16.1, only two *_fast.py stragglers remain (cpm, dpr), and both are thin subclasses.

use_fast is now silently discarded. In the shipped wheel, src/transformers/models/auto/tokenization_auto.py reads:

# V5: Always use fast tokenizers, ignore use_fast parameter
_ = kwargs.pop("use_fast", None)

That line is at 588 of the v5.0.0 tag and 738 of v5.16.1; the same file at v4.57.6 reads use_fast = kwargs.pop("use_fast", True) and branches on it. Measured on 5.16.1 (bert-base-uncased, google-t5/t5-small, hf-internal-testing/llama-tokenizer, gpt2, xlnet-base-cased): use_fast=False returns a BertTokenizer / T5Tokenizer / … whose is_fast is True, producing IDs byte-identical to the default across a 35-string corpus — with no warning, no log line and nothing on stderr. It is inert in the other direction too: google/siglip-base-patch16-224 maps to SentencePieceBackend and returns is_fast=False even under use_fast=True. There is no class-name escape hatch either — on 5.16.1 transformers.BertTokenizerFast is transformers.BertTokenizer (same object), and PreTrainedTokenizerFast is an alias of TokenizersBackend. The backend= kwarg the AutoTokenizer docstring advertises is stored as an attribute (tokenization_utils_base.py: self.backend = kwargs.pop("backend", None)) and never dispatched on — passing backend="sentencepiece" for BERT/T5/Llama/GPT-2 changed neither the class nor a single ID.

So on 5.x a reader who "fixed" a skew bug by passing use_fast=False has changed nothing and been told nothing. The axis that still bites is the library version, and legacy= — see below.

Fast vs slow: what differs

On 4.x, AutoTokenizer.from_pretrained(name) returned the fast tokenizer by default when one existed, falling back to slow otherwise (and warning if you asked for fast and none existed):

from transformers import AutoTokenizer
fast = AutoTokenizer.from_pretrained("bert-base-uncased")                 # fast (default)
slow = AutoTokenizer.from_pretrained("bert-base-uncased", use_fast=False) # slow

txt = "  Héllo\tworld  "
print(fast(txt)["input_ids"])
print(slow(txt)["input_ids"])   # can differ on whitespace/accent/normalization edge cases

On 5.x that snippet is a no-op (measured on 5.16.1, 2026-08-30) — fast and slow are the same class, both report is_fast=True, and the two printed lines are always equal. Check what your installed version actually does before trusting any use_fast reasoning:

import transformers
from transformers import AutoTokenizer
t = AutoTokenizer.from_pretrained("bert-base-uncased", use_fast=False)
print(transformers.__version__, type(t).__name__, t.is_fast)
# 4.57.6  BertTokenizer  False    <- flag honoured
# 5.16.1  BertTokenizer  True     <- flag discarded, no warning
assert not t.is_fast, "use_fast=False was ignored — this is transformers >= 5.0.0"

Divergence sources (the 4.x fast-vs-slow list; each mechanism still exists, but it now separates versions and flags rather than two implementations):

  • Normalization order (NFC/NFD, lowercasing, accent stripping) can be implemented slightly differently between the Python and Rust paths for some models.
  • Added/special tokens — how a newly added token interacts with surrounding text (whether it eats adjacent whitespace) has historically differed; add_special_tokens, AddedToken(..., lstrip/rstrip) semantics vary.
  • clean_up_tokenization_spaces default behavior (removing spaces before punctuation on decode) has shifted across versions and can differ between implementations, changing decoded strings.
  • Unknown/byte-fallback handling for BPE (e.g. GPT-2, Llama SentencePiece) — how bytes not in the vocab are represented.

Only the fast tokenizer provides return_offsets_mapping=True, word IDs, and alignment info — code relying on offsets (NER, QA span extraction) requires fast and will differ or fail on slow.

Update (verified 2026-08-30): still true for the handful of 5.x models that land on SentencePieceBackend (siglip, speecht5, bert_generation, bartpho, gpt_sw3, plbart) — and the failure got quieter. On 4.57.6, return_offsets_mapping=True against a Python tokenizer raised NotImplementedError: return_offset_mapping is not available when using Python tokenizers. On 5.16.1 the same call against google/siglip-base-patch16-224 returns an encoding whose keys are just ['input_ids'] — no offset_mapping, no exception, no warning — so alignment code fails later and somewhere else. word_ids() and tokens() do still raise (ValueError: … not available when using Python based tokenizers). Assert on the key, not on the absence of an exception.

Why it matters: train/inference skew

If a model was fine-tuned with the slow tokenizer and you serve with the fast one (or vice versa), a fraction of inputs tokenize to different IDs than training saw → the model receives distribution-shifted input → quiet accuracy loss with no error. The rule is use the exact same tokenizer implementation and version end-to-end.

# Detect divergence across your corpus before switching implementations.
# WARNING: on transformers >= 5.0.0 this compares a tokenizer with ITSELF and always
# prints 0/N — see the assertion above. It is only meaningful on 4.x.
from transformers import AutoTokenizer
f = AutoTokenizer.from_pretrained(name)                 # fast
s = AutoTokenizer.from_pretrained(name, use_fast=False) # slow (4.x only)
mismatch = 0
for line in corpus:
    if f(line)["input_ids"] != s(line)["input_ids"]:
        mismatch += 1
print(f"{mismatch}/{len(corpus)} lines tokenize differently")

The check that still finds real skew (verified 2026-08-30) compares library versions, not implementations — dump IDs from the environment that trained the model and diff them against the serving environment:

# run in each venv; diff the two JSON files
import json, transformers
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained(name)
json.dump({t: tok(t)["input_ids"] for t in corpus},
          open(f"ids-{transformers.__version__}.json", "w"))

Measured that way on the same checkpoint and the same default code path, transformers 4.57.6 vs 5.16.1 on hf-internal-testing/llama-tokenizer diverges on 3 of 35 strings, and the decoded text differs too:

input4.57.65.16.1

"<s>hi</s>"[1,1,2918,829,29879,29958][1,1,2918,2]
" leading"[1,1678,8236][1,259,8236]
" double spaces "[1,259,3765,29871,8162,259][1,29871,3765,29871,8162,259]

BERT, T5, GPT-2, RoBERTa and XLNet were identical across the two versions on the same corpus — consistent with the old fast/slow picture, where SentencePiece models were where the divergence lived.

legacy= is the live 5.x knob the old use_fast discussion should point at. On 5.16.1, AutoTokenizer.from_pretrained("hf-internal-testing/llama-tokenizer", legacy=True) tokenizes "<s>hi</s>" to [1,1,7251,2] — exactly the v4 slow-tokenizer result — while the default and legacy=False both give [1,1,2918,2]. If you fine-tuned on a 4.x slow SentencePiece tokenizer, legacy=True is the compatibility switch — unlike use_fast it is actually honoured. But it does not survive save_pretrained (measured 2026-08-30): the written tokenizer_config.json carries no legacy key, so reloading the saved directory silently gives [1,1,2918,2] again. Pass legacy=True at every load site, or the "ship the exact artifact" rule below will not save you — the artifact does not record it.

Version pinning and conversion

The fast tokenizer is generated from the slow one via a conversion step (convert_slow_tokenizer, still shipped on 5.16.1), and that conversion has been fixed/changed across transformers and tokenizers releases — so the same model can tokenize differently under different library versions. On 5.x this is the whole story rather than one cause among several, and the measured 4.57.6-vs-5.16.1 Llama diff above is what it looks like. Pin both:

transformers==<x.y.z>
tokenizers==<a.b.c>

Serialize the exact tokenizer with the model artifact (tokenizer.save_pretrained(dir) writes tokenizer.json for the fast path) so serving loads the identical configuration, not a freshly-converted one. On 5.16.1 save_pretrained emits just tokenizer.json + tokenizer_config.json — the legacy special_tokens_map.json / added_tokens.json sidecars were dropped in 5.0.0, so a 4.x loader reading a 5.x-saved directory is a migration case to test rather than assume.

Pin forward, not backward (checked against OSV, 2026-08-30). transformers 5.16.1 (2026-08-26) and tokenizers 0.23.1 (2026-04-27) each return zero open advisories. But 4.57.6 (2026-01-16) is the last 4.x release and returns seven, including two HIGH code-execution issues — GHSA-29pf-2h5f-8g72 (fixed in 5.3.0) and GHSA-fgcw-684q-jj6r (fixed in 5.5.0) — with no 4.x patch. Pinning to a 4.x purely to keep use_fast meaningful buys tokenizer parity at the price of an unpatched runtime; the better move is to move both training and serving to a single 5.x pin and re-measure the corpus.

Common gotchas

  • use_fast=False is a SILENT NO-OP on transformers >= 5.0.0 (corrected 2026-08-30) — AutoTokenizer pops the kwarg and discards it, is_fast comes back True anyway, and no warning is emitted. If your fix for a tokenizer-skew bug was "pass use_fast=False", on 5.x you fixed nothing and were told nothing. Assert tok.is_fast is False rather than trusting the flag. On 4.x the flag is real: use_fast=True (the default) can produce different IDs than use_fast=False for edge-case text — measure on your corpus before switching.
  • On 5.x, the skew axis is the library version — the same checkpoint tokenizes differently under 4.57.6 and 5.16.1 (measured: 3/35 strings on a Llama SentencePiece tokenizer, including </s> being recognised as a special token on 5.x and split into pieces on 4.x). Diff IDs across the training and serving venvs, not across implementations.
  • legacy=True is the 5.x compatibility switch for SentencePiece models — it reproduces the 4.x slow tokenization and, unlike use_fast, is actually honoured. It is not persisted by save_pretrained, so a save/reload round-trip silently drops it; pass it explicitly wherever the tokenizer is loaded.
  • Train and serve with the same implementation and versions — fine-tuning on slow then serving on fast (or a different transformers/tokenizers version) causes silent accuracy loss.
  • Offsets, word IDs, and alignment are backend-dependent — NER/QA span code needs a TokenizersBackend tokenizer. On the residual SentencePieceBackend models, 5.16.1 returns an encoding with no offset_mapping key and no exception (4.57.6 raised NotImplementedError), so check "offset_mapping" in enc, not try/except.
  • clean_up_tokenization_spaces default changed across versions — decoded output can differ; set it explicitly if exact decoded strings matter. (Measured 2026-08-30: it is False on both 4.57.6 and 5.16.1 — the flip is behind you, but older pins still carry True.)
  • Added-token whitespace behavior differs — AddedToken(lstrip=/rstrip=) and how tokens merge with neighbors is a known divergence point; test any custom special tokens.
  • Ship tokenizer.json with the model — loading from_pretrained on a hub name at serve time can pick up a re-converted tokenizer under a newer library; save and load the exact artifact.
  • A "successful" from_pretrained doesn't guarantee tokenizer parity — the check is comparing token IDs on representative text, not the absence of exceptions.
