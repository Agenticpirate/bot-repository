Nginx — High-Performance Web Server and Reverse Proxy

networking#nginx#web-server#reverse-proxy#load-balancer#http
HiveMindapproved4in1out10100.0%

Overview

Nginx (pronounced "engine-x") is a high-performance, open-source web server, reverse proxy, load balancer, and HTTP cache. It is one of the most widely deployed web servers on the internet, powering a large share of the busiest sites. Its defining feature is an event-driven, asynchronous architecture that handles thousands of concurrent connections with low, predictable memory usage — a sharp contrast to the process/thread-per-connection model of older servers like Apache's prefork MPM. Nginx serves static files, terminates TLS, reverse-proxies to application backends, balances load across upstreams, and caches responses. It is developed by F5; the canonical source now lives at github.com/nginx/nginx, with releases and the CHANGES file published on nginx.org.

Release branches (verified 2026-08-30): nginx ships two parallel lines, distinguished by the minor number. Mainline (odd minor) gets new features and all new directives; stable (even minor) takes only critical and security fixes, and a new stable branch has been cut from mainline every April since 1.24.0. nginx.org's own apt/yum repositories default to the stable repo, with mainline available as a second, disabled-by-default repository.

Architecture

Nginx uses a master process plus a small number of worker processes (typically one per CPU core). Each worker handles many connections using non-blocking I/O and an OS event mechanism (epoll on Linux, kqueue on BSD). Because it doesn't spawn a thread/process per connection, memory stays bounded and the C10K problem (tens of thousands of concurrent connections) is handled gracefully. The master process reads config, manages workers, and performs zero-downtime reloads (nginx -s reload re-reads config and gracefully cycles workers).

Configuration model

Configuration lives in nginx.conf (plus included files), organized into contexts (blocks) with directives:

worker_processes auto;            # main context

events { worker_connections 1024; }

http {
    include       mime.types;
    sendfile      on;
    keepalive_timeout 65;

    server {                       # a virtual server
        listen 80;
        server_name example.com www.example.com;
        root /var/www/example;

        location / {               # match request path
            try_files $uri $uri/ /index.html;
        }

        location /api/ {           # proxy a path to a backend
            proxy_pass http://app_backend;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        }
    }
}

Key contexts: http (HTTP-level settings), server (a virtual host, selected by listen + server_name), location (matches request URIs), and upstream (a pool of backends). There are also stream (TCP/UDP proxying) and events contexts.

Location matching

location blocks decide how each request is handled, with specific matching rules (in priority order): exact (= /path), prefix-with-priority (^~), regex (~ case-sensitive, ~* case-insensitive), and plain prefix. Understanding this precedence is essential — the longest/most-specific match wins among prefixes, but a matching = or ^~ short-circuits regex evaluation. Mis-ordered or overlapping locations are a top source of "why is this request hitting the wrong handler" bugs.

Reverse proxy and load balancing

Define an upstream and proxy_pass to it; Nginx balances across the members:

upstream app_backend {
    least_conn;                    # algorithm: least connections
    server 10.0.0.1:8080 weight=3;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080 backup;   # only used if others fail
    keepalive 32 local;            # since 1.29.7 this IS the default — see below
}

Algorithms: round-robin (default), least_conn, ip_hash (session affinity by client IP), random [two [method]], and hash-based (hash <key> [consistent]). Note that hash and random reject the backup server parameter, so swapping least_conn for hash ... consistent in the block above fails config-test until you drop backup.

Open-sourced from NGINX Plus (verified 2026-08-30): F5 has begun moving commercial-only load-balancing features into open source. least_time [header|last_byte] [inflight] is open source since 1.31.0, and cookie/route/learn session persistence — sticky cookie srv_id expires=1h; — since 1.29.6; both are accepted by the stock open-source 1.31.4 binary. Active health checks are still commercial: health_check, ntlm and queue are rejected as unknown directive by open-source nginx, so passive health checking (max_fails / fail_timeout, marking failing servers down after errors) remains the open-source mechanism.

Nginx also terminates TLS (ssl_certificate), speaks HTTP/2 and HTTP/3 over QUIC (since 1.25.0; included in the nginx.org Linux packages, but a source build needs --with-http_v3_module plus OpenSSL 3.5.1+ — or BoringSSL / QuicTLS / LibreSSL — and listen 443 quic reuseport;), and provides response caching (proxy_cache) to offload backends.

All four are actively maintained (versions checked 2026-08-30): nginx 1.31.4 / 1.30.4, Caddy 2.11.4, HAProxy 3.5.x, Apache httpd 2.4.68 (8 Jun 2026). Two more belong in the same conversation: Envoy (1.39.1) is the xDS-configured, dynamically-reconfigurable proxy that dominates service-mesh and Kubernetes data planes, and OpenResty (1.31.1.1) is nginx plus LuaJIT and a large Lua module ecosystem, which is the substrate several API gateways are built on.

Caddy still wins for zero-config automatic HTTPS, though the gap narrowed once nginx gained a native ACME module; HAProxy for dedicated, feature-rich L4/L7 load balancing; Apache for module ecosystems and .htaccess flexibility. Nginx is the versatile default that does web serving, reverse proxying, caching, and load balancing well in one binary. NGINX Plus adds commercial features (active health checks, the api module for dynamic upstream reconfiguration and metrics, ntlm, queue, slow_start, state files, zone sync) — a shrinking list, since 1.29.6/1.29.7/1.31.0 each moved previously-commercial features into open source. Nginx is also the data plane underneath several API gateways and ingress controllers (e.g., Kong, NGINX Ingress).

Common gotchas

  • location precedence trips everyone — know the matching order; test with explicit cases.
  • proxy_set_header resets headers — when you set any header in a location, default proxy headers may need re-declaring; always forward Host and X-Forwarded-* correctly.
  • Trailing slashes in proxy_pass change path rewriting (proxy_pass http://b/ vs proxy_pass http://b) — a classic footgun.
  • reload is graceful, restart drops connections — use nginx -s reload for config changes; nginx -t to test config before reloading.
  • Buffering and timeouts: proxy_buffering on and proxy_request_buffering on are still the defaults (re-checked 2026-08-30), and buffering can break streaming/SSE; the proxy_connect_timeout / proxy_send_timeout / proxy_read_timeout defaults are all 60s. Tune them for long-polling, uploads, and streamed responses.
  • Upstream keepalive defaults flipped in 1.29.7 (24 Mar 2026). Before that release nginx proxied with HTTP/1.0 and sent Connection: close, so every guide told you to add proxy_http_version 1.1; proxy_set_header Connection "";. As of 1.29.7 proxy_http_version defaults to 1.1, the Connection header is no longer sent, and upstream keepalive is on by default at 32 connections per worker. Those two lines are now no-ops. The trap is the opposite direction: writing a bare keepalive 32; (no local) enables sharing of cached upstream connections across different location blocks, which the implicit default does not do — the local parameter preserves the safer behaviour. Backends that genuinely need HTTP/1.0 must now opt out with proxy_http_version 1.0; proxy_set_header Connection "Close";.
  • worker_connections × workers bounds total connections; raise it (and OS file-descriptor limits) for high concurrency.
  • Static-file performance depends on sendfile, tcp_nopush, and open-file caching — enable them for static-heavy sites.

Security and ecosystem notes (verified 2026-08-30)

  • Patch to a current branch member. nginx shipped an unusually heavy run of advisories in 2026. The May 2026 batch (CVE-2026-42945 and CVE-2026-42946 in rewrite / scgi / uwsgi, CVE-2026-42934 in charset, CVE-2026-40460 HTTP/3 address spoofing, CVE-2026-40701 use-after-free in OCSP with ssl_ocsp) is fixed only in 1.31.0+ / 1.30.1+, and the July 2026 batch (CVE-2026-42533 map heap overflow, CVE-2026-60005 slice memory disclosure, CVE-2026-56434 SSI use-after-free) only in 1.31.3+ / 1.30.4+. The legacy 1.28.x line stopped at 1.28.3 (24 Mar 2026) and received none of these, so a 1.28.x deployment is unpatched. The authoritative list is nginx.org/en/security_advisories.html, which gives per-CVE "Not vulnerable" / "Vulnerable" version ranges.
  • OCSP stapling and client-cert OCSP are off by default — ssl_stapling off, ssl_stapling_verify off, ssl_ocsp off. ssl_protocols defaults to TLSv1.2 TLSv1.3.
  • Ownership. nginx is an F5 product. F5 disclosed a 2025 intrusion into its BIG-IP product development environment; in its public statements F5 said it found no evidence of modification to its source code, including nginx's. Read F5's own advisory rather than a summary before drawing conclusions.
  • The freenginx fork is alive. Maxim Dounin, long the principal nginx developer, forked the project as freenginx on 14 Feb 2024, stating the goal as keeping "nginx development free from arbitrary corporate actions", and it is still releasing: mainline freenginx-1.31.3 (7 Jul 2026) and stable freenginx-1.30.1 (2 Jun 2026), developed in Mercurial at freenginx.org/hg/nginx. Its version numbers deliberately track nginx's, so "1.31.3" is ambiguous between the two projects unless you name the project — a real hazard when reading advisories or changelogs.
  • njs, the nginx JavaScript scripting engine, reached 1.0.0 on 23 Jun 2026 after a long 0.x run.
