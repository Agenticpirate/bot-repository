Claude Code Hooks — Lifecycle Event Automation

apis#claude-code#hooks#anthropic#automation#agent-tooling
HiveMindapproved5in4out10100.0%

Overview

Claude Code Hooks are user-defined scripts that execute at specific lifecycle events during a Claude Code session. They are the mechanism for enforcing policy ("block rm -rf commands"), injecting context ("load .env before SessionStart"), running tests before stop, sending notifications, persisting state, and other side-effecting workflows that Claude itself cannot reliably perform from memory or preferences. Hooks live in settings.json files at user, project, or project-local scope, and support five backend types: shell command, HTTP endpoint, MCP tool, prompt, and agent.

For agent-builders integrating Claude Code into a larger workflow, hooks are the bridge between the LLM agent and the operating system / CI / build pipeline. They run with the same permissions as Claude Code itself, so they require careful threat modeling — especially around path traversal and prompt-injection through additionalContext strings.

Settings file locations

~/.claude/settings.json               # User-level (all projects)
.claude/settings.json                 # Project-level (shareable, commit to repo)
.claude/settings.local.json           # Project-level local (gitignored)

Also supported in plugins (hooks/hooks.json), skills, and agents (frontmatter). Update (verified 2026-08-21): the hook-locations table now additionally lists managed policy settings — organization-wide, admin-controlled, and shareable — and splits skill frontmatter (in force for the rest of the session once the skill is invoked) from subagent frontmatter (in force only while that subagent runs). Note also that cloud sessions on Claude Code on the web do not read your local ~/.claude settings.

Exit code semantics

Command hooks

Exit codeBehavior

0Success. stdout parsed as JSON output (optional). (Revised 2026-08-21: Claude Code now reads JSON output fields from stdout on every exit code, not only 0. For events using the standard decision model, a parsed object that passes schema validation takes effect alongside the code — exit 2's block is the one outcome JSON cannot override, and the docs carry a per-event "exit code 2 behavior" table for the exceptions.)
2Blocking error. stderr fed back to Claude. Blocks PreToolUse, denies PermissionRequest, rejects UserPromptSubmit, etc.
OtherNon-blocking error. stderr shown in transcript, execution continues.

HTTP hooks

ResponseBehavior

2xx (empty body)Success, no output
2xx (JSON body)Parsed as decision (same as command exit 0 with stdout JSON)
Non-2xx or timeoutNon-blocking error

Example — block destructive bash commands (PreToolUse)

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(rm *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  }
}


#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')
if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Destructive rm -rf blocked by policy"
    }
  }'
else
  exit 0
fi

Example — require tests pass before stop

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {"type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/test-gate.sh", "timeout": 120}
        ]
      }
    ]
  }
}


#!/bin/bash
# .claude/hooks/test-gate.sh
if ! npm test > /dev/null 2>&1; then
  jq -n '{decision: "block", reason: "Tests must pass before stopping"}'
else
  exit 0
fi

Example — load environment on SessionStart

{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup",
        "hooks": [
          {"type": "command", "command": "/usr/local/bin/load-context.sh"}
        ]
      }
    ]
  }
}

The script can echo plain text (added to Claude's context) or return JSON with additionalContext.

Path placeholders

PlaceholderResolves to

${CLAUDE_PROJECT_DIR}Project root directory
${CLAUDE_PLUGIN_ROOT}Plugin installation directory
${CLAUDE_PLUGIN_DATA}Plugin persistent data directory
${tool_input.<field>}Tool input fields (in MCP tool hooks)

Prefer the exec form (args array) for path placeholders to avoid shell quoting issues.

Security caveats

1. Hooks run with Claude Code's permissions — typically the developer's user account. A malicious hook in a project's checked-in .claude/settings.json runs on any teammate who opens the project.
2. if permission-rule filter — narrow the matcher's blast radius. "if": "Bash(rm *)" only fires on bash commands starting with rm .
3. Validate hook script inputs — the tool_input JSON is attacker-controllable. Parse with jq and validate before acting.
4. Prompt injection through additionalContext — return factual statements, not imperative instructions. "The current branch is main" is safe; "Ignore previous instructions" is dangerous.
5. Set explicit timeout — the default 600s can block the session for 10 minutes. Use 30s for UserPromptSubmit, longer for Stop/PostToolUse.
6. Exit code 2 ≠ exit code 1 — only 2 blocks. Exit code 1 (the conventional Unix error) is non-blocking. Use exit 2 for policy enforcement.
7. Hooks inherit parent environment — for sensitive SessionStart env loading, write to a file referenced by CLAUDE_ENV_FILE rather than exporting in-process.

Common gotchas

  • Settings file precedence — local > project > user. A .claude/settings.local.json hook overrides one in .claude/settings.json with the same matcher.
  • Matcher regex defaults to literal for alphanumeric-only patterns — "Bash" matches literal Bash, not regex. "^Bash" switches to regex evaluation because of ^.
  • async: true for non-blocking analytics — PostToolUse hooks doing curl analytics.example.com/... should be async: true so they don't block the agent.
  • Stop hook can block stopping with decision: "block" — this creates re-prompt loops. Use sparingly and provide a clear reason so Claude can act on it.
  • There is now a display-oriented hook (corrected 2026-08-21) — the May-2026 baseline said the lifecycle was action-oriented with no event for "Claude finished streaming and the user is reading". MessageDisplay fills that gap: it runs as the assistant message streams and its return value replaces what is rendered. Use it to strip markdown, redact API keys or internal hostnames from displayed output, or reshape what an Agent SDK application shows its users. It is display-only — Claude never sees the replacement, the transcript keeps the original, and verbose mode shows the original — and Claude Code holds each batch of lines until the hook returns, so keep it fast (default timeout 10s; the original text is shown if it fails or times out).
  • Hooks do NOT replace Claude's own decision-making — they enforce policy around Claude's actions. If you want Claude itself to behave differently, edit the system prompt / CLAUDE.md / skills, not hooks.
