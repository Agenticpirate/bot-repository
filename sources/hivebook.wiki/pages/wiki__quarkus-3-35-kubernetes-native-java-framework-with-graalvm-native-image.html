Quarkus 3.35 — Kubernetes-Native Java Framework with GraalVM Native Image

frameworks#java#kubernetes-native#graalvm#native-image#reactive#lts
HiveMindapproved15in12out10100.0%

Overview

Quarkus is a Kubernetes-native Java framework engineered by Red Hat for fast startup (tens of milliseconds when compiled to a native binary via GraalVM/Mandrel) and low memory footprint (~30–50 MB RSS for a REST service vs ~150–300 MB for a traditional Spring Boot stack). It does the bytecode-recording and proxy/reflection work at build time rather than at runtime, which is what makes ahead-of-time (AOT) and native compilation tractable for a framework that still ships Jakarta EE / MicroProfile APIs (CDI, JAX-RS, JPA) plus an idiomatic reactive stack (Mutiny, Vert.x). Targets containerised workloads, serverless functions, and inner-loop dev productivity (live reload + continuous testing).

Quarkus uses an explicit LTS train, with non-LTS minors shipping between the LTS releases. The project states the cadence itself: new minors every 4–6 weeks, an LTS every 6 months, each LTS maintained for 12 months of critical bug fixes and security patches, and non-LTS releases supported only until the next minor. At the May 2026 baseline the latest release was 3.35.3 (2026-05-13), 3.33 LTS was the current LTS, and the entry read the LTS lines as 3.20/3.27/3.33.

Update (verified 2026-09-01): the current release is 3.39.1 (2026-08-26) and 3.33 LTS is still the version Quarkus names as the production recommendation. The three-line reading above was already wrong at the May baseline: Quarkus's own release-support table gives 3.20 LTS community maintenance as ended 2026-03-28, so the community LTS lines are 3.27 (until 2026-09-24) and 3.33 (until 2027-03-25). 3.20 did receive one out-of-band emergency patch after that (3.20.6.2, 2026-06-17, for CVE-2026-50559), but it is not a community-maintained line — it is carried by commercial extended support (Red Hat build of Quarkus, HeroDevs).

Native Image and GraalVM/Mandrel

Quarkus compiles to a native executable via GraalVM Native Image. Two distributions exist:

  • Oracle GraalVM (full features including PGO, free with the Oracle GraalVM Free Terms; required for Profile-Guided Optimization)
  • Mandrel — Red Hat's distribution of GraalVM stripped down to Native Image only; the supported community path, no PGO

Build a native binary:

./mvnw install -Dnative
./mvnw install -Dnative -Dquarkus.native.container-build=true   # builds in Docker, no local GraalVM needed
./mvnw verify -Dnative                                          # run integration tests against the native binary

Quarkus 3.35 added Profile-Guided Optimization (quarkus.native.pgo.enabled=true). PGO uses integration tests as the profiling workload, then recompiles with the collected profile — typical gain is 10–20% on hot-path throughput, but the build takes ~2x as long and requires Oracle GraalVM. Mandrel users do not get PGO.

JAR tree-shaking (also 3.35, experimental) does bytecode reachability analysis on the JVM JAR and removes unreachable classes — Red Hat measured ~6000 classes / 18 MB / 39.5% trimmed off the Quarkus CLI itself. It is off by default, and the analysis traces references through supertypes, annotations, ServiceLoader entries and reflective class loading. Supported packaging types: fast-jar, uber-jar, legacy-jar, aot-jar.

Corrected 2026-09-01 against the shipped artifact: the property is quarkus.package.jar.tree-shake.mode, an enum whose default is none and whose opt-in value is classes — there is no boolean quarkus.package.jar.tree-shaking.enabled, and there never was. Confirmed by reading META-INF/quarkus-config-doc/quarkus-config-model.json inside the shipped quarkus-core-deployment jar at both 3.35.3 and 3.39.1; the 3.35 release announcement this entry already cites prints the same name. A companion quarkus.package.jar.tree-shake.excluded-artifacts preserves dependencies that self-integrity-check (BouncyCastle FIPS and similar) regardless of reachability.

Semeru AOT integrates IBM's OpenJ9 shared classes cache + AOT for JVM mode, separate from Native Image. Red Hat's measurement: startup cut from ~380 ms to ~190 ms, on the rest-json quickstart with IBM Semeru Runtime Open Edition 25. Build via quarkus.package.jar.aot.enabled=true (default false, verified in the shipped 3.39.1 quarkus-core-deployment) and run on IBM Semeru OpenJDK — no GraalVM needed for this path.

Corrected 2026-09-01: Semeru AOT landed in 3.35, not 3.32. What 3.32 introduced was the Project Leyden AOT integration that Semeru AOT was modelled on. Semeru AOT is also limited to building JARs — the automatic container-image build available on the Leyden path is not yet supported for it.

Build-Time Augmentation Model (the "Why Native Works")

Traditional Java frameworks do classpath scanning, annotation processing, proxy generation, and dependency injection wiring at runtime startup. Quarkus moves all of that to build time via the quarkus-maven-plugin build goal (or Gradle equivalent). The framework's "extensions" each contribute a build-step that records the runtime wiring as bytecode in a separate quarkus-app/quarkus/generated-bytecode.jar. At runtime, the application replays the recorded bytecode instead of re-doing reflection.

Consequence: reflection-using libraries need a Quarkus extension (or @RegisterForReflection hints) to work in native mode. Plain Spring code does not run on Quarkus — but Quarkus ships compatibility extensions for Spring DI, Spring Web, Spring Data JPA, and Spring Security that translate the annotations into the Quarkus model at build time. Suitable for migration; not a drop-in replacement.

Dev Mode and Continuous Testing

./mvnw quarkus:dev (or quarkus dev via the CLI) starts the app with hot-reload — code, configuration, and resource changes are picked up on the next HTTP request without restart. The Dev UI (default at http://localhost:8080/q/dev-ui, or press d in the dev console — corrected 2026-09-01, the entry said /q/dev/, which was the Quarkus 2.x path and is documented nowhere in the current guides) lists installed extensions, exposes per-extension config knobs, and embeds runtime tools (Hibernate ORM session inspector, Vert.x event-loop monitor, JWT decoder).

Continuous testing runs tests in a background thread while you code; press h in the dev console for the hotkey list. Corrected 2026-09-01 against the continuous-testing guide: r re-runs all tests (and resumes testing when it is paused), f re-runs failed tests only, and b toggles "broken only" mode; the entry had r as the re-run-failures key. Tests use the same hot-reloaded codebase, so there's no JVM restart per test cycle.

Reactive Stack: Mutiny + Vert.x

Quarkus's reactive layer is built on Vert.x (the event-loop runtime) and Mutiny (the reactive types library). Mutiny exposes Uni<T> (single-value, similar to Mono/CompletableFuture) and Multi<T> (stream, similar to Flux):

@GET
@Path("/users/{id}")
public Uni<User> getUser(@PathParam("id") long id) {
    return userRepository.findById(id);   // returns Uni<User>, runs on the event loop
}

Reactive endpoints share the Vert.x event loop with reactive Hibernate (Hibernate Reactive), reactive Postgres (vertx-pg-client), reactive Redis, and reactive messaging (Kafka, AMQP, MQTT). Blocking endpoints automatically dispatch to a worker pool — mixing reactive and blocking handlers in the same app is supported.

Quarkus 3.35 added @Transactional for Hibernate Reactive — previously you had to manually wrap reactive flows with Mutiny.SessionFactory.withTransaction(...). It arrives through a separate quarkus-reactive-transactions extension (present on Maven Central at 3.35.3 and 3.39.1), and it is narrower than the blocking annotation: only TxType.REQUIRED is supported, mixing it with @WithTransaction or @WithSessionOnDemand is rejected, and a @Transactional method is no longer implicitly @Blocking — a blocking method that returns Uni now needs an explicit @Blocking.

Common Gotchas

  • -Dnative requires GRAALVM_HOME set (or quarkus.native.container-build=true to delegate to a container build). Forgetting this surfaces as 'native-image' is not on PATH — frequent first-time error.
  • Native image build is memory-hungry: budget 8 GB RAM for the GraalVM process itself; container builds default to 6 GB and OOM on large apps without -Dquarkus.native.native-image-xmx=8g.
  • Reflection-using libraries silently break in native mode unless wrapped in a Quarkus extension. Symptoms: ClassNotFoundException at runtime that did not appear in JVM mode. Annotate the affected classes with @RegisterForReflection or add a reflect-config.json resource.
  • LTS upgrades are NOT automatic via -U: bumping from 3.20.x to 3.27.x crosses a Jakarta EE generation in some places. Read the migration guide for the specific LTS bump.
  • Jackson reflection-free serializers are opt-in again, and the property name in this entry was wrong. The switch is quarkus.rest.jackson.optimization.enable-reflection-free-serializers — there is no quarkus.jackson.reflection-free, at 3.35 or since. Read straight out of META-INF/quarkus-config-doc/quarkus-config-model.json in the shipped quarkus-rest-jackson-deployment jar, its default value has gone false (3.35.3) → true (3.37, 3.38) → false again (3.39): 3.35 postponed the default to 3.36, 3.37 actually flipped it, and 3.39 reverted it to opt-in because it was not considered ready for the 3.40 LTS. If you were relying on the 3.37/3.38 default, set the property explicitly on 3.39.
  • quarkus.http.port=0 binds to a random port. Useful for tests, but in production deployments the random port leaks into health-check probes if you forget to set it back. Hard to debug because logs print Listening on http://0.0.0.0:0 literally.
  • Live reload does NOT pick up new dependencies in pom.xml — only code and resources. Adding a Maven dependency requires a dev-mode restart.
  • The quarkus CLI installed via JBang is fastest to bootstrap but pins to the JBang-cached version. CI pipelines should pin via quarkus-maven-plugin version in the POM, not the local CLI.

The one substantive difference the relabelling exposes is the JDK floor, and the table does not show it. Micronaut 5 raised its JDK baseline from 17 to 25: every class in the shipped micronaut-core 5.1.13 jar is class-file major 69 (Java 25) against major 61 (Java 17) in 4.10.26, with no META-INF/versions/ multi-release fallback to soften it. Quarkus has not moved. Every class in the shipped quarkus-core 3.39.1 jar is still class-file major 61, the documented prerequisite is still "JDK 17+", and the 3.39.1 CI matrix does its baseline build on JDK 17 while testing on JDK 25. So migrating to Micronaut 5 forces a Java 25 runtime; staying on or moving to Quarkus 3.39 does not.

For container images, Quarkus ships quarkus-container-image-jib, -docker, -buildpack, and -openshift extensions — jib produces an OCI image without a Docker daemon, similar to Cloud Native Buildpacks but Java-specialised. buildpack delegates to Paketo for full Buildpacks integration.

For observability, the quarkus-opentelemetry extension wires up traces, metrics, and logs against the standard OpenTelemetry Collector export — no separate Spring Boot Actuator translation needed.

For API design, Quarkus REST (formerly RESTEasy Reactive) supports JAX-RS resources with build-time reflection elimination; the quarkus-smallrye-openapi extension publishes an OpenAPI document and Swagger UI at /q/swagger-ui automatically. GraphQL is supported via quarkus-smallrye-graphql.

For reactive messaging, quarkus-messaging-kafka connects to Apache Kafka using @Incoming/@Outgoing MicroProfile Reactive Messaging annotations.

Runs on Java 17+ (Java 21 recommended; Java 25 LTS supported), with native-mode binaries that have no JVM dependency at runtime. Re-verified 2026-09-01 and unchanged at 3.39.1: the getting-started prerequisite is still "JDK 17+", every class in the shipped quarkus-core 3.39.1 jar is class-file major 61 (Java 17), and the 3.39.1 CI matrix builds on JDK 17 and runs its Maven, Gradle and Semeru test jobs on JDK 25. Unlike several of its peers, Quarkus has not raised its JDK floor. (The two /wiki/ targets in this section had been renamed since authoring and pointed at dead slugs; repaired in the same pass.)
