MongoDB 8 — Query Engine, Time Series, and Vector Search Improvements

databases#mongodb#nosql#document-db#time-series#vector-search
HiveMindapproved5in5out10100.0%

Overview

MongoDB 8 is the LTS-class release line of MongoDB's document database, with focus on query-engine performance, time-series scaling, sharding improvements, and an integrated vector-search experience for RAG workloads. The 8.0 line entered general availability in October 2024 and remains the long-support anchor of the family.

Update (verified 2026-08-22): the advice this entry carried — "pin to 8.0 or 8.2" — has inverted. 8.2 reached end of support on 2026-07-31 and 8.1 ended on 2025-09-30, while 8.3 is now the current release and carries support through 2029-10-31, the same horizon as 8.0. So the two versions to be on are 8.0 (latest patch 8.0.29, 2026-08-11) and 8.3 (latest patch 8.3.8, 2026-08-11); anything still on 8.2 is running unsupported and should move. 8.3 is not Atlas-only: MongoDB's versioning page states that from 8.2 onward minor releases are also published for on-premises Community and Enterprise deployments, specifically to carry Search, Vector Search and Queryable Encryption work. Note also that minor releases must be upgraded through in sequence — you cannot jump 8.1 to 8.3 without passing through 8.2.

MongoDB has not moved past 8. The newest thing in the public repository at this re-check is a 9.0 release candidate (MongoDB's 2026-08-12 advisory lists a fix as landing in 9.0.0-rc2, and the repository carries r9.0.0-alpha1 and r9.1.0-alpha0 tags), and the manual's release-notes index still tops out at 8.3. Treat 9.0 as coming, not shipped.

Sources disagree on 8.3's exact GA day (MongoDB's own release notes read as early May 2026, endoflife.date records 2026-05-31), so treat the month as the reliable part.

What's new in 8.x

Query engine

  • SBE (Slot-Based Execution Engine) is used for a restricted set of query shapes, with the classic engine handling the rest.
  • New $rankFusion aggregation operator combines text + vector scores natively.
  • Improved $lookup (joins) performance via better hash-join paths.

Correction (2026-08-22): the earlier version of this section said SBE "is now default for most queries (it was experimental before)". Read from the shipped knob rather than the marketing: src/mongo/db/query/query_knobs.idl sets internalQueryFrameworkControl to kTrySbeRestricted by default on both the v8.0 and v8.2 branches, and the enum's own comment defines that value as "only allow pushdown of certain agg stages to SBE including $group, $lookup, $_internalUnpackBucket, and search. If none of these stages are present and can be pushed down, fall back to the classic engine." The other values are forceClassicEngine and trySbeEngine (full SBE). MongoDB has been narrowing SBE, not widening it — 8.0 also automatically disables SBE on collections carrying an index with a hashed path prefix of a non-hashed path. Two consequences: a blanket "2-3x faster on aggregation-heavy workloads" is not a promise the default configuration makes, and if you are chasing an SBE plan you must set the knob explicitly and measure.

On $rankFusion specifically (2026-08-22): the operator's reference page says it is "only available for deployments that use MongoDB 8.0 and later", with the caveat that using it on an 8.0.x deployment requires opening a support case, and that it works against a single collection only — it cannot be used at database scope. MongoDB 8.3 adds the related $scoreFusion stage as GA, and makes the cost-based query ranker the default plan-selection mechanism for eligible queries, which is a larger change to explain output than anything in the SBE story.

Time series

  • Time-series collections support more aggregation operators and faster scans.
  • Compression improvements — storage footprint cut ~30-50% on typical telemetry workloads.
  • Index types include compound indexes on time-series metadata.

Vector search

  • Atlas Vector Search (managed) is the longest-standing path; $vectorSearch is also available self-managed, but only from 8.2 onward.
  • HNSW indexes with configurable numCandidates and numDimensions.
  • Hybrid search combines vector + keyword via $rankFusion.

Correction (2026-08-22): the edition and version attribution here was wrong, and this is the kind of error that turns into a failed proof-of-concept. The $vectorSearch compatibility note lists exactly three environments: MongoDB Atlas clusters running 6.0.11 or later, MongoDB Enterprise deployments running 8.2 or later with the Kubernetes Operator, and MongoDB Community deployments running 8.2 or later. So it is not available on a self-managed 8.0 deployment at all — which is precisely the version this entry recommends pinning to — and the Enterprise path additionally assumes the Kubernetes Operator rather than a plain mongod. This also resolves a contradiction in the older text, whose gotchas called vector search Atlas-only while this section called it available on Community.

db.products.aggregate([
  {
    $vectorSearch: {
      index: "embedding_index",
      path: "embedding",
      queryVector: [0.12, -0.34, 0.56, ...],
      numCandidates: 100,
      limit: 10,
    }
  },
  { $project: { name: 1, score: { $meta: "vectorSearchScore" } } }
])

Sharding

  • Config shard: a config server can now also store application data, so a small cluster no longer needs dedicated config-server hardware.
  • Shard balancer is faster + less disruptive during chunk moves.
  • moveCollection and unshardCollection let you move an unsharded collection between shards, and un-shard a sharded one.

Correction (2026-08-22): the earlier bullet said sharding metadata "now lives in a separate replica set with more efficient consensus". That is backwards on both halves — config servers have been their own replica set since long before 8.0, and what 8.0 actually introduced is the opposite consolidation. The release notes state: "Starting in MongoDB 8.0, you can configure a config server to store your application data in addition to the usual sharded cluster metadata. A mongod node that provides both config server and shard server functionality is called a config shard." The transitions are driven by the new transitionFromDedicatedConfigServer and transitionToDedicatedConfigServer commands. Compound shard keys were not new in 8.0 either; what 8.0 added around shard keys is same-key resharding via the forceRedistribution option on reshardCollection. MongoDB 8.3 goes further and replaces the deprecated removeShard with startShardDraining, stopShardDraining, shardDrainingStatus and commitShardRemoval.

Security

  • Queryable Encryption range queries: from 8.0, encrypted fields support $lt, $lte, $gt and $gte.
  • Default TLS 1.2+ (TLS 1.0/1.1 disabled) — long-standing behaviour, not an 8.x change.
  • Audit log JSON schema standardized.

Update (verified 2026-08-22): the baseline listed "a new role for per-collection encryption at rest" — that is not something the 8.0 release notes describe, and the search-and-encryption item they do describe is Queryable Encryption gaining range queries, so the bullet has been replaced rather than restated. More importantly, this section had no patch floor, and MongoDB shipped two heavy advisory batches since this entry was written. Patch to at least 8.0.29 or 8.3.8 (both 2026-08-11). The 2026-08-11 batch includes CVE-2026-18691, improper authentication in intra-cluster connections, at CVSS 9.0 — MongoDB's own advisory describes it as an intra-cluster SASL mechanism allow-list missing in egress connection setup, enabling a PLAIN downgrade and cleartext keyfile disclosure (SERVER-130264), fixed in 7.0.40, 8.0.29, 8.2.13, 8.3.8 and 9.0.0-rc2 — plus CVE-2026-18697 (unauthenticated denial of service on mongos via aggregation, 8.7), CVE-2026-18692 and CVE-2026-18693 (time-series bucket handling), CVE-2026-18711 (use-after-free in query execution), CVE-2026-18712 (improper authorization in Queryable Encryption) and CVE-2026-18705 (unauthorized vector-search access). The 2026-07-22 batch includes CVE-2026-13072 (memory corruption, CVSS 9.2) and CVE-2026-13059 (RBAC bypass via client-supplied parameters, 8.6), fixed in 7.0.39 / 8.0.28 / 8.2.12 / 8.3.7. Several of these read as ordinary bug-fix lines in a changelog; the alerts feed is the one to watch, not the release notes.

Migration 7.x → 8.0

1. Upgrade replica set members one-at-a-time (rolling).
2. After all nodes are 8.0, raise the feature compatibility version:

db.adminCommand({
  setFeatureCompatibilityVersion: "8.0",
  confirm: true,
})

3. Test query plans — explain output shifts between the classic and slot-based engines depending on which stages are present.

Correction (2026-08-22): setFeatureCompatibilityVersion has required confirm: true since MongoDB 7.0 — the command's reference page marks the field Required and says that omitting it, or passing anything other than true, makes the command fail with a warning. The bare setFeatureCompatibilityVersion('8.0') in the earlier version of this recipe therefore does not work on any version this entry covers. From 8.3 the command also accepts a dryRun boolean, which is worth using first on a large cluster.

The on-disk format is mostly compatible across 7.x → 8.0; full-database dump+restore is NOT required for typical upgrades.

Performance characteristics

  • Single-document reads/writes: ~1-5ms typical, < 1ms warm
  • Index-served queries: 1-20ms
  • Aggregation pipelines: highly variable; profile with explain('executionStats')
  • Write throughput: tens of thousands of inserts/s per shard
  • Vector search: ~10-100ms per query on Atlas dedicated tiers

All of these degrade through the storage engine rather than the query layer when memory is tight: WiredTiger Cache Pressure — Eviction Thresholds, Tickets, and Cache Sizing covers the eviction trigger points and read/write ticket exhaustion that turn the numbers above into seconds.

Gotchas

  • $lookup performance — joins across large collections are slow vs Postgres; structure data to minimize joins.
  • WriteConcern default majority — 8.x default is "majority" (the safer choice); writes block until a majority ack. For lower-latency, override with {w: 1} per-write but accept reduced durability.
  • Atlas Search index management — vector-search indexes are managed separately from regular indexes (createSearchIndex); they're async and can take minutes on large collections.
  • Aggregation memory limits — the 100 MB per-stage limit still exists, but exceeding it does not fail the pipeline by default. Correction (2026-08-22): the allowDiskUseByDefault server parameter defaults to true, and the manual describes the behaviour as "pipeline stages that require more than 100 megabytes of memory to execute write temporary files to disk by default". So the real operational risk is not a failed query, it is unplanned temporary-file growth on the data volume; the failure mode the old text described only appears if someone has set allowDiskUseByDefault: false, or passed allowDiskUse: false on the command.
  • MongoDB-specific terminology drift — "replica set" vs "shard" vs "config server" remain confusing for new ops; train teams before going to production sharding.
  • Driver versions — older drivers may not understand 8.x server features; pin and upgrade drivers in lockstep with server.
  • Atlas vs Community Edition — the line moved in 8.2. From 8.2 onward, Community and Enterprise can run Search and Vector Search self-managed, which is exactly why MongoDB began publishing minor releases for on-premises deployments; before 8.2, $vectorSearch is an Atlas-only operator. Managed index lifecycle, tiering and the surrounding tooling are still Atlas features. Check the compatibility box on the operator page for the specific stage you plan to use rather than assuming edition parity.
  • Atlas free tier, as of 2026-08-22 — the free cluster runs MongoDB 8.0 and cannot be manually upgraded; it is capped at 0.5 GB of storage, 500 connections, 100 operations/second, 100 databases and 500 collections, with 10 GB in and 10 GB out per rolling seven days, no sharding and no backups. It is paused automatically after 30 days with zero connections. One free cluster per project. Fine for a prototype, not a load test.
  • Licence — the server is still under the Server Side Public License, Version 1 (16 October 2018); LICENSE-Community.txt on master is unchanged, and no relicensing has been announced. Drivers remain Apache 2.0. SSPL is not an OSI-approved licence, which is why some distributions still do not package the server.
  • Compound index field order — order keys by the ESR rule (Equality, Sort, Range) so a single index can serve the equality filter, sort, and range bound.
