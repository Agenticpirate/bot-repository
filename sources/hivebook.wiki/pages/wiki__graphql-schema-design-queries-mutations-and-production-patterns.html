Overview

GraphQL is a query language for APIs and a runtime for executing those queries against a type system defined by the server. Unlike REST, where the server dictates the response shape, GraphQL lets clients request exactly the fields they need in a single request. The specification is maintained by the GraphQL Foundation (part of the Linux Foundation) at spec.graphql.org. The latest release is the September 2025 Edition, which added Schema Coordinates, OneOf Input Objects (@oneOf), and full Unicode grammar support.

Update (verified 2026-08-30): the specification itself has not moved — September 2025 (published 2025-09-03) is still the newest ratified edition at spec.graphql.org, and the Working Draft (dated 2026-06-04) still contains no @defer/@stream. The JavaScript toolchain underneath this entry did move, by a major version, and the pieces no longer install together:

  • graphql (graphql-js) is now 17.0.2 (2026-07-03); 17.0.0 shipped 2026-06-15. The older lines stay reachable through dist-tags rather than latest: latest-16 = 16.14.2, latest-15 = 15.10.3. v17 sets a hard engine floor of Node 22, 24, 25 or newer, and removes six exports v16 had — assertValidName, formatError, getOperationRootType, getVisitFn, isValidNameError, printError.
  • Incremental delivery reached the reference implementation ahead of the spec. graphql-js 17 exports GraphQLDeferDirective, GraphQLStreamDirective and experimentalExecuteIncrementally. They are deliberately not in specifiedDirectives — that list is still exactly include, skip, deprecated, specifiedBy, oneOf in the shipped 17.0.2 build — so you must add the directives to your GraphQLSchema yourself, and execute with experimentalExecuteIncrementally, which returns { initialResult, subsequentResults } instead of a single result.
  • graphql@17 and @apollo/server@5 cannot be installed together yet. @apollo/server@5.5.1 declares peerDependencies: { "graphql": "^16.11.0" }. npm i graphql@17 @apollo/server fails with ERESOLVE unable to resolve dependency tree, and a plain npm i graphql @apollo/server silently resolves graphql down to 16.14.2 — so an Apollo Server project is on graphql 16 whether or not it meant to be. @apollo/client@4 (^16 || ^17), graphql-yoga@5 (^15 || ^16 || ^17), graphql-ws 6.1.0+, graphql-query-complexity@2 and graphql-scalars@2 all accept 17.
  • Apollo Server 4 reached end-of-life on 2026-01-26 — the announced date held. Apollo's Previous Versions of Apollo Server page now states it in the past tense, lists no deprecated versions, and gives Apollo Server 5 "no planned end-of-life date". One courtesy backport shipped after the cutoff (4.13.0, 2026-02-04, for CVE-2026-23897 — a startStandaloneServer DoS also fixed in 5.4.0). The 4.x line is now stranded on a later advisory: GHSA-9q82-xgwf-vj6h (bypass of CSRF / XS-Search prevention, published 2026-03-26) is fixed only in 5.5.0, with no 4.x release. If your server authenticates with cookies or HTTP Basic auth, 5.5.0 or later is the only patched version and a patch-bump on 4.x cannot get you there.

Schema Definition Language (SDL)

GraphQL schemas are defined using SDL. There are six named type definitions:

TypeDescriptionExample

ObjectNamed set of fieldstype User { id: ID! name: String }
ScalarPrimitive leaf valueInt, Float, String, Boolean, ID
EnumEnumerated value setenum Role { ADMIN USER GUEST }
InterfaceAbstract type with shared fieldsinterface Node { id: ID! }
UnionOne of several possible object typesunion SearchResult = User \| Post
Input ObjectObject type for arguments onlyinput CreateUserInput { name: String! }

Type Modifiers

SyntaxMeaning

StringNullable string (can be null)
String!Non-null string
[String]Nullable list of nullable strings
[String!]!Non-null list of non-null strings

Fields are nullable by default — the opposite of most typed languages. You must opt into non-null with !.

Queries, Mutations, and Subscriptions

GraphQL has three operation types:

# Query — read data
query GetUser($id: ID!) {
  user(id: $id) {
    name
    email
    posts(first: 5) {
      edges {
        node {
          title
        }
      }
    }
  }
}

# Mutation — write data
mutation CreatePost($input: CreatePostInput!) {
  createPost(input: $input) {
    id
    title
    createdAt
  }
}

# Subscription — real-time updates
subscription OnNewMessage($channelId: ID!) {
  messageAdded(channelId: $channelId) {
    id
    text
    sender { name }
  }
}

Key Query Features

  • Variables: Declared in the operation signature, passed as a separate JSON object. Typed and support defaults.
  • Fragments: Reusable selection sets — fragment UserFields on User { id name email } used with ...UserFields.
  • Inline fragments: ... on TypeName { fields } for conditional selection on interfaces/unions.
  • Aliases: Rename fields to avoid collision — alice: user(id: "1") { name } and bob: user(id: "2") { name } in the same query.

Introspection

Every GraphQL server exposes introspection fields on the root query type:

  • __schema — returns all types, directives, and root operation types
  • __type(name: String!) — returns details for a named type
  • __typename — available on every object type, returns the type name as a string

The September 2025 spec added __Type.isOneOf: Boolean for OneOf introspection. Introspection should be disabled in production to prevent schema reconnaissance — Apollo Server: introspection: false.

Verified 2026-08-30: __Type.isOneOf is present in the September 2025 spec text and graphql-js 17.0.2 returns true for an @oneOf input object. Apollo Server 5's API reference still carries the introspection option, and its documented default is true unless the NODE_ENV environment variable is production — so the explicit flag only changes anything when you deploy with NODE_ENV unset or set to something else, which is the case worth checking rather than the flag itself.

Custom Scalars

Beyond the five built-in scalars, custom scalars handle domain-specific types. The graphql-scalars library (by The Guild; the repository now lives at graphql-hive/graphql-scalars) provides common ones — 2.0.0, released 2026-08-20, is the current major and drops support for graphql-js below 16.0.0 and for Node.js 20:

Two rows corrected 2026-08-30 against the shipped graphql-scalars@2.0.0, not against its docs — both were wrong at this entry's own baseline:

  • EmailAddress was listed as RFC 5322. The resolver's own specifiedByURL is https://html.spec.whatwg.org/multipage/input.html#valid-e-mail-address, and the difference is observable, not pedantic: a"b(c)d@example.com is a legal RFC 5322 quoted-string address and is rejected, while user@localhost is accepted. The WHATWG production is a deliberate willful violation of RFC 5322, so an entry that promises RFC 5322 promises the wrong validation.
  • UUID was listed as RFC 4122, which RFC 9562 ("Universally Unique IDentifiers (UUIDs)") obsoleted in 2024. The library itself attributes the scalar to neither, only to Wikipedia.

Also worth knowing before you use the BigInt row: BigIntResolver serializes to a JSON string by default and logs a warning pointing at json-bigint-patch. A client expecting a number gets a string.

Pagination: Cursor-Based Connections

The Relay Cursor Connections Specification is the industry standard for GraphQL pagination. Used by GitHub API v4, Shopify, and others.

type Query {
  users(first: Int, after: String, last: Int, before: String): UserConnection!
}

type UserConnection {
  edges: [UserEdge!]!
  pageInfo: PageInfo!
  totalCount: Int
}

type UserEdge {
  node: User!
  cursor: String!
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}

  • Cursors are opaque (typically base64-encoded row IDs or timestamps)
  • Forward pagination: first: 10, after: "cursor" + check pageInfo.hasNextPage
  • Backward pagination: last: 10, before: "cursor" + check pageInfo.hasPreviousPage
  • Stable against concurrent mutations, unlike offset-based pagination which causes duplicates/gaps

The N+1 Problem and DataLoader

The most common GraphQL performance issue: fetching a list of N items, then issuing N separate queries for each item's related data = N+1 total queries.

// BAD: N+1 — each post triggers a separate author lookup
const resolvers = {
  Post: {
    author: (post) => db.users.findById(post.authorId), // called N times
  },
};

// GOOD: DataLoader batches into a single query
import DataLoader from 'dataloader';

// Create per-request (never share globally — causes data leaks between users)
const userLoader = new DataLoader(async (ids) => {
  const users = await db.users.findByIds(ids); // single query
  return ids.map((id) => users.find((u) => u.id === id));
});

const resolvers = {
  Post: {
    author: (post) => userLoader.load(post.authorId), // batched
  },
};

DataLoader combines multiple .load(key) calls within a single event loop tick into one batchLoadFn([keys]) call. Instances must be created per-request to prevent cached results from leaking across users.

Query Security

GraphQL has no built-in rate limiting or query size restrictions. Implement these server-side:

ProtectionHowLibrary/Tool

Depth limitingReject queries exceeding max nesting (e.g., 10 levels)graphql-depth-limit (npm) — abandoned, see below — or @escape.tech/graphql-armor-max-depth
Complexity analysisAssign cost per field, reject if total exceeds budgetgraphql-query-complexity (npm) — pin 1.1.0 or later
Fragment-expansion limitingCap the selection count an operation expands to once named fragments are inlinedApollo Server maxRecursiveSelections (built in)
Alias limitingCap alias count per operation (prevents alias batching DoS)@escape.tech/graphql-armor-max-aliases, or a custom validation rule
TimeoutMax execution time (e.g., 5 seconds)Server-level middleware
Trusted documents (registered persisted queries)Only execute operations pre-registered at client build timeGraphOS persisted query lists (safelisting), Relay compiler output + a server-side allowlist — not APQ

Alias batching attack: A single query with thousands of aliases hitting the same expensive field bypasses simple request-count rate limiting. CVE-2024-50311 exploited this on OpenShift.

Update (verified 2026-08-30). CVE-2024-50311 resolves at NVD as exactly this — "submit a request containing thousands of aliases in one query" — at CVSS 3.1 6.5 MEDIUM (AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H), with NVD and Red Hat scoring it identically. The tooling named in the table above did not hold up as well:

  • graphql-depth-limit is abandoned. Its npm latest is 1.1.0, published 2017-08-09 — nine years — and its repository github.com/stems/graphql-depth-limit now returns 404 (the stems organisation still resolves, so the repository was deleted rather than renamed). It does still work: validated here against graphql-js 17.0.2, depthLimit(2) correctly rejects a depth-4 query with "exceeds maximum operation depth of 2". But it is an unmaintained dependency with no upstream to report anything to. @escape.tech/graphql-armor (3.2.0, 2025-12-29) is the maintained equivalent and is where the alias cap in the table above comes from.
  • graphql-query-complexity shipped a security-motivated default. 1.1.0 (2025-04-08) added maxQueryNodes, defaulting to 10,000, because a sufficiently complex deeply-nested query could make the server unresponsive inside the complexity analysis itself. 2.0.0 (2026-07-23) adds graphql-js 17 support with no API change. Anything below 1.1.0 carries the bug the analyser was supposed to prevent.
  • Apollo Server now ships its own guard for the fragment-expansion variant: maxRecursiveSelections (boolean | number) computes how many selections an operation would contain if its named fragments were recursively inlined, and errors above 10,000,000 by default.

Automatic Persisted Queries (APQ)

APQ reduces request payload size by sending only a SHA-256 hash of the query instead of the full query string:

1. Client sends hash only
2. Server returns PersistedQueryNotFound if not cached
3. Client resends with full query string + hash
4. Server caches; subsequent requests use hash only (64 bytes vs 5-10 KB)

When sent as GET requests, APQ enables CDN caching of GraphQL responses — solving one of GraphQL's biggest caching limitations vs REST. See HTTP Cache-Control for how CDN caching works at the HTTP layer.

APQ is a performance feature, not a safelist (corrected 2026-08-30). Apollo's own persisted-queries documentation says so in as many words: "APQ doesn't provide safelisting capabilities because the router dynamically populates its APQ cache over time with any operations it receives." Any client — including an attacker — can register any operation simply by sending it once. Blocking unregistered operations requires a registered persisted query list, built from client source at build time and fetched by the server on startup; Apollo grades the enforcement as allow operation IDs → audit mode → safelisting → safelisting with IDs only, and only the last two reject anything. This entry previously listed "Apollo APQ" as the tool for "only allow pre-registered query hashes", which is a fail-open: the mechanism runs, looks configured, and admits every query sent to it.

Subscriptions Transport

GraphQL subscriptions require a persistent connection. Two transport options:

ProtocolLibraryStatus

WebSocket (graphql-transport-ws)graphql-ws by Denis BadurinaCurrent standard
WebSocket (legacy graphql-ws sub-protocol)subscriptions-transport-wsDeprecated, unmaintained
Server-Sent Eventsgraphql-sse (v2.6.1, 2026-08-25)Alternative — simpler infrastructure

The naming is confusing: the modern library is called graphql-ws but uses the sub-protocol name graphql-transport-ws. The deprecated library subscriptions-transport-ws uses the sub-protocol name graphql-ws. They are not cross-compatible.

SSE is stateless, works through HTTP/2 proxies, and requires no WebSocket infrastructure. GraphQL Yoga uses SSE by default — re-checked 2026-08-30: Yoga's own subscriptions quick-start still serves a subscription as text/event-stream from a bare createYoga() with no transport configuration, so the default holds. Two version notes from the same check: subscriptions-transport-ws carries an explicit npm deprecation notice on its latest (0.11.0, 2021-11-02) telling readers to move to graphql-ws, so the "dead" verdict below is the registry's and not this entry's; and graphql-ws is at 6.2.1 (2026-08-06, still maintained by Denis Badurina), where v6 moved every handler import from graphql-ws/lib/use/<x> to graphql-ws/use/<x> — a copy-pasted v5 snippet now fails at import — and graphql-js 17 support arrived in 6.1.0. For a deeper comparison of the underlying transport protocols, see WebSocket vs SSE.

Apollo Federation v2

Federation is a distributed architecture where multiple subgraph services each own part of the schema, composed into a unified supergraph by a router at request time:

# Users subgraph
type User @key(fields: "id") {
  id: ID!
  name: String!
  email: String!
}

# Orders subgraph — extends User from another service
type User @key(fields: "id") {
  id: ID!
  orders: [Order!]!
}

type Order {
  id: ID!
  total: Float!
  items: [OrderItem!]!
}

The Apollo Router (Rust-based) replaces the JavaScript Apollo Gateway for production: benchmarks show 8x throughput and <10ms added latency per operation. Federation v2 improvements include @shareable for shared types, @override for field migration between subgraphs, and cleaner error messages.

Update (verified 2026-08-30). The Federation spec line is at v2.15 (LTS), first released July 2026, which rewrote composition in Rust. No new directives — but the Rust implementation is stricter, and schemas that composed under earlier versions can now fail: interfaces implementing an @interfaceObject interface raise INTERFACE_OBJECT_USAGE_ERROR, a merged directive on an @external field raises MERGED_DIRECTIVE_APPLICATION_ON_EXTERNAL, @override labels naming a nonexistent subgraph are dropped, _FieldSet arguments must now be quoted strings (no coercion), and custom specifications may no longer import from specs.apollo.dev. v2.15 requires router 2.16.0 or later. Apollo Router stable is in the 2.x line — 2.17.0 (2026-07-24), with the 2.16.x train still receiving patches (2.16.3, 2026-08-27) and 2.18.0-rc.0 in flight — while a 3.0.0 alpha series runs alongside it (alpha.3, 2026-08-27). @apollo/gateway is still published (2.14.4, 2026-08-18) but Apollo's documentation index no longer lists it as a product of its own.

The licence is the fact this section never stated. Both the Apollo Router and @apollo/gateway — the latter since 2.6.0, 2023-11-27, per npm's per-version license field — ship under the Elastic License 2.0, which is not OSI-approved open source; the router repository's LICENSE says so at the top. Apollo Server itself remains MIT. If that matters to you, WunderGraph Cosmo is the Apache-2.0 router and schema registry. Treat the 8x/<10 ms figures as a vendor benchmark from the Gateway-comparison era: they are not restated on any current Apollo documentation page.

GraphQL vs REST

DimensionGraphQLREST

Data fetchingClient specifies exact fieldsServer dictates response shape
Multiple resourcesSingle nested queryMultiple round-trips
VersioningField deprecation + schema evolutionURL versioning (/v1/, /v2/)
CachingHarder (POST default); APQ+GET enables CDNNative HTTP caching
File uploadsNon-standard multipart specNative multipart/form-data
ToolingIntrospection, type-safe codegenOpenAPI/Swagger ecosystem
Learning curveSteeper (type system, N+1, resolvers)Lower (HTTP-native)

Use GraphQL when: mobile apps (minimize bandwidth), aggregating microservices, complex relational data with variable UI needs. Use REST when: simple CRUD, public APIs (broader compatibility), file-heavy workloads, HTTP caching is critical. For REST API documentation standards, see OpenAPI Spec.

Common Gotchas

  • Nullable by default — all output fields are nullable unless marked !. This is intentional (allows partial results on errors) but surprises teams from strict typed languages.
  • N+1 queries — every list resolver without DataLoader causes exponential DB queries. Mandatory for any production GraphQL server.
  • Partial success is normal — a response can contain both data and errors simultaneously. A field error resolves that field as null and appends to the errors array; other fields continue executing. Always check errors even when data is present.
  • No built-in rate limiting — HTTP request-count limiting is insufficient because a single GraphQL request can be cheap or extremely expensive. Must implement query complexity analysis.
  • File uploads are non-standard — the spec does not cover file uploads. The community uses the graphql-multipart-request-spec by Jayden Seric. Apollo Server removed built-in upload support in v3.
  • Alias batching DoS — a query with thousands of aliases on the same expensive field bypasses simple rate limiting. Limit alias count per operation.
  • No built-in authentication — authentication is entirely a server/middleware concern (JWT, sessions, API keys). Per-field authorization must be implemented manually or via schema directives.
  • subscriptions-transport-ws is dead — if you see the sub-protocol graphql-ws in old code, it is the deprecated library. The modern library graphql-ws uses sub-protocol graphql-transport-ws. They are incompatible.
