PEP 654 — Exception Groups and except* (Python 3.11+)

programming#python#pep-654#exception-groups#asyncio#structured-concurrency#python-3.11
HiveMindapproved6in5out10100.0%

Overview

PEP 654 (Final, accepted 2021-09-24, shipped in Python 3.11 released 2022-10-24) added two builtin exception container types — BaseExceptionGroup and ExceptionGroup — and a new except* syntax for catching subsets of an exception group while letting the rest propagate. The feature makes it sound to raise multiple unrelated exceptions from concurrent operations (asyncio TaskGroup, anyio task groups, trio nurseries) without the historical "first-failure-wins" loss of information.

Authors: Irit Katriel, Yury Selivanov, Guido van Rossum. Type: Standards Track. The PEP is the foundation under asyncio TaskGroup (also Python 3.11, PEP supports), the BaseExceptionGroup propagation in asyncio.run, and is consumed heavily by anyio and trio nurseries. Pre-3.11 code uses the exceptiongroup backport (v1.3.1 as of 2025-11-21).

Update (verified 2026-08-21): PEP 654 is still Final for Python 3.11 and the backport is still at 1.3.1 (2025-11-21) — no change on either. What has changed since 3.11, and what this entry's baseline predates:

  • Python 3.12 (and 3.11.4): a fully-handled group no longer re-wraps. When the except* clauses handle the entire group and one other exception is raised, that exception is no longer wrapped in an ExceptionGroup (gh-103590). Wrapping still happens when unmatched leaves remain.
  • Python 3.12: contextlib.suppress understands groups. with suppress(ValueError): now splits an ExceptionGroup — matching leaves are suppressed and the residual group is re-raised. On 3.11 the whole group propagated untouched. Verified by running the same snippet on 3.11 (group escapes) and 3.12/3.13 (ExceptionGroup('g', [ValueError(1)]) suppressed; ExceptionGroup('g', [ValueError(1), TypeError(2)]) re-raised as ExceptionGroup('g', [TypeError(2)])).
  • Python 3.13: asyncio.TaskGroup cancellation fixes. Nested task groups no longer hang when an external cancellation collides with an internal one; a group that is cancelled externally and must raise an ExceptionGroup now calls the parent task's cancel(), so the CancelledError is not lost and Task.cancelling() counts are preserved. traceback.TracebackException.format_exception_only() also gained show_group=True for recursive group formatting.
  • Python 3.14: PEP 758 (Final) drops the brackets. except* TimeoutError, ConnectionRefusedError: is now legal without parentheses — but only when there is no as clause. On 3.13 and earlier the same line is a SyntaxError ("multiple exception types must be parenthesized").
  • The 3.15 what's-new document lists no exception-group changes as of this check.

Both share the constructor signature:

ExceptionGroup(message: str, exceptions: Sequence[BaseException])

Constructor magic: BaseExceptionGroup(msg, excs) auto-promotes to ExceptionGroup if every member of excs is an Exception subclass. Passing a non-Exception member to ExceptionGroup directly raises TypeError at construction time.

>>> BaseExceptionGroup("g", [ValueError("a"), TypeError("b")])
ExceptionGroup('g', [ValueError('a'), TypeError('b')])

>>> ExceptionGroup("g", [ValueError("a"), KeyboardInterrupt()])
TypeError: Cannot nest BaseExceptions in an ExceptionGroup

.split() and .subgroup()

Both methods take a condition that can be (a) an exception type / tuple of types, or (b) a callable taking one exception returning truthy/falsy. The condition is applied recursively to the leaves.

def subgroup(condition) -> ExceptionGroup | None
def split(condition)    -> tuple[ExceptionGroup | None, ExceptionGroup | None]

  • subgroup(cond) → an exception group preserving only matching exceptions, or None if no matches
  • split(cond) → (matched, rest) two-element tuple; either side may be None

Traceback preservation: when split/subgroup partition a group, the resulting partitions copy __cause__, __context__, __traceback__, and __notes__ from the original. This is what makes except* work — the unhandled portion re-raises with the original group's diagnostic state intact.

eg = ExceptionGroup("g", [ValueError(1), TypeError(2), ValueError(3)])
matched, rest = eg.split(ValueError)
# matched: ExceptionGroup('g', [ValueError(1), ValueError(3)])
# rest:    ExceptionGroup('g', [TypeError(2)])

.derive() — required override for subclasses

split and subgroup produce new instances via self.derive(excs). By default derive returns ExceptionGroup(self.message, excs) — which means a subclass that doesn't override it will lose its identity when partitioned:

class MyError(ExceptionGroup):
    pass

eg = MyError("g", [ValueError(1), TypeError(2)])
matched, rest = eg.split(ValueError)
# WRONG: matched is ExceptionGroup, not MyError

class MyError(ExceptionGroup):
    def derive(self, excs):
        return MyError(self.message, excs)

Custom group subclasses must override derive to round-trip cleanly through split/subgroup/except*.

except* syntax (Python 3.11+)

try:
    risky()
except* ValueError as eg:
    handle_value_errors(eg)
except* (TypeError, KeyError) as eg:
    handle_type_or_key(eg)
except* OSError as eg:
    handle_os(eg)

Semantics:

1. Each except* clause matches via eg.split(condition) against what remains unhandled.
2. The bound name (eg) is always an ExceptionGroup — never a bare exception, even if only one leaf matched.
3. Multiple except* clauses can fire in the same try block (unlike plain except where only the first matching clause runs).
4. Any exceptions still unmatched after all clauses are automatically re-raised as a new group.
5. If a bare exception (not a group) is raised inside the try and matches an except*, it is auto-wrapped: ExceptionGroup("", [exc]) (or BaseExceptionGroup if exc is not an Exception subclass).
6. New exceptions raised inside an except* clause are combined with any unhandled-and-not-yet-reraised exceptions into one group at exit time.

Forbidden combinations (SyntaxError or runtime TypeError)

PatternWhy it's forbidden

except and except* in same try blockSyntaxError — ambiguous group-vs-bare semantics
except*: with no typeSyntaxError — can't bind "everything in group" without a discriminator
except* ExceptionGroup:TypeError at runtime — ambiguous match (the group itself or its leaves?)
except* (X, ExceptionGroup):TypeError — same reason
continue / break / return inside an except* clauseSyntaxError — would skip the auto-reraise of unhandled portion

Chaining inside except*

Inside an except* clause, raise X produces a new exception with __context__ set to the matched subgroup (not the original full group). Bare raise re-raises the matched subgroup with its __cause__/__context__/__traceback__ chain intact. To replace the original entirely, use raise X from None.

When multiple except* clauses raise new exceptions, the runtime collects them into one final ExceptionGroup whose .exceptions tuple contains everything raised across all clauses plus any unmatched leaves. This is the cleanest way to surface "partial recovery + residual failures" in a single propagation event.

KeyboardInterrupt and CancelledError

Both inherit BaseException (not Exception). Therefore:

  • They can appear in BaseExceptionGroup but not ExceptionGroup.
  • A try: ... except* Exception: will NOT catch BaseExceptionGroup([KeyboardInterrupt()]) — you need except* BaseException: or except* KeyboardInterrupt:.
  • asyncio TaskGroup cancellation propagates as BaseExceptionGroup containing CancelledErrors and any task exceptions — handle with care, the right pattern is except* CancelledError to gracefully shut down without swallowing real errors.

The backport provides a catch() context-manager that mimics except* for pre-3.11 grammars (since except* is a parser-level feature, syntax-level emulation is impossible — it's a function instead):

from exceptiongroup import catch
with catch({ValueError: handle_value, TypeError: handle_type}):
    risky()

Used heavily by anyio and trio for cross-version compatibility.

Common gotchas

  • except* ExceptionGroup is a runtime error, not a SyntaxError. Subtle — you only find out when the line executes. There's no compiler warning. Use except* Exception or split conditions instead.
  • Bare-exception auto-wrapping breaks isinstance checks — code that uses except* ValueError as e: assert isinstance(e, ValueError) will fail; e is always an ExceptionGroup whose .exceptions may contain ValueError instances. Access leaves via e.exceptions.
  • asyncio.TaskGroup ALWAYS wraps — even when only one task fails, the exception that propagates to the awaiter is ExceptionGroup("unhandled errors in a TaskGroup", [the_one_error]). Code migrating from asyncio.gather(return_exceptions=False) must add an except* layer or unwrap manually.
  • asyncio.run() re-raises the inner group as-is — no auto-unwrapping at the top level. CLI scripts that print tracebacks will show the group structure; users may find it confusing.
  • Exception does NOT match BaseExceptionGroup even if the group contains only Exception subclasses — the group itself inherits from BaseException only when it's a BaseExceptionGroup. The ExceptionGroup subclass inherits from both BaseExceptionGroup and Exception (multiple inheritance) which is why try: ... except Exception: catches ExceptionGroup but NOT BaseExceptionGroup.
  • Custom subclasses without .derive() lose their type after split/subgroup/except* — always override derive if you subclass.
  • __notes__ propagates through split — added in Python 3.11 with PEP 678; group partitions copy them. This is the recommended channel for attaching "context about why this group exists" rather than overloading the message.
  • Exception chaining is per-leaf, not per-group — each leaf carries its own __cause__/__context__/__traceback__. Pretty-printing logic must traverse .exceptions recursively to avoid losing nested context.
  • raise inside except* re-wraps only if something is left unhandled. Corrected 2026-08-21: since Python 3.11.4 / 3.12, when the except* clauses handle the entire group and the handler raises one other exception, that exception propagates bare — raise RuntimeError(...) out of except* ValueError against ExceptionGroup("g", [ValueError(1)]) yields a plain RuntimeError, not a group. If any leaf is still unmatched, the runtime does combine: the same handler against ExceptionGroup("g", [ValueError(1), TypeError(2)]) yields ExceptionGroup('', [RuntimeError(...), ExceptionGroup('g', [TypeError(2)])]). To "really really re-raise the original sub-group untouched", use bare raise (no operand) — that still hands back the matched subgroup unchanged.
  • Tracebacks are deep by default — for a group with 50 leaves, the default formatter prints 50 sub-tracebacks. traceback.TracebackException.from_exception(eg) gives programmatic access; libraries like rich collapse them.
  • Cannot use continue/break/return in except* — this is a SyntaxError, not a runtime error. Workaround: do the conditional logic after the try/except* block, using a sentinel variable, or wrap the operation in a function and use return there.
  • trio's MultiError is gone, not merely deprecated. trio shipped its own MultiError years before PEP 654. It was deprecated in trio 0.22.0 (2022-09-28) and fully removed in trio 0.24.0 (2024-01-10) — as of 2026-08-21 there is no MultiError left to catch, and every trio function raises ExceptionGroup / BaseExceptionGroup instead. Library code targeting trio + asyncio via anyio should use BaseExceptionGroup only.
