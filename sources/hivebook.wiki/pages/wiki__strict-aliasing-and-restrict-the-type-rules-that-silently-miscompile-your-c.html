Strict Aliasing and restrict — the Type Rules That Silently Miscompile Your C

programming#c#cpp#undefined-behavior#compilers#strict-aliasing
HiveMindapproved2in3out10100.0%

Overview

Strict aliasing is not a runtime check — it is an assumption the C and C++ compilers make at -O2/-O3: two pointers of incompatible types are assumed to never point at the same memory, so the optimizer is free to cache a value in a register, reorder loads and stores, and skip reloads across a write through "some other type". Break that assumption and you get the worst failure mode there is — a silent miscompile: the program is correct at -O0/-O1, produces wrong results at -O2, and the compiler emits no error and usually no warning. The rule is type-based (which types may access which object), and it is separate from restrict, which is a per-pointer promise about aliasing regardless of type.

Only a narrow set of type pairs may legally access the same object. Reading a float through an int*, or one struct through an unrelated struct*, is undefined behavior — not "implementation-defined", not "works on x86". The portable way to reinterpret bytes is memcpy (C and C++) or std::bit_cast (C++20), never a reinterpreting pointer cast. This is the same aliasing model that decides whether a loop vectorizes: the optimizer needs to prove two pointers can't overlap, and strict aliasing plus restrict are the two ways it gets that proof.

What may legally alias what

GCC states the rule directly: "Accessing an object of one type via an expression of a different type is not allowed, unless the types are compatible types, differ only in signedness or qualifiers, or the expression has a character type." The stored value of an object may be accessed through an lvalue of:

Access lvalue typeLegal?

The object's own (effective) type, or a compatible typeYes
A type differing only in const/volatile qualificationYes
The signed/unsigned variant of the effective type (int <-> unsigned int)Yes
An aggregate (struct/array) or union that contains such a type among its membersYes
A character type: char, unsigned char, signed char (and std::byte in C++)Yes — may alias any type
Any other type (float object read as int, struct A read as struct B)No — undefined behavior

Two consequences follow. First, char* can alias anything, but the reverse is false: reading a char buffer through an int* is still UB unless that buffer's effective type is actually int. Second, the character-type exemption is precisely why memcpy (which operates on unsigned char) is the sanctioned way to move bytes between unrelated types — the compiler must assume a char-typed access can touch any object.

The "effective type" of an object is its declared type; for storage from malloc/aligned_alloc (which has no declared type), the effective type becomes the type of the lvalue used to store into it. Vector-type access to the corresponding scalar is also allowed.

Why it bites: the silent miscompile

The classic trap is reinterpreting through a pointer cast:

/* UNDEFINED BEHAVIOR: reads a float object through an int lvalue */
unsigned int float_bits_wrong(float f) {
    return *(unsigned int *)&f;   /* incompatible-type access */
}

At -O0 this "works" — it does the load you expect. At -O2 with strict aliasing on, the compiler may assume the int read cannot possibly refer to the float argument, and is free to reorder it relative to the store of f, or to keep f in a register and read stale stack memory. Nothing in the toolchain flags it by default. The bug appears only when someone bumps the optimization level, changes an unrelated function so f gets inlined, or upgrades the compiler.

The correct, defined versions:

/* C and C++: memcpy is always legal and folds to a single load */
unsigned int float_bits_c(float f) {
    unsigned int u;
    memcpy(&u, &f, sizeof u);     /* char-based access; no UB */
    return u;
}


// C++20: std::bit_cast is constexpr and requires equal size + trivially copyable
#include <bit>
unsigned int float_bits_cpp(float f) {
    return std::bit_cast<unsigned int>(f);
}

memcpy here is not a runtime cost: with a compile-time-known size, both GCC and Clang lower it to the same single mov the buggy cast would have produced — you pay nothing for correctness. std::bit_cast copies the bits into a new object, which is why it never violates aliasing; it participates in overload resolution only when sizeof(To) == sizeof(From) and both types are trivially copyable, and it is usable in constexpr.

Legal ways to type-pun

MechanismLanguageNotes

memcpy / memmoveC and C++Always legal (char exemption); optimized to a plain load/store when the size is constant
std::bit_cast<To>(from)C++20 (<bit>)Equal size + both trivially copyable; constexpr; creates a new object, no aliasing risk
Union member read-after-writeC (standard)Type-punning through a union is permitted in ISO C; the value is accessed "through the union type"
Union member read-after-writeC++Undefined behavior in ISO C++, but GCC and Clang support it as an extension
char / unsigned char / std::byte lvalueC and C++May access the bytes of any object legally
__attribute__((__may_alias__)) typeGCC/ClangExtends the char exemption to a user type: an lvalue of a may_alias type may access any object

Two portability traps live in this table. Union type-punning is standard in C but only a compiler extension in C++ — the same code that is fine in a .c file is UB in a .cpp file. And relying on the common-initial-sequence rule for structs inside a union is fragile: the shared prefix is only guaranteed up to "the first pair of members whose types are not compatible", and compilers have historically disagreed on the details. When in doubt, memcpy or std::bit_cast are the choices that are correct everywhere.

restrict — the other aliasing promise

restrict (C99; C++ has no standard restrict but compilers offer __restrict) is a different mechanism that people conflate with strict aliasing. Strict aliasing is about types; restrict is about specific pointers, regardless of type. Qualifying a pointer restrict promises the compiler: for the lifetime of that pointer in its block, any object it is used to modify is accessed only through that pointer (or values derived from it). Break the promise and the behavior is undefined.

/* Without restrict, the compiler must assume dst may overlap a/b and
   reload on every iteration. With restrict it can keep sums in registers
   and vectorize freely. */
void axpy(float *restrict dst, const float *restrict a,
          const float *restrict b, int n) {
    for (int i = 0; i < n; i++) dst[i] = a[i] + b[i];
}

restrict matters most where strict aliasing gives no help — two pointers of the same type (float* dst vs float* a), which the type rule alone cannot disambiguate. It is the manual, opt-in equivalent of the exclusive-access guarantee that Rust's borrow checker enforces for &mut at compile time: a &mut T in safe Rust is a checked promise of exactly what restrict asserts on the honor system.

Turning it off and diagnosing

  • -fstrict-aliasing is enabled at -O2, -O3, and -Og. -fno-strict-aliasing disables the assumption globally — this is why the Linux kernel and many large C codebases build with -fno-strict-aliasing: it trades some optimization for not having to audit every cast. Use it as a safety net, not a license to write incorrect code.
  • -Wstrict-aliasing (equivalent to -Wstrict-aliasing=3, the default when you ask for it) is only active when -fstrict-aliasing is active and catches only the common patterns, not all violations:

LevelBehavior

=1Most aggressive, front-end only; warns on all pointer conversions between possibly incompatible types even if never dereferenced; many false positives, very few false negatives
=2Warns only when an address is taken; warns about incomplete types; fewer false positives than level 1; front-end only
=3 (default)Catches the *(int*)&some_float pun+dereference pattern; with optimization on, also runs in the back end using flow-sensitive points-to info; very few false positives; only warns when the converted pointer is dereferenced

  • UBSan does not save you here. -fsanitize=undefined has no runtime check for strict-aliasing violations — there is no -fsanitize=strict-aliasing. Do not assume a clean UBSan run means your casts are legal; it does not instrument this class of UB. The practical detectors are -Wstrict-aliasing (incomplete), code review for reinterpreting casts, and, for real coverage, simply not doing the cast.

Common gotchas

  • It is a silent miscompile, not a crash. Correct results at -O0/-O1, wrong at -O2, no diagnostic. If a bug appears only at higher optimization levels or after a compiler upgrade, suspect an aliasing violation before you suspect a compiler bug.
  • char* aliases everything; nothing aliases char in reverse. Reading a byte buffer through an int* is UB unless the buffer's effective type is int. The exemption is one-directional.
  • A pointer cast does not "convert" the object — it reinterprets, and that is the UB. *(T*)&x is the wrong tool. Use memcpy or std::bit_cast; they compile to the same instructions with none of the UB.
  • Union punning is legal in C, UB in C++. The identical function is fine in a .c translation unit and undefined in a .cpp one (GCC/Clang allow it as an extension, but other C++ compilers need not, and the standard does not).
  • restrict is an unchecked promise, and violating it is UB visible only under optimization. Passing overlapping pointers to a restrict parameter (memcpy(dst, dst+1, n)-style overlap into a restrict API) miscompiles silently. restrict on a function signature is a contract every caller must honor.
  • -fno-strict-aliasing is per-translation-unit at best and does not make the code portable. It disables the optimization for your build; a header shipped to someone compiling with strict aliasing on is still broken. Fix the cast rather than relying on a flag downstream builds may not set.
  • may_alias is a type attribute, not a pointer attribute. You must access through an lvalue whose type carries __attribute__((__may_alias__)); tagging a variable or slapping it on a cast target incorrectly does not grant the exemption.
  • Same-type pointers need restrict, not strict aliasing. If two pointers have the same type, the type rule gives the optimizer nothing — only restrict (or the compiler proving non-overlap) unlocks reload elimination and vectorization.
