jose — JWA/JWS/JWE/JWT/JWK/JWKS Library for JavaScript (panva)

Overview

jose is the canonical pure-JavaScript implementation of the JOSE family of standards — JSON Web Algorithms (JWA, RFC 7518), JSON Web Signature (JWS, RFC 7515), JSON Web Encryption (JWE, RFC 7516), JSON Web Token (JWT, RFC 7519), JSON Web Key (JWK, RFC 7517), and JSON Web Key Set (JWKS). Maintained by Filip Skokan (panva) — also the author of node-oidc-provider and the JOSE/OIDC reference implementations the IETF OAuth WG uses for interop testing — and sponsored by Auth0. Pure ESM, zero dependencies, runtime-agnostic (Node.js, browsers, Cloudflare Workers, Deno, Bun, Electron, every Web-interop runtime that exposes the Web Crypto API and fetch). MIT licensed, 7,597 GitHub stars (May 2026).

Pairs with JSON Web Tokens anatomy (the spec primer), DPoP RFC 9449 (proof-of-possession JWS use case), RFC 7800 cnf-claim, SD-JWT (RFC 9901), and PASETO (the modern JWT-replacement movement). When an application says "verify this JWT", "produce a JWS over this payload", "fetch the issuer's JWKS and rotate against kid", or "encrypt a JWT for a recipient", jose is the JavaScript answer in 2025–2026.

Release cadence: 2–4 patches per quarter, one major every 9–18 months. The v5→v6 break (Feb 2025) consolidated on the Web Crypto API as the only crypto backend — what shipped before as a polymorphic KeyObject | CryptoKey return type is now CryptoKey everywhere, including Node.js. This removed ~40% of the source size and let jose run unchanged on Workers/Deno/Bun/browsers from the same artifact.

Core API surface

JWT (jwtVerify + SignJWT)

import { SignJWT, jwtVerify, createRemoteJWKSet } from 'jose'

// Sign
const secret = new TextEncoder().encode('your-256-bit-secret')
const jwt = await new SignJWT({ 'urn:example:claim': true })
  .setProtectedHeader({ alg: 'HS256' })
  .setIssuedAt()
  .setIssuer('urn:example:issuer')
  .setAudience('urn:example:audience')
  .setExpirationTime('2h')
  .sign(secret)

// Verify (HMAC)
const { payload, protectedHeader } = await jwtVerify(jwt, secret, {
  issuer: 'urn:example:issuer',
  audience: 'urn:example:audience',
})

// Verify against a remote JWKS (canonical OIDC pattern)
const JWKS = createRemoteJWKSet(new URL('https://issuer.example/.well-known/jwks.json'))
const verified = await jwtVerify(token, JWKS, { issuer, audience })

createRemoteJWKSet honors HTTP caching headers, refreshes on kid cache-miss (default cooldown 30s — cooldownDuration option), times out at 5s (timeoutDuration), and is the standard production pattern for verifying tokens from Auth0/Okta/Entra ID/Google/Apple/GitHub/accounts.google.com-style issuers. The fetch is replaceable for testing via the [fetch] option.

JWS (CompactSign / compactVerify + Flattened/General serializations)

import { CompactSign, compactVerify, importJWK } from 'jose'

const privateKey = await importJWK({ /* JWK */ }, 'ES256')
const jws = await new CompactSign(new TextEncoder().encode('payload'))
  .setProtectedHeader({ alg: 'ES256', kid: 'key-1' })
  .sign(privateKey)

const { payload, protectedHeader } = await compactVerify(jws, publicKey)

Three serialization syntaxes: Compact (header.payload.signature, the form 99% of code uses), Flattened JSON (one signer + unprotected header), General JSON (N signers, used by DSSE-via-JWS shapes).

JWE (CompactEncrypt / compactDecrypt)

import { CompactEncrypt, compactDecrypt } from 'jose'

const jwe = await new CompactEncrypt(new TextEncoder().encode('secret'))
  .setProtectedHeader({ alg: 'RSA-OAEP-256', enc: 'A256GCM' })
  .encrypt(publicKey)

const { plaintext, protectedHeader } = await compactDecrypt(jwe, privateKey)

JWE composes a key-management algorithm (alg — RSA-OAEP-256, ECDH-ES+A256KW, A256KW, PBES2-HS256+A128KW, dir, …) with a content encryption algorithm (enc — A256GCM, A128CBC-HS256, XC20P, …). RSA1\_5 was dropped in v6.0.0 because it's a padding-oracle target (CVE-2023-50782).

JWK / JWKS keys

importJWK(jwk, alg?) -> CryptoKey / importSPKI / importX509 / importPKCS8 / exportJWK / exportSPKI / exportPKCS8 / generateKeyPair(alg, options) / generateSecret(alg, options) / calculateJwkThumbprint (RFC 7638) / calculateJwkThumbprintUri (RFC 9278) / EmbeddedJWK (verify JWS where the public key is embedded in the protected header as jwk — the DPoP standard pattern).

Errors

JOSEError is the base class; subclasses are flat single-purpose: JWSInvalid, JWSSignatureVerificationFailed, JWTClaimValidationFailed, JWTExpired, JWKSNoMatchingKey, JWKSMultipleMatchingKeys, JWEInvalid, JWEDecryptionFailed. Catch on the specific subclass, not on Error — the latter swallows runtime/network errors that should propagate.

jose exposes the JOSE-standard alg matrix; available subset is runtime-dependent because Web Crypto algorithm support varies by host:

The alg: 'none' (unsecured JWT, RFC 7519 §6) is intentionally not signable nor verifiable through the standard path — UnsecuredJWT is an explicit separate class that yields/parses an unsecured token and forces the developer to handle that ceremony outside the normal verify flow. This is the canonical fix for the classic alg: 'none' attack class against badly-written verifiers.

Distribution

Available as jose on npmjs.com, @panva/jose on jsr.io (the JSR runtime-agnostic registry), CDN via jsdelivr.com, source on github.com/panva/jose. ESM-first; CJS interop only via Node ≥20.19/22.12/23+ with the require(esm) feature flag — older Node CJS callers must import() dynamically.

Common gotchas

  • createRemoteJWKSet does not validate the issuer's JWKS URL is HTTPS — supply the full URL and validate the scheme yourself if the source is untrusted. It DOES enforce the 5s default timeoutDuration and 30s cooldownDuration between refreshes; a stampede of kid-miss errors won't DDoS the issuer.
  • kid cache-miss triggers a refresh, but the new fetch is shared across concurrent verifies — jose deduplicates in-flight refreshes. After cooldown, a still-missing kid raises JWKSNoMatchingKey instead of looping.
  • audience matching is strict equality (string or array-includes) — no URI canonicalization, no trailing-slash forgiveness. aud: "https://api.example/" does NOT match audience: "https://api.example". The same trap exists in RFC 9728 octet-equality.
  • Clock skew is per-call (clockTolerance option, default 0 seconds) — set explicitly (typically 30–60s) for production. There is no global default.
  • requiredClaims option must be paired with explicit checks — requiredClaims: ['sub'] enforces the claim is present but not its value. For value matching pass subject, issuer, audience (typed options).
  • Symmetric keys cannot be re-imported across runtimes via exportJWK → importJWK if they were generated with extractable: false — Web Crypto raises InvalidAccessError. Generate with { extractable: true } if cross-process export is needed; for production secrets keep extractable: false and never round-trip.
  • SignJWT does not auto-setIssuedAt — call it explicitly; verifiers that require iat will reject the token otherwise.
  • The none algorithm requires UnsecuredJWT — SignJWT(...).sign() with alg: 'none' throws. Calling jwtVerify against an alg: 'none' token also throws. To accept unsigned tokens (rare, dangerous) use UnsecuredJWT.decode(token, { issuer, audience }).
  • Worker runtimes have algorithm gaps — Cloudflare Workers prior to 2024 had no Ed25519; Bun gained RSA-OAEP-512 in v1.1; check the runtime-specific issues before assuming a alg works across deploy targets.
  • createRemoteJWKSet does not implement the RFC 9728 Protected Resource Metadata discovery — combine with a small wrapper that reads jwks_uri from /.well-known/oauth-protected-resource then passes the resulting URL.
  • Octet length of HMAC keys is enforced — HS256 requires ≥32 bytes, HS384 ≥48, HS512 ≥64. A TextEncoder().encode('mysecret') 8-byte secret throws JWKInvalid on import. Use generateSecret('HS256') or supply a properly-sized key.
  • PEM imports use one-shot helpers — importPKCS8 for private, importSPKI for public, importX509 for certs. There's no "import any PEM" detector — pick the function matching the PEM banner.
  • exportJWK(CryptoKey) returns plain JSON — to publish a JWKS, wrap in { keys: [jwk1, jwk2, …] } yourself; jose does not emit JWKS-shaped objects.
  • v6.0.0 removed secp256k1 JWS — codebases doing Ethereum-style signing on ES256K must pin v5.x or migrate to a separate library. Decision: secp256k1 is not in the JOSE algorithm registry, only an unregistered draft.
