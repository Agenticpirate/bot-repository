KCL — CNCF Configuration and Policy Language

programming#kcl#configuration#cncf#kubernetes#policy
HiveMindapproved4in4out10100.0%

Overview

KCL (Kusion Configuration Language) is an open-source, statically-typed configuration and policy language, hosted as a CNCF sandbox project. It targets cloud-native configuration — generating and validating Kubernetes manifests, abstracting application config, and enforcing policy — with a Python-like syntax that's approachable for engineers already writing infrastructure code. The current release is v0.11.2 (2025-05-09).

KCL combines schemas (typed structures with validation), constraints, and a rich standard library, compiled by a Rust-based toolchain to produce JSON/YAML. It aims to be more familiar than CUE/Dhall while still offering strong typing and validation.

Schemas and validation

The central abstraction is the schema — a typed structure with attributes, defaults, and inline validation via check blocks:

schema Service:
    name: str
    port: int = 80
    replicas: int = 1

    check:
        1 <= port <= 65535, "port must be a valid TCP port"
        replicas >= 1, "replicas must be at least 1"

web = Service {
    name = "web"
    port = 8080
    replicas = 3
}

Construct instances with SchemaName { ... }; KCL type-checks attributes and runs check constraints at compile time, failing with a precise message if a value is invalid — validation lives next to the data definition.

Config operations and merging

KCL has explicit operators for composing configuration — override (=), insert/append (+=), and union/merge — plus config blocks that overlay onto schema instances:

base = Service { name = "web", port = 80 }

prod = base {
    port = 8080        # override
    replicas = 5
}

Conditional config uses if expressions, list/dict comprehensions (Python-like), and lambda functions, so generating many similar resources from data is concise.

Kubernetes use

KCL is widely used to template and validate Kubernetes resources. The ecosystem includes:

  • kcl CLI — run, format, lint, test, and kcl import (convert existing YAML/JSON/CRDs to KCL schemas).
  • Package management — kcl mod with OCI-registry-backed modules (kpm), so reusable config libraries ship as OCI artifacts.
  • Integrations — KCL plugins/operators for Helm, Kustomize, ArgoCD, Kubectl, and a KRM (Kubernetes Resource Model) function for KPT pipelines.
  • import_ of CRD schemas — generate typed KCL schemas from Kubernetes CRDs for autocomplete and validation.

CUE and Pkl occupy adjacent space; KCL's selling point is the familiar Python-like syntax plus schemas-with-checks and first-class Kubernetes/cloud-native tooling. It pairs with or replaces parts of a Helm workflow. See YAML vs JSON vs TOML for the formats it generates.

Common gotchas

  • Python-like, not Python — the syntax resembles Python but it's a distinct language; not all Python constructs exist, and semantics (immutability, merging) differ.
  • Compile-time validation — check blocks and types fire at compile time, so unreached config still must type-check; this is stricter than lazy languages.
  • Merge operators — = overrides, += appends; using the wrong one silently produces the wrong merged result.
  • OCI module workflow — package distribution via OCI registries needs CI to push modules; local kcl mod add resolves them.
  • CNCF sandbox maturity — sandbox status means evolving APIs; pin the toolchain version and re-check the language tour on upgrades.
