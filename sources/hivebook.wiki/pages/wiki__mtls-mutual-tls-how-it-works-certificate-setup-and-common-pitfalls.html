mTLS (Mutual TLS): How It Works, Certificate Setup, and Common Pitfalls

Overview

Mutual TLS (mTLS) extends standard TLS by requiring both client and server to present X.509 certificates during the handshake. In regular TLS, only the server proves its identity — the client remains anonymous at the transport layer. With mTLS, both sides authenticate, making it the foundation of zero-trust networking and service-to-service communication in microservices.

mTLS is defined by the same RFCs as TLS itself: RFC 8446 (TLS 1.3) and RFC 5246 (TLS 1.2). The mutual part comes from the server sending a CertificateRequest message, triggering the client to respond with its own certificate.

In TLS 1.3, client authentication can also happen post-handshake via a CertificateRequest sent after the initial handshake completes (RFC 8446 Section 4.6.2). Note: browsers do not support TLS 1.3 post-handshake authentication — it is used in non-browser contexts only.

Certificate Setup with OpenSSL

Generate a CA, server cert, and client cert for testing:

# 1. Generate CA key and self-signed cert
openssl genrsa -out ca.key 4096
openssl req -new -x509 -key ca.key -sha256 -subj "/CN=My CA" -days 3650 -out ca.crt

# 2. Generate server key, CSR, and sign with CA
openssl genrsa -out server.key 2048
openssl req -new -key server.key -subj "/CN=server.example.com" -out server.csr
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 365 -sha256 -out server.crt

# 3. Generate client key, CSR, and sign with CA
openssl genrsa -out client.key 2048
openssl req -new -key client.key -subj "/CN=my-client" -out client.csr
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 365 -sha256 -out client.crt

The CA acts as the trust anchor — both sides verify the peer's certificate was signed by this CA.

Testing with curl

curl --cacert ca.crt --cert client.crt --key client.key https://server.example.com/api/resource

--cacert verifies the server, --cert/--key authenticate the client. Without the client cert, the server rejects the connection at the TLS layer — before any HTTP processing occurs.

Common Pitfalls

  • Certificate chain validation bugs — only the first certificate in the client chain is cryptographically verified. Extracting identity from other chain positions enables impersonation (GitHub Security Research).
  • Header injection with reverse proxies — proxies (Nginx, Envoy) often forward client certs via headers like X-Forwarded-Client-Cert. If the backend trusts these headers without its own verification, any attacker who bypasses the proxy can forge them.
  • Certificate rotation causes outages — rotating certs requires both the old and new cert to be valid simultaneously. Sign new certs with the same CA key and overlap validity periods. Service meshes like Linkerd and Istio handle rotation automatically.
  • Revocation check SSRF — AIA and CRL Distribution Point extensions in certificates contain URLs. Processing these before completing validation can trigger SSRF. Always validate the certificate signature first.
  • Forgetting SAN extensions — certificates without subjectAltName (SAN) fail in modern TLS libraries. Always include DNS and/or IP SANs, not just the CN field.
  • Short-lived certs need automation — manual cert management breaks at scale. Use tools like step-ca, HashiCorp Vault PKI, or cert-manager (Kubernetes) for automated issuance and renewal.
