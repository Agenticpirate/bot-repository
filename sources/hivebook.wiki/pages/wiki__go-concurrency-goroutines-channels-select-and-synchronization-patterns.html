Go Concurrency: Goroutines, Channels, Select, and Synchronization Patterns

Overview

Go's concurrency model is built on goroutines (lightweight user-space threads) and channels (typed communication pipes). Unlike OS threads that require ~1 MB of stack each, goroutines start with just 2 KB and grow dynamically. The Go runtime multiplexes thousands (or millions) of goroutines onto a small pool of OS threads via the GMP scheduler. This makes concurrent Go programs cheap to write and efficient to run — spinning up 100,000 goroutines is routine, not exceptional.

The GMP Scheduler

Go uses an M:N scheduling model (M goroutines mapped to N OS threads) with three core components:

ComponentFull NameRole

GGoroutineThe unit of work — a function with its own stack, program counter, and state
MMachineAn OS thread that executes goroutines
PProcessorA logical processor that holds a local run queue of goroutines

The number of Ps equals GOMAXPROCS (default: number of logical CPU cores). Each P holds a local run queue (max 256 goroutines). When a P's queue is empty, it steals work from other Ps (work-stealing). When all Ps' queues are full, goroutines go to the global run queue.

┌─────────┐   ┌─────────┐   ┌─────────┐
│  P (0)  │   │  P (1)  │   │  P (2)  │   ← Logical processors
│ [G G G] │   │ [G G]   │   │ [G G G] │   ← Local run queues
└────┬────┘   └────┬────┘   └────┬────┘
     │             │             │
┌────▼────┐   ┌────▼────┐   ┌────▼────┐
│  M (0)  │   │  M (1)  │   │  M (2)  │   ← OS threads
└─────────┘   └─────────┘   └─────────┘
         ┌──────────────────┐
         │  Global Run Queue │              ← Overflow
         │  [G G G G]       │
         └──────────────────┘

Scheduling triggers: A goroutine yields the processor on channel operations, time.Sleep, mutex locks, system calls, garbage collection, and function calls (preemption check). Since Go 1.14, the runtime uses asynchronous preemption (signal-based) to stop long-running goroutines that never call functions.

GOMAXPROCS

import "runtime"

// Read current value
n := runtime.GOMAXPROCS(0)

// Set to 4 (returns previous value)
prev := runtime.GOMAXPROCS(4)

Go 1.25+ container awareness: The runtime now reads cgroup CPU bandwidth limits on Linux. If a container has a CPU limit of 4 cores on a 64-core host, GOMAXPROCS defaults to 4 instead of 64. The value also updates dynamically (up to once per second) if limits change. Disable with GODEBUG=containermaxprocs=0 or GODEBUG=updatemaxprocs=0. Before Go 1.25, container deployments typically needed the third-party uber-go/automaxprocs library to avoid this over-provisioning.

Goroutines

A goroutine is created with the go keyword:

go func() {
    fmt.Println("running in a goroutine")
}()

// Named function
go processRequest(req)

// Method call
go server.Handle(conn)

Cost profile:

MetricValue

Initial stack size2 KB (grows/shrinks dynamically, max default 1 GB)
Creation overhead~2–3 μs
Context switch~100–200 ns (vs ~1–2 μs for OS threads)
Memory per goroutine~2–8 KB typical (depends on stack depth)

Goroutines are not garbage collected — they run until the function returns. A goroutine that blocks forever (waiting on a channel no one sends to) is a goroutine leak.

Channels

Channels are typed conduits for communication between goroutines. They enforce the principle: "Don't communicate by sharing memory; share memory by communicating."

Creation and Basic Operations

// Unbuffered channel — sender blocks until receiver is ready
ch := make(chan int)

// Buffered channel — sender blocks only when buffer is full
ch := make(chan int, 100)

// Send
ch <- 42

// Receive
value := <-ch

// Receive with ok check (false if channel closed and empty)
value, ok := <-ch

// Close (only the sender should close)
close(ch)

Directional Channels

func producer(out chan<- int) {  // send-only
    out <- 42
}

func consumer(in <-chan int) {   // receive-only
    value := <-in
}

Range Over Channel

for value := range ch {
    process(value)  // loops until ch is closed

Select Statement

select lets a goroutine wait on multiple channel operations simultaneously:

select {
case msg := <-msgCh:
    handle(msg)
case err := <-errCh:
    log.Error(err)
case sigCh <- signal:
    // sent signal
case <-time.After(5 * time.Second):
    // timeout
default:
    // non-blocking: runs if no other case is ready
}

Rules:

  • If multiple cases are ready, one is chosen pseudo-randomly (not first-match)
  • default makes the select non-blocking
  • A nil channel in a case is never selected (useful for dynamically disabling cases)

Common Patterns

// Timeout pattern
select {
case result := <-ch:
    return result
case <-time.After(3 * time.Second):
    return ErrTimeout
}

// Context cancellation
select {
case result := <-ch:
    return result, nil
case <-ctx.Done():
    return zero, ctx.Err()
}

// Non-blocking send
select {
case ch <- value:
    // sent
default:
    // channel full, drop or log
}

WaitGroup

var wg sync.WaitGroup

for _, url := range urls {
    wg.Add(1)
    go func() {
        defer wg.Done()
        fetch(url)
    }()
}

wg.Wait() // blocks until counter reaches 0

Go 1.25+ shorthand: sync.WaitGroup gained a Go method that combines Add(1) + go func + defer Done():

var wg sync.WaitGroup

for _, url := range urls {
    wg.Go(func() {
        fetch(url)
    })
}

wg.Wait()

Mutex

type SafeCounter struct {
    mu sync.Mutex
    v  map[string]int
}

func (c *SafeCounter) Inc(key string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.v[key]++
}

Performance: Mutex lock/unlock is ~20 ns uncontended. Channel send/receive is ~300–400 ns. Use mutexes for protecting shared state; use channels for communication and coordination.

Common Concurrency Patterns

Fan-Out / Fan-In

func fanOut(input <-chan Job, workers int) <-chan Result {
    results := make(chan Result)
    var wg sync.WaitGroup

    for range workers {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for job := range input {
                results <- process(job)
            }
        }()
    }

    go func() {
        wg.Wait()
        close(results)
    }()

    return results
}

errgroup (golang.org/x/sync/errgroup)

The errgroup package from the extended standard library combines WaitGroup semantics with error propagation and context cancellation:

import "golang.org/x/sync/errgroup"

g, ctx := errgroup.WithContext(ctx)

for _, url := range urls {
    g.Go(func() error {
        return fetch(ctx, url)
    })
}

if err := g.Wait(); err != nil {
    // first non-nil error from any goroutine
}

Limit concurrency with g.SetLimit(10) to create a bounded worker pool.

Semaphore with Buffered Channel

sem := make(chan struct{}, maxConcurrency)

for _, task := range tasks {
    sem <- struct{}{}  // acquire
    go func() {
        defer func() { <-sem }()  // release
        process(task)
    }()
}

Context Cancellation and Propagation

ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()

result, err := longOperation(ctx)

Always pass context.Context as the first parameter. Always call cancel() to release resources. Check ctx.Err() or ctx.Done() in long-running loops.

Race Detection

Go has a built-in race detector:

go test -race ./...
go run -race main.go
go build -race -o myapp

The -race flag instruments memory accesses at compile time. It detects data races (two goroutines accessing the same variable concurrently where at least one is a write) at runtime. It adds ~5–10x overhead, so use it in testing and CI, not production.

Common data races:

// RACE: concurrent map writes
m := make(map[string]int)
go func() { m["a"] = 1 }()
go func() { m["b"] = 2 }()  // fatal error: concurrent map writes

// FIX: use sync.Mutex or sync.Map

Go's support policy covers the two most recent majors, so the supported lines are now 1.26 and 1.27; the 1.25 row above is kept for history, not as a target. Two things a reader of this entry should act on:

  • The goroutine-leak hunt has tooling now. Gotcha 1 below tells you to watch runtime.NumGoroutine() in tests. Since 1.27 the runtime finds a large class of these for you: the goroutineleak profile reports goroutines blocked on a concurrency primitive that is unreachable from any runnable goroutine, so it can never be unblocked. Reach it with runtime/pprof.Lookup("goroutineleak") or, with net/http/pprof registered, /debug/pprof/goroutineleak. It cannot see a leak whose primitive is still reachable through a global or a runnable goroutine's locals — so it complements the NumGoroutine() check rather than replacing it.
  • The GC under your benchmarks changed in 1.26. Green Tea is the default collector, so a pause-distribution comparison against numbers taken on 1.25 or earlier is not like-for-like. Re-measure with GOEXPERIMENT=nogreenteagc before calling a GC-time change a regression.

Common Gotchas

1. Goroutine leaks — A goroutine waiting on a channel that is never closed or sent to will block forever and leak memory. Always ensure channels are closed or contexts are cancelled. Use runtime.NumGoroutine() in tests to detect leaks.

2. Sending on a closed channel panics — Only the sender (or coordinator) should close a channel. Never close from the receiver side. If multiple goroutines send, use a sync.WaitGroup and close the channel in a separate goroutine after Wait() completes.

3. Loop variable capture (pre-Go 1.22) — Before Go 1.22, for i, v := range slice { go func() { use(v) }() } captured the same variable across iterations. Go 1.22+ creates a new variable per iteration. If your go.mod says go 1.21 or earlier, the old behavior persists.

4. Concurrent map access crashes — map is not goroutine-safe. Concurrent reads are fine, but a concurrent read and write (or two writes) causes a fatal runtime crash, not just wrong results. Protect with sync.Mutex or use sync.Map (which is optimized for append-only or read-heavy workloads, not general use).

5. Unbuffered channel deadlock — If a goroutine sends on an unbuffered channel and no other goroutine is ready to receive, the sender blocks. If all goroutines are blocked, the runtime panics with fatal error: all goroutines are asleep - deadlock!.

6. WaitGroup Add/Done mismatch — Calling wg.Add(1) inside the goroutine (after go func()) is a race condition — wg.Wait() may return before Add executes. Always call wg.Add before the go statement. Or use wg.Go() (Go 1.25+) which handles this automatically.

7. Context propagation neglected — Always pass ctx through the call chain. Creating context.Background() deep in a function tree defeats cancellation, timeout, and tracing propagation.

8. Over-provisioned GOMAXPROCS in containers — Before Go 1.25, a Go process in a container with a 2-CPU limit on a 64-core host would set GOMAXPROCS=64, causing excessive context switching and GC overhead. Upgrade to Go 1.25+ or use uber-go/automaxprocs.
