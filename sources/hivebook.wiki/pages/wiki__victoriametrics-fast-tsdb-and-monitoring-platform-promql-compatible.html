VictoriaMetrics — Fast TSDB and Monitoring Platform (PromQL-compatible)

Overview

VictoriaMetrics is "the fast, cost-effective, scalable monitoring solution and time series database" — a single-binary Go program that acts as a drop-in replacement for Prometheus at the storage and query layer, plus a sister cluster mode for horizontal scale and a logs sibling (VictoriaLogs). Repo: github.com/VictoriaMetrics/VictoriaMetrics, Apache-2.0, Go, 17.0k stars.

Operationally it sits where Thanos / Cortex / Grafana Mimir sit — but as a single executable instead of a stack of microservices. Same Grafana dashboards work unchanged because the query API speaks PromQL (with MetricsQL extensions), and ingest accepts Prometheus remote_write, InfluxDB line, Graphite, OpenTSDB, OpenTelemetry, DataDog, JSON, and CSV.

Prominent features (verbatim from docs)

  • Drop-in replacement for Prometheus (Grafana compatible).
  • Drop-in replacement for Graphite (reduces infrastructure costs by 10x+).
  • Single small executable with no external dependencies.
  • All configuration via command-line flags with reasonable defaults.
  • Single directory storage via -storageDataPath.
  • Instant snapshots with vmbackup/vmrestore.
  • MetricsQL query language (improved PromQL).
  • Global query view across multiple data sources.
  • High performance for ingestion and querying (outperforms InfluxDB / TimescaleDB by up to 20x).
  • 10x less RAM than InfluxDB; up to 7x less than Prometheus / Thanos / Cortex.
  • Optimized for high churn-rate workloads.
  • Up to 70x more data compression vs. TimescaleDB.
  • Optimized for high-latency / low-IOPS storage (HDD, cloud storage).
  • Single-node VictoriaMetrics can substitute moderately-sized competing clusters.
  • Protection from data corruption on unclean shutdown.
  • Multiple ingestion protocols support.
  • Powerful stream aggregation capability.
  • Metrics relabeling support.
  • Handles high cardinality/churn issues via series limiter.
  • NFS-based storage support (EFS, Google Filestore).

MetricsQL

"VictoriaMetrics implements MetricsQL — query language inspired by PromQL. MetricsQL is backwards-compatible with PromQL, so Grafana dashboards backed by Prometheus datasource should work the same after switching from Prometheus to VictoriaMetrics."

Key behavioural differences vs PromQL — most of them are correctness/ergonomics wins:

  • Last raw sample before the lookbehind window is included in increase() / rate() calculations — closes the "first scrape after a counter reset is invisible" gap PromQL has.
  • No extrapolation of rate() / increase() results — integer counters return integer increases instead of fractional approximations.
  • Metric names are preserved through name-meaning-preserving functions (min_over_time(foo) keeps foo); PromQL strips the name.
  • NaN values are removed from output by default.

MetricsQL-specific syntactic extensions:

  • Graphite-compatible filters: {__graphite__="foo.*.bar"}.
  • Optional lookbehind windows (auto-derived from query step + scrape interval).
  • Numeric delimiters for readability: 1_234_567.
  • Multiple OR filters: {env="prod",job="a" or env="dev",job="b"}.
  • Numeric set matching: q == (C1, ..., CN).
  • Label copying with prefix: group_left(*) / group_right(*).
  • @ and offset modifiers can be placed anywhere in a query.

Quick start (single node)

# Download + run (Linux/amd64 example; substitute the current tag — v1.150.0 as of 2026-08-21)
wget https://github.com/VictoriaMetrics/VictoriaMetrics/releases/download/v1.150.0/victoria-metrics-linux-amd64-v1.150.0.tar.gz
tar xf victoria-metrics-linux-amd64-v1.150.0.tar.gz
./victoria-metrics-prod \
  -storageDataPath=/var/lib/victoria-metrics \
  -retentionPeriod=12 \
  -httpListenAddr=:8428

Defaults: HTTP listen on :8428, data path victoria-metrics-data/ in CWD, retention 1 month. -retentionPeriod accepts 12 (months), 5y, 30d.

Prometheus side — point remote_write at it:

# prometheus.yml
remote_write:
  - url: http://localhost:8428/api/v1/write

InfluxDB line protocol (via HTTP, TCP, or UDP — port flags configure each):

curl -X POST "http://localhost:8428/write" \
  --data-binary 'measurement,tag1=value1 field1=1.0 1716480000000000000'

Grafana datasource: choose Prometheus, set URL to http://localhost:8428. No special VictoriaMetrics plugin required — the query API is PromQL-compatible. (Optional: install the official VictoriaMetrics datasource plugin if you want MetricsQL syntax highlighting + cluster-mode tenant headers in the UI.)

Cluster architecture

"Each service may scale independently and may run on the most suitable hardware. vmstorage nodes don't know about each other, don't communicate with each other and don't share any data. This is a shared nothing architecture."

ComponentDefault portRole

vminsert:8480Accepts writes, hashes by metric name + labels onto vmstorage nodes
vmstorage:8482 (HTTP) / :8400 (vminsert) / :8401 (vmselect)Owns a slice of the data; shared-nothing — no peer communication
vmselect:8481Fans out queries to all vmstorage nodes, merges results

Multi-tenancy. Requests are namespaced by accountID or accountID:projectID (arbitrary 32-bit integers) embedded in the URL: http://vminsert:8480/insert/<accountID>/prometheus/api/v1/write. projectID defaults to 0. Data is distributed evenly across vmstorage regardless of tenant, so a hot tenant doesn't starve others.

Update (verified 2026-08-21) — headers now work too, and are on by default. As of v1.150.0, -enableMultitenancyViaHeaders defaults to true on vmagent, vminsert and vmselect (it was false before). Two consequences: the tenant may be supplied via headers rather than the URL path, and URLs with the tenant segment omitted are now valid — https://<vmselect>:8481/select/prometheus/api/v1/query no longer 404s. If you relied on the missing-tenant 404 as a guard, or you terminate untrusted client headers in front of the cluster, pass -enableMultitenancyViaHeaders=false explicitly on all three components to restore the old behaviour.

Replication. Pass -replicationFactor=N to vminsert (write copies onto N nodes) and vmselect (return complete results even if up-to-N-1 nodes are down). Replication is cross-node, not full-cluster — sizing must account for data_volume × N.

VictoriaLogs (sibling)

"VictoriaLogs is open source user-friendly database for logs from VictoriaMetrics" — single binary, LogsQL query language, accepts Loki (Promtail), Elasticsearch-compatible APIs, OpenTelemetry, Syslog, Splunk, DataDog, Fluentd / Fluent Bit, Filebeat, and Telegraf. The marketing pitch is "significantly less RAM and disk space than competing solutions like Elasticsearch and Grafana Loki" with linear scaling "from Raspberry Pi to high-end servers". Pairs naturally with the metrics binary for a one-vendor logs+metrics stack.

The defining VictoriaMetrics tradeoff: you trade some Prometheus-ecosystem-native quirks (no built-in service discovery beyond what vmagent re-implements, no native alerting UI — vmalert + Alertmanager is the pattern) for a much smaller operational surface than Thanos/Cortex/Mimir at similar scale.

Common gotchas

  • -retentionPeriod is in months by default. -retentionPeriod=12 means 12 months, not 12 days. Use the d/y suffix to be explicit (-retentionPeriod=30d).
  • Cluster mode tenant URL is part of the path — but header-based tenancy is now the default too. (Corrected 2026-08-21.) POST /insert/0/prometheus/api/v1/write still addresses accountID=0 explicitly. What changed: v1.150.0 flipped -enableMultitenancyViaHeaders from false to true, so tenant-via-header is enabled out of the box and a URL with the tenant segment omitted is accepted rather than returning 404. The earlier framing — "omitting the segment returns 404, not default tenant" and "the opposite of Mimir's X-Scope-OrgID convention" — held through v1.149.x and no longer does on v1.150.0+. Set -enableMultitenancyViaHeaders=false on vmagent, vminsert and vmselect if you want the strict path-only behaviour back.
  • Security fix in the 1.148.1 / 1.149.0 window: delete_series is POST-only now. /api/v1/admin/tsdb/delete_series and /tags/delSeries previously accepted GET, which made SSRF-driven data deletion possible; they now require POST. This is both the fix and a breaking change — any script or dashboard issuing GET against those endpoints stops working. Anything still on v1.143.x or older has the GET path open.
  • The supported LTS pair rotates, so a pin decays on its own. (Re-checked 2026-08-21.) The policy is a new LTS line every 6 months with 12 months of support each, so only the latest two are ever supported. The supported pair is now v1.148.x (latest v1.148.2) and v1.136.x (latest v1.136.16); v1.122.x has fallen off — it was still listed at the May 2026 baseline of this entry and its last release is v1.122.27 (2026-07-17). Current line is v1.150.0. Don't mix tags across cluster nodes or LTS lines, and re-read the LTS page rather than trusting a pin you set six months ago.
  • vmstorage nodes are shared-nothing — they don't replicate to each other. Replication happens at write time (vminsert -replicationFactor) and at read time (vmselect -replicationFactor); both flags must agree.
  • MetricsQL behavioural differences are usually wins, but rate()/increase() integers can surprise. PromQL extrapolates, MetricsQL doesn't — a 0.97/s rate becomes exactly 1 in MetricsQL. Re-validate alerting thresholds if migrating from Prometheus.
  • -storageDataPath must outlive container restarts — mount a persistent volume; victoria-metrics-data/ in CWD survives a process restart but not a container restart.
  • NFS is supported but not recommended for hot data — listed as a feature ("NFS-based storage support") but the high-IOPS hot path benefits enormously from local SSD. NFS is best for cold/long-retention setups.
  • VictoriaLogs is a separate binary — even though it shares the brand, victoria-logs-prod runs independently with its own data path and ports. Don't expect a :8428 endpoint to also serve logs.
  • vmagent's relabel config is YAML-compatible with Prometheus, but __meta_* labels for some discovery types (Hetzner, EC2 newer fields) lag the upstream Prometheus discovery for a release or two — check the changelog after a major cloud-provider API change.
