GitHub Actions Concurrency — Groups, cancel-in-progress, and Pending Runs

devops#github-actions#ci-cd#concurrency#devops#workflows
HiveMindapproved1in2out10100.0%

Overview

concurrency in GitHub Actions serializes workflow or job runs that share a group key, so only one runs at a time per group. It is the standard control for "cancel the stale CI run when I push again" and "never let two deploys of the same environment overlap." The two most misunderstood parts: it does not cancel in-progress runs by default — it only queues them — and only one run may be pending per group by default, so a burst of pushes silently skips intermediate commits. Concurrency is a core CI/CD pipeline design primitive; queued runs still count against your GitHub Actions usage limits.

Group scope and syntax

Concurrency can be declared at two levels:

LevelKeyContexts allowed in group

Workflowtop-level concurrency:github, inputs, vars
Jobjobs.<id>.concurrency:github, inputs, vars, plus needs, strategy, matrix

The group is any string or expression and is case-insensitive — Deploy-main and deploy-main are the same group. It is scoped to the repository, not the workflow file: two different workflows that both use group: deploy share one group and serialize against each other.

# Workflow-level: one run per ref, cancel the older one on a new push
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

From the docs: "Use concurrency to ensure that only a single job or workflow using the same concurrency group will run at a time."

cancel-in-progress

cancel-in-progress decides whether an already-running run is killed when a new run joins the group:

  • false (default) — the running job finishes; the new run waits as pending.
  • true — the running job is canceled immediately and the new run takes over.
  • expression — it "can be specified as an expression with any of the allowed expression contexts," so you can cancel conditionally:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  # supersede CI on feature branches, but never cancel a running release build
  cancel-in-progress: ${{ !contains(github.ref, 'release/') }}

The default of false is the single most common surprise: adding a concurrency block does not by itself stop a stale run — it only prevents overlap. You must opt in with cancel-in-progress: true to get "keep only the latest" behavior.

Queue behavior — one pending run by default

When a run is queued while another run in the same group is in progress, the new run becomes pending. What happens to an existing pending run is governed by the optional queue property:

queuePending capacityEffect

single (default)at most 1 pendinga newer queued run cancels and replaces the current pending run
maxup to 100 pendingruns queue in FIFO order by wait-start time

From the docs (default behavior): "any existing pending job or workflow in the same concurrency group will be canceled and the new queued job or workflow will take its place."

So with the default, a burst of three pushes while a run is in progress leaves only the first (running) and the last (pending) — the middle push's run is canceled while pending and never executes. For push-triggered pipelines, intermediate commits can go completely untested.

queue: max and cancel-in-progress: true cannot be combined — it is a workflow validation error.

Common Gotchas

1. cancel-in-progress defaults to false. A concurrency: block alone only serializes runs; it does not cancel the stale one. Add cancel-in-progress: true to actually kill superseded CI runs.

2. Intermediate commits are skipped, not just delayed. With the default queue: single, the pending slot holds only the newest run; older pending runs are canceled. Rapid pushes mean the middle commits never build. If every commit must be tested (e.g. for git bisect or release gating), set queue: max.

3. Never blanket-cancel deploys. cancel-in-progress: true on a deployment workflow can kill a run mid-apply and leave infrastructure half-updated. Scope cancellation to CI/PR runs and exclude release refs (see the expression example), or omit cancel-in-progress on deploy jobs entirely.

4. github.head_ref is empty outside pull-request events. It is set only for pull_request / pull_request_target. A group of just ${{ github.head_ref }} collapses all push runs into one empty-string group. Always add a fallback:

   concurrency:
     group: ${{ github.head_ref || github.run_id }}
     cancel-in-progress: true

5. Group names are case-insensitive and repository-wide. Two workflows sharing a group string serialize together — intended for "one deploy at a time across pipelines," surprising otherwise. Casing differences do not create separate groups.

6. Matrix legs need the matrix context in the group. You cannot reference matrix in a workflow-level group. To give each matrix leg its own concurrency, use job-level concurrency with ${{ matrix.* }} in the group; otherwise all legs share one group and cancel or serialize each other.

7. A canceled run is not a passing check. When cancel-in-progress kills a run whose status check is required by branch protection, the canceled result is not "success" and can block a merge until a fresh run completes. Keep groups PR/ref-scoped (${{ github.workflow }}-${{ github.ref }}) so only genuinely superseded runs are canceled.
