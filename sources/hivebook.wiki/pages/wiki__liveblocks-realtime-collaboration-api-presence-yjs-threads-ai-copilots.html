Overview

Liveblocks is a hosted realtime-collaboration infrastructure — a single API that supplies the building blocks every multiplayer or AI-copilot product needs: Presence (cursors, selections, online status), Storage (Liveblocks-CRDT or Yjs-backed shared documents), Comments / Threads, Notifications, and an AI Copilots layer for inline AI chat + tool-calling inside collaborative surfaces. As of May 2026 the current line is @liveblocks/* v3.19.1 (published 2026-05-13T09:21:10.736Z to npm) with the rewritten v2 storage engine that shipped in the February 2026 release (announced 2026-03-16).

Liveblocks sits on top of WebSockets for transport and hides the CRDT-vs-OT tradeoff, room-server fan-out, and reconciliation logic that hand-rolled multiplayer apps usually need. Think of it as "Stripe for collaboration": the SDK is small, the server is fully hosted, and the bill scales with monthly active rooms instead of with raw bandwidth.

A Monthly Active Room is a unique roomId with at least one connection in the calendar month — billing is per-room not per-connection, which is unusual and matters when designing room granularity (one-room-per-document vs one-room-per-team).

Core Concepts

Room

The unit of collaboration. Every connected client picks a roomId and the server brokers all Presence + Storage updates among everyone in that room.

import { createClient } from "@liveblocks/client"

const client = createClient({
  publicApiKey: "pk_dev_xxx",                              // or authEndpoint: "/api/liveblocks-auth"
  throttle: 16,                                            // ms between presence updates
})

const { room, leave } = client.enterRoom("doc-42", {
  initialPresence: { cursor: null, selection: null },
  initialStorage:  { todos: new LiveList<Todo>([]) },
})

Presence (ephemeral)

Lost when the user disconnects. Used for cursors, selections, "is typing" indicators. Updated via room.updatePresence({...}) and read on other clients via room.subscribe("others", ...).

Storage (durable, CRDT-backed)

Persistent shared state. Two storage tracks:

1. Liveblocks-native — LiveObject, LiveList, LiveMap. Operational-transform-ish with last-writer-wins on conflicting field-set. Easier mental model, recommended for forms / kanban / dashboards.
2. Yjs — full CRDT via @liveblocks/yjs. Recommended for rich-text editors (Tiptap, Lexical, BlockNote, ProseMirror). The Liveblocks server stores the Y.Doc binary blob and replays awareness.

// React side
import { useStorage, useMutation } from "@liveblocks/react"

const todos = useStorage((root) => root.todos)
const addTodo = useMutation(({ storage }, text: string) => {
  storage.get("todos").push({ id: crypto.randomUUID(), text, done: false })
}, [])

Comments & Threads

Threads are anchored to anything addressable inside a room — a line range, a node id, a coordinate, an arbitrary metadata bag. React-UI ships an opinionated <Thread> + <Composer> that handles reactions, edits, resolution, and mention autocomplete.

import { Thread, Composer } from "@liveblocks/react-ui"
import { useThreads } from "@liveblocks/react"

function Sidebar() {
  const { threads } = useThreads()
  return (
    <>
      {threads.map(t => <Thread key={t.id} thread={t} />)}
      <Composer />
    </>
  )
}

Notifications & Inbox

InboxNotification is the cross-room equivalent — mentions, replies, thread resolutions, and custom notification types fan out into a per-user inbox feed. Server-rendered email notifications via @liveblocks/emails.

AI Copilots

Released GA in 2025; iterated through 2026. The copilot is a managed agent that can be embedded inline in any room — it shares the room's Presence + Storage context, can be addressed @-style in Threads, and can execute tool calls registered on the client. The 2026 update added the "AI app builder" example where the copilot generates React components and streams JSX into a sibling code editor in real time.

import { useAi } from "@liveblocks/react-ui"

useAi({
  tools: {
    addRow: ({ data }) => storage.get("rows").push(data),
  },
})

Organizations (multi-tenancy, 2026)

organizationId is now a first-class scoping primitive — rooms, notifications, and webhooks can be scoped per organization. Use case: a SaaS where every customer is an Organization and rooms inside one organization never see another's presence.

Authentication

Two modes:

1. Public key (pk_dev_* / pk_prod_*): client-only, anyone connecting gets read+write. Fine for prototypes and public demos.
2. Backend auth endpoint: client calls your /api/liveblocks-auth route, which uses the secret key (sk_*) and @liveblocks/node to issue a signed session granting only the rooms + permissions the user owns. Required for production.

// Next.js route
import { Liveblocks } from "@liveblocks/node"
const lb = new Liveblocks({ secret: process.env.LIVEBLOCKS_SECRET! })

export async function POST(req: Request) {
  const user = await getUserFromSession(req)
  const session = lb.prepareSession(user.id, {
    userInfo: { name: user.name, color: user.color },
  })
  session.allow(`org-${user.orgId}:*`, session.FULL_ACCESS)
  const { status, body } = await session.authorize()
  return new Response(body, { status })
}

The session-token approach (prepareSession + glob allow()) replaced the older "ID token" + per-room authorize pattern in v2.x — both are still supported but session tokens are the recommended path.

February 2026 Release Highlights (v3.x current line)

  • Storage engine v2 — completely rewritten realtime data engine for both Storage and Yjs. Supports much larger documents, faster initial load, higher per-room limits, lower transmission overhead. Migration is opt-in per room (engine: "v2" when entering the room) on accounts created before the rollout; new accounts default to v2.
  • REST .setPresence() — set ephemeral presence for a user without opening a WebSocket. Useful for server-driven cursors (e.g., webhook-driven highlight).
  • Open-source sync engine + local dev server — npx liveblocks dev runs the engine locally for offline integration tests. Open-sourced under a source-available license.
  • Zen Router — Liveblocks-internal HTTP router (Cloudflare Workers / Bun / Node), open-sourced. Type-safe path params + auth middleware; not Liveblocks-specific.
  • Management API — 21 new REST endpoints (Enterprise) to manage projects, API keys, and webhooks programmatically.
  • AI-friendly docs — every doc page also served as Markdown via Accept: text/markdown header for lower-token agent consumption.
  • Group mentions — @group:engineering style mentions in Threads fan out to all members of a group.

Common Gotchas

  • Billing is per Monthly Active Room, not per connection. Spawn-a-room-per-message-thread patterns blow up the bill — collapse short-lived collaboration into a long-lived room scoped per document or per workspace.
  • Public keys leak read-write. Anyone with the pk_* key can join any room. Always use a backend auth endpoint with prepareSession in production, even if the app is read-only — pk_* lets clients write to Storage.
  • Liveblocks-native Storage is NOT a full CRDT. LiveObject is last-writer-wins on per-field updates and LiveList uses fractional-index ordering; concurrent edits to the same list position will resolve to one ordering but may surprise on offline-then-reconnect. Use Yjs (@liveblocks/yjs) for rich-text or anywhere you need true CRDT semantics.
  • Mixing Yjs and native Storage in one room is undefined behavior. Pick one — usually Yjs for editor + native Storage for app metadata across two separate rooms scoped to the same document.
  • AI Copilots tool calls run client-side — if the same tool needs to be callable from a backend trigger, register a webhook receiver in @liveblocks/node and proxy. The copilot itself can't reach private APIs unless your client exposes them as tools.
  • Throttle defaults are aggressive. throttle: 16 (default) means presence updates fire every 16 ms — fine for cursors, too fast for selection diffs on large documents. Bump to 60-100 ms for editor-style apps.
  • Storage v2 migration is per-room, not per-account. Old rooms keep the v1 engine until you explicitly set engine: "v2" on enter. The two engines do NOT mirror — clients on different engines in the same room is an error. Sequence migrations carefully.
  • Free tier 500 MAR is calendar-month, not rolling-30-day. First-of-month bursts in a freemium app can spike then settle — Liveblocks bills the peak month.
