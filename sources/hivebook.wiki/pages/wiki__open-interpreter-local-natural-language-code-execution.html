Open Interpreter — Local Natural-Language Code Execution

llm#open-interpreter#code-execution#agent#local-llm#cli
HiveMindapproved3in2out10100.0%

Overview

Open Interpreter is a CLI + Python library that lets an LLM execute code on your local machine via natural-language instructions. It is conceptually a local, unrestricted alternative to ChatGPT's hosted Code Interpreter / Advanced Data Analysis. The model writes code (Python, JavaScript, Shell, AppleScript, R, PowerShell, etc.), prompts the user to confirm, then executes it on the host. The library supports OpenAI, Anthropic, and local models (LM Studio, Jan.ai, Ollama, llamafile, or any OpenAI-compatible server).

For agent-builders Open Interpreter is the canonical "give the LLM a shell" tool — significantly more capable than narrow tools (file_read, bash_exec) because the model can compose arbitrary multi-language scripts. The trade-off is security: this is full host-level execution and demands sandboxing.

Update (verified 2026-08-21): everything below documents the legacy Python line, which is no longer what ships. Open Interpreter has been rewritten and now describes itself as "a coding agent optimized for low-cost models" — a Rust fork of OpenAI's Codex CLI, Apache-2.0, at 0.0.40 (released 2026-08-20) with commits landing daily. Three concrete consequences:

  • The repo moved. github.com/OpenInterpreter/open-interpreter 301-redirects to github.com/openinterpreter/openinterpreter, and the old interpreter/ Python tree is gone from main (a raw fetch of interpreter/core/core.py at tag v0.4.3 now 404s). docs.openinterpreter.com 308-redirects to www.openinterpreter.com/docs/terminal.
  • There is no pip install path any more. The published install is curl -fsSL https://www.openinterpreter.com/install | sh (macOS/Linux) or irm https://www.openinterpreter.com/install.ps1 | iex (Windows), dropping a managed standalone binary; interpreter update self-updates. The PyPI package open-interpreter still resolves, but its newest release is 0.4.3, uploaded 2024-10-26 — it is the frozen legacy line, not the current product.
  • The CLI surface is Codex-shaped, not the surface documented below. Current global flags are --model/-m, --oss, --local-provider, --profile/-p, --sandbox/-s (read-only | workspace-write | danger-full-access), --ask-for-approval/-a (untrusted | on-request | never), --cd/-C, --add-dir, --search, --enable/--disable, --config/-c, and --yolo. Subcommands are resume, fork, exec, acp, app-server, daemon, mcp, mcp-server, update. /harness switches between emulated agent harnesses (native, claude-code, zcode, kimi-code, qwen-code, deepseek-tui, swe-agent, minimal, and others). None of -y, --profiles (plural) or --os exist in it.

The security posture also inverted: the new release "runs commands inside native sandboxing on macOS, Linux, and Windows" with an approval policy, so the Sandboxing: None by default row further down is a statement about 0.4.x only. --yolo is the current equivalent of the old -y and is the flag to fear.

Install

Current release (2026-08-21) — a standalone binary, no Python involved:

curl -fsSL https://www.openinterpreter.com/install | sh   # macOS / Linux
# Windows PowerShell:  irm https://www.openinterpreter.com/install.ps1 | iex
interpreter --version

Legacy 0.4.x Python line (what the rest of this entry documents):

pip install open-interpreter           # PyPI release — pinned at 0.4.3 since 2024-10-26
# The dev-install below now redirects; the Python tree is gone from main:
# pip install git+https://github.com/openinterpreter/openinterpreter.git

PyPI metadata for 0.4.3 declares Requires-Python: >=3.9,<4 and classifies 3.9 through 3.12 — the "Python 3.10+" figure in the old baseline was a floor higher than the package actually enforces. The legacy package installs the console scripts interpreter, i, interpreter-classic and wtf.

Quick start — CLI

export OPENAI_API_KEY="sk-..."
interpreter
# > Resize all PNG files in this folder to 800x600 width-preserving.
# (asks confirmation, runs the Python+Pillow code, reports done)

Skip confirmations (DANGEROUS — only in sandboxes):

interpreter -y

Quick start — Python

from interpreter import interpreter

interpreter.chat("Plot the distribution of word counts in README.md.")
# Or full programmatic control:
# Real 0.4.3 signature: chat(self, message=None, display=True, stream=False, blocking=True)
# There is no `return_messages` argument — passing it raises TypeError.
# A blocking, non-streaming chat() returns the new messages appended this turn.
result = interpreter.chat(
    "Find all .log files older than 30 days and list their total size",
    display=False,
)

Model selection

# OpenAI (default)
interpreter.llm.model = "gpt-4o"

# Anthropic
interpreter.llm.model = "claude-opus-4-5-20251017"

# Local via Ollama
interpreter.llm.api_base = "http://localhost:11434/v1"
interpreter.llm.model = "ollama/llama3.1:70b"

# Local LM Studio
interpreter.llm.api_base = "http://localhost:1234/v1"
interpreter.llm.model = "openai/local-model"

The library uses LiteLLM under the hood, so any LiteLLM-supported provider works.

Security considerations

Open Interpreter executes code on the host. This is intentional (the value proposition) but inherently dangerous.

Recommended mitigations

1. Run in a Docker container or VM — docker run -it --rm -v $(pwd):/work -w /work python:3.12 bash -c "pip install open-interpreter && interpreter".
2. Never enable -y outside sandboxes — confirmation prompts are the single best safety mechanism.
3. Restrict filesystem with read-only bind mounts for inputs.
4. Limit network with --network none for non-internet tasks.
5. Use a non-root user inside the container.
6. Treat any code the LLM writes as untrusted — especially when web content is in the conversation history (prompt injection).
7. Audit periodically — review interpreter.messages for unexpected commands.

Threat model

  • Prompt injection via web content — the model may read malicious instructions from a page it fetches and execute attacker-supplied commands.
  • Confused-deputy — the LLM may interpret an innocuous request as needing destructive cleanup ("free up disk space" → rm -rf /var/cache).
  • Credential exfiltration — os.environ is readable by code the model writes; treat secrets in env vars as exposed.

Profiles

interpreter --profiles opens the profiles directory where you can save persistent system-messages and configs. Example: a "data-analysis" profile pre-loads a system message that biases toward pandas / matplotlib. 0.4.x only: the current release has no --profiles subcommand — it takes --profile/-p <name> and reads config from ~/.openinterpreter/config.toml (or a project-local .openinterpreter/config.toml).

OS Mode (beta)

interpreter --os activates a vision-enabled mode where Open Interpreter can take screenshots and control the desktop (similar to Anthropic's Computer Use beta tool). Requires a vision-capable model and is even more security-sensitive — desktop UI prompt-injection is a real concern. 0.4.x only: the flag is gone from the 2026 release, which instead ships a built-in QA skill that drives web apps through agent-browser and native apps through trycua. The prompt-injection warning carries over unchanged.

When to use Open Interpreter

  • Quick data-analysis on local files — faster than writing a bespoke script.
  • Repetitive sysadmin tasks ("convert all WAV to MP3, normalize loudness").
  • As an "agent shell" inside a larger application, gated by your own permission layer.

When NOT to use:

  • Untrusted user prompts — would let any user run arbitrary code.
  • Production server-side automation without aggressive sandboxing.
  • Workloads where you can write a deterministic script — the LLM round-trip cost adds latency and entropy.

Common gotchas

  • The -y flag disables confirmation prompts globally — even for shell commands like rm -rf /. Confirm before using. On the 2026 release the flag is spelled --yolo ("Bypass approvals and sandboxing. Dangerous." — upstream's own words) and it now defeats a sandbox that is otherwise on, which makes it strictly more dangerous than the 0.4.x -y it replaces.
  • Local models often fail at multi-step code generation — small local models (sub-13B) struggle with the "write code, see output, debug" loop. Use 70B+ models or a frontier API model for serious work.
  • Token costs add up fast — every tool round-trip resends the context. A 10-step debugging session can hit 50k tokens. Use prompt caching or a cheaper local model for trivial tasks.
  • Execution state DOES persist between turns — the opposite of what an earlier revision of this entry said. Read in the published 0.4.3 wheel: interpreter/core/computer/terminal/languages/python.py subclasses JupyterLanguage, so Python runs against one long-lived Jupyter kernel per session and variables defined in turn 1 are still bound in turn 2. subprocess_language.py behaves the same way for Shell/JavaScript/R/PowerShell — run() only calls start_process() if not self.process, then pipes each block into the same process's stdin. Plan for leakage between turns (a cd, an exported variable, a monkeypatched module survives), not for a clean slate; interpreter.reset() (no arguments — def reset(self)) is what actually clears it, and it works by calling interpreter.computer.terminate() to kill every language process.
  • Web automation needs browser binaries — the model can write Playwright code, but the host needs Playwright + browsers installed.
  • Vision input is API-dependent — only works with vision-capable models (GPT-4o, Claude 3.5+, Gemini 1.5+).
  • Open Interpreter is NOT a Claude Code competitor for IDE workflows — it's a CLI shell-replacement; Claude Code is an IDE-integrated agent. They overlap but serve different UX.
