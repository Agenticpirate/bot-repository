gRPC: Core Concepts, Streaming Patterns, and When to Use It

Overview

gRPC is an open-source, high-performance RPC framework originally developed by Google. It uses HTTP/2 for transport, Protocol Buffers (protobuf) for serialization, and supports four communication patterns including bidirectional streaming. gRPC is the go-to choice for internal microservice communication where latency and throughput matter.

Four RPC Types

PatternClient SendsServer SendsUse Case

Unary1 message1 messageStandard request/response
Server Streaming1 messageStreamReal-time feeds, large result sets
Client StreamingStream1 messageFile uploads, telemetry ingestion
Bidirectional StreamingStreamStreamChat, live collaboration, gaming

Message ordering is guaranteed within an individual RPC call. The two streams in bidirectional RPCs are independent -- client and server can read and write in any order.

Proto Definition Example

syntax = "proto3";

service Greeter {
  rpc SayHello (HelloRequest) returns (HelloReply);           // Unary
  rpc SayHelloStream (HelloRequest) returns (stream HelloReply); // Server streaming
}

message HelloRequest {
  string name = 1;
}

message HelloReply {
  string message = 1;
}

The .proto file generates client stubs and server interfaces in 10+ languages (Go, Python, Java, TypeScript, Rust, C++, etc.).

Performance benchmarks vary by workload, but gRPC is typically 3-7x faster than REST for internal service-to-service calls due to binary serialization and HTTP/2 multiplexing. For a broader comparison of API styles, see GraphQL vs REST; for documenting REST endpoints, see OpenAPI.

Key Lifecycle Features

  • Deadlines/Timeouts: Client sets max wait time. Server gets DEADLINE_EXCEEDED error if exceeded. Servers can query remaining time.
  • Metadata: Key-value pairs (like HTTP headers) attached to calls. Keys are case-insensitive ASCII. The grpc- prefix is reserved.
  • Cancellation: Either side can cancel at any time. Pre-cancellation side effects are not rolled back.
  • Channels: A channel is a connection to a server on a specific host:port. Channels have states (connected, idle) and support compression settings.

Common Gotchas

  • Browser clients need grpc-web: Native gRPC requires HTTP/2, which browsers do not fully expose. Use grpc-web or an Envoy proxy.
  • Proto file versioning: Both client and server must agree on the proto. Use package versioning (v1, v2) and never reuse field numbers after deletion.
  • Large messages: Default max message size is 4 MB. Override with MaxRecvMsgSize/MaxSendMsgSize channel options.
  • Error model: gRPC uses numeric status codes (0-16), not HTTP status codes. Map them explicitly when building gRPC gateways.
  • No native JSON debugging: Protobuf is binary. Use grpcurl or Postman gRPC support for manual testing.
  • Load balancing: HTTP/2 multiplexing means one TCP connection handles many RPCs. L4 load balancers may route all traffic to one backend. Use L7 (application-level) balancing or client-side balancing.
