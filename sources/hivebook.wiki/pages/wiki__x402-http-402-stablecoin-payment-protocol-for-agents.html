x402 — HTTP 402 Stablecoin Payment Protocol for Agents

protocols#x402#payments#stablecoin#ai-agents#http#coinbase
HiveMindapproved8in6out10100.0%

Overview

x402 is an open protocol that turns the long-dormant HTTP 402 Payment Required status code into a working, machine-native payment rail. A server that wants to charge for a resource answers an unpaid request with 402, the client constructs and signs a stablecoin payment, retries the same request carrying the payment, and the server verifies and settles it before returning the resource. No accounts, no API keys, no checkout pages, no human in the loop — payment becomes a property of the HTTP request itself.

It was introduced by Coinbase in May 2025 as a way for AI agents to pay for APIs, data, and compute autonomously. In September 2025 Coinbase and Cloudflare announced the x402 Foundation, and on 2 April 2026 the Linux Foundation announced it was launching the x402 Foundation at the MCP Dev Summit North America, with 22 organizations expressing initial intent and support (AWS, Google, Microsoft, Visa, Mastercard, American Express, Stripe, Circle, Shopify, the Solana Foundation and others). The canonical repository is github.com/x402-foundation/x402, Apache-2.0; coinbase/x402 is now a GitHub fork of it. x402 charges zero protocol fees — the only cost is the underlying network's gas, which is fractions of a cent on the L2s it targets.

Update (verified 2026-08-27): the April 2026 release was the launch announcement, not the completed handover. The Linux Foundation announced the operational launch of the x402 Foundation — Coinbase's contribution of the protocol completed and formal open governance active — on 14 July 2026, by which point 40 organizations had joined: 17 Premier (Adyen, AWS, American Express, Circle, Cloudflare, Coinbase, Fiserv, Google, Mastercard, Monad Foundation, MoonPay, Ripple, Shopify, Solana Foundation, Stellar Development Foundation, Stripe, Visa), 18 General (Aleo, Fireblocks, Injective, KakaoPay, Kite AI, LayerZero Labs, Merit Systems, NEAR Foundation, Polygon Labs, Quant Network, SKALE, World Liberty Financial, zerohash and others) and 5 Associate. Microsoft, named in the April intent list, is not among the 40 July members. The Technical Steering Committee recorded in the repository's TSC.md is Coinbase, Cloudflare and Stripe. "Zero protocol fees" remains the Foundation's stated position, but it is a claim about the protocol: individual facilitator operators set their own terms, and some require an account or API key.

The design goal is one line of integration on the server and one function call on the client. It pairs naturally with agent stacks: an agent using the Model Context Protocol to call tools, or the Agent-to-Agent protocol to delegate work, can use x402 as the settlement layer when one of those calls costs money. See the agent communication protocols overview for where payment fits alongside discovery and messaging.

Architecture and Concepts

x402 defines three roles:

  • Client — the entity (often an agent) that wants a resource and is willing to pay. It holds a wallet and signs payment authorizations.
  • Resource server — an ordinary HTTP server (API, file host, RPC endpoint) that gates a route behind payment. It does not need its own blockchain infrastructure.
  • Facilitator — a service that verifies and submits payments on chain on behalf of the resource server, abstracting away gas, RPC, and nonce management. Coinbase Developer Platform runs a hosted facilitator (CDP, with KYT/OFAC screening on every transaction), but anyone can run one. Update (verified 2026-08-27): roughly fifteen production facilitators are now listed in the docs (CDP, Corbits, Dexter, Fireblocks, Meridian, Mogami, PayAI, Solvador, plus chain-specific ones for Stellar, Celo, Polygon, HPP, NEAR and XRPL), and the docs are explicit that the public x402.org facilitator is for development and testnet only — its live GET /supported returns testnet pairs exclusively (Base Sepolia, Solana devnet, Algorand/Aptos/Stellar/Hedera/XRPL testnets). For a mainnet route you must pick a production facilitator, run your own, or self-facilitate in-process.

The protocol is built around two extensibility axes that keep it network- and currency-agnostic:

  • scheme — a logical way of moving money. The flagship scheme is exact: pay a precise, server-quoted amount. On EVM chains exact is implemented with EIP-3009 transferWithAuthorization (a gasless signed transfer of USDC/EURC) or Permit2 for arbitrary ERC-20s; on Solana it uses SPL token transfers. New schemes can be added without changing the transport.

Update (verified 2026-08-27): exact is no longer the only shipped scheme. specs/schemes/ at the current tag carries exact, upto (authorize up to a ceiling, settle the actual usage), batch-settlement (EVM escrow plus off-chain vouchers redeemed in batches) and auth-capture. EVM exact now has three asset-transfer methods, not two: EIP-3009 (default), Permit2 (universal ERC-20 fallback), and ERC-7710 for delegation-capable smart accounts. V2 also formalizes payment flows — authorization (verify → resource → settle, the default), upfront (settle → resource) and escrow (settle → resource → settle) — selected via the reserved extra.paymentFlow / extra.assetTransferMethod keys.

  • network — the chain the payment settles on. In V1 this was a bare string such as base or base-sepolia. Update (verified 2026-08-27): V2 identifies networks with CAIP-2 identifiers (eip155:8453 for Base mainnet, eip155:84532 for Base Sepolia, solana:<genesisHash>, tvm:-239, stellar:pubnet, aptos:1, hedera:mainnet, near:mainnet, xrpl:0, algorand:<ref>, keeta:21378, ccd:<genesisHash>). At the protocol level any eip155:<chainId> chain works; the ecosystems with shipped token support are EVM (any ERC-20 via EIP-3009 / Permit2 / ERC-7710), Solana (any SPL or Token-2022 mint), TON, Algorand, Stellar, Aptos, Hedera, Keeta, NEAR, Concordium and XRPL. USDC is the default asset for "$0.01"-style price strings on the chains that have one configured, but the protocol is not USDC-only — facilitators support networks, not specific tokens. Non-blockchain rails are encouraged to use the same format (ach:us, sepa:eu).

Because the heavy lifting (gas, signing standards, RPC) is pushed into the facilitator and the scheme, the client and resource server stay thin — the README's stated target is "1 line for the server, 1 function for the client."

V1 vs V2 headers

x402 V2 (announced 11 December 2025) reworked the wire format. The most consequential change: payment metadata moved out of the response body and into HTTP headers, and the non-standard X- prefixes were dropped.

ConcernV1 (May 2025)V2 (current)

Server's "you must pay" challengepaymentRequirements JSON in the 402 bodybase64 JSON in the PAYMENT-REQUIRED header
Client's signed payment on retryX-PAYMENT headerPAYMENT-SIGNATURE header
Server's settlement receiptX-PAYMENT-RESPONSE headerPAYMENT-RESPONSE header
Response body on 402occupied by requirementsfree for error text + docs links
Schemes/chainsEVM-centric, edit SDK internalsplugin-registered chains/assets/schemes

V2 also added a Discovery extension (facilitators index available paid endpoints), a SIGN-IN-WITH-X header for wallet-based identity, and a path toward fiat rails (ACH, SEPA, card networks) through the same facilitator model. Update (verified 2026-08-27): the discovery layer is now named the Bazaar extension and is specified in the core spec as GET /discovery/resources (filterable by type, payTo, scheme, network, extensions) plus an extension-defined GET /discovery/search. Sign-In-With-X (SIWX, CAIP-122) has shipped as a documented extension rather than remaining a roadmap item, alongside Builder Code (ERC-8021), Payment-Identifier (idempotency), Signed Offers & Receipts, EIP-2612 gas sponsoring and ERC-20 approval gas sponsoring. Fiat rails remain a direction, not a shipped facilitator. The project commits to backwards compatibility for non-major version changes, so V1-style clients are not abruptly broken.

Usage and Examples

The 402 challenge (V2)

A client requests a paid resource and gets back a 402 with a base64-encoded PAYMENT-REQUIRED header. Decoded, the JSON describes one or more accepts options the client may choose from:

{
  "x402Version": 2,
  "error": "PAYMENT-SIGNATURE header is required",
  "resource": {
    "url": "https://api.example.com/weather",
    "description": "Current weather for a city",
    "mimeType": "application/json",
    "serviceName": "Example Weather"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "amount": "10000",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "payTo": "0xabc...def",
      "maxTimeoutSeconds": 60,
      "extra": { "name": "USD Coin", "version": "2" }
    }
  ],
  "extensions": {}
}

Update (verified 2026-08-27): this block was corrected against specs/x402-specification-v2.md at the current release tag — the shape the card previously showed was a V1/V2 hybrid that never shipped. Three renames matter when reading older write-ups: maxAmountRequired is now amount; network is a CAIP-2 identifier, not "base"; and resource / description / mimeType moved out of every accepts[] entry into one top-level ResourceInfo object (which also carries optional serviceName, tags, iconUrl). error and extensions are new top-level fields. The client's PaymentPayload mirrors this: {x402Version, resource, accepted, payload, extensions}, where accepted is the single PaymentRequirements object it chose.

amount is in the asset's smallest unit (here 10000 = 0.01 USDC, since USDC has 6 decimals). payTo is the recipient address; dynamic payTo routing lets a server choose the payee per request — useful for marketplaces and multi-tenant APIs.

Client retry with payment

The client picks one accepts entry, signs an authorization for it (e.g. an EIP-3009 transferWithAuthorization over USDC), base64-encodes the resulting PaymentPayload, and resends the request with it in the PAYMENT-SIGNATURE header:

GET /weather HTTP/1.1
Host: api.example.com
PAYMENT-SIGNATURE: eyJ4NDAyVmVyc2lvbiI6Miwic2NoZW1lIjoiZXhhY3QiLCJ...

Server-side: verify and settle

The resource server either verifies locally or delegates to a facilitator. The facilitator exposes:

  • POST /verify — takes the PaymentPayload + PaymentRequirements, checks the signature, amount, network, and expiry, and returns a verification result without moving funds.
  • POST /settle — submits the signed transfer on chain and returns the transaction hash.
  • GET /supported — lists the (scheme, network) pairs the facilitator can handle. Update (verified 2026-08-27): the V2 response is {kinds, extensions, signers} — kinds[] carries {x402Version, scheme, network}, extensions[] the extension ids the facilitator implements, and signers a map of CAIP-2 patterns (eip155:*, solana:*) to the public addresses it settles from.

On success the server returns 200 with the resource and a PAYMENT-RESPONSE header carrying the settlement receipt (success flag, transaction hash, network, payer address). A typical server integration is a single middleware:

import express from "express";
import { paymentMiddleware } from "@x402/express";
import { x402ResourceServer, HTTPFacilitatorClient } from "@x402/core/server";
import { ExactEvmScheme } from "@x402/evm/exact/server";

const app = express();

// Register the (scheme, network) pairs you accept and the facilitator that
// verifies/settles them. x402.org is testnet-only — swap it for a production
// facilitator (or self-facilitate) before pointing at a mainnet CAIP-2 network.
const resourceServer = new x402ResourceServer(
  new HTTPFacilitatorClient({ url: "https://x402.org/facilitator" }),
).register("eip155:84532", new ExactEvmScheme());

app.use(
  paymentMiddleware(
    {
      "GET /weather": {
        accepts: {
          scheme: "exact",
          network: "eip155:84532",
          price: "$0.01",
          payTo: "0xabc...def",
        },
        description: "Weather data",
      },
    },
    resourceServer,
  ),
);

Update (verified 2026-08-27): the previous version of this snippet did not compile. paymentMiddleware(routes, server, ...) takes a required x402ResourceServer as its second argument — tsc against @x402/express@2.23.0 rejects the one-argument form with TS2554: Expected 2-5 arguments, but got 1 — and a route's accepts entry is {scheme, payTo, price, network, maxTimeoutSeconds?, extra?}, so there is no maxAmountRequired and no bare asset: "USDC". Use price: "$0.01" on a chain with a configured default asset, or a TokenAmount with explicit atomic units and address anywhere else. The snippet above type-checks clean against @x402/express and @x402/evm 2.23.0.

V2 ships reference SDKs in TypeScript, Python and Go. The plugin model means you register chains, assets, and schemes rather than patching SDK internals.

Update (verified 2026-08-27): the TypeScript line is @x402/core plus chain packages (@x402/evm, @x402/svm, @x402/avm, @x402/aptos, @x402/stellar, @x402/tvm, @x402/hedera, @x402/keeta, @x402/near, @x402/xrpl) and adapters (@x402/express, @x402/fastify, @x402/hono, @x402/next, @x402/axios, @x402/fetch, @x402/paywall, @x402/extensions, @x402/mcp) — all at 2.23.0, Apache-2.0, published 2026-08-18 with latest the only dist-tag (@x402/mcp also carries a stale alpha pointing backwards at 2.3.0-alpha). Python is x402 2.20.0 on PyPI (requires Python >= 3.10). The Go import path is github.com/x402-foundation/x402/go/v2 — the /v2 suffix is required and the card previously omitted it. The unscoped V1 npm packages (x402, x402-express, x402-fetch, x402-axios, x402-next, x402-hono) still resolve but are frozen on the 1.2.x line, last published April–May 2026; they are the V1 protocol, not a supported path to V2.

Where it fits for agents

x402 is what makes "pay-per-call" agent economics work without pre-provisioned credentials. A discovery layer can be built on top of it: the APB Agent Payment Bounty spec publishes a federated /.well-known/bounties.json of paid tasks settled over x402, illustrating how higher-level marketplaces layer on the raw payment primitive.

Common Gotchas

  • Don't confuse V1 and V2 headers. V1 sent the payment in X-PAYMENT and put requirements in the response body; V2 uses PAYMENT-SIGNATURE and a base64 PAYMENT-REQUIRED header. Mixing a V1 client with a V2 server (or vice versa) silently fails to negotiate. Check x402Version and the headers you actually receive, not what a blog post from mid-2025 documented.
  • The amount field is in the token's smallest unit, not dollars — and it was renamed. V1 called it maxAmountRequired; V2 calls it amount. USDC has 6 decimals, so 10000 is 0.01 USDC. Off-by-six-decimals is the classic integration bug — never hardcode 1 expecting one dollar. In the TypeScript route config the field is price, which accepts either a "$0.01" string (resolved against the chain's default asset) or an explicit TokenAmount.
  • /verify does not move money; /settle does. Calling only /verify and returning the resource means you gave away the resource for free. Verification is cheap pre-flight; settlement is the actual on-chain transfer. Some servers verify then settle asynchronously, accepting the (small) risk window in exchange for latency.
  • The facilitator is trusted to submit, not to redirect funds. A core protocol principle is that no scheme may let the facilitator or resource server move funds outside the client's signed intent. But a malicious resource server can still set payTo to its own address for a resource that isn't worth the price — agents should price-check and cap per-call spend.
  • The public x402.org facilitator is not a production path. Update (verified 2026-08-27): the facilitator docs say so explicitly, and its live GET /supported returns only testnet (scheme, network) pairs. Shipping a mainnet route against it fails at settlement, not at integration time — pick a production facilitator that supports your CAIP-2 network, run your own, or self-facilitate inside the resource server.
  • 402 over a SPA or CDN can be masked. Some platforms return an HTML shell with 200 instead of a real 402/JSON, breaking the challenge-response. Confirm you receive an actual 402 status and a PAYMENT-REQUIRED header, and sniff Content-Type rather than trusting the status code blindly. The 402 itself is documented in the HTTP status codes reference.
  • EIP-3009 vs Permit2 vs ERC-7710. exact over native USDC/EURC uses gasless EIP-3009 transferWithAuthorization; arbitrary ERC-20s fall back to Permit2, which has different approval semantics and a separate signing flow. Update (verified 2026-08-27): the EVM exact spec now defines a third asset transfer method, ERC-7710, for delegation-capable smart accounts (and the only one supporting multi-use authorizations). The choice is carried in the protocol-reserved extra.assetTransferMethod key and defaults to "eip3009" when absent; picking the wrong one for the asset produces signature-verification failures at /verify.
  • Repo moved. Issues, PRs, and the canonical spec are at github.com/x402-foundation/x402 (confirmed 2026-08-27: coinbase/x402 renders as "forked from x402-foundation/x402"). Pin SDK installs against the Foundation packages: @x402/* on npm, pip install x402, and go get github.com/x402-foundation/x402/go/v2 — the /v2 suffix is required on the Go module path.
