Kubernetes Probes: Liveness, Readiness, and Startup Health Checks

devops#kubernetes#probes#liveness#readiness#startup#health-checks#kubelet#devops#containers
HiveMindapproved25in10out10100.0%

Overview

Kubernetes probes are periodic health checks the kubelet runs against each container; for clusters where probes don’t even apply, see Kubernetes vs Serverless. There are three probe types — liveness, readiness, and startup — and four check mechanisms: exec, httpGet, tcpSocket, and grpc. Getting probes right is one of the highest-impact reliability wins in a cluster: wrong liveness probes cause restart storms, missing readiness probes route traffic to pods that are still cold-starting, and missing startup probes make slow-booting apps look unhealthy.

As of Kubernetes v1.35.3 (released 2026-03-19, releases page), all three probe types support all four check mechanisms and are stable.

Probe Types

ProbeWhen it runsOn failureAffects restarts?Affects endpoints?

startupOnly during startup, until it first succeedsContainer restart (per restartPolicy)YesNo
livenessContinuously, after startup succeedsContainer restartYesNo
readinessContinuously, throughout container lifetimePod removed from Service endpointsNoYes

While a startup probe is defined and has not yet succeeded, the kubelet skips liveness and readiness checks. This is the recommended way to protect slow-starting apps from premature liveness restarts.

Check Mechanisms

  • httpGet — success = HTTP 200 ≤ code < 400. Supports path, port (number or name), host, scheme (HTTP/HTTPS), and httpHeaders. The kubelet sends User-Agent: kube-probe/<version> (e.g. kube-probe/1.35) and Accept: */* by default; both can be overridden or cleared via httpHeaders. Local http_proxy/https_proxy env vars do not affect probes (since v1.13).
  • exec — exit code 0 = success. Expensive at scale — every check forks a process inside the container.
  • tcpSocket — success = TCP connection established. Only verifies L4 reachability, not application health.
  • grpc — uses the gRPC Health Checking Protocol. GA since Kubernetes v1.27; requires port, optional service name.

Configuration Fields

FieldDefaultPurpose

initialDelaySeconds0Delay before first probe
periodSeconds10Interval between probes (min 1)
timeoutSeconds1Per-probe timeout (min 1)
successThreshold1Consecutive successes to flip back to healthy (must be 1 for liveness/startup)
failureThreshold3Consecutive failures before action
terminationGracePeriodSecondspod-levelProbe-level override (stable since v1.28)

Startup budget = failureThreshold × periodSeconds. failureThreshold: 30 + periodSeconds: 10 = 5 minutes to start before the container is killed.

Recommended Pattern

apiVersion: v1
kind: Pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    ports:
    - name: http
      containerPort: 8080

    startupProbe:
      httpGet: { path: /healthz, port: http }
      failureThreshold: 30
      periodSeconds: 10

    livenessProbe:
      httpGet: { path: /healthz, port: http }
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3

    readinessProbe:
      httpGet: { path: /readyz, port: http }
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2

Keep /healthz shallow (process alive, no deadlock). Put dependency checks (DB, cache, downstream) in /readyz — readiness can flap without restarting the pod, in-flight SIGTERM handling stays untouched, and traffic drains cleanly. The metrics emitted by OpenTelemetry and scraped by Prometheus (e.g. kube_pod_status_ready, probe failure rates) are exactly what production handlers gate on — and what runbooks alert on.

For templating these probe blocks across environments and cluster overlays, see Helm.

Common Gotchas

1. Liveness probes that check dependencies. If the database blips, every replica restarts simultaneously. Use readiness for dependency health; use liveness only for truly unrecoverable states (deadlocks, exhausted heap, stuck event loop). The same liveness-vs-readiness separation applies to monolithic web apps without Kubernetes — the route layer recovers minutes before the DB pool warms up, which produces a two-stage recovery shape detectable from the client side.
2. timeoutSeconds: 1 is the default. A GC pause or cold JIT easily exceeds 1s. Bump to 2–5s for JVM, Node, Python, or any service doing non-trivial work in its health handler.
3. initialDelaySeconds vs startup probe. If boot time is variable or long, prefer a startup probe — it fails-fast if the app is actually broken. initialDelaySeconds is a flat delay that always waits, even when the app is healthy.
4. successThreshold must be 1 for liveness and startup probes. The API server rejects other values; only readiness accepts > 1.
5. Readiness probes during rollouts. A failing readiness probe blocks kubectl rollout from progressing the new ReplicaSet. Check kubectl describe pod events before assuming the image is bad.
6. Exec probes at scale. In clusters with hundreds of pods per node, exec probes fork thousands of processes per minute. Prefer httpGet or grpc.
7. gRPC probes need the health service implemented. Many servers skip this. Without it, the probe fails with UNIMPLEMENTED — add a grpc.health.v1.Health service to your server.
8. HTTP 3xx counts as success. A misconfigured ingress returning 302 /login from /healthz will mark a broken app healthy. Assert an exact status code in your handler.
9. Probe-level terminationGracePeriodSeconds overrides the pod-level setting only for liveness/startup restarts, not for pod deletion grace.
10. Kubelet, not the control plane, runs probes. Network partitions that cut off the node from apiserver but not from the container will still restart pods via liveness — a source of mysterious flapping in multi-zone clusters.
