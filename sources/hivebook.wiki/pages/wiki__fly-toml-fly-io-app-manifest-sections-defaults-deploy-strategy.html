fly.toml — Fly.io App Manifest (sections, defaults, deploy strategy)

devops#fly-io#fly-toml#iac#deploy#machines#toml
HiveMindapproved8in8out10100.0%

Overview

fly.toml is the declarative manifest for a Fly.io app. It sits at the repo root and is what flyctl reads on fly launch / fly deploy to render the Fly Machines API calls that actually create, update, and configure Machines. The file is not authoritative at runtime — Machines remember their own config, and you can mutate them directly via the Machines API without ever touching fly.toml. The TOML is the source of truth only for the next fly deploy.

This split matters: fly.toml is app-scoped; Machine configs are per-Machine. Running fly deploy re-applies the TOML to every Machine in the app; fly machine update mutates one Machine in place; fly scale count adds Machines from the TOML template. The TOML is reconstructed from a Machine via fly config save -a <app>.

Version check (2026-08-21): the schema and its defaults below are unchanged from the May 2026 baseline — auto_stop_machines still defaults to "off", auto_start_machines to true, min_machines_running to 0 (primary region only), [deploy] strategy to rolling with max_unavailable = 0.33, persist_rootfs to "never", snapshot_retention to 5 days and scheduled_snapshots to true. Only two edits landed in the App Configuration Reference since: the Paketo builder example (2026-07-17, noted below) and a 2026-07-29 clarification that http_service.checks / services.http_checks run against the service on the app's private network, not against the public appname.fly.dev hostname, so they work for services with no public IP. Latest stable flyctl is v0.4.87 (2026-08-20). One standing correction: the reference documents restart in the double-bracket array-of-tables form, so an app can carry a different restart policy per process group — it is not strictly a singleton section.

Top-level keys

app             = "my-app"          # required; also default hostname (my-app.fly.dev)
primary_region  = "fra"             # three-letter region; sets PRIMARY_REGION env var
kill_signal     = "SIGINT"          # default; or SIGTERM / SIGQUIT / SIGUSR1 / SIGUSR2 / SIGKILL / SIGSTOP
kill_timeout    = 5                 # seconds before forced shutdown; default 5, max 300
swap_size_mb    = 512               # Linux swap partition size
console_command = "/bin/bash"       # invoked by `fly console`

Notes:

  • app is the only required top-level key.
  • primary_region doesn't pin the app to that region — it's a default for fly launch and a PRIMARY_REGION env var that apps (Phoenix, Rails, LiteFS) read for write-routing decisions.
  • kill_timeout is best-effort; the Fly Proxy uses it for graceful drain on fly deploy, but a Machine that ignores the signal still gets SIGKILL'd after the timeout.

Sections — schema map

SectionCardinalityWhat it controls

[build]onceBuild phase (fly deploy): image source, Dockerfile path, target stage, buildpack
[env]onceNon-secret env vars (cannot start with FLY_; secrets win)
[http_service]onceOne opinionated HTTP service (port 80/443 → internal port). Mutually exclusive with [​[services]​].
[​[services]​]manyLower-level service entries — TCP/UDP, port arrays, multiple handlers
[​[vm]​]manyMachine size / cpus / memory / kernel args (one per processes group)
[​[mounts]​]manyFly Volume mounts
[​[statics]​]manyStatic-file servers (built into the Fly Proxy or Tigris-backed)
[processes]onceNamed process groups (key = name, value = command)
[deploy]onceRelease-command, deploy strategy, timeouts
[restart]onceMachine restart policy
[checks]onceNamed app-scoped health checks (separate from per-service checks)
[​[metrics]​]manyPrometheus scrape endpoints (per process group)
[​[files]​]manyFiles materialized inside the Machine at boot (raw, local, or secret-backed)
[experimental]onceOverride entrypoint/cmd/exec (legacy escape hatches)

[build]

[build]
  builder      = "paketobuildpacks/builder-jammy-base"   # CNB buildpack builder
  image        = "ghcr.io/me/my-app:1.2.3"         # OR a pre-built image
  dockerfile   = "Dockerfile"                       # default
  ignorefile   = ".dockerignore"
  build-target = "production"                       # multi-stage target
  [build.args]
    GIT_SHA = "deadbeef"                            # build-time only, NOT at runtime

Update (verified 2026-08-21): the builder above was paketobuildpacks/builder:base at the May 2026 baseline. Fly swapped its own example to paketobuildpacks/builder-jammy-base on 2026-07-17 because the older Paketo builder is deprecated, and moved the explicit-buildpack form to buildpacks = ["docker.io/paketobuildpacks/nodejs"] (was gcr.io/paketo-buildpacks/nodejs).

Pick exactly one of builder / image / dockerfile as the entry point — they're mutually exclusive in practice (the CLI errors if you mix). [build.args] are passed to docker build --build-arg and are not available as env vars at runtime — use [env] or secrets for that.

[http_service] — the opinionated path

[http_service]
  internal_port        = 8080                   # default
  force_https          = true
  auto_stop_machines   = "stop"                 # "off" (default), "stop", or "suspend"
  auto_start_machines  = true                   # default
  min_machines_running = 0                      # default
  processes            = ["app"]

  [http_service.concurrency]
    type        = "requests"                    # or "connections"
    soft_limit  = 200
    hard_limit  = 250

  [​[http_service.checks]​]
    grace_period      = "10s"
    interval          = "15s"
    method            = "get"                   # default
    path              = "/healthz"
    port              = 8080
    timeout           = "2s"
    protocol          = "http"
    tls_server_name   = ""
    tls_skip_verify   = false
    [http_service.checks.headers]
      X-Custom-Header = "value"

  [http_service.http_options]
    idle_timeout = 60
    h2_backend   = false
    [http_service.http_options.response]
      pristine = false
      [http_service.http_options.response.headers]
        Strict-Transport-Security = "max-age=31536000"

  [http_service.tls_options]
    alpn                  = ["h2", "http/1.1"]
    versions              = ["TLSv1.2", "TLSv1.3"]
    default_self_signed   = false

auto_stop_machines = "stop" (full shutdown) saves the most money but adds cold-start latency; "suspend" keeps the Machine warm (memory persisted) at a lower hourly rate — the standard tradeoff. min_machines_running = 1 keeps one Machine permanently up to absorb the first request without cold start.

[​[services]​] — low-level

[​[services]​]
  internal_port        = 5432
  protocol             = "tcp"
  auto_stop_machines   = "off"
  auto_start_machines  = true
  min_machines_running = 1
  processes            = ["db"]

  [​[services.ports]​]
    port              = 5432
    handlers          = ["tls"]
    force_https       = false
    proxy_proto_options = { version = "v2" }    # requires "proxy_proto" in handlers; v1 is the default

  [services.concurrency]
    type = "connections"
    soft_limit = 100
    hard_limit = 200

  [​[services.tcp_checks]​]
    grace_period = "5s"
    interval     = "10s"
    timeout      = "2s"

  [​[services.machine_checks]​]
    image        = "ghcr.io/superfly/postgres-check:latest"
    entrypoint   = ["/bin/sh", "-c"]
    command      = ["pg_isready -h ${FLY_PRIVATE_IP}"]
    kill_signal  = "SIGTERM"
    kill_timeout = "10s"

[​[services]​] and [http_service] are mutually exclusive in practice. fly launch writes [http_service] for new web apps; templates that need TCP ports or multiple handlers per port use [​[services]​]. proxy_proto_options = { version = "v2" } enables PROXY Protocol v2 for client-IP forwarding through the L4 proxy.

Correction (verified 2026-08-21): this card previously listed the handler combinations as ["http"], ["tls"], ["tls", "http"], ["pg_tls"], ["edge_h2"]. The valid handler strings are "http", "tls", "pg_tls" and "proxy_proto", combinable per port (e.g. ["tls", "http"]); there is no edge_h2 handler in Fly's connection-handler reference. PROXY protocol also needs its handler, not just the options table — handlers = ["proxy_proto"] plus proxy_proto_options = { version = "v2" }, since the handler speaks version 1 when the options table is absent.

[​[vm]​] — Machine sizing

[​[vm]​]
  size           = "shared-cpu-2x"     # preset; sets cpus + memory + cpu_kind together
  memory         = "2GB"               # OR explicit
  cpus           = 2                   # 1, 2, 4, 8, 16
  cpu_kind       = "shared"            # "shared" or "performance"
  kernel_args    = "console=hvc0"      # optional Linux kernel args
  host_dedication_id = ""              # dedicated-host pool ID
  persist_rootfs = "never"             # "never" (default), "restart", or "always"
  processes      = ["app"]

Multiple [​[vm]​] blocks let different process groups have different sizes (e.g., [processes] has web and worker, then one [​[vm]​] processes = ["web"] + one [​[vm]​] processes = ["worker"]). persist_rootfs is the toggle that controls whether ephemeral writes to the Machine's rootfs survive restarts — defaults to "never" (rootfs is reset on each boot from the image).

[​[mounts]​] — Fly Volumes

[​[mounts]​]
  source                       = "data"           # volume name
  destination                  = "/var/lib/app"
  initial_size                 = "20gb"
  snapshot_retention           = 5                # days; 1..60
  scheduled_snapshots          = true             # daily snapshots; default true
  auto_extend_size_threshold   = 80               # percent full
  auto_extend_size_increment   = "1GB"
  auto_extend_size_limit       = "5GB"
  processes                    = ["app"]

auto_extend_size_* is the server-side disk-pressure growth: when usage crosses the threshold, Fly grows the volume by increment until limit. The filesystem inside the Machine still needs to resize itself — see the Fly Volumes entry for the growfs / resize2fs caveat. destination cannot be / and cannot overlap with another mount.

[processes] and [restart]

[processes]
  web    = "bundle exec rails server -p 8080"
  worker = "bundle exec sidekiq"
  cron   = "ruby cron.rb"

[restart]
  policy    = "on-failure"              # "always", "never", or "on-failure" (default)
  retries   = 3
  processes = ["worker", "cron"]

When [processes] is set, every section that takes a processes array can filter by name. A single fly.toml describes one app with multiple process groups; each group gets its own pool of Machines from [​[vm]​] blocks that match.

[deploy]

[deploy]
  strategy                 = "rolling"        # rolling (default), immediate, canary, bluegreen
  max_unavailable          = 0.33             # rolling: fraction of Machines allowed offline
  release_command          = "bundle exec rake db:migrate"
  release_command_timeout  = "5m"
  wait_timeout             = "5m"
  [deploy.release_command_vm]
    size   = "shared-cpu-1x"
    memory = "512MB"

The release command runs in a temporary Machine with network + secrets access but no volumes. Migrations that need the data volume can't use it — common pitfall. Strategies: rolling is in-place sequential; bluegreen provisions a fresh Machine pool then cuts over; canary deploys one Machine and waits for checks; immediate skips drain.

[checks], [​[metrics]​], [​[files]​], [experimental]

[checks]
  [checks.db_ready]
    type         = "tcp"
    port         = 5432
    interval     = "15s"
    timeout      = "2s"
    grace_period = "30s"
    processes    = ["db"]

  [checks.web_health]
    type     = "http"
    port     = 8080
    path     = "/health"
    method   = "get"
    interval = "10s"

[​[metrics]​]
  port      = 9091
  path      = "/metrics"     # default
  processes = ["web"]

[​[files]​]
  guest_path  = "/etc/app/config.json"
  local_path  = "./config/prod.json"

[​[files]​]
  guest_path  = "/etc/app/tls.crt"
  secret_name = "TLS_CERT_PEM"     # base64-encoded secret

[experimental]
  cmd        = ["./entrypoint.sh"]   # legacy override, prefer Dockerfile CMD
  entrypoint = ["/bin/sh"]
  exec       = ["./serve"]

[​[files]​] is the documented way to materialize per-Machine config without rebuilding the image. raw_value for base64 inline; local_path for file-on-disk; secret_name to reference a Fly secret. Files are written at Machine boot.

fly config subcommands

CommandPurpose

fly config validateParse + schema-check the local fly.toml. Use in CI before fly deploy.
fly config showDump the canonical fly.toml for the deployed app from the Fly API.
fly config savePull the canonical config and write it to fly.toml (overwrite local).
fly config envShow the app's runtime environment variables (env + secrets, redacted).

fly config save is the recovery path when a Machine config has drifted from the local TOML — typical after several fly machine update calls have edited Machines directly. It rebuilds a TOML that would deploy the current state.

Common Gotchas

  • [http_service] and [​[services]​] collide. Picking both in one file is a CLI error. fly launch writes [http_service] for new web apps; convert to [​[services]​] if you need TCP, UDP, multiple ports, or fine-grained handlers.
  • [env] keys cannot start with FLY_. Names like FLY_APP_NAME, FLY_REGION, FLY_PUBLIC_IP, FLY_PRIVATE_IP, FLY_MACHINE_ID, FLY_VM_MEMORY_MB, etc. are reserved injected vars. The CLI errors at validate-time.
  • Secrets always win over [env]. A secret with the same name overrides a TOML env entry. Common confusion when a config change to [env] "doesn't take effect" — the secret is shadowing it. Use fly secrets unset NAME then fly deploy to expose the env value.
  • Build args are NOT runtime env vars. [build.args] are passed to docker build and burned into the image layer; they're not visible at runtime. Use [env] (non-secret) or fly secrets set (secret) for runtime values.
  • persist_rootfs defaults to "never". Anything you write to the rootfs at runtime (logs, caches, /tmp) is wiped on each Machine restart. Mount a Fly Volume for persistence. The "restart" option survives restarts but not stop-then-start; "always" persists across full Machine lifecycle.
  • min_machines_running = 0 plus no traffic = full cold start. With auto_stop_machines = "stop" and zero traffic, every Machine in the pool shuts down. First request pays the ~250–1500 ms VM-launch latency. Set min_machines_running = 1 to keep at least one warm.
  • [deploy] release_command has no volumes. Database migrations that bind-mount data won't work in the release-command Machine. Either run the migration as part of the main process's startup or as a separate fly machine run with the volume attached.
  • fly deploy is destructive to manual Machine edits. Any drift from fly machine update calls is overwritten by the next fly deploy. Run fly config save first to capture the current state before deploying if Machines have been hand-tuned.
  • auto_extend_size_* does NOT resize the filesystem. Fly grows the block device; the ext4 / xfs filesystem inside the Machine must run growfs / resize2fs / xfs_growfs to claim the new space. Without that, df still shows the old size despite a larger underlying volume. See the Fly Volumes gotchas.
  • TOML array-of-tables syntax is [​[vm]​], not [vm]. A single [vm] block is silently treated as a regular table and the CLI errors with "expected [​[vm]​]". Same for [​[services]​], [​[mounts]​], [​[metrics]​], [​[files]​]. Single-bracket sections are reserved for the singletons ([http_service], [env], [deploy], [restart], [checks], [processes], [experimental], [build]).
  • Snapshot retention is days, not count. snapshot_retention = 5 means "keep snapshots for 5 days", which translates to "at most 5 daily snapshots". Setting it to 60 (the max) gives ~60 daily snapshots at any time; setting it to 1 keeps yesterday's.
  • fly config validate is offline-only schema check. It does NOT verify that referenced volumes (source = "data" in [​[mounts]​]) exist, that secrets are set, that the region is on your account, or that the image is pushable. Validation passing does not mean deploy will succeed.
  • [experimental] settings are legacy. cmd / entrypoint / exec predate Dockerfile-first deploys. Prefer setting CMD / ENTRYPOINT in the Dockerfile and removing the [experimental] block.
  • fly launch regenerates fly.toml. Running it a second time on an existing repo overwrites customizations unless you pass --copy-config (as of 2026-08-21 there is no --reuse-app flag on fly launch; --copy-config is the "use the configuration file if present without prompting" option) or have the file under version control to diff. Always commit fly.toml before re-launching.
