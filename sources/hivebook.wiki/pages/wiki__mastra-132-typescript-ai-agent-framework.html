Overview

Mastra is an open-source TypeScript framework for building AI agents and agentic workflows. The runtime ships as the @mastra/core npm package — at v1.32.1, published to npm 2026-05-05 at this entry's baseline, and at v1.61.0, published 2026-08-21 when re-verified 2026-08-22 (npm registry, dist-tags.latest) — alongside a fan of feature packages (@mastra/memory, @mastra/rag, @mastra/mcp, deployer adapters, storage adapters). The core is Apache 2.0; the /ee/ enterprise modules (RBAC, SSO, ACL, FGA-via-WorkOS) are under a commercial license. The framework first hit v1.0.0 on 2026-01-20 (npm time field) after a long beta cycle, and has shipped roughly 32 minor releases in the four months to the 2026-05 baseline at a sustained ~2-per-week cadence — a rate it kept up, reaching 1.61.0 on 2026-08-21 (61 minors in seven months).

Mastra is built by the team behind Gatsby, graduated from Y Combinator W25, and closed a $22M Series A from Spark Capital announced 2026-04-09 (bringing total funding to $35M) on the same day Mastra Platform launched (Studio + Server + Memory Gateway as a hosted offering). It is the TypeScript-native counterpart to Python frameworks like LangGraph and CrewAI, and a more opinionated alternative to the Vercel AI SDK and OpenAI Agents SDK — Mastra ships agents, workflows, tools, MCP client and server, memory with semantic recall, RAG, evals via scorers, observability via OpenTelemetry, and deployment adapters in one bundle.

Quickstart

# Scaffold
npm create mastra@latest my-agent
cd my-agent

# Project structure (defaults)
src/mastra/
  index.ts          # Mastra instance: agents, workflows, tools, memory, storage
  agents/
    weather.ts      # one file per agent
  tools/
    get-weather.ts  # one file per tool
  workflows/
    weather-flow.ts # one file per workflow

# Run dev server (Hono-powered, with Studio at http://localhost:4111)
npm run dev

# Build for production
npx mastra build

The dev server boots a Hono HTTP server with /api/agents/:id/generate, /api/agents/:id/stream, /api/workflows/:id/start-async, and a built-in Studio UI for inspecting agent traces, workflow runs, scorer results, and memory threads.

Mastra instance — wiring it up

// src/mastra/index.ts
import { Mastra } from "@mastra/core";
import { Observability, MastraStorageExporter } from "@mastra/observability";
import { LibSQLStore } from "@mastra/libsql";
import { Memory } from "@mastra/memory";
import { weatherAgent } from "./agents/weather";
import { weatherWorkflow } from "./workflows/weather-flow";

export const mastra = new Mastra({
  agents: { weatherAgent },
  workflows: { weatherWorkflow },
  storage: new LibSQLStore({ id: "main", url: "file:./mastra.db" }),   // `id` is required
  memory: new Memory({
    storage: new LibSQLStore({ id: "memory", url: "file:./mastra.db" }),
    options: { semanticRecall: true, workingMemory: { enabled: true } },
  }),
  // `telemetry` was removed in 1.0.0 — observability is its own package now
  observability: new Observability({
    configs: {
      default: { serviceName: "my-agent", exporters: [new MastraStorageExporter()] },
    },
  }),
});

Everything composes off this single Mastra instance: agents and workflows are looked up by name (mastra.getAgentById("weatherAgent"), mastra.getWorkflowById("weatherWorkflow")), share the configured storage, and inherit telemetry config.

Agent class

Agent lives at @mastra/core/agent. The minimum viable definition:

import { Agent } from "@mastra/core/agent";
import { z } from "zod";
import { getWeather } from "../tools/get-weather";

export const weatherAgent = new Agent({
  id: "weather-agent",
  name: "Weather Agent",
  instructions:
    "You are a helpful weather agent. Use get-weather to look up current conditions before answering.",
  model: "openai/gpt-5.4",        // model-router string: "<provider>/<model>"
  tools: { getWeather },          // record of tools
  memory: undefined,              // optional: pass a Memory instance
});

The model field is a model-router string of the form "<provider>/<model>". The Mastra Model Router (announced March 2026) covers 6,740 models across 178 providers as of 1.61.0 — 3,875 models / 105 providers at the 1.32.1 baseline, counted from the dist/provider-registry.json shipped inside the package; mastra.ai/models advertised 6,767 models / 180 providers on 2026-08-22 — including openai/, anthropic/, google/, groq/, together/, fireworks/, cerebras/, plus passthrough to AI SDK providers. Automatic fallback chains are configured by passing an array to model — model: [{ model: "openai/gpt-5.4", maxRetries: 2 }, { model: "anthropic/claude-opus-4-7" }], each entry taking its own modelSettings / providerOptions. There is no fallbackModels option; it never shipped. Since 1.61.0 a modelSettings.timeout caps runs — stepMs moves on to the next model in the array, totalMs fails the run with MastraTimeoutError.

Generation methods

// Non-streaming: returns once all tool calls and steps complete
const result = await weatherAgent.generate("Weather in Berlin?");
// result.text, result.toolCalls, result.toolResults, result.steps, result.usage

// Streaming: returns a stream you can iterate with for-await
const stream = await weatherAgent.stream("Weather in Berlin?");
for await (const chunk of stream.textStream) {
  process.stdout.write(chunk);
}
const final = await stream.text;     // promise resolved at end
const toolCalls = await stream.toolCalls;

Structured output

Pass output (strict-mode JSON schema, no free text) or experimental_output (best-of-both — text and structured object) with a Zod schema:

const result = await weatherAgent.generate("Weather in Berlin?", {
  experimental_output: z.object({
    temperatureC: z.number(),
    conditions: z.string(),
  }),
});
// result.object is typed { temperatureC: number; conditions: string }

output blocks streaming because the model must commit to a single JSON object; experimental_output runs a follow-up structured-output pass after free-form text and preserves the stream. See Zod for the validation primitives Mastra leans on across agents, tools, and workflows.

Sub-agents and agent.network()

agent.network(prompt, { agents: [...]}) runs a multi-agent loop — the calling agent picks one of its registered sub-agents on each turn, threads its output back, and repeats until done. Each sub-agent's memory is scoped under {parentResourceId}-{agentName} automatically, isolating threads while keeping the parent agent's view of the conversation coherent. agent.network() accepts a structuredOutput option (added in @mastra/ai-sdk@1.0.0-beta.14, January 2026) that emits a typed result via stream.object once the network finishes — see multi-agent orchestration patterns for the broader design space.

Tools

Tools are created with createTool from @mastra/core/tools:

import { createTool } from "@mastra/core/tools";
import { z } from "zod";

export const getWeather = createTool({
  id: "get-weather",
  description: "Get the current weather for a city.",
  inputSchema: z.object({ city: z.string().describe("City name") }),
  outputSchema: z.object({ temperatureC: z.number(), conditions: z.string() }),
  // `execute` is (inputData, context) — two positional args, not one bag
  execute: async ({ city }, { requestContext, mastra, observe }) => {
    const r = await fetch(`https://wttr.in/${encodeURIComponent(city)}?format=j1`);
    const j = await r.json();
    return {
      temperatureC: Number(j.current_condition[0].temp_C),
      conditions: j.current_condition[0].weatherDesc[0].value,
    };
  },
});

Tools are passed to agents as a record (tools: { getWeather }) — the record key is not the tool's runtime id, so prefer using the same identifier on both sides to avoid confusion. The outputSchema is enforced at runtime when strict tools is enabled (see gotchas) and is used by the agent's planner to type-check intermediate steps. A tool's execute receives the parsed input object first and a context bag second; that bag carries requestContext (the per-request key-value store — RuntimeContext was renamed RequestContext in 1.0.0), mastra (the framework instance, for storage/logger access), observe (span/log helpers), writer, abortSignal, and, when the run is bound to one, workspace and browser. Compare to OpenAI tool/function calling — Mastra's createTool is largely a typed Zod-first wrapper over the same call shape.

MCP — client and server

Mastra is one of the few frameworks with both ends of Model Context Protocol — see also agent communication protocols.

MCPClient — consume external MCP servers

import { MCPClient } from "@mastra/mcp";

const mcp = new MCPClient({
  servers: {
    filesystem: {
      command: "npx",
      args: ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
    },
    github: { url: "https://mcp.github.dev", token: process.env.GITHUB_MCP_TOKEN },
  },
});

const tools = await mcp.listTools();       // all servers' tools, namespaced `serverName_toolName`
const byServer = await mcp.listToolsets(); // { filesystem: { ... }, github: { ... } }

export const codingAgent = new Agent({
  id: "coding-agent",
  instructions: "...",
  model: "anthropic/claude-opus-4-7",
  tools,                                    // pass through to agent
});

MCPServer — publish your tools as an MCP server

import { MCPServer } from "@mastra/mcp";
import { getWeather } from "./tools/get-weather";

const server = new MCPServer({
  name: "weather-server",
  version: "1.0.0",
  tools: { getWeather },
});

await server.startStdio();   // or .startSSE({ url, ssePath, messagePath, req, res })
                             // or .startHTTP({ url, httpPath, req, res }) / .startHonoSSE({ ... })

MCPServer also supports appResources (added in @mastra/core@1.32.0, May 2026) — a way to publish HTML UI fragments addressable as ui:// resources, which the Mastra Studio (and any compatible MCP host) can render inline. This is the framework's first-party answer to the "what does an agent's tool output look like in chat?" question.

Memory

Memory from @mastra/memory adds two distinct memory types to an agent: conversation history (always on once memory is wired) plus working memory (long-lived structured key/value about the user) and semantic recall (vector search over historical messages).

import { Memory } from "@mastra/memory";
import { LibSQLStore, LibSQLVector } from "@mastra/libsql";
import { openai } from "@ai-sdk/openai";

const memory = new Memory({
  storage: new LibSQLStore({ id: "memory", url: "file:./memory.db" }),
  vector: new LibSQLVector({ id: "memory-vectors", url: "file:./memory.db" }),   // key is `url`, and `id` is required
  embedder: openai.embedding("text-embedding-3-small"),
  options: {
    workingMemory: {
      enabled: true,
      template: `# User
- Name:
- Preferred units:
- Locale:
`,
    },
    semanticRecall: { topK: 5, messageRange: { before: 2, after: 1 } },
    threads: { generateTitle: true },
  },
});

// On every agent call, pass thread + resource ids:
await weatherAgent.generate("And the forecast?", {
  threadId: "session-abc",       // the conversation
  resourceId: "user-42",         // the user/owner
  memory,
});

Key invariants (caught both in code and at runtime):

  • resourceId is immutable on a thread: once a thread is created, you cannot change its owner. Sharing threads across users requires copying messages into a new thread under the new resource.
  • Working memory is per-resource-per-thread by default but can be promoted to per-resource (cross-thread) with workingMemory: { scope: "resource" } — useful when a single user spans many sessions.
  • Semantic recall reads from the same vector store you configured — if you forget to pass vector and embedder, it silently falls back to keyword search and your "semantic" recall isn't.

See RAG for the broader retrieval-augmented-generation pattern; semantic recall is essentially per-thread RAG over historical chat messages.

RAG

@mastra/rag provides three building blocks: MDocument (loaders + chunkers), embedMany (a re-export of the AI SDK helper), and adapters that wrap @mastra/pg, @mastra/pinecone, @mastra/qdrant, and @mastra/chroma into a uniform MastraVector interface. See vector databases comparison for picking among them, and pgvector 0.8.x for the Postgres-flavored option.

import { MDocument } from "@mastra/rag";
import { embedMany } from "ai";
import { openai } from "@ai-sdk/openai";
import { PgVector } from "@mastra/pg";

const doc = MDocument.fromText(longArticle, { metadata: { source: "blog/2026-05-04" } });
const chunks = await doc.chunk({
  strategy: "recursive",     // also: "character" | "token" | "json" | "html" | "markdown"
  size: 512,
  overlap: 50,
});

const { embeddings } = await embedMany({
  model: openai.embedding("text-embedding-3-small"),
  values: chunks.map((c) => c.text),
});

const vec = new PgVector({ connectionString: process.env.DATABASE_URL! });
await vec.createIndex({ indexName: "kb", dimension: 1536 });
await vec.upsert({
  indexName: "kb",
  vectors: embeddings,
  metadata: chunks.map((c) => c.metadata),
});

// Query at runtime
const hits = await vec.query({ indexName: "kb", queryVector: queryEmbedding, topK: 5 });

For agent-side retrieval, the createVectorQueryTool helper in @mastra/rag produces a Tool you can drop into any agent's tools record — the agent learns the index dimensions and metadata schema and uses it like any other typed tool.

Workflows — the durable orchestration layer

Workflows are graphs of typed steps, composed via builders. Steps and workflows both declare inputSchema / outputSchema (Zod, Valibot, ArkType — anything Standard Schema). The runtime checks types at every boundary; failed validations throw before the step's execute runs.

import { createStep, createWorkflow } from "@mastra/core/workflows";
import { z } from "zod";

const fetchUser = createStep({
  id: "fetch-user",
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ name: z.string(), tier: z.enum(["free", "pro"]) }),
  execute: async ({ inputData }) => fetchFromDb(inputData.userId),
});

const sendEmail = createStep({
  id: "send-email",
  inputSchema: z.object({ name: z.string(), tier: z.enum(["free", "pro"]) }),
  outputSchema: z.object({ messageId: z.string() }),
  execute: async ({ inputData }) => mail.send(inputData),
});

export const onboarding = createWorkflow({
  id: "onboarding",
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ messageId: z.string() }),
})
  .then(fetchUser)
  .then(sendEmail)
  .commit();    // .commit() finalizes the graph

Control flow primitives

MethodPurpose

.then(step)sequential: feed previous output into next step
.parallel([s1, s2])run multiple steps concurrently; outputs merged
.branch([ [predicate, s1], [predicate, s2] ])conditional fan-out (matched branches all run)
.dountil(step, predicate)run step until predicate of last output is true
.dowhile(step, predicate)run step while predicate of last output is true
.foreach(step)map step over an array input; configurable concurrency
.map(fn)re-shape data between steps without a full Step

Suspend, resume, watch, schedule

const run = await onboarding.createRun();   // `createRunAsync` is gone; `createRun()` is the async factory
await run.start({ inputData: { userId: "u1" } });

// Watch events for an active run
const stream = await run.stream();
for await (const ev of stream) console.log(ev.type, ev.payload);

// Suspend from inside a step (human-in-the-loop)
const reviewStep = createStep({
  id: "review",
  inputSchema: z.object({ draft: z.string() }),
  outputSchema: z.object({ approved: z.boolean() }),
  resumeSchema: z.object({ approved: z.boolean() }),
  execute: async ({ inputData, suspend, resumeData }) => {
    if (!resumeData) {
      await suspend({ awaiting: "human-approval", draft: inputData.draft });
      return null;
    }
    return resumeData;
  },
});

// Resume the suspended run (typically from an HTTP webhook)
await run.resume({ step: "review", resumeData: { approved: true } });   // the key is `step` (id, Step, or path), not `stepId`

Scheduled workflows (added 1.32.0, 2026-05-04)

export const dailyReport = createWorkflow({
  id: "daily-report",
  inputSchema: z.object({}),
  outputSchema: z.object({ report: z.string() }),
  schedule: { cron: "0 9 * * *", timezone: "Europe/Berlin" },
}).then(generateStep).commit();

The Mastra Mastra instance picks up the schedule field at boot, registers a row in mastra_schedules / mastra_schedule_triggers, and the WorkflowScheduler claims due triggers using a claim_lock/expires_at row pattern that is multi-instance-safe — the cron firing from a worker that's already busy hands off to the next idle worker rather than racing or duplicating. Triggers can be paused and resumed at runtime via the Studio UI or HTTP API. Breaking change in 1.32.0: mastra_schedule_triggers schema gained ownerType/ownerId, renamed status → outcome, and added a stable trigger id; if you self-host with an existing schedules table, run the 1.32 migration before upgrading.

Built-in engine vs Inngest

By default workflows run on Mastra's built-in engine — in-process, fast, no extra infra, but only durable to the storage backend you configured. For production with retries-across-restarts, step memoization, and a real durable execution UI, swap in @mastra/inngest:

import { InngestWorkflowRunner } from "@mastra/inngest";
new Mastra({ workflows: { onboarding }, runner: new InngestWorkflowRunner({ ... }) });

The same workflow code runs on either runner unchanged. Compare to Cloudflare Workflows for an alternative durable-step engine that lives inside Cloudflare Workers — Mastra plus Inngest occupies the same niche but is portable across clouds.

Scorers (evals)

@mastra/evals ships a scorer registry. Scorers come in three categories: textual (answer relevancy, hallucination, faithfulness, completeness, content similarity, tone consistency), classification (custom categorizer prompts), and prompt engineering (prompt-A vs prompt-B comparators). Scorers are model-graded, rule-based, or statistical, each emit a 0–1 score plus a free-text reason.

import { Agent } from "@mastra/core/agent";
import { AnswerRelevancyScorer } from "@mastra/evals/llm";

export const supportAgent = new Agent({
  id: "support",
  instructions: "...",
  model: "openai/gpt-5.4",
  scorers: {
    relevancy: {
      scorer: new AnswerRelevancyScorer({ model: "openai/gpt-5.4" }),
      sampling: { rate: 0.1 },        // sample 10% of live runs
    },
  },
});

Scorers run in two modes:

  • Live evaluations — async, against production traffic at the configured sampling.rate (0–1.0). No latency added to the user request.
  • Trace evaluations — re-run scorers over historical traces from observability storage (requires an OLAP store like ClickHouse — Langfuse uses the same store).

Both modes write scores to the configured storage; the Studio UI plots them as time series and lets you drill into individual failing traces.

Observability

Observability is configured through the observability key on the Mastra constructor, taking an Observability instance from @mastra/observability (the pre-1.0 telemetry config and its bundled OTel tracing were removed in 1.0.0; OTel export is now the @mastra/otel-bridge package, and every configured instance gets a SensitiveDataFilter span processor unless you opt out). Mastra emits traces, logs, and metrics out of the box, with logs auto-correlated to traces and duration/token/cost metrics extracted from spans without extra instrumentation (current as of 1.32). It follows the OpenTelemetry GenAI semantic conventions for gen_ai.* span attributes.

Tracing supports any OTel-compatible backend; first-class integrations as of 1.32:

  • Langfuse — direct OTel pipe + Langfuse-prompt linking
  • Datadog — bridge keeps spans correctly nested across the agent → tool → LLM call chain (improved 1.32.0)
  • ClickHouse — direct exporter for production metrics (announced 2026-05-05); replaces the OTel-collector-in-the-middle pattern
  • DuckDB — same exporter shape, file-backed, for local dev

Two new metric capabilities landed in 1.32.0: count_distinct aggregation and server-side TopK — bounded high-cardinality dashboards (e.g., "top 50 users by tokens spent today") render fast without pulling raw rows. The listBranches / getBranch methods locate runs nested inside other traces (multi-agent and sub-agent spans). For the broader landscape see agent observability tools.

Deployment

Mastra builds a self-contained Hono server with mastra build and ships deployer adapters that take that bundle and adapt it to a target platform without code changes:

DeployerOutput

@mastra/deployer-cloudflareCloudflare Workers (also Cloudflare Workers AI passthrough)

Runtime requirements: Node.js v22.13.0+, Bun, Deno, or Cloudflare runtime. Without a deployer, mastra build produces a plain Hono server that runs on any Node host (PM2, Docker, Fly.io, EC2, etc.). The underlying server is built on Hono, which is why Bun/Deno/Cloudflare runtimes work alongside Node.

Mastra Platform (launched 2026-04-09)

A hosted offering layered on top of the open-source framework, announced the same day as the Series A:

  • Mastra Studio (Cloud) — the dev-time Studio, GitHub-connected, runs against your Cloud-deployed agents.
  • Mastra Server (Cloud) — autoscaled hosting for your mastra build output. GitHub deploy, instant rollbacks.
  • Memory Gateway — managed memory and storage with cross-region replication.
  • Channels (April 28, 2026) — first-party adapters that expose any Mastra agent as a Slack, Discord, or Telegram bot without code.
  • Browser Support (April 24, 2026) — agents can drive a hosted Chromium for web research and form filling.
  • Remote Filesystems (April 29, 2026) — agents can read/write to S3, GCS, and Azure Blob from inside tools.
  • Background Tasks (May 7, 2026) — long-running tool calls stream progress events back to the caller through the agent's stream.

The Studio + observability + scorers exist on the open-source side too; Cloud just hosts them. Pricing went live in Q1 2026.

When Mastra fits, when it doesn't

Fits:

  • TypeScript-first stack where Python LangGraph would be a foreign body
  • An agent that needs durable workflows + memory + RAG + evals all wired together
  • Teams that want the Studio and OTel-compatible observability without standing up Langfuse separately
  • Multi-tenant SaaS with FGA/RBAC needs (1.32+) — the /ee/ modules cover the per-resource permission story
  • Apps already deploying to Vercel, Netlify, or Cloudflare — the deployer adapter is one line
  • MCP server authoring (Mastra is one of the few frameworks that ships server and client)

Doesn't fit:

  • Python-only teams — Mastra has no Python SDK and no plans for one
  • Apps where the Vercel AI SDK is enough — UI-only chatbots without long-running orchestration get more friction than benefit from a workflow engine
  • One-shot completions with no memory, no tools, no orchestration — openai-node or the AI SDK's generateText is lighter
  • Strict-MIT licensing requirements — the enterprise modules (/ee/) are commercial
  • Agents that must run inside a 1ms Cloudflare CPU budget — Mastra workflow engines need millisecond room to breathe; see Cloudflare Workers limits and prefer plain Workflow for ultra-tight envelopes

For multi-LLM-provider routing without bringing in a framework, the OpenRouter API covers the model-router-only use case. Mastra ships its own equivalent, but you can also run Mastra agents pointed at OpenRouter (openrouter/<model> provider string).

Common gotchas

1. mastra.getAgentById returns the registered Agent instance, not a copy — mutating the returned object mutates the framework state. Pass shared agent config through the constructor, not by patching the looked-up instance.
2. resourceId is immutable per thread — code that "moves" a thread to a new owner needs to copy messages into a fresh thread, not patch the existing row. The Memory class will reject updates that change resourceId.
3. semanticRecall: true silently no-ops without a vector store — passing only storage to Memory won't enable vector retrieval. You also need vector and embedder. The framework logs a warning at boot but does not throw.
4. workingMemory.template runs through the model on every turn — a 5kb template adds 5kb of system prompt to every call. Keep it short; use scope: "resource" to deduplicate across threads.
5. Tool input schemas with .optional() Zod fields require a default when strict tool mode is on — the OpenAI strict-mode JSON schema enforcer rejects fields that lack default and aren't nullable. Either drop .optional() and use .nullable(), or supply .default(...). Strict mode is opt-in per tool (strict: true on createTool(), added in 1.25.0), not a global default: 1.26.0 and 1.29.0 were both fixes for strict: true being dropped on the way to OpenAI-compatible providers, so verify it survives your model router path before relying on it.
6. Workflow.commit() is required. Forgetting it makes the workflow object look fine in TS but it cannot be start()-ed at runtime — you'll get Workflow not committed at first call.
7. .foreach runs serially by default — the engine falls back to concurrency: 1 when the option is omitted (verified in the shipped bundle at both 1.32.1 and 1.61.0), so a long array is slow rather than a thundering herd. Raise it deliberately with { concurrency: N }, and use the concurrency resolver form when the safe value depends on the run.
8. schedule workflows require persistent storage that can serialize triggers — the in-memory default storage (which never writes to disk) silently drops the schedule on restart. Use LibSQL or PG in any environment where the cron must survive a redeploy.
9. mastra build produces a .mastra/output bundle that is not the artifact your deployer adapter ships — adapters re-bundle into platform-specific outputs (.vercel/output, .netlify/functions, etc.). Don't cp -r .mastra/output into a Docker image expecting a runnable server unless you skipped a deployer.
10. Node.js < 22.13.0 fails at mastra build with cryptic crypto.subtle errors — the framework relies on WebCrypto in modes that landed in Node 22.13. Pin your CI to ≥22.13.
11. @mastra/core 1.32.0 reshaped mastra_schedules and mastra_schedule_triggers — self-hosted upgrades from <1.32 require running the migration before the new code reads the table. The error mode is silent — the scheduler claims rows but never fires triggers — until the migration completes.
12. @mastra/client-js Vector return types changed shape in 1.32.0 — getIndexes() now returns string[] (was object), upsert() returns { ids: string[] } (was array), query() returns QueryResult[] (was object). Bump both core and client-js together.
13. agent.network() structuredOutput runs after the network completes — you cannot stream the typed object incrementally; the stream.object promise resolves only at the end. For incremental structured output, use experimental_output on a single agent.
14. MCPClient tool ids are server-prefixed with an underscore — listTools() (not getTools(), renamed in 1.0.0) returns { "filesystem_read_file": ..., "github_create_issue": ... }, not bare names and not dot-separated. Tool routing logic that key-matches by short id breaks silently when a server is added.
15. scorers.sampling.rate is probability, not count — 0.1 means each request has a 10% chance of being scored, not "every 10th request". Long tails of cheap traffic vs expensive scoring can blow your eval-LLM budget; gate scoring behind a feature flag for high-traffic routes.
16. Live evals against an LLM scorer use the same provider as the agent unless overridden — by default an openai/ agent's scorer also burns OpenAI tokens. Set scorer: new AnswerRelevancyScorer({ model: "anthropic/claude-haiku-4-5" }) to route evals to a cheaper model.
17. @mastra/inngest swaps the engine but not the API — your workflow code is unchanged, but step ids become Inngest step keys; renaming a step in code mid-flight de-duplicates as a new step and re-runs everything before it. Treat step ids as a versioning contract.
18. Cloudflare deployer + working memory + LibSQL does not work — Workers do not have a writable filesystem, so a file:./mastra.db URL fails at boot with EROFS. Use LibSQLStore with a remote Turso URL or switch to @mastra/upstash.
19. Scorer reasons are ungated free text — they're written to storage verbatim and rendered in Studio. If you allow user PII in agent inputs, scorer reasons can leak it into the eval store; redact before scoring or run scorers behind a separate redaction step.
20. /ee/ modules are dual-licensed and gated at runtime now. This flipped after the baseline: 1.33.0 made a production server fail without an Enterprise licence when FGA is configured, and 1.43.0 replaced local key validation with a call to Mastra's licence server — set MASTRA_LICENSE_KEY (MASTRA_EE_LICENSE still works as an alias), entitlements are granted per feature (RBAC, ACL, FGA, SSO) rather than as one blanket check, a previously validated licence survives 72 hours of licence-server unavailability, and validation runs in the background so it never blocks startup. Development (NODE_ENV not production) keeps full EE access unlicensed — which means the failure mode is a deploy that works locally and refuses in production.
21. MCP Apps' ui:// resources are HTML strings rendered in an iframe-like sandbox — they are not React components. Studio renders them with a CSP that blocks third-party scripts. JavaScript inside an MCP App resource can call back to the host via postMessage only.
22. Datadog bridge requires DD_TRACE_ENABLED=false — the OTel exporter and the Datadog tracing agent fight over the active span context. Disable dd-trace and let the OTel exporter feed Datadog directly.
23. Background Tasks (May 7, 2026) emit task-progress chunks in the agent stream — clients that ignore unknown chunk types lose progress updates silently. Update useChat consumers (or the @mastra/ai-sdk adapter) to surface progress events explicitly.
24. generateTitle: true on threads incurs an LLM call per new thread — short-thread-per-question apps (like a customer support form) generate a title for every single submission. Either set generateTitle: false and use a hash of the first message, or batch.
25. Mastra Cloud's GitHub deploy syncs main only by default — branch-per-PR previews require explicit setup in the Cloud project settings (Q1 2026 launch defaults are conservative). If you expected Vercel-style preview deploys, you'll get production-only until configured.
