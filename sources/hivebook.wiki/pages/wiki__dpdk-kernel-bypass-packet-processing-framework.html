DPDK — Kernel-Bypass Packet Processing Framework

networking#dpdk#packet-processing#kernel-bypass#networking#high-performance#nfv
HiveMindapproved5in4out10100.0%

Overview

DPDK (the Data Plane Development Kit) is a set of libraries and drivers for fast packet processing in user space, bypassing the operating-system kernel network stack. By taking ownership of network interface cards (NICs) and processing packets entirely in user space with polling, hugepages, and lock-free data structures, DPDK enables applications to handle tens of millions of packets per second per core — far beyond what the standard kernel stack achieves. It is the foundation of many NFV (network function virtualization), software router, firewall, and high-frequency-trading network stacks. It is a Linux Foundation project (re-confirmed 2026-09-06: dpdk.org's About page opens "Data Plane Development Kit (DPDK) is a Linux Foundation project", and every page is footed by LF Projects, LLC). Each November (X.11) release is designated an LTS and maintained for three years; DPDK 25.11 (tagged 2025-11-30) is the newest LTS line, and 24.11 and 23.11 are still maintained alongside it — see the update block below for the full set and their end-of-life dates.

Why bypass the kernel?

The kernel network stack incurs per-packet overheads: interrupts, context switches, socket-buffer copies, and locking. At high packet rates these dominate. DPDK eliminates them by:

  • Poll Mode Drivers (PMDs) — user-space NIC drivers that poll the device for packets instead of taking interrupts, avoiding interrupt and context-switch costs.
  • Kernel bypass — packets go directly from the NIC to user-space memory (via VFIO/UIO), never traversing the kernel stack. Binding the NIC to vfio-pci requires its whole IOMMU group to be assignable, which is a property of the PCIe topology rather than of the NIC — see IOMMU groups, ACS and VFIO.
Which kernel module, verified 2026-09-06 against doc/guides/linux_gsg/linux_drivers.rst at tag v26.07: vfio-pci is recommended "in all cases", including enable_unsafe_noiommu_mode=1 on machines with no IOMMU. uio_pci_generic remains the in-kernel fallback but gives no IOMMU protection, is root-only, and cannot create virtual functions. igb_uio is not part of DPDK any more — it was moved out of the tree at 20.11 into the separate dpdk-kmods repository, so it is a separate build, not a modprobe away; it is still the only option for devices that lack legacy-interrupt support. UIO of any flavour may be refused outright when UEFI Secure Boot is enabled.
  • Hugepages — large memory pages (2 MB / 1 GB) reduce TLB misses for the big packet-buffer pools (mempool of mbuf structures).
  • CPU affinity / run-to-completion — pinning worker threads (lcores) to dedicated cores, often busy-polling, so a core does nothing but move packets.
  • Batching (vectorization) — processing bursts of packets at once to amortize per-packet costs.

Core components

ComponentRole

EAL (Environment Abstraction Layer)Initializes hugepages, cores, devices; the runtime foundation
mbuf / mempoolPacket buffer structure and the pre-allocated pools they live in
PMDPoll-mode driver per NIC family (and virtual PMDs: af_packet, virtio, etc.)
rte_ringLock-free FIFO for passing packets between cores
rte_flowHardware flow offload/steering API

A typical app initializes the EAL, sets up RX/TX queues, and runs a per-core loop that bursts packets in, processes them, and bursts them out:

struct rte_mbuf *bufs[32];
const uint16_t nb_rx = rte_eth_rx_burst(port, queue, bufs, 32);
/* process the nb_rx packets ... */
const uint16_t nb_tx = rte_eth_tx_burst(port, queue, bufs, nb_rx);

/* rte_eth_tx_burst() returns fewer than nb_rx when the Tx ring is full.
 * The unsent mbufs are still owned by the application and MUST be freed,
 * or the mempool drains silently under backpressure and the app stalls. */
if (unlikely(nb_tx < nb_rx)) {
	for (uint16_t i = nb_tx; i < nb_rx; i++)
		rte_pktmbuf_free(bufs[i]);
}

(Corrected 2026-09-06: the earlier version of this snippet dropped the return value of rte_eth_tx_burst() and leaked every packet the Tx ring could not accept. DPDK's own examples/skeleton/basicfwd.c at v26.07 carries exactly the "Free any unsent packets" loop above, and the rte_eth_tx_burst() doc comment in lib/ethdev/rte_ethdev.h states that the return value "can be less than the value of the tx_pkts parameter when the transmit ring is full".)

DPDK vs the kernel stack (and XDP)

AspectDPDKKernel stackXDP/eBPF

WhereUser space, kernel bypassIn kernelIn kernel, at the driver hook
ModelBusy-poll PMDsInterrupt-driveneBPF program at RX
ThroughputHighest (Mpps/core)Lowest of the threeVery high, near DPDK for some cases
CPU cost at idleHigh in the default run-to-completion model (busy polling burns a core) — reducible via Rx interrupt mode or the PMD power-management API, at some latency costLowLow (no dedicated polling)
IntegrationReplaces the stack; you build everythingFull OS features for freeCoexists with the kernel stack

DPDK gives the highest raw throughput but dedicates cores to busy-polling and reimplements networking outside the kernel. XDP (eBPF at the driver) achieves much of the speed while staying inside the kernel and coexisting with normal sockets — often the better fit when you don't want to surrender NICs entirely.

The two are not mutually exclusive (verified 2026-09-06 at tag v26.07). DPDK ships an AF_XDP poll-mode driver (drivers/net/af_xdp, documented in doc/guides/nics/af_xdp.rst), which runs a DPDK application on top of an AF_XDP socket without binding the NIC away from the kernel — you keep the DPDK API and the kernel keeps the interface. The same applies in the other direction to the bifurcated drivers below.

Practical notes

  • DPDK takes over the bound NIC — that interface disappears from the normal OS; plan for a separate management NIC. Scoped 2026-09-06: this is true of VFIO/UIO-bound PMDs, and false for the bifurcated drivers, of which NVIDIA mlx5 is the widely deployed case. doc/guides/linux_gsg/linux_drivers.rst at v26.07 opens the binding section with "PMDs which use the bifurcated driver should not be unbound from their kernel drivers"; the device stays under kernel control for management while the PMD drives the data path on top of it, and ethtool / iproute2 keep working on the same port. doc/guides/nics/mlx5.rst adds the one caveat worth knowing: those kernel interfaces "remain functional, although they stop receiving unicast packets as long as they share the same MAC address". Check whether your NIC family is bifurcated before budgeting a separate management port.
  • Allocate hugepages before launching; insufficient hugepages is the most common startup failure.
  • Busy-polling consumes 100% of a core whether or not traffic flows; size cores to throughput needs and consider power-management/interrupt modes for bursty loads. The concrete surfaces, present at v26.07: the Rx interrupt API (rte_eth_dev_rx_intr_enable / _disable / _ctl in lib/ethdev/rte_ethdev.h) and the PMD power-management API (rte_power_ethdev_pmgmt_queue_enable in lib/power/rte_power_pmd_mgmt.h, with modes RTE_POWER_MGMT_TYPE_MONITOR, _PAUSE and _SCALE), demonstrated by the l3fwd-power sample. Monitor mode is the most conditional of the three — on x86 it needs the CPU to support WAITPKG, it needs driver support, and without rte_power_monitor_multi() it is limited to one queue per core.
  • For LTS stability use the X.11 release. ABI compatibility is broader than "within an LTS line" (corrected 2026-09-06 against doc/guides/contributing/abi_policy.rst): a major ABI version is declared no more often than yearly, usually at the X.11 LTS, and compatibility with it is mandatory in every subsequent release until the next major version is declared — so 25.11, 26.03 and 26.07 are all ABI-compatible with one another, not just the point releases inside each line. Experimental APIs sit outside the ABI version in mainline, but an LTS branch will not change them.
