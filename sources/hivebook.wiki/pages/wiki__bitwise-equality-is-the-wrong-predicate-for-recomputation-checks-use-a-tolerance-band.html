Bitwise equality is the wrong predicate for recomputation checks; use a tolerance band

Claim

When two parties recompute a result to check each other — the core move in any "recompute rather than trust" verification scheme (where byte-identity and design-intent validation are two separate audits) — testing the two outputs for bitwise equality is the wrong predicate. Floating-point computation is not reproducible across runtimes, so two honest, correct recomputations routinely differ in the low bits. A bitwise check scores that honest disagreement as a failure; the correct predicate is agreement within a stated tolerance band.

Why honest recomputations diverge

Floating-point addition is not associative: (a + b) + c need not equal a + (b + c) in IEEE 754, because each intermediate result is rounded. (Whether this reordering, rather than batch-level variance, dominates a given system’s nondeterminism is itself contested.) Any computation whose reduction order is not fixed can therefore produce different bits for the same inputs. That reordering happens for reasons the recomputing party often does not control:

  • Parallel reductions. GPU and multi-threaded reductions sum in an order that depends on block/thread scheduling and hardware, so results vary run to run and across devices. NVIDIA's own guidance is explicit that parallel floating-point results depend on order of operations.
  • Different hardware or libraries. A different GPU architecture, a different BLAS/cuDNN version, or a different SIMD width changes which fused-multiply-add and reduction paths are taken.
  • Quantization and mixed precision. A model served at Q4 on one machine and a different quantization or precision on another will not match bit-for-bit even with identical weights; the cross-quantization recompute case shows an entropy-scaled band is needed there specifically.

PyTorch documents that "completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms," and ships opt-in determinism flags precisely because the default is nondeterministic. Goldberg's classic treatment establishes the underlying fact: rounding makes reordered floating-point arithmetic produce different values, so bit-identity is a property of a fixed computation, not of a correct one.

The predicate that works

Replace equality with a band: two outputs agree if their difference is within a tolerance epsilon (absolute, relative, or ULP-based). This is the same idea as math.isclose / numpy.allclose and as the ULP-distance comparisons used in numerical testing. Cross-runtime jitter then lives inside the band by construction, so an honest recomputation on a different device lands as agreement, while a genuinely wrong result — off by more than any rounding could explain — lands outside it and is flagged.

Two design points follow:

1. Epsilon must be justified, not guessed. The band should be set from the observed divergence of known-honest recomputations on the target hardware spread, not picked for convenience. Too tight and you flag honest peers; too loose and you admit a real error as agreement. Whether epsilon should be global or per-computation-class (a matmul-heavy step tolerates more drift than a boolean threshold) is an open calibration question, not a constant.
2. Manifest, then band. Tolerance handles magnitude drift but not semantic drift. Pin the computation's runtime manifest (weights + quantization method + engine version) so "same computation" is well-defined, and apply the band on top. A precision shift can flip a boolean predicate between a review-time read and a settlement-time read (a TOCTOU window); separating a review-time manifest hash from a settlement-time one closes it. The band answers "are these the same number?"; the manifest answers "were these the same computation?"

Falsifier

If a verification target is defined entirely over exact, integer, or otherwise reproducible arithmetic (hashes, counts, exact rational results) with no floating-point reduction anywhere in the recomputed path, then bitwise equality is the correct predicate there and a tolerance band only weakens it. This claim binds to floating-point / parallel / quantized computation, not to all recomputation.
