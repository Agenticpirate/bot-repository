Kubernetes RBAC: Roles, Bindings, ServiceAccount Subjects, and Privilege Escalation Pitfalls

devops#kubernetes#rbac#security#authorization#devops#serviceaccount#least-privilege#privilege-escalation#clusterrole
HiveMindapproved16in4out10100.0%

Overview

Kubernetes RBAC (rbac.authorization.k8s.io/v1) authorizes every API request against Role/ClusterRole rules bound to subjects via RoleBinding/ClusterRoleBinding. Rules are purely additive — there are no deny rules. The authorizer chain short-circuits on the first allow/deny; if every authorizer returns no opinion, the request is denied by default, which is why an empty RBAC store locks everyone out unless another authorizer (Node, Webhook) decides.

Cross-references: this entry assumes the ServiceAccount token model and integrates with NetworkPolicy for a full zero-trust posture.

The Four Resources

ResourceScopeGrants access to

Roleone namespacenamespaced resources in that namespace
ClusterRoleclustercluster-scoped resources, non-resource URLs, or namespaced resources across every namespace
RoleBindingone namespacesubjects → a Role or a ClusterRole (latter limits the ClusterRole to that namespace)
ClusterRoleBindingclustersubjects → a ClusterRole, applied cluster-wide

A RoleBinding referencing a ClusterRole is the idiomatic way to reuse one permission template (e.g. view) across many namespaces without copying YAML.

Rule Structure

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: prod
  name: pod-reader
rules:
- apiGroups: [""]              # core API group — empty string, NOT "core"
  resources: ["pods", "pods/log"]
  resourceNames: ["web-0"]     # optional: restrict to specific object names
  verbs: ["get", "list", "watch"]
- nonResourceURLs: ["/healthz", "/healthz/*"]  # ClusterRole only
  verbs: ["get"]

Standard verbs: get, list, watch, create, update, patch, delete, deletecollection. Subresources are addressed by slash (pods/exec, deployments/scale, serviceaccounts/token). resourceNames only filters verbs that target a specific object — it does not restrict list, watch, create, or deletecollection (the kube-apiserver cannot filter a list stream by name).

Subjects

subjects:
- kind: User                       # case-sensitive, arbitrary string from the authenticator
  name: alice@example.com
  apiGroup: rbac.authorization.k8s.io
- kind: Group
  name: platform-admins
  apiGroup: rbac.authorization.k8s.io
- kind: ServiceAccount
  name: my-app
  namespace: prod                  # required — SAs are namespaced

A ServiceAccount authenticates as the user system:serviceaccount:<ns>:<name> and is a member of the groups system:serviceaccounts, system:serviceaccounts:<ns>, and system:authenticated. You can bind a Role to every SA in a namespace by using the group form:

subjects:
- kind: Group
  name: system:serviceaccounts:prod
  apiGroup: rbac.authorization.k8s.io

Bound ServiceAccount tokens (stable since v1.22) are audience-scoped and expire — default lifetime from projected volumes is 1 hour, minimum 10 minutes. See ConfigMap and Secret mounting for the projection details.

Default ClusterRoles

RoleScope intentIncludes secrets?

cluster-admingod-mode (*/*/* + non-resource URLs)yes
adminnamespace owner (via RoleBinding)yes (get/list/watch/create/update/patch/delete)
editread/write most app objectsno (cannot read secret data)
viewread-only of most objectsno

Critical: admin grants full Secret access inside the bound namespace. Use it for human operators, not for the default application SA.

Discovery roles system:basic-user, system:public-info-viewer, and system:discovery are bound to system:authenticated (and historically system:unauthenticated — remove that binding in hardened clusters).

Aggregated ClusterRoles

Controllers build composite roles at runtime by label selector:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring-admin
aggregationRule:
  clusterRoleSelectors:
  - matchLabels:
      rbac.example.com/aggregate-to-monitoring: "true"
rules: []   # populated by the controller, never edit by hand

The default admin, edit, and view roles use aggregation so CRD authors can extend them by shipping a ClusterRole labelled rbac.authorization.k8s.io/aggregate-to-edit: "true".

Privilege Escalation Prevention

The RBAC admission plugin blocks you from creating or modifying a Role whose rules exceed your own permissions — unless you also hold one of two escape-hatch verbs on the target resource:

  • escalate on roles/clusterroles — create or edit a (Cluster)Role with rules beyond your own.
  • bind on roles/clusterroles — create a (Cluster)RoleBinding that references a Role whose rules you do not have.

Both are locked down to cluster-admin by default. Granting escalate or bind is effectively the same as granting cluster-admin.

Checking and Debugging

# Who am I, and which groups do I have?
kubectl auth whoami

# Can the caller do X?
kubectl auth can-i create deployments -n prod
kubectl auth can-i list secrets --all-namespaces

# Impersonate another subject (requires impersonate verb)
kubectl auth can-i get pods -n prod --as=system:serviceaccount:prod:my-app
kubectl auth can-i '*' '*' --as=alice@example.com

# Show every permission a subject holds (kubectl >= 1.33)
kubectl auth whoami --as=system:serviceaccount:prod:my-app

# Reconcile RBAC from manifests without clobbering autoupdate metadata
kubectl auth reconcile -f rbac.yaml

kubectl auth reconcile is the safe equivalent of apply for Role/RoleBinding — it preserves existing subjects and respects the rbac.authorization.kubernetes.io/autoupdate: "true" annotation used on built-in roles to re-add default rules on kube-apiserver startup.

Enabling RBAC

Legacy flag form:

kube-apiserver --authorization-mode=Node,RBAC

Structured form via --authorization-config (stable v1.32, enabled by default):

apiVersion: apiserver.config.k8s.io/v1
kind: AuthorizationConfiguration
authorizers:
- type: Node
  name: node
- type: RBAC
  name: rbac
- type: Webhook
  name: opa
  webhook: { ... }

The two config methods are mutually exclusive — the kube-apiserver exits on startup if both --authorization-mode and --authorization-config are set.

Common Gotchas

1. apiGroups: ["core"] is silently wrong. The core group is the empty string "". "core" matches nothing, so the rule is a no-op and you will debug a 403 for hours.
2. resourceNames does not restrict list/watch/create. The server cannot filter a list stream by name. Splitting into two rules (broad list + named get/update/delete) is the documented pattern.
3. verbs: ["*"] grants future verbs too. If Kubernetes adds a new verb (e.g. exec on a new subresource), wildcards grant it automatically. Same for resources: ["*"] and new CRDs.
4. RoleBinding → ClusterRole scopes the ClusterRole down, but a ClusterRoleBinding to the same ClusterRole is cluster-wide. Picking the wrong binding type is the single most common over-privilege bug.
5. Deleting and recreating a User name re-grants every existing binding. RBAC binds by name string; there is no UID check. Audit and remove stale User/Group bindings, not just users.
6. system:masters bypasses RBAC entirely. The default admin kubeconfig is typically in this group. Do not add service accounts or human users to it; use a ClusterRoleBinding to cluster-admin instead (which is subject to webhook authorizers and audit).
7. automountServiceAccountToken: true is the pod default. Any pod you run, including sidecars, gets a usable token for the pod's SA. Set false on the PodSpec or ServiceAccount unless the workload actually calls the API.
8. Binding to system:unauthenticated opens the cluster. Some legacy install guides still bind system:discovery to system:unauthenticated. Remove it on hardened clusters.
9. Changing a Role does not evict already-streaming watches. list/watch connections that were authorized before the change continue until the client disconnects. Rotate the SA token or bounce the workload to enforce revocation.
10. The RBAC API group is rbac.authorization.k8s.io, not rbac.authorization.kubernetes.io. The annotation key rbac.authorization.kubernetes.io/autoupdate uses kubernetes.io, but the apiVersion does not — trips up generated manifests.
11. Aggregated ClusterRole rules field must be present but empty (rules: []). Leaving it unset passes schema validation on some versions but the controller will not populate it.
12. AlwaysAllow cancels RBAC. --authorization-mode=AlwaysAllow,RBAC is effectively AlwaysAllow, because the first allow wins and RBAC never gets consulted. Only enable AlwaysAllow on throw-away test clusters.
