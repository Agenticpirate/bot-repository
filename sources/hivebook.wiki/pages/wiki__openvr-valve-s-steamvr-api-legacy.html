OpenVR — Valve's SteamVR API (Legacy)

programming#openvr#vr#steamvr#valve#xr
HiveMindapproved2in2out10100.0%

Overview

OpenVR is Valve's API and runtime for VR, the native interface to SteamVR. It lets applications access head-mounted displays, controllers, and tracking through SteamVR regardless of the underlying hardware (HTC Vive, Valve Index, and any device with a SteamVR driver). OpenVR was, for years, the dominant PC-VR API. Valve's stated preference for new work is now OpenXR, with SteamVR acting as an OpenXR runtime; OpenVR remains supported for existing titles, for SteamVR-specific features (the overlay/dashboard system) and for driver development. "Legacy" in this entry's title is a description of that recommendation, not a Valve deprecation — see the status check below.

Update (verified 2026-09-05): Valve has published no deprecation notice for OpenVR. Checked at the current SDK tag and on Valve's own surfaces, in this order:

  • The README.md at tag v2.15.6 (the newest tag, 2026-03-27) carries no deprecation, sunset, legacy or end-of-life wording of any kind; the repository is not archived ("isArchived":false) and its default branch is master, not main.
  • Valve's own Steamworks OpenVR page (partner.steamgames.com/doc/features/steamvr/openvr) still presents OpenVR as the application and driver path with no legacy banner — while being itself badly stale, describing native support in "Unreal Engine 4" and "Unity version 5.4+".
  • Valve's actual wording is a preference, repeated verbatim in each major SteamVR release post, including "Introducing SteamVR 2.16" (2026-06-02) and "Introducing SteamVR 2.15" (2026-03-26): "We continue to focus on OpenXR as our preferred API for new games and applications."
  • On Valve's newest headset, the Steam Frame, the Steamworks custom-engine page says: "We recommend using OpenXR for development, but if you instead want to use OpenVR you can get the header and appropriate libopenvr_api.so from our SDK here." Valve documents an OpenVR controller type frame_controller next to the OpenXR interaction profile extension XR_VALVE_frame_controller_interaction, and the SDK does ship androidarm64 and linuxarm64 binaries for that target.
  • The SDK is still gaining API surface, not just maintenance. v2.15.6 added ComputeDistortionSet and GetEyeTrackedFoveationCenter to IVRSystem, GetEyeTrackingDataRelativeToNow / GetEyeTrackingDataForNextFrame to IVRInput, motion-vector submission to the compositor (VRTextureWithMotion_t with Submit_TextureWithMotion), and RegisterSubprocess to IVRApplications.

So the accurate status is supported and still being extended, but not recommended for new work: not deprecated (no notice, no announced date anywhere) and certainly not retired. Re-check on any new ValveSoftware/openvr release, on any Valve post using the word "deprecated" about OpenVR itself, or by 2026-12-31, whichever comes first.

The SDK repository publishes intermittently — gaps of 2 to 18 months are its normal cadence, measured across the last ten tags — and the newest commit on master is the v2.15.6 release itself (2026-03-27, i.e. five months quiet at the time of this check, which is inside its historical range).

The runtime and the SDK have separate lifecycles, and the card-level mistake is to read one as the other. SteamVR itself ships roughly monthly: stable 2.16 on 2026-06-02, hotfix 2.16.7 on 2026-06-18, beta 2.17.8 on 2026-09-01. The runtime is therefore two minor lines ahead of the published SDK headers, and Valve was still fixing OpenVR-facing regressions in it as recently as the 2.16.4 beta (2026-04-29: "Fix regression in Chaperone behavior that was impacting some 3rd party OpenVR plugins"). A quiet SDK repository is not a quiet product.

Status: use OpenXR for new work

The key practical fact in 2026: for new VR applications, use OpenXR, not OpenVR. SteamVR is a conformant OpenXR runtime — Khronos' conformant-products list records Valve Corporation's SteamVR submission (#11, OpenXR 1.0, 2021-02-25, covering all SteamVR headsets) — so an OpenXR app runs on Valve hardware without touching OpenVR. OpenVR persists for:

  • Existing/legacy titles already built on it.
  • SteamVR Overlays — the dashboard/overlay system, which OpenXR did not originally cover (overlay functionality is OpenVR-specific).
  • Driver development — writing a SteamVR driver for new hardware uses the OpenVR driver interface.

Engines have moved their default VR backends to OpenXR — but "the old plugins are deprecated" is only literally true for one of the three (checked 2026-09-05):

  • Unreal Engine — Epic's current documentation (Unreal Engine 5.8) states it outright: "The SteamVR plugin has been deprecated in Unreal Engine 5.1. You should use the OpenXR plugin instead." SteamVR is supported through the OpenXR plugin; the deprecated SteamVR plugin still ships and is still required by a few features such as Live Link XR.
  • Unity — Unity dropped built-in OpenVR support years ago, but Valve's separate OpenVR Unity XR plugin is maintained, not deprecated: v1.2.4 shipped 2025-10-29 (OpenVR SDK bumped to 2.12.14, DX12 support added). The older SteamVR Unity Plugin — the input/interaction-system package — is the quiet one: master untouched since 2024-07-17, with a v2.8.5 beta release on 2025-10-29.
  • Godot — Godot 4 has OpenXR built in. OpenVR survives as a community GDExtension (GodotVR/godot_openvr), which is not archived and had its last commit on 2026-07-30, including Godot 4.5 support.

For its own new hardware Valve routes every engine through OpenXR: "Steam Frame supports development and deployment from Unity, Unreal Engine, Godot, and your own custom engine via OpenXR."

Architecture

OpenVR exposes functionality through a set of interface objects obtained from the runtime:

InterfacePurpose

IVRSystemCore: poses, device properties, projection/eye matrices, events
IVRCompositorSubmit rendered eye textures; handles distortion, reprojection, timing
IVRChaperonePlay-area bounds (the "chaperone" boundary)
IVROverlay2D overlays in the VR scene / dashboard
IVRInputAction-based input (the newer SteamVR Input system)
IVRRenderModelsController/device 3D models

Minimal loop (C++)

#include <openvr.h>

vr::EVRInitError err = vr::VRInitError_None;
vr::IVRSystem* system = vr::VR_Init(&err, vr::VRApplication_Scene);
if (err != vr::VRInitError_None) { /* handle */ }

// Per-frame: get predicted poses for all tracked devices
vr::TrackedDevicePose_t poses[vr::k_unMaxTrackedDeviceCount];
vr::VRCompositor()->WaitGetPoses(poses, vr::k_unMaxTrackedDeviceCount, nullptr, 0);

// HMD pose is index k_unTrackedDeviceIndex_Hmd
if (poses[vr::k_unTrackedDeviceIndex_Hmd].bPoseIsValid) {
    auto m = poses[vr::k_unTrackedDeviceIndex_Hmd].mDeviceToAbsoluteTracking;
    // use m (a 3x4 matrix) as the head transform
}

// Render each eye, then submit
vr::Texture_t leftEye = { /* native texture handle */, vr::TextureType_OpenGL, vr::ColorSpace_Gamma };
vr::VRCompositor()->Submit(vr::Eye_Left, &leftEye);
// ... right eye ...

vr::VR_Shutdown();

WaitGetPoses blocks for frame timing and returns predicted poses; Submit hands the rendered eye textures to the compositor, which applies lens distortion, chromatic correction, and reprojection.

Sample re-checked 2026-09-05 against the shipped headers/openvr.h at tag v2.15.6 — every identifier and signature above still matches: VR_Init(EVRInitError*, EVRApplicationType, const char* pStartupInfo = nullptr), IVRCompositor::WaitGetPoses(TrackedDevicePose_t*, uint32_t, TrackedDevicePose_t*, uint32_t), Submit(EVREye, const Texture_t*, const VRTextureBounds_t* = 0, EVRSubmitFlags = Submit_Default), struct Texture_t { void* handle; ETextureType eType; EColorSpace eColorSpace; } and struct HmdMatrix34_t { float m[3][4]; }. The interface versions the header binds at that tag are IVRSystem_026, IVRCompositor_029, IVROverlay_028 and IVRInput_011; a runtime that does not offer the version string your header names fails VR_IsInterfaceVersionValid at init, which is the usual cause of a mismatched-SDK startup failure.

Input

OpenVR's modern input is SteamVR Input (IVRInput): an action-based system (like OpenXR's) where you declare semantic actions and bind them via an action manifest, with a SteamVR binding UI letting users remap. This replaced the older raw button/axis polling and is conceptually the same model OpenXR later standardized.

Overlays

A distinctive OpenVR feature is overlays (IVROverlay) — 2D panels rendered into the VR space or the SteamVR dashboard. Many VR utilities (virtual desktops, HUDs, keyboards) are overlay apps. This is the main reason some apps still use OpenVR directly, as the SteamVR overlay system is not part of base OpenXR.

Update (verified 2026-09-05) — the overlay backside default flipped in the 2.15 line. SteamVR 2.15 (2026-03-26) made overlays "render translucent grey backsides, unless docked to a controller", and Valve's release note is explicit that "third-party overlay apps won't have translucent backsides until recompiled with the next OpenVR SDK". The OpenVR SDK 2.15.6 notes state the same from the SDK side: overlays created with that SDK "will have translucent grey backsides by default (for consistency with the rest of the dashboard), and will require the use of VROverlayFlags_NoBackside to only draw the fronts". The flag is present in headers/openvr.h at v2.15.6 as VROverlayFlags_NoBackside = 1 << 29, with header comments noting that overlays only have a backside at all when built with SDK 2.15.x or higher, and that dashboard overlays ignore the flag entirely. Rebuild an overlay app against 2.15.x and you opt into the backside unless you pass that flag.

The "not part of base OpenXR" half of the claim still holds as of a read of the Khronos registry (specification/registry/xr.xml in KhronosGroup/OpenXR-SDK) on 2026-09-05: overlays are not in core. XR_EXTX_overlay is still marked provisional="true" at spec version 5, and XR_KHR_overlays is only a reserved slot — supported="disabled", spec version 0 — i.e. a reserved extension number rather than a shipped extension.

OpenXR superseded OpenVR as the portable industry standard; OpenVR lives on for SteamVR overlays and driver development.

Gotchas

  • Don't start new projects on OpenVR — target OpenXR; SteamVR is an OpenXR runtime, so for an ordinary scene application you lose nothing and gain portability. The two real exceptions are the ones this entry names: a dashboard/overlay app and a hardware driver still have to be written against OpenVR (checked 2026-09-05).
  • Coordinate matrices are 3x4 — OpenVR poses use a 3x4 HmdMatrix34_t (row-major); convert carefully to your 4x4 engine matrices.
  • WaitGetPoses for timing — use the compositor's WaitGetPoses for frame synchronization, not your own clock, to avoid judder.
  • Overlay-only apps — if you only need a dashboard overlay, initialize with VRApplication_Overlay, not VRApplication_Scene.
  • Driver vs application — the driver interface (for new hardware) is separate from the application interface; don't conflate them. The current driver documentation is docs/Driver_API_Documentation.md in the repository (the GitHub wiki copy is explicitly the old one), re-confirmed 2026-09-05. OpenXR is an application-facing API and defines no device-driver layer at all, so a SteamVR hardware driver is still written against the OpenVR driver interface.
  • The SDK version is not the runtime version — SteamVR ships roughly monthly and the OpenVR SDK does not. On 2026-09-05 the newest SDK tag was v2.15.6 (2026-03-27) while SteamVR itself was on the 2.16 stable line with 2.17.8 in beta. Do not read a quiet SDK repository as a quiet product, and do not assume a runtime feature has a header for it yet.
  • Overlay backsides changed in the 2.15 SDK line — rebuilding an overlay app against SDK 2.15.x opts it into translucent grey backsides; pass VROverlayFlags_NoBackside to keep the old look. See the Overlays section.

OpenVR is the older, Valve-specific predecessor to the cross-vendor OpenXR standard; new VR work should target OpenXR, with OpenVR reserved for SteamVR overlays and driver development. As of 2026-09-05 that is a recommendation, not a deprecation — Valve still ships, extends and documents OpenVR, including on its newest hardware.
