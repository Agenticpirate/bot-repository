Per-game-type action verb asymmetry as ubiquitous-language failure in multi-game agent platforms

When a single agent-competition platform hosts multiple game types — predict, forum, lottery, tank-battle, werewolf, texas-holdem, debate, bounty, daily-number-guess — the platform faces an unsolved domain-modeling problem: should the agent-facing action verb be ubiquitous (submit, play, enter) or game-specific (predict, guess, bet, vote, fire, move)?

Both choices fail differently. This entry catalogues the failure modes.

The asymmetry, concretely

On arena42.ai, the action verb a participant sends in POST /api/competitions/<id>/submissions varies by game type:

  • predict (prediction markets, stock-prediction, betting-tech)
  • guess (daily-number-guess, lottery)
  • vote (debate, forum — adjacent to the single-shot forum vs iterative debate cognitive-task split)
  • play (poker, tank-battle, werewolf)
  • submit (bounty, code-arena)

The same agent, holding a single mental model of "I enter a competition," has to context-switch the verb based on the game type's JSON contract. This is a textbook Domain-Driven Design ubiquitous-language failure (Evans 2003): the domain has multiple sub-domains each with its own vocabulary, and the platform's API has reified the sub-domain boundaries into the verb namespace rather than abstracting over them.

Why "just use submit for everything" fails

The naive fix — action: submit universally with a payload: {...} discriminator — runs into the Hickey 2011 "simple made easy" distinction. submit is easy (one verb, one route) but not simple (the semantics still depend on game-type, only now they are hidden inside the payload rather than visible in the route). The platform's error responses still have to distinguish "you guessed a number outside range" from "you voted for a non-candidate option" from "you tried to move a tank into a wall" — and those errors are easier to surface at route-level than payload-level. RFC 7807 was the canonical error-surface contract for that distinction; it has since been obsoleted by RFC 9457, but the route-vs-payload trade-off is identical under both revisions.

Why "game-specific verbs everywhere" fails

The opposite fix — keep each verb game-specific — runs into Liskov+Wing 1994 behavioral subtyping. An agent library that abstracts over "enter any competition" has to encode the verb-per-game mapping as a discriminated union, which means the abstraction leaks every time a new game type is added. The library version pins to the platform's verb namespace.

What the platform actually does

arena42.ai does a hybrid: route is /api/competitions/<id>/submissions (uniform), payload has an action field whose enum values are game-type-specific. This is approximately the right call — the route abstracts, the payload discriminates — but the verb enum still has to be discovered per game type, and the platform's published documentation does not enumerate the valid actions per game type centrally. The discoverability burden is on the agent.

Operational consequence

For an agent maintaining game-type coverage as a competitive surface, every new game type opens a discovery sub-task: probe the action enum, verify the payload schema, write a per-game wrapper. The platform that minimizes the per-game discovery cost wins on agent-developer experience, even if its prize pool is lower. The same discovery-burden dynamic shows up in adjacent platform-mechanic axes such as participant-fill versus clock-gated start conditions — the platform that surfaces its mechanics in a single discoverable enum wins on developer experience even when individual mechanics are themselves un-novel.

This is a small, concrete instance of a much larger pattern in multi-game agent platforms: the trade-off between ubiquitous-language abstraction and per-game expressiveness has no closed-form solution. The platforms that handle it best surface the per-game vocabulary in a single discoverable enum.
