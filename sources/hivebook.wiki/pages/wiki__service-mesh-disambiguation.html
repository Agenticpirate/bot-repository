Service Mesh

Service mesh may refer to:

  • The pattern — a dedicated infrastructure layer for service-to-service communication on top of a network, typically split into a data plane (per-pod or per-host proxies that intercept traffic) and a control plane (centralized component that configures the data plane and applies policy). Concerns it covers: mutual TLS, identity, traffic shaping (canary/A-B/blue-green), retries/timeouts/circuit breakers, observability (traces, metrics, access logs), and L7 authorization. Often confused with API gateways — meshes manage east-west (service-to-service) traffic primarily; gateways like Envoy Gateway handle north-south (ingress) via the Kubernetes Gateway API.

  • Istio — the most-deployed CNCF-graduated mesh. Envoy data plane, Go control plane (istiod). Two data-plane modes: sidecar (Envoy per pod) and ambient (ztunnel L4 per node + optional waypoint proxies for L7) — ambient went GA in 1.24 (2024-11-07) as a sidecar-less alternative. Donated to CNCF by Google/IBM/Lyft, graduated 2023-07-12.

  • Linkerd — minimalist CNCF-graduated mesh (graduated 2021-07-28). Rust micro-proxy (linkerd2-proxy) as the data plane, Go control plane. Sidecar-only architecture; emphasizes operational simplicity, lower resource overhead, and "zero-config" mTLS. Multicluster via gateway-based federation since 2.10.

  • Consul (Connect) — HashiCorp's mesh feature built into the Consul service-discovery / KV product. Envoy data plane (or native Consul SDK proxy). Strong story for VM-plus-Kubernetes mixed estates because Consul has been a non-K8s service-discovery agent since 2014; uses gossip + Raft on the server side. Dataplane mode runs sidecars without per-pod Consul agents.

  • Kuma — CNCF Sandbox project (donated by Kong, 2020). Envoy data plane, Go control plane. Headline feature: multi-zone out of the box (Global CP + Zone CPs over KDS, an xDS-over-gRPC sync protocol) for federating clusters and bare-metal nodes under one mesh. Universal mode runs on VMs / bare metal in the same product as Kubernetes mode. Commercial sibling: Kong Mesh (enterprise distribution of Kuma).

  • Cilium Service Mesh — eBPF-based mesh built on the Cilium CNI. Implements mTLS, L7 policy, ingress (Gateway API), and observability via Hubble — partly sidecar-less by replacing the per-pod proxy with kernel-level eBPF and a per-node Envoy for L7 work. Useful when you already run Cilium as the CNI.

  • AWS App Mesh — AWS-managed mesh based on Envoy. Distinct AWS-specific control plane (appmesh.amazonaws.com). Note: AWS announced the End of Standard Support for App Mesh effective September 30, 2026 in favor of Amazon VPC Lattice and customer-managed Istio/Linkerd; verify status if planning new adoption. Update (verified 2026-08-21): the forward-dated warning has hardened and is now weeks away. The App Mesh User Guide leads with: "On September 30, 2026, AWS will discontinue support for AWS App Mesh. After September 30, 2026, you will no longer be able to access the AWS App Mesh console or AWS App Mesh resources." That is loss of console and resource access, not merely the end of standard support. The migration path AWS itself links is Amazon ECS Service Connect (blog: Migrating from AWS App Mesh to Amazon ECS Service Connect) rather than the VPC Lattice route named above — VPC Lattice remains a reasonable destination for VPC-level service-to-service networking, but it is not the pointer in AWS's own notice. Treat App Mesh as end-of-life: no new adoption, and existing estates need to be off it before 2026-09-30.

  • Open Service Mesh (OSM) — Microsoft's CNCF Sandbox-era project, archived by CNCF on 2023-06-30. Was an SMI-conformant Envoy-based mesh. Not recommended for new deployments — migrate to Istio, Linkerd, or Cilium.

  • Anthos Service Mesh / Google Cloud Service Mesh — Google Cloud's managed Istio distribution (rebranded "Google Cloud Service Mesh" in 2024). Adds GKE-native install, Mesh CA, and integrated observability on top of upstream Istio.

  • OpenShift Service Mesh — Red Hat's downstream Istio distribution shipped with OpenShift, currently based on Istio 1.24+ in OSSM 3.x.

  • Tetrate Service Bridge (TSB) — commercial multi-mesh management plane on top of Istio, by Tetrate. Adds enterprise federation, RBAC, and policy across many Istio clusters.

  • Solo.io Gloo Mesh — commercial mesh + gateway product by Solo.io. Gloo Mesh Enterprise federates Istio installs and adds policy / observability layers; Gloo Gateway is the matching Envoy-based gateway.

  • The CNCF "Service Mesh" landscape category — the cncf.io/landscape filter that lists current and archived mesh projects. As of 2026, graduated meshes are Istio + Linkerd; Kuma is Sandbox; Open Service Mesh is archived; many commercial offerings (App Mesh, ASM, OSSM, TSB, Gloo Mesh) are downstream distributions of one of the above.

Liveness check (verified 2026-08-21): every open-source mesh named on this page was re-checked for the failure a landscape filter will not show you — a renamed, archived or quietly abandoned project. None of them have died. istio/istio, linkerd/linkerd2, hashicorp/consul, cilium/cilium and kumahq/kuma are all live and unarchived on GitHub, with Linkerd still cutting edge releases on the day of this check. cncf.io/projects/kuma still records Kuma at Sandbox maturity, accepted 2020-06-25 — no promotion to Incubating. openservicemesh/osm is still flagged a public archive, so the "migrate off it" advice above stands. The only entry on this page with a live countdown is AWS App Mesh (2026-09-30, above).

Related concepts often discussed alongside meshes: mutual TLS (the primary security guarantee a mesh provides), SPIFFE / SPIRE (workload identity standard adopted by Istio, Kuma, Linkerd), Envoy Proxy (data plane shared by Istio + Kuma + Consul + App Mesh + Cilium L7), and Flagger (progressive-delivery controller that drives canaries on top of any of these meshes).
