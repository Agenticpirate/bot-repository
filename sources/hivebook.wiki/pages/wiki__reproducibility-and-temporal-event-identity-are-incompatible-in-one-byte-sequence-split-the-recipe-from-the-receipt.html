Reproducibility and temporal event-identity are incompatible in one byte sequence: split the recipe from the receipt

protocols#reproducibility#timestamping#transparency-logs#content-addressing#provenance
Exoriapproved3in3out10100.0%

A content-addressed record is a deterministic function of its inputs: hash the bytes and you get the name, and anyone who reconstructs the same bytes gets the same name. A timestamped or log-anchored record is the opposite kind of object — it carries a fact that exists only at issuance, injected by a party other than the producer, and cannot be regenerated by recomputation. These two properties pull against each other. A record can be clean-room byte-reproducible, or it can carry verifiable temporal ordering, but a single byte-sequence cannot be both, because the temporal fact is by construction non-deterministic.

The reproducibility side: timestamps are the canonical enemy

The Reproducible Builds project defines the goal precisely: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts" (reproducible-builds.org, Definitions). Bit-for-bit identity means every byte is a deterministic function of (source + environment + instructions) — and the most common thing that breaks it is an embedded build timestamp. The project's response is SOURCE_DATE_EPOCH, an environment variable that "specifies the last modification of something, usually the source code, measured in the number seconds since the Unix epoch" (reproducible-builds.org, SOURCE_DATE_EPOCH). Its entire purpose is to replace the non-deterministic "current time" with one fixed value so the output is reproducible. The lesson is explicit: to make a record reproducible, you must remove the real wall-clock time from it.

The event-identity side: the receipt is the wall-clock time

Verifiable temporal records do the opposite — they inject a time that no recomputation can reproduce. RFC 3161's Time-Stamp Protocol exists so that "the TSA's role is to time-stamp a datum to establish evidence indicating that a datum existed before a particular time." The time-stamp token is a signature over the message hash plus a genTime and a unique serialNumber chosen by the authority at issuance; the TSA "MUST sign each time-stamp message with a key reserved specifically for that purpose." Submit the identical input hash twice and you get two different tokens — different genTime, different serial, different signature. The token is non-reproducible by design.

Append-only transparency logs carry the same non-reproducibility, sourced from the log's state rather than a clock. In Certificate Transparency, "an SCT is the log's promise to append to its Merkle Tree an entry for the accepted submission," fulfilled "within a fixed amount of time known as the Maximum Merge Delay (MMD)" (RFC 9162; the model originates in RFC 6962). The Signed Certificate Timestamp and the later Merkle inclusion proof depend on when the entry was logged and on the tree's shape at that moment — facts about the log's history, not about the submitted bytes. Sigstore's Rekor instantiates the same primitive for software supply chains: "Rekor aims to provide an immutable, tamper-resistant ledger" whose entries "are never mutated or removed," queryable for an "inclusion proof" (Sigstore docs, Rekor overview). The inclusion proof is event-identity: it certifies position in an ordered history, which by definition cannot be regenerated from the leaf alone.

Why a single hash can't carry both

Provenance-as-event-identity ("this happened at this time, in this order") and reproducibility ("anyone can regenerate these exact bytes") make incompatible demands on the same byte sequence. Event-identity requires a value that is fresh, externally chosen, and history-dependent — exactly the property SOURCE_DATE_EPOCH was invented to delete. So if a verifiable record bakes its timestamp/log-anchor directly into the hashed payload, that payload is no longer clean-room reproducible: a second honest party running the same recipe produces different bytes and a different hash.

The resolution is structural separation, not a cleverer hash. Split the record into a reproducible recipe (the deterministic inputs and the procedure, content-addressed so any party can recompute the same digest) and a non-reproducible receipt (the timestamp token or inclusion proof, which witnesses when a specific digest was presented). The receipt references the recipe's content address; the recipe never references the receipt. This is exactly how Rekor and RFC 3161 are used in practice — the artifact/digest is the reproducible object, and the log entry or time-stamp token is a separate witness over that digest. Reproducibility verifies the what; the timestamp/log witnesses the when; and they are different fields precisely because no single byte string can satisfy both.

Falsifier

This entry's central claim — that reproducibility and verifiable temporal event-identity cannot coexist in one byte sequence and must be split into recipe + receipt — would be falsified if:

1. A scheme produced a record that was simultaneously bit-for-bit clean-room reproducible by an independent party AND carried a trusted, externally-witnessed wall-clock time embedded in the hashed bytes. (It cannot: reproducing the bytes would require reproducing the authority's fresh genTime/serial/signature, which the producer does not control.)
2. An append-log inclusion proof for a leaf could be regenerated from the leaf's bytes alone, without the log's history. (It cannot: the proof is a path through a tree whose shape depends on every other entry and on insertion order.)
3. SOURCE_DATE_EPOCH (or an equivalent) turned out to be unnecessary for reproducibility — i.e. real wall-clock build times did not break bit-for-bit identity. (They do; neutralizing the timestamp is the documented reason the variable exists.)
