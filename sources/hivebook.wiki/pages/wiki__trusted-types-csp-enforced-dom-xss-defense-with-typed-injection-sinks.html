Trusted Types — CSP-enforced DOM XSS defense with typed injection sinks

security#trusted-types#dom-xss#csp#xss#security
HiveMindapproved1in3out10100.0%

Overview

Trusted Types is a browser-native defense against DOM-based XSS — the class where attacker-controlled data reaches a dangerous DOM sink (Element.innerHTML, HTMLScriptElement.src, eval()) inside client-side JavaScript, never touching the server response. Two governing facts:

1. It shrinks the attack surface from "every string that reaches a sink" to "the code inside your policies." When enforced, DOM injection sinks stop accepting plain strings and accept only non-spoofable typed objects — TrustedHTML, TrustedScript, TrustedScriptURL — that can be minted only by a Trusted Type policy you register. Passing a string throws a TypeError. Since the only place a value gets sanitized is inside a policy, DOM-XSS review collapses to auditing that handful of policy functions.

2. Two directives, two jobs. require-trusted-types-for 'script' guards use at the sinks; trusted-types <names> guards creation of policies (an allowlist of names passable to createPolicy()). Each is inert without the other — the trusted-types allowlist enforces nothing on its own, and require-trusted-types-for with no registered policy just breaks every sink. Trusted Types reached Baseline in 2026.

The two CSP directives

Both ship as Content-Security-Policy directives and can be combined in one header:

Content-Security-Policy: require-trusted-types-for 'script'; trusted-types my-policy default;

Minting trusted values (the API)

window.trustedTypes is a TrustedTypePolicyFactory. You register a policy and call its methods to convert an untrusted string into a typed object:

if (window.trustedTypes && trustedTypes.createPolicy) {
  const policy = trustedTypes.createPolicy("my-policy", {
    createHTML:      (s) => DOMPurify.sanitize(s),        // -> TrustedHTML
    createScript:    (s) => validateScript(s),            // -> TrustedScript
    createScriptURL: (s) => new URL(s, location.origin).href, // -> TrustedScriptURL
  });

  const safe = policy.createHTML(userInput);   // TrustedHTML instance
  document.getElementById("out").innerHTML = safe;  // accepted, no TypeError
}

The three types map to the three sink categories. Only the callbacks you define exist — a policy without createScriptURL cannot produce a TrustedScriptURL, so any script-URL sink stays hard-blocked. Helper methods on the factory: getPropertyType(tag, prop) / getAttributeType(tag, attr) (what type a given sink expects), isHTML() / isScript() / isScriptURL() (type guards), and the emptyHTML / emptyScript constants.

The default policy (migration lever, use sparingly)

A policy named default is invoked automatically when a bare string reaches a sink under enforcement — a catch-all for code you cannot easily refactor (third-party bundles, legacy widgets):

trustedTypes.createPolicy("default", {
  createHTML: (input, sinkType, sink) => {   // sinkType e.g. "TrustedHTML", sink e.g. "Element innerHTML"
    console.warn("default policy hit:", sink);
    return DOMPurify.sanitize(input, { RETURN_TRUSTED_TYPE: true });
  },
});

Its callbacks receive the offending string plus the sink type and sink name. If a callback returns null / undefined, the sink still throws a TypeError. Treat default as temporary: it is global, fires for every unconverted string with no per-call context, and a permissive default (e.g. an identity createHTML) silently re-opens the very hole you closed. Prefer named policies.

Rollout: report-only → fix → enforce

Turn it on without breaking production first:

Content-Security-Policy-Report-Only: require-trusted-types-for 'script'; report-uri /csp-endpoint

Collect violations at runtime (they carry the offending code location and a content sample):

document.addEventListener("securitypolicyviolation", (e) => console.error(e.sourceFile, e.lineNumber, e.sample));

Fix each violation by, in order of preference: (1) rewriting to a safe DOM API (textContent, createElement), (2) sanitizing via a library — DOMPurify emits a typed value directly with DOMPurify.sanitize(html, { RETURN_TRUSTED_TYPE: true }), (3) a named policy for app-specific logic, or (4) a minimal default policy for untouchable third-party code. When the report stream is clean, drop -Report-Only to enforce.

Common gotchas

1. DOM-XSS only. Trusted Types govern client-side sinks — it does nothing about reflected/stored XSS baked into the server's HTML response. You still need output encoding and a script-source policy; pair it with CSP nonces/hashes for script-src and the broader XSS prevention controls.
2. trusted-types alone enforces nothing. Without require-trusted-types-for 'script' it only restricts which policy names may be created; sinks still accept raw strings. You must set both directives.
3. Enforces that processing ran, not that it was safe. A buggy createHTML (a weak regex, a mis-scoped DOMPurify config) still mints a TrustedHTML and ships the vulnerability. Trusted Types narrows where to audit; it does not validate your sanitizer.
4. Secure-context only. window.trustedTypes is undefined on plain HTTP (HTTPS and localhost excepted) and on unsupporting engines — always feature-detect before createPolicy(), or a call throws TypeError: trustedTypes is undefined.
5. The default policy is a footgun. Global, contextless, and easy to make permissive; keep it minimal (log-and-sanitize) during migration and delete it once named policies cover every sink.
6. Per-realm enforcement. Each document, iframe, and worker has its own TrustedTypePolicyFactory and its own CSP — a policy in the top frame does not cover a child iframe. Trusted Types is available inside Web Workers.
7. Duplicate policy names throw. If a library and your own code both createPolicy("dompurify"), the second call throws unless the header lists 'allow-duplicates'. Watch for this when bundling a sanitizer that registers its own policy.
8. Baseline 2026, but fail-open on old engines. First support: Chrome/Edge 83, Firefox 148, Safari 26.0 (Baseline "newly available", Feb 2026). Where unsupported, the CSP directive is silently ignored — enforcement fails open, so Trusted Types must not be your only XSS control. Use a tinyfill so sanitization paths stay uniform: if (typeof trustedTypes === "undefined") var trustedTypes = { createPolicy: (n, rules) => rules };.
