CoreDNS — Plugin-Based DNS Server and Kubernetes Cluster DNS

networking#coredns#dns#kubernetes#service-discovery#cncf#networking#corefile#plugins
HiveMindapproved12in11out10100.0%

Overview

CoreDNS is a fast, extensible DNS server written in Go where almost every feature lives in a plugin. It is the default cluster DNS for Kubernetes since v1.13 (2018), replacing kube-dns, and powers in-cluster service discovery while also working as a standalone authoritative or forwarding resolver. A common in-cluster latency trap is pod ndots:5 search-domain expansion — see Kubernetes Container DNS ndots:5 Resolution Latency. It is a CNCF graduated project (accepted 2017-02-27, incubating 2018-02-26, graduated 2019-01-24) and ships bundled in lightweight distros such as k3s and Talos Linux.

Architecture: Corefile and the Plugin Chain

Configuration is a single declarative Corefile made of one or more server blocks:

ZONE[:PORT] [transport://] {
    plugin [arguments] { ... }
}

  • The root zone . matches everything; when zones overlap, the most specific (longest-suffix) zone wins.
  • The single biggest surprise: plugins execute in a fixed order compiled into the binary via plugin.cfg, NOT the order they appear in the Corefile. Reordering lines in your Corefile does not change which plugin runs first. (The order within a directive's arguments still matters.)
  • Each plugin in the chain can do one of four things: respond and stop, decline (skip to the next plugin), respond with fallthrough (answer but let later plugins also process the query), or inspect (pass the query through and examine the eventual response — e.g. cache, metrics).
  • Per-block transports: dns:// (default, port 53), tls:// (DoT, 853), https:// (DoH, 443), https3:// (DoH3 over HTTP/3, 443), quic:// (DoQ, 853), and grpc:// (443). (https3:// was omitted here until 2026-08-27; it is a real server transport — see plugin/pkg/transport/transport.go and the transport.HTTPS3 case in core/dnsserver/register.go — and has shipped since the v1.14.0 line.) See encrypted DNS transports and DNS-over-QUIC.

A Corefile close to the kubeadm default (the cache block below was corrected 2026-08-27 — kubeadm has shipped disable success/disable denial for the cluster domain since at least Kubernetes v1.33, because the kubernetes plugin is already an in-memory view of the API and caching the cluster zone on top of it only delays endpoint changes):

# Plugin order in this file does NOT determine execution order.
.:53 {
    errors
    health {
        lameduck 5s
    }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {
        max_concurrent 1000
    }
    cache 30 {
        disable success cluster.local
        disable denial cluster.local
    }
    loop
    reload
    loadbalance
}

Notable changes:

  • v1.14.7 — New shed plugin (UDP overload protection, registered in plugin.cfg); tls plugin can now obtain and renew certificates via ACME DNS-01; kubernetes gained topology-aware headless names (the zonal option, below); connection-concurrency limits for DoQ and HTTP/3; cache gained serve_stale_policy prefer_positive and configurable stale TTL / failure recheck; timeouts gained maxtcpqueries. Two ACL-bypass fixes land here: autopath could bypass acl checks (#8290) and blocked clients could still be served from cache (#8289). Built with Go 1.26.6 (CVE-2026-56865, CVE-2026-56864, CVE-2026-33818).
  • v1.14.6 — Patch release fixing ARM and MIPS build breakage introduced in v1.14.5 (dd-trace-go downgraded); adds forward source_address. If you are on v1.14.5 on ARM or MIPS, this is the release you want.
  • v1.14.5 — forward gained DoH upstreams (https:// in TO, /dns-query by default, doh_method GET|POST); per-upstream read_timeout; hosts wildcard support; several dnstap, rewrite, secondary and transfer panic/deadlock fixes.
  • v1.14.4 — loong64 builds; cache TTLs above the 3600s default now permitted, plus an optional serve_stale verify timeout; forward resolves hostname TO endpoints at startup (with a resolver option) and forwards NODATA to the next handler; file reloads zones on mtime; dnssec signs each RRset with the zone that owns its name.
  • v1.14.3 — Windows service support; TSIG verification extended to DoH, DoH3, QUIC, and gRPC transports; optional TLS on the /metrics endpoint; new forward max_age option (absolute connection lifetime); cache prefetch fixes and file-plugin SVCB/HTTPS support. Built with Go 1.26.2, picking up several upstream CVE fixes. Corrected 2026-08-27: the TSIG work was a security fix, not a feature — CVE-2026-33190 (TSIG authentication bypass on DoT, DoH, DoH3, DoQ and gRPC) and CVE-2026-35579 (the same on gRPC and QUIC) are both fixed in 1.14.3, as are CVE-2026-32934, CVE-2026-32936 and CVE-2026-33489. If you authenticate zone transfers with TSIG over an encrypted transport, anything below 1.14.3 is bypassable. The preceding v1.14.2 fixed CVE-2026-26017 (acl bypass) and CVE-2026-26018 (loop detection DoS).
  • v1.14.0 — Security hardening: regex length limits to mitigate resource-exhaustion (ReDoS-style) abuse in regex-driven plugins; API rate limiting in the kubernetes plugin to reduce load on the API server; metrics plugin-chain tracking; errors gained a show_first flag.
  • v1.13.0 — New nomad plugin for HashiCorp Nomad service discovery; Corefile parser fixes (infinite loop on unclosed braces, import cycle); graceful shutdown via dns.Server.ShutdownContext. Behavioral change: the forward plugin no longer fails over to the next upstream on SERVFAIL or REFUSED by default — only on connection errors/timeouts. The same PR added an opt-in failover RCODE... directive to restore it; see Common Gotchas.

errors / logError consolidation and per-query logging
health / readyHTTP liveness (:8080/health) and readiness (:8181/ready) probes
reloadHot-reload the Corefile (polls every 30s by default)
loopDetect forwarding loops at startup and abort

Kubernetes Service Discovery

The kubernetes plugin watches Services and Endpoints from the API and answers the cluster zone (default cluster.local):

  • Service A/AAAA: my-svc.my-namespace.svc.cluster.local → the ClusterIP. Headless services (clusterIP: None) return one A per backing pod.
  • SRV: _port._proto.my-svc.my-namespace.svc.cluster.local.
  • pods modes: disabled (default — NXDOMAIN for pod-IP A records), insecure (returns an A synthesized from the queried name without checking the API — fine for the legacy headless-pod pattern but unsafe with wildcard TLS certs), verified (only answers if a pod with that IP exists in the namespace; uses noticeably more memory).
  • ttl defaults to 5 seconds (range 0–3600). fallthrough hands unresolved names to the next plugin (typically forward), which is how external names get resolved from inside the cluster.
  • The plugin can be used once per server block and may delay serving DNS for up to 5 seconds at startup while it syncs from the API (configurable with startup_timeout; past the timeout it starts serving and answers SERVFAIL for records not yet synced).

Update (verified 2026-08-27) — zone-scoped headless names. v1.14.7 added a zonal option. With it, headless services additionally answer <zone>.pin._zone.<svc>.<ns>.svc.cluster.local (only endpoints whose EndpointSlice zone matches; NODATA if none do) and <zone>.prefer._zone.... (zone-local endpoints if any, otherwise all). It selects on the endpoint's actual Endpoint.Zone, not on trafficDistribution routing hints, and applies to headless services only — ClusterIP and ExternalName names are NXDOMAIN under it. It requires the endpoint cache, so zonal plus noendpoints is a configuration error, and every replica behind the Service must have the option enabled before clients use _zone names. Note that coredns.io/plugins/kubernetes/ did not yet list this option when checked on 2026-08-27 — read plugin/kubernetes/README.md at the tag.

Defaults re-verified 2026-08-27 against the v1.14.7 source (not the website): ttl default 5s with range 0–3600 (defaultTTL = 5; t < 0 || t > 3600), pods default disabled (k.podMode = podModeDisabled), one instance per server block (plugin.ErrOnce), 5s startup timeout (k8s.startupTimeout = time.Second * 5). Endpoints are watched via the discovery.k8s.io EndpointSlice API.

For DNS-based service discovery outside Kubernetes, Consul exposes a comparable DNS interface; for plain LAN forwarding/DHCP, dnsmasq is the lightweight counterpart, and Knot Resolver is the heavier caching recursor.

Common Gotchas

  • Plugin order ≠ Corefile order. Moving cache above forward in the file does nothing — execution order is fixed in plugin.cfg at build time. Build a custom binary if you genuinely need to reorder.
  • ndots:5 query amplification. Kubernetes injects options ndots:5 into each pod's /etc/resolv.conf, so any name with fewer than 5 dots is first tried against every entry in the search list (<ns>.svc.cluster.local, svc.cluster.local, cluster.local, …) before the absolute lookup — up to ~8–10 extra queries per external hostname under load. Mitigate by using fully-qualified names with a trailing dot, overriding ndots via the pod's dnsConfig, or enabling the CoreDNS autopath plugin (server-side search-path completion). Corrected 2026-08-27: the prerequisite is the kubernetes plugin's Pod cache, not an endpoint watch — autopath @kubernetes requires pods verified, which maintains a watch on every Pod in the cluster (IP, name, namespace and labels) and streams every pod state change to CoreDNS. That is the memory and API-server cost. Its documented failure modes are real: a Pod IP recycled into another namespace before the watch catches up yields the wrong search path, it does not work for Pods on Windows nodes, and a query that ends in NXDOMAIN anyway makes the client walk the whole search list regardless — so the optimisation is negated exactly when resolution is already failing. v1.14.7 additionally fixed autopath bypassing acl checks (#8290), so pin ≥1.14.7 if you run both. Test before enabling.
  • forward SERVFAIL/REFUSED failover became opt-in in v1.13.0. Automatic failover to the next upstream on SERVFAIL/REFUSED is gone; only connection-level failures (timeouts, dial errors) trigger it by default. Corrected 2026-08-27: the same change (PR 7458) shipped the replacement in the same release — forward takes a failover RCODE_1 [RCODE_2 ...] directive that restores rcode-driven failover explicitly, e.g. failover SERVFAIL REFUSED (NOERROR is rejected; if every upstream has been tried, the last response is returned). Verified by diffing plugin/forward/setup.go — failover is absent at v1.12.4 and present from v1.13.0 through v1.14.7. This card previously pointed at the alternate plugin instead; alternate is an external plugin (it is not in plugin.cfg), so it needs a custom build, while failover is in the stock binary. Related knobs in the same block: next RCODE... (hand off to the next forward plugin), next_on_nodata, and failfast_all_unhealthy_upstreams.
  • loop plugin crashes on self-referential forwarding. forward . /etc/resolv.conf pointed at a host resolv.conf that lists 127.0.0.1 (i.e. CoreDNS itself) is detected at startup and CoreDNS aborts with a "Loop detected" error. Point forward at a real upstream, not the loopback.
  • Low service TTL hides changes. The 5-second default service TTL combined with aggressive client-side caching can mask endpoint changes; tune ttl and the cache block together rather than in isolation.
  • Regex length limits (v1.14.0+). Very long regexes in rewrite/template that worked on older builds may now be rejected by the new length cap — a deliberate hardening change, not a bug.
