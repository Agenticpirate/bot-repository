Overview

Permify is an open-source authorization service inspired by Google Zanzibar that centralises permission logic outside your application code. You model resources, relations, and permissions in a small DSL, push relationship tuples and attributes through gRPC or HTTP, then ask check, lookup-entity, or lookup-subject questions and get a yes/no answer plus the list of permitted resources. The repository is Permify/permify (~5.9k stars). Update (verified 2026-08-23): current stable is v1.7.3 (2026-08-17), with v1.7.1 (2026-06-12) and v1.7.2 (2026-07-07) in between; v1.7.0 (2026-05-20) was current at the May 2026 baseline. Release dates below come from github.com/Permify/permify/releases.

Two facts shape every Permify decision in 2026 and they are not obvious from the GitHub front page:

1. Permify is now part of FusionAuth. The acquisition was announced 2025-11-20 in A CRO's Perspective: User Identity Isn't Complete Without Authorization. The post commits to "continuing investment in the open-source community" and promises "a formal announcement of the fully integrated offering and streamlined pricing model in early 2026". As a concrete consequence the canonical documentation URL has moved — docs.permify.co now 301-redirects to fusionauth.io/permify-docs/.
2. The server is AGPL-3.0. The SDK licences are mixed, not uniformly Apache-2.0. The server half holds: Permify/permify ships under GNU Affero General Public License v3, confirmed byte-for-byte in LICENSE at both the v1.7.0 baseline tag and v1.7.3. The SDK half is wrong, and was already wrong at the May 2026 baseline — corrected 2026-08-23 against the shipped packages. Apache-2.0 LICENSE files really are present in permify-node, permify-typescript, permify-javascript, permify-go, permify-java, permify-csharp, vscode-perm, helm-charts and homebrew-tap. But permify-python, permify-php and permify-ruby carry no LICENSE file at all and declare AGPL-3.0 in the metadata that actually ships: setup.py license="AGPL-3.0 license" (which is what PyPI's license field and the wheel's METADATA header say for every release from 1.6.9 to 1.7.2), composer.json "license": "AGPL-3.0", and permify.gemspec s.license = "AGPL-3.0". permify-python contradicts itself inside one repo — pyproject.toml says Apache-2.0 and an Apache-2.0 text file is present under the British spelling LICENCE, while the published wheel says AGPL-3.0. The clean AGPL-server/Apache-client boundary this entry's title asserts is real only for the six SDKs listed first. See the License & governance section below.

OpenFGA (Apache-2.0, CNCF Incubating), SpiceDB (Apache-2.0, AuthZed), and Cedar (Apache-2.0, Amazon) are the closest peers. Permify's distinguishing axes are its native ABAC+ReBAC composition (rules inside relation graphs), the vscode-perm schema-authoring extension, and — now — FusionAuth's commercial backing.

Architecture

Permify is a single Go binary. Corrected 2026-08-23 against a locally built v1.7.3: a stock permify serve opens three listeners — HTTP :3476, gRPC :3478, and an "invoker" gRPC server on :5000 — and nothing listens on :6060. The profiler is profiler.enabled: false with no default port, there is no Prometheus scrape endpoint (GET :3476/metrics returns 404), and metrics leave over OTLP push (meter.exporter: otlp, itself disabled by default). Authorization state lives in one of two storage drivers:

DriverUse casePersistence

memory (default)Local dev, CI, embedded testingLost on restart
postgresProduction — the only persistent driverPostgreSQL 13.8+ (corrected 2026-08-23; the server validates the version at startup and errors on older). Enable track_commit_timestamp = on if you use the watch API.
~~mysql~~Does not exist — corrected 2026-08-23. permify serve --database-engine=mysql exits with Error: mysql connection is unsupported, and internal/factories/storage.go has carried only postgres and memory branches since v1.0.0.—

"By default, the container is configured to listen on ports 3476 (HTTP) and 3478 (gRPC) and store the authorization data in memory rather than an actual database" — verbatim from the Docker install guide at proxy-docs.permify.co/setting-up/installation/container.md. Run the in-memory driver only for development. All tuples vanish on restart, which is precisely the failure mode that produces "all my permissions disappeared after a redeploy" reports.

Update (verified 2026-08-23 by running v1.7.3): the second default that matters more for a security deployment is that authentication is off. authn.enabled defaults to false and server.http.cors_allowed_origins defaults to [*], so a stock permify serve accepts an unauthenticated POST /v1/tenants/t1/schemas/write from anyone who can reach port 3476 — that is, anyone who can reach it can rewrite your authorization model. Set --authn-enabled together with --authn-preshared-keys or the --authn-oidc-* options before the port is reachable by anything but your own services.

Schema and relationship data are versioned independently. The schema_version is a hash of the active schema; the snap_token is an encoded timestamp committed when relationship tuples or attributes change. Pass both in check requests to pin to a known snapshot.

Schema DSL (Permify language)

Schema files use the .perm extension. Five primitives compose the language: entity, relation, permission, attribute, and rule. The following example (verbatim from proxy-docs.permify.co/getting-started/modeling.md) shows all five:

entity user {}

entity organization {
    relation admin @user
    attribute ip_range string[]
    permission view = check_ip_range(ip_range) or admin
}

rule check_ip_range(ip_range string[]) {
    context.data.ip in ip_range
}

  • entity — a typed resource (user, organization, document, …). The user entity is conventional but not built in.
  • relation — typed edge between entities: relation owner @user, relation parent @folder. Relations can chain (relation maintainer @organization#admin) to express transitive group membership — the Zanzibar userset rewrite pattern.
  • permission — boolean expression over relations and attributes. Operators are or, and, not, parenthesised subexpressions, and () rule invocations. Two corrections made 2026-08-23 against the shipped v1.7.3 parser (pkg/dsl/parser/parser.go, each confirmed by running permify validate with assertions): (1) not is registered only as an infix operator — permission x = not admin does not parse, it fails with no prefix parse function for NOT found. Write a not b, which evaluates as a AND NOT b. (2) and, or and not all sit at one precedence level and bind left to right, so a or b and c parses as (a or b) and c, not as a or (b and c) — a subject holding only a comes back DENIED. Parenthesise every mixed expression. action also remains a lexer alias for permission at v1.7.3 (pkg/dsl/token/token.go maps both words to PERMISSION), so pre-rename schemas still parse.
  • attribute — typed value attached to an entity (boolean, string, integer, double, plus array variants). Supplied at evaluation time via the attributes field of a data/write call or via inline context.data.
  • rule — first-class function returning bool, used inside permission expressions. CEL-style; can reference context.data.<field> for request-time inputs (IP, time-of-day, MFA flag) without writing a separate tuple.

This ABAC-inside-ReBAC composition is the headline differentiator versus OpenFGA (pure ReBAC) and Cedar (pure policy expressions). You get Zanzibar's userset rewriting and runtime attribute evaluation in one decision step, without needing a sidecar OPA.

Permission Check API

JSON payload, verbatim from proxy-docs.permify.co/api-reference/permission/check-api:

{
  "metadata": {
    "snap_token": "",
    "schema_version": "",
    "depth": 20
  },
  "entity": {
    "type": "repository",
    "id": "1"
  },
  "permission": "edit",
  "subject": {
    "type": "user",
    "id": "1",
    "relation": ""
  }
}

POST to http://localhost:3476/v1/tenants/{tenant_id}/permissions/check. The response is {"can": "CHECK_RESULT_ALLOWED" | "CHECK_RESULT_DENIED", "metadata": {...}} with checked-tuple metadata for debugging.

Update (verified 2026-08-23 by replaying this exact payload against a locally built v1.7.3): the path, the field names and the response shape are all still correct — the server answered {"can":"CHECK_RESULT_ALLOWED", "metadata":{"check_count":2}}. One constraint the sample hides: metadata.depth is validated as >= 3, so depth: 1 or 2 is rejected with HTTP 400 value must be greater than or equal to 3.

The permission service exposes seven RPCs, not four — corrected 2026-08-23 against proto/base/v1/service.proto, which already carried all seven at the v1.7.0 baseline:

EndpointQuestion answered

checkCan subject S do permission P on entity E?
bulk-checkThe same question for up to 100 (entity, permission, subject) items in one round trip — POST .../permissions/bulk-check, capped by service.permission.bulk_limit (default 100). Added December 2025.
expandReturn the permission tree for entity E as a graph, for debugging and visualisation.
lookup-entityWhich entities of type T can subject S do permission P on? (subject-based filtering)
lookup-entity-streamServer-streaming form of lookup-entity, for result sets too large to buffer.
lookup-subjectWhich subjects can do permission P on entity E? (entity-based listing)
subject-permissionWhat permissions does subject S have on entity E? (full subject capability set)

Beyond permissions, the API surfaces five more capability families — the sentence originally said "six" and then listed five; corrected 2026-08-23 against the shipped service.proto, which defines exactly these five services alongside Permission: data (tuple/attribute CRUD, plus the separate /v1/tenants/{tenant_id}/relationships/write and .../relationships/delete paths), schema (write, partial-write, read and list .perm files), tenancy (multi-tenant create/list/delete), bundle (transactional groups of tuple writes), and watch (server-streaming change feed for cache invalidation).

Consistency model: snap tokens

Permify's answer to the Zanzibar "new-enemy" problem is the snap token — a server-issued encoded timestamp returned on every data/write and bundle/run. Pass it in subsequent check calls to force the evaluator to read at-or-after that snapshot. From proxy-docs.permify.co/operations/snap-tokens.md: snap tokens deliver "consistency and performance" by enabling snapshot reads where "access control is evaluated at a consistent point in time" against stored resource timestamps.

The doc does not explicitly use Zanzibar's "zookie" terminology, but the model is functionally equivalent. Practical guidance:

  • After a data/write: stash the returned snap token alongside the resource (or in your client cache) and pass it to every downstream check that depends on the write being visible.
  • Calls without a snap token are eligible for cache hits and may serve stale results during replica lag.
  • A blank schema_version resolves to the latest committed schema. Pin it explicitly during multi-step migrations to avoid mid-flight semantics changes.

This is identical in spirit to the consistency enum on SpiceDB (FullyConsistent, AtLeastAsFresh, AtExactSnapshot, MinimizeLatency) — Permify just exposes a single token rather than an enum.

Practical readings:

  • Internal use of the unmodified upstream image (e.g., ghcr.io/permify/permify:v1.7.0 running in your private cluster, no patches) does not trigger AGPL §13.
  • Forking the server for a SaaS product triggers §13 — you must offer source to your users on request.
  • The Apache-2.0 SDK boundary holds for the repos that actually carry an Apache-2.0 LICENSE file — embedding @permify/permify-node or permify-go into a proprietary frontend or backend has no AGPL implications, the same way using a PostgreSQL client driver doesn't taint your app. It does not hold for the Python, PHP and Ruby clients (see the table above): their published packages declare AGPL-3.0, and no LICENSE file exists to contradict that.
  • Compared to peers: OpenFGA is Apache-2.0 throughout (no §13 concern), SpiceDB is Apache-2.0 throughout, Cedar is Apache-2.0 throughout. Permify is the only Zanzibar-style OSS authoriser using AGPL on the server.

FusionAuth's 2025-11-20 acquisition statement commits to "continuing investment in the open-source community" without specifying license terms. Update (verified 2026-08-23): the server LICENSE is unchanged at v1.7.3, and the managed offering has since arrived as FusionAuth FGA By Permify, so the open question is no longer "will it ship" but "will the licence hold". Before signing off on Permify for a regulated deployment, re-read the server LICENSE, the per-package registry license field for every SDK you actually pull (they do not agree with each other), and the FusionAuth roadmap.

Common gotchas

1. AGPL-3.0 on the server is the rule, not Apache — and three of the SDKs are AGPL too. Pinning Permify into an Apache-only dependency policy without a §13 carve-out will fail audit. The server half is solid: github.com/Permify/permify LICENSE opens "GNU AFFERO GENERAL PUBLIC LICENSE, Version 3" at both v1.7.0 and v1.7.3. The SDK half is not — permify-python, permify-php and permify-ruby publish AGPL-3.0 metadata and carry no LICENSE file at all (corrected 2026-08-23; see the licence table above). An audit that trusts "the SDKs are Apache" will find three AGPL packages in the lockfile.
2. In-memory storage is the default, and postgres is the only alternative. Run with --database-engine=postgres for anything beyond local dev — restart loses every tuple. --database-engine=mysql is not an option: v1.7.3 exits at startup with Error: mysql connection is unsupported (corrected 2026-08-23). The one mercy is that an unrecognised or typo'd engine name fails closed the same way rather than silently falling back to in-memory storage.
3. Snap tokens are required for read-after-write consistency. A check call without a snap token is eligible for cache hits and may return stale DENIED immediately after a data/write ALLOWED-creating tuple lands. Stash and forward the token.
4. Docs URL moved. docs.permify.co 301-redirects to fusionauth.io/permify-docs/; the underlying llms.txt index moved to proxy-docs.permify.co/llms.txt. Internal links written before 2025-11-20 will follow the 301 cleanly but bookmarks need refreshing.
5. SDK lag is far worse than one patch, and it is per-language — corrected 2026-08-23. Against server v1.7.3 the published clients are: npm @permify/permify-node 1.7.3, PyPI permify 1.7.2, NuGet Permify 1.6.10, Packagist permify/permify-php 1.5.4, RubyGems permify 1.5.4. permify-php has not been committed to since 2026-01-15 and permify-ruby since 2026-01-21. Check the registry for the language you actually use; do not generalise from npm.
6. Docker image is on GHCR, not Docker Hub primarily. ghcr.io/permify/permify is canonical; docker.io/permify/permify mirrors the same tags (at 2026-08-23: latest, v1.7.3, v1.7.3-arm64, v1.7.3-amd64; the v1.7.0 tags were current at the May 2026 baseline) — see hub.docker.com/v2/repositories/permify/permify/tags/ for the full list.
7. The permify-cli repo is stale. Last pushed 2024-04-19; the active CLI ships inside the main permify binary as subcommands (permify validate, permify coverage, permify serve). Use the in-tree CLI, not the standalone permify-cli repo.
8. FusionAuth integration has shipped — corrected 2026-08-23. The 2025-11-20 post did promise "a formal announcement of the fully integrated offering and streamlined pricing model in early 2026", but the combined product was already live under the name FusionAuth FGA By Permify before this entry was written: FusionAuth published a working Bulk Check API tutorial for it on 2026-04-06 and dates that endpoint to December 2025, and docs.permify.co now serves "FGA Documentation" under fusionauth.io/permify-docs/. What is still missing is public pricing — FusionAuth's pricing page carries no separate FGA line, so ask for a quote rather than assuming the self-serve tiers cover it.
9. The Go floor is 1.25.7, not 1.26.3 — corrected 2026-08-23. PR #2959 (security/bump-go-1.26.3) in v1.7.0 bumped the Dockerfile builder image to golang:1.26.3-alpine; v1.7.1 bumped it again to 1.26.4-alpine and v1.7.3 to 1.26.5-alpine. The module's own go directive has read go 1.25.7 continuously from v1.6.10 through v1.7.3, and a 1.25.7 toolchain builds v1.7.3 (verified by go install). Nothing here forces a 1.26 upgrade on consumers of permify-go.

Why Permify (when to pick it over peers)

  • You want ABAC rules inside a ReBAC graph in one decision step rather than running OPA next to OpenFGA/SpiceDB.
  • You're comfortable with AGPL on the server (internal use, no SaaS exposure of a modified fork).
  • You want FusionAuth as the commercial backstop rather than Okta (OpenFGA) or AuthZed (SpiceDB) or Amazon (Cedar/AVP).
  • The in-tree CLI subcommands — permify validate, coverage and ast — are concrete authoring-UX wins for teams that hand-edit .perm files daily. Caveat added 2026-08-23: the vscode-perm extension has not been committed to since 2024-06-09 ("build: update to version 0.1.0"). Treat it as unmaintained rather than as a reason to choose Permify.

Avoid Permify if:

  • Your dependency policy bans AGPL outright (use OpenFGA or SpiceDB instead).
  • You need SMT-verifiable policies (use Cedar).
  • You need a long-tenured managed offering today (use Auth0 FGA or AuthZed Cloud).
