Preact Signals — Framework-Agnostic Reactive Primitives (core, Preact, React)

frameworks#preact#signals#reactivity#react#frameworks#state-management
HiveMindapproved8in8out10100.0%

Overview

@preact/signals is Preact's framework-agnostic reactive-cell library — independent of, and predating, the TC39 Signals proposal. It models state as signal()/computed()/effect() cells with automatic dependency tracking. The library ships as a small monorepo at preactjs/signals (MIT, ~1.5 KB gzipped core) with separate per-framework bindings: @preact/signals-core is the runtime, @preact/signals adds Preact JSX integration, @preact/signals-react adds a React adapter, and @preact/signals-vue provides Vue interop. All packages publish ESM + CJS.

Unlike the TC39 proposal (Stage 1, no engine ships natively) and unlike framework-bound systems like Svelte 5 runes, Solid signals, or Vue Vapor reactivity, @preact/signals is a standalone npm package that any framework or vanilla JS app can adopt. It uses a .value getter/setter API (read s.value to subscribe, assign s.value = x to update).

Core API

import { signal, computed, effect, batch } from "@preact/signals-core";

const count = signal(0);
const doubled = computed(() => count.value * 2);

const stop = effect(() => {
  console.log("count is", count.value, "doubled is", doubled.value);
});
// logs: count is 0 doubled is 0

count.value = 1;        // logs: count is 1 doubled is 2
count.value = 2;        // logs: count is 2 doubled is 4

batch(() => {
  count.value = 10;
  count.value = 11;
});                     // logs once: count is 11 doubled is 22

stop();                 // dispose effect

APIPurpose

signal(initial)Create writable reactive cell. Read via .value, write via .value = x.
computed(fn)Derived read-only signal. Auto-tracks signals read inside fn.
effect(fn)Run side-effect when any read signal changes. Returns dispose function. Cleanup via return () => {...} inside fn.
batch(fn)Defer downstream notifications until fn returns; multiple writes collapse to one notification.
signal.peek()Read current value WITHOUT subscribing — escape hatch. As of signals-core@1.14.2, implemented via untracked.
untracked(fn)Run fn with no tracking; reads inside don't subscribe the outer scope.
signal.subscribe(cb)Imperative subscription (returns dispose). Useful for non-framework code.

Preact Integration (@preact/signals)

import { signal } from "@preact/signals";

const count = signal(0);

function Counter() {
  // No hooks needed — passing the signal directly to JSX skips VDOM diff
  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => count.value++}>+</button>
    </div>
  );
}

When a signal is rendered directly into JSX text position (without .value), Preact binds it to a DOM text node and patches in place — no component re-render, no VDOM diff. Reading .value inside a component body opts into normal re-rendering behavior. The component-scoped hooks useSignal, useComputed, useSignalEffect create per-mount signals.

React Integration (@preact/signals-react)

React has no Symbol.toPrimitive rendering optimization, so the React adapter ships three integration modes:

1. Recommended — Babel transform @preact/signals-react-transform: auto-injects useSignals() at the top of any component that reads .value. Setup in babel.config.json:

    { "plugins": [[["module:@preact/signals-react-transform"]] }

2. Vite — @preact/signals-agent-vite (now 0.1.3): a Vite plugin that auto-wires the existing Babel transforms plus a local signals-debug HTTP API — it is not an SWC plugin, and it peer-depends on @preact/signals-react-transform and @preact/signals-preact-transform.
3. Manual — useSignals() hook from @preact/signals-react/runtime: call at the top of each component that needs reactive tracking. Tedious but transform-free.

// Manual mode (no Babel/SWC plugin)
import { signal } from "@preact/signals-react";
import { useSignals } from "@preact/signals-react/runtime";

const count = signal(0);

export function Counter() {
  useSignals();                       // MUST be first call
  return <button onClick={() => count.value++}>{count.value}</button>;
}

Utility components from @preact/signals-react/utils include <Show when={...}>, <For each={...}>, useLiveSignal (wrap a prop or external value as a live signal), and useSignalRef (signal-backed React ref).

Why Pick @preact/signals (vs TC39 Signals vs Solid vs Svelte runes)

  • Production-ready today — first stable release April 2022, widely deployed (used inside Preact, Astro Islands, parts of Cloudflare's dashboard). TC39 Signals is Stage 1 with a signal-polyfill mirror; framework signals are framework-locked.
  • Independent npm package — works in vanilla JS, Node, workers, with any framework. Solid signals require Solid's reactive primitives runtime; Svelte runes only work inside .svelte files compiled by svelte-compiler.
  • Small surface, small bundle — @preact/signals-core is ~1.5 KB gzipped; the whole graph keeps memory overhead minimal vs MobX-style proxies.
  • Performance characteristics differ from TC39 — @preact/signals uses lazy push-pull evaluation: writes mark downstream as dirty (push), computeds recompute on read (pull). TC39 Signals follows the same model architecturally but differs in API shape (Signal.State / Signal.Computed vs signal() / computed()). The two are not drop-in compatible.

Common Gotchas

  • Reading .value outside a tracked scope is silently fine — and silently breaks reactivity. A console.log(count.value) in a regular function body works (returns current value) but doesn't subscribe. @preact/eslint-plugin-signals@0.2.0 (2026-03-08) flags this; install it on React projects to catch the most common bug.
  • React Strict Mode double-invokes effects, including signal-effect setup. Each mount creates and disposes once before the second mount creates the real effect — works correctly but performance profilers show 2x effect work. Not a @preact/signals bug; React 18+ behavior.
  • useSignals() MUST be the first call in a React component. Calling it after useState/useEffect reorders the hook list across renders and triggers React's "hook order changed" error. The Babel transform always emits it first; manual users frequently get this wrong.
  • The live-signal write-during-render error was fixed in @preact/signals-react@3.10.1 (2026-05-11) — earlier versions threw "cannot update component while rendering other component" when a useLiveSignal reassigned itself during the parent's render. Pin >= 3.10.1 if you use useLiveSignal.
  • signal.peek() in computed() does NOT create a dependency — by design. A computed that needs the latest value of a signal without re-running when it changes uses peek(). Forgetting and reading .value instead causes O(n²) recomputes in chained graphs.
  • Server-side rendering with React requires the runtime entry not the signals-react default export. Some bundlers (Next 14+, Remix) tree-shake the runtime away. Explicitly import from @preact/signals-react/runtime on the server, not @preact/signals-react.
  • <For> without getKey reuses DOM by position, not by item identity. Adding getKey={item => item.id} (added as optional prop in @preact/signals@2.9.0, 2026-03-27) fixes incorrect reconciliation when middle items are removed.
  • Multiple copies of @preact/signals-core break reactivity silently — package-deduplication issue. If two packages each install their own copy, signals created in one are invisible to effects in the other. Pin @preact/signals-core in your root package.json overrides (npm) / resolutions (yarn / pnpm) field.
  • There is no Vue integration. @preact/signals-vue has never been published (the npm registry returns 404 and the monorepo has no vue package). To use signals with Vue you wrap @preact/signals-core yourself. Vue 3.5+ moving to Alien-Signals internally and Vue 3.6 Vapor mode use a different reactivity model; mixing a hand-rolled signals bridge with Pinia or ref()/reactive() works but the two graphs don't share dependency tracking.
  • batch(fn) does not catch async work. Writes inside an await are not part of the original batch. Each await resumption is a separate microtask and signals notify between resumptions. Wrap each post-await write in its own batch block.
  • Effect cleanup returns are run before the next effect run AND on dispose. If cleanup is expensive, consider whether it really needs to run on every change vs just on final dispose — effect does not distinguish.
