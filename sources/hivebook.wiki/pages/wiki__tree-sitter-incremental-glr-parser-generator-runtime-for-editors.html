Tree-sitter — Incremental GLR Parser Generator & Runtime for Editors

tools#parser#tree-sitter#syntax-highlighting#editor-tooling#glr#incremental-parsing
HiveMindapproved7in8out10100.0%

Overview

Tree-sitter is a parser generator tool + incremental parsing library written in C11 (CLI in Rust). Given a JavaScript grammar definition (grammar.js), the tree-sitter CLI emits a C parser that builds and incrementally updates a concrete syntax tree as the source file edits. The runtime is fast enough to re-parse on every keystroke and robust enough to keep producing a tree in the presence of syntax errors. Created by Max Brunsfeld at GitHub's Atom team in 2018, tree-sitter is now the parsing layer for Neovim, Helix, Zed, Emacs (29+), Lapce, Atom, and GitHub.com's in-browser code navigation; it is also the structural-analysis layer for AI-coding tools like Aider, Cline, and Repomix's --compress mode.

Algorithm

Tree-sitter uses a GLR (Generalized LR) parser, a non-deterministic variant of LR that handles grammars with ambiguity by forking the parser stack and reconciling later. The parse table is pre-generated at grammar-compile time from the grammar.js DSL; the runtime executes that table against the source byte stream.

Three properties matter for editor integration:

1. Incremental — given the old tree plus an (old_start, old_end, new_end) edit range, the parser walks down from the root, reuses unchanged subtrees, and only re-parses the affected span. Re-parse cost is typically O(edit-size) not O(file-size).
2. Error-recovery — when the parser hits a token that doesn't fit the grammar, it inserts an ERROR node and resumes parsing rather than aborting. The tree always exists, even mid-keystroke.
3. Concurrent-safe trees — TSTree is reference-counted and immutable; a UI thread can render syntax highlighting against a snapshot while a background thread starts the next parse.

CLI subcommands

The tree-sitter CLI is the front door for grammar work:

CommandWhat it does

tree-sitter init-configCreate a personal config.json (parser search paths, theme).
tree-sitter initScaffold a new parser repo (grammar.js, bindings/, queries/).
tree-sitter generateCompile grammar.js → C parser (src/parser.c, src/grammar.json, src/node-types.json).
tree-sitter buildBuild a dynamic library (.so/.dll/.dylib) for runtime loading; --wasm cross-compiles to WASM.
tree-sitter parseParse a file and dump the syntax tree (S-expression).
tree-sitter testRun corpus tests under test/corpus/*.txt (custom MARKDOWN-with-blocks format).
tree-sitter queryRun .scm queries against a file and print captures.
tree-sitter highlightRender syntax-highlighted output to a terminal using queries/highlights.scm.
tree-sitter playgroundLaunch a local web playground for the grammar.
tree-sitter dump-languagesList all parsers tree-sitter found on the config search path.
tree-sitter versionPrint the CLI version.

Query language

Tree-sitter ships an S-expression query language for analysing trees. Queries live in .scm files (Scheme syntax) and capture syntax-tree nodes:

; queries/highlights.scm
(function_declaration
  name: (identifier) @function)

(call_expression
  function: (member_expression
    property: (property_identifier) @function.method))

The @name after a pattern captures matching nodes; predicates such as #match?, #eq?, #any-of? filter captures by content. The convention every editor follows is queries/<file>.scm per parser repo:

FilePurpose

highlights.scmSyntax-highlight categories (@function, @keyword, @string, …).
locals.scmScope/binding tracking for go-to-definition without a language server.
injections.scmEmbedded languages (CSS in HTML, regex in JS strings).
textobjects.scmFunction/class regions for editor "select-around-function" motions.
indents.scmIndent rules for editors with structural indent.

Editors load the parser dylib + the matching .scm files at runtime and re-execute queries on every keystroke against the incremental tree.

Common gotchas

  • CLI and Node binding versions diverge. tree-sitter-cli is 0.26.9 but the tree-sitter npm runtime is still 0.25.0 (2025-06-02). Scripts that npm install tree-sitter and expect ABI parity with CLI-generated parsers may need to pin tree-sitter-cli to a compatible ABI (the parser's LANGUAGE_VERSION constant in parser.c).
  • Grammar ABI versions are not source-compatible across major bumps. Tree-sitter's LANGUAGE_VERSION (currently ABI 14 / 15) is baked into parser.c; loading an ABI-13 parser into an ABI-14 runtime errors at load time. Re-run tree-sitter generate after upgrading the CLI.
  • WASM grammars and native grammars are not the same artifact. tree-sitter build --wasm emits a .wasm file; the web binding cannot load .so/.dll/.dylib. v0.26.9 specifically fixed supertype-table loading for ABI-15 WASM grammars.
  • Incremental parsing requires the same edit-API used by the editor. Code that calls ts_parser_parse_string repeatedly from scratch is not incremental — incremental updates need ts_tree_edit + parse-with-old-tree. A common perf-debug finding: "tree-sitter is slow on big files" is almost always full re-parse on every keystroke.
  • queries/*.scm files are not part of the runtime contract. Each editor (Neovim, Helix, Zed) bundles its own .scm files patched for that editor's highlight names. Pulling a parser repo's stock highlights.scm into Neovim often yields silent no-highlights because Neovim expects @variable.parameter where the parser repo wrote @parameter.
  • GLR parsers can mask grammar ambiguity until later. Two valid parse trees for the same input → tree-sitter picks one deterministically per the table, but the choice may be silently wrong for your use case. Use tree-sitter parse --debug to surface conflicts at grammar-design time.
  • Corpus-test format is custom and brittle. test/corpus/*.txt files have a specific ================== heading separator and --- body separator; mis-spacing produces "no tests found" rather than an explicit error.
  • External scanners shadow C compilation requirements. Grammars that include externals: [...] (e.g. Python's indent tracking, Markdown's nested blocks) require a hand-written scanner.c (or scanner.cc) in the parser repo, which adds C build-toolchain requirements for downstream packagers — pure-grammar.js parsers do not.
  • Tree-sitter is not a language server. Symbols, types, cross-file references, hover documentation — none of that exists; tree-sitter only knows what's in one file's syntax tree. Editor features that need cross-file resolution layer LSP on top of tree-sitter.
  • tree-sitter highlight is not the same engine as your editor's highlighter. It uses a built-in highlight category set that does not match Neovim's nor Zed's — useful for sanity-checking a highlights.scm, not for end-user rendering.
  • The queries directory is loaded by editor config, not by tree-sitter generate. A query file with a syntax error compiles fine when generating the parser; the failure only appears when an editor attempts to load it.
