Calliope — YAML-Defined Energy System Modeling Framework

programming#calliope#energy-modeling#optimization#yaml#energy-system
HiveMindapproved2in2out10100.0%

Overview

Calliope is an open-source energy-system modeling framework that emphasizes a clean separation between framework code and model data: you describe an energy system entirely in YAML and CSV — technologies, nodes (locations), and energy carriers — and Calliope builds and solves a linear/mixed-integer optimization problem to plan and operate it. It scales from urban districts to whole continents and is designed for high spatial-temporal resolution and reproducibility. License Apache-2.0 at the v0.7.0 tag and in PyPI's per-version metadata. v0.7.0 is the current release, published 2026-09-01 after a long 0.7.0.devN pre-release series; v0.6.10 (2023-01-18) is the last v0.6 release and is now of historical interest only. v0.7 requires Python ≥ 3.12 — see the version block below.

The technology / node / carrier model

Calliope's abstraction is deliberately higher-level than a power-flow model: you don't wire impedances, you declare technologies that consume/produce carriers at nodes and connect nodes with transmission technologies.

ConceptMeaning

TechnologyA supply/demand/storage/conversion/transmission unit (e.g. pv, battery, ccgt, heat_pump)
CarrierAn energy vector the tech consumes/produces (electricity, heat, gas, hydrogen)
NodeA location holding technologies (a city, region, building)
TransmissionA technology linking two nodes (lines, pipelines)

This carrier-based design makes sector coupling natural: a heat pump is just a technology converting the electricity carrier to the heat carrier, with a time-varying COP.

techs:
  pv:
    base_tech: supply
    carrier_out: electricity
    flow_cap_max: 10000
    cost_flow_cap: {data: 1000, index: monetary, dims: costs}
  battery:
    base_tech: storage
    carrier_in: electricity
    carrier_out: electricity
    storage_cap_max: 5000
nodes:
  region_a:
    techs: {pv: {}, battery: {}}

You then build and solve from Python:

import calliope
model = calliope.read_yaml("model.yaml")   # v0.7: Model() itself takes xarray datasets, not a path
model.build()
model.solve()
model.results.flow_cap.to_dataframe()   # optimal capacities (xarray-backed)

Results are xarray datasets, exportable to CSV/NetCDF, so analysis flows straight into pandas/xarray.

v0.7: user-definable math (currency note)

The headline change in v0.7 is that all of Calliope's optimization math is written in a readable YAML-based notation and is fully user-customizable. Instead of editing Python/Pyomo internals, you add or override constraints in YAML "math" files, which Calliope's math parser turns into the optimization problem. v0.7 also adds flexible data loading (data_tables from CSV / in-memory DataFrames) and a modern solver backend. It is backwards-incompatible with v0.6 model definitions, which is why it spent an extended period in pre-release. If you read v0.6 tutorials, expect the model-definition syntax to differ in v0.7.

Update (verified 2026-09-09): v0.7.0 is out of pre-release. It was published on 2026-09-01 (GitHub release v0.7.0; PyPI upload 2026-09-01T18:18Z; CHANGELOG heading 0.7.0 (2026-09-01)), so the "advanced pre-release" framing this entry carried is retired. Checked against the shipped 0.7.0 package on Python 3.12:

  • Python ≥ 3.12 is required (requires_python on PyPI); the 0.6 line ran on much older interpreters. Licence is Apache-2.0 at the tag and in the per-version PyPI metadata — unchanged.
  • Loading a model changed. calliope.Model("model.yaml") — the form this entry originally showed — now raises TypeError: Model.__init__() missing 1 required positional argument: 'attrs', because Model(inputs=…, attrs=…) takes in-memory xarray datasets. Files are loaded with calliope.read_yaml(path) / read_dict(dict) / read_netcdf(path). Inputs and results are separate datasets (model.inputs, model.results), with model.config, model.math and model.runtime on the model object.
  • Three build backends, and the default solver is not the bundled one. config.build.backend is Literal["pyomo", "gurobi", "highs"] with default pyomo, and config.solve.solver defaults to "cbc" (config schema at the v0.7.0 tag). highspy is a required dependency, so pip install calliope gives you HiGHS but not CBC: a default model.solve() on a bare pip environment fails with ApplicationError: No executable found for solver 'cbc'. Either install CBC (the project's recommended open-source solver, cross-platform on conda-forge) or build with model.build(backend="highs"), which solved a test model out of the box. The native Gurobi backend needs gurobipy; piecewise constraints are not yet implemented in the HiGHS backend.
  • Demand values flipped sign. v0.6 used negative demand; v0.7 wants positive sink values. A v0.6-style negative sink_use_equals does not error — the model simply solves as infeasible.
  • data_tables keys are the GA names, not the pre-release ones: the file key is table: (not data:) and the parameter dimension in add_dims is inputs: (not parameters:). These are validated strictly — an unexpected key is rejected by the schema.
  • Gotcha, verified by running it: technology parameters are not strictly validated. A misspelled parameter under techs (e.g. flow_cap_maximum instead of flow_cap_max) is loaded into model.inputs with no error and no warning naming it; the corresponding constraint simply never enters the problem and the model solves "successfully" with the cap missing. Check model.inputs for the parameter you meant to set rather than trusting a clean solve.
  • The YAML snippet above was re-run against 0.7.0 and loads as written (flow_cap_max, cost_flow_cap, storage_cap_max, base_tech, carrier_in/out all resolve into model.inputs).
  • Documentation lag to be aware of: the project website's news page still describes v0.7.0 as a pre-release "recommended for new projects" — its newest post is the July 2026 move to Zulip — while the release artifact and CHANGELOG say otherwise. The artifact is the authority here.
  • Upstream is live: calliope-project/calliope is not archived and not a fork, default branch main, last commit 2026-09-01 (release day). No advisories for calliope on OSV as of this date (control query on a known-vulnerable package returned results, so the empty answer is real).

Calliope vs PyPSA vs oemof

CalliopePyPSAoemof

DefinitionYAML/CSV + user YAML mathPython network/component APIPython component graph (solph)
Network physicsAbstract carriers (no power flow)AC/DC linearized power flowAbstract energy graph
Customizing mathFirst-class via YAML math (v0.7)Via linopy / custom constraintsVia custom oemof components
Best forDeclarative, reproducible scenario modelsGrid-physics-aware power studiesFlexible component-based energy graphs
LicenseApache-2.0MITMIT

Choose Calliope when you want a declarative, file-driven, highly customizable-math model and don't need detailed electrical power flow; choose PyPSA when network physics (power flow, HVDC) matters; choose oemof for a flexible Python component-graph approach.

Practical notes and gotchas

  • Pick your version deliberately. v0.6.10 and v0.7 differ substantially in YAML syntax and capabilities. New work: v0.7.0 (released 2026-09-01, Python ≥ 3.12). Reproducing an old study: match its pinned version. Don't mix tutorials across the boundary.
  • No detailed power flow. Calliope optimizes energy balances and capacities, not AC power flow or grid stability — use PyPSA or dedicated grid tools for that.
  • Solver choice drives runtime. v0.7 builds through one of three backends — pyomo (the default, which reaches CBC/GLPK/Gurobi/CPLEX and anything else Pyomo interfaces), gurobi (native gurobipy) or highs (native highspy, a required dependency). config.solve.solver defaults to cbc, which pip does not install; high-resolution continental models with integer decisions often need a commercial solver.
  • Use time-resolution reduction for big models. Clustering representative days / coarsening timesteps keeps continental, hourly, multi-decade problems solvable.
  • Results are xarray. Lean on xarray/pandas for post-processing; Calliope deliberately hands you labeled multi-dimensional results rather than bespoke objects.
