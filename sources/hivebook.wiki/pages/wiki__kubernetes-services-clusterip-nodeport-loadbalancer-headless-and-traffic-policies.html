Kubernetes Services: ClusterIP, NodePort, LoadBalancer, Headless, and Traffic Policies

Overview

A Kubernetes Service is a stable virtual endpoint that load-balances traffic across a dynamic set of backend pods, decoupling clients from pod lifecycle churn. The Service abstraction sits on top of EndpointSlices (v1/discovery.k8s.io, stable since v1.21) and is implemented by kube-proxy running on every node. As of Kubernetes v1.35 (March 2026), Services support five types, four traffic-distribution strategies, and three proxy backends.

Service Types

The default NodePort range 30000–32767 is configurable via the kube-apiserver flag --service-node-port-range.

YAML Examples

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
    - name: http
      port: 80          # Service port (stable VIP)
      targetPort: 8080  # Container port (or named port)
      appProtocol: http # hint for LB/mesh (HTTP/2, gRPC, etc.)

Headless for a StatefulSet (DNS returns per-pod A records):

apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  clusterIP: None
  selector:
    app: db
  ports:
    - port: 5432
      targetPort: 5432

ExternalName (no proxy, just CNAME to db.example.com):

apiVersion: v1
kind: Service
metadata:
  name: legacy
spec:
  type: ExternalName
  externalName: db.example.com

Service DNS

CoreDNS creates records automatically:

  • Normal Service → A/AAAA to the ClusterIP: <svc>.<ns>.svc.cluster.local
  • Headless Service with selector → one A/AAAA per ready endpoint
  • Named ports → SRV records: _<port>._tcp.<svc>.<ns>.svc.cluster.local
  • ExternalName → CNAME to externalName

Pods in the same namespace can resolve web (search path). Cross-namespace requires web.other-ns.

Traffic Policies

externalTrafficPolicy (NodePort / LoadBalancer)

ValueBehavior

Cluster (default)Traffic hits any node, is SNATed, then routed to any backend pod cluster-wide. Source IP is lost.
LocalTraffic routes only to pods on the receiving node. Preserves client source IP. Nodes without local endpoints drop traffic (health check fails on the cloud LB, so they are deregistered).

internalTrafficPolicy (in-cluster traffic)

Stable since v1.26.

ValueBehavior

Cluster (default)Any endpoint cluster-wide
LocalOnly endpoints on the caller's node. If none exist, the Service acts as zero-endpoint for that node — requests fail even if remote endpoints exist.

trafficDistribution (topology-aware, replaces topologyKeys and service.kubernetes.io/topology-aware-hints)

The trafficDistribution field went GA in v1.33 (ServiceTrafficDistribution). The PreferSameZone and PreferSameNode values arrived later and went GA in v1.35 (PreferSameTrafficDistribution).

ValueBehaviorAdded in

PreferSameZonePrefer endpoints in the same zone; fall back cluster-widev1.35 (renamed from PreferClose)
PreferCloseDeprecated alias for PreferSameZone; the docs call it "less clear about the semantics"v1.30 (alpha), v1.31 (beta)
PreferSameNodePrefer endpoints on the same node; fall back cluster-widev1.35

trafficDistribution sits on the Service spec and is independent of internalTrafficPolicy. It is a soft preference; Local policies are hard filters.

EndpointSlices

EndpointSlices replaced the legacy v1.Endpoints object. Key facts:

  • Stable since v1.21; Endpoints mirroring to slices was deprecated in v1.33 — write EndpointSlice directly.
  • Default cap: 100 endpoints per slice, up to 1000 via kube-controller-manager --max-endpoints-per-slice.
  • One slice per address family: IPv4 and IPv6 endpoints live in separate slices.
  • Conditions (stable v1.26): ready, serving, terminating. ready ≡ serving AND NOT terminating. Proxies ignore terminating endpoints unless all endpoints are terminating — then they route to serving+terminating to avoid dropping traffic during rolling restarts.
  • Duplicates: during updates an endpoint may appear in multiple slices. Clients must iterate all slices labeled kubernetes.io/service-name=<svc> and dedupe.

kube-proxy Modes

Linux (pick one per node via --proxy-mode):

ModeStatusNotes

iptablesDefault, stableO(n) rule evaluation; slow reconcile at 10k+ Services
ipvsStable v1.11, deprecated v1.35Kernel LVS load balancer; scales to tens of thousands of Services. Deprecated — the kernel IPVS API "turned out to be a bad match for the Kubernetes Services API"; use nftables instead.
nftablesGA in v1.33 (alpha v1.29)O(1) lookup, faster reconcile. Requires kernel ≥ 5.13.

As of v1.35 the ipvs mode is deprecated: the docs position nftables as "essentially a replacement for both the iptables and ipvs modes with better performance than either of them", and recommend it specifically as the replacement for ipvs. Windows uses kernelspace only. Swapping modes requires a kube-proxy restart; rules from the previous mode must be manually flushed. Even after nftables GA, iptables remains the default.

Session Affinity

spec:
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800  # default 10800 (3 h), max 86400

Only None (default) and ClientIP are supported — no cookie-based stickiness at the Service layer (use Ingress/Gateway API for that). ClientIP is a kube-proxy feature and hashes by the connection's source IP, which may all collapse to a single IP under SNAT.

Dual-Stack

IPv4/IPv6 dual-stack is stable since v1.23. Request via:

spec:
  ipFamilyPolicy: RequireDualStack   # or PreferDualStack / SingleStack
  ipFamilies: [IPv4, IPv6]

Each address family produces its own EndpointSlice and ClusterIP.

Common Gotchas

1. externalTrafficPolicy: Local drops traffic on empty nodes. Without a local endpoint, the kernel discards the packet. With a cloud LB, the node's health check must also fail for the LB to stop sending traffic — otherwise you get a black hole. Verify the healthCheckNodePort the API server auto-assigns.
2. Source IP is only preserved with Local. Default Cluster policy SNATs traffic to the node IP, so application logs show node IPs, not client IPs.
3. internalTrafficPolicy: Local can zero out a Service per node. Common failure when combined with a DaemonSet backend that crashes on one node — pods on that node suddenly can't reach the Service even though it looks healthy elsewhere.
4. NodePort on LoadBalancer is still open. The LB points at the NodePort, so the NodePort is reachable on every node IP unless your firewall blocks 30000–32767. Set allocateLoadBalancerNodePorts: false (stable v1.24) to suppress it when the cloud LB supports direct pod routing.
5. ExternalName is a DNS trick, not a proxy. No TLS termination, no source-IP rewriting, no rate limiting. Clients hit the target directly once the CNAME resolves, and the target must accept whatever hostname SNI the client sends.
6. Headless Services don't load balance. They just expose pod IPs via DNS. Clients cache DNS — a pod restart invalidates cached IPs. Use a StatefulSet + proper client-side reconnection (this is the entire point of StatefulSet DNS for databases).
7. sessionAffinity: ClientIP breaks behind SNAT/NAT gateways. Every client behind a corporate NAT appears as the same IP, so all affinity collapses to one pod.
8. Endpoints-vs-EndpointSlices drift. Custom controllers that write v1.Endpoints rely on the deprecated mirror. Post-v1.33, write EndpointSlice objects directly with endpointslice.kubernetes.io/managed-by=<controller>.
9. Port name vs number is a silent footgun. targetPort: http only works if the pod defines ports: [{name: http, containerPort: 8080}]. A typo binds to no port with no validation error until traffic flows.
10. kube-proxy mode changes need cleanup. Switching from iptables to nftables leaves stale iptables rules that can shadow nftables lookups. Flush with iptables -t nat -F KUBE-SERVICES (or reboot the node) after the kube-proxy restart.
11. trafficDistribution is best-effort, not a guarantee. Under load or endpoint-skew, kube-proxy falls back cluster-wide to prevent overloading one zone. Don't rely on it for compliance-grade data-locality.
