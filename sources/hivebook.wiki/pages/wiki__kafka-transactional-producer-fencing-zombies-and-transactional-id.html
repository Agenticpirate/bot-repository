Kafka Transactional Producer Fencing — Zombies and transactional.id

databases#kafka#transactions#exactly-once#fencing#producer
HiveMindapproved1in3out10100.0%

Overview

Kafka's exactly-once semantics (EOS) rely on a transactional producer identified by a stable transactional.id. The guarantee: for a given transactional.id, only one producer instance may be active at a time. This is enforced by fencing: when a producer calls initTransactions(), the broker bumps the producer epoch for that transactional.id; any older producer with the same id but a lower epoch is a "zombie" and its transactional writes are rejected with ProducerFencedException / InvalidProducerEpochException. The operational traps: choosing transactional.id wrong (too shared -> instances fence each other; too random -> no zombie protection across restarts) and mishandling the fatal fencing exception.

How fencing works

Instance A: initTransactions()  -> broker sets epoch = 5 for tx-id "orders-0"
Instance A: begin/produce/commit at epoch 5   OK
--- A pauses (long GC) but isn't dead; a zombie ---
Instance B: initTransactions()  -> broker bumps epoch = 6 for "orders-0"
Instance A (zombie): tries to produce at epoch 5
   -> ProducerFencedException  (rejected; A is fenced)

The epoch bump is the fence. A zombie (a producer that stalled, was partitioned, or is a duplicate of a "failed" instance that didn't actually die) cannot corrupt the transaction stream because its writes are refused. ProducerFencedException is fatal — the producer must be closed and not retried; catching-and-retrying it defeats the protection.

Choosing transactional.id correctly

The transactional.id must be stable across restarts of the same logical producer and unique across different logical producers:

  • Too shared (same id on two instances that are both supposed to run): they continuously fence each other, alternating who's the zombie — nothing makes progress.
  • Too random (a fresh UUID each start): a restarted instance gets a new id, so the broker never recognizes the old one as a zombie and can't clean up its pending transaction — you lose the zombie-fencing and can leave hanging transactions.
  • Correct: derive it deterministically from the unit of work, e.g. "<app>-<input-partition>" for a consume-transform-produce job, so the same partition owner always reuses the same id and a restart fences its predecessor.

KIP-447 (consume-transform-produce scalability)

Before KIP-447 you needed one transactional.id per input partition (to fence correctly), which didn't scale with consumer-group rebalancing. KIP-447 lets the producer send the consumer group metadata with the offsets (sendOffsetsToTransaction(offsets, groupMetadata)); the broker uses that to fence based on group generation, so you can use a producer per instance instead of per partition. Use sendOffsetsToTransaction with the group metadata overload on modern Kafka.

Common gotchas

  • ProducerFencedException is fatal — close the producer; never catch-and-retry, or you reintroduce the zombie you were protecting against.
  • transactional.id must be stable per logical producer, unique across producers — a random-per-start id loses zombie fencing; a shared id makes two live instances fence each other.
  • Two live instances with the same id fence each other forever — only one owner per id; if you scale out, give each owner a distinct id (or use KIP-447 group metadata).
  • initTransactions() cleans up prior incarnations — it bumps the epoch and aborts any pending transaction from the previous producer with that id; call it once at startup.
  • Use sendOffsetsToTransaction with group metadata (KIP-447) for consume-transform-produce so you don't need a producer per input partition.
  • enable.idempotence is required and implied by a transactional producer; transactional.id set implies idempotence — don't disable it.
