pgvector 0.8.x — Postgres vector similarity extension

Overview

pgvector is a Postgres extension that adds vector similarity search to PostgreSQL via four data types (vector, halfvec, sparsevec, bit), six distance operators, and two approximate-nearest-neighbor (ANN) index methods (HNSW and IVFFlat). It supports Postgres 13 through 18 and is the de-facto on-Postgres vector store for retrieval-augmented generation workloads, complementing dedicated vector databases for teams that already operate Postgres. Current release is 0.8.6 (2026-07-29); 0.8.2 (2026-02-25) — which fixed a parallel-HNSW build buffer overflow and added Postgres 18 EXPLAIN compatibility — was current at the May 2026 baseline of this entry. 0.8.3 fixed possible index corruption with HNSW vacuuming, so 0.8.4+ is the practical floor for any production HNSW index — see the dated update block below. The 0.7.0 release (2024-04-29) added halfvec (16-bit float vectors), sparsevec, and binary_quantize; 0.8.0 (2024-10-30) added iterative index scans, the most important operational feature for filtered queries.

This entry covers the surface that production RAG and similarity-search code actually touches: the four types and six operators, both index methods with their parameters, iterative scans with their relaxed/strict ordering trade-offs, binary-quantization re-ranking, hybrid search with Postgres full-text, and the gotchas that have caused real outages. For multi-database trade-offs, see vector databases comparison.

Installation

# From source (Linux/Mac), using a tagged release
cd /tmp && git clone --branch v0.8.6 https://github.com/pgvector/pgvector.git
cd pgvector && make && sudo make install

# Docker (covers Postgres 13-18)
docker pull pgvector/pgvector:pg18-trixie

# Homebrew
brew install pgvector

# Debian / Ubuntu
sudo apt install postgresql-18-pgvector

Then in any database:

CREATE EXTENSION vector;

Hosted Postgres providers that ship pgvector pre-installed include AWS RDS / Aurora, Google Cloud SQL / AlloyDB, Azure Database for PostgreSQL, Supabase, Neon, Crunchy Bridge, Render, Railway, DigitalOcean Managed Postgres, and Heroku Postgres (list re-checked 2026-08-22; Tembo was dropped from it — tembo.io now sells a cloud for running coding agents, not managed Postgres. Check the per-provider docs for the exact pgvector version available, since hosted versions usually trail upstream by 1-3 minor releases).

For in-process / embedded Postgres (Node.js, Bun, Deno, or the browser), PGlite bundles pgvector as a 42.9 KB plugin (@electric-sql/pglite/vector) — useful for agent sandboxes, local-first apps, or test fixtures that need vector search without a Postgres server.

The hard 2,000-dim cap on indexed vector columns is the most-cited friction point: anyone using OpenAI text-embedding-3-large (3,072 dims) must use halfvec or reduce dims via the dimensions parameter at embedding time.

    embedding vector(1536)              -- OpenAI text-embedding-3-small

    id bigserial PRIMARY KEY,

    id bigserial PRIMARY KEY,
    embedding sparsevec(30000)          -- e.g., SPLADE output
);

Distance operators

OperatorDistanceFunction formSmaller = closer

<->L2 (Euclidean)l2_distance(a, b)yes
<#>Negative inner productinner_product(a, b)negative: ORDER BY ascending picks max IP
<=>Cosine distancecosine_distance(a, b)yes
<+>L1 (Manhattan / taxicab)l1_distance(a, b)yes (added in 0.7.0)
<~>Hamming distancehamming_distance(a, b)yes (bit only)
<%>Jaccard distancejaccard_distance(a, b)yes (bit only)

The <#> operator returns the negated inner product so ORDER BY a <#> b LIMIT k returns the top-k by raw inner product. If your embeddings are L2-normalized (unit length), cosine distance and inner product produce identical orderings - prefer inner product (<#>) because it's slightly cheaper and pgvector skips the normalization step.

Helper functions added in 0.7.0:

SELECT l2_normalize('[3,4]'::vector);                  -- [0.6, 0.8]
SELECT subvector('[1,2,3,4,5]'::vector, 2, 3);         -- [2, 3, 4]
SELECT binary_quantize('[1, -2, 3]'::vector);          -- 101 (bit type)
SELECT '[1,2,3]'::vector || '[4,5,6]'::vector;         -- concat (0.7.0+)

HNSW index

HNSW (Hierarchical Navigable Small World, Malkov & Yashunin 2016) builds a multi-layer proximity graph. It has the best recall/speed trade-off in pgvector and is the default choice unless you have specific build-time or memory constraints.

CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

Parameters:

  • m (default 16) - max bidirectional links per node per layer. Higher = better recall and larger index size.
  • ef_construction (default 64) - candidate list size during build. Higher = better recall + slower builds. Must be >= 2 * m.
  • hnsw.ef_search (default 40, query-time GUC) - candidate list size during search. Set per session: SET hnsw.ef_search = 100;

Operator classes per type:

sparsevecsparsevec_l2_opssparsevec_ip_opssparsevec_cosine_opssparsevec_l1_ops
bitbit_hamming_opsbit_jaccard_ops

Build memory. HNSW builds significantly faster when the entire graph fits in maintenance_work_mem. Set this before bulk loads:

SET maintenance_work_mem = '8GB';
CREATE INDEX CONCURRENTLY ON items USING hnsw (embedding vector_cosine_ops);

If insufficient, Postgres logs NOTICE: hnsw graph no longer fits into maintenance_work_mem after 100000 tuples. Building will take significantly more time. Estimate: roughly (4 * dims + 32 * m) * rows bytes for vector, halve for halfvec. For a 1M-row, 1536-dim, m=16 index that is roughly 6.5 GB.

Parallel builds. Added in 0.6.0 and now hardened (the 0.7.4 lock-correctness fix and the 0.8.2 buffer-overflow fix both targeted parallel HNSW builds; the separate HNSW vacuum corruption bug was fixed in 0.8.3). Postgres uses max_parallel_maintenance_workers (default 2) - raise it for faster bulk index builds. HNSW's parallelism advantage means it usually finishes index creation faster than IVFFlat for large tables despite the higher per-tuple work.

No training step. Unlike IVFFlat, HNSW indexes can be created on empty tables and grown by INSERTs without a re-cluster. This matters for multi-tenant or streaming-ingest setups.

IVFFlat index

IVFFlat partitions vectors into k-means clusters at index-build time, then scans only the nearest probes clusters at query time. Faster to build and lower memory than HNSW, but lower recall at the same speed.

CREATE INDEX ON items USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 1000);

Parameters:

  • lists (build-time, no default) - number of clusters. Pgvector recommends rows / 1000 up to 1M rows, then sqrt(rows) above 1M. Build the index after loading representative data; IVFFlat needs samples to fit centroids.
  • ivfflat.probes (default 1, query-time GUC) - clusters to scan per query. Start at sqrt(lists) and tune. SET ivfflat.probes = 32;

Supported types: vector, halfvec, bit. No sparsevec IVFFlat support - HNSW only.

When to choose IVFFlat over HNSW: shrinking-window or full-rebuild ingestion where index build time matters more than query latency, or memory-constrained environments where HNSW's graph overhead is prohibitive. For most steady-state RAG, HNSW is better.

Iterative index scans (0.8.0+)

The largest pre-0.8.0 footgun: ANN indexes return at most ef_search (HNSW) or probes * lists_avg (IVFFlat) candidate rows, and a WHERE filter is applied after the index scan. A selective filter (e.g. WHERE user_id = 42) often left far fewer than LIMIT k matches, silently truncating results.

Iterative scans (0.8.0, 2024-10-30) re-enter the index when the candidate pool runs short. Set per session before the query:

SET hnsw.iterative_scan = strict_order;     -- exact distance order
-- or
SET hnsw.iterative_scan = relaxed_order;    -- better recall, slight reordering allowed
SET hnsw.max_scan_tuples = 50000;           -- ceiling on tuples visited (default 20000)
SET hnsw.scan_mem_multiplier = 4;           -- multiple of work_mem (default 1)

SELECT id FROM items
WHERE user_id = 42
ORDER BY embedding <-> $1
LIMIT 10;

relaxed_order lets pgvector return results out of distance order in exchange for better recall on heavily-filtered queries. To get strict order on top of relaxed-mode results, wrap in a materialized CTE and re-sort with ORDER BY distance + 0 (the + 0 is required to defeat the planner inlining the materialization on Postgres 17+):

WITH relaxed AS MATERIALIZED (
  SELECT id, embedding <-> $1 AS dist FROM items
  WHERE user_id = 42 ORDER BY embedding <-> $1 LIMIT 100
)
SELECT * FROM relaxed ORDER BY dist + 0 LIMIT 10;

IVFFlat has the equivalent: SET ivfflat.iterative_scan = relaxed_order; plus SET ivfflat.max_probes = 100; to bound work.

Binary quantization (memory-bound RAG)

binary_quantize(vector) returns a bit (one bit per dimension, sign-quantized). At 1536 dims, an OpenAI embedding shrinks from 6,144 bytes (vector) to 192 bytes (bit) - 32x smaller. The standard production pattern is two-stage retrieval: HNSW recall on a binary-quantized expression index, then exact re-rank on the full-precision column.

-- Expression index over the bit projection
CREATE INDEX ON items USING hnsw (
  (binary_quantize(embedding)::bit(1536)) bit_hamming_ops
);

-- Two-stage query: shortlist via Hamming, re-rank via L2 on full vector
SELECT id, embedding <-> $1 AS dist
FROM (
  SELECT id, embedding
  FROM items
  ORDER BY binary_quantize(embedding)::bit(1536) <~> binary_quantize($1)::bit(1536)
  LIMIT 200
) shortlist
ORDER BY embedding <-> $1
LIMIT 10;

Recall typically lands in the 90-95 percent range with 200-row shortlists for cosine-trained embeddings (e.g. OpenAI, Cohere, Voyage), and the index is 32x smaller, dramatically reducing the maintenance_work_mem HNSW build target.

halfvec is the middle ground: 2x smaller than vector with negligible recall loss in practice. Many production setups now default to halfvec for the storage column with no re-ranking step at all.

Hybrid search with Postgres full-text

The recommended hybrid pattern combines vector similarity (semantic) with Postgres full-text search (keyword/lexical). Index both sides, then merge ranks with Reciprocal Rank Fusion (RRF):

WITH semantic AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank
  FROM items ORDER BY embedding <=> $1 LIMIT 60
),
lexical AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank_cd(content_tsv, query) DESC) AS rank
  FROM items, plainto_tsquery('english', $2) query
  WHERE content_tsv @@ query
  ORDER BY ts_rank_cd(content_tsv, query) DESC LIMIT 60
)
SELECT COALESCE(s.id, l.id) AS id,
       (1.0 / (60 + COALESCE(s.rank, 1000))) +
       (1.0 / (60 + COALESCE(l.rank, 1000))) AS rrf_score
FROM semantic s FULL OUTER JOIN lexical l USING (id)
ORDER BY rrf_score DESC LIMIT 10;

The 60 is the standard RRF k constant from the original Cormack/Clarke/Buettcher paper. RRF is parameter-free and robust against the wildly different score distributions of cosine distance and ts_rank_cd.

Filtering with WHERE

For low-cardinality filters (WHERE deleted = false, WHERE org_id = 42), the cleanest approach is a partial index:

CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
WHERE deleted = false;

CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops)
WHERE org_id = 42;          -- one per high-traffic tenant

For high-cardinality filters, partition the table by the filter column (Postgres declarative partitioning) and rely on partition pruning to scan only relevant per-partition HNSW indexes. For everything in between, use iterative scans (0.8.0+) so the index re-enters when the post-filter result is short. Pre-0.8.0 the only general escape was raising ef_search enormously, which hurt unfiltered query latency.

Common gotchas

1. 2,000-dim HNSW cap on vector - OpenAI text-embedding-3-large (3,072 dims) must use halfvec(3072) (4,000 cap), binary_quantize, or dimensions reduction at embedding time. Same applies to Voyage voyage-3-large (1,024 dims fits, but voyage-3 extended also exists). Check your embedding model's native dim before deciding the column type.
2. <#> returns negative inner product - ORDER BY embedding <#> $1 LIMIT 10 correctly returns top-IP, but if you alias the result as score, the value is negative. Negate at the SELECT list ((embedding <#> $1) * -1 AS ip_score) for human-readable scores.
3. L2-normalized embeddings: prefer <#> over <=> - cosine distance is 1 - inner_product for unit vectors, so they produce identical orderings. Inner product is slightly cheaper and avoids the normalization step. Verify your embedding API returns normalized vectors (OpenAI, Voyage, Cohere v3 all do; some open-source models do not).
4. IVFFlat needs data before index creation - building IVFFlat on a near-empty table produces poor centroids. Bulk-load 10k-100k representative rows, build the index, then continue inserting. HNSW does not have this constraint.
5. ef_search < LIMIT silently truncates - if LIMIT 100 but hnsw.ef_search = 40 (default), only 40 candidates are evaluated and results are short. Always set ef_search >= LIMIT * 2 for top-k queries.
6. Filter selectivity + no iterative scans = wrong results - pre-0.8.0 a filtered query like WHERE org_id = 42 ORDER BY embedding <-> $1 LIMIT 10 could return 0-3 results when the org owned only a thin slice of the table, even if hundreds of relevant matches existed. Upgrade to 0.8.0+ and SET hnsw.iterative_scan = relaxed_order (or use a partial index per high-traffic filter value).
7. relaxed_order reorders results - if the application assumes strict distance ordering (e.g. visual gallery sorted by similarity), wrap the relaxed query in a materialized CTE and re-sort with ORDER BY dist + 0 on Postgres 17+ to defeat the inlining optimizer.
8. maintenance_work_mem exhaustion crashes the build - set it explicitly before HNSW creation. Do not set so high that it starves the rest of the server. Estimate (4 * dims + 32 * m) * rows for vector; halve for halfvec.
9. CREATE INDEX CONCURRENTLY doubles build time - use it for production tables that cannot tolerate the AccessExclusiveLock from a normal CREATE INDEX, but plan for ~2x wall-clock time and significantly more maintenance_work_mem pressure.
10. Recall regression after VACUUM FULL - VACUUM FULL rebuilds tables and reclusters HNSW graphs, which can change the empirical recall slightly. Re-tune ef_search against your benchmark after major maintenance.
11. shared_preload_libraries is not required - pgvector loads on first CREATE EXTENSION; do not add it to shared_preload_libraries. Pre-0.6.1 doing so caused segfaults; the entry was kept simple by avoiding it.
12. Logical replication broken pre-0.6.1 - vector columns in publications could fail to replicate. Fixed in 0.6.1 (2024-03-04). On older deployments, upgrade before relying on logical replication for vector tables.
13. Iterative-scan ceiling needs raising on big tables - default hnsw.max_scan_tuples = 20000 is fine for low-millions row counts; on 100M+ tables under heavy filtering, raise to 100000 or higher. Each session can tune independently.
14. Binary quantization re-ranking shortlist size matters - 200 rows is the production default; below 50 rows recall drops sharply, above 1,000 the re-rank step gets slow. Profile against your domain - cluster-tight embeddings (image, code) tolerate smaller shortlists than long-form text embeddings.
15. Postgres 18 EXPLAIN format changed - 0.8.1 fixed Index Searches rendering for the new pg18 EXPLAIN structure; older pgvector on pg18 shows malformed plans. Separately, 0.8.3 fixed a Hamming/Jaccard distance performance regression specific to Postgres 18 — the binary-quantization shortlist below is the pattern that regression hits, so re-measure on 0.8.3+ rather than on 0.8.1/0.8.2. The pg18-AIO subsystem (details) does not yet apply to HNSW index reads but does affect the heap fetches that follow ANN scans on pg18.
16. Embedding-model upgrades change distance distributions - migrating from text-embedding-ada-002 (1,536 dims) to text-embedding-3-small (also 1,536 dims) changes the embedding manifold; do not assume tuned ef_search thresholds carry over. Re-benchmark recall.
17. Batch-generate embeddings, do not loop - one row at a time hammers the embedding-API rate limit and is 10-50x slower per token. Use the OpenAI Batch API (or your provider's equivalent) for backfills above ~10k rows.
18. COPY FROM with vectors needs the [1,2,3] literal format - text-format COPY accepts the bracketed text form; binary-format COPY needs the wire format documented in the pgvector source. Most ORMs handle this automatically; raw \copy from CSV requires the bracketed text in the column.
19. An HNSW index vacuumed on 0.8.0-0.8.2 may already be corrupt - the 0.8.3 fix stops new corruption, it does not repair an index that was damaged before the upgrade. Any autovacuumed table carrying an HNSW index built on 0.8.0-0.8.2 should be treated as suspect: upgrade the extension binaries, run ALTER EXTENSION vector UPDATE, and REINDEX (ideally REINDEX INDEX CONCURRENTLY) the HNSW indexes that were vacuumed on an affected build. Recall that silently collapses on a previously well-tuned index is the symptom to look for.
