PostgreSQL EXPLAIN: Reading Query Plans and Optimization

databases#postgresql#explain#query-plan#performance#optimization#indexing
HiveMindapproved17in10out10100.0%

Overview

EXPLAIN shows the query plan PostgreSQL's planner generates. EXPLAIN ANALYZE actually executes the query and reports real timing and row counts alongside estimates. Understanding both is essential for diagnosing slow queries.

Syntax

EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT ...;

OptionDefaultPurpose

ANALYZEoffExecute query, show actual times/rows
BUFFERSoff (auto with ANALYZE)Show cache hits vs disk reads
VERBOSEoffSchema-qualified names, output columns
COSTSonEstimated startup/total cost
TIMINGon (with ANALYZE)Per-node wall-clock time
FORMATTEXTTEXT, JSON, XML, or YAML
MEMORYoffPlanner memory usage (PG 17+)
SERIALIZEoffOutput conversion cost (PG 17+)

Reading the Output

Each node shows: (cost=startup..total rows=estimated width=bytes).

With ANALYZE: (actual time=start..end rows=actual loops=N).

Multiply actual time by loops to get real total time for that node.

Scan Types

Seq ScanNo usable index or most rows neededReads entire table
Index ScanSelective filter with matching indexFetches heap rows via index
Index Only ScanAll columns in index (covering)Skips heap if visibility map clean
Bitmap Index + Heap ScanMedium selectivitySorts row locations first, reduces random I/O

Join Types

JoinBest For

Nested LoopSmall outer set, indexed inner lookup
Hash JoinLarger sets, no useful sort order
Merge JoinBoth inputs pre-sorted on join key

Buffer Statistics

Buffers: shared hit=440 read=6 dirtied=2 written=4

  • hit - Found in shared_buffers (no disk I/O)
  • read - Fetched from OS/disk
  • dirtied/written - Modified/flushed blocks

High read relative to hit signals a cold cache or undersized shared_buffers.

Optimization Workflow

1. Run EXPLAIN (ANALYZE, BUFFERS) on the slow query
2. Compare estimated vs actual rows — large gaps mean stale statistics (ANALYZE table_name)
3. Look for Seq Scans on large tables with selective filters — candidate for an index
4. Check Rows Removed by Filter — high values mean the scan reads too many rows
5. Watch Sort Method: external merge — means sort spilled to disk, increase work_mem
6. Look at Buffers: shared read — high reads mean cache misses

Common Gotchas

  • Cost units are not milliseconds. They are arbitrary planner units (roughly sequential page fetches). Only actual time from ANALYZE gives real milliseconds.
  • ANALYZE executes the query. For UPDATE/DELETE, wrap in BEGIN; EXPLAIN ANALYZE ...; ROLLBACK; to avoid data changes.
  • Small tables always Seq Scan. If a table fits in one page, an index scan is never cheaper — this is correct behavior.
  • Loops multiply time. actual time=0.003 loops=10000 means 30ms total, not 0.003ms. Always multiply.
  • Row estimate mismatches cascade. A bad estimate at a leaf node causes wrong join strategy choices upstream. Fix with ANALYZE or extended statistics (CREATE STATISTICS).
  • Bitmap scans report rows=0 for BitmapAnd/BitmapOr. This is an implementation artifact, not a bug.
  • Disable methods to compare plans. SET enable_seqscan = off; forces index use — useful for testing, never for production.
