Overview

Expo is an open-source framework for building universal native apps with React. A single TypeScript codebase targets Android, iOS, and the web, with file-based routing (Expo Router), a managed native module system (Expo Modules), a production-grade native UI layer (Expo UI), and a hosted build / submit / OTA-update / workflows backend (Expo Application Services, EAS). The project is MIT-licensed, lives at expo/expo on GitHub (51,821 stars as of 2026-08-25, TypeScript), and is shepherded by 650 Industries, Inc.

Expo's value proposition for agent builders is: write React 19.2 and TypeScript once, ship signed App Store / Play Store binaries without owning a Mac runner or a CI fleet, and push JavaScript-only updates to running clients over-the-air without resubmitting through review. SDK 56 (released 2026-05-21, npm tag latest = 56.0.0 published 2026-05-20T21:57:07Z) was the current stable line at the 2026-05-27 baseline, and the SDK-56-specific sections below describe that release.

Update (verified 2026-08-25): SDK 57 is the current stable line. It was announced 2026-06-30 and npm latest = next = expo@57.0.16 (published 2026-08-24). SDK 57 is deliberately small — it bumps React Native 0.85 → 0.86 and leaves React at 19.2.3; Expo calls it "the easiest Expo SDK upgrade you've ever made" and the upgrade path is npx expo install expo@latest --fix (expo.dev/changelog/sdk-57). Two things to carry over from that post: (a) the first SDK 57 releases inherited a Hermes V1 memory regression that badly inflates memory in apps importing react-native-worklets or react-native-reanimated — fixed in expo@57.0.9 (React Native 0.86.2), so never pin below that; (b) a development-only Hermes V1 startup-time regression (expo/expo#48298) is fixed upstream but not yet released. SDK 57 also raises the minimum Node.js to 22.13.x (SDK 56 required 20.19.x) — the single most likely upgrade blocker in CI.

Versions and Release Cadence

Expo shipped one numbered SDK per ~4 months for several years, but that changed mid-2026: SDK 57 landed six weeks after SDK 56 because React Native now ships six times a year and aims for every second release to carry no user-facing breaking changes, and Expo has started passing those non-breaking React Native bumps straight through as an optional new SDK. Each SDK is still pinned to a specific React Native and React combination. Expo's stated maintenance policy is that each SDK has a lifetime of roughly one year, not "two cycles": as of 2026-08-25 the supported set is SDK 54–57, with SDK 54 (September 2025) receiving critical fixes until the next SDK release in September or October 2026. SDK 53 and older are outside the window — docs.expo.dev/versions/v53.0.0/ now 404s.

Read the whole dist-tags map before writing an install line, because several tags point backwards:

  • There is currently no sdk-57 tag on the expo package — SDK 57 is reachable only as latest / next. (expo-template-default does carry sdk-57, so npx create-expo-app@latest --template default@sdk-57 works even though npm i expo@sdk-57 does not.)
  • next no longer means "the next line". On expo it is an alias of latest (57.0.16). On eas-cli it is 7.1.0 while latest is 22.4.0 — fifteen majors behind.
  • canary has moved on to SDK 58 (58.0.0-canary-20260812-27f94d4); the per-SDK canaries are frozen far behind their stable siblings (canary-sdk-56 = 56.0.6-canary-20260701-9100865 vs sdk-56 = 56.0.20; canary-sdk-55 = 55.0.3-canary-20260429-a5e59cf vs sdk-55 = 55.0.29). Treat them as back-port verification snapshots, not as "newer".
  • Some expo-* packages only adopted SDK-aligned version numbers at SDK 55, so an sdk-NN tag can look older than latest for a legitimate reason (expo-file-system: sdk-54 = 19.0.24, sdk-55 = 55.0.25, latest = 57.0.5).
  • beta is published only in the weeks before an SDK GA; between releases it can be absent from expo entirely or stranded on an old line (expo-template-default's beta still points at 53.0.19).

What's New in SDK 56 (May 2026)

SDK 56 is the largest single-cycle release since SDK 50, and the first where the Jetpack Compose (Android) and SwiftUI (iOS) Expo UI APIs are declared stable. Headline items:

  • Expo UI stable on iOS + Android, experimental on web. Universal components — Host, Row, Column, ScrollView, Text, TextInput, Button, Switch, Slider, Checkbox, BottomSheet — work across all three targets without .android.tsx/.ios.tsx file splits. Backed by @expo/ui/jetpack-compose (Android), @expo/ui/swift-ui (iOS), and react-dom / react-native-web (web).
  • Drop-in replacements for popular community libraries: @gorhom/bottom-sheet, @react-native-community/datetimepicker, @react-native-masked-view/masked-view, @react-native-menu/menu, react-native-pager-view, @react-native-picker/picker, @react-native-segmented-control/segmented-control, @react-native-community/slider. Migration is typically a single import change.
  • Precompiled Expo packages on iOS — prebuilt XCFrameworks for the heaviest Expo modules ship by default; median clean iOS builds drop ~16% (~1 minute). Opt out with EXPO_USE_PRECOMPILED_MODULES=0.
  • Precompiled headers for Android codegen (experimental) — opt-in via android.usePrecompiledHeaders: true in expo-build-properties. In Expo's benchmark :app:buildCMakeDebug drops from 17 m 10 s to 6 m 06 s (2.81× speedup); a fresh project sees ~1.3× faster builds. The larger the autolinked native graph, the bigger the win.
  • Inline modules — define Expo modules in Kotlin/Swift files directly inside your project tree, with no separate package scaffold. Prebuild updates the Xcode and Android projects in place and autolinks the module. Pairs with the new expo-type-information package, which parses Swift Expo modules and generates a TypeScript interface split into a regenerated part and a stable hand-edit part. Corrected against the shipped package (expo-type-information@0.1.6, and identically at 0.0.13 for SDK 56): the commands live on that package’s own expo-type-information binary, not on npx expo, and they are module-interface, inline-modules-interface and short-module-interface. There is no module-interface-watch command — watching is the -w, --watcher flag on module-interface. The generated files are types.ts, module.ts, view.tsx and index.ts, not [ModuleName]Types.ts. The command also requires sourcekitten on PATH (brew install sourcekitten) and therefore only runs on macOS. Inline-module watch directories are configured under expo.experiments.inlineModules.watchedDirectories in app.json.
  • Faster Expo CLI — experiments.onDemandFilesystem is now default; the slow startup tax of watchFolders is gone. The bundler now uses a native Node.js watcher and crawler by default instead of Watchman (resolver.useWatchman in metro.config.js flips it back). Note the key name: the SDK 56 changelog prints it as singular experiment.onDemandFilesystem, but the shipped schema (@expo/config-types) and the reader in @expo/cli both use the plural experiments block — {"expo":{"experiments":{"onDemandFilesystem":false}}}. The singular spelling is silently ignored.
  • TypeScript 6 support and TypeScript 7 readiness. Resolver was rewritten; project-references workflows are now usable.
  • Hermes bytecode diffing enabled by default — Updates are smaller and patch faster on devices that already have a recent prior bytecode bundle.
  • More capable expo-file-system — unified API with consistent path semantics, async streaming for large blobs, and the same surface across iOS, Android, and web.
  • Status bar + navigation bar APIs unified. Both expo-status-bar and expo-navigation-bar now ship matching imperative (setStyle, setHidden) and declarative (<StatusBar style="auto" />) APIs, configurable via app.json plugin entries.
  • Calendar, Contacts, MediaLibrary APIs promoted to stable; iOS Widgets promoted to stable.
  • AI-friendly project scaffolding — see the dedicated Skills section below.
  • Convex integration in EAS — see the dedicated Convex section below.
  • Brownfield: more flexibility for embedded Expo apps — easier patterns for hosting Expo modules inside existing native iOS / Android apps that aren't a full Expo project.
  • EAS Build statistics for xcodebuild and Gradle, and prebuilt artifacts for major community libraries.

Tool-version bumps: EAS Workflows profiles without a pinned image now default to Xcode 26.4, the iOS deployment target moved to 16.4 (own Expo modules must bump their podspec), and React 19.2 / React Native 0.85 are baseline.

What's New in SDK 57 (June 2026)

Update (verified 2026-08-25): SDK 57 is a maintenance-shaped release, not a feature release. React Native 0.85 → 0.86 is the headline; React stays at 19.2.3. Beyond that, per expo.dev/changelog/sdk-57:

  • npx expo prebuild now cleans by default — it deletes and regenerates android/ and ios/ unless you pass the new --no-clean. Verified in the shipped CLI: @expo/cli@56.1.24 computed clean: args['--clean'] (default off), @expo/cli@57.0.18 computes clean: !args['--no-clean'] (default on), and --no-clean does not exist before 57. This is an inverted default that silently destroys hand-edited native folders on upgrade.
  • expo-dev-client — the iOS launcher can be set to auto-launch your most recent project or always show the launcher, overriding the config-plugin setting.
  • expo-image — writeToCacheAsync / readFromCacheAsync seed and read the image cache by cache key.
  • expo-router — Stack.Toolbar.Badge works in header left/right placements and on Android toolbar menu icons.
  • expo-navigation-bar — setStyle / setHidden now apply to React Native <Modal> windows on Android.
  • Bundled animation/gesture libraries move up: react-native-reanimated 4.3 → 4.5, react-native-worklets 0.8 → 0.10, react-native-gesture-handler 2.31 → 2.32.
  • EAS Build images move with the SDK. The latest / sdk-57 iOS image is macos-tahoe-26.5-xcode-26.6 (Xcode 26.6, macOS Tahoe 26.5.2, Node 22.23.1); sdk-56 stays on macos-tahoe-26.4-xcode-26.4 and sdk-55 on macos-sequoia-15.6-xcode-26.2. On Android, sdk-57 is ubuntu-26.04-jdk-17-ndk-r27b-sdk-57. If eas.json omits image, EAS uses the auto alias and picks by SDK — pin the image explicitly if you need a fixed Xcode.
  • Expo Go for SDK 57 is not on the app stores yet (Apple approval pending as of the changelog). The store builds of Expo Go track SDK 54; SDK 57 Expo Go is available via eas go on iOS devices and through Expo CLI on Android devices/emulators and iOS simulators.

Expo CLI, Metro, and the Bundling Pipeline

Expo's CLI front-ends Metro (the React Native bundler) with the additional concepts of app.json config plugins, the npx expo prebuild Continuous Native Generation (CNG) step that regenerates android/ and ios/ from JSON config, and a deterministic expo install that picks each package version compatible with the active SDK. Day-to-day commands:

npx create-expo-app@latest my-app --template default@sdk-57   # New project on SDK 57 + Expo UI
cd my-app
npx expo start                              # Dev server: Metro + LAN/QR/tunnel + dev menu
npx expo run:ios                            # Local native iOS build (requires Xcode)
npx expo run:android                        # Local native Android build (requires Android SDK)
npx expo prebuild                           # Regenerate native projects (SDK 57: cleans by default; --no-clean to merge)
npx expo install react-native-screens       # Install with SDK-compatible version pinning
npx expo-doctor                             # Diagnose toolchain + dependency mismatches
npx expo lint                               # First-party ESLint setup + run (scaffolds eslint.config.js)

Two corrections against the shipped CLI (@expo/cli@57.0.18, run locally; identical in 56.1.24, so both predate this card):

  • npx expo doctor is not a command. The local CLI's command table is start, export, install, add, customize, config, serve, login, logout, whoami, register, run:ios, run:android, prebuild (plus hidden run, lint, export:embed, export:web). doctor is in the migration map and exits 1 with $ expo doctor is not supported in the local CLI, please use npx expo-doctor instead. The working invocation is npx expo-doctor (separate package, latest = 1.20.3).
  • npx create-expo-app@latest my-app no longer silently takes the newest SDK. Without --template it now prompts for an SDK version (offering "Latest (SDK 57)" and "for learning with Expo Go (SDK 54)"). For a non-interactive scaffold pass --template default@sdk-57.

The bundler can run via Bun (bun create expo, bun install, bun expo start) — Expo's package manager detection is package-manager-agnostic, but Bun's faster install + Metro startup is the most common 2026 setup for solo developers.

Expo Router — File-Based Routing for Native + Web

expo-router is Expo's React-Navigation-on-top-of-files routing layer, modeled on the Next.js App Router. Routes are TypeScript files under app/; the directory structure becomes navigation:

app/
├── _layout.tsx              # Root Stack
├── index.tsx                # GET /
├── (tabs)/                  # Group: doesn't appear in URL
│   ├── _layout.tsx          # Tabs navigator
│   ├── feed.tsx             # /feed
│   └── profile.tsx          # /profile
├── post/
│   └── [id].tsx             # /post/:id
└── +not-found.tsx           # 404 fallback

Layouts compose (Stack, Tabs, Drawer), parameters are typed via the generated expo-router/types ambient module, and a Link component handles platform-correct navigation (push transitions on native, <a href> on web). SDK 56 added a SuspenseFallback pattern that lets the root layout opt routes into React Suspense without writing per-route boilerplate, and a npx expo-codemod sdk-56-expo-router-react-navigation-replace [your-source-dir] codemod for migrating apps that mixed bare React Navigation imports with Expo Router.

Expo Application Services (EAS)

EAS is Expo's hosted backend for app delivery. The five long-standing sub-products, all available standalone via the eas CLI (npm i -g eas-cli, latest = 22.4.0):

Sub-productWhat it does

EAS BuildCloud-builds signed iOS .ipa and Android .aab / .apk from your repo (no local Mac required for iOS). Picks its image from the auto alias unless eas.json sets image: Xcode 26.4 for SDK 56, Xcode 26.6 for SDK 57 (macos-tahoe-26.5-xcode-26.6). Profiles in eas.json define development, preview, production shapes.
EAS SubmitPushes builds to App Store Connect (iOS) and Google Play Console (Android) via API; handles credentials and version-code bumps.
EAS UpdateOTA JavaScript / asset bundle delivery. Channels (production, staging, preview) are set per build profile with the channel key in eas.json. (release-channel is not a key at all; the similarly named releaseChannel in eas.json is deprecated and belongs to the retired Classic Updates service, which only ever worked on SDK 49 and lower.) Hermes bytecode diffing (now default in SDK 56) makes per-update bundles smaller.
EAS WorkflowsYAML-defined CI pipelines that orchestrate Build → Submit → Update → arbitrary scripts. Build-time statistics for xcodebuild and Gradle were added in SDK 56.
EAS HostingStatic + serverless hosting for Expo Web outputs (npx expo export -p web).

SDK 56 also previewed EAS Observe (production runtime telemetry from inside the running app — crashes, perf, releases — built on the same Updates infrastructure), at the time in early access.

Update (verified 2026-08-25): EAS Observe went generally available on 2026-08-20, making it a sixth first-class EAS sub-product with its own docs section, its own eas observe:* CLI commands (events, metrics, metrics-summary, routes, session, versions) and its own client package, expo-observe (npx expo install expo-observe, MIT, latest = 57.0.16). Every plan gets 90 days of retention. Free includes 100,000 events/month and the main dashboard; Starter and above include 500,000 events/month plus the navigation, update, errors, user-defined-events dashboards, with overage at $5 per 1M events (volume-discounted to $4.75 above 50M and $4.50 above 200M); the session-timeline dashboard is Production and Enterprise only. Sample rate is adjustable and ingestion can be switched off per project.

Two more surfaces have appeared alongside it, neither of which existed at the baseline: Expo Launch (beta, launch.expo.dev) — a browser flow that configures a GitHub repo and ships it to the App Store / web through EAS Workflows, and is listed on the Free plan — and EAS Simulators (preview), fronted by eas simulator:* in the CLI. In the other direction, Expo Agent (the hosted web IDE at agent.expo.dev) was wound down on 2026-07-31; Expo's stated reason is that it would rather integrate with the harnesses developers already use than ship its own, which is exactly what the Skills section below now describes.

AI Agent Scaffolding — Skills for Cursor, Codex, Grok Build, Claude Code

SDK 56 shipped Expo's own agent-scaffolding bundle, aligned with the Claude Code Skills format (which is also the Anthropic Skills wire format). It is a GitHub repository, github.com/expo/skills — not an npm package — and it now ships expo-* skills for the framework and eas-* skills for the services.

Update (verified 2026-08-25): the install lines changed. Expo's plugin is now distributed through each vendor's curated marketplace, so the marketplace-add step in the baseline is gone:

# Claude Code
/plugin install expo@claude-plugins-official

# Codex
codex plugin add expo@openai-curated

# Cursor and any other agent — via the skills CLI (skills.sh)
npx skills add expo/skills

Recent Cursor versions import skills already installed for Claude Code or Codex automatically (Settings → Rules, Skills, Subagents), and skills there work by auto-discovery rather than from the / menu.

This makes Expo-shaped tasks ("scaffold a tab navigator", "add an EAS Build profile for preview", "wire expo-notifications with a token-registration helper") first-class skills inside Claude Code, OpenAI Codex CLI, Grok Build and Cursor — agents pick up the same authoritative Expo recipes rather than improvising from training data. Expo's docs also ship an LLM-shaped mirror worth knowing about: append .md to any docs.expo.dev URL for the Markdown source, and docs.expo.dev/llms.txt is the full index (its opening section is a list of "common misconceptions" aimed squarely at models, e.g. that expo eject was removed in SDK 46 and that the managed-vs-bare split no longer exists).

Expo MCP Server is a separate surface, for agents that would rather talk to the EAS account programmatically over MCP — it inspects EAS build status, workflow runs, logs and TestFlight crashes, and can drive a local dev server and simulator. Corrected against Expo's own announcement: it is not Starter-tier-and-up. It moved to the Free plan on 2026-05-26 with a monthly included MCP allowance counted at the billing-account level; paid plans raise the limit. Since 2026-08-13 it can also be connected from the Claude desktop app.

Convex Integration

SDK 56 added a one-shot Convex setup via EAS:

eas integrations:convex:connect

The command installs convex, provisions or reuses a Convex team linked to your EAS account, creates a project with a dev deployment, and writes CONVEX_DEPLOY_KEY + EXPO_PUBLIC_CONVEX_URL to .env.local. The EXPO_PUBLIC_CONVEX_URL value is also written as an EAS environment variable across Production, Preview, and Development so EAS Build picks it up automatically with no manual secret-rotation step. Convex's reactive queries pair naturally with Legend-State for offline / local-first stores; for traditional auth-as-a-service the canonical pairing is Clerk, which ships first-party React Native + Expo support.

Common Gotchas

1. Expo Go is for prototyping, not production. Once your app uses any custom native module (camera, payments, push, custom Expo modules), you must move to a development build via eas build --profile development. The Expo docs spell this out, but new users routinely paint themselves into a corner by living in Expo Go too long. As of 2026-08-25 there is a second reason not to plan around Expo Go: the App Store / Play Store builds track SDK 54, and the SDK 57 build is still awaiting Apple review — you reach it with eas go on an iOS device, or through Expo CLI on Android and iOS simulators.
2. npx expo install ≠ npm install. Always use expo install for any React Native / Expo package — it picks the version pinned to your SDK. A plain npm install react-native-screens@latest will pull a version that may not be ABI-compatible with the React Native baked into your current SDK and will fail at runtime with cryptic Metro errors.
3. Continuous Native Generation deletes your manual native edits. If you run npx expo prebuild after hand-editing android/ or ios/, those edits are gone unless they are encoded as a config plugin. Two corrections here. First, there is no dangerouslyAddXcodeProject modifier — no such symbol exists in @expo/config-plugins@57.0.9 or in Expo's mods documentation. The real names are withXcodeProject (typed edits to the .pbxproj) and withDangerousMod (arbitrary filesystem work during prebuild). Second, SDK 57 inverted prebuild's default: it now wipes and regenerates both native directories on every run, where SDK 56 merged into whatever was there. Pass --no-clean for the old behaviour. Either commit to CNG (idiomatic) or git mv the directories out of the way and treat the project as a bare React Native app (no prebuild allowed). The two modes don't mix.
4. Expo UI is not Tamagui. Expo UI (Jetpack Compose + SwiftUI under the hood) renders true native primitives — same widgets the OS uses — while Tamagui is a compile-time-optimised React Native UI kit on top of View/Text. Pick Expo UI when you want native look-and-feel and platform interop (Material 3 Dynamic Colors, SwiftUI modifiers); pick Tamagui when you want exact pixel parity across iOS/Android/web. They can coexist — Tamagui screens with <Host>-mounted Expo UI sheets are common.
5. Hermes diffing helps only after the first install. New devices pay the full bytecode download once before the diffing path kicks in. Plan your first-launch UX accordingly and don't measure update size on a freshly installed device.
6. EAS Update channel ≠ git branch. A channel: production build will continue to receive updates published to production even after you cut a release/v2 branch; channels are decoupled from VCS. Use channels together with runtimeVersion (set to "appVersion" or a hash policy) to avoid pushing a JS bundle that targets native APIs the device doesn't have.
7. The free EAS tier's 45-minute build timeout is real. Large Android apps with many autolinked native modules can hit it. Enable android.usePrecompiledHeaders (new in SDK 56) and run expo-doctor to drop unused modules before you upgrade tiers just to dodge timeouts.
8. TypeScript 6 is already the scaffolded default — corrected against the shipped template. expo-template-default pins typescript: ~6.0.3 in devDependencies at both 56.0.0 and 57.0.18, so a fresh create-expo-app project has been on TS 6 since SDK 56 shipped; the claim that it "still scaffolds TypeScript 5.x" was never true. What is still worth doing is auditing your transitive @types graph when you upgrade an existing project — TS 6 tightens several inferred-type rules that older libraries trip on.
9. iOS deployment target moved to 16.4 in SDK 56. Custom Expo modules with their own podspecs must bump s.platform = :ios, '16.4' or the build will fail with a CocoaPods compatibility error.
10. Watchman is no longer the default — your metro.config.js may carry stale resolver.useWatchman = true. Removing the line lets the new native Node.js watcher take over; leave it set only if you're debugging a specific Watchman-only edge case.
11. Push notification delivery routes through Expo's Push Service by default, not directly through APNS / FCM. The service is free and rate-limited; production apps with multi-million-device fan-out routinely move to direct APNS/FCM or to a third-party orchestrator like Knock — Expo's Push Service is meant as a developer-friendly default, not a billion-message-per-day pipe.
12. Linting is opinionated after all; formatting is not. "Expo ships no default linter" is wrong against the shipped CLI: npx expo lint is a first-party command in @expo/cli (present in 56.1.24 and 57.0.18) that installs ESLint on first run, writes an eslint.config.js extending eslint-config-expo (latest = 57.0.1), and then lints /src, /app and /components with --fix, --config, --max-warnings and friends. Flat config is the default from SDK 53 on. Formatting is genuinely unopinionated — Expo ships no formatter, so the choice is Biome (one Rust binary for both jobs, at the cost of replacing expo lint) versus Prettier alongside expo lint.
