Overview

Redis Streams are an append-only log data type introduced in Redis 5.0 (October 2018) for building event-driven systems on top of Redis. A stream is an ordered, time-keyed sequence of field-value entries supporting fan-out reads (XREAD) and a Kafka-style consumer-group pattern (XREADGROUP + Pending Entries List + XACK) for at-least-once delivery across competing workers. Streams are the right Redis primitive for event sourcing, agent message queues, audit trails, and ordered work distribution — and the wrong one for ephemeral pub/sub fan-out (use PUBLISH/SUBSCRIBE for that). Compared to Apache Kafka, Streams trade Kafka's per-partition durability and infinite retention for in-process latency, simpler ops, and tight integration with the rest of the Redis data model — see Message Brokers Compared for the full matrix. Streams ship identically in Valkey (the BSD-3 fork). This entry covers the wire-level commands, consumer-group semantics, idempotent producers (8.6+), trimming reference policies (8.2+), and the operational gotchas that catch teams in production.

Stream Entry IDs

Every entry has an ID <ms>-<seq> where ms is Unix epoch milliseconds and seq is a per-millisecond counter. IDs are strictly monotonic — Redis guarantees that the next ID is greater than the previous, even if the local clock jumps backward (it falls back to top.ms-(top.seq+1)).

XADD mystream * field1 value1   # auto-generates "1745678901234-0"
XADD mystream 1745678901234-1 f v   # explicit ID; must be > last
XADD mystream 1745678901234-* f v   # auto-sequence under given ms

Special IDs in command arguments:

Minimum valid explicit ID is 0-1 — 0-0 is reserved as the "before the beginning" sentinel.

Producing: XADD

XADD key [NOMKSTREAM] [KEEPREF | DELREF | ACKED]
  [IDMPAUTO producer-id | IDMP producer-id idempotent-id]
  [<MAXLEN | MINID> [= | ~] threshold [LIMIT count]] <* | id>
  field value [field value ...]

OptionSinceEffect

NOMKSTREAM6.2Do not create the stream key if it doesn't exist; return nil
MAXLEN <N>5.0Cap the stream to N entries; oldest evicted
MINID <id>6.2Evict entries with ID < id
~ N (approx)5.0Trim near-N, allow a macro-node's worth of slack — much faster
= N (exact)5.0Trim to exactly N entries
LIMIT count6.2Cap entries examined per trim pass; 0 = unlimited
KEEPREF (default)8.2Trim entries from stream, keep references in consumer-group PELs
DELREF8.2Trim entries and remove references from all PELs
ACKED8.2Only trim entries acknowledged by all consumer groups
IDMPAUTO producer-id8.6Server auto-generates idempotency ID for this producer
IDMP producer-id idempotent-id8.6Caller-supplied idempotency ID; duplicate returns the original entry's ID

Use * for the entry ID unless you have a strong reason — the server's monotonic clock is correct under leadership changes too. Always use ~ (approximate) for high-throughput trimming; = is O(N) on large streams. LIMIT count is mandatory with ~ if you must bound worst-case latency on each XADD.

# Append + trim near 10000 entries, examine at most 100 per pass
XADD events MAXLEN ~ 10000 LIMIT 100 * type signup user_id 42

# Idempotent produce: retries return the original entry ID
XADD events IDMP webhook-1 evt-abc123 * type payment amount 999
# 1st call → "1745678901234-0"
# Retry with same producer-id+idempotent-id → "1745678901234-0" (deduped)

XADD returns the entry ID (or nil if NOMKSTREAM and the stream is missing). With IDMP*, a duplicate returns the original ID without re-appending or modifying the existing entry — even if you supplied different fields. Time complexity: O(1) per entry, O(N) per evicted entry during trim.

Trimming: XTRIM

XTRIM key <MAXLEN | MINID> [= | ~] threshold [LIMIT count] [KEEPREF | DELREF | ACKED]

Same trimming options as XADD's trim suffix, available standalone. Returns the number of entries deleted. Use XTRIM for periodic background trimming when you can't tolerate the burst latency of trim-on-every-XADD. Combine with MINID and a time-derived threshold for time-based retention:

# Keep the last 24 hours
XTRIM events MINID ~ $(($(date +%s%3N) - 86400000))

Reference policies in 8.2+:

  • KEEPREF (default) — entries vanish from XLEN and XRANGE but their IDs remain in consumer-group PELs. Subsequent XACK still works; XAUTOCLAIM will move them through the cursor and report them in the third "deleted IDs" reply element.
  • DELREF — entries also vanish from PELs. Pending consumers stop seeing them on history reads. Use only if reprocessing-after-trim is impossible (e.g., the data already moved downstream).
  • ACKED — entries only trimmed once every consumer group has acknowledged them. Safest for at-least-once chains; the trade-off is unbounded growth if a group goes silent.

Reading without Consumer Groups

XREAD and XRANGE/XREVRANGE are for fan-out: every reader sees every entry, no PEL, no acknowledgment.

# Block until new entry arrives after the latest current ID
XREAD BLOCK 5000 COUNT 10 STREAMS mystream $

# Replay range [1745678900000-0, +)
XRANGE mystream 1745678900000-0 +

# Last 10 entries (reverse order)
XREVRANGE mystream + - COUNT 10

# Read multiple streams concurrently
XREAD COUNT 100 STREAMS s1 s2 s3 0-0 0-0 0-0

XREAD BLOCK 0 blocks indefinitely. Multi-key BLOCK is supported — Redis returns as soon as any one stream advances. Server-side complexity: O(M) per stream where M is entries returned; O(N) on XADD when N clients are blocked on the stream. XREAD does not maintain per-client state — your client must remember the last ID it saw and pass it back next call.

Consumer Groups: The Core Pattern

Consumer groups give you Kafka-style competing-consumer semantics on a Redis Stream: each entry is delivered to exactly one consumer in a group, and a per-consumer Pending Entries List (PEL) tracks unacknowledged messages so a crashed worker's load can be reclaimed. The pattern is the same one NATS JetStream uses for "pull consumers" and that Apache Kafka uses across partitions, just embedded in a single-process Redis instance instead of a distributed broker.

Creating a group

XGROUP CREATE key group <id | $> [MKSTREAM] [ENTRIESREAD entries-read]

Start IDMeaning

$Only entries added after group creation
0Replay everything from the beginning
<specific-id>Replay everything > that ID

XGROUP CREATE events workers $ MKSTREAM        # create stream + group, only new entries
XGROUP CREATE events backfill 0                 # replay full history
XGROUP CREATE events realtime $ ENTRIESREAD 1000  # 7.0+: enable lag tracking

MKSTREAM creates a zero-length stream when the key is missing — without it, the call errors ERR The XGROUP subcommand requires the key to exist. Group creation on an existing group fails with BUSYGROUP; idempotent setup uses a ROLE check or swallows that error.

ENTRIESREAD (7.0+) enables the lag field on XINFO GROUPS. Without it, lag is nil and you can't tell how far behind a group is.

Reading: XREADGROUP

XREADGROUP GROUP group consumer
  [COUNT count] [BLOCK milliseconds] [CLAIM min-idle-time] [NOACK]
  STREAMS key [key ...] id [id ...]

The ID per stream changes the mode entirely:

  • > — deliver only entries never delivered to any consumer in this group; adds them to this consumer's PEL (unless NOACK)
  • specific ID (or 0) — replay this consumer's PEL starting from that ID; BLOCK, NOACK, CLAIM are ignored in this mode

# Consumer "w-1" pulls up to 100 new entries, blocking 5s
XREADGROUP GROUP workers w-1 COUNT 100 BLOCK 5000 STREAMS events >

# After a crash: rescue this consumer's pending entries before resuming
XREADGROUP GROUP workers w-1 STREAMS events 0

NOACK skips PEL insertion — equivalent to immediate ack, suitable when occasional message loss is acceptable. Combined with > only.

CLAIM min-idle-time (8.4+) atomically auto-claims pending entries idle ≥ min-idle-timems on the same call that fetches new ones — claimed entries appear first in the response, ordered by descending idle time, with extra metadata [id, fields, idle-ms, delivery-count]. This collapses the classic "scan for stale + claim + read new" pattern into one round trip:

# Pull up to 100 entries; auto-claim anything idle ≥ 60s
XREADGROUP GROUP workers w-1 COUNT 100 CLAIM 60000 STREAMS events >

CLAIM only applies with >; with a specific ID it's silently ignored.

Acknowledging: XACK

XACK key group id [id ...]

Removes one or more IDs from the group's PEL. Returns the count of IDs that were actually pending and got removed — already-acked or never-pending IDs return 0 contribution. XACK does not delete the entry from the stream — only from the consumer-group PEL. Trimming is separate (via XTRIM/XADD MAXLEN).

XACK events workers 1745678901234-0 1745678901234-1
# (integer) 2

Failure Recovery: XCLAIM and XAUTOCLAIM

When a consumer crashes, its PEL entries don't move on their own. Use claim commands to transfer ownership to a healthy consumer.

XCLAIM (manual)

XCLAIM key group consumer min-idle-time id [id ...]
  [IDLE ms] [TIME unix-ms] [RETRYCOUNT n] [FORCE] [JUSTID]

Useful when you know the specific IDs you want to move (e.g., from XPENDING output). min-idle-time is the safety check — claim only succeeds if the entry has been idle ≥ that many ms (prevents racing the original consumer mid-processing). Resets idle to 0 and increments delivery count unless JUSTID is set.

FORCE creates a PEL entry even when the ID isn't currently pending in any consumer's list — useful for emergency reassignment of entries lost from PEL but still present in the stream.

XAUTOCLAIM (cursor-based scan, 6.2+)

XAUTOCLAIM key group consumer min-idle-time start [COUNT count] [JUSTID]

Scans the PEL from start (use 0-0 to begin), claims up to COUNT (default 100) entries idle ≥ min-idle-time, and returns:
1. Cursor — pass to next call; 0-0 means scan complete
2. Claimed entries — [id, fields] pairs (or just IDs with JUSTID)
3. Deleted IDs (7.0+) — entries that were trimmed out from under the PEL

# Sweep stale pending in 100-entry batches
cursor="0-0"
while true; do
  reply=$(redis-cli XAUTOCLAIM events workers janitor 60000 "$cursor" COUNT 100)
  # ... process claimed entries
  cursor=$(echo "$reply" | head -1)
  [ "$cursor" = "0-0" ] && break
done

Idle time resets to 0 on each successful claim — so two janitors with the same min-idle-time won't both grab the same entry. Use a dedicated "janitor" consumer name and either re-XCLAIM to the original target consumer afterward, or just keep claimed work on the janitor and process it locally.

COUNT only bounds the number of claimed entries — internally Redis scans up to COUNT × 10 PEL entries per call. Big PELs need multiple calls.

Inspection: XPENDING and XINFO

XPENDING — see the PEL

Two forms:

# Summary: total pending + smallest/greatest IDs + per-consumer counts
XPENDING key group

# Extended: per-entry detail
XPENDING key group [IDLE min-idle-time] start end count [consumer]

Summary returns [count, min-id, max-id, [[consumer, count], ...]]. Extended returns rows of [id, consumer, idle-ms, delivery-count] — the workhorse for "what's stuck and on whom":

XPENDING events workers - + 100              # 100 oldest pending
XPENDING events workers IDLE 60000 - + 100   # only idle > 60s (6.2+)
XPENDING events workers - + 100 w-1          # filter to consumer w-1

XINFO STREAM — overall stream state

XINFO STREAM key [FULL [COUNT count]]

Summary fields: length, radix-tree-keys, radix-tree-nodes, groups, last-generated-id, max-deleted-entry-id (7.0+), entries-added (7.0+), recorded-first-entry-id (7.0+), first-entry, last-entry. With FULL, also dumps every entry plus full group/consumer detail (use COUNT to bound the dump).

8.6+ adds IDMP tracking fields when idempotent production is configured: idmp-duration, idmp-maxsize, pids-tracked, iids-tracked, iids-added, iids-duplicates.

XINFO GROUPS — per-group state

Returns rows of name, last-delivered-id, entries-read, lag, pel-count, plus optional pending and consumers arrays in FULL mode. lag is nil if the group was created without ENTRIESREAD and the server can't reconstruct it — the only way to fix that for an existing group is XGROUP SETID ... ENTRIESREAD <count>.

XINFO CONSUMERS — per-consumer state

Returns rows of name, pending count, idle (ms since any interaction), inactive (ms since last successful work), and 7.2+ seen-time / active-time UNIX-ms timestamps. In 7.2+ seen-time was redefined to mean "last attempt" not "last success" — code that checked seen-time to detect a healthy consumer will now flag a thrashing-but-non-progressing consumer as healthy. Use active-time instead for "is this consumer making progress".

Idempotent Producers (Redis 8.6+)

XADD with IDMPAUTO or IDMP gives you at-most-once production: a deduplication ID is recorded and a retry of the same (producer-id, idempotent-id) pair returns the original entry's ID without re-appending. Configure per-stream limits via XCFGSET:

XCFGSET key [idmp-duration seconds] [idmp-maxsize count]

SettingDefaultMeaning

idmp-durationfrom stream-idmp-duration configSeconds to retain dedup records
idmp-maxsizefrom stream-idmp-maxsize configMax IDs tracked per producer (LRU eviction)

XCFGSET events idmp-duration 300 idmp-maxsize 10000

# Producer side: same (producer, iid) within window → same entry ID
XADD events IDMP webhook-1 evt-abc123 * type payment
XADD events IDMP webhook-1 evt-abc123 * type payment    # returns first ID, no append

The dedup state is included in RDB snapshots (XIDMPRECORD AOF emission added in 8.6.2 / PR #14794) — so persistence-load + replication propagate the dedup window correctly. Both IDMP* modes require the entry ID argument to be *; explicit IDs are rejected.

Known limitation in 8.6.0: avoid IDMP* with appendonly yes and aof-use-rdb-preamble no — the combination doesn't restore the dedup state on AOF replay. Fixed-class issue and slated for removal in a follow-up patch; safest path is to stay on 8.6.2 and use the default aof-use-rdb-preamble yes (see Redis Persistence).

Trimming Strategies and KEEPREF/DELREF/ACKED (8.2+)

The intersection of trimming and consumer-group PELs is where production bugs hide. Pre-8.2, trimming an entry that was still pending in a group's PEL left a dangling reference — the PEL still pointed at an ID the stream no longer contained. XACK still worked (just removed the PEL row), but XCLAIM/XAUTOCLAIM would skip it (no entry in the stream to deliver). The 8.2 reference policies make this explicit and configurable:

PolicyTrim behaviorUse when

KEEPREFStream entry deleted, PEL ref keptYou want consumers to be able to XACK historical entries even after trim, and you accept that XCLAIM will see "deleted" markers (third reply element of XAUTOCLAIM)
DELREFStream entry deleted, PEL refs removedYou're done with the data downstream and want clean PELs; consumers can no longer history-read trimmed entries
ACKEDOnly trim entries acked by all groupsSafest at-least-once: nothing leaves the stream while any group hasn't acked. Risk: a silent group blocks trimming forever (monitor XINFO GROUPS lag and DESTROY dead groups)

Across 8.2+, XTRIM ... DELREF and XADD ... MAXLEN ~ ... DELREF will iterate the affected entries' PEL refs — this is O(N×G) where N is evicted entries and G is the count of groups holding refs to each. Stay on KEEPREF (the default) for high-throughput streams unless DELREF/ACKED is operationally required.

Operational Gotchas

1. $ in XGROUP CREATE means "the current last ID" — not "future". The group then sees only entries added after the call. If the stream is empty when you create, $ resolves to 0-0 and you get all subsequent entries; if it's non-empty, you skip everything currently there. Use 0 if you wanted history.

2. > in XREADGROUP is per-group, not per-consumer. Once any consumer in a group reads an entry with >, no other consumer in the same group will ever see it via > — the entry is now in that consumer's PEL until acked or claimed. If the consumer dies, you must XCLAIM/XAUTOCLAIM to re-route.

3. Specific-ID mode of XREADGROUP ignores BLOCK, NOACK, and CLAIM. Calls like XREADGROUP GROUP g c BLOCK 5000 STREAMS s 0 return immediately with the consumer's PEL (or empty array if PEL is empty) — they do not block waiting for new entries.

4. XACK does not trim the stream. Acked entries stay in the log until XTRIM / XADD MAXLEN evicts them. Long-running streams without trimming grow unbounded; XINFO STREAM length is the canary. Use MAXLEN ~ N on the producer or a cron-driven XTRIM ... ACKED for safe bounded retention.

5. MAXLEN = is O(N) on each call; MAXLEN ~ is amortized O(1) but only trims at macro-node boundaries. Production code should always use ~ unless the cap must be exact (rare; usually you want "keep around N for memory" not "exactly N").

6. LIMIT 0 disables the trim examination cap entirely — a slow XADD MAXLEN ~ ... LIMIT 0 * on a very oversized stream can stall the server for seconds. Always set LIMIT 100 (or similar) on hot paths.

7. Stream IDs are not contiguous. 1234-0, 1234-1, 1235-0, 1340-0 are all legal — never assume XLEN equals last-id - first-id. Use XINFO STREAM entries-added (7.0+) for the cumulative produce count.

8. Crashed consumers leave PEL entries forever. Consumer rows in XINFO CONSUMERS persist until you XGROUP DELCONSUMER them, but their PEL entries don't auto-claim. Pattern: a janitor process runs XAUTOCLAIM periodically with min-idle-time ≥ your processing SLA; old consumers are dropped via XGROUP DELCONSUMER once their PEL is empty.

9. XGROUP DELCONSUMER returns the count of PEL entries the consumer still had — those entries become unreachable via XREADGROUP 0 (no consumer to scope to). They remain in the group PEL summary but you can only get them back via XCLAIM from another consumer with FORCE (since they're no longer "owned"). Always drain or claim before deleting.

10. XGROUP DESTROY drops the group and its entire PEL — any unprocessed messages are gone from the group's perspective (they remain in the stream, but no other group will pick them up unless it was created with 0 or earlier). No undo. Verify zero pending and snapshot the PEL before destroy.

11. Consumer names are arbitrary strings, not registered identities. Two processes that pick the same consumer name will share the PEL — both will see the same entries via XREADGROUP 0, both can XACK, and you'll get arbitrary interleaving. Always namespace consumer names by hostname/pod/PID (worker-{HOSTNAME}-{PID}).

12. min-idle-time on XCLAIM/XAUTOCLAIM should exceed your maximum processing latency. Setting it too low races healthy consumers and causes spurious claims that show up as duplicate processing. Common production value: 2 × p99_processing_ms.

13. XAUTOCLAIM claims reset idle time to 0. So after a sweep, the just-claimed entries won't be eligible for re-claim until they age past min-idle-time again — that's the protection against thrash. With JUSTID, the delivery counter is not incremented (idle still resets).

14. XPENDING summary form returns nil if the group has no pending entries — clients that expect the 4-element array crash on the empty case. Check for nil.

15. XPENDING extended form start end count requires count (positional) — it's not optional. XPENDING key group - + errors; XPENDING key group - + 100 is correct.

16. Streams in cluster mode are single-key — they cannot be partitioned across slots. To horizontally scale, partition at the application layer using {tag} hash tags (e.g., events:{user:42}) and run multiple co-located streams. Compare to Apache Kafka where partitioning is built in.

17. XADD on a key that exists but isn't a stream returns WRONGTYPE. Same goes for every X* command. Use TYPE key if your code path is generic; see Redis Data Types for the full type-keying reference.

18. The last-delivered-id of a group can be rewound with XGROUP SETID — but only the group cursor moves; the PEL is not cleared. After SETID, any entry that's both in the new range and in the PEL gets delivered twice (history once via XREADGROUP 0, then again via >). Use XGROUP SETID only when you've verified the PEL is empty.

19. MKSTREAM on XGROUP CREATE creates a zero-length stream — but XLEN returns 0, and the group's last-delivered-id is 0-0. The first XADD works normally, and > reads pick up everything from there. Useful when you want "create-if-not-exists" semantics in a single round trip.

20. XADD ... NOMKSTREAM and a missing key returns nil, not an error. Code that expected a stream ID and got nil may fail later. Always handle the nil case explicitly (typically: log & retry creation, or fail fast).

21. Idempotency dedup state is per-stream, not per-cluster. Replicas inherit it via the RDB/AOF stream; a manual MIGRATE of the key carries it; but DEBUG RELOAD on 8.6.0 (without 8.6.2's #14869 fix) drops the cron expiration timer. Pin to ≥ 8.6.2 if you rely on IDMP*.

22. IDMPAUTO returns deterministic IDs only within idmp-duration — once the dedup record expires, the same call appears as a fresh produce and gets a new entry ID. Set the duration to ≥ your client's longest retry timeout, not "the average network blip".

23. Streams on managed Redis tiers vary. Upstash Redis supports streams within the free-tier command quota and 256 MB cap, but BLOCKing reads cost commands per second; AWS ElastiCache requires Redis 5+; Redis Cloud free tier supports the full command set but caps total memory. Always benchmark stream throughput on the target tier — radix-tree allocations are dense and stream-heavy workloads OOM faster than key/value workloads of the same byte volume.

24. AOF rewrites can briefly miss a stream's IDMP state on 8.6.0 — fixed in 8.6.2 (#14794). Stay on 8.6.2+ for production; the IDMP feature isn't safe for at-most-once SLAs on the GA point release. See Redis Persistence for AOF/RDB interaction.

25. 8.4+ CLAIM on XREADGROUP returns claimed entries with extra metadata ([id, fields, idle-ms, delivery-count]) — RESP2 clients that flat-mapped the 2-element entry shape now have a length mismatch on those rows. Update parsers; check XINFO STREAM for the active feature flag, or rely on the server reply length per row.

Streams vs. Pub/Sub vs. Lists

NeedUse

Fan-out, no replay, no ack — pure broadcastPUBLISH / SUBSCRIBE (or SSE / WebSockets)
Single-consumer FIFO queue, ephemeralLPUSH / BRPOP (List type)
Multi-worker competing-consumer with retry + ackStreams + consumer groups
Time-windowed event log with multiple readersStreams (each reader uses XREAD with its own cursor)
Cross-host durable queue with infinite retentionApache Kafka or NATS JetStream

Streams sit between Lists and Kafka: ordered, durable through Redis persistence, replayable, with built-in consumer-group accounting — but bounded by Redis's single-process memory and replication topology. Crossing the multi-GB or multi-broker threshold is the usual signal to move to a real broker.
