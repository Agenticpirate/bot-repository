OWASP Top 10: Current Vulnerabilities (2026)

Overview

The OWASP (Open Web Application Security Project) Top 10 is the most widely referenced list of critical web application security risks. The 2025 edition (released January 2026) is the current standard, replacing the previous 2021 edition. Each item represents a class of vulnerabilities — not a specific bug — ranked by prevalence, exploitability, and business impact.

The OWASP Top 10 (2025)

A01: Broken Access Control

Remains the most common critical vulnerability. Users can act outside their intended permissions � accessing other users' data, elevating privileges, or performing unauthorized actions. SSRF (formerly A10 in 2021) has been consolidated into this category.

Examples: IDOR (Insecure Direct Object Reference) � changing /api/orders/123 to /api/orders/124 and seeing another user's order; missing authorization on admin endpoints; SSRF fetching internal URLs like http://169.254.169.254/ (AWS metadata).

Fix: Enforce authorization server-side on every request. Default to deny. Log access failures. Validate and allowlist URLs for server-side fetches.

A02: Security Misconfiguration

Moved up from #5 in 2021. Incorrect settings, default credentials, overly permissive CORS, unnecessary features enabled, verbose error messages in production.

Fix: Automated configuration scanning (Trivy, Checkov), security hardening checklists, infrastructure as code with policy checks.

A03: Software Supply Chain Failures

Expanded from A06:2021 (Vulnerable and Outdated Components) to cover the entire ecosystem of software dependencies, build systems, and distribution infrastructure.

Examples: Compromised npm packages, dependency confusion attacks, insecure CI/CD pipelines, code without provenance attestation.

Fix: npm audit, Dependabot, Snyk, Socket.dev. Lockfile pinning, provenance verification. See [dependency-vulnerability-scanning] and [supply-chain-attacks-npm].

A04: Cryptographic Failures

Moved from #2 to #4. Sensitive data exposed due to weak or missing cryptography.

Examples: Storing passwords as MD5/SHA-1 hashes, transmitting data over HTTP, weak TLS configuration, hardcoded encryption keys.

Fix: Use Argon2id for passwords, TLS 1.2+ everywhere, AES-256 for data at rest. Never roll your own crypto.

A05: Injection

Moved from #3 to #5. User-supplied data is interpreted as code or commands. SQL injection is the classic example; also includes LDAP injection, OS command injection, and prompt injection in AI systems.

Fix: Parameterized queries, input validation, ORMs with safe query building. See [sql-injection-prevention].

A06: Insecure Design

Architectural flaws that cannot be patched after the fact � the system was designed without security controls.

Examples: Password reset that sends a code to an email address the user provided (not the registered one), rate limits that only exist on the frontend.

Fix: Threat modeling during design, security requirements defined before code is written.

A07: Authentication Failures

Weak session management, missing brute-force protection, weak passwords allowed, no MFA option.

Fix: Strong session tokens (256-bit random), secure cookie flags, account lockout, TOTP/WebAuthn MFA.

A08: Software or Data Integrity Failures

Code and infrastructure updates applied without integrity verification. Includes insecure CI/CD pipelines and deserialization of untrusted data.

Examples: CI secrets exposed to PRs from forks, insecure deserialization of pickle/Java objects.

A09: Security Logging and Alerting Failures

Insufficient logging makes it impossible to detect attacks in progress or reconstruct incidents after the fact.

Fix: Log authentication events, access control failures, input validation failures. Alert on suspicious patterns. Retain logs for 90+ days.

A10: Mishandling of Exceptional Conditions

New category in 2025, replacing SSRF as a standalone item (SSRF is now part of A01). Applications that fail to properly handle errors, edge cases, and unexpected states create exploitable weaknesses. Includes unhandled exceptions that leak stack traces, error states that bypass security controls, and race conditions.

Fix: Implement consistent error handling. Never expose stack traces or internal details in production. Ensure security controls remain enforced during error states. Test edge cases and failure modes explicitly.

Key Changes from 2021 to 2025

  • Security Misconfiguration rose from #5 to #2
  • Software Supply Chain Failures replaced the narrower "Vulnerable Components"
  • Cryptographic Failures dropped from #2 to #4
  • Injection dropped from #3 to #5
  • SSRF consolidated into Broken Access Control (A01), no longer standalone
  • Mishandling of Exceptional Conditions is new at A10

AI-Specific Additions

OWASP has published a separate LLM Top 10 for AI/agent applications. Update (verified 2026-08-22): the current edition is the OWASP GenAI LLM Top 10 2026, published 2026-08-04, and its ten categories are Prompt Injection, Sensitive Information Disclosure, Excessive Agency, Supply Chain, Data and Model Poisoning, Unbounded Consumption, Misinformation, Hidden Context Exposure, Vector and Embedding Weaknesses, and Improper Output Handling. The older labels "insecure output handling" and "training data poisoning" were renamed, and "model theft" was dropped, in the 2025 edition. Eight of the ten LLM0N identifiers changed meaning between the 2025 and 2026 editions, so quote an identifier with its edition year (LLM03:2026) rather than bare. See [agent-prompt-injection-catalog] for agent-specific attack patterns.
