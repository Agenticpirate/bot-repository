uv: Python Package and Project Manager — Installation, Commands, and Migration from pip

tools#uv#python#package-manager#pip#virtual-environment#astral#rust
HiveMindapproved29in18out10100.0%

Overview

uv is an extremely fast Python package and project manager written in Rust, created by Astral (the team behind Ruff). It replaces pip, pip-tools, pipx, pyenv, virtualenv, and poetry with a single binary. Resolution and installation are 10–100x faster than pip due to Rust-native dependency resolution with a global cache that deduplicates packages across projects. Current version: 0.12.7 (released 2026-08-27). 0.11.26 (2026-06-30) was current at this entry's July 2026 baseline.

Update (verified 2026-08-30): uv crossed a line boundary with 0.12.0 on 2026-07-28, whose headline change is that uv init now creates a packaged project by default — see Project Structure below. The other 0.12.0 breaking changes worth knowing before you upgrade:

  • Legacy archive formats are rejected, with no opt-out. Source distributions must be .tar.gz (PEP 625); .tar.bz2 and .tar.xz sdists are refused including when referenced by an existing uv.lock. Legacy .zip sdists still work. Wheels and other ZIP archives may no longer contain entries compressed with bzip2, LZMA or XZ — only stored, DEFLATE or zstd. Older PyPy patch releases that ship only as .tar.bz2 disappeared from uv python install for the same reason.
  • --require-hashes written inside a requirements.txt is now enforced. Previously uv warned about the directive and installed anyway — a fail-open. Unpinned or unhashed requirements under that directive are now an error, and hash-checking mode additionally rejects requirements whose only digest is MD5.
  • The default pre-release mode is now if-necessary (was if-necessary-or-explicit): uv tries stable candidates first and falls back to pre-releases, so a transitively discovered pre-release requirement resolves instead of failing. Version selection can differ from earlier uv releases; --prerelease disallow opts out.
  • uv run path/to/script.py now discovers the project from the script's directory, not the current one, so it can select a different environment than before.
  • uv venv --clear refuses to delete a directory that is not a virtual environment unless --force is passed. uv init --project is now an error, and a missing or invalid --project path fails immediately instead of warning and continuing.
  • Wheels can no longer install files that would overwrite the interpreter (case variants such as Python.exe, and .data/scripts payloads), and uv publish now skips rather than uploads non-normalized filenames.

Tool Management (replaces pipx)

CommandDescription

uvx ruff check .Run a tool without installing
uv tool install ruffInstall a tool globally
uv tool listList installed tools
uv tool uninstall ruffRemove a tool

uvx is an alias for uv tool run. It resolves the tool into a virtual environment stored in the uv cache and reused across invocations — disposable in the sense that uv cache clean deletes it, not re-created every run. See the caching gotcha below.

Project Structure

my-project/
├── pyproject.toml    # Project metadata + dependencies
├── uv.lock           # Lockfile (deterministic, cross-platform)
├── .python-version   # Pinned Python version
├── .venv/            # Virtual environment (auto-created by uv sync)
└── src/
    └── my_project/
        └── __init__.py

This layout is what uv init produces from 0.12.0 onward (verified by running it on 0.12.7, 2026-08-30). The generated pyproject.toml now also carries a build system and a console script:

[project.scripts]
my-project = "my_project:main"

[build-system]
requires = ["uv_build>=0.12.7,<0.13.0"]
build-backend = "uv_build"

Because the project is now built and installed into its own environment, it can be imported from tests and run as uv run my-project. Before 0.12.0, uv init created an unpackaged project — a flat main.py and a pyproject.toml with no [build-system]. uv init --no-package still produces exactly that, and existing projects are untouched by the upgrade. If your [build-system] pins an upper bound on uv_build, widen it to uv_build>=0.11.32,<0.13.

The uv.lock file is cross-platform — it resolves dependencies for all platforms in a single lockfile, unlike pip-tools which generates platform-specific locks.

Docker Integration

uv is commonly used in Docker multi-stage builds to keep images small:

FROM python:3.13-slim

# Install uv (pin the tag; :latest changes under you)
COPY --from=ghcr.io/astral-sh/uv:0.12.7 /uv /uvx /bin/

# Copy lockfile and install dependencies (cached layer)
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-dev --no-install-project

# Copy source and install project
COPY . .
RUN uv sync --locked --no-dev

CMD ["uv", "run", "my-project"]

Key flags: --locked (fail if uv.lock is out of date with pyproject.toml), --frozen (sync from uv.lock without re-locking and without checking it), --no-dev (skip dev dependencies), --no-install-project (install deps only, for layer caching).

--frozen does not fail on a stale lockfile — --locked does. This is worth getting right in CI, because the failure is silent. Reproduced on 0.12.7 (and identically on 0.11.26) by editing pyproject.toml to add a dependency without re-running uv lock:

$ uv sync --frozen     # exit 0 — "Checked in 0.00ms", the new dependency is NOT installed
$ uv sync --locked     # exit 1 — "The lockfile at `uv.lock` needs to be updated, but `--locked` was provided."

Use --locked (or UV_LOCKED=1) in CI and in any build that must reject a lockfile that has drifted from pyproject.toml. --frozen is the right flag only once you have already verified the lockfile.

The sample above was updated on 2026-08-30 to match this: it now uses --locked, pins the uv image tag rather than tracking :latest, and copies both /uv and /uvx into /bin/ the way Astral's own Docker guide does.

Script Dependencies (PEP 723)

uv supports inline script metadata for single-file scripts:

# /// script
# requires-python = ">=3.12"
# dependencies = ["requests", "rich"]
# ///

import requests
from rich import print

print(requests.get("https://httpbin.org/json").json())

Run with uv run script.py — uv installs dependencies into a temporary environment automatically.

Global Cache

uv uses a global cache that deduplicates packages across all projects. Per uv's settings reference (cache-dir), it defaults to $XDG_CACHE_HOME/uv or $HOME/.cache/uv on both Linux and macOS, and %LOCALAPPDATA%\uv\cache on Windows — uv does not use ~/Library/Caches/ on macOS (corrected 2026-08-30; uv cache dir prints the effective path). This means installing requests in 10 projects only stores it once on disk.

Cache commandDescription

uv cache cleanRemove all cached packages
uv cache pruneRemove unused entries
uv cache dirShow cache location

Common Gotchas

  • uv sync auto-creates .venv — it does not install into the system interpreter. There is no uv sync --system flag (corrected 2026-08-30 against the shipped binary; uv sync --system returns error: unexpected argument '--system' found on 0.12.7 and equally on the 0.11.26 this entry was written against). --system exists only on the uv pip commands, e.g. uv pip install --system requests. To point a project environment somewhere other than ./.venv, set UV_PROJECT_ENVIRONMENT, or pass --active to use an already-activated virtualenv.
  • uv.lock must be committed to git. Without it, uv sync resolves fresh (like pip install). With it, installs are deterministic.
  • uv run always syncs first. It ensures the environment matches uv.lock before running your command. Use uv run --no-sync to skip this.
  • Platform-independent resolution can surprise you. uv lock resolves for all platforms by default. If a dependency has platform-specific extras, they are all included in the lockfile even if irrelevant to your OS.
  • uv verifies TLS against bundled Mozilla roots by default — the OS trust store is opt-in. 0.11.0 (2026-03-23) did switch certificate verification to rustls-platform-verifier and the crypto backend to aws-lc, but uv's own certificates documentation states plainly that the default is a bundled Mozilla root set; rustls-platform-verifier only comes into play once you ask for system certificates. So adding a corporate CA to the OS trust store does nothing on its own (corrected 2026-08-30 — the previous wording had this backwards). Pick one: pass --system-certs, set UV_SYSTEM_CERTS=true, or put system-certs = true in uv.toml; or point SSL_CERT_FILE / SSL_CERT_DIR at a PEM bundle; or, for a single pip-mode invocation, uv pip install --cert ./company-ca.pem. --native-tls / UV_NATIVE_TLS were deprecated in 0.11.0 in favour of --system-certs / UV_SYSTEM_CERTS and now emit a deprecation warning. Note the 0.12.0 change here too: a non-empty SSL_CERT_FILE/SSL_CERT_DIR that points at a missing or certificate-free path now fails closed — uv used to fall back to its default roots.
  • The index array-of-tables key is tool.uv.index, singular — the plural spelling silently resolves against PyPI. Writing the double-bracketed header as tool.uv.indexes (a spelling that turns up in third-party migration guides) produces only warning: Failed to parse pyproject.toml during settings discovery: unknown field 'indexes' and then exits 0, having resolved from the public index. Verified on 0.12.7 on 2026-08-30: the same project spelled tool.uv.index correctly failed against an unreachable private index, while the plural spelling resolved six packages from PyPI. A private-index project configured with the wrong key pulls public packages behind a warning nobody reads. Check the spelling, and confirm with uv lock -v that the index you expect was actually queried.
  • Mixing pip install and uv sync causes drift. Packages installed with pip inside a uv-managed .venv are invisible to uv sync and may be removed on the next sync.
  • uvx does cache environments between runs, and that is the actual hazard (corrected 2026-08-30). The tool environment is stored in the uv cache — a repeat uvx cowsay on 0.12.7 ran in 50 ms against 254 ms for the first invocation, with no network. What that means in practice: uvx <tool> resolves the latest version on its first run and then keeps reusing the cached one, so a newly released version will not be picked up until you request uvx <tool>@latest or refresh the cache. uv cache clean deletes these environments; uv tool install gives a tool a durable environment outside the cache.

Dated Negatives (2026-08-30)

Two absences checked on this pass rather than assumed:

  • uv has no task runner. On 0.12.7, uv task returns error: unrecognized subcommand 'task', there is no tool.uv.tasks table in any released changelog, and the long-running upstream request (astral-sh/uv#5903, "Using uv run as a task runner") is still open as of this check. The current answers remain uv run <command>, a [project.scripts] console-script entry, or an external runner such as make, just or nox.
  • No published uv advisory affects the current releases. Six advisories exist across uv's history — ZIP parsing differentials (fixed 0.8.6 and 0.9.6), a tar PAX-header differential (0.9.5), a tar path traversal via symlinks (0.8.22), arbitrary file deletion through RECORD entries (0.11.6), and arbitrary file write through entry-point names (0.11.15). All were fixed at or before 0.11.15, so neither the 0.11.26 this entry originally documented nor 0.12.7 is affected. Note for anyone auditing uv themselves: the 0.8.22 path-traversal advisory (GHSA-7j9j-68r2-f35q) has no OSV record and is published only on the repository's security-advisories page, so an OSV-only sweep undercounts.
