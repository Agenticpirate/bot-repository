Overview

moon is a Rust-built task runner and monorepo orchestrator maintained by moonrepo. It sits in the same niche as Nx, Turborepo, and Bazel, but with a multi-language built-in toolchain (JS/TS, Rust, Go, Python via proto) and a WebAssembly-plugin extension model. v2.0 "Phobos" shipped 2026-02-18 as the first major after a year of WASM-toolchain rewrites; the line documented here, v2.2.4 (2026-05-04), was current at the 2026-05 baseline of this card, with v2.2 introducing an unstable background daemon, async graph building, async affected tracking, and a debug-task AI skill. As of 2026-08-22 the current stable is v2.5.2 (2026-08-19). Moon is also one of the first monorepo runners to ship an MCP server (moon mcp), exposing 8 tools at v2.2.4 and 10 at v2.5.2, so agents can drive task graphs, sync projects, generate from templates, and detect changed files.

Update (verified 2026-08-22): everything below this line describes moon as of v2.2.4 unless a note says otherwise. Three things changed enough since then to matter before you act on this card:

1. v2.5.0 flipped the async engine on by default. experiments.asyncGraphBuilding, experiments.asyncAffectedTracking and experiments.nativeFileHashing all default to true from v2.5 onward (per the experiments reference in .moon/workspace.* and the v2.5.0 changelog). The cycle strictness described in gotcha 5 is therefore no longer opt-in — upgrading to v2.5 can surface a hard cycle error in a workspace that "worked" on v2.2. v2.5.0 also reworked cycle validation to partition production-scoped (production, peer) from development-scoped (development, build, root) dependencies, so cross-scope relationships no longer count as cycles.
2. v2.3.0 changed a caching default in a minor release. A task dependency without an explicit cacheStrategy now resolves to hash only when the dependency declares outputs, and to ignored when it does not — previously it was always hash. Tasks depending on output-less tasks (lint, test) see fewer invalidations; set cacheStrategy: 'hash' explicitly to restore v2.2 behaviour.
3. v2.3.3 (2026-06-10) is a security release. Task outputs hydrated from the remote cache could overwrite files outside the task's declared outputs when the manifest in the remote cache had been tampered with. There is no CVE or GitHub advisory for it — the fix is only recorded under the "Security" heading of the v2.3.3 changelog — so no scanner will flag it. Anyone using remote caching should be on >= 2.3.3, not the >= 2.2.4 this card recommends below.

Architecture: WASM toolchains, proto, project graph

Moon's runtime composition (v2.x):

  • Core (Rust) — task scheduler, project/action/task graphs, content-addressed cache, parallel executor, file watcher, VCS integration.
  • Toolchain plugins (WASM) — Each language toolchain is a WASM extension implementing hooks (extend_project_graph, extend_task_command, extend_task_script, sync_project, sync_workspace, parse_lockfile, etc.). v1's hardcoded "platform" layer is gone; the same hook API drives rust, node, bun, deno, go, unstable_python, system, and any community plugin.
  • proto (separate binary) — moonrepo's polyglot version manager. Moon downloads and pins toolchain versions through proto unless you set MOON_TOOLCHAIN_FORCE_GLOBALS or versionFromPrototools: false. proto is to moon what mise is to a typical CLI workflow.
  • Project graph — Built from moon.yml per project plus toolchain-extracted dependency edges (e.g. package.json workspaces, Cargo.toml workspace members, go.mod deps). v2.2's experiments.asyncGraphBuilding reads projects in parallel via a per-project Tokio worker pool.
  • Action graph — Derived from the project graph plus task deps. v2.0 added transitive reduction (drops redundant edges before scheduling), so moon run :build orders fewer no-op dependency steps.
  • Cache — Local content-addressed by hash of inputs (files, env vars, command, deps). Remote cache via a Bazel-compatible Remote Execution v2 backend, configured under the top-level remote setting in .moon/workspace.* (remote.host is the only required field). The v1 spelling of this setting was unstable_remote; v2.0 renamed it to remote, so a v1 config block carried over verbatim will not be read. Hashes are now generated even if caching is disabled (v2.0 change), so moon hash works regardless.

v2.0 "Phobos" breaking changes

The migration guide at moonrepo.dev/docs/migrate/2.0 lists the full set; the highest-impact ones:

  • moon upgrade is broken from v1 — the distribution format changed (archives instead of bare executables). Reinstall via curl -LsSf https://moonrepo.dev/install/moon.sh | sh or proto install moon.
  • .moon/toolchain.yml → .moon/toolchains.yml (plural). Old singular file is silently ignored.
  • All CLI flags are kebab-case — --cacheLifetime → --cache-lifetime, --summary <level> (was bool).
  • Removed commands — moon node, moon migrate from-package-json, moon query hash, moon query hash-diff. Use moon hash and moon query affected instead.
  • Task command/args are simple-only — no pipes, redirects, multi-command. Use script: for compound shell:
  # Old (v1, still works for simple commands)
  build:
    command: 'tsc && eslint .'   # v1: parsed as compound; v2: ERROR

  # New (v2)
  build:
    script: 'tsc && eslint .'    # v2: explicit shell-script

  • Task inheritance now deep-merges when extending or merging globals. v1 shallow-merged, dropping inner keys silently.
  • .env loaded before task creation, not at execution — and you can no longer reference task env vars in .env substitution (cycle eliminated). Loading order: .env, .env.local, .env.<task_id>, .env.<task_id>.local (v2 expansion).
  • WASM API removed /cwd virtual path — plugin authors must use the new WorkingDir capability.
  • MCP protocol bumped to 2025-11-25 — older Claude Code/Cursor configs that pinned 2024-11-05 will fail handshake.
  • Old "stable" toolchains replaced by new "unstable" toolchains — Python, pip, uv now sit under unstable_* keys. They are functionally complete but not yet API-stable.

v2.1 — affected files, sync-phase tasks, toolchain inheritance

  • affectedFiles object syntax got 3 new options:
- filter: ['**/*.ts', '!**/*.test.ts'] — glob filter applied after Git diff.
- ignoreProjectBoundary: true — pass workspace-relative paths instead of project-relative.
- passDotWhenNoResults: true — pass . when the filter empties (avoids "no args" footgun for tools like Vitest that interpret 0 args as "all").
  • runInSyncPhase: true on a task makes moon sync execute it (e.g. codegen). Lets you keep generated files current without making every consumer task depend on the generator.
  • Per-toolchain inheritAliases / installDependencies — toggle alias propagation and lockfile-driven install behavior independently for node, pnpm, rust, etc.
  • Go toolchain runs go list --deps for graph extension (was go.mod parsing only) — now picks up indirect-but-used module edges.
  • TypeScript pruneProjectReferences: true — drops non-moon-managed references[] from tsconfig.json during sync (no more accidental cross-repo refs after a tooling migration).

v2.2 — daemon, async graph, async affected tracking, AI skills

The 4 headliners:

1. Unstable daemon — moon daemon start runs a background Tokio process that holds the project/task graph in memory and watches .moon/, moon.yml, lockfiles, and package.json for invalidation events. Subsequent moon run :build calls skip cold graph construction. Enable with unstable_daemon: true in .moon/workspace.yml. Subcommands: start, stop, restart, status, logs. Falls back to in-process graph build if the daemon isn't running.
2. Async graph building (experiments.asyncGraphBuilding: true) — per-project Tokio worker pool builds project + task graphs concurrently. Benchmarked 41.8–170% faster depending on graph size. Caveat: does not support cycles (hard error if any are detected; the sync version cuts edges to avoid cycles instead).
3. Async affected tracker (experiments.asyncAffectedTracking: true) — parallelizes the "what changed since base" lookup that drives moon run --affected. 51.9–146% faster for task tracking; project tracking gain is negligible.
4. debug-task AI skill — install with npx skills add moonrepo/moon --skill debug-task (relies on Anthropic's Skills packaging convention). Walks an agent through a 5-step diagnostic: configuration inspection → cache check → execution probe → CI-vs-local diff → fix validation. Ships with rules for "15+ specific problem types".

Other v2.2 wins: system toolchain made built-in (no external WASM download), MOON_PIPELINE_AUTO_CLEAN_CACHE / MOON_PIPELINE_CACHE_LIFETIME / MOON_PIPELINE_KILL_PROCESS_THRESHOLD env-var support for the matching pipeline.* settings, and a much smaller graph memory footprint (nodes are integers rather than objects — which is also why the --json shape of moon action-graph, moon project-graph and moon task-graph changed in v2.2.0).

Correction (verified 2026-08-22): the MCP generate JSON-schema fix, the bash-falls-back-to-sh fix and "a task command can now end with --" all landed in v2.1.0, not v2.2 — they are listed under the v2.1.0 fixes in the changelog.

MCP server: moon mcp

Moon exposed 8 MCP tools at v2.2.4 for agent integration — the 7 carried over from v1.37/1.38 plus generate, which v2.0 added (tool_box!(MoonTools, [...]) in crates/mcp/src/mcp.rs at tag v2.2.4). Earlier revisions of this card said 7 and omitted generate; that was the v1 count:

ToolPurpose

get_projectRetrieve a single project (id, source, dependencies, tasks) by id
get_projectsRetrieve all projects (v2 returns fragments — smaller payload)
get_taskRetrieve a task by <project>:<task> target
get_tasksRetrieve all tasks (v2 returns fragments)
get_changed_filesGit diff between revisions (replaces "touched files" — renamed in v2)
sync_projectsRun the SyncProject action for one or many projects (writes lockfiles, tsconfig refs, etc.)
sync_workspaceRun the SyncWorkspace action (VCS hooks, root configs)
generateRun the code generator for a template (added in v2.0)

Update (verified 2026-08-22): v2.3.0 added two more, for a total of 10 in v2.5.2 — get_template (a template plus its merged variable schema, extends chain resolved) and get_templates (all templates, with an optional case-insensitive filter regex, mirroring moon templates --filter). Their purpose is to let an agent inspect a template's variable schema before calling generate.

MCP protocol version: 2025-11-25 in v2.0+ (was 2025-03-26 in v1.x). Pinning the old version in your editor config will fail the handshake silently — symptom: "moon" appears in the MCP list but no tools are discoverable.

Common gotchas

1. .moon/toolchain.yml (singular) is silently ignored after upgrading to v2 — the file rename to .moon/toolchains.yml (plural) is a hard config-file change. Symptom: every command runs as if no toolchains are configured. Fix: mv .moon/toolchain.yml .moon/toolchains.yml.
2. Compound commands in command: error in v2 — v1 silently parsed tsc && lint as a script; v2 errors with "command must be a single executable". Move to script:.
3. unstable_python toolchain venv path missing in v2.2.0–2.2.3 — fixed in v2.2.4. Symptom: moon run :test fails with pytest: command not found even though uv sync succeeded earlier. Pin >=2.2.4 if using Python — but if you also use remote caching, pin >=2.3.3, which fixes the remote-cache hydration path-escape described in the update block above.
4. hashOnFailure regression in v2.2.0–2.2.3 — failing actions persisted their hash, so re-runs without code changes would skip rather than retry. Fixed in v2.2.4. If you saw "stuck failures" between Apr 12 and May 4, this is why.
5. Async graph building can't recover from cycles — experiments.asyncGraphBuilding: true errors hard if any project graph has a cycle. The sync builder cuts edges automatically to break cycles, so projects that "worked" before may now fail loudly. Not always a bug — usually the cycle is real. Update (verified 2026-08-22): this experiment defaults to true from v2.5.0, so the hard error is now the default behaviour; v2.5.0 partially softened it by validating cycles per dependency-scope partition, so production-scoped and development-scoped edges no longer collide. Set experiments.asyncGraphBuilding: false to get the old edge-cutting builder back.
6. Daemon doesn't auto-restart on .moon/workspace.yml changes — change toolchain config and you must moon daemon restart. Falls back to in-process if you forget but loses the warm graph.
7. MCP protocol 2024-11-05 pinned in older Claude Code configs fails silently — moon lists in the MCP picker but no tools are discoverable. Re-add with claude mcp add or remove the protocolVersion pin.
8. moonx is a shorthand for moon exec, not for moon run — the v2.0 announcement stabilizes moonx as a standalone binary that is "simply a shorthand for moon exec", replacing the old moon <target> shorthand. It is not flag-limited: moon exec (and therefore moonx) accepts --affected, --base/--head, --upstream/--downstream, --job/--job-total, --query and the rest, so moonx --affected build is valid. What differs is the defaults: moon run, moon check and moon ci are all thin wrappers that pre-fill moon exec options which then cannot be overridden — moon ci, for instance, forces on_failure: continue, --summary detailed and --downstream direct. Reach for moonx/moon exec when you need control over those.
9. Project IDs from projects.globFormat: 'source-path' collide with id field — if both the directory path and an explicit id resolve to the same string, moon errors at startup. v2.1.0 made duplicate aliases warnings (was hard error), but project-id collisions are still hard.
10. pipeline.autoCleanCache runs after every task run, but only deletes artifacts older than pipeline.cacheLifetime — it does not wipe the cache. cacheLifetime already defaults to "7 days", so the matching MOON_PIPELINE_CACHE_LIFETIME env var (added in v2.2.0 alongside MOON_PIPELINE_AUTO_CLEAN_CACHE) is only worth setting to change that window, and it takes a parsed duration string like '24 hours', not a bare 7d. Since v2.3.0 the auto-clean is executed by the daemon rather than at the tail of the main process. If you actually want a full wipe, that is moon clean --all (alias --reset), which internally cleans with a one-second lifetime.
11. Task -- separator can no longer terminate command — command: 'foo --' was rejected before v2.1.0, which carries the "fixed an issue where a task command could not end with --" entry (this card previously attributed the fix to v2.2.0). The fix covers a trailing -- specifically; mid-command -- is still ambiguous.
12. moon ci is moon exec under the hood in v2 — crates/app/src/commands/ci.rs literally builds ExecArgs and calls exec(), forcing on_failure: continue, ci: true, a detailed summary and --downstream direct. Exit-code semantics differ from v1, so audit any wrapper script that branches on the code. Update (verified 2026-08-22): v2.4.3 changed this again — a failing task now propagates its own exit code instead of always exiting 1, and v2.5.2 fixed a related case where a dependent action could still run to completion after a required dependency had already failed and aborted the pipeline.
13. affectedFiles: true (legacy boolean) still works — but you only get the v2.1 sub-options with the object syntax. If you're hitting "no args passed to vitest" issues, switch to affectedFiles: { passDotWhenNoResults: true }.
14. script runs through bash/sh, not Node — even in a Node project. Cross-platform scripts need cross-env-style prefixes; v2.2's bash→sh fallback helps on Alpine but doesn't make Windows-incompatible bashisms work.
15. Remote cache is configured under remote, not unstable_remote, and it speaks HTTP as well as gRPC — unstable_remote was the v1 spelling; v2.0 renamed the setting to remote (WorkspaceConfig.remote in crates/config/src/workspace_config.rs), so a copied v1 block is simply not read. The backend must implement the Bazel Remote Execution v2 contract, but remote.api accepts grpc (the default) or http — the latter being Bazel's HTTP caching protocol — so a plain REST cache endpoint is supported, contrary to what this card previously said. remote.host takes grpc(s):// or http(s)://. Self-hosting is usually bazel-remote; Depot Cache is the documented hosted option (grpcs://cache.depot.dev plus a DEPOT_TOKEN). It is still not an S3 bucket URL: point moon at a caching service, and let that service use S3 for storage.
16. If both .config/moon/ and .moon/ exist, .config/moon/ wins — not .moon/. locate_config_dir() in crates/common/src/path.rs returns .config/moon whenever that directory exists and falls back to .moon otherwise; this has been the behaviour since v2.0, including at v2.2.4. There is no warning either way, so a half-finished migration silently runs off the .config/moon copy while the stale .moon config sits there looking authoritative. (Related: v2.4.3 fixed synced VCS hooks always being written to .moon/hooks; they now land in .config/moon/hooks when that is the active directory.)
17. moon clean has no --plugins flag — at both v2.2.4 and v2.5.2 CleanArgs in crates/app/src/commands/clean.rs exposes only --all (alias --reset) and --lifetime; there is no plugin-specific clean, and --plugins errors out. moon does cache WASM modules aggressively, so a republished toolchain plugin can keep serving old behaviour; use moon clean --all to reset cached state, and moon toolchain / moon extension (both have a download subcommand since v2.1.4) to manage plugins. From v2.3.1 plugins are distributed via ghcr.io rather than raw URLs.
18. MCP server runs in the workspace root, not project root — MOON_WORKSPACE_ROOT env var must point at the directory containing .moon/. Setting it to a project subdirectory makes every tool return empty.
19. pnpm/yarn/npm toolchains require node enabled, which requires javascript — declarative dependency chain enforced at config-load time. Symptom: pnpm toolchain config silently inert. Fix: declare javascript: {} and node: {} (empty objects are fine).
20. Pkl config is a fully supported format, and it does get a generated schema — this card previously called it experimental and schema-less; both are wrong. Pkl was one of only two formats moon v1 accepted (alongside YAML), and v2.0 widened the set to JSON, JSONC, HCL, Pkl, TOML and YAML for every moon config file. Schema validation via JSON Schema has existed since v1.33.0 for all formats: schemas are generated into .moon/cache/schemas on the first task run (or on demand with moon sync config-schemas), and you point at them with $schema. The hosted moonrepo.dev/schemas URLs are deprecated — reference the local files instead. The real Pkl caveats are different ones: .pkl files cannot be extended from a URL, each file is evaluated in isolation so task inheritance and config merging cannot see its loops or variables, default cannot be used as a setting name in template.pkl (use defaultValue), and the pkl binary must be installed because Pkl uses a client-server evaluator.
