Overview

Atlas (ariga.io/atlas) is an open-source schema management engine that treats a SQL database schema as version-controlled HCL or SQL code, computes the diff against the live target, plans a safe migration, lints it for destructive changes, and applies it through a CI/CD pipeline. It is language-agnostic (no Go/Python/TS dependency at runtime), works with PostgreSQL, MySQL/MariaDB, SQLite, SQL Server, ClickHouse, Redshift, Oracle, Snowflake, Spanner, Databricks, CockroachDB, Aurora DSQL, YugabyteDB and Azure HorizonDB (most of those only under the commercial tier — see the licensing update below), and is the canonical "Terraform for databases" answer when the desired-state model fits better than the imperative migration files that Flyway / Liquibase / golang-migrate / goose / dbmate maintain.

Atlas published v1.0.0 on 2025-12-24, marking long-term API stability after running in production at Ariga's customers for several years. v1.2.0 (2026-04-10) was current at the 2026-05-27 baseline, with v1.1.0 (2026-02-05) adding declarative database-security-as-code, declarative seed data, Aurora DSQL, Azure Fabric, and CockroachDB. The community OSS binary is Apache-2.0; default-distributed binaries are proprietary, and the commercial Atlas Pro / Atlas Cloud tier layers the registry, drift monitoring, and CI checks on top.

Update (verified 2026-08-25): current stable is v1.3.0, published 2026-08-02 (Go module ariga.io/atlas @latest resolves to v1.3.0; the tag commit is dated 2026-07-29). Patch releases v1.2.1 (2026-05-21), v1.2.2 (2026-06-04) and v1.2.3 (2026-06-22) also shipped — note that v1.2.1 predates this card's own 2026-05-27 fetch, so "the latest stable as of fetch is v1.2.0" was already off by one when it was written. v1.3 adds the Cloud Security Graph, Atlas Scripts (data operations as code), an atlas cloud CLI command group, schema annotations, pre-apply drift detection, and atlas config validate.

Two Workflows: Declarative and Versioned

Atlas supports two distinct migration models, and most teams pick one and stay with it:

Declarative workflow (atlas schema apply) — Atlas computes the diff between the desired schema (HCL or SQL file) and the target database at apply-time, then prints the migration plan for explicit approval. Closest analog: kubectl apply. Best fit when the source of truth is the schema file and you don't need a permanent record of every migration step.

Versioned workflow (atlas migrate diff + atlas migrate apply) — Atlas generates explicit numbered SQL migration files on demand by diffing the desired schema against a migrations/ directory, then atlas migrate apply runs the unapplied files in order against the target. Closest analog: a managed Flyway/golang-migrate workflow where the migration files are auto-generated instead of hand-written. Best fit when you want an auditable migration history committed alongside the schema.

The versioned workflow can read and write migration files in atlas (default), golang-migrate, goose, dbmate, flyway, or liquibase formats via the format= query parameter on the file://migrations URL — so you can introduce Atlas into an existing project without rewriting the migration directory. See database-migrations-best-practices for the trade-offs between the formats.

HCL Schema Definition

Atlas's HCL language is its primary schema-as-code surface. Files use a per-database extension that editor plugins recognize: .pg.hcl (PostgreSQL), .my.hcl (MySQL), .ma.hcl (MariaDB), .lt.hcl (SQLite), .ms.hcl (SQL Server), .ch.hcl (ClickHouse), .rs.hcl (Redshift), .oc.hcl (Oracle), .sp.hcl (Spanner), .sf.hcl (Snowflake), .dbx.hcl (Databricks).

schema "public" {
  comment = "Application schema"
}

table "users" {
  schema = schema.public

  column "id" {
    type = int
  }
  column "email" {
    type = varchar(255)
    null = false
  }
  column "manager_id" {
    type = int
    null = true
  }

  primary_key {
    columns = [column.id]
  }

  index "idx_email" {
    columns = [column.email]
    unique  = true
  }

  foreign_key "manager_fk" {
    columns     = [column.manager_id]
    ref_columns = [column.id]
    on_delete   = SET_NULL
    on_update   = NO_ACTION
  }

  check "non_empty_email" {
    expr = "length(email) > 0"
  }
}

Atlas also accepts SQL files directly (schema.sql) as the desired state, and can import an external ORM schema from GORM, Ent, Hibernate, SQLAlchemy, Prisma, Drizzle, TypeORM, Sequelize, and others via the data "external_schema" block in atlas.hcl, referenced from an env as src = data.external_schema.<name>.url, so the ORM model becomes the source of truth. Corrected 2026-08-25: the baseline said "via the --env integration", which names a flag rather than the mechanism — --env only selects which env block to use. The ORM bridge is the external_schema data source documented at atlasgo.io/atlas-schema/external, whose supported list also includes Django and Beego.

Core Commands

# Inspect a live database and emit HCL or SQL
atlas schema inspect -u "postgres://user:pass@host:5432/db?sslmode=disable" > schema.pg.hcl

# Declarative: apply desired-state diff against the target
atlas schema apply \
  --url "postgres://user:pass@host:5432/db?sslmode=disable" \
  --to  "file://schema.pg.hcl" \
  --dev-url "docker://postgres/15/dev?search_path=public"

# Versioned: generate the next migration file by diffing desired vs migrations/
atlas migrate diff create_users \
  --dir "file://migrations" \
  --to  "file://schema.pg.hcl" \
  --dev-url "docker://postgres/15/dev?search_path=public"

# Versioned: apply unapplied migrations to the target
atlas migrate apply \
  --url "postgres://user:pass@host:5432/db?sslmode=disable" \
  --dir "file://migrations"

# Lint migrations for destructive / dangerous changes
atlas migrate lint --dir "file://migrations" --dev-url "docker://postgres/15/dev"

The --dev-url flag is mandatory for diff and lint operations: Atlas spins up a disposable database matching the production URL (Atlas's Docker driver pulls the image, runs the schema, computes the diff, then tears down), so the plan is computed against a clean baseline rather than the polluted target. This is the single most important detail to internalize. Corrected 2026-08-25: --dev-url is a hard-required flag, not a quality knob — running atlas migrate diff or atlas migrate lint without it on the shipped v1.3.0 binary exits immediately with Error: required flag(s) "dev-url" not set. It never silently computes a worse diff. The reason it is required is that Atlas needs a clean baseline to reason about database-specific constructs (PostgreSQL CHECK constraints, MySQL stored functions, ClickHouse engine settings). If Docker is unavailable, sqlite://dev?mode=memory is a valid Docker-free dev URL for SQLite work.

Migration Linting

atlas migrate lint runs a configurable suite of analyzers over generated migration files and flags destructive or dangerous operations before they reach production:

atlas migrate lint --dir "file://migrations" --dev-url "docker://postgres/15/dev" --latest 1

Corrected 2026-08-25 — five of the six analyzer codes originally listed here were attached to the wrong rule. Re-derived from the vendor's own check table at atlasgo.io/lint/analyzers and from a live migrate lint run on the shipped v1.3.0 binary:

Other families: CD1xx (constraint deletion — Atlas Pro), MY1xx (MySQL, including the enum-reorder table-copy checks), LT101 (SQLite), NM1xx (naming conventions), OW1xx (ownership policy) and PG110 (table created with non-optimal column alignment). v0.38 did add the SQL-injection and transaction-misuse analyzers as the baseline says. Every migrate lint finding prints its own doc anchor, e.g. https://atlasgo.io/lint/analyzers#DS102 — read that rather than trusting a remembered code.

The lint stage is the second mandatory thing to internalize: an atlas migrate diff that successfully generates a file does NOT mean the file is safe to apply. Always pipe diffs through atlas migrate lint in CI before merging.

Update (verified 2026-08-25) — atlas migrate lint is not free on the default binary. Since v0.38 the standard distribution gates it behind Atlas Pro. On the shipped v1.3.0 default binary with no atlas login, atlas migrate lint aborts with Abort: Starting with v0.38, 'atlas migrate lint' is available only to Atlas Pro users.; atlas schema lint and atlas config validate abort the same way. The Apache-2.0 atlas-community build does run migrate lint without any token — verified: it flagged DS102 on a generated DROP TABLE and printed the suggested pre-migration check — because, in Ariga's words, "the command and existing code remain open source and available in the Community Edition." The practical consequence: a CI job that installs the default binary and runs migrate lint without an Atlas token fails the build rather than silently passing, so budget for a token or pin the community binary in CI.

CI/CD Integration

Atlas ships first-party integrations for GitHub Actions, GitLab CI, Terraform (via the HashiCorp Terraform / OpenTofu provider ariga/atlas), Kubernetes (via the Atlas Operator CRD), and any platform via Docker. The typical pipeline shape:

# .github/workflows/atlas-ci.yml
name: atlas-migrate-ci
on: [pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
        env: {POSTGRES_PASSWORD: pass}
        options: --health-cmd pg_isready
        ports: ["5432:5432"]
    steps:
      - uses: actions/checkout@v4
      - uses: ariga/setup-atlas@v0
        with:
          cloud-token: ${{ secrets.ATLAS_CLOUD_TOKEN }}
      - uses: ariga/atlas-action/migrate/lint@v1
        with:
          dir: "file://migrations"
          dev-url: "postgres://postgres:pass@localhost:5432/dev?sslmode=disable"

The migrate/push and migrate/apply actions handle the deploy half — push to the Atlas Schema Registry on merge, apply to staging/prod on tag. See GitHub Actions limits for runner concurrency caps that affect Atlas's parallel-tenant rollout strategy on large fleets.

For Kubernetes-native deployments, the Atlas Operator watches AtlasSchema and AtlasMigration CRDs and applies schemas to in-cluster databases (often paired with CloudNativePG for PostgreSQL). For data-warehouse pipelines, Atlas pairs naturally with dbt (Atlas owns DDL, dbt owns transformations) and with lakehouse formats like DuckLake when the warehouse target is ClickHouse MergeTree or chDB.

Multi-Tenant and Staged Rollouts (v1.0+)

v1.0's deployment block in atlas.hcl lets you express staged rollouts as code — canary cohorts, free-tier parallelism, paid-tier serialization, error-handling policy. Note (verified 2026-08-25): "Deployment Rollout" is an Atlas Pro feature on the vendor's compatibility matrix, and the block does not exist in the Apache-2.0 community build.

deployment "staged" {
  variable "name" { type = string }
  variable "tier" { type = string }

  group "canary" {
    match = startswith(var.name, "canary-")
  }
  group "free" {
    match       = var.tier == "FREE"
    parallel    = 10
    on_error    = CONTINUE
    depends_on  = [group.canary]
  }
  group "paid" {
    parallel    = 3
    depends_on  = [group.free]
  }
}

env "prod" {
  for_each = toset(data.sql.tenants.values)
  url      = urlsetpath(var.url, each.value.schema)
  migration {
    dir = "atlas://my-app"
  }
  rollout {
    deployment = deployment.staged
    vars = {
      name = each.value.name
      tier = each.value.tier
    }
  }
}

Corrected 2026-08-25: the baseline sample set the rollout source with src = "atlas://my-app". src is the declarative desired-state key and is ignored by the versioned rollout path — running atlas migrate status --env prod against that config silently falls back to the default file://migrations directory. Ariga's own examples (atlasgo.io/versioned/apply, atlasgo.io/atlas-schema/projects) use migration { dir = "atlas://my-app" }, corrected above.

This solves the "database per tenant, thousands of databases, can't downtime any of them" problem that the PostgreSQL JSON vs JSONB single-schema multi-tenancy pattern was the previous-generation workaround for.

Common Gotchas

  • --dev-url is not optional. Corrected 2026-08-25: skipping it does not produce a wrong diff — migrate diff and migrate lint refuse to start at all (Error: required flag(s) "dev-url" not set). The reason Atlas requires it is that it needs a clean baseline for database-specific server-side state (PostgreSQL extensions, MySQL collations, ClickHouse engine settings). The dev URL spins up a clean disposable database from a Docker image (docker://postgres/15, docker://mysql/8, docker://clickhouse/23.11); Atlas computes the diff against that baseline, then tears it down. The Docker driver is built into Atlas — no separate docker invocation is needed, but Docker must be running locally.
  • Default binaries are NOT Apache 2.0. The pre-built atlasgo.sh / Homebrew / Docker binaries are proprietary. Updated 2026-08-25: from v1.3.0 they are governed by Ariga's Master License and Services Agreement (ariga.io/legal/msa), which replaced the separate Atlas EULA and SaaS terms; it is an ordinary commercial licence with prohibited-use clauses (no building or supporting competing products, no unauthorised redistribution, telemetry that cannot be fully opted out of), so the baseline's "permissive but proprietary" characterisation should not be relied on in a legal review. The Apache-2.0 build is atlas-community, and it is not a GitHub release asset — it is downloaded from release.ariga.io/atlas/atlas-community-<os>-<arch>-<version>, documented at atlasgo.io/community-edition. atlas version does report the channel (atlas community version v1.3.0 vs atlas version v1.3.0), and atlas license prints the governing licence for the build you have.
  • Atlas Pro / Cloud features fail closed without a license token — and the free surface is smaller than the baseline claimed. Drift detection, the Atlas Schema Registry, monitoring-as-code, the declarative-migration UI and column-level lineage all require an Atlas Cloud token (ATLAS_TOKEN env var or the cloud-token CI input). Corrected 2026-08-25 against the shipped v1.3.0 binary and atlasgo.io/features: the commands that genuinely run without a token are schema inspect, schema diff, schema apply, migrate diff and migrate apply. migrate lint is Pro (see the linting section), as are custom schema rules, pre-migration checks, drift detection, migration checkpoints, schema visualization, interactive migrations, the testing framework, deployment rollout, database-security-as-code, declarative data management and Atlas Scripts. One of these degrades quietly rather than failing closed: an unauthenticated atlas schema inspect prints Notice: Skipping triggers, functions, stored procedures and other advanced objects. Upgrade to Pro to enable these features and more. and then emits an incomplete schema, so atlas schema inspect > schema.pg.hcl on a free install hands you a file with no views, triggers, functions or procedures in it. Look for that notice before committing inspected output.
  • HCL file extension matters for editor support. A file named schema.hcl works at the CLI level but loses editor syntax highlighting and the per-database validation. Rename to schema.pg.hcl / schema.my.hcl / etc. to activate the VSCode and JetBrains plugins. The CLI doesn't care about the suffix; the editor plugins do.
  • Versioned-workflow migration ordering uses lexicographic comparison. A migration named 20260527-add-users.sql sorts before 20260527000000-add-orders.sql because the dash comes before the digit in ASCII. Atlas auto-generates YYYYMMDDHHmmss_name.sql by default — leave the timestamp format alone unless you control all generated names everywhere. Mixing migrate diff defaults with hand-written files in a non-standard format is the most common "migrations apply in the wrong order" bug class.
  • Down migrations (atlas migrate down). Corrected 2026-08-25 — the baseline claim was wrong. atlas migrate down needs neither an Atlas Cloud-bound directory nor paired up/down files. Verified on the shipped v1.3.0 default binary with no atlas login, against a plain file:// migration directory: Atlas planned the inverse itself, ran a generated pre-migration safety check (a SELECT NOT EXISTS emptiness probe on the table) and reverted the version. What is true is that migrate down is a Pro-tier command absent entirely from the Apache-2.0 atlas-community build — that build's own startup notice lists "down migrations" among the things it lacks — and that --to-tag and registry-backed rollback do require Atlas Cloud. Use --dry-run first; --plan forces on-the-fly planning even when down files already exist.
  • The migrate hash step must be committed alongside the migration files. Atlas writes an integrity hash (atlas.sum) covering every file in migrations/, and migrate apply refuses to run if the hash doesn't match. Forgetting to commit atlas.sum (or hand-editing a migration file after migrate diff regenerated it) produces a "checksum mismatch" error in CI. Fix is always atlas migrate hash --dir file://migrations + commit.
  • PostgreSQL search_path matters in the URL. A postgres://... URL without ?search_path=public inspects ALL schemas in the database and emits HCL/SQL for everything, including pg_catalog system tables. Always pin search_path=<your-schema> on inspect, diff, apply. Same pattern applies to Redshift.
  • CockroachDB and Aurora DSQL drivers landed in v1.1 (2026-02-05). Corrected 2026-08-25: the "still preview-quality" label was not the vendor's. atlasgo.io/features lists both as ordinary Pro-tier drivers with no beta marker, both have shipping guides (atlasgo.io/guides/cockroachdb/automatic-migrations, atlasgo.io/guides/dsql/automatic-migrations), both have dedicated Docker dev-URLs (docker://crdb/v25.1.1, docker://dsql/16), and Atlas's only "preview support for CockroachDB" language dates back to v0.4.2 in 2022. Pinning a known-good patch and linting remains sound advice for any driver, but it is not a documented caveat for these two. Two drivers have joined since this card was written: YugabyteDB (now GA) and Azure HorizonDB.
