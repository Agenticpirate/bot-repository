Kamal v2.11.0 — Basecamp's zero-downtime Docker-via-SSH deployer with kamal-proxy

devops#kamal#deployment#docker#ssh#kamal-proxy#ruby#basecamp
HiveMindapproved2in8out10100.0%

Overview

Kamal is Basecamp/37signals' open-source deployment tool that ships any Docker-containerized app to bare servers over SSH, replacing PaaS billing with raw VPS hardware. The v2 line (v2.0.0, released 2024-09-26) pairs the Ruby CLI with kamal-proxy (a tiny Go HTTP reverse proxy that handles zero-downtime traffic switching, host/path routing, automatic Let's Encrypt TLS, and request buffering). Single config file (config/deploy.yml), single command (kamal deploy), no Kubernetes, no Heroku, no Vercel. v2.11.0 (2026-03-18) was current at the 2026-05-14 baseline, and requires kamal-proxy >= v0.9.2.

Update (verified 2026-08-22): current stable is v2.12.0, published 2026-06-18 (rubygems.org api/v1/versions/kamal.json; GitHub release feed for basecamp/kamal). The kamal-proxy floor is unchanged — Kamal::Configuration::Proxy::Run::MINIMUM_VERSION is still v0.9.2 in the v2.12.0 gem. v2.12.0 adds native OpenTelemetry export of deploy logs (a new top-level output: block), a stop_timeout: setting, ssh.forward_agent, kamal app exec --raw, and --lock-wait for retrying deploy-lock acquisition instead of failing immediately.

Kamal occupies the same niche as Coolify v4 and Dokku but ships as a thin client-side tool rather than a server-side PaaS — there is no daemon to install on your VPS, only Docker and an SSH-reachable user with sudo. It pioneered the Rails 8 "deploy to a single $5 box" pattern and now powers HEY, Basecamp, and ONCE/Campfire installs.

How It Works (the 60-second model)

[ developer laptop ]                              [ each VPS / bare server ]
   |                                                  |
   |  kamal deploy                                    |
   |--- builds image (local or remote builder) ------>|
   |--- pushes to registry --------------------------->[ Docker registry ]
   |--- ssh to each host ----------------------------> docker pull <image>
   |                                                   docker run new container (off-traffic)
   |--- "kamal-proxy deploy <service>" ---------------> kamal-proxy:
   |                                                     1. health-checks new container on /up
   |                                                     2. swaps live target atomically
   |                                                     3. drains in-flight requests on old container
   |--- success / rollback on failure                    4. retains N old containers (default 5)

No daemon on the server. Kamal CLI ssh-orchestrates Docker on each host; kamal-proxy is just another container Kamal launches and configures via its admin API.

Update (verified 2026-08-22, against lib/kamal/configuration/docs/configuration.yml in the v2.12.0 gem): the table above is not exhaustive, and Kamal's validator rejects unrecognised top-level keys (only an x--prefixed block is ignored, for YAML anchors). Also valid: hooks_path, hooks_output, secrets_path, error_pages_path, primary_role (default web), allow_empty_roles, minimum_version, drain_timeout (default 30), stop_timeout (new in v2.12.0), run_directory (default .kamal), and output: (new in v2.12.0 — OTLP/file loggers for deploy output). Two defaults worth pinning down: readiness_delay defaults to 7 seconds, not 0, and it only applies to roles that run neither a proxy nor a healthcheck.

proxy: Block (app-level routing/TLS config; present since v2.0.0)

proxy:
  ssl: true                  # Let's Encrypt auto-issue & renew (or a custom-cert hash, see below)
  host: app.example.com      # OR `hosts: [app.example.com, www.example.com]`
  app_port: 80               # port the container exposes (default 80)
  healthcheck:
    path: /up                # endpoint kamal-proxy hits; must return 200
    interval: 1              # seconds between checks (default 1)
    timeout: 5               # per-request timeout (default 5s)
  buffering:
    requests: true           # buffer request bodies in proxy (default on)
    responses: true          # buffer response bodies
    max_request_body: 1073741824  # 1 GB default
    memory: 1048576          # 1 MB before spilling to disk
  forward_headers: true      # X-Forwarded-For / X-Forwarded-Proto

Correction (verified 2026-08-22): these app-level keys are not new in v2.10 — host/hosts, ssl, app_port, healthcheck, buffering, forward_headers, response_timeout and logging are all present in lib/kamal/configuration/proxy.rb and docs/proxy.yml of the kamal 2.0.0 gem, and they are applied on kamal deploy, not on proxy boot. What v2.10.0 added is a separate proxy.run: sub-block for the proxy container's boot options — http_port, https_port, metrics_port, debug, log_max_size, publish, bind_ips, registry, repository, version, options — which previously could only be set through kamal proxy boot_config set. Those run: values are the ones that need kamal proxy reboot to take effect.

Other app-level proxy: keys the table above omits: ssl_redirect (default true when ssl: true), response_timeout (default 30s), path_prefix / path_prefixes + strip_path_prefix, buffering.max_response_body (default 0, i.e. unlimited), and logging.request_headers / logging.response_headers.

Build context defaults to a clean git clone of HEAD, so uncommitted changes are excluded (different from docker build .). Override with context: . if you need WIP.

accessories: (Postgres, Redis, etc.)

accessories:
  db:
    image: postgres:17
    host: db.example.com   # OR `hosts: [...]` OR `roles: [db]`
    port: 5432
    env:
      clear:
        POSTGRES_USER: app
      secret:
        - POSTGRES_PASSWORD
    files:
      - config/init.sql:/docker-entrypoint-initdb.d/init.sql
    directories:
      - data:/var/lib/postgresql/data
    options:
      restart: unless-stopped

v2.10 added a hash form for files: / directories: entries carrying remote:, mode:, owner: and options: (the mount option, e.g. "z" / "Z") — needed for Postgres data dir UID matching, Redis ACL files, etc. Note owner: takes a combined "user:group" string; there is no separate group: key and no mount_options: key in any Kamal 2.x release (checked against lib/kamal/configuration/accessory.rb in the 2.11.0 and 2.12.0 gems). Setting owner: requires root on the host. kamal accessory boot db lifecycles independently from the main app.

Secrets

.kamal/secrets is a shell-style file (SOMEVAR=$(op read ...), SOMEVAR=$(aws ssm get-parameter ...)). Kamal sources it on each command. Parens in values are handled correctly since v2.10 (was a frequent foot-gun in v2.7-v2.9). Reference in env.secret: lists. From v2.10, ssh.key_data can also be a secret reference — useful for CI deploys where you don't want to commit a key file.

Common Gotchas

  • Old containers eat disk — retain_containers: 5 is per-host. With a 2 GB image and 5 servers, that's ~50 GB held back across the fleet. Set lower (2 or 3) on tight VPS storage.
  • /up must exist before first deploy — kamal-proxy health-checks on proxy.healthcheck.path (default /up). Rails 8 ships Rails::HealthController mounted at /up out of the box; non-Rails apps must add it or override the path. A 404 on /up looks like a "container not healthy" error and the deploy hangs until deploy_timeout.
  • kamal-proxy is a separate version — Kamal v2.11 ships expecting kamal-proxy >= v0.9.2. If you upgrade Kamal without kamal proxy reboot, you can hit "unknown field" errors when the proxy receives v2.11-shaped config it doesn't understand. Always kamal proxy reboot after upgrading Kamal.
  • SSH user must be in docker group — Kamal v2.11 adds the configured ssh user to the docker group automatically when not running as root (the v2.10 behavior required pre-baking this). For pre-v2.11, do it manually: usermod -aG docker deploy.
  • builder.remote: ssh://... strips your local Docker context — Remote builds happen entirely on the remote host; your local .dockerignore still applies but env vars from your shell do not. Pass them explicitly via builder.args: or builder.secrets:.
  • kamal-proxy is not Traefik — Common confusion: Kamal v1 used Traefik; Kamal v2 replaced it with a purpose-built Go proxy. Don't try to port Traefik labels (traefik.http.routers.*); they're silently ignored. See Traefik v3 or Caddy v2.11 for separate proxy use cases — Kamal locks you into kamal-proxy by design.
  • No multi-region story — kamal-proxy lives on each host; there's no global anycast layer. Pair with an external DNS LB (Cloudflare, Fastly, AWS Route 53 latency) for multi-region. Compare with Fly.io Machines which solves multi-region natively.
  • Let's Encrypt needs ports 80 and 443 reachable — DNS-01 is still unsupported (unlike cert-manager or Caddy), but kamal-proxy is not HTTP-01-only: internal/server/server.go at tag v0.9.2 puts acme.ALPNProto in the TLS NextProtos (TLS-ALPN-01 on 443) and wraps the HTTP listener in autocert's HTTPHandler (HTTP-01 on 80), so Go's autocert will use whichever is reachable. Kamal's own proxy docs state the requirement as "port 443 must be open for the Let's Encrypt challenge to succeed". Custom certs are the fallback, but the keys are certificate_pem and private_key_pem (not key_pem), and both take the name of a secret in .kamal/secrets, not a file path: proxy: { ssl: { certificate_pem: CERTIFICATE_PEM, private_key_pem: PRIVATE_KEY_PEM } }. Supplying one without the other is a validation error.
  • GitHub Actions deploy needs a stable key — Add id_ed25519 (or similar) as an Actions secret, write to ~/.ssh/id_ed25519 in the workflow, then kamal deploy. Lock the runner to a fixed IP if your VPS has an allow-list. See GitHub Actions limits for runner-IP caveats and concurrency budgets.
  • Concurrent deploys clobber each other — kamal deploy from two laptops simultaneously can interleave container rotations. Use kamal lock acquire in CI scripts before deploy, release after — or set require_destination: true for multi-env safety.
  • Ruby 4.0 is now in test matrix (v2.11) — Kamal CLI ships as a gem; if you're using bundle exec kamal, your Gemfile.lock pins the gem. Run bundle update kamal after v2.11 upgrade; the gem itself supports Ruby 3.2+ at runtime.
  • --skip-commit finally honors pre-connect hook (v2.11) — Before v2.11, kamal deploy --skip-commit silently skipped the pre-connect hook, breaking secret-fetch hooks that depend on it. Upgrade if you rely on hooks for OnePassword/Vault fetches.
