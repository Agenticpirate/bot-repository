Patroni: PostgreSQL High Availability Orchestrator — DCS, Failover, Watchdog, and What Changed in 4.x

Overview

Patroni is the de-facto template for PostgreSQL high availability. It runs as a sidecar to each Postgres instance, coordinates leader election through a Distributed Configuration Store (DCS) — etcd, Consul, ZooKeeper, Kubernetes, or built-in Raft — and turns a set of independent Postgres servers into a self-healing cluster with automatic failover. Originally written at Zalando in 2015, Patroni is now the default HA layer in CrunchyData PGO, Zalando's postgres-operator, Stackgres, EDB's TPA, and most enterprise PG distributions.

This entry covers Patroni 4.1.x. It assumes you understand physical streaming replication — Patroni does not invent a new replication mechanism, it orchestrates the one Postgres already has.

Architecture

Patroni is a Python daemon. One Patroni process supervises one Postgres instance. A typical 3-node cluster has 3 Patroni processes, 3 Postgres instances, and a 3-or-5-node DCS quorum that all Patroni processes talk to.

ComponentRole

Patroni processWatches local Postgres, holds the DCS leader key, runs the HA loop
Postgres instanceThe actual database; Patroni starts/stops/promotes it
DCS (etcd/Consul/...)Holds cluster state: leader key, members list, dynamic config, history
REST API (port 8008)Health checks, control commands, used by HAProxy/PgBouncer for routing
Watchdog (/dev/watchdog)Optional kernel watchdog; reboots node if Patroni hangs
patronictlOperator CLI for list/edit-config/switchover/failover/restart

The HA loop (every loop_wait, default 10 s)

1. Each Patroni process reads the cluster state from the DCS.
2. The leader Patroni renews its leader key (TTL ttl, default 30 s) and pets the watchdog.
3. Each replica Patroni checks: am I in sync, is my LSN healthy, is the leader's key still valid?
4. If the leader key expires (leader Patroni dies, network partition, hung Postgres), the surviving Patroni processes race to acquire the leader key in the DCS.
5. The winner promotes its local Postgres (pg_promote() or pg_ctl promote), updates DCS, and existing replicas re-point at the new primary via primary_conninfo rewrite + restart-or-reload.

The fundamental safety property: the node that holds the DCS leader key is the primary, and at most one node can hold the key at a time. Split-brain is prevented by the DCS being a strongly consistent distributed log (Raft for etcd/Consul, ZAB for ZooKeeper) — not by Patroni itself.

DCS choice

DCSUse whenNotes

etcd / etcdv3Default for new installs, K8s-nativeSmallest dependency footprint; v3 API recommended (v2 deprecated)
ConsulYou already run Consul for service discoveryPatroni registers cluster members as Consul services automatically
ZooKeeperYou already run ZK (Kafka shop, Hadoop shop)Mature but heavier; use Kazoo client
Kubernetes (kubernetes / k8s)Patroni inside K8s podsUses ConfigMaps or Endpoints as the DCS — no separate cluster needed
Raft (built-in)Lab / small dev clustersPatroni nodes run their own Raft via pysyncobj. Not recommended for production — DCS quorum and PG quorum are coupled

Default recommendation: etcd v3, deployed as its own 3- or 5-node cluster on dedicated VMs (or as a K8s-native etcd if you're on K8s). Use a separate etcd cluster from your Kubernetes control-plane etcd — never share. The Kubernetes DCS mode is the exception: Patroni-on-K8s uses the apiserver and stores state in ConfigMaps, no extra etcd.

DCS sizing: 3 nodes survives 1 failure, 5 nodes survives 2. Even numbers are pointless (no quorum benefit, more votes to gather). One DCS per region; cross-region Patroni clusters require a stretched DCS or multi-cluster topology with tooling like Patroni's standby_cluster mode.

Static (YAML) vs Dynamic (DCS) config

Patroni splits configuration into two stores:

  • Static (per-node patroni.yml): identity, listen addresses, DCS connection, paths, watchdog. Changes require a Patroni restart.
  • Dynamic (DCS-stored, edited via patronictl edit-config): TTLs, replication parameters, Postgres parameters, pg_hba, sync behavior. Changes propagate to all members within loop_wait.

Important: most Postgres parameters belong in the dynamic config, not in the static YAML. Putting shared_buffers in patroni.yml overrides the dynamic value but still works on a per-node basis. Putting it in the dynamic config is the correct default — every node gets the same value.

Dynamic config (DCS, edited with patronictl edit-config)

loop_wait: 10
ttl: 30
retry_timeout: 10
maximum_lag_on_failover: 1048576    # 1 MiB; replicas lagging more cannot win election
master_start_timeout: 300
synchronous_mode: false
synchronous_node_count: 1

postgresql:
  use_pg_rewind: true
  use_slots: true
  parameters:
    wal_level: replica
    hot_standby: "on"
    max_wal_senders: 10
    max_replication_slots: 10
    wal_keep_size: 1GB
    archive_mode: "on"
    archive_command: "pgbackrest --stanza=pg-prod archive-push %p"
    shared_buffers: 8GB
    effective_cache_size: 24GB
  pg_hba:
    - local all postgres peer
    - host replication replicator 10.0.1.0/24 scram-sha-256
    - host all all 10.0.0.0/8 scram-sha-256

The TTL invariant: loop_wait + 2 * retry_timeout <= ttl. With defaults (10 + 20 = 30), this is exactly equal, leaving no slack. Lowering ttl below 30 without lowering loop_wait and retry_timeout first will be rejected. Failover detection takes roughly ttl seconds (the leader key must expire before another node can grab it).

Replication modes

Patroni supports four modes, controlled by synchronous_mode (and synchronous_mode_strict):

Modesynchronous_modeBehaviorFailover safety

Async (default)falseStandbys lag freely; fast writesPossible data loss bounded by maximum_lag_on_failover
SynctruePrimary blocks on commit until at least 1 standby acksNo data loss on planned failover; standalone-fallback if no sync standby
Strict synctrue + synchronous_mode_strict: trueSame, but never fall back to standalonePrimary blocks all writes if no sync standby exists
Quorum syncquorumQuorum-based commit, list of eligible standbys voted on in DCSLower worst-case latency than on, same data-loss safety

Sync modes also respect synchronous_node_count (default 1) — the number of standbys that must ack each commit. With 3 standbys and synchronous_node_count: 2, any 2 of 3 must ack.

The synchronous-blocking caveat (yet again): in synchronous_mode: true with one standby and synchronous_mode_strict: true, losing the standby blocks all writes on the primary until either the standby returns or you flip the strict flag. This is the safety guarantee — but operations teams are routinely surprised by it. Quorum mode reduces but does not eliminate the issue.

Watchdog

Patroni's watchdog uses the kernel softdog module (or hardware watchdog on physical servers). The leader Patroni opens /dev/watchdog and "pets" it on every successful HA-loop iteration. If the Patroni process hangs, crashes, or is paused (kernel scheduler starvation, OOM, debugger), the watchdog timer expires and the kernel hard-reboots the host — guaranteeing the now-stale leader key is gone before another node can promote.

# Enable softdog
modprobe softdog
chown postgres /dev/watchdog
echo "softdog" >> /etc/modules-load.d/softdog.conf


watchdog:
  mode: required        # off | automatic | required
  device: /dev/watchdog
  safety_margin: 5      # seconds reserved between key renewal and watchdog ping

mode: required is the production setting: Patroni refuses to become leader if the watchdog cannot be opened. safety_margin: -1 configures the watchdog to expire after half of ttl, giving the strongest guarantee that the host reboots before the leader key expires elsewhere. Without a watchdog, a stuck primary that does not lose its DCS lease but stops processing queries can cause a brief split-brain window during failover.

patronictl essentials

patronictl -c /etc/patroni/patroni.yml list                    # cluster status
patronictl -c /etc/patroni/patroni.yml topology                # tree view of replication
patronictl -c /etc/patroni/patroni.yml show-config             # current dynamic config
patronictl -c /etc/patroni/patroni.yml edit-config             # edit dynamic config in $EDITOR
patronictl -c /etc/patroni/patroni.yml history                 # past failovers/switchovers
patronictl -c /etc/patroni/patroni.yml switchover --leader pg-node-1 --candidate pg-node-2
patronictl -c /etc/patroni/patroni.yml failover --candidate pg-node-2     # emergency
patronictl -c /etc/patroni/patroni.yml restart pg-prod pg-node-3
patronictl -c /etc/patroni/patroni.yml reinit pg-prod pg-node-3           # rebuild standby
patronictl -c /etc/patroni/patroni.yml pause                              # disable auto-failover
patronictl -c /etc/patroni/patroni.yml resume                             # re-enable
patronictl -c /etc/patroni/patroni.yml query -r replica -- "SELECT now()"

switchover performs a controlled handoff in a healthy cluster (zero data loss, brief blip). failover is the emergency knob — use only when the current primary is gone or sync standbys are unavailable.

REST API

Patroni exposes a REST API on port 8008. Health-check endpoints are unauthenticated (HAProxy/PgBouncer rely on this); control endpoints (/restart, /switchover, /failover, /config) require basic auth.

EndpointReturns 200 when

GET / or GET /primaryThis node is the primary
GET /replicaThis node is a healthy replica
GET /replica?lag=1MBReplica lagging less than 1 MB
GET /syncThis node is a synchronous standby
GET /asyncThis node is an asynchronous standby
GET /read-onlyPrimary or any replica (anything that can serve reads)
GET /healthPostgres is up (any role)
GET /livenessPatroni process is alive
GET /readinessPatroni + Postgres ready to serve

Use these in your load balancer config — never connect-and-query to determine role. HAProxy example:

backend pg_primary
  option httpchk GET /primary
  http-check expect status 200
  default-server inter 3s fall 3 rise 2 on-marked-down shutdown-sessions
  server pg-node-1 10.0.1.10:5432 check port 8008
  server pg-node-2 10.0.1.11:5432 check port 8008
  server pg-node-3 10.0.1.12:5432 check port 8008

backend pg_replicas
  balance roundrobin
  option httpchk GET /replica?lag=10MB
  http-check expect status 200
  default-server inter 3s fall 3 rise 2
  server pg-node-1 10.0.1.10:5432 check port 8008
  server pg-node-2 10.0.1.11:5432 check port 8008
  server pg-node-3 10.0.1.12:5432 check port 8008

The 200 only when role matches design means HAProxy automatically removes the failed-over node from the primary backend and adds it to the replicas backend without any external orchestration. pgBouncer sits in front of HAProxy in many production stacks for connection pooling.

What changed in Patroni 4.x

1. Quorum-based synchronous failover (4.0.0) — synchronous_mode: quorum reduces worst-case commit latency by allowing any quorum of standbys to ack instead of requiring a fixed list. Internally maintains the synchronization state in DCS.
2. primary replaces master everywhere (4.0.0, breaking) — DCS state, REST API parameters, callback script role= argument all changed from master to primary. Update HAProxy option httpchk GET /master to GET /primary before upgrading. Old endpoints still respond, new field names do not accept old values.
3. Configurable retention of member replication slots (4.0.0) — member_slots_ttl (default 30 minutes) controls how long Patroni keeps physical slots for offline replicas before reaping them. Prevents WAL bloat from a permanently-removed node while still allowing brief outages.
4. Citus secondary registration in pg_dist_node (4.0.0) — Patroni now registers Citus secondaries automatically, eliminating manual citus_add_node calls in HA-managed Citus clusters.
5. PostgreSQL 17 + 18 support (4.0.x) — full compatibility tested against PG 18; Patroni reads pg_control_checkpoint() to detect data checksums (PG 18 default-on) and chooses pg_rewind automatically without wal_log_hints=on.
6. patronictl demote-cluster and promote-cluster (4.1.0) — first-class commands for standby_cluster topologies (cross-region DR). Replaces the old config-edit dance.
7. sync_priority tag (4.1.0) — per-member priority for synchronous-standby selection. Higher priority members are preferred when choosing the sync standby; falls back to alphabetical when priorities tie.
8. Receive vs replay LSN/lag in API + ctl (4.1.0) — patronictl list now shows both Lag in MB (replay) and a separate receive lag column, distinguishing network from apply lag.
9. systemd notify-reload and STOPPING=1 (4.1.0/4.1.2) — Patroni runs as a Type=notify-reload systemd unit, integrating with systemctl reload patroni and reporting shutdown progress to systemd.
10. etcd CVE compatibility (4.1.1) — required after etcd 3.6.9 / 3.5.28 / 3.4.42 security fixes; older Patroni releases break against patched etcd.
11. Python 3.14 support (4.1.1) — relevant for distros that ship 3.14 (Fedora 41+, Ubuntu 26.04 path).

Minimum production recipe (3-node cluster on Linux)

# 1. On all 3 PG hosts: install Postgres 18 + Patroni
apt install postgresql-18 postgresql-18-server patroni etcd-client
pip install --upgrade patroni[etcd3,psutil]

# 2. On 3 separate etcd hosts (or use existing K8s-adjacent etcd cluster): set up etcd v3 with TLS
# Out of scope here; use etcd-cluster-operator or static config.

# 3. On all 3 PG hosts: enable softdog + permissions
modprobe softdog && echo softdog > /etc/modules-load.d/softdog.conf
chown postgres /dev/watchdog

# 4. Write /etc/patroni/patroni.yml on each host with unique 'name', 'connect_address',
#    common 'scope: pg-prod', shared etcd hosts, watchdog mode: required.

# 5. Bootstrap the first node only (creates initial cluster + DCS state)
systemctl enable --now patroni    # on pg-node-1 first
patronictl -c /etc/patroni/patroni.yml list
# Expect: pg-node-1 as Leader, running.

# 6. Bring up the other 2 nodes; they will basebackup from the leader
systemctl enable --now patroni    # on pg-node-2, then pg-node-3
patronictl -c /etc/patroni/patroni.yml list
# Expect: 1 Leader + 2 Replicas, all running, lag near 0.

# 7. Edit dynamic config to enable sync replication
patronictl -c /etc/patroni/patroni.yml edit-config
# Set: synchronous_mode: true, synchronous_node_count: 1

# 8. Front with HAProxy on a 4th host (or on each app node) using the httpchk pattern above.

# 9. Verify failover: stop the leader's Patroni, watch a replica promote within ~30s.
systemctl stop patroni    # on the leader
patronictl -c /etc/patroni/patroni.yml list    # from another host

Gotchas

1. Never systemctl restart postgresql directly. Patroni owns the Postgres process — bypassing Patroni causes it to lose track and may trigger unnecessary failover. Use patronictl restart or systemctl restart patroni.
2. Never edit postgresql.conf directly. Patroni overwrites it on every reload. Put parameters in patroni.yml (per-node) or dynamic config (cluster-wide). Same applies to pg_hba.conf and recovery.conf (PG 12+ no longer uses recovery.conf, but the principle holds for standby.signal and postgresql.auto.conf).
3. Do not run Patroni without a watchdog in production. A stuck Patroni can cause a brief split-brain window during failover; watchdog reboots the host before the new leader promotes.
4. DCS quorum loss is more dangerous than PG quorum loss. If etcd loses quorum, Patroni demotes the primary to read-only after ttl expires (no leader key can be renewed). Always run DCS as 3 or 5 nodes on separate failure domains.
5. maximum_lag_on_failover is in bytes, not seconds. Default unset means any lag is acceptable. Set it (e.g., 1 MiB) to prevent a wildly-behind replica from winning election in async mode.
6. use_pg_rewind: true requires the rewind user. Configure authentication.rewind in patroni.yml and grant pg_rewind privileges to that role. Otherwise Patroni falls back to a full basebackup on every former-primary rejoin — minutes-to-hours instead of seconds.
7. use_slots: true (default) creates physical slots per replica. A permanently-disconnected replica's slot will retain WAL forever. The default member_slots_ttl: 30min (4.0+) reaps abandoned slots after 30 minutes of absence — but disable use_slots entirely for short-lived ephemeral replicas (CI sandboxes).
8. switchover requires a target candidate explicitly. Without --candidate, Patroni picks the most-up-to-date eligible standby; passing --candidate overrides. failover is non-graceful — use only when the primary is unreachable.
9. The pause / resume toggle is global. Once paused, Patroni will not auto-failover even if the leader dies. Always resume after maintenance — set a reminder. patronictl list shows Maintenance Mode when paused.
10. The tags.nofailover: true tag prevents leader candidacy. Use it on read-replicas (analytics box, BI host) to keep them out of the primary rotation. The opposite mistake — forgetting to set it — causes a surprise promotion of a smaller hardware tier.
11. Patroni reads bin_dir to find Postgres binaries. On Debian/Ubuntu, this is /usr/lib/postgresql/<version>/bin. Mismatched bin_dir and data_dir (e.g., upgrading PG 17 to 18 without updating both) causes start failure with cryptic errors.
12. The REST API is HTTP by default. Use TLS (certfile, keyfile) for production — the API exposes cluster control endpoints. Restrict by network ACL even with auth.
13. master_start_timeout (300s default) is per-startup-attempt. If Postgres takes longer than 5 minutes to start (giant shared_buffers warmup, slow disks, large data dir), Patroni will give up and demote. Increase for very large clusters.
14. Patroni does not back up your database. It orchestrates HA; pair it with pgBackRest or WAL-G for PITR. The archive_command in dynamic config feeds the backup tool.
15. Bootstrap config (bootstrap.dcs block) only applies on first cluster init. Editing it later does nothing. Use patronictl edit-config for ongoing changes.
16. Read-replica lag-based load balancing is approximate. Patroni's GET /replica?lag=10MB checks the cached LSN diff at the previous loop iteration — up to loop_wait stale. Apps with strict freshness requirements should re-check via pg_last_wal_replay_lsn().
17. Quorum sync mode requires PG 10+ and at least 3 nodes for actual benefit. With 2 nodes, quorum mode is identical to synchronous_mode: on. The latency win shows up at 3+ standbys.
18. use_pg_rewind was conditional in PG <18; default-on in PG 18. PG 18's default-on data checksums make pg_rewind work without wal_log_hints=on. On PG <18, you must set wal_log_hints=on (or initdb with checksums) for rewind to work — otherwise rewind fails and Patroni falls back to basebackup.
19. Do not skip the etcd upgrade path during PG-distribution upgrades. Patroni 4.1.1+ requires etcd ≥ 3.6.9 / 3.5.28 / 3.4.42 (CVE patches). Upgrading Patroni without upgrading etcd causes silent connection failures.
20. The kubernetes DCS uses ConfigMaps + Endpoints by default; switch to kubernetes_use_endpoints: false only if you have RBAC reasons. Endpoints are denser (one Endpoints object per cluster) and reduce apiserver load vs ConfigMaps. Most K8s operators (Stackgres, CrunchyData PGO, Zalando postgres-operator) use Endpoints.

Patroni vs alternatives

ToolArchitectureDCS dependencyWhen to pick

PatroniSidecar Python daemon per PG nodeYes (etcd/Consul/ZK/K8s)Default for new K8s + non-K8s PG HA; widest ecosystem
repmgrCLI + daemon, manages replication topologyNo (uses PG itself)Smaller clusters, simpler model, no DCS to operate; fewer auto-recovery features
