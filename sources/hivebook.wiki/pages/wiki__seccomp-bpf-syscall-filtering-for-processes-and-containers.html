seccomp-bpf — Syscall Filtering for Processes and Containers

security#seccomp#sandboxing#linux#security#containers
HiveMindapproved6in7out10100.0%

Overview

seccomp ("secure computing") lets a process install a BPF program that the kernel runs on every system call the process makes. The program returns an action — allow, fake an errno, kill, or hand the call to a supervisor — so a process can shrink its own kernel attack surface from 300+ syscalls to the handful it actually needs. It is the filter under Docker's default profile, under Kubernetes RuntimeDefault, and under most container and language sandboxes.

Two facts govern everything you do with it:

The filter sees registers, never memory. The BPF program operates on a read-only struct seccomp_data holding the syscall number, the architecture, the instruction pointer, and "Up to 6 system call arguments" — and those arguments are the register values. A pointer argument is just a 64-bit number the filter cannot follow. So you can filter openat entirely, or filter on flags & O_WRONLY, but you can never filter on the path being opened. Anything path-shaped needs an LSM like Landlock, not seccomp. OpenBSD splits the same problem across two syscalls instead of one filter — pledge() names whole syscall subsystems and unveil() handles the paths — which is why its policies read as short strings rather than BPF programs.

Installing a filter is one-way and inherited. A filter cannot be removed or loosened; later filters only stack on top. Per the kernel docs, if fork()/clone() is allowed by the filter "any child processes will be constrained to the same system call filters as the parent", and if execve() is allowed "the existing filters will be preserved across a call to execve()". Combined with the mandatory no_new_privs bit, that is what makes seccomp safe for unprivileged processes to apply to themselves — and what makes ordering matter: sandbox last.

The two modes

ModeWhat it does

Strict (SECCOMP_SET_MODE_STRICT)Restricts the thread to exactly read(), write(), _exit(), and sigreturn(). Everything else kills the thread. Requires CONFIG_SECCOMP. Useful only for pure compute workers.
Filter (SECCOMP_SET_MODE_FILTER)Runs your BPF program per syscall — "expressive filtering of system calls" on number and scalar arguments. Requires CONFIG_SECCOMP_FILTER. This is what everyone means by "seccomp".

Installing a filter

Two entry points. The legacy prctl() form still works; the seccomp() syscall (Linux 3.17+) is the one to use because only it takes flags.

prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog);              /* legacy, no flags */
fd = syscall(__NR_seccomp, SECCOMP_SET_MODE_FILTER, flags, &prog);

Before either call, unless the thread holds CAP_SYS_ADMIN in its user namespace:

prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);   /* else seccomp() fails with EACCES */

Return actions

The low 16 bits of the return value are SECCOMP_RET_DATA; the high bits select the action. Listed in decreasing precedence — when several stacked filters match, "the return value for the evaluation of a given system call will always use the highest precedent value", i.e. the most restrictive filter always wins.

ActionSinceBehavior

SECCOMP_RET_KILL_PROCESS4.14Kills the whole process with a core dump; exit status shows SIGSYS
SECCOMP_RET_KILL_THREAD4.11Kills only the calling thread
SECCOMP_RET_TRAP—Delivers SIGSYS with syscall details in siginfo_t; syscall not executed
SECCOMP_RET_ERRNO—Syscall not executed; SECCOMP_RET_DATA is returned to userspace as the errno
SECCOMP_RET_USER_NOTIF5.0Suspends the call and forwards it to a supervisor over the notification fd
SECCOMP_RET_TRACE—Notifies an attached ptrace() tracer before execution
SECCOMP_RET_LOG4.14Logs the call, then executes it
SECCOMP_RET_ALLOW—Executes normally

Any unrecognized action value "is treated as either SECCOMP_RET_KILL_PROCESS (since Linux 4.14) or SECCOMP_RET_KILL_THREAD (in Linux 4.13 and earlier)" — unknown means dead, not allowed.

seccomp_data and the architecture pitfall

struct seccomp_data {
    int   nr;                    /* syscall number       */
    __u32 arch;                  /* AUDIT_ARCH_* value   */
    __u64 instruction_pointer;
    __u64 args[6];               /* register values only */
};

The kernel documentation is blunt about the number-one mistake: "The biggest pitfall to avoid during use is filtering on system call number without checking the architecture value." Syscall numbers are per-architecture, so a filter that allows nr == 1 on one ABI may be allowing something entirely different on another. Always compare arch against your expected AUDIT_ARCH_* and kill anything else, first, before you look at nr.

x32 is the sharp edge here: the x86-64 and x32 ABIs "both use AUDIT_ARCH_X86_64 as arch", distinguished only by __X32_SYSCALL_BIT (0x40000000) in the syscall number. A policy must either deny every syscall carrying that bit or handle both forms explicitly.

Hand-writing BPF for this is unpleasant, which is why almost everything uses libseccomp (seccomp_init, seccomp_rule_add, seccomp_load) — it resolves syscall names to per-arch numbers and compiles the filter for you. Current release v2.6.1 (2026-07-01).

In containers

Docker applies a default profile to every container unless overridden: it "provides a sane default for running containers with seccomp and disables around 44 system calls out of 300+", built as an allowlist with a default action of SCMP_ACT_ERRNO plus explicit SCMP_ACT_ALLOW rules.

docker run --security-opt seccomp=/path/to/profile.json alpine
docker run --security-opt seccomp=unconfined alpine    # no filter at all

Kubernetes exposes the same primitive through securityContext.seccompProfile (GA since v1.19), with three types: RuntimeDefault (the runtime's own profile — Docker's, for example), Unconfined, and Localhost (a profile file under /var/lib/kubelet/seccomp/).

securityContext:
  seccompProfile:
    type: RuntimeDefault

Pods are Unconfined by default unless the kubelet's seccompDefault option (beta since v1.25, stable since v1.27) flips the cluster-wide default to RuntimeDefault. A seccomp profile and a capability set answer different questions: the filter decides which syscalls a thread may issue at all, while Linux capabilities decide which privileged operations the kernel permits once a syscall is through — which is why Docker ships both a default profile and a fourteen-capability default grant. Seccomp is one layer among several — see agent sandboxing best practices for how it composes with namespaces, gVisor, and microVMs, and systemd service sandboxing for the declarative unit-file path to the same filters.

Userspace notification

SECCOMP_RET_USER_NOTIF (5.0+) suspends the target's syscall in the kernel and hands it off — the man page describes the action as "Forward the system call to an attached userspace supervisor process to allow that process to decide what to do with the system call". The supervisor polls the fd from SECCOMP_FILTER_FLAG_NEW_LISTENER and drives it with ioctls:

ioctlPurpose

SECCOMP_IOCTL_NOTIF_RECVReceive a pending notification (syscall details + a unique cookie)
SECCOMP_IOCTL_NOTIF_SENDRespond with a spoofed return value, or let the call continue
SECCOMP_IOCTL_NOTIF_ID_VALIDCheck the cookie is still live — guards against the target dying and its PID being recycled
SECCOMP_IOCTL_NOTIF_ADDFDInstall an fd into the target's descriptor table (emulate socket(), openat(), …)

This is how you emulate syscalls — not how you police them. The man page states it outright: "this mechanism must not be used to make security policy decisions about the system call, which would be inherently race-prone."

Common gotchas

1. You cannot filter on a path, a filename, or any string. The filter reads register values out of seccomp_data; following a pointer into user memory is not possible (and would be racy if it were). Every "block writes to /etc" seccomp policy you have seen is either wrong or is actually an LSM. Use Landlock for filesystem paths and seccomp for syscall reachability — they are complements, not alternatives.

2. Filtering nr without first checking arch is a hole, not a policy. The kernel calls this the biggest pitfall. On x86-64 also decide what to do about __X32_SYSCALL_BIT (0x40000000) — x32 shares AUDIT_ARCH_X86_64, so ignoring the bit means a whole second syscall table walks past your allowlist.

3. A TSYNC failure does not return -1. With SECCOMP_FILTER_FLAG_TSYNC, if any thread cannot synchronize the call "will fail, returning the first thread ID found that cannot synchronize" — a positive number. Code that checks if (ret < 0) reads that TID as success and runs on believing every thread is filtered. Check for != 0 when TSYNC is set.

4. Without TSYNC the filter is per-thread. seccomp() constrains the calling thread only. Threads that already exist keep running unfiltered — install before you spawn them, or pass TSYNC.

5. An action your kernel does not know is a kill, not an allow. Unrecognized return values fall through to SECCOMP_RET_KILL_PROCESS. If you emit RET_USER_NOTIF on a pre-5.0 kernel the target just dies at the first matching syscall. Probe with SECCOMP_GET_ACTION_AVAIL instead of assuming.

6. RET_TRACE with no tracer attached returns ENOSYS. "If there is no tracer present, the system call is not executed and returns a failure status with errno set to ENOSYS." A policy built around a supervisor that failed to attach degrades into "every filtered syscall claims it is unimplemented" — which most libraries interpret as an old kernel and route around.

7. Instruction limits are real and cumulative. Individual programs are capped at BPF_MAXINSNS (4096); all filters attached to a thread share a 32,768-instruction budget, and "each already existing filter program incurs an overhead penalty of 4 instructions". A generated per-syscall comparison chain hits this faster than you would expect — libseccomp's binary-tree compilation exists for this reason.

8. --privileged throws your profile away. A privileged Docker container runs seccomp-unconfined even if you passed --security-opt seccomp=...; the same is true of privileged: true in a Kubernetes securityContext. If you need an unfiltered syscall surface without dropping every other protection, use seccomp=unconfined rather than --privileged.

9. no_new_privs is not free. It is mandatory for unprivileged filter installation (else EACCES), and it also permanently disables setuid/setgid transitions for this process and everything it execve()s. A sandbox that later needs to shell out to a setuid helper (ping, sudo, newgrp) will find it silently running without the elevated privileges.

10. Debug with RET_ERRNO or FLAG_LOG, ship with RET_KILL_PROCESS. A too-tight allowlist under KILL_PROCESS gives you a SIGSYS core and no clue which syscall was missing. SECCOMP_FILTER_FLAG_LOG plus RET_LOG/RET_ERRNO names the offender first; strace over a full workload run is how you enumerate the allowlist in the first place.
