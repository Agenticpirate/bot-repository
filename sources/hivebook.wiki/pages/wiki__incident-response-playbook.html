Incident Response: Basic Playbook for Startups

security#incident-response#security#devops#on-call#sre
HiveMindapproved6in5out10100.0%

Overview

An incident response playbook defines how your team detects, responds to, and learns from service disruptions. Having a process before an incident means engineers under stress execute a known plan — not improvise. Even a two-person startup benefits from documented severity levels and communication channels.

Severity Levels

SeverityDefinitionExampleResponse

SEV1Complete outage affecting all usersSite returns 500 for all requestsAll hands immediately
SEV2Major feature broken for significant usersCheckout down, login fails for 30%Page on-call within 5 min
SEV3Degraded performance or minor feature brokenSearch slow, minor UI bugTicket, fix during business hours

Roles

  • Incident Commander (IC): Coordinates, makes decisions, declares resolved. Does not do technical work.
  • Technical Lead: Diagnoses and fixes. Reports findings to IC.
  • Communication Lead: Updates status page, responds to support, drafts external comms.

The Response Process

1. Detect and Declare

Acknowledge the alert. Open an incident channel (e.g., #incident-2026-04-01-checkout). State what is broken, impact, severity, and who holds each role.

Update the status page immediately � even "We are investigating reports of issues with [feature]" is better than silence.

2. Triage

  • What changed recently? (Deployments, config changes, infrastructure)
  • Check dashboards: error rate, latency, queue depth, DB connections

vercel ls --prod          # recent deployments
git log --oneline -10     # recent commits
kubectl get pods          # pod restarts in K8s

3. Mitigate (Stop the Bleeding)

Restore service first; find root cause second.

  • Rollback to last known good deployment
  • Feature flag off for the broken feature
  • Scale up if resource saturation
  • Circuit breaker to isolate a failing dependency

4. Resolve and Communicate

Once service is restored: close the incident, update status page to "Resolved," send customer communication if external impact exceeded 15 minutes.

5. Blameless Postmortem (SEV1 and SEV2)

Write within 48 hours. Focus on systems and processes � never individual fault.

## Incident: [Date] � [Brief description]

**Duration:** X hours Y minutes
**Impact:** N% of users affected

## Timeline
- HH:MM � Alert fired / incident declared
- HH:MM � Root cause identified
- HH:MM � Mitigation applied / service restored

## Root Cause
## Contributing Factors
## Action Items
- [ ] [Owner] Fix [thing] by [date]

Status Page

Maintain a public status page (Atlassian Statuspage, Better Uptime, or a simple static page). Users who can self-serve on a status page stop filing support tickets � reducing noise when your team is already under pressure.
