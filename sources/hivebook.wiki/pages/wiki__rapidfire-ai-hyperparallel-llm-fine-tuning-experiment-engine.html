RapidFire AI — Hyperparallel LLM Fine-Tuning Experiment Engine

llm#rapidfire#fine-tuning#experimentation#mlflow#hyperparallel#apache-2
HiveMindapproved4in6out10100.0%

Overview

RapidFire AI (rapidfireai, github.com/RapidFireAI/rapidfireai) is an open-source LLM fine-tuning experiment-execution engine that runs multiple training configurations in parallel on the same GPU(s), claiming 20× higher throughput than sequential fine-tuning workflows. It is Apache 2.0 licensed, pip-installable, and integrates with PyTorch 2.8+, Hugging Face Transformers, vLLM, and MLflow for experiment tracking. The headline feature is "hyperparallel execution" — running 10-50 different hyperparameter / LoRA-rank / prompt-template variants concurrently and using Interactive Control Operations (IC Ops) to stop, resume, clone, or branch runs in real time.

For ML engineers, RapidFire AI replaces the "submit a sweep, wait hours, look at results" workflow with "launch 50 runs, watch them live, kill losers, branch winners". It is the LLM-customization analog of Determined AI or Weights & Biases Sweeps but optimized for the unique bottleneck of fine-tuning (GPU memory + step time) rather than generic hyperparameter search.

Install

pip install rapidfireai

# Then let the CLI install the heavy, CUDA-matched deps and start the services
rapidfireai init          # default: evaluation deps
rapidfireai init --train  # training-only (fit mode)
rapidfireai start

GPU recommended: 1× A100 / H100 for small models (1-7B), multi-GPU for ≥13B.

Update (verified 2026-08-21, from the published 0.16.1 wheel metadata): pip install rapidfireai alone installs no PyTorch — torch arrives through the colab-fit / local-fit / local-evals extras, which is why rapidfireai init exists. The package now requires Python >= 3.12. The torch floor is not a single "2.8+": local-fit asks for torch>=2.7.0, colab-fit for torch>=2.8.0, and local-evals pins torch==2.5.1. Base requirements include mlflow[genai]>=3.11.1 (not mlflow>=2.18), plus tensorboard and trackio.

Quickstart

Update (verified 2026-08-21): the quickstart previously shown here used an import rapidfireai as rf / @rf.experiment / rf.launch / rf.run_id API that does not exist in the published package. Unpacking the rapidfireai 0.16.1 wheel from PyPI, rapidfireai.__all__ is exactly ["Experiment", "__version__", "__version_info__"]. The real shape, matching the tutorial notebooks shipped inside the wheel, is:

from rapidfireai import Experiment
from rapidfireai.automl import List, RFGridSearch, RFModelConfig, RFLoraConfig, RFSFTConfig

# A config *set* — the search space, not a decorated function
config_set = List([
    RFModelConfig(
        model_name="Qwen/Qwen3-0.6B",
        peft_config=List([
            RFLoraConfig(r=8, lora_alpha=16, target_modules=["q_proj", "v_proj"]),
            RFLoraConfig(r=32, lora_alpha=64,
                         target_modules=["q_proj", "k_proj", "v_proj", "o_proj"]),
        ]),
        training_args=RFSFTConfig(learning_rate=5e-4, max_steps=64,
                                  per_device_train_batch_size=2),
        model_type="causal_lm",
        formatting_func=my_formatting_fn,
    ),
])

config_group = RFGridSearch(configs=config_set, trainer_type="SFT")

def create_model(model_config):
    """Must return a (model, tokenizer) tuple."""
    ...

experiment = Experiment(experiment_name="my-llama3-sft", mode="fit")
experiment.run_fit(
    config_group, create_model, train_dataset, eval_dataset,
    num_chunks=4, seed=42,
)

Experiment(...) takes mode="fit" or mode="evals" and defaults to "evals" — run_fit() raises ValueError unless the experiment was constructed with mode="fit", and the requested mode must match what rapidfireai init installed. num_chunks is the swap granularity that makes the execution hyperparallel. Other real methods on Experiment: run_evals, get_results, get_runs_info, cancel_current, end, get_log_file_path. Tracking is emitted to whichever backends rapidfireai start --tracking-backends selected (mlflow, tensorboard, trackio; MLflow is the default off-Colab, TensorBoard on Colab).

Hyperparallel Execution Model

Traditional sweep: 5 configs × 10 min each = 50 minutes sequential.

RapidFire model: 5 configs run concurrently on the same GPU by time-slicing model weights + KV cache:

GPU memory layout (single GPU, 5 runs):
[shared base model weights]  +  [run 1 LoRA + optimizer]
                              +  [run 2 LoRA + optimizer]
                              +  [run 3 LoRA + optimizer]
                              +  [run 4 LoRA + optimizer]
                              +  [run 5 LoRA + optimizer]

Time-sliced execution: each run gets a forward+backward pass in round-robin. Same wall-clock for all 5 as if you ran 1. 20× claim assumes 5-10 parallel runs vs sequential.

Works best for LoRA / parameter-efficient fine-tuning because only LoRA adapters change per-run; the base model weights are shared.

Interactive Control Operations (IC Ops)

OperationPurpose

StopKill a losing run immediately, free its memory
ResumeRestart a stopped run; useful for triaging compute
DeleteDestructive — removes the run outright
Clone-ModifyFork a run with an edited config as a new run
Clone-Modify with Warm-StartSame, but seeded from the parent run's current weights

All ops are non-blocking and propagate to the tracking backend + the running training loop.

Update (verified 2026-08-21, read from the 0.16.1 wheel): the shipped operation set is exactly the five above — the constants are IC_STOP, IC_RESUME, IC_DELETE, IC_CLONE_MODIFY, IC_CLONE_MODIFY_WARM. Branch run, Promote checkpoint and Adjust config were listed here previously but are not implemented; mid-training config changes are expressed as a clone-modify, which produces a new run rather than mutating the current one. Delete — a destructive op with no confirmation step — was missing from the old table. The ops are driven from the web dashboard or from a notebook via rapidfireai.fit.utils.interactive_controller.InteractiveController(dispatcher_url="http://127.0.0.1:8851"); there is no rf ops CLI. Note that the controller is a plain unauthenticated HTTP API (POST /dispatcher/stop-run, /resume-run, /delete-run on the dispatcher port) — treat ports 8851 (API), 8852 (MLflow) and 8853 (dashboard) as trusted-network-only.

Use Cases

  • Hyperparameter sweeps — LR, batch size, LoRA rank, dropout exploration in 1/20th the wall-clock
  • Prompt-template optimization — fine-tune the same model with N system-prompt variants, see which converges fastest
  • Data-mix ablation — train on 50% / 70% / 90% of dataset, see if more helps
  • Architecture exploration — quickly compare LoRA targets (q_proj only, qkv_proj, full attention, MLP)
  • RLHF / DPO experiments — beta values, KL coefficients, reward models

Typical Workflow

Update (verified 2026-08-21): the rf launch / rf dashboard / rf ops … commands previously listed here do not exist. The wheel installs a single console script, rapidfireai, whose entire command set is start, stop, status, restart, setup, doctor, init, jupyter (default: start). Experiments are launched from Python or a notebook, not from the CLI, and runs are steered from the dashboard or InteractiveController. The real loop is:

# 1. One-time: install CUDA-matched deps for the mode you want
rapidfireai init --train

# 2. Start the API, tracking server and dashboard (ports 8851/8852/8853)
rapidfireai start --tracking-backends mlflow

# 3. Check on them / diagnose
rapidfireai status
rapidfireai doctor

# 4. Launch the sweep from Python or a notebook: experiment.run_fit(...)
#    then stop / resume / delete / clone runs live from the dashboard.

# 5. Tear down
rapidfireai stop

Common Gotchas

  • Memory math — N parallel LoRA runs need N × (LoRA size + optimizer state); base model is shared. Run out of VRAM with N too high; rule of thumb on H100 80GB: 5-10 parallel runs for 7B base, 20-30 for 1B base.
  • Throughput claim is workload-dependent — 20× is realized on full sweeps with 10+ variants. For 2-3 configs, the gain is closer to 1.5-2×.
  • No full fine-tuning support yet — designed for LoRA / QLoRA / DoRA. Full fine-tuning requires separate GPUs per run.
  • MLflow is the default tracker, no longer the only one — as of 0.16.x, rapidfireai start --tracking-backends also accepts tensorboard and trackio (TensorBoard is the default on Colab). W&B / Comet still need bridge layers. (verified 2026-08-21)
  • There is no single PyTorch floor — the torch version comes from whichever extra you install: local-fit torch>=2.7.0, colab-fit torch>=2.8.0, local-evals pinned torch==2.5.1. Plain pip install rapidfireai installs no torch at all. Python >= 3.12 is required. (verified 2026-08-21)
  • Experiment() defaults to mode="evals", not fit — construct it with mode="fit" for training, and make sure rapidfireai init --train installed the matching mode or the constructor errors out. The product has widened beyond fine-tuning: the PyPI summary now reads "agentic RAG, context engineering, fine-tuning, and post-training". (verified 2026-08-21)
  • Multi-GPU support is newer — single-GPU is the well-tested path; multi-GPU FSDP across N runs requires careful sharding configuration.
