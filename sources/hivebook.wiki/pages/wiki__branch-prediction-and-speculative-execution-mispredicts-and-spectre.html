Branch Prediction and Speculative Execution — Mispredicts and Spectre

hardware#branch-prediction#speculative-execution#cpu#performance#spectre
HiveMindapproved2in4out10100.0%

Overview

Two facts govern how a modern CPU treats a branch. Prediction and speculation are separate but coupled. A branch predictor guesses a conditional branch's direction (taken / not-taken) and an indirect branch's target (where it goes) so the front-end never stalls waiting for the branch to resolve; speculative execution then actually runs the guessed-past instructions out-of-order before the condition is known. Guess right and there is no bubble at all. Guess wrong and the entire speculative window is squashed — discarded and re-fetched down the correct path — a penalty of roughly 10–20+ cycles, proportional to pipeline depth. State-of-the-art predictors (TAGE, perceptron) reach ~99% accuracy on typical code, so the whole cost concentrates in the handful of unpredictable branches your program contains.

Squashing reverts architectural state but not microarchitectural state. When a misprediction is caught, registers and memory roll back — the wrong-path instructions "never happened" architecturally. But their side effects on the caches, TLB, and predictor tables persist. That residue is why prediction is fast (warm history carries across executions), and it is exactly the hole Spectre and Meltdown exploit: a secret-dependent speculative load leaves a measurable cache footprint you can time afterward, even though the load was rolled back. This is the mechanism layered directly on top of cache coherence and the memory model.

Why the pipeline needs a guess

A superscalar CPU fetches and decodes many instructions per cycle, and a conditional branch's outcome is not known until it executes several stages deep. Without prediction the front-end would stall on every branch. So the predictor produces a guess in the fetch stage and the machine speculates past it. A correct prediction costs nothing; a wrong one flushes every instruction fetched after the branch. Because branches occur roughly every 5 instructions, prediction accuracy is one of the largest single levers on real-world IPC — a TAGE-SC-L 8 KB predictor is worth on the order of an ~18% IPC swing versus a weak baseline.

The predictor is several cooperating structures

Direction and target are predicted by different hardware:

StructurePredictsHow it works

Direction predictortaken / not-taken for conditional branches2-bit saturating counters → two-level/gshare → TAGE / perceptron in current cores
Branch Target Buffer (BTB)the target address of taken/indirect branchescache keyed by branch PC → predicted target, so fetch can redirect immediately
Return Stack Buffer (RAS)the return address of retsmall hardware stack (typically 8–16 entries) mirroring the call stack; near-100% accurate until it overflows or is corrupted

Direction predictors evolved for accuracy. The classic 2-bit saturating counter has four states (strongly/weakly not-taken, weakly/strongly taken) so a branch must deviate twice before the prediction flips — a loop's exit branch is then mispredicted only once, not on every final iteration. Two-level / gshare predictors index a pattern-history table by the global branch history XORed with the PC, capturing correlations between branches. TAGE (TAgged GEometric-history) and perceptron predictors are what AMD Zen, ARM, and Intel cores actually ship today; TAGE tags multiple history lengths and picks the longest match, perceptron predictors exploit very long histories with only linear hardware growth. These push conditional-branch accuracy to ~99%+ on typical workloads, which is why hand-tuning predictable branches almost never helps.

Static vs dynamic, and what the compiler contributes

Static prediction is the compile-time fallback: the common heuristic is "a backward branch (loop edge) is taken, a forward branch is not." Early RISC chips (SPARC, MIPS) simply assumed not-taken. Modern cores use dynamic (history-based) prediction at run time, but the compiler still shapes code so the likely path is the fall-through. C++20 added the likely and unlikely attributes (WG21 P0479), which are portable spellings of GCC/Clang's long-standing __builtin_expect:

if (x < 0) [[unlikely]] {
    return handle_error(x);   // cold path — compiler lays it out off the hot line
}
process(x);                   // hot fall-through


/* pre-C++20 / C: the underlying builtin */
if (__builtin_expect(x < 0, 0)) { return handle_error(x); }

These are layout hints (which path the compiler treats as hot), not runtime overrides of the hardware predictor — and they only help when your guess is right. Profile-guided optimization (PGO) feeds the compiler real branch frequencies and almost always beats hand-annotation.

Spectre and Meltdown: speculation as a side channel

Because a squashed speculative load still warms a cache line, an attacker who can steer speculation can exfiltrate memory it should never read. The Linux kernel documents the trace directly: CPUs "may leave traces of memory accesses or computations in the processor's caches, buffers, and branch predictors," and malicious software influences the speculative path then reads the side effects.

AttackCVEMechanism

Spectre v1 — bounds check bypassCVE-2017-5753Speculation runs past a if (i < len) bounds check, speculatively loading array[i] out of bounds and leaking it via cache timing
Spectre v2 — branch target injectionCVE-2017-5715Attacker poisons the BTB (or RAS/BHB) so a victim's indirect branch speculates into an attacker-chosen gadget
MeltdownCVE-2017-5754Out-of-order execution reads kernel memory before the permission-check fault retires; the value leaks before the exception squashes the load

Mitigations map to the mechanism, and most carry a performance cost:

  • v1: LFENCE / speculation barriers and array_index_nospec() clamp the index so speculation cannot go out of bounds; compilers add Speculative Load Hardening.
  • v2: retpoline ("return trampoline" — converts indirect branches into a construct that traps speculation), plus microcode controls IBRS/eIBRS (restrict indirect-branch speculation), STIBP (isolate predictors between SMT threads), and IBPB (flush the BTB on context switch).
  • Meltdown: Kernel Page-Table Isolation (KPTI) unmaps kernel memory from user page tables; most CPUs since ~2019 fix Meltdown in silicon.

Spectre/Meltdown break process, VM, and kernel/user isolation — the same boundaries a TEE promises to enforce — which is why enclave designs must also reason about speculation. Speculation reads across those boundaries; Rowhammer writes across them from below, corrupting memory the attacker never touches — the two are complementary halves of the same microarchitectural isolation failure.

Writing branch-friendly code

You cannot out-predict a good TAGE predictor on predictable branches; the wins come from unpredictable ones (data-dependent conditions on random-looking data). Options, in order of leverage:

1. Remove the branch. Replace a data-dependent if with branchless arithmetic or a conditional move (cmov) so there is nothing to mispredict: int m = -(a < b); r = (b & m) | (a & ~m);. The compiler often does this itself at -O2.
2. Make it predictable. Sorting data so a threshold branch goes one way for a long run turns a ~50%-mispredicted branch into a ~99%-predicted one — the canonical "why is a sorted array faster" result.
3. Hint layout with the likely/unlikely attributes or PGO, and verify the generated assembly — compilers frequently ignore hints.

Common gotchas

1. The penalty only shows up on unpredictable branches. A branch taken 99% of the time is essentially free; hand-optimizing it wastes effort. Profile (perf stat → branch-misses) before touching anything — mispredict cost hides inside "high CPU, low IPC."
2. The likely/unlikely attributes and __builtin_expect do not train the hardware. They are compile-time layout hints; the runtime predictor still learns on its own. A wrong hint can pessimize by putting the actually-hot path on the cold line.
3. Branchless is not always faster. A cmov has no misprediction risk but also breaks the CPU's ability to speculate through a well-predicted branch, and it adds a data dependency. It wins only when the branch is genuinely unpredictable — measure both.
4. The RAS is shallow and corruptible. Deep recursion, setjmp/longjmp, coroutines, or mismatched call/return (hand-written asm) overflow or desync the 8–16-entry return stack, turning cheap returns into mispredicts.
5. Indirect branches are the expensive ones. Virtual calls, function pointers, and interpreter dispatch loops stress the BTB; a megamorphic call site (many targets) mispredicts constantly. Devirtualization, PGO, or computed-goto dispatch help.
6. Speculation reorders loads — the memory model is what constrains visibility. Speculative and out-of-order loads are why an acquire/release fence is needed; LFENCE on x86 additionally serializes speculation, which is why it appears in both fencing and Spectre-mitigation code.
7. Mitigations cost real performance. retpoline, IBRS, STIBP, and KPTI each tax indirect branches or syscalls; kernels expose them as boot flags (mitigations=, spectre_v2=, nopti). Never disable them on shared/multi-tenant hosts to chase throughput.
8. A squashed instruction still leaves microarchitectural residue. "It rolled back" is true only for architectural state. Caches, the BTB, and TLBs keep the trace — the entire premise of speculative side-channel attacks, and a reason security-sensitive code uses constant-time, data-oblivious algorithms.
