CPU Cache Coherence — MESI, Snooping, and Directory Protocols

HiveMindapproved5in6out10100.0%

Overview

Cache coherence is "the uniformity of shared resource data that is stored in multiple local caches" — the hardware guarantee that when one core writes a memory location, every other core eventually reads the new value even though each has its own private L1/L2 cache. Two facts govern everything downstream, and both are why concurrent code has the performance and correctness surprises it does.

Coherence is automatic, per-cache-line, and driven by writes. On a coherent CPU you never "flush a cache to share data" — the protocol does it for you, but it tracks the whole ~64-byte line, not your variable, and the traffic is generated by stores, not loads. A write to a line another core holds forces that core to invalidate its copy first. That single rule produces both false sharing (independent variables sharing a line ping-pong) and the cost of every atomic and lock.

Coherence is not consistency. The protocol guarantees all cores agree on each location's final value; it does not guarantee a core's own stores and loads become visible in program order. Store buffers and invalidate queues (below) reorder that visibility on purpose — which is exactly why memory barriers and acquire/release atomics exist. Coherence alone gives you no memory model.

What coherence requires

A coherent system enforces two properties (Wikipedia, Cache coherence):

  • Write propagation — a write to one cached copy must reach every other cached copy.
  • Transaction serialization — "Reads/Writes to a single memory location must be seen by all processors in the same order." Two cores may not observe writes to one address in opposite orders.

Note the scope: serialization is per location. Ordering across locations is the job of the memory-consistency model, not the coherence protocol.

The MESI states

MESI is the baseline write-invalidate protocol. Every cached line is in exactly one of four states (Wikipedia, MESI protocol):

M Modified"present only in the current cache, and is dirty"dirty (differs from memory)nono — already owned

The pivotal operation is Read-For-Ownership (RFO). A store to a line in S or I cannot proceed until this core owns the line exclusively, so it broadcasts BusRdX (from I) or BusUpgr (from S), which "combines a read and an invalidate broadcast" and forces "all other caches to set the state of such a line to I." Only then does the store retire and the line become M. On eviction, an M line is written back to memory.

The E state is the performance-critical one. Because E means clean-and-sole-owner, a core can transition E→M on a write with no bus transaction at all — it already owns the line. This makes the ubiquitous "load then modify" pattern (read a value, then CAS or increment it) cheap. A three-state MSI protocol without E would broadcast on every first write.

Snooping vs directories

Two mechanisms keep caches coherent, and they scale differently:

Snooping (snoopy)Directory-based

How"All caches on a bus monitor all the transactions on that bus"a shared directory tracks which caches hold each line
Trafficbroadcast to everyonepoint-to-point to holders only
Latencylow (single request/response)higher (3-hop: request → forward → respond)
Scalingbandwidth-bound; degrades as cores growstorage-bound; scales to many cores

Snooping "tend[s] to be faster, if enough bandwidth is available" because every transaction is one broadcast. But a bus every core must watch is a hard bandwidth ceiling, so large and multi-socket machines switch to directories with point-to-point messaging. This is the microarchitectural reason cross-socket coherence is slower than intra-socket — the extra directory hop — and it compounds the remote-memory penalty covered in NUMA tuning.

MESI, MOESI, MESIF

Real CPUs extend MESI to avoid bouncing dirty data through main memory. The added state changes what happens when one core reads a line another core holds Modified:

ProtocolAddsVendorDirty-line read behavior

MESI—baselinewriter must write back to memory (or downgrade M→S) before the reader gets it
MOESIO OwnedAMD (AMD64 Arch. Programmer's Manual Vol. 2)writer keeps the dirty data in Owned and supplies it cache-to-cache; no write-back needed
MESIFF ForwardIntelone shared copy is the Forward designated responder; only it replies, not every S copy

MOESI's Owned state is "both modified and shared": the owner retains "the exclusive responsibility for ensuring main memory is eventually updated" and "must respond to a snoop request with data." This enables "direct cache-to-cache transfers" without a write-back — "beneficial when the communication between two CPUs is significantly better than to main memory."

MESIF's Forward state is "a specialized form of the S state, and indicates that a cache should act as a designated responder." Without it, every cache holding a Shared copy answers a read request — redundant traffic. With it, exactly one replies. "The most recent requestor of a line is assigned the F state; when a cache in the F state responds, it gives up the F state to the new cache." An F line is clean and "may be discarded at any time without notice" — unlike Owned, which holds dirty data.

The practical takeaway: do not assume a read of a dirty line hits DRAM. On modern multicore it is usually a cache-to-cache transfer, and the exact path differs across AMD (MOESI) and Intel (MESIF). When a read does reach DRAM, its cost is set by row-buffer state rather than by the coherence protocol — see DRAM row buffers and bank conflicts.

Store buffers, invalidate queues, and why barriers exist

Coherence is correct but slow if done naively: a core writing a line it does not own must send an invalidate and wait for every other cache to acknowledge before the store commits. Two hardware buffers hide that latency, and both weaken ordering — the mechanism Paul McKenney documents in Memory Barriers: a Hardware View for Software Hackers:

  • Store buffer. Rather than stall, the core records the store in a store buffer and continues; when the line arrives owned, the data drains into the cache. Store forwarding keeps the writing core self-consistent (it snoops its own store buffer on loads) — but other cores cannot see the buffered store yet.
  • Invalidate queue. A core receiving an invalidate "send[s] an acknowledge immediately and the actual invalidation is queued," speeding the writer's commit. The cost: a window in which this core "will read stale values" because the invalidate has not yet been applied.

Neither buffer breaks coherence (every location still converges), but together they let stores and loads become globally visible out of program order. That is the entire reason for barriers: a write (store) barrier drains/marks the store buffer so buffered stores publish before later ones; a read (load) barrier marks the invalidate queue so later loads wait for pending invalidates. Acquire/release atomics compile down to exactly these. Coherence hardware plus these buffers is why you need them — not an alternative to them.

Common gotchas

  • Coherence tracks the line, not the variable. The protocol operates on ~64-byte lines, so two unrelated variables on one line invalidate each other on every write. That is precisely false sharing; the cure is data layout (padding/alignment), because the protocol is behaving correctly.
  • A store is never free. A write to a Shared or Invalid line is a Read-For-Ownership: it broadcasts and waits for other caches to reach Invalid before retiring. The cost of atomics, spinlocks, and shared counters is this coherence transaction, not the instruction — contention is on the line.
  • Reads are cheap; writes generate the traffic. Read/read sharing sits happily in Shared/Forward forever. The ping-pong starts the instant one core writes (write-invalidate). Move read-mostly fields off write-heavy lines.
  • Exclusive is not Modified. E is clean-sole-owner; the silent E→M on write (no bus transaction) is why E exists and why load-then-CAS is cheap. Reasoning about coherence cost means reasoning about which core currently owns the line.
  • volatile (C/C++) creates neither coherence nor a barrier. Coherence is automatic hardware; you never "flush a cache for coherence" on a coherent CPU. When threads see stale data the missing piece is a barrier or atomic (acquire/release), not a cache flush — a common and expensive misconception.
  • Coherence ≠ ordering. Per-location agreement (coherence) does not give cross-location visibility order (consistency). Store buffers and invalidate queues reorder visibility on purpose; only barriers/atomics restore the order your algorithm assumes.
  • The TLB is not coherent, even though the caches are. x86 hardware keeps no protocol for translations: when one thread unmaps or reprotects a page, the kernel has to IPI every other CPU that might hold a stale entry and wait for the acknowledgement. So the mental model that works for data lines does not transfer to address translation — see TLB misses and page-table walks for shootdowns and what AMD's INVLPGB changes.
  • Snooping does not scale. On a bus every core sees every transaction — a bandwidth wall. Multi-socket and many-core parts are directory-based, adding a hop; this is the hardware root of the cross-socket coherence penalty behind NUMA effects.
  • Dirty-line reads usually stay on-chip. Assume cache-to-cache transfer (MOESI Owned / MESIF Forward), not a DRAM round trip, and remember the path is vendor-specific (AMD vs Intel).
  • Coherence extends past one chip. Multi-socket links and coherent device interconnects such as CXL carry the same M/E/S/I invariants across a wider fabric — the model is unchanged, only the latency grows.
