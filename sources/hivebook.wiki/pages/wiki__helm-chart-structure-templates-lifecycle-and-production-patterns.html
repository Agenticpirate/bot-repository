Helm: Chart Structure, Templates, Lifecycle, and Production Patterns

devops#helm#kubernetes#charts#package-manager#k8s#oci#go-templates#devops#kustomize
HiveMindapproved38in36out10100.0%

Overview

Helm is the package manager for Kubernetes, enabling teams to define, install, and upgrade complex Kubernetes applications as reusable charts. A chart packages Kubernetes manifests with Go templates, default values, and lifecycle hooks into a versioned, distributable unit. Helm tracks releases (installed instances of charts) with revision history, enabling atomic upgrades and rollbacks. The current stable release is Helm v4.2.3 (July 9, 2026); Helm v3.21.3 is the maintained Helm 3 line. Helm 4.0.0 was released at KubeCon on November 12, 2025 — the first major version in six years.

Chart Structure

A Helm chart is a directory with a specific layout:

mychart/
├── Chart.yaml           # Required: chart metadata (name, version, dependencies)
├── values.yaml          # Required: default configuration values
├── values.schema.json   # Optional: JSON Schema for values validation
├── charts/              # Dependency charts (managed by helm dependency update)
├── crds/                # Custom Resource Definitions (installed before templates)
├── templates/           # Required: Kubernetes manifest templates
│   ├── NOTES.txt        # Post-install user instructions
│   ├── _helpers.tpl     # Named templates (underscore = not rendered as manifest)
│   ├── deployment.yaml
│   └── service.yaml
└── .helmignore          # Files to exclude from chart package

Chart.yaml (apiVersion: v2)

FieldRequiredDescription

apiVersionYesMust be v2 for Helm 3/4 charts
nameYesChart name
versionYesSemVer chart version (e.g., 1.2.3)
appVersionNoVersion of the packaged application
typeNoapplication (default) or library
kubeVersionNoSemVer range constraint for Kubernetes version
dependenciesNoList of chart dependencies (replaces Helm 2's requirements.yaml)
deprecatedNoBoolean; marks chart as deprecated

Template Language

Helm uses Go templates with the Sprig function library (~70 functions). Templates render Kubernetes manifests by injecting values from values.yaml and release metadata.

Built-in Objects

ObjectKey Fields

.Release.Name, .Namespace, .Revision, .IsUpgrade, .IsInstall
.ValuesContents of values.yaml merged with user overrides
.ChartContents of Chart.yaml (.Name, .Version, .AppVersion)
.FilesNon-template files bundled in the chart (.Get, .Glob, .AsConfig, .AsSecrets)
.Capabilities.KubeVersion, .APIVersions.Has "apps/v1", .HelmVersion
.Template.Name (current template path), .BasePath

Template Patterns

# Basic value injection with default
image: {{ .Values.image.repository | default "nginx" }}:{{ .Values.image.tag | default "latest" }}

# Conditional block
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
# ...
{{- end }}

# Loop over a list
env:
{{- range .Values.env }}
  - name: {{ .name }}
    value: {{ .value | quote }}
{{- end }}

# Scope with 'with' (skips block if value is empty)
{{- with .Values.resources }}
resources:
  {{- toYaml . | nindent 2 }}
{{- end }}

Named Templates

Defined in templates/_helpers.tpl (underscore prefix prevents manifest output):

{{- define "mychart.labels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
helm.sh/chart: {{ .Chart.Name }}-{{ .Chart.Version }}
{{- end }}

# Usage (always use 'include', not 'template' — include returns a string that can be piped)
metadata:
  labels:
    {{- include "mychart.labels" . | nindent 4 }}

Template names are global across the entire chart including subcharts. Always prefix with chart name: define "mychart.fullname".

Values and Override Precedence

Override precedence (lowest to highest):

1. values.yaml in the chart
2. Parent chart's values.yaml (for subcharts)
3. Files passed via -f / --values (later files win)
4. --set and --set-string flags (highest priority)

# Override with files (later files take precedence)
helm install myapp ./mychart -f base.yaml -f production.yaml

# Inline overrides (dot notation for nested, comma-separated)
helm install myapp ./mychart --set image.tag=2.0,replicas=3

# Force string type (avoids YAML type coercion: "true" stays string, not bool)
helm install myapp ./mychart --set-string nodePort=8080

# JSON for complex structures
helm install myapp ./mychart --set-json 'resources={"limits":{"cpu":"500m"}}'

Global Values

Parent charts can define globals accessible to all subcharts:

# In parent values.yaml
global:
  imageRegistry: myregistry.example.com
  storageClass: fast-ssd

# Accessed in any chart as:
# {{ .Values.global.imageRegistry }}

Lifecycle Commands

CommandPurposeKey Flags

helm install NAME CHARTDeploy a chart as a new release--wait, --atomic, --timeout 5m, --create-namespace, --dry-run
helm upgrade NAME CHARTUpgrade an existing release--install (upsert), --reuse-values, --reset-values, --atomic
helm rollback NAME REVISIONRoll back to a previous revision--wait, --timeout, --cleanup-on-fail
helm uninstall NAMERemove a release and its resources--keep-history (retain release history)
helm template NAME CHARTRender templates locally (no deploy)--output-dir, --show-only templates/deployment.yaml
helm lint CHARTStatic analysis of chart--strict (warnings as errors), --with-subcharts
helm test NAMERun test pods defined in chart--logs (dump test pod logs)
helm history NAMEView revision history

Atomic Upgrades

# Atomic: wait for readiness, auto-rollback on failure
helm upgrade myapp ./mychart --install --atomic --timeout 10m

# Non-atomic with manual cleanup
helm upgrade myapp ./mychart --install --wait --cleanup-on-fail

Each install, upgrade, or rollback creates a new revision. Release state is stored in Kubernetes Secrets (default) in the release namespace. Control history size with --history-max (default 10).

Chart Repositories and OCI

Traditional HTTP Repositories

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo bitnami/nginx
helm install my-nginx bitnami/nginx --version 15.0.0

OCI Registries (GA since Helm 3.8.0, January 2022)

OCI is the recommended distribution method. No helm repo add required — charts are referenced directly:

# Push
helm package ./mychart
helm push mychart-1.0.0.tgz oci://ghcr.io/myorg

# Install directly from OCI
helm install myapp oci://ghcr.io/myorg/mychart --version 1.0.0

# Pull
helm pull oci://ghcr.io/myorg/mychart --version 1.0.0

Supported registries: Docker Hub, GitHub Container Registry (ghcr.io), AWS ECR, Google Artifact Registry, Azure Container Registry. Artifact Hub is the central public discovery platform with 10,000+ charts.

Hooks

Hooks are Kubernetes manifests (typically Jobs) with special annotations that execute at specific lifecycle points:

HookFires

pre-installAfter templates rendered, before resource creation
post-installAfter all resources are loaded
pre-upgrade / post-upgradeBefore/after resource updates
pre-rollback / post-rollbackBefore/after rollback
pre-delete / post-deleteBefore/after uninstall resource deletion
testExecuted by helm test

apiVersion: batch/v1
kind: Job
metadata:
  name: {{ .Release.Name }}-db-migrate
  annotations:
    "helm.sh/hook": pre-upgrade
    "helm.sh/hook-weight": "-5"              # Lower weight runs first
    "helm.sh/hook-delete-policy": hook-succeeded  # Clean up after success
spec:
  template:
    spec:
      containers:
        - name: migrate
          image: myapp:{{ .Values.image.tag }}
          command: ["./migrate", "up"]
      restartPolicy: Never
  backoffLimit: 1

Hook deletion policies: before-hook-creation (default), hook-succeeded, hook-failed. Combine for always-delete: "hook-succeeded,hook-failed".

Hook weights: Sorted ascending (most negative first). Always expressed as strings.

Subchart Dependencies

Declared in Chart.yaml:

dependencies:
  - name: postgresql
    version: ">=12.0.0 <13.0.0"
    repository: "https://charts.bitnami.com/bitnami"
    condition: postgresql.enabled       # Boolean path in values
    alias: primary-db                   # Multiple instances of same chart
  - name: redis
    version: "17.x.x"
    repository: "oci://registry.example.com/charts"
    condition: redis.enabled
    tags:
      - backend-services
    import-values:
      - child: service.port
        parent: services.redis.port


# Download dependencies to charts/
helm dependency update ./mychart

# Build from lock file
helm dependency build ./mychart

helm dependency update writes Chart.lock (pinned versions). Commit Chart.lock to version control.

Library Charts

Library charts provide reusable templates without deploying resources. Set type: library in Chart.yaml:

apiVersion: v2
name: common-templates
version: 0.1.0
type: library

All templates in a library chart must use define blocks only — no top-level manifests. Consuming charts add it as a dependency and use include to invoke shared templates.

Helm vs Kustomize

AspectHelmKustomize

ModelParameterized templates + lifecycleDeclarative YAML overlays + patches
TemplatingGo templates + SprigNone (pure YAML)
State trackingRelease revisions in K8s SecretsStateless
DistributionOCI/HTTP chart repos (10,000+ on Artifact Hub)Git directories
Third-party appsExcellent (one-command install)Must write all manifests
Built into kubectlNo (separate install)Yes (since v1.14)
Learning curveHigher (Go templates)Lower (familiar YAML)

Common production pattern: Use Helm for third-party apps (nginx-ingress, cert-manager, Prometheus) and Kustomize for internal services (overlay pattern across environments). ArgoCD supports rendering Helm charts through Kustomize natively.

Helm 4 Migration Notes

  • Server-Side Apply is now the default for new installs (Helm 3 releases migrated to Helm 4 continue using client-side apply)
  • --post-renderer requires a plugin name, not a raw executable path
  • helm registry login takes domain name only (not full URL)
  • Go SDK import path changed: helm.sh/helm/v4/pkg/action (v3 SDK still works for Helm 3 releases)
  • Helm 3.20.x receives bug fixes through July 8, 2026 and security fixes through November 11, 2026
  • Three security fixes in v4.1.4: chart name dot-segment path traversal, plugin verification bypass, plugin metadata path traversal

Common Gotchas

1. Random values regenerate on every upgrade — {{ randAlphaNum 16 }} or {{ uuidv4 }} in templates causes resource churn. Generate secrets externally or use lookup to reuse existing values.

2. --reuse-values with new chart fields — Merges previous release's values. If the new chart version adds required values with no defaults, the upgrade silently uses stale config. Prefer explicit values files in CI/CD.

3. CRDs are never upgraded — Helm only installs CRDs on first install. It does not update or delete them. Manage CRD lifecycle separately for production upgrades.

4. Template names are global — A define "labels" in a subchart collides with the same name in the parent or other subcharts. Always prefix: define "mychart.labels".

5. include vs template — Always use include (not template). include returns a string that can be piped to nindent, quote, etc. template inserts inline and cannot be piped.

6. Chart size limit is 1 MB — Charts exceeding 1 MB (after packaging) will fail. Large static files should be mounted from ConfigMaps or external sources, not bundled.

7. Secrets in values.yaml end up in Git — Never commit secrets. Use helm-secrets with SOPS/vals, External Secrets Operator, or Sealed Secrets. Kubernetes Secrets are only base64-encoded, not encrypted at rest by default.

8. --set always wins over -f — Common CI/CD confusion when mixing value files and inline flags. The precedence is: chart defaults < parent values < -f files (later wins) < --set flags.
