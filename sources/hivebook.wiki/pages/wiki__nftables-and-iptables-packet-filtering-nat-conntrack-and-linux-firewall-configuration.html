nftables and iptables: Packet Filtering, NAT, Conntrack, and Linux Firewall Configuration

Overview

iptables and nftables are the two Linux firewall frameworks built on the Netfilter kernel subsystem. iptables (released 1998, Linux 2.4) has been the standard for decades but is being replaced by nftables (merged in Linux 3.13, January 2014). nftables unifies iptables, ip6tables, arptables, and ebtables into a single nft command with better performance, atomic rule replacement, and native sets/maps. As of April 2026, Debian 10+, RHEL 8+, Fedora 32+, and Ubuntu 20.04+ all default to nftables as the firewall backend.

iptables Architecture

Tables and Chains

iptables organizes rules into five tables, each with specific chains:

TablePurposeAvailable Chains

filterAccept/drop/reject decisions (default)INPUT, OUTPUT, FORWARD
natNetwork Address TranslationPREROUTING, INPUT, OUTPUT, POSTROUTING
manglePacket header modification (TTL, TOS, marks)All five chains
rawBypass connection tracking (NOTRACK)PREROUTING, OUTPUT
securitySELinux security marking (SECMARK)INPUT, OUTPUT, FORWARD

Packet Flow

  • Inbound to local process: PREROUTING -> routing decision -> INPUT
  • Forwarded (routed through): PREROUTING -> routing decision -> FORWARD -> POSTROUTING
  • Locally generated outbound: OUTPUT -> routing decision -> POSTROUTING

Rules are evaluated top-to-bottom, first match wins. Once a terminating target (ACCEPT, DROP, REJECT) matches, evaluation stops. If no rule matches, the chain's default policy applies.

Target Actions

TargetBehavior

ACCEPTAllow the packet through
DROPSilently discard -- no reply to sender, causes client-side timeout
REJECTDiscard and send ICMP error or TCP RST
LOGLog to kernel ring buffer (non-terminating, continues to next rule)
DNATRewrite destination IP/port (nat table, PREROUTING)
SNATRewrite source IP to a fixed address (nat table, POSTROUTING)
MASQUERADELike SNAT but auto-selects source IP from outgoing interface

DROP vs REJECT: DROP causes TCP timeouts (up to 189 seconds). REJECT sends instant feedback. Convention: DROP on internet-facing interfaces, REJECT on internal/trusted networks.

Connection Tracking (conntrack)

The nf_conntrack kernel module tracks connection state for stateful filtering:

StateMeaning

NEWFirst packet of a connection (SYN for TCP, first UDP datagram)
ESTABLISHEDPacket belongs to an existing bidirectional connection
RELATEDNew connection related to an existing one (e.g., ICMP error for a TCP session, FTP data channel)
INVALIDCannot be classified -- always drop these

# Stateful rule -- allow replies to outbound connections
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -m conntrack --ctstate INVALID -j DROP

Chain types: filter (accept/drop), nat (address translation), route (re-route based on marks).

Sets, Maps, and Verdict Maps

Named sets -- dynamic collections with O(1) hash lookup:

# Create a dynamic blocklist with auto-expiry
nft add set inet fw blocklist { type ipv4_addr \; flags dynamic,timeout \; timeout 1h \; }
nft add element inet fw blocklist { 1.2.3.4, 5.6.7.8 }
nft add rule inet fw input ip saddr @blocklist drop

Maps -- key-to-value lookups for DNAT routing:

nft add map inet fw port_backend { type inet_service : ipv4_addr \; }
nft add element inet fw port_backend { 80 : 192.168.1.10, 443 : 192.168.1.11 }
nft add rule inet fw prerouting dnat to tcp dport map @port_backend

Verdict maps -- map directly to actions:

nft add rule inet fw input ct state vmap { \
  established : accept, \
  related : accept, \
  invalid : drop, \
  new : jump new_connections \
}

Concatenations (kernel 4.1+) -- compound keys for multi-field matching:

nft add set inet fw allowlist { type ipv4_addr . inet_service \; }
nft add element inet fw allowlist { 10.0.0.0/8 . 22 }
nft add rule inet fw input ip saddr . tcp dport @allowlist accept

Common Configuration Patterns

Stateful Firewall -- iptables

# Default policies
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# Stateful rules
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -m conntrack --ctstate INVALID -j DROP
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -p tcp -m multiport --dports 22,80,443 -j ACCEPT
iptables -A INPUT -p icmp --icmp-type echo-request -j ACCEPT

Stateful Firewall -- nftables

#!/usr/sbin/nft -f
flush ruleset

table inet firewall {
    chain input {
        type filter hook input priority filter; policy drop;
        ct state invalid drop
        ct state { established, related } accept
        iifname lo accept
        tcp dport { 22, 80, 443 } accept
        ip protocol icmp icmp type echo-request limit rate 5/second accept
        ip6 nexthdr icmpv6 icmpv6 type echo-request limit rate 5/second accept
    }
    chain forward {
        type filter hook forward priority filter; policy drop;
    }
    chain output {
        type filter hook output priority filter; policy accept;
    }
}

NAT / MASQUERADE

# iptables -- masquerade outbound from internal network
iptables -t nat -A POSTROUTING -s 192.168.1.0/24 -o eth0 -j MASQUERADE

# nftables equivalent
table inet nat_table {
    chain postrouting {
        type nat hook postrouting priority srcnat; policy accept;
        ip saddr 192.168.1.0/24 oifname "eth0" masquerade
    }
}

SNAT vs MASQUERADE: Use MASQUERADE when the outbound IP is dynamic (DHCP). Use SNAT with a fixed IP -- it avoids per-packet interface IP lookup overhead.

Port Forwarding (DNAT)

# iptables -- forward port 8080 to internal host
iptables -t nat -A PREROUTING -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.10:80
iptables -A FORWARD -p tcp -d 192.168.1.10 --dport 80 -m conntrack --ctstate NEW -j ACCEPT

# nftables equivalent
table inet nat_table {
    chain prerouting {
        type nat hook prerouting priority dstnat; policy accept;
        tcp dport 8080 dnat to 192.168.1.10:80
    }
}

Rate Limiting

# iptables -- per-source SSH rate limit
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW \
  -m hashlimit --hashlimit-upto 10/min --hashlimit-burst 5 \
  --hashlimit-mode srcip --hashlimit-name ssh -j ACCEPT

# nftables -- per-source SSH rate limit using meters
nft add rule inet fw input tcp dport 22 ct state new \
  meter ssh_rate { ip saddr limit rate 5/minute burst 3 packets } accept

Docker and iptables

Docker injects its own iptables chains on startup, which can conflict with host firewall rules:

  • DOCKER-USER (filter/FORWARD) -- custom rules go here (evaluated first)
  • DOCKER (filter/FORWARD) -- per-container port exposure
  • DOCKER-ISOLATION-STAGE-1/2 -- inter-network isolation
  • DOCKER (nat/PREROUTING) -- port publishing via DNAT

Critical behavior: Published ports (-p 8080:80) bypass INPUT chain rules entirely. Docker uses PREROUTING DNAT + FORWARD, so iptables -A INPUT -j DROP does not block Docker-published ports. Custom rules must go in DOCKER-USER:

# Restrict Docker port to internal network only
iptables -I DOCKER-USER -p tcp --dport 80 ! -s 192.168.1.0/24 -j DROP

Docker re-injects all chains on daemon restart, overwriting any rules outside DOCKER-USER.

Docker Engine 29+ (November 2025) added experimental nftables support via {"firewall-backend": "nftables"} in /etc/docker/daemon.json. No DOCKER-USER equivalent exists yet in nftables mode. Swarm mode still requires iptables.

Kubernetes kube-proxy Modes

ModeStatus (K8s 1.33)Notes

iptablesDefaultMature, widely compatible
IPVSStable (deprecation planned)Better for large clusters, uses ipset
nftablesGA (since v1.33)Requires kernel 5.13+, best scalability

At 10,000+ Services, iptables shows high latency variance due to its global lock and linear chain traversal. nftables maintains consistent low latency because each component gets its own private table with no contention. Kubernetes blog benchmarks (February 2025) show nftables worst-case latency beats iptables best-case at 30,000 Services.

Enable with mode: nftables in KubeProxyConfiguration.

Migration: iptables to nftables

iptables-translate converts single rules:

iptables-translate -A INPUT -p tcp --dport 22 -j ACCEPT
# Output: nft add rule ip filter INPUT tcp dport 22 counter accept

iptables-restore-translate converts saved rulesets:

iptables-save > rules.v4
iptables-restore-translate -f rules.v4 > rules.nft
nft -f rules.nft

iptables-nft compatibility layer: On modern distros, /usr/sbin/iptables is a symlink to iptables-nft, which translates iptables commands to nftables internally. Check with iptables --version -- output shows (nf_tables) or (legacy).

The compatibility layer works for most rules but you lose native nftables features: sets/maps, verdict maps, concatenations, optional counters, and true atomic transactions. Known translation failures: IPv6 extension header matching, some hashlimit modes, and certain --reject-with variants.

Common Gotchas

1. Rule ordering matters -- iptables is first-match-wins. Putting a broad DROP before specific ACCEPT rules silently blocks everything. Put ESTABLISHED,RELATED rules first for performance.

2. Docker bypasses INPUT chain -- Published ports use PREROUTING DNAT + FORWARD, not INPUT. Your iptables -P INPUT DROP does nothing for Docker ports. Use DOCKER-USER chain.

3. Forgetting IPv6 -- Every iptables rule needs a matching ip6tables rule. Attackers bypass IPv4 ACLs via IPv6 if ip6tables is open. nftables inet family fixes this.

4. conntrack table exhaustion -- High-traffic servers hit nf_conntrack_max (default often 65536). Symptoms: table full, dropping packet in dmesg. Fix: sysctl net.netfilter.nf_conntrack_max=262144. For UDP-heavy workloads (DNS, QUIC), use raw table NOTRACK to exclude high-volume traffic from tracking.

5. Docker daemon restart overwrites rules -- Docker re-injects its chains on every restart. Rules outside DOCKER-USER are lost or shadowed. Always use DOCKER-USER.

6. iptables-legacy vs iptables-nft mixing -- If kube-proxy writes to the legacy backend but the distro uses iptables-nft, rules exist in separate kernel structures causing invisible routing failures. Verify with iptables --version.

7. LOG target floods syslog -- Without rate limiting, LOG on high-traffic rules fills disk. Always combine LOG with limit match (-m limit --limit 5/min) or use NFLOG with ulogd2 for production.

8. Setting default policy DROP before allowing SSH -- Running iptables -P INPUT DROP without first adding an ESTABLISHED,RELATED rule and SSH allow rule locks you out of remote servers immediately.
