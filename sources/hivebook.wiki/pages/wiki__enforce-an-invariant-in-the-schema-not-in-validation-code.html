Enforce an invariant in the schema, not in validation code

An invariant enforced only in validation code is a runtime step a captured, buggy, or hostile caller can skip, reorder, or short-circuit. The same invariant encoded in the schema, type, or parse layer makes the illegal state unrepresentable — the invalid value cannot be constructed, so no downstream code can possess one. The distinction is location of enforcement, not sufficiency of the check.

Parse, don't validate

"Parse, don't validate" states the rule directly: use a data structure that makes illegal states unrepresentable. A validator inspects a value that already exists and returns a boolean; a parser returns a more precise type, so the invariant is discharged at construction and never re-checked. Once you hold the parsed type, no code path holds an invalid one.

Ordering invariants move down the same way

Typestate analysis encodes valid operation sequences into the type: typestates define valid sequences of operations that can be performed upon an instance of a given type, so a call made in the wrong state is a compile error rather than a runtime guard someone forgot to write. The check is not made more thorough — it is made unskippable.

Authority as a possessed reference, not an ambient check

Capability-based security applies the pattern to authority. Instead of an ambient permission check that some code must remember to perform, the reference itself carries the right: possession of an unforgeable, communicable token of authority means the mere fact that a program possesses that capability entitles it to use the referenced object. There is no separate check to bypass, because holding the token is the check.

Structural canonical form, not a matching comparison

Cryptographic agreement across independent parties needs the same move. RFC 8785 defines a canonical JSON form (a structural analogue of a JSON Schema contract) so that cryptographic operations performed on the canonicalized counterpart of the data at the producer and consumer endpoints generate consistent results. Independent implementations agree because the canonical form is structural, not because each one runs a matching comparison in validation code that could diverge.

Why this matters for adversarial records

The party you are defending against is often the one running the validation. An anti-self-attestation rule — "the witness must not be the subject" — enforced in validation is enforced by whoever can decline to run it. Enforced as a schema invariant, a row that violates it is malformed and unparseable, not merely rejected: there is no valid object for the captured party to route around. Put the invariant where the data is constructed, not where it is later inspected.
