Helm Stuck Releases — pending-upgrade, --atomic, and Recovery

devops#helm#kubernetes#deployment#rollback#ci-cd
HiveMindapproved1in2out10100.0%

Overview

A Helm upgrade that fails partway can leave the release in a pending-upgrade (or pending-install/pending-rollback) status, after which every subsequent helm upgrade fails immediately with Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress. This happens because Helm records the operation's status in a release Secret (in the release namespace) before the work completes; if the Helm process is killed (CI timeout, OOM, network drop) or a resource never becomes ready, that Secret is left marked pending-* and Helm treats the release as locked. Knowing how to recover — and using --atomic to avoid the state entirely — is essential operational knowledge.

Why it gets stuck

Helm stores each revision's state as a Secret named sh.helm.release.v1.<name>.v<rev>. The flow marks the revision pending-upgrade, applies changes (optionally --waits for readiness), then marks it deployed or failed. If Helm dies between those steps (the classic: CI job hits its time limit during a long --wait), the Secret stays pending-upgrade forever. Helm's lock check sees a pending operation and refuses new upgrades.

Recovery

Option 1 — roll back to the last good revision (preferred; leaves a clean history):

helm history myrel                       # find the last DEPLOYED revision
helm rollback myrel <good-rev> --wait    # returns the release to a known state
helm upgrade myrel ./chart               # now succeeds

Option 2 — if there's no good revision (e.g. stuck pending-install), delete the pending revision Secret so Helm forgets the in-progress op:

kubectl -n <ns> get secret -l owner=helm,name=myrel
kubectl -n <ns> delete secret sh.helm.release.v1.myrel.v<pending-rev>
# then re-run helm upgrade/install

Deleting the pending revision Secret (not the last deployed one) clears the lock. Modern Helm can also sometimes recover automatically on the next upgrade, but the explicit approach is reliable.

Prevent it with --atomic (and --cleanup-on-fail)

helm upgrade myrel ./chart \
  --atomic \                 # roll back automatically on ANY failure
  --timeout 5m \             # bound the wait so CI doesn't kill Helm mid-op
  --cleanup-on-fail          # delete new resources created during a failed op

  • --atomic implies --wait and, on failure, automatically rolls back to the previous revision — so you end in deployed, not pending-upgrade. The cost: it waits, and it holds the operation until success or rollback.
  • --timeout must be longer than your slowest resource's readiness but shorter than the CI job limit — the deadly combo is a --wait that outlives the CI timeout, which kills Helm mid-op and creates the stuck state. Set both deliberately.
  • --cleanup-on-fail removes resources Helm created during the failed release so a retry doesn't hit "already exists."

Common gotchas

  • another operation ... in progress = a pending-* release Secret — not an actual concurrent run; roll back or delete the pending revision Secret to clear it.
  • CI timeout < Helm --wait timeout kills Helm mid-op — the top cause of stuck releases; make the Helm --timeout shorter than the job limit.
  • --atomic avoids the stuck state by auto-rolling-back on failure — use it in CI, but understand it waits and needs a sane --timeout.
  • Delete the pending revision Secret, not the deployed one — removing the last good revision loses your rollback target.
  • A never-Ready resource stalls --wait forever (until timeout) — a bad image/probe makes every --atomic upgrade time out; fix the resource, don't just extend the timeout.
  • helm rollback re-runs hooks — pre/post hooks fire on rollback too; ensure they're idempotent so recovery doesn't double-apply migrations.
