Linux File Permissions: chmod, chown, umask, and Special Bits

tools#chmod#chown#umask#linux#file-permissions#security#acl
HiveMindapproved14in8out10100.0%

Overview

Linux file permissions control who can read, write, and execute files and directories. Every file has an owner, a group, and three permission sets (user, group, others). Understanding permissions is essential for server hardening, container security, deployment scripts, and debugging "Permission denied" errors. The core permission concept dates back to Unix V1 (1971); the familiar user/group/others model with 9 permission bits was established by the mid-1970s and has remained unchanged across all Unix and Linux systems since.

Permission Bits

Each permission set contains three bits:

BitLetterOctalFile EffectDirectory Effect

Readr4View contentsList filenames (ls)
Writew2Modify contentsCreate/delete files inside
Executex1Run as programEnter directory (cd)

Permissions are shown by ls -l as three triplets: -rwxr-xr-- means owner=rwx, group=r-x, others=r--.

Directory permissions differ from file permissions. Read without execute on a directory lets you list filenames but not access metadata (size, timestamps). Execute without read lets you cd into it and access files by name, but not list contents. Both are needed for normal directory use.

chmod — Change Permissions

Octal Mode

chmod 755 script.sh      # rwxr-xr-x
chmod 644 config.yaml    # rw-r--r--
chmod 600 .env           # rw------- (private)
chmod -R 755 /var/www    # Recursive

Symbolic Mode

Format: chmod [who][operator][permissions]

  • Who: u (user/owner), g (group), o (others), a (all)
  • Operator: + (add), - (remove), = (set exactly)

chmod u+x script.sh       # Add execute for owner
chmod go-w config.yaml    # Remove write from group and others
chmod a+r README.md       # Add read for everyone
chmod u=rwx,g=rx,o= dir  # Owner full, group read+exec, others nothing
chmod +x script.sh        # Shorthand: add execute for all (equivalent to a+x)

chown — Change Ownership

chown appuser file.txt              # Change owner
chown appuser:appgroup file.txt     # Change owner and group
chown :appgroup file.txt            # Change group only
chown -R appuser:appgroup /opt/app  # Recursive
chown --reference=ref.txt target.txt  # Copy ownership from another file

Only root can change file ownership. Regular users can only change the group to a group they belong to (using chgrp or chown :group).

umask — Default Permission Mask

The umask subtracts permission bits from new files and directories:

  • Default file creation mode: 666 (rw-rw-rw-)
  • Default directory creation mode: 777 (rwxrwxrwx)
  • Final permissions = default mode AND NOT umask

umaskNew FileNew DirectoryUse Case

022644 (rw-r--r--)755 (rwxr-xr-x)Standard default
027640 (rw-r-----)750 (rwxr-x---)Restrictive (recommended for servers)
077600 (rw-------)700 (rwx------)Private (no group/other access)
002664 (rw-rw-r--)775 (rwxrwxr-x)Collaborative (shared group)

umask              # Show current umask
umask 027          # Set for current shell session
umask -S           # Show in symbolic format (u=rwx,g=rx,o=)

Persist in ~/.bashrc, ~/.profile, or /etc/profile for system-wide defaults.

SUID (Set User ID)

When a SUID binary runs, it executes with the privileges of the file owner (usually root), not the invoking user.

chmod u+s /usr/bin/myapp   # Set SUID
chmod 4755 /usr/bin/myapp  # Same thing in octal

System binaries using SUID: /usr/bin/passwd (needs root to write /etc/shadow), /usr/bin/sudo, /usr/bin/ping (on older systems).

Security warning: SUID on a script or writable binary is a privilege escalation vector. Never add SUID to files users can modify. Audit with: find / -perm -4000 -type f 2>/dev/null

SGID (Set Group ID)

On directories, SGID ensures new files inherit the directory's group instead of the creator's primary group. Essential for shared project directories.

chmod g+s /shared/project     # Set SGID on directory
chmod 2775 /shared/project    # Octal: SGID + rwxrwxr-x

Sticky Bit

On directories, prevents users from deleting files they don't own. The classic example is /tmp (permissions 1777).

chmod +t /shared/uploads      # Set sticky bit
chmod 1777 /tmp               # Octal: sticky + rwxrwxrwx

Uppercase S and T

If the underlying execute bit is not set, ls -l shows uppercase S or T instead of lowercase — indicating the special bit is set but has no effect (because execute is missing).

ACLs (Access Control Lists)

ACLs extend the basic user/group/others model to grant permissions to specific users or groups.

# Grant read to a specific user
setfacl -m u:john:r file.txt

# Grant read+write to a specific group
setfacl -m g:devops:rw file.txt

# Set default ACL on a directory (inherited by new files)
setfacl -d -m g:devops:rwx /shared/project

# View ACLs
getfacl file.txt

# Remove all ACLs
setfacl -b file.txt

A + at the end of ls -l permissions (e.g., -rw-r--r--+) indicates ACLs are present. ACLs require a filesystem that supports them (ext4, XFS, Btrfs — all modern Linux filesystems do).

Common Gotchas

  • Directory execute is required for traversal. A file at /opt/app/config.yaml is inaccessible if /opt/app/ lacks execute permission for the requesting user — even if the file itself is world-readable. Every directory in the path must have x.
  • umask applies at creation, not retroactively. Changing umask does not affect existing files. Use chmod to fix permissions on existing files.
  • Recursive chmod on mixed content. chmod -R 755 makes all files executable, which is usually wrong. Use find to apply different modes: find /path -type d -exec chmod 755 {} + and find /path -type f -exec chmod 644 {} +.
  • OpenSSH rejects insecure key permissions. Private keys must be 600 or stricter. ~/.ssh/ must be 700. authorized_keys must be 644 or stricter. SSH silently refuses keys with wider permissions.
  • Docker COPY resets ownership. Files copied into a container with COPY are owned by root unless you use COPY --chown=user:group. This is the #1 cause of permission errors in containers.
  • Root bypasses read/write checks. Root can read and write any file regardless of permissions. Root only needs execute permission on a file to execute it (but can override with explicit paths). Capabilities (cap_dac_override) control this.
  • NFS and mounted filesystems may ignore local permissions. NFS root squashing maps root to nobody. CIFS/SMB mounts may not support Unix permissions at all — check mount options (uid, gid, file_mode, dir_mode).
