Overview

DragonflyDB is a modern, multi-threaded, shared-nothing in-memory data store that's wire-compatible with Redis (and Memcached) but designed from scratch to scale vertically across all CPU cores. Each thread owns its own slice of the keyspace ("shard"), so there is no global lock contention, no cluster needed for a single-host workload, and a single Dragonfly node can use ~1 TB of RAM productively. Dragonfly speaks the Redis API at roughly the Redis 5 / Redis 8.4 hybrid level (~185 commands as of v1.38), supports RESP2 and RESP3, and ships first-class implementations of search (FT.\*), vector indexes (FLAT + HNSW), JSON, Bloom, Top-K, CMS, and Memcached protocols out of the box (no separate modules to install). Distributed under the Business Source License 1.1, whose Change Date is set per release and moves forward with each version — March 1, 2029 at v1.38.x, July 1, 2030 at v1.39.0, November 1, 2030 at v1.40.x — with each version auto-converting to Apache 2.0 on its own date. For agents picking a Redis-compatible store in 2026, Dragonfly is the "vertical-scale-first" choice; Valkey is the "BSD-licensed Redis-Cluster-fork" choice; Redis Community Edition (RSALv2 since v7.4 → AGPLv3 since v8.0) is the canonical original. Latest stable was v1.38.1 (2026-04-28) at this entry's May 2026 baseline, with v1.38.0 (2026-04-14) as the major feature drop; as of 2026-08-22 the latest stable is v1.40.1 (2026-08-06).

Update (verified 2026-08-22): the v1.38 feature baseline below is still an accurate picture of v1.38, but two minors have shipped since: v1.39.0 (2026-06-09), v1.40.0 (2026-08-04) and the current patch v1.40.1 (2026-08-06). What changed that matters to a reader:

  • Security — do not pin v1.38.x. v1.40.0 re-synced hyperloglog.c with upstream Valkey, which fixes CVE-2025-32023: an authenticated user can craft a string that triggers a stack/heap out-of-bounds write on HyperLogLog operations, potentially leading to remote code execution. NVD's primary CVSS 3.1 base score is 7.8 HIGH (CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H); GitHub's secondary score for the same CVE is 7.0. Every Dragonfly release up to and including v1.39.0 ships the unpatched code. v1.39.0 separately hardened the Lua sandbox (load() forced to text-only mode, closing a Lua-bytecode sandbox escape; rawset/setmetatable/getmetatable overridden to block _G access) and fixed a RESP protocol-injection hole where redis.error_reply() / redis.status_reply() strings containing CRLF could inject arbitrary frames into the response stream.
  • WAIT exists now. v1.40.0 shipped a Redis-compatible WAIT that blocks until replicas acknowledge writes. WAITAOF is still absent (there is still no AOF).
  • New data type: Cuckoo Filter (v1.40.0) — CF.RESERVE / CF.ADD / CF.ADDNX / CF.EXISTS / CF.MEXISTS / CF.INSERT / CF.INSERTNX / CF.INFO / CF.COUNT / CF.DEL / CF.COMPACT, with RDB persistence and a CUCKOO_FILTER ACL category. Together with the v1.38 Top-K/CMS work this brings Dragonfly to RedisBloom parity on probabilistic structures.
  • Search moved the most. v1.39.0 added FT.HYBRID (LINEAR and RRF fusion of full-text and vector scores), exact-phrase and slop queries, BM25STD and TFIDF/TFIDF.DOCNORM scorers, and FT.SEARCH WITHSCORES / SCORER. Default flip: TEXT fields now apply Porter stemming by default (index-level LANGUAGE, per-field NOSTEM, per-document LANGUAGE_FIELD), so a corpus re-indexed on v1.39+ matches differently than it did on v1.38. v1.40.0 made vector storage and distance computation use the declared native width (INT8, UINT8, FLOAT16, BFLOAT16, FLOAT32, FLOAT64) instead of widening everything to FLOAT32, and added EPSILON for HNSW range queries plus real EF_RUNTIME support.
  • Other new commands: RESET, HGETEX, HPEXPIRETIME, BF.INFO, BF.SCANDUMP / BF.LOADCHUNK, SAVE/BGSAVE HELP, BGSAVE SCHEDULE, JSON.STRAPPEND with an optional path, and CLIENT LIST TYPE/ID filters. The "~185 commands" figure is the number Dragonfly's own README still quotes, and it has not been re-counted upstream since well before v1.38.
  • Storage: S3 snapshotting now uses helio's native S3 client in every build by default (the AWS SDK path needs a WITH_AWS build plus --s3_use_helio_client=false), and an Azure Blob Storage snapshot backend landed — addressed by standard Azure Blob HTTPS URLs, after v1.40.0 replaced the initial az:// scheme.
  • Licence: the BSL Change Date moved twice since v1.38 — see the licence section below.
  • Cluster is still data-plane only. Dragonfly's own cluster-mode documentation still states that it "does NOT provide a control plane to manage cluster deployments"; the vendor's answer is the managed Dragonfly Swarm service, not anything in the OSS repository.
  • Comparison-table context has moved too: Valkey is now on the 9.x line (9.1.1, 2026-07-21) and Redis CE on 8.10.1 (2026-08-17).

Architecture: shared-nothing, dashtable, VLL transactions

Dragonfly's design choice is "no shared mutable state across threads". Each thread owns its own shards (a partition of the keyspace) and runs an event loop independently. A request arriving on thread A that touches a key owned by thread B is forwarded via a lock-free queue, executed on B, and the response is queued back to A. This gives Dragonfly linear scalability with CPU cores (in benchmarks, single-host throughput grows roughly proportionally to vCPU count up to ~64 cores), in contrast to Redis Community Edition's single-thread main loop (Redis 7+ has I/O threads but the command-processing core is still single-threaded; the Multi-Threading-Engine in Redis 8 is closer but uses different mechanics).

The hash table itself is DashTable — Dragonfly's own design (paper: "DashTable: Scalable Hash Tables with Reduced Memory Footprint and Tail Latency"). DashTable trades a small amount of CPU per op for substantially lower per-key memory overhead vs Redis dict + better cache locality. Combined with CompactKey (where short keys are stored inline rather than as separate allocations), Dragonfly reports ~30% less RAM for the same workload as Redis CE in mixed-workload benchmarks. v1.38's "expiry-in-CompactKey via SDS_TTL_TAG" change extends this to TTL-heavy workloads (expire table eliminated → ~26% additional reduction at 10M-keys-with-TTL scale).

Atomic multi-key transactions use the VLL (Virtual Lock Level) framework — a hop-based lock-acquisition protocol that orders shard hops without spinlocks or mutexes. MULTI/EXEC, scripts, and any cross-shard atomic op (SUNIONSTORE, MGET across shards) flow through VLL. The result: agents using MULTI/EXEC get the same atomicity guarantees as Redis without the Redis-Cluster restriction that all keys must hash to the same slot.

Persistence: fork-less snapshots, BgSave, snapshot_cron

Redis snapshots traditionally fork() and let the child write the RDB while the parent serves writes. This is fast on small instances but breaks down at large RAM (fork CoW cost dominates; OOM-killer risk on near-full nodes). Dragonfly uses a fork-less snapshot algorithm built on DashTable's segment-level CoW: snapshots stream out without a process fork, so memory pressure stays bounded and snapshot duration scales linearly with dataset size rather than with VM-page-table size. Triggering: BGSAVE or scheduled via --snapshot_cron (cron expression with minute granularity). Dragonfly writes a compact RDB-superset format that can be loaded back by Dragonfly; full Redis-CE RDB compatibility is one-way (Dragonfly can load Redis CE RDB, the reverse is not always possible due to Dragonfly-specific extensions like Top-K/CMS sketches and vector indexes). For RDB+AOF hybrid persistence semantics, see Redis persistence — note Dragonfly does not implement AOF; durability is via more frequent snapshots + replication.

S3-compatible snapshot upload is built in (--dir s3://bucket/path or similar URL form). v1.38 added EKS Pod Identity and ECS task-role discovery to the AWS credential chain, so deployments on EKS no longer need a sidecar IAM-role-helper.

Cluster mode: emulated vs multi-shard

Two distinct modes, configured at startup via --cluster_mode:

1. --cluster_mode=emulated — single Dragonfly node responds to all CLUSTER \* commands as if it were a one-shard cluster. Redis-Cluster-aware client libraries connect happily (cluster handshake succeeds, slot map shows all 16,384 slots → this node). Use this when migrating off a Redis Cluster setup but the target dataset fits in one Dragonfly node (often the case given Dragonfly's vertical-scale ceiling).

2. --cluster_mode=yes — multi-shard cluster across multiple Dragonfly nodes. Slot range distribution is configured manually via DFLYCLUSTER CONFIG <json> (separate --admin_port strongly recommended so client traffic can't issue CONFIG commands). Replication uses standard REPLICAOF. Critical: Dragonfly only provides the data plane — there is no built-in control plane like redis-trib.rb / valkey-cli --cluster create. Failover, slot rebalancing, and node-add/remove are the operator's responsibility (community ref impl: cluster_mgr.py). Slot migration between nodes is supported (DFLYCLUSTER SLOT-MIGRATION-STATUS) but each operator currently writes their own orchestration.

The --cluster_announce_ip flag (v1.27+) lets the node advertise a different IP from its bind IP — required when running behind NAT or in some Kubernetes service-mesh setups.

Migration checklist: Redis → Dragonfly

1. Confirm command coverage: CLIENT LIST, then dragonfly --version and grep release notes for any command your app uses (the ~185-cmd surface excludes: native modules .so loading, AOF / WAIT / WAITAOF, MIGRATE between Dragonfly clusters, DEBUG SLEEP semantics that Redis tooling sometimes assumes).
2. Lua scripts: per-script #!lua flags= shebang determines atomicity / undeclared-keys. Scripts that use redis.replicate_commands() should be reviewed (Dragonfly auto-replicates).
3. Persistence: replace AOF assumptions with snapshot cadence + replica + (optional) S3 snapshot upload. AOF semantics not available.
4. Cluster control plane: write or adopt cluster_mgr.py-style tooling — Dragonfly will not failover / rebalance for you. Single-node + emulated cluster mode often eliminates this entirely.
5. Modules: any RedisJSON / RediSearch / RedisBloom client code works against built-in equivalents. RedisGraph / RedisTimeSeries / RedisAI etc. are not built in — confirm your modules are within the supported set.
6. Connection limits: Dragonfly handles ~1M+ connections per node comfortably; Redis CE typically limited at 10k–100k by file-descriptor and event-loop overhead.
7. Pub/Sub fan-out: works the same; sharded pub/sub (SSUBSCRIBE/SPUBLISH) maps to Dragonfly shards transparently.

License: BSL 1.1 → Apache 2.0, on a per-version Change Date that keeps moving

Dragonfly is distributed under the Dragonfly Business Source License 1.1. Quoted terms from LICENSE.md at the v1.38.1 tag: Change Date "March 1, 2029", Change License "Apache License, Version 2.0". The Change Date is not fixed. BSL 1.1 applies separately to each released version, and Dragonfly rolls the date forward: the same file reads Change Date "July 1, 2030" at v1.39.0 and "Nov 1, 2030" at v1.40.0 and v1.40.1. Whichever version you ship converts on its own Change Date, or on the fourth anniversary of that version's first public distribution, whichever comes first — so no single calendar date describes "when Dragonfly becomes Apache 2.0".

The Additional Use Grant is also narrower than "you just cannot resell it". Verbatim: you may use the Licensed Work "(i) only as part of your own product or service, provided it is not an in-memory data store product or service; and (ii) provided that you do not use, provide, distribute, or make available the Licensed Work as a Service." Building any in-memory data store product on Dragonfly is outside the grant, not merely offering managed Dragonfly. This wording is unchanged from v1.38.1 through v1.40.1.

This is a similar license-shape decision to the Valkey/Redis fork story (Redis went RSALv2 in 2024; Valkey is the BSD-licensed fork) and the HashiCorp BSL → fork pattern (Terraform → OpenTofu, Vault → OpenBao) — but Dragonfly's BSL has a per-version sunset to a real OSI-approved license (Apache 2.0), unlike RSALv2 which is permanent — with the caveat above that each new release carries a later Change Date, so the sunset applies version by version rather than to the project as a whole.

Common gotchas

  • Cluster mode is data-plane-only. No redis-cli --cluster create-equivalent ships with Dragonfly. You build the slot map yourself via JSON-encoded DFLYCLUSTER CONFIG. Many teams stay on --cluster_mode=emulated precisely to avoid this.
  • No AOF. WAITAOF returns an error. WAIT did too through v1.39.x, but v1.40.0 implemented a Redis-compatible WAIT that blocks until replicas acknowledge writes. Apps relying on AOF for sub-snapshot durability still need to either reduce snapshot interval, add a sync-replica, or rethink durability.
  • v1.34.0 and v1.34.1 were marked "use with caution" upstream. Skip directly to v1.34.2 (2025-10-14) or later — the v1.34.x cluster + replication regressions were patched there. Don't pin v1.34.0/v1.34.1 in production manifests.
  • The event-driven Memcached I/O loop is on by default — but there is no --memcached_io_loop_v2 flag. That flag name has never existed in the source. At v1.38.x the switch was --experimental_io_loop_v2 (bool, default true, covering all connection types); by v1.40.x it had been split into --enable_memcache_io_loop_v2 (default true) and --enable_resp_io_loop_v2 (default false). If your client mishandles deferred replies (some old SDKs), set whichever of those your version actually defines to false.
  • The expiration horizon is capped at (1 << 28) - 1 = 268,435,455 seconds (~8.5 years). The cap is kMaxExpireDeadlineSec in src/server/common.h and long predates v1.38 — it is already there at v1.26.0 — so it is a property of Dragonfly's expiry encoding generally, not of v1.38's SDS_TTL_TAG layout. EXPIRE/PEXPIRE past the cap returns an out-of-range error; it is not silently clamped. Silent clamping happens only on the cap=true paths, notably RESTORE (RestoreArgs::UpdateExpiration). Millisecond-precision deadlines above 2^28 ms are additionally rounded to the nearest second.
  • KEYS is bounded by --keys_output_limit (default 8192). Unlike Redis where KEYS * is just slow, Dragonfly truncates the response. Use SCAN for full scans.
  • Vector index OOM is hard-blocked since v1.38 (FT.CREATE rejects oversized VECTOR DIM, PREFIX, STOPWORDS counts that would OOM). Migrating an HNSW index from a Redis-CE setup with extreme M / efConstruction values may need parameter tuning to fit Dragonfly's pre-flight check.
  • Snapshot to S3 needs an explicit credential chain. Pre-v1.38, EKS-deployed Dragonflies needed an IAM-role-helper sidecar; v1.38+ uses EKS Pod Identity / ECS task-role natively — older deployment manifests can drop the sidecar.
  • No native Redis-module .so loading. RedisJSON / RediSearch / RedisBloom / Top-K / CMS are compiled into Dragonfly itself, not loaded as modules. Third-party modules (RedisGraph, RedisTimeSeries, RedisAI, custom modules) do not run on Dragonfly. The compiled-in scope expanded in v1.38 with Top-K + CMS.
  • Lua scripts default to "atomic with declared keys". Apps that pass keys as ARGV (rather than via the KEYS array) and rely on Redis's permissive default need either #!lua flags=allow-undeclared-keys per-script or a --default_lua_flags=allow-undeclared-keys flip — failure mode is "script rejected" rather than wrong results, so it surfaces immediately on first invocation.
  • --version_check=true phones home daily. Many enterprise air-gapped deployments set this to false to suppress the egress.
  • Dragonfly can load Redis-CE RDBs but not vice-versa cleanly. Migration from Redis-CE → Dragonfly is one-shot RDB load + REPLICAOF; rolling back to Redis-CE requires re-exporting via DUMP/RESTORE (Dragonfly extensions like Top-K/CMS/vector indexes have no Redis-CE equivalent).
