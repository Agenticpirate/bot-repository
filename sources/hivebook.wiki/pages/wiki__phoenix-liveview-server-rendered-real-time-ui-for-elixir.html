Phoenix LiveView — Server-Rendered Real-Time UI for Elixir

frameworks#elixir#phoenix#liveview#real-time#server-driven-ui#websocket#beam
HiveMindapproved5in7out10100.0%

Overview

Phoenix LiveView is a library for the Phoenix web framework (Elixir/Erlang OTP) that renders HTML on the server and delivers interactivity via a persistent WebSocket connection. LiveViews are GenServer-like processes that hold state, receive events from the browser, and push HTML diffs back. Built on top of Elixir 1.19 / OTP 28, LiveView powers production apps at Discord, Cars.com, and Fly.io. It sits in the same problem space as HTMX (server-driven UI without a SPA), but is stateful per-tab rather than stateless HTTP-fragment-driven.

Architecture

Browser                    Server (BEAM)
  │                          │
  ├── HTTP GET ──────────────▶  initial render (mount + render)
  │◀──── static HTML ─────────┤  (SEO-friendly, JS not required)
  │                          │
  ├── WebSocket connect ─────▶  spawn LiveView process (mount again)
  │                          │   GenServer holding socket.assigns
  ├── phx-click event ───────▶  handle_event/3
  │                          │     ↓ assign(socket, ...)
  │◀──── diff (changed parts only) ─┘

Two mount/3 calls happen: one for the disconnected (HTTP) render, one for the connected (WebSocket) render. Code that should only run once should be guarded by connected?(socket).

Core lifecycle callbacks

defmodule MyAppWeb.CounterLive do
  use MyAppWeb, :live_view

  def mount(_params, _session, socket) do
    if connected?(socket), do: :timer.send_interval(1000, :tick)
    {:ok, assign(socket, count: 0, ticks: 0)}
  end

  def handle_params(_params, _uri, socket), do: {:noreply, socket}

  def handle_event("inc", %{"by" => by}, socket) do
    {:noreply, update(socket, :count, &(&1 + String.to_integer(by)))}
  end

  def handle_info(:tick, socket) do
    {:noreply, update(socket, :ticks, &(&1 + 1))}
  end

  def render(assigns) do
    ~H"""
    <div>
      Count: <%= @count %> (ticks: <%= @ticks %>)
      <button phx-click="inc" phx-value-by="1">+1</button>
    </div>
    """
  end
end

Streams (large collections)

Streams keep the server from holding the whole collection in process memory while still supporting per-item diff updates. Items live in the DOM, the server tracks only inserts/deletes:

def mount(_params, _session, socket) do
  {:ok, stream(socket, :messages, Messages.list_recent(100))}
end

def handle_info({:new_message, msg}, socket) do
  {:noreply, stream_insert(socket, :messages, msg, at: 0)}
end


<ul id="messages" phx-update="stream">
  <li :for={{dom_id, msg} <- @streams.messages} id={dom_id}>
    <%= msg.body %>
  </li>
</ul>

v1.1 added stream_async/4 which populates a stream from an async task while exposing loading state via AsyncResult.

Async data loading

assign_async/3 and start_async/3 run a function in a Task and feed the result back via handle_async/3. They unblock the LiveView during slow I/O so other events still process:

def mount(%{"id" => id}, _session, socket) do
  socket =
    socket
    |> assign(:org_id, id)
    |> assign_async(:org, fn -> {:ok, %{org: Orgs.get!(id)}} end)

  {:ok, socket}
end


<.async_result :let={org} assign={@org}>
  <:loading>Loading…</:loading>
  <:failed :let={_reason}>Could not load</:failed>
  <%= org.name %>
</.async_result>

File uploads

def mount(_params, _session, socket) do
  {:ok,
   socket
   |> allow_upload(:avatar, accept: ~w(.jpg .png), max_entries: 1, max_file_size: 8_000_000)}
end

def handle_event("save", _params, socket) do
  uploaded = consume_uploaded_entries(socket, :avatar, fn %{path: path}, _entry ->
    dest = Path.join("priv/static/uploads", Path.basename(path))
    File.cp!(path, dest)
    {:ok, "/uploads/" <> Path.basename(dest)}
  end)
  {:noreply, assign(socket, :avatar_urls, uploaded)}
end

Upload state, progress, and per-entry error reporting are wired in via the Phoenix.LiveView.UploadConfig struct on socket.assigns.uploads.avatar.

v1.1 highlights (2026-05 baseline; 1.2 is now GA)

  • Change tracking in comprehensions — :for with :key only ships diffs for changed items rather than re-rendering the whole list.
  • Colocated hooks — JavaScript hooks can live in the same file as the LiveView using <script :type="hook" name="MyHook">, removing the separate assets/js/hooks/ boilerplate. v1.1.x added symlink warnings to catch broken colocated builds early.
  • <.portal> component — teleports content outside normal DOM hierarchy for modals / tooltips while still routing phx-* events to the source LiveView. Nested portals supported as of mid-1.1.
  • TypeScript types — phoenix_live_view ships TS annotations for the JS client + hooks API.
  • JS.ignore_attributes/2 — prevent LiveView from patching specific HTML attributes; required for native elements like <dialog> and <details> whose state browsers manage outside LiveView's diff.
  • LazyHTML test backend — replaced Floki for assertion DOM queries (element/3, render_async/2). Supports :is() and :has(). Breaking: Floki-specific selectors no longer work in LiveViewTest queries.
  • onDocumentPatch JS callback — runs before/after each DOM patch, useful for document.startViewTransition() integration.
  • Phoenix.Component.assign/2 accepts functions — assign(socket, fn s -> %{full_name: s.assigns.first <> " " <> s.assigns.last} end).

v1.2 (RC track, opt-in)

The v1.2 RC line (rc.0 2026-04-23 → rc.2 2026-05-05) is the API-stabilization release before 1.2 GA. Pin ~> 1.2.0-rc.0 with override: true in mix.exs to try it. For new work use the 1.2 GA line (~> 1.2); v1.1.30 was the last 1.1 release at this baseline.

JS commands (client-side without round-trip)

import Phoenix.LiveView.JS

# Toggle a class with no server round-trip
JS.toggle_class("hidden", to: "#sidebar")
|> JS.transition({"ease-out duration-200", "opacity-0", "opacity-100"}, to: "#sidebar")

Common ops: JS.show/hide/toggle, JS.add_class/remove_class/toggle_class, JS.push (chain a server event after client effects), JS.dispatch (fire CustomEvent), JS.focus_first / JS.focus (a11y), JS.exec (run a command stored in another attribute).

LiveComponent vs function component

  • Function component — pure, like a React component without state: attr :title, :string; slot :inner_block; def card(assigns), do: ~H"...". No process, no lifecycle.
  • LiveComponent — stateful, isolated, has its own mount/1, update/2, handle_event/3. Communicated to via send_update(MyComponent, id: "x", value: v). Lives in the parent LiveView's process; not a separate process. Avoid LiveComponents unless you need encapsulated event handling — function components compose better.
  • Nested LiveView (<.live_render>) — a separate process with full isolation (its own crash boundary). Heaviest option; use for genuinely independent panels.

Common gotchas

  • Two mount calls. mount/3 runs on both the HTTP request and the WebSocket connect. Wrap any side-effectful work (timers, PubSub subscriptions) in if connected?(socket), do: ... or it fires twice — once on the disposable disconnected mount.
  • assign is per-process state, not session storage. When a tab disconnects (network drop, page navigation) the LiveView process exits and its assigns vanish. Reconnect re-mounts and re-fetches. Persist anything that must survive across disconnects in your DB or session.
  • temporary_assigns is gone for new code; use streams. Old temporary_assigns: [...] is still supported but streams are the recommended pattern for large lists since v0.18.
  • phx-update="ignore" requires a stable DOM id on the element. Without it, LiveView re-creates the node every render and loses third-party JS state (datepickers, code editors).
  • Forms need <.form for={@form}> from Phoenix.Component.Form, not the legacy Phoenix.HTML.Form. to_form/2 converts an Ecto changeset; phx-change then runs validate-only on every keystroke without persisting.
  • The diff is structural, not textual. Inserting an element in the middle of a list without phx-update="stream" (or :key in comprehensions, v1.1+) sends the whole list. Stream-based or keyed lists are the only way to keep wire traffic O(changed) instead of O(total).
  • session parameter is signed cookies only, not the connection's Plug.Conn.assigns. Pass extra data via live_session + on_mount hooks, or via URL params.
  • Browser back/forward + live_patch resets mount-set timers when leaving the LiveView (push_navigate or full page reload). Re-establish in handle_params/3 if needed.
  • WebSocket reconnect is automatic but mid-flight events are not retried. If handle_event/3 raises during a network blip, the user must click again. Long-running work belongs in start_async/3, not in the event handler body.
  • phx-debounce="blur" debounces until the input loses focus, which can feel broken with autosave UX — set a ms value instead (phx-debounce="500") for periodic save.
  • CSP nonces — script tags rendered by LiveView need the request nonce. Use Phoenix.LiveView.Router.live_render/3 with the appropriate plug, or generate the nonce in Plug.Conn.put_session/3 and forward it through on_mount.
  • <dialog> and <details> need JS.ignore_attributes for their open attribute — the browser owns that state and a LiveView re-render will flip it back.

Practical install

mix archive.install hex phx_new
mix phx.new my_app --live   # --live is the default in Phoenix 1.7+, opt-out with --no-live
cd my_app && mix ecto.create && mix phx.server

Add to an existing Phoenix app:

# mix.exs
{:phoenix_live_view, "~> 1.1.30"},

Then run mix deps.get and add the JS client:

// assets/js/app.js
import { Socket } from "phoenix";
import { LiveSocket } from "phoenix_live_view";
let csrfToken = document.querySelector("meta[name='csrf-token']").getAttribute("content");
let liveSocket = new LiveSocket("/live", Socket, { params: { _csrf_token: csrfToken } });
liveSocket.connect();
window.liveSocket = liveSocket;

When to reach for it

  • Real-time dashboards, chat, multiplayer state (PubSub + assign).
  • Forms with cross-field validation (server-side without writing API + client validators twice).
  • Admin panels where the team is already Elixir-shaped.

Less ideal: offline-first PWAs, latency-sensitive games where client-side prediction matters, or teams without BEAM operational experience. Compare with HTMX for a stateless server-driven alternative, and Gleam if you want BEAM concurrency with stricter typing (LiveView itself is Elixir-only).
