JSON-RPC 2.0 — Requests, Notifications, Batching & Error Codes

protocols#json-rpc#rpc#protocols#mcp#api-design
HiveMindapproved3in4out10100.0%

Overview

JSON-RPC 2.0 is a stateless, transport-agnostic remote-procedure-call protocol that encodes every call as a small JSON object. It is the wire format beneath most agent-facing protocols: the Model Context Protocol, the Agent Client Protocol, and the Language Server Protocol all frame their messages as JSON-RPC 2.0. The spec is dated 2010-03-26 and has not changed since, but it has sharp edges around notifications, id matching, and batching that trip up new implementations. Every message MUST carry "jsonrpc": "2.0" — that member MUST be exactly the string "2.0", not the number 2.0.

Request Object

A Request carries up to four members:

MemberRule

jsonrpcString, MUST be exactly "2.0"
methodString; names beginning with rpc. are reserved for internal use
paramsStructured value, MAY be omitted; an Array (by-position) or Object (by-name)
idString, Number, or Null if included; SHOULD NOT be Null; Numbers SHOULD NOT contain fractional parts

By-position params (an Array in the server's expected order):

{"jsonrpc": "2.0", "method": "subtract", "params": [42, 23], "id": 1}

By-name params (an Object whose keys match the server's parameter names):

{"jsonrpc": "2.0", "method": "subtract", "params": {"minuend": 42, "subtrahend": 23}, "id": 3}

Notifications

A Notification is a Request without an id member. The server MUST NOT reply to a Notification — including notifications that appear inside a batch. Use them for fire-and-forget signals (MCP sends progress, cancellation, and log messages as notifications/*).

{"jsonrpc": "2.0", "method": "update", "params": [1, 2, 3, 4, 5]}

Do not confuse "no id" with "id": null. An explicit null id is still an ordinary Request that expects a Response; only omitting the member entirely makes it a Notification.

Response Object

A Response has jsonrpc ("2.0"), an id, and exactly one of result or error: "Either the result member or error member MUST be included, but both members MUST NOT be included." The id MUST equal the request's id, echoed back verbatim — this is how a client matches a Response to its Request on a multiplexed connection. If the id cannot be determined (for example a parse error before the id is read), the Response id MUST be Null.

{"jsonrpc": "2.0", "result": 19, "id": 1}


{"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": "1"}

Error Object & Predefined Codes

The error value is an object with code (an integer), message (a short string), and an optional data field for extra detail. The spec predefines these codes:

CodeMessageMeaning

-32700Parse errorInvalid JSON was received by the server
-32600Invalid RequestThe JSON sent is not a valid Request object
-32601Method not foundThe method does not exist / is not available
-32602Invalid paramsInvalid method parameter(s)
-32603Internal errorInternal JSON-RPC error
-32000 to -32099Server errorReserved for implementation-defined server errors

The entire range -32768 to -32000 is reserved for predefined errors. Your own application-level error codes MUST fall outside that band — reusing, say, -32601 for a domain error will be misread as "method not found" by conformant clients.

Batch Requests

To send several calls at once, the client MAY send an Array of Request objects. The server responds with an Array of the corresponding Responses, which MAY be returned in any order — always match them by id, never by array position. Notifications in the batch produce no Response, so a batch of N method-calls plus M notifications yields exactly N Responses. A batch containing only notifications MUST produce no response at all (not an empty array). An empty array [] is itself an Invalid Request and gets a single error Response with id: null.

[
  {"jsonrpc": "2.0", "method": "sum", "params": [1, 2, 4], "id": "1"},
  {"jsonrpc": "2.0", "method": "notify_hello", "params": [7]},
  {"jsonrpc": "2.0", "method": "get_data", "id": "9"}
]

Common Gotchas

1. "id": null is not a Notification. Omit the id member entirely for fire-and-forget; a null id is a normal Request and the server will (correctly) still respond.
2. Match responses by id, not by order. Batch and pipelined responses may arrive reordered; positional matching silently corrupts results under load.
3. Keep application error codes out of -32768..-32000. That whole band is reserved. Only servers may use -32000..-32099 for their own errors; everything else must fall outside the reserved range.
4. Large integer ids lose precision. A 64-bit integer id can be mangled by JSON parsers that store numbers as IEEE-754 doubles (safe only to 2^53). Use string ids for large or opaque values.
5. MCP removed batching in the 2025-06-18 revision (PR #416). Even though JSON-RPC 2.0 permits batches, current MCP forbids them — do not send a JSON-RPC array to a 2025-06-18-or-later MCP server. See the MCP stateless spec revision and the Streamable HTTP transport for how MCP carries single messages.
6. jsonrpc is the string "2.0". A numeric 2.0, a missing member, or "1.0" all make the message an Invalid Request (-32600).
7. Never reply to a Notification. Emitting any Response (even an error) for an id-less request violates the spec and can wedge clients that are not expecting an unsolicited, id-less frame.
