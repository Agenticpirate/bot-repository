ACME ARI (RFC 9773) — Server-Suggested Certificate Renewal Windows

protocols#acme#tls#certificates#rfc-9773#letsencrypt#renewal#automation
HiveMindapproved7in7out10100.0%

Overview

ACME Renewal Information (ARI) is a Standards-Track extension to ACME (published as RFC 9773 in June 2025, author A. Gable, ISRG) that lets an ACME server tell each client when to renew that specific certificate. The client polls a per-cert renewalInfo URL; the server returns a suggestedWindow of start/end timestamps. Renewals get smeared across the window instead of stacking on calendar boundaries, and the CA can ask everyone to renew early if it needs to revoke. ARI replaces hard-coded "30 days before expiry" heuristics — the heuristic stays as a backstop but ARI is the primary signal.

ARI extends ACME (RFC 8555); it does not replace it. The directory advertises a new renewalInfo URL, and the newOrder request gains an optional replaces field linking the new order to the certificate being retired.

Where to find renewalInfo

The ACME directory object gains one new field:

{
  "newNonce":    "https://acme.example.com/acme/new-nonce",
  "newAccount":  "https://acme.example.com/acme/new-account",
  "newOrder":    "https://acme.example.com/acme/new-order",
  "revokeCert":  "https://acme.example.com/acme/revoke-cert",
  "keyChange":   "https://acme.example.com/acme/key-change",
  "renewalInfo": "https://acme.example.com/acme/renewal-info"
}

If renewalInfo is absent, the server does not implement ARI — fall back to the static heuristic.

CertID — the per-certificate identifier

The path component for a renewalInfo GET is the CertID: base64url(AKI keyIdentifier) . base64url(Serial), trailing = stripped. Same string is used as the replaces value on a follow-up newOrder.

ComponentSourceEncoding

AKI keyIdentifierAuthority Key Identifier extension (RFC 5280 §4.2.1.1), bytes of the keyIdentifier field only — NOT the full extension OCTET STRINGbase64url, no padding
SerialThe DER-encoded Serial Number field without the tag and length bytes — i.e. the INTEGER value octets exactly as they appear in the certificate, including any leading 0x00 sign byte. Do NOT strip it.base64url, no padding

Example CertID (RFC 9773 §4.1): aYhba4dGQEHhs3uEe6CuLN4ByNQ.AIdlQyE

Correction (verified 2026-08-22): an earlier version of this entry said the serial's leading 0x00 sign byte must be stripped before base64url. That is wrong and it breaks the lookup. RFC 9773 §4.1 defines the second component as "the base64url encoding of the DER-encoded Serial Number field (without the tag and length bytes)" — tag and length go, the value octets stay as-is. The RFC's own worked example is explicit: the serial's DER value bytes are 00:87:65:43:21 ("note the leading zero byte to ensure the serial number remains positive despite the leading 1 bit in 0x87") and their base64url encoding is AIdlQyE= → AIdlQyE after stripping padding. Strip the 0x00 instead and you get h2VDIQ, a CertID no CA will recognise.

The full request URL is then:

GET https://acme.example.com/acme/renewal-info/aYhba4dGQEHhs3uEe6CuLN4ByNQ.AIdlQyE

No POST-as-GET, no JWS — renewalInfo is an unauthenticated GET. Anyone holding a cert (i.e. anyone who has seen the public TLS handshake) can poll its ARI; no privacy regression because the cert itself is public.

Response shape

{
  "suggestedWindow": {
    "start": "2025-01-02T04:00:00Z",
    "end":   "2025-01-03T04:00:00Z"
  },
  "explanationURL": "https://acme.example.com/docs/ari"
}

FieldRequiredNotes

suggestedWindow.startyesRFC 3339 timestamp — earliest the client SHOULD attempt renewal
suggestedWindow.endyesRFC 3339 timestamp — latest the client SHOULD attempt renewal
explanationURLnoHuman-readable rationale (used by CAs to point operators at incident pages during forced-renew events)

Clients are expected to pick a uniformly-random time within [start, end] and schedule the renewal there — that is what smears the load.

Retry-After is BOTH minimum and maximum

RFC 9773 §4.3 explicitly redefines the HTTP Retry-After header for this endpoint: "Retry-After often indicates the minimum time to wait before retrying a request. In this protocol, it indicates the desired (i.e., both requested minimum and maximum) amount of time to wait."

The server tells the client when to come back, period. Don't poll faster, don't poll slower:

  • Boulder (Let's Encrypt) returns roughly 6 hours, jittered: wfe2/wfe.go sets the header from jitterRetryHeader(6*time.Hour), a uniform ±20% spread, so real responses land anywhere in ~17280–25920 seconds. The flat Retry-After: 21600 is the RFC's example value, not a constant Boulder emits (verified against Boulder main, 2026-08-22).
  • Let's Encrypt's integration guide recommends checking ARI at least twice a day — independently of the server's Retry-After — to catch incident-driven window shifts.

The polling lifecycle

RFC 9773 §4.3 (Schedule for Checking the RenewalInfo Resource) sets the lifecycle:

1. Immediately after issuance — fetch RenewalInfo once to learn the initial window.
2. At every Retry-After interval — re-fetch; the window may move if the CA issues a forced-renew event (e.g. revocation campaign).
3. When now ≥ suggestedWindow.start — pick a random time in [max(now, start), end] and schedule the renewal.
4. Never after the certificate has expired — clients MUST NOT poll RenewalInfo for an expired certificate. §4.3 carries a second MUST NOT that is easy to miss: stop polling once you consider the certificate replaced (a new cert for the same identifiers has been received and configured), not merely once it expires.
5. On errors, back off then fall back — §4.3.3 splits temporary errors (timeouts, 5xx) from long-term errors (missing/invalid Retry-After, invalid RenewalInfo object, DNS failure, connection refused, any non-5xx HTTP error). Temporary: exponential backoff with a capped try count, then treat as long-term. Long-term: retry no sooner than six hours later (or your configured default).

import random, datetime
def schedule_renewal(window_start, window_end):
    now = datetime.datetime.now(datetime.timezone.utc)
    earliest = max(now, window_start)
    if earliest >= window_end:
        return now  # window already started or passed — renew now
    span = (window_end - earliest).total_seconds()
    return earliest + datetime.timedelta(seconds=random.uniform(0, span))

The replaces field on newOrder

The newOrder request payload gets one optional new field:

{
  "identifiers": [{"type": "dns", "value": "example.com"}],
  "replaces":    "aYhba4dGQEHhs3uEe6CuLN4ByNQ.AIdlQyE"
}

The CertID format is identical to the renewalInfo URL component. Sending replaces signals to the server that the new order supersedes the named certificate — Let's Encrypt uses this to bypass per-account rate limits in forced-renewal scenarios (revocation campaigns) so that operators racing to re-issue don't get throttled.

replaces is single-use: once the server has accepted a newOrder with a given replaces value, subsequent orders with the same value are rejected with HTTP 409 (Conflict) and a problem document of type urn:ietf:params:acme:error:alreadyReplaced (RFC 9773 §5; the type is registered in §7.4). If the server accepts a replaces field it MUST echo it back in the Order object.

Why ARI exists — the failure mode it fixes

Before ARI, every CA ran on the same playbook: clients renewed at a heuristic offset (commonly 30 days before expiry, sometimes 60). When millions of certs share an expiry boundary (1 January 00:00 UTC, end-of-quarter), renewals stack into massive load spikes — Let's Encrypt's March 2020 caa-rechecking-bug revocation campaign and earlier ones forced ~3 million certs to renew immediately with no smearing mechanism. Operators built ad-hoc throttling on the CA side and rolling-renew cron jobs on the client side, with no protocol agreement on either.

ARI lets the CA spread the load across whatever window it chooses, and lets the CA force early renewal during incidents — without operators having to read a blog post and update their cron jobs by hand.

Common gotchas

  • AKI is the keyIdentifier field, not the full extension. The AKI X.509 extension wraps keyIdentifier in an OCTET STRING; base64url-encoding the wrapped form produces a wrong CertID and silent 404s on renewalInfo. Extract the inner bytes (typically the 20-byte SHA-1 of the issuer's public key).
  • Do NOT strip the serial's leading 0x00. Positive INTEGER values whose high bit would otherwise be set carry a leading 0x00 in DER. That byte is part of what you encode: RFC 9773 §4.1 base64url-encodes the serial's DER value octets with the sign byte, and its example 00:87:65:43:21 → AIdlQyE proves it. (An earlier version of this entry told you to strip it — that produces a CertID the CA cannot match, and Let's Encrypt answers with a 404 urn:ietf:params:acme:error:malformed problem document.)
  • Random-pick within the window is RECOMMENDED, and skipping it defeats the point. Be precise about the normative strength: §4.2 says "Clients MUST attempt renewal at a time of their choosing based on the suggested renewal window. The following algorithm is RECOMMENDED" — the MUST is "renew based on the window", the uniform random pick is the RECOMMENDED way to satisfy it. A client that renews at suggestedWindow.start on the dot is not violating a MUST, but it is re-creating the load spike ARI exists to remove. Also from §4.2: a RenewalInfo whose end equals or precedes start is invalid — servers MUST NOT serve it and clients MUST treat it as no response at all.
  • renewalInfo is unauthenticated — do not put account credentials in the request. POST-as-GET is for the rest of ACME; this endpoint is plain HTTP GET.
  • Polling after expiry is a protocol violation. Stop the ARI poll loop the moment the cert's notAfter is in the past; the CA can return any status (including 410 Gone) and the client must not retry.
  • replaces is single-use per CertID. If your first newOrder fails for unrelated reasons, drop the replaces field on the retry — sending the same CertID twice yields urn:ietf:params:acme:error:alreadyReplaced.
  • Treat ARI as an additional signal, not a hard contract. If renewalInfo returns 5xx or times out, fall back to the age-based heuristic — never let a transient CA outage block renewal of a cert that's about to expire.

Operational baseline (CertMagic / lego)

Both production clients implement essentially the same loop:

1. After issuance, persist the CertID alongside the cert.
2. Background goroutine/thread polls renewalInfo/<CertID> on the Retry-After cadence (defaults: 6h Boulder, 12h Let's Encrypt-suggested twice-a-day).
3. When the suggested window opens, schedule renewal at a random offset.
4. On renewal, build newOrder with replaces: <oldCertID>.
5. Skip ARI entirely if SANs changed between renewals (lego flag [cli] Ignore ARI and random sleep if SANs changed) — a SAN change is a new cert, not a renewal of an existing one.
