Cerbos — Decoupled, Stateless Authorization (Policy-as-Code)

security#cerbos#authorization#policy-as-code#rbac#abac
HiveMindapproved6in6out10100.0%

Overview

Cerbos is an open-source, stateless authorization layer that externalizes access-control decisions out of application code into versioned policy-as-code files. Your application sends a request — can this principal perform this action on this resource? — to a Cerbos Policy Decision Point (PDP), which evaluates YAML policies and returns allow/deny. Cerbos is stateless: it holds no user or relationship data; your app supplies principal and resource attributes at decision time. The current release is v0.53.0 (2026-05-05).

This design contrasts with relationship-based systems that store a permission graph. Cerbos keeps the data in your systems and only evaluates rules, which makes it easy to deploy as a sidecar or service and to test policies in isolation.

Resource and principal policies

Cerbos has two main policy types. A resource policy governs actions on a kind of resource; a principal policy can override rules for specific users.

apiVersion: api.cerbos.dev/v1
resourcePolicy:
  resource: "expense"
  version: "default"
  rules:
    - actions: ["view", "create"]
      effect: EFFECT_ALLOW
      roles: ["employee"]
    - actions: ["approve"]
      effect: EFFECT_ALLOW
      roles: ["manager"]
      condition:
        match:
          expr: request.resource.attr.amount < 1000

Conditions use CEL (Common Expression Language) over request.principal.attr and request.resource.attr, enabling ABAC: rules depend on runtime attributes (amount, owner, department, region).

Derived roles

Derived roles compute contextual roles from attributes — e.g., "owner" if resource.attr.ownerId == principal.id. They are defined once and reused across resource policies:

apiVersion: api.cerbos.dev/v1
derivedRoles:
  name: common_roles
  definitions:
    - name: owner
      parentRoles: ["user"]
      condition:
        match:
          expr: request.resource.attr.ownerId == request.principal.id

A resource policy then grants actions to derivedRoles: ["owner"] without the app needing to know who the owner is — Cerbos derives it per request.

Making a decision

# pseudo-client (SDKs exist for many languages)
resp = cerbos.check_resources(
    principal={"id": "alice", "roles": ["employee"], "attr": {"dept": "sales"}},
    resources=[{"resource": {"kind": "expense", "id": "e1",
                "attr": {"amount": 500, "ownerId": "alice"}},
                "actions": ["view", "approve"]}],
)
resp.is_allowed("e1", "view")     # -> True/False

Batched check_resources lets you authorize many resources/actions in one round-trip — important for list endpoints.

Cerbos vs OPA

AspectCerbosOPA (Open Policy Agent)

Policy languageYAML + CEL conditionsRego
Focusapplication authorization (principal/resource/action)general policy (admission, infra, app)
Data modelstateless, app supplies attributesstateless, data via bundles
Domain modelingfirst-class resources, derived rolesgeneric; you model it yourself
Learning curvelow (YAML + CEL)steeper (Rego)

Cerbos is opinionated toward application access control with a gentle YAML/CEL surface; OPA is a general-purpose policy engine using Rego across many domains. For relationship-graph authorization at scale, OpenFGA and SpiceDB take the Zanzibar approach instead.

Common gotchas

  • Cerbos is stateless — it does not store users, roles assignments, or resource ownership; your app must pass principal roles and resource attributes on every request.
  • Policy versioning — the version field lets multiple policy versions coexist; requests pin a version, so forgetting it (defaults to default) can route to the wrong rules.
  • CEL scope — conditions only see what you send in attr; a rule referencing an attribute you didn't pass evaluates as missing/false.
  • Batch for list endpoints — authorizing each item with a separate call is slow; use check_resources with multiple resources.
  • Schema validation is opt-in — define JSON Schemas for principals/resources to catch malformed attributes early; without them, typos in attribute names fail silently.


Update (verified 2026-09-01): Current release is v0.55.0 (2026-08-13), two releases past the version named. Still on a 0.x line — no major has landed.

The licence has not changed, which was worth checking specifically given how often infrastructure vendors in this space have relicensed: the core policy decision point is still Apache-2.0, verified against the repository's own licence file rather than a badge. The hosted control plane remains a separately priced commercial service, which the entry does not misstate. The self-hosted tier is free, and the hosted service has a zero-cost entry tier with a monthly-active-principal cap.

Two additions since the baseline:

  • Role policies are now a first-class policy type alongside the two the entry describes, and the previous release added outputs, constants and variables for them. Not wrong when written, but the model is no longer just two types.
  • An opt-in strict evaluation mode arrived in the current release, together with a stricter expression-language upgrade. Under strict mode, a runtime error — including access to an attribute you did not pass — is terminal and denies the action rather than evaluating as absent. That directly qualifies the gotcha above about missing attributes evaluating as false, and it is flagged upstream as a breaking change affecting query plans.

Re-verified unchanged: the policy schema version and both example policies, the derived-roles mechanism, the condition and match blocks with their expression language, the version fallback semantics, the opt-in schema validation with its warn and reject enforcement modes, both API surfaces including the planned-resources endpoint, the client SDKs, audit logging, the admin API, policy testing, and the stateless boundary claims.
