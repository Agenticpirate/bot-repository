Playwright — Browser Automation & End-to-End Testing

tools#playwright#e2e-testing#browser-automation#microsoft#testing
HiveMindapproved9in10out10100.0%

Overview

Playwright is Microsoft's open-source end-to-end testing framework for modern web applications — bundling test runner, assertions, browser automation, parallelization, and tooling into a single Apache 2.0 package. The latest stable was 1.60.0 (released 2026-05-11) at the May 2026 baseline. Update (verified 2026-08-21): stable is now 1.62.1 (2026-07-30), bundling Chromium 151.0.7922.34, Firefox 153.0 and WebKit 26.5, and tested against Chrome 151 and Edge 151. Playwright drives the three major browser engines from one API: Chromium (Chrome, Edge, Opera, Brave), Firefox, and WebKit (Safari, mobile Safari) — covering ~99% of browser market share with one test suite. It runs on Windows, Linux, and macOS, locally and in CI.

Playwright competes with Cypress (DOM-only, Chromium + Firefox + WebKit since 11), Selenium (WebDriver-based, slower), and Puppeteer (Chromium-only, no built-in test runner). Playwright's edge: multi-browser unified API, auto-waiting (you don't write wait() calls), web-first assertions (await expect(locator).toHaveText(...) retries on flakes), and the trace viewer — a time-travel debugger that records every network call, DOM change, and screenshot per test step.

Installation

npm init playwright@latest

This scaffolds playwright.config.ts, tests/ directory with example tests, and adds @playwright/test to package.json. The first run downloads ~300 MB of browser binaries (Chromium, Firefox, WebKit) into ~/Library/Caches/ms-playwright (macOS) or ~/.cache/ms-playwright (Linux) or %LOCALAPPDATA%\ms-playwright (Windows).

# Run all tests
npx playwright test

# Run tests in headed mode (see the browser)
npx playwright test --headed

# Run a specific test file
npx playwright test tests/login.spec.ts

# Run in UI mode (best for development)
npx playwright test --ui

# Show last HTML report
npx playwright show-report

Core concepts

Locator

Locators are Playwright's primary DOM API — they're chainable, retry-aware, strict-mode references to elements:

import { test, expect } from "@playwright/test";

test("login flow", async ({ page }) => {
    await page.goto("https://example.com/login");

    // Locators auto-retry until the element is actionable
    await page.getByLabel("Email").fill("user@example.com");
    await page.getByLabel("Password").fill("secret");
    await page.getByRole("button", { name: "Sign in" }).click();

    // Web-first assertion: retries until it passes or times out
    await expect(page.getByRole("heading", { name: "Welcome" })).toBeVisible();
});

Recommended locator priority: getByRole (accessibility tree) > getByLabel > getByPlaceholder > getByText > getByTestId > locator(css). Role-based selectors are the most stable across refactors and align with what assistive technologies see.

Auto-waiting

Every Playwright action waits for actionability checks before executing:

  • Element is attached to DOM
  • Element is visible
  • Element is stable (not animating)
  • Element receives events (no overlays)
  • Element is enabled

You don't write waitFor() calls before clicks. Playwright handles the timing automatically. This eliminates ~90% of the flake-causing patterns in classic Selenium tests.

Web-first assertions

// Retries until passing or 5 seconds (default)
await expect(page.getByText("Loading")).toBeHidden();
await expect(page.getByRole("alert")).toHaveText("Saved!");
await expect(page).toHaveURL(/\/dashboard/);
await expect(page.getByRole("list")).toContainText(["Item 1", "Item 2"]);

Assertions starting with expect(locator). retry. Assertions on plain values (expect(5).toBe(5)) don't retry. The retry-aware ones are the "web-first" assertions.

Fixtures

Playwright's fixture system isolates test state and enables custom setup:

import { test as base } from "@playwright/test";

type Fixtures = {
    loggedInPage: Page;
};

export const test = base.extend<Fixtures>({
    loggedInPage: async ({ page }, use) => {
        await page.goto("/login");
        await page.getByLabel("Email").fill("user@example.com");
        await page.getByLabel("Password").fill("secret");
        await page.getByRole("button", { name: "Sign in" }).click();
        await use(page);  // hand the logged-in page to the test
    },
});

test("dashboard", async ({ loggedInPage }) => {
    await expect(loggedInPage.getByRole("heading", { name: "Dashboard" })).toBeVisible();
});

Each fixture runs in its own scope and is automatically cleaned up.

Configuration

// playwright.config.ts
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
    testDir: "./tests",
    fullyParallel: true,
    forbidOnly: !!process.env.CI,
    retries: process.env.CI ? 2 : 0,
    workers: process.env.CI ? 4 : undefined,
    reporter: [
        ["html"],
        ["list"],
        ["junit", { outputFile: "results.xml" }],
    ],
    use: {
        baseURL: "http://localhost:3000",
        trace: "on-first-retry",
        screenshot: "only-on-failure",
        video: "retain-on-failure",
    },
    projects: [
        { name: "chromium", use: devices["Desktop Chrome"] },
        { name: "firefox", use: devices["Desktop Firefox"] },
        { name: "webkit", use: devices["Desktop Safari"] },
        { name: "mobile-chrome", use: devices["Pixel 7"] },
        { name: "mobile-safari", use: devices["iPhone 15"] },
    ],
    webServer: {
        command: "npm run dev",
        url: "http://localhost:3000",
        reuseExistingServer: !process.env.CI,
    },
});

projects is how you run the same tests across multiple browsers / devices. webServer boots your dev server automatically before tests run.

Codegen (auto-generate tests)

npx playwright codegen https://example.com

This opens a real browser. Click around — Playwright records every action as TypeScript code in a side panel. Copy the generated test as a starting point. The codegen output uses role-based locators by default.

Trace viewer

When a test fails (or always, with trace: "on"), Playwright records a full trace — DOM snapshots, network calls, console logs, every action — into a .zip file. View it:

npx playwright show-trace test-results/example-trace.zip

The trace viewer is the killer feature for debugging flaky tests. You see exactly what the browser saw at every step, can rewind to before-the-failure, hover over locators to see what matched, inspect network calls.

Visual testing

test("homepage screenshot", async ({ page }) => {
    await page.goto("/");
    await expect(page).toHaveScreenshot("homepage.png");
});

First run creates a baseline. Subsequent runs compare and fail on visual diff above a threshold. toHaveScreenshot() supports element-level screenshots, masks (block dynamic regions), and animations (wait for them or disable).

API testing

test("create user via API", async ({ request }) => {
    const response = await request.post("/api/users", {
        data: { name: "Alice", email: "alice@example.com" },
    });
    expect(response.ok()).toBeTruthy();
    const user = await response.json();
    expect(user.id).toBeDefined();
});

The request fixture works without a browser — useful for backend API tests and setup/teardown actions.

Mocking & network interception

test("offline mode", async ({ page }) => {
    await page.route("**/api/data", route => route.abort());
    await page.goto("/");
    await expect(page.getByText("Offline")).toBeVisible();
});

test("mock API response", async ({ page }) => {
    await page.route("**/api/users", route =>
        route.fulfill({ json: [{ id: 1, name: "Mock User" }] })
    );
    // ...
});

Common gotchas

Browser binaries are NOT part of npm install — @playwright/test is the SDK, but the browsers need separate download via npx playwright install. CI runners need this step. The Playwright Docker images come with browsers pre-bundled.

Tests run in parallel by default — fullyParallel: true means each test file's tests run concurrently within workers. Tests that share state (cookies, localStorage, database) need explicit isolation (use unique users, separate database schemas, or test.describe.configure({ mode: 'serial' })).

Locator strictness causes "strict mode violation: resolved to N elements" — if page.getByText("Submit") matches multiple elements, the strict-mode locator errors. Use .first(), .nth(n), or refine the selector. This is intentional — ambiguous selectors hide bugs.

page.click() is deprecated; use locator.click() — the page-level methods predate locators. New code uses locators throughout. The old API still works but loses retry semantics.

Auto-waiting waits for actionability, NOT data load — Playwright doesn't know your data is loaded. After goto, the page may have rendered but background fetches may still be in flight. Use web-first assertions to wait for the rendered state you care about: await expect(page.getByText("3 results")).toBeVisible();.

Test failures don't auto-record traces — trace: "on-first-retry" records only when a test fails and retries. For deep debugging, set trace: "on" temporarily (large file output) or trace: "retain-on-failure".

expect(page).toHaveScreenshot() is platform-sensitive — fonts, antialiasing, and OS-level rendering differ between Linux (CI), macOS (dev), and Windows. Visual tests pass on the platform they were recorded on but fail elsewhere. Solutions: run visual tests only on Linux CI, or use Docker locally to match CI.

page.fill() does NOT trigger React onChange properly in some cases — fill clears the input and types. If your React component uses onChange with controlled inputs, this usually works, but some component libraries (Material-UI, Mantine) need per-keystroke events. Corrected 2026-08-21: use locator.pressSequentially(), not page.type(). playwright.dev/docs/api/class-page now marks page.type Deprecated, directing readers to locator.fill() in most cases and to locator.pressSequentially() when the page genuinely needs keys pressed one at a time.

webServer.reuseExistingServer saves time but can hide bugs — when you set reuseExistingServer: true and forget to restart your dev server after a code change, tests run against stale code. The CI config (false) is safer; the local-dev config (true) trades safety for speed.

navigationTimeout and actionTimeout are separate — navigationTimeout for goto/waitForURL; actionTimeout for clicks/fills. Override the global config in use: per-test if a specific page needs longer.

page.goto() waits for load event by default — for SPAs that don't fire load traditionally, rely on web-first assertions after goto. Corrected 2026-08-21: do not reach for waitUntil: 'networkidle'. The waitUntil option table in the Playwright API docs now marks networkidle DISCOURAGED, with the note "Don't use this method for testing, rely on web assertions to assess readiness instead". The remaining values are load, domcontentloaded and commit.

Workers ≠ parallelism level — workers: 4 runs 4 worker processes, each running tests serially within. Test files distribute across workers. Setting workers: 4 with 1 test file gets 1 worker; need many files for parallelism.

HTML report serves on port 9323 by default — npx playwright show-report opens a browser. If 9323 is occupied, pass --port. CI workflows often archive playwright-report/ as a build artifact for post-hoc viewing.

Codegen produces good first-draft tests but they need cleanup — codegen picks locators it can find at recording time, sometimes selecting fragile CSS selectors when semantic ones exist. Always review codegen output and tighten locators before committing.
