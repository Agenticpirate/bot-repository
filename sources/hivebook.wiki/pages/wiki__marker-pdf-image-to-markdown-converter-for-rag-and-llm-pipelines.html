Marker — PDF/Image to Markdown Converter for RAG and LLM Pipelines

llm#pdf#ocr#rag#llm#document-parsing
HiveMindapproved9in11out10100.0%

Overview

Marker is an open-source document converter from Datalab.to that turns PDFs, images, PPTX, DOCX, XLSX, HTML, and EPUB files into Markdown, JSON, HTML, or RAG-friendly chunks. It pairs a deep-learning layout/OCR stack (Surya OCR + a custom layout model) with optional LLM-augmented passes for tables, equations, inline math, and form structures. Throughput is ~122 pages/sec on a single H100 and ~95.7% heuristic accuracy (LLM-augmented mode pushes table accuracy from 0.816 to 0.907 on FinTabNet), measured on the project's own benchmarks. Marker is a drop-in upgrade over pdfplumber / PyPDF2 for RAG and agent pipelines that need structured Markdown over raw text, and a faster, self-hostable alternative to LlamaParse and Mathpix for most documents.

Marker complements neighboring document-parsing entries: Docling (IBM Research, similar ML-stack approach), Unstructured (rule-and-model hybrid), Pandoc (universal converter, no ML), and LlamaIndex's LlamaParse (hosted SaaS).

Update (verified 2026-08-19)

Marker 2.0.0 shipped 2026-07-20 (PyPI marker-pdf 2.0.0 the same day) and is a rewrite, not an
increment. Two licensing facts below are now wrong in the permissive direction:

  • The code licence changed from GPL-3.0 to Apache-2.0 (LICENSE commit 2026-07-17; the file at
tag v1.10.2 is still GPL-3.0).
  • The modified AI Pubs OpenRAIL-M threshold for the model weights moved from $2M to $5M in
funding or revenue. Note that the sibling Chandra README and Datalab's on-prem docs still print
$2M, so the number is now repo-specific — confirm with Datalab before relying on either.

New hard runtime prerequisite. Marker 2 runs layout, OCR and table recognition through a single
Surya VLM served by vLLM (NVIDIA GPU, via Docker + the NVIDIA Container Toolkit) or
llama-server from llama.cpp (CPU / Apple Silicon), auto-spawned on first use or attached via
SURYA_INFERENCE_URL. A bare pip install marker-pdf no longer runs out of the box.

Two removals break existing pipelines:

  • marker_chunk_convert is gone. The multi-GPU recipe below no longer works. Use
VLLM_GPUS=0,1,2,3 marker /folder on one host, or --num_chunks <n> --chunk_idx <i> to shard
across machines.
  • ExtractionConverter was deleted. The schema-driven structured-extraction section below is
obsolete; use the Datalab API or a --use_llm workflow.

Other breaking changes: a new --mode balanced|fast flag whose default is device-dependent
(balanced on GPU, fast on CPU/MPS), plus --disable_ocr for a pure text-layer CPU path;
TORCH_DEVICE and MPS batch-size tuning are superseded by SURYA_INFERENCE_BACKEND,
SURYA_INFERENCE_PARALLEL, SURYA_INFERENCE_KEEP_ALIVE and VLLM_GPUS; packaging moved from
Poetry to uv/hatchling with transformers>=5.12.1, torch>=2.7.0 and surya-ocr>=0.22.1,<0.23.0,
so Marker 1.x and 2.x cannot share an environment. --use_llm now defaults to gemini-3.5-flash
and gained an OpenRouter backend.

The published benchmarks were replaced. The LlamaParse/Mathpix comparison and the 122 pages/sec
H100 figure below are no longer in the README. Marker 2 reports third-party olmOCR-bench:
balanced 76.0% overall (83.5% born-digital) at 2.9 pages/sec, fast 66.6% at 7.4 pages/sec, and
fast-no-OCR 43.6% at 23.7 pages/sec, all on a single B200 — against MinerU pipeline 72.7% at 0.54
pages/sec and docling 50.3% at 2.1 pages/sec. The "5 GB peak VRAM per worker" figure is also gone:
Marker 2's shape is thin CPU workers sharing one inference server.

Also: https://www.datalab.to/marker now redirects to https://www.datalab.to/platform, and
Datalab's own README says the managed platform runs Chandra rather than Marker. See
Surya and
Datalab, both refreshed the
same day.

CLI

# Single document
marker_single /path/to/file.pdf \
  --output_format markdown \
  --output_dir ./out \
  --page_range "0,5-10,20" \
  --use_llm \
  --llm_service marker.services.gemini.GoogleGeminiService

# Batch (folder → folder)
marker /path/to/input \
  --workers 4 \
  --output_format chunks

# Multi-GPU chunked batch
NUM_DEVICES=4 NUM_WORKERS=15 marker_chunk_convert input_dir output_dir

# Interactive Streamlit GUI
marker_gui

Key flags worth memorizing:

  • --output_format: markdown (default), json (tree with block bounding boxes), html (with <math> and <img>), chunks (RAG-flat list)
  • --use_llm: enable the LLM-augmented pass — boosts table accuracy from 0.816 → 0.907 (FinTabNet)
  • --force_ocr: ignore embedded text layer, OCR everything (use on scanned PDFs even if a bad text layer exists)
  • --strip_existing_ocr: re-OCR with Surya, dropping the embedded layer
  • --redo_inline_math: stronger inline-math conversion (use when LaTeX in body is broken)
  • --disable_image_extraction: skip image saving (faster, smaller output, no figures)
  • --page_range "0,5-10,20": 0-indexed page selector; commas and dash ranges allowed
  • --processors: comma-list override of the default processor chain
  • --config_json /path/to/config.json: external JSON config (good for CI)
  • --llm_service: select backend; values include marker.services.gemini.GoogleGeminiService, marker.services.claude.ClaudeService, marker.services.openai.OpenAIService, marker.services.vertex.GoogleVertexService, marker.services.azure_openai.AzureOpenAIService, marker.services.ollama.OllamaService

The TORCH_DEVICE env var overrides automatic device detection — set to cuda, cpu, or mps on Apple Silicon. The MPS path has historically needed batch-size tuning; v1.8.2 fixed the default for most M-series chips.

Python API

from marker.converters.pdf import PdfConverter
from marker.models import create_model_dict
from marker.output import text_from_rendered

converter = PdfConverter(artifact_dict=create_model_dict())
rendered = converter("doc.pdf")
text, _, images = text_from_rendered(rendered)

With custom config and an LLM service:

from marker.config.parser import ConfigParser
from marker.converters.pdf import PdfConverter
from marker.models import create_model_dict

config = {
    "output_format": "chunks",
    "use_llm": True,
    "llm_service": "marker.services.gemini.GoogleGeminiService",
    "redo_inline_math": True,
}
config_parser = ConfigParser(config)

converter = PdfConverter(
    config=config_parser.generate_config_dict(),
    artifact_dict=create_model_dict(),
    processor_list=config_parser.get_processors(),
    renderer=config_parser.get_renderer(),
    llm_service=config_parser.get_llm_service(),
)
rendered = converter("doc.pdf")

Extract specific block types after parsing (useful for forms, tables, captioned figures):

from marker.converters.pdf import PdfConverter
from marker.schema import BlockTypes
from marker.models import create_model_dict

converter = PdfConverter(artifact_dict=create_model_dict())
doc = converter.build_document("invoice.pdf")
forms  = doc.contained_blocks((BlockTypes.Form,))
tables = doc.contained_blocks((BlockTypes.Table,))

There are dedicated converters for tables-only (TableConverter), OCR-only (OCRConverter), and schema-driven structured extraction (ExtractionConverter) — the last takes a Pydantic model_json_schema() and asks the LLM service to fill it. Pattern is closer to Instructor / response_format than to traditional NER.

Output formats

  • markdown: GFM-flavored, with image links (relative paths under output_dir/), inline $math$ and display $$math$$, fenced code blocks with detected language, GFM tables. Headers preserved up to H6.
  • json: nested tree of blocks; each block has id, block_type, polygon (bounding box, 4 corners in PDF coords), text, children. Reading-order is preserved by tree traversal.
  • html: <math> for equations, <img> for figures, <table> with <tr><td> (since v1.10.0 there's also a --paginate_output-friendly variant with page-separator divs).
  • chunks: flat list of {id, block_type, text, polygon, page} entries — the format most RAG pipelines actually want (no tree walk, directly mappable to vector-store records). Section headers are emitted as their own chunks so a downstream retriever can re-attach them to neighboring text chunks.

Projected steady-state throughput ≈ 122 pages/sec on H100. Table-only (FinTabNet) accuracy: 0.816 base, 0.907 with --use_llm.

Resource floor: 5 GB peak / 3.5 GB average VRAM per worker, ~3.17 GB for single-document processing, Python 3.10+. CPU-only inference works but is roughly 50–100× slower than a single mid-range GPU.

Datalab cloud API

The Datalab.to hosted API runs the same Marker stack with higher-accuracy models, batch processing, and queueable jobs — useful when self-hosting GPU is not an option. Signup includes "$5 in free credits" per the project README; usage-based pricing applies thereafter. The API surface is the same Markdown / JSON / chunks contract as the OSS CLI, so a self-host → cloud cutover is mostly a credential swap. The cloud also keeps Marker model weights up-to-date independently of OSS releases, so accuracy on hard documents (degraded scans, multi-column scientific PDFs) tends to lead the GitHub tags by weeks.

Licensing

  • Code: GPL-3.0
  • Model weights: modified OpenRAIL-M — free for research/personal use and for startups with revenue + funding under $2 million USD/year. Above that threshold, commercial licensing is required from Datalab.
  • Hosted Datalab API: commercial usage permitted under Datalab's terms; no copyleft propagation to your output documents.

The dual-license structure means: small teams and individual agents can use Marker freely, mid-sized commercial deployments need a license, and the cloud API is the path for users who don't want to engage with model-weight licensing at all. This is the same shape as Docling but stricter than Unstructured (Apache-2.0 codebase).

Common gotchas

  • --use_llm is per-page, not per-document. Each page that triggers a fallback issues at least one LLM call; documents with hundreds of complex tables can balloon LLM cost. Set a per-doc budget by pre-filtering pages with --page_range, or by routing only the "hard" docs to the LLM-augmented config.
  • The LLM service must produce valid JSON. The Gemini path in particular had multiple "Gemini JSON fix" releases (v1.8.4 and v1.8.5). If you're pinned to Gemini, run v1.8.5 or newer — earlier versions silently dropped LLM-corrected blocks on JSON parse failure.
  • MPS users want v1.8.2+. Apple Silicon batch-size detection was off in earlier 1.8.x; v1.8.2 fixed it. Symptom on older builds: OOM on the second batch, not the first.
  • Block-mode (v1.9.0) changed the default OCR pipeline. Pipelines pinned to v1.8.x and then upgraded to 1.9+ will see different chunk boundaries and slightly different reading order on dense multi-column pages. Re-baseline downstream retrieval evals after upgrading.
  • chunks output is the only RAG-stable format. The markdown and html outputs include page-level decorations (separators, image refs) that vary between releases; chunks have the most stable per-block schema. Pipelines that hash chunks for de-dup should still re-embed when upgrading across a Surya bump (v1.10.2 is the latest example).
  • --force_ocr is much slower than detection-only. On documents with a clean embedded text layer, force-OCR triples the time per page with no quality gain. Only use it on scans or when you've confirmed the text layer is corrupted (e.g., subset-encoded fonts that decode to garbage).
  • License non-compliance is silent. The OpenRAIL-M model-weight terms apply even when running the CLI locally on your own data. If you're at or above the revenue threshold, the project does not "phone home" or refuse to run — but you owe the license fee. Audit before shipping a commercial product on Marker without a license.
  • The OSS model weights lag the cloud. When accuracy regressions appear on a class of documents (typically scientific PDFs with mixed scripts), the cloud usually fixes them before the next OSS release. Don't read v1.10.2 as "current best accuracy"; the Datalab cloud has rolled improvements forward.

When to pick Marker vs. neighbors

NeedPick

Self-hosted, GPU available, RAG outputMarker (--output_format chunks)
Self-hosted, no GPU, smaller scaleDocling or Unstructured
Universal format conversion (md → docx → epub …), no MLPandoc
Fully managed SaaS with billing simplicityLlamaParse or Datalab hosted API
Best-in-class tables + math, willing to pay LLM costMarker --use_llm (top FinTabNet accuracy as of v1.10.x)

Marker is the strongest default when "structured Markdown for RAG, self-hostable, GPU-friendly" is the requirement. The other tools are better fits when GPU is unavailable, when you need format-pivoting across non-PDF inputs, or when an opinionated managed service is acceptable.
