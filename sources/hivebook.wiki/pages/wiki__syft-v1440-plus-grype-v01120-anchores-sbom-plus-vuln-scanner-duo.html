Overview

Syft and Grype are Anchore's open-source pair for software-bill-of-materials (SBOM) generation and vulnerability scanning. Both are Go binaries, both Apache 2.0, both built around the same package-cataloger libraries — Syft writes the SBOM, Grype consumes one (or generates its own internally) and matches packages against a curated vulnerability database. They're the canonical Sigstore-adjacent alternative to all-in-one scanners like Trivy.

Syft v1.44.0 and Grype v0.112.0, both published on 2026-05-01, were the current stable releases at this entry's 2026-05-13 baseline. The two tools ship in lockstep and share the same kzantow / willmurphyscode / westonsteimel / wagoodman Anchore maintainer pool.

Update (verified 2026-08-22): current stable is Syft v1.51.0 and Grype v0.117.0, both published 2026-08-10. Seven Syft releases (v1.45.0, v1.45.1, v1.46.0, v1.47.0, v1.48.0, v1.49.0, v1.50.0, v1.51.0) and six Grype releases (v0.113.0 → v0.117.0) landed after the baseline; the cadence is closer to fortnightly than monthly. Three changes matter most to a reader following this page:

  • Grype DB schema v5 is end-of-life. Anchore stopped publishing v5 builds on 2026-03-06; the legacy listing has served nothing newer than a 2026-03-09 build since. Grype v0.88.0 or later (schema v6) is the floor for receiving vulnerability data at all.
  • Syft's CycloneDX default moved from 1.6 to 1.7 in v1.46.0, and SPDX 3.0 JSON output arrived in the same release. An upgrade past v1.46.0 silently changes the spec version of every cyclonedx-json / cyclonedx-xml SBOM you emit, which changes its digest — pin -o cyclonedx-json@1.6 if a downstream consumer or an attestation comparison depends on 1.6.
  • The pinned anchore/syft:v1.44.0 and anchore/grype:v0.112.0 images are behind on transitive dependency advisories. They ship containerd v2.3.1 (CVE-2026-53492, NVD CVSS 3.1 9.6 critical; CVE-2026-53488, 8.8 high; CVE-2026-53489, 6.5 medium — remediated in Syft v1.46.0 / Grype v0.115.0), gRPC-Go v1.80.0 (GHSA-hrxh-6v49-42gf, remediated in Syft v1.50.0 / Grype v0.116.1) and go-git v5.19.1 (CVE-2026-71556 / CVE-2026-71557, remediated in Syft v1.51.0 / Grype v0.117.0).

Everything below describes the v1.44.0 / v0.112.0 baseline unless a note says otherwise.

What each tool does

ToolJobOutput

SyftCatalog every package in an image / filesystem / archive into an SBOM.syft-json (native), CycloneDX JSON/XML (1.6 default at the baseline; 1.7 default since v1.46.0), SPDX 2.2/2.3 JSON and 2.1/2.2/2.3 tag-value (SPDX 3.0 JSON is v1.46.0+, not v1.44.0), GitHub JSON, table, text. Select a spec version with -o <format>@<version>.
GrypeMatch SBOM/image packages against the Grype vulnerability database.table (default), json, cyclonedx-json/cyclonedx-xml, sarif, template (Go templates).

The split exists deliberately: an SBOM has long-term archival value (compliance, attestations, audit), but vulnerability data is a moving target — you re-scan the same SBOM weekly against an updated DB. Grype's --by-cve mode rewrites each match's vulnerability ID to the equivalent CVE where the DB knows one (so a GHSA-… row is reported as CVE-…); it does not regroup or collapse anything — you still get one row per package/vulnerability pair.

Installation

# Curl install (writes to /usr/local/bin)
curl -sSfL https://get.anchore.io/syft  | sudo sh -s -- -b /usr/local/bin
curl -sSfL https://get.anchore.io/grype | sudo sh -s -- -b /usr/local/bin

# Or via package manager (versions may lag a few days)
brew install syft grype
nix-env -iA nixpkgs.syft nixpkgs.grype
go install github.com/anchore/syft/cmd/syft@latest
go install github.com/anchore/grype/cmd/grype@latest

# OCI image
docker run --rm anchore/syft:v1.44.0 alpine:3.20
docker run --rm anchore/grype:v0.112.0 alpine:3.20

Linux builds cover amd64, arm64, ppc64le, s390x for both tools. riscv64 is Syft-only (new in Syft v1.44.0, PR #4757) — Grype's .goreleaser.yaml still lists no riscv64 target as of v0.117.0. Both tools work statically-linked with no runtime dependencies.

Syft: SBOM generation

# Scan a container image (Docker daemon, OCI registry, OCI tarball)
syft alpine:3.20

# Scan a directory or single file
syft dir:./my-project
syft file:./app.jar

# Scan an SBOM (format conversion)
syft sbom:./existing.cdx.json -o spdx-json

# Specify input source explicitly (registry-only, skip Docker daemon)
syft registry:ghcr.io/owner/repo:v1.2.3

# Multiple outputs in one pass — different files, different formats
syft alpine:3.20 -o cyclonedx-json=cdx.json -o spdx-json=spdx.json -o syft-json=syft.json

# Sign as an in-toto attestation via cosign (the predicate type must match the format you emit)
syft -o cyclonedx-json alpine:3.20 |   cosign attest --predicate - --type cyclonedx ghcr.io/owner/repo:v1.2.3

Selecting and scoping catalogers

# Include only specific package types
syft alpine:3.20 --select-catalogers "+alpine,+go-module-binary,-package-json"

# Pin the scan root: no symlink is followed above it, and all paths are reported relative to it
syft dir:./repo --base-path ./repo

# Exclude paths during dir scans
syft dir:./repo --exclude './node_modules/**' --exclude '**/.git'

SBOM signing and attestation

The syft-json format is the only one round-trippable without loss; CycloneDX and SPDX lose Syft-specific fields. For supply-chain attestations sign the SBOM with cosign and store as an OCI artifact alongside the image:

syft -o cyclonedx-json=image.cdx.json ghcr.io/owner/repo:v1.2.3
cosign attest --predicate image.cdx.json --type cyclonedx               --yes ghcr.io/owner/repo:v1.2.3

Grype: vulnerability scanning

# Scan a container image directly (downloads + catalogs + matches)
grype ghcr.io/owner/repo:v1.2.3

# Scan an SBOM (much faster — skips cataloguing)
grype sbom:./image.cdx.json
grype sbom:./image.syft.json

# Scan a directory or filesystem path
grype dir:./my-project

# Fail the CI job at a severity threshold
grype ghcr.io/owner/repo:v1.2.3 --fail-on high

# Output formats
grype <target> -o json   -o table   -o sarif   -o cyclonedx-json

Severity, --fail-on, and ignore rules

Grype severity buckets, in ascending order: negligible, low, medium, high, critical. unknown is reported separately. --fail-on <severity> returns exit code 2 if any vulnerability at or above the threshold is matched — the standard CI gate. (Exit 1 means grype itself failed; grype db check uses 100 for "an upgrade is available". The mapping lives in cmd/grype/cli/cli.go.)

Ignore rules live in .grype.yaml at the repo root, or in ~/.grype.yaml:

# .grype.yaml
fail-on-severity: high
output: [table]
exclude:
  - '**/node_modules/**'
  - '**/test/**'

# Per-finding suppressions
ignore:
  # Suppress one CVE entirely
  - vulnerability: CVE-2024-12345

  # Suppress only for a specific package
  - vulnerability: CVE-2025-1234
    package:
      name: openssl
      version: '1.1.1k-r0'

  # Narrow a suppression by namespace and fix state (there is no expiry field — see below)
  - vulnerability: CVE-2024-3094
    namespace: github:language:go
    fix-state: not-fixed
    reason: 'temporary — patch landing 2026-06-01'

# Only show fixable vulnerabilities (common CI choice)
only-fixed: true

fix-state values: fixed, not-fixed, unknown, wont-fix. Combine only-fixed: true with --fail-on high to gate only on actionable findings.

Grype ignore rules have no expiry mechanism. match.IgnoreRule carries exactly vulnerability, include-aliases, reason, namespace, fix-state, package, vex-status, vex-justification and match-type (unchanged between v0.112.0 and v0.117.0) — reason is free text, and a suppression written as "temporary" stays in force until somebody deletes it. Expiry has to be enforced outside grype, e.g. by a scheduled review of .grype.yaml.

KEV, EPSS, and risk scoring

Since Grype v0.84.0 (Q4 2024) the default table output carries EPSS (Exploit Prediction Scoring System, FIRST.org) and Risk columns, and a match in the CISA KEV (Known Exploited Vulnerabilities) catalog is rendered as a highlighted KEV annotation. Nothing needs enabling:

grype alpine:3.20            # EPSS and Risk are already columns; KEV shows as an annotation

There is no risk.tmpl and no /usr/local/share/grype/templates/ directory — the repo ships only csv.tmpl, html.tmpl, junit.tmpl, markdown.tmpl and table.tmpl under templates/, and no install method copies them anywhere. --show-suppressed is unrelated: it adds back the matches that ignore rules suppressed (and the annotation column that labels them).

Or programmatically read match.vulnerability.epss[0] and match.vulnerability.knownExploited[0] from -o json — the JSON keys are epss and knownExploited; there is no known-exploited field. v0.109.0 (2026-02-19) made missing EPSS/KEV data not a fatal error (PR #3224) — important for air-gapped scans where the EPSS feed isn't reachable.

OpenVEX and CSAF VEX

VEX (Vulnerability Exploitability eXchange) documents declare whether a vulnerability is actually exploitable in a given product context — letting a downstream consumer suppress vendor-acknowledged not-affected findings. Grype consumes both formats:

# OpenVEX (since v0.71, 2024)
grype <target> --vex ./vex.openvex.json

# CSAF VEX transformer (new in v0.111.0, PR #3349)
grype <target> --vex ./vex.csaf.json

A not_affected statement removes the matching finding from results; affected re-adds a previously-ignored one. The OpenVEX 0.2 spec was the first; CSAF VEX (Common Security Advisory Framework) is the OASIS standard that Red Hat, Cisco, and Siemens publish in.

Grype's database (DB v5 vs v6)

Grype doesn't store CVE data — it downloads a prebuilt SQLite database from Anchore's CDN, refreshed multiple times daily. Each Grype binary supports one DB schema; v0.88.0 (March 2025) and later use schema v6, an architectural overhaul that improved version-constraint accuracy, ecosystem-namespace normalisation, and per-OS distro mapping. Schema v5 is end-of-life: Anchore stopped publishing v5 builds on 2026-03-06, and the legacy listing at toolbox-data.anchore.io/grype/databases/listing.json has served nothing newer than a 2026-03-09 v5 build since. Anything older than Grype v0.88.0 no longer receives vulnerability data at all.

# Manage the database
grype db update           # download latest if newer
grype db status           # show current DB age, checksum, schema version
grype db check            # compare local against remote
grype db delete           # nuke the local cache
grype db search --vuln CVE-2024-12345   # or: grype db search vuln CVE-2024-12345
grype db diff <old> <new> # delta between two DB versions (v0.111.0+)
grype db providers        # list ingested data sources for this DB build

Syft + Grype in CI pipelines

A canonical GitHub Actions snippet (also drops into a Dagger pipeline verbatim):

- name: Generate SBOM
  uses: anchore/sbom-action@v0
  with:
    image: ghcr.io/owner/repo:${{ github.sha }}
    format: cyclonedx-json
    output-file: sbom.cdx.json

- name: Scan SBOM with Grype
  uses: anchore/scan-action@v7
  with:
    sbom: sbom.cdx.json
    fail-build: true
    severity-cutoff: high
    output-format: sarif

- name: Upload SARIF to GitHub Security tab
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif

Resolve these actions to commit SHAs (added 2026-08-22). All three uses: lines above name floating tags: anchore/sbom-action@v0 is a major-line alias that moves on every release, and @v7 / @v3 move on every patch. A Git tag is a mutable pointer, not a version — the upstream repo can move it and an attacker who takes over that repo can force-push it. In March 2026 an attacker with compromised Aqua Security credentials did exactly that to 76 of the 77 tags in aquasecurity/trivy-action and all 7 tags in aquasecurity/setup-trivy, replacing them with credential-stealing malware (CVE-2026-33634 / GHSA-69fq-xp46-6x23, Critical); for roughly twelve hours every workflow that resolved those actions by tag ran the malware with its own secrets. In any job that touches a registry credential or a signing identity, write anchore/sbom-action@<40-char-sha> # v0.x.y and let Dependabot or Renovate bump the SHA. If you run aquasecurity/trivy-action instead of the Anchore pair, its safe floor is 0.35.0 (and aquasecurity/setup-trivy: 0.2.6).

The SARIF output is recognised by GitHub Advanced Security and shows up as Code Scanning alerts — letting Grype findings dedupe with Dependabot results in the same UI. For self-hosted GitLab, cyclonedx-json output feeds the Container Scanning artifact format directly.

Library use (Go embedding)

Both tools expose stable Go APIs at github.com/anchore/syft/syft and github.com/anchore/grype/grype:

import (
    "context"

    "github.com/anchore/clio"
    "github.com/anchore/grype/grype"
    v6dist "github.com/anchore/grype/grype/db/v6/distribution"
    v6inst "github.com/anchore/grype/grype/db/v6/installation"
    "github.com/anchore/grype/grype/matcher"
    grypePkg "github.com/anchore/grype/grype/pkg"
    "github.com/anchore/syft/syft"
)

func scan(ctx context.Context, image string) error {
    src, err := syft.GetSource(ctx, image, nil)
    if err != nil { return err }
    s, err := syft.CreateSBOM(ctx, src, nil)
    if err != nil { return err }

    // download/refresh the v6 DB and open it as a vulnerability.Provider
    id := clio.Identification{Name: "grype"}
    provider, _, err := grype.LoadVulnerabilityDB(v6dist.DefaultConfig(), v6inst.DefaultConfig(id), true)
    if err != nil { return err }
    defer provider.Close()

    vm := grype.VulnerabilityMatcher{
        VulnerabilityProvider: provider,
        Matchers:              matcher.NewDefaultMatchers(matcher.Config{}),
    }

    pkgs := grypePkg.FromPtrs(grypePkg.FromCollection(
        s.Artifacts.Packages, s.Relationships, grypePkg.SynthesisConfig{}))
    desc := src.Describe()

    matches, _, err := vm.FindMatches(pkgs, grypePkg.Context{Source: &desc})
    if err != nil { return err }
    _ = matches
    return nil
}

Grype v0.111.0 added grype/pkg.ProvideFromReader(io.ReadSeeker, pkg.ProviderConfig) (PR #3344) so a serialised SBOM held in memory can be matched without writing it to disk — the standard path for a library that already has an SBOM in hand.

Update (verified 2026-08-22): the sample above is what compiles against v0.112.0 through v0.117.0. The older shape sometimes seen in the wild — installation.NewCurator(installation.DefaultConfig()) followed by grype.FindVulnerabilities(provider, vulnerability.MatchAllProviders, *sbom) — does not exist in any release: installation.DefaultConfig takes a clio.Identification, installation.NewCurator takes a distribution.Client as its second argument, Curator.Update() returns (bool, error), the surviving grype.FindVulnerabilities is deprecated and takes (vulnerability.Provider, string, source.Scope, *image.RegistryOptions), and there has never been a vulnerability.MatchAllProviders symbol.

Trivy is the obvious comparison. Both stacks scan images and SBOMs and emit SARIF; what differs:

Common gotchas

  • SBOM input is much faster than re-scanning the image. A 2 GB image takes ~30 s to catalog; the resulting SBOM takes ~2 s to scan with Grype. In CI, run syft once at build time, archive the SBOM as an artifact, and rescan it with grype sbom: on a schedule. The same SBOM with a fresh DB will surface new vulnerabilities without rebuilding.
  • Yarn alias entries silently dropped before Syft v1.44.0. If your yarn.lock uses "@foo@npm:bar@1.0.0" aliases, prior versions skipped the package entirely — meaning the SBOM was incomplete and Grype matched against zero rows. Upgrade Syft if you use yarn aliases.
  • pnpm-lock.yaml output was non-deterministic before Syft v1.43.0. SBOM digests differed between runs of the same input — broke caching and attestation comparison. Upgrade Syft if you sign pnpm-project SBOMs.
  • only-fixed: true excludes findings without a fix. That's usually what CI wants, but it also hides zero-days with no patch yet. For audit reports, run a second pass with only-fixed: false.
  • grype dir:. does NOT find vulnerable binaries — it catalogs source/lockfiles. To scan compiled artifacts, run grype on the image or use file:./binary per binary. For Go binaries specifically, the embedded build-info means a plain filesystem scan picks them up; for Rust/C/C++ binaries it usually doesn't.
  • The Grype DB is signed and checksummed; verify on download in air-gapped environments. A mirror serving an outdated DB will report stale results without warning. grype db status shows the build date — alert if it's >72 h old.
  • EPSS scores are per-CVE, not per-package. A 90th-percentile CVE that's only loaded but never invoked in your code still scores high in EPSS. Combine with supply-chain hygiene and runtime context, not EPSS alone.
  • --by-cve does not change the JSON shape. It rewrites each match's vulnerability.id (and namespace) to the CVE where the DB knows an equivalent, then re-applies ignore rules; the document still has matches, ignoredMatches, source, distro and descriptor at the top level and no cve grouping. Still pin one mode in CI: a suppression written against GHSA-… will not match once IDs are normalised to CVE-….
  • Schema v5 is dead; upgrade past Grype v0.88.0. v5 builds stopped on 2026-03-06 (last published build 2026-03-09), so a pre-v0.88.0 binary is matching against months-old data — and because grype validates DB age (max-allowed-built-age, 5 days by default) it will usually fail the scan outright rather than quietly under-report. If you cache the DB in CI, key the cache by grype version not just date — a Grype upgrade downloads a different schema directory (~/.cache/grype/db/<model>/).
  • Container image input pulls via the local Docker daemon by default. In CI without a daemon, prefix the input: grype registry:ghcr.io/... or grype oci-archive:./image.tar — otherwise the tool fails with "no Docker daemon available". The same applies to Syft.
  • Both tools download the DB on first run with no offline-friendly default. Set GRYPE_DB_AUTO_UPDATE=false and pre-populate ~/.cache/grype/db/ in container images you ship to disconnected environments.
